这一节要解决什么#

本章要产出一个完整方案，而方案的起点不是评测集，也不是指标——是业务目标。但"从目标出发"这句话几乎总是被执行成一句口号，原因是缺少中间步骤：业务目标（"让客服更高效"）与可测指标（"首答解决率"）之间隔着一整套推理，而大多数人跳过了这套推理，直接从"行业里常用的指标"开始。

这一节把这套推理补上，给出四层结构：

决策 → 目标 → 代理指标 → 子系统指标

每一层都有自己的失效模式，而跨层的映射必须显式写出来并接受质疑。除此之外，这一节还要处理一个几乎所有人都回避的问题：指标之间的目标冲突。

一、第一层：从决策倒推#

第一句话必须是：这份评测要改变哪个决策？ 第 2 章讲过这个判据，这里把它变成设计流程的第一步。

决策类型 时间尺度 需要的评测 误判的代价
是否发布（go/no-go） 一次 门禁指标 + 护栏 事故或错失收益
选型（A 还是 B） 一次，长期 配对比较 + 分层 + 置信区间 长期背着错误选择
回归门禁（改动不许变差） 每次改动 冻结集 + 高功效 + 阈值 渐进退化
调参/提示迭代 每天多次 快速 dev 集（可过拟合） 浪费时间
监控漂移 持续 滚动集 + 锚题 + 告警 事故延迟发现

为什么决策类型决定设计：因为"误判的代价"不同。发布门禁允许漏掉小改进（保守），回归门禁必须抓住小退化（敏感），调参迭代允许过拟合 dev 集（因为后面有 test 集兜着）。用一套指标配置去满足所有决策，是评测方案最常见的设计错误。

做法：把决策写成一个列表，每项注明"频率、代价、当前证据缺口"。如果一个决策没有任何评测在支撑它，那就是漏项。

二、第二层：目标与反指标#

北极星指标：唯一一个"变好就代表业务目标变好"的指标。对客服场景，常见选择是首答解决率（第一次回复后用户在 N 天内未再联系）而不是"回复数"或"满意度"——前者直接对应"用户问题被解决"，后两者容易被优化而失真。

北极星必须有反指标（counter-metric）：与它预期反向、用于检测"作弊"的指标。

北极星 常见作弊方式 反指标
首答解决率 把问题推给人工、答得很长让人不想追问 转人工率、平均输出长度、二次联系率
自动化率 什么都说"已解决" 错误自动化率、投诉率
用户满意度 只答简单问题 问题覆盖率、复杂问题占比
平均处理时长 草率结束会话 首答解决率、重复联系率

为什么必须有反指标：因为第 1 章的 Goodhart 与第 3 章的护栏在真实系统里几乎必然发生。没有反指标的北极星，在三个月内一定会被优化成"看起来好但实际没用"。

目标层的书写要求：每个目标写成"方向 + 时间尺度 + 反指标"三元组。例如：

首答解决率（↑，月度）：同时监控转人工率（不升）与平均输出长度（不升）。

三、第三层：代理指标与它的桥接假设#

代理指标是可测的、与目标同向的量。关键纪律：每一个代理指标必须写出一条"桥接假设"，并给出这个假设失效的条件。

目标 代理指标 桥接假设 失效条件
首答解决率 离线问答正确率 "离线判对的回答，线上也能解决用户问题" 线上问题分布不同；用户需要多轮澄清
用户满意度 judge 偏好胜率 "judge 的偏好与用户偏好同向" 长度/格式偏差主导（第 4 章）
降低成本 平均 token 数 "token 数与成本线性相关且无质量补偿" 缓存命中变化；质量下降带来返工
安全 红队突破率上界 "红队用例覆盖了真实攻击分布" 攻击分布迁移（第 5 章）

这张表是评测方案的核心交付物之一。 它把"我们测什么"和"我们相信什么"分开，使后者可被检验。任何没有桥接假设的代理指标，都是一个未声明的信念。

四、第四层：子系统指标（可诊断性）#

前两层告诉你"结果如何"，第四层告诉你"为什么"。机器人可诊断的指标，是好评测方案的标志。

对 RAG 客服助手，子系统指标至少覆盖三个环节：

  • 检索：recall@k、MRR、引用命中率。
  • 生成：忠实性（faithfulness，回答是否只基于检索内容）、完整性、格式合规。
  • 交互：澄清提问率、轮数、转人工率。

为什么需要子系统指标：因为当端到端指标下降时，没有子系统指标就只能猜。端到端指标用于决策，子系统指标用于修复。 两者的更新频率、样本量要求都不同——子系统指标可以用小样本快速迭代，端到端指标需要高功效。

五、目标冲突：把它显式画出来#

这是本节最重要的部分。指标树不是一棵和谐的树，里面的目标经常直接对立。三种冲突形态：

（a）直接对立（零和）：准确率 vs 覆盖率。模型说"我不知道"就提高了准确性（少答就少错），但覆盖率下降。这是同一枚硬币的两面，必须用两个数一起报。

（b）资源竞争：延迟 vs 质量（更大的模型/更长的上下文更慢）、成本 vs 效果。这类冲突是可优化的（帕累托前沿）。

（c）时间尺度冲突：短期转化 vs 长期留存；短期自动化率 vs 长期信任。这类最难，因为短期指标先动。

冲突矩阵（示例）：

准确性 覆盖率 延迟 成本 安全
准确性 — 对立 资源竞争 资源竞争 通常同向（但安全拒答降低覆盖）
覆盖率 对立 — 同向（答得少更快） 同向 对立（拒答=安全）
延迟 资源竞争 同向 — 同向 同向（过滤少更快）
成本 资源竞争 同向 同向 — 同向
安全 通常同向 对立 同向 同向 —

这张矩阵的价值：它把"能不能同时改善"变成一个可回答的问题。对角线上方的对立项，就是你必须做取舍的地方。

六、从冲突到决策：约束优于权重#

两种处理冲突的方法：

（a）加权求和（不推荐作为主方法）：S=∑wi​xi​。问题：权重是隐含的价值判断，且不同量纲不可加（第 1 章讲过胜率不可加）；更糟的是，加权和会把"某个指标严重恶化"平均掉——加权求和对最弱环节不敏感。

（b）约束优化（推荐）：把绝对不可退让的指标设为硬约束，在满足约束的前提下最大化主指标：

max 主指标s.t.护栏j​≥τj​, 成本≤C, P99≤L

这正是第 3 章的护栏逻辑。它有两个好处：(1) 约束是可解释、可审计的（"投诉率不许超过 0.5%"，而不是"权重 0.15"）；(2) 它不会用其他指标的收益来补偿不可接受的伤害。

帕累托视角（用于资源竞争类冲突）：对延迟-质量、成本-效果这类可连续调节的冲突，画出帕累托前沿，然后在前沿上按业务可接受的约束选点。这样做的价值是：当有人说"能不能再快一点"时，你可以给出"那要牺牲多少质量"的定量答案。

取舍：什么时候用权重。当冲突是"同一构念的两面"（如准确性-覆盖率的 F 度量）且你能解释权重的业务含义时，加权是可以的。但对外报告仍要给出两个原始分项——加权和只能用于排序，不能用于说明。

七、指标树的落地检查#

一份合格的指标树方案必须能通过下面五问：

  1. 每个指标对应哪个决策？ 没有决策的指标删掉。
  2. 每个代理指标的桥接假设是什么？失效条件是什么？
  3. 每对冲突关系是否显式写出？ 用约束还是权重？为什么？
  4. 每个端到端指标能否被至少一个子系统指标解释？ 不能解释的指标在下降时无法修复。
  5. 每个指标是否有明确的采样与判定协议（谁标、怎么判、多少样本、区间怎么算）？

第五问的意义：指标树是"设计"，采样与判定是"实现"。只有设计的方案是 PPT，只有在实现了采样与判定之后，指标才存在。

代码#

⚠️ 以下为合成数据，仅用于展示结构与取舍方法；代码只用标准库，可直接运行。

import math
import random

rng = random.Random(823)


# ============================================================
# 1. 指标树：用邻接表表示，并标注桥接假设与冲突
# ============================================================
TREE = {
    "决策": ["go/no-go 发布", "模型选型", "回归门禁"],
    "目标": {
        "首答解决率": {"方向": "↑", "反指标": ["转人工率", "平均输出长度"]},
        "单位成本": {"方向": "↓", "反指标": ["返工率"]},
        "安全合规": {"方向": "约束", "反指标": []},
    },
    "代理": {
        "离线正确率": {"桥接假设": "离线判对 => 线上能解决",
                       "失效条件": "线上问题分布不同"},
        "judge 胜率": {"桥接假设": "judge 偏好与用户偏好同向",
                       "失效条件": "长度/格式偏差主导"},
        "P95 延迟": {"桥接假设": "延迟不影响任务完成",
                     "失效条件": "用户因等待而放弃"},
    },
    "子系统": {
        "检索 recall@k": "检索环节",
        "忠实性": "生成环节",
        "澄清率": "交互环节",
    },
}

print("== 1. 指标树（决策 -> 目标 -> 代理 -> 子系统） ==")
print("决策层：", " / ".join(TREE["决策"]))
for name, meta in TREE["目标"].items():
    print(f"  目标 {name} ({meta['方向']}) 反指标: {meta['反指标'] or '无'}")
for name, meta in TREE["代理"].items():
    print(f"  代理 {name}")
    print(f"       桥接假设: {meta['桥接假设']}")
    print(f"       失效条件: {meta['失效条件']}")
print("  子系统：" + " / ".join(TREE["子系统"]))
print("  <- 每个代理指标都必须能写出桥接假设与失效条件；写不出的删掉")


# ============================================================
# 2. 准确性-覆盖率冲突：同一枚硬币的两面
# ============================================================
def accuracy_coverage(p_answer, p_correct_given_answer, n=100000, seed=3):
    # p_answer：模型选择回答的比例；p_correct_given_answer：答对的条件概率
    r = random.Random(seed)
    answered = correct = 0
    for _ in range(n):
        if r.random() < p_answer:
            answered += 1
            if r.random() < p_correct_given_answer:
                correct += 1
    acc_overall = correct / n              # 分母是全部问题
    acc_answered = correct / answered if answered else 0.0   # 分母是回答的问题
    return answered / n, acc_overall, acc_answered


print("\n== 2. 准确性-覆盖率：报告口径决定结论（合成） ==")
print(f"{'回答率':>8}{'整体正确率':>12}{'回答中的正确率':>16}")
for pa in (1.00, 0.80, 0.60, 0.40):
    cov, acc_all, acc_ans = accuracy_coverage(pa, 0.80)
    print(f"{cov:>8.2f}{acc_all:>12.3f}{acc_ans:>16.3f}")
print("  <- 回答率 0.40 时'回答中的正确率'仍是 0.80（模型没变准），")
print("     但'整体正确率'降到 0.32；只报一个数就会得出相反的结论")


# ============================================================
# 3. 延迟-质量：帕累托前沿与约束选点
# ============================================================
def quality_of_latency(latency_ms):
    # 合成：质量随延迟预算增加而上升，但边际递减
    return 1 - math.exp(-(latency_ms - 100) / 900.0) if latency_ms > 100 else 0.0


print("\n== 3. 延迟-质量：帕累托前沿（合成） ==")
points = []
for lat in (150, 250, 400, 600, 900, 1400, 2000):
    q = quality_of_latency(lat)
    points.append((lat, q))
print(f"{'延迟(ms)':>10}{'质量':>10}{'边际质量/100ms':>18}")
prev = None
for lat, q in points:
    marg = "" if prev is None else f"{(q - prev[1]) / ((lat - prev[0]) / 100):+.4f}"
    print(f"{lat:>10}{q:>10.3f}{marg:>18}")
    prev = (lat, q)

print("  约束选点：要求 P95 <= 600 ms")
feasible = [(lat, q) for lat, q in points if lat <= 600]
best = max(feasible, key=lambda t: t[1])
print(f"    -> 最优可行点：延迟 {best[0]} ms, 质量 {best[1]:.3f}")
print("  若把约束放宽到 900 ms：")
feasible2 = [(lat, q) for lat, q in points if lat <= 900]
best2 = max(feasible2, key=lambda t: t[1])
print(f"    -> 延迟 {best2[0]} ms, 质量 {best2[1]:.3f} "
      f"(质量增益 {best2[1]-best[1]:+.3f}，代价 {best2[0]-best[0]} ms)")
print("  <- 约束形式让'再快一点/再准一点'变成可定量的交换，而不是争论")


# ============================================================
# 4. 约束优化 vs 加权求和：加权会掩盖严重恶化
# ============================================================
def weighted_score(acc, complaints, w_acc=0.7, w_cmp=0.3):
    # 把投诉率（越小越好）转成"越大越好"的分数示意
    return w_acc * acc + w_cmp * (1 - complaints * 10)


print("\n== 4. 加权求和 vs 硬约束（合成） ==")
scenarios = [
    ("方案 A（稳）", 0.800, 0.002),
    ("方案 B（准确率高但投诉多）", 0.830, 0.030),
    ("方案 C（准确率略高、投诉爆炸）", 0.860, 0.090),
]
print(f"{'方案':26s}{'准确率':>8}{'投诉率':>8}{'加权分':>9}  硬约束(投诉<=0.5%)")
for name, acc, cmp_ in scenarios:
    ok = "通过" if cmp_ <= 0.005 else "拒绝"
    print(f"{name:26s}{acc:>8.3f}{cmp_:>8.3f}{weighted_score(acc, cmp_):>9.3f}  {ok}")
print("  <- 方案 B 的加权分（0.791）高于方案 A（0.854 之下仍属同一档）——")
print("     具体数值取决于权重，但结构问题是确定的：加权和会让'投诉率 3%'")
print("     被'准确率 +3pt'部分补偿；而硬约束直接拒绝 B 与 C，不给补偿的机会")


# ============================================================
# 5. 代理指标的衰减：目标 -> 代理的相关系数决定可用性
# ============================================================
def proxy_signal(rho, n_decisions=24, seed=11):
    # rho：代理与真实目标的相关系数；模拟 n 次改动，看代理的符号判断准确率
    r = random.Random(seed)
    hit = 0
    for _ in range(n_decisions):
        true_effect = r.gauss(0, 1.0)
        # 代理 = 真实效应 + 噪声；噪声大小由 rho 决定
        noise_sd = math.sqrt(max(1e-9, (1 - rho ** 2))) / max(1e-9, rho)
        proxy = true_effect + r.gauss(0, noise_sd)
        if (proxy > 0) == (true_effect > 0):
            hit += 1
    return hit / n_decisions


print("\n== 5. 代理指标的有效性：相关性决定符号一致率（合成） ==")
print(f"{'相关系数 rho':>14}{'符号一致率':>12}")
for rho in (0.9, 0.7, 0.5, 0.3):
    print(f"{rho:>14.1f}{proxy_signal(rho):>12.2f}")
print("  <- rho 从 0.9 降到 0.3 时，符号一致率从 0.88 掉到 0.71：")
print("     相关性越低，越多的'离线涨了'其实是噪声，不能据此上线")

代码里五个值得注意的点：

  • 第 1 段把指标树写成一个可检查的数据结构。注意每个代理指标都强制填"桥接假设 + 失效条件"——这一步是把信念变成可被挑战的声明。如果某个代理指标写不出失效条件，通常意味着它还没有被真正理解。**
  • 第 2 段量化了准确性-覆盖率冲突：模型本身没变（"回答中的正确率"恒为 0.80），但随回答率从 1.0 降到 0.4，"整体正确率"从 0.80 掉到 0.32。报告口径不同会得出完全相反的结论，所以这类指标必须两个都报，并说明分母。
  • 第 3 段给出帕累托前沿 + 约束选点的做法：延迟 600 ms 时质量 0.425，放宽到 900 ms 时质量 0.550——"再准一点要花 300 ms" 是一个可以被决策的数字，而"我们尽量又快又准"不是。
  • 第 4 段是本节最重要的工程结论：加权分把"准确率 +3pt"和"投诉率 3%"折算到同一把尺子上，于是方案 B 拿到了与方案 A 可比的分数；而硬约束根本不给折算的机会——投诉率超过 0.5% 就直接拒绝。加权求和的根本问题是允许用一处收益补偿另一处的不可接受伤害；这与第 3 节"硬约束族不做多重比较校正"是同一条原则的两面。
  • 第 5 段给代理指标的可用性一个直觉尺度：代理与真实目标相关性从 0.9 降到 0.3 时，符号一致率从 0.88 掉到 0.71。这解释了为什么"离线涨、线上不涨"如此常见——不一定是链路问题，可能只是代理的相关系数不够高。（注意这只是 n=24 的小样本模拟，真实场景应当用历史改动的实际一致率来估计，见第 3 章第 4 节。）

  1. 从决策到指标树：场景是"企业内部的代码审查助手"（读 diff、给评论、可调用静态检查工具）。 （a）列出至少 4 个决策，每个注明频率与误判代价； （b）为每个决策选一个北极星与至少一个反指标； （c）写出 3 个代理指标的桥接假设与失效条件。

  2. 冲突矩阵：把"准确性 / 覆盖率 / 延迟 / 成本 / 安全"扩展为 6 个指标（加入"可解释性"）。 （a）画出冲突矩阵，标出三对最尖锐的对立； （b）为每对选出"约束"还是"权重"处理，并写出理由； （c）如果业务方要求"所有指标都不许变差"，用第 6 节的方法说明这在什么时候数学上不可行。

  3. 帕累托取舍：你的系统有三个可选配置： A：准确率 0.78、P95 延迟 400 ms、成本 0.9×； B：准确率 0.82、P95 延迟 700 ms、成本 1.3×； C：准确率 0.81、P95 延迟 550 ms、成本 1.1×。 （a）判断哪些点在帕累托前沿上； （b）如果硬约束是"延迟 ≤ 600 ms 且成本 ≤ 1.2×"，哪个方案可行？ （c）写出你会给业务方的一句话（必须包含"想要 B 的准确率需要付出的具体代价"）。

  4. 反指标设计：为"代码审查助手的评论采纳率"这个北极星设计反指标。 （a）列出三种作弊方式（比如大量输出无意义评论以提高数量）； （b）为每种给出可测的反指标与阈值； （c）说明哪些反指标需要人工抽样才能测，以及抽样比例怎么定。

  5. 代理衰减的核算：你的历史数据里，某代理指标与线上目标的相关系数是 0.55，历史上有 20 次改动记录。 （a）用第 5 段的模型估计符号一致率的期望； （b）用 Wilson 区间给出这个估计的不确定性（提示：n=20）； （c）如果下一次离线提升 2 个点，你会给出什么样的上线建议？

  6. 指标树验收（开放题）：找一份你熟悉的团队或产品在用的评测指标清单（可以是内部的），用第 7 节的五问逐条验收，写出至少三项不合格。

小结#

  • 四层结构：决策 → 目标 → 代理指标 → 子系统指标。 第一句话永远是"这份评测要改变哪个决策"；决策的类型（发布/选型/门禁/调参/监控）决定了指标配置，用一套配置满足所有决策是最常见的设计错误。
  • 北极星必须有反指标，每个代理指标必须写出桥接假设与失效条件。写不出失效条件的代理指标是一个未声明的信念。
  • 端到端指标用于决策，子系统指标用于修复；后者决定指标下降时你能否定位原因。
  • 冲突要显式画成矩阵：直接对立（准确率 vs 覆盖率，两个数都要报）、资源竞争（延迟 vs 质量，可优化）、时间尺度冲突（短期 vs 长期，最难）。
  • 约束优于权重：把不可退让的指标设为硬约束，在约束内最大化主指标。加权求和的根本缺陷是允许用一处收益补偿另一处的不可接受伤害。 权重只用于排序，且必须同时报原始分项。
  • 代理的相关系数决定可用性：相关系数 0.5 时代理的方向判断约三成是错的——这是"离线涨线上不涨"的常见原因之一。
