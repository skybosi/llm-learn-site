Offload 与异构存储：什么时候值得用#

前三课的杠杆都在 GPU 内部：切分模型状态、重算激活、降低精度。这一课把优化器状态、甚至参数搬到 CPU 内存或 NVMe 上，用主机侧存储换显存。CPU 内存通常比显存大一个数量级，但硬约束是：搬家要走 PCIe 或 NVLink，而这条链路的带宽比显存带宽低一到两个数量级。Offload 的成败因此不是"能不能放下"，而是"每次迭代搬的字节数乘上链路时间，能否被计算掩盖"。

一、概念讲解#

1. 三种"存储"，三种带宽量级#

层级 容量量级 带宽量级（示例） 训练里放什么
显存（HBM） 数十至上百 GB 数 TB/s（片内） 参数、梯度、激活、优化器状态
主机内存（DDR） 数百 GB 至数 TB 取决于 PCIe/NVLink 连接 优化器状态、参数副本、检查点缓冲
本地 NVMe 数 TB GB/s 级 检查点、数据集、冷数据

关键数字是第二列的"示例"二字：请用自己机器上的实测值替代。PCIe 代际与通道数（x16 与 x8 差一倍）、CPU 到内存的 NUMA 位置、以及同机多卡是否共享同一条 PCIe，都会让同一个 offload 方案从可用变成不可用。测量层次是 nvbandwidth（设备↔主机带宽）、ib_write_bw（跨机 RDMA）这类工具，而不是看规格表。

2. 一笔账：一次 offload 到底要搬多少#

设模型参数量 Ψ，混合精度 Adam 的账本仍是上一课的 16 B/参数。ZeRO-Offload 式做法的典型流程是：反向算出梯度（2Ψ）→ 梯度 reduce-scatter 到各卡 → 把梯度搬到 CPU（D2H）→ 在 CPU 上更新 fp32 主权重与优化器状态（12Ψ）→ 把更新后的参数搬回 GPU（H2D）。

以 8.72B 模型为例：参数 17.4 GB、梯度 17.4 GB、优化器状态 104.6 GB。一次往返的搬家量约 226.7 GB；在示例 PCIe Gen4 x16 的 25 GB/s 下需要 5580.8 ms/步，换成示例 50 GB/s 需要 2790.4 ms/步。

判据由此得到：要藏住搬家，单步计算时间必须 ≥ 搬家时间——PCIe Gen4 x16 示例值下这个门槛是 9068.8 ms/步（全量 2Ψ+12Ψ 口径）。真正可行的前提是搬家与计算重叠，而它受两个结构性限制：优化器更新必须等梯度 reduce-scatter 完成（顺序依赖），以及主机链路往往被同机所有卡共享。

3. 分片与 offload 是乘法关系，不是替代关系#

Offload 不该替代 ZeRO，而应与它叠乘：优化器状态切成 1/P 后每卡要搬的字节数也变成 1/P（示例里 P=8 时每卡 28.3 GB、约 1133.6 ms/步；P=64 时每卡 3.5 GB、约 141.7 ms/步）。但有个反直觉的结论：同一台机器上 P 个进程共享同一条 PCIe 时，每卡时间并不随 P 下降——每卡字节数变成 1/P，能用的带宽也变成约 1/P，两者正好抵消（示例输出里 1/2/4/8 个 rank 都停在 9068.8 ms/步）。要让 offload 随 P 变好，靠的是跨机：不同机器各自有一条 PCIe，主机链路才真正成为分布式资源。

4. 什么时候值得用，什么时候是陷阱#

值得用的场景（越接近三条同时成立越好）：显存是硬墙、算力还有富余（GPU 利用率长期不满，用主机带宽换 batch 是净赚）；训练规模已到上限、想再多塞参数；计算/通信时间足够长，能把搬家藏进计算后面。是陷阱的场景：计算本来很快、GPU 已打满；同机多卡共享一条窄 PCIe（如上，P 变大也不能救）；只 offload 一小部分却有同步开销（每次搬家过一次主机往返，α 按每层累加）。

5. 与 offload 相邻的另一笔工程账：检查点#

异构存储最稳妥的用法其实是检查点（checkpoint）：把训练状态定期写到 CPU 内存或 NVMe。一次全量检查点的字节数是"参数 + 优化器状态"（示例里 122.1 GB），收益是"故障后少重算的步数"。以整机 25 GB/s、单步 300 ms 为例：每 10 步存一次摊到每步是 162.8% 的吞吐损失（不可接受），每 100 步一次是 16.3%，每 1000 步一次只 1.6% 却要重算 1000 步。结论：频率是"故障率 × 重算代价"与"写盘开销"的权衡，不是越勤越好；大模型常用异步写（先拷到主机内存、由 CPU 慢慢落盘）来打破它。

6. 常见坑#

  • 拿规格表带宽当可用带宽：PCIe 的有效带宽通常明显低于标称，且双向不对称。
  • 在同机多卡场景下期待 1/P 的线性收益：主机链路是共享资源。
  • 把 offload 当"免费扩容"：它的价格是每步固定字节数的搬迁时间。
  • 忘记异步：同步 offload 会把 GPU 挡住；工程实现要做预取与多流。
  • 检查点只存参数不存优化器状态：恢复后动量为零，loss 曲线会出现可见的断裂。

二、可运行代码示例#

纯 Python，不需要 GPU。它把"一次 offload 要搬多少、要多久"和"检查点频率的性价比"都算成可读的数字。

# ===== 示例：Offload 值不值得 —— 把一次搬家算清（纯 Python，示例带宽） =====
GB = 1e9
def ms(nbytes, gbps):
    return nbytes / (gbps * GB) * 1e3

print("示例链路带宽（不是实测值，请用你自己机器上 nvbandwidth / ib_write_bw 的结果替换）：")
links = (("PCIe Gen4 x16 单向（示例 25 GB/s）", 25.0),
         ("PCIe Gen5 x16 单向（示例 50 GB/s）", 50.0),
         ("NVLink 级设备间（示例 300 GB/s）", 300.0))
for k, v in links:
    print(f"  {k:<34} {v:6.1f} GB/s")

N = 8.72e9
param, grad, opt = 2 * N, 2 * N, 12 * N
print(f"\n8.72B 模型（混合精度 Adam）：参数 {param/GB:.1f} GB，梯度 {grad/GB:.1f} GB，"
      f"优化器状态 {opt/GB:.1f} GB")
print(f"  一次 offload 往返要搬：优化器状态 D2H + 参数 H2D + 梯度 D2H = "
      f"{(2*opt+grad)/GB:.1f} GB")

print("\n不分片时，这一趟要多久（每步都要做，且不能与梯度归约重叠）：")
for name, bw in links:
    t = ms(opt, bw) + ms(param, bw) + ms(grad, bw)
    print(f"  {name:<34} {t:9.1f} ms/步")

print("\n分片到 P 卡（每卡只搬 1/P 的字节，链路带宽按 P 路复用后的每卡份额算）：")
for P in (8, 64):
    per_rank = (2 * opt + grad) / P
    for name, bw in links[:2]:
        print(f"  P={P:<3} {name:<30} {ms(per_rank, bw):9.1f} ms/步（每卡搬 {per_rank/GB:6.2f} GB）")

print("\n同一台机器上 P 个 rank 同时搬，共享的是一条 PCIe：")
for P in (1, 2, 4, 8):
    per_rank = (2 * opt + grad) / P
    share = 25.0 / P
    print(f"  {P} 个 rank：每卡份额 {share:6.2f} GB/s，每卡 {ms(per_rank, share):9.1f} ms/步 "
          f"（P 路复用下每卡时间不随 P 下降）")

print("\n判据：把搬家时间藏进计算需要什么条件")
for name, bw in links:
    t = ms(2 * opt + grad, bw)
    print(f"  {name:<34} 需要单步计算 ≥ {t:8.1f} ms 才能真正藏住")
print("  （注意：优化器更新必须等梯度归约完，这段搬家通常只能与预取/通信重叠）")

print("\ncheckpoint 的性价比：整机吞吐 25 GB/s（示例），单步 300 ms")
ckpt = param + opt
for interval in (10, 50, 100, 1000):
    t_ck = ms(ckpt, 25.0)
    step_ms = 300.0
    ovh = t_ck / (interval * step_ms)
    print(f"  每 {interval:>4} 步存一次（{ckpt/GB:5.1f} GB → {t_ck/1e3:6.2f} s）："
          f"摊到每步 {ovh:6.1%} 吞吐损失；故障后最多重算 {interval} 步")

两条可直接用于决策的读数：8.72B 模型的一次 offload 往返是 226.7 GB，在示例 PCIe 上 5580.8 ms/步；同机多卡共享 PCIe 时分片不能让每卡时间下降。再加上"每 1000 步一次检查点只花 1.6% 吞吐、但故障后要重算 1000 步"，结论是：offload 只适合算力有富余的场景，检查点频率必须按故障率定。

三、练习#

  1. 实现：把示例里的 links 换成你自己机器实测的 D2H/H2D 带宽（用 nvbandwidth 两个方向分别测），重算 8.72B 模型的一次往返时间；若两方向差异明显，说明该给哪个方向留更大的预取缓冲。
  2. 解释：为什么"分片到 P 卡"不能让同机 offload 的每卡时间按 1/P 下降？写出"每卡字节数"与"每卡带宽份额"两条式子对消一次。
  3. 对比/验证：分别取单步计算 200 ms、2000 ms、20000 ms，判断 offload 是否值得（门槛用示例 PCIe Gen4 的 5580.8 ms/步）；再说明"值得"的场景里 GPU 利用率大概是什么状态。
  4. 思考：把检查点从"同步全量写"改成"异步写 + 每 100 步增量"，吞吐损失与恢复时间会怎样变？列出两个必须监控的指标。
