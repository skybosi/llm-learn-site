TTFT 与 TPOT#

上一课我们把推理拆成了 prefill 和 decode 两个阶段，这一课把它们"翻译"成两个用户能直接感受到的延迟指标：TTFT（首 token 时间）和 TPOT（每个输出 token 时间）。学完本课，你应当能用一个请求的时间轴把这两个指标标出来，并说出优化它们各自该往哪个方向使劲。

一、概念讲解#

1. TTFT：用户要等多久才看到第一个字#

TTFT（Time To First Token，首 token 时间） 是从用户发出请求、到模型吐出第一个 token 之间经过的时间。它的物理来源就是prefill 阶段：模型必须先把整段 prompt 并行处理完，才能算出第一个输出 token 的概率分布。

因此 TTFT 大致等于"prefill 耗时 + 排队等待 + 网络往返"。其中：

  • prompt 越长，prefill 越久，TTFT 越大；
  • 排队越严重（请求多、算力被占满），TTFT 越大。

TTFT 是用户体验的第一印象：用户点下发送后盯着空白屏幕，等 200ms 和等 3 秒是完全不同的体感。

2. TPOT：字与字之间的"出字速度"#

TPOT（Time Per Output Token，每个输出 token 时间） 是 decode 阶段里，相邻两个输出 token 之间的平均间隔。它的物理来源就是decode 每步的耗时：读一遍权重、算一个 token、采样一次。

TPOT 决定了"一旦开始出字，字出得有多快"。对长回答来说，TPOT 主导了整体体验——生成 1000 个 token，TPOT 是 50ms 的话要等 50 秒，是 20ms 的话只要 20 秒。

3. 两个指标的权衡#

这里有一个贯穿全课程的矛盾：提高吞吐（batch 调大）会同时恶化 TTFT 和 TPOT。

  • 一个 GPU 同时服务更多请求（更大的 batch），每张卡的单位时间产出（吞吐）会上升，但每个请求要跟别人抢算力和带宽，于是每个请求的 prefill 和 decode 都变慢，TTFT 和 TPOT 都变大。
  • 反过来，batch 调到最小，每个请求的 TTFT/TPOT 最好，但 GPU 可能"吃不饱"，吞吐很低。

好的推理服务要在吞吐与延迟之间取一个业务可接受的平衡点，这正是下一课的主题。

4. 为什么要分开看这两个指标#

因为它们的优化方向不同：

  • 优化 TTFT：加速 prefill——比如用前缀缓存跳过重复 prompt 的计算（SGLang 的 RadixAttention 就是干这个的，第 3 章会讲）、限制 prompt 长度、把 prefill 优先调度。
  • 优化 TPOT：加速 decode——比如用更小的模型、量化减少权重字节数（第 4 章）、提升显存带宽、用投机解码（speculative decoding）一次多吐几个字。

二、可运行示例#

下面的 Python 模拟一次请求，分别测量 TTFT 与 TPOT，并展示"batch 越大，两个指标越差"的权衡关系。

# -*- coding: utf-8 -*-
# 模拟测量 TTFT 与 TPOT，观察它们随并发请求数（batch）的恶化

def simulate_request(prompt_len, gen_len, concurrent,
                     base_prefill_per_token=0.02,   # 每 token 的 prefill 基础耗时(ms)，近似
                     weight_read_ms=20.0):           # decode 单步读权重的基础耗时(ms)
    """返回 (TTFT 秒, TPOT 秒/字)。并发越大，算力/带宽被均分，两者都变慢。"""
    # prefill 受算力限制：并发翻倍，单请求 prefill 约翻倍
    ttft_ms = base_prefill_per_token * prompt_len * concurrent
    # decode 受带宽限制：并发翻倍，单请求每步读权重时间约翻倍
    tpot_ms = weight_read_ms * concurrent
    # TPOT 用户感受到的是"每个字平均多久"，与生成总长无关
    return ttft_ms / 1000, tpot_ms / 1000

for concurrent in [1, 4, 16, 32]:
    ttft, tpot = simulate_request(prompt_len=512, gen_len=200, concurrent=concurrent)
    total = ttft + tpot * 200  # 生成 200 字的总延迟
    print(f"并发 {concurrent:>2}：TTFT={ttft*1000:6.0f} ms | TPOT={tpot*1000:5.0f} ms/字 | "
          f"200字总延迟={total:5.1f} s")

运行后你会看到一条清晰的趋势：并发从 1 提到 32，TTFT 和 TPOT 都线性恶化，单请求总延迟被拉长很多。这就是"高吞吐"的代价——单位时间处理的请求多了，但每个请求的体验变慢了。

三、练习#

  1. 改并发：把并发列表改成 [1, 2, 8, 64]，观察 TTFT 和 TPOT 各自放大了多少倍，验证"线性恶化"。
  2. 分开看瓶颈：只把 base_prefill_per_token 从 0.02 改成 0.1（模拟超长 prompt），TTFT 变化多大、TPOT 受影响吗？说明 TTFT 与 TPOT 的优化是解耦的。
  3. 换权重：把 weight_read_ms 从 20 改成 10（模拟把模型量化后权重减半），TPOT 怎么变？为什么量化能改善 TPOT 却基本不影响 TTFT 中的 decode 部分？
  4. 思考：一个实时对话产品，你更愿意优先优化 TTFT 还是 TPOT？一个批量批处理（离线）任务呢？给出你的判断和理由。
