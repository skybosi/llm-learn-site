可观测性：轨迹、因果链、每一步的输入输出与代价#

这一节要解决什么#

前三节把循环跑起来了、也停得下来了。现在面对一个更根本的问题：你怎么知道它为什么这么跑、为什么在这儿停？

一个 Agent 出了一次事故，你要回答的问题是具体的：

"第 7 步它为什么调用了 send_email 而不是先做校验？"
"它在第 7 步看到的那份数据，是从哪一步来的？"
"这次运行比 p50 贵了 18 倍，钱花在哪一步？"
"我把这个提示词改一个字，结论会变吗？"

如果轨迹里没有对应的字段，这些问题一个都答不了 —— 而它们正是第 7 章"失效归因四象限"的输入。

这一节要把可观测性从"打日志"变成三个具体的数据结构问题：

  1. 轨迹（trace）：记什么字段？为什么它必须是"事件流"而不是"最终状态"？
  2. 因果链（causal chain）：怎么知道第 7 步用的信息来自第 3 步？这里有一个真正困难的技术点（引用 vs 复制）。
  3. 代价归因（cost attribution）：怎么找出"最贵的步骤"和"被浪费的步骤"？
  4. 可重放（replay）：确定性边界在哪里？什么能重放、什么永远不能？—— 这一节最需要诚实的地方。

学完这一节你应该能回答：

  • 为什么"在循环结束后把状态 dump 出来"不能当作轨迹？
  • 日志里有全部的工具返回，为什么还是定位不了"它为什么这么做"？
  • 为什么 Agent 的成本归因必须能区分"有效成本"和"无效成本"？怎么自动识别无效步？
  • temperature=0 就能复现了吗？（答案是不能，原因不止一个。）
  • 为了让 L3 可重放，你的代码必须付出哪些额外的约束？

一、可观测的四个层级，以及每层的数据结构后果#

第 1 章给过 L1~L4 的层级。这一节的关键补充是：每一层不是一个"开关"，而是一组具体的数据结构要求。 选错层级，不是"记少了一点"，而是"问题从可答变成不可答"。

层级 数据结构要求 能回答 不能回答
L1 事件轨迹 只追加的 step 事件流（每步一行） 第几步？做了什么？花了多少？ 它为什么这么做？它看到了什么？
L2 因果链 每个决策输入片段带来源引用（src=step3.result.x） 这个决定基于哪一步的哪个数据？ 换个参数结果会变吗？
L3 可重放 输入快照 + 模型配置 + 随机种子 + 工具桩 微小改动的影响是什么？ 人工介入后它会怎么走？
L4 可干预 断点/暂停/状态恢复（与第 2.1 节的 Suspend 同构） 我在这里纠正它会怎样？ ——

回归本节的核心区分：

L1，多数团队止步于此记了"发生了什么"​​=L2 起记了"为什么发生"​​

绝大多数 Agent 事故定位不了，不是因为没记日志，而是因为记的是 L1。 L1 告诉你"第 7 步发了邮件"，但说不出"它为什么判断应该发"。要回答后者，必须记录决策时它看到的那份输入，以及这份输入里每一段的来源。

二、轨迹：为什么必须是事件流#

2.1 状态 dump 不是轨迹#

最常见的错误做法：循环结束（或崩溃）时把当前 state 序列化下来当"轨迹"。它不够用的原因有三条：

  1. 丢掉了被覆写的中间值。状态是收缩的（第 1 章），KV 的旧值被覆盖了。而 bug 往往正好藏在"第 3 步写进去、第 5 步被正确值覆盖"的那个瞬间。
  2. 丢掉了顺序。因果关系依赖顺序："先校验后执行"和"先执行后校验"的状态可能一样，安全性完全不同。
  3. 丢掉了失败路径。状态 dump 只反映成功收敛后的样子；而失败的那几次尝试（被重试覆盖掉的）恰恰是归因的关键。

规则：轨迹是只追加（append-only）的事件流，与状态存储物理分离。 这也解释了第 1 章那条设计决策（state 收缩 / trace 扩张）在这里的用处。

2.2 轨迹的 schema：每个字段都对应一个无法被替代的问题#

下面是 L2 级别的最小可用 schema。读法是"字段 → 它让你能回答的问题"：

字段 类型 它让你能回答
step int 第几步出的问题
span_id / parent_id str 这是子调用还是主循环的步（支持嵌套子 Agent，第 6 章）
ts_start / ts_end float 时延归因；卡在哪一步
decision_kind enum(tool/final/wait/plan) 是决策错了还是执行错了
tool / args str / dict 它做了什么
args_src dict[str, ref] 每个参数值来自哪一步的哪个字段 ← 因果链的核心
result_ok bool 行动段的真实结果
error_kind enum 参数错 / 权限错 / 目标不存在 / 超时 / 上游 5xx（第 3 章的错误分类）
hint str 反馈给模型的可行动诊断（原始内容）
tokens_in / tokens_out int 成本归因的基本量
cost float 折算后的成本（便于跨模型比较）
context_ids list[str] 本步送进模型的上下文片段（内容寻址）← L2 的核心
model / prompt_ver str 归因"是模型变了还是提示词变了"
temp / seed float / int 复现的前提
tool_ver str 工具实现变了没有
state_digest str 决策时刻的状态指纹（不存全量，见隐私取舍）
validations list 本步通过的硬约束检查（第 3 节的判据执行记录）

两个字段值得单独说明：

  • context_ids（内容寻址）：不存上下文的原文，存片段的 ID/哈希。原文存在一个可单独做脱敏与过期策略的片段库里。这样轨迹本身不携带 PII（第 1 章 L2 的隐私取舍），但要复盘时能取回片段。代价：片段库过期后轨迹的语义就丢失了 —— 这是一个必须写进设计文档的已知盲区。
  • state_digest：状态指纹而不是全量状态。用途是"判断两次运行是否在同一个状态上分叉"，代价是无法从轨迹完整恢复状态（要恢复就得靠 L3 的输入快照）。

2.3 一个容易忽略的要求：失败路径也要记#

✓ 记：ok / 参数错 / 权限拒 / 超时 / 重试 / 被用户中断 / 硬约束违反 / 挂起
✗ 常见遗漏：只记成功的工具调用

为什么失败路径的价值高于成功路径：成功路径已经在结果里体现了（任务完成）；失败路径是唯一能解释"为什么多花了 15 步"的数据。而且从统计上看，失败步的数量常常占总步数的一半以上（第 1 章 E[Nr​]≈k(1+αpr​1−pr​​) 里的第二项全是失败步）。

三、因果链：从"记录"到"可归因"#

这是本节技术上最难的一段。

3.1 问题陈述#

L1 轨迹能告诉你：第 7 步执行了 send_email(to="alice@x.com")。但它回答不了：这个 to 的值是从哪儿来的？ 可能来自：

  • 第 2 步工具的返回（用户提供的收件人）；
  • 第 5 步模型自己编造的（幻觉）；
  • 状态里一个很早就写入、从未被验证过的字段。

这三种情况的修复方向完全不同（工具错 / 模型错 / 记忆错 —— 正好是第 7 章四象限里的三类）。所以因果链不是"锦上添花"，它是归因的前提。

3.2 填法一：让模型自报来源（不可靠，但有用）#

最省事的做法是在工具的 schema 里要求模型标出来源：

{"tool": "send_email", "args": {"to": "alice@x.com"}, "provenance": {"to": "step2.result.contact"}}

问题：这是模型自报的，它会编（尤其在长轨迹里它自己也"记不清"）。所以它可以作为线索，不能作为证据。

3.3 填法二：结构绑定（推荐的默认做法）#

正确做法是从数据流上自动推导，而不是问模型。两个实现路径：

路径 A：句柄式上下文（context as handles）。 送给模型的上下文不是纯文本，而是带 ID 的片段：

[ctx:step2.result] {"contact": "alice@x.com", "name": "Alice"}
[ctx:step5.memo]    "根据上面的联系人，准备发送"

模型在决策里引用这些句柄（{"to": {"$ref": "ctx:step2.result.contact"}}）。引用由你的代码解析成真实值，于是 args_src 是结构性记录的，不依赖模型诚实。代价是模型必须学会使用句柄（提示词与 schema 要把这一步做好），以及引用语法增加了模型出错的面。

路径 B：上下文组装器记账（assembler bookkeeping）。 不改模型输出，只改你的上下文组装代码：每次把片段拼进 prompt 时，记录"这次 prompt 由哪些片段组成"。

assemble(view) → (prompt_text, fragment_ids)
decide(prompt_text) → decision
trace.append({..., "context_ids": fragment_ids})

这样你能知道"第 7 步看到了哪些片段"，但不能精确知道"它用了哪一个"。也就是说：能定位到"候选来源集合"，不能定位到单个来源。

做法 精度 实现成本 模型配合 建议
模型自报 低（会编） 极低 需要 仅作线索
组装器记账 中（候选集合） 低 不需要 默认起点
句柄式引用 高（精确到字段） 中高 需要 关键字段（收件人、金额、ID、SQL 条件）

实用的混合策略：对"高副作用动作的关键参数"强制句柄式引用，其余用组装器记账。 这是一条很好的工程线：把精确归因的成本花在真正要紧的字段上 —— 收件人错了会发给客户，日志级别传错了没人管。

3.4 从因果链到失效归因#

有了 args_src + context_ids，就能构造因果图并回答"这个错误值是从哪来的"：

反查算法（事故现场的一个具体查询）：
  错误参数 v 出现在 step 7
  → args_src["to"] = ctx:step2.result.contact        （句柄式）
     → 若 step2 是工具返回：值是外部给的 → 工具/上游错（或工具契约错）
     → 若 step2 是模型生成：值是模型造的 → 模型错（幻觉）
  → 若用组装器记账：context_ids = [f3, f5, f9]
     → 逐个检查哪个片段里含 v
        → 若 v 只出现在 f9（模型自己的 memo）→ 记忆污染（第 4 章）
        → 若 v 来自 f3（一个过期片段）        → 上下文组装错（选了过期数据）

这张图直接对应第 7 章的四象限（模型错 / 工具错 / 规划错 / 记忆错）。没有因果链，四象限里只有"模型错"是能猜的 —— 这就是为什么很多团队把一切失败都归给模型：不是模型总错，而是他们的轨迹只能支持这一个结论。

3.5 因果链的成本：一个必须承认的取舍#

因果链不是免费的：

代价 说明
上下文变大 带 ID 的片段比纯文本啰嗦（句柄式尤甚）→ 成本上升、可能影响 pdecide​
实现复杂 组装器要重构成"记账式"；句柄要解析与校验
模型可能用错句柄 引用语法本身成为新的错误来源
存了"它看到了什么"就存了敏感内容 片段库需要脱敏与保留期策略

判据：只有当失败归因的价值 > 这些成本时才做。反过来：如果这个 Agent 的失败代价只是"重跑一次"，L1 够了；如果它的失败代价是"给客户发了错邮件"，因果链是必须的。

四、代价归因：找出最贵的那一步和被浪费的那一步#

4.1 三个维度分别归因，不要合成一个"钱"#

第 1 章 2.5 说过：token、调用次数、时延的瓶颈可能只有一个。归因时同样分开：

costi​=wT​Ti​+wC​Ci​+wL​Li​

但分析时要看三个分量的占比，因为优化手段不同：

瓶颈分量 优化手段
token 上下文裁剪（第 4 章）、摘要、减少全量重传
调用次数 批量取回、合并工具、减少往返
时延 并行化互不依赖的步骤、缓存、挂起（而非轮询空转）

4.2 有效成本 vs 无效成本：自动识别"被浪费的步骤"#

这是代价归因里最有价值的分析。定义：

浪费率=∑i​costi​∑i∈W​costi​​

其中 W 是"无效步"集合。关键在于：W 可以被自动识别，用因果链的反向引用：

无效步的一个可计算定义：
  step i 属于 W  ⟺  ① 它没有被任何后续步引用（context_ids / args_src 里没出现）
                    ∧ ② 它的结果被后续步的同类调用覆盖（重复查询）
                    ∧ ③ 或者它触发了重试/回退（其结果被丢弃）
无效类型 识别方式 典型成因
未被引用的步 反向引用计数 = 0 漂移：做了与目标无关的事
重复步 同类工具 + 相似参数（相似度阈值） 无长期记忆：忘了自己查过（第 1 章边界二）
被回退的步 后续有对应的补偿/回滚记录 计划错 / 工具失败
空转等待 decision_kind == wait 且实际未阻塞 轮询式等待（第 2.1 节）

为什么这个分析重要：它把"Agent 很贵"这个模糊抱怨，变成"37% 的成本花在未被引用的步骤上，其中大部分是重复查询同一个接口" —— 这句话直接指向一个可修的 bug（缓存/去重），而不是"换个便宜的模型"。

4.3 长尾归因：p99 的那些运行贵在哪#

成本分布是重尾的（第 1 章 2.5）。所以归因必须分开看 p50 和 p99：

  • p50 的构成告诉你"正常路径的成本结构" → 优化它对总账影响最大。
  • p99 的构成告诉你"事故路径长什么样" → 通常是"重试循环"或"漂移导致的空转"，而不是"某一步特别贵"。

一个实用的报表：

按终止状态分组统计成本分布：
  done            p50=12k tokens  p99=31k
  budget_steps    p50=58k tokens  p99=60k   ← 撞上预算上界（正常的）
  violation       p50=8k  tokens  p99=45k   ← ★ 异常：违规前的漂移很贵
  blocked         p50=5k  tokens  p99=9k    ← 挂起很省（符合预期）
  error           p50=30k tokens  p99=61k   ← ★ 崩溃前的重试很贵

这张报表能立刻指出钱花在哪：如果 violation 和 error 占了总成本的 40%，那优化对象不是"正常路径"，而是更早的违规检测（第 3 节的三把闸）与更稳的工具。

五、可重放：确定性边界在哪里#

L3 可重放是最贵的一层，也最容易被承诺得过头。先说清楚它做不到什么。

5.1 temperature=0 不等于确定性#

一个流行的误解。即使把 temperature 设为 0（贪心解码），你仍会遇到：

非确定性来源 能否消除 说明
采样（temperature/top-p） ✓ 可设 greedy 但 greedy 只保证"给定相同 logits 时取 argmax"
浮点非结合性 ✗ 不可消除 归约顺序随批大小/硬件而变，logits 会有微小差异
批处理效应（continuous batching） ✗ 不可控 同一请求在不同 batch 组成下可能落到不同的浮点路径
硬件/驱动/kernel 版本 ~ 固定环境可 换机器换版本就可能变
服务端的静默模型更新 ✗ 不可控 供应商侧更新权重或推理栈，你无从知晓
采样之外的随机（如某些实现的 dropout、top-k 平局处理） ~ 平局时的 argmax 选择可能不稳定
你自己的工具 ✓ 可控（录制回放） 但需要显式实现
时间/随机数/环境变量 ✓ 可控（注入） 但要在写代码时就把它们参数化

结论：真正能提供的不是"比特级重放"，而是"结构性重放"。 这两个概念必须区分：

比特级重放 结构性重放
目标 输出逐字相同 决策序列相同（调了哪些工具、什么顺序、什么参数）
依赖 要求模型与推理栈完全确定 只要求工具与状态被冻结
可行性 实际不可行（供应商侧不可控） 可行且足够
用途 —— 回归测试："改了提示词，工具调用序列变了吗？"

这个区分是本节最重要的实践结论：不要承诺"可复现"，要承诺"结构性可重放"，并把它作为回归测试的基础。第 7 章的评测集正是建立在这个承诺上。

5.2 为了让结构性重放成立，代码必须付出的约束#

① 所有随机性参数化：seed、temperature、时间戳、随机 id 都从注入的 context 取，
   不直接调用 time.time() / random.random() / uuid4()
② 所有工具可桩化（stub）：工具走统一的注册表入口，允许替换成"录制-回放"实现
③ 工具版本入库：tool_ver 进轨迹，工具实现变更会被检测到（否则重放会静默失真）
④ 输入冻结：任务输入、检索结果、外部 API 响应都录下来（录制的时点要标注）
⑤ 状态可恢复：状态可序列化，能从任一步恢复（与第 2.1 节的 Suspend 共用机制）

这五条的每一条都是对代码的约束 —— 这就是 L3 的成本。它们必须在写代码时就满足，事后加不上：一个直接调用 time.time() 的 Agent 事后无法变成可重放的。

可重放的产物：一份"回放包" = 输入快照 + 模型配置 + 工具桩数据 + 版本清单。有了它，你可以在离线环境里重跑任意一条历史轨迹，并回答"如果当时把提示词改成 X 会怎样"。

5.3 重放能验证什么、不能验证什么#

能验证 不能验证
提示词/工具 schema 改动的行为差异（工具调用序列是否变化） 真实环境下的性能（桩数据是旧的）
失败是否可复现（同一个 bug 是否还在） 上游服务的时序问题（桩不回放时序）
成本变化（同样序列下的 token 数） 模型版本更新后的行为（除非固定了模型）
判据阈值调整的影响（离线评测集上） 人工介入后的路径

    ★ 设计决策：轨迹里只存片段的 id（内容哈希），不存原文。
    好处：轨迹本身不含 PII；片段库可以单独做过期与脱敏策略。
    代价（必须写进设计文档）：片段过期后轨迹的语义丢失 —— 已知盲区。
    """
    def __init__(self, ttl_days: int = 30):
        self.ttl_days, self._d = ttl_days, {}
    def put(self, text: str) -> str:
        fid = "f" + hashlib.sha256(text.encode()).hexdigest()[:12]
        self._d[fid] = {"text": text, "ts": time.time()}
        return fid
    def get(self, fid: str) -> Optional[str]:
        rec = self._d.get(fid)
        return rec["text"] if rec else None          # None = 已过期（语义丢失）

# ============ L2 轨迹的一行 ============
@dataclass
class Span:
    step: int
    span_id: str
    parent_id: Optional[str] = None
    ts_start: float = 0.0
    ts_end: float = 0.0
    decision_kind: str = "tool"          # tool | final | wait | plan
    tool: Optional[str] = None
    args: dict = field(default_factory=dict)
    args_src: dict = field(default_factory=dict)   # ★ 每个参数来自哪（因果链核心）
    result_ok: bool = True
    error_kind: Optional[str] = None     # bad_param | denied | timeout | upstream
    hint: Optional[str] = None
    tokens_in: int = 0
    tokens_out: int = 0
    cost: float = 0.0
    context_ids: list = field(default_factory=list)  # 本步看到的片段（内容寻址）
    model: str = ""
    prompt_ver: str = ""
    temp: float = 0.0
    seed: Optional[int] = None
    tool_ver: str = ""
    state_digest: str = ""               # 状态指纹（不存全量）
    validations: list = field(default_factory=list)  # 本步执行的硬约束检查

def digest(state: dict) -> str:
    return hashlib.sha256(json.dumps(state, sort_keys=True,
                                     ensure_ascii=False).encode()).hexdigest()[:16]

# ============ 上下文组装器（路径 B：记账）============
def assemble(view: dict, store: FragmentStore) -> tuple[str, list[str]]:
    """
    把状态视图组装成 prompt，并记录'这次 prompt 由哪些片段组成'。
    ★ 设计决策：组装器负责记账 —— 不依赖模型诚实（模型自报来源会编）。
    精度限制：只能给出'候选来源集合'，不能精确定位到单个片段。
    要精确到字段，对关键参数改用句柄式引用（见 bind_handle）。
    """
    parts, ids = [], []
    for k, v in view.items():
        text = f"[{k}] {v}"
        fid = store.put(text)
        parts.append(f"[ctx:{fid}] {text}")
        ids.append(fid)
    return "\n".join(parts), ids

def bind_handle(value_ref: str, view_lookup: dict) -> Any:
    """
    路径 A：句柄式引用 —— 由代码解析，因而 args_src 是结构性记录（不靠模型诚实）。
    ★ 只对高副作用动作的关键参数用（收件人/金额/ID/SQL 条件），
      因为句柄语法本身会增加模型的出错面。
    """
    assert value_ref.startswith("ctx:"), f"非法引用: {value_ref}"
    return view_lookup[value_ref]

# ============ 成本归因与无效步识别 ============
def attribute_cost(spans: list[Span]) -> dict:
    """三维度分开归因 —— 合成一个'钱'会掩盖是哪个瓶颈。"""
    tot = sum(s.cost for s in spans) or 1e-9
    return {
        "总成本": round(tot, 3),
        "token": round(sum(s.tokens_in + s.tokens_out for s in spans), 1),
        "按决策类型": {k: round(sum(s.cost for s in spans if s.decision_kind == k), 3)
                    for k in {s.decision_kind for s in spans}},
        # ★ 分开看错误步成本：异常路径常常才是成本大头（撞预算/漂移/重试）
        "错误步成本占比": round(sum(s.cost for s in spans if not s.result_ok) / tot, 3),
    }

def find_wasted(spans: list[Span], sim_threshold: float = 0.9) -> list[dict]:
    """
    自动识别无效步 —— 把'Agent 很贵'这个模糊抱怨变成可修的 bug。
    三类：未被引用 / 重复查询 / 被回退。
    """
    # 反向引用计数：谁的产出被后续步的 args_src / context_ids 引用过
    referenced = set()
    for s in spans:
        for src in list(s.args_src.values()) + list(s.context_ids):
            referenced.add(str(src))
    out = []
    for s in spans:
        sid = f"ctx:{s.span_id}"
        reasons = []
        if s.decision_kind == "tool" and sid not in referenced:
            reasons.append("未被任何后续步引用（漂移型浪费）")
        for p in spans[:s.step - 1]:
            if p.tool == s.tool and _sim(p.args, s.args) >= sim_threshold:
                reasons.append(f"与 step {p.step} 重复（无长期记忆型浪费）")
                break
        if reasons:
            out.append({"step": s.step, "cost": s.cost, "reasons": reasons})
    return out

def _sim(a: dict, b: dict) -> float:
    if not a and not b: return 1.0
    ka = set(a) | set(b)
    return sum(1 for k in ka if a.get(k) == b.get(k)) / max(len(ka), 1)

# ============ 因果链反查（事故定位的核心查询）============
def trace_back(spans: list[Span], step: int, arg: str) -> dict:
    """
    从'第 step 步的错误参数'反查到源头，并给出四象限归类。
    ★ 这是把'为什么模型总是被归因'变成'能区分模型/工具/记忆'的关键函数。
    """
    s = next(x for x in spans if x.step == step)
    src = s.args_src.get(arg)
    if src is None:
        return {"结论": "无来源记录 → 只能猜'模型错'（这正是 L1 的局限）"}
    origin = next((x for x in spans if f"ctx:{x.span_id}" == str(src)), None)
    if origin is None:
        return {"来源": src, "结论": "来源片段不在轨迹内（可能已过期或来自输入）"}
    if origin.decision_kind == "tool":
        return {"来源": f"step{origin.step} 工具 {origin.tool} 的返回",
                "归因": "工具错 / 上游数据错（不是模型幻觉）"}
    return {"来源": f"step{origin.step} 模型生成",
            "归因": "模型错（幻觉）或记忆污染（第 4 章）"}

# ============ 回放包（结构性重放）============
@dataclass
class ReplayPack:
    """
    ★ 承诺'结构性重放'（决策序列相同），不承诺'比特级重放' ——
      因为浮点非结合性、批处理效应、供应商侧静默更新都不可控。
    这五件东西必须在写代码时就满足，事后加不上。
    """
    input_snapshot: dict          # ① 冻结的任务输入
    retrieved: list               # ② 冻结的检索/外部响应（含录制时点）
    model: str                    # ③ 模型版本（固定，不跟随 latest）
    prompt_ver: str
    tool_stubs: dict              # ④ 工具录制数据（可回放）
    env: dict                     # ⑤ 注入的随机种子/时间/环境变量
    versions: dict                # tool_ver / kernel / 依赖清单
    recorded_at: float

    def to_json(self) -> str:
        return json.dumps(asdict(self), ensure_ascii=False, sort_keys=True)

REQUIRED_INJECTED = ["seed", "now", "rng", "uuid"]
def check_replayable(code_grep_hits: list[str]) -> dict:
    """
    自检：代码里是否还在直接调用不可控的随机源？
    ★ 一个直接调用 time.time() 的 Agent，事后无法变成可重放的。
    """
    banned = ["time.time()", "random.random()", "uuid.uuid4()", "datetime.now()"]
    hits = [b for b in banned if b in code_grep_hits]
    return {"可结构性重放": not hits,
            "必须先参数化": hits or "无（符合要求）"}

if __name__ == "__main__":

五处关键设计决策：

  1. FragmentStore 只让轨迹存哈希 id。这直接兑现第 1 章 L2 的隐私取舍，同时把"片段过期"这个盲区变成显式参数（ttl_days）。
  2. assemble 在组装时记账，而不是问模型。精度是"候选集合"—— 这个限制被明确写在文档字符串里，不假装更高精度。
  3. find_wasted 用反向引用计数自动识别漂移型浪费。这是把可观测数据变成优化目标的关键一步。
  4. trace_back 的返回里带四象限归类 —— 这是第 7 章评测的直接输入。注意它明确标出"无来源记录 → 只能猜模型错"，把 L1 的局限说清楚。
  5. check_replayable 用禁用清单自检。可重放不是事后能加的属性 —— 它要求代码从一开始就不直接碰随机源。

练习#

  1. schema 审阅：下面这份轨迹缺了哪 4 个字段，导致哪 4 个问题无法回答？请补齐并说明每个字段的用途。 {step, tool, args, ok, tokens} → 问题：无法回答"参数来自哪"、"为什么选这个工具"、"这次比上次贵在哪"、"能不能复现"。
  2. 因果链精度：某任务里 Agent 把 500 元转给了错误账户。用构造器记账法得到 context_ids = [f2, f7, f9]，用句柄法则得到 args_src = {"amount": "ctx:s4.result.total"}。请分别写出两种情况下你的定位结论，并说明哪个结论更可行动。然后回答：如果只有构造器记账，你还需要什么额外信息才能定位到真正来源？
  3. 归因实战：一次运行的轨迹显示 22 步、58k tokens，其中 step 4~12 是同一个工具 search_docs 用不同关键词的 9 次调用，其产出没有任何后续步引用。请：(a) 判断这属于哪类无效成本；(b) 给出两个不同的修复方向（一个减少浪费、一个改变设计避免它发生）；(c) 说明哪个方向更根本。
  4. 可重放诚实评估：你的 Agent 用了三个外部 HTTP API 和一个会变化的数据库。请写出你的"结构性重放"方案：哪些能被冻结、哪些不能、不能冻结的部分怎么处理（提示：录制时点 + 桩 + 已知偏差声明）。然后写出一段给用户的诚实说明：这个系统能复现什么、不能复现什么。
  5. 成本报表设计：用第四节的"按终止状态分组"思路，为一个"客服工单处理 Agent"设计一张成本归因报表（要包含行维度、列维度、以及你会从哪些异常模式里读出什么问题）。要求至少包含一个"看 p99 才能发现"的模式。
  6. 反例：构造一个场景，说明过度可观测反而有害（提示：L2 上下文快照可能包含用户密钥而被写进日志；或者为了记录慢工具而引入的同步写入拖慢了热路径；或者日志本身成为提示注入的载体 —— 想想它会不会被回喂给模型）。

小结#

  • L1 记"发生了什么"，L2 起记"为什么发生"。 多数团队事故定位不了，不是没记日志，是只到 L1。
  • 轨迹必须是只追加的事件流，与状态存储分离。状态 dump 丢掉三样东西：被覆写的中间值、顺序、失败路径 —— 而 bug 往往正在这三处。
  • 失败路径的价值高于成功路径：失败步常常占总步数的一半以上，且是唯一能解释"为什么多花 15 步"的数据。
  • 因果链的技术核心是"引用 vs 复制"：模型自报（会编，仅作线索）< 组装器记账（候选集合，默认起点）< 句柄式引用（精确到字段）。混合策略：高副作用动作的关键参数强制句柄，其余记账。
  • 没有因果链，四象限里只有"模型错"能被猜出来 —— 这不是模型总错，而是数据只支持这一个结论。
  • 代价归因三维度分开（token / 调用 / 时延），分析时看占比而不是合成一个"钱"。
  • 无效成本可以自动识别（反向引用计数 = 0 → 漂移；重复同类调用 → 无长期记忆；被回退 → 计划错）。这让"Agent 很贵"变成一句可修的 bug 描述。
  • p50 与 p99 要分开归因：p99 的异常通常集中在 violation / error 这类终止状态上，指向"更早的违规检测"而不是"更便宜的模型"。
  • temperature=0 ≠ 确定性：浮点非结合性、批处理效应、供应商侧静默更新都不可控。所以承诺的是结构性重放（决策序列相同），不是比特级重放。
  • 可重放是写代码时的约束，不是事后能加的功能：随机源必须注入、工具必须可桩化、输入必须冻结、版本必须入库、状态必须可恢复。
  • 可观测有成本，也有风险：上下文快照可能携带密钥、同步写日志可能拖慢热路径、日志本身可能成为提示注入载体（若被回喂给模型）。按失败代价选层级，并把盲区写进设计文档。
