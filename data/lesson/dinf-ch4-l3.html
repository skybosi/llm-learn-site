SLO 与容量规划：把 TTFT/TPOT 的百分位目标换成副本数与 KV 显存#

这一节要解决什么#

SLO 通常被写成三个数：

TTFT≤250 ms (p99),TPOT≤30 ms,可用性≥99.9%

运维团队拿它当验收标准，但工程团队真正需要回答的是：

要几个副本？每个副本给多少 KV 显存？单位成本是多少？

这一节就是把这三个数换成三个工程量。其中最容易做错的一步是：把 TTFT 与 TPOT 当成同一个约束。它们其实是两个不同的排队系统：

TTFT 管的是 prefill 的等待：请求到达 → 排队等一个"prefill 位" → 开始出第一个 token
      → 约束是「prefill 排队位 ≥ 多少」，由 (λ, prompt 长度, prefill 吞吐) 决定
TPOT 管的是 decode 的槽位：一个请求在 decode 期间一直占一个"并发槽"
      → 约束是「槽位总数 ≥ λ·输出长度·TPOT」，由 (KV 显存, TPOT 目标) 决定

两者的资源是分开的：prefill 排队位由算力与调度决定，并发槽位由显存与带宽决定。把它们合成一个 ρ 是容量规划最常见的错，后果是先按"显存够用"配好机器，再发现 TTFT 不达标（或反过来）。

一、三个约束，谁在什么时候最紧#

1.1 KV 的显存账（复述并修订第 2 章）#

第 2 章算过分页的碎片，这里要的是决策级的量：

KVtok​=2(K,V)⋅L⋅nkv​⋅dh​⋅σ

对 70B 级模型（L=80、nkv​=8、dh​=128、fp16 σ=2）：

KVtok​=2×80×8×128×2=327680 B=320 KiB/token

这个数值得记住：它意味着 8192 token 的上下文要 2.5 GiB 的 KV。它在两个方向上同时起作用：既限制单请求的长度，也限制并发数（× batch）。

1.2 TPOT 的 batch 上界#

第 1 章把 decode 的 TPOT 写成四项之和：

TPOT(b)=权重访存βhbm​Wgpu​​​​+KV 访存βhbm​b⋅KVtok​​​​+TP 通信2L⋅2(N−1)α​​+算力N⋅FLOPS⋅η2P​​​

只有第二项与 b 有关，所以反解出

btpot​=⌊KVtok​/βhbm​TPOTtarget​−(w+c+f)​⌋​

本节数值（βhbm​=3.35 TB/s、Wgpu​=130.4/8=16.3 GiB、N=8、α=1.5μs）：

b=1     : 权重访存 5.22 ms + KV访存 0.00 + TP通信 3.36 + 算力 0.03 = 8.6 ms
b=512   : 权重访存 5.22 ms + KV访存 0.05 + TP通信 3.36 + 算力 0.03 = 8.7 ms
b=2048  : 权重访存 5.22 ms + KV访存 0.20 + TP通信 3.36 + 算力 0.03 = 8.8 ms

两个可算的结论：

  1. 小 batch 下 TPOT 与 batch 几乎无关：b 从 1 到 2048（2048×），TPOT 只从 8.6 ms 涨到 8.8 ms。因为 KV 访存项在 b<bkink​=KVtok​/βhbm​w​≈53405 时远小于权重访存项。
  2. TPOT 的墙不在 KV 访存，而在 TP 通信：3.36 ms 是固定的，占 8.6 ms 的 39%。要压 TPOT，先减通信步数（第 3 章的树形全归约），而不是省 KV 显存。

1.3 三个约束的交叉：R 会换瓶颈#

把 KV 配额按副本数平摊，得到两条曲线的交叉点：

bkv​(R)=KVtok​Ckvtotal​/R​∝R1​,btpot​(R)=btpot​=const⟹Rcross​=Ckvtotal​btpot​⋅KVtok​​

本节算例（Ckvtotal​=128 MiB）：Rcross​≈534。也就是说在 R<534 的整个区间里，KV 都是更紧的那个；只有当集群大到 500+ 副本时 TPOT 才开始接管。这个数的大小完全由 Ckvtotal​ 决定 —— 所以"哪个约束更紧"是一个可算的、随部署规模变化的问题，不是一句经验。

二、TTFT 的尾约束：Erlang-C 与它的两种近似#

2.1 模型#

把 prefill 看成一个 M/M/c 排队系统：c=R 个"prefill 位"，到达率 λ，每个请求的服务时间 1/μ（本节 μ=12.82 req/s，即 78 ms = 30 ms 干扰 + 600 token / 12500 token/s）。

Erlang-B 的稳定递推（这是这一节最值得抄下来的一个算法）：

B(0,a)=1,B(k,a)=k+aB(k−1,a)aB(k−1,a)​

它避免了 c!ac​ 的溢出（c=20 时 20!≈2.4×1018，c=200 直接溢出）。由 B 得排队概率

C=1−ca​(1−B(c,a))B(c,a)​,a=λ/μ

等待时间的分布是指数尾：

Pr{W>t}=Ce−(cμ−λ)t⟹Wp​=cμ−λln(C/(1−p))​​

读法（三条路径必须同量级才可信）：

  • 闭式与蒙特卡洛在 R=3 时分别是 487 / 614 ms（同一量级），R=4 时 155 / 379 ms。差的那一部分是服务时间本身的随机性：闭式算的是"等待"分位，蒙卡算的是"逗留"（等待 + 服务）分位。
  • Kingman（Wq​≈1−ρρ​⋅2ca2​+cs2​​⋅E[S]）在多服务器下系统性地偏高（506 vs 155）。原因：它把 M/M/c 当 M/M/1 近似，丢掉了"多个服务台并联"的收益。工程上可以用它做保守估计，但不能用它做验收。
  • 真正的非线性在 ρ：R 从 3 到 4，ρ 从 0.780 到 0.585，Wp99​ 掉 3.1 倍。而 (cμ−λ) 在分母上 —— 这就是"最后一点余量最贵"的数学形式。

三、百分位税：SLO 的百分位就是容量参数#

R∗(p)=min{R:Wp​(R)+1/μ≤B}

目标 R∗ ρ Wp​ 相对 p50
p50 3 0.780 24 ms 1.00×

p99.9 5 0.468 136 ms 1.67×

p50→p99.9 的副本倍数是 1.67× —— 这就是百分位税​

它由排队模型的指数尾决定，与推理框架、模型结构无关：换一个更快的框架只是平移 1/μ，尾部的斜率 ln(C/(1−p))/(cμ−λ) 不变。所以"我们要 p99.9"这句话的价格是可以事先算出来的。

反面算例（同一个 SLO 的不同读法）：

若把 SLO 写成「p99 ≤ 250 ms」却按 p50 配容量（R=3）：
    超时比例 = C·exp(-(Rμ-λ)·B) = 7.4%（而目标只有 1%）
要从 7.4% 压到 1%：R 从 3 提到 4 就够，再多买是浪费

这张对照表是本节给运营团队的核心工具：它把"我们要不要更严的 SLO"变成一个价格标签（多 33% 的副本），而不是一场关于"用户体验"的辩论。

Rslots​=min{R:R⋅b(R)≥λLout​TPOT},b(R)=min(bkv​(R),btpot​)(decode 并发)

4.3 长上下文的容量墙#

把场景换成高吞吐 + 小 KV 池（λ=300 req/s、out=256、每副本 KV 128 MiB），只改 prompt：

prompt bkv​ 需并发 Rslots​ Rtail​ R∗ 瓶颈
1000 409 2304 6 37 37 TTFT
2000 409 2304 6 67 67 TTFT
4000 409 2304 6 不可行 6 KV/槽位
8000 409 2304 6 不可行 6 KV/槽位
32000 409 2304 6 不可行 6 KV/槽位

读法：

  1. prompt 变长只改 TTFT（30 ms+prompt/12500），完全不改 bkv​。所以上下文越长，Rtail​ 涨得越快（1k→37、2k→67）。
  2. 到 prompt=4k 时一次 prefill 本身已经 350 ms > 250 ms 的预算 —— TTFT 目标在当前 prefill 吞吐下不可达，此时 Rslots​=6 成为唯一的下界。
  3. 这就是长上下文服务的容量墙：它由 λLout​TPOT/bkv​ 决定，与 prompt 长度无关；优化 TTFT（加 prefill 算力、改块大小）救不了它。要过这堵墙只有三条路：加显存（降 KVtok​，如 GQA/量化 KV）、降 Lout​（提前停止）、或降 λ（限流）。

五、单位成本：$/1M output token 的 U 形曲线#

单位成本=有效输出吞吐λ⋅sat⋅Lout​​​⋅3600R⋅ngpu​⋅cgpu​​×106​

其中 sat 是被 SLO 打折后的满足率（本节用 min(1,B/Tp99​) 近似）。注意分母是有效吞吐而不是额定吞吐 —— 这是本节成本模型与"买机器算账"最本质的区别。

4 233 ms 9000.0 80 2.47 100%

最优R†=argRmin​sat(R)cR​（分子线性涨，分母在 SLO 达标后饱和）

三个结论：

  1. 成本曲线是 U 形，最优点在"刚好达标"处（R=4）。
  2. 在 U 形左侧，扩容是降本动作：R 从 2 到 3，单位成本从 1234.57 掉到 4.18（分母从 0.1% 恢复到 44%）。所以"为了省钱而少买机器"在 SLO 约束下往往恰好是反的。
  3. 越过最优点后每加一个副本纯涨价。多买的机器不产生任何额外有效吞吐（分母饱和），只抬分子。

六、取舍与边界#

  1. M/M/c 的假设在两个方向上都会破：(a) 真实服务时间不是指数分布（chunked prefill 让它接近确定性），此时 ρ 的尾部比指数尾更瘦，本节的 p99 估计是保守的；(b) 真实到达不是泊松（有突发），此时尾部比指数尾更胖，估计是乐观的。两者相抵，工程上用 Kingman 做上界、用闭式做下界，取区间。
  2. KV 配额的粒度决定了 b 的浪费。bkv​=⌊Ckv​/KVtok​⌋ 是向下取整的：Ckv​ 恰好比整数倍少 1 字节，就少一个并发槽。第 2 章的分页（块大小 16）把浪费控制在块内，但容量规划时必须按"块"而不是"字节"做除法。
  3. 副本数不是唯一的旋钮。R∗=max(Rtail​,Rslots​) 里，Rtail​ 可以通过"提高 prefill 吞吐"降下来（换更快的 attention kernel、减通信步数），Rslots​ 可以通过"降 KVtok​"降下来（GQA、KV 量化、滑窗）。先判断哪一个在 binding，再动那个旋钮 —— 这就是 §1.3 的交叉点判据的用途。
  4. 不要用"平均值"做容量规划。E[Lout​] 对槽位需求是线性的（Little 定律），但 SLO 是百分位 —— 输出长度的方差会通过"长请求占槽更久"放大尾延迟。本节把它吸收进 sat，真实系统需要按输出长度分桶算。
  5. 成本模型要包含"未计入的"资源：网络（第 3 章的 ρ⋅sbw​）、CPU 侧调度、对象存储出口（第 2 节的权重加载）。本节只算了 GPU·小时，所以它给出的是下界。
  6. SLO 的多维性：TTFT/TPOT/可用性三个目标共用一个副本池时，不能分别优化。本节的 max 形式只对"硬约束"成立；如果 SLO 是"三个指标各自有罚金"，就要解一个带权重的最小化问题（第 4 节的降级阶梯是它的离散版）。

代码#

这段程序是本节所有数字的来源。它包含四块：① KV 与 TPOT 的解析模型（每 token 字节、batch 上界、拐点）；② 数值稳定的 Erlang-B/Erlang-C 递推与等待时间分位闭式；③ Kingman 近似与 Monte Carlo 复核；④ 联合容量规划（Rtail​ 与 Rslots​ 取 max）、百分位税与单位成本。

⚠️ 合成负载：Monte Carlo 部分用固定 seed，结果可复现；其余是纯解析计算。

"""第 4 章第 3 节：SLO 与容量规划 —— 把 TTFT/TPOT 的百分位目标换成副本数与 KV 显存。

纯标准库。三套可算的东西：
  ① M/M/c 的 Erlang-C（稳定递推，不溢出）+ 等待时间分位闭式
  ② Allen-Cunneen / Kingman 近似（工程上真正用的：只要均值与 SCV）
  ③ M/M/c 逗留时间的蒙特卡洛复核（seed 固定，验证①没有算错）

容量账把两个约束**分开**算，再取 max —— 这是本节的结构性结论：
  TTFT 尾约束 → R 的下界（prefill 排队位）        R_tail = max{R : Wq_p99(R) + 1/μ ≤ B}
  吞吐槽位约束 → R 的下界（decode 并发槽位）      R_slots = min{R : R·b(R) ≥ λ·out·TPOT}
"""
import math
import random

# ---------------- 模型与硬件口径 ----------------
L_, N_KV, N_H = 80, 8, 128      # 70B 级：80 层、8 个 KV 头、head_dim 128
SIGMA_KV = 2                    # fp16
P_PARAM = 70e9
HBM_BW = 3.35e12                # 单卡 HBM 带宽 B/s
HBM_PER_REPLICA = 40e9          # 每副本可用显存（8 卡里分给 KV 的池，按 GiB 口径算）
N_GPU = 8                       # 单副本卡数（TP=8）
ALPHA_TP = 1.5e-6
MSG_PER_TOKEN = 2 * L_
PEAK_FLOPS = 989e12
EFF = 0.55
KV_PER_REPLICA = 128 * 2**20    # 每副本 KV 配额 = 128 MiB

PREFILL_RATE = 12500.0          # 每请求可见的有效 prefill 速率 token/s（聚合 2e5 ÷ 16 路）
TTFT_DECODE = 0.030             # 一次 TTFT 里被 decode 干扰的固定量（30 ms）

KV_TOK = 2 * L_ * N_KV * N_H * SIGMA_KV        # 每 token KV 字节 = 320 KiB
WEIGHTS = P_PARAM * 2                          # fp16 权重 = 130.4 GiB


def tp_comm_per_token(n_gpu=N_GPU):
    return MSG_PER_TOKEN * 2 * (n_gpu - 1) * ALPHA_TP


def tpot_terms(b, kv_rep=KV_PER_REPLICA):
    """TPOT 的四项：权重访存 / KV 访存 / TP 通信 / 算力。"""
    w = WEIGHTS / N_GPU / HBM_BW
    kv = b * KV_TOK / HBM_BW
    comm = tp_comm_per_token()
    flops = 2 * P_PARAM / (N_GPU * PEAK_FLOPS * EFF)
    return dict(weight=w, kv=kv, comm=comm, flops=flops, total=w + kv + comm + flops)


def b_kv(kv_rep=KV_PER_REPLICA):
    return int(kv_rep // KV_TOK)


def b_tpot(tpot_target, kv_rep=KV_PER_REPLICA):
    t = tpot_terms(1, kv_rep)
    fixed = t["weight"] + t["comm"] + t["flops"]
    return max(1, int((tpot_target - fixed) / (KV_TOK / HBM_BW)))


def b_of_R(R, tpot_target=0.030):
    """全集群 batch 上界：KV 上界随 R 线性摊薄，TPOT 上界与 R 无关。"""
    kv_rep = KV_PER_REPLICA / R
    return min(b_kv(kv_rep), b_tpot(tpot_target, kv_rep)), kv_rep


# ---------------- 一、M/M/c：稳定的 Erlang-C 与分位闭式 ----------------
def erlang_b(c, a):
    B = 1.0
    for k in range(1, c + 1):
        B = a * B / (k + a * B)
    return B


def erlang_c(c, a):
    if a >= c:
        return 1.0
    B = erlang_b(c, a)
    return B / (1 - a / c * (1 - B))


def wq_quantile(c, lam, mu, p):
    """P(W>t)=C·e^{-(cμ−λ)t} → t = ln(C/(1−p))/(cμ−λ)。"""
    a = lam / mu
    if a >= c:
        return float("inf")
    C = erlang_c(c, a)
    if C <= 1 - p:
        return 0.0
    denom = c * mu - lam
    if denom <= 1e-12:
        return float("inf")
    return math.log(C / (1 - p)) / denom


def kingman_wq(c, lam, mu, ca2=1.0, cs2=1.0):
    rho = lam / (c * mu)
    if rho >= 1:
        return float("inf")
    return rho / (1 - rho) * (ca2 + cs2) / 2.0 / mu


def mc_sojourn(c, lam, mu, n=60000, seed=11):
    rng = random.Random(seed)
    a = lam / mu
    if a >= c:
        return (float("inf"),) * 4
    C = erlang_c(c, a)
    out = []
    for _ in range(n):
        w = 0.0 if rng.random() >= C else rng.expovariate(c * mu - lam)
        out.append(w + rng.expovariate(mu))
    out.sort()
    q = lambda p: out[min(n - 1, int(p * n))]
    return q(0.50), q(0.90), q(0.99), sum(out) / n


# ---------------- 二、容量规划 ----------------
def capacity_table(lam, prompt, out, ttft_budget, tpot_target, prefill_rate):
    """逐 R 给出两套约束的余量。prefill_rate = 每请求可见的有效 prefill 速率。"""
    t_pref = TTFT_DECODE + prompt / prefill_rate
    mu = 1.0 / t_pref
    need_slots = lam * out * tpot_target          # Little 定律
    rows = []
    for R in range(1, 41):
        b, kv_rep = b_of_R(R, tpot_target)
        slots = R * b
        a = lam / mu
        if a >= R:
            ttft99 = float("inf")
        else:
            ttft99 = wq_quantile(R, lam, mu, 0.99) + t_pref
        rows.append(dict(R=R, kv_rep=kv_rep, b=b, slots=slots, need=need_slots,
                         ttft99=ttft99, tpot=tpot_terms(b, kv_rep)["total"],
                         ok_tail=ttft99 <= ttft_budget, ok_slots=slots >= need_slots,
                         rho_prefill=a / R, rho_slots=need_slots / slots))
    r_tail = next((r["R"] for r in rows if r["ok_tail"]), None)
    r_slots = next((r["R"] for r in rows if r["ok_slots"]), None)
    r_star = max(x for x in (r_tail, r_slots) if x is not None) \
        if (r_tail or r_slots) else None
    return t_pref, mu, rows, r_tail, r_slots, r_star


def replicas_for_percentile(lam, mu, t_pref, p, budget, Rmax=200):
    for R in range(1, Rmax + 1):
        if lam / mu < R and wq_quantile(R, lam, mu, p) + t_pref <= budget:
            return R
    return None


def unit_cost(lam, out, R, ttft99, budget, cost_gpu_h=2.5, n_gpu=N_GPU):
    """$/1M output token：分母是**被 SLO 打折后的有效输出吞吐**。"""
    sat = 1.0 if ttft99 <= budget else max(1e-3, min(1.0, budget / ttft99))
    tok_rate = lam * sat * out
    cost_h = R * n_gpu * cost_gpu_h
    return cost_h / max(1e-9, tok_rate * 3600) * 1e6, tok_rate, sat

(7) 长上下文什么时候把容量锁死：R* 对 prompt 长度的敏感性
  换成 KV 池偏小的场景：λ=300 req/s、out=256、每副本 KV 128 MiB、TPOT≤30 ms、TTFT p99≤250 ms；只改 prompt
    prompt   b(KV)     需并发  R_slots  R_tail  R*=max       瓶颈     每副本KV

      2000     409    2304        6      67      67     TTFT        2MiB

五处关键设计决策：

  1. Erlang-B 用递推而不是阶乘：B = a*B/(k + a*B) 循环 c 次，c=500 也不溢出。用 c!ac​ 的写法在 c>170 时会 OverflowError —— 这不是理论问题，本节的脚本第一次跑就是这么挂掉的。
  2. wq_quantile 在 C≤1−p 时返回 0，而不是算 ln 的负数。含义是"排队概率本身已经低于目标的尾部预算，所以等待分位是 0"。这个分支让表格在小 ρ 下可读（否则会出现 −∞）。
  3. mc_sojourn 用"伯努利决定是否需要等待 + 指数抽样"，而不是真的模拟到达与服务过程。这是 M/M/c 的精确抽样法（P(等待)=C，等待时间服从 Exp(cμ−λ)），几十行就能验证闭式，比事件驱动模拟快 100 倍。
  4. plan() 返回整张表而不是只返回 R∗。因为容量规划的决策依据在表格的形状里（哪一行从 ✗ 变 ✓、ρ 的跳变在哪），一个数说明不了问题。
  5. b_of_R 把"每副本 KV 随 R 摊薄"显式写出来，而不是把 KV 总量当常数。这是 §1.3 那个交叉点的来源；如果把它写成常数，"小集群 TPOT 紧、大集群 KV 紧"这个结论就消失了。

读输出的三处要点：

  • (1) 段的"需要槽位 270"与"全集群槽位 408"：这就是 §4 的 Rslots​ 视角。它在 R=1 时就满足（409 ≥ 270），说明本节参数下真正的瓶颈是 TTFT（Rtail​=4） —— 这是可以立刻省下 3 个副本的信息。
  • (3) 段 Kingman 一列系统性高于闭式（506 vs 155）：这是把它当"上界工具"而非"验收工具"的理由。
  • (6) 段的 U 形最低点是 2.47 $/1M：注意 R=3 时是 4.18（SLO 打折 44.3%），R=5 时是 3.09（不打折但多买一个）。两侧的"贵"来自完全不同的机制：左侧是 SLO 罚金，右侧是容量浪费。

小结#

  • TTFT 与 TPOT 是两个排队系统：前者是 prefill 排队（由 R 与 prefill 吞吐决定），后者是 decode 并发槽位（由 KV 显存与 TPOT 目标决定）。R∗=max(Rtail​,Rslots​)​，把它们合成一个 ρ 是容量规划最常见的错。
  • 每 token KV = 2Lnkv​dh​σ（70B 级 = 320 KiB）。它同时限制单请求长度与并发数；bkv​=⌊Ckv​/KVtok​⌋ 随 R 走 1/R，而 btpot​ 与 R 无关 —— 两者在 Rcross​=btpot​KVtok​/Ckvtotal​ 交叉，所以"哪个约束更紧"随部署规模变。
  • Erlang-B 要递推（B(k)=k+aB(k−1)aB(k−1)​），等待分位 Wp​=ln(C/(1−p))/(cμ−λ)。Kingman 在多服务器下系统性偏高，可用作保守上界但不能做验收。
  • 百分位税是 1.67×（p50 → p99.9）。它由指数尾决定，与框架/模型无关；"我们要 p99.9"的价格可以事先算出来。按 p50 配容量会在 p99 口径下产生 7.4% 的超时（目标 1%）。
  • $/1M output token 是 U 形：分母是被 SLO 打折后的有效吞吐。最优点在"刚好达标"处（本节 R=4、2.47 $/1M）。U 形左侧扩容是降本，右侧扩容纯涨价，两侧的"贵"来自完全不同的机制。
  • 长上下文的墙由 λLout​TPOT/bkv​ 决定，与 prompt 长度无关：优化 TTFT 救不了它。要么加显存、要么降输出长度、要么限流。
  • 一句话：SLO 不是验收标准，是容量参数；把百分位、输出长度、KV 字节数写进同一个不等式，副本数与成本就都能算出来。

下一节：本节的所有模型都假设"服务时间与容量是稳定的"。但真实系统里节点会变慢、请求会超时、失败会被重试，而重试本身会放大负载 —— 于是一个 ρ=0.99 的"健康"系统可能在一次失败后直接排队发散。第 4 节给出慢节点的影响面、重试的成功到达率方程与稳定上界、过载的相变，以及超时阈值与降级阶梯的可算判据。
