bank conflict：成因、检测与消除#

共享内存（shared memory）被称作「软件管理的片上仓库」，每 SM 每周期能供 128 字节。但把一块 32×32 的 tile 按列读一遍，这条带宽会掉到 1/32——代码一行没改，只是交换了两个索引的方向。这就是 bank conflict（bank 冲突）。本课给出 bank 的映射规则、能手算的冲突路数、四种消除手段，以及没有 GPU 时的检测路径。

一、概念讲解#

1. bank 是「地址 → 端口」的固定映射#

共享内存被切成 32 个 bank，每个 bank 宽 4 字节，合起来正好是每周期 128 字节。映射规则只有一条：

bank_of(word_addr) = word_addr % 32      # word_addr = 字节地址 / 4

一个 warp 的共享访存按三条规则结算周期数：

  • 32 个线程落在 32 个不同 bank → 1 个周期；
  • 落在同一 bank 的不同地址 → 串行化，N 个不同地址花 N 个周期（N 路冲突）；
  • 落在同一地址 → 广播（broadcast），只花 1 个周期，不算冲突。

这套公式适用于 32-bit 访问；64-bit / 128-bit 的共享访存会被硬件拆成更细的请求，计数规则不同，必须查官方文档或用 ncu 实测。

2. 经典来源：32×32 tile 的列访问#

__shared__ float tile[32][32];
  • 行访问 tile[k][tid]：字地址 k*32 + tid → bank = (k*32 + tid) % 32 = tid，32 个线程落在 32 个不同 bank → 1 个周期。
  • 列访问 tile[tid][k]：字地址 tid*32 + k → bank = k，32 个线程全挤在同一个 bank（k=5 时 32 个不同地址都在 bank 5）→ 32 个周期。

32 倍差距，只因为两个下标换了位置。GEMM 里对第二个操作数的「转置读」、矩阵转置 kernel 的写回，都会自然产生列方向访问——第 4 章做 tiling 时会正面撞上它。

3. padding：把行长从 32 改成 33#

声明改成 __shared__ float tile[32][33];（每行多留 1 个元素）后再看列访问：字地址 tid*33 + k → bank = (tid*33 + k) % 32 = (tid + k) % 32。tid 取 0~31 时这 32 个余数互不相同，冲突消失，回到 1 个周期。模拟器里整个 K 循环的周期数从 1024 降到 32（快 32 倍）。

代价是共享内存多占 3.1%（33/32）。拷贝阶段仍按行连续写每行前 32 个元素，不破坏全局侧的合并访存；但循环边界必须同步改成 33 的步长，否则会写进 padding 区域甚至越界——这是 padding 最常见的 bug。

4. 还有哪些消除手段#

手段 做法 代价与适用
padding 行长 32 → 33（步长与 32 互质即可，如 33） 多占约 3% 共享内存，最通用
swizzle（异或重排） 把列下标映射成 k ^ tid 一类的模式 不增加容量；TMA（Tensor Memory Accelerator）从 Hopper 起提供硬件 swizzle 模式，第 4 章展开
改数据到线程的映射 每个线程处理 4 个连续元素（float4） 减少请求数；但宽访问的冲突计数规则不同
用广播代替错位访问 让多个线程读同一地址，或把值留在寄存器里转发 零成本，前提是语义上确实同值

5. 检测：手算 / 计时 / ncu 三层#

  1. 手算：写出字地址表达式，对 32 取模，看 32 个线程的 bank 分布。本课模拟器就是这一步的自动化。
  2. 计时：只改 padding，对比同一 kernel 的耗时——最省事，但其他瓶颈可能掩盖差异，所以要配合第 1 课的「先确认是访存瓶颈」。
  3. ncu：Memory Workload Analysis 小节里看 shared memory bank conflicts（指标形如 l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld/st）。当前版本的准确名字用 ncu --query-metrics | grep bank_conflicts 确认，不要照抄旧版本的写法。

没有 GPU 时：手算公式 + 本课模拟器足以判断冲突路数和 padding 收益；上机前就能知道「该不该改」。

6. 常见坑#

  • 把广播当冲突：同一地址的多次访问只花一个周期。
  • padding 后忘记改循环边界：最常见的越界来源。
  • padding 加过头：共享内存占用上升，每 SM 能同时驻留的 block 变少，occupancy 下降，可能把冲突省下的时间又还回去（第 4 课算这笔账）。
  • 只按 32-bit 公式算 128-bit 访问：规则不同，必须实测。
  • 以为「shared 一定比 global 快」：32 路冲突时，共享内存每周期只供 1 个字，比合并良好的全局访存还差。
  • 把 L1 的 cache line 冲突与 bank 冲突混为一谈：前者是缓存行为，后者是端口映射，机制不同。

二、可运行代码示例#

下面这段纯 Python（不需要 numpy、更不需要 GPU）把 bank 映射与冲突结算规则实现出来，然后跑一遍行访问、列访问、padding、广播、strided 五种情形，并算出整个 K 循环的周期数。

# ---- shared memory bank 冲突模拟器（纯 Python，不需要 GPU）----
from collections import defaultdict

BANKS = 32                      # 32 个 bank，每个 4 字节宽

def conflict_ways(word_addrs):
    """word_addrs：warp 内每个线程访问的「字」下标。
    硬件规则：落在同一个 bank 的不同地址被串行化（N 个 → N 轮），
    落在同一个地址的多次访问算一次广播（只占 1 轮）。
    返回：本次共享访存需要的周期数（即最大冲突路数）。"""
    per_bank = defaultdict(set)
    for w in word_addrs:
        per_bank[w % BANKS].add(w)
    return max(len(addrs) for addrs in per_bank.values())

def report(name, word_addrs):
    ways = conflict_ways(word_addrs)
    print(f'{name:<30} 周期 {ways:>2}（{ways} 路）')

T = 32
print('访问 32×32 的 tile（float，1 个字 = 1 个元素）')
report('行访问 tile[k][tid]，k=5', [5 * 32 + t for t in range(T)])
report('列访问 tile[tid][k]，k=5', [t * 32 + 5 for t in range(T)])
report('列访问 + padding 33', [t * 33 + 5 for t in range(T)])
report('广播：所有线程读同一个字', [5 for _ in range(T)])
report('stride 2 字', [2 * t for t in range(T)])
report('stride 16 字', [16 * t for t in range(T)])

# 一次完整的 K 循环：32 个线程各读 32 个元素（GEMM 内积的普遍形态）
def kloop_cycles(padded):
    stride = 33 if padded else 32
    return sum(conflict_ways([t * stride + k for t in range(T)]) for k in range(32))

plain, pad = kloop_cycles(False), kloop_cycles(True)
print()
print(f'32×32 tile 跑完一轮 K 循环：未 padding {plain} 周期，'
      f'padding 后 {pad} 周期（快 {plain/pad:.0f} 倍）')
print(f'代价：33/32 = {33/32:.3f}，共享内存多占 {100*(33/32-1):.1f}%')

print()
print('列访问（未 padding）时，每个 bank 被多少个不同地址命中：')
hits = defaultdict(int)
for t in range(T):
    hits[(t * 32 + 5) % BANKS] += 1
for lo in (0, 16):
    rng = range(lo, lo + 16)
    print('  bank : ' + ' '.join(f'{b:>2}' for b in rng))
    print('  命中 : ' + ' '.join(f'{hits[b]:>2}' for b in rng))

最后那个直方图是理解冲突的关键：32 个不同地址全部落在 bank 5 上。padding 做的事，就是把这个「全部挤在一个端口」的映射打散成「每个端口各拿一个」。

三、练习#

  1. 实现：给 conflict_ways 加上 64-bit（double）访问——一个 double 占两个字，把它们当作两次 32-bit 请求分别统计，看看 double tile 的列访问是几路，并解释与 32-bit 情形的差别。
  2. 解释：为什么 padding 用 33 有效？用模拟器验证 stride 34（偶数）时的冲突路数，并说明「行长与 32 互质」为什么是关键。
  3. 对比/验证：把列访问改成「每线程读 2 个连续字（float2）」的映射，算一算冲突路数是否下降；再解释为什么 128-bit 访问不能直接套 32-bit 的公式。
  4. 思考：如果把 bank 数从 32 改成 64（每 bank 仍 4 字节），padding 策略要怎么变？共享内存每周期带宽会变吗？
