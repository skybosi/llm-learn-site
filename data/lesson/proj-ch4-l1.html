项目规划（本地部署与成本核算）#

你已经学完《LLM 推理引擎与优化》，知道 prefill/decode 两阶段、KV Cache、vLLM 的 PagedAttention、量化（AWQ/GPTQ/GGUF）这些概念。现在要把它们落地成一个能写进简历的项目：真正部署一个开源 LLM，实测它的显存、吞吐、延迟，并写出一份"成本核算报告"。

这个项目的价值不在"能跑起来"——网上教程谁都能照抄一条 vllm serve 命令——而在"算得清账"。面试官最常问的一类问题是："给你一个 70B 模型和固定预算，你怎么选卡和量化方案？" 背参数答不出来，真正量过、算过的人才能答。本课先做规划：选什么模型、什么引擎、什么硬件，以及"账"该怎么算。

一、目标与步骤#

1. 项目目标（一句话）#

用 vLLM / llama.cpp 在本地（或云 GPU）部署 Qwen/Llama 7B 级别的开源模型，对 FP16 与三种量化方案（AWQ / GPTQ / GGUF）分别实测显存、吞吐、延迟，产出一份成本核算报告。

2. 验收标准（做完项目你手里必须有这些）#

交付物 验收标准
可复现的部署记录 每条命令、每个参数都能照着重跑出同样的服务
实测对比表 至少 4 行（FP16、AWQ、GPTQ、GGUF）× 显存/吞吐/延迟 三列，数字来自你的实测而非抄网文
成本核算报告 含单 token 成本、每百万 token 成本，并推算"70B 要几张什么卡、每小时多少钱"
3 分钟口头总结 能不看稿讲清"你做了什么、量出了什么、省了多少"

3. 分步计划（5 步走完）#

  1. 选型：模型 + 推理引擎 + 硬件，三者要匹配（见下一节）。
  2. 环境：Docker / conda + 正确的 CUDA 版本。
  3. 部署：先跑 FP16 基准，再部署三种量化，逐一定量记录。
  4. 压测：并发请求测吞吐、TTFT、TPOT。
  5. 核算：把"显存/吞吐/延迟"翻译成"钱"。

二、选型与目标#

1. 模型选型：7B~8B 是"甜点区"#

选 Qwen2.5-7B-Instruct 或 Llama-3.1-8B-Instruct。理由：

  • 单卡消费级能跑：7B 权重 FP16 约 15 GB，一张 24 GB 显卡装得下，做量化后余量更大，适合大多数学习者的硬件条件；
  • 成本可控：云上租一张 24 GB 卡跑一天只有几十块量级，实验成本低；
  • 有代表性：7B 是开源生态里被讨论最多、量化文件最全的档位，你量出的规律可以外推到 70B。
模型 参数规模 FP16 权重 特点
Qwen/Qwen2.5-7B-Instruct ~7.6B ~15 GB 中文强、指令跟随好、GGUF/AWQ 生态全
meta-llama/Llama-3.1-8B-Instruct ~8B ~16 GB 英文与通用能力强、社区资料多

二选一即可，本课程示例统一用 Qwen2.5-7B-Instruct，Llama 的操作几乎完全相同（换模型名即可）。

2. 推理引擎选型：vLLM 主打，llama.cpp 补位#

  • vLLM：高吞吐在线服务的首选。PagedAttention 管理 KV Cache、continuous batching 提高 GPU 利用率，内置 AWQ/GPTQ 支持，暴露 OpenAI 兼容接口。
  • llama.cpp：跑 GGUF 格式的引擎。CPU 就能跑、量化档位极细（Q4_K_M/Q5_K_M/Q8_0…）、苹果芯片/Metal 支持好，适合"低资源、边缘设备"场景。

本项目两条线都走：在线高并发场景用 vLLM（FP16/AWQ/GPTQ），低资源场景用 llama.cpp（GGUF），这样对比表才有说服力。

3. 硬件选型：先看显存够不够#

硬件 显存 能跑什么（7B） 成本定位
消费级 RTX 4090 24 GB FP16 + 中等并发；量化后更高并发 一次性购卡
云 GPU A10 / L4 24 GB 同上 按小时租用，便宜
云 GPU A100 80 GB FP16 高并发；70B AWQ 也放得下 按小时租用，较贵

选型铁律：先算显存，再谈性能。 一张卡"装不下"就一切免谈，所以规划阶段的第一件事是把显存账算出来。

4. 显存估算：算账的第一步#

一次推理服务占用的显存 ≈ 四块之和：

显存 ≈ 模型权重 + KV Cache + 激活/中间结果 + 框架/碎片开销
  • 权重：7B × 每参数字节数。FP16/BF16 每参数 2 字节 ≈ 15 GB；INT8 ≈ 7.5 GB；INT4 ≈ 3.8 GB。
  • KV Cache：随"并发数 × 序列长度"线性增长，是决定能同时服务多少人的关键变量。粗略地，7B 模型每 1K token 的 KV Cache 约 5060 MB，8K 上下文一个请求就占约 0.40.5 GB——并发一高，它才是显存大头。
  • 激活/中间结果：与当前 batch 大小、序列长度有关，通常几 GB 量级。
  • 框架/碎片：CUDA context、vLLM 的预留，一般几百 MB 到 1~2 GB。

规划阶段结论：7B FP16 在一张 24 GB 卡上能跑，但并发要克制；量化（尤其 INT4）把权重从 15 GB 压到约 4 GB，省出的显存几乎全给 KV Cache，于是能扛更高的并发——这就是量化在"成本"上的意义。

三、代码骨架：先"纸面算账"#

正式部署前，先写一个不需要真 GPU 的显存估算脚本，把预期占用量和成本先算一遍。这一步练的是"算账能力"，也是后面写报告的骨架。

# -*- coding: utf-8 -*-
# estimate_vram.py —— 部署前的"纸面算账"：估算显存占用与单 token 成本
# 数字是估算公式，真实值以部署后 nvidia-smi / 压测为准

def estimate_weights(params_b, bits):
    """按参数量(billion)与位宽估算权重显存(GB)。"""
    bytes_per_param = bits / 8
    return params_b * 1e9 * bytes_per_param / (1024 ** 3)

def estimate_kv_cache(per_1k_token_mb, context_len, concurrency):
    """估算 KV Cache 占用(GB)：每 1K token 占用的 MB × 上下文长度 × 并发数。"""
    total_kb = (context_len / 1000) * per_1k_token_mb * concurrency
    return total_kb / 1024  # MB -> GB

def unit_token_cost(gpu_hour_price, num_gpus, throughput_tps):
    """按吞吐(tokens/s)估算每百万 token 成本(元)。"""
    # 每小时产出 token = throughput * 3600；总费用 = 单价 * 卡数
    tokens_per_hour = throughput_tps * 3600
    cost_per_million = (gpu_hour_price * num_gpus) / (tokens_per_hour / 1e6)
    return cost_per_million

# ---- 场景 1：7B FP16 部署在 24GB 卡 ----
params_b, bits = 7.6, 16
w = estimate_weights(params_b, bits)
kv = estimate_kv_cache(per_1k_token_mb=56, context_len=8192, concurrency=8)
print(f"[7B FP16] 权重 {w:.1f} GB + KV(8并发×8K) {kv:.1f} GB "
      f"+ 激活~3GB + 框架~1GB ≈ {w + kv + 4:.1f} GB（24GB 卡，余量 {24 - w - kv - 4:.1f} GB）")

# ---- 场景 2：7B INT4(AWQ) 同卡、更高并发 ----
w4 = estimate_weights(params_b, 4)
kv4 = estimate_kv_cache(56, 8192, 32)
print(f"[7B INT4] 权重 {w4:.1f} GB + KV(32并发×8K) {kv4:.1f} GB "
      f"+ 激活~3GB + 框架~1GB ≈ {w4 + kv4 + 4:.1f} GB（同样的卡，并发从 8 提到 32）")

# ---- 场景 3：把吞吐翻译成钱 ----
price = 1.2        # 示例：一张 24GB 云卡每小时单价（元），替换为你的账单
fp16_tps = 400     # 示例：FP16 实测吞吐（tokens/s）
awq_tps  = 900     # 示例：AWQ 实测吞吐（tokens/s）
print(f"[成本] FP16 每百万 token ≈ {unit_token_cost(price, 1, fp16_tps):.2f} 元")
print(f"[成本] AWQ  每百万 token ≈ {unit_token_cost(price, 1, awq_tps):.2f} 元")
print("结论：量化省下的显存转化为更高并发/吞吐，从而摊薄单 token 成本。")

说明：脚本里的 per_1k_token_mb=56、吞吐、单价都是示例值，目的在讲清公式；真实数字要在下一课部署压测后填进去。这份"先估算、后实测、再对照"的过程，本身就是面试里能讲的亮点。

四、验收与复盘#

1. 本课验收（规划阶段完成标志）#

  • 选定模型、引擎、硬件，并能一句话说清"为什么这么配"；
  • 能写出显存四段构成，并口算 7B FP16 与 INT4 的权重大小；
  • 能写出单 token 成本公式，并说清吞吐如何摊薄成本。

2. 动手练习#

  1. 把脚本里的模型换成 70B（参数 70B、INT4 权重约 35 GB），算一算：FP16 权重约多少 GB？需要几张 24 GB 卡（张量并行）才放得下？INT4 呢？
  2. 把 concurrency 从 8 加到 64，观察 KV Cache 如何成为显存大头，说明为什么"量化省权重"在高并发下尤其值钱。
  3. 查一下你所在云平台的真实 GPU 单价，替换脚本里的 price，估算"7B 服务跑一个月的常驻成本"（按 30 天 × 24 小时）。

3. 复盘要点（规划阶段要避开的坑）#

  • 别上来就挑最大的模型：70B 是"结果"不是"起点"，先用 7B 把流程和公式跑通；
  • 别抄网文数字：所有显存/吞吐必须来自你自己的 nvidia-smi 和压测，这是项目的可信度所在；
  • 算账要落到"钱"：GB 和 tokens/s 是中间量，最终都要折算成"每百万 token 多少元"或"每小时多少元"，面试官只认这个。
