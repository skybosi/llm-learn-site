vLLM 启动与压测#

环境搭好、模型量化完，下一步是把它"serve 起来"并测出真实性能。本课聚焦两个动作：用 vLLM 拉起一个 OpenAI 兼容的推理服务，以及用压测脚本测出吞吐与延迟分位数。压测不是"跑一下看个数字"，而是要在控制并发/请求速率的前提下，找到"满足 P99 延迟前提下的最大吞吐"——这正是上一章容量规划需要的那个关键输入。学完本课，你应当能启动服务、用 curl 验证、用脚本压测并读懂 TTFT/TPOT/吞吐三组指标。

一、概念讲解#

1. vLLM 启动：一个命令拉起服务#

现代 vLLM 用 vllm serve 直接启动 OpenAI 兼容服务：

vllm serve Qwen/Qwen2.5-7B-Instruct \
    --host 0.0.0.0 --port 8000 \
    --gpu-memory-utilization 0.9 \
    --max-model-len 8192 \
    --max-num-seqs 256

关键参数（下一课深入调优）：

  • --gpu-memory-utilization 0.9：模型 + KV Cache 最多用 90% 显存；
  • --max-model-len 8192：允许的最大序列长度（决定 KV Cache 上限）；
  • --max-num-seqs 256：同时处理的序列数上限（并发批）；
  • --quantization awq：加载量化模型时加这个参数。

启动后可用 curl 验证（OpenAI 兼容协议）：

curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"Qwen/Qwen2.5-7B-Instruct","messages":[{"role":"user","content":"你好"}]}'

2. 压测测什么#

压测核心三指标（上一门课的定义，这里落到测量）：

  • 吞吐（token/s）：单位时间产出的 token，衡量"能接多少活"；
  • TTFT（首 token 延迟）：请求发出到收到第一个 token，衡量"反应快不快"；
  • TPOT（每 token 延迟）：生成阶段每个 token 的平均间隔，衡量"读起来顺不顺"。

压测的关键是扫请求速率（QPS）：从低到高逐步加压，画出"吞吐上升、延迟在某个点后陡增"的曲线，拐点之前就是"达标吞吐"。只测一个并发点是看不出拐点的。

3. 自编压测脚本 vs 现成工具#

  • vLLM 自带 bench serve：一条命令出吞吐/延迟，适合快速摸底；
  • 自编脚本：能精确控制并发、采集每个请求的 TTFT/TPOT、算 P99，适合验证 SLO。

本课用自编脚本，因为它把"延迟分位数"和"吞吐"一起算出来，更贴近需求分析的验收标准。

4. 压测的坑#

  • 预热：首几个请求含模型加载/内核编译，数据要丢弃；
  • 限流：短时间狂发会被限流或 OOM，要按速率逐步加压；
  • 长尾：只报平均值会漏掉 P99 尖峰，必须算分位数；
  • 输出长度：TTFT 受 prompt 长度影响，TPOT 受输出长度影响，压测要固定代表性长度。

二、可运行示例#

示例 1：启动服务 + curl 冒烟#

# 启动（量化模型加 --quantization awq；原始权重则省略）
vllm serve Qwen/Qwen2.5-7B-Instruct \
    --host 0.0.0.0 --port 8000 \
    --gpu-memory-utilization 0.9 \
    --max-model-len 8192 \
    --max-num-seqs 128

# 另开终端冒烟验证
curl -s http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"Qwen/Qwen2.5-7B-Instruct","messages":[{"role":"user","content":"用一句话介绍 GPU"}],"max_tokens":32}'

示例 2：自编压测脚本（扫 QPS，算 TTFT/TPOT/吞吐）#

# -*- coding: utf-8 -*-
# 压测脚本：以固定 QPS 打 OpenAI 兼容接口，统计吞吐 + 延迟分位数
# 运行前先 pip install openai aiohttp，并确保服务已启动在 8000 端口
import asyncio, time, random
from openai import AsyncOpenAI

client = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")
MODEL = "Qwen/Qwen2.5-7B-Instruct"

async def one_request(ttft_list, tpot_list, out_tok_list, in_tok=200, out_tok=128):
    prompt = "请用中文详细解释" + "量子计算" * 10   # 构造约 200 token 的输入
    t0 = time.perf_counter()
    ttft = tpot_sum = None
    n_out = 0
    stream = await client.chat.completions.create(
        model=MODEL,
        messages=[{"role": "user", "content": prompt}],
        max_tokens=out_tok, temperature=0.0, stream=True)
    async for chunk in stream:
        if chunk.choices and chunk.choices[0].delta.content:
            now = time.perf_counter()
            if ttft is None:
                ttft = now - t0            # 首个 token -> TTFT
                tpot_sum = 0.0
            else:
                tpot_sum += now - t0       # 累计 token 时间戳
            n_out += 1
            t0 = now
    if n_out > 0:
        ttft_list.append(ttft)
        tpot_list.append(tpot_sum / max(n_out - 1, 1))   # 平均每 token 间隔
        out_tok_list.append(n_out)

async def run(qps: float, seconds: float = 30):
    """按 qps 的速率持续发请求 seconds 秒，返回(吞吐, P50/P99 TTFT, P50/P99 TPOT)。"""
    ttft, tpot, ntok = [], [], []
    interval = 1.0 / qps
    tasks, start = [], time.perf_counter()
    while time.perf_counter() - start < seconds:
        tasks.append(asyncio.create_task(one_request(ttft, tpot, ntok)))
        await asyncio.sleep(interval)                    # 限速：控制请求速率
    await asyncio.gather(*tasks)
    ttft.sort(); tpot.sort()
    def pct(xs, p): return xs[int(len(xs) * p)] if xs else 0
    total_tok = sum(ntok)
    dur = time.perf_counter() - start
    return dict(qps=qps, throughput=total_tok / dur,
                p50_ttft=pct(ttft, .5), p99_ttft=pct(ttft, .99),
                p50_tpot=pct(tpot, .5), p99_tpot=pct(tpot, .99))

async def main():
    for qps in [2, 4, 8, 16, 32]:          # 从低到高扫速率，找"拐点"
        r = await run(qps)
        print(f"QPS={r['qps']:>2} | 吞吐={r['throughput']:6.0f} tok/s | "
              f"P50/P99 TTFT={r['p50_ttft']:.2f}/{r['p99_ttft']:.2f}s | "
              f"P50/P99 TPOT={r['p50_tpot']*1000:4.0f}/{r['p99_tpot']*1000:4.0f}ms")

asyncio.run(main())

跑完你会看到典型曲线：QPS 低时延迟很小、吞吐随 QPS 线性上升；超过某个点后吞吐不再涨、P99 延迟陡增——那个拐点对应的吞吐，就是"守住延迟 SLO 的最大吞吐"，正是容量规划要填的数字。

三、练习#

  1. 找拐点：把示例 2 的 QPS 列表加密（如 [2,4,8,16,24,32,48,64]），定位你机器上"P99 TTFT 开始超过 2s"的 QPS，并记录该点的吞吐。
  2. 改输出长度：把 out_tok 从 128 改成 512，重跑一个 QPS 点，观察 TPOT 和吞吐怎么变，说明为什么长输出场景吞吐会下降。
  3. 加预热：给脚本加"正式压测前先发 3 个请求丢弃"的预热逻辑，并解释预热为什么能避免把模型加载时间算进延迟。
  4. 对比现成工具：用 vllm bench serve --help 查看官方压测工具的用法，与自编脚本对比，说明各自适合什么场景。
