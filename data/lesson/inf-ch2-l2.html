显存计算#

上一课我们定性地知道"KV Cache 占显存"。这一课把它变成可以手算的公式：给定模型配置和序列长度，算出 KV Cache 到底吃多少显存，进而算出"一张卡能同时服务多少个请求"。这是推理部署中最实用的一项硬技能——不靠猜，靠算。学完本课，你应当能对任意一个开源模型心算出它的 KV Cache 占用。

一、概念讲解#

1. 每 token 的 KV Cache 大小#

KV Cache 存的是每一层、每个 token 的 K 和 V 向量。所以单个 token 的 KV Cache 字节数可以这样数：

每 token 字节=2×L×Hkv​×dhead​×b

逐项解释：

  • 2：K 和 V 各一份；
  • L：模型的层数（transformer blocks）；
  • Hkv​：KV 头数（注意：不一定是注意力头数！见下文 GQA）；
  • dhead​：每个头的维度（head dim）；
  • b：每个数值的字节数（FP16=2，FP8=1，INT8=1，INT4=0.5）。

2. GQA/MQA：KV 头可以比注意力头少#

现代模型普遍用 GQA（分组查询注意力） 甚至 MQA（多查询注意力） 来压缩 KV Cache：

  • 原始 MHA：Hkv​=Hq​（KV 头数等于查询头数）；
  • GQA：多个查询头共享一组 KV 头，例如 Llama-2-70B 的 Hq​=64、Hkv​=8，即 8 个查询头共享 1 组 KV；
  • MQA：Hkv​=1，所有查询头共享同一组 KV。

KV 头越少，KV Cache 越小——这是 GQA 能显著降低显存、提高批量上限的关键。

3. 总 KV Cache = 每 token × 序列长度 × 请求数#

单个请求占用：

单请求 KV Cache=每 token 字节×Stotal​

其中 Stotal​ 是该请求的 prompt 长度 + 已生成长度。注意：KV Cache 随生成长度动态增长，所以"最长能生成多少"和"能同时服务多少请求"是互相挤压的。

整卡 KV Cache：

总 KV Cache=每 token 字节×所有活跃请求∑​Si​

4. 一个具体例子：Llama-2-7B#

Llama-2-7B 的参数：L=32 层、Hq​=32、Hkv​=32（MHA，7B 未用 GQA）、dhead​=128、FP16（b=2）。则每 token：

2×32×32×128×2=524,288 字节=0.5 MB

一个 2048 长度的请求就要 0.5×2048=1 GB 的 KV Cache。若换成 GQA（Hkv​=8），每 token 降到 0.125 MB，同样 2048 长度只需 0.25 GB——省了 4 倍。

二、可运行示例#

下面的 Python 实现上面的公式，帮你对几个常见模型算一笔 KV Cache 账。

# -*- coding: utf-8 -*-
# KV Cache 显存计算：手算每 token、单请求、整卡可服务请求数

def kv_per_token(layers, kv_heads, head_dim, bytes_per_val=2):
    """每 token 的 KV Cache 字节数：2 × 层数 × KV头数 × head_dim × 每值字节。"""
    return 2 * layers * kv_heads * head_dim * bytes_per_val

def format_mb(b):
    return f"{b/1024/1024:.3f} MB"

# 常见模型配置（层数, KV头数, head_dim）——均为公开结构的近似值
models = {
    "Llama-2-7B (MHA)":  (32, 32, 128),
    "Llama-2-13B (MHA)": (40, 40, 128),
    "Llama-2-70B (GQA)": (80, 8, 128),   # 64 个查询头共享 8 组 KV
    "Llama-3-8B (GQA)":  (32, 8, 128),
}

for name, (L, Hkv, dh) in models.items():
    per_token = kv_per_token(L, Hkv, dh)
    # 2048 长度的单请求
    per_req = per_token * 2048
    # 假设 80GB 显存里给 KV Cache 留 40GB，可同时服务多少个 2048 请求
    capacity = 40 * 1024**3 / per_req
    print(f"{name:22s} 每token={format_mb(per_token):>10s} | "
          f"2048长度单请求={per_req/1024**3:5.2f} GB | 40GB可并发≈{capacity:6.0f} 个请求")

# 观察：序列长度如何挤压并发数
print("\nLlama-2-70B 在不同序列长度下的并发数（40GB KV 预算）：")
for seq in [512, 1024, 2048, 4096, 8192]:
    per_req = kv_per_token(80, 8, 128) * seq
    print(f"  序列 {seq:>5}：单请求 {per_req/1024**3:5.2f} GB -> 并发 {40*1024**3/per_req:6.0f} 个")

运行后你会看到两个直观规律：

  • 模型越大，每 token KV 越大；GQA 能把 70B 的每 token KV 压到比 7B 的 MHA 还小；
  • 序列越长，并发越低：同样 40GB 预算，70B 模型在 2048 长度能放 1600 个请求，到 8192 长度就只剩 400 个。
