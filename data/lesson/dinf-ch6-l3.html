1.2 三条读法#

读法 1：N∗ 随 λ 近似线性，但每卡吞吐也在缓慢上升。

从 25 到 800 req/s，λ 涨 32 倍，N∗ 从 1 涨到 9（9 倍）。差额来自"b 变大 → T0​ 摊得更薄"：

thr(b)=cw​+bckv​+T0​b​⟹∂b∂thr​>0 （当 b<b∗）

thr(b)=cw​+bckv​+T0​b​⟹∂b∂thr​>0 （当 b<b∗）

λ b T0​/b（占每 token 时间） 卡速
25 16.28 3.0/16.28 = 0.184 ms 2,552
200 48.51 0.062 ms 6,792
800 69.02 0.043 ms 9,045

这是"规模效应"的准确来源：不是硬件变好，而是固定开销被摊薄。它同时给出一条重要的工程结论 —— 小集群的单位成本必然更高（0.2174 vs 0.0614 元/1M，差 3.5 倍）。

读法 2：节点数是阶跃的。

每节点 4 卡、每副本 2 卡 → 每节点 2 副本。于是"卡数"与"节点数"不是连续的：

N∗ 卡 节点 该节点上的空闲卡
1 2 1 2
2 4 1 0
3 6 2 2
4 8 2 0
6 12 3 0
9 18 5 2

容量规划的粒度是"节点"，而节点上可能有 50% 的空闲卡​

为什么这很重要：λ 从 200 涨到 210（+5%）时，N∗ 仍是 3，成本不变；而涨到 250 时可能突然要 N=4（+1,944 元）。容量曲线是阶梯函数，任何"按比例扩"的直觉都是错的。

读法 3：TTFT 随 λ 缓慢上升，但这不是排队恶化的信号。

从 25 到 800，TTFT 只从 36.2 涨到 64.9 ms。原因是每加一档 λ 就加副本，ρ 始终保持在低位（≤0.5）。这说明：

TTFT(λ) 的斜率取决于"扩容策略"而非"负载本身"

如果扩副本慢一拍（比如按 5 分钟均值扩），TTFT 会沿另一条曲线走 —— 那条曲线才是压测要测的（§2 的固定配置阶梯）。

2.2 破点的精确定位#

C1 的破点可以用解析式算出来（不用扫表）。C1 破的条件是"即使 b 顶到 bkv​，吞吐仍不够"：

N⋅tstep​(bkv​)bkv​​<λPout​ ⟹ λ>Pout​N​⋅cw​+bkv​ckv​+T0​bkv​​

N⋅tstep​(bkv​)bkv​​<λPout​ ⟹ λ>Pout​N​⋅cw​+bkv​ckv​+T0​bkv​​

代入 N=3、Pout​=100、bkv​=77.01、tstep​=7.821 ms：

λ∗=100×7.8213×77.01×1000​=295.5 req/s=1.48×

λ∗=100×7.8213×77.01×1000​=295.5 req/s=1.48×

表里 1.4×（280）通过、1.6×（320）失败，与解析式给出的 1.48× 完全一致。 这就是"曲线的膝盖"：

安全运行区=λ≤λ∗⋅(1−余量),λ∗=Pout​tstep​(bkv​)Nbkv​1000​​

安全运行区=λ≤λ∗⋅(1−余量),λ∗=Pout​tstep​(bkv​)Nbkv​1000​​

2.3 为什么"破"是从 b 到顶开始的#

观察 tstep​ 这一列：从 0.4× 到 1.4× 它只从 6.40 涨到 7.74（+21%），从 1.4× 到 1.6× 几乎不动（7.74 → 7.82），之后完全不动。

b 到顶⟹tstep​ 冻结⟹吞吐冻结⟹需求继续涨=缺口线性扩大

这条因果链给出了压测最重要的一个"读法"：

如果 tstep​ 和吞吐在负载上升时冻结了，说明瓶颈是"容量"（bkv​），不是"带宽"或"算力"。 如果 tstep​ 继续线性上升而吞吐不涨，说明瓶颈是"带宽"（cw​+bckv​ 主导）。 如果 tstep​ 停止上升但 p99​ 开始指数上升，说明瓶颈是"排队"（ρ→1）。

三种形状互相排斥，所以只看两条曲线（吞吐 vs 负载、tstep​ vs b）就能定位到瓶颈层。

2.4 同时破的约束之间也有优先级#

1.6× 那一行同时报了三条：C1（0.92×）、C2（显存）、C3（prefill 0.90×）。这三条不是并列的：

约束 为什么同时破 修复动作
C2 显存（b>bkv​） 根因：b 被显存夹住 提 KV 预算（量化/加卡）
C1 吞吐（0.92×） C2 的后果：b 封顶 → 吞吐封顶 同上（或加副本）
C3 prefill（0.90×） 独立的第二原因：λLp99​(1−h) 超过 Nrprefill​ 开缓存 / 加卡 / 降 L

同时报警的约束里，只有"最先被顶住的那个"是根因​

怎么区分：把负载再往上加一档（1.6× → 2.0×）。C1 从 0.92× 掉到 0.74×、C3 从 0.90× 掉到 0.72×，两者都在恶化；但 C2 始终是"恰好顶住"（b/bkv​ 恒大于 1）。根因的特征是"不随负载继续变差，而是始终保持 binding"。

三、从曲线反推瓶颈层：四条上限与判据#

3.1 四条上限#

上一节算过三条上限，加上排队上限共四条：

候选瓶颈 上限值 单位 判据（实测特征）
带宽上限（读权重 + KV） 9,846 每卡 tok/s 实测 ≈ 此值，且 tstep​ 随 b 线性升
算力上限（FLOPs） 84,771 每卡 tok/s 实测远低于带宽上限（本节 8.6×）
显存上限（KV 容量） 77.01（= 9,846 tok/s） 并发槽 b 贴住 bkv​ 且吞吐不再涨
排队上限（SLO） 427 每副本 req/s p99​ 涨而 p50​ 平稳

3.2 当前工作点离哪条上限最近#

量 实测/模型值 上限 占上限
每卡吞吐 6,792 tok/s 9,846 69.0%
KV 显存 5.03 GB 15.98 GB 31.5%
算力 0.48 PFLOPS 等效 84,771 tok/s × … 0.2‰
每副本请求率 66.7 req/s 427 15.6%

离上限最近的是"每卡吞吐"（69.0%）；所以瓶颈在带宽，不在显存、算力、排队​

这张表就是"瓶颈定位"的全部：不需要更多指标 —— 因为四条上限相差 1~2 个数量级，"离谁最近"就是单值答案。

注意显存只占 31.5%：这解释了一个常见困惑 —— "显存还有 70% 空闲，为什么不能加 batch？"。答案是：加 batch 会让 tstep​ 上升、TPOT 恶化，而吞吐提升很小。显存不是瓶颈，带宽才是。

3.3 三个实验："改一个参数，看曲线怎么动"#

判据必须能区分不同的原因，所以最好的验证方式是主动扰动：

实验 改什么 若瓶颈=带宽 若瓶颈=显存 若瓶颈=算力 若瓶颈=排队
E1 bcap​（调度上限）128 → 64 吞吐几乎不变 吞吐降（b 被压） 不变 不变
E2 Bkv​（KV 预算）+50% 吞吐不变 吞吐升（b 可更大） 不变 不变
E3 TP 2 → 4 吞吐约翻倍 吞吐升 吞吐升 不变
E4 qmax​（并发槽）128 → 256 不变 不变 不变 p99​ 降

E2 是最有诊断力的一个：它把"显存"这一项单独动。注意 E2 的效果取决于"b 是否被显存夹住"：

  • 若当前 b<bkv​（如 N=3 时 b=48.51<77.01）：加 Bkv​ 没用（不是 binding）。
  • 若当前 b=bkv​（如 N=2 时）：加 Bkv​ 直接涨吞吐。

这就是压测报告必须写清"当时的 b/bkv​"的原因 —— 同样的扰动在不同工作点有相反的效果。

3.4 一条"负向"判据：什么情况下不该继续压#

压测常见的错误是"压到崩为止"。但从 §2 的表看，崩的位置（1.6×）与"该报警的位置"不同：

信号 阈值 动作
b/bkv​>0.90 0.90 已进入"无余量区"
ρ>0.60 0.60 排队开始主导 p99​
吞吐不再随 λ 增长 斜率 < 5% 撞容量上限

本节这三个阈值对应的负载分别是 1.4×、1.6×、1.5× —— 都远早于"p99​ 爆掉"。所以：

压测的终点是"最小余量信号出现"，不是"服务挂掉"​

理由：挂掉之后的曲线（ρ>1、队列无界）不提供额外信息，而且会污染缓存与状态，让后续测试不可复现。

四、可复现的压测方案#

4.1 到达过程：必须开环泊松#

方式 实现 何时用 问题
开环泊松 独立泊松过程，请求不等待 容量/SLO 验收 需要生成器能"发不住"
闭环固定并发 C 个 worker 循环发 吞吐上限测量 会掩盖排队（客户端自适应降速）
闭环固定速率 尽力发到 λ 压到崩溃 崩溃后自动降速，看不到真实尾

为什么闭环会掩盖排队：闭环里"在飞请求数"被客户端限制住，服务变慢时客户端也跟着变慢，于是 ρ 永远到不了 1。第 5 章算过的 p99​ 尾部特征在闭环下根本不会出现。

4.2 负载点与时长#

L2 0.8× 160 无排队区对比
L3 1.0× 200 目标负载，验收带在这里判

4.3 样本量：为什么 8 分钟绰绰有余#

nmin​(p)≈1−p10​窗口=λnmin​​

指标 样本下限 窗口（λ=200） 位置误差 ±zp(1−p)/n​
TTFT p50​ 20 0.10 s ±0.2191
TTFT p95​ 200 1.00 s ±0.0302
TTFT p99​ 1,000 5.00 s ±0.0062
TPOT p99​ 1,000 5.00 s ±0.0062
TPOT p99.9​ 10,000 50.00 s ±0.0006

统计窗口的样本量=420×200=84,000 个请求 ≫ nmin​(p99​)=1,000

8 分钟窗口对 p99​ 有 84 倍富余；但只够 p99.9​ 的 8.4 倍​

这条核算给出两条实践规则：

  1. 不要在验收里放 p99.9​：它需要每档 50 s 的可测窗口，还要在有干扰的环境里保持稳定，成本不成比例。
  2. 不要只看 p99​ 的单点：位置误差 ±0.0062（0.62 个百分点）在 n=1,000 时对应延迟上的 ±0.6 ms（若 p99​≈100 ms）—— 比"该检出的退化幅度"小，所以够用；但如果要检出 1% 的退化（1 ms），就必须把样本量加到 104 量级（第 4 节的金丝雀算这个）。

4.4 验收带：与模型比对#

压测的目的不只是"看它没崩"，而是验证模型。所以每档都要把实测与模型预测并列，落在 ±5% 内才算过：

量 模型预测 允许区间
单卡吞吐 6,791.61 tok/s [6,452.03, 7,131.19]
TTFT p99 49.20 ms [46.74, 51.66]
TPOT p99 7.14 ms [6.79, 7.50]
稳态批 b 48.51 序列 [46.09, 50.94]

模型的用途是"给出应该看到什么"；实测偏离 5% 之外时，先复标定模型，再谈容量​

为什么是 ±5% 而不是 ±1%：模型里的 MFU=0.60、η=0.70、T0​=3.0 ms 都是标定量，本身就带 5% 量级的不确定度。用 ±1% 的验收带会永远不过，然后团队就会开始调验收带而不是调模型 —— 这是比模型误差更坏的结果。

代码#

这段程序产出本节的四块：容量曲线、压测阶梯、瓶颈判据、可复现方案参数。

⚠️ 合成数据：负载点与 prompt 分布是设定值；容量曲线与阶梯都是模型计算，不是实测 —— 它的用途是给出"压测时应该看到什么"的预期，实测必须按 §4.4 与它比对。

"""第 6 章第 3 节：容量与压测。

纯标准库。四块：
  ① 容量曲线：λ 从 25 到 800，每个负载下的最小舰队与瓶颈
  ② 压测阶梯：固定配置逐级加负载，看哪个约束先破、破在哪个量上
  ③ 从曲线反推瓶颈层：单卡吞吐上限、显存上限、算力上限三者的可区分判据
  ④ 可复现的压测方案：开环泊松到达 + 样本量 + 验收带
"""
import math

GB = 1024 ** 3
P = 7.0e9
LAYERS, D_MODEL, KV_HEADS, HEAD_DIM = 32, 4096, 8, 128
PEAK, MFU = 989e12, 0.60
BW, BW_EFF = 3.35e12, 0.70
T0 = 3.0
VGPU = 24 * GB
ACT = 1.5 * GB
KV_B = 2 * LAYERS * KV_HEADS * HEAD_DIM * 2
LOG50 = math.log(50.0)
CFG = dict(lam=200.0, lp50=800.0, lp99=1600.0, pout=100.0,
           ttft=300.0, tpot=30.0, qmax=128, h=0.45,
           price=2.70, usd=0.74, node_gpus=4)


class Svc:
    def __init__(self, tp=2, wq=2, dtype_bytes=2.0, h=0.45, **kw):
        self.__dict__.update(CFG)
        for k, v in kw.items():
            setattr(self, k, v)
        self.tp, self.wq, self.dtype_bytes, self.h = tp, wq, dtype_bytes, h
        self.w_gpu = P * self.dtype_bytes / self.wq
        self.kv_budget = VGPU - self.w_gpu - ACT
        self.seq_max = self.lp99 + self.pout
        self.b_kv = self.kv_budget / (self.seq_max * KV_B)
        self.r_pref = self.tp * PEAK * MFU / (2 * P)
        self.Lkv = self.lp50 + self.pout / 2
        self.c_w = self.w_gpu / (BW * BW_EFF) * 1e3
        self.c_kv = self.Lkv * KV_B / (self.tp * BW * BW_EFF) * 1e3
        self.thr_req = self.lam * self.pout
        self.b_cap = min(self.b_kv, self.qmax)
        self.thr_max = self.b_cap / (self.t_step(self.b_cap) / 1e3)

    def tp_comm_ms(self, b):
        act = b * D_MODEL * self.dtype_bytes / 2
        attn = self.tp * self.seq_max * HEAD_DIM * self.dtype_bytes / 2
        return 4.0 * (act + attn) / 450e9 * 1e3

    def t_step(self, b):
        return (max(self.c_w + b * self.c_kv, 2 * P * b / (self.tp * PEAK * MFU) * 1e3)
                + self.tp_comm_ms(b) + T0)

    def t_prefill(self, L):
        return (2 * P * L / (self.tp * PEAK * MFU) * 1e3
                + self.tp_comm_ms(self.b_cap) + T0)

    @property
    def T_pref(self):
        return self.t_prefill(self.lp99 * (1 - self.h))

    def solve(self, N):
        lam_r = self.lam / N
        cap = self.b_cap
        s = self.T_pref / 1e3 + self.pout * self.t_step(cap) / 1e3
        for _ in range(800):
            b = min(lam_r * s, cap)
            s_new = self.T_pref / 1e3 + self.pout * self.t_step(b) / 1e3
            if abs(s_new - s) < 1e-13:
                s = s_new
                break
            s = 0.5 * (s + s_new)
        b = min(lam_r * s, cap)
        t = self.t_step(b)
        thr = b / (t / 1e3)
        mu = self.qmax / s
        rho = lam_r / mu
        tq = LOG50 / (mu - lam_r) * 1e3 if rho < 1 else float("inf")
        ttft = tq + self.T_pref
        margin = thr * N / self.thr_req
        pref_m = self.r_pref * N / (self.lam * self.lp99 * (1 - self.h))
        why = []
        if margin < 1.0:
            why.append(f"C1吞吐{margin:.2f}×")
        if lam_r * s > cap + 1e-9:
            why.append("C2显存")
        if t > self.tpot:
            why.append(f"C4 TPOT{t:.1f}")
        if ttft > self.ttft:
            why.append(f"C5 TTFT{ttft:.0f}")
        if rho >= 1:
            why.append(f"C5 ρ{rho:.2f}")
        if pref_m < 1:
            why.append(f"C3prefill{pref_m:.2f}×")
        return dict(N=N, gpus=N * self.wq, nodes=math.ceil(N * self.wq / self.node_gpus),
                    b=b, cap=cap, b_kv=self.b_kv, b_dem=lam_r * s, t=t, thr_gpu=thr,
                    thr_tot=thr * N, margin=margin, rho=rho, tq=tq, ttft=ttft,
                    kv_used=b * self.seq_max * KV_B / self.tp, pref_m=pref_m,
                    T_pref=self.T_pref, s=s, ok=not why, why=" ".join(why))

    def best(self):
        for N in range(1, 200):
            r = self.solve(N)
            if r["ok"]:
                return r
        return None

    def money(self, r, days=30):
        rev_h = r["N"] * self.price
        return dict(month=rev_h * 24 * days,
                    usd_M=rev_h * self.usd / (r["thr_tot"] * 3600) * 1e6)

五处关键设计决策：

  1. 用"固定配置 + 逐级加负载"而不是"每档都重新调优"：前者测的是余量（发现破点），后者测的是最优解（做容量规划）。两者都要，但顺序是先测余量 —— 因为线上扩容有延迟，运行点总在"最优解"的右侧。
  2. 破点用解析式定位，再用阶梯验证：λ∗=Nbkv​1000/(Pout​tstep​(bkv​))=295.5 与阶梯的 1.4× 通过 / 1.6× 失败完全一致。解析式给点，阶梯给形状。
  3. 四条上限用不同单位（每卡吞吐 / 并发槽 / 每秒请求）：因为它们的物理意义不同 —— 带宽与算力都是"每卡产出速率"，显存是"并发容量"，排队是"进入速率"。统一成"每卡吞吐"会掩盖显存那一条的特殊性（它不随 b 单调）。
  4. 扰动实验（E1–E4）作为判据的验证手段：只看数值不够，因为"离上限最近"可能是巧合（比如带宽与显存同时得到 9,846）。E2（改 Bkv​）能唯一区分这两者。
  5. 验收带用 ±5% 而不是 ±1%：模型里有三个标定量（MFU、η、T0​），合计不确定度就有 5% 量级。用 ±1% 的带子会导致团队去调带子而不是调模型。

读输出的三处要点：

  • (2) 段的"tstep​ 在 1.4× 之后冻结在 7.82 ms"：这是"容量瓶颈"的指纹。冻结的位置恰好是 tstep​(bkv​)，可以反推出 bkv​ 的实测值 —— 这就是从曲线反推参数。
  • (3) 段的"带宽 9,846 与显存 9,846 数值相同"：这不是巧合，而是因为 bkv​ 恰好 落在 thr(b) 的单调段。在这种重合的情况下，必须靠扰动实验（E2）区分，否则会给出错误的修复建议。

小结#

  • 容量曲线是阶梯函数：N∗ 随 λ 增长，但节点数每 +2 副本才跳一级。容量规划的粒度是一个节点（本节 1,944 元/月的台阶）。
  • 小集群的单位成本必然更高：T0​ 的摊薄效应让 25 req/s 的集群是 0.2174 元/1M，800 req/s 是 0.0614 元/1M，差 3.5 倍。
  • 固定配置的破点可以解析求出：λ∗=Nbkv​1000/(Pout​tstep​(bkv​))=295.5 req/s（1.48×）。阶梯验证：1.4× 通过、1.6× 失败。
  • 三种瓶颈的曲线指纹互相排斥：吞吐与 tstep​ 同时冻结 = 容量瓶颈；tstep​ 继续线性升 = 带宽瓶颈；tstep​ 停涨而 p99​ 指数升 = 排队瓶颈。
  • 四条上限相差 1~2 个数量级：带宽 9,846 / 算力 84,771 / 显存 77.01 槽 / 排队 427 req/s。"实测离谁最近"就是单值答案；当两条上限数值重合时，用扰动实验（改 Bkv​）区分。
  • 同时报警的约束里只有"始终 binding 的那个"是根因：C1 与 C3 会随负载继续恶化，C2 始终保持恰好顶住。
  • 必须开环泊松：闭环客户端会自适应降速，掩盖排队，使 p99​ 尾部特征消失。
  • p99​ 的样本下限 1,000，8 分钟窗口富余 84×；但 p99.9​ 只富余 8.4×。验收只放 p99​，p99.9​ 留给长期监控。
  • 验收带用 ±5%：模型里三个标定量合计不确定度就是 5% 量级；带子过紧会导致团队去调带子而不是调模型。
  • 一句话：压测不是"看它没崩"，而是"用受控扰动把四条上限中最 binding 的那条找出来，并把模型里的标定量改对"。
