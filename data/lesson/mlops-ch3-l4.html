从告警到定位：故障树、检查顺序与停止判据#

这一节要解决什么#

前三节把监控做完了：判据有了（ch3-l1）、指标与不确定度有了（ch3-l2）、阈值是代价模型的最小值点（ch3-l3）。现在告警响了。

周四 03:12  P1 告警：拒答率 0.0120 → 0.0193（超出变化型阈值）
周四 03:12  同一分钟：输入层「空值率」也越过阈值、成本层「每千 token 成本」上涨 8%
周四 03:13  值班同学打开看板：三条告警，四个层，200 个指标
周四 03:14  开始查……查哪一条？

这就是本节要解决的问题：告警之后的那段时间。它的特点是信息过载、时间压力、以及一个非常容易犯的错误 —— 先做最贵的动作（重训、回滚），再去找原因。

这个错误的具体形态有两种，都很常见：

错误动作 代价 为什么诱因是"没判据"
先回滚 如果根因在上游数据管道，回滚无效；而且回滚会销毁证据（旧版本的输入快照可能被覆盖） 没有"先分类再处置"的判据
先重训 重训要几小时到几天；如果根因是一个字段单位变了，重训出来的模型会把错误学进去 没有"概念漂移 vs 管道故障"的判据

所以本节要回答：

告警响了之后，按什么顺序查、查到什么程度可以停、什么情况下必须升级？这三件事都要有可算的判据。

四个子问题：

  1. 为什么"先看哪一层"有确定的答案？ —— 因为四层信号的检出延迟差着数量级（本节实测：输入层 schema 检查 1.5 分钟 vs 输出层次日离线指标 810 分钟，差 540 倍）。先看慢的那一层等于浪费 13 个小时（§一）。
  2. 检查顺序怎么算出来？ —— 把排查写成故障树 + 贝叶斯更新：先验 × 似然 → 后验，检查的排序依据是单位成本信息增益（期望熵减少 / 耗时）（§二、§三）。
  3. 什么时候可以停止排查？ —— 停止判据是"最大后验 ≥ 0.80"（或"证据不再改变决策"），不是"把清单走完"。实测：真因是"上游 schema 变更"时，走两步（4 分钟）就达到后验 0.9220，剩余检查不必做（§五）。
  4. 有哪些"看不见"的盲区？ —— 边际全不变、只改相关性的漂移，逐特征监控全静默（实测：两条 KS 都不显著，而相关系数从 −0.0244 变成 0.8035）（§四）。

一句话给本节定调：

排查不是"把可能的原因都看一遍"，而是"在每一步用最小的代价把后验推过处置门槛"。 没有这个框架，排查会退化成一个没有终止条件的仪式：查得越多越不确定，最后靠猜。

一、第一条规则：按检出延迟从小到大的顺序读#

告警是信号，不是证据。同一个根因会在不同层、不同时间产生信号，而这些信号的到达时间差着数量级。设一次上游数据事故发生在 t=0，各层信号的检出延迟可以拆成三段：

Tdetect​=传播Tprop​​​+窗口内平均等待Twindow​/2​​+人工/自动判定Tdecision​​​

本节算例（一次上游数据事故）：

层 信号 传播/分 窗口/分 决策/分 总延迟/分
输入 schema 版本 / 字段单位 0 1 1 1.5
输入 特征分布漂移（PSI） 5 15 5 17.5
输出 拒答率 / 格式失败率 2 1 1 3.5
输出 离线指标（次日标签） 720 60 60 810.0
延迟 p99 端到端延迟 1 5 3 6.5
成本 每千 token 成本 1 30 10 26.0
业务 人工客服工单量 45 120 60 165.0

读数三条：

  1. 最快与最慢差 540 倍（1.5 分钟 vs 810 分钟）。如果值班同学先去看离线指标（"我先确认一下质量到底掉了没"），他就把 13.5 小时花在了一个不可能在 13 小时内给出答案的信号上；
  2. "最快的层未必是根因所在的层"。schema 检查最先说话，但它只能告诉你"上游有个字段变了"，不能告诉你"这个变化是否真的伤了模型"；
  3. 传播延迟 Tprop​ 是最容易被忽略的一段：业务层工单量的 45 分钟传播延迟、离线指标 720 分钟的标签延迟，都不是"系统慢"，而是因果链本身的长度。

1.1 由此得到的第一条值班规则#

告警响应顺序（按信号延迟，不按仪表盘的重要性）：
  ① T_detect < 5 分钟：schema/版本检查、输出侧格式失败率、延迟 p99
  ② 5 ~ 30 分钟：特征分布漂移（PSI/KS）、成本指标
  ③ 30 分钟 ~ 数小时：业务工单量、人工抽检
  ④ 数小时 ~ 次日：离线指标、A/B 的最终结论
先把 ① 全部读到，再动 ②；在 ① 的结果出来之前，不要去读 ④。

这条规则的依据不是经验，是上表的算术：读 ④ 的信息在 T<810 分钟时根本不存在（标签还没到），而读 ① 的信息在 T>5 分钟时已经存在很久了。

1.2 报警时间线的对齐：一个必须先做的检查#

在开始任何"原因分析"之前，先做一件很朴素的事：把告警时间线与变更事件对齐。

变更事件（示例）
  02:40  上游数据管道发版（字段 unit: s -> ms）
  02:55  缓存配置变更（TTL 30min -> 5min）
  03:05  模型服务扩缩容（pod 数 8 -> 12）  <- 注意：扩容本身也会改变流量分布
告警
  03:12  拒答率超阈值
  03:12  空值率超阈值
  03:12  成本上涨 8%

对齐后立刻有两个观察：

  1. 三条告警同一分钟出现 → 指向一个共同的上游原因（而不是三个独立的模型问题）；
  2. 03:12 距 02:40 是 32 分钟、距 02:55 是 17 分钟、距 03:05 是 7 分钟 → 时间距离把 03:05 的扩缩容排在嫌疑第一位（但要注意：扩缩容经常是"结果的陪跑者"，比如因为重试变多而自动扩容 —— 这时它是症状不是原因）。

这一步的成本是几分钟，收益是排除掉一半的假设。 它的判据也很简单：对每个变更事件算出"距首次告警的时间差" Δi​，按 ∣Δi​∣ 排序；Δi​ 明显小于该层检出延迟的变更事件基本可以排除（因为"来不及"产生该层的信号）。

二、第二条规则：用故障树把"可能原因"列成可检验的假设#

时间线对齐之后，剩下的是"到底哪个原因"。这一步需要一张故障树：把可能原因列成互斥（或可加权的）假设，并为每个原因列出"可检查的信号"及其似然。

2.1 三个必须具备的字段#

字段 含义 常见错误
先验 Pr(c) 这个原因在没有新证据时有多可能 用"上次是哪一类"当唯一依据（会锁死在历史里）
似然 Pr(检查结果∣c) 如果真因是 c，这个检查会给出什么结果 只写"这个检查与 c 有关"，不写通过率/失败率
成本 做这个检查要多久、要动多少权限 忽略"需要申请权限"这一类非技术成本

本节算例给出四个原因与四个检查（CHECKS[name][cause] 是"在该原因成立时，这个检查通过的概率"，于是 1−p 是"发现异常的概率"）：

检查 \ 原因 上游 schema 变更 流量构成变化 检索索引陈旧 模型/配置变更 耗时/分
校验上游 schema 版本 0.05 0.95 0.95 0.90 3.0
对比近 24h 的流量构成 0.80 0.10 0.85 0.85 10.0
比对索引的 doc 数与 hash 0.90 0.85 0.05 0.80 4.0
核对 manifest/binding 哈希 0.85 0.90 0.85 0.03 1.0

先验（示例）：上游 schema 变更 0.30、流量构成变化 0.25、检索索引陈旧 0.20、模型/配置变更 0.25。

表的读法：如果真因是"上游 schema 变更"，那么"校验上游 schema 版本"这个检查只有 5% 的概率通过（即 95% 会发现异常）—— 它是一个强信号；而同一个检查在"流量构成变化"下通过率 0.95，几乎不提供信息。

2.2 信息增益：一个检查值多少#

给定先验 P，一个检查的"价值"可以用期望后验熵的下降（互信息）度量：

IG(check)=先验熵H(P)​​−期望后验熵E结果​[H(P∣结果)]​​

其中熵 H(P)=−∑c​P(c)lnP(c)（本节用自然对数，单位是纳特）。再把成本除进去，得到排序用的量：

单位成本增益=cost(check)IG(check)​

本节实测（先验熵 H(P)=1.3762）：

检查 耗时/分 先验熵 期望后验熵 单位成本增益
核对 manifest/binding 哈希 1.0 1.3762 0.7023 0.6739
校验上游 schema 版本 3.0 1.3762 0.5761 0.2667
比对索引的 doc 数与 hash 4.0 1.3762 0.6845 0.1729
对比近 24h 的流量构成 10.0 1.3762 0.7918 0.0584

排序结果：核对 manifest 哈希 > 校验 schema > 比对索引 > 对比流量构成。

两条读数：

  1. 最强信号既不是最便宜的、也不是最贵的，而是"两者之比最优"的：核对 manifest 哈希的期望后验熵 0.7023 不是最低（校验 schema 的 0.5761 更低），但它只要 1 分钟，所以单位成本增益第一；
  2. "对比流量构成"排最后不是因为它没用，而是因为它贵：它的期望后验熵 0.7918 是四个里最差（信息最少），耗时又是 10 倍。

2.3 一个必须说清的边界：似然从哪来#

上表的 Pr(通过∣c) 是给定的，而实践中它们必须从历史事故里估。三个现实约束：

约束 后果 缓解
事故样本极少（一年几次） 似然的不确定度极大（±0.2 很常见） 用区间而不是点值；对区间做敏感性分析（§三.3）
检查会引入假阴性（"看起来正常"但实际有问题） 单次检查通过不能排除该原因 给每个检查留一个"最小可发现幅度"，低于它的漂移不保证被发现
检查之间不独立 贝叶斯连乘会过度自信（把后验推得比实际更极端） 把强相关的检查合并成一个；或者给每次更新加一个"折扣"

这三条决定了本节框架的正确用法：它是排序工具，不是概率真相机。它的输出（"先查哪一个、查到什么程度可以停"）比它的中间量（后验的具体数值）更可靠。

三、第三条规则：排序策略要按真因分层评估#

"哪个顺序最好"这个问题有一个反直觉的答案：没有全局最优顺序，只有针对真因分布的最优顺序。本节把三种策略放在两个真因下各测 4000 次：

策略说明：

  • 固定清单（按字母序）：校验上游 schema 版本 → 对比近 24h 的流量构成 → 比对索引的 doc 数与 hash → 核对 manifest/binding 哈希（这是"中文拼音/字典序"的典型产物 —— 也是很多团队真实使用的顺序）；
  • 随机顺序：把四个检查按固定随机种子打乱；
  • 成本加权信息增益：按 §2.2 的排序。

停止判据统一为"真因的后验 ≥ 0.80"；"命中率"指"清单走完之前就已经达标"的比例。

策略 真因 平均步数 命中率 平均耗时/分 未命中后验均值
固定清单（按字母序） 上游 schema 变更 1.15 0.9485 3.77 0.1534
随机顺序 上游 schema 变更 3.19 0.8087 14.77 0.4917
成本加权信息增益 上游 schema 变更 2.40 0.8015 6.78 0.4937
固定清单（按字母序） 模型/配置变更 4.00 0.6042 18.00 0.4863
随机顺序 模型/配置变更 3.26 0.7408 15.04 0.4343
成本加权信息增益 模型/配置变更 2.25 0.8728 5.78 0.2904

这张表的三个结论：

  1. 真因是"上游 schema 变更"时，字母序反而最好（1.15 步、3.77 分钟）—— 纯属巧合：按字母序恰好把 校验上游 schema 版本 排在第一位，而它对这个真因的发现概率是 0.95；
  2. 真因是"模型/配置变更"时，字母序最差（4.00 步、18.00 分钟、命中率只有 0.6042）—— 因为对这个真因最强的两个检查（核对 manifest 哈希 发现概率 0.97、校验 schema 版本 只有 0.10）都被排到了最后一个和第一个之后；
  3. 信息增益顺序在两个真因下都是"接近最优"的（2.40 步和 2.25 步），代价是它不是任何单一真因下的最优。

所以正确的工程做法是：

不要问"哪个顺序最好"，而要问"在我最可能的三个真因上，这个顺序各要几步"。 一个顺序如果在某个真因上要 4 步、耗时 18 分钟，那就该把它改掉 —— 即使它在另一个真因上只要 1.15 步。

3.1 顺序改进的迭代方法#

实践中最省力的改进是把"最便宜且对多个真因都有分辨力"的检查提到前面。本节算例里 核对 manifest/binding 哈希 满足这个条件（1 分钟、对三个真因的发现概率都不低于 0.10、对"模型/配置变更"是 0.97）。这与 ch2-l1 的"门槛单价"结论同构：便宜的粗筛要放在前面，因为它保护的是后面所有昂贵检查的到达批次。

四、盲区：逐特征监控看不见的漂移#

排查时最容易掉进的坑是"每个特征都正常，所以输入没问题"。本节给出一个反例（与 ch3-l1 §1.3 同构，但这次用相关系数）：

构造：两个特征 x,y，旧环境相互独立（ρ≈0），新环境 y=0.8x+1−0.82​⋅ε。边际分布完全不变（都还是标准正态）。

实测（n=4000，KS 临界值 1.36/4000​=0.0215）：

视角 旧 新 判定
x 的 KS — 0.0210 不显著
y 的 KS — 0.0253 略超临界值，但仍属噪声量级
x 的均值 −0.0097 0.0070 无变化
y 的均值 0.0307 −0.0066 无变化
相关系数 −0.0244 0.8035 Fisher z=87.9，p<10−10

读数：两条 KS 一在临界值上下摆动（0.0210 vs 0.0215、0.0253），按"逐列告警"的口径会被静音（前者不显著、后者只是刚过线）；而相关性已经从 ≈0 涨到 0.80。

这条盲区对排查的直接影响：

  1. 排查清单里必须有一条联合判据（MMD、两样本分类器、或者关键特征对的相关系数），否则"逐列全绿"会被误读成"输入正常"；
  2. 联合判据的输出要能定位到"哪一对/哪一组特征"。MMD 只给一个数，所以工程上通常配一个"逐对相关系数矩阵的变化热图"或者用两样本分类器的特征重要性；
  3. "输入正常"这个结论必须写明它的覆盖范围：逐列判据覆盖单变量边际、联合判据覆盖二阶依赖。更高阶的依赖（三阶及以上）通常没人监控 —— 这是一个应该被显式声明的已知盲区，而不是默认不存在。

五、第四条规则：停止判据与升级出口#

排查有两个失败方式：停太早（后验还没到门槛就动手，动作可能是错的）和停太晚（信息已经足够却还在走清单，把 MTTR 花在了确认上）。两者都要有判据。

5.1 停止判据#

停止排查⟺cmax​Pr(c∣证据) ≥ θ

本节取 θ=0.80。实测一次：

检查 结论 真因后验 最大后验 熵
（未查） — 0.3000 0.3000 1.3762
核对 manifest/binding 哈希 正常 0.3878 0.3878 1.1351
校验上游 schema 版本 异常 0.9220 0.9220 0.3375

读数：走两步、用 4 分钟（1 + 3），最大后验从 0.3000 推到 0.9220，越过 0.80 → 停止排查，开始处置。剩余两个检查（比对索引 4 分钟、对比流量构成 10 分钟）不必做。

这个例子里"省掉最贵那一步"的收益是 10 分钟（占清单总耗时 18 分钟的一半以上）。在真实事故里，这个数字经常是"几十分钟 vs 几小时"。

5.2 三个必须写清的细节#

细节 1：阈值的选取。 θ 不是拍的，它由"错判的代价比"决定：

θ=正确处理的收益+C错判​C错判​​

实务上：如果"误判方向"会导致一次错误的重训（几小时 + 一次无效发布），而"继续查"只要几分钟，那么 θ 应该取高（0.9 以上）；如果"误判方向"只是多花十分钟查一个多余的信号（比如查一下成本指标），θ 可以取低（0.6 即可）。

细节 2：升级出口。 必须有"走完清单仍不达标"的处理：

若全部检查走完，最大后验仍 < θ：
  ① 输出"未判定" + 当前的假设排名与各自的概率（不要输出"没有异常"）
  ② 加入新的检查（扩大故障树），或者放宽 θ 并明确记录"这是在信息不足下做的决定"
  ③ 如果告警是 P0（用户已受损），先处置（回滚/限流/降级）再继续查 —— 处置与排查可以并行

这里的顺序很关键："未判定"必须是一个合法输出。如果流程默认"查不出原因就是没问题"，那么所有"证据不足"的情况都会被静默归零。

细节 3：证据的记录格式。 每一次检查都要落成一条记录，字段至少包括：检查名、时间、结论（异常/正常）、原始读数与其不确定度、影响的切片、以及快照引用。理由有两个：

  • 事故复盘（ch3 之外的第 5 节内容）需要一条可重放的时间线；
  • "正常"这个结论也需要证据 —— 否则三周后没人能解释当时为什么排除了某个原因。

5.3 一张可以贴墙的处置流程#

告警
 ├─ 0. 对齐变更时间线（几分钟；排除"来不及"的事件）
 ├─ 1. 按 T_detect 从小到大读信号（§一）
 │     <5min：schema/版本、格式失败率、p99
 │     5-30min：分布漂移、成本
 ├─ 2. 用故障树算单位成本信息增益，排检查顺序（§二）
 ├─ 3. 逐个检查，贝叶斯更新后验
 │     每步之后判断：max 后验 >= θ ?
 │       是 → 停止排查，进入处置
 │       否 → 继续（但优先选"对剩下真因分辨力最高"的检查）
 ├─ 4. 若清单走完仍不达标 → 输出"未判定" + 排名 + 扩大故障树
 └─ 5. 处置（回滚 / 校准 / 重训 / 修上游）—— 注意：处置动作本身要记录，
        因为它会成为下一轮排查的先验

第 5 步的"处置动作进先验"值得单独说：如果这次事故的原因是"上游字段单位变了"，那么下一次同类告警时，"上游 schema 变更"的先验就应该被调高。这就是"故障树要维护"的具体含义 —— 它是活的，不是一次画完的图。

代码#

下面的脚本只用标准库，把本节的量全部算出来。⚠️ 所有数据都是合成数据（random，固定种子），目的是让每个数字可复算，而不是给出现实数据上的结论。

脚本 242 行，运行 python3 /tmp/mlops_ch3_l4.py 可复现下面的全部输出。

"""
mlops-ch3-l4：从告警到定位的四个可运行实验。

① 基础函数自检：正态 CDF / 分位数 / 熵
② 故障树：先验 × 似然 → 后验，用「单位成本信息增益」排出检查顺序
③ 排序策略对比：随机顺序 / 按先验 / 成本加权信息增益，到 80% 命中各要几步
④ 越往下游越晚：分层监控的检出延迟账本
⑤ 相关性漂移：两个特征的边际都不动，逐特征监控全静默

运行：python3 /tmp/mlops_ch3_l4.py
⚠️ 全部为合成数据（random，固定种子），目的是让每个数字可复算。
"""
from __future__ import annotations

import math
import random


def mean(xs) -> float:
    return sum(xs) / len(xs)


def stdev(xs) -> float:
    m = mean(xs)
    return math.sqrt(sum((x - m) ** 2 for x in xs) / (len(xs) - 1))


def entropy(p: dict) -> float:
    h = 0.0
    for v in p.values():
        if v > 0:
            h -= v * math.log(v)
    return h


def update(prior: dict, lr: dict) -> dict:
    """贝叶斯更新：后验 ∝ 先验 × 似然比，归一化。"""
    post = {c: prior[c] * lr[c] for c in prior}
    z = sum(post.values())
    return {c: v / z for c, v in post.items()}


def kl(p: float, q: float) -> float:
    """伯努利分布的 KL(p||q)：一个检查对「有故障 / 无故障」的分辨力（纳特）。"""
    out = 0.0
    for a, b in ((p, q), (1 - p, 1 - q)):
        if a > 0 and b > 0:
            out += a * math.log(a / b)
    return out

print("  KL(0.9||0.5) = %.4f；KL(0.55||0.5) = %.4f" % (kl(0.9, 0.5), kl(0.55, 0.5)))
print("  -> 自检留在代码里：熵或 KL 错一点，检查顺序就排反")

    "对比近 24h 的流量构成": {"上游 schema 变更": 0.80, "流量构成变化": 0.10, "检索索引陈旧": 0.85, "模型/配置变更": 0.85},
    "比对索引的 doc 数与 hash": {"上游 schema 变更": 0.90, "流量构成变化": 0.85, "检索索引陈旧": 0.05, "模型/配置变更": 0.80},
    "核对 manifest/binding 哈希": {"上游 schema 变更": 0.85, "流量构成变化": 0.90, "检索索引陈旧": 0.85, "模型/配置变更": 0.03},
}
COST = {"校验上游 schema 版本": 3.0, "对比近 24h 的流量构成": 10.0, "比对索引的 doc 数与 hash": 4.0, "核对 manifest/binding 哈希": 1.0}
print("  先验：", "，".join("%s %.2f" % (c, p) for c, p in PRIOR.items()))
print("  %-28s %8s %8s %14s %14s"
      % ("检查", "耗时/分", "先验熵", "期望后验熵", "单位成本增益"))
h0 = entropy(PRIOR)
rank = []
for name, lrs in CHECKS.items():
    exp_h = 0.0
    for outcome in (0, 1):     # 0 = 检查失败（发现异常），1 = 检查通过
        lr = {c: (1.0 - lrs[c]) if outcome == 0 else lrs[c] for c in CAUSES}
        post = update(PRIOR, lr)
        p_fail = sum(PRIOR[c] * lr[c] for c in CAUSES)
        exp_h += (p_fail if outcome == 0 else (1 - p_fail)) * entropy(post)
    gain = (h0 - exp_h) / COST[name]
    rank.append((gain, name, exp_h))
    print("  %-28s %8.1f %8.4f %14.4f %14.4f" % (name, COST[name], h0, exp_h, gain))
rank.sort(reverse=True)
print("  按单位成本信息增益排序：", " > ".join(n for _, n, _ in rank))
print("  -> 最强信号是「核对 manifest 哈希」（KL 最大）且最便宜，所以排第一；")
print("     「对比流量构成」虽然也有信息，但耗时是它的 10 倍，单位成本增益掉到最后")

for true_cause in ("上游 schema 变更", "模型/配置变更"):
    fail_prob = {name: 1.0 - lrs[true_cause] for name, lrs in CHECKS.items()}
    for sname, order in STRATEGIES.items():
        steps, times, hit, miss_post = [], [], 0, []
        for _ in range(4000):

            used, t_used, reached = 0, 0.0, False
            for name in order:
                used += 1
                t_used += COST[name]
                found = rng.random() < fail_prob[name]
                lrs = CHECKS[name]
                lr = {c: (1.0 - lrs[c]) if found else lrs[c] for c in CAUSES}
                post = update(post, lr)
                if post[true_cause] >= TARGET:
                    reached = True
                    break
            steps.append(used)
            times.append(t_used)
            hit += 1 if reached else 0
            if not reached:
                miss_post.append(post[true_cause])
        print("  %-24s %-22s %9.2f %9.4f %10.2f %14.4f"
              % (sname, true_cause, mean(steps), hit / 4000, mean(times),
                 mean(miss_post) if miss_post else 0.0))
print("  -> 真因是「上游 schema 变更」时，字母序恰好把它排在第一位（平均 1.15 步），")
print("     信息增益顺序因为把最便宜的检查排在前面，平均 2.40 步 —— 顺序的好坏依赖真因。")
print("  -> 真因是「模型/配置变更」时，字母序把最强的两个检查都排到了最后，")
print("     平均步数与耗时都明显高于信息增益顺序。这正是「按先验+似然排序」的价值。")
print("  -> 结论不是「某个顺序最好」，而是：清单的顺序必须用「先验 × 似然 / 成本」算出来，")
print("     而且要按真因分层评估（最可能的几个真因各自多久能定位）")

print("[4] 相关性漂移：两个特征的边际都没动，逐特征监控全部静默")
rng = random.Random(2024)

base_x = [rng.gauss(0, 1) for _ in range(N)]
base_y = [0.0 * x + math.sqrt(1 - 0.0 ** 2) * rng.gauss(0, 1) for x in base_x]
new_x = [rng.gauss(0, 1) for _ in range(N)]
new_y = [0.8 * x + math.sqrt(1 - 0.8 ** 2) * rng.gauss(0, 1) for x in new_x]


def pearson(a, b):
    ma, mb = mean(a), mean(b)
    sa = math.sqrt(sum((v - ma) ** 2 for v in a))
    sb = math.sqrt(sum((v - mb) ** 2 for v in b))
    return sum((u - ma) * (v - mb) for u, v in zip(a, b)) / (sa * sb)


def ks_stat(a, b):
    sa, sb = sorted(a), sorted(b)
    i = j = 0
    best = 0.0
    while i < len(sa) or j < len(sb):
        if j >= len(sb) or (i < len(sa) and sa[i] <= sb[j]):
            v = sa[i]
            while i < len(sa) and sa[i] == v:
                i += 1
        else:
            v = sb[j]
            while j < len(sb) and sb[j] == v:
                j += 1
        best = max(best, abs(i / len(sa) - j / len(sb)))
    return best


crit = 1.36 / math.sqrt(N)
print("  构造：相关系数从 %.1f 变成 %.1f，两列的均值与方差都保持不变" % (0.0, 0.8))
print("  逐特征看：x 的 KS = %.4f（临界 %.4f）、y 的 KS = %.4f（临界 %.4f）"
      % (ks_stat(base_x, new_x), crit, ks_stat(base_y, new_y), crit))
print("  逐特征看：x 的均值 %.4f → %.4f、y 的均值 %.4f → %.4f"
      % (mean(base_x), mean(new_x), mean(base_y), mean(new_y)))
r_base, r_new = pearson(base_x, base_y), pearson(new_x, new_y)
z_corr = (r_new - r_base) * math.sqrt(N - 3) / math.sqrt(1 - r_new ** 2)
print("  联合看  ：相关系数 %.4f → %.4f（Fisher z 变换：z = %.1f，p < 1e-10）"
      % (r_base, r_new, z_corr))
print("  -> 两条 KS 都在临界值以下（静默），但相关性从 0.00 涨到 %.2f ——"
      % pearson(new_x, new_y))
print("     任何「逐列看边际」的监控体系都看不见这种漂移，必须留一条联合判据")

  核对 manifest/binding 哈希     正常             0.3878       0.3878       1.1351
  校验上游 schema 版本             异常             0.9220       0.9220       0.3375

     没有这个判据，排查会退化成执行清单；有了它，最贵的那一步常常可以省掉。
     但它也要付代价：当信号弱到后验永远到不了 0.80，就必须有升级人工的出口。

5.4 四处关键设计决策#

  1. 停止阈值 θ=0.80 用"最大后验"而不是"某个指定原因的后验"。理由：排查的输出不是"我认为是 X"，而是"我要开始处置，处置方向是 X"。用最大后验作为判据，等价于"我已经有把握把动作押在这一个原因上"。若用某个固定原因的后验，那排查就变成了"证明我是对的"，会漏掉"其实是另一个原因、只是我一直在查错的方向"这种情况。

  2. 命中率与"未命中后验均值"两列一起看。命中率单独看会误导：一个策略可能命中率高（早停），但它早停的时候后验只有 0.81；另一个策略命中率低（走得远），但没命中时后验也到了 0.49。两列合起来才能判断"这个停止是不是有意义的停止"。实测字母序在"模型/配置变更"下的命中率只有 0.6042、未命中后验均值 0.4863 —— 这就是"走完清单也没查出来"的真实比例。

  3. 分层延迟表格里加"业务"那一行。它不属于四层指标（ch3-l2 的四层是输入/输出/延迟/成本），但它是最慢、也是最终拍板的那一层。把它放进表格，是为了让"为什么不能等业务指标再动手"这个结论有数字支撑：810 分钟与 165 分钟都远超任何合理的 MTTR。

  4. 相关性实验用 Fisher z 变换而不是直接比较相关系数。ρ 的抽样分布在 ∣ρ∣ 接近 1 时严重偏斜（标准误 ≈(1−ρ2)/n−3​），所以在 ρ=0.80 附近直接比较会低估显著性。改用它：

z=artanh(ρ),SE(z)=n−3​1​

于是检验统计量 ztest​=(z1​−z2​)n−3​/1−ρ2​（代码里的写法）。实测 z=87.9，与"两条 KS 都不显著"形成鲜明对照。

  1. 写出你的故障树：选一个你熟悉的告警（比如"检索命中率下降"）。 （a）列出 4 个互斥的原因，给出先验（并说明依据：过去半年各占几次）； （b）为每个原因列出 3 个可检查的信号，写出"该原因成立时这个检查通过的概率"（用区间估计，并标注区间宽度）； （c）算出每个检查的期望后验熵与单位成本信息增益，排出顺序； （d）用这张表回答：在查第一个检查之前，你的最大后验是多少？查完之后最多能到多少？

    （a）对每个变更事件算出"距首次告警的时间差"； （b）用 §一 的检出延迟表判断哪些事件"来不及"产生对应层的信号； （c）给出你会在前 10 分钟内做的三个动作，按顺序； （d）说明如果一个变更事件既可能是原因也可能是症状（比如扩缩容），你会用什么信号区分它们。

小结#

  • 排查的第一条规则是算术不是经验：四层信号的检出延迟 Tdetect​=Tprop​+Twindow​/2+Tdecision​ 差着数量级（实测输入层 schema 检查 1.5 分钟 vs 输出层次日离线指标 810 分钟，差 540 倍）。先读慢的层等于浪费十几个小时：那些信息在 T<810 分钟时根本不存在。
  • 告警时间线必须先和变更事件对齐。"三条告警同一分钟出现"指向共同上游原因；"距首次告警的时间差"能排除"来不及"的变更。这一步成本几分钟、收益是砍掉一半假设。
  • 检查顺序是可算的：故障树（先验 × 似然）→ 期望后验熵 → 单位成本信息增益。实测排序：核对 manifest 哈希（0.6739）> 校验 schema（0.2667）> 比对索引（0.1729）> 对比流量构成（0.0584）。最强信号未必最便宜也未必最贵，而是增益/成本最优的那一个。
  • 没有全局最优的检查顺序，只有按真因分布评估的顺序：真因是"上游 schema 变更"时，字母序恰好平均 1.15 步 / 3.77 分钟（巧合地把最强检查排到了第一）；真因是"模型/配置变更"时字母序要 4.00 步 / 18.00 分钟、命中率仅 0.6042，而信息增益顺序只要 2.25 步 / 5.78 分钟 / 命中率 0.8728。所以要按"最可能的三个真因"分层评估顺序。
  • 停止判据是"最大后验 ≥ θ"，不是"把清单走完"：实测走两步（1 + 3 = 4 分钟）后验到 0.9220，越过 0.80 → 停止排查，剩余检查（4 分钟 + 10 分钟）不必做。θ 由错判代价比决定（θ=C错判​/(R+C错判​)），不是拍的。
  • "未判定"必须是一个合法输出。走完清单仍不达标时，要输出"当前假设排名 + 各自的概率 + 建议扩大故障树"，而不是"没有异常"。否则所有"证据不足"的情况都会被静默归零。
  • 逐特征监控有结构性盲区：实测相关系数从 −0.0244 变成 0.8035（Fisher z=87.9）时，两条 KS 是 0.0210 与 0.0253（临界 0.0215）——一在临界值上下摆动、会被静默。排查清单里必须有一条联合判据，并且"输入正常"这个结论要写明它覆盖到几阶依赖。
  • 似然是从历史事故里估的，不是给的：事故样本极少、检查有假阴性、检查之间不独立（会让贝叶斯连乘过度自信）。所以故障树是排序工具，不是概率真相机 —— 它的输出（先查哪个、查到什么程度可以停）比它的中间量（后验的具体数值）更可靠。
  • 处置动作要回写先验：这次事故是"上游字段单位变了"，下次同类告警时"上游 schema 变更"的先验就该调高。故障树是活的，需要按季度复算 —— 否则半年后它的排序会因为先验过期而失效。

本章到此结束：第 1 节把"漂移"拆成可分别检验的断言（数据 / 概念 / 标签），给出两条带标准误的判据；第 2 节把监控做成四层指标表，并给每个指标配上样本量与不确定度（n≥1/(pρ2)、n≥3/p、p99 的区间宽 22.9%）；第 3 节把阈值写成代价模型的最小值点（τ∗ 恰好压在 SLO 折点上，误报率 8.21×10−2）；第 4 节把告警之后的排查写成故障树 + 贝叶斯更新，给出"4 分钟停止排查"的判据。四条线合起来是一句话：监控的价值 = 它最早说出的那句话的准确性 − 它让人付出的注意力成本；而这句话里的每一个量（判据的判定阈值、指标的 λ、告警的 α 与 E[D]、检查的单位成本增益）都必须能被测量，或者被明确假设。
