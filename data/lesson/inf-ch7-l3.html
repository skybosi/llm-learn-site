SLA 与成本优化#

这是本课程的最后一课。前面我们把"算得快、装得下、扛得住、看得见"都走了一遍，最后要回答两个工程里最现实的问题：怎么向用户承诺服务质量（SLA），以及怎么在满足承诺的前提下把每一分钱花得值（成本优化）。两者本质是一对张力——延迟越好通常越贵，越省通常越慢。这一课教你量化这组张力，并给出可落地的优化清单。

一、概念讲解#

1. SLA / SLO / SLI：三个容易混淆的概念#

  • SLI（Service Level Indicator，指标）：可度量的服务质量数值，如"P99 TTFT = 2.3s""可用性 = 99.95%"；
  • SLO（Service Level Objective，目标）：内部给自己定的达标线，如"P99 TTFT ≤ 3s""月度可用性 ≥ 99.9%"；
  • SLA（Service Level Agreement，协议）：对外部客户的正式承诺，通常比 SLO 更宽松（留安全边际），违约要赔钱。

一条经验：SLO 要比 SLA 更严，SLA 要比 SLO 更松，中间留出缓冲。SLO 一旦设下，就要用上一课的监控去盯，并设告警与错误预算（error budget）——把"允许违反 SLO 的时间"量化成一个预算，快用光时就暂停发布新功能、先修稳定性。

2. 延迟目标该怎么设#

LLM 服务最常见的 SLA 指标是延迟分位数：

  • P50：一半请求的体验，看整体水平；
  • P99：最差 1% 用户的体验，是承诺的重点；
  • TTFT：用户开始看到回复的时间，最影响体感；
  • TPOT：生成速度，影响"读起来顺不顺"。

承诺时通常写"P99 TTFT ≤ X 秒、P99 TPOT ≤ Y 毫秒、可用性 ≥ Z%"。注意：平均值是最有欺骗性的指标——平均 TTFT 好看，但 P99 可能已经烂到用户投诉。所以 SLA 一定要落在分位数上。

3. 成本从哪来，怎么算#

推理成本的构成几乎就是GPU 时间。核心公式：

单位成本 = GPU 小时单价 × 服务时长 × GPU 数 / 服务期间总产出 token 数

反过来，单位算力产出（token/美元 或 token/GPU-小时）是衡量成本效率的关键。提升它的手段，其实正是前六章的全部内容，汇总成一个"省成本清单"：

  • 量化（第 4 章）：INT8/INT4 让同一张卡装更大的模型、跑更大的批；
  • PagedAttention + 更大批（第 2 章）：提高 GPU 利用率；
  • 张量/流水线并行（第 5 章）：让大模型能落地、平衡负载；
  • FlashAttention（第 6 章）：长序列预填充又快又省显存；
  • 投机解码（第 6 章）：decode 一次前向多出 token；
  • 前缀缓存（第 6 章）：重复前缀少算。

除了"单实例更高效"，还有供给侧的省钱：

  • 自动扩缩容（autoscaling）：按流量动态加减副本，闲时缩到 0，忙时弹上去，避免为峰值长期买单；
  • 抢占式/竞价实例（spot）：用便宜的算力跑可中断的离线/批处理任务；
  • 混合路由：简单请求走小模型，难请求才走大模型（模型分级），把昂贵的 GPU 用在刀刃上。

4. 延迟与吞吐/成本的权衡#

省成本最常见的代价是延迟：批越大吞吐越高、单位成本越低，但单个请求等待批次凑满的时间也越长；抢占式实例便宜，但可能随时被回收导致延迟尖峰。因此成本优化的边界是 SLO——在"仍能满足 P99 延迟"的前提下尽量省钱。真正的高手不是"最便宜"，而是"用最低成本守住承诺"。这需要容量规划：根据流量峰值、单实例吞吐、SLO 反推需要多少副本，再决定常驻多少、弹性多少。

二、可运行代码示例#

示例 1：算一笔推理成本账#

下面脚本根据 GPU 单价、副本数、吞吐，算出"单位 token 成本"，并演示扩大批量如何摊薄成本（但提醒延迟代价）：

# 参数（示例数值，替换成你的实际账单）
gpu_hour_price = 3.5        # 单卡每小时单价（美元）
num_gpus = 4                # 副本用的卡数
uptime_hours = 720          # 一个月运行小时数

# 两种配置下的吞吐（tokens/s）
configs = {
    "小批量(latency优先)": 500,   # 批量小，延迟低但吞吐低
    "大批量(throughput优先)": 1800, # 批量大，吞吐高但单请求等待长
}

for name, tokens_per_sec in configs.items():
    total_cost = gpu_hour_price * num_gpus * uptime_hours
    total_tokens = tokens_per_sec * 3600 * uptime_hours
    cost_per_million = total_cost / (total_tokens / 1e6)
    print(f"{name}: 月成本 ${total_cost:.0f}, "
          f"月产出 {total_tokens/1e9:.1f}B token, "
          f"每百万 token ${cost_per_million:.3f}")

你会看到大批量把每百万 token 成本压到了小批量的约 1/3——但这部分"省下的钱"是用更高的单请求排队延迟换来的。所以下一步必须把它和 SLO 放在一起看。

示例 2：用延迟分位数检查是否守住 SLO#

下面采集一批请求的 TTFT，算出 P50/P99，判断是否违反承诺，体现"SLA 落在分位数上"：

import random
import statistics

# 模拟 1000 个请求的 TTFT（秒）：多数很快，少量长尾
random.seed(0)
ttft = [random.expovariate(1/0.8) for _ in range(1000)]   # 大部分 ~0.8s
ttft += [4.5, 5.0, 6.2, 7.0]                              # 长尾尖峰

ttft.sort()
def percentile(data, p):
    idx = int(len(data) * p)          # 近似分位数（真实场景用直方图更准）
    return data[min(idx, len(data)-1)]

slo_p99 = 3.0      # 承诺：P99 TTFT ≤ 3s
p50 = percentile(ttft, 0.50)
p99 = percentile(ttft, 0.99)
print(f"平均 TTFT {statistics.mean(ttft):.2f}s（看似很健康）")
print(f"P50 = {p50:.2f}s, P99 = {p99:.2f}s")
print("SLO 达标" if p99 <= slo_p99 else f"SLO 违反：P99 超出 {slo_p99}s")

注意平均 TTFT 只有约 0.8s、看起来很健康，但 P99 已远超 3s 承诺——这正是"看平均值会被骗"的直观教训：长尾请求决定用户口碑，SLA 必须盯分位数。

三、练习#

  1. 把示例 1 的参数换成你所在云平台的真实 GPU 单价，估算一个 7B 模型服务在"峰值流量下"的月成本，并对比量化前后（吞吐变化）的成本差。
  2. 修改示例 2，加入 temperature 变化导致的长尾，分别用平均值、P50、P99、P99.9 评估，说明为什么高可用服务要盯 P99.9。
  3. 为一个"日活 10 万、人均 3 次请求、每次 200 token 输出"的产品做容量规划：给定单实例吞吐与 P99 SLO，计算常驻副本数与弹性副本数。
  4. 综合本课程所学，写一份"降本清单"：针对一个正在跑的服务，列出可选的量化/批处理/投机解码/前缀缓存/扩缩容手段，并标注每项对延迟、吞吐、成本、风险的影响。
