图执行与运行时：内存池、CUDA Graphs、执行顺序#

一个编译得很漂亮的 kernel，可能因为"下发它的那几微秒"而白干：decode 阶段每次推理只算 33 MFLOP，而每个算子都要宿主侧调用一次驱动——算得少、等得多。落地之后，决定每次推理耗时的是三件运行时的事：按什么顺序走表、中间张量放在哪、下发本身要花多少。本课把执行器、内存池与 CUDA Graphs 拆开讲，并用纯 Python 模型把三类开销分别打印出来。

一、概念讲解#

1. 编译产物只是一张表和一组函数#

运行时（runtime）负责加载编译产物、分配内存、按下发顺序调用 kernel；执行器（executor）是运行时里"走表"的部分；执行计划（execution plan，也叫算子表）是有序的 (kernel 入口, 输入槽, 输出槽) 列表。TVM 说得最直白：编译产物的单位是 Module，用户从中取函数（PackedFunc）来调，并缓存首次取到的句柄；官方把运行时核心刻意做小，约 200K–600K 字节，取决于是否带上 CUDA 之类的 driver 模块——这正是端侧部署的硬约束（第 2 课展开）。走表方式决定开销从哪来：

执行器 顺序由谁决定 主要开销来源
逐算子解释（eager） 宿主语言逐行调用 每次调用都要查表 + 下发
图执行器（graph executor） 编译期排好表，运行期循环 每次仍要下发一次 kernel
图回放（CUDA Graphs） 驱动抓一次，之后整段重放 一次 replay 摊掉 N 次下发

2. 执行顺序：拓扑序不唯一，这是运行时的自由度#

第 3 课已确定"图是 DAG"，直接推论是拓扑序不唯一：只要每条边都指向下游，任何顺序都合法。代码第 1 节给出两条完全不同的执行顺序，数值结果逐元素一致。自由度是优化空间，也把三件事交给运行时：排对同一 buffer 的写后读、决定哪些节点能并到不同流并发、在哪里插同步点。顺序还决定内存峰值——早释放的张量能让后续分配复用地址，所以"顺序"与"内存池"是一体两面。

3. 内存池：把地址在计划期就定死#

按需分配（一个张量一次 cudaMalloc）有三个代价：分配器调用是宿主侧串行点、显存碎片化、地址每次都可能不同——最后一条直接否掉图回放（它要求地址固定）。所以运行时普遍用内存池：编译期算好生命周期区间与复用关系（第 4 课的静态内存规划），执行期只从池里切块，按 256~512 字节对齐。TVM 用统一静态内存规划把这件事落在编译器侧，PyTorch 对应 caching allocator，capture 时切成图私有池。

代码第 2 节把池跑了一遍：激活区 6.0 MiB → 2.0 MiB（降 66.7%），全图峰值只降 2.2%——因为 128 MiB 权重完全主导。报"峰值降了多少"必须说清是哪一块，否则数字既不可比也不可复现。

4. CUDA Graphs：把 N 次下发压成 1 次#

CUDA Graph 的做法是捕获（capture）一段已在旁路流上执行过的 kernel 序列，实例化成一张图，之后每次推理只做一次回放（replay）。约束全来自"图里的东西必须静态"：地址、形状静态，捕获期间不得分配显存与做 CPU 同步、不得有依赖数据的动态控制流；要变的输入必须 copy_ 进固定缓冲。PyTorch 封装为 torch.cuda.CUDAGraph 与 torch.cuda.graphs.graph_pool_handle()（私有池），torch.compile(mode="reduce-overhead") 就是把生成的 kernel 段交给它。

关键是什么时候才值：代码第 3 节（参数为假设模型参数）里 decode 单 token 回放快 5.12 倍，prefill 512 token 只剩 1.12 倍——回放省的是固定 host 开销，算得越多它占比越小。

5. 常见坑#

  • 换输入就换张量对象：地址一变图就失效，要往捕获时的静态缓冲拷数据。
  • 捕获期间分配：必须走图私有内存池，否则捕获失败或回放越界。
  • 动态形状：guard 失败要重编译并重建图，第 2 课的冷启动代价会再付一次。
  • 池与回放叠加：池地址固定是回放的前提，但池的重用策略一变，旧图就得重捕。
  • 对齐想当然：池按 512 字节切块，个别 kernel 的对齐要求更大，跨块共享 buffer 会踩到。

二、可运行代码示例#

下面这段纯 Python（无第三方依赖）实现三件事：两种合法拓扑序、按生命周期复用的内存池（含对齐与空洞合并）、eager 与 graph replay 的时间分解。硬件常量都写成显式假设的模型参数并打印，避免与实测混淆。

# ---- 第 1 课示例：纯 Python 模拟"运行时 = 执行器 + 内存池 + 图回放" ----
# 无 GPU、无第三方依赖。下面所有硬件参数都是**显式假设的模型参数**，不是任何真实设备的实测值。
ALIGN      = 512        # 池内块对齐字节数（分配器普遍按 256~512 B 对齐）
LAUNCH_US  = 3.0        # 假设：一次 kernel 下发的 host 侧开销（模型参数）
REPLAY_US  = 5.0        # 假设：一次 graph replay 的固定开销（模型参数）
PEAK_TFLOP = 100.0      # 假设：峰值算力 100 TFLOP/s（模型参数）
F32        = 4

def T(name, shape, resident=False):
    n = 1
    for d in shape: n *= d
    return {'name': name, 'bytes': n * F32, 'resident': resident}

# 图 = 节点表（沿用第 3/4 课的表示）：(op, deps, out)。表顺序只是"可读"，不是执行顺序。
# resident=True 表示常驻张量（权重/输入缓冲），激活张量由内存池按生命周期复用。
def build_graph():
    return [
        ('input', [],           T('x',  (64, 4096), True)),
        ('param', [],           T('W1', (4096, 4096), True)),
        ('param', [],           T('b1', (4096,), True)),
        ('mm',    ['x', 'W1'],  T('y1', (64, 4096))),
        ('add',   ['y1', 'b1'], T('y2', (64, 4096))),
        ('relu',  ['y2'],       T('y3', (64, 4096))),
        ('param', [],           T('W2', (4096, 4096), True)),
        ('mm',    ['y3', 'W2'], T('y4', (64, 4096))),
        ('add',   ['y4', 'b1'], T('out', (64, 4096))),
        ('relu',  ['y2'],       T('aux', (64, 4096))),   # 分支：与主链独立的辅助输出
    ]

def topo(nodes, key=None):
    """拓扑序：依赖先于使用者；key 让"同层可交换"显式化，从而暴露顺序自由度。"""
    idx = {n[2]['name']: i for i, n in enumerate(nodes)}
    done, out, pending = set(), [], list(nodes)
    while pending:
        ready = [n for n in pending if all(d in done for d in n[1])]
        if not ready: raise ValueError('图里有环')
        ready.sort(key=key or (lambda n: idx[n[2]['name']]))
        n = ready[0]; pending.remove(n); done.add(n[2]['name']); out.append(n)
    return out

def last_use(order):
    """每个张量"最后一次被读"在第几步 —— 内存池据此决定何时回收。"""
    lu = {}
    for i, (op, deps, out) in enumerate(order):
        for d in deps: lu[d] = i
    return lu

class Pool:
    """按对齐切块的内存池：free 后合并相邻空洞；地址一旦分配就不再移动。"""
    def __init__(self, align): self.align, self.blocks, self.high = align, [], 0
    def alloc(self, size):
        size = -(-size // self.align) * self.align
        for i, (off, sz) in enumerate(self.blocks):
            if sz >= size:
                if sz == size: self.blocks.pop(i)
                else: self.blocks[i] = (off + size, sz - size)
                return off, size
        off = self.high; self.high += size
        return off, size
    def free(self, off, size):
        self.blocks.append((off, size)); self.blocks.sort()
        merged = []
        for off, sz in self.blocks:
            if merged and merged[-1][0] + merged[-1][1] == off:
                merged[-1] = (merged[-1][0], merged[-1][1] + sz)
            else: merged.append((off, sz))
        self.blocks = merged

def run_with_pool(nodes, order):
    lu, pool, live, log = last_use(order), Pool(ALIGN), {}, []
    for i, (op, deps, out) in enumerate(order):
        nm, sz, off = out['name'], out['bytes'], 0
        off, got = pool.alloc(sz)
        log.append((nm, i, off, got, '常驻' if out['resident'] else '激活'))
        if not out['resident']:
            live[nm] = (off, got)
        for d in deps:                       # 依赖读完之后立即回收
            if d in live and lu.get(d) == i: pool.free(*live.pop(d))
    return pool.high, log

def naive_bytes(items):
    return sum(-(-t['bytes'] // ALIGN) * ALIGN for t in items)

if __name__ == '__main__':
    g = build_graph()
    print('=== 1. 两种合法执行顺序（拓扑序不唯一）===')
    o1 = topo(g)
    o2 = topo(g, key=lambda n: -list(x[2]['name'] for x in g).index(n[2]['name']))
    print('  顺序 A（表序）:', ' → '.join(n[2]['name'] for n in o1))
    print('  顺序 B（部分逆序）:', ' → '.join(n[2]['name'] for n in o2))
    print(f'  依赖全部满足，两个结果都对：顺序自由度 = {[n[2]["name"] for n in o1] != [n[2]["name"] for n in o2]}')

    order = o1
    print(f'\n=== 2. 内存池分配（对齐 {ALIGN} B；块在最后一次使用后立刻回收）===')
    peak, log = run_with_pool(g, order)
    for nm, i, off, sz, kind in log:
        print(f'  step{i:>2}  {nm:<4} {kind}  offset={off:>10}  size={sz:>10} B')
    act = [n[2] for n in g if not n[2]['resident']]
    na_act = naive_bytes(act)
    pk_act = 0                                   # 激活区峰值 = 池里同时活着的最多字节
    live, lu, cur = {}, last_use(order), 0
    for i, (op, deps, out) in enumerate(order):
        if not out['resident']:
            live[out['name']] = out['bytes']; cur += -(-out['bytes'] // ALIGN) * ALIGN
        for d in deps:
            if d in live and lu.get(d) == i: cur -= -(-live.pop(d) // ALIGN) * ALIGN
        pk_act = max(pk_act, cur)
    allt = [n[2] for n in g]
    print(f'\n  激活区：朴素 {na_act} B（{na_act/2**20:.1f} MiB）→ 池化峰值 {pk_act} B（{pk_act/2**20:.1f} MiB）'
          f'  降 {(1-pk_act/na_act)*100:.1f}%')
    print(f'  全图  ：朴素 {naive_bytes(allt)} B（{naive_bytes(allt)/2**20:.1f} MiB）→ 池化 {peak} B（{peak/2**20:.1f} MiB）'
          f'  降 {(1-peak/naive_bytes(allt))*100:.1f}%')
    print('  注意：总峰值被 128 MiB 权重主导，池真正优化的是激活区 —— 报"峰值降了多少"必须说清是哪一块')

    print('\n=== 3. 一次推理的时间分解：图回放什么时候才值（全部为假设模型参数）===')
    print(f'  假设：单次下发 {LAUNCH_US} µs，一次 replay {REPLAY_US} µs，峰值 {PEAK_TFLOP:.0f} TFLOP/s，算子数固定为 9')
    print(f'  {"场景":<22}{"FLOPs":>14}{"纯计算":>10}{"eager":>10}{"replay":>10}{"加速比":>9}')
    cases = [('decode 单 token', 2*1*4096*4096), ('小 batch 推理(8)', 2*8*4096*4096),
             ('prefill 512 token', 2*512*4096*4096), ('训练型 batch=64', 2*64*4096*4096)]
    for name, fl in cases:
        comp = fl / (PEAK_TFLOP*1e12) * 1e6
        ea, gr = comp + 9*LAUNCH_US, comp + REPLAY_US
        print(f'  {name:<22}{fl:>14,}{comp:>9.2f}µ{ea:>9.2f}µ{gr:>9.2f}µ{ea/gr:>8.2f}x')
    print('  读法：算得越少，host 侧下发越像瓶颈 → 回放收益越大；计算量上去后两者收敛')

    print('\n=== 4. 正确性：两条执行顺序必须算出同一结果（小张量实算）===')
    import random
    rnd = random.Random(0)
    env = {'x': [rnd.uniform(-1, 1) for _ in range(4)], 'W1': [rnd.uniform(-1, 1) for _ in range(4)],
           'b1': [0.5, -0.5], 'W2': [rnd.uniform(-1, 1) for _ in range(8)]}
    def mm2(a, b, m, n, k):
        return [sum(a[i*k+t]*b[t*n+j] for t in range(k)) for i in range(m) for j in range(n)]
    def exec_order(env, order):
        e = dict(env)
        for op, deps, out in order:
            nm = out['name']
            if op in ('input', 'param'): continue
            if op == 'mm':   e[nm] = mm2(e[deps[0]], e[deps[1]], 2, 2, 2) if len(e[deps[0]]) == 4 else mm2(e[deps[0]], e[deps[1]], 2, 4, 2)
            elif op == 'add': e[nm] = [u + v for u, v in zip(e[deps[0]], [0.5, -0.5]*2)]
            elif op == 'relu': e[nm] = [max(u, 0.0) for u in e[deps[0]]]
        return e
    ra, rb = exec_order(env, o1), exec_order(env, o2)
    print('  顺序 A out:', [round(v, 6) for v in ra['out']])
    print('  顺序 B out:', [round(v, 6) for v in rb['out']])
    print('  逐元素一致:', all(ra[k] == rb[k] for k in ('y1','y2','y3','y4','out','aux')))

  顺序 B（部分逆序）: W2 → b1 → W1 → x → y1 → y2 → aux → y3 → y4 → out
  依赖全部满足，两个结果都对：顺序自由度 = True

=== 3. 一次推理的时间分解：图回放什么时候才值（全部为假设模型参数）===
  假设：单次下发 3.0 µs，一次 replay 5.0 µs，峰值 100 TFLOP/s，算子数固定为 9
  场景                             FLOPs       纯计算     eager    replay      加速比
  decode 单 token            33,554,432     0.34µ    27.34µ     5.34µ    5.12x
  小 batch 推理(8)            268,435,456     2.68µ    29.68µ     7.68µ    3.86x
  prefill 512 token     17,179,869,184   171.80µ   198.80µ   176.80µ    1.12x
  训练型 batch=64           2,147,483,648    21.47µ    48.47µ    26.47µ    1.83x
  读法：算得越少，host 侧下发越像瓶颈 → 回放收益越大；计算量上去后两者收敛

=== 4. 正确性：两条执行顺序必须算出同一结果（小张量实算）===
  顺序 A out: [0.462164, -0.365194, 0.489574, -0.462855]
  顺序 B out: [0.462164, -0.365194, 0.489574, -0.462855]
  逐元素一致: True

四处可核对结论：顺序自由度是真实的（两条不同顺序输出逐元素一致，这是运行时能重排的依据）；池只优化激活区（6.0→2.0 MiB），内存结论必须带口径；回放收益与计算量成反比（5.12x vs 1.12x），选它是看阶段不是看名气；地址固定才可回放，复用策略一变旧图就得重捕。

三、练习#

  1. 实现：给 Pool 加"保留余量"参数（每块向上取整到 1 MiB，模拟整块预留），重跑第 2 节，看激活区与总峰值各变多少，解释总峰值为何几乎不动。
  2. 解释：第 3 节把算子数固定为 9。若融合（第 5 章）把它降到 4，四个场景的回放收益会怎么变？用代码验算，并说明"融合"与"图回放"是互补还是替代。
  3. 对比/验证：把 topo 的排序键改成"输出字节数从大到小"，看池化峰值是否变化——这暴露"执行顺序"与"内存峰值"的哪种依赖？
  4. 思考：CUDA Graph 要求"地址与形状静态"。若 batch 大小随请求波动（服务端常态），有哪些可行设计？提示：列出"按 bucket 捕获多张图"与"回放 + 动态形状重编"两条路的代价。
