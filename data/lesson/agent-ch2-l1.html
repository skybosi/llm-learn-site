循环的基本形态：感知 → 决策 → 行动 → 反思#

这一节要解决什么#

第 1 章说 Agent 是"闭环系统"，但闭环有形态上的差别。同样是循环，写成四段式（感知 → 决策 → 行动 → 反思）和写成一句 while not done: act()，在能力、可靠性和可调试性上是三件不同的东西。

这一节把循环拆开，逐个说清四段的职责、输入输出、以及各自的失败模式。然后处理一个被严重低估的设计选择：这个循环由什么驱动？ 轮询（polling）还是事件（event-driven）—— 这不是代码风格问题，它决定了 Agent 能不能做"长时间等待"和"与外部世界并发"的任务。

学完这一节你应该能回答：

  • 四段式里的"反思"段，什么时候该有、什么时候是纯浪费甚至有害？
  • 为什么"感知"段是 Agent 里最被低估、最容易出错的环节？（提示：第 1 章的 p感知​）
  • 轮询循环和事件驱动循环，各自在什么任务上会失败？
  • 循环的"一拍"（tick）里，哪些工作必须在模型之外完成？

一、四段式的每一段到底在做什么#

        ┌───────────────────────────────────────────────┐
        │                                               │
        ▼                                               │
  ① 感知 Perceive                                        │
     把环境/工具结果 → 模型可读的输入                     │
     （选择、结构化、截断、脱敏、附上新鲜度）              │
        │                                               │
        ▼                                               │
  ② 决策 Decide                                          │
     模型：下一步做什么（唯一的模型环节）                  │
        │                                               │
        ▼                                               │
  ③ 行动 Act                                             │
     校验 → 授权 → 执行 → 回填（第 3 章）                 │
        │                                               │
        ▼                                               │
  ④ 反思 Reflect                                         │
     评估"刚才这一步对目标有进展吗" → 更新计划/终止判断    │
        │                                               │
        └───────────────────────────────────────────────┘

读这张图的关键：四段里只有 ② 是模型。①③④ 都是工程代码 —— 但它们的质量决定了模型的输入质量和输出的去向。这是第 1 章"能力上限由两侧工程决定"的具体化。

① 感知：不是"把结果拼进 prompt"#

"感知"这个词容易让人以为是自动的。实际上它是一个设计决策密集的环节，每一个决策都在权衡"信息量 vs 噪音"：

感知环节的决策 选项 不做的后果
选择（selection） 全部结果 / top-k / 按字段过滤 / 按相关性排序 上下文被无关内容填满 → 注意力稀释（第 1 章 pdecide​ 下降）
结构化（structuring） 原始文本 / 结构化 KV / 表格 模型要花步数解析格式 → 抬高 n 且引入解析错误
截断（truncation） 头部截断 / 尾部截断 / 摘要 / 分页 截断掉关键字段而模型不知道被截断了（静默错误！）
标注新鲜度 是否附上"这是第几步的数据" 模型把旧数据当新数据用于决策（经典 bug）
脱敏 是否过滤 PII / 密钥 合规问题；且把敏感内容写进轨迹（第 1 章 L2 的取舍）

这里最危险的是截断：它是静默的。模型看到一份被腰斩的日志，会理所当然地按不完整的信息决策，而它不知道自己看到的是不完整的。修法只有一条：

截断必须显式标注 —— 不是 "…"，而是
[已截断：原 12,340 字符，此处显示前 4,000 字符；缺失部分可能含错误详情]

这条规则值得当成硬规范：任何"模型看见的内容"与"真实内容"不一致的地方，都必须在输入里显式声明差异。因为模型没有能力察觉"我看到的不是全部"。

另一个设计决策：感知要不要做"差分"？ 在长循环里，每步都把完整环境状态塞回去是昂贵的（成本线性上升 + 注意力稀释）。更好的做法是送增量：

全量：{ "files": [...50 个文件...], "last_result": ... }     ← 每步都一样，浪费
差分：{ "changed": ["a.py", "b.py"], "deleted": [], "last_result": ... }

差分的代价是：你必须在自己的代码里维护"上一拍的环境快照"（这属于第 4 章的状态管理）。所以这是一处典型的耦合：感知段的优化要求状态管理支持快照对比。

② 决策：输入是"状态视图"，不是"历史"#

第 1 章强调过：状态（收缩）与轨迹（扩张）分开。在循环里，这条规则落成一句话：

decide( state_view )     ← 只给"现在是什么情况"
trace.append( ... )      ← 完整历史只进日志，不进决策输入

把全部历史喂给决策，会同时恶化三个指标：成本（token 线性上升）、pdecide​（无关内容稀释注意力）、可复现性（输入越大，微小变化的影响越不可控）。

一个可操作的判据：如果你的 decide() 里出现了"把最近 N 轮原始消息直接拼接"，那说明你还没有"状态视图" —— 你有一个历史缓冲区，并且把它误称为状态。

③ 行动：循环里最需要"不像代码"的代码#

行动段的核心不是"调用"而是网关（第 3 章整章展开）。在循环的语境里只需强调一件事：行动段必须能返回"结构性结果"，而不是抛异常。

✗ 抛异常     → 循环崩掉，或者异常穿透到最外层被吞掉
✗ 返 bool    → 模型只知道"失败了"，不知道改什么
✓ 返结构化   → { ok: false, kind: "bad_param", field: "date", hint: "ISO-8601" }

这个设计的意义在循环层面才显现：只有结构化的行动结果，才能让 ④ 反思段做事。如果行动只返回 bool，反思段无从判断"这次失败是策略问题还是参数问题"，于是它只能输出"再试一次" —— 这就是盲目重试的机制来源。

④ 反思：最需要条件才能存在的一段#

反思段是四段里争议最大的。它的直觉很吸引人："让模型看看刚才做得怎么样，然后改进。" 但第 1 章的机制二已经给出了警告：自评 s^ 有系统偏差，会形成局部最优吸引子。

所以反思段的正确设计问题是：在什么条件下反思的收益 > 0？ 三个必要条件：

(a) 判据来自外部。 反思必须基于可验证的信号（测试通过/失败、断言结果、工具错误码、另一个独立评审器的输出），而不是"你觉得呢"。有外部信号时，反思段实际上是一个基于真实反馈的重新规划，它很有价值；没有外部信号时，它退化成自我安慰式的改写。

(b) 反思要能改变后续行为。 如果反思的输出只是"我下次要更小心"，那它没有任何信息量。有效的反思输出必须是可执行的状态变更：

✗ {"reflection": "我应该更仔细地检查文件路径"}         ← 无法执行
✓ {"plan_update": {"drop": ["step3"], "insert": ["verify:path_exists"]}}
✓ {"state_update": {"known_bad_paths": ["/tmp/x"]}}   ← 缩小搜索空间

(c) 反思的频率要远低于行动的频率。 每步都反思是纯浪费：它把成本乘以 2，而收益在单步尺度上几乎为零（单步的信息量不足以支持一个统计学上可靠的判断）。合理的频率是按事件触发：一次失败之后、一个子目标完成之后、或者每 k 步（k 通常 3~10）。

反思时机 收益 成本 何时该用
每一步后 极低（信息不足） 每次都多一次模型调用 几乎不用
每 k 步 中（能发现停滞） 1/k 的额外调用 长任务、无自然检查点
失败后 高（有针对性的反馈） 只在失败时付 默认选择
子目标完成后 高（及时纠偏） 按子目标数 有明确分解的任务

⚠️ 一个反直觉但要记住的结论：反思是"止损"手段，不是"增值"手段。 它擅长的是"发现走错了、尽快换路"，而不是"让正确的路走得更好"。把反思当成质量提升手段（"让它自我改进一下"）几乎总是失望的 —— 因为质量提升需要的是更好的判据或更好的工具，而不是更多的自我审视。

二、循环由什么驱动：轮询 vs 事件#

这是一个被低估的架构选择。两种形态：

形态 A：轮询式（要我做，我做完就停）

while not done:
    result = act(decide(state))
    state = perceive(result)

形态 B：事件驱动（有事发生，我处理）

on event(e):
    result = act(decide(state, e))       # 事件本身是感知输入的一部分

差异不在语法，在三个能力上：

能力 轮询式 事件驱动 说明
等待外部世界 只能忙等或阻塞睡眠 天然支持（无事可做时不消耗） 等审批、等部署、等回信
并发处理多源输入 难（单线程推进一条轨迹） 天然（多个事件队列） 多个用户、多个数据源
被中断与抢占 难（中断点要自己埋） 天然（事件之间就是安全点） 需要人工介入时
可预测性 高（一条主线，易推理） 低（交错顺序不确定） 调试与复现
成本 可能空转（浪费调用） 空闲时不花钱 长周期任务差别巨大

关键设计决策：任务的"时间尺度"决定驱动方式。

秒级任务（一次问答、一次修复）        → 轮询式：简单、可预测、易测试
分钟级任务（一次调研、一次部署）      → 轮询式 + 显式等待（把等待变成一步）
小时/天级任务（监控、审批流、订阅）    → 事件驱动：否则你在为"什么都没发生"付费

最容易犯的错：用轮询式实现长周期任务，于是循环里出现"每 30 秒查一次状态"的步骤。这有三个后果：成本按时间线性增长（其中 99% 是无用调用）、n 被大量空转步数撑大（第 1 章的 pn 惩罚）、而且终止条件变得难以定义（"还没好"和"永远不会好"看起来一样）。

正确的"等待"设计：把等待变成一个显式的一步，而不是循环里的空转：

✗ 每步都问"好了吗？"            → n 膨胀，成本线性
✓ 决策输出 {"kind": "wait", "until": "...", "on": "webhook:deploy_done"}
                                 → 循环挂起，事件到达时恢复，n 不增长

注意这带来一个要求："等待"必须进入状态（记住在等什么、等多久、超时怎么办）。否则超时之后 Agent 会忘记自己在等 —— 这是长周期 Agent 最典型的 bug。

混合形态：外层事件驱动 + 内层轮询#

实践中绝大多数可用的 Agent 是混合的：

外层（事件驱动）：收到任务 → 唤醒一条会话；收到审批结果 → 唤醒
内层（轮询式）：  会话内部用 while 循环推进，直到 done / blocked / need_approval

"blocked / need_approval" 是内层向外层的出口 —— 这也是"暂停等人工"的标准实现方式：内层遇到需要授权或无法自行解决的步骤时不阻塞，而是持久化状态并退出，把控制权交回外层。事件到达后从状态恢复续跑。

这个模式同时解决了第 1 章"可回滚"和"可观测"的一部分要求：能挂起就能在挂起点上做检查、做审批、做快照。

三、循环的"一拍"里不能有的东西#

反向列一下：哪些工作必须在模型之外、且必须每拍都做一遍。这是循环设计的检查清单：

✓ 预算检查（执行前！）—— 否则钱已经花掉（第 1 章 2.5）
✓ 硬约束检查（每一步）—— 拦住漂移，不允许"跑完再看"（第 1 章 3.4）
✓ 幂等键生成与登记 —— 每次有副作用的行动（第 3 章）
✓ 轨迹写入 —— 至少 L1；失败路径也要写（第 4 节）
✓ 上下文裁剪决策 —— 不是每拍都裁，但要每拍检查是否该裁（第 4 章）
✗ 不该有：让模型判断"预算还剩多少"     → 它算不准，且这会成为可被操纵的信号
✗ 不该有：让模型决定"要不要记录这一步"  → 审计不能由被审计者决定
✗ 不该有：把异常直接抛给模型（原始栈）  → 既不必要也不安全（第 3 章 3）

一句话原则：循环的骨架是代码，模型只在骨架的一个格子里工作。 循环里所有"是否继续/是否记录/是否越界"的判断，必须在模型之外。

四、四段式的取舍总表#

设计点 选择 A 选择 B 判据
感知：全量 vs 差分 全量（简单、无状态耦合） 差分（省 token、需维护快照） 状态是否已支持快照 + 环境变化率是否低
感知：截断策略 硬截断 + 显式标注（可预测） 摘要（信息密度高） 关键是必须标注；摘要会失真
决策：状态视图 vs 全历史 状态视图（可控成本、可复现） 全历史（信息最全） 状态视图几乎总是对的；全历史是新手默认
反思：每步 vs 事件触发 每步（实现简单） 事件触发（成本低、收益集中） 默认事件触发；每步反思是浪费
循环：轮询 vs 事件 轮询（可预测、易测） 事件（支持等待与并发） 任务时间尺度决定
等待：空转 vs 显式挂起 空转（实现容易） 挂起（成本低、n 不膨胀） 等待时长 > 数秒就该挂起

代码：四段式循环 + 显式挂起#

from dataclasses import dataclass, field
from typing import Any, Optional
import time

@dataclass
class LoopState:
    """
    循环的持久状态。★ 设计决策：这个对象必须可序列化 ——
    因为'挂起等事件'要求状态能落盘，'可重放'要求它能被恢复（第 4 节 L3）。
    """
    goal: str
    step: int = 0
    env_snapshot: dict = field(default_factory=dict)   # 用于感知差分
    waiting_for: Optional[str] = None                  # 在等哪个事件（★ 必须进状态）
    wait_deadline: Optional[float] = None
    known_bad: list = field(default_factory=list)      # 反思段的产出：缩小搜索空间
    plan: list = field(default_factory=list)

    def to_dict(self) -> dict:
        return {"goal": self.goal, "step": self.step,
                "env_snapshot": self.env_snapshot,
                "waiting_for": self.waiting_for,
                "wait_deadline": self.wait_deadline,
                "known_bad": self.known_bad, "plan": self.plan}

class Suspend(Exception):
    """内层向外层的出口：需要等待/审批时不阻塞，而是持久化并退出。"""
    def __init__(self, reason: str, event: str): 
        self.reason, self.event = reason, event

# ---------- ① 感知 ----------
def perceive(state: LoopState, env) -> dict:
    """
    环境 → 模型可读的状态视图。
    设计决策 1：只送差分（省 token、抗注意力稀释）。
    设计决策 2：截断必须显式标注 —— 模型无法察觉'我看到的不全'。
    """
    now = env.snapshot()
    changed = [k for k in now if now.get(k) != state.env_snapshot.get(k)]
    state.env_snapshot = now                    # 更新快照（供下一拍差分）
    view = {"goal": state.goal, "step": state.step,
            "changed": changed, "known_bad": state.known_bad,
            "current_plan": state.plan}
    for k in changed:
        v = str(now[k])
        if len(v) > 4000:                        # 截断 + 显式声明差异
            view[k] = (v[:4000] +
                       f"\n[已截断：原 {len(v)} 字符，此处前 4000 字符；"
                       f"缺失部分可能含错误详情]")
        else:
            view[k] = v
    return view

# ---------- ④ 反思（事件触发，不是每步） ----------
def should_reflect(step: int, last_act_ok: bool, subgoal_done: bool) -> bool:
    """
    ★ 设计决策：反思是止损手段而非增值手段 —— 所以按事件触发。
    三个触发条件对应三类有效信息：失败（有反馈）、子目标完成（有检查点）、长间隔（防停滞）。
    """
    return (not last_act_ok) or subgoal_done or (step % 5 == 0 and step > 0)

def reflect(state: LoopState, view: dict, feedback: dict) -> dict:
    """
    反思的产出必须是'可执行的状态变更'，不是感想。
    注意：feedback 必须来自外部（工具错误码 / 断言 / 独立评审）——
    没有外部信号时这个函数退化成自言自语（第 1 章机制二）。
    """
    if feedback.get("kind") == "bad_param":
        # 参数类失败 → 记录'已知坏路径'，缩小后续搜索空间
        state.known_bad.append(feedback.get("value"))
        return {"state_update": {"known_bad": state.known_bad}}
    if feedback.get("kind") == "stalled":
        return {"plan_update": {"drop_last": True}}   # 停滞 → 丢一步计划
    return {}                                        # 无信息可提炼 → 什么也不做

# ---------- 主循环 ----------
def run_loop(state: LoopState, env, decide, act, verify, budget_steps=15,
             budget_seconds=90.0):
    t0 = time.time()
    last_ok, last_fb = True, {}

    while True:
        # ===== 循环的骨架（全部在模型之外）=====
        if state.step >= budget_steps:
            return {"status": "budget_steps", "state": state.to_dict()}
        if time.time() - t0 >= budget_seconds:
            return {"status": "budget_time", "state": state.to_dict()}
        if env.hard_violated(state.env_snapshot):
            # 硬约束每步检查 → 在违规当步停下（拦漂移，第 1 章 3.4）
            return {"status": "violation", "state": state.to_dict()}

        # ===== ① 感知 =====
        view = perceive(state, env)

        # ===== ④ 反思（事件触发，且发生在决策之前：用上一拍的反馈修正计划）=====
        if should_reflect(state.step, last_ok, subgoal_done=False):
            for k, v in reflect(state, view, last_fb).items():
                if k == "state_update": view.update(v)
                if k == "plan_update" and state.plan:
                    state.plan.pop()

        # ===== ② 决策（唯一模型环节）=====
        d = decide(view)

        if d["kind"] == "final":
            ok, why = verify(state, env)          # ★ 模型说完了不算数
            if ok:
                return {"status": "done", "why": why, "state": state.to_dict()}
            last_ok, last_fb = False, {"kind": "not_done", "why": why}
            state.step += 1
            continue

        if d["kind"] == "wait":
            # ★ 显式挂起：不空转（把等待变成一步，n 不膨胀，成本不随时长增长）
            state.waiting_for = d["on"]
            state.wait_deadline = time.time() + d.get("timeout", 3600)
            raise Suspend(d.get("reason", "waiting"), d["on"])

        # ===== ③ 行动（网关）+ 回填 =====
        res = act(d, idem_key=f"{state.step}:{d.get('name')}")
        last_ok = res["ok"]
        last_fb = res                       # 结构化结果 → 反思段的输入
        state.step += 1

# ---------- 外层：事件驱动 ----------
def resume_on_event(persisted: dict, event: dict, **kw):
    """
    外层唤醒内层。★ 关键：从持久化状态恢复 ——
    这就是'可观测 L3 可重放'与'挂起等审批'共用的机制。
    """
    st = LoopState(**{k: v for k, v in persisted.items()})
    if event.get("name") == st.waiting_for:      # 等到的是我在等的事件
        st.waiting_for = st.wait_deadline = None
    return run_loop(st, **kw)

四处必须停下来看的设计决策：

  1. LoopState 里包含 waiting_for —— "在等什么"必须进状态。这是长周期 Agent 最常漏的一处：漏了它，事件到达时无法判断这个事件是不是自己要等的。
  2. should_reflect 只在失败/子目标完成/每 5 步触发。每步反思是纯浪费（第一节的结论）。
  3. reflect 的返回是 state_update / plan_update，不是文本。反思必须能改变后续行为，否则它只是 token 消耗。
  4. raise Suspend 而不是阻塞等待 —— 内层退出，控制权交回外层。这让"挂起 → 审批 → 恢复"成为可能（即可回滚目标的实现基础）。

练习#

  1. 补齐感知段：给一个"读 HTTP 接口返回的 JSON 并抽取订单"的场景，写出至少 4 个感知段的设计决策（选择/结构化/截断/标注/脱敏各一条），并说明每个决策不做的后果。特别说明你如何让模型知道"某个字段因为权限被脱敏了，而不是它不存在"。
  2. 反思的收益分析：设反思的额外成本是每步 c、每次反思能纠正一个错误的概率是 β。请写出"反思使期望总成本下降"的条件（提示：对比"不反思时错误导致的重跑成本"）。然后解释：为什么 β 在没有外部信号时会接近 0？
  3. 驱动方式选择：下面三个任务各自该用轮询、事件驱动还是混合？给出理由，并说明"等待"在这一拍里怎么表示。 （a）读一个 issue、改代码、跑测试、提 PR； （b）监控一个部署，直到它成功或失败，成功后再跑一遍冒烟测试； （c）一个每天早 8 点汇总昨日数据的任务。
  4. 差分感知的代价：把感知段从"全量"改成"差分"，需要状态管理额外维护什么？请举出一个差分反而导致错误的场景（提示：环境里发生了"删除"，但你的差分只报告了 change 的 key，模型据此认为文件仍存在）。
  5. 设计：为一个需要"提交工单 → 等人工审批 → 审批通过后执行"的 Agent 画出状态机（状态 + 转移 + 事件），要求明确：挂起时状态里存什么、超时怎么处理、审批被拒之后走哪条路径、以及恢复执行时如何保证幂等（提示：第 3 章的幂等键）。

小结#

  • 四段式里只有决策是模型；感知、行动、反思都是工程，且"感知"是最被低估的一段（它直接决定 1 章 p感知​）。
  • 截断必须显式标注 —— 模型没有能力察觉"我看到的不是全部"，静默截断是最廉价的错误制造机。
  • 感知差分（只送变化）省 token、抗稀释，代价是要维护上一拍快照；差分必须能表达"删除"。
  • 决策的输入是"状态视图"，不是"历史"。把历史缓冲误称状态，是"跑长了就胡言乱语"的根因。
  • 反思有三个存在条件：判据来自外部、产出是可执行的状态变更、频率远低于行动频率。反思是止损手段，不是增值手段。
  • 驱动方式由任务时间尺度决定：秒级轮询、小时级事件驱动，实践中是"外层事件驱动 + 内层轮询"的混合形态。
  • "等待"必须变成显式的一步（{"kind": "wait", "on": ...}）并进入状态，否则 n 被空转撑大、成本随时间线性增长、且超时后 Agent 会忘记自己在等什么。
  • 循环骨架是代码：预算检查、硬约束检查、幂等键、轨迹写入全部每拍必做；而"还剩多少预算""要不要记录"这类判断绝不能交给模型。
