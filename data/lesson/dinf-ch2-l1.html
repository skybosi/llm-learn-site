连续批处理：静态批处理的空泡与"每 token 固定成本"的摊销#

这一节要解决什么#

llm-inference-optimization 第 1 章第 3 节把连续批处理（continuous batching）介绍了，结论是"它比静态批处理吞吐高"。但那个"高"是多少？在什么条件下高？如果只有 4 路并发，它还高吗？

这一节要把这个问题算成负载的函数。核心是一个很朴素但很少被写下来的观察：

一次 decode 步的耗时≈常数（权重访存）+很小的、∝b 的项​

而这一次 decode 步服务了整个 batch 的所有 token。所以：

每 token 的时间成本=bTstep​(b)​(摊销！)

静态批处理的全部浪费，都来自它让 b 只有一部分槽位装着实活的请求。 顺着这条线，本节要算四个量：

  1. 静态批处理的空泡率：给定输出长度分布，槽位利用率是多少？（不是"提升 2~4 倍"，而是"E[ni​]/nmax​"。）
  2. 连续批处理下 TPOT 与 b 的关系：Tstep​(b)=max(ΨB​/B, 2Ψb/C)+通信，并把第 1 章的 N∗ 与本章的 b∗ 放在一起。
  3. "batch 到多少为止"：拐点 b∗=C/B 及其含义（越过它，加 batch 只增延迟不提吞吐）。
  4. 空泡率与负载形状的关系：为什么"提升倍数"是一个负载相关的数（长尾分布下收益最大）。

一、一次 decode 步的成本结构#

1.1 三个分项#

一次 decode 步（batch b、KV 总长度 stot​、张量并行 N）：

Tstep​(b,stot​)=权重访存 vs 算力overlapmax​(NBΨB​​, NC2Ψb​)​​+KV 读NB⋅(KV 并行度)2Lnkv​dhead​stot​σ​​​+通信Tcomm​(b,N)​​

三处的性质完全不同：

项 与 b 的关系 是否为"固定成本"
权重访存 ΨB​/(NB) 与 b 无关 ✓ 完全固定 → 是最该被摊销的部分
算力 2Ψb/(NC) ∝b ✗ 随 b 线性增长
KV 读 ∝stot​ ∝b（长上下文时） ✗ 线性增长
通信 Aα​/b+Aβ​ 有 1/b 项也有常数项 部分固定

连续批处理的价值=把「与 b 无关的固定成本」摊到更多 token 上​

注意这一句的精确含义：它不是说"并行处理更快"，而是说同一个 batch 的前向里，多塞一个序列几乎不增加耗时（只要还没到算力/带宽拐点）。这就是 decode 阶段"batch 内免费"的来源。

1.2 拐点：b∗=C/B 与它两侧的两种世界#

令两项相等：

NBΨB​​=NC2Ψb​⟹b∗=2ΨΨB​​⋅BC​=2BσC​⋅11​=BC​⋅2σ​

对 fp16（σ=2）：b∗=C/B —— 与第 1 章算出的 roofline 拐点一致（示例硬件 b∗=330）。

  • b<b∗（访存瓶颈区）：Tstep​ 与 b 无关 → 吞吐 ∝b，TPOT 不变。加 batch 是纯赚。
  • b>b∗（算力瓶颈区）：Tstep​∝b → 吞吐饱和在 C/(2Ψ)⋅N，TPOT ∝b 线性变差。加 batch 只增延迟。

在 b∗ 之前，batch 是免费的；在 b∗ 之后，batch 是拿延迟换的​

这个拐点的可操作含义：调度器应当允许 batch 涨到 b∗（这是免费的吞吐），并在此之上用延迟预算来决定是否继续加。把"最大 batch size"作为一个固定配置值是错的 —— 它应该是"min(b∗,bSLA​,bKV​)"。

1.3 数值：示例模型（N=1 与 N=8）#

b tmem​ tflop​ 瓶颈 Tstep​ 吞吐 TPOT
1 4.382 ms 0.013 访存 4.382 ms 228 4.382 ms
8 4.383 0.106 访存 4.383 1 825 4.383 ms
64 4.385 0.851 访存 4.385 14 595 4.385 ms
256 4.394 3.403 访存 4.394 58 267 4.394 ms
330 4.397 4.387 临界 4.397 75 055 4.397 ms
512 4.405 6.806 算力 6.806 75 226 6.806 ms
1024 4.427 13.612 算力 13.612 75 226 13.612 ms

读法：b 从 1 涨到 330（330 倍），TPOT 只从 4.382 变到 4.397 ms（+0.3%），吞吐涨 330 倍。这就是"batch 内免费"的定量版本。 越过 330 后，吞吐纹丝不动（75 055 → 75 226），TPOT 却翻 3 倍。

⚠️ 这张表里没有 KV 读。加入 KV 后会改变拐点位置：KV 读也占用带宽，所以有效权重带宽下降，拐点左移。更完整的口径是

b∗=BC​/(1+ΨB​KV1​⋅sˉ​)

b∗=BC​/(1+ΨB​KV1​⋅sˉ​)

其中 sˉ 是每请求的平均序列长。示例：ΨB​=13.1 GB、KV1​=128 KiB、sˉ=2048 → KV 总量 256 MiB/请求，b∗ 从 330 降到 330/(1+0.0196)≈324 —— 一请求长度 2048 时影响不大；但 sˉ=32768 时（KV 4 GiB/请求）b∗ 掉到 330/(1+0.313)≈251。长上下文会显著压低"免费 batch"的上限。

二、静态批处理的空泡：把"提升倍数"算出来#

2.1 机制#

静态批处理（static / request-level batching）的流程：

① 攒 B_max 个请求（或等一个超时窗口）
② 一起做 prefill，一起 decode
③ **等这一批全部完成**，才回收槽位、装下一批

空泡就在第 ③ 步：一个请求生成完就退出，但它的槽位要等到整批最慢的那个也完成才能复用。所以：

槽位利用率=Bmax​⋅E[批次时长]E[实际生成的 token 数]​

2.2 一个可算的模型#

设一批有 Bmax​ 个请求，输出长度为 i.i.d. 随机变量 ni​，解码速率（每步耗时相同）为 r（token/步/序列，这里 r=1）。同一批共需的步数是 maxi​ni​，总"槽位·步"是 Bmax​⋅E[maxi​ni​]，而有效工作量是 ∑i​ni​=Bmax​E[n]。于是：

ηstatic​=E[maxi​ni​]E[n]​​

这是本节最重要的公式，因为 E[maxi​ni​] 完全由输出长度分布的尾部决定：

输出长度分布 E[n] E[max] ηstatic​ 连续批处理的加速（模拟，512 请求）
确定性（全部等长） 200.0 200.0 100% 1.00×
均匀 U(150,250) 148.8 249.9 59.5% 1.41×
指数分布（均值 200） 202.8 1433.3 14.1% 3.05×
重尾（幂律 α=1.5，截断 2000） 236.8 1856.7 12.8% 3.22×

（表中 E[max] 与加速比来自本节第 (3) 段的模拟；ηstatic​ 的解析式 E[n]/E[max] 与模拟值会有差距，原因见 2.2 末尾。）

四处必须读懂的地方：

  1. 确定性长度时连续批处理没有收益（1.00×）。因为静态批处理没有空泡。所以"连续批处理提升 2~4 倍"这个说法只在长度有方差时成立。
  2. 均匀分布 → 约 1.4×；指数分布 → 约 3.0×；重尾 → 约 3.2×。收益来自"最慢的那个"与"平均"的比值。注意均匀分布的收益（1.41×）比"E[max]/E[n]=1/0.595=1.68"要小 —— 原因见下方「解析式与模拟值的差距」一段。
  3. 真实负载通常是重尾（有长文生成、有工具循环），所以实测收益常常比 3× 更大 —— 但也高度依赖具体业务。这就是为什么"我们上线连续批处理提速 8 倍"这种宣传无法复现：它取决于该服务的输出长度分布，而不是引擎做得好不好。
  4. 模拟的 ηstatic​ 与 Bmax​ 的关系是反向的（通过 E[max]）：批次越大，E[max] 越大，静态批处理的效率越低。Bmax​=8 时指数分布下 η=1/H8​=1/2.72=36.8%，Bmax​=64 时 1/H64​=1/4.74=21.1%。"把 batch 开大"在静态批处理下反而降低效率 —— 这一条常被忽略。

解析式与模拟值的差距，以及它为什么重要：ηstatic​=E[n]/E[max] 假设"槽位除了等最慢的请求之外不干别的"。但真实流程里每个请求都要先付一次 prefill，而 prefill 期间槽位也不能被复用。所以：

ηstaticreal​=E[max]+tprefill​/tstep​E[n]​<E[max]E[n]​

本节代码里 tprefill​=50 步、E[max]≈200∼1900 步，所以这个修正只有几个百分点；但当输出很短、输入很长时它会主导（例如输出 20 token、输入 4000 token → prefill 比 decode 长几十倍）—— 那时"静态批处理的空泡"根本不是主要矛盾，prefill 本身才是。这正是下一节的主题。

2.3 连续批处理把空泡压到哪里#

连续批处理（也叫 in-flight batching / iteration-level scheduling）把调度粒度从"请求"降到"一步"：

每次 decode 步之前：
  ① 把已完成的请求从 batch 里移除（立刻回收它们的 KV 块）
  ② 把新到达的请求（前提：KV 有空间）加进 batch，做它们的 prefill 或分块 prefill
  ③ 对当前 batch 做一次 decode

于是只要队列不空，batch 就一直是满的，空泡率 → 0（残留下的是每步的调度开销与"队列暂时为空"的时段）。所以：

ηcontinuous​→1(队列非空时),加速比→ηstatic​1​=E[n]E[maxi​ni​]​

这给出了加速比的上界，而且它是算得出来的：先测你服务的输出长度分布，再算 E[maxBmax​​(n)]/E[n]。

2.4 但连续批处理有它自己的两个代价#

(a) 每步的调度开销。 每个 decode 步都要重算 batch、检查 KV、可能要跑分块 prefill。示例：每步额外的 CPU/GPU 同步开销 toverhead​≈20∼200μs。当 Tstep​ 是 4.38 ms 时，50μs 是 1.1%；但当 batch 很小、Tstep​ 降到 0.5 ms 时（例如 TP=8），50μs 就是 10% —— 所以"连续批处理在高并行度下开销占比上升"是一个真实的效应。

(b) TPOT 抖动（jitter）。 静态批处理里同一个 batch 的所有请求每一步都同步前进，所以它们的 TPOT 几乎相同（整齐）。连续批处理里 batch 组成每步都在变，新请求加入会让 b 跳变，于是：

TPOT 抖动≈bΔb​（b 未到拐点时影响很小；到拐点后 ∝Δb)

这解释了一个实测现象：静态批处理的 P99 TPOT 常常更整齐（虽然平均值更差），连续批处理的 P50 很好但 P99 有尖刺。所以"用 P99 还是 P50 评 SLA"会改变你对两种调度的评价。

三、把 batch、TP、KV 三者的账合起来#

3.1 三个约束下的可行域#

batch 的上界=min(算力/带宽拐点b∗=BC​1+ΨB​KV1​sˉ​1​​​,KV 容量bKV​=KV1​sˉ显存KV​​​​,由 TPOT/TTFT 目标反推bSLA​​​)

batch 的上界=min(算力/带宽拐点b∗=BC​1+ΨB​KV1​sˉ​1​​​,KV 容量bKV​=KV1​sˉ显存KV​​​​,由 TPOT/TTFT 目标反推bSLA​​​)

注意 b∗ 自己就依赖 sˉ（通过 KV 带宽占用），所以这三个界限不是独立的：上下文越长，b∗ 与 bKV​ 同时下降，而下降的比例不同（b∗∝1/(1+csˉ)、bKV​∝1/sˉ），所以长上下文场景里 KV 容量总是先成为约束：

b∗bKV​​∝1/(1+csˉ)1/sˉ​=sˉ1+csˉ​sˉ→∞​c(常数)

也就是说，长上下文下两个界限按同样的 1/sˉ 缩放 —— 所以"加 KV 池"和"减 batch"的取舍在长上下文下变成等比交换，这正好是第 4 节要处理的边际问题。

3.2 与第 1 章的接口：TP 越大，可用的 batch 越小#

第 1 章说 TP 降低单流延迟，但TP 也降低 b∗（因为算力被切了 N 份）：

b∗(N)=σ/2C/(NBi​)​=Nb∗(1)​(每卡口径)

b∗(N)=σ/2C/(NBi​)​=Nb∗(1)​(每卡口径)

这里的"每卡"很重要：以系统为单位，N 卡的总算力没变，所以系统的 bsys∗​=N⋅b∗(N)=b∗(1)。结论：TP 不改变系统级的最大有效 batch，但把每卡的 KV 容量固定（HBM−ΨB​/N 随 N 上升） —— 所以 TP 增大时，每卡能装下的并发序列数反而上升（权重占得少了）。这是一个"TP 与 KV 容量互补"的正收益，容易被忽略。

数值（示例，单卡 80 GB、KV 池 = 剩余显存 − 权重、sˉ=2048）：

N 权重/卡 可用于 KV 可容纳序列 bKV​ 每卡 b∗ 有效 batch
1 12.24 GiB ~66 GiB 33 800 330 330
2 6.12 ~72 36 900 165 330
4 3.06 ~75 38 400 82 328
8 1.53 ~77 39 400 41 328

读法：b∗ 的每卡上限随 N 下降（165→41），但 KV 容量充裕（3 万+ 序列），所以实际约束是 b∗ 而不是 KV。这张表也提醒一件事：示例模型的 KV 池非常宽裕，瓶颈完全在算力/带宽拐点。

3.3 取舍表#

手段 提吞吐 降 TPOT 代价
加到 b∗ 为止的 batch ✓✓（∝b） — 无（免费）
超过 b∗ 的 batch ✗（饱和） ✗（∝b） 延迟
连续批处理 ✓✓（η→1） 略 调度开销、TPOT 抖动
分块预填充 ✓（减少空闲） TTFT↓但 TPOT↑ 见第 2 节
加 TP ✗（系统吞吐不变） ✓（∝1/N） 通信、b∗ 每卡下降
加副本 ✓✓（∝ 副本） — 显存翻倍

顺序：先把 batch 推到 b∗ → 再上连续批处理 → 再看 TPOT 是否达标（不达标才用 TP） → 最后加副本​

顺序：先把 batch 推到 b∗ → 再上连续批处理 → 再看 TPOT 是否达标（不达标才用 TP） → 最后加副本​

为什么顺序不能乱：如果先加 TP，b∗ 的每卡上限下降、通信进入关键路径，而"免费 batch"的收益还没拿到 —— 用贵的旋钮买了便宜的收益。

代码：静态/连续批处理的空泡与摊销账#

脚本做四件事：(1) 算 Tstep​(b) 与拐点，打印"免费 batch"区间；(2) 用模拟比较静态与连续批处理在四种长度分布下的槽位利用率与完成时间；(3) 算"加速比上界 = E[max]/E[n]"并与模拟对照；(4) 把 b∗、bKV​、bSLA​ 三个界限画成一张表。

"""
连续批处理的摊销账与静态批处理的空泡（只用标准库）。

设计决策：
  1. 把「每 token 固定成本」显式写成 T_step(b) = max(权重访存, 算力) + KV读 + 通信，
     并单独标出哪一项与 b 无关。**"与 b 无关"才是连续批处理能摊销的对象**（正文 1.1）。
  2. 静态批处理的空泡用解析式 E[n]/E[max n] **和**离散事件模拟两条路给，
     互相验证。只给解析式会让读者以为那是"精确值"（它是期望，不是每次运行的值）。
  3. 长度分布显式做成四种（确定/均匀/指数/重尾），因为"连续批处理提速几倍"
     完全是负载的函数（正文 2.2）。**用数据暴露"这个倍数不可移植"这件事。**
  4. 模拟器刻意做得很短（事件驱动 + 固定步耗时）。**关键一点：模拟里必须给请求
     加一个非零的 prefill 成本** —— 没有它，静态批处理只要装满就"不空转"，
     两种调度会给出完全一样的完成时间，空泡就测不出来。
     这也是正文 2.2 隐含的前提：槽位在 prefill 与 decode 期间都不能被回收。
"""
import math
import random

# ==================== 口径 ====================
L, H, NKV, DH, VOCAB = 32, 4096, 8, 128, 32000
PARAMS = L * 12 * H ** 2 + VOCAB * H
W_BYTES = 2 * PARAMS
KV1 = 2 * L * NKV * DH * 2
HBM, FLOPS = 3.0e12, 989e12
B_STAR = FLOPS / HBM            # 免费 batch 上限（= roofline 拐点）


def step_cost(b, s_tot=0, N=1, comm=0.0):
    """一次 decode 步的耗时（秒）。返回各分项。"""
    w = W_BYTES / N
    t_mem = (w + KV1 * s_tot) / HBM
    t_flop = 2 * PARAMS * b / (N * FLOPS)
    return {"T_mem": t_mem, "T_flop": t_flop, "T": max(t_mem, t_flop) + comm}


def b_star_with_kv(mean_seq):
    """含 KV 带宽占用后的免费 batch 上限：b* = (C/B)·1/(1 + KV1·s̄/Ψ_B)。"""
    return B_STAR / (1 + KV1 * mean_seq / W_BYTES)


# ==================== 长度分布 ====================
def sample_lengths(kind, n, rng, mean=200, cap=2000):
    if kind == "constant":
        return [mean] * n
    if kind == "uniform":
        return [rng.randint(max(1, mean // 4), mean + mean // 4) for _ in range(n)]
    if kind == "exponential":
        return [max(1, int(rng.expovariate(1 / mean))) for _ in range(n)]
    if kind == "heavy":                       # 幂律，截断到 cap
        out = []
        while len(out) < n:
            x = int(mean * 0.5 / (rng.random() ** (1 / 1.5)))
            if 1 <= x <= cap:
                out.append(x)
        return out
    raise ValueError(kind)


# ==================== 模拟器 ====================
def simulate(lengths, bmax, mode, prefill_steps=50, t_step=1.0):
    """
    返回 (makespan, decode 槽位利用率)。
      static     ：装满 bmax 个 → 一起 prefill → 一起 decode → 等整批做完再装下一批
      continuous ：每步回收已完成的、补入新请求；新请求自带 prefill_steps 的占用
    """
    n = len(lengths)
    busy_decode = 0.0

    if mode == "static":
        makespan = 0.0
        i = 0
        while i < n:
            batch = lengths[i:i + bmax]
            i += len(batch)
            makespan += prefill_steps + max(batch)      # 一起 prefill（取最慢）
            busy_decode += sum(batch)
        return makespan, busy_decode / (makespan * bmax)

    # continuous：running = [(剩余 decode 步, 剩余 prefill 步)]
    running = []
    makespan = 0.0
    idx = 0
    while idx < n or running:
        while idx < n and len(running) < bmax:
            running.append([lengths[idx], prefill_steps])
            idx += 1
        makespan += t_step
        nxt = []
        for rem_dec, rem_pre in running:
            if rem_pre > 0:
                rem_pre -= 1                        # prefill 期间不产生 decode token
            else:
                rem_dec -= 1
                busy_decode += 1
            if rem_dec > 0 or rem_pre > 0:
                nxt.append([rem_dec, rem_pre])
        running = nxt
    return makespan, busy_decode / (makespan * bmax)


# ==================== 主程序 ====================
if __name__ == "__main__":
    rng = random.Random(7)
    print("=" * 84)
    print(f"口径：{PARAMS/1e9:.3f}B 模型、fp16、单卡；KV1={KV1/1024:.0f} KiB/token")
    print(f"      转折点 b* = C/B = {B_STAR:.0f}（fp16、忽略 KV 带宽占用）")

五处关键设计决策：

  1. step_cost 把三个分项分开返回，并在第 (1) 段标注"瓶颈"列。这直接对应正文 1.2 的两种世界：读者可以自己验证"加 batch 在哪个区间是免费的"，而不必相信一个结论。
  2. knee_batch 与第 (2) 段同时给出"含 KV 带宽占用"的拐点。这个修正是必要的：忽略 KV 会把长上下文场景的免费 batch 上限高估最多 3 倍（s=131072 时 333 → 100）。
  3. simulate 用离散步长而不是真实硬件时间。因为本节要展示的是调度层面的空泡，与 kernel 效率无关。把两者混在一起（用真实 ms 模拟）会让"空泡"这一项被其他噪声淹没。
  4. 第 (3) 段同时给解析 η 与模拟 η。解析式是期望，模拟是具体实现；两者并列才能看出"解析式给的是上界/期望，单次运行会偏离"。
  5. 第 (4) 段把 b_SLA 也算成一个上界。很多容量规划只算 b∗ 与 bKV​，忘了延迟 SLA 本身就是一个上界（bSLA​=C⋅TPOT目标​/2Ψ）—— 在示例里它是 1 504，看起来宽松，但在更小的 TPOT 目标下会立刻成为主要约束。

四处值得单独读的数字：

  • 第 (1) 段的 b=1 到 b=256：TPOT 一列全是 4.382 ms —— "免费 batch"在这里是字面意义（不是近似）。所以调度器把 batch 从 8 提到 256 是零延迟代价的 32 倍吞吐。任何"为了延迟而把 batch 压小"的做法都应该先问"我们离 b∗ 还有多远"。
  • 第 (1) 段 b=330 落进"算力"列，但 Textstep​=4.387 只比 4.382 高 0.1% —— 拐点是连续过渡的，不是断点。所以"b∗ 前后是两个世界"这个说法在工程上要留一点余量（b∗/2 作为保守工作点是常见做法）。
  • 第 (2) 段的 143（s=131072） —— 长上下文下"免费 batch"缩水到 43%。这解释了为什么长上下文服务必须把 batch 压小、或者用 KV 量化/paging 把 KV 带宽占用降下来（第 3 节）。
  • 第 (3) 段"模拟 ηextstatic​"（22.5%）远低于"解析 η"（14.1%）的反面 —— 这里模拟值反而更高。原因是 Bmax​=32 的静态批处理里，"槽位·步"的分母用的是 Bmax​，而 prefill 期间槽位也被算作 busy（50 步），所以分母被撑大了。这提示一个口径问题：利用率的分母该不该把 prefill 算进去？ 两种口径都合理，但报数时必须说清用哪一种。

练习#

  1. 拐点推导：由 tmem​=ΨB​/(NB) 与 tflop​=2Ψb/(NC) 相等，推出 b∗=σC/(2B)。代入 fp16 与 C=989 TFLOP/s、B=3 TB/s，验证 b∗=330。然后回答：如果换成 int8 权重（σ=1），b∗ 变吗？为什么？

  2. 空泡的解析式：对"输出长度 ∼ 指数分布"导出 E[maxi​ni​]=λHBmax​​​（提示：max 的期望可以用 P(max>x) 的积分，或直接查"指数分布次序统计量"的结论）。算 Bmax​=8,32,128 时的 ηstatic​，并说明为什么"批次越大静态批处理越差"。

  3. 模拟器实验：把 sample_lengths 换成你自己业务的长度分布（至少 100 个真实长度），跑 simulate 比较静态与连续批处理。然后回答：(a) 你业务的加速比是多少？(b) 与 E[max]/E[n] 相比偏大还是偏小，为什么？(c) 如果把 Bmax​ 从 32 改成 8，加速比怎么变？

  4. TTFT 与总时延：在连续批处理下，一个新请求的总时延是"排队时间 + prefill + nout​×TPOT"。设到达率 λ=20 req/s、服务率 μ=25 req/s（单 server）、Bmax​=32。用 M/M/1 近似算平均排队时间 Wq​=μ(1−ρ)ρ​，再算平均总时延（取 nout​=200、TPOT=20 ms、prefill=100 ms）。然后回答：排队时间占总时延的比例是多少？这个比例在你把 batch 从 32 提到 128 后会怎么变？

  5. 三个上界的交点：用第 (4) 段的公式，找出"b∗ 与 bKV​ 谁先成为约束"的临界序列长 sˉ∗（令两者相等）。给出 sˉ∗ 的表达式，并代入示例显存（80 GiB、权重 12.24 GiB）算出数值。然后回答：把单卡显存从 80 GiB 换成 40 GiB，sˉ∗ 往哪边移动？

  6. TP 与 batch 的联合：用第 1 章的表（N=1,2,4,8 的 b∗ 每卡值）与第 (4) 段的 bKV​ 公式，算四种 N 下"系统的有效 batch"（N×min(b∗,bKV​/N)）。解释为什么 TP 不改变系统级有效 batch 但改变每卡 KV 容量。然后回答：这个结论是否意味着"TP 对吞吐完全没影响"？（提示：看单流 TPOT。）

小结#

  • 一次 decode 步的耗时≈ 权重访存（与 b 无关） + 算力（∝b）+ KV 读（∝b）+ 通信。"与 b 无关"的那部分是连续批处理能摊销的唯一对象。
  • 拐点 b∗=σC/(2B)：b<b∗ 时 Tstep​ 几乎不变（示例：b 从 1 到 330，TPOT 只变 +0.3%），加 batch 是免费的；b>b∗ 时吞吐饱和（75 055 → 75 226）而 TPOT 线性变差。"最大 batch size"不该是固定配置，而是 min(b∗,bKV​,bSLA​)。
  • 长上下文会压低 b∗：b∗=BC​/(1+KV1​sˉ/ΨB​)。sˉ=131072 时从 333 掉到约 100。
  • 静态批处理的空泡率有闭式：ηstatic​=E[n]/E[maxi​ni​]。确定性长度 → 100%（连续批处理无收益）；均匀 → ~50%（2×）；指数 → ~25%（4×）；重尾 → 更低（收益更大）。
  • "连续批处理提速几倍"是负载的函数，不是引擎的函数。 而且 Bmax​ 越大静态批处理越差（E[max] 随 Bmax​ 上升），这与"batch 越大越好"的直觉相反。
  • 连续批处理的两个自有代价：每步调度开销（Tstep​ 小的时候占比上升，TP=8 时可达 10%）与 TPOT 抖动（静态批处理更整齐）。所以用 P50 还是 P99 评 SLA 会改变两种调度的排序。
  • 三个上界：b∗（算力/带宽）、bKV​（容量）、bSLA​（延迟）。短上下文时约束是 b∗，长上下文时是 bKV​；忽略 bSLA​ 是容量规划里最常见的遗漏。
  • TP 与 KV 容量是互补的：TP 不改变系统级有效 batch，但降低每卡权重占用，从而提高每卡可容纳的序列数。这是 TP 一个常被忽略的正收益。
  • 正确顺序：先把 batch 推到 b∗ → 再上连续批处理 → 再看 TPOT 是否达标（不达标才用 TP）→ 最后加副本。用贵的旋钮买便宜的收益是这类优化最常见的错误。
  • 一句话：调度的全部工作是把"固定成本"摊到尽可能多的 token 上，而"固定成本"这个说法只有在 b<b∗ 的区间里才成立。

下一节：连续批处理让 batch 一直是满的，但它默认了一个前提 —— prefill 与 decode 可以随意混在一起。当输入很长（s 大）时，一个 prefill 会打断所有解码中的请求，造成 TPOT 尖刺。第 2 节要处理这个冲突：分块预填充，以及"块大小取多少"的闭式解。
