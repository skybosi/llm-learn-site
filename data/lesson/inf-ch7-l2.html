负载均衡与监控#

上一课我们有了一个能对外服务的 API。但单个推理实例扛不住线上流量——你需要多副本 + 负载均衡把请求分到各实例上，还需要监控看清每个实例的健康与性能。这一课把"服务化"从"能跑"推进到"能扛、能看"：负载均衡怎么选策略、推理服务的监控指标怎么看、怎么用 Prometheus + Grafana 搭一套可观测体系。

一、概念讲解#

1. 为什么需要多副本与负载均衡#

单个推理实例的吞吐有上限（受 GPU 显存、批大小、算力约束），高并发时请求会排长队、延迟飙升甚至被打爆。解决方式是水平扩展：起多个相同的推理实例（可能分布在不同机器上），前面放一个负载均衡器（Load Balancer，LB），把请求分发到后端实例。LB 的职责包括：转发流量、健康检查、故障摘除。

对推理服务，LB 有一个特殊挑战：请求是长时间占用资源的（一个回答可能生成几十秒），且显存是硬约束（同时能容纳的活跃序列有上限）。因此"谁有空接谁"比"轮流接"更重要。

2. 负载均衡的常见策略#

  • 轮询（Round Robin）：依次把请求发给每个后端，简单但不看后端实际负载——某个实例正在跑长任务时，轮询仍可能把新请求塞给它；
  • 最少连接（Least Connections）：发给当前活跃连接最少的实例。对推理更合理，因为"活跃连接"近似于"正在生成的请求数"；
  • 加权轮询：给不同配置的实例不同权重（大卡实例权重大）；
  • 会话保持（Session Affinity）：同一用户的多轮对话尽量路由到同一实例，便于命中该实例上的前缀缓存；
  • 基于队列/容量的调度：由引擎暴露自身"还能接多少请求"的指标，LB 据此决策，这是最贴合 LLM 的做法，但实现最复杂。

实践中常用 Nginx、Envoy、K8s Ingress 或云 LB 做转发，再结合引擎侧暴露的负载指标做精细化调度。会话保持与"前缀缓存命中"直接相关：同一对话路由到同一实例，公共前缀才复用得上。

3. 监控什么：推理服务的核心指标#

监控分两层：系统层（通用）与推理层（LLM 专属）。

系统层：GPU 利用率、显存使用量、CPU、网卡吞吐、请求错误率、实例存活（健康检查）。

推理层才是重点，要盯住这几个：

  • TTFT（首 token 延迟）：请求到达 → 第一个 token 出来的时间，直接决定用户"等多久开始看到字"；
  • TPOT / ITL（每 token 间隔）：后续每个 token 之间的平均耗时，决定"字往外蹦的快慢"；
  • 吞吐（tokens/s、requests/s）：整体产出速度；
  • 排队长度 / 排队时间：请求在调度队列里等了多久，是延迟劣化的主要来源；
  • KV Cache 使用率：块池用了多少，逼近 100% 说明要开始抢占或拒绝请求了；
  • 批大小：一次前向实际并行的序列数，反映连续批处理的效率；
  • 前缀缓存命中率：上一课讲的前缀复用效果。

这些指标的分位数（P50/P99）比平均值更有意义——P99 延迟直接对应"最差的一批用户体验"。

4. 用 Prometheus + Grafana 搭可观测#

主流推理引擎（vLLM、SGLang）都暴露 Prometheus 格式的指标端点（vLLM 在 /metrics，且需 --enable-metrics 或依赖 prometheus_client）。搭建链路：

  1. 推理实例暴露 /metrics；
  2. Prometheus 定期抓取（scrape）各实例的指标并存储；
  3. Grafana 从 Prometheus 查询，画仪表盘、设告警。

告警要设在"体验临界点"上，例如 P99 TTFT > 3s、KV Cache 使用率 > 90%、实例存活探测失败，而不是等用户来报。

二、可运行代码示例#

示例 1：用最少连接策略做一个简化负载均衡模拟#

下面不依赖真实网络，用"活跃请求数"模拟各实例的负载，演示"最少连接"与"轮询"的差异：

import random

class Instance:
    def __init__(self, name):
        self.name = name
        self.active = 0            # 当前正在处理的请求数

    def load(self):
        return self.active

def least_connections(instances):
    """选择活跃请求最少的实例（推理服务的推荐策略）。"""
    return min(instances, key=lambda i: i.load())

def round_robin(instances, counter):
    """轮询：不看负载，依次分配。"""
    return instances[counter % len(instances)]

# 两个实例，模拟实例 A 正在跑一个长请求（活跃=5），实例 B 空闲（活跃=0）
a, b = Instance("A"), Instance("B")
a.active = 5
pool = [a, b]

# 来 6 个新请求，对比两种策略把它们分到哪
print("最少连接分配：")
for _ in range(6):
    chosen = least_connections(pool)
    print(f"  -> {chosen.name}（当前活跃 {chosen.load()}）")
    chosen.active += 1

# 重置，再看轮询
a.active, b.active = 5, 0
print("轮询分配：")
for i in range(6):
    chosen = round_robin(pool, i)
    print(f"  -> {chosen.name}（当前活跃 {chosen.load()}）")
    chosen.active += 1

轮询会把一半新请求塞给已经满载的 A，而最少连接会先把 B 填起来——对"长时占用、显存受限"的推理服务，后者明显更合理。

示例 2：抓取 vLLM 的 Prometheus 指标#

# 启动时开启指标（vLLM 在 /metrics 暴露 Prometheus 格式）
vllm serve meta-llama/Llama-3.1-8B-Instruct --enable-metrics
# 抓取指标并过滤出与延迟/吞吐相关的几行
curl -s http://localhost:8000/metrics | grep -E "vllm:(time_to_first_token|e2e_request_latency|num_requests_running|gpu_cache_usage)"

常见指标含义（以 vLLM 为例）：

  • vllm:time_to_first_token_seconds：TTFT 的直方图（分位数可从这里算）；
  • vllm:e2e_request_latency_seconds：端到端请求延迟；
  • vllm:num_requests_running：当前活跃请求数；
  • vllm:gpu_cache_usage_perc：KV Cache 使用率。

把这些指标接进 Prometheus 的抓取配置（scrape_configs 指向 localhost:8000），就能在 Grafana 里画出延迟分位数与显存曲线。

三、练习#

  1. 把示例 1 扩展成三个实例，分别用最少连接、轮询、加权轮询各跑 100 个随机时长请求，统计每个实例的总负载，比较三种策略的均衡程度。
  2. 解释为什么"最少连接"对推理服务优于轮询，以及为什么它仍可能不如"基于引擎剩余容量的调度"（提示：不同请求的显存占用不同）。
  3. 起一个 vLLM 服务并 curl /metrics，找出 TTFT、TPOT、KV Cache 使用率对应的指标名，并说明如何从直方图算 P99。
  4. 用 Prometheus + Grafana（或本地自绘）搭一个最小可观测：持续压测服务，画出 P50/P99 TTFT 随并发上升的曲线，找到延迟开始陡增的拐点。
