LLM 的三重边界：无状态、无长期记忆、无行动能力#

这一节要解决什么#

绝大多数 Agent 教程从"框架怎么用"开始，于是学到的是调用方式，一旦出了怪事（重复调用工具、忘记前面做过什么、把已经完成的任务再做一遍）就无从下手。这一节反过来，先把 LLM 当成一个函数看清楚它做不到什么，然后你会发现：Agent 里几乎所有设计，都是在补这三个洞。

学完这一节你应该能回答：为什么"上下文窗口变大"不等于"有了记忆"？为什么同一个提示重复调用会得到不同结果，而这对系统设计意味着什么？以及：Agent 到底是不是"更聪明的模型"，还是别的什么东西？

边界一：无状态 —— 它只是一个函数#

把模型写成一个函数签名，是理解后面一切的前提：

output = LLM(prompt)        // 纯函数：同样的输入 → 分布的采样；模型内部不保存任何东西

严格说它是随机的纯函数：给定同一 prompt，输出是某个分布上的采样结果。注意两件事：

  1. 模型不记得上一次调用。所谓"多轮对话"，实现上每次都是把完整历史重新拼进 prompt 再调一次。对话状态存在于你的代码里，不在模型里。
  2. 没有副作用。模型不能读写文件、不能发请求、不能改数据库。它能做的只有"生成 token"。

这两点决定了 Agent 的第一层结构：状态与行动必须由外部系统提供，模型只负责在每一步做判断。

常见误解：上下文窗口不是记忆#

"窗口已经 100 万 token 了，记忆问题解决了" —— 这是本领域最贵的误解之一。

窗口          = 一次调用的输入容量上限（容量问题）
记忆          = 跨调用持久化、可检索、可更新、可遗忘的状态（生命周期问题）

两者是不同的维度：把 50 万字塞进窗口，你会同时得到三个后果 —— 成本线性上升、注意力被稀释（关键信息淹没在长文里）、且没有任何持久化（下一次调用还得重塞）。第 4 章「状态与记忆架构」会给出工程解：什么写进工作记忆、什么落到长期记忆、什么时候压缩与遗忘。

一句话：窗口解决"这次能不能看见"，记忆解决"下次还记不记得"，并且额外要解决"该不该记得"。

边界二：无长期记忆 —— 每一步都是"失忆的天才"#

一个具体的失败模式，几乎每个做 Agent 的人都踩过：

第 1 步：模型调用 search() 查到了关键事实 F
第 2 步：模型调用 write_file() 写文件
第 3 步：模型又问了一遍"这个事实是什么" —— 但它已经看不到第 1 步的工具返回（除非你把它放回 prompt）

这就是无长期记忆的直接后果：模型不会"记得"自己上一步干了什么，除非你显式地把上一步的结果放进当前上下文。于是 Agent 框架的核心工作之一，变成了决定每一步把什么带进上下文：

带什么 好处 代价
全部历史 信息最全 成本高、注意力稀释、易被无关内容干扰
只带最近 N 步 便宜 早期关键结论会丢
摘要 + 检索 成本可控且保留关键信息 摘要会失真，检索会漏（第 4 章展开）

这不是"框架替你搞定"的细节，而是 Agent 质量的主要来源之一。

边界三：无行动能力 —— 生成 ≠ 执行#

模型能描述如何删除一个文件，但不能删除文件。要把"描述"变成"执行"，中间必须插入一个受你控制的环节：

模型输出 → [解析] → [校验] → [授权] → 真正执行 → [把结果回填给模型]
                    ↑ 这三步是你写的，也是安全边界所在

这个插入环节带来三个硬约束，第 3、7 章分别展开：

  1. 工具契约：模型只能通过你定义的 schema 行动 —— schema 设计得含糊，模型就会"发明"参数。
  2. 幂等与副作用：真实动作可能已生效但结果没传回来（超时），盲目重试就会重复下单/重复写库。
  3. 权限与沙箱：凡是不可逆或高副作用的动作，必须能在执行前被拦住（人工审批 / 沙箱 / 限额）。

为什么"让模型自己循环"会放大误差：误差累积的原理#

把上面三点合起来，就得到 Agent 的本质：一个由模型驱动每一步决策的闭环系统。闭环带来一个必须正视的数学后果 —— 误差累积。

设每一步决策正确的概率为 p（比如 0.95），独立地连续做 n 步，整条轨迹全对（到达预期目标）的概率是：

Pn​=pn

步数 n p=0.95 p=0.99
5 0.77 0.95
20 0.36 0.82
50 0.08 0.61

结论很直接，也很反直觉：

  • 单步"看起来不错"（95%）在 20 步任务上只剩 36% —— 这就是为什么"模型很强但 Agent 老是跑偏"。
  • 提升单步质量（0.95 → 0.99）收益是超线性的；而在工程上，单步质量靠的不是换更大的模型，而是减少歧义（工具契约清晰、指令明确、给出可验证的中间结果）。
  • 缩短轨迹长度与允许纠错同样关键：允许"发现错了能回退重来"，等价于把独立乘性误差改成可恢复的过程。这解释了后面几章的设计动机：为什么要有终止条件（第 2 章）、为什么要幂等与补偿（第 3 章）、为什么要把状态显式化以便重放（第 4 章）。

⚠️ 注意 pn 是简化模型（假设每步独立、错误不可恢复），它用于说明量级而不是精确预测。真实的 Agent 里，工具返回本身就是"检查点"，能把一部分错误挡在下一步之前 —— 这正是"设计"能改变这个乘积的地方。

从"一次调用"到"闭环系统"#

把 LLM 放进闭环，它就不再是一个函数，而是一个系统的决策部件。三类角色必须分清：

感知（把环境/工具结果变成模型能读的输入）  ── 你写
决策（模型：下一步做什么）                ── 模型
行动（真正执行 + 结果校验 + 记录）        ── 你写

只有中间那个是模型，两边都是工程。 这也直接推出：Agent 的能力上限不取决于"模型多聪明"，而取决于两侧工程做得多扎实 —— 工具是否清晰、状态是否显式、失败是否可恢复、代价是否可控。

设计目标：五个目标，以及它们之间的冲突#

把 Agent 当系统设计，就要先写清楚"好"的标准。五个目标，缺一不可，但彼此冲突：

目标 度量 与其他目标的冲突
可靠性 同一任务多次运行的成功率与方差 提可靠常要"多问一次/多验证一步" → 抬高成本与延迟
可观测 每步的输入/输出/耗时/代价是否可回放 完整记录会放大存储与隐私面
可组合 工具/子 Agent 是否能独立替换与测试 强约束接口会牺牲"灵活的提示技巧"
可回滚 高副作用动作能否撤销/补偿 补偿逻辑要写两遍（正向 + 反向），且并非都可逆
成本可控 每任务 token/调用/时延的上界 与"多试几次更稳"直接对立，必须设预算与剪枝

工程上的做法不是"全都最优"，而是显式取舍并写进设计：例如"检索类任务优先可靠性（允许 3× 成本），对外写操作为先可回滚（宁可多一步确认）"。第 7 章会把每个目标落到可评测的指标上。

代码：一个最小的闭环（看清结构，而不是用框架）#

def run(task, tools, state, budget_steps=8):
    """
    最小 Agent 闭环：注意模型只出现在 decide() 里，其余都是工程。
    """
    history = [{"role": "system", "content": SYSTEM_PROMPT}]
    history.append({"role": "user", "content": task})

    for step in range(budget_steps):            # ① 预算：终止条件之一
        decision = decide(history)               # ② 模型只做这一步决策
        if decision.kind == "final":
            return decision.answer               # ③ 收敛：模型声明完成
        if decision.kind == "tool":
            tool = tools.get(decision.name)      # ④ 契约：名字必须在注册表里
            if tool is None:
                history.append(feedback("未知工具，可用：{list(tools)}"))
                continue
            params = validate(decision.args, tool.schema)      # ⑤ 校验
            if not params.ok:
                history.append(feedback(f"参数不合法：{params.error}"))  # 反馈给模型，而不是抛异常
                continue
            if tool.side_effect and not approve(tool, params): # ⑥ 授权：副作用前置拦截
                history.append(feedback("该操作未获授权"))
                continue
            result = tool.call(params, idempotency_key=key(step, decision))  # ⑦ 幂等键
            state.record(step, decision, result)               # ⑧ 状态与轨迹显式记录
            history = trim(history + [tool_message(result)])    # ⑨ 上下文裁剪（第 4 章）
    return "达到步数预算仍未完成"                # ⑩ 失败也要是可解释的结论

这 30 行里，模型只占 1 行（② ），其余 9 处都是设计决策 —— 而它们决定了这个 Agent 能不能用。这也是本课程后面每一章要展开的对象。

练习#

  1. 边界判断：下面四个需求，分别撞的是"无状态 / 无长期记忆 / 无行动能力"哪一个？说明理由。 （a）"让它记住我上周的偏好"；（b）"让它每天 9 点自动发一封日报"；（c）"它把同一个订单提交了两次"；（d）"它在第 5 步忘了第 2 步算出的中间结果"。
  2. 算误差：某任务平均需要 15 步，单步正确率 0.97。用 Pn​=pn 估算一次成功的概率；若把单步提到 0.99，提升多少？再算：如果允许"任一步失败后可回退重试一次"，直观看误差乘积会发生什么变化？
  3. 设计目标冲突：为"给生产数据库执行写操作"的 Agent 排出五个设计目标的优先级，并写出你为了可回滚愿意牺牲什么（成本？延迟？灵活性？）。
  4. 反例设计：构造一个例子，说明"把上下文窗口塞得更满"反而让结果变差。指出变差的具体机制（成本 / 注意力稀释 / 无关信息干扰）。

小结#

  • LLM 是一个随机的纯函数：无状态、无长期记忆、无行动能力 —— Agent 的全部结构都是在补这三个洞。
  • 上下文窗口 ≠ 记忆：前者是单次容量，后者是跨调用的生命周期管理（写入、检索、压缩、遗忘）。
  • 闭环会带来误差累积（Pn​=pn）：单步质量、轨迹长度、可恢复性三者共同决定成败。
  • 闭环里只有决策是模型，两侧都是工程 —— 这决定了 Agent 的能力上限。
  • 五个设计目标（可靠 / 可观测 / 可组合 / 可回滚 / 成本可控）互相冲突，必须显式取舍。
