原子操作与规约的正确用法#

第 4 章的 tiling 把每个输出元素的乘加锁在寄存器里，代价是"块与块互不相干"成了硬约束——一旦两个 block 往同一块输出累加，那套账全部失效。跨 block 累加靠原子操作（atomic operation）：把"读-改-写"绑成不可分割的一步。用对它有两个层次的问题：语义上会不会丢更新，工程上要不要每个线程都去撞同一把锁。

一、概念讲解#

1. acc += a 在全局内存上不是一条指令#

编译器把 acc += a 放进 SASS 至少是三条微指令：load 到寄存器、寄存器内相加、store 回内存。两条这样的序列交错执行时，完全可能出现"两个线程都读到旧值，后写者覆盖先写者"。下面这个模型把 1024 次 += 1.0 按最坏交错排一遍：非原子写法只剩 1（丢了 1023 次更新），原子写法正确得到 1024。这不是 GPU 特有的毛病，而是"并发写同一地址"的普遍后果——GPU 只是把它放大到几千个线程同时竞争。

2. CUDA 提供了什么#

入口 语义要点 典型用途
atomicAdd(p, v) 等 atomic* 族 读-改-写不可分割，返回旧值；默认是 device 作用域的 relaxed 语义 全局累加、计数器、直方图
atomicCAS(p, cmp, v) 比较-交换，是自定义原子操作的地基 实现 atomicMin 之外的自定义语义
cuda::atomic_ref<T, Scope> 把普通内存当原子对象用，可显式指定内存序与作用域 需要 acquire/release 的发布-订阅（下一课）
atomicAdd_block / atomicAdd_system 把作用域收窄到 block / 放大到系统 收窄可省一致性开销；放大用于多卡与 CPU

作用域（scope）与内存序（memory order）是两件不同的事：本课只用默认语义，下一课展开。先记住一条——默认的 device 作用域覆盖同一张卡上的所有线程。

3. 竞争不是唯一的问题，"位数"也要算#

原子操作的吞吐由同一地址上的串行化程度决定。设规约 8192 个线程、结果写进一个地址：

策略 原子指令数 最大同址并发度 最长冲突链
每线程 1 次原子 8,192 1 1.0
先做 4 线程聚合 8,192 4 3.0
warp 内聚合（32） 8,192 32 6.0
block 内聚合（256） 8,192 256 9.0

最反直觉的是第一列：原子指令数一次都没少。聚合改变的不是"发多少条指令"，而是"这些指令打在几个地址上"。同址并发度从 1 抬到 256，等于把原本必须串行的 256 次操作并成一次；最后一列用指数退避模型估算的串行深度（同一地址上 c 次操作约需 log2​c+1 轮）从 1.0 涨到 9.0——这是收益：256 次操作被压进 9 个串行轮次。

工程结论：先用片上手段（寄存器 + shared memory + shuffle）把结果收敛到每块一次，再让这一次原子操作去撞全局地址——第 2 章两级归约的延长线。

4. warp 聚合为什么成立#

warp 内先做前缀和（__shfl_up_sync），每个 lane 掌握左边所有 lane 的局部和；再用后缀和（__shfl_down_sync）拿到右边的和。两者相加等于"全 warp 之和减去自己"，于是只需 lane 0 发一次 atomicAdd。下面这段纯 Python 用更朴素的方式验证同一件事：5 步之后 lane i 手里的下标恰好是 i…31，lane 0 就握有全部 32 个元素。

s = list(range(32))                                    # 待求和的 32 个元素
lanes = [{i: s[i]} for i in range(32)]                 # 每个 lane 先持有自己的元素
for off in (16, 8, 4, 2, 1):
    lanes = [(lanes[i] if i + off >= 32 else {**lanes[i], **lanes[i + off]})
             for i in range(32)]                        # 并入右边第 off 个 lane 的子集
print("lane 0 持有", len(lanes[0]), "个元素，下标", min(lanes[0]), "..", max(lanes[0]),
      "| lane 7 持有", len(lanes[7]), "个，下标", min(lanes[7]), "..", max(lanes[7]))

5. 浮点原子加：换顺序就换结果#

atomicAdd 对 float 不保证任何顺序，而浮点加法不满足结合律。两个可复现的实测观测：

  • float32 累加 100 万次 0.1 得 100958.34，精确值是 100000——绝对误差 958.34；
  • 65536 个 float32 随机数：顺序累加 -122.873650，numpy 的成对（pairwise）求和 -122.875633，差 1.98e-03。

所以原子操作只保证正确性，不保证可复现性。要求逐次按位一致的场景（对拍、单元测试）要么用确定性规约（固定分区与固定累加顺序），要么改用 float64，要么接受容差。

6. 常见坑#

  • 拿 atomicAdd 当同步原语：它只保证这一次读-改-写不可分割，不保证"你写的其它数据也已可见"——那是下一课的 fence 与内存序。
  • 每个线程都去做全局原子：正确但慢；先把块内收敛掉。
  • 把 atomicAdd 的返回值当"当前值"：它返回加之前的旧值；用它分配唯一编号是对的，用它读最终值就错了。
  • 目标未初始化：原子操作不会替你清零，cudaMemset 或初始化 kernel 不能省。
  • 指望浮点原子加的确定性：见上一节。

二、可运行代码示例#

第一段纯 Python/numpy（无 GPU）：先让"丢更新"发生一次，再看聚合如何减少同址竞争，最后量出浮点求和的顺序敏感性。

# ===== 本课示例 1：非原子累加为什么会丢更新（交错执行） =====
import math

def simulate(chunks_a, chunks_b, atomic):
    """把 acc += a 看成 LOAD/ADD/STORE 三条微指令，并让两个线程交错执行。
    atomic=True：三条微指令不可分割；False：允许两个 LOAD 都发生在 STORE 之前。"""
    acc, reg = 0.0, {"A": 0.0, "B": 0.0}
    if atomic:
        for a in chunks_a + chunks_b:
            acc += a
        return acc
    for a in chunks_a:      # 最坏交错：A、B 各自先读（读到同一个旧值）
        reg["A"] = acc
    for a in chunks_b:
        reg["B"] = acc
    for a in chunks_a:      # A 写回
        acc = reg["A"] + a
    for a in chunks_b:      # B 写回：用的是旧值，覆盖 A 的结果
        acc = reg["B"] + a
    return acc

N = 512
got = simulate([1.0]*N, [1.0]*N, atomic=False)
print(f"非原子累加：acc = {got:>6.0f}  期望 {2*N}  丢失 {2*N-got:.0f} 次更新")
got = simulate([1.0]*N, [1.0]*N, atomic=True)
print(f"原子累加：  acc = {got:>6.0f}  期望 {2*N}  丢失 {2*N-got:.0f} 次更新")

# ===== 本课示例 2：warp/block 聚合把原子指令数与最长冲突链一起降下来 =====
def agg_stats(groups):
    """groups：每次原子操作落到的地址列表。返回 (原子指令数, 最长冲突链, 最大同址并发度)。
    同一地址上的 c 次原子操作必须串行；指数退避把它压到约 log2(c)+1 轮。"""
    hist = {}
    for addr in groups:
        hist[addr] = hist.get(addr, 0) + 1
    ops = sum(hist.values())
    cmax = max(hist.values())
    return ops, (math.log2(cmax) + 1 if cmax > 1 else 1.0), cmax

BLOCKS, WARPS, THREADS = 32, 8, 32
print(f"\n规约 {BLOCKS} block × {WARPS} warp × {THREADS} thread = {BLOCKS*WARPS*THREADS} 个线程")
print(f"{'策略':<20}{'原子指令数':>12}{'最长冲突链':>12}{'最大同址并发度':>14}")
for name, groups in (
    ("每线程 1 次原子",   [(b, w, t)   for b in range(BLOCKS) for w in range(WARPS) for t in range(THREADS)]),
    ("4 线程聚合后再原子", [(b, w, t//4) for b in range(BLOCKS) for w in range(WARPS) for t in range(THREADS)]),
    ("warp 内聚合(32)",   [(b, w)      for b in range(BLOCKS) for w in range(WARPS) for _ in range(THREADS)]),
    ("block 内聚合(256)", [(b,)        for b in range(BLOCKS) for _ in range(WARPS) for _ in range(THREADS)]),
):
    ops, depth, cmax = agg_stats(groups)
    print(f"{name:<20}{ops:>12,}{depth:>12.1f}{cmax:>14}")

# ===== 本课示例 3：求和顺序变了，结果就变（原子加不保证顺序） =====
import numpy as np
f32 = np.float32
def seq_sum(vals):
    acc = f32(0.0)
    for v in vals:
        acc = f32(acc + v)
    return float(acc)

print("\nfloat32 不满足加法结合律，三个可复现的观测：")
acc = f32(0.0)
for _ in range(1_000_000):
    acc = f32(acc + f32(0.1))
print(f"  1) 1e6 次累加 0.1  = {float(acc):.2f}（期望 100000.00，绝对误差 {float(acc)-100000.0:.2f}）")

rng = np.random.default_rng(7)
x = rng.standard_normal(65536).astype(np.float32)
seq = seq_sum(x)
pw = float(np.add.reduce(x, dtype=np.float32))
ex = math.fsum(float(v) for v in x)
print(f"  2) 65536 个随机数：顺序累加 {seq:.6f} vs numpy 成对求和 {pw:.6f}，"
      f"差 {abs(seq-pw):.2e}（精确和 {ex:.6f}）")

ones = 1_000_000
for big in (1e7, 1e6):                              # 大数放尾部 vs 放开头
    A = [f32(1.0)] * ones + [f32(big)] * 4
    B = [f32(big)] * 4 + [f32(1.0)] * ones
    print(f"  3) 大数 {big:g}：{seq_sum(A):.1f} vs {seq_sum(B):.1f}，"
          f"差 {seq_sum(B) - seq_sum(A):.1f}")

float32 不满足加法结合律，三个可复现的观测：
  1) 1e6 次累加 0.1  = 100958.34（期望 100000.00，绝对误差 958.34）
  2) 65536 个随机数：顺序累加 -122.873650 vs numpy 成对求和 -122.875633，差 1.98e-03（精确和 -122.875634）
  3) 大数 1e+07：41000000.0 vs 40000000.0，差 -1000000.0
  3) 大数 1e+06：5000000.0 vs 5000000.0，差 0.0

第三组是结论的关键：同一批数据只是换了大数的位置，1e7 时相差 1000000，换成 1e6 时又分毫不差——误差方向不可预测，不能靠"换个顺序碰运气"。

把结论落到真实 kernel 的写法如下，核心是"块内先用 shared memory 收敛到每块一次原子"：

// 每块一次全局 atomicAdd：块内用 shared memory 归约，再让一个线程入账
__global__ void blockSumOnce(const float* __restrict__ in, float* __restrict__ out, int n) {
    __shared__ float partial[256];
    int tid = threadIdx.x;
    float v = 0.f;
    for (int i = blockIdx.x * blockDim.x + tid; i < n; i += gridDim.x * blockDim.x)
        v += in[i];                              // 每线程先在自己的寄存器里累加
    partial[tid] = v;
    __syncthreads();
    for (int s = blockDim.x / 2; s > 0; s >>= 1) {   // 8 轮，每轮之间必须同步
        if (tid < s) partial[tid] += partial[tid + s];
        __syncthreads();                             // 上一轮的写对下一轮的读可见
    }
    if (tid == 0) atomicAdd(out, partial[0]);    // 全块只剩这一次原子操作
}

// warp 内聚合：0 次块内原子，只让 lane 0 发一次全局 atomicAdd
__device__ __forceinline__ float warpSum(float v) {
    #pragma unroll
    for (int off = 16; off > 0; off >>= 1)
        v += __shfl_down_sync(0xffffffffu, v, off);
    return v;                                    // 每个 lane 都得到同一个 warp 总和
}

三、练习#

  1. 实现：改造 blockSumOnce——先用 __shfl_down_sync 在 warp 内求和，再让每个 warp 的 lane 0 写 shared，最后 warp 0 做一次 5 步 shuffle。数一数改完后 __syncthreads() 从 8 次降到几次。
  2. 解释：为什么"原子指令数"在示例 2 里完全没变，而最大同址并发度却从 1 变到 256？把这两个量分别对应到硬件上的哪种资源。
  3. 对比/验证：把示例 3 的第 2 组数据换成 np.float64 重跑，观察顺序累加与成对求和的差会变成多少；再解释为什么"精度更高的累加器"能减轻顺序敏感性。
  4. 思考：如果一个 kernel 用 float32 原子加得到的结果每次都不一致，但它要参与分布式训练的梯度同步，你会付出什么代价来换取确定性？至少列出两种方案及其代价。
