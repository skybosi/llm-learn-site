错误的分类与"给模型的反馈"设计#

这一节要解决什么#

前两节把"调用能成功"这条路打通了：契约写清楚、重试安全。但失败是常态，而且失败里有一大半是重试解决不了的：参数不合法、权限不足、业务规则拒绝、资源不存在。

这类失败有一个被浪费掉的价值：它们是最便宜、最精确的学习信号。 一个说清"哪个参数、为什么、合法范围是什么"的错误反馈，能让模型一次修正；一个栈回溯或一句 Error: invalid input，会让模型原地打转甚至编造。

先看清这件事的规模。设每步的失败中可修复类占比 q，模型在收到反馈后能正确修复的概率为 r，而"无法修复"的失败会导致至少一次无效尝试：

无效步数期望≈t∑​[(1−q)+q(1−r)]

把 r 从 0.4 提到 0.85（只改错误信息的写法，不改任何模型和工具），无效步数就下降近一半。这是投入产出比最高的改动之一 —— 它不需要换模型、不需要训练、不需要加工具。

但"写清楚"不等于"写更多"。错误信息进入上下文，会占据 token、挤掉其他内容，并且可能泄漏不该给模型的信息。所以这一节的核心张力是：

可修复性∝反馈里的可行动信息量,成本与风险∝反馈里的信息总量

这一节的目标是把这个张力变成一组可执行的设计规则：分类维度、必须携带的字段、绝对不出现的内容、重复检测与升级。

学完这一节你应该能回答：

  • 为什么"把异常原样抛给模型"通常会让循环更快卡死，而不是慢下来？
  • 错误分类的维度为什么不是"按异常类型"，而是"按模型能不能采取不同动作"？
  • 一条合格的错误反馈里必须有哪些字段？为什么"HTTP 500"这四个字符的信息量是负的？
  • 模型连续两次犯同一个错，正确的响应是什么？（不是"再给它一次同样的反馈"。）
  • 错误信息里有哪些东西绝对不能出现？"表不存在"和"你无权访问"的差别在哪里？

一、异常不是反馈：原样抛出的三重代价#

先看一个真实会发生的形态：

# ✗ 最常见的实现
try:
    result = tool(**args)
except Exception as e:
    observation = f"Error: {e}"          # 或 str(traceback.format_exc())
    messages.append({"role": "tool", "content": observation})

三重代价，逐条展开：

1.1 代价一：可行动信息为零，而噪声占满 token#

一个典型的 Python 栈回溯是 800–3000 字符，其中对模型有用的信息通常只有一句（"limit 必须是 1..100 的整数"）。后果有两个：

  • token 成本：每次失败烧掉的钱不多，但 Agent 会反复失败。设一次失败反馈 1500 token、循环里失败 20 次，仅错误信息就占 3 万 token —— 在 6 万预算的循环里（第 2 章案例）这是致命的。
  • 注意力稀释：上下文里多数内容是无关的文件路径、内部函数名、库版本。这些会稀释真正关键的观察（第 4 章的上下文工程会量化这一点）。

1.2 代价二：模型会去"修栈回溯里的东西"#

这是最反直觉的一条。栈回溯里有函数名、模块名、行号 —— 模型会把它们当成任务的一部分去处理：

Observation: Traceback (most recent call last):
  File "/srv/app/tools/db.py", line 88, in fetch_orders
    cur.execute(sql, params)
psycopg2.errors.UndefinedColumn: column "statu" does not exist

→ 模型接下来的行为（真实观察到的模式）：
  · 试图"修复" db.py（它没有编辑权限，或者不该改代码）
  · 在 SQL 里加上 "statu" 的双引号（错误的修法）
  · 猜测表结构，编造更多列名，进入试错循环

根因：栈回溯是给程序员看的内部实现细节，而模型看到的是一段文本 —— 它无法区分"这是我该用的信息"和"这是我该忽略的实现细节"。给它栈回溯，等于给它一个误导性的任务描述。

1.3 代价三：把系统的内部结构泄露给了一个"可被注入的组件"#

第 4 节会展开工具投毒，这里先说结论：工具返回值是一条不可信输入通道。栈回溯会泄露：

  • 内部文件路径、模块结构、库与版本（攻击者可据此选择已知漏洞）
  • SQL 片段与表结构（可用于构造注入）
  • 有时甚至是连接串、环境变量（KeyError: 'STRIPE_SECRET_KEY'）

而这条通道的另一端是一个会把内容当指令读的模型。这个组合是提示注入得以成立的基础设施之一。

1.4 结论：错误必须被"消费"一次再给模型#

正确的形态是中间加一层错误适配器：

原始异常 分类 ​结构化错误 面向模型渲染 ​反馈文本 审计 ​完整日志（不给模型）

注意最后一跳：完整信息不能丢，只是不给模型。 它要进轨迹/日志（第 2 章），供第 7 章的失效归因使用。给模型的是裁剪+翻译版本，给人看的是完整版本。这两者必须分开存放。

二、分类维度：按"模型能采取什么不同动作"#

2.1 为什么不用异常类型分类#

按 ValueError / TimeoutError / HTTPError 分类是程序员的本能，但它对 Agent 无用。因为模型需要知道的不是"这是什么异常"，而是：

我现在应该做什么不同的事？

两种分类方式的对照：

按异常类型（✗） 按"可采取的动作"（✓）
ValueError 参数可以修 → 让模型改参数
TimeoutError 结果未知 → 先核对或原样重试（第 2 节）
HTTPError 按状态码分五类，动作各不相同
PermissionError 换工具 / 挂起求人 / 放弃
KeyError 我猜错了字段名 → 看返回的可用字段列表

同一个异常类型可能对应不同动作（ValueError 既可能是"参数的格式错"也可能是"业务规则拒绝"），不同的异常类型可能对应同一个动作（PermissionError 与 403 都是"换路或求人"）。所以分类的主键必须是动作，异常类型只是特征。

2.2 六类错误：修复主体与反馈要点#

这是本节的核心表。每一类的列"谁来修"决定了反馈要写给谁看。

类别 典型表现 谁来修 反馈必须包含 可以重试？
① 调用格式错 类型错、字段名拼错、枚举值不在集合内、缺必需参数 模型自己 哪个字段、期望什么类型/集合、当前收到什么、可用字段列表 ✗（改参数后可重调）
② 参数语义/值域错 超范围、格式不匹配（日期/邮箱/ID）、跨字段约束违反 模型自己 哪个字段、合法域/格式、当前值、以及"哪个组合才合法" ✗
③ 业务规则拒绝 余额不足、状态不允许、配额超限、重复提交 模型（换策略）或人 规则是什么、当前资源状态、有哪些可选路径（换额度/换方式/降级） ✗（除非规则带时间窗口）
④ 资源/前置条件缺失 404、依赖资源未创建、会话未打开、顺序错 模型自己 缺什么、哪个工具能创建它、正确的调用顺序 ✗（做完前置后可重调）
⑤ 瞬态/基础设施 超时、连接重置、503、限流 框架（不是模型） 已尝试几次、结果是否未知（决定能不能重试）、下次可重试的时间 ✓（见第 2 节）
⑥ 权限/安全 401、403、审批未通过、越权访问 人（模型无法解决） 需要什么权限、向谁申请、是否有替代的只读路径 ✗

四个必须记住的推论：

  1. ⑤ 类根本不该让模型看到（或者只给一句摘要）。它是框架层的重试职责；让模型知道"基础设施抖了一下"只会诱发它做无意义的动作。只有重试用尽后才把它交给模型，并且必须附带"结果是否未知"这个关键信息。
  2. ①②④ 类是"高价值反馈"：它们几乎全部可以自动化修复，前提是反馈里有足够信息。这三类的反馈质量直接决定 Agent 的任务成功率。
  3. ③⑥ 类是"必须升级"的：模型无论多想都修不了。反馈里必须包含升级路径（"这个操作需要 payments:write 权限，请让管理员授权，或改用只读的 get_balance"），否则模型会花掉大量预算尝试各种"绕过"。
  4. 类别决定是否重试，而重试策略必须是同一份分类的结果。第 2 节的 FailureKind 与这里的六类有一一映射，必须共用一份分类代码，否则会出现"错误适配器说不可重试、重试器却在重试"这种自相矛盾。

2.3 分类的判据树（可直接实现）#

收到失败
├─ 请求是否到达远端？
│    ├─ 否（连接前失败）→ ⑤-未执行（可安全重试，即使不幂等）
│    └─ 是 ─┐
├─ 远端是否明确表示"未执行"？
│    ├─ 是 + 瞬态（503/限流）  → ⑤-未执行（退避重试）
│    ├─ 是 + 确定性            → ① / ② / ③ / ④ / ⑥（按下面的细分）
│    └─ 否（超时/500/连接重置）→ ⑤-结果未知（★ 只有幂等才可重试）
└─ 确定性错误的细分（看错误里"谁违规"）
     ├─ 参数本身不合法        → ① 或 ②（模型改参数）
     ├─ 资源不存在/前置未满足 → ④（模型补前置，反馈要给工具名）
     ├─ 规则拒绝（资源状态）  → ③（模型换策略，反馈要给可选路径）
     └─ 身份/权限            → ⑥（升级给人）

分类器的输入不只是异常，还包括：HTTP 状态码、响应体的 error.code（如果有的话）、以及这次调用的参数（用于判断"是字段名错还是值域错"）。这就是为什么工具应该返回机器可读的错误码，而不是只返回一句话：{"error": {"code": "limit_out_of_range", "param": "limit", "allowed": [1,100]}} 可以被精确分类；"invalid limit" 只能靠字符串匹配猜。

三、反馈的构成：字段、顺序与长度预算#

3.1 一条合格反馈的六个字段#

按重要性排序（前面的必须有，后面的按类别选）：

# 字段 作用 示例
1 状态 一句话说清发生了什么 status=invalid_argument
2 定位 哪个参数/哪一步/哪个资源 param=limit
3 期望 合法域、格式、前置条件 期望 1..100 的整数，默认 20
4 下一步 模型应该做的一个具体动作 请把 limit 改为不超过 100 的值后重新调用
5 护栏 明确禁止危险动作（针对模型倾向） 不要修改 user_id，也不要重复提交相同参数
6 升级路径 当模型无法解决时的出口 若需要超过 100 条，请改用 export_all（需审批）

第 4 项有一个反直觉的设计要求：只给一个动作。给多个选项（"你可以改 limit，或者用分页，或者用 export"）会让模型在选项间摇摆，甚至尝试全部三个。给一条最优路径，把备选放在第 6 项（升级路径）里，措辞上区分"现在做"和"若不行则"。

第 5 项是 Agent 场景特有的，也是最容易被忽略的。它针对的是模型的系统性倾向，而不是这一次的错误：

模型的倾向 必须加的护栏
改参数后重试（结果未知时最危险） "不要修改参数重试；结果未知，请先核对"
重复提交相同参数（明知会失败） "不要重复提交相同参数"，并配合重复检测
编造缺失的字段值（猜 ID） "不要自行构造 id；用 resolve_* 工具获取"
遇到权限错时尝试其他工具绕过 "不要尝试绕过权限；这是策略限制"
遇到空结果时随机换关键词猛试 "已检索范围是 X；换关键词无用，请改用 archive_search"

这五项本质上是在错误反馈里做"提示工程" —— 但它是合法的，因为它不是把答案给模型，而是防止模型做已知的有害动作。这与第 2 章"不要把终止判据写进提示词"形成对照：护栏应当写，答案不应当写。

3.2 顺序：把最重要的放在最前#

模型对长文本的注意力分布不均匀（第 3 章第 4 节的上下文工程会给出机制）。反馈文本的实用顺序是：

[状态码] 一句话摘要（★ 最重要：模型可能只看第一行）
定位：字段/资源
期望：合法域
下一步：一个动作
护栏：禁止动作
升级：备选路径
补充：可选的原始细节（如 upstream_request_id，供人排查）

如果只保留一行，应该是"摘要 + 定位 + 期望"。这三者的组合足以让模型完成大多数修复。所以实现上可以做一个两级反馈：默认给精简版，模型连续失败后再给详细版（见 4.2）。

3.3 长度预算：反馈也必须"可裁剪"#

反馈是上下文的一部分，所以它必须有预算。建议的量化规则：

反馈长度上界≈min(Lhard​,20⋅nfailures​Bctx​​)

其中 Lhard​ 是单条硬上限（经验值 500–800 字符），Bctx​ 是上下文预算。第二项的直觉：如果预计会失败很多次，单条反馈就要更短，否则错误信息会把预算吃光。实践中更简单的做法是：

第 1 次失败：完整反馈（≤800 字符）
第 2 次同类失败：精简反馈（≤300 字符）+ "你已犯过同样的错误"
第 3 次同类失败：升级（不再给同类细节，改给替代路径或求人）

这直接引出下一节。

四、重复错误：检测、升级与"不再给同样的话"#

4.1 为什么重复错误必须被特殊处理#

如果同一个错误反馈原样出现第二次，模型的行为通常不会改变 —— 因为它看到的信息没变。更糟的是三种退化：

退化 表现 机制
原地重试 完全相同的调用再发一次 模型把"重试"当成一个可尝试的动作
发散试错 参数随机微调，每次都错 反馈没告诉它合法域，它只能搜索
放弃并编造 "由于工具不可用，我根据经验推测..." 模型为避免卡死而编造结果（最危险）

第三种是 Agent 里最贵的事故：失败转化为幻觉。它往往发生在重复失败 3–5 次之后，且很难被发现（输出看起来合理）。

4.2 处理策略：递减信息 + 强制升级#

同一 (工具, 错误类别, 关键字段) 在窗口内第 n 次出现：
  n = 1 → 完整反馈（含期望与下一步）
  n = 2 → 精简反馈 + 「这是第 2 次相同错误。不要重复提交相同参数。」
          + 把"期望"字段再强调一遍（这是唯一还可能被忽略的信息）
  n ≥ 3 → 不再重复细节，改为：
          · 明确宣布局部失败：「本工具在当前参数空间内无法完成该请求」
          · 给替代路径或求人：「请改用 X，或向用户说明需要 <具体信息>」
          · 降低终止状态的等级（第 2 章）：从"继续尝试"变成 need_human

第 3 步的关键是"不再重复细节"。再给一遍同样的信息，等于指望同一个输入产生不同输出。必须改变输入的性质：从"修复提示"变成"路径切换"。

4.3 重复检测的键#

检测重复需要定义"什么是同一个错误"。键的选择：

重复键=(tool_name,error_class,locator,fingerprint(args))

  • 若把 fingerprint(args) 算进去，那么"参数微调后的失败"不算重复 —— 这是不够的，因为发散试错正是要拦的模式。所以实践中应同时维护两个计数：
    • 精确重复（同参数同错误）→ 判定"原地重试"
    • 类别重复（同工具同错误类别，参数不同）→ 判定"发散试错"
  • 类别重复的阈值要更低（例如 3 次），因为发散试错比原地重试消耗更多预算且更接近幻觉。

4.4 升级：把"我修不了"变成可执行的交接#

第 2 章定义了终止状态枚举。错误升级必须映射到其中的状态：

情况 终止状态 必须携带
① ② 类，修好了 继续循环 ——
① ② 类，连错 3 次 need_human 尝试过的参数、每次的错误、你的建议
③ 类（规则拒绝）且无替代路径 blocked 哪条规则、需要什么条件才能满足
⑥ 类（权限） need_human 需要哪个权限、向谁申请、有无只读替代
⑤ 类，重试用尽且结果未知 error + 未知标记 幂等键、查询手段（第 2 节）

"升级"必须是一个主动的产物，而不是"卡住"：need_human 状态要带上足够的信息让人在 30 秒内做决定。这直接复用第 2 章"任何终止状态都必须产生可解释的结论"。

五、绝对不能出现在反馈里的东西#

这一节是安全边界，逐条都对应真实事故：

禁止内容 为什么 替代做法
栈回溯 / 内部路径 / 模块名 诱发模型"修代码"，泄露内部结构 只给分类后的摘要
SQL 语句原文与表结构 注入素材；诱导模型直接构造 SQL 给字段级提示（"可用参数：..."）
凭据、连接串、环境变量名 直接泄露；且会被模型写进输出 永不进入上下文；只在服务端日志
资源是否存在（对无权访问者） 信息泄露（枚举攻击）：403 与 404 的区分会泄露"这个 ID 存在" 对无权资源统一返回 404 语义
内部业务阈值（风控规则的具体数值） 可被用于规避（对抗性探测） 给定性描述（"该金额超过当前限额"）
其他用户/租户的数据 越权 只给当前主体范围内的信息
完整的下游响应体 常含注入内容与无关字段 提取必需字段，丢弃其余

403 vs 404 这一条值得单独强调：它不只是"信息安全"，而是Agent 可靠性问题。如果权限错返回的细节足够多，模型会学到"多试几个参数就能进去"，于是开始对抗性探测 —— 这在自动循环里会变成真实的越权尝试（第 7 章的沙箱与权限会处理这个，但反馈层是第一个关口）。

代码：分类器 + 反馈渲染 + 重复检测 + 升级#

下面的代码把本节落成一个模块：(1) 一个不依赖异常类型的分类器；(2) 面向模型的两级反馈渲染（含长度预算）；(3) 精确重复与类别重复的双计数检测；(4) 升级到第 2 章终止状态的映射。

from collections import defaultdict
from dataclasses import dataclass, field
from enum import Enum
from typing import Any, Optional


# ==================== 分类：主键是"模型能做什么" ====================
class ErrorClass(Enum):
    FORMAT = "format"            # ① 调用格式错 → 模型改参数
    VALUE = "value"              # ② 值域/语义错 → 模型改参数
    BUSINESS_RULE = "rule"       # ③ 业务规则拒绝 → 模型换策略或求人
    PRECONDITION = "precond"     # ④ 资源/前置缺失 → 模型补前置
    TRANSIENT = "transient"      # ⑤ 瞬态/基础设施 → 框架重试，不给模型
    PERMISSION = "permission"    # ⑥ 权限/安全 → 升级给人


# ★ 设计决策：谁负责修复，决定反馈写给谁看
OWNER = {
    ErrorClass.FORMAT: "model", ErrorClass.VALUE: "model",
    ErrorClass.BUSINESS_RULE: "model_or_human", ErrorClass.PRECONDITION: "model",
    ErrorClass.TRANSIENT: "framework", ErrorClass.PERMISSION: "human",
}

# ★ 与第 2 节 FailureKind 共用同一份"可否重试"的判定，避免两处矛盾
RETRYABLE = {ErrorClass.TRANSIENT}

# 模型倾向 → 必须加的护栏（3.1 第 5 项）
GUARDRAILS = {
    ErrorClass.FORMAT: "不要重复提交相同参数；按上面的可用字段修正后重新调用一次。",
    ErrorClass.VALUE: "不要靠试错搜索边界；上面的合法域就是全部可能的取值。",
    ErrorClass.BUSINESS_RULE: "不要尝试绕过该规则；若需要例外，请向用户说明并请求确认。",
    ErrorClass.PRECONDITION: "不要自行构造缺失的资源标识；用上面指出的工具获取它。",
    ErrorClass.TRANSIENT: "结果可能未知，不要修改参数重试；原样重试或用查询工具核对。",
    ErrorClass.PERMISSION: "不要尝试其他工具绕过权限；这是策略限制，需人工授权。",
}


@dataclass
class ToolFailure(Exception):
    """
    ★ 设计决策：工具侧抛出的结构化失败。原始异常只用于内部日志（raw），
      绝不出现在 feedback 里 —— 这一层就是"把异常消费一次"的地方。
    """
    error_class: ErrorClass
    summary: str                       # 一句话，给模型的第一行
    locator: str = ""                  # 哪个参数/资源/步骤
    expected: str = ""                 # 合法域/格式/前置条件
    next_action: str = ""              # 唯一推荐动作
    escalate: str = ""                 # 升级路径（人/替代工具/审批）
    raw: str = ""                      # ★ 只进日志，永不进 feedback
    code: str = ""                     # 机器可读错误码（供分类与评测断言）


# ==================== 分类器：输入是构造好的失败，不是裸异常 ====================
def classify(status_code: Optional[int], code: str, arrived: bool,
             executed: Optional[bool]) -> ErrorClass:
    """
    ★ 设计决策：先回答"请求到了吗 / 执行了吗"，再细分。
      这个顺序是第 2 节 1.2 表的直接编码 —— 顺序错了会把"结果未知"当成"参数错"。
    """
    if not arrived:
        return ErrorClass.TRANSIENT                      # 连接前失败：可安全重试
    if executed is None and status_code in (None, 500, 502, 504):
        return ErrorClass.TRANSIENT                      # ★ 结果未知：必须走幂等通道
    if status_code == 429 or status_code == 503:
        return ErrorClass.TRANSIENT                      # 明确未执行 + 瞬态
    if status_code in (401, 403) or code.startswith("auth"):
        return ErrorClass.PERMISSION
    if code in ("unknown_field", "missing_field", "type_mismatch", "bad_enum"):
        return ErrorClass.FORMAT
    if code in ("out_of_range", "bad_format", "cross_field"):
        return ErrorClass.VALUE
    if code in ("not_found", "precondition_failed", "session_required"):
        return ErrorClass.PRECONDITION
    return ErrorClass.BUSINESS_RULE                       # 兜底：规则拒绝（最保守）


# ==================== 反馈渲染：两级 + 长度预算 + 顺序 ====================
MAX_LEN_FULL, MAX_LEN_TERSE = 800, 300


def render_feedback(f: ToolFailure, repeat_exact: int, repeat_class: int) -> str:
    """
    ★ 设计决策：按重复次数递减信息（4.2）。
      第 3 次起不再重复同类细节，改为"路径切换" —— 因为同一个输入不会产生不同输出。
    """
    guard = GUARDRAILS[f.error_class]
    head = f"[{f.code or f.error_class.value}] {f.summary}"

    if repeat_exact == 1 and repeat_class == 1:
        parts = [head]
        if f.locator:
            parts.append(f"定位：{f.locator}")
        if f.expected:
            parts.append(f"期望：{f.expected}")
        if f.next_action:
            parts.append(f"下一步：{f.next_action}")
        parts.append(f"注意：{guard}")
        if f.escalate:
            parts.append(f"若仍然失败：{f.escalate}")
        text = "\n".join(parts)
        return text[:MAX_LEN_FULL]

    if repeat_class <= 2:
        # ★ 第二次：只保留"唯一还可能被忽略的信息"，并显式指出重复
        text = (f"{head}\n这是第 {repeat_class} 次相同类别的错误。"
                + (f"\n期望：{f.expected}" if f.expected else "")
                + f"\n{guard}")
        return text[:MAX_LEN_TERSE]

    # ★ 第三次起：停止重复细节，宣布局部失败 + 给出口（对应 4.2 的"改变输入性质"）
    return (f"{head}\n本工具在已尝试的参数空间内无法完成该请求（已连续 {repeat_class} 次同类失败）。"
            f"\n不要再调用本工具相同参数。请改用：{f.escalate or '向用户说明并请求指示'}")


# ==================== 重复检测：精确重复 + 类别重复 ====================
@dataclass
class ErrorLedger:
    """
    ★ 设计决策：必须维护两个计数。只看"精确重复"会漏掉发散试错
      （参数每次微调 → 精确键每次都不同 → 永远不触发升级 → 最终演变成编造结果）。
    """
    window: int = 12
    exact: dict[tuple, int] = field(default_factory=lambda: defaultdict(int))
    by_class: dict[tuple, int] = field(default_factory=lambda: defaultdict(int))
    history: list[tuple] = field(default_factory=list)

    def record(self, tool: str, cls: ErrorClass, locator: str,
               args_fp: str) -> tuple[int, int]:
        exact_key = (tool, cls.value, locator, args_fp)
        class_key = (tool, cls.value)
        self.exact[exact_key] += 1
        self.by_class[class_key] += 1
        self.history.append(exact_key)
        if len(self.history) > self.window:
            old = self.history.pop(0)
            self.exact[old] = max(0, self.exact[old] - 1)
        return self.exact[exact_key], self.by_class[class_key]

    def terminal_status(self, tool: str, cls: ErrorClass,
                        class_count: int) -> Optional[str]:
        """★ 映射到第 2 章的终止状态枚举：升级必须是一个主动产物。"""
        if cls is ErrorClass.TRANSIENT:
            return "error"            # 结果未知 → 必须带幂等键与查询手段
        if cls is ErrorClass.PERMISSION:
            return "need_human"       # 权限：模型无法解决
        if cls is ErrorClass.BUSINESS_RULE:
            return "blocked" if class_count >= 3 else None
        return "need_human" if class_count >= 3 else None


# ==================== 组装：从原始失败到模型可见的 observation ====================
@dataclass
class Adapted:
    observation: str
    log_only: str            # ★ 完整信息进日志（第 2 章轨迹 / 第 7 章归因）
    retryable: bool
    terminal: Optional[str] = None


def adapt(tool: str, failure: ToolFailure, ledger: ErrorLedger,
          args_fp: str) -> Adapted:
    e_exact, e_class = ledger.record(tool, failure.error_class, failure.locator, args_fp)
    obs = render_feedback(failure, e_exact, e_class)
    log = (f"tool={tool} class={failure.error_class.value} code={failure.code} "
           f"exact={e_exact} class_count={e_class} raw={failure.raw[:2000]}")
    return Adapted(observation=obs,
                   log_only=log,
                   retryable=failure.error_class in RETRYABLE,
                   terminal=ledger.terminal_status(tool, failure.error_class, e_class))


if __name__ == "__main__":
    ledger = ErrorLedger()

    # ---- 案例 1：字段名拼错（① 格式错）—— 完整反馈 + 可用字段列表 ----
    f1 = ToolFailure(
        error_class=ErrorClass.FORMAT, code="unknown_field",
        summary="参数 statu 不存在，本次调用未执行任何操作",

        next_action="把 statu 改为 status，取值范围 ['paid','pending','shipped']",

    print("① 首次：")

    print("① 同参数重发：")
    print(adapt("list_orders", f1, ledger, "fp_a").observation, "\n")

    print("① 参数微调后仍失败（类别重复）：")
    for fp in ("fp_b", "fp_c"):
        a = adapt("list_orders", f1, ledger, fp)
        print(a.observation, "| terminal =", a.terminal, "\n")

    # ---- 案例 4：权限错（⑥）→ 升级给人，不含任何内部细节 ----
    f2 = ToolFailure(
        error_class=ErrorClass.PERMISSION, code="auth_scope_missing",
        summary="当前身份缺少该操作的权限，本次调用未执行",
        locator="scope=orders:write",
        expected="需要 orders:write 权限",

        error_class=ErrorClass.TRANSIENT, code="result_unknown",

        locator="idempotency_key=charge:order-9:0",
        expected="同一 idempotency_key 的重试不会重复扣款",
        next_action="原样重试（相同 idempotency_key），或用 get_transaction 核对",
        escalate="若两次核对仍不一致，请生成对账工单并暂停该订单的后续步骤")
    a3 = adapt("transfer_funds", f3, ledger, "fp_e")
    print("⑤ 结果未知：")
    print(a3.observation)
    print("retryable =", a3.retryable, "| log_only(截断) =", a3.log_only[:120], "...")

六处关键设计决策：

  1. ToolFailure 把 raw（原始异常/栈回溯）与 summary/expected 显式分开，render_feedback 永不读取 raw。这是"错误必须被消费一次"在类型层面的强制 —— 想泄露内部细节都得先绕过类型设计。
  2. classify 的顺序是"到达了吗 → 执行了吗 → 权限 → 格式/值域/前置 → 兜底规则拒绝"。顺序是语义的一部分：把 status_code == 500 放到前面会把"结果未知"误判为"可安全重试"（第 2 节里最危险的误判）。
  3. OWNER 与 RETRYABLE 是显式的映射表，且注释里指向第 2 节的 FailureKind —— 分类与重试策略必须共用一份判定，否则两处会漂移出矛盾。
  4. render_feedback 的三档（完整 / 精简+强调 / 只给出口）是 4.2 的直接实现。第三档的核心是改变输入的性质，而不是把同一句话说第三遍。
  5. ErrorLedger 同时维护 exact 与 by_class。类别计数是拦"发散试错"的唯一手段 —— 而发散试错是幻觉的前一步。
  6. adapt 返回 observation 与 log_only 两份产物。log_only 进轨迹（第 2 章）供第 7 章归因，observation 进上下文给模型。给人看的信息量必须 ≥ 给模型的信息量，反过来就是信息泄露。

练习#

  1. 重写错误文案：下面三条是原始反馈，请按 3.1 的六字段与 3.2 的顺序重写，并说明每一处改动减少了哪一类无效行为： （a）Error: 400 Bad Request; （b）KeyError: 'user_id'（附 1200 字符栈回溯）; （c）{"detail": "insufficient balance"}。

  2. 分类练习：为下面八种失败各判定 ①–⑥ 类别、修复主体、是否重试，并写出反馈里必须包含的一句话： （a）amount 传了字符串 "100"；（b）amount 传了 -5；（c）账户余额不足；（d）order_id 不存在；（e）先用 ship 再 pay（顺序错）；（f）HTTP 502；（g）请求发出后客户端超时；（h）缺少 orders:write 权限。

  3. 护栏设计：针对模型在失败后的四种危险倾向（改参数重试、重复提交、编造 ID、绕过权限），各写出一条护栏文案。要求：护栏必须是可执行的行为约束（能对照判断模型是否遵守），而不是"请小心"这类空话。然后说明为什么给模型写护栏是合理的，而"把终止判据写进提示词"是不合理的（提示：前者防有害动作，后者泄露答案）。

  4. 重复检测的阈值：某 Agent 的轨迹显示，它在失败后平均会尝试 4.2 次不同的参数。请设计你的升级阈值：精确重复阈值、类别重复阈值、窗口大小。若类别重复阈值设成 5 会怎样？设成 2 呢？给出一个可测量的选择依据（提示：用离线轨迹统计"第 n 次失败后成功修复"的比例）。

  5. 信息泄露审计：给定一条真实风格的错误反馈（你自己编造一个含 3 处泄露的），指出三处泄露、各自的攻击面（枚举攻击 / 注入素材 / 凭据泄露），并给出改写。特别说明 403 与 404 的区分在 Agent 循环里会怎样被"学会利用"。

  6. 从失败到幻觉：构造一个具体场景：某工具连续返回同一句 Error: invalid request，模型在第 4 次失败后开始输出"根据我的分析，该数据为 X"并继续后续步骤。请写出这条轨迹里模型每一步的输入（错误反馈）与它可能的内在推理，指出哪一步的信息缺失导致了幻觉，并给出修复方案（要具体到反馈文案与升级条件）。

小结#

  • 异常不是反馈。原样抛出有三重代价：可行动信息为零却占满 token（稀释注意力）、模型会去"修"栈回溯里的内部细节、泄露内部结构给一个可被注入的组件。
  • 完整信息不能丢，只是不给模型：raw 进日志/轨迹（供第 7 章归因），feedback 进上下文。给人看的信息量必须 ≥ 给模型的信息量。
  • 分类的主键是"模型能采取什么不同动作"，不是异常类型。六类：格式错 ①、值域/语义错 ②、业务规则 ③、前置缺失 ④、瞬态 ⑤、权限 ⑥。①②④ 是模型能自修的（高价值反馈），③⑥ 必须给升级路径。
  • 顺序即语义：分类必须先回答"请求到达了吗 / 执行了吗"，再细分。把 500 放在前面会把"结果未知"误判为"可安全重试"。
  • ⑤ 类通常不该给模型看（框架职责）；只有重试用尽后才交给模型，且必须附带"结果是否未知"。分类与重试策略必须共用一份判定，否则两处漂移出矛盾。
  • 反馈六字段：状态 / 定位 / 期望 / 下一步（只给一个） / 护栏（针对模型倾向）/ 升级路径。护栏必须写（防有害动作），答案不能写（不自造 ID、不泄露合法集之外的探测路径）。
  • 重复错误必须改变输入的性质：第 1 次给完整反馈、第 2 次精简并强调唯一可能被忽略的信息、第 3 次起停止重复细节（同一个输入不会产生不同输出），改为宣告"局部失败"并给出口。
  • 必须同时检测精确重复与类别重复：只看精确重复会漏掉发散试错，而发散试错是幻觉的前一步（"工具不可用，我根据经验推测……"是 Agent 最贵的事故）。
  • 绝不能出现在反馈里：栈回溯/内部路径、SQL 与表结构、凭据、无权资源的"存在性"（403 vs 404 的区分会被学会利用）、内部阈值数值、他人数据。

下一节：单个工具的契约已经可靠了。但当你把工具从 10 个加到 40 个，会出现三类新问题：模型开始选错工具、描述里的一句话能改变整个选择分布、以及工具描述与返回值都成了攻击通道。这是本章的最后一节，也是安全边界正式登场的地方。
