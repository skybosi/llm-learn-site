三种记忆的职责与写入时机：工作记忆、长期记忆、检索式记忆#

这一节要解决什么#

先纠正一个起点错误：上下文窗口不是记忆。 它是 Agent 的工作区（寄存器 / 栈），不是存储。两者的差别不是容量，而是四条性质：

性质 上下文窗口 记忆
持久性 进程结束即消失 跨会话存活
容量 硬上限，满了必须丢弃 可增长（代价是检索难度）
可检索 没有索引，只有位置 有键/向量/图上的索引
可遗忘 只能整体丢弃或压缩 可以按条删除、衰减、设 TTL

把这两者混为一谈，会同时产出两种相反的病："记不住"（把该持久的东西留在上下文里，进程一重启就没了）和 "记错"（把上下文里的一切不加区分地写进持久存储，包括模型的猜测和过时的中间结论）。

所以这一节的第一个任务是把"记忆"从一个大词拆成三种生命周期完全不同的东西。

学完这一节你应该能回答：

  • 一段"用户偏好简洁的报表"应该写进哪种记忆？写在什么结构里？什么时候写？
  • 为什么工作记忆必须是结构化的，而不能就是"消息列表"？
  • 为什么长期记忆的写入需要验证门槛，而工作记忆不需要？
  • "检索式记忆"和 RAG 有什么本质差别？（不是"都是向量检索"。）
  • 三种记忆的更新频率差了几个数量级，这对系统设计意味着什么？

一、分解的依据：按生命周期，而不是按存储#

1.1 一个常见的错误分类#

很多资料把记忆分成"短期记忆 / 长期记忆"，或者按存储介质分成"向量库 / 关系库 / 图数据库"。前者太粗（会把工作记忆和会话内的观察混为一谈），后者是实现而不是职责（同一个向量库可以承载完全不同的两种记忆）。

正确的分解依据是生命周期：

记忆类型=(存活范围, 写入触发, 读取代价, 失效方式)

按这个四元组拆，得到三种彼此不重叠的类型：

工作记忆（working） 长期记忆（long-term） 检索式记忆（episodic / retrieval）
存活范围 单次任务 / 单次 run 跨任务、跨会话，永久或有 TTL 跨任务，累积后按需检索
内容 当前任务的结构化状态 稳定的事实与偏好（去语境化） 过去的轨迹与经验（带语境）
写入触发 每步都写（状态转移即写） 验证后写（罕见，低频） 任务结束时写（中频，附结果标签）
读取方式 直接读字段（O(1)，无检索） 按主体键精确读（O(1)）+ 少量语义检索 按情境检索（O(logn) 近似最近邻 + 重排）
失效方式 任务结束即丢弃（或归档进③） 显式撤销 / TTL / 版本 衰减 + 被更好的经验覆盖
写错的后果 本任务跑偏（可见、可回退） 跨任务持续污染（不可见） 检索到错误的先例，模仿错误做法
容错要求 中等（可重算） 最高（一旦污染，影响面无限） 高（错误先例会被复制）

这张表的读法是"写入频率与容错要求成反比"：

写入频率↑⟺单条写入的容错要求↓

工作记忆每步都写，所以它必须便宜、可覆盖、可丢弃 —— 它容错的方式是"下一步会修正它"。长期记忆几乎不写，但每一条都可能影响未来所有任务 —— 它容错的方式只能是写之前验证。把这两个要求弄反（长期记忆随手写、工作记忆谨慎写）是最常见的架构错误。

1.2 三种记忆各自的"一句话职责"#

把上面的表压缩成可以贴在设计文档里的三句话：

工作记忆：让"当前这个任务"在下一步仍然是同一个任务（连贯性）。
长期记忆：让"未来的任务"不必重新学习已经确定的事实（省重复劳动）。
检索式记忆：让"类似的情境"可以复用过去的做法与教训（经验迁移）。

这三句话对应三种不同的失败：

  • 工作记忆坏 → 任务断裂（重复做已完成的事、丢失已确认的约束、前后矛盾）
  • 长期记忆坏 → 持续放错（把过时/错误的事实当真理，且每用一次就强化一次）
  • 检索式记忆坏 → 错误模仿（检索到一个看似相似的失败先例，复制它的做法）

二、工作记忆：结构化任务状态#

2.1 为什么不能就是"消息列表"#

最省事的做法是把工作记忆实现为 messages: list[dict]（对话历史）。它的三个致命缺陷：

缺陷 机制 后果
状态隐含在文本里 "做到哪了"要靠模型从历史里推断 推断会错；无法程序化检查
无法检查不变量 没有字段可以断言（"已经付过款了吗"） 重复副作用（第 3 章）、自相矛盾
无法恢复 恢复只能靠重放整个消息列表，且模型每次读出的理解可能不同 崩溃恢复不可靠（第 4 节）

结论：工作记忆必须有一份结构化的状态对象，消息列表只是它的渲染形式。

上下文里的对话=render(状态对象, 最近的观察)

这个区分有一个立即可验证的好处：状态对象可以被断言。 你可以在每一步开始前检查不变量：

assert not (state.paid and state.refunded), "已付款又已退款：状态矛盾"
assert state.step <= state.budget_steps, "步数超预算"
assert state.pending_approval is None or state.committed, "审批未完成却已提交"

这类断言在"消息列表"实现里是写不出来的。

2.2 任务状态的四个正交维度#

一个实用的工作记忆 schema 可以按四个维度组织（正交意味着任意组合都合法，这让状态空间可管理）：

维度 内容 更新频率 例子
目标（goal） 要达成什么、验收标准、硬约束 几乎不变 objective, acceptance, hard_constraints
进展（progress） 已完成的子目标、当前阶段、待办 每步 done: [...], phase, todo: [...]
世界模型（world） 已知的事实（观察结果的摘要）、已知的实体 ID 每步 entities: {order_id: ...}, facts: {...}
执行元数据（meta） 预算、步数、幂等键、审批状态、错误计数 每步 steps, tokens_used, idem_keys, error_counts

"世界模型"这一维要特别小心：它存的是观察的摘要，而摘要必然有损（下一节展开）。所以规则是：

world 里存"可核验的指针"优先于"模型的总结"

即 {"order_id": "o_123", "status_observed": "paid", "observed_at_step": 7} 好过 {"order_summary": "这个订单看起来已经付款了，客户应该是在上周下的单"}。

2.3 写入时机：每步两次，位置固定#

工作记忆的写入时机是确定的，两次：

步 t 开始时：读状态 → 组装上下文（第 3 节）→ 模型决策
步 t 结束时：决策落地为状态转移 → 写状态（★ 与轨迹同时写，见第 4 节）

关键规则：状态转移必须与轨迹写入在同一个原子步骤里完成。 若先执行了副作用、再写状态，中间崩溃就会出现"世界变了但状态不知道"（第 3 章的未知区间在状态层的版本）。正确顺序：

T1​: 写"将要执行"→T2​: 执行副作用（带幂等键）→T3​: 写"已执行 + 结果"→commit

这里 T1/T2/T3 不必是数据库事务（副作用在外部系统，做不到）。但检查点必须记录 T1 已写，这样恢复时才知道"这一步可能已经执行了"，从而走幂等去重而不是盲目重放。这正是第 3 节幂等键与第 4 节重放的接合点。

2.4 工作记忆的容量与"重算 vs 保留"#

工作记忆不需要全部进上下文。一个实用的分档：

分档 内容 进上下文？
必须每步可见 目标、硬约束、当前阶段、待办 ✓ 全量
按需可见 已收集的实体 ID 列表、已完成子目标的结论 ✓ 摘要形式（引用/列表）
仅在轨迹里 每一步的完整输入输出、原始观察 ✗（可检索，见第 3 节）
可重算 从原始观察可推导的中间量 ✗（宁可重算）

最后一行是一条重要准则：

若某信息可由已保存的原始数据重算，就不要单独存它

理由与"单一事实来源"同理：存了两份，就有不一致的可能；而不一致的中间量是最难归因的 bug（第 7 章的"记忆错"象限）。

三、长期记忆：去语境化的事实与偏好#

3.1 长期记忆的判据：去语境化#

一条信息是否该进长期记忆，有一个清晰的判据：

该进长期记忆⟺去掉"这次任务"的语境后，它仍然成立且有用

候选 去语境化后还有用？ 结论
"用户希望报表用千分位分隔符" ✓（对未来的报表任务成立） 进长期记忆（偏好）
"本次任务的订单 o_123 已付款" ✗（只对这次任务有意义） 工作记忆
"该客户的发票抬头是 XX 公司" ✓（未来开票都要用） 进长期记忆（事实），但需要时效性
"上次查库存时 API 报了 500" ✗（一次性的瞬态故障） 不进（或只进轨迹）
"用户拒绝了删除操作，理由是不合规" ✓（这可能是一条约束偏好） 进长期记忆，附来源与时间

最后一行值得展开：拒绝行为会产生一条否定的偏好（"不要自动删除"），它比肯定偏好更重要，也更容易被漏掉 —— 因为它不在用户的显式指令里，而在行为里。这类记忆的写入需要从行为中提取策略（第 5 章的规划会因为这条约束而改变）。

3.2 结构：类型化条目，不是自由文本#

自由文本的长期记忆（"用户说报表要简洁，上次还提到过不要太多颜色"）有三个问题：无法按主体检索、无法撤销单条、无法判断时效。所以长期记忆应当是类型化条目：

{
  "mem_id": "m_7f21",
  "type": "preference",              // fact | preference | constraint | identity
  "subject": "user:u_8f3a",
  "key": "report.number_format",
  "value": "thousands_separator",
  "confidence": 0.9,
  "source": "user_message:msg_5512",  // ★ 可追溯：哪条原始输入产生它
  "verified": true,                   // ★ 是否被显式确认过（vs 模型推断）
  "created_at": "2026-02-14T10:02:00Z",
  "ttl_seconds": null,                 // 偏好可永久；事实类常需要 TTL
  "supersedes": null                   // ★ 版本链：新值替代旧值，而不是覆盖
}

四个字段承担的职责：

字段 承担的职责 缺了会怎样
source 可追溯 / 可撤销 / 可审计 无法判断这条记忆是否可信，也无法在源被删除时连带清理
verified 区分"用户说的"与"模型猜的" 幻觉与事实混在一起（下一节的核心问题）
ttl_seconds 时效性：事实会过期，偏好不会 三年前的"客户地址"被当现值用
supersedes 版本链：保留历史 覆盖式更新后，无法回答"它什么时候变的、为什么变"

supersedes 这一项体现的是一条通用架构原则：记忆应当是追加式日志 + 派生视图，而不是原地覆盖。

memorycurrent​=fold(append-only log of assertions)

好处有三：不丢历史（可审计、可回滚）、并发写不互相覆盖（两条冲突的断言都留下，供矛盾检测）、撤销变成"追加一条撤销断言"而不是删除（删除是不可逆的）。

3.3 写入时机：三个门槛#

长期记忆的写入频率必须极低。用一道三级门槛控制：

门槛 1（候选）：这条信息是否"去语境化后仍有用"？（3.1 的判据）
门槛 2（验证）：它的来源是什么？
    · 用户显式陈述 → 可写，verified=true
    · 工具的确定性返回值 → 可写，verified=true，附 fetched_at
    · 模型推断/总结 → ★ 默认不写；必须经"确认"才能写（见门槛 3）
门槛 3（确认的形式）：模型的推断只能作为"候选断言"存在 pending 区，
    在满足下列任一条件后转正：
      · 用户在后续交互中确认；
      · 被至少 k 个独立来源佐证（k=2 起）；
      · 它是"可核验的指针"（如 ID 映射），而非"结论"。

门槛 2 的分类是这一节最重要的一条规则：它把第 3 章"事实 vs 声明"的区分用到了记忆上。

写入权限={直接写pending（待验证）​来源：用户显式陈述 / 工具确定性返回来源：模型推断 / 第三方内容 / 摘要​

为什么模型的推断默认不写？因为它可能是幻觉，而且一旦写入就会被反复读取并强化（下一节的"幻觉固化"）。让它在 pending 区等一等，成本几乎为零；放它直接进长期记忆，代价是无限的污染面。

3.4 长期记忆的读取：按主体 + 按需#

读取的方式决定了它是否值得存在：

读取方式 实现 延迟 适用
按主体精确读 get(subject, key) 微秒级 偏好、身份、稳定事实 —— 主力
按主体全量读 get_all(subject) 微秒级 任务开始时装载"关于这个用户我知道什么"（要有条数上限）
语义检索 向量召回 + 重排 毫秒级 事实条目很多、key 不确定时

主力应当是精确读：因为长期记忆的条目本来就不多（一个用户几十条），而精确读没有召回失败的问题。把长期记忆做成"一个向量库"是常见的过度设计 —— 它在条目少时比精确读更差（有召回失败，且无法解释为什么没读到）。

装载策略（任务开始时读多少）：按预算定上限，而不是"全读"：

装载条数≤⌊Lavg_entry​Bmemory​​⌋

超出时要按"与当前任务的相关性 × 重要性 × 新近度"排序截取，并且截取这件事必须被记录（否则你会以为"Agent 不记得"，实际是"没装载"）。

四、检索式记忆：带语境的过去经验#

4.1 与 RAG 的本质差别#

检索式记忆听起来像 RAG（都是"向量检索 + 塞进上下文"），但两者的对象与用途完全不同：

RAG 的外部知识 检索式记忆
检索对象 文档 / 知识片段 过去的轨迹与结论（含做法、失败、代价）
检索依据 与问题的语义相似 与当前情境的相似（任务类型 + 状态 + 约束）
用途 补充事实 复用做法 / 避免重蹈覆辙
关键元数据 来源、时间 结果标签（成功/失败）、代价、当时的约束
失效方式 文档更新即失效 衰减：旧经验价值下降，且环境变了会误导

第四行是本质：检索式记忆的每一条都必须带结果标签，否则你会在"看起来相似"的先例里检索到一个失败的做法并复制它。这是检索式记忆最常见的失效模式（第三节的"错误模仿"）。

4.2 条目结构：经验单元#

{
  "ep_id": "e_31b0",
  "task_type": "arxiv_digest",           // ★ 情境归纳键（用于"相似情境"检索）
  "situation": {
    "goal": "汇总当日 LLM 推理论文",
    "constraints": ["只保留有代码的", "上限 8 篇"],
    "tools_available": ["arxiv_search", "pdf_extract"]
  },
  "approach": [                            // ★ 做法（可复用）
    "先按 cs.CL 分类检索再按引用数排序",
    "用 pdf_extract 抓摘要而不是全文（省 token）"
  ],
  "outcome": "success",                    // ★ 结果标签：success | partial | failure
  "lesson": "全文抓取会超预算；摘要足够判定相关性",
  "cost": {"tokens": 41000, "steps": 9, "seconds": 74},
  "created_at": "2026-02-20T02:00:00Z",
  "model_version": "…",                    // ★ 环境指纹：换模型后经验可能失效
  "hit_count": 3, "last_hit_at": "…"        // 衰减与价值统计
}

三个容易忽略的字段：

  • model_version / tool_versions：经验是有环境的。一个在旧模型上"必须拆两步"的经验，在新模型上可能是过度保守。环境指纹让检索时能降权过期经验。
  • cost：经验的价值不只是"能不能成"，还有"多贵"。检索时应当偏好同等成功率下更便宜的先例。
  • hit_count / last_hit_at：用于衰减评分（下一节）与"这条经验到底有没有用"的反馈。

4.3 写入时机：任务结束时写一次，且必须带结果#

任务结束（任何终止状态，含 budget_steps / blocked / error）
  → 生成一条经验单元
  → 打上结果标签
  → 写入（★ 成功与失败都要写）

失败的经验必须写，而且往往更有价值："上次走这条路预算耗尽了"。只写成功经验是常见错误 —— 它让检索式记忆只提供"正面先例"，而 Agent 最需要的是避免重复的坑。

写入时的一个纪律：lesson 字段必须是可操作的一句话，而不是泛泛的总结。

好的 lesson=条件+动作+后果(“当 X 时不要做 Y，因为 Z”)

反例："需要注意预算控制。"（无法据此行动） 正例："当目标论文数 > 10 时不要抓全文，会超 60k token 预算；用摘要筛选后再抓 top-3。"

4.4 检索式记忆的两个陷阱#

陷阱 机制 缓解
表面相似 ≠ 情境相同 向量相似度匹配的是文字，而"情境"包含约束与工具集 检索时把约束/工具集作为过滤条件（不只靠向量），并在条目里显式存 constraints
先例的幸存者偏差 库里成功案例多、失败案例少（因为失败常被忽略不写） 强制"失败也写"，并在检索时分别按结果标签取回（成功先例 + 失败先例各取 k 条）

第二个陷阱的缓解手段值得写成规则：

检索=top-ksuccess​∪top-kfailure​(分别检索，再合并)

这保证上下文里同时有"该怎么做"和"别怎么做"两类信息。

4.5 三种记忆的读写频率：一个数量级对比#

把整节的内容压成一张"频率表"，它决定了实现的复杂度分配：

工作记忆 长期记忆 检索式记忆
写频率 每步（10 数量级/任务） 每几十个任务一条 每任务一条
读频率 每步 任务开始装载一次 任务开始或需要建议时
存储量增长 任务内线性（任务结束归档） 极慢 线性（需衰减）
该投入的工程 快、原子、可序列化 准、可追溯、可撤销 检索质量、结果标签、衰减

一个推论：如果你发现自己在给工作记忆做复杂的冲突消解，那你多半把该进长期记忆的东西放错了地方；反过来，如果你在给长期记忆做"每步更新"，那你在制造污染。

代码：三层记忆骨架 + 写入门槛 + 归档#

下面的代码实现：(1) 结构化工作记忆（含不变量断言与两阶段写入）；(2) 长期记忆（追加式日志 + 验证状态 + 时效 + 精确读）；(3) 检索式记忆（经验单元 + 按结果标签分别检索）；(4) 任务结束时的归档流程（把工作记忆的纯逻辑部分转成经验，把该持久的事实送进长期记忆门槛）。

import time
from dataclasses import dataclass, field, asdict
from typing import Any, Optional


# ==================== (1) 工作记忆：结构化任务状态 ====================
@dataclass
class WorkingMemory:
    """
    ★ 设计决策：工作记忆是一个**可断言的对象**，不是消息列表。
      消息列表只是它的渲染形式；"做到哪了"必须是可程序化检查的字段，
      否则无法恢复、无法校验、无法防止重复副作用（第 3 章）。
    """
    run_id: str
    objective: str
    acceptance: list[str] = field(default_factory=list)          # 验收标准
    hard_constraints: list[str] = field(default_factory=list)    # 硬约束（AND 守，第 2 章）
    phase: str = "plan"                                          # 当前阶段
    done: list[str] = field(default_factory=list)                # 已完成的子目标
    todo: list[str] = field(default_factory=list)
    entities: dict[str, Any] = field(default_factory=dict)        # 世界模型：ID 与可核验指针
    facts: dict[str, Any] = field(default_factory=dict)           # 世界模型：观察摘要（★ 尽量存指针）
    # 执行元数据
    step: int = 0
    budget_steps: int = 15
    tokens_used: int = 0
    idem_keys: dict[str, str] = field(default_factory=dict)       # (tool, attempt) -> key
    error_counts: dict[str, int] = field(default_factory=dict)    # 第 3 章的重复检测
    pending_effect: Optional[dict] = None   # ★ 两阶段写入的"将要执行"槽位
    paid: bool = False
    refunded: bool = False

    # ---- 不变量：这是结构化工作记忆相对"消息列表"的核心优势 ----
    def check_invariants(self) -> list[str]:
        bad = []
        if self.paid and self.refunded:
            bad.append("已付款又已退款：状态矛盾")
        if self.step > self.budget_steps:
            bad.append("步数超预算却仍在推进")
        if self.pending_effect is not None:
            bad.append("存在未结算的副作用：必须先经幂等去重确认其状态，不可盲目重放")
        if set(self.done) & set(self.todo):
            bad.append("同一子目标同时出现在 done 与 todo")
        return bad

    # ---- 两阶段写入：先记"将要执行"，再执行，再结算 ----
    def mark_pending(self, tool: str, args: dict, idem_key: str) -> None:
        """
        ★ 设计决策：副作用之前先落检查点。这样崩溃恢复时能知道"这一步可能已执行"，
          从而走幂等去重（第 3 章）而不是盲目重放。
        """
        self.pending_effect = {"tool": tool, "args": args, "idem_key": idem_key,
                               "step": self.step, "at": time.time()}
        self.idem_keys[f"{tool}@{self.step}"] = idem_key

    def settle_pending(self, result_summary: str) -> None:
        self.facts[f"step_{self.step}_result"] = result_summary
        self.pending_effect = None

    def render(self, max_facts: int = 8) -> str:
        """★ 设计决策：进上下文的是**渲染后的摘要**，而不是整个状态对象。
        完整状态留在检查点里（第 4 节），上下文只带当前决策需要的那部分。"""
        lines = [f"目标: {self.objective}",
                 f"阶段: {self.phase} | 步 {self.step}/{self.budget_steps}",
                 f"已完成: {self.done or '（无）'}",
                 f"待办: {self.todo or '（无）'}",
                 f"硬约束: {self.hard_constraints or '（无）'}"]
        if self.entities:
            lines.append(f"已知实体: {list(self.entities)[:10]}")
        for k, v in list(self.facts.items())[-max_facts:]:
            lines.append(f"  · {k}: {v}")
        if self.pending_effect:
            lines.append(f"⚠ 未结算副作用: {self.pending_effect['tool']} "
                         f"(idem_key={self.pending_effect['idem_key']})")
        return "\n".join(lines)


# ==================== (2) 长期记忆：追加式日志 + 三级门槛 ====================
SOURCES_TRUSTED = ("user_explicit", "tool_deterministic")


@dataclass
class MemoryAssertion:
    """★ 设计决策：记忆是"断言日志"，不是"当前值表"。撤销 = 追加一条撤销断言。"""
    mem_id: str
    type: str                     # fact | preference | constraint | identity
    subject: str
    key: str
    value: Any
    source: str
    verified: bool
    created_at: float
    ttl_seconds: Optional[float] = None
    supersedes: Optional[str] = None
    revoked: bool = False

    def expired(self, now: float) -> bool:
        return self.ttl_seconds is not None and (now - self.created_at) > self.ttl_seconds


class LongTermMemory:
    def __init__(self, now_fn=time.time):
        self.now = now_fn
        self.log: list[MemoryAssertion] = []
        self._pending: list[MemoryAssertion] = []      # ★ 模型推断的暂存区
        self._seq = 0

    def propose(self, type_: str, subject: str, key: str, value: Any,
                source: str) -> dict:
        """
        ★ 设计决策：写入权限由来源决定（3.3 门槛 2）：
          用户显式陈述 / 工具确定性返回 → 直接写；
          模型推断 / 第三方内容         → 进 pending，等待确认。
          这是防止"幻觉固化"的第一道也是最重要的一道闸。
        """
        self._seq += 1
        entry = MemoryAssertion(
            mem_id=f"m_{self._seq:04d}", type=type_, subject=subject, key=key,
            value=value, source=source,
            verified=source in SOURCES_TRUSTED, created_at=self.now())
        if source in SOURCES_TRUSTED:
            self.log.append(entry)
            return {"written": True, "mem_id": entry.mem_id, "verified": True}
        self._pending.append(entry)
        return {"written": False, "pending": True,
                "hint": "来源为模型推断：进入待验证区。需用户确认或两个独立来源佐证后才能转正。"}

    def confirm(self, mem_id: str, by: str, evidence: int = 1) -> bool:
        """转正：pending → log。★ 保留 source 与确认者，便于审计。"""
        for e in list(self._pending):
            if e.mem_id == mem_id and evidence >= 1:
                e.verified = True
                e.source = f"{e.source}+confirmed_by:{by}"
                self.log.append(e)
                self._pending.remove(e)
                return True
        return False

    def revoke(self, mem_id: str, reason: str) -> None:
        """★ 撤销是追加，不是删除：历史必须可审计（3.2）。"""
        for e in self.log:
            if e.mem_id == mem_id:
                e.revoked = True
                self.propose("fact", e.subject, f"__revoked__{e.key}", reason, "user_explicit")

    def get(self, subject: str, key: str) -> Optional[Any]:
        """精确读：主力读取方式（3.4）。取最后一条未撤销且未过期的断言。"""
        now = self.now()
        hits = [e for e in self.log
                if e.subject == subject and e.key == key
                and not e.revoked and not e.expired(now)]
        return hits[-1].value if hits else None

    def snapshot(self, subject: str, limit: int = 20) -> list[dict]:
        now = self.now()
        entries = [e for e in self.log
                   if e.subject == subject and not e.revoked and not e.expired(now)]
        # ★ 装载必须限量并记录截断（3.4）—— 否则会被误读成"Agent 不记得"
        return [asdict(e) for e in entries[-limit:]] + (
            [{"truncated": True, "total": len(entries)}] if len(entries) > limit else [])


# ==================== (3) 检索式记忆：经验单元 + 分标签检索 ====================
@dataclass
class Episode:
    ep_id: str
    task_type: str
    situation: dict
    approach: list[str]
    outcome: str                  # success | partial | failure
    lesson: str                   # ★ 条件 + 动作 + 后果
    cost: dict
    created_at: float
    env: dict = field(default_factory=dict)      # model_version / tool_versions
    hit_count: int = 0
    last_hit_at: float = 0.0


class EpisodicMemory:
    """
    ★ 设计决策：不做真正的向量检索（那是实现细节），
      但把"检索契约"固定下来：按 task_type 过滤 + 成功/失败**分别**取回。
      检索是接口，向量库只是其中一种实现。
    """
    def __init__(self, now_fn=time.time, half_life_days: float = 60.0):
        self.now, self.half_life = now_fn, half_life_days * 86400.0
        self.items: list[Episode] = []
        self._seq = 0

    def write(self, ep: Episode) -> None:
        """★ 成功与失败都写。只写成功会造成幸存者偏差（4.4）。"""
        assert ep.outcome in ("success", "partial", "failure")
        assert ep.lesson and len(ep.lesson) > 8, "lesson 必须是可操作的一句话"
        self.items.append(ep)

    def record_from_working(self, wm: WorkingMemory, outcome: str,
                            lesson: str, cost: dict, task_type: str,
                            env: dict) -> Episode:
        self._seq += 1
        ep = Episode(ep_id=f"e_{self._seq:04d}", task_type=task_type,
                     situation={"goal": wm.objective,
                                "constraints": wm.hard_constraints,
                                "entities": list(wm.entities)[:5]},
                     approach=[f"phase={wm.phase}"] + wm.done[-4:],
                     outcome=outcome, lesson=lesson, cost=cost,
                     created_at=self.now(), env=env)
        self.write(ep)
        return ep

    def retrieve(self, task_type: str, k_success: int = 3,
                 k_failure: int = 2) -> dict:
        """
        ★ 设计决策：成功与失败**分别**检索再合并（4.4 的缓解手段）。
          同池检索会让失败先例（通常更少）被成功先例挤出上下文。
        """
        def score(e: Episode) -> float:
            age = self.now() - e.created_at
            decay = 0.5 ** (age / self.half_life)          # 半衰期衰减
            value = 1.0 + 0.1 * min(e.hit_count, 10)        # 被证明有用的加权
            return decay * value

        pool = [e for e in self.items if e.task_type == task_type]
        succ = sorted([e for e in pool if e.outcome == "success"],
                      key=score, reverse=True)[:k_success]
        fail = sorted([e for e in pool if e.outcome in ("failure", "partial")],
                      key=score, reverse=True)[:k_failure]
        for e in succ + fail:
            e.hit_count += 1
            e.last_hit_at = self.now()
        return {"do_this": [asdict(e) for e in succ],
                "avoid_this": [asdict(e) for e in fail]}


# ==================== (4) 归档：任务结束时把信息送到正确的层 ====================
def archive(wm: WorkingMemory, ltm: LongTermMemory, epm: EpisodicMemory,
            terminal_status: str, cost: dict, task_type: str,
            env: dict, candidate_facts: list[dict]) -> dict:
    """
    ★ 设计决策：归档是一个**显式的分流步骤**，不是自动行为。
      它强制回答两个问题：哪些是"去语境化后仍成立的事实"（→ 长期记忆门槛），
      这次任务教了什么（→ 经验单元，成功与失败都写）。
    """
    routed = {"to_long_term": [], "to_episodic": [], "discarded": []}

    for cand in candidate_facts:
        # 门槛 1：去语境化后仍有用吗？
        if not cand.get("context_free"):
            routed["discarded"].append({"key": cand["key"], "why": "依赖本次任务语境"})
            continue
        res = ltm.propose(cand["type"], cand["subject"], cand["key"],
                          cand["value"], cand["source"])
        routed["to_long_term"].append({"key": cand["key"], **res})

    lesson = (f"以 phase={wm.phase} 结束并返回 {terminal_status}；"
              f"已完成 {len(wm.done)} 个子目标、剩余 {len(wm.todo)} 个"
              f"（{', '.join(wm.todo[:3]) or '无'}）")
    ep = epm.record_from_working(
        wm, outcome=("success" if terminal_status == "done" else
                     "failure" if terminal_status in ("error", "violation") else "partial"),
        lesson=lesson, cost=cost, task_type=task_type, env=env)
    routed["to_episodic"].append(ep.ep_id)

    # ★ 工作记忆里"可重算"的部分不单独存（2.4）；只把轨迹留给第 2 章的存储
    routed["discarded"].append({"key": "raw_observations",
                                "why": "已在轨迹中，可由轨迹重算，不重复存储"})
    return routed

七处关键设计决策：

  1. WorkingMemory 是一个可断言的对象：check_invariants 能检查出"已付款又已退款""存在未结算副作用"这类在消息列表里无法发现的状态矛盾。这是"结构化工作记忆"相对"消息列表"的唯一核心优势，也是崩溃恢复的前提。
  2. mark_pending / settle_pending 把副作用之前的检查点显式化。这就是第 3 章未知区间在状态层的落地：恢复时看到 pending_effect 未清空，就知道"这一步可能已经执行"，必须先走幂等去重。
  3. render 只输出摘要，完整状态留在检查点里。工作记忆不等于"要全部进上下文"（2.4 的分档）。
  4. LongTermMemory.propose 用来源决定写入权限：user_explicit / tool_deterministic 直接写，model_inference 进 _pending 等确认。这一行是防"幻觉固化"最重要的一道闸（下一节展开）。
  5. 记忆是追加式日志（log + revoked 标记 + supersedes），撤销是追加而非删除。这让历史可审计、并发写不互相覆盖、并为下一节的矛盾检测留出数据基础。
  6. EpisodicMemory.retrieve 分别取回成功与失败先例。同池检索会让失败先例（通常更少）被挤出上下文，导致 Agent 只看到"别人怎么成功"，看不到"别人怎么踩坑"。
  7. archive 是一个显式分流步骤：它强制回答"哪些去语境化后仍成立""这次教了什么"，并且把"可由轨迹重算"的信息明确丢弃（2.4 的单一事实来源）。

练习#

  1. 分层判定：把下面八条信息分到工作记忆 / 长期记忆 / 检索式记忆 / 不进记忆，并说明理由（要引用去语境化判据与写入门槛）： （a）用户说"以后报表都用中文"；（b）本次任务的 order_id 列表；（c）某工具在高并发下会限流；（d）用户没有明说但连续三次把英文报表退回；（e）这次调用返回的原始 JSON；（f）客户的营业执照号；（g）本次任务在第 12 步耗尽预算；（h）某个内部 API 的字段名拼写。

  2. 工作记忆的 schema：为"自动把论文草稿格式化成期刊模板并提交"的 Agent 设计完整的工作记忆 schema。要求：四个维度（目标/进展/世界模型/执行元数据）都要有字段；写出至少五条 check_invariants 断言；并指出哪些字段不应该进上下文渲染（要说明理由）。

  3. 幻觉固化的预防：某 Agent 把模型的一次推断"客户是制造业企业"写进了长期记忆（source=model_inference）。请设计三条独立的防线来阻止它，并说明每条防线在哪一层（写入门槛 / 存储结构 / 读取过滤）。然后论证：为什么"让模型自己判断这条推断是否可信"不是一条有效防线？

  4. 频繁更新的长期记忆：如果业务要求"每次用户交互后都更新用户画像"，请给出一个既能满足业务、又不违反 3.3 三级门槛的设计。要求说明：哪些字段是"断言"（可追加）、哪些是"派生视图"（可重算）、以及为什么"派生视图"不能被当成记忆条目来写。

  5. 检索式记忆的陷阱：某团队的检索式记忆库里 92% 是成功案例。请解释这会产生什么行为偏差（要给出具体任务场景），并设计修正方案：如何强制写入失败经验？如何在检索端保证失败先例进入上下文？如何度量"这个修正真的起作用了"？

小结#

  • 上下文窗口不是记忆：它是工作区（易失、有硬上限、无索引、不可按条遗忘）。把它当记忆会同时产出"记不住"和"记错"。
  • 分解依据是生命周期，不是存储介质：工作记忆（单任务、每步写）/ 长期记忆（跨会话、验证后写）/ 检索式记忆（跨任务、任务结束时写）。核心规律是 写入频率与单条容错要求成反比。
  • 工作记忆必须是结构化的状态对象，消息列表只是它的渲染形式。结构化带来三个能力：可断言不变量、可程序化检查"做到哪了"、可恢复。副作用之前必须落检查点（pending_effect），这样恢复时才不会盲目重放。
  • 长期记忆的判据是去语境化：去掉"这次任务"的语境后仍成立且有用。结构上必须是类型化条目 + 追加式日志（含 source / verified / ttl / supersedes），撤销是追加而不是删除。
  • 写入门槛由来源决定：用户显式陈述与工具确定性返回可直接写；模型推断默认不写（进 pending 等确认）。这是防止幻觉固化的第一道闸。读取的主力是按主体精确读，不是向量检索。
  • 检索式记忆与 RAG 的本质差别是"带结果标签的经验"：条目必须记录 outcome / cost / env / lesson（条件+动作+后果）。失败经验必须写，并且检索时要成功与失败分别取回（否则失败先例会被挤出上下文）。
  • 单一事实来源：可由轨迹或原始数据重算的信息不要单独存 —— 存两份就有不一致的可能，而不一致的中间量是最难归因的 bug。
  • 归档是显式分流，不是自动行为：它逼你回答"哪些是去语境化后仍成立的事实""这次教了什么"。

下一节：三种记忆的职责分清了。但真正的难点在写什么、写多少、什么时候必须忘。记忆的容量不是瓶颈，写入纪律才是 —— 一条错误的记忆会被反复读取并自我强化。这一节要处理记忆污染的三个机制与它们的检测手段。
