状态机 vs 无状态重放：崩溃恢复与可复现性#

这一节要解决什么#

一个跑了 40 步、花了 3 块钱的 Agent 任务在第 41 步崩了。你有两个选择：

① 载入检查点，从第 41 步继续       ← 状态机路线
② 从头再跑一遍                      ← 无状态重放路线

这个选择看似是工程偏好，实际由三个可以量化的量决定：检查点的成本、重放的确定性、以及副作用的重放安全性。这一节要把这三个量算清楚，并说明为什么纯靠其中一条路线都不成立，正确的形态是两者的组合。

先把这一章前面三节的线索收拢：第 1 节说工作记忆必须是结构化的（可恢复的前提）；第 2 节说记忆是追加日志（可重放的素材）；第 3 节说上下文是每步重新装配的（重放时要重装）。这一节回答最后一块：

可恢复性⟺状态机状态可载入​​∨重放过程可重跑​​(工程上必须两者都有)

学完这一节你应该能回答：

  • 为什么"每步都存检查点"既不是最省的、也不是最可靠的？该按什么规则决定检查点频率？
  • 重放的确定性有哪几个来源？哪些能消除、哪些只能"锁定"，哪些根本无法消除？
  • 一次崩溃发生在"副作用已执行、状态未提交"之间，恢复时该做什么？（这是本节的核心场景。）
  • "可复现"有几种不同的含义？为什么工程上通常只能承诺其中一种？
  • 为什么说"重放"与第 3 章的"幂等键"是同一个东西的两面？

一、恢复的两种形态与它们的成本#

1.1 状态机路线：检查点 + 载入#

机制：每隔若干步把完整状态持久化（检查点），崩溃后载入最后一个检查点继续。

恢复成本ckpt​=Cload​+自上个检查点以来丢失的步Clost​​​≈Cload​+2f​⋅cstep​

其中 f 是检查点间隔（步），cstep​ 是单步成本。检查点本身的成本：

Cwrite​(f)=fN​⋅cckpt​

总成本（一次运行 + 一次恢复）：

Jckpt​(f)=fN​cckpt​+Cload​+2f​cstep​

对 f 求导取零：

f∗=cstep​2Ncckpt​​​

f∗=cstep​2Ncckpt​​​

这个公式给出三条可用的直觉：

  1. 检查点越贵（cckpt​ 大），间隔越大 —— 与常识一致。
  2. 单步越贵（cstep​ 大），间隔越小 —— 因为丢失的步贵。这意味着"贵步骤"（外部 API 调用、长模型调用）应当在完成后立刻检查点。
  3. f∗ 随 N​ 增长：长任务用更疏的检查点。

一个反直觉的推论：f∗ 与崩溃概率无关。如果崩溃概率极低，f∗ 仍然是这个值 —— 因为检查点的成本是每次运行都要付的，而恢复成本只在崩溃时付。实践中会用"预期崩溃率"给第二项加权，但只要任务会重跑很多次，检查点的固定成本就占主导。

1.2 重放路线：从头再跑#

机制：不存检查点，崩溃后重跑。前提是重跑能到达同样的状态。

Jreplay​=P(崩溃)⋅E[重跑步数]⋅cstep​+这一项常常是无穷大C副作用重放风险​​​

最后一项是关键：如果过程中有不可逆副作用（发了邮件、转了账），重放就是在重复这些操作。所以重放路线的可行性完全取决于第 3 章的幂等设计：

重放可行⟺所有副作用都是幂等的（或可被去重）

这就是"幂等键与重放是同一个东西的两面"的含义：

幂等键=trace_id+step_id⟹重放时自动命中第 3 节的去重表

Agent 场景有一个独特的优势：第 2 章的轨迹天然提供了 (run_id, step_index)，这正好是幂等键的骨架。所以"让副作用可去重"和"让过程可重放"是同一件事的两种说法。

1.3 两者的组合：这是唯一可用的形态#

状态机（载入检查点） 重放（重跑）
恢复的是什么 状态（跳过已完成的步） 过程（重演决策）
前提 状态可序列化 过程确定性 + 副作用幂等
恢复后的一致性 与崩溃前完全一致 取决于确定性等级
成本 存储 + 载入 重跑的计算与调用
覆盖的失效 进程崩溃、机器故障 代码/模型/提示词变了（要复现旧行为）
不覆盖 代码变了（载入旧状态跑新代码 = 未定义行为） 非确定性步骤（每次结果不同）

正确形态：

恢复 = 载入最后一个检查点（状态机）
     + 从该检查点**重放**（重放）
     + 已提交的副作用步骤跳过（靠 journal 的"已完成"标记）
     + 未提交的副作用步骤按幂等键去重（第 3 章）

两条路线各覆盖对方不能覆盖的失效：状态机覆盖"进程崩溃"，重放覆盖"要复现旧行为"。所以缺任何一条都会有一类事故无法处理。

二、显式状态机：状态是什么#

2.1 三个正交的状态维度#

"状态"这个词被用得太泛。工程上需要拆成三个可以分别持久化、分别验证的维度：

维度 内容 谁改它 恢复要求
世界状态（world） 外部系统的实际状态（订单已付、文件已写） 工具调用（我们无法回滚它） 无法恢复，只能重新观测；所以要记"观察点"
任务状态（task） 目标、阶段、已完成/待办、已确认事实 循环（每步） 完全可序列化，必须能载入
执行状态（exec） 步数、预算、幂等键、检查点指针、未结算副作用 框架 必须原子持久化（与副作用配对）

第一行是这一节最重要的区分：

世界状态不属于我们⟹恢复时只能"重新观测"，不能"恢复"

所以我们能做的只是记录观察点（在第几步观测到世界是什么样），并在恢复时判断"这个观察是否还新鲜"。这与第 2 节的"过时"检测是同一件事。

2.2 转移的原子性：WAL 形态的 journal#

任务状态与执行状态的转移必须与副作用配对记录。这就是日志先行（write-ahead log）的形态：

journal 记录四种条目：
  INTENT(step, tool, args_hash, idem_key)      ← 副作用之前写
  COMMIT(step, result_ref)                     ← 副作用成功之后写
  ABORT(step, reason)                          ← 副作用明确未发生
  CHECKPOINT(step, state_ref)                  ← 完整状态快照

恢复时的判定表（这是本节的核心，逐行都可实现）：

journal 末尾状态 世界可能已变 恢复动作
COMMIT(step=41) ✓（已确认变了） 从 42 继续；跳过 41 的副作用
INTENT(step=41) 无对应 COMMIT/ABORT 未知 ★ 用 idem_key 去重：命中则读回首次结果（世界已变，步骤视为完成）；未命中则重试（世界未变）
ABORT(step=41) ✗ 重试该步
无 41 的任何记录 ✗ 从 41 正常执行

第二行是全部设计的价值所在：它是第 3 章"未知区间"在恢复流程里的落点。没有 journal，"未知"就被迫当成"没发生"，于是重复副作用。

恢复的正确性⟺INTENT 与 COMMIT 的分界被持久化

2.3 幂等键在重放中的取值#

这是第 3 章留给本节的一个具体问题：重放时幂等键该是什么？

idem_key=hash(run_id, step_index, tool_name)

三个字段的含义缺一不可：

字段 作用 缺了会怎样
run_id 区分不同运行 两次不同任务的同一步骤会互相去重（静默丢操作）
step_index 区分同一次运行的多次调用 同一工具在循环里被调用多次时全部被去重（只执行一次）
tool_name 区分不同工具 同一步骤的不同工具会撞键

注意不要包含 attempt（重试序号）：网络重试必须复用同一个键（第 3 章）；而重放也必须复用同一个键。这两者是同一件事 —— 都是"同一逻辑步骤"。

但有一处需要小心：如果模型在收到错误后改变参数重新决策，那是新的意图，需要新的键。所以键里是否包含参数哈希，取决于语义：

key={(run,step,tool)(run,step,tool,args)​同一步骤的传输重试与重放允许同一步骤内多次不同调用（如循环检索）​

推荐做法：键里含 args 的哈希，但指纹校验（第 3 章）负责拦住"同键不同参数"。

2.4 检查点里必须存什么#

一个常被写漏的清单（每一条的缺失都会在下一次恢复时暴露）：

必须存 为什么
任务状态（目标/阶段/已完成/待办） 否则不知道做到哪
已确认事实与实体 ID 否则要重新观测（贵）或重新推断（错）
执行元数据（步数/预算/错误计数） 否则预算闸失效，可能无限重试（第 2 章）
未结算的 INTENT 否则无法判断"未知区间"，会重复副作用
已用的幂等键 否则重放时重新生成键，去重失效
模型与工具的版本指纹 否则载入旧状态跑新代码 = 未定义行为
随机种子 重放确定性的输入之一（见第三节）
上下文装配的引用集合（哪些 handle 被内联） 否则恢复后的上下文与崩溃前不同，决策可能不同

倒数第二、三条最容易漏，而且后果最隐蔽：恢复后的上下文与崩溃前不同，于是模型做了不同的决策，任务走向分叉。这不是"从第 41 步继续"，而是"从第 41 步开始了一个新任务"。

三、重放的不确定性边界#

3.1 确定性等级：L0 / L1 / L2#

"可复现"有三种强弱不同的含义，工程上必须明确承诺哪一种：

L0 逐字≻L1 因果≻L2 结果

等级 定义 达成条件 用途
L0 逐字可复现 每一步的输入输出逐字节相同 固定种子 + 重放所有外部输入（模型响应、工具返回、时间） 调试、回归测试、评测
L1 因果可复现 关键决策序列与副作用集合相同（措辞可不同） 固定种子 + 锁定外部输入的关键字段 事故归因、审计
L2 结果可复现 最终产物满足同一验收标准（过程可不同） 只需任务与环境稳定 业务 SLA、可靠性的实际含义

关键事实：

L0 需要"重放"外部输入（cassette 模式），而不是"重新请求"

即：把每一次模型响应与工具返回记录下来，重放时直接喂回记录。这样"模型是随机的"这件事就不再是障碍 —— 因为随机性被记录替换了。这在本章第 2 节叫"从原始日志重算"，在这里叫"回放模式"。

L0 的两个成本：存储（每次调用的完整响应）与失去对新模型的测试意义（回放旧响应当然复现旧行为）。所以 L0 用于回归，不用于评估新版本。

3.2 不确定性来源清单（五种，处置方式不同）#

# 来源 能消除？ 处置
1 模型采样（温度） ✓ 可消除 设 temperature=0 并且固定种子；但注意即使这样也非严格确定（批次/并行/floating point 归约顺序）
2 时间与日期 ✓ 可锁定 把"当前时间"作为显式的环境输入注入，而不是让工具各自读时钟
3 外部检索/API 的返回变化 ✗ 无法消除 记录"当时返回了什么"（含版本/hash），重放时用记录
4 副作用的实际效果 ✗ 无法消除 用幂等 + journal 跳过或读回（第 3 章）
5 并发与调度顺序 △ 可部分消除 单线程化关键段；或记录顺序并在重放时按记录顺序执行

第 1 项的细节值得强调：很多人以为"temperature=0 就是确定的"。实际上即使在贪心解码下，同一请求在不同批次大小、不同硬件、不同并行度下也可能产生不同输出（浮点归约顺序不同）。所以：

可复现性=模型参数设置,可复现性=锁定了多少外部输入

第 2 项是最容易修、收益最大的一项：把时钟变成参数。代码里不要出现 datetime.now()，而是从 env.now 读 —— 后者在重放时由轨迹提供。这一条把"时间"从一个隐式全局变量变成可注入的依赖，顺带消除了大量偶发 bug。

3.3 分层：纯逻辑层与副作用层#

要把重放做对，架构上必须把两类步骤分开：

纯逻辑层（pure）：无副作用、无时间依赖、只读外部输入
   → 可以任意重放、可以并行、可以缓存（结果只依赖输入）
副作用层（effectful）：改变外部世界
   → 必须经 journal + 幂等键；重放时按 journal 跳过或去重

判据：

步骤 i∈pure⟺执行两次对世界无影响∧输出仅依赖已记录的输入

这个分层的三个收益：

  1. 重放成本大降：纯逻辑层可以重跑而不产生任何风险，所以只需要对副作用层做 journal 与去重。
  2. 评测可做：把纯逻辑层冻结（喂固定输入），只评估副作用层的决策质量 —— 这是第 7 章"可复现的最小评测集"的基础。
  3. 调试可行：纯逻辑层的 bug 可以本地重放（不需要外部系统），副作用层的问题靠 journal 定位。

3.4 无法重放的边界：必须承认的三件事#

边界 说明 应对
不可逆的外部效果 邮件已发、款已转，重放不会撤销它 不做"重放修复"，做补偿/对账（第 3 章）
依赖未记录的随机性 如果某步用了系统随机数却没记录，重放必然分叉 强制所有随机源经注入的 rng；禁止裸 random()
依赖外部世界当时的状态 重放时外部世界已变（价格、库存） 记录观察值而不是重新查询；或明确标注"重放使用当前状态"（这会降级为 L2）

第三项是最容易被忽视的：重放一个"按当时库存做决策"的步骤时，如果重新查询库存，你会得到一个当时不可能做出的决策。所以重放必须用记录的观察，而不是重新观测 —— 除非你的目标只是 L2（结果可复现）。

四、恢复流程的设计#

4.1 恢复的六步#

把前面的结论汇成一个可实现的流程：

1. 读取最后一个 CHECKPOINT，以及其后的 journal 条目
2. 载入任务状态与执行元数据
3. 校验版本指纹：
     模型/工具/提示词版本与检查点时一致 → 继续
     不一致 → ★ 拒绝载入（"载入旧状态跑新代码"是未定义行为），改为 L2 重跑或人工
4. 处理未结算的 INTENT：
     用 idem_key 查询去重表 → 命中：读回结果，视为完成
                              → 未命中：重试该副作用
5. 重建上下文（第 3 节）：
     用检查点里记录的引用集合与"当时的观察"，而不是重新检索
6. 从下一个未完成的步骤继续；恢复事件本身写入轨迹（供第 7 章归因）

第 3 步的"拒绝载入"是一个重要的设计选择。很多系统默默地用旧状态跑新代码，结果是难以归因的诡异行为。明确拒绝比默默继续好得多：

版本不一致⇒不可恢复（fail-fast），而不是"尽力而为"

第 6 步容易被漏：恢复本身是一个事件，必须进轨迹。否则"这次任务为什么走了不同的路"永远查不出来（第 7 章的失效归因需要知道"中途恢复过"）。

4.2 检查点频率的实证规则#

回到 f∗=2Ncckpt​/cstep​​，把它变成可操作的规则：

场景 建议
步骤便宜（本地计算） 稀疏检查点（f 大），靠重放补
步骤贵（外部 API/长模型调用） 每步之后检查点
有不可逆副作用 该步之前写 INTENT、之后写 COMMIT（这不是"检查点频率"问题，是必需的）
长任务 f 随 N​ 增长

一条压倒性的规则：不可逆副作用必须每步记账，与检查点频率无关。 检查点频率优化的是"重做多少计算"，而不能用来优化"是否重复副作用"。

4.3 与第 3 章幂等键的接合（完整图景）#

把两章的内容合成一张图，这是本课程里"可靠性"这条线的完整形态：

        ┌──────────── 正常运行 ────────────┐
决策 → 写 INTENT(key=(run,step,tool,args)) → 执行工具 → 写 COMMIT(结果引用)
                    │                              │
                    │                      去重表(幂等键) ← 同一行由第 3 章维护
                    ↓                              ↓
              崩溃在 INTENT 之后             崩溃在 COMMIT 之后
                    │                              │
        恢复：用同一 key 查去重表 → 命中则读回结果  恢复：直接跳过该步
                                   → 未命中则重试

三处接合点：

接合点 第 3 章 第 4 章
键的生成 幂等键的三个必要条件（确定性/唯一性/不可枚举） 键由 (run_id, step_index) 提供，天然确定
键的复用 网络重试复用同一键 重放也复用同一键
未知区间的处置 先去重，未命中才重试 恢复流程第 4 步

代码：journal + 检查点 + 确定性重放#

下面的代码实现完整的一套：(1) WAL 形态的 journal 与检查点；(2) 恢复流程（含未知区间与版本校验）；(3) 分层执行器（纯逻辑可重放、副作用经幂等）；(4) 确定性重放（cassette 模式，L0）；(5) 检查点间隔的成本最优化。

import hashlib
import json
import math
import time
from dataclasses import dataclass, field, asdict
from typing import Any, Callable, Optional


# ==================== 幂等去重表（第 3 章的简化实现，供接合演示） ====================
class DedupTable:
    def __init__(self):
        self.rows: dict[str, dict] = {}

    def lookup(self, key: str) -> Optional[dict]:
        return self.rows.get(key)

    def commit(self, key: str, result: Any) -> None:
        self.rows[key] = {"status": "committed", "result": result}

    def intent(self, key: str) -> None:
        self.rows.setdefault(key, {"status": "in_progress", "result": None})


def idem_key(run_id: str, step: int, tool: str, args: dict) -> str:

      · 含 run_id：两次不同任务不会互相去重
      · 含 step_index：同一工具在循环里多次调用不会被全部去重
      · 含 args_hash：同一步骤内的不同调用是不同的意图（指纹校验兜住键复用）
      · **不含 attempt**：网络重试与重放都必须复用同一个键（这正是它有效的原因）
    """
    blob = json.dumps(args, sort_keys=True, ensure_ascii=False, default=str)
    h = hashlib.sha256(blob.encode()).hexdigest()[:12]
    return f"{run_id}:{step}:{tool}:{h}"


# ==================== (1) journal + 检查点 ====================
class Journal:
    """
    ★ 设计决策：追加式、只写不改（WAL 形态）。
      四种条目各自承担一个语义，**INTENT 与 COMMIT 的分界是恢复正确性的全部来源**。
    """
    def __init__(self):
        self.entries: list[dict] = []

    def intent(self, step: int, tool: str, key: str, args_hash: str) -> None:
        self.entries.append({"kind": "INTENT", "step": step, "tool": tool,
                             "key": key, "args_hash": args_hash, "at": time.time()})

    def commit(self, step: int, result_ref: str) -> None:
        self.entries.append({"kind": "COMMIT", "step": step,
                             "result_ref": result_ref, "at": time.time()})

    def abort(self, step: int, reason: str) -> None:
        self.entries.append({"kind": "ABORT", "step": step, "reason": reason})

    def checkpoint(self, step: int, state_ref: str, env_fingerprint: str,
                   seeds: dict, inlined_handles: list[str]) -> None:
        self.entries.append({"kind": "CHECKPOINT", "step": step, "state_ref": state_ref,
                             "env": env_fingerprint, "seeds": seeds,
                             "inlined_handles": inlined_handles})

    # ---- 恢复分析：这是本节的核心逻辑 ----
    def last_checkpoint(self) -> Optional[dict]:
        for e in reversed(self.entries):
            if e["kind"] == "CHECKPOINT":
                return e
        return None

    def tail_since(self, step: int) -> list[dict]:
        out, seen = [], False
        for e in self.entries:
            if e["kind"] == "CHECKPOINT" and e["step"] == step:
                seen = True
                continue
            if seen:
                out.append(e)
        return out

    def pending_intents(self, since_step: int) -> list[dict]:
        """
        ★ 找出"未知区间"：有 INTENT 但既无 COMMIT 也无 ABORT 的步骤。
          这些步骤的副作用**可能已经发生**，恢复时必须走去重表而不是直接重试。
        """
        tail = self.tail_since(since_step)
        resolved = {e["step"] for e in tail if e["kind"] in ("COMMIT", "ABORT")}
        return [e for e in tail if e["kind"] == "INTENT" and e["step"] not in resolved]


@dataclass
class Checkpoint:
    step: int
    task_state: dict
    exec_meta: dict
    env_fingerprint: str          # 模型/工具/提示词版本指纹
    seeds: dict
    inlined_handles: list[str]    # ★ 上下文装配的引用集合（2.4 最后一条）


# ==================== (2) 恢复流程 ====================
@dataclass
class RecoveryPlan:
    ok: bool
    from_step: int = 0
    pending: list[dict] = field(default_factory=list)
    reason: str = ""


def plan_recovery(journal: Journal, checkpoints: dict[int, Checkpoint],
                  current_env: str) -> RecoveryPlan:
    """
    ★ 设计决策：版本不一致 → **拒绝载入**（fail-fast）。
      "载入旧状态跑新代码"是未定义行为；默默继续会产生难以归因的诡异行为。
    """
    cp = journal.last_checkpoint()
    if cp is None:
        return RecoveryPlan(ok=True, from_step=0, reason="无检查点：从头开始（L2 重跑）")
    ck = checkpoints.get(cp["step"])
    if ck is None:
        return RecoveryPlan(ok=False, reason=f"检查点 {cp['step']} 的状态引用缺失")
    if ck.env_fingerprint != current_env:
        return RecoveryPlan(
            ok=False, reason=(f"环境指纹不一致（checkpoint={ck.env_fingerprint}, "
                              f"now={current_env}）：拒绝载入旧状态，请改用重跑或人工处理"))
    pending = journal.pending_intents(cp["step"])
    return RecoveryPlan(ok=True, from_step=cp["step"] + 1, pending=pending,
                        reason=(f"从检查点 {cp['step']} 恢复；"
                                f"未结算 INTENT {len(pending)} 个（结果未知，须走幂等去重）"))


def resume_pending(pending: list[dict], dedup: DedupTable,
                   effect: Callable[[str], Any]) -> list[dict]:
    """
    ★ 恢复的核心动作（2.2 判定表的第二行）：
      用同一 idem_key 查去重表 → 命中则读回首次结果（世界已变，视为完成）
                              → 未命中则重试（世界未变）
    """
    out = []
    for p in pending:
        row = dedup.lookup(p["key"])
        if row and row["status"] == "committed":
            out.append({"step": p["step"], "action": "replay_result",
                        "result": row["result"], "note": "副作用已发生：读回首次结果，不重复执行"})
        else:
            res = effect(p["key"])
            dedup.commit(p["key"], res)
            out.append({"step": p["step"], "action": "retried", "result": res,
                        "note": "去重表无记录：副作用未发生，安全重试"})
    return out


# ==================== (3) 分层执行器 ====================
@dataclass
class StepResult:
    step: int
    kind: str                     # pure | effectful | skipped
    output: Any
    note: str = ""


class LayeredRunner:
    """
    ★ 设计决策：把"纯逻辑层"与"副作用层"在类型上分开。
      纯逻辑层可以任意重放（无风险）；副作用层必须经 journal + 幂等键。
      这让"重放要小心"这件事从人的纪律变成结构约束。
    """
    def __init__(self, run_id: str, journal: Journal, dedup: DedupTable,
                 record: dict, replay: bool = False):
        self.run_id, self.journal, self.dedup = run_id, journal, dedup
        self.record = record          # ★ cassette：记录/回放所有外部输入
        self.replay = replay

    def _extern(self, kind: str, key: str, real_fn: Callable[[], Any]) -> Any:
        """
        ★ L0 可复现的关键：重放时**不重新请求**，而是喂回记录。
          这让"模型是随机的""外部 API 变了"都不再是障碍。
        """
        full = f"{kind}:{key}"                     # ★ 读写用同一个键，避免回放时查不到
        if self.replay:
            if full not in self.record:
                raise KeyError(f"回放缺失输入 {full}：该步骤没有记录 → 只能降级为 L2 重跑")
            return self.record[full]
        out = real_fn()
        self.record[full] = out
        return out

    def pure(self, step: int, fn: Callable[..., Any], *args: Any) -> StepResult:
        out = fn(*args)
        return StepResult(step, "pure", out, "纯逻辑：重放无副作用")

    def effectful(self, step: int, tool: str, args: dict,
                  effect: Callable[[], Any]) -> StepResult:
        key = idem_key(self.run_id, step, tool, args)
        # 已有 COMMIT 决定 → 跳过（恢复时不重做）
        done = {e["step"] for e in self.journal.entries if e["kind"] == "COMMIT"}
        if step in done:
            return StepResult(step, "skipped", None, "journal 已有 COMMIT：跳过副作用")
        # 先查去重表（可能是上一次崩溃留下的 in_progress/committed）
        row = self.dedup.lookup(key)
        if row and row["status"] == "committed":
            return StepResult(step, "skipped", row["result"], "幂等命中：读回首次结果")
        self.journal.intent(step, tool, key, hashlib.sha256(
            json.dumps(args, sort_keys=True, default=str).encode()).hexdigest()[:8])
        self.dedup.intent(key)
        out = effect()
        self.dedup.commit(key, out)
        self.journal.commit(step, result_ref=f"res:{step}")
        return StepResult(step, "effectful", out, "副作用完成并记账")


# ==================== (4) 检查点间隔的成本最优化 ====================
def optimal_interval(n_steps: int, c_ckpt: float, c_step: float) -> dict:
    """
    ★ 1.1 的结论：f* = sqrt(2·N·c_ckpt / c_step)。
      三条可读出的直觉：检查点贵→间隔大；单步贵→间隔小；长任务→更疏。
    """
    f = max(1, int(round(math.sqrt(2 * n_steps * c_ckpt / max(c_step, 1e-9)))))
    write_cost = (n_steps / f) * c_ckpt
    lost_cost = (f / 2) * c_step
    return {"f*": f, "检查点写入总成本": round(write_cost, 2),
            "期望重做成本": round(lost_cost, 2), "合计": round(write_cost + lost_cost, 2)}


# ==================== (5) 演示 ====================
if __name__ == "__main__":
    ENV = "model:m1|tools:v3|prompt:p7"
    jr, dedup, cassette = Journal(), DedupTable(), {}
    runner = LayeredRunner("run_7", jr, dedup, cassette)

    effects: list[str] = []

    def send_email() -> str:
        effects.append("email_sent")
        return "msg_1"

    def freeze_quote() -> str:
        effects.append("quote_frozen")
        return "q_9"

    # ---- 正常运行：第 1 步纯逻辑、第 2 步副作用（已提交）、第 3 步副作用（崩溃在 INTENT 之后）----
    print("【正常运行 + 崩溃】")
    print(" ", runner.pure(1, lambda x: x * 2, 21))
    print(" ", runner.effectful(2, "send_email", {"to": "a@b.c"}, send_email))
    jr.checkpoint(3, "state:3", ENV, seeds={"py": 0, "model": 12345},
                  inlined_handles=["doc_17"])

    # ★ 模拟崩溃：写 INTENT 后进程死掉（COMMIT 从未写入）
    key3 = idem_key("run_7", 4, "freeze_quote", {"order": "o_1"})
    jr.intent(4, "freeze_quote", key3, "aabbccdd")
    effects.append("quote_frozen")          # 副作用实际发生了，但没记账
    dedup.commit(key3, "q_9")
    print("  （进程在 step 4 的 INTENT 之后、COMMIT 之前崩溃；副作用实际已发生）")

    # ---- 恢复 ----
    print("\n【恢复分析】")
    cps = {3: Checkpoint(3, {"phase": "quoting", "done": ["send_email"]},
                         {"steps": 3, "tokens": 5200}, ENV,
                         {"py": 0, "model": 12345}, ["doc_17"])}
    plan = plan_recovery(jr, cps, current_env=ENV)
    print("  计划:", plan)

    # 版本不一致 → 拒绝载入
    plan_bad = plan_recovery(jr, cps, current_env="model:m2|tools:v3|prompt:p7")
    print("  版本变化:", plan_bad.ok, "|", plan_bad.reason)

    # 未结算 INTENT 的处置：命中幂等键 → 读回结果，不重复副作用
    before = len(effects)
    resumed = resume_pending(plan.pending, dedup, effect=lambda k: (effects.append("re-exec"),
                                                                    "q_9_new")[1])
    print("  未结算处置:", resumed)
    print("  副作用新发生次数:", len(effects) - before, "← 0 表示成功避免了重复副作用")

    # ---- L0 重放（cassette）----
    print("\n【L0 逐字重放】")
    outer = LayeredRunner("run_7", Journal(), DedupTable(), cassette, replay=False)
    v1 = outer._extern("llm", "s1", lambda: "动作: 查询库存")
    v2 = outer._extern("tool", "s2", lambda: {"stock": 7})
    print("  原始运行记录:", cassette)
    inner = LayeredRunner("run_7", Journal(), DedupTable(), cassette, replay=True)
    r1 = inner._extern("llm", "s1", lambda: "动作: 完全不同的回答（不应被调用）")
    r2 = inner._extern("tool", "s2", lambda: {"stock": 999})
    print("  重放得到:", r1, r2, "| 与原始一致:", (r1, r2) == (v1, v2))
    try:
        inner._extern("tool", "s3", lambda: "x")
    except KeyError as e:
        print("  缺记录时:", e, "← 只能降级为 L2 重跑，而不是假装能 L0 复现")

    # ---- 检查点间隔 ----
    print("\n【检查点间隔最优化】")
    for n, c_ck, c_st in ((40, 5, 800), (40, 500, 5), (400, 5, 800)):
        print(f"  N={n:4d} c_ckpt={c_ck:4.0f} c_step={c_st:4.0f} → {optimal_interval(n, c_ck, c_st)}")
    print("  ★ 不可逆副作用必须每步记账，与检查点频率无关（4.2）")

    # ---- 成本对比：状态机 vs 重放 ----
    print("\n【恢复成本对比（N=40, c_step=800, c_ckpt=5）】")
    f = optimal_interval(40, 5, 800)["f*"]
    print(f"  状态机（f={f}）总成本 ≈ {optimal_interval(40, 5, 800)['合计']}")
    print(f"  全量重放总成本 ≈ {40 * 800}（且副作用需去重，否则风险不可估）")

八处关键设计决策：

  1. idem_key 的构成显式排除了 attempt，并注释说明"不含 attempt 正是它有效的原因"。这一行把第 3 章的"网络重试复用同一键"与第 4 章的"重放复用同一键"统一起来。
  2. Journal.pending_intents 是本节的核心逻辑：找出有 INTENT 但无 COMMIT/ABORT 的步骤 —— 这就是"未知区间"的形式化定义，也是恢复时唯一需要特殊处理的集合。
  3. plan_recovery 在环境指纹不一致时拒绝载入（fail-fast）。"载入旧状态跑新代码"是未定义行为，明确拒绝远好于默默继续。
  4. Checkpoint.inlined_handles 记录了崩溃时上下文内联了哪些引用（2.4 的最后一条）。缺了它，恢复后的上下文与崩溃前不同，模型会做出不同决策 —— 那不是"继续"，而是"开始一个新任务"。
  5. resume_pending 实现 2.2 判定表的第二行：命中幂等键则读回结果（不重复执行）。演示里"副作用新发生次数 = 0"就是这一条生效的证据。
  6. LayeredRunner 把 pure 与 effectful 分成两个方法。这是 3.3 的"纯逻辑层可任意重放"在类型层面的表达 —— 让纪律变成结构。
  7. _extern 的 cassette 模式是 L0 复现的唯一实现方式：重放时不重新请求而是喂回记录；缺记录时显式抛错，而不是悄悄降级为重新请求（那会让"以为在复现，其实在探索"）。
  8. optimal_interval 把 f∗=2Ncckpt​/cstep​​ 变成可算的函数，并在演示里对比了三种参数（贵的检查点 / 贵的步骤 / 长任务）。

练习#

  1. 检查点频率：某任务 60 步，单步平均成本 = 1 次模型调用 + 1 次工具调用（约 2000 token），检查点写入成本约 300 token 等价。用 f∗=2Ncckpt​/cstep​​ 算出最优间隔。如果这个任务里第 30 步是"发送合同邮件"（不可逆），你的检查点策略要怎么变？为什么这个变化不是由 f∗ 决定的？

  2. journal 判定表：下面四种 journal 末尾状态，分别写出恢复动作与理由： （a）INTENT(step=12, key=K) + COMMIT(step=12)； （b）INTENT(step=12, key=K)（无后续）； （c）INTENT(step=12, key=K) + ABORT(step=12)； （d）CHECKPOINT(step=11)，之后什么都没有。 然后回答：如果去重表过期清理了 K 的记录，情况 (b) 会发生什么？这与第 3 章的 TTL 设计有什么关联？

  3. 确定性等级判定：为下面五个需求分别判定需要 L0 / L1 / L2，并说明理由： （a）复现一个用户报告的 bug（要看到完全相同的行为）； （b）审计"这次退款是谁触发的"； （c）日常运行的 SLA 达标统计； （d）比较新旧提示词的效果； （e）事故归因：判断是模型错还是工具错。 其中哪一个不能用 L0 完成？为什么？（提示：回放旧响应会掩盖新模型的问题。）

  4. 确定性来源清单：在你写过（或设想过）的一个 Agent 里，列出所有引入不确定性的地方（至少 5 处）。对每一处标注：能消除 / 能锁定 / 无法消除，以及你的处置方式。特别检查有没有裸的 random()、datetime.now()、以及"并行执行顺序影响结果"的地方。

  5. 版本不一致的处置：某系统在崩溃恢复时发现"工具版本从 v3 升到 v4"。请给出三种可选方案（拒绝载入并重跑 / 载入旧状态但用旧工具版本 / 载入并尽力而为），逐个分析它们各自会产生什么风险。然后论证为什么"尽力而为"在有副作用的系统里是最危险的选项。

  8. 端到端设计：为一个"自动把论文草稿格式化成期刊模板并提交"的 Agent 设计完整的崩溃恢复方案。要求写出：检查点里存什么（对齐 2.4 的清单）、journal 的条目类型、恢复六步的具体动作、以及"提交"这个不可逆步骤的记账方式。最后说明：如果崩溃发生在"提交成功但 COMMIT 未写"的窗口里，你的方案如何避免重复提交？

小结#

  • 恢复有两条路线，各有对方不能覆盖的失效：状态机（载入检查点，覆盖进程崩溃，恢复后与崩溃前一致）与重放（重跑，覆盖"代码/模型变了要复现旧行为"）。工程上必须两者组合。
  • 检查点间隔有最优解：f∗=2Ncckpt​/cstep​​。检查点贵 → 间隔大；单步贵 → 间隔小；长任务 → 更疏。但不可逆副作用必须每步记账，与 f∗ 无关 —— 频率优化的是"重做多少计算"，不是"是否重复副作用"。
  • 状态有三个正交维度：世界状态（不属于我们，只能重新观测；所以要记观察点）、任务状态（可完全序列化）、执行状态（必须与副作用配对原子持久化）。
  • 恢复正确性的全部来源是"INTENT 与 COMMIT 的分界被持久化"。判定表：有 COMMIT → 跳过；只有 INTENT → 结果未知，走去重表；有 ABORT → 重试；无记录 → 正常执行。
  • 幂等键 = (run_id, step_index, tool, args_hash)，不含 attempt：网络重试与重放都复用同一键 —— 这正是"幂等键是可靠性地基"的完整含义。缺 run_id 会跨任务误去重，缺 step_index 会让循环内多次调用被全部去重。
  • 检查点必须存"未结算 INTENT / 已用幂等键 / 版本指纹 / 随机种子 / 上下文引用集合"。最后两项缺失会导致"恢复后的上下文与崩溃前不同" → 模型做出不同决策 —— 那不是继续，而是分叉。
  • 可复现分三级：L0 逐字（需回放外部输入，即 cassette 模式）、L1 因果、L2 结果。可复现性=锁定了多少外部输入，不是"设了 temperature=0"。L0 不能用于评估新模型（回放旧响应会掩盖新问题）。
  • 不确定性五种来源：模型采样（可消除但不彻底）、时间（可锁定，收益最大：把时钟变成注入参数）、外部检索（不可消除，须记录）、副作用效果（不可消除，靠幂等 + journal）、并发顺序（可部分消除）。
  • 架构上必须分层：纯逻辑层（可任意重放、可并行、可缓存）与副作用层（必须经 journal + 幂等键）。判据：执行两次对世界无影响 且 输出仅依赖已记录输入。
  • 必须承认三条重放边界：不可逆外部效果（只能补偿/对账）、未记录的随机性（禁止裸 random()）、依赖当时外部状态（用记录的观察，而不是重新观测）。
  • 恢复第 3 步的"版本不一致则拒绝载入"是刻意的 fail-fast：载入旧状态跑新代码是未定义行为，明确拒绝好于默默继续。恢复本身必须写入轨迹 —— 否则"这次为什么走了不同的路"永远查不出来。
