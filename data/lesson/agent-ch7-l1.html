轨迹级 vs 结果级评测：可复现的最小评测集设计#

这一节要解决什么#

前六章把系统搭起来了。现在要回答一个问题：怎么知道它行？ 最常见的做法是"跑一批任务，看最终结果对不对"。这个做法有一个致命的盲区：

一个 Agent 用错误的过程得到了正确的答案 —— 记为"成功"
一个 Agent 用正确严谨的过程，被外部系统拖累而失败 —— 记为"失败"

第一行是侥幸成功，第二行是冤枉失败。只看结果级评测，这两类都被错误分类，于是：

评测的作用=指出"该改哪里"⟹只报一个通过率，等于没指出该改哪里

这一节要把评测做成两级的：

级别 看什么 回答什么问题 语言
结果级 最终产物是否满足验收标准 "这次任务成了吗？" 业务语言
轨迹级 过程：步数、工具选择、无效调用、回退、副作用、证据链 "为什么会这样？该改哪里？" 工程语言

两级不可互相替代，因为它们的盲区正好互补：

结果级盲区​过程质量轨迹级盲区​真实价值

一个 Agent 过程完美但结果没用（例如认真查了错的数据源），另一个 Agent 投机取巧但结果正确 —— 两者的处置完全不同，只有两级同时看才能区分。

学完这一节你应该能回答：

  • 为什么"逐字比对标准轨迹"是错的？正确做法是什么？
  • 结果级判定器为什么比轨迹级判定器更难写？"用模型当裁判"有哪些系统性偏差？
  • 可复现的三个必要条件是什么？（第 4 章已经给过两个，第三个是评测特有的。）
  • 一个"最小"评测集该覆盖什么？规模怎么定？
  • 为什么"在同一批用例上反复调参"会让评测数字失效？怎么防？
  • 部分完成算成功还是失败？为什么这个判定会显著改变优先级？

一、两类评测：各自的定义与盲区#

1.1 结果级：便宜、可自动化、会误判#

结果级评测只检查最终产物：

OutcomePass(x)⟺Verify(output(x))=true

Verify 有三种实现，可靠性依次下降：

实现 可靠性 成本 适用
确定性校验器（断言、schema 校验、数值比对、可执行测试） 高 极低 有明确验收标准的任务
规则 + 阈值（相似度、覆盖率、正则） 中 低 半结构化产物
模型评判（LLM-as-judge） 低（有系统偏差） 中 开放文本、难以形式化的标准

结果级的两个盲区：

侥幸成功⟺OutcomePass∧¬TrajectoryOK,冤枉失败⟺¬OutcomePass∧TrajectoryOK

  • 侥幸成功的危害是它会掩盖真实缺陷：通过率看起来 62%，但其中一部分是"过程错了却碰对了"。上线后输入一变，这部分立刻全部失效。
  • 冤枉失败的危害是它会误导优先级：团队去修一个其实没坏的东西，而真正的问题（外部系统的超时）没人管。

1.2 轨迹级：昂贵、需要定义"好过程"、能定位#

轨迹级评测对过程提性质（不是比对）：

TrajectoryOK(x)⟺a∈Assertions⋀​a(trace(x))

关键设计决策：断言式，不是逐字比对。 逐字比对为什么错：

同一目标有多条合法路径⟹"标准轨迹"是一个并不存在的唯一解

一个"查库存然后下单"的任务，先查价格再查库存也可以，用不同的工具也可以。逐字比对会把所有合法的变体判为失败，于是你会去优化"如何更像标准轨迹"，而不是"如何更可靠"。

断言该写什么（可编码的类型）：

断言类型 例子 抓什么
must_call(tool) 必须调用过 verify_signature 漏步骤（第 5 章第 2 节的执行时版本）
must_not_call(tool) 不得在无权限时调用 pay 越权、安全
max_side_effects(n) 不可逆操作 ≤ 1 次 重复副作用（第 3 章）
must_cite_evidence() 每个结论必须有来源引用 幻觉、无依据推断
max_steps(n) / max_cost(c) 步数/成本上限 效率、预算（第 5 章第 4 节）
no_repeat_failed_call(n) 同一个失败调用不得重复 ≥ n 次 死循环重试（第 5 章第 3 节）
must_confirm_before(irreversible) 不可逆动作前必须有确认/审批 安全（第 7 章第 3 节）
monotone_progress() 已确认事实集单调增长 活锁/震荡（第 6 章第 2 节）
context_hygiene() 子 Agent 的中间过程未进入主上下文 隔离失效（第 6 章第 3 节）

轨迹级的盲区：过程好但结果错（例如工具返回的数据本身错了、或者验收标准理解错了）。所以它是必要条件不是充分条件。

1.3 为什么必须两级同时报#

把两个维度交叉，得到四类，每一类的处置都不同：

轨迹 OK 轨迹不 OK
结果通过 ✓ 真成功：可以放心扩大用例 ⚠ 侥幸成功：缺陷被掩盖，输入一变就失效
结果不通过 ⚠ 冤枉失败：查外部系统/验收标准，不要改 Agent ✗ 真失败：按第 2 节的四象限归因

报告格式：

报告={结果通过率, 轨迹断言通过率, 四种组合的计数, 成本/步数/回退的分布}

没有"四类计数"的评测报告是不完整的 —— 因为它无法区分"该修 Agent"和"该修环境"。

二、结果级判定的难点#

2.1 验收标准必须可执行#

可评测⟺验收标准能被写成一个可执行的判定器

写不出来时，有两种情况，处置不同：

情况 例子 处置
标准模糊 "写得好一点" 先跟业务方把标准结构化（这是产品问题，不是评测问题）
标准可意会不可形式化 "这份报告要有洞察力" 退而用模型评判 + rubric 分解，并接受它的偏差

不要用"标准模糊"作为跳过评测的理由 —— 那只是把问题从评测阶段推到线上。

2.2 模型当裁判的系统性偏差#

模型评判（LLM-as-judge）能用，但必须知道它的偏差方向，否则会把偏差当成质量：

偏差 机制 缓解
位置偏好 成对比较时偏向第一个（或第二个，取决于模型） 随机化顺序 + 双向各评一次取一致
长度偏好 更长的回答得分更高（即使更啰嗦） 长度归一化；或把长度作为独立指标单列
自我偏好 同一模型写的答案它更偏爱 用异源模型当裁判
格式偏好 有标题/列表的得分更高 rubric 明确"格式不计分"
顺从 被问"这个答案好吗"时倾向说好 改为成对比较（"哪个更好"）而不是绝对打分

模型裁判可用⟺偏差被测量过，且在报告中与质量分开呈现

最强的一条实践规则：判定器必须与被测系统解耦。

解耦⟺判定器不用被测 Agent 自己的判断、自己的模型、自己的提示词

用被测 Agent 自己判自己，等于第 5 章第 2 节"自评不是验证"的同一个错误，只是搬到了评测阶段。

2.3 部分完成必须显式#

完成度∈[0,1]而不是{成功,失败}

为什么必须显式：把"完成了 7 个子任务中的 5 个"记为"失败"，会让通过率看起来很低，而团队会去追一个"从 0 到 1"的难题；记为"成功"又会掩盖缺失。正确做法是三级记录：

结果=⎩⎨⎧​fullpartial(k/n)none​全部验收标准满足部分满足，且缺失项可枚举无可交付​

partial 的可枚举性是关键：partial(5/7, 缺 = ["审计日志", "通知"]) 才能告诉你"缺的是哪两个子任务"，从而指向具体的修复动作。只报一个百分比是没有可操作性的。

2.4 指标的选取#

指标 定义 用途
结果通过率 full / 总用例 业务 SLA
部分完成率 partial 的分布 定位"差一点"的部分
轨迹断言通过率 逐条断言的通过比例 工程改进的抓手
步数 / token / 成本分布 分位数（P50​,P95​）而不是均值 成本与延迟的异常检测
回退率 / 重规划次数 每次运行的平均值 规划质量（第 5 章）
副作用次数分布 尤其不可逆动作 风险
pass@k 与 pass^k k 次独立运行至少一次成功 / 全部成功 见下

pass@k 在 Agent 场景的含义变了。在代码生成里 pass@k 衡量"多样性带来的机会"；但在 Agent 场景，任务通常只会被执行一次，所以真正该看的是：

passk=P(k 次全部成功)=∏单次成功率 （近似）

如果一个 Agent 的 pass@3 = 0.9 但 pass^3 = 0.2，它在生产上是不可用的 —— 因为你没有"跑三次挑一次"的机会。这是一个很容易被错过的指标陷阱。

三、可复现：三个必要条件#

第 4 章讲过 L0/L1/L2 三个确定性等级与"重放外部输入"（cassette）。评测在此基础上再加两条：

条件 内容 违反的后果
输入冻结 固定随机种子、把时钟变成注入参数（第 4 章）、固定输入数据 同一用例每次结果不同，无法比较配置
环境指纹 记录模型版本 / 工具版本 / 提示词版本（第 4 章检查点的指纹） 改了提示词却以为是模型升级的功劳
判定器与被测系统解耦 判定器不用被测 Agent 的判断/模型/提示词 自评偏差；被测系统"自己给自己打分"

可复现⟺输入冻结∧环境指纹一致∧判定器独立

两种评测形态，用途不同，必须分清：

形态 机制 用途 不能用于
离线重放（cassette） 把每次模型响应与工具返回记录下来，重放时喂回记录 回归测试（改了代码，行为是否一致） 评估新模型（回放旧响应当然复现旧行为 —— 第 4 章的结论）
在线小样本 真跑，固定输入与种子，记录环境指纹 评估新版本（新模型/新提示词） 逐字回归（外部系统会变）

这个区分是评测设计的第一个岔路口：如果你想验证"新提示词更好"，必须用在线跑（离线重放永远显示"没变化"）；如果你想验证"我的重构没破坏行为"，必须用离线重放（在线跑会被外部变化干扰）。

四、最小评测集的设计#

4.1 覆盖"失效模式"而不是"功能点"#

这是本节最重要的一条。功能点覆盖的思路是"每个功能都要有用例"，结果是 200 条用例全在 happy path，而生产事故来自五个失效模式。正确做法是从失效模式反推用例：

用例来源={生产事故}∪{归因四象限的各种形态（第 2 节）}∪{边界输入}

具体做法（一个可操作的映射表）：

失效模式 用例形态
工具超时/失败 注入工具故障（第 3 章的错误分类逐类各一条）
结果未知（幂等） 让工具"执行成功但返回超时"，检查是否重复副作用
前提被证伪 提供一个与前设矛盾的输入
计划漏步 构造一个需要"容易漏掉的那一步"的输入
记忆污染 先写入一条错误记忆，再看后续是否被误导
上下文超载 长输入，检查是否剪裁而非崩溃
死锁/活锁（第 6 章） 构造互相等待的场景（多 Agent）
权限越界 提供一个诱导越权的输入（提示注入）

每一条生产事故都应该固化成一条用例（这就是"事故 → 用例"的闭环，4.5 会讲）。

4.2 每个用例必须自带什么#

字段 作用
input + env_snapshot 输入冻结（第 4 章）
判定器（可执行） 结果级评测
轨迹断言列表 轨迹级评测
预算上限（多维，第 5 章第 4 节） 效率评测 + 防跑飞
失败时归因所需的证据字段（第 2 节） 让失败可归因
期望的失效模式标签 便于按失效模式统计（而不是总体通过率）

倒数第一项容易被忽略但极有用：给每条用例打上"它想测哪个失效模式"的标签，于是报告可以是"每类失效模式的通过率"，而不是一个混合的总通过率。后者会把"简单任务全过、难任务全败"平均成一个看不出问题的数字。

4.3 规模：要多少条用例才够#

要判断"配置 A 比配置 B 好"，需要足够样本让差异不是噪声。用两个比例的比较（正态近似）：

n≳(p1​−p2​)2(z1−α/2​+z1−β​)2⋅[p1​(1−p1​)+p2​(1−p2​)]​

取 α=0.05（z=1.96）、β=0.20（z=0.84，即 80% 检验力）：

p1​ p2​ 需要 n（每组）
0.50 0.70 ≈ 91
0.60 0.70 ≈ 354
0.70 0.80 ≈ 291
0.80 0.90 ≈ 197
0.85 0.90 ≈ 683

读法：想区分 60% 与 70%，需要约 350 条用例。很多团队的评测集只有 20~50 条，却用它判断"新版本好 5%" —— 那个差异完全在噪声里。注意 n 对差异的大小非常敏感：0.80 vs 0.90（差 10 个百分点）只要约 200 条，而 0.85 vs 0.90（差 5 个百分点）要约 680 条 —— 需要区分的差异越小，样本量按平方增长。

这个公式的用途是"估算需要多少样本"，不是"证明差异显著"。两个必须避免的误用：

  1. 用同一批样本反复调参：调 20 个配置，挑在评测集上最好的那个 —— 即使所有配置都一样好，也必然有一个看起来最好。这叫过拟合评测集：

E[j=1..mmax​p^​j​]>p即使所有配置真实相同

让 m=20 个配置在 n=50 条用例上选出最大值，期望通过率会高出真实值几个百分点到十几个百分点。防线是 held-out 集：调参用 dev 集，报数用 test 集，且 test 集不参与任何决策。 2. 把统计显著当成业务显著：≈350 条用例能测出 +10% 的差异，但业务上 +10% 是否值得上线是另一个问题。

4.4 常见的评测集反模式#

反模式 后果 修正
只覆盖 happy path 通过率虚高，上线崩 按失效模式补用例（4.1）
用例互相重复（同一模式的 20 个变体） 样本量看着大，有效信息少 按失效模式去重，统计每类的通过率
用被测系统的输出作为期望值 自我实现的评测 期望值来自外部规格（人写/独立系统）
环境不固定 数字不可比 输入冻结 + 环境指纹（第三节）
无法判定的用例（标准模糊） 只能人工看，逐渐腐烂 要么形式化，要么标为"人工检查"并限制数量
没有预算上限 一个用例跑飞吃掉整轮预算 多维预算硬闸（第 5 章第 4 节）

4.5 维护：事故 → 用例的固化#

评测集的价值∝它覆盖的真实失效模式数

所以评测集应当随生产事故增长。每条事故的标准处置流程：

1. 用第 4 章的 journal + cassette 冻结这次事故的输入与环境
2. 写一条用例：input + env_snapshot + 判定器 + 轨迹断言 + 失效模式标签
3. 确认：修复前该用例失败（可复现），修复后通过
4. 加入回归集（离线重放形态，用于 CI）
5. 定期轮换 held-out 集，防止长期过拟合

第 3 步（修复前必须失败）是关键：一条"无论怎么改都通过"的用例是无效用例。这也顺带验证了"你确实定位到了原因" —— 它是第 2 节归因闭环的最后一步。

代码：双级评测框架 + 最小样本量 + 断言式轨迹评测#

下面的代码实现：(1) 用例与双级评测框架（含四种组合分类）；(2) 轨迹断言库；(3) 最小样本量计算；(4) 过拟合演示；(5) 可复现性诊断。

"""
ch7-l1：双级评测框架 + 断言式轨迹评测 + 最小样本量 + 过拟合演示。

设计目标：把"通过率 62%"这一个数字，拆成能指出"该改哪里"的报告。
"""
import math
import random
from dataclasses import dataclass, field


# ==================== 轨迹与用例 ====================
@dataclass
class Trace:
    steps: list[dict] = field(default_factory=list)   # [{tool, args, ok, cost, side_effect}]
    side_effects: list[str] = field(default_factory=list)
    evidence: list[str] = field(default_factory=list)
    facts_verified: int = 0
    tokens: int = 0
    cost: float = 0.0

    def calls(self) -> list[str]:
        return [s["tool"] for s in self.steps]


@dataclass
class Case:
    """★ 设计决策：每个用例自带失效模式标签与预算上限。

    标签让报告能按**失效模式**统计（而不是一个混合的总通过率）；
    预算上限防止单个用例跑飞吃掉整轮评测预算（第 5 章第 4 节的多维闸门）。
    """
    cid: str
    failure_mode: str                       # 这条用例想测哪种失效
    outcome_verifier: object                # (output) -> (bool, str)
    assertions: list = field(default_factory=list)   # [(name, fn)]
    budget_steps: int = 20
    budget_cost: float = 5.0
    env_fingerprint: str = "model:m1|tools:v3|prompt:p7"


@dataclass
class RunResult:
    output: object
    trace: Trace
    outcome_pass: bool
    outcome_note: str = ""
    assertion_results: dict[str, bool] = field(default_factory=dict)


# ==================== (2) 轨迹断言库 ====================
def must_call(tool: str):
    def f(tr: Trace) -> bool:
        return tool in tr.calls()
    return (f"must_call({tool})", f)


def must_not_call(tool: str):
    def f(tr: Trace) -> bool:
        return tool not in tr.calls()
    return (f"must_not_call({tool})", f)


def max_side_effects(n: int, kind: str | None = None):
    def f(tr: Trace) -> bool:
        items = [e for e in tr.side_effects if kind is None or e == kind]
        return len(items) <= n
    return (f"max_side_effects({n}{',' + kind if kind else ''})", f)


def must_cite_evidence():
    def f(tr: Trace) -> bool:
        return len(tr.evidence) > 0
    return ("must_cite_evidence()", f)


def max_steps(n: int):
    def f(tr: Trace) -> bool:
        return len(tr.steps) <= n
    return (f"max_steps({n})", f)


def no_repeat_failed_call(n: int):
    def f(tr: Trace) -> bool:
        counts: dict[str, int] = {}
        for s in tr.steps:
            if not s.get("ok", True):
                counts[s["tool"]] = counts.get(s["tool"], 0) + 1
        return all(v < n for v in counts.values())
    return (f"no_repeat_failed_call({n})", f)


def must_confirm_before(irreversible: str):
    def f(tr: Trace) -> bool:
        idx = [i for i, s in enumerate(tr.steps) if s["tool"] == irreversible]
        if not idx:
            return True
        return any(s["tool"] == "ask_confirmation" for s in tr.steps[:idx[0]])
    return (f"must_confirm_before({irreversible})", f)


def monotone_progress():
    def f(tr: Trace) -> bool:
        vals = [s.get("facts_verified", 0) for s in tr.steps]
        return all(b >= a for a, b in zip(vals, vals[1:]))
    return ("monotone_progress()", f)


# ==================== (1) 双级评测框架 ====================
@dataclass
class EvalReport:
    total: int = 0
    outcome_pass: int = 0
    traj_pass: int = 0
    # 四种组合
    true_success: list[str] = field(default_factory=list)
    lucky_success: list[str] = field(default_factory=list)     # ★ 结果过、轨迹不过
    wrongful_fail: list[str] = field(default_factory=list)     # ★ 结果不过、轨迹过
    true_fail: list[str] = field(default_factory=list)
    by_mode: dict[str, dict] = field(default_factory=dict)
    assertion_fail_counts: dict[str, int] = field(default_factory=dict)
    cost: list[float] = field(default_factory=list)
    steps: list[int] = field(default_factory=list)
    partial: list[tuple[str, int, list[str]]] = field(default_factory=list)

    def summary(self) -> dict:
        def pct(a: int, b: int) -> float:
            return round(a / b, 4) if b else 0.0
        return {
            "用例数": self.total,
            "结果通过率": pct(self.outcome_pass, self.total),
            "轨迹断言通过率": pct(self.traj_pass, self.total),
            "真成功": len(self.true_success),
            "★ 侥幸成功": len(self.lucky_success),
            "★ 冤枉失败": len(self.wrongful_fail),
            "真失败": len(self.true_fail),
            "成本 P50/P95": (round(sorted(self.cost)[len(self.cost) // 2], 2),
                             round(sorted(self.cost)[int(len(self.cost) * 0.95)], 2))
            if self.cost else (0, 0),
            "步数 P50/P95": (sorted(self.steps)[len(self.steps) // 2],
                             sorted(self.steps)[int(len(self.steps) * 0.95)])
            if self.steps else (0, 0),
        }


class EvalHarness:
    """★ 设计决策：结果级与轨迹级**必须分开**判定与记录，最后再交叉成四类。

    这保证了"侥幸成功"与"冤枉失败"不会被混进总通过率 ——
    而那两类恰恰是"该改 Agent"与"该改环境"的分界线。
    """

    def __init__(self, held_out_ids: set[str] | None = None) -> None:
        self.cases: list[Case] = []
        self.held_out_ids = held_out_ids or set()

    def add(self, c: Case) -> None:
        self.cases.append(c)

    def run(self, system) -> EvalReport:
        rep = EvalReport()
        for c in self.cases:
            rep.total += 1
            r: RunResult = system(c)                    # system(case) -> RunResult
            rep.cost.append(r.trace.cost)
            rep.steps.append(len(r.trace.steps))

            # 轨迹层：逐条断言
            traj_ok = True
            for name, fn in c.assertions:
                ok = bool(fn(r.trace))
                r.assertion_results[name] = ok
                if not ok:
                    traj_ok = False
                    rep.assertion_fail_counts[name] = rep.assertion_fail_counts.get(name, 0) + 1
            if traj_ok:
                rep.traj_pass += 1
            if r.outcome_pass:
                rep.outcome_pass += 1

            # ★ 四种组合：这是本框架的核心产出
            if r.outcome_pass and traj_ok:
                rep.true_success.append(c.cid)
            elif r.outcome_pass and not traj_ok:
                rep.lucky_success.append(c.cid)
            elif not r.outcome_pass and traj_ok:
                rep.wrongful_fail.append(c.cid)
            else:
                rep.true_fail.append(c.cid)

            # 按失效模式统计
            m = rep.by_mode.setdefault(c.failure_mode, {"n": 0, "outcome": 0, "traj": 0})
            m["n"] += 1
            m["outcome"] += int(r.outcome_pass)
            m["traj"] += int(traj_ok)

            # 部分完成（由判定器返回 notes 表示）
            if not r.outcome_pass and r.outcome_note.startswith("partial"):
                parts = r.outcome_note.split("|")
                missing = parts[2].split(",") if len(parts) > 2 else []
                k, n = (int(x) for x in parts[1].split("/"))
                rep.partial.append((c.cid, k, missing))
        return rep


# ==================== (3) 最小样本量 ====================
def z(p: float) -> float:
    """正态分位数（Acklam 近似的简化版，够用于样本量估算）。"""
    # 用有理逼近，误差 < 1e-3，足够本用途
    a = [-3.969683028665376e+01, 2.209460984245205e+02, -2.759285104469687e+02,
         1.383577518672690e+02, -3.066479806614716e+01, 2.506628277459239e+00]
    b = [-5.447609879822406e+01, 1.615858368580409e+02, -1.556989798598866e+02,
         6.680131188771972e+01, -1.328068155288572e+01]
    c = [-7.784894002430293e-03, -3.223964580411365e-01, -2.400758277161838e+00,
         -2.549732539343734e+00, 4.374664141464968e+00, 2.938163982698783e+00]
    d = [7.784695709041462e-03, 3.224671290700398e-01, 2.445134137142996e+00,
         3.754408661907416e+00]
    plow, phigh = 0.02425, 1 - 0.02425
    if p < plow:
        q = math.sqrt(-2 * math.log(p))
        return (((((c[0]*q+c[1])*q+c[2])*q+c[3])*q+c[4])*q+c[5]) / \
               ((((d[0]*q+d[1])*q+d[2])*q+d[3])*q+1)
    if p > phigh:
        q = math.sqrt(-2 * math.log(1 - p))
        return -(((((c[0]*q+c[1])*q+c[2])*q+c[3])*q+c[4])*q+c[5]) / \
               ((((d[0]*q+d[1])*q+d[2])*q+d[3])*q+1)
    q = p - 0.5
    r = q * q
    return (((((a[0]*r+a[1])*r+a[2])*r+a[3])*r+a[4])*r+a[5])*q / \
           (((((b[0]*r+b[1])*r+b[2])*r+b[3])*r+b[4])*r+1)


def min_sample_size(p1: float, p2: float, alpha: float = 0.05,
                    power: float = 0.80) -> int:
    """4.3 的公式：区分两个通过率需要多少样本（每组）。

    ★ 设计决策：返回的是"需要多少样本"的估算，**不是显著性检验**。
      它的用途是判断"我的 20 条用例能不能支撑 5% 的结论"——答案通常是不能。
    """
    z_a = z(1 - alpha / 2)
    z_b = z(power)
    num = (z_a + z_b) ** 2 * (p1 * (1 - p1) + p2 * (1 - p2))
    return math.ceil(num / (p1 - p2) ** 2)


def overfit_demo(n_configs: int, n_cases: int, true_p: float = 0.6,
                 seed: int = 0) -> dict:
    """4.3 的过拟合演示：所有配置一样好时，"评测集上的最优"期望是多少。"""
    rng = random.Random(seed)
    best = 0.0
    for _ in range(n_configs):
        hits = sum(1 for _ in range(n_cases) if rng.random() < true_p)
        best = max(best, hits / n_cases)
    return {"配置数": n_configs, "用例数": n_cases, "真实通过率": true_p,
            "评测集上最优": round(best, 3), "虚高": round(best - true_p, 3)}


# ==================== (5) 可复现性诊断 ====================
def reproducibility_check(case: Case, r1: RunResult, r2: RunResult,
                          env_now: str) -> dict:
    """三个必要条件逐条诊断（第三节）。"""
    issues = []
    if c2 := (case.env_fingerprint != env_now):
        issues.append(f"环境指纹变了（用例={case.env_fingerprint}, 现在={env_now}）"
                      f" → 结果差异无法归因到被测系统")
    if [s["tool"] for s in r1.trace.steps] != [s["tool"] for s in r2.trace.steps]:
        issues.append("两次运行的工具序列不同 → 未冻结随机种子或存在未记录的外部输入")
    if r1.outcome_pass != r2.outcome_pass:
        issues.append("两次结果判定不同 → 判定器依赖了外部变化的状态")
    return {"可复现": not issues, "问题": issues,
            "提示": "离线重放（cassette）用于回归；评估新版本必须在线跑（第 4 章）"}

八处关键设计决策：

  1. Case.failure_mode 是必填字段。这让报告能按失效模式统计（by_mode），而不是只给一个混合的总通过率 —— 后者会把"简单任务全过、难任务全败"平均成一个看不出问题的数字。
  2. EvalReport 里 lucky_success 与 wrongful_fail 是一等字段，并在 summary() 里单独报。这是本节的核心：这两种情况分别指向"该改 Agent"与"该改环境"，混进总通过率就失去了这个信息。
  3. 断言库全部是性质的（must_call / must_not_call / max_side_effects / must_confirm_before / monotone_progress），没有一条是"轨迹必须等于某序列"。演示第 2 段专门对照了这个差别：三条合法变体里逐字比对只通过 2 条，断言式全通过。
  4. max_side_effects(n, kind) 把不可逆动作的计数做成断言。这是第 3 章幂等与第 5 章回退的可测化：重复副作用在生产里是最贵的失效，而在评测里它可以被一条断言拦住。
  5. min_sample_size 的实现带一个正态分位数函数，并把用途写进文档字符串：它是"需要多少样本"的估算，不是显著性检验。这个区分很重要，否则团队会拿 20 条用例的差异当结论。
  6. overfit_demo 是本节唯一一个"用随机数演示一个统计事实"的函数：即使所有配置真实相同，"在评测集上挑最好"也会虚高。演示里 20 个配置 × 50 条用例的虚高幅度直接给出来了 —— 这就是 held-out 集的必要性证明。
  7. reproducibility_check 逐条诊断可复现的三个必要条件（环境指纹、轨迹一致、判定一致），并在返回里写明两种评测形态的分工（离线重放用于回归、在线跑用于评估新版本）。把第 4 章的 L0/L1/L2 结论直接接进来，避免重复推导。
  8. 最后一段把 pass@k 与 pass^k 的差值算出来。这是最容易被误用的指标：Agent 任务通常只执行一次，所以 pass@3 高而 pass^3 低意味着"跑三次有一次成"在生产上等于不可用。

  5. 部分完成：某任务有 7 个验收标准。方案 A 完成 6 个（缺"审计日志"），方案 B 完成 3 个（缺"审计日志"、"通知"、"重试"、"校验"）。请：(a) 用三级记录写出两者的结果；(b) 说明为什么"方案 A 记 85.7%、方案 B 记 42.9%"这种百分比记法不能指导优先级；(c) 给出你认为正确的报告形式。

  6. 可复现性：某团队发现"同一用例两次运行结果不同"，于是把温度设为 0，结果仍然不稳定。请列出至少四个可能原因（提示：第 4 章的确定性来源清单 + 评测特有的判定器解耦），并给出每个的验证方法。然后回答：如果他们的目标是"评估新提示词是否更好"，应该用离线重放还是在线跑？为什么？

  7. 最小评测集：为一个"客服工单自动处理 Agent"设计最小评测集。要求：(a) 从失效模式反推（≥8 类失效模式，每类给一个用例的构造方法）；(b) 给出每类用例的判定器与关键轨迹断言；(c) 估算总规模并说明依据（用 4.3 的公式）；(d) 设计"事故 → 用例"的固化流程（要包含"修复前必须失败"这一步）。

  8. 指标陷阱：某 Agent 的 pass@3 = 0.95、pass^3 = 0.55。请：(a) 解释这两个数字的差说明了什么；(b) 如果业务要求"每次执行都要成功"，这个 Agent 能不能上线，缺什么；(c) 给出两条降低单次方差的工程手段（提示：第 5 章的验证与第 4 章的确定性）。

小结#

  • 结果级与轨迹级不可互相替代，因为盲区互补：结果级看"成了吗"（业务语言、便宜），轨迹级看"为什么、该改哪里"（工程语言）。交叉得到四类：真成功 / 侥幸成功（结果过轨迹不过 → 缺陷被掩盖）/ 冤枉失败（结果不过轨迹过 → 该查环境不该改 Agent）/ 真失败。报告里没有这四类计数就是不完整的。
  • 轨迹评测必须用断言式，不是逐字比对：同一目标有多条合法路径⇒不存在唯一标准轨迹。逐字比对会把合法变体判为失败，于是你去优化"更像标准轨迹"而不是"更可靠"。断言类型覆盖漏步、越权、重复副作用、幻觉、效率、震荡、隔离。
  • 结果级判定的三种实现可靠性递减：确定性校验器 > 规则阈值 > 模型评判。用模型当裁判必须知道其系统偏差（位置/长度/自我/格式/顺从偏好），缓解手段是顺序随机化 + 双向比较 + 异源模型 + rubric 分解。判定器必须与被测系统解耦 —— 让被测 Agent 自评是第 5 章"自评不是验证"的错误搬到了评测阶段。
  • 部分完成必须显式且可枚举：结果∈{full,partial(k/n,缺失项),none}。只报百分比无法指导优先级。
  • 可复现有三个必要条件：输入冻结（种子 + 时钟注入）、环境指纹（模型/工具/提示词版本，第 4 章）、判定器与被测系统解耦。两种形态分工明确：离线重放（cassette）用于回归，在线跑用于评估新版本 —— 用离线重放评估新模型永远显示"没变化"（第 4 章的结论）。
  • 最小评测集覆盖失效模式而不是功能点，来源是生产事故 + 归因四象限 + 边界输入。每个用例必须自带：输入与环境快照、可执行判定器、轨迹断言、多维预算上限、失败时归因所需的证据字段、失效模式标签（让报告能按类统计）。
  • 规模可以估：n≳(p1​−p2​)2(z1−α/2​+z1−β​)2[p1​(1−p1​)+p2​(1−p2​)]​。区分 60% 与 70% 需要约 354 条；20 条只能看量级。必须防过拟合：同一批样本反复调参会让"评测集上的最优"系统性虚高（即使所有配置一样好），防线是 held-out 集（调参用 dev、报数用 test、test 不参与任何决策）。
  • 指标陷阱：Agent 任务通常只执行一次，所以该看 passk=∏单次成功率，而不是 pass@k。pass@3 高而 pass^3 低意味着生产不可用。另外成本与步数用分位数（P50​,P95​）而不是均值。
  • 评测集随事故增长：事故 → 冻结输入与环境（第 4 章）→ 写用例 → 确认修复前该用例失败 → 加入回归集 → 定期轮换 held-out。第三步是关键：一条"怎么改都通过"的用例是无效用例。

下一节：有了双级评测，我们能看到"失败了、而且过程有问题"。但问题出在模型、工具、规划还是记忆？第 2 节要给出失效归因四象限：每个象限的操作化判据、受控实验（只改一个变量）、以及为什么归因器本身也需要被评测。
