推理与部署：流式 vs 离线、端侧算力与功耗账、批处理与延迟权衡#

这一节要解决什么#

前两节把"能不能算"和"怎么算得便宜"讲完了。这一节换到部署视角，问的是最后一层工程问题：

同样的模型、同样的精度，摆在离线批处理、在线流式、端侧、边缘四种位置上，各自的瓶颈资源是什么？"实时"这个词在流式里是哪个量？把模型做小 5 倍在端侧能省多少电？为什么按平均延迟扩容的服务上线后会被尾延迟打崩？

全部结论如下：

  1. "实时"与"低时延"是两个方向，混淆它们会选错分块大小。 分块 b 时 tchunk​=btenc​+thead​，实时因子 RTF=tchunk​/(b/f)，算法时延 Lalg​=b/f+tchunk​。b:8→128 时 RTF 从 0.487500 降到 0.311719（更"跟得上"），而 Lalg​ 从 396.6667 ms 涨到 5.5967 s（更"不实时"）。b=32 时采集等待占 Lalg​ 的 74.25%——流式的时延下限由块长决定，不由算力决定（表 1）。
  2. 块内全注意力对边界帧的上下文保证是 0；重叠是唯一的解，价格恰好是 b/so​ 倍。 窗口长 b、步长 so​ 时 min_context=(b−so​)/2，反解 b≥2c+so​：要保证每帧至少 16 帧上下文、步长 16，需要 b=48（代价 3×、块内 KV 1.4766 GiB）（表 2）。
  3. 视频端侧是算力受限，LLM 解码是带宽受限——判据是一个与参数量无关的比值。 算术强度 I=2Ttok​/bw​ FLOP/byte，设备脊点 ridge=Feff​/BW。Ttok​=1（LLM 解码）时 I=2，远低于脊点 10∼80；Ttok​=64 时 I=128，已经超过高脊点 80（表 3）。"批处理对两者意义不同"的根源在此。
  4. 端侧功耗账被固定功耗主导。 每帧能量 E=tframe​W：tframe​=25.6 ms、W=1 W 时 25.6 mJ/帧、模型功耗 0.768 W；把 W 提到 5 W（5 倍），总功耗只从 2.7680 W 涨到 5.8400 W（2.1098 倍），15 Wh 续航从 5.4191 h 掉到 2.5685 h（保留 47.40%）。"模型做小 5 倍省 5 倍电"在端侧是错的（表 3）。
  5. 吞吐-延迟曲线有一个与 tfix​ 无关的渐近上限。 t(B)=tfix​+Btper​，吞吐 →1/tper​=83.3333 req/s；B=1 时只有渐近值的 0.1935。给定 SLO =0.30 s 反解 B∗=20.8333（表 4）。再加批只买到延迟，买不到吞吐。
  6. 静态批相对连续批的代价有硬上限 M+12M​，只与请求时长分布有关。 时长均匀 {1..M} 时：M=10 的上限是 1.818182（B=32 已达 1.811793），M=2 只有 1.333333（表 5）。请求本来就短时，连续批几乎没有收益。
  7. 按平均延迟扩容是灾难性的。 M/M/1 下 λ=18,μ=20 时 E[W]=500 ms 而 P99=2.2499 s（4.4998 倍）；ρ 从 0.9 涨到 0.975（8.33%）时 P99 涨 4.0712 倍到 9.1597 s。带 SLO 的正确容量式是 μ≥λ+1/Wmax​：λ=18、Wmax​=0.2 s 时 ρmax​=0.782609，不是 0.9（表 6）。
  8. 四种部署形态对应四种瓶颈，且"先检索"会把瓶颈换掉。 离线全扫 255.7000 GPU 秒/视频小时、单卡并发 14.0790 路（算力受限）；检索式 1.5535 秒（便宜 164.5961 倍），流式检索式被 SLO 批上限 20.8333 卡住（此时算力能撑 2317.3 路）。选型就是选"你被哪一个卡住"（表 7）。

一、流式 vs 离线：先把三个时延区分开#

1.1 三个时延不是一回事#

1.3 流式的状态与显存#

流式真正的显存压力来自块内二次注意力而不是模型权重：

KVchunk​=2L(bNc​)ds

L=28、Nc​=256、d=1152、s=2 时：b=8 是 0.2461 GiB，b=32 是 0.9844 GiB，b=128 是 3.9375 GiB（表 1）。这是与视频长度无关的常数——这是分块（第 1 节）买到的最重要的东西：显存峰值不随流长度增长。但它仍然随 b 线性增长，于是在端侧（内存通常几 GiB 且要和系统共享，见 §2）b 往往被内存而不是算力卡住。

跨块的状态（记忆槽位）是另一个常数：m=64、d=1152、s=2 时 mds=147456 B =144 KiB——可以忽略。所以流式的显存账是"块内 KV 主导、跨块状态可忽略、权重固定"三项，其中只有第一项是 b 的函数。

1.4 重叠窗口：最小上下文保证是 (b−so​)/2#

块内全注意力对边界帧不给任何保证（第 1 节的"硬断点"）。用重叠窗口（窗口长 b、步长 so​）补救时，可以给出一个紧的下界：窗口中心间距 so​，故任一帧最近的窗口中心距它不超过 so​/2，于是它在窗内较近一侧至少有

min_context(b,so​)=2b−so​​ 帧上下文,代价倍数=so​b​

反解（要保证每帧至少 c 帧）：

b ≥ 2c+so​

1.5 取舍/边界#

  • 先定 KPI 再选 b：KPI 是 RTF（不丢帧）就取大 b；KPI 是 Lalg​（快速响应）就取小 b。两者不可兼得。
  • thead​ 越小，b 的最优点越靠左：thead​→0 时 RTF→ftenc​（与 b 无关），此时唯一还随 b 变的就是 Lalg​，于是 b 应该取到最小。
  • 内存是第三条约束：KVchunk​∝b，端侧内存预算往往先把 b 定死，然后再看 RTF 够不够。
  • 重叠是"用算力买连续性"：b/so​ 倍的代价换 (b−so​)/2 帧的最小上下文。当 so​<b/2 时边际收益已经很小（b=32：so​ 从 16 到 8，代价翻倍只把保证从 8 提到 12）。

二、端侧与边缘：算力账、带宽账、功耗账#

2.1 算术强度：一个与参数量无关的判据#

端侧可行性的第一问不是"模型多大"，而是"这次前向会被算力还是带宽卡住"。对一次前向：

FLOPs=2PTtok​,权重字节=Pbw​ ⟹ I=Pbw​2PTtok​​=bw​2Ttok​​​ FLOP/byte

FLOPs=2PTtok​,权重字节=Pbw​ ⟹ I=Pbw​2PTtok​​=bw​2Ttok​​​ FLOP/byte

参数量 P 在比值里被约掉了。 设备侧对应的是脊点

ridge=BWFeff​​ FLOP/byte

判据：I>ridge 算力受限，否则带宽受限。表 3（BW=50 GB/s）：

Ttok​ bw​ I ridge@0.5e12 ridge@4e12 受限类型
1 1 2.000000 10.0000 80.0000 带宽受限
1 2 1.000000 10.0000 80.0000 带宽受限

这张表解释了一个经常被搞混的现象：LLM 端侧解码每步只处理 1 个 token，I=2/bw​（int8 时 2.000000），永远落在带宽受限区——所以 LLM 端侧的核心手段是"少读权重"（量化、稀疏、投机解码）。视频端侧每帧 64∼256 个 token，I=128∼512，先天是算力受限——核心手段是"少算"（第 2 节的采样/裁剪/合并/降采样）。两套优化手段之所以不同，是因为这个比值差了两个量级。

2.4 端侧可行性判据（一次算完）#

给定平台 (Fpeak​,η,BW,W0​,Cbatt​) 与模型 (P,Ttok​,bw​)，可行性是三条不等式同时成立：

实时性Fpeak​η2PTtok​​ ≤ f1​​​内存Pbw​+KVchunk​ ≤ Mavail​​​续航W0​+Fpeak​η2PTtok​​WfCbatt​​ ≥ Trequired​​​

把 §2.2 的数值代进第一条：25.6 ms ≤1/30=33.33 ms——勉强成立（余量 1.30 倍）。第二条由 §1.3 的 KVchunk​=2L(bNc​)ds 给出：b=32 要 0.9844 GiB，端侧通常拿不到，所以端侧的 b 一般被压到 4∼8。第三条用表 3 的 5.4191 h 判断是否满足 Trequired​。

注意三条不等式的耦合方向：减小 b 让内存变好、Lalg​ 变好，但 RTF 变差（表 1），而算力账不变。端侧的最优点通常落在"内存够、RTF 还有余量"的边界上，而不是任一条单独的最优点。

  • 流式检索式：同样的 W，但必须实时，于是并发被 SLO 批上限 20.8333 卡住——"先检索"把瓶颈从算力换成了延迟 SLO。 这是本节最实用的一条：优化手段换了，瓶颈也可能换；换了瓶颈之后，原来的优化就不再是收益。

def dwidth(s):
    return sum(2 if unicodedata.east_asian_width(ch) in ("W", "F") else 1 for ch in s)

    gap = max(0, w - dwidth(s))
    if align == ">":
        return " " * gap + s
    if align == "<":
        return s + " " * gap
    left = gap // 2
    return " " * left + s + " " * (gap - left)


def row(cells, widths, aligns=None):
    aligns = aligns or [">"] * len(cells)
    return " | ".join(pad(c, w, a) for c, w, a in zip(cells, widths, aligns))

小结#

  • 三个时延必须分开：采集等待 b/f、计算 tchunk​=btenc​+thead​、算法时延 Lalg​；RTF=ftenc​+fthead​/b 随 b 降，Lalg​ 随 b 升。b=32 时采集等待占 Lalg​ 的 74.25%。报"实时"必须带 b 与 KPI。
  • 块内 KV 是流式的显存主体：KVchunk​=2L(bNc​)ds，b=32 时 0.9844 GiB、b=128 时 3.9375 GiB；跨块状态 mds 只有 144 KiB（可忽略）。显存峰值与视频长度解耦，但仍随 b 线性增长。
  • 重叠的保证是紧的：min_context=(b−so​)/2，代价 b/so​，反解 b≥2c+so​；so​=b 时保证为 0.000000，so​→0 时上界 b/2。
  • 算术强度 I=2Ttok​/bw​ 与参数量无关：LLM 解码 I=2/bw​≈2（带宽受限），视频端侧 Ttok​=64∼256 给 I=128∼512（算力受限）。这解释了两套优化手段为什么不同。
  • 端侧三张账的排序：tc​=25.6000 ms vs tm​=6.0000 ms（4.2667 倍）→ 先省算力；功耗 Wtotal​=W0​+Wmodel​，模型功耗涨 5 倍续航只掉到 47.40%——W0​ 主导端侧功耗账。
  • 吞吐-延迟：吞吐 →1/tper​=83.3333 req/s，B=1 只有 0.1935，SLO 0.30 s 反解 B∗=20.8333。超过 B∗ 只买到延迟。
  • 静态批的代价上限是 M+12M​：M=10→1.818182、M=2→1.333333。请求越"齐"，连续批越不值得。
  • 尾延迟不是均值的常数倍：λ=18,μ=20 时 P99 是均值的 4.4998 倍；ρ:0.9→0.975 时 P99 涨 4.0712 倍。容量公式 μ≥λ+1/Wmax​，ρmax​ 随 λWmax​ 变化（18×0.2 时 0.782609）。
  • 四种瓶颈不可换算：吞吐 255.700000 GPU 秒/视频小时、算力 14.0790 路、延迟 SLO 20.8333 路、功耗（端侧，W 与小时）。换优化手段会换瓶颈，换了瓶颈原来的优化就不再是收益。
