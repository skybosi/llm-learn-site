Mac 与云实例#

不想买昂贵的 H100，又需要跑大模型，摆在面前的有两条典型路线：用 Apple Silicon 的 Mac（大统一内存、低功耗）和租云上的 GPU 实例（按小时付费、算力强）。学完本课，你应当能说清两者的架构差异、各自的代价，以及什么场景该选谁。

一、概念讲解#

1. Apple Silicon：统一内存架构#

Mac 的 M 系列芯片（M1/M2/M3/M4 的 Pro/Max/Ultra）用统一内存（unified memory）：CPU 和 GPU 共享同一块高速内存，模型直接放进这大内存里，不需要像独立 GPU 那样经 PCIe 来回搬。关键规格有两项：

  • 容量：M3 Max / M4 Max 最高约 128 GB，M2 Ultra 最高约 192 GB——能装下 70B 甚至更大模型；
  • 带宽：M3 Max 约 400 GB/s，M4 Max 约 546 GB/s，M2 Ultra 约 800 GB/s。

这个带宽和 H100 的 3.35 TB/s 仍有几倍差距，但换来了巨大的统一内存容量和极低的整机功耗。

2. Mac 的优与劣#

  • 优势：几十 GB～上百 GB 内存，一次买断、长期可用、安静省电，适合本地跑 70B 量化的个人实验；
  • 劣势：绝对带宽偏低（生成速度受限）、算力有限、软件生态较新（主要靠 MLX / llama.cpp 等），多机扩展、高并发服务能力弱。

简单说：Mac 是"能跑起来，但不追求快"的个人方案。

3. 云 GPU 实例：按小时租算力#

不想一次投入大笔钱买卡，就租云厂商的 GPU 实例：

  • 公有云：AWS（p4d 是 A100、p5 是 H100）、GCP、Azure，按需付费，配套成熟但单价高；
  • GPU 云（性价比向）：Lambda、RunPod、Vast.ai 等，单价低、按秒/小时计费，适合个人和中小团队。

云实例的付费模式多样：按需（on-demand）最贵但随时可用，竞价/现货（spot）便宜但有被回收风险，预留/包月介于两者之间。

4. 决策要点#

选 Mac 还是云，本质是"拥有 vs 租用"与"容量 vs 速度"的权衡：要便宜地跑大模型做实验、不在乎速度，Mac 划算；要服务真实用户、要高吞吐、要快速迭代，云 GPU 更合适。

二、可运行示例#

用带宽估算 Mac 跑不同模型的解码吞吐，再和云 GPU 的"每 token 成本"放到一起对比。

# -*- coding: utf-8 -*-
# 对比 Mac（统一内存）与云 GPU 实例的吞吐与成本

def decode_throughput(bandwidth_gb_s, params, bytes_per_param=2):
    """解码吞吐 ≈ 带宽 / 每 token 需读权重字节数（访存密集近似）。"""
    return bandwidth_gb_s * 1e9 / (params * bytes_per_param)

# Apple Silicon 的大致带宽（GB/s）
macs = {
    "M3 Max (约400GB/s)":  400,
    "M4 Max (约546GB/s)":  546,
    "M2 Ultra (约800GB/s)": 800,
}
# 云 GPU 对照
cloud_gpus = {
    "A100 80G (2.0TB/s)": 2039,
    "H100 80G (3.35TB/s)": 3350,
}

print("跑 7B（FP16）模型的解码吞吐（tokens/s）：")
for name, bw in macs.items():
    print(f"  Mac  {name:<22} {decode_throughput(bw, 7e9):>7.1f}")
for name, bw in cloud_gpus.items():
    print(f"  云   {name:<22} {decode_throughput(bw, 7e9):>7.1f}")

# 70B 量化（INT4，每 token 约读 35 GB）在 Mac 上能否顺畅跑
print("\n跑 70B（INT4，每 token 约 35 GB）的吞吐：")
for name, bw in macs.items():
    print(f"  Mac  {name:<22} {decode_throughput(bw, 70e9, bytes_per_param=0.5):>7.1f}")

# 成本视角：每 100 万 token 的成本（仅算硬件/租金，不含电费等）
def cost_per_million_tokens(hourly_price, tokens_per_sec):
    """每小时租金 / (每秒 token × 3600) × 1e6 = 每百万 token 成本（美元）。"""
    tokens_per_hour = tokens_per_sec * 3600
    return hourly_price / tokens_per_hour * 1e6

# 云实例参考价（美元/小时，波动大，仅作示例）
instances = {
    "H100 云 (约$2.5/h)":    (2.5,  decode_throughput(3350, 7e9)),
    "A100 云 (约$1.3/h)":    (1.3,  decode_throughput(2039, 7e9)),
    "RTX 4090 云 (约$0.7/h)": (0.7,  decode_throughput(1008, 7e9)),
}
print("\n云实例跑 7B 的每百万 token 成本（美元，估）：")
for name, (price, tps) in instances.items():
    print(f"  {name:<26} {tps:>6.1f} tok/s -> ${cost_per_million_tokens(price, tps):.2f}/百万token")

# Mac：假设 M2 Ultra 整机约 $4000，按 3 年折旧到每月 111 美元，忽略电费
mac_monthly = 4000 / 36
mac_tps = decode_throughput(800, 7e9)
mac_cost = cost_per_million_tokens(mac_monthly / 730, mac_tps)   # 月费摊到每小时
print(f"\nM2 Ultra 自购（约$4000，3 年折旧）跑 7B：{mac_tps:.1f} tok/s -> 约 ${mac_cost:.2f}/百万token（未计电费）")

运行后你会看到：Mac 跑 7B 的吞吐只有 H100 的几分之一，但没有每小时租金，折旧摊下来单位 token 成本可以非常低——前提是你能接受它的速度。这是"容量与低价"换"速度"的典型权衡。

三、练习#

  1. 手算吞吐：M2 Ultra 带宽约 800 GB/s，跑 7B FP16（每 token 约读 14 GB），吞吐约多少 token/s？
  2. 换模型：把模型改成 13B 和 70B（INT4），观察 Mac 吞吐的下降，解释为什么"模型越大，Mac 的体验下降越明显"。
  3. 改价格：把 H100 云单价从 2.5 改成 1.0（spot/促销价），重算每百万 token 成本，体会"竞价实例"对成本的冲击。
  4. 算折旧：把 Mac 折旧年限改成 5 年、整机价改成 7000 美元，重算单位成本，看看"用得更久"对摊薄成本的作用。
  5. 思考：如果你要对外提供一个 7B 模型的在线问答服务，你会选 Mac 还是云 GPU？如果只是自己本地跑一个 70B 助手呢？分别说明理由。
