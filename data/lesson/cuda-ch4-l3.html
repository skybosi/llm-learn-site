TMA 与 Hopper 起的异步数据搬运#

上一课的 cp.async 已经让搬运不经过寄存器，但"谁去搬"这件事没变：每个线程仍要自己算 global 与 shared 地址、发自己的那条指令。搬一个 16 KiB 的 tile，256 个线程要发 1024 条指令，全部占用发射槽（issue slot）——这些指令不搬数据，只是在指挥搬运。Hopper（compute capability 9.0）引入的 TMA（Tensor Memory Accelerator，张量内存加速器）把整块多维搬运压缩成"一个线程发一条描述符"的动作。

一、概念讲解#

1. 描述符搬运：TMA 的模型#

官方 Hopper Tuning Guide 对 TMA 的定位很明确：它在 Ampere 异步拷贝基础上提供更完整的异步拷贝引擎，能在 global 与 shared memory 之间双向搬运 1D 到 5D 张量，也能在同一 cluster 内不同 SM 的 shared memory 之间搬运。有四个直接后果：

  1. 搬运不用寄存器：数据不再借道线程的寄存器文件。
  2. 搬运不用 SM 指令：单个线程就能发起大批量搬运，整个 block 可以继续干别的活，只在真正要消费数据时才等。
  3. 让 warp specialization（线程束特化）变得自然：一部分 warp 专管数据搬运，另一部分只算片上的数据（第 5 课展开）。
  4. shared → global 方向可带规约：写回时支持按元素做 add/min/max，以及多数数据类型上的按位与/或。

和第 2 课的指令账对比：同样 16 KiB 的 tile、256 线程，同步路径 8 条指令/线程、cp.async 4 条，而 TMA 是整块 1 条——逐元素地址计算被外包给了专用硬件。

2. 描述符（TensorMap）与硬约束#

TMA 的搬运任务不是循环语句，而是一个描述符：用 cuTensorMapEncodeTiled 把张量的形状、步长、要搬的盒子（box）以及布局变换一次性编码好。主要参数包括 rank、globalAddress、globalDim、globalStrides、boxDim、elementStrides、interleave、swizzle、fill mode。

几条约束直接影响能不能用：

约束 内容
对齐 global 地址与 stride 按 16 字节对齐；shared memory 目标也要求 16 字节对齐。cuda::memcpy_async 只有在两边 16 字节对齐且大小是 16 的倍数时才走 TMA，否则回退成同步拷贝
box 尺寸 每个维度的 box 以元素计不能超过 256（以官方 cuTensorMapEncodeTiled 文档为准）
swizzle 上限 32B/64B/128B swizzle 分别要求 box 内层维度不超过 32/64/128 字节
完成信号 用 mbarrier（异步 barrier）：发起前声明期望的事务字节数（barrier_expect_tx），搬运完成时硬件累减，归零即完成；1D bulk 拷贝也可走 bulk async-group

跑在更低层时用 cuda::ptx::cp_async_bulk（PTX 的 cp.async.bulk.tensor）；它总是走 TMA，条件不满足就是未定义行为——这正是"先自检几何"必须写进代码的原因。

3. swizzle：TMA 顺手把 bank conflict 也解决了#

TMA 写 shared memory 时可以让列坐标按固定模式打乱，目的写在官方文档里：避免 shared memory bank conflict。以 128 字节 swizzle 为例（CUTLASS 记作 Swizzle<3,4,3>，具体以官方实现为准）：一个 128 字节的行被切成 8 个 16 字节块，第 c 块的数据实际写到第 c⊕(rowmod8) 块的位置。

为什么有用？下一节的代码把 32 个 bank 的映射算了出来：同一列、跨 32 行的一次 warp 访问，不 swizzle 时 32 个线程全落在同一个 bank，是 32-way conflict、要 32 拍；128B swizzle 后落到 8 个不同 bank，降到 4-way；只在一个 8 行组内访问时是 1-way（无冲突）。也就是说，TMA 顺手做掉了一部分本来要手写的 padding/转置技巧。

注意 swizzle 改变了 shared memory 的物理布局：读的时候必须用同一套模式（CUTLASS 用布局类型把这件事变成编译期检查），否则拿到的是错位数据。

4. multicast：cluster 内一次搬运，多份落地#

Hopper 还引入了 thread block cluster（线程块簇）这一层：cluster 内的 block 可以互相读写对方的 shared memory（分布式共享内存）。TMA 在这里有一个额外能力——multicast：一次搬运把同一块 global 数据同时送进 cluster 内多个 block 的 shared memory。

收益直接：C 个 CTA 都要同一个 A tile 时，没有 multicast 要从 L2 搬 C 份，有 multicast 只搬 1 份，L2 → SM 流量降到 1/C（数字见下节代码）。cluster 的 portable 上限是 8，H100 上可选非 portable 的 16（需显式打开 cudaFuncAttributeNonPortableClusterSizeAllowed），更大 cluster 可能降低同时驻留的 block 数。

5. 与 cp.async 的选择#

维度 同步 LDG/STS cp.async（LDGSTS） TMA
谁发指令 每个线程 每个线程（4/8/16 字节） 单线程发整块描述符
占寄存器 是 否 否
维度 任意 逐元素（高维需手工算地址） 1D–5D，硬件算地址
对齐要求 宽松 4/8/16 字节，128B 最佳 16 字节对齐（含 stride）
完成机制 __syncthreads() commit/wait group mbarrier + expect_tx
额外能力 — L1 bypass（16B） swizzle、multicast、写回规约
适用 小/不规则 中小块、逐元素 大块、规则多维（GEMM/Attention）

结论不是"TMA 取代一切"：搬运越规则、块越大、维度越高，TMA 优势越明显；零散的不规则访存仍要靠 cache 与 cp.async 兜底。

6. 常见坑#

  • 忘记 expect_tx：mbarrier 的事务计数没声明，等不到归零，直接死锁。
  • 忘记代理栅栏：用普通（generic proxy）方式写完 shared memory 再让 TMA（async proxy）去读，中间要有 fence.proxy.async，否则读到旧值。
  • 对齐/stride 不满足：cuTensorMapEncodeTiled 会失败，或上层 cuda::memcpy_async 静默回退同步拷贝（性能掉了但结果对，最难发现）。
  • swizzle 只做了一半：写用 128B、读按线性布局，数据错位。
  • box 超限：单维超过 256 个元素、内层超过 swizzle 宽度，描述符建不出来。
  • 以为 TMA 能提升复用：它只让搬运更省指令、更好重叠；复用仍来自第 1 课的 tiling。

二、可运行代码示例#

三段纯 Python：几何与对齐自检（把描述符的约束变成可跑的断言）、swizzle 的 bank conflict 计算、multicast 的 L2 流量账。

# ===== 本课示例：TMA 几何自检 + swizzle 消冲突 + multicast 流量账 =====
import numpy as np

# ---------- 1. TMA 几何与对齐自检 ----------
def check_tma(rows, cols, itemsize, box_rows, box_cols, swizzle_bytes=128, name=''):
    stride_b = cols * itemsize
    inner_b = box_cols * itemsize
    ok_addr = stride_b % 16 == 0
    ok_box = box_cols <= 256 and box_rows <= 256
    ok_sw = inner_b <= swizzle_bytes
    tiles = -(-rows // box_rows) * -(-cols // box_cols)
    print(f"{name}: {rows}x{cols} {itemsize*8}bit, box {box_rows}x{box_cols}, swizzle {swizzle_bytes}B")
    print(f"  行 stride = {stride_b} B ({'16B 对齐 ✓' if ok_addr else '16B 未对齐 ✗'})；"
          f"box 内层 {inner_b} B {'≤ swizzle ✓' if ok_sw else '> swizzle ✗'}；"
          f"box 维度 {'≤256 ✓' if ok_box else '>256 ✗'}")
    print(f"  tile 数 = {tiles}，每 tile {box_rows*box_cols*itemsize} B，"
          f"每 tile 1 次 TMA 事务 → 共 {tiles} 次（cp.async 需 {box_rows*box_cols*itemsize//16} 条指令）")

check_tma(8192, 8192, 2, 128, 64, 128, 'A 的 128x64 tile')
check_tma(8192, 8192, 2, 128, 72, 128, 'box 内层超 swizzle')
check_tma(8192, 8191, 2, 128, 64, 128, '行宽奇数（stride 未对齐）')

# ---------- 2. swizzle 如何消除 bank conflict ----------
R, C, ITEM = 32, 64, 2                 # 32 行 x 64 个 fp16 = 128 B/行
assert C * ITEM == 128
def bank(r, c, swizzle):
    if swizzle:                        # 128B swizzle：16B 块下标 ^ (行号 % 8)
        off = r * C + ((c // 8) ^ (r % 8)) * 8 + (c % 8)
    else:
        off = r * C + c
    return (off * ITEM // 4) % 32

def conflict(rows, c, swizzle):
    banks = [bank(r, c, swizzle) for r in rows]
    counts = np.bincount(banks, minlength=32)
    return int(counts.max()), len(set(banks))

print(f"\n同一列、跨 {len(range(0,32))} 行的 warp 访问（列 c=24）")
for sw in (False, True):
    deg, used = conflict(range(32), 24, sw)
    print(f"  {'128B swizzle' if sw else '不 swizzle':<12} bank 冲突 = {deg}-way，"
          f"用到 {used} 个不同 bank，耗时 {deg} 拍")
for r0 in (0, 8, 16, 24):
    deg, used = conflict(range(r0, r0 + 8), 24, True)
    print(f"  128B swizzle，8 行组 r=[{r0},{r0+7}] → {deg}-way（{used} 个 bank）")

# ---------- 3. cluster multicast 省下的 L2 流量 ----------
tile_b = 128 * 64 * 2
print(f"\n一个 128x64 fp16 tile = {tile_b} B；cluster 内 C 个 CTA 共享同一块 A tile：")
for Cl in (1, 2, 4, 8):
    print(f"  C={Cl}: 无 multicast {Cl*tile_b:>6} B，有 multicast {tile_b:>6} B，"
          f"L2→SM 流量降到 1/{Cl}")

三、练习#

  1. 实现：给 check_tma 增加"元素类型为 int8、box 内层 256 字节"的用例，判断 128B swizzle 是否可用；再给出两种修法（换 swizzle 模式、拆 box），并说明各自的代价。
  2. 解释：为什么 TMA 需要 mbarrier + expect_tx 这套"事务计数"机制，而 cp.async 只需要 commit/wait group？（提示：一次 TMA 搬运的字节数是硬件按描述符展开的，发起线程并不知道会分成多少个内部事务。）
  3. 对比/验证：把 swizzle 的 XOR 改成 row % 4、row % 16 各算一次跨 32 行访问的 bank 冲突，解释为什么 128B swizzle 选的是 % 8。
  4. 思考：multicast 把 L2 → SM 流量降到 1/C，但 cluster 变大会降低可驻留 block 数。你会用什么量来判断某个 GEMM 配置是否该开 cluster？写出判断式。
