Profiling 实战：用 ncu 定位瓶颈并给出优化前后数据#

第 7 章结束时你手上已有 GEMM、Attention、Triton 三套实现，但"下一个该优化哪个"仍只能靠感觉。差别在于：没有假设就不要开 profiler。本课把 profile 变成能产出结论的动作——先用 nsys 找到值得看的 kernel，再用 ncu 拿到搬运量与 SOL（Speed Of Light，相对理论峰值的达成率），最后把优化前后写成一张可逐项复核的表。

一、概念讲解#

1. 三问法：进 profiler 之前先写下预测#

开 ncu 之前必须能用一句话回答三个问题，否则拿到的是几百个指标而不是结论：这个 kernel 的时间由哪个资源决定？（用第 1 章的算术强度 AI=FLOPs/搬运字节 与拐点比大小）；离该资源上限还差多少？（即 SOL，必须给数字）；下一步动作是什么？（减字节、提合并度、提 occupancy，还是收手）。

价值在于预测错了才有信息量：预测"GEMM 1024³ fp32 要搬 2MNK×4=8.6×109 字节、带宽打满约 4.3 ms"，实测 5.1 ms 说明带宽只到八成，该查合并度与 L2 复用；实测 50 ms 则说明瓶颈根本不是带宽。

2. ncu 与 nsys 的分工：一个看全局，一个看单个 kernel#

Nsight Systems（nsys） Nsight Compute（ncu）
粒度 整个程序时间线：kernel、memcpy、同步、CPU 段 单个 kernel 内部的资源使用
采集 单遍采集，不刷 cache 默认重放 kernel，多趟采集
时钟 不锁频 默认锁 SM 频率
发射 不串行化 默认串行化 kernel 发射
回答 哪个 kernel / 哪段代码值得看 这个 kernel 卡在哪、还剩多少

顺序是 nsys 缩小范围 → ncu 深挖；同一 kernel 在两条命令下时长常有出入，原因就是上表后三行——跨工具比数字前必须先统一这三条（见 §5）。

3. 读 SOL 段：两条吞吐决定下一步动作#

SpeedOfLight（界面名 "GPU Speed Of Light Throughput"）给出 Compute 与 Memory 两条吞吐，都是"相对理论最大值的百分比"。名称规律是基名 + 后缀：sm__throughput 只是基名、不能直接取值，sm__throughput.avg.pct_of_peak_sustained_elapsed 才可求值（分母是 elapsed cycle），..._sustained_active 的分母则是单元 active cycle——报告里必须写清用了哪个。

Compute 吞吐 Memory 吞吐 结论与动作
低 低 延迟受限 → 查 occupancy、stall 原因
高 低 算力受限 → 减指令数、提 ILP、考虑 Tensor Core 路径
低 高 带宽受限 → 减搬运字节（tiling/融合）或提合并度
高 高 接近硬件上限 → 收益递减，收手并写结论

两段补充细节：MemoryWorkloadAnalysis 回答"字节从哪来、浪费在哪"，LaunchStats 回答"配置是否合理"。Roofline 图（SpeedOfLight_Hierarchical*RooflineChart）把两条屋顶与当前算术强度画在一起，适合一眼判断该减字节还是减指令。

4. 有效带宽 vs 实际带宽：浪费率才是可行动的数字#

Best Practices Guide 的有效带宽定义（Br​、Bw​ 为每次 kernel 读/写字节数）：

Effective bandwidth=time(Br​+Bw​)÷109​(GB/s)

它用的是算法要求搬的字节；硬件真正搬的字节（含没用上的扇区）更大，官方直接把两者之差定义为 coalescing 不理想造成的浪费：浪费率=实际带宽/有效带宽−1。

第 3 章给过口径：访存事务的最小单位是 32 字节的扇区（sector），L1/L2 cache line 是 128 字节 = 4 个扇区。浪费率无非三种来源：跨步访问只用一个扇区里的几个字节、边界不对齐使事务数翻倍、L2 复用不足。三者动作完全不同，单看时长区分不了——报文节数，不要只报时长。

5. 测量的卫生：五条会影响结论的默认行为#

  1. cache 被刷：ncu 默认在重放各趟间刷掉全部 GPU cache，测到的是冷 cache 数字；对象高度依赖 cache 时，官方建议改用 --replay-mode application --cache-control none。
  2. 频率被锁 / 发射被串行化：要与 nsys 对比，官方建议先用 nvidia-smi 外部锁频、再给 ncu 加 --clock-control none；本该并发的多个 kernel 也会被排开，此时时长不代表真实场景。
  3. 开销被计入：依赖 software patching 的指标会给 kernel 执行引入显著开销；ncu 文档明确说明，profiling 时用 host 计时器或 CUDA event 反推 kernel 时长是不可能的——要时长就用 gpu__time_duration。
  4. 采集范围要收窄：不给 --set/--section/--metrics 时只采 basic 集合，很多指标是空的；--set full 采全部段但更慢。先用 --list-sets、--list-sections 看本机有什么，再用 --kernel-name、--launch-count 压住重放次数。

指标名一律用本机清单核对：示例 CSV 的列名是示意名，真名要用 ncu --query-metrics 在本机确认（--query-metrics-mode suffix --metrics sm__throughput 可列出该基名全部后缀）；抄别人的指标名是最常见的翻车方式。

6. 常见坑#

  • 只报时长不报字节：时长受频率、并发、cache 状态影响，字节数不会。
  • 把 SOL 100% 当目标：分母假设了理想访存模式，达不到不等于代码差。
  • 拿一次运行下结论：机器噪声与降频都会影响结果，屋顶要多测几次取最优值。
  • 把 basic 集合当 full 集合：没加 --set full 时该段根本没采，却得出"没有 bank conflict"。

二、可运行代码示例#

下面这段纯标准库代码把方法固化成工具：解析 ncu CSV → 自己从原始字节与时长算 SOL → 与 ncu 报的百分比交叉核对 → 输出优化前后账本与浪费率：

# ===== 本课示例：把 ncu 报告变成瓶颈结论 =====
# 依赖：仅标准库。直接 python3 l1.py 即可运行（无 GPU 也能跑）。
import csv
import io
import re

# ---------- 1. 一段 ncu CSV 导出片段 ----------
# 说明：CSV 的列名由"你实际采了哪些指标"决定，ncu 版本与架构不同则名字不同。
# 下面这些列名是为了让解析器可运行而写的示意名；真实名字请用
#   ncu --query-metrics | grep -E 'dram|throughput|registers|duration'
# 在你自己机器上确认，再把 parse_ncu_csv 里的键名换成它。
NCU_CSV = '''"ID","Kernel Name","gpu__time_duration.sum","dram__bytes_read.sum","dram__bytes_write.sum","sm__throughput.avg.pct_of_peak_sustained_elapsed","dram__throughput.avg.pct_of_peak_sustained_elapsed","launch__registers_per_thread","sm__warps_active.avg.pct_of_peak_sustained_active","l1tex__data_bank_conflicts_pipe_lsu.sum"
"0","gemm_naive(float*, float*, float*)","5.10 ms","8,589,934,592","4,194,304","2.2 %","84.3 %","24","62.5 %","131072"
"1","gemm_tiled(float*, float*, float*)","195.0 us","268,435,456","4,194,304","55.1 %","70.2 %","96","50.0 %","2097152"
'''

UNIT = {"s": 1e0, "ms": 1e-3, "us": 1e-6, "ns": 1e-9}

def parse_value(raw):
    """把 ncu 的值转成 (数, 单位)：'5.10 ms'->(5.10,'ms')；'84.3 %'->(84.3,'%')。"""
    raw = raw.strip().replace(",", "")
    m = re.match(r"^(-?[\d.]+(?:[eE][-+]?\d+)?)\s*([a-zA-Z%]*)$", raw)
    return (float(m.group(1)), m.group(2)) if m else (float("nan"), "")

def parse_ncu_csv(text):
    """ncu CSV -> {kernel: 秒/字节/百分数}。跳过 ==PROF== 等非数据行。"""
    body = "\n".join(l for l in text.splitlines() if not l.startswith("==PROF=="))
    out = []
    for r in csv.DictReader(io.StringIO(body)):
        v = {k: parse_value(x) for k, x in r.items() if k and x}
        dur, unit = v.get("gpu__time_duration.sum", (float("nan"), ""))
        out.append({
            "kernel": r["Kernel Name"].split("(")[0],
            "seconds": dur * UNIT.get(unit, float("nan")),
            "bytes": int(v.get("dram__bytes_read.sum", (0, ""))[0]
                         + v.get("dram__bytes_write.sum", (0, ""))[0]),
            "sm_pct": v.get("sm__throughput.avg.pct_of_peak_sustained_elapsed", (0, ""))[0],
            "dram_pct": v.get("dram__throughput.avg.pct_of_peak_sustained_elapsed", (0, ""))[0],
            "regs": int(v.get("launch__registers_per_thread", (0, ""))[0]),
            "occ_pct": v.get("sm__warps_active.avg.pct_of_peak_sustained_active", (0, ""))[0],
        })
    return out

# ---------- 2. 三问定位：算力打满还是带宽打满？还剩多少？ ----------
def sol_report(row, flops, peak_gbs, peak_tflops):
    """peak_gbs / peak_tflops 必须来自自己显卡的官方规格，本函数不做任何假设。"""
    t = row["seconds"]
    floor_mem, floor_cmp = row["bytes"] / (peak_gbs * 1e9), flops / (peak_tflops * 1e12)
    ai = flops / row["bytes"]                             # 算术强度 FLOP/Byte
    balance = peak_tflops * 1e12 / (peak_gbs * 1e9)       # 机器拐点 FLOP/Byte
    floor = max(floor_mem, floor_cmp)
    return {
        "kernel": row["kernel"], "seconds": t, "bytes": row["bytes"],
        "ach_gbs": row["bytes"] / t / 1e9,                # 有效带宽 (Br+Bw)/t
        "sol_mem_pct": 100 * floor_mem / t, "sol_cmp_pct": 100 * floor_cmp / t,
        "ai": ai, "balance": balance, "floor_s": floor,
        "bound": "memory-bound" if ai < balance else "compute-bound",
        "ceiling_x": t / floor,
    }

M = N = K = 1024
FLOPS = 2 * M * N * K
PEAK_GBS, PEAK_TFLOPS = 2000.0, 20.0   # 占位示例：请替换为你显卡官方规格的数字
rows = parse_ncu_csv(NCU_CSV)
print(f"GEMM {M}x{N}x{K} fp32：FLOPs = {FLOPS:,}；假设峰值 带宽 {PEAK_GBS:.0f} GB/s、"
      f"fp32 算力 {PEAK_TFLOPS:.0f} TFLOP/s（占位，请换成官方规格）")
print(f"机器拐点 = 算力/带宽 = {PEAK_TFLOPS*1e3/PEAK_GBS:.1f} FLOP/Byte\n")
hdr = (f"{'kernel':<12}{'时长(ms)':>10}{'DRAM 字节':>18}{'有效带宽GB/s':>13}{'带宽SOL':>9}"
       f"{'算力SOL':>9}{'AI':>8}{'瓶颈':>14}{'还能快':>8}")
print(hdr); print("-" * len(hdr))
rep = {}
for r in rows:
    s = sol_report(r, FLOPS, PEAK_GBS, PEAK_TFLOPS); rep[r["kernel"]] = s
    print(f"{s['kernel']:<12}{s['seconds']*1e3:>10.3f}{s['bytes']:>18,}{s['ach_gbs']:>13.1f}"
          f"{s['sol_mem_pct']:>8.1f}%{s['sol_cmp_pct']:>8.1f}%{s['ai']:>8.2f}{s['bound']:>16}"
          f"{s['ceiling_x']:>7.2f}x")

# ---------- 3. 交叉核对：自己算出的 SOL 与 ncu 报的百分比是否一致 ----------
print("\n[核对] 从原始字节/时长算出的 SOL  vs  ncu 直接报的百分比（差 < 1 个百分点说明解释一致）")
for r in rows:
    s = rep[r["kernel"]]
    print(f"  {s['kernel']:<12} 带宽 {s['sol_mem_pct']:6.1f}% vs {r['dram_pct']:6.1f}%   "
          f"算力 {s['sol_cmp_pct']:6.1f}% vs {r['sm_pct']:6.1f}%   "
          f"寄存器 {r['regs']:>3}  达成 occupancy {r['occ_pct']:.1f}%")

# ---------- 4. 优化前后账本：倍数从哪来、还剩多少 ----------
before, after = rep["gemm_naive"], rep["gemm_tiled"]
print(f"\n[账本] 时长 {before['seconds']*1e3:.3f} ms -> {after['seconds']*1e3:.3f} ms = "
      f"{before['seconds']/after['seconds']:.1f}x")
print(f"       DRAM 字节 {before['bytes']:,} -> {after['bytes']:,} = 降到 "
      f"1/{before['bytes']/after['bytes']:.0f}")
print(f"       有效带宽 {before['ach_gbs']:.0f} -> {after['ach_gbs']:.0f} GB/s"
      f"（提高 {after['ach_gbs']/before['ach_gbs']:.2f}x）")
print(f"       带宽 SOL {before['sol_mem_pct']:.1f}% -> {after['sol_mem_pct']:.1f}%："
      f"{'还没打满，仍有空间' if after['sol_mem_pct'] < 85 else '已接近带宽上限'}")
print(f"       下一站上限 {after['floor_s']*1e3:.3f} ms（带宽地板），当前还有 {after['ceiling_x']:.2f}x")

# ---------- 5. 带宽浪费率：请求的 vs 实际搬的（对齐 BPG §9.2.3） ----------
def wasted(requested_bytes, actual_bytes):
    return 100 * (actual_bytes / requested_bytes - 1)

req_naive = 2 * M * N * K * 4 + M * N * 4      # 算法请求：读 A/B 各 MNK 次 + 写 C
req_tiled = int(req_naive / 32)                # 分块后请求量降到 1/T（见第 4 章）
print("\n[浪费率] actual/requested - 1 = 合并访存与 L2 复用没吃到的部分")
for name, req in (("gemm_naive", req_naive), ("gemm_tiled", req_tiled)):
    print(f"  {name:<12} 请求 {req:>15,} B  实际 {rep[name]['bytes']:>15,} B  "
          f"浪费 {wasted(req, rep[name]['bytes']):+7.1f}%")

三、练习#

  1. 实现：扩展 parse_ncu_csv 支持 --page raw 的多行格式，并把读、写字节分开报出，说明两者为什么要分开看。
  2. 解释：gemm_tiled 算术强度 7.88 低于机器拐点 10.0，故判 memory-bound，但它的算力 SOL 已达 55.1%。说明"算力 SOL 过半却仍判 memory-bound"是否矛盾，并指出下一步该动哪个量。
  3. 对比/验证：把 PEAK_GBS 依次设为真实规格的一半、真实规格、明显高于真实值，观察"还能快"一列的变化，解释屋顶取值失真为什么会产出假结论。
  4. 思考：本次 profile 里 gemm_tiled 的 bank conflict 计数比 gemm_naive 高一个数量级，整体却快 26 倍。为什么单一指标（哪怕冲突数）不能当结论用？
