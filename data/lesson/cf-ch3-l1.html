符号表与作用域链#

a + b 已经能正确解析成语法树了，但语法树没回答一个更基本的问题：a 和 b 到底是谁？局部变量、函数参数还是全局？同名声明有好几个时，这行代码在加哪两个东西？把"名字"接到"声明"上的这一步叫绑定（binding）或名字解析（resolution），它与类型检查一起构成语义分析（static analysis）。本课只解决一个问题：编译器凭什么为每个名字挑出唯一正确的那个声明。

一、概念讲解#

1. 语义分析：把"能解析"变成"有含义"#

语法分析只关心结构是否合法：a + b 的语法树记录了"这是一个二元加法"，但 a、b 只是拼写，不是含义。Crafting Interpreters 第 2 章讲得很直白：静态分析的第一步是 binding / resolution，为每个标识符找出它的声明并接起来；而作用域（scope）的定义正是"某个名字可以指代某个声明的那段源码区域"。若语言是静态类型的，也在这里做类型检查。

解析结果存哪里？第 2 章给了三条路：写回语法树节点当属性、放在旁边一张以标识符为键的符号表（symbol table）、或换成语义更显式的新结构。本章走第二条路。

2. 符号表里的一条记录放什么#

一条记录不是"名字 → 值"，而是"名字 → 一切编译期已知的声明信息"。缺字段的符号表会在报错与后续阶段立刻露馅：

字段 含义 写入者 → 读取者
name 标识符拼写（词法器给出） 声明语句 → 所有引用
kind 类别：var / func / param / type 声明语句 → 语义检查
type 类型表达式（下一课展开） 声明语句 → 类型检查器
depth / scope 所属作用域层 进入作用域时 → 遮蔽判定
decl_line 声明所在行 声明语句 → 报错定位
storage 存储类别：参数 / 局部 / 全局 语义分析 → 后端分配地址

龙书 §2.7 讨论了符号表的多种实现（线性表、有序表、哈希表等）：线性表插入便宜、查找 O(n)；有序表可二分但插入要挪；哈希表两边都平衡，因此生产编译器几乎都用它，再外套一层作用域结构。

3. 作用域链：一层一张表 + 一个 enclosing 指针#

作用域是词法的：由代码文本的嵌套结构决定（lexical scope），而不是由函数调用的先后顺序决定（dynamic scope）。最直观的实现是链式环境：

Scope { table: {name → Symbol}, enclosing: Scope | None }

declare(sym) 只写当前层；resolve(name) 从当前层开始沿 enclosing 上溯，命中即停，走到 None 还没命中就报"未定义变量"。内层同名声明因此遮蔽（shadowing）外层——遮蔽既是语言特性，也是"由内向外查找"的自动结果。

4. 两种工程实现#

做法 怎么做 代价
链式映射（environment chain） 每层一个哈希表，表间用指针串起来 查找 O(depth)；结构清晰，闭包直接引用环境即可
单表 + 作用域栈 全程序一张表，条目带 scope 字段；进出作用域时压/弹可见性（或用 undo log 撤销插入） 查找 O(1)；必须显式处理遮蔽与回滚

Crafting Interpreters 的 jlox 走第一条路：Environment 持有 values 与 enclosing，进入块建子环境、离开块丢弃。收益在实现闭包时完全体现：函数抓住定义处的环境，就自然捕获外层变量。

5. 为什么名字必须在编译期解析掉#

这不只是为了快。早绑定让每个名字在编译期唯一确定到某个声明，含义与运行路径无关；晚绑定（运行时查表）会让同名引用随运行状态漂移。例 2 用三行 Python 演示：[lambda: i for i in range(3)] 里的 i 在调用时才查表，三个函数返回同一个 i；写成 lambda i=i: 把名字在定义处绑死，才得到 0、1、2。同一个语法，两种绑定策略，两种程序。

6. 常见坑#

  1. 进入作用域压表、离开时忘了弹出：后面所有名字都被污染。作用域生命周期必须与语法结构的进入/退出严格配对。
  2. 同一层重复声明：int x; int x; 有的语言报错，有的允许后者覆盖前者。这是语言规范的选择，不是实现细节——两种都要在 declare 里写清。
  3. 单遍编译的副作用：没有全局符号表，编译器只能"看到什么才知道什么"，这正是 C 需要显式前向声明的原因。
  4. 行号来源搞混：报"未定义变量"要给引用处的行号，而符号表里存的是声明处的行号，两个字段都要有。

二、可运行代码示例#

例 1 是最小可用的符号表：Scope 就是上面那个 table + enclosing 结构，PROGRAM 列表描述一段带块作用域的源码，我们一步步走，看每次引用的绑定结果。

# ---- 例 1：符号表 + 作用域链：声明、遮蔽、解析 ----
class Symbol:
    """符号表里的一条记录：名字 + 类别 + 类型 + 声明所在行"""
    def __init__(self, name, kind, typ, line):
        self.name, self.kind, self.typ, self.line = name, kind, typ, line
    def __repr__(self):
        return f'<{self.kind} {self.name}:{self.typ} @L{self.line}>'

class Scope:
    """一层作用域 = 一张哈希表 + 指向外层的 enclosing 指针"""
    def __init__(self, kind, parent=None):
        self.kind = kind
        self.parent = parent
        self.table = {}
        self.depth = 0 if parent is None else parent.depth + 1

    def declare(self, sym):
        if sym.name in self.table:              # 同一层重复声明 → 报错
            raise NameError(f'L{sym.line}: 重复声明 {sym.name}')
        self.table[sym.name] = sym
        return sym

    def resolve(self, name):
        """作用域链：由内向外逐层查找，返回 (命中层, 符号)"""
        s = self
        while s is not None:
            if name in s.table:
                return s, s.table[name]
            s = s.parent
        return None, None

    def chain(self):
        s, out = self, []
        while s is not None:
            out.append(f'{s.kind}#{s.depth}')
            s = s.parent
        return ' <- '.join(out)

# 与下面这段源码一一对应：
#   x = 1                              ← 全局
#   { x = 1.5; y = 2; y + 1; x * 2 }   ← 块内 x 遮蔽全局 x
#   print(x)
PROGRAM = [
    ('decl',  'x',   'int',   1),
    ('enter', None,  None,    2),
    ('decl',  'x',   'float', 2),
    ('decl',  'y',   'int',   3),
    ('use',   'y',   None,    3),
    ('use',   'x',   None,    4),
    ('leave', None,  None,    4),
    ('use',   'x',   None,    5),
    ('use',   'avg', None,    6),          # 从未声明
]

scope = Scope('global')
for op, name, typ, line in PROGRAM:
    if op == 'enter':
        scope = Scope('block', parent=scope)
        print(f'L{line} 进入块 -> 当前链 {scope.chain()}')
    elif op == 'leave':
        print(f'L{line} 离开块 -> 弹出 {scope.kind}#{scope.depth}')
        scope = scope.parent
    elif op == 'decl':
        scope.declare(Symbol(name, 'var', typ, line))
        print(f'L{line} 声明 {name}:{typ} -> 写入 {scope.kind}#{scope.depth}')
    else:
        hit, sym = scope.resolve(name)
        if sym is None:
            print(f'L{line} 引用 {name} -> 未定义（查完 {scope.chain()}）')
        else:
            print(f'L{line} 引用 {name} -> 绑定 {sym}（命中 depth={hit.depth}）')

运行输出（每一行都是一次真实查表）：

L1 声明 x:int -> 写入 global#0
L2 进入块 -> 当前链 block#1 <- global#0
L2 声明 x:float -> 写入 block#1
L3 声明 y:int -> 写入 block#1
L3 引用 y -> 绑定 <var y:int @L3>（命中 depth=1）
L4 引用 x -> 绑定 <var x:float @L2>（命中 depth=1）
L4 离开块 -> 弹出 block#1
L5 引用 x -> 绑定 <var x:int @L1>（命中 depth=0）
L6 引用 avg -> 未定义（查完 global#0）

注意 L4 与 L5 的对照：块内 x 命中 depth=1 的 float 声明，离开块后再引用 x 就落回 depth=0 的全局声明。同一个名字，两处绑定——这就是遮蔽。

例 2 把"晚绑定会改变程序含义"压到三行 Python 里：

# ---- 例 2：为什么名字要在编译期"解析"掉，而不是运行时再查表 ----
fns_late = [lambda: i for i in range(3)]          # 名字晚绑定：三个函数查的是同一个 i
fns_early = [lambda i=i: i for i in range(3)]     # 名字早绑定：各捕获自己的 i
print('晚绑定（运行时查表）:', [f() for f in fns_late])
print('早绑定（静态解析）  :', [f() for f in fns_early])
晚绑定（运行时查表）: [2, 2, 2]
早绑定（静态解析）  : [0, 1, 2]

这也是"名字解析必须在编译期做完"的最短论据：若推到运行期，同一段源码的含义就取决于"运行时那张表里恰好有什么"。

三、练习#

  1. 实现：给 Scope 加 resolve_cost(name)，返回从当前层到命中层走过的层数；对一段嵌套 5 层、共 100 次引用的样例程序统计总代价，再比较"链式映射"与"单表 + 作用域栈"的最坏情况。
  2. 解释：为什么"内层遮蔽外层"在链式映射里是查找顺序的自动结果，在"单表 + 作用域栈"里却必须额外处理？两种做法各要多存什么？
  3. 对比/验证：把例 1 的 PROGRAM 改成"块内不声明 x 只引用 x"，看解析结果如何从 depth=1 变成 depth=0；再把最后一行改成引用 y（y 声明在已退出的块里），解释输出说明了什么。
  4. 思考：C 的 static 局部变量、Python 的 global、JavaScript 的 var 提升，各自是对符号表的哪种干预？能否只用"声明写进哪一层的表"解释这三者？
