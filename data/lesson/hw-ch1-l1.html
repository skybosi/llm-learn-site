为什么需要专用硬件#

本课程要回答的问题很具体：一张卡到底能跑多大的模型、跑多快、怎么跑最划算。要回答它，第一步是搞清楚一件事——为什么我们不能靠手里那颗万能的 CPU，而要去买 GPU、TPU、NPU 这些"专用硬件"。答案可以浓缩成一句：深度学习的计算模式高度规整、规模巨大，而通用 CPU 的算力与带宽都差了两个数量级。

一、概念讲解#

1. 深度学习算的是"矩阵乘"，而且算得极多#

无论多复杂的 Transformer，前向计算的主体都可以归约到矩阵乘法（GEMM）。你已经学过线性代数，知道 C=AB 中每个输出元素是 A 的一行与 B 的一列做内积：

C[i,j]=k∑​A[i,k]⋅B[k,j]

这件事对硬件意味着两点：第一，计算量随规模按 O(n3) 增长；第二，每个输出元素之间互不依赖，可以完全并行。这两点合在一起，恰恰是"专用硬件"的用武之地。

2. 大模型的算力需求已经爆炸#

参数量的增长速度远超单颗通用 CPU 性能的增长。以"每生成一个 token 需要约 2P 次浮点运算"（P 为参数量，下一章会推导）来估算：

模型 参数量 每 token 浮点运算量（约）
BERT-base 1.1 亿 ~2.2 亿次
GPT-3 1750 亿 ~3.5 千亿次
现代开源大模型（70B 级） 700 亿 ~1400 亿次

生成一句话要几十上百个 token，服务成千上万个用户又要乘以并发数——算力缺口是指数级拉开的。

3. 通用 CPU 的两个硬伤：算力低、带宽低#

CPU 的设计目标是"单线程复杂逻辑跑得快"：核数少（几到几十个）、主频高、分支预测和缓存做得精巧。但深度学习的两个关键指标上，CPU 差得很远：

  • 算力：一颗高端服务器 CPU 的 FP32 算力通常在 1～4 TFLOPS 量级；而一块 NVIDIA H100 的 FP16 张量算力高达 989 TFLOPS，相差两个数量级。
  • 带宽：CPU 走双通道/八通道 DDR，带宽约几十到上百 GB/s；H100 的 HBM 带宽是 3.35 TB/s，同样差一两个数量级。

而大模型推理最缺的正是带宽（后续章节会详细论证），所以 CPU 天然不是这块料。

4. 专用硬件赌的是"确定性"#

通用 CPU 要处理千奇百怪的负载，必须面面俱到。而神经网络的计算图在结构上是已知且高度规整的：矩阵乘、卷积、逐元素激活、归一化……数据流可预测。专用硬件就是抓住了这份"确定性"：

  • 用更多、更简单的小计算单元换吞吐，而不是少数几个复杂大核；
  • 用更高的显存带宽匹配"读得多"的需求；
  • 牺牲一点通用性和单线程延迟，换取数倍的吞吐与能效。

5. 一句话总结#

不是"GPU 比 CPU 聪明"，而是"深度学习恰好是 GPU 擅长的那类问题"：海量、并行、可预测。理解了这一点，后面算 FLOPs、算带宽、画 Roofline 曲线时，你才明白这些数字到底在为谁服务。

二、可运行代码示例#

下面用 Python 把上面的"体感数字"亲手算一遍。

# ---- 例 1：GEMM 的计算量随规模 O(n^3) 增长 ----
def gemm_flops(m, n, k):
    # C[m,n] = A[m,k] @ B[k,n]，每个输出元素做 k 次乘加（2 次浮点运算）
    return 2 * m * n * k

for size in [256, 512, 1024, 2048]:
    flops = gemm_flops(size, size, size)
    print(f"{size}x{size}x{size} 的 GEMM = {flops/1e9:.2f} GFLOPs")

# ---- 例 2：大模型"每 token"的浮点运算量 ≈ 2P ----
def flops_per_token(params):
    return 2 * params  # 前向：每个参数参与一次乘加

models = {"BERT-base": 1.1e8, "GPT-3": 1.75e11, "LLaMA-70B": 7e10}
for name, p in models.items():
    print(f"{name}: 每 token ≈ {flops_per_token(p)/1e9:.0f} GFLOPs")

# ---- 例 3：如果只看"算力"，CPU 和 GPU 各要花多久 ----
def compute_time(flops, peak_tflops):
    # peak_tflops 是 TFLOPS（每秒 1e12 次浮点运算）
    return flops / (peak_tflops * 1e12)

token_flops = flops_per_token(7e10)          # 70B 模型每 token 的 FLOPs
cpu = compute_time(token_flops, peak_tflops=3.0)      # 高端 CPU，假设 3 TFLOPS
gpu = compute_time(token_flops, peak_tflops=989.0)    # H100 FP16 张量算力
print(f"纯算力耗时：CPU ≈ {cpu*1e3:.2f} ms，H100 ≈ {gpu*1e6:.0f} us")

# ---- 例 4：真正拖后腿的其实是带宽 ----
def read_time(bytes_needed, bw_tb_s):
    # bw_tb_s 是 TB/s（每秒 1e12 字节）
    return bytes_needed / (bw_tb_s * 1e12)

weight_bytes = 7e10 * 2   # 70B 参数，FP16 每参数 2 字节 = 140 GB
cpu_read = read_time(weight_bytes, bw_tb_s=0.1)    # CPU 内存带宽约 0.1 TB/s
gpu_read = read_time(weight_bytes, bw_tb_s=3.35)   # H100 HBM 带宽
print(f"读完 140GB 权重：CPU ≈ {cpu_read:.1f} s，H100 ≈ {gpu_read*1e3:.1f} ms")

要点：例 3、例 4 放在一起看最有意思——纯算力上 H100 快 CPU 两个数量级，但"读完一遍权重"这一步，连 H100 都要 40 毫秒以上。这说明推理的瓶颈常常不在算力而在"搬数据"，这正是本课程后半程要反复回到的主题。

三、练习#

  1. 推导：写出 Am×k​ 与 Bk×n​ 相乘产生 C 的总浮点运算次数公式，并说明为什么是 2mnk 而不是 mnk。
  2. 计算：用代码里的 gemm_flops，算一个 4096×4096×4096 的 GEMM 有多少 GFLOPs，再估算 H100（989 TFLOPS）在"算力拉满"的理想情况下要花多少秒。
  3. 对比：把例 4 的权重换成 8B 模型（FP16 共 16GB），分别算 CPU 和 H100 读完一遍要多久，感受带宽差距如何随模型变小而变化。
  4. 思考：如果某块芯片算力很高但显存带宽很低，跑大模型推理时会发生什么？试着用例 3、例 4 的框架说明。
