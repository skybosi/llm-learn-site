性能验证#

部署做完不算完，没验证过性能的服务，上线就是赌博。这一课是前 8 课的收口：把功能正确性、延迟 SLO、吞吐、扩展效率、通信带宽、长稳稳定性串成一套验收清单，并重点回答一个残酷的问题——加卡到底值不值。学完本课，你应当能对任意一套部署方案输出一份可交付的性能验收报告，并判断多卡并行是否真的带来了对应的收益。

一、概念讲解#

1. 验收要验什么#

一份完整的性能验收包含六项：

  1. 功能正确性：输出格式、内容质量是否符合预期，量化后有没有明显退化；
  2. 延迟 SLO：P99 TTFT / TPOT 是否达标（复用第二章的压测）；
  3. 吞吐：达标延迟前提下的最大 token/s；
  4. 扩展效率：加卡/加副本后吞吐是否成比例增长；
  5. 通信带宽：多卡之间 all-reduce 是否健康（NCCL 测试）；
  6. 长稳与容错：长时间压测是否泄漏显存、延迟是否漂移、单副本挂掉是否影响整体。

2. 扩展效率：加卡的"性价比尺子"#

扩展效率 = 实际吞吐提升 / 理论吞吐提升
  • TP=2 理想吞吐翻倍，但通信 + 负载不均会打折扣，实测 1.6–1.9 倍是常见区间；
  • 数据并行多副本的扩展效率通常高于 TP（副本间无通信），接近线性；
  • 经验法则：扩展效率 < 0.7 就要警惕——可能通信瓶颈、负载不均、或单卡已非瓶颈（比如已到 CPU/网络上限）。

3. 通信验证：NCCL 是基础体检#

多卡并行的一切都建立在集合通信健康之上。上线前用 nccl-tests 的 all_reduce_perf 测一条基线：

# 2 卡 all-reduce 带宽测试
mpirun -np 2 ./all_reduce_perf -b 8M -e 128M -f 2 -g 2

关注：实测带宽是否接近卡的理论互连带宽（NVLink 约 600–900 GB/s/卡，PCIe Gen4 约 32 GB/s）。若远低于理论值，说明拓扑/驱动/互连有问题，会直接拖垮 TP 性能。

4. 长稳与容错#

  • 长稳：连续压测 1–2 小时，盯 nvidia-smi 显存是否持续增长（碎片/泄漏）、P99 延迟是否漂移；
  • 容错：多副本下杀掉一个副本，验证 LB 能否摘除、其余副本能否兜住流量（这是高可用的核心）。

二、可运行示例#

示例 1：单卡 vs 多卡扩展效率对比脚本#

# -*- coding: utf-8 -*-
# 扩展效率验证：对比 TP=1 与 TP=2 的实测吞吐，算扩展效率
# 吞吐数据来自第二章的压测脚本，这里填入实测值

def speedup_analysis(name, tp1_tps, tp2_tps):
    ideal = tp1_tps * 2              # TP=2 的理想吞吐（翻倍）
    actual = tp2_tps
    efficiency = actual / ideal
    verdict = "合格" if efficiency >= 0.7 else "需排查（通信/负载/瓶颈）"
    print(f"{name}: TP=1 吞吐={tp1_tps} tok/s, TP=2 吞吐={actual} tok/s, "
          f"理想={ideal} tok/s, 扩展效率={efficiency:.2f} -> {verdict}")
    return efficiency

# 示例实测值：7B 模型 TP=1 vs TP=2（填入你自己的压测结果）
speedup_analysis("7B AWQ4 单机双卡", tp1_tps=2200, tp2_tps=3900)   # 效率 ~0.89
speedup_analysis("70B AWQ4 单机双卡", tp1_tps=1800, tp2_tps=3300)  # 效率 ~0.92
# 反例：跨机 TP 通信开销大，效率可能跌破 0.7
speedup_analysis("70B FP16 跨机 TP=8(示意)", tp1_tps=1500, tp2_tps=1800)  # 效率 0.6

解读：单机内 TP 效率普遍 0.85–0.95；一旦跨机通信成为瓶颈，效率可能跌破 0.7，此时"多卡"反而可能不如"单机多副本"划算。

示例 2：NCCL 带宽基线 + 长稳监控#

# 1. 卡间拓扑与 NVLink 状态
nvidia-smi topo -m

# 2. all-reduce 带宽测试（2 卡，8MB~128MB 消息）
mpirun -np 2 ./all_reduce_perf -b 8M -e 128M -f 2 -g 2

# 3. 长稳压测时，另开终端盯显存与延迟（每 5 秒采样）
while true; do
  nvidia-smi --query-gpu=memory.used,utilization.gpu --format=csv,noheader
  sleep 5
done

示例 3：容错验证（多副本摘除）#

# -*- coding: utf-8 -*-
# 容错验证：杀掉一个副本，看负载均衡是否还能正常服务
import httpx, itertools, time

REPLICAS = ["http://localhost:8000", "http://localhost:8001"]
pool = itertools.cycle(REPLICAS)

def ping(replica):
    try:
        return httpx.get(replica + "/health", timeout=2).status_code == 200
    except Exception:
        return False

# 模拟：8001 副本挂掉
print("8001 副本已宕机（模拟）")
healthy = [r for r in REPLICAS if r != "http://localhost:8001"]

# 只向存活副本发请求，验证仍可服务
ok = 0
for i in range(10):
    try:
        httpx.post(healthy[i % len(healthy)] + "/v1/chat/completions",
                   json={"model": "m", "messages": [{"role": "user", "content": "hi"}]},
                   timeout=30)
        ok += 1
    except Exception:
        pass
print(f"存活副本服务成功 {ok}/10，说明摘除宕机副本后仍可兜住流量")

三、练习#

  1. 跑真实扩展效率：用第二章的压测脚本分别测你环境里 TP=1 与 TP=2 的达标吞吐，套进示例 1 的 speedup_analysis，算出你的真实扩展效率。
  2. 画扩展曲线：收集 TP=1/2/4 三组吞吐，画出"吞吐 vs 卡数"曲线，与理想线性对比，找出你环境里效率开始下跌的卡数。
  3. NCCL 基线：运行 all_reduce_perf，记录 NVLink 直连与 PCIe 桥接两对卡的带宽差异，说明它对 TP 组选卡的指导意义。
  4. 写验收报告：按本课六项清单，为一个已部署的 70B 服务（TP=2 + 2 副本）写一份验收报告模板，列出每项要测什么、用什么命令、达标线是多少。
