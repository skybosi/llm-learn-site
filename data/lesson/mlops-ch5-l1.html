成本归因：把账单拆成单位经济（每千次请求 / 每千 token / 每次训练）#

这一节要解决什么#

第 4 章结束时你手上有一份能解释的变更记录：哪个实验、哪次训练、哪次发布、哪次事故。这一章要问一个第 4 章不回答的问题：这些变更各自花了多少钱，而且这个"多少钱"能不能被拆到可以单独决策的粒度上。

现实里，成本这件事通常停在三个地方：

  1. 账单层：一张月末发票，"GPU 12 万、存储 1 万、网络 8 千"。它无法回答"聊天功能是否该涨价""batch 通道是不是在补贴""换个小模型能省多少"。
  2. 利用率层："GPU 利用率 66%"。它把"贵"指向了"用得不干净"，但 66% 的利用率下单位成本可能是另一个系统的 3 倍 —— 利用率是分母，不是成本。
  3. 感觉层："最近推理变贵了"。没有单位，这句话不可证伪，也就无法进入任何决策。

本节要把成本变成一组可计算、可对账、可归因的数。它回答五个具体问题：

  1. 一个请求到底花多少钱？ 答案至少有三个数（分配口径 0.4286 元/千请求、消耗口径 0.2847、增量口径现金 0），选错口径差 50.6%。为什么必须同时给出这三个数？
  2. "贵"是指什么贵？ 同一个系统里，chat 每千 token 0.000366 元、batch 0.000144 元 —— 差 2.55 倍；而按每请求看，rag 是 internal 的 3.11 倍。两个口径下"最贵的租户"不是同一个，为什么？
  3. 哪些钱是白花的？ 重试占消耗 3.04%、截断输入占 0.31%、前缀缓存省下 8.86%。为什么缓存这个"最便宜的优化"在本例里只值 0.865% 的弹性？
  4. 训练贵还是推理贵？ 在 140,000 请求/天、27000 元一次微调的构型下，训练摊销要与推理成本同级需要服务 677 天（117.39 B token）。把日流量乘 10，这个数缩到 67.7 天 —— 结论是规模的函数，所以"训练贵"这句话在没有规模时没有意义。
  5. 自建还是调 API？ 本例自建服务侧单位成本 0.000346 元/千 token，API 0.0025 元/千，盈亏平衡量 27.86 M token/天，当前流量是它的 6.22 倍。

一句话：本节不产生"降本方案"（那是第 4 节），它产生的是后面三节都要用的那把尺子。

一、概念：成本要写成「单价 × 数量」，而"数量"有两个#

1.1 可归因成本的三段分解#

一次推理在硬件上消耗的不是"一次请求"，而是一段 GPU 时间。把它拆成三段：

creq​=prefill3600ph​​⋅Rpre​npre​​​​+decode3600ph​​⋅Rdec​ndec​​​​+固定开销3600ph​​⋅s0​​​

其中 ph​ 是元/卡·小时，Rpre​,Rdec​ 是该卡在连续批处理下的聚合吞吐（token/s），s0​ 是每请求固定摊销的 GPU 秒（调度、KV 分配、收尾）。

这个分解之所以是唯一可用的口径，原因很直接：它每一项都对应一个可以独立测量的量，而且对 npre​,ndec​ 是线性的 —— 线性意味着可以对请求求和，于是"一天的成本"就是逐请求成本的和，不需要任何近似。

数值（本节全部数字来自 [0]–[7] 的实测输出，⚠️ 合成日志、显式假设的吞吐与单价）：

项 每请求成本（元） 占三段之和
prefill（npre​=760，Rpre​=6000） 8.796296×10−5 40.08%
decode（ndec​=220，Rdec​=1200） 1.273148×10−4 58.02%
固定开销（s0​=6 ms） 4.166667×10−6 1.90%
合计 2.194444×10−4 100%

先记住这个 5:1。 decode 与 prefill 的单位成本比是 Rpre​/Rdec​=5.0（0.000579 vs 0.000116 元/千 token），这不是常数，而是由硬件的算力/带宽比与模型结构共同决定的。它直接决定了一件常被忽略的事：同样 1000 个 token，放在输入里还是放在输出里，成本差 5 倍。

单位成本不是"一个数"，是三个数，因为它们回答三个不同的问题：

其中 ρ=66.42% 是分配利用率。这个恒等式解释了一个反复出现的组织冲突：业务方看到的是分配口径，工程师汇报的是消耗口径，两者差 50.6%，于是"我们明明只用了 40 元"与"这一天的服务要 60 元"可以同时为真。

1.3 为什么必须同时有"每请求"和"每 token"#

两个口径不是冗余，它们的分母不同，因此对同一条优化给出相反的方向。实测的弹性（自变量 +10%）：

自变量 +10% 元/千请求 元/千 token
decode 吞吐 −5.296% −5.296%
prefill 吞吐 −3.657% −3.657%
前缀命中率 −0.865% −0.865%
重试率 +0.304% +0.304%
输出长度 +5.826% −3.794%
固定开销 +0.151% +0.151%

最后一行是本节的第一个反直觉：输出变长 10%，每请求成本涨 5.83%，每千 token 成本反而降 3.79% —— 因为分母（token 数）也涨了 10%，把固定成本与 prefill 摊薄了。所以"我们单位成本降了"这句话，如果分母自己在动，就不能作为优化有效的证据。这与第 3 章那条"判据问的是相容性，不是指标的方向"是同一个结构。

二、为什么这样设计：可归因的三个必要条件#

2.1 条件一：每个计量事件必须带齐三个标签#

成本要能回答反事实问题（"如果把 rag 关掉能省多少"），每个计量事件至少要带：

Event=(tenant/team谁​​, model+config哪个版本​​, route/feature哪条路径​​)

缺任意一个，某类反事实问题就永久无法回答：

  • 缺 tenant → 无法对内结算，也没法发现"某个租户在用长上下文补贴自己"；
  • 缺 model/config → 优化收益无法归因，A/B 的成本差会被算进"总体变贵了"；
  • 缺 route/feature → 无法回答"这个功能值不值"。

实测的代价很轻：1.1% 的请求因为缺 tenant tag 落进"未归因"，成本 0.4334 元（当天消耗的 1.1%），归属覆盖率 98.913%。这个残差必须被显式打印出来，而不是把 1.1% 摊回各租户 —— 摊回去就等于承认"我不知道这钱是谁花的"，却把它伪装成"我知道"。

2.2 条件二：分摊必须闭合，且闭合式必须被断言#

归因表最容易出的错不是估错，而是不闭合：各租户之和比总成本多出几个百分点，没人发现，于是所有人都在用一个错的数做决策。本节代码里有一条自检（[0] 与 [3]）：

t∈T∑​ct​+cunattr​=cused​,t∈T∑​ct​+cunattr​+cidle​=calloc​

t∈T∑​ct​+cunattr​=cused​,t∈T∑​ct​+cunattr​+cidle​=calloc​

实测对账误差 Δ=5.19×10−13 元（浮点量级），并且这条等式在任何口径下都要成立 —— 包括"重试按二次计费"这种容易被漏掉的情形。本节的实现里，重试请求的基础工作被计入 base，其重复的那一次被单独记为 retry_extra；如果只按 base 分摊，覆盖率会算出 102.045%（大于 100% 就是不自洽的信号），这是本节第一版代码真实踩到的坑。

2.3 条件三：计量单位必须与决策单位一致#

"每天的 GPU 小时"不是决策单位。决策单位是那些能被单独开关、单独定价、单独替换的东西：

  • 一次请求 → 限流与定价；
  • 一个租户/团队 → 预算与结算；
  • 一千 token（分输入/输出）→ 模型替换与缓存策略；
  • 一次训练 → 训练/推理的资源配比；
  • 一条路由（小模型/大模型）→ 质量-成本前沿。

一个具体例子：batch 租户输入 1799 token、输出 83 token，chat 是 485/407。如果用混合单价 0.000230 元/千 token 对内结算，batch 被多收、chat 被少收 —— 实测两者真实单位成本差 2.55 倍。用错的单位结算，等价于给不同业务发了不同的补贴，而没人知道补贴给了谁。

2.4 为什么"GPU 小时 / 总请求"必然失效#

因为它把两个自由度压成了一个数：

NCtotal​​=3600ph​​⋅(Rpre​nˉpre​​+Rdec​nˉdec​​+s0​)⋅ρ1​

右边有 4 个可独立变化的量（nˉpre​,nˉdec​,R,s0​）与 1 个利用率 ρ。任何两个不同的系统都可以给出相同的"元/请求"而有完全不同的优化路径。第 4 节的"降本顺序"就是在这个分解上做的排序 —— 没有分解，排序无从谈起。

三、怎么做：从日志到一张单位成本表#

3.1 计量放在哪里#

三个候选位置，各有系统性偏差：

位置 拿得到什么 系统性偏差
API 网关 tenant、route、状态码、端到端延迟、重试 拿不到 token 数，只能用字符数或估算
推理引擎 精确 prefill/decode token、批大小、KV 占用、缓存命中 拿不到业务标签（除非透传）
计费/账本 单价、承诺折扣、跨期结转 拿不到请求级明细

工程上唯一可行的做法是网关 + 引擎两侧都记，用 request_id 关联，并且以引擎侧为准（token 是引擎的事实），网关侧只提供标签。本节代码模拟的正是引擎侧口径加上网关标签后的合并结果。

3.2 单位成本的四个数#

一张最小可用的单位成本表只有四行，但每行都必须带样本量与时间窗：

  1. 元/千请求：0.2847（消耗口径）；
  2. 元/千 token：0.000230（消耗口径）；分输入 0.000116、输出 0.000579；
  3. 元/请求的可归因成本：sˉ⋅ps​=0.2847/1000；
  4. 元/请求的无效部分：重试 0.0000086 + 截断 0.0000009。

第 4 行是最容易被丢掉的。实测重试率 3.13% 占消耗成本的 3.04% —— 它不带来任何质量收益，是纯粹的漏损；而它的弹性只有 +0.304%（重试率 +10% 只让单位成本涨 0.3%）。"弹性小"与"该不该修"是两件事：弹性小意味着它不是成本的主要驱动，但它没有任何收益，所以修它的判据不是"省多少钱"，而是"修它要几个人天"。

3.3 缓存收益为什么可能很小#

前缀缓存的收益可以直接算：

Δccache​=h⋅(1−k)⋅Rpre​nˉin​​⋅ps​⋅N

其中 h 是命中率、k 是命中后仍需重算的比例（本例 k=0.35）。实测命中率 26.5%，省下 3.87 元/天，占"无缓存成本"的 8.86%；但命中率再翻倍（相对 +100%）也只多省 4.42 元/天 —— 因为 prefill 只占 39.03% 的 GPU 秒，而缓存只作用于 prefill。

这条算术给出一个可迁移的判据：缓存的收益上界 = prefill 的 GPU 秒占比 ×(1−k)。本例是 39.03%×0.65=25.4%，而这需要 100% 的命中率。第 4 节会把它和量化、批处理放在同一张排序表上 —— 那时你会发现缓存的真正价值不在省钱，而在降低单位成本的可预测性（命中率稳定时，一次请求的方差也小）。

c_{\text{train per req}}(L) = \frac{C_{\text{train}}}{N_{\text{req}}\cdot L},\qquad\rL^{\ast} = \frac{C_{\text{train}}}{c_{\text{used per day}}}

c_{\text{train per req}}(L) = \frac{C_{\text{train}}}{N_{\text{req}}\cdot L},\qquad\rL^{\ast} = \frac{C_{\text{train}}}{c_{\text{used per day}}}

实测 Ctrain​=1200 GPU⋅h×2.50+80 人时×300=3000+24000=27000 元：

同时注意 Ctrain​ 的构成：工程人时 24000 元是 GPU 成本 3000 元的 8 倍。在微调这个尺度上，"训练成本"主要是人的成本，而人的成本通常不在任何 GPU 账单里 —— 这就是为什么"训练成本被低估"是一个结构性现象，而不是记账疏忽。

  • 用消耗口径算 ctok​ 会得到更低的盈亏点（21.9 M/天），因为它假装空闲不要钱；
  • 用API 的阶梯价会得到更高的盈亏点（量大时 API 单价下降）。

所以"自建更便宜"这句话至少要带三个限定：口径、流量、以及在什么时间尺度上（承诺期 vs 按需）。这与 3.4 是同一个教训：成本结论 = 数字 + 口径 + 时间尺度，缺一个都不可复核。

四、取舍与边界#

4.1 有些成本原则上不可分#

网络、存储、控制面（调度器、监控、镜像仓库）、共享缓存、人的时间，都不能按请求线性分摊。工程上的处理只有两条路：

  • 单列为共享池（本例的"空闲/不可归因"就是这一类的雏形），按明示规则（人头 / 流量占比 / 峰值占用）二次分摊；
  • 不上分摊，只做对比：优化决策只看消耗口径的差，不看分配口径。

最差的做法是"按请求数平均摊回去" —— 它让共享成本正比于一个与它无关的量，于是所有人都觉得自己的单位成本被别人的流量污染了。

4.2 tag 基数与采样计费的方差#

每个标签的每个取值组合都会产生一条时间序列。10 个租户 × 8 个模型版本 × 20 条路由 =1600 条，而监控系统的成本正比于基数。三个实践约束：

  1. 高基数维度（user_id、session_id）只用于离线对账，不进实时指标；
  2. 采样计费只在 λ=ϕNp≥3 时可用（ϕ 为采样率，见第 3 章第 2 节），否则你的"单位成本"在低流量租户上全是噪声；
  3. 采样率必须随租户分层（大租户全采、小租户抽样），否则小数租户的成本表不可用，而它们恰恰是最需要被看清的。

4.3 归因不等于归咎#

一旦单位成本进入绩效，就会出现两种可预测的博弈：把长请求拆成多个短请求（降低"每请求成本"）、把流量挪到便宜时段然后宣称降本。可执行的防线是同时公布每请求与每 token 两个口径，并冻结分母的定义（"一次用户可见的会话"而不是"一次 API 调用"）。这与第 1 章"追踪 schema 决定六个月后能回答什么问题"是同一件事：指标的定义就是激励的形状。

4.4 单位成本有时间尺度，别用日成本做季度决策#

  • 日成本用于发现异常（第 2 节的预算告警）；
  • 周成本用于验证优化（要能覆盖一次发布周期）；
  • 月/季成本用于容量采购与自建判断（要覆盖承诺期）。

混用会得到自相矛盾的结论：本例里"缓存省 8.86%"是日尺度的比例，"训练摊销 677 天"是季度尺度的时间常数，两者放在同一张 PPT 上会让读者以为它们可比。

4.5 边界：本节不做的事#

  • 不做定价：定价要价格弹性与竞争信息，单位成本只是下界；
  • 不判断"贵不贵"：0.2300 元/百万 token 本身没有好坏，要与质量（第 3 章的护栏）和替代方案放在一起才有意义；
  • 不覆盖训练侧的数据成本：数据采集、标注、存储的账要单独建，且它的时间尺度与 GPU 完全不同。

② 把 GPU-秒拆成 prefill + decode + 固定开销（这是唯一能把成本拆下去的口径）
③ 三个口径的单位成本：分配口径 / 消耗口径 / 增量口径，以及它们的比值
④ 按租户归因：归属覆盖率、未归因残差、各租户单位成本的差异从哪来
⑤ 无效 token 的账：重试与截断各花了多少钱，前缀缓存到底省了多少
⑥ 训练成本摊销：摊销额与服务期长度的关系，以及交叉点
⑦ 自建 vs API 的盈亏平衡量，以及单位成本对吞吐/缓存/重试/输出长度的弹性

运行：python3 /tmp/mlops_ch5_l1.py
⚠️ 全部为合成数据（random，固定种子）。价格与吞吐是显式假设，不是实测值。
"""
from __future__ import annotations

import math
import random

# ==================================================================== 显式假设
P_GPU_H = 2.50          # 元 / 卡·小时（按需价）
P_GPU_S = P_GPU_H / 3600.0

R_PREFILL = 6000.0      # 每卡聚合 prefill 吞吐（token/s），连续批处理下
R_DECODE = 1200.0       # 每卡聚合 decode 吞吐（token/s）
S_FIXED = 0.006         # 每请求固定 GPU-秒（调度 + KV 分配 + 收尾）

N_ALLOC_CARDS = 1
CARD_HOURS = 24.0       # 服务为这一天分配了 1 卡 × 24 小时

PREFIX_KEEP = 0.35      # 缓存命中后仍需重算的 prefill 比例
P_RETRY = 0.032         # 首次失败、整单重发的比例
P_TRUNC = 0.008         # 撞上 max_tokens 被截断的比例

#                名字        权重    输入中位数  输入σ  输出中位数  输出σ  缓存命中
TENANTS = [
    ("chat",     0.52,      380.0, 0.70,     300.0, 0.80, 0.28),
    ("batch",    0.27,     1500.0, 0.60,      60.0, 0.80, 0.10),
    ("rag",      0.14,     2600.0, 0.70,     200.0, 0.60, 0.55),
    ("internal", 0.07,      200.0, 0.80,     120.0, 0.70, 0.20),
]
P_UNTAGGED = 0.011      # 打点缺失、归不到任何租户的比例

N_REQ = 140_000
SEED = 20260923

C_TRAIN_GPU_H = 1200.0  # 一次微调的 GPU·小时
RATE_ENG_H = 300.0      # 元 / 人时
ENG_HOURS = 80.0        # 一次微调配套的工程人时
API_PRICE_1K = 0.0025   # API 混合价（元 / 千 token，输入输出混合）
HORIZONS = (1, 30, 90, 365, 730)


# ==================================================================== 日志（合成 ⚠️）
def gen_log() -> list[dict]:
    rng = random.Random(SEED)
    names = [t[0] for t in TENANTS]
    weights = [t[1] for t in TENANTS]
    rows: list[dict] = []
    for _ in range(N_REQ):
        name = rng.choices(names, weights)[0]
        t = next(x for x in TENANTS if x[0] == name)
        n_in = int(min(8000, max(40, round(math.exp(rng.gauss(math.log(t[2]), t[3]))))))
        n_out = int(min(2000, max(8, round(math.exp(rng.gauss(math.log(t[4]), t[5]))))))
        hit = rng.random() < t[6]
        tenant = None if rng.random() < P_UNTAGGED else name
        rows.append({
            "tenant": tenant,
            "n_in": n_in,
            "n_out": n_out,
            "cache": hit,
            "pre_tokens": n_in * (PREFIX_KEEP if hit else 1.0),
            "retry": rng.random() < P_RETRY,
            "trunc": rng.random() < P_TRUNC,
        })
    return rows


def gpu_seconds(n_pre: float, n_out: float) -> float:
    """一个请求可归因的 GPU-秒：prefill + decode + 固定开销。"""
    return n_pre / R_PREFILL + n_out / R_DECODE + S_FIXED


# ==================================================================== [0] 自检
def self_check() -> None:
    """拆解必须闭合，且缓存前后的差值恰等于省下的 prefill。"""
    n_in, n_out = 760.0, 220.0
    a, b, c = n_in / R_PREFILL, n_out / R_DECODE, S_FIXED
    tot = gpu_seconds(n_in, n_out)
    assert abs((a + b + c) - tot) < 1e-12
    saved = gpu_seconds(n_in, n_out) - gpu_seconds(n_in * PREFIX_KEEP, n_out)
    assert abs(saved - n_in * (1 - PREFIX_KEEP) / R_PREFILL) < 1e-12
    print("[0] 自检：三段分解闭合；缓存节省 == 省下的 prefill token / 吞吐")
    print(f"    prefill={a*P_GPU_S:.6e} + decode={b*P_GPU_S:.6e} + fixed={c*P_GPU_S:.6e}"
          f" = {tot*P_GPU_S:.6e} 元/请求")
    print(f"    三段占比：prefill={a/tot*100:5.2f}%  decode={b/tot*100:5.2f}%"
          f"  fixed={c/tot*100:5.2f}%")


# ==================================================================== [1] 汇总
def summarize(rows: list[dict]) -> dict:
    # 按「是否重试」分两组聚合，任何口径的扰动都能精确重算
    g = {False: [0.0, 0.0, 0], True: [0.0, 0.0, 0]}     # pre_tokens, out_tokens, n
    raw_in = 0.0
    s_base = s_retry = s_nocache = s_trunc_in = 0.0
    n_cache = n_trunc = 0
    for r in rows:
        s = gpu_seconds(r["pre_tokens"], r["n_out"])
        grp = g[r["retry"]]
        grp[0] += r["pre_tokens"]
        grp[1] += r["n_out"]
        grp[2] += 1
        raw_in += r["n_in"]
        s_base += s
        if r["retry"]:
            s_retry += s
        s_nocache += gpu_seconds(r["n_in"], r["n_out"])
        if r["trunc"]:
            s_trunc_in += r["pre_tokens"] / R_PREFILL
            n_trunc += 1
        if r["cache"]:
            n_cache += 1
    pre_tok = g[False][0] + g[True][0]
    out_tok = g[False][1] + g[True][1]
    return {
        "g": g, "raw_in": raw_in,
        "s_base": s_base, "s_retry": s_retry, "s_billed": s_base + s_retry,
        "s_nocache": s_nocache, "s_trunc_in": s_trunc_in,
        "pre_tok": pre_tok, "out_tok": out_tok,
        "n_tok": pre_tok + out_tok, "n_tok_raw": raw_in + out_tok,
        "n_retry": g[True][2], "n_trunc": n_trunc, "n_cache": n_cache,
        "n_hit_rate": n_cache / N_REQ,
    }


def lenses(t: dict) -> dict:
    alloc_s = N_ALLOC_CARDS * CARD_HOURS * 3600.0
    c_alloc = N_ALLOC_CARDS * CARD_HOURS * P_GPU_H
    c_billed = t["s_billed"] * P_GPU_S
    n_tok = t["n_tok"]
    d = {
        "alloc_s": alloc_s,
        "util": t["s_billed"] / alloc_s,
        "headroom": 1.0 - t["s_billed"] / alloc_s,
        "c_alloc": c_alloc,
        "c_billed": c_billed,
        "c_idle": c_alloc - c_billed,
        "n_tok": n_tok,
        "n_tok_raw": t["n_tok_raw"],
        "c_1kreq_alloc": c_alloc / N_REQ * 1000.0,
        "c_1kreq_used": c_billed / N_REQ * 1000.0,
        "c_1ktok_alloc": c_alloc / (n_tok / 1000.0),
        "c_1ktok_used": c_billed / (n_tok / 1000.0),
        "c_1ktok_in": (1.0 / R_PREFILL * P_GPU_S) * 1000.0,
        "c_1ktok_out": (1.0 / R_DECODE * P_GPU_S) * 1000.0,
        "c_req_marginal": (S_FIXED * P_GPU_S),
    }
    d["overhead_ratio"] = d["c_1kreq_alloc"] / d["c_1kreq_used"]
    d["in_out_ratio"] = d["c_1ktok_out"] / d["c_1ktok_in"]
    return d


# ==================================================================== [2] 归因
def attribute(rows: list[dict]) -> tuple[dict, float, int]:
    per: dict[str, dict] = {}
    unattr, unattr_n = 0.0, 0
    for r in rows:
        c = gpu_seconds(r["pre_tokens"], r["n_out"]) * (2.0 if r["retry"] else 1.0) * P_GPU_S
        if r["tenant"] is None:
            unattr += c
            unattr_n += 1
            continue
        a = per.setdefault(r["tenant"], {"cost": 0.0, "req": 0, "tok": 0.0, "out": 0.0,
                                        "raw_in": 0.0, "pre_in": 0.0, "retry": 0})
        a["cost"] += c
        a["req"] += 1
        a["tok"] += r["pre_tokens"] + r["n_out"]
        a["out"] += r["n_out"]
        a["raw_in"] += r["n_in"]
        a["pre_in"] += r["pre_tokens"]
        a["retry"] += 1 if r["retry"] else 0
    return per, unattr, unattr_n


# ==================================================================== [3] 摊销
def amortize(d: dict) -> list[tuple[int, float, float]]:
    c_train = C_TRAIN_GPU_H * P_GPU_H + ENG_HOURS * RATE_ENG_H
    c_req_serve = d["c_billed"] / N_REQ
    return [(L, c_train / (N_REQ * L), (c_train / (N_REQ * L)) / c_req_serve) for L in HORIZONS]


# ==================================================================== [4] 弹性
def elasticity(t: dict, d: dict) -> list[tuple[str, float, float]]:
    """自变量 +10% 时，元/千请求 与 元/千 token 各变化多少 %。"""
    h = t["n_hit_rate"]
    gp = t["pre_tok"]

    def billed(scale_pre=1.0, scale_out=1.0, scale_fix=1.0,
               dpre=0.0, retry_extra=1.0) -> float:
        """retry_extra=1.0 表示重试的一次重复计费；基线 = s_billed。"""
        tot = 0.0
        for is_retry, (pre, out, n) in t["g"].items():
            mul = 1.0 + (retry_extra if is_retry else 0.0)
            pre2 = (pre - dpre * (pre / gp)) * scale_pre
            tot += (pre2 / R_PREFILL + out * scale_out / R_DECODE
                    + S_FIXED * n * scale_fix) * mul
        return tot

    base_s = t["s_billed"]
    base_t = d["c_1ktok_used"]
    cases = [
        ("decode 吞吐", dict(scale_out=1 / 1.10), 1.0),
        ("prefill 吞吐", dict(scale_pre=1 / 1.10), 1.0),
        ("前缀命中率", dict(dpre=0.10 * h * (1 - PREFIX_KEEP) * t["raw_in"]), 1.0),
        ("重试率", dict(retry_extra=1.10), 1.0),
        ("输出长度", dict(scale_out=1.10), 1.10),
        ("固定开销", dict(scale_fix=1.10), 1.0),
    ]
    out = []
    for name, kw, tok_mul in cases:
        s = billed(**kw)
        n_tok = t["n_tok"] * tok_mul
        out.append((name, (s / N_REQ) / (base_s / N_REQ) - 1.0,
                    (s * P_GPU_S / (n_tok / 1000.0)) / base_t - 1.0))
    return out

练习#

  1. 给你的系统算三个口径。 取任意一天的账单与流量，算出 calloc​、cused​、以及可用性溢价；回答：你平时汇报的是哪一个？三者相差多少？如果业务方按你汇报的口径付费，谁会亏？
  2. 把三段分解做出来。 用你实际的输入/输出长度与吞吐，算 prefill、decode、固定开销三段各占多少。如果 prefill 占比超过 50%，说明你的瓶颈与本节算例不同 —— 那对你的优化排序意味着什么？
  3. 测一次归因覆盖率。 你的计量事件里有多少比例能归到（租户，模型版本，路由）三元组？把未归因金额单列，然后回答：如果强行摊回去，会把钱错分给谁？
  4. 算清无效 token。 分别估重试率、截断率、因超时取消的请求率，算出它们各占消耗成本多少。哪一项的"修复成本 / 省下的钱"最小？把它排在第一位。
  5. 给训练成本指定服务期。 用你最近一次训练的实际成本（含人时），在 L=30/90/365 天三个假设下算每请求摊销，并算出交叉点 L∗。L∗ 与你们的模型迭代周期相比如何？谁更长？
  6. 做一次盈亏平衡。 用你当前的 API 单价与你估算的自建单位成本，算 V∗，并给出安全边际。再回答：如果只算消耗口径，结论会翻转吗？
  7. 复核一条弹性。 选你最想改的一个自变量（吞吐、命中率、重试率、输出长度），用 +10% 的扰动实测它对"元/千请求"与"元/千 token"的影响。两个口径的符号是否相反？如果是，你该用哪个口径向谁汇报？

小结#

  • 成本要写成"单价 × 数量"，而数量至少有两个：请求与 token（再分输入/输出）。本例中输出 token 的单位成本是输入的 5.0 倍。
  • 三个口径必须同时给出：分配 0.4286、消耗 0.2847、增量 0 元/千请求。三者满足 calloc​=cused​+(1−ρ)calloc​，本例差 50.6%。
  • 三段分解是唯一的可加口径：prefill 40.08%、decode 58.02%、固定 1.90%（npre​=760,ndec​=220 的先验算例）。它的线性性使"对请求求和"不需要近似。
  • 归因的三个必要条件：三元标签（谁/哪个版本/哪条路径）、分摊闭合且被断言、计量单位与决策单位一致。本例覆盖率 98.913%，残差 0.4334 元必须单列而不是摊回。
  • 不要用单一混合单价对内结算：chat 与 batch 的真实单位成本差 2.55 倍，rag 与 internal 的每请求成本差 3.11 倍。
  • 无效成本要单列：重试占 3.04%、截断占 0.31%；它们的弹性很小（+0.304%），但没有质量收益，所以修它们的判据是人天，不是省钱。
  • 缓存收益有上界 prefill 占比×(1−k)：本例 39.03%×0.65=25.4%，且需要 100% 命中率；现实中 26.5% 命中率只换来 8.86%。
  • 训练摊销是服务期的函数：L=1 天时是推理成本的 677 倍，L=677 天时相等（117.39 B token）。且 Ctrain​ 里工程人时是 GPU 的 8 倍 —— 训练成本被低估是结构性的。
  • 盈亏平衡要带口径与流量：V∗=27.86 M token/天，当前流量的安全边际 6.22 倍。
  • 弹性告诉你去改什么，口径告诉你怎么汇报：decode 吞吐 −5.296%、前缀命中率 −0.865%、输出长度 +5.826%（元/千请求）与 −3.794%（元/千 token）。
