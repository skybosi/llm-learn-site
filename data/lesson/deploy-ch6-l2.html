完整部署实现#

上一课把蓝图画好了，这一课动手把它变成能跑的一整套服务。我们把前面所有章节的产物——量化、张量并行、OpenAI 兼容 API、Docker、监控——装进一个 docker compose，用一个命令把"客服问答助手"完整拉起来。

一、概念讲解#

1. 实现顺序：自底向上，逐步点亮#

不要一上来就写整套编排。正确顺序是每一步都可验证：

  1. 先裸机跑通：命令行 vllm serve，确认模型能加载、能回答（第 2 章）；
  2. 再容器化：用官方镜像 + 挂载权重，确认 GPU 在容器内可见（第 4 章 l2）；
  3. 再加网关：Nginx 前置，确认 SSE 流式能透传；
  4. 再加监控：Prometheus 抓取指标、Grafana 出图（第 4 章 l3）；
  5. 最后写成一个 Compose：一条命令拉起全部。

2. 三个最容易踩的集成点#

  • SSE 透传：Nginx 默认会缓冲上游响应，导致流式 token 攒成一大块才吐出，打字机效果消失。必须 proxy_buffering off；
  • 张量并行与容器设备声明：vLLM 里写了 --tensor-parallel-size 2，Compose 里就要申请 count: 2 的 GPU，两边必须一致，否则要么起不来、要么只有一张卡在干活；
  • 监控网络打通：Prometheus 容器访问 vLLM 用的是容器网络里的服务名（vllm:8000），不是宿主机 localhost，写错就抓不到指标。

示例 2：完整的 docker-compose.yml#

# docker-compose.yml —— 一条命令拉起客服问答助手全套
services:
  vllm:
    image: vllm/vllm-openai:latest
    command: >
      --model /models/Llama-3.1-8B-Instruct-AWQ
      --quantization awq
      --served-model-name support-assistant
      --max-model-len 8192
      --max-num-seqs 64
      --gpu-memory-utilization 0.85
      --enable-chunked-prefill
      --tensor-parallel-size 2
    volumes:
      - /data/models:/models:ro       # 只读挂载 AWQ 权重
    shm_size: 8g
    ipc: host
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 2                # 与 TP=2 一致
              capabilities: [gpu]
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 30s
      timeout: 10s
      retries: 5
      start_period: 180s              # 模型加载 + 量化初始化较慢

  gateway:
    image: nginx:alpine
    ports:
      - "8080:80"
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - vllm

  prometheus:
    image: prom/prometheus:latest
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml:ro

  grafana:
    image: grafana/grafana:latest
    ports:
      - "3000:3000"
    depends_on:
      - prometheus

示例 3：nginx.conf —— 流式透传 + 统一入口#

# nginx.conf：对外暴露 8080，代理到 vllm
server {
    listen 80;

    # 关键：关闭代理缓冲，SSE 才能逐 token 透传
    proxy_buffering off;
    proxy_cache off;

    location /v1/ {
        proxy_pass http://vllm:8000;
        proxy_read_timeout 300s;          # 长生成不超时
        proxy_set_header Host $host;
        proxy_set_header Connection '';
    }

    location /metrics {
        proxy_pass http://vllm:8000;       # 监控也走网关或直连
    }
}

示例 4：prometheus.yml#

# prometheus.yml：抓取 vllm 的 /metrics
global:
  scrape_interval: 15s
scrape_configs:
  - job_name: vllm
    static_configs:
      - targets: ["vllm:8000"]     # 容器网络内用服务名

示例 5：启动并冒烟测试#

# 1. 一键拉起全套
docker compose up -d

# 3. 冒烟：经网关发一次请求
curl http://localhost:8080/v1/chat/completions \

# 4. 验证监控

示例 6：流式客户端（验证网关没把 SSE 卡住）#

# -*- coding: utf-8 -*-
# 走网关请求，确认流式逐 token 返回（打字机效果）
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8080/v1", api_key="EMPTY")
stream = client.chat.completions.create(
    model="support-assistant",
    messages=[{"role": "user", "content": "退货流程是怎样的？"}],
    stream=True,
)
for chunk in stream:
    d = chunk.choices[0].delta
    if d.content is not None:
        print(d.content, end="", flush=True)
print()

三、练习#

  1. 把 --tensor-parallel-size 2 改成 1、Compose 的 count 也改成 1，重跑并对比吞吐，验证双卡 TP 对 decode 吞吐的提升。
  2. 故意删掉 nginx.conf 里的 proxy_buffering off，再跑示例 6，观察流式是否变成"憋一大段才吐"，说明网关缓冲对流式的影响。
  3. 在 Grafana 里把 Prometheus 配成数据源，画一张"P99 TTFT + 排队长度"大盘，完成监控闭环。
  4. 思考：为什么监控指标经网关走 /metrics 转发时，要小心限流策略把 Prometheus 的抓取也限掉？如何为监控路径单独放行？
