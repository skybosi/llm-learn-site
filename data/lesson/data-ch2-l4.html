内容提取与规范化：顺序、幂等与可复现#

这一节要解决什么#

"清洗"这个词给人的印象是把脏东西擦掉。但这一步真正在做的事情是定义等价类：哪些文本表示应当被视为同一份内容？哪些差异是有意义的、必须保留？

这个视角的转换会立刻带来三个具体问题，而它们都不是"用什么库"能回答的：

  1. 规范化的有损性。Unicode 的 NFKC 形式会把 x² + y² 变成 x2 + y2 —— 上标没了，代码里 x2 与 x² 的区分被抹掉。哪些损失可以接受？这取决于你的语料里有什么。
  2. 不可见字符。a + 零宽空格 + b 与 ab 在人眼里完全相同，在字节上不同，在 tokenizer 里也可能不同，在去重指纹上一定不同。零宽字符还是 prompt injection 的常用载体。
  3. 管线的顺序不是随意的。本节代码会给出两个实测：去重键放在规范化之前，两份只差全角/连字/空白的文档不会被识别为重复（唯一指纹 3 个 vs 规范化后的 2 个）；把随机化的 PII 脱敏放在去重之前，两份完全相同的内容会得到不同指纹（c65569d81d16 vs b2af89c7f0ab），去重直接失效。

最后落到全课程的基础设施：确定性（同输入同输出，逐字节）、幂等性（f(f(x))=f(x)）、以及数据版本 = 输入指纹 + 管线版本 + 参数。这三件东西是后面所有关于可复现训练、配比实验、撤下重跑的讨论的前提。

一、为什么"提取"是质量的第一道关#

1.1 网页：欠提取与过提取#

把 HTML 变成正文有两种失败，方向相反，危害不同：

失败 表现 危害 检测
欠提取 正文没抓到（空壳、只留标题） 有效内容丢失；大量空文档进入语料 提取后长度 / 原始 HTML 长度 的比值过低
过提取 导航、广告、页脚、评论区混入正文 boilerplate 被当成"正文"，见 1.2 链接密度、重复块检测

欠提取最容易被发现（长度比异常），因为它的结果是"内容不见了"。过提取最危险，因为它的结果看起来很正常 —— 一段有意义的正文，后面跟着一段版权声明。而这正是下一小节要说的。

1.2 过提取的隐蔽危害#

假设一个站点的页脚是"版权所有 © 2026 示例公司 京ICP备…"，被 200 万页过提取进正文。会发生什么？

  1. 这 200 万个样本不是"重复"（它们的主体内容各不相同，文档级 Jaccard 很低），所以文档级去重不会动它们；
  2. 但这段页脚在语料里出现了 200 万次 —— 它是一个高频 n-gram。后果有三：
    • 子串级去重要处理一个 200 万文档的巨型簇（第 2 节 8.1 的"巨型桶"问题）；
    • 模型会把这串字当成"正文的一部分"来建模，可能学会在生成时输出它（记忆化 + 逐字复读）；
    • 它污染了"重复率"等一切基于 n-gram 的质量指标（第 1 章 4.1 的 n-gram 污染检测里，"仅模板"的误报率是 100%）。
  3. 它还会成为统计陷阱：所有基于"文档级相似度"的去重报告都会显示"重复率很低"，于是团队认为数据很干净。

所以"去除 boilerplate"不是可选的优化，而是去重与质量度量的前置条件。 本节代码的第一段就演示了这个打分过程：一个 167 字的页面，提取后剩 123 字，去掉 26% 的模板噪声。

1.3 PDF：另一套完全不同的失败模式#

PDF 没有"正文"这个结构概念，只有绘制指令。抽取时的问题：

  • 文本层 vs 扫描件：有文本层的 PDF 可以直接抽字符（但顺序可能乱）；扫描件必须先 OCR，OCR 错误会成为语料里的系统性噪声。
  • 阅读顺序：多栏排版、浮动图注、脚注，抽取器按坐标顺序读会得到交错的两栏文字 —— 语义完全乱掉，但看起来像正常的句子（因为没有错别字）。这是最阴险的一类：语料看起来干净，逻辑是错的。
  • 连字符断行：行尾的 - 是断词符还是真正的连字符？判错会把 train-ing 与 training 变成两个 token。
  • 页眉页脚页码：与网页的 boilerplate 同样的问题（1.2）。
  • 表格与公式：表格会被拉平成一行数字（丢失列对应关系）；公式变成乱码或丢失。

工程结论：PDF 抽取必须按来源做质量校验（长度比、语言识别置信度、替换字符比例、以及"句子完整性"启发式），并且把每一个 PDF 来源的抽取器版本记进 manifest（换抽取器 = 数据变了）。

1.4 失效清单（写管线时逐条过）#

  • 空壳页（JS 渲染）：HTML 有内容、文本为空 → 长度比 ≈ 0
  • 反爬登录页：第 1 章 4.4 已讲
  • 编码猜测错误：GBK 当 UTF-8 解 → 大量 U+FFFD
  • 单栏正文被识别成多块：只取到一段（本节代码里"只取最高分块"就是这个失败）
  • 评论区被当正文：论坛页的正文其实是评论，而"帖子"是标题 → 选错块
  • 图文页：正文在图片里 → 文本长度为 0 但有大量 <img>
  • 无限滚动的"加载更多"占位符 → 混入语料

二、正文提取的原理#

2.1 单页启发式（块打分）#

主流单页算法的核心是把 DOM 切成候选块，给每块打分，选最高分（并合并相邻高分块）。打分的信号：

信号 方向 理由
文本长度 加分 正文块通常比导航块长得多
链接密度（链接文本长度 / 总文本长度） 减分 导航、页脚、相关阅读都是链接堆
标点密度 加分（有上限） 正文是句子；导航是无标点的短语堆
标签的语义权重 加分 <article>、<p> 优于 <div>
class/id 关键词 加分/减分 comment、nav、footer 减分；content、post 加分

⚠️ 最后一项（关键词）是最不稳健的：它依赖站点命名习惯，且会被对抗性地绕过（把广告栏命名为 content）。它有效但必须与其他信号一起用。

本节代码的实现是前三个信号的最小组合：

块序号   文本长度   链接密度   得分
  0       17      0.706     2.0     <- 导航（短 + 高链接密度）
  1       71      0.000    36.4     <- 正文第一段
  2       51      0.000    26.4     <- 正文第二段
  3        0      0.000     0.0
  4       23      0.348     6.0     <- 页脚（版权声明）
  5        0      0.000     0.0

注意这里的"合并"步骤是必需的：只取最高分块会得到 71 字（只有第一段），合并相邻高分块后得到 123 字（两段）。真实实现里"正文"总是被切成多个 <p>，所以"选一个块"这种简化会在真实数据上系统性欠提取。

2.2 站点级模板挖掘：为什么它更准#

单页启发式只看一页；模板挖掘看同一站点的多页：把 N 个页面切成 DOM 子树，统计每个子树的"出现率"。出现率接近 100% 的子树就是模板（导航、页脚、侧栏）；出现率低但文本占比高的就是正文。

为什么它比单页启发式准：它用的是跨文档的统计证据，而不是单页的启发式阈值。一个只有 50 字的短正文页，在单页启发式下会被导航块打败（导航可能有 80 字），但在模板挖掘下：导航在 1000 个页面里都出现 → 判为模板删掉；那 50 字只在这一页出现 → 判为正文保留。

代价：

  • 必须按站点批量处理（需要先按域名分组，改变管线的数据流形状）；
  • 对新站点/低频站点无效（样本不足）；
  • 站点改版会让模板集合失效（必须按时间窗口重新挖掘，并记录模板版本）。

工程上的组合：先按站点做模板挖掘，对样本不足的站点回退到单页启发式。两条路径都要记进 manifest（因为它们的输出不同）。

2.3 提取质量的校验#

提取器是不可信的，必须让它的输出通过一组校验（本节代码第 4 段）：

校验 判据（示意） 触发后
长度比 提取文本长度 / HTML 长度 ≥ 某个下限 判为欠提取，丢弃或换抽取器
绝对长度 提取文本 ≥100 字符 空壳页，丢弃
链接密度 ≤0.6 判为导航页/列表页，丢弃或标记
替换字符 U+FFFD 比例 >0 编码错误，进人工队列（不要静默保留）
语言识别 置信度 ≥ 阈值且与预期语言一致 否则丢弃（防止混入其它语言/乱码）
重复块 该块在本站点出现率 >90% 判为模板，删除

本节代码的实测：

正常页        文本长度 167  链接密度 0.12  替换字符 0  -> 通过
空壳页（JS 渲染） 文本长度   0  链接密度 0.00  替换字符 0  -> 可疑
导航页        文本长度 110  链接密度 1.00  替换字符 0  -> 可疑

三条规则分别抓住了三种完全不同的失败：长度抓空壳，链接密度抓导航，替换字符抓编码。它们的作用是让"提取失败"从静默变成可见 —— 这是本节最重要的一条工程原则。

三、Unicode 规范化：定义等价类#

3.1 四种形式#

形式 做什么 典型用途
NFC 规范合成：把"基字符 + 组合符"合成预组合字符 通用文本（最常用）
NFD 规范分解：把预组合字符拆成基字符 + 组合符 需要按字符比较（如重音不敏感搜索）
NFKC 兼容合成：在 NFC 基础上再做兼容分解 搜索、去重（有损）
NFKD 兼容分解 同上，需要拆开时

关键区分："规范"（canonical）变换是无损的（NFC 与 NFD 互为逆），"兼容"（compatibility）变换是有损的。这一条是本节的核心。

3.2 NFKC 的有损性：具体损失清单#

本节代码的实测（原始 → NFKC）：

原始 NFKC 损失了什么
① 第一步 1 第一步 "带圈"这个语义（有序列表符号 / 编号样式）
ﬁnal final 连字（影响字符串长度与视觉）
ＡＢＣ１２３ ABC123 全角（在某些文本里有对齐/艺术用途）
x² + y² x2 + y2 上标 —— 数学语义丢失，且 x² 与变量 x2 不再可区分
㍿東京 株式会社東京 方形连字被展开（长度变化 1 → 4）
café café 无（NFC 与 NFKC 在此相同）

最重要的两行：

  • 上标丢失是数学/科学语料的实质损失：x² 变成 x2 后，模型无法区分"x 的平方"与"变量 x2​"。如果你的语料含公式、化学式（H₂O）、单位（m³），NFKC 会系统性地破坏它们。
  • 方形连字展开会改变长度：㍿ 一个字符变四个字符，于是基于字符长度的所有启发式规则（词数区间、长度分位）都会偏移。这类变化量小但全局，很难发现。

因此规范化的选择必须按域决定：

语料 推荐 理由
自然语言（网页、对话、书籍） NFKC 合并全角/连字带来的冗余收益大于损失
代码 NFC（或只做空白与零宽清理） NFKC 会把全角括号、上标改成半角，破坏标识符与字符串
数学/科学 NFC + 单独的上标/下标保留规则 NFKC 破坏公式语义
标识符/ID/URL 完全不规范化（或另存一份规范化的） 改一个字符就改了指代对象

3.3 不可见字符：四类，双重影响#

本节代码的实测（肉眼都像 ab）：

'ab'         len=2  sha256[:12]=fb8e20fc2e4c  含不可见=False
'a\u200bb'   len=3  sha256[:12]=8df62aef5f92  含不可见=True   <- 零宽空格 ZWSP
'a\ufeffb'   len=3  sha256[:12]=47a12dcb64e9  含不可见=True   <- BOM / 零宽不换行空格
'a\xadb'     len=3  sha256[:12]=15463234df2c  含不可见=True   <- 软连字符
'a\u200db'   len=3  sha256[:12]=57d3077bde56  含不可见=True   <- 零宽连接符 ZWJ

四类要处理的东西：

类别 Unicode 类别 例子 为什么要处理
零宽字符 Cf ZWSP U+200B、ZWNJ U+200C、ZWJ U+200D 视觉不可见、影响 tokenizer 与去重；是 prompt injection 的常用载体（把 "ignore previous instructions" 用零宽字符打断以绕过关键词过滤）
BOM / 方向控制 Cf U+FEFF、U+202A~`U+202E`（双向覆盖） 文件头的 BOM 会进入第一个 token；双向控制字符能让显示的文本顺序与字节顺序不同（欺骗性很强）
软连字符 / 不换行空格 Cf / Zs U+00AD、U+00A0 断词与空白语义；U+00A0 会被很多 tokenizer 当普通空格，但字符串比较不等
组合标记 Mn U+0301（重音） 不要删（它是内容），用 NFC 合成即可

本节代码的 canon 选择删掉所有 Cf 类字符（零宽、BOM、方向控制、软连字符），保留 Mn（组合符交给 NFC 处理）。这是一个可以 defended 的选择：Cf 是"格式控制"而非内容，且它们的存在通常来自复制粘贴或抓取噪声。但要注意它的代价：某些语言里 ZWJ/ZWNJ 是必需的（如波斯语、印地语的正字法），删掉会改变词形。所以如果你的语料包含这些语言，规则要按语言分支。

3.4 U+FFFD 是上游错误的信号#

U+FFFD（替换字符 �）的意思是"编码解码失败，我不知道这个字节是什么"。它出现在语料里意味着上游有编码错误（用了错误的字符集解码）。

正确处理不是"去掉它"，而是把它当成一个信号：

  • 统计每个来源的 U+FFFD 比例；
  • 比例异常高的来源 → 编码猜测错误 → 换编码重解（或标记为不可用）；
  • 比例很低的 → 保留并记录（因为去掉它会把"某个字符无法解码"这个事实抹掉，反而让语料看起来更干净）。

为什么不能静默保留：一个 U+FFFD 可能替换掉了 1 个字符也可能替换掉了 100 个字节（取决于错误类型）。它会让长度统计、语言识别、以及下游的可读性都失真。

3.5 空白、大小写、标点#

  • 空白：\r\n → \n、连续空白折叠、去首尾。但不能折叠代码的缩进（Python 的缩进是语法）与 Markdown 的结构（两个空格 = 换行）。
  • 大小写：小写化会丢 NER 信号（Apple 公司 vs apple 水果）、代码标识符（Foo 类 vs foo 变量）。除非有明确的理由（比如做大小写不敏感的匹配），不要小写化。
  • 标点：去标点会丢数学、代码、句边界。唯一的例外是标点变体归一（全角 ↔ 半角），但那属于 NFKC 的范畴。

判据：任何有损操作都要能回答"我丢了什么、为什么可以丢、有多少样本受影响"。答不上来就不要做。

3.6 核心原则#

规范化只能合并真正等价的表示。任何"为了好看"或"为了统一"的有损变换，都必须有明确的、可测量的理由。

这条原则有一个很实用的推论：规范化应该按域分层，而不是全管线一套。自然语言走 NFKC，代码走 NFC，标识符不动 —— 代价是维护多套指纹（第 2 节的去重必须按域分开做，否则跨域指纹不可比），收益是不丢信息。

四、管线的顺序：为什么不能随意#

4.1 推荐顺序#

原始快照（raw，只追加）
 → 解码/编码修复（含 U+FFFD 比例统计）
 → Unicode 规范化（按域选择 NFC / NFKC）
 → 去不可见字符与格式控制（Cf 类）
 → 空白规范化（按内容类型分支：自然语言折叠，代码保留）
 → 语言识别（在规范化之后）
 → 正文提取 / boilerplate 去除（DOM 层或站点模板层）
 → 质量打分与过滤
 → PII 脱敏（必须是确定性的）
 → 去重（精确 → 近似 → 子串级）
 → 分词 / 打包

4.2 三条判据（记住这三条，顺序基本就定了）#

  1. 去重之前的所有步骤都必须确定性且幂等。 理由：去重键是内容的指纹。如果指纹函数对同一内容在不同时间/不同路径给出不同结果，去重就是随机的。任何随机化或非幂等的变换必须放在去重之后。

  2. 有损操作要尽量靠后，且有明确理由。 理由：一旦信息丢了，后面的步骤（语言识别、质量打分、去重）都无法再恢复。例如把 NFKC 放在语言识别之前是对的（它提高短文本的语言识别准确率），但把 NFKC 放在代码语料上是错的（它破坏标识符）。

  3. 语言识别放在规范化之后、过滤之前。 理由：短文本的语言识别对不可见字符与全角字符很敏感；规范化能显著提高它的准确率。而质量过滤常常依赖语言（不同语言的阈值不同），所以语言识别必须先于过滤。

4.3 顺序错误的三个代价（都有代码实测）#

代价一：去重键放在规范化之前 → 去重失效。

原始文本指纹:   d1=ea919a5c7ce9  d2=120ba4a7c9f7  d3=8a2f41f56289  -> 唯一 3 个
规范化后指纹:   d1=703705905ed9  d2=703705905ed9  d3=8a2f41f56289  -> 唯一 2 个

d1 与 d2 只差全角数字、连字、多余空格与一个零宽字符 —— 人眼看是同一份文档，规范化后指纹相同，规范化前完全不同。这是"顺序错误"最常见的一种：管线里明明有规范化，只是位置放错了，于是去重率低得莫名其妙，而任何报告都不会指出原因。

代价二：随机化的脱敏放在去重之前 → 去重失效。

随机占位符  : 两份相同内容的指纹 = c65569d81d16 / b2af89c7f0ab -> 不一致（去重失效）
确定性占位符: 两份相同内容的指纹 = e4fa4af947cb / e4fa4af947cb -> 一致

这一条比第一条更隐蔽，因为"随机替换 PII"听起来是个更安全的做法（避免所有样本共享同一个占位符，从而减少占位符本身成为高频 token 的风险）。但它把去重键破坏了。

解法不是二选一：用确定性替换（同一实体 → 同一占位符，例如对原实体做加盐哈希后映射到固定长度的占位符，再加一张仅存于安全域的映射表）。这样既避免了"所有邮箱都变成 <邮箱>"的过度合并，又保持了去重的确定性。

代价三：非幂等的步骤放在去重之前 → 结果不可复现。

canon       非幂等样本 0 个 []
canon_bad   非幂等样本 1 个 ['&amp;amp;x']

canon_bad 只做一趟 HTML 实体解码，于是 &amp;amp;x 第一次变成 &amp;x、第二次变成 &x —— 同一份内容在"处理一次"与"处理两次"之后指纹不同。这在批处理管线里可能看不出问题（每份文档只处理一次），但在流式/增量管线里是致命的：同一份文档可能被处理两次（重跑、补数据、去重失败重试），于是产生两个不同指纹、两份"不同"的数据。

幂等性是去重可复现的前提，而它也是最便宜的检查：f(f(x)) == f(x) 对一批样本跑一遍。

4.4 PII 脱敏作为一种规范化#

把 4.3 的代价二推到底，会得到一条对 PII 处理的完整要求：

要求 理由
确定性 保证去重键稳定（同一内容 → 同一指纹）
一致性 同一实体在全语料中要么全删要么全留（否则模型学到部分信息，可从"未脱敏的部分"反推）
不引入新碰撞 若所有邮箱都变成 <邮箱>，两篇只在邮箱上不同的文档会变成"完全相同" → 被误判重复
映射表本身要保护 映射表（原值 → 占位符）就是 PII 本身，必须与训练数据隔离存储与访问

"不引入新碰撞"这一条最容易被忽略：它意味着占位符必须保留区分度（同一实体的不同实例共享占位符，不同实体不同占位符）。做法是对原实体做带密钥的哈希，取前 k 位作为占位符后缀。代价：k 小则碰撞多（误去重），k 大则占位符多样（占位符本身成为长尾 token）。这是一个可以量化的取舍：k=64 bit 时碰撞概率在 108 个实体下约为 10−3 量级。

五、可复现：把管线做成确定性函数#

5.1 不确定性来源清单#

来源 表现 修法
多进程/线程完成顺序 合并结果的顺序不同 排序后归并（按稳定键）
set / dict 遍历顺序 输出顺序不同（Python 3.7+ 的 dict 保序但仍依赖插入顺序） 显式排序
未固定的随机种子 采样、打乱、去重保留、哈希 所有随机性走同一注入的种子
哈希函数 Python hash() 带进程随机化 用 hashlib 的确定性哈希
时间戳进入内容 每次运行内容不同 时间戳只记录在元数据里
浮点求和顺序 打分或统计量在小数位抖动 固定聚合顺序（或用量化后的整数分数）
文件系统遍历顺序 输入顺序不同 显式排序输入
并行归约的分片边界 边界变化导致浮点结果变化 固定分片方案

本节代码的最后一段给了一个可用的检查：两次运行同一批文档，输出列表与整批指纹完全一致（两次运行输出一致 = True）。

5.2 幂等性#

f(f(x))=f(x)

为什么它是"最小充分检查"：如果管线满足幂等性，那么"处理一次"与"处理两次"结果相同 —— 这在流式/增量/重试的场景里直接决定了正确性。而且它很容易测：拿一批样本跑一遍，再跑一遍，比较。

什么样的变换不幂等（都会破坏它）：

  • 单趟解码/替换（&amp;amp; → &amp;）；
  • 截断（按长度截断到 1000 字符，第二次不变 —— 这个其实幂等）；
  • 追加标记（加 [已处理] 前缀）；
  • 带状态的去重（第二次运行时"已经见过"）；
  • 随机化的脱敏。

5.3 manifest：数据版本三元组#

把整条管线的产出做成可追溯的：

manifest = {
    "input":  {"source_id": "web-crawl-01", "n_docs": 120000, "fingerprint": "..."},
    "pipeline": {"version": "clean-2.3.0", "git_commit": "a1b2c3d"},
    "params": {"unicode_form": "NFKC", "min_len": 100, "dedup_tau": 0.8,
               "dedup_shingle_k": 8, "pii_mode": "deterministic_hmac"},
    "output": {"n_docs": 41200, "unique_tokens": 812345678, "fingerprint": "..."},
    "stats":  {"pii_hits": 5123, "u_fffd_docs": 42, "dedup_removed": 78800},
}

四个字段各自的作用：

  • input.fingerprint + pipeline.version + params → 数据版本（三元组唯一确定一份数据）；
  • output.fingerprint → 验收（重跑能复现同一个指纹，说明管线是确定的）；
  • stats → 审计（u_fffd_docs = 42 是一个要在评审里被看到的质量信号，不是日志噪声）；
  • params 里的每一个值都要能被追溯到一次决策（为什么 τ=0.8？PR 曲线在哪？）。

六、取舍清单#

取舍 一端 另一端 怎么选
规范化强度 只做 NFC（保信息） NFKC（合并冗余） 按域：自然语言 NFKC，代码/数学 NFC
不可见字符 全删（干净） 保留（保语言正确性） 除非含波斯/印地语等 ZWJ 必需的语言，全删 Cf
大小写 小写化（合并冗余） 保留（保 NER/代码信号） 默认保留；只在明确需要不敏感匹配时小写
正文提取 单页启发式（简单、可流式） 站点模板挖掘（更准、需批量） 组合使用：有批量则模板挖掘，否则启发式 + 质量校验
PII 脱敏 全部替换成同一占位符 保留区分度的确定性占位符 后者（避免误去重），代价是多一张受保护的映射表
pdf 抽取 快（按坐标顺序） 慢（重排阅读顺序） 语料价值高的来源用重排；其余标记风险等级
幂等 vs 便利 严格幂等（可复现） 允许单趟变换（代码简洁） 严格幂等 —— 这是可复现的前提，不是偏好

代码#

四段：Unicode 规范化的有损性、正文提取与质量校验、管线顺序与确定性、以及幂等性检查。

# -*- coding: utf-8 -*-
"""内容提取与规范化：NFKC 的有损性、正文提取、管线顺序、确定性。"""
import hashlib
import re
import unicodedata

# ============ 1. Unicode 规范化：四种形式的差别与"有损"在哪 ============
SAMPLES = ["① 第一步", "ﬁnal", "ＡＢＣ１２３", "x² + y²", "㍿東京",
           "e\u0301cole", "a\u200bb", "\ufeff开头", "soft\u00adhyphen", "caf\u00e9"]
print("=== 1. 四种规范化形式（只列出发生变化且值得注意的）===")
print(f"{'原始':>14} {'NFC':>14} {'NFKC':>16} {'NFD':>14} 说明")
NOTES = {"① 第一步": "带圈数字：NFKC 变普通数字（丢语义）",
         "ﬁnal": "连字：NFKC 分解为两个字母",
         "ＡＢＣ１２３": "全角：NFKC 转半角",
         "x² + y²": "上标：NFKC 降为普通数字 -> x2 与变量名歧义",
         "㍿東京": "方形连字：NFKC 展开成多个字",
         "e\u0301cole": "组合字符：NFC 合成，NFD 分解",
         "a\u200bb": "零宽空格：四种形式都不动它（不可见字符）",
         "\ufeff开头": "BOM：四种形式都不动它",
         "soft\u00adhyphen": "软连字符：四种形式都不动它",
         "caf\u00e9": "预组合字符：NFD 分解"}
for s in SAMPLES:
    nfc = unicodedata.normalize("NFC", s)
    nfkc = unicodedata.normalize("NFKC", s)
    nfd = unicodedata.normalize("NFD", s)
    print(f"{s!r:>14} {nfc!r:>14} {nfkc!r:>16} {nfd!r:>14} {NOTES.get(s,'')}")

print("\n=== 1b. 不可见字符：肉眼相同，字节不同 -> token / 去重都受影响 ===")
for t in ["ab", "a\u200bb", "a\ufeffb", "a\u00adb", "a\u200db"]:
    print(f"   {t!r:16s} len={len(t)}  sha256[:12]={hashlib.sha256(t.encode()).hexdigest()[:12]}"
          f"  含不可见={any(unicodedata.category(c) in ('Cf','Mn') for c in t)}")

# ============ 2. 正文提取：最小 Readability 类（块打分） ============
TAG = re.compile(r"<(/?)(\w+)[^>]*>")
def text_of(html):
    return re.sub(r"<[^>]+>", "", html)

CLOSE = re.compile(r"</(?:p|div|li)>")
def blocks(html):
    """把 HTML 粗切成候选块：以 <p>/<div>/<li> 的闭合为界（教学用极简解析）。"""
    out, buf = [], ""
    for tok in re.split(r"(</(?:p|div|li)>)", html):
        buf += tok
        if CLOSE.fullmatch(tok):
            out.append(buf); buf = ""
    if buf.strip():
        out.append(buf)
    return [b for b in out if b.strip()]

def score_block(b):
    txt = text_of(b)
    ln = len(txt.strip())
    link_len = sum(len(text_of(m)) for m in re.findall(r"<a\b.*?</a>", b, flags=re.S))
    link_density = link_len / max(1, ln)
    punct = len(re.findall(r"[。！？；，.!?;,]", txt)) / max(1, ln)
    # 打分：长文本加分、链接密度与标点密度过低减分
    return ln * (1 - link_density) * (0.4 + 2.0 * min(punct, 0.25)), ln, link_density

PAGE = """<html><head><title>示例页</title></head><body>
<div id="nav"><a href="/a">首页</a><a href="/b">产品</a><a href="/c">价格</a>
<a href="/d">关于</a><a href="/e">联系</a><a href="/f">招聘</a></div>
<div class="article">
<p>大规模语言模型的训练依赖高质量语料。语料的质量决定了模型的上限，而清洗与去重是其中最关键的环节。本文从来源、许可、去重与过滤四个方面展开讨论。</p>
<p>去重的第一步是定义"重复"。字节级相同只是最简单的一种情形，模板化与改写后的近重复同样会主导训练分布。</p>
</div>
<div id="footer"><a href="/tos">服务条款</a><a href="/privacy">隐私政策</a>
版权所有 示例公司 2026</div>
</body></html>"""

print("\n=== 2. 正文提取：块打分 + 相邻块合并 ===")
print(f"{'块序号':>6} {'文本长度':>8} {'链接密度':>9} {'得分':>9}")
scored = []
for i, b in enumerate(blocks(PAGE)):
    sc, ln, ld = score_block(b)
    scored.append((sc, b))
    print(f"{i:6d} {ln:8d} {ld:9.3f} {sc:9.1f}")
best_i = max(range(len(scored)), key=lambda i: scored[i][0])
best_sc = scored[best_i][0]
# 合并相邻的高分块（真实实现里正文常被切成多个 <p>）
keep = [i for i in range(len(scored)) if scored[i][0] >= 0.5 * best_sc]
merged = " ".join(text_of(scored[i][1]).strip() for i in keep)
print(f"\n   最高分块 = {best_i}；合并的高分块 = {keep}")
print(f"   提取正文（前 60 字）：{merged[:60]}...")
print(f"   全文文本长度 {len(text_of(PAGE).strip())}  ->  提取长度 {len(merged)}"
      f"（去掉 {1 - len(merged)/len(text_of(PAGE).strip()):.0%} 的模板噪声）")

# ============ 3. 管线顺序与确定性 ============
WS = re.compile(r"\s+")
def canon(t):
    """确定性且幂等：NFKC + 空白折叠 + 去控制/零宽字符。"""
    t = unicodedata.normalize("NFKC", t)
    t = "".join(c for c in t if unicodedata.category(c) != "Cf")   # 去掉格式字符（零宽/BOM）
    return WS.sub(" ", t).strip()

def key(t):
    return hashlib.sha256(t.encode("utf-8")).hexdigest()[:12]

# 三份内容：d1 与 d2 只差全角/连字/空白/零宽，d3 是不同内容
d1 = "研究报告：ﬁnal 结果见 ① 附录。作者  张三"
d2 = "研究报告：final 结果见 1 附录。作者\u200b 张三"
d3 = "完全不同的另一篇文档内容。"
docs = {"d1": d1, "d2": d2, "d3": d3}

print("\n=== 3a. 去重键放在规范化之前 vs 之后 ===")
raw_keys = {k: key(v) for k, v in docs.items()}
can_keys = {k: key(canon(v)) for k, v in docs.items()}
print(f"   原始文本指纹: {raw_keys}  -> 唯一 {len(set(raw_keys.values()))} 个")
print(f"   规范化后指纹: {can_keys}  -> 唯一 {len(set(can_keys.values()))} 个")
print("   结论：先规范化再去重，d1 与 d2 才被识别为同一份；顺序反了就去不掉")

print("\n=== 3b. 非确定性的脱敏放在去重之前：指纹不稳定 ===")
import random
EMAIL = re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+")
def mask_random(t, seed):
    r = random.Random(seed)                     # 随机占位符：同一实体每次不一样
    return EMAIL.sub(lambda m: f"<EMAIL_{r.randrange(16**4):04x}>", t)
def mask_det(t):
    return EMAIL.sub("<邮箱>", t)
e1 = "联系方式 zhang@example.com，请勿外传。"
e2 = "联系方式 zhang@example.com，请勿外传。"
for name, f in (("随机占位符", lambda t, s: mask_random(t, s)), ("确定性占位符", lambda t, s: mask_det(t))):
    k1, k2 = key(canon(f(e1, 1))), key(canon(f(e2, 2)))
    print(f"   {name:8s}: 两份相同内容的指纹 = {k1} / {k2} -> {'一致' if k1 == k2 else '不一致（去重失效）'}")

print("\n=== 3c. 幂等性与两次运行一致性 ===")
def canon_bad(t):
    """反例：只做一次单趟实体解码 —— 不幂等。"""
    return t.replace("&amp;", "&").replace("&lt;", "<")
for name, f in (("canon", canon), ("canon_bad", canon_bad), ("mask_det", mask_det)):
    samples = ["  多  空白 ", "&amp;amp;x", "ＡＢＣ", "a\u200bb"]
    bad = [s for s in samples if f(f(s)) != f(s)]
    print(f"   {name:9s} 非幂等样本 {len(bad)} 个 {bad[:2]}")
before = [canon(d) for d in docs.values()]
after = [canon(d) for d in docs.values()]
print(f"   两次运行输出一致 = {before == after}   "
      f"整批指纹 = {hashlib.sha256(''.join(sorted(can_keys.values())).encode()).hexdigest()[:16]}")

# ============ 4. 提取质量校验与 PII ============
print("\n=== 4. 提取质量校验：长度比 / 链接密度 / 替换字符 ===")
for name, html in (("正常页", PAGE), ("空壳页（JS 渲染）", "<html><div id='app'></div></html>"),
                   ("导航页", "<html>" + "".join(f"<a href='/{i}'>链接{i}</a>" for i in range(30)) + "</html>")):
    txt = text_of(html).strip()
    ld = sum(len(text_of(m)) for m in re.findall(r"<a\b.*?</a>", html, flags=re.S)) / max(1, len(txt))
    bad = txt.count("\ufffd")
    flag = "可疑" if (len(txt) < 100 or ld > 0.6 or bad > 0) else "通过"
    print(f"   {name:16s} 文本长度 {len(txt):4d}  链接密度 {ld:.2f}  替换字符 {bad}  -> {flag}")

   canon_bad 非幂等样本 1 个 ['&amp;amp;x']
   mask_det  非幂等样本 0 个 []
   两次运行输出一致 = True   整批指纹 = a518840e10c7d3dd

=== 4. 提取质量校验：长度比 / 链接密度 / 替换字符 ===
   正常页              文本长度  167  链接密度 0.12  替换字符 0  -> 通过
   空壳页（JS 渲染）       文本长度    0  链接密度 0.00  替换字符 0  -> 可疑
   导航页              文本长度  110  链接密度 1.00  替换字符 0  -> 可疑

七个实现决策背后的理由：

  • 第 1 段把所有变化都打印出来，而不是只打印"哪个不同"：规范化的危害只在具体的字符上才能被评审。看到 x² + y² → x2 + y2 的人会立刻意识到"我的语料里有公式"，而看到"NFKC 是有损的"这句话不会。
  • 第 1b 段用 sha256 而不是"看起来不同"来说明问题：a\u200bb 与 ab 在终端里可能是同一个样子，指纹是唯一能让人相信它们不同的证据。这一段同时也是"不可见字符会破坏去重"的最小证明。
  • 第 2 段的 score_block 只用三个信号（长度、链接密度、标点密度）：刻意不加 class/id 关键词，因为关键词规则依赖站点习惯，会掩盖"结构信号的泛化能力"。实测结果（导航 2.0 / 正文 36.4 / 页脚 6.0）说明这三个信号已经足够分开三类块。
  • 第 2 段的"合并相邻高分块"：这一行是必需的，因为正文总是被切成多个 <p>。第一版实现只取最高分块，提取长度 71（只有第一段）；合并后 123。这个差别在真实数据上就是"每篇文档丢掉一半内容"，而长度校验不会报警（71 字仍然超过下限）。
  • canon 用 unicodedata.category(c) != "Cf" 而不是列一张字符黑名单：黑名单永远不全（零宽字符有二十多个变体，方向控制有九个）。按 Unicode 类别过滤是完备的，代价是要接受"删掉所有格式字符"这个语义（4.3 节的边界：某些语言需要 ZWJ）。
  • 第 3a/3b 两组对照都是"只改一处"：3a 只改去重键的位置，3b 只改脱敏的确定性。这是做取舍实验的基本纪律 —— 一次改两个变量，得到的结论无法归因。
  • 第 3b 段揭示了一个反向直觉：随机化脱敏"看起来更安全"，实际破坏了去重。这类"为了安全引入的不确定性"是最难发现的，因为它只在下游（去重率异常低）表现，而在脱敏这一步看起来完全正常。
  • 第 4 段用三条规则抓三种不同的失败，并让它们显式变成"可疑"标记而不是静默丢弃。提取失败必须可见 —— 这是本节的工程核心：一个静默的欠提取会让整个来源的数据质量被高估。
  • ⚠️ 本段代码是教学实现：正文提取用的是极简解析（不处理嵌套、不处理 <script> 内容、不做实体解码），生产环境要用成熟的抽取库，并记录抽取器版本（换版本 = 数据变了）。Unicode 部分则是完整的 —— 它直接用标准库的 unicodedata，没有简化。

练习#

  1. 规范化的损失评估：取一份你熟悉的语料（代码片段、数学文本、中文网页各一段）。 （a）对每一段分别算 NFC 与 NFKC 后的结果，列出所有不同的位置； （b）对每个差异判断"语义是否改变"，给出一个判定标准； （c）据此为三类语料各选定一个规范化形式，并写出这个选择在 manifest 里对应的字段。

  2. 不可见字符的攻防：用零宽字符构造一个绕过关键词过滤的样本。 （a）把"忽略之前的所有指令"用至少两种方式插入零宽字符，展示字符串比较与正则匹配效果的差异； （b）设计一个清洗函数把它还原（说明你怎么保证它幂等）； （c）说明这个清洗对波斯语/印地语语料的副作用，以及你会怎么按语言分支。

  3. 提取质量校验的阈值标定：本节代码用"长度 < 100、链接密度 > 0.6、替换字符 > 0"三条规则。 （a）收集 50 个真实网页（或用你自己的语料），人工标"提取正确/错误"，测这三条规则的 precision/recall； （b）调整阈值使 recall 达到 0.95，报告此时的 precision 与误杀率； （c）说明为什么"长度比"（提取长度 / HTML 长度）比"绝对长度"更适合作为跨站点的判据，以及它自己的失效条件。

  4. 顺序的形式化：把管线步骤记为 s1​,s2​,…,sn​，其中一些是幂等的（I 类），一些不是（N 类）。 （a）证明：若所有 si​∈I 且两两可交换，则整个管线幂等； （b）举一个反例说明"两两可交换"这个条件不能去掉； （c）给出你的规则："去重必须排在所有 N 类步骤之后"，并用 (a)(b) 论证它。若某个 N 类步骤必须放在去重之前（例如语言识别），你怎么办？

  5. PII 占位符的区分度：设你有 108 个不同的邮箱实体，占位符用"HMAC 前 k 位"。 （a）用生日问题估计 k=32 与 k=64 时的碰撞对数； （b）说明碰撞会造成什么后果（提示：会制造假重复，第 2 节的 FP）； （c）在"碰撞少"与"占位符多样（占位符本身成为长尾 token）"之间，你会选哪个 k？为什么？

  6. 确定性审计：为你手上的（或假想的一条）管线写一个"确定性审计"脚本。 （a）列出你会检查的 8 个不确定性来源（对照 5.1 的表），并为每个写出一个可执行的检查； （b）设计一个验收测试：同输入跑两次，比较哪些量（输出字节指纹？样本数？唯一 token 数？）； （c）如果两次运行的"唯一 token 数"一致但"输出字节指纹"不同，最可能的原因是什么？

小结#

  • 这一步的实质是定义等价类，不是"擦掉脏东西"：哪些差异应当被合并（全角/连字/不可见字符），哪些必须保留（上标、大小写、代码缩进）。
  • 正文提取的两种失败方向相反：欠提取（内容不见了，容易被长度校验发现）与过提取（boilerplate 混入，最危险）。过提取的危害是隐性的：模板在百万页里重复 → 高频 n-gram → 记忆化风险 + 巨型簇 + 污染一切基于 n-gram 的质量指标（代码实测：去掉 26% 模板噪声）。
  • 站点级模板挖掘比单页启发式更准（用跨文档统计证据），代价是需要按站点批量处理、对新站点无效、站点改版后要重挖。工程上是两者组合 + 质量校验。
  • NFKC 是有损的，具体损失包括：带圈数字、连字、全角、上标（x² → x2，数学语义丢失）、方形连字展开（改变长度）。所以规范化必须按域选择：自然语言用 NFKC，代码/数学用 NFC，标识符不动。
  • 不可见字符（零宽、BOM、方向控制、软连字符）肉眼不可见但字节不同 —— 代码实测五组"看起来一样"的字符串全部有不同指纹。它们既破坏去重，也是 prompt injection 的载体。处理方式是按 Unicode 类别（Cf）过滤而不是列黑名单，但要按语言分支（ZWJ 在某些语言里必需）。
  • U+FFFD 是上游编码错误的信号，不能静默保留也不能静默删除 —— 要按来源统计比例，异常高的换编码重解。
  • 管线的顺序由三条判据决定：① 去重之前所有步骤必须确定性且幂等；② 有损操作尽量靠后且有理由；③ 语言识别放在规范化之后、过滤之前。代码实测了两个反面：去重键放在规范化之前 → 唯一指纹 3 个而不是 2 个；随机化脱敏放在去重之前 → 同一内容指纹不同（c65569d81d16 vs b2af89c7f0ab）。
  • PII 脱敏的要求不止"删掉"：还要确定性、一致性、不引入新碰撞、映射表受保护。占位符的区分度（k 位哈希）是一个可量化的取舍。
  • 可复现 = 确定性 + 幂等 + manifest。不确定性来源有八类（并行顺序、set 遍历、随机种子、hash()、时间戳、浮点求和、文件遍历、分片边界），逐条可查；幂等性 f(f(x))=f(x) 是最便宜的充分检查；manifest 用输入指纹 + 管线版本 + 参数三元组定义数据版本，并用输出指纹做验收。
