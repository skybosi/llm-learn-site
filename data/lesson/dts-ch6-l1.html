ZeRO-1/2/3 与 FSDP：分片对象、通信代价与适用场景#

上一章结尾你已经能给并行方案分工。可只要动手配一次真实模型，最先撞上的不是通信、而是显存：8.72B 参数的模型，即使用 bf16 存参数，混合精度 Adam 的模型状态也要 130 GiB——单卡装不下，而数据并行本来是要每张卡都存一份完整副本的。ZeRO 的全部内容只有一句话：把这份副本切开。这一课把"切什么"与"切了要多付多少通信"做成可打印的账本。

一、概念讲解#

1. 数据并行的内存困境：模型状态被复制了 P 份#

数据并行（DP）的目标是让 P 张卡算不同的数据，但每张卡必须持有完整的模型状态才能做前向和反向。混合精度 Adam 的账本是固定的（单位：字节/参数）：

组成 精度 字节/参数 说明
模型参数 fp16 / bf16 2 前向反向用的那份
梯度 fp16 / bf16 2 反向产出、AllReduce 后同步
主权重 master weight fp32 4 更新必须落在高精度副本上
Adam 一阶动量 m fp32 4 优化器状态
Adam 二阶动量 v fp32 4 优化器状态
合计 16 ZeRO 论文的 16Ψ 口径

Ψ 表示参数量。这张表解释了两件事：第一，优化器状态（12Ψ）占了 75%，但它只在参数更新那一步被用到；第二，参数与梯度（各 2Ψ）在每一步的前向反向里都要用。切分谁，代价完全不同——这正是 ZeRO 分三档的原因。

2. 三档切法：P 越大，省得越多，但收益有上限#

设数据并行组内有 P 张卡（ZeRO 论文用 Nd​ 表示），每卡每参数字节数如下：

档位 切什么 每卡每参数（B） 大 P 极限
ZeRO-0 / 纯 DP 不切 16 16
ZeRO-1 优化器状态 4+12/P 4
ZeRO-2 优化器状态 + 梯度 2+14/P 2
ZeRO-3 优化器状态 + 梯度 + 参数 16/P 0

代进刚算的例子：8.72B 模型（16Ψ=130 GiB），P=8 时从 130 GiB 降到 ZeRO-1 的 44.7 GiB、ZeRO-2 的 30.5 GiB、ZeRO-3 的 16.3 GiB；P=64 时 ZeRO-3 只剩 2.0 GiB。注意"极限"那一列：ZeRO-1/2 的收益很快饱和（P=64 已经拿到大部分好处），而 ZeRO-3 可以随 P 线性下降——这也是它能训练万亿参数的唯一原因。

3. 通信代价：三档分别多付多少#

切分不是免费的。反向必须先得到完整梯度才能更新，所以无论哪一档，每步都要做一次 reduce-scatter + all-gather（第 2 章讲过：这就是 ring AllReduce 的两个阶段，每卡搬迁量 2(P−1)/P⋅Ψ）。

档位 每步的集合通信 相对纯 DP
纯 DP / ZeRO-1 reduce-scatter + all-gather 1×
ZeRO-2 同上，但分片梯度需要额外一次 all-gather 才能凑齐 2×
ZeRO-3 前向 all-gather 参数、反向再 all-gather 参数、反向 reduce-scatter 梯度 3×

关键点是这个比例与 P 无关：ZeRO-3 的通信量始终是纯 DP 的 3 倍。实际实现用两个手段打掉这堵墙：通信与计算重叠，以及只在需要时 all-gather 当前层的参数（用完立刻释放）。

4. FSDP 是什么：把 ZeRO-3 做成框架原语#

FSDP（Fully Sharded Data Parallel，全分片数据并行）是 PyTorch 原生实现，思路与 ZeRO-3 同类但粒度不同：它把模型按单元拆开，每个单元的参数 flatten 成一个 flat parameter，单元计算前 all-gather、算完立刻释放，反向时再 all-gather，梯度用 reduce-scatter 回收。单元边界决定重叠质量——太小摊不掉启动延迟，太大压不住峰值显存。

选型可以记成三条：

  1. 单卡装得下完整模型状态、只想省显存 → ZeRO-1，零额外通信。
  2. 梯度本身是瓶颈 → ZeRO-2。
  3. 参数都装不下 → ZeRO-3 / FSDP，接受 3 倍通信与更多往返。

5. 常见坑#

  • 把 ZeRO-3 当成"无脑更快"：它省显存，但通信 3 倍、每层多两次同步；小模型上 ZeRO-1 往往更快。
  • 以为切了优化器状态就等于省下梯度：ZeRO-1 里梯度仍是每卡完整一份 2Ψ。
  • 在很小的 P 上期待线性收益：12/P 在 P=8 时只把 12 压到 1.5。
  • 忽略参数 all-gather 的往返次数：ZeRO-3 每层多一次同规模通信，α 按层数累加。

二、可运行代码示例#

纯 Python，不需要 GPU。第一段把账本算出来；第二段把三种并行/分片方案的通信量换成毫秒。

# ===== 示例 1：模型的显存账本 —— 固定部分与可切分部分 =====
# 混合精度 Adam 的账本（单位 B/参数）：参数 2 + 梯度 2 + 优化器状态 12（主权重 4 + 一阶 4 + 二阶 4）
BYTES = {"params": 2, "grads": 2, "master": 4, "m": 4, "v": 4}
WORLD = sum(BYTES.values())
G = 1_000_000_000

def n_params(vocab, hidden, layers, ffn=None):
    """Llama 式架构的参数量估算：每层 4 个注意力投影 + 3 个 MLP 矩阵，加嵌入与输出头。"""
    ffn = ffn or 4 * hidden
    return (4 * hidden * hidden + 3 * hidden * ffn) * layers + vocab * hidden + hidden

def per_param(P, zero):
    """每卡每个参数字节数。P 为同一个数据并行组内的卡数。"""
    if zero == 0: return WORLD                                  # 完全复制
    if zero == 1: return BYTES["params"] + BYTES["grads"] + (BYTES["master"] + BYTES["m"] + BYTES["v"]) / P
    if zero == 2: return BYTES["params"] + (BYTES["grads"] + BYTES["master"] + BYTES["m"] + BYTES["v"]) / P
    return WORLD / P                                             # 参数、梯度、优化器状态全切

print("混合精度 Adam 的固定账本：", BYTES, "合计", WORLD, "B/参数")
print("\n参数量估算（示例配置，不对应任何具体发布的模型）：")
cfgs = (("hidden 1024 / 24 层 / vocab 32k", (32768, 1024, 24)),
        ("hidden 4096 / 32 层 / vocab 32k", (32768, 4096, 32)),
        ("hidden 12288 / 96 层 / vocab 50k", (50257, 12288, 96)))
for name, cfg in cfgs:
    print(f"  {name:<34} {n_params(*cfg) / G:7.2f}B")

print("\n每卡每参数字节数（P 是数据并行组内卡数，越小越省）：")
for P in (1, 8, 64, 512, 4096):
    print(f"  P={P:<5} " + "  ".join(f"ZeRO-{z}: {per_param(P, z):7.3f}" for z in range(4)))

print("\n把 8.72B 模型塞进各组：每卡模型状态（GiB）")
N = n_params(32768, 4096, 32)
for P in (1, 8, 64, 512):
    row = "  ".join(f"ZeRO-{z} {N * per_param(P, z) / 2**30:8.2f}" for z in range(4))
    print(f"  P={P:<4} {row}")

print("\n把 232.55B 模型塞进各组：每卡模型状态（TiB）")
N2 = n_params(50257, 12288, 96)
for P in (64, 512, 2048):
    row = "  ".join(f"ZeRO-{z} {N2 * per_param(P, z) / 2**40:8.3f}" for z in range(4))
    print(f"  P={P:<4} {row}")

print("\n渐进口径：P→∞ 时 ZeRO-1 每卡 4 B/参数、ZeRO-2 每卡 2 B/参数、ZeRO-3 趋近 0")
for P in (8, 64, 512, 4096):
    print(f"  P={P:<5} ZeRO-1 {per_param(P,1):6.3f}  ZeRO-2 {per_param(P,2):6.3f}  ZeRO-3 {per_param(P,3):7.4f}")

# ===== 示例 2：把 ZeRO 三档的通信代价换成毫秒（α-β 模型，无 GPU） =====
ALPHA_US, BETA_GBPS = 5.0, 25.0          # 示例链路：跨机 25 GB/s 级 + 5 μs 单跳延迟
def t_ms(nbytes, rounds, alpha=ALPHA_US, beta=BETA_GBPS):
    """T = rounds·α + V/β（α、β 用示例值，请换成本机实测）。"""
    return (rounds * alpha + nbytes / (beta * 1e3)) / 1e3

def ring_bytes(psi, P):
    """ring AllReduce 每卡的收发量：2(P-1)/P × Ψ。"""
    return 2 * (P - 1) / P * psi

psi = 8.72e9 * 2                          # 8.72B 参数的 fp16 梯度
print(f"Ψ = {psi/2**30:.2f} GiB；ring 每卡收发 2(P-1)/P·Ψ，大 P 时封顶在 2Ψ")
plan = ((0, "纯 DP / ZeRO-1：reduce-scatter + all-gather = 2Ψ", 2, 64),
        (2, "ZeRO-2：梯度也切，额外一次 all-gather = 4Ψ", 4, 128),
        (3, "ZeRO-3：参数也切，前向/反向各 all-gather + reduce-scatter = 6Ψ", 6, 192))
for _, desc, mult, rounds in plan:
    V = mult * psi
    print(f"  {desc}")
    print(f"      总量 {V/2**30:6.2f} GiB，{rounds} 次往返 → 下界 {t_ms(V, rounds):9.1f} ms/步")
    print(f"      换 β=5 GB/s 的悲观链路 → {t_ms(V, rounds, beta=5.0):9.1f} ms/步")

print("\n对照：优化器状态放回 CPU（PCIe 单向 12 GB/s 示例值）")
opt, grad = 12 * 8.72e9, 2 * 8.72e9
print(f"  优化器状态 {opt/2**30:6.2f} GiB + 梯度 {grad/2**30:6.2f} GiB → "
      f"{t_ms(opt + grad, 4, beta=12.0):9.1f} ms/步（还要与计算抢这条链路）")

print("\nZeRO-3 相对纯 DP 的通信倍数（只看带宽项，与 P 无关）：")
for P in (8, 64, 512):
    print(f"  P={P:<5} {ring_bytes(psi,P)*3/(ring_bytes(psi,P)):.2f}×  "
          f"（{ring_bytes(psi,P)*3/2**30:.2f} GiB vs {ring_bytes(psi,P)/2**30:.2f} GiB）")

三、练习#

  1. 实现：把 per_param 改成支持"梯度也用 fp32 累加"的口径（16→20 B/参数），重算 8.72B 模型在 P=8 与 P=64 下的每卡账本，并指出哪一档受影响最大。
  2. 解释：为什么 ZeRO-1 与 ZeRO-2 的收益随 P 迅速饱和，而 ZeRO-3 不会？用第 2 节的两个公式（4+12/P 与 16/P）分别求"P 再翻一倍还能省多少"。
  3. 对比/验证：把示例 2 的 β 换成 300 GB/s（同机 NVLink 级），重算三档的通信下界；再算一遍 P=8 与 P=512 的差值，说明"什么时候加卡不再有用"。
  4. 思考：某任务用 ZeRO-3 后吞吐下降到原来的 60%，但显存从 70 GiB 降到 18 GiB。列出三种可能原因，并各给一个只靠日志/计时的验证方法。
