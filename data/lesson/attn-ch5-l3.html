训练与推理差异#

同一个 Transformer，训练时和推理时的"跑法"几乎完全不同。训练时它像个开了挂的学生：老师把正确答案（右移一位的真实目标）直接塞给它，它一次性、并行地算出整条序列每个位置的预测；推理时它却只能白手起家：从起始符开始，一个字一个字地吐，吐完还要把新字接回输入再来一遍。理解这两套流程——teacher forcing 与自回归生成——以及它们背后的效率差异（为什么训练快、推理慢，以及 KV cache 如何补救），是真正会用 Transformer 的分水岭。这一课就把这两条路径拆开讲透。

一、概念讲解#

1. 训练：teacher forcing，一次算完一整句#

假设要训练一个"把 abc 翻译成 xyz"的模型。目标序列是 [x, y, z, <eos>]。训练时，解码器的输入不是模型自己生成的猜测，而是"右移一位的真实答案"：

解码器输入: [<bos>, x, y, z]      ← 真实的、整体右移一位
预测目标:   [   x,   y, z, <eos>] ← 每个位置预测下一个真实词

这一步叫 teacher forcing（教师强制）——让"老师"（真实标签）牵着走，而不是让模型的错误预测滚雪球。它的巨大好处是：整条序列的所有位置可以一次性并行计算。因为因果掩码已经保证了位置 t 只能看见 1..t，而 1..t 这些 token 又都是已知的真实值，所以一个 forward 就能得到每个位置的 logits，一次反向传播就能更新所有位置的梯度。这就是训练能并行的根本原因。

2. 推理：自回归，一个 token 一个 token 地吐#

推理时没有"老师"了，只有模型自己。流程变成循环：

已生成 = [<bos>]
重复直到遇到 <eos> 或达到最大长度：
    用"已生成"序列做解码器输入
    取最后一个位置的输出，算出下一个 token 的概率
    采样/贪心地选出下一个 token，追加到"已生成"末尾

每一步都要做一次完整的前向，且只能基于已生成的前缀。所以推理天然是串行的：生成长度 L 的句子，就要跑 L 次前向。这也解释了为什么训练时一大段话几秒就"学"完，而推理时同样长度要一个字一个字地"等"。

3. 训练快、推理慢的根源与 KV cache#

训练并行、推理串行，速度差距来自两点：一是并行度（一次算全部 vs 一次算一步），二是重复计算。

在自回归推理里，第 t 步和第 t+1 步的输入只差一个 token，但朴素实现会把整个前缀的 Key、Value 重新算一遍。前缀越来越长，浪费越来越严重。KV cache 的思路是：把已经算过的 Key、Value 缓存起来，下一步只算新 token 的 K、V，然后拼接：

第 1 步: 计算 K_1, V_1，缓存
第 2 步: 只算 K_2, V_2，拼接成 [K_1 K_2]、[V_1 V_2]
第 t 步: 只算 K_t, V_t，拼接成 [K_1 ... K_t]、[V_1 ... V_t]

这样每一步的注意力只需要"新 Query 与全量 Key 点积"，省掉了对历史前缀的重复投影。KV cache 是让 LLM 推理提速的核心工程手段之一。代价是显存：要缓存所有层、所有头的历史 K/V。

4. 一张图看懂两条路径#

训练 推理
解码器输入 真实目标右移一位 已生成的前缀
计算方式 一次前向算完整句 每个 token 一次前向
并行度 高（全位置并行） 低（串行）
依赖真实标签 是（teacher forcing） 否
加速手段 并行训练 KV cache、批处理、投机解码

二、可运行代码示例#

用一个极简的"下一个词预测"模型，分别演示训练（teacher forcing）与推理（自回归）两条路径。模型本身故意造得很小，只为把流程看清楚。

import torch
import torch.nn as nn
import torch.nn.functional as F

# 极简模型：输入 token id 序列，输出词表 logits（真实 Transformer 见第 6 章）
class TinyNextWord(nn.Module):
    def __init__(self, vocab, d_model):
        super().__init__()
        self.emb = nn.Embedding(vocab, d_model)
        self.proj = nn.Linear(d_model, vocab)
    def forward(self, ids):
        return self.proj(self.emb(ids))   # (T, vocab)

torch.manual_seed(0)
VOCAB, BOS, EOS = 10, 0, 9
model = TinyNextWord(VOCAB, d_model=8)

# —— 训练：teacher forcing，一次前向得到整句所有位置的 logits ——
target = torch.tensor([1, 2, 3, 4, EOS])                 # 目标序列
decoder_input = torch.cat([torch.tensor([BOS]), target[:-1]])  # 右移一位，头部补 BOS

logits = model(decoder_input)                            # (5, vocab)
loss = F.cross_entropy(logits, target)                   # 每个位置预测下一个真实词
print("teacher forcing: 一次前向得到 5 个位置的 logits, loss =", round(loss.item(), 4))

# —— 推理：自回归，逐个生成，每次只看已生成的前缀 ——
model.eval()
generated = [BOS]
with torch.no_grad():
    for _ in range(6):
        logits = model(torch.tensor([generated[-1]]))    # 只看最后一个 token
        nxt = logits.argmax(dim=-1).item()
        generated.append(nxt)
        if nxt == EOS:
            break
print("自回归生成:", generated)

注意两处对比：训练版一个 model(decoder_input) 就覆盖了 5 个位置；推理版在循环里 model 被反复调用，每次只推进一个 token。

再看 KV cache 的核心思想（示意代码，重在"只算新 token、旧的部分复用"）：

d = 8
W_k = nn.Linear(d, d)
W_v = nn.Linear(d, d)

# 用一次随机序列模拟"已生成的前缀"，逐步演示缓存
prefix = torch.randn(3, d)                 # 已生成 3 个 token 的表示
past_k = W_k(prefix)                       # 第 1 次：算全部 3 个 K 并缓存
past_v = W_v(prefix)

new_token = torch.randn(1, d)              # 第 4 个 token 到来
k_new, v_new = W_k(new_token), W_v(new_token)

# 关键：不重算 prefix 的 K/V，只把新 token 的拼上去
k_full = torch.cat([past_k, k_new], dim=0) # (4, d)
v_full = torch.cat([past_v, v_new], dim=0)
print("缓存后拼接的 K 形状:", k_full.shape)  # (4, 8)，前缀部分零重算

真实实现里，缓存发生在每一层、每一个注意力头，且会随着推理逐步增长；这里只是把"复用历史、只算增量"的思想落地成代码。

三、练习#

  1. 把上面自回归循环里的 argmax 改成按概率采样（torch.multinomial），连续生成 20 个 token，观察输出与贪心结果的差异，思考"温度采样"的意义。
  2. 为什么 teacher forcing 训练时，模型可能在推理阶段表现骤降（"exposure bias"）？结合"训练看真实、推理看自己"解释，并列出至少一种缓解手段（如 scheduled sampling）。
  3. 推导 KV cache 的显存占用：设层数 L、头数 H、维度 d_model、已生成长度 t、batch B，写出缓存 Key 和 Value 各自占多少元素（忽略 batch 维度可先取 B=1）。
  4. 思考：交叉注意力的 K/V 来自编码器，编码器只需算一次，因此交叉注意力天然就"自带缓存"。为什么自注意力却需要显式的 KV cache？
