动态形状：guard、重编译与编译缓存#

第 1 课里那条 guard('T', '命中分支') 节点埋着一个麻烦：编译器为了生成高效代码，需要具体的 shape 与 dtype（决定 tile、向量化宽度、寄存器占用）；而推理服务的输入长度天然是变的——今天 128、明天 300，同一个函数就落进不同的编译假设。于是每个前端都要回答三个问题：这次编译结果在什么条件下才有效（guard）、条件不成立时怎么办（重编译）、结果存在哪里复用（缓存）。本课用纯标准库实现一个编译器式 shape 缓存，把"特化 / 桶化 / 符号形状"三种策略的编译次数与补零代价算成表。

一、概念讲解#

1. 什么时候必须按具体形状编译#

代码生成要做两类决定：循环怎么切（tile 大小、展开因子、向量宽度）和内存怎么算（要几个缓冲、偏移怎么算）。两者都依赖 shape 的具体值，而不仅是 rank。一个 (B,T) 的 GEMM，T=128 时适合的 tile 与 T=4096 时不同；T 是符号时，生成器只能写出"通用循环"，把 tiling 交给运行时的动态分支。

所以"支持动态形状"实际是"允许同一份编译结果服务于一批不同的具体形状"，前提是你敢为这批形状的共同点作保。这个"作保"就是 guard。

2. guard 的三件套#

组件 内容 例子
条件 一组关于输入的判断 dtype == float32、rank == 2、T % 16 == 0
key 由条件求值出的缓存标识 (float32, 2, 128)
动作 命中 → 直接跑；未命中 → 编译新版本并记入缓存 命中率决定"编译开销摊薄了几次"

粒度是设计变量：rank==2 & dtype==f32 粗而稳，命中率高但代码通用性差；T==300 细而准，命中率高时很划算，形状频繁变化时就把缓存放满了。guard 的粒度直接等价于"缓存条目数 × 单条代码质量"这个乘积的取舍。

3. 三种抓 shape 的策略#

策略 编译次数随时间 代价
按形状特化 每种 shape 一次，最坏 O(N) 缓存膨胀、重编译风暴
桶化 按档位取整，最多是档位数 补零浪费算力
符号形状 rank 相同就共用一份 代码通用性下降，运行时多分支

桶化的账可以手算：序列长度 [100,130,200,257,300]、档位取 2 的幂 {1…512} 时，被算成 128+256+256+512+512=1664 个元素，而真实需要 987 个——多算 68.6%。档位放到 {1024} 这一档，变成 5120 个，多算 418.7%。桶越粗，编译越少，算力浪费越大，这就是要拿实测数字调的那条曲线。

4. 重编译风暴与缓存上限#

最坏的情况不是"形状多"，而是"形状在两个值之间来回跳"。本课实验：100 次调用、两种形状交替、缓存上限为 1 时，每次调用都重编译（100 次）；上限放到 2 以上，只需 2 次编译。这正是深度学习框架里 recompile_limit 一类配置要防的场景——它通常不解决"编译慢"，而是把"抖动"变成显式的报错或警告，让使用者去固定形状。

5. 常见坑#

  • 以为 guard 是免费的：每次调用都要把 guard 条件求值一遍，条件集越大、"检查"本身越贵。
  • 把缓存上限当成性能旋钮：调大上限只是不报错，形状抖动时的编译开销照旧；真正的解法是固定形状或桶化。
  • 忽略 dtype/device 也在 guard 里：混用 fp32/fp16 或在 CPU/GPU 间搬张量，会各自触发一次编译。

二、可运行代码示例#

下面用纯标准库（本机 python3.10 与 python3.14 输出一致）实现一个 ShapeCache：mode 决定 key 怎么算，run() 模拟"一次调用"，统计编译次数、命中次数与补零浪费。

# ===== 动态形状：guard 命中率、桶化与"重编译风暴"的定量对照 =====
# 纯标准库实现（本机 python3.10 与 python3.14 输出一致）
import collections

# ---------- 1. 一个极简编译缓存：key = guard 的条件集合 ----------
class ShapeCache:
    def __init__(self, mode, buckets=None):
        buckets = buckets or (1, 2, 4, 8, 16, 32, 64, 128)
        self.mode, self.buckets = mode, tuple(buckets)
        self.cache, self.compiles, self.hits, self.pad_elems = {}, 0, 0, 0
        self.real_elems = 0

    def bucket(self, n):
        for b in self.buckets:
            if n <= b: return b
        return n                                     # 超出档位表就按原值算

    def key(self, shape):
        if self.mode == 'specialize':
            return shape                             # 精确 guard：每个形状一条
        if self.mode == 'bucket':
            return tuple(self.bucket(n) for n in shape)
        return ('*',) * len(shape)                   # 符号形状：同 rank 共用一个 key

    def run(self, shape):
        k = self.key(shape)
        eff = tuple(self.bucket(n) for n in shape) if self.mode == 'bucket' else shape
        elems, real = eff[0] * eff[1], shape[0] * shape[1]
        if k in self.cache:
            self.hits += 1
        else:
            self.cache[k] = elems; self.compiles += 1
        self.pad_elems += elems - real               # 只为补零多算的部分
        self.real_elems += real
        return elems

# ---------- 2. 三种策略跑同一串输入 ----------
SHAPES = [(8, 128), (8, 128), (10, 200), (16, 128), (8, 128), (12, 300), (10, 200), (24, 512), (8, 128)]
BIG = (1, 2, 4, 8, 16, 32, 64, 128, 256, 512)
print('=== 同一串 9 次调用（shape 见下），三种抓 shape 策略的账 ===')
print('  调用序列：', ' '.join(f'{a}x{b}' for a, b in SHAPES))
for mode, name in (('specialize', '按形状特化'), ('bucket', '桶化（2 的幂档位）'), ('symbolic', '符号形状（一个 key）')):
    c = ShapeCache(mode, BIG)
    for sh in SHAPES: c.run(sh)
    waste = c.pad_elems / c.real_elems if c.real_elems else 0.0
    print(f'  {name:<22} 编译 {c.compiles} 次（缓存 {len(c.cache)} 项），命中 {c.hits} 次，'
          f'为补零多算 {waste:+.1%}')

# ---------- 3. 重编译风暴：N 种形状逐个变，编译次数随 N 增长 ----------
print('\n=== 形状每次都不一样（最坏情况）时，编译次数的增长 ===')
for N in (1, 4, 16, 64, 256):
    shapes = [(4, 100 + i) for i in range(N)]
    line = f'  N={N:>3}  '
    for mode in ('specialize', 'bucket', 'symbolic'):
        c = ShapeCache(mode)
        for sh in shapes: c.run(sh)
        line += f'{mode:<11} 编译 {c.compiles:>3} 次   '
    print(line)

# ---------- 4. 桶化的补零浪费：档位越粗，省编译但费算力 ----------
def waste(buckets, sizes):
    tot = sum(next((b for b in buckets if b >= n), n) for n in sizes)
    return tot, sum(sizes)
for buckets in ((1, 2, 4, 8, 16, 32, 64, 128), (1, 2, 4, 8, 16, 32, 64, 128, 256, 512), (128, 512), (1024,)):
    pad, real = waste(buckets, [100, 130, 200, 257, 300])
    print(f'\n  档位 {buckets}：长度 {[100,130,200,257,300]} 被算成 {pad} 个元素，'
          f'真实需要 {real}，多算 {pad / real - 1:+.1%}')

# ---------- 5. guard 失败之后：缓存上限一到就"抖动"（compile → evict → compile） ----------
def steady_state(cache_limit, pattern=('a', 'b')):
    cache, compiled = collections.OrderedDict(), 0
    for step in range(100):
        k = pattern[step % len(pattern)]
        if k in cache:
            cache.move_to_end(k)
        else:
            compiled += 1
            if len(cache) >= cache_limit: cache.popitem(last=False)
            cache[k] = True
    return compiled
print('\n=== 100 次调用在两种形状之间交替，缓存上限的影响 ===')
for limit in (1, 2, 4, 64):
    n = steady_state(limit)
    note = '（上限放不下两个 key，于是每次都重编译）' if limit < 2 else ''
    print(f'  缓存上限 {limit:>2}：100 次调用共编译 {n:>3} 次{note}')

=== 100 次调用在两种形状之间交替，缓存上限的影响 ===
  缓存上限  1：100 次调用共编译 100 次（上限放不下两个 key，于是每次都重编译）
  缓存上限  2：100 次调用共编译   2 次
  缓存上限  4：100 次调用共编译   2 次
  缓存上限 64：100 次调用共编译   2 次

三张表各说一件事。第一张：同一串 9 次调用，特化与桶化都编译 5 次，但桶化多算 49.5% 的零——桶化的价值不在"少编译"，而在"形状连续变化时最多只编译档位数那么多次"。第二张是那个边界：形状每次都不重复时，特化是 O(N)（N=256 就编译 256 次），桶化被档位表兜住（228 次），符号形状恒定 1 次。第三张：档位从"2 的幂到 128"放宽到"单一 1024"，多算从 2.8% 涨到 418.7%——档位表就是"编译次数换算力浪费"的那个旋钮。最后一张表是工程现场最常见的坑：缓存上限为 1 时两种形状交替，100 次调用触发 100 次编译。

三、练习#

  1. 实现：给 ShapeCache 加第四种模式 bucket+shape——按档位建 key，但把真实 shape 也记进同一 key 的集合，命中时检查是否首次见到该精确 shape；统计这样能省下多少编译、又丢了多少命中。
  2. 解释：为什么"缓存上限调大"不能解决重编译风暴？在什么真实场景下形状会来回抖动（提示：变长序列 + padding 策略）？
  3. 对比/验证：把 SHAPES 换成连续变化的 64 个形状，重跑第二张表；解释 mode='bucket' 的编译次数为什么是 36 而不是 64。
  4. 思考：如果给一个 transformer 推理服务定编译策略，你会选符号形状 + 桶化中的哪一个组合？用本课的"编译次数 / 补零浪费"两组数字说明取舍。
