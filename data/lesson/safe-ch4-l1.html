监管与合规的技术含义：把合规要求翻译成可验证的系统属性#

这一节要解决什么#

前几章处理的是"这套系统会不会被打破"：威胁模型给了分母，注入与隐私给了机理，对齐给了条件保证，防护与红队给了纵深与覆盖度。这一章换一个方向，处理一个完全不同类型的问题：

当有人（监管方、客户、甲方、内部风控）要求你证明这套系统是可控的，你交得出什么？

这两类问题的差别值得先说清楚。安全问题是"对手在你不知道的地方做了什么"；合规问题是"你能否在别人指定的位置上，拿出别人能核对的东西"。一个系统可以很安全但交不出证据（防护做得好，但没人能复算它为什么安全），也可以交出一堆文件但完全不安全（模板填得很满，一条可判定的断言都没有）。本章处理的是后者的反面：把"要求"变成"可核对的系统属性"，再把属性变成"证据"。

本节的任务是把这句话做成可执行的三件东西：

 判定清单 + 证据格式 + 就绪度如何被算出来（含它的陷阱） ​

在这之前，先给本节的两条纪律，它们贯穿整章：

纪律一：不要凭记忆陈述法条。 法规的编号、生效日期、适用门槛、罚则金额都会变，而且逐条背诵法条不是工程能力。本节只处理"某类要求"的类型（要求你说明数据来源、要求你保留记录、要求你提供异议入口……），把篇幅全部放在技术侧怎么落地。凡涉及具体制度的地方，一律写成"以某类要求为例（具体以当地法条为准）"。

纪律二：区分可算的事实、行业惯例与推测。 全章用三级标注：

  • A 级：可算的算术或结构事实（本节里的碰撞概率、可复算率连乘、排队尾概率、集合交）；
  • B 级：行业惯例（有实践共识，但依赖组织与场景）；
  • C 级：推测——不得写成结论，只能写成"当前无法给出判别性检验"，并附上"什么观测能证伪它"。

本节的路线图：

§1 翻译问题合规不能被直接实现​​→§2来源/许可​​→§3可追溯/可解释​​→§4可申诉​​→§5留痕​​→§6清单+证据格式​​→§7边界​​

一、为什么"合规"不能被直接实现#

1.1 法规写的是结果义务，系统需要的是可判定的谓词#

一条要求通常长这样："处理个人信息应当具有明确、合理的目的，并应当与处理目的直接相关"（以这类表述为例，具体以当地法条为准）。这句话对人的行为有约束力，但它不是一个程序能执行的判定：

  • "明确"：明确是对谁明确？写在隐私政策里算明确，还是写进数据集的元数据里算明确？
  • "合理"：合理是一个规范判断，需要一个裁量者；
  • "直接相关"：相关性的度量是什么？谁来定义阈值？

工程上要做的第一步，是把它降级成一个可判定的谓词。降级的方式是固定的：把规范判断替换为"存在性 + 可核对性"。

"目的明确、合理、相关" ⟹ ⎩⎨⎧​存在字段 purpose 且非空存在字段 purpose 与 use 的映射表该映射表的每一次变更都有记录与签字​

注意这一步做了什么、没做什么：它没有让系统判断"目的合理"——那仍然是人（或监管方）的判断；它做的是保证当有人要判断时，判断所需的材料是齐的、可核对的。这就是本章标题里"技术含义"四个字的全部意思：

合规的技术含义 = 让一次规范性判断 所需的事实 随时可取、且不可被单方改写

1.2 翻译必须满足的四条规则#

把要求降到系统属性时，逐条检查四条规则。任何一条不满足，"这条要求已满足"这句话就不能说：

规则 判定问题 反例（看起来满足、实际不满足）
可判定 给定系统状态，能否在有限步骤内判真假？ "我们重视数据安全"
可取证 判定所依赖的事实，能否以结构化形式导出？ 口头确认、聊天记录里的"已确认"
可重复 换一个人、换一天，能否得到同一结论？ 依赖某位工程师的记忆
可追责 每个判定是否有具名主体与时间？ "团队决定"

这四条不是本节的发明，它们是审计这件事的最低要求：审计的动作就是"用一个不在场的人、只靠留痕、重放一次判断"。任何一项属性只要不能被不在场的人重放，它在审计场景里就不存在。

1.3 五类可验证属性#

把所有"某类要求"归纳一遍，会发现它们最终落在五类属性上。本节后面五节各处理一类：

属性 要求它在系统里意味着什么 最小证据形态
provenance 来源 每条数据、每个权重、每次评测都能说出它从哪来、依据什么许可 内容指纹 + 机器可读许可字段
traceability 可追溯 给定一次输出，能回到当时的输入、模型版本、策略版本 决策记录（含版本三元组）
explainability 可解释 给定一次决策，能读出它依据了哪些字段与哪条规则 结构化依据字段（不是自由文本）
contestability 可申诉 存在可执行的异议入口，且有时限与容量 工单系统 + 容量规划 + 处理记录
recordkeeping 留痕 上述四类都能被保住：完整、不可静默改写、可抽样核对 追加式日志 + 链式哈希 + 外部锚定

这五类之间有依赖：留痕是其余四类的载体。来源、可追溯、可解释、可申诉产生的所有事实，都要落到留痕里才有审计价值。所以 §5 会在五类里最后讲，但它的位置是"地基"。

1.4 一个先说的反直觉#

把"合规"做成工程属性之后，最容易犯的错误是把它做成打分表：给每条要求打分、加权、汇总成一个"合规就绪度"。这看起来很像工程，但 §6.3 会算出一件让人不舒服的事：分数的排序完全由权重决定，而权重不是技术量。 一份就绪度 0.85 的报告，如果没人能说出那 0.85 的权重从哪来，它和"我们很重视"是同一种陈述。

本节不反对打分——打分有用（它能暴露短板）；本节反对的是只交分数不交权重来源。

二、数据来源与许可：把"我们有权用"变成可核对的事实#

2.1 需要记录的三样东西#

"来源可说明"在工程上要落到三个字段组：

  1. 标识：这份数据是什么。必须是内容寻址的指纹，而不是自增 ID 或文件名。
  2. 许可：允许做什么。必须是机器可读的：允许用途集合、是否要求相同方式共享（share-alike）、是否要求署名、是否限制再分发。
  3. 链条：它是从哪些上游派生来的，经过哪些处理步骤。

理由很直接：自增 ID 和文件名都不具备跨系统识别能力。同一份语料在数据平台里叫 corpus_v3，在训练脚本里叫 s3://bucket/a/b.jsonl，在标注平台里叫 batch-2024-11——这三个名字之间没有可计算的对应关系，于是"这条数据用到了哪里"永远只能靠人对账。内容指纹把这件事变成一个可计算的等式：

同一份字节 ⟺ 同一枚指纹

2.2 内容指纹的位宽：一个必须算的数#

指纹不需要保密，它需要的是不碰撞。给定 N 个产物、指纹宽度 k bit，碰撞概率由生日问题给出：

pcollide​(N,k) ≈ 1−exp(−2k+1N(N−1)​)

代码块 1 把这张表算了出来（⚠️ 合成参数：N 与 k 是选定的网格）：

N 32 bit 48 bit 64 bit 96 bit
103 1.163×10−4 1.775×10−9 2.709×10−14 下溢
105 6.878×10−1 1.776×10−5 2.710×10−10 下溢
106 1.000 1.775×10−3 2.711×10−8 下溢
107 1.000 1.628×10−1 2.711×10−6 6.661×10−16

读数有三条：

  1. 32 bit 在 106 量级上已经等于必然碰撞（p=1.000）。把 CRC32 或"数据集的 md5 前 8 位"当标识，在真实数据量下等于没有标识。
  2. 64 bit 在 106 量级上还有 2.711×10−8，但到 107 就涨到 2.711×10−6——涨了 100 倍（N 只涨 10 倍，因为 p∝N2）。
  3. 反向问题的答案在代码里：要让 106 个产物的碰撞概率低于 10−9，需要

k > log2​−2ln(1−p∗)N(N−1)​ ⇒ k≥68.8 bit

k > log2​−2ln(1−p∗)N(N−1)​ ⇒ k≥68.8 bit

所以"用 64 位指纹"这个常见选择，在 106 产物、p∗=10−9 的目标下差 4.8 bit。这不是漏洞，是量级问题；能不能接受取决于碰撞的后果（把两条数据算成一条 vs 把一条算成两条）。这个判断必须写下来，而不是默认。

2.3 许可的传递性：只做交，不做并#

许可在合并时的语义是集合交：派生数据集能做的事，是全部上游都能做的事的交集。

uses(派生) = i⋂​uses(上游i​)

代码块 5 的算例（⚠️ 合成许可，仅用于演示语义）：

上游 允许用途 share-alike 要求署名
上游A {训练, 评估} 否 是
上游B {训练} 是 是
上游C {再分发, 训练, 评估} 否 否

合并三者后：允许用途 ={训练}，share-alike 变成必须（任一上游要求即传染），署名必须保留。于是"评估"和"再分发"都被挡住——尽管上游 A 和 C 都允许评估。

两条结论：

  • 合并越多来源，可用范围只会变小（两两组合里最大只剩 2 项用途，三个合并只剩 1 项）。
  • share-alike 与署名是"或"语义，允许用途是"与"语义。把这三者混在一个布尔字段里（"许可是否宽松"）必然出错。

2.4 边界#

  • 许可字段只能表达已经被法律意见翻译过的结论。工程不该、也无法从条款原文自动推出允许用途（那是 §1.1 说的规范判断）。
  • 内容指纹只能证明"同一份字节"，不能证明"这份字节是合法获得的"。后者是采购与合规流程的事。
  • 许可会变（上游改了条款、数据被撤回）。所以许可是需要版本化与复核期限的数据，不是一个常量表——这一点在 §6 的复核期限字段里落地。

三、可追溯与可解释：从"能查到"到"能判定"#

3.1 可追溯的最小粒度#

"单次输出可追溯到输入"听起来只需要一条日志，但要写清楚追到哪一层。至少有三种粒度，成本差一个数量级：

粒度 记录什么 成本量级 能回答的问题
请求级 请求 ID、模型版本、时间 最低 "那天模型是哪个版本"
上下文级 加上检索到的文档 ID、工具调用序列 中 "它当时看到了什么"
字段级 加上每条依据字段的值与规则命中 最高 "它为什么给出这个结论"

选择哪一级不是技术偏好，而是由"谁会在什么场景下问什么问题"决定的。 若业务里有申诉环节（§4），字段级通常是必需的：申诉人要的不是"系统当时看到了什么"，而是"系统凭什么这么判"。反过来，若系统只做内容生成、输出没有人身或财产后果，请求级可能足够。

这就是本节反复出现的那个结构：要求 → 属性 → 证据 → 成本。跳过"成本"这一步的清单，最后都会在实施时被砍成前两级。

3.2 可解释不是"可解释性研究"#

这里要挡住一个常见的偷换。学术意义上的"可解释性"（注意力可视化、显著性图、概念探针）回答的是"模型的内部机制大致如何"；合规场景要的"可解释"回答的是另一个问题：

合规要的可解释 = 「这次决策依据了哪些**被授权的字段**与哪条**书面规则**」

两者的差别是决定性的：

  • 前者是研究工具，输出是图与统计，不能判定真假；
  • 后者是记录，输出是字段与规则 ID，可以判定真假（"这条规则当时生效吗""这个字段当时的值是什么"）。

把注意力热图当成"可解释证据"交上去，会立刻遇到一个无法回答的问题：热图里的哪一部分是"依据"，哪一部分是"噪声"？ 没有阈值、没有版本、没有留痕，它不具备可核对性。

3.3 可解释字段要写成谓词#

可解释属性落地时，最小可用形态是三个字段：

decision_id        一次决策的唯一标识（与留痕共用）
inputs_used[]      被规则实际读取的字段名与值（不是全部入参）
rule_ids[]         命中的规则 ID 与版本（策略版本，见第 4 节 §5）
counterfactual     可选：若某关键字段取值改变，决策是否改变

第三项 counterfactual（反事实）值得单独说：它把"可解释"从"我读了哪些字段"升级为"这些字段中哪些是决定性的"。代价是每次决策要额外跑若干次判定（字段数 × 取值数）。这是一个明确的成本—信息量权衡，不是默认打开的功能。

3.4 边界#

  • 可解释不等于正确。一条规则被完整记录、命中的字段都正确，结论仍可能是错的——记录能让错误被发现，不能让它不发生。
  • 存在不可解释的结构：深度网络的内部计算。工程上的解法不是"解释它"，而是把决策点放到模型之外（模型只提供特征或分数，规则做决策），这样"依据"就有了书面形态。这个设计的代价是表达能力下降，取舍见 §6.4。
  • 可解释字段本身是高价值目标：它既包含输入数据，又包含规则，是泄露面。留痕与最小化在这里直接冲突，冲突的处理方式见 §7.2。

四、可申诉：入口、时限与容量#

4.1 四个必要条件#

"提供异议渠道"这句话要能被检验，必须同时满足四个条件，缺一即形式化：

  1. 可知：受影响的人能知道决策是自动做出的、且知道去哪提（这需要披露，见第 2 节）。
  2. 可提交：入口在时限内可达，且不要求申诉人具备他没有的信息（例如"请提供决策依据"——依据本应是你提供的）。
  3. 有时限：承诺一个处理期限，并能被测量（有开始时间、结束时间、结果）。
  4. 有约束力：处理结果真的能改变决定（可撤销、可更正、可补偿），而不是"已阅"。

第 4 条最容易被绕过：一个只能"记录意见"的入口，在审计里应当被判定为不构成申诉机制。判定它的方法很机械：查最近 N 次申诉里，有多少次导致了决定被改变或更正。 若这个数是 0，机制存在与否没有区别。

4.2 时限是容量问题，不是文本问题#

这是本节最实用的一条：时限能不能兑现，取决于处理能力与到达率，与文本写了几天无关。

把申诉处理看成一个队列（⚠️ 下面用 M/M/1 做粗模型：到达近似泊松、处理时间近似指数；真实分布不同，但结论的形状不变）。处理能力 μ 件/天、到达率 λ 件/天、利用率 ρ=λ/μ<1，则

E[Wq​]=μ−λρ​,P(W>t)=ρe−(μ−λ)t

4.3 申诉与留痕的耦合#

申诉处理必须能回到当时的决策记录，否则处理者只能重新判一次（这时系统已经变了，重判的不是同一次决策）。所以申诉机制对 §5 的留痕提出了两个硬要求：

  • 决策记录必须包含足够重建判定的信息：输入字段值、规则版本、模型版本（§3.1 的字段级粒度）；
  • 记录必须能在申诉时限内保持可读：保留期设置必须 ≥ 申诉时限 + 处理时长，否则会出现"申诉期内证据已过期删除"。

五、留痕：证据、完整性与不可否认#

5.1 一份证据必须能被别人复算#

留痕的质量不该用"记了多少条"来衡量，而该用别人能不能用这份记录重放你的判断来衡量。把一次可复算的证据拆开，需要八个字段：

P(可复算)=f∈F∏​(1−qf​) ≈ (1−q)∣F∣(各字段缺失率同量级时)

0.05 0.9500 0.7738 0.6634

0.20 0.8000 0.3277 0.1678

q=0.10 时，把字段从 5 个补到 8 个，可复算率从 0.5905 掉到 0.4305。这里有一个反直觉的结论：

A 级事实：字段更多 ≠ 证据更强。 若新增字段靠人工填写，每个字段都在乘一次缺失率；只有把缺失率压下去（自动采集）才能把可复算率提回来：q=0.05 时 0.663420，q=0.01 时 0.922745，q=0.001 时 0.992028。

工程上的正确做法因此不是"少写字段"（那会丢掉复算能力），而是把字段变成流水线的副产品。这条也是本节对"证据格式"设计的核心要求：字段必须是采集出来的，不是填出来的。

5.2 链式哈希与锚定窗口#

留痕的第二个要求是"不可被静默改写"。机制是链式哈希：每条记录包含前一条的哈希，

hi​=H(hi−1​∥recordi​)

于是改第 i 条必须重算其后所有记录的哈希。这个性质常被表述成"日志不可篡改"，但准确的表述是：

链式哈希 ⇒ 局部篡改 必须变成 后缀整体重写

它本身不提供不可否认性——一个能写日志的系统，通常也能重写整个后缀。要把重写变成不可能，需要外部锚定：定期把链尾哈希写到一个本团队改不动的地方。于是：

篡改窗口 = 一个锚定周期内的记录数

代码块 3 的读数（速率 1e4 条/天）：

锚定周期 窗口内可被整段重写的记录
1 天 104
7 天 7×104
30 天（速率 106/天） 3×107

锚定周期就是篡改窗口。 不做外部锚定的日志，在事后争议里只是一份自证材料——它的可信度不高于写它的人。这一条也说明了"留痕"与"审计"必须分开（§6 会用到）：留痕是数据基础设施，审计是独立核查。

5.3 抽样审计：存在性与总量#

有了留痕之后，核查方式通常是抽样。抽 m 条、篡改比例 p，至少命中一条的概率是

P(至少命中一条)=1−(1−p)m

p m（90% 把握） m（95%） m（99%）
0.05 45 59 90
0.01 230 299 459
0.001 2302 2995 4603
0.0001 23025 29956 46050

这里必须说清一件容易被混的事：

  • 抽到一条 ⇒ 存在篡改（这是存在性结论，p=0.001 要 2995 条样本才有 95% 把握）；
  • 抽不到 ⇒ 什么也不能说。抽 300 条、p=0.001 时命中条数期望只有 0.300——大概率一条都抽不到，而这不代表日志干净。

要估计篡改总量，必须随机抽样并给出比例的置信区间（例如抽 3000 条、命中期望 3.000），而不是"抽到一条就收工、抽不到就出无异常报告"。后者是本节最典型的伪证据形式之一。

5.4 留痕的最小字段集#

把上面几条合成一份可落地的记录格式（字段名是工程约定，不是规范要求）：

ts                 事件时间（单调时钟 + 墙钟，两者都记）
actor              主体（人 / 服务账号 / 系统任务）
action             动作类型（读 / 写 / 判定 / 导出 / 删除）
subject            对象（数据指纹 / 模型版本 / 决策 ID）
policy_version     当时生效的策略版本（第 4 节展开）
evidence{}         支撑本次判定的字段值（§3.3 的 inputs_used）
prev_hash          前一条的哈希
hash               本条哈希（覆盖以上全部字段）
anchor_ref         该条所属锚定周期的外部锚点标识（可为空，但必须能查到）

anchor_ref 是可选的，但"能否查到"不是可选的：一条没有锚点的记录，其可信度上限就是系统的自证能力。

六、判定清单与证据格式#

6.1 三元组：要求 → 属性 → 证据#

判定清单的每一条都写成三元组，缺一列就不算条目：

要求（规范语言，人写） 属性（五类之一） 证据（可导出的结构化事实）

R2 用途与许可可核对 provenance 机器可读许可字段 + 允许用途判定记录
R3 单次输出可追溯到输入 traceability 决策记录（请求 → 上下文 → 规则版本）
R4 决策依据可读出 explainability inputs_used[] + rule_ids[]（含版本）

这张表本身就是交付物。它的价值在于右列——右列空着的条目，等于没有实施。

6.2 证据强度：四档而不是两档#

"有/没有证据"是一个太粗的划分。本节用四档（这也是全章后面反复使用的分级）：

档 含义 判定方式
E0 只有声明 有人写了这句话
E1 有配置快照 能导出当时的配置
E2 有可重复检验 有脚本/查询，任何人可重跑并得到同一结论
E3 有独立复核 本团队之外的人复核过，且复核记录可查

E1 与 E2 的差别是整个体系的关节：配置快照说明"当时是什么样"，可重复检验说明"当时是这样、现在还能验证它曾经是这样"。审计要的几乎总是后者。

6.3 就绪度评分，以及它的陷阱#

把权重 wi​ 与证据强度 v(ei​)∈{0,0.35,0.75,1.00} 加权求和，得到就绪度

S=∑i​wi​∑i​wi​v(ei​)​

代码块 0 的两份"合规包"（⚠️ 合成权重）：同一份 8 条清单、同一个"全部满足"，打勾式包（4 条只有声明 E0）得 SA​=0.1837，证据式包得 SB​=0.8562，差 366.0%。

这个差距值得停一下：两个包在"清单满足情况"这一栏是完全一样的（都是 8/8），差别只在证据强度。若你的报告只写"8 条全部满足"，这两个包在纸面上无法区分。

再看分项弱点：证据式包里最弱的是 explainability（0.7500），因为"可解释"在多数系统里只落到一份声明——它没有被写成可判定的谓词（§3.2）。

最后是陷阱（代码块 6）：把每条要求从当前档提到 E2 的增量排序是

要求 权重 从 到 增量
R5 有可执行的异议入口 3.0 E0 E2 0.1125
R7 记录不可被静默改写 2.5 E0 E2 0.0938

R6 处理活动有完整记录 2.5 E1 E2 0.0500

排序完全由权重决定（所有条目都在补同一档）。也就是说：只要你给某个属性更高的权重，它就会出现在"该优先补"的位置——技术侧的边际收益计算无法告诉你权重该是多少。权重的来源是"违反这条的后果有多严重"，那是一个规范判断，必须由业务/法律给出，并显式写在报告里。

就绪度分数 + 缺席的权重来源 = 一个好看的数 = 可核对性

6.4 证据格式#

证据的最小可用形态（字段表在 §5.1 已给，这里给出一条证据的形状）：

{
  "requirement_id": "R3",
  "attribute": "traceability",
  "evidence_level": "E2",
  "subject": {"kind": "decision", "id": "d-8f3c…", "ts": "2026-09-23T10:00:00Z"},
  "claim": "该决策可追溯到当时的模型版本、策略版本与输入字段值",
  "check": {
    "kind": "replayable_query",
    "entrypoint": "audit/replay_decision.py",
    "inputs": ["model_sha256", "policy_version", "policy_sha256", "context_ids"],
    "expected": "reproduced_decision == recorded_decision"
  },
  "owner": {"team": "risk-eng", "accountable": "…"},
  "review_due": "2027-03-31",
  "refs": ["log://decisions/2026-09-23#d-8f3c"]
}

四个字段决定了它是不是一份"有用的"证据：

  • evidence_level：四档之一（§6.2）。没有它，"已满足"没有强度。
  • check.inputs + check.entrypoint：可复算的入口。若这一项不存在，expected 里的等式无法被任何人验证——那它就是 E0。
  • owner.accountable：具名主体，不是"团队"。
  • review_due：复核期限。没有期限的条目会静默腐烂；留痕、许可、风险都是会变的东西。

6.5 上线前审查的 gate 判据（与第 3 节的分工）#

本章第 3 节会专门讲治理机制（模型卡、风险登记册、审查与审计）。这里只留一个衔接点：本节产出的判定清单与证据格式，是上线前审查的输入。一个会拒绝的审查 gate，至少要能回答三个问题：

  1. 清单里哪几条是 E0/E1？谁签字接受这个强度？
  2. review_due 已过期的条目有多少？过期条目在审查里是否被当作不满足？
  3. 上次审查列出的条件，这一轮由谁验证完成？

第 3 节会把这三个问题做成 gate 的 entry/exit criteria。

七、边界与取舍#

7.1 证据不等于合规#

本节全程在做一件事：把"是否合规"的事实基础做实。但必须清楚边界：

本节交付 = 可核对性;合规 = 规范性判断

一份就绪度 0.86 的证据包，不构成"我们合规"的结论。反过来，工程能做到的最有价值的事，是让那次规范性判断变得便宜：判断者不需要飞过来访谈两周，只需要跑几个查询。

7.2 留痕与最小化的冲突#

留痕要记全部判定依据（§3.3 的字段级粒度），而数据最小化要求不保留超出必要范围的数据。这两者的冲突是结构性的，不是执行不到位：

  • 留痕字段里往往包含个人信息（输入文本、检索到的文档、被引用的记录 ID）；
  • 保留期越长、粒度越细，申诉与审计越可实现，泄露面与合规成本越大。

可行的处理方式有三条，都不是免费的：分级留痕（字段级只保留结构化摘要与哈希，原文短期保留）、分离存储（留痕与业务库分开、权限分离、只追加）、基于用途的保留期（不同类别记录用不同期限）。选择哪一条取决于"申诉时限"与"数据敏感度"，这是一个需要写下来的取舍。

7.3 打分会被优化#

一旦就绪度分数进入考核，被考核方会去优化分数而不是属性。三条可预期的退化路径：

  1. 只补权重高的条目（§6.3 的排序已给出激励）；
  2. 把 E1 包装成 E2（写一个只跑固定用例的"复算脚本"）；
  3. 证据字段由人工填，使可复算率按 (1−q)f 下降（§5.1）。

对 2 的判别方式很机械：换一个不在场的人、用当时的记录、独立重放一次。能重放就是 E2，不能就是 E1 或 E0。这不依赖证据自称的档位。

  要估总量，必须随机抽样并给出比例的置信区间，而不是抽到一条就收工：
      p=0.001、抽 m=3000 条：命中条数期望 = 3.000（足以估出量级）
      p=0.001、抽 m=300 条：命中条数期望 = 0.300（大概率一条都抽不到）

    训练    -> 允许

  数据集数量上去以后，人工读条款必然漏。

练习#

  1. （把要求降级成谓词） 取一条你所在领域的规范性要求（例如"应当保证数据的准确性""应当能够说明自动化决策的逻辑"）： （a）按 §1.1 的方式写它的"存在性 + 可核对性"版本，明确它替换掉了哪个规范判断； （b）按 §1.2 的四条规则逐条检查你的版本，指出哪一条最弱； （c）给出这条要求的证据形态，并标注它是 E0/E1/E2/E3 中的哪一档，说明理由。
  2. （指纹位宽） 你的数据平台有 5×105 个数据集版本，用 64 bit 指纹： （a）用 §2.2 的公式算出碰撞概率（用代码块 1 的网格插值或直接计算）； （b）若碰撞的后果是"两个数据集被当成同一个"，你能接受的最大碰撞概率是多少？据此算出所需位宽； （c）如果成本不允许加宽指纹，给出一个替代方案（提示：指纹 + 长度/字节数 + 来源三元组），并说明它为什么仍可能碰撞。
  3. （许可传递） 你的训练数据来自 4 个上游：两个允许"训练+评估"且要求署名、一个只允许"训练"且要求 share-alike、一个允许"训练+评估+再分发"不要求署名： （a）算出派生数据集的允许用途集合、share-alike 与署名要求； （b）如果你的产品需要"用模型输出再训练另一个模型"，这个用途落在允许集合里吗？为什么"用模型输出"这件事让问题变得比 §2.3 更难？ （c）给出一条能自动检测"用途越界"的检查（说明它读哪些字段、在哪个时点运行）。
  4. （可申诉容量） 你的申诉入口目前 μ=3 件/天、实测 λ=2.85 件/天： （a）算出平均排队时间与 P(W>14天)（用代码块 4 的模型）； （b）若业务量上涨 10%（λ 变成 3.135），队列会怎样？给出 30 天与 90 天的积压量； （c）给出两种应对方案（加人 vs 降低到达率），并各写出一条它们的副作用。
  5. （证据格式） 为 R7（记录不可被静默改写）写一条完整的证据 JSON（照 §6.4 的形状）： （a）填出 check 字段：入口是什么、输入是什么、期望的等式是什么； （b）说明这条证据的 evidence_level 为什么不能是 E2 而是 E3（或反之）； （c）写出它的 review_due，并说明这个期限由什么决定（提示：锚定周期的变更频率）。
  6. （就绪度与权重） 用代码块 0 的清单与权重： （a）若把 explainability 两条的权重从 2.0 提到 4.0，重算 SA​ 与 SB​； （b）解释为什么 SB​ 的增幅与 SA​ 的增幅不同； （c）写出你自己项目里 8 条要求的权重，并给出每一条权重的来源（一句话），然后回答：如果权重来源说不清，这份评分能用来做什么、不能用来做什么？

小结#

  • 合规不能被直接实现，只能被翻译。 翻译的固定动作是把规范判断替换为"存在性 + 可核对性"：不判断"目的合理"，只保证判断所需的材料随时可取、且不可被单方改写。翻译后必须过四条规则：可判定、可取证、可重复、可追责。
  • 五类可验证属性：来源、可追溯、可解释、可申诉、留痕，其中留痕是其余四类的载体。每类都要落到"最小证据形态"，否则它在审计里不存在。
  • "全部满足"这句话没有强度。 同一份 8 条清单、同一个"8/8 满足"，打勾式包（4 条只有声明）就绪度 0.1837，证据式包 0.8562，差 366.0%。
  • 证据强度分四档（E0 声明 / E1 配置快照 / E2 可重复检验 / E3 独立复核）。 E1 与 E2 的差别是关节：前者说"当时是什么样"，后者说"当时是这样、现在还能验证它曾经是这样"。
  • 内容指纹的位宽必须算：N=106、64 bit 时碰撞概率 2.711×10−8，107 时涨到 2.711×10−6（p∝N2）；要把 p∗ 压到 10−9，N=106 需要 ≥68.8 bit。32 bit 在 106 量级上 p=1.000。
  • 许可在合并时只做交，不做并：三个上游各有 1~3 项允许用途，交集只剩 {训练}；而 share-alike 与署名是或语义（任一上游要求即传染）。把三者压成一个"是否宽松"的布尔字段必然出错。
  • 字段更多 ≠ 证据更强：可复算率按 (1−q)f 连乘，q=0.10 时 8 字段只有 0.430467，q=0.001 时才回到 0.992028。杠杆是自动采集（把 q 压下去），不是字段数量。
  • 链式哈希本身不提供不可否认性：篡改窗口 = 一个锚定周期的记录数（104/天 × 7 天 = 7×104 条）。不做外部锚定的日志只是自证材料。
  • 抽样审计只能给存在性结论：p=0.001 要抽 2995 条才有 95% 把握命中一条；抽 300 条时命中期望只有 0.300——抽不到什么也不能说。要估总量必须给区间。
  • 时限是容量问题：μ=3 件/天、ρ=0.90 时平均排队 3.00 天，ρ=0.99 时 33.00 天、P(W>14天)=6.505×10−1；λ 只比 μ 高 20%（3.60）时，90 天积压 54 件。"有入口"与"权利可实现"是两句话。
  • 就绪度评分的排序完全由权重决定（R5 补到 E2 的增量 0.1125 排第一，因为它权重 3.0）。技术侧的边际收益算不出权重该是多少——只交分数不交权重来源的报告，与"我们很重视"是同一类陈述。
  • 本节交付物三件：① §6.1 的判定清单三元组表；② §6.2 的四档证据强度定义 + §6.4 的证据 JSON 形状；③ §6.3 的就绪度加权公式与它的权重陷阱说明。
  • 边界：证据不等于合规（工程只交付可核对性）；留痕与数据最小化的冲突是结构性的；一旦打分进入考核，分数会被优化（用"换人独立重放"来判别 E2 与 E1）。C 级五条只是待检验命题，不是结论。

下一节：本节把"要求"变成了"系统属性 + 证据"，但它留下一个刻意没有回答的问题：证据齐了之后，出了事算谁的？ 判定清单能告诉你"当时模型是哪个版本"，不能告诉你"这个版本的选择该由谁负责"。第 2 节处理责任与边界：把一次事故分解成必要条件的合取，用控制点与信息两种切分方式算出各角色（设计者 / 部署者 / 使用者）的边际贡献，并回答那个最容易被含糊过去的问题——"这是自动化决策、我们只输出了概率（或只给了建议）"能不能免除责任。论证的方向不是法律解释，而是三条可算的事实：决策函数 δ(p) 是系统的一部分（把概率确定化并不转移决策）、未校准的概率输出不能传递信息（p 与 p^​ 的对数损失比较）、以及"人审"在自动化偏差下的实际拦截率（a 与偏差系数如何决定有效准确率）。最后给出自动化决策的五级分级与每一级的门槛条件——申诉与回滚不是可选项，而是分级的定义的一部分。
