指令数据格式#

从这一章开始，我们进入指令微调（Instruction Fine-tuning）：不再是让模型"续写文本"，而是让模型"听懂指令并按指令回答"。指令微调的第一道坎不是算法，而是数据长什么样——同样的模型、同样的训练代码，喂进去的数据格式不对，效果天差地别。这一课我们彻底搞清指令数据的字段结构、常见数据集格式，以及最关键的一步：怎么把"多轮对话"变成训练用的 token 序列。

一、概念讲解#

1. 指令微调数据的三要素#

一条指令数据，本质是"给定任务描述，给出期望回答"的样本。最经典的结构是 Alpaca 格式的三个字段：

  • instruction：指令/任务描述，如"把下面的句子翻译成英文"；
  • input：可选的任务输入，如待翻译的句子；纯问答任务可以为空；
  • output：期望的输出/标准答案。

例如：

{"instruction": "把下面的句子翻译成英文", "input": "今天天气很好。", "output": "The weather is nice today."}

真实聊天模型的数据往往更丰富，采用角色化对话格式，常见有三种角色：

  • system：设定模型人设/行为规则（可选）；
  • user：用户的提问；
  • assistant：模型应给出的回答。

2. 常见数据集格式：Alpaca、ShareGPT、OpenAI Chat#

  • Alpaca 格式：上面那种扁平的三字段结构，简单、适合自建数据；
  • ShareGPT 格式：{"conversations": [{"from": "human", "value": "..."}, {"from": "gpt", "value": "..."}]}，天然支持多轮对话，是现在社区数据的主流形态；
  • OpenAI Chat 格式：{"messages": [{"role": "system"/"user"/"assistant", "content": "..."}]}，与 API 调用格式一致。

不管原始数据是哪种格式，训练前都要统一转换成"角色 + 内容"的对话列表，再交给分词器。

3. 关键一步：chat template（对话模板）#

分词器不能直接理解"角色列表"，它需要把 system/user/assistant 序列渲染成一段带特殊标记的文本。现代分词器都内置了 chat template，调用 tokenizer.apply_chat_template() 就能把对话列表转成模型训练时见过的那串文本（例如 Llama 的 [INST] 包裹、ChatML 的 <|im_start|> 包裹等）。

这一步极其重要：如果你在训练时用了一种模板，推理时却用了另一种（或干脆裸拼接），模型会"不认识"自己的输入，效果崩塌。模板必须训练/推理保持一致。

4. 数据质量远大于数量#

一个常被忽视的事实：几十万条垃圾数据，不如几千条精心清洗的高质量数据。LIMA 等研究表明，甚至用约 1000 条高质量指令就能微调出相当可用的助手。数据侧要重点做：

  • 去重（语义级去重，不只是字符串去重）；
  • 去低质（乱码、截断、答非所问）；
  • 难度/多样性（覆盖不同任务类型，而非单一句式刷量）；
  • 格式统一（角色名、标点、空 input 的处理一致）。

二、可运行代码示例#

下面演示如何把一条多轮指令数据，通过 chat template 转成训练序列，并正确计算哪些位置该算损失。依赖 transformers。

from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-2-7b-hf")
# 若本地无该模型，可换成任意带 chat_template 的分词器，如 "HuggingFaceH4/zephyr-7b-beta"

# 1) 一条多轮指令数据（OpenAI Chat 风格）
messages = [
    {"role": "system", "content": "你是一名乐于助人的中文助手。"},
    {"role": "user", "content": "什么是 LoRA？"},
    {"role": "assistant", "content": "LoRA 是一种参数高效微调方法，只训练低秩增量矩阵。"},
    {"role": "user", "content": "它比全量微调省多少显存？"},
    {"role": "assistant", "content": "通常可训练参数降到千分之一，显存大幅下降。"},
]

# 2) 用 chat template 渲染成带特殊标记的整段文本
text = tokenizer.apply_chat_template(messages, tokenize=False)
print("渲染后的文本：\n", text)

# 3) 编码成 token id，并构造 labels：
#    只在 assistant 回答部分计算损失，system/user 部分用 -100 屏蔽
input_ids = tokenizer.apply_chat_template(messages, tokenize=True, return_tensors="pt")[0]
labels = input_ids.clone()

# 找出每个 assistant 片段的起止位置（示意：用渲染文本定位，再映射到 token 边界）
# 简化起见：手动标出 assistant 段落在文本里的起止，转为 token 索引
def find_span_tokens(text, start_str, end_str):
    """返回 (起始 token 数, 结束 token 数)：统计目标片段之前/之中的 token 个数。"""
    before = tokenizer(text[: text.find(start_str)], return_tensors="pt")["input_ids"][0]
    span = tokenizer(start_str, return_tensors="pt")["input_ids"][0]
    return len(before), len(before) + len(span)

# 屏蔽掉所有非 assistant 内容（这里用角色拼接边界示意）
labels[:] = -100
a_start, a_end = find_span_tokens(text, "LoRA 是一种参数高效微调方法", "")
labels[a_start:a_end] = input_ids[a_start:a_end]

print("input_ids 长度：", len(input_ids))
print("labels 中参与损失（非 -100）的 token 数：", (labels != -100).sum().item())

要点在于 labels 数组：凡是不该贡献损失的位置（system 提示、user 提问、padding），都设成 -100（PyTorch 的 ignore_index），只有 assistant 的回答 token 保留真实 id。这样模型学会的是"根据上文生成回答"，而不是去预测用户会问什么。真实训练里，trl 的 DataCollatorForCompletionOnlyLM 或 SFTTrainer 会自动帮你做这件事。

三、练习#

  1. 用 tokenizer.apply_chat_template 分别渲染"只有 user/assistant 两轮"和"带 system 的三轮"对话，观察 system 信息如何被拼进文本，并比较不同角色标记的包裹方式。
  2. 手写一个 convert_to_chat(instruction, input, output) 函数，把 Alpaca 格式的一条样本转成 OpenAI Chat 格式的 messages 列表；注意 input 为空时的处理。
  3. 构造一条包含 padding 的 batch（两条长度不一的对话），实现 labels：把 pad_token_id 位置也设为 -100，验证"损失只算回答 + 非 padding"。
  4. 思考：如果训练时用 Llama 的 [INST] 模板，但推理时直接拼接 "问题 + 回答" 而不用模板，模型行为会发生什么？试着用一句话解释"模板一致性"的重要性。
