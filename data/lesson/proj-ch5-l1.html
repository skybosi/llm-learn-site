项目规划#

这是《AI 实战项目》的最后一章，也是你的毕业项目。前面四章分别练了结构化预测、RAG、LoRA 微调、部署与成本核算，这一章要求你把它们串成一个完整产品：从需求到数据、到模型、到部署、到上线，走完整闭环。做完它，你的简历上就有了最亮的一笔——"我自己从 0 到 1 做了一个能用的 AI 产品"。

一、目标与步骤#

1. 项目目标#

自选方向，做一个"能真实使用"的端到端 AI 产品，交付一套完整作品：可运行代码 + README + 架构图 + 成本/性能数据。方向不限定，但必须走完"需求 → 数据 → 模型 → 部署 → 上线"五步闭环，不能只训练一个模型就交差。

2. 三个参考方向（选一个，或自拟等价方向）#

方向 一句话描述 串起的前置技能 适合谁
A. 私有知识库 RAG 助手 上传你的文档，用自然语言问答，回答带引用来源 P8 RAG + P10 部署 想突出 LLM 应用能力
B. 领域问答微调助手 微调一个 7B 模型做客服/医疗/代码助手，并部署成服务 P9 LoRA + P10 部署 想突出模型训练能力
C. 线上推理服务 把开源 LLM 做成 OpenAI 兼容 API 服务 + 监控 + 压测 P10/P11 部署与工程 想走 AI Infra 方向

本课程以 方向 A（私有知识库 RAG 助手） 作为贯穿示例，因为它把 RAG、向量检索、LLM 部署、服务化、前端全串了起来，是"综合"最充分的一条线；其余两个方向在每节给出对应的替代做法。

3. 验收标准（毕业项目的"及格线"与"亮点线"）#

及格线（必须有）：

  • 产品能真实跑起来，走通"提问 → 检索 → 生成 → 展示"全链路；
  • 有 README（怎么跑、怎么用、技术选型理由）；
  • 有一张架构图（数据流从用户到模型再回来）；
  • 有一份成本/性能数据（显存、延迟、单次请求成本）。

亮点线（拉开差距）：

  • 有评测：不只"能回答"，还能量化回答质量（引用命中率/人工评分）；
  • 有迭代记录：记录"初版 → 优化 chunk → 换向量模型 → 换生成模型"每一改的收益；
  • 有上线：部署到云、别人能访问（哪怕是内网或试用链接）。

4. 五步闭环与里程碑#

把整个项目拆成 5 个里程碑，每个里程碑有明确产出：

里程碑 阶段 产出
M1 需求 用户画像、要解决的痛点、成功指标（如"80% 问题能命中文档并给对答案"）
M2 数据 文档集、切块策略、向量库建成、检索可跑
M3 模型 生成模型选型与部署（复用 P10 的 vLLM 部署）、RAG 编排完成
M4 部署 服务化（FastAPI）、容器化、接口可用
M5 上线 前端/入口、云上部署、成本与性能数据、README 收尾

二、需求与选型（规划的核心）#

1. 需求先行：先定义"成功"，再写代码#

动手前先回答三个问题（写进 README 的第一段）：

  • 给谁用：例如"考研学生 / 公司新员工 / 我自己"；
  • 解决什么：例如"在 200 篇复习资料里快速找到并引用原文回答"；
  • 怎么算成：例如"评测 50 个问题，引用命中率 ≥ 80%，平均回答延迟 ≤ 3 秒"。

没有成功指标的项目只是"演示 demo"，有指标才是"产品"。

2. 数据：从哪里来、怎么切#

  • 来源：你自己的私有文档（PDF/Word/Markdown），或一份开源文档集（如某技术手册、公开教程）。用真实文档，不用玩具数据。
  • 切块（chunking）：块太大检索不精、太小上下文丢失。先用"块 512 字符 + 重叠 64"起步，再按结果调优（这是 P8 的核心技能，也是后面"迭代记录"里的第一项优化点）。

3. 模型：检索用 embedding，生成用 LLM#

  • Embedding：把文档块转成向量，选中文友好的开源模型（如 BGE 系列 BAAI/bge-small-zh-v1.5 或 bge-m3），本地可跑、免费可控；
  • 生成 LLM：直接复用 P10 部署的 Qwen2.5-7B-Instruct（vLLM 服务），把"检索到的段落 + 用户问题"拼成 prompt 交给它生成。这样 P10 的成果直接被复用，是"技能串联"的体现。

4. 技术选型矩阵（自拟方向时按此表替换）#

环节 推荐方案 替代方案
文档解析 PyMuPDF / Unstructured 手工转 Markdown
切块 LangChain RecursiveCharacterTextSplitter 自写滑窗切分
Embedding BGE 系列（本地） OpenAI embedding API
向量库 Chroma（本地持久化） FAISS / Milvus
生成 Qwen2.5-7B + vLLM（P10 复用） llama.cpp / API
编排 自写检索+拼 prompt（轻量透明） LangChain / LlamaIndex
服务化 FastAPI Flask / vLLM 直接暴露
前端 简单 Web（HTML/JS）或微信小程序 Streamlit / Gradio
部署 Docker + 云服务器 本地跑

选型原则：每一层都要能说清"为什么选它"。例如"用自写检索而不用 LangChain，是为了少一层黑盒、更可控，也更好在面试里讲清原理"——这种"有理由的取舍"正是面试官想听的。

5. 成本预算（复用 P10 的算账能力）#

规划阶段先估一笔账：embedding 模型很小（几百 MB），本地 CPU 就能跑；生成模型用 7B AWQ，一张 24 GB 卡即可。若上云，月度成本 ≈ GPU 小时单价 × 运行时长 + 服务器/存储费用。把预算写进规划，上线后再对照真实账单，这就是"算清账"的延续。

三、规划阶段的代码骨架#

先搭项目骨架与"最小可跑"的检索原型，验证数据链路通不通，再谈完整实现。

# 项目目录骨架（下一课逐文件实现）
ai-knowledge-assistant/
├── data/                 # 原始文档放这里
├── src/
│   ├── ingest.py         # 解析文档 → 切块 → 向量化入库
│   ├── retrieve.py       # 根据问题检索 top-k 相关块
│   ├── rag.py            # 拼 prompt 调 LLM 生成回答（带引用）
│   └── serve.py          # FastAPI 服务
├── requirements.txt
├── Dockerfile
└── README.md

一个最小检索原型（先证明"问题能搜到正确文档块"，这是 RAG 成败的第一道关）：

# -*- coding: utf-8 -*-
# prototype.py —— 规划阶段的最小原型：验证"检索能否命中"
# 目标：先别接 LLM，先确认 embedding + 向量库 能搜到相关内容
import chromadb
from chromadb.utils import embedding_functions

# 用中文友好的开源 embedding（本地下载，可离线跑）
ef = embedding_functions.SentenceTransformerEmbeddingFunction(
    model_name="BAAI/bge-small-zh-v1.5"
)
client = chromadb.PersistentClient(path="./chroma_db")
col = client.get_or_create_collection("docs", embedding_function=ef)

# 塞入几条"文档块"（真实项目里由 ingest.py 从文件切出来）
chunks = [
    "考研英语：阅读理解先看题干再回原文定位，注意同义替换。",
    "线性代数：矩阵的秩等于其非零奇异值的个数。",
    "深度学习：过拟合时可用早停、正则化、数据增强缓解。",
]
col.upsert(
    documents=chunks,
    ids=[f"c{i}" for i in range(len(chunks))],
)

# 检索：问一个和"过拟合"相关的问题
q = "模型训练时验证集误差上升了怎么办？"
res = col.query(query_texts=[q], n_results=2)
print("问题：", q)
for doc, dist in zip(res["documents"][0], res["distances"][0]):
    print(f"  命中(距离{dist:.3f})：{doc}")
print("验收：若第一条命中了'过拟合'那条，说明数据链路基本打通。")

这一步的价值：用最小代价先验证检索质量。如果连向量检索都搜不对，后面接再好的 LLM 也白搭——这是 RAG 项目规划阶段就该排除的第一风险。

四、验收与复盘#

1. 本课验收（规划完成标志）#

  • 选定了产品方向，并写出用户、痛点、成功指标三句话；
  • 画出了技术选型矩阵，每一层能说清"为什么选它"；
  • 跑通了最小检索原型，确认"问题能搜到正确文档块"；
  • 估算了成本预算，立下了 5 个里程碑的产出清单。

2. 动手练习#

  1. 用一句话写清你的产品：给谁用、解决什么、怎么算成功。写不出来说明需求还没想清楚。
  2. 把你的文档集（哪怕只有 10 篇）丢进最小原型，人工抽 10 个问题测检索，统计"第一条结果就相关"的比例，作为检索基线。
  3. 换一个 chunk_size（如 256 vs 1024）重跑检索，观察命中率变化，初步体会切块对 RAG 的影响。

3. 复盘要点（规划阶段要避开的坑）#

  • 方向贪大：毕业项目要"小而完整"，不要"大而残缺"；先做通一条窄场景，再谈扩展；
  • 跳过成功指标：没有指标的"能跑"，面试时会被一句"那效果怎么样"问倒；
  • 纠结选型：RAG 用 Chroma + BGE + Qwen 这条链足够做出好作品，别在 LangChain vs LlamaIndex 上内耗，先跑通再优化。
