通信-计算重叠：梯度分桶、多流、分块#

"通信与计算重叠"常被说得像免费的午餐：改一个开关，通信就消失了。可 DDP 的 bucket_cap_mb 默认值是 25 MiB，而不是 1 MiB—如果桶越小越能重叠，为什么不干脆切成无穷多份？本课把重叠写成分段函数：算出每个桶何时就绪、通信何时开始、哪一段时间注定裸露。

一、概念讲解#

1. DDP 的分桶到底做了什么#

PyTorch 官方对 DDP 内部设计的描述可以直接当规格读：构造阶段，每个进程创建一个 Reducer，它把参数梯度组织成多个桶，一次归约一个桶；桶大小由 bucket_cap_mb 决定（官方默认 25 MiB）。参数进桶的顺序是大致反向的 Model.parameters() 顺序，理由是反向传播时梯度的就绪顺序大致也是这个顺序。同时，每个参数注册一个 autograd hook。

反向阶段：某个梯度就绪 → 对应 hook 触发 → 标记该参数可归约；一个桶里的梯度全部就绪 → Reducer 在这个桶上发起一次异步 allreduce（求均值）；所有桶都完成后才阻塞等待，结果写回 param.grad。这里有一条硬约束：所有进程必须以完全相同的顺序发起 allreduce，官方实现是靠"永远按桶下标顺序发起"保证的—顺序不一致会导致结果错误或 DDP 反向挂死。

2. 重叠的时间线：三个时刻决定一切#

把第 k 个桶记作 Bk​，就绪时刻 rk​（桶内最后一个梯度算完的时刻），通信时长

ck​=α+βsk​​

其中 sk​ 是桶字节数，α、β 沿用第 1 章的 α-β 模型。通信在独立流上串行推进，于是开始时刻 startk​=max(rk​,endk−1​)，结束 endk​=startk​+ck​，端到端

Te2e​=max(Tcompute​, endn−1​),裸露尾巴=endn−1​−Tcompute​

这个模型立刻给出三条结论：

  1. 能藏的只有"后面还有计算"的那部分。第一个桶最早启动，几乎全被藏住；最后一个桶的通信没有计算可遮，永远裸露—这就是尾巴效应。
  2. 桶越大，尾巴越长：尾巴 ≈ α+cap/β。
  3. 桶越小，α 累积越多：桶数 n 时至少多付 nα，而且每桶一次通信调用也有 CPU 侧开销。

3. 两种情形：桶大小没有全局最优#

示例模型的 48 层、每层 8 MiB 梯度正好给出两种相反的结论。计算受限时（示例 β=6 GB/s、纯反向计算 384 ms）：25 MiB 桶端到端 385.62 ms，通信 67.91 ms 里 66.29 ms（97.6%）被计算遮住，裸露 1.62 ms；把桶放大到不切分，尾巴涨到 67.16 ms，端到端 451.16 ms。通信受限时（示例 β=1.5 GB/s）故事反过来：小桶把通信尽量提前，反而更快（1 MiB 桶 384.75 ms vs 不切分 652.49 ms）。

4. 多流、分块：什么时候有用#

  • 多流：DDP 的通信本来就发生在通信流上，与计算流并行；TORCH_NCCL_HIGH_PRIORITY 让 NCCL 用高优先级流，减少计算 kernel 抢资源造成的抖动。但多流不改变尾巴：示例里计算受限时 1/2/4 条通信流端到端都是 385.62 ms；只有通信量远超计算量时（示例 β=0.6 GB/s）多流才有明显收益：696.89 ms → 418.74 ms。
  • 分块：NCCL 内核本身就把大消息切成缓冲流水，NCCL_CHUNK_SIZE 控制 ncclSend/ncclRecv 与 AlltoAll 过网的切块大小，官方提示增大它可以改善延迟受限场景的带宽。它是库内行为，不替代分桶。
  • static_graph=True：告诉 DDP 前反向图固定，Reducer 可以更早、更准地安排桶；图变化时它反而会出错。

5. 与梯度累积的交互#

梯度累积时每个 micro-batch 都做一次反向，如果每步都 allreduce，通信量乘以累积步数却毫无收益。正确做法是用 model.no_sync() 包住前 k−1 个 micro-batch 的反向，只在最后一个同步—这样"桶"的自然边界变成累积窗口，重叠只发生在最后一段；有效 batch 的换算在第 7 章。

6. 常见坑#

  • 把 bucket_cap_mb 调得极小：α 累积与 CPU 侧开销会把收益吃光。
  • 假设"梯度就绪顺序一定是参数逆序"：官方明确这个假设可能不成立，find_unused_parameters=True 还要遍历 autograd 图，额外开销不小。
  • 只调桶大小不看流：计算受限时桶大小的收益上限就是尾巴。
  • 累积训练忘记 no_sync()：通信量按 micro-batch 数翻倍。
  • 破坏 allreduce 顺序（不同 rank 走不同分支）：这是挂死与错误的头号原因。

二、可运行代码示例#

下面这段代码不需要 GPU：它把反向计算、分桶、异步 allreduce 排成一条时间线，扫桶大小并对比"串行"与"重叠"两种排法。

# ===== 把 DDP 的"梯度分桶 + 异步 AllReduce"排成时间线（纯 Python，无 GPU） =====
import numpy as np

L, PER_LAYER_MIB, CHUNK_MIB = 48, 8, 1   # 48 层，每层梯度 8 MiB，按 1 MiB 的参数块装桶
T_LAYER = 8.0                            # 每层反向计算时间 (ms)，示例值
ALPHA   = 0.05                           # 每次 AllReduce 的固定开销 (ms)，示例值
TOTAL_MIB = L * PER_LAYER_MIB
print(f"模型：{L} 层 × {PER_LAYER_MIB} MiB 梯度 = {TOTAL_MIB} MiB（fp16），"
      f"纯反向计算 {L*T_LAYER:.0f} ms，α={ALPHA} ms")

def bucketize(cap_mib):
    """DDP 的做法：按参数逆序装入桶，装不下就封口。桶的顺序 = 梯度就绪顺序。"""
    chunks = [CHUNK_MIB] * (TOTAL_MIB // CHUNK_MIB)     # 逆序：最后一个 chunk 最先就绪
    buckets, cur = [], 0
    for c in chunks:
        if cur and cur + c > cap_mib:
            buckets.append(cur); cur = 0
        cur += c
    if cur:
        buckets.append(cur)
    return buckets

def timeline(cap_mib, beta_gbps):
    """单条通信流：桶内梯度全就绪才启动；桶在通信流上串行，与后续反向计算重叠。"""
    buckets = bucketize(cap_mib)
    ready, acc = [], 0.0
    for b in buckets:
        acc += T_LAYER * (b / PER_LAYER_MIB)                 # 该桶最后一层的就绪时刻
        ready.append(acc)
    comm = [ALPHA + b * 2**20 / (beta_gbps * 1e9) * 1e3 for b in buckets]
    free, ends = 0.0, []
    for r, c in zip(ready, comm):
        free = max(r, free) + c; ends.append(free)
    ct = L * T_LAYER
    e2e = max(ct, free)
    return dict(nb=len(buckets), comm=sum(comm), compute=ct, e2e=e2e,
                tail=max(0.0, free - ct), hidden=sum(comm) - max(0.0, free - ct))

for beta, tag in ((6.0, "A：计算受限（β=6 GB/s 示例）"),
                  (1.5, "B：通信受限（β=1.5 GB/s 示例）")):
    print(f"\n场景 {tag}")
    print(f"{'bucket_cap':>10} {'桶数':>4} {'通信合计':>9} {'串行 e2e':>9} "
          f"{'重叠 e2e':>9} {'裸露尾巴':>9}")
    for cap in (1, 5, 25, 100, 10000):
        r = timeline(cap, beta)
        print(f"{cap:>8}MiB {r['nb']:>4} {r['comm']:>8.2f}ms "
              f"{r['compute']+r['comm']:>8.2f}ms {r['e2e']:>8.2f}ms {r['tail']:>8.2f}ms")

def streams(cap_mib, beta_gbps, ns):
    """ns 条通信流并行；每条流内部串行，桶按就绪顺序投给最早空闲的流。"""
    buckets = bucketize(cap_mib)
    ready, acc = [], 0.0
    for b in buckets:
        acc += T_LAYER * (b / PER_LAYER_MIB); ready.append(acc)
    comm = [ALPHA + b * 2**20 / (beta_gbps * 1e9) * 1e3 for b in buckets]
    free = [0.0] * ns
    for rd, cm in zip(ready, comm):
        i = int(np.argmin(free)); free[i] = max(rd, free[i]) + cm
    return max(L * T_LAYER, max(free))

print("\n通信流条数的影响（bucket_cap=25 MiB）")
for beta, tag in ((6.0, "β=6 GB/s（计算受限）"), (0.6, "β=0.6 GB/s（通信受限）")):
    line = "  ".join(f"{ns} 条 {streams(25, beta, ns):7.2f}ms" for ns in (1, 2, 4))
    print(f"  {tag:<20} 端到端：{line}")

三、练习#

  1. 实现：把 timeline 改成支持"桶内最后一个梯度所在的层"不同（即让某些层梯度更早就绪），观察尾巴与桶内就绪顺序的关系；给出"桶划分应该顺着梯度就绪顺序"的定量理由。
  2. 解释：为什么计算受限时把桶从 25 MiB 调到 100 MiB 反而更慢，而调到 1 MiB 只快了一点点？用 nα 与 cap/β 两项分别回答。
  3. 对比/验证：把示例里的 ALPHA 从 0.05 ms 提到 0.5 ms，重跑场景 A 的表，指出哪个桶大小变成最优；再解释真实系统里 α 变大可能来自什么（提示：通信调用次数、CPU 侧提交、跨节点排队）。
  4. 思考：一条训练流要在 8 卡上跑，反向计算 300 ms、梯度 400 MiB、链路有效带宽 50 GB/s。先算出"完全重叠后"的端到端下限，再说明要接近它，桶大小、通信流、算子顺序各需满足什么条件。
