角色分工与通信协议（共享黑板 / 消息传递 / 编排者）#

这一节要解决什么#

第 5 章把任务切成了依赖图。图上的节点总要有人做。最省事的答案是"同一个循环依次做"，但很多系统选了另一个答案：让多个执行者各自负责一部分，然后协作。这一章处理这个选择。

它要先拆掉一个默认假设：多智能体是能力的增强。第 1 章讲过误差累积，这里要讲的是它的一个变体 —— 把一个循环拆成多个协作的循环，会同时引入四类新成本：

总开销=Cwork​+搬运Ccomm​​​+协调Ccoord​​​+重复/返工Crework​​​+新的失效模式Cfailure​​​

其中 Cwork​ 是单执行者也要付的，所以"要不要多智能体"这个问题的实质是：后四项之和是否能被某种收益抵消。本章的三节依次回答：收益从哪来（第 3 节的上下文隔离）、成本怎么算（本节）、什么时候成本超过收益（第 2 节的负优化判据）。

这一节本身处理结构问题：谁负责什么（角色）、他们怎么交换信息（协议）。三种基本拓扑是：

① 共享黑板（blackboard）：状态由黑板持有，所有人读写同一份
② 消息传递（message passing）：状态由各自的上下文持有，靠消息交换
③ 编排者（orchestrator）：决策集中在一处，执行者只领任务交结果

这三种不是"同步 vs 异步"的区别，而是"谁持有状态"的区别 —— 这是本节最重要的一句话。

学完这一节你应该能回答：

  • "角色"到底是什么？"你是一个资深法务"这种设定为什么不算角色定义？
  • 黑板和消息传递的核心差别是什么？为什么黑板的正确形态是"追加式只读共享 + 单写者"？
  • 消息传递必须面对哪三种投递扰动？它们的处置分别是什么？
  • 编排者比"多一个 Agent"多做了什么？为什么它常常是最落地的形态？
  • 协议里必须携带哪些字段？缺哪个字段会导致哪种不可诊断的故障？
  • 三者的通信量随规模怎么增长？为什么全连接在 n 大时不可用？

一、角色分工的本质：分区，不是人格#

1.1 角色的四要素#

"你是这个团队的资深法务，请仔细审查合同" —— 这不是角色分工，这是提示词装饰。它没有约束任何东西：这个 Agent 能读什么、能写什么、做完的标准是什么，全都没有变。

工程意义上的角色定义是一次分区，必须显式给出四个要素：

要素 内容 不定义它会怎样
职责边界 负责产出什么对象（可命名的产物） 两个 Agent 都以为对方会做 → 责任稀释
可见信息 能读哪些状态/黑板条目/消息 要么信息不足（做错），要么读到不该读的（上下文污染、越权）
可执行动作 能调用哪些工具、能写哪些对象 能力越界（安全）或功能缺失（任务卡住）
完成判据 谁判定它做完、判据是什么 主循环必须反复介入问"好了吗"（第 2 节的协调成本爆炸）

"职责边界必须产出可命名的对象" 这一条尤其重要，因为它把"角色"从主观描述变成了结构：

角色重叠⟺∃ 两个 Agent 同时声明产出对象 x⟹重复工作（第 2 节）

反过来，如果两个 Agent 的产出对象集合不相交且并集覆盖依赖图的所有节点，那么分工是完备的。这是一个可以在启动前检查的条件（第 2 节的检测器就基于它）。

1.2 分区带来什么收益#

角色分区的收益不是"人多力量大"，而只有两样：

  1. 上下文隔离（第 3 节的主题）：每个角色只装自己需要的信息。这是最主要的正当理由。
  2. 权限隔离（第 7 节的主题）：不同角色持有不同工具与凭据，于是"能力上限"被结构限制，而不是靠提示约束。

注意这两样都不是"更聪明"。一个拆成三个角色的系统，它的判断质量上限不比单角色高 —— 它只是把信息负荷和权限范围分开了。所以如果一个任务既不需要隔离上下文、也不需要隔离权限，多角色的收益就是零，而成本为正。

1.3 角色划分与依赖图的对应#

角色划分应当由依赖图导出，而不是凭想象：

划分准则（按优先级）：
 1. 按"需要的信息集合"聚簇：读同一批信息的节点尽量归同一个角色
    → 减少跨角色通信（每次跨角色都要搬运，而搬运失真）
 2. 按"写集合"隔离：写同一外部对象的节点必须归同一个角色或加锁
    → 消除资源冲突（第 2 节）
 3. 按权限分级隔离：不可逆操作集中在少数角色里
    → 权限最小化（第 7 节）
 4. 不让一个角色同时承担"生产者"和"验证者"的同一产物
    → 否则验证退化为自评（第 5 章第 2 节）

第 1 条与第 2 条有时冲突（读的信息共享受欢迎，写同一对象则必须隔离），冲突时的处置是：按写集合切，通过只读快照传递信息。这也正是黑板拓扑存在的理由。

二、三种拓扑：谁持有状态#

2.1 共享黑板#

机制：存在一个所有 Agent 都能访问的共享结构（黑板）。每个 Agent 从黑板上读自己需要的条目，把自己的产出写回黑板。

正确形态是"追加式只读共享 + 单一写者/带版本的条件写"，三个要点：

  1. 追加式：条目一旦写入就不修改（要改就写新版本）。这与第 4 章"记忆是追加日志"同构，好处是可审计、可回溯、可重放。
  2. 单一写者：每个条目有唯一的写者身份。多个 Agent 同时写同一 key 是冲突，必须被拒绝。
  3. 带版本的条件写（CAS）：写的时候带上"我基于哪个版本"，如果黑板上的版本已经变了就拒绝。

写成功⟺expected_version=current_version

这三条一起解决了并发写的覆盖问题：两人同时基于 v1 计算，先写的变 v2，后写的因 expected=v1 ≠ current=v2 而失败，于是它必须重读再决策（而不是静默覆盖）。

黑板的失效模式：

失效 机制 处置
黑板成为巨型上下文 每个 Agent 都读全部条目 → 上下文爆炸 + 干扰项 读的时候切片：只给该角色该看的字段（2.3 的隔离视图）
脏读 读到别人正在写的中间状态 用版本号 + "条目完成后才可见"（两阶段发布）
无人清理 废弃条目永久累积，后加入的 Agent 读到过期信息 条目带 TTL 与显式失效标记（第 4 章的墓碑）
热点争用 一个 key 被频繁 CAS 失败，活锁 退避重试 + 上限后转编排者裁决

2.2 消息传递#

机制：没有共享结构，每个 Agent 持有自己的状态，通过收发消息协作。

它必须面对三种投递扰动，而且每一种都必须有处置：

扰动 后果 处置
丢失 工作静默消失（最危险：没人报错） at-least-once 投递 + 超时重发 + 确认（ack）机制
重复 同一个任务被执行两次 → 重复副作用 幂等键（第 3 章）+ 收方去重表
乱序 基于过期信息决策（"先收到撤销，后收到创建"） 消息带逻辑时钟/版本，过期消息被丢弃

"丢失"是最危险的，因为它是静默的：发送方以为对方收到了，接收方什么都没收到，整个系统没有任何一方认为出了问题。所以确认机制是消息传递的必要组成，不是可选优化：

可靠投递=at-least-once+ack+重发+幂等去重

注意 at-least-once 加上幂等去重，其效果等价于"恰好一次"（exactly-once）的业务效果，但不是"恰好一次投递" —— 投递永远是至少一次。这是第 3 章"幂等键是可靠性地基"在分布式场景的推广。

消息传递的失效模式：

失效 机制 处置
静默丢失 无 ack 引入 ack 与超时告警
重复副作用 重发 + 无去重 幂等键（必须）
顺序错乱 网络/并行导致 逻辑时钟 + 版本检查
环状等待 A 等 B 的消息，B 等 A 的 wait-for 检测（第 2 节）
邮箱爆满 某 Agent 被消息淹没 背压（backpressure）+ 消息过滤

2.3 编排者（orchestrator）#

机制：一个中心 Agent 决定"谁做什么、什么时候做"，把任务派给执行者、收集结果、决定下一步。

关键认识：编排者不是"多一个更聪明的 Agent"，而是把控制流集中化。它把 P2P 协商（任意两个 Agent 可能互相商量）变成星形（所有协调都经过中心）。这一个结构变化带来三个可保证的性质：

性质 为什么星形能保证
可判定 全局只有一个决策点，不会出现"两个 Agent 各自认为该做 X"
可审计 所有决策的因果链汇聚在一处（第 7 章的轨迹级评测受益）
可预算 预算集中管理：O(n) 个执行者共享一个 B，可以做全局分配（第 5 章第 4 节）

代价是单点：

编排者=单点瓶颈+单点失败+上下文爆炸风险

上下文爆炸风险最容易被忽视：如果编排者把每个执行者的全部过程都收进自己的上下文，它会比任何单个执行者更快地被塞满。所以有一条规定：编排者只保留摘要 + 句柄（第 4 章的引用），细节留在执行者的轨迹里，需要时再按句柄取。

编排者上下文⊇{目标,计划,每个子任务的摘要,产物句柄,预算与状态},⊇{子任务的完整过程}

2.4 三者的对照与混合#

共享黑板 消息传递 编排者
谁持有状态 黑板（共享） 各 Agent 自己 编排者（控制）+ 各 Agent（状态）
耦合度 松（时间解耦、空间解耦） 松（时间解耦） 紧（中心知道全局）
通信复杂度 O(读写次数) O(n2) 全连接 / O(n) 星形 O(n)
调试难度 中（黑板可完整回放） 高（消息轨迹要拼） 低（中心轨迹完整）
单点风险 黑板（可复制/分区） 无 编排者
最适合 信息共享密集、需要全局视图 流水线、异构部署、弱耦合 需要全局预算/审计/裁决

最常见的落地形态是"编排者 + 黑板"：编排者管控制流与预算，黑板管事实与产物的共享（避免把大产物在消息里搬来搬去）。这个组合同时拿到"决策集中"与"信息共享便宜"两个好处，代价是要处理黑板的一致性问题（2.1 的三条）。

2.5 通信成本模型#

消息数(n)=⎩⎨⎧​n−1(2n​)=2n(n−1)​O(k⋅n)​星形（编排者 fan-out/fan-in 一轮）全连接（任意两方都可能协商）黑板（k = 每个 Agent 平均读写轮次）​

n 星形 全连接
2 1 1
4 3 6
8 7 28
16 15 120
32 31 496

这不是理论担忧：如果每条消息平均 800 token（含上下文与产物摘要），n=16 的全连接一轮就烧掉 120×800≈96k token，而实际工作可能只需要 20k。这就是"通信占比"这个指标的意义（第 2 节的负优化判据会用它）：

通信占比=Cwork​+Ccomm​+Ccoord​Ccomm​​,超过约 40%≈该改拓扑或干脆别拆

一个反直觉推论：降低通信量最有效的手段不是"优化消息格式"，而是减少 Agent 数量或改用星形。因为消息数对 n 是二次的，而消息体优化只是常数因子。O(n2)→O(n) 的拓扑改变，比"把消息压缩 30%"的收益大一个量级。

三、协议：消息与黑板条目必须携带什么#

协议字段的设计标准不是"够用"，而是"缺了它会导致哪种故障不可诊断"。逐字段给出后果：

字段 作用 缺失导致的不可诊断故障
task_id / subtask_id 归属 无法判断"这条消息属于哪个任务"，多任务并发时轨迹搅在一起
sender / recipient 责任 无法追责、无法做权限校验
sent_at / 逻辑时钟 顺序 无法判断"这是不是过期信息"（乱序无法处置）
depends_on_version 因果 无法判断"这个结论是基于哪个版本的产物"（脏读/矛盾结论）
idem_key 去重 重复投递无法去重 → 重复副作用（第 3 章）
waiting_for 依赖等待 无法检测死锁（第 2 节）★
expects_reply_by / 租约 超时 无法打破"对端已经死了"的等待（假死锁）
expected_response 语义 无法判断"这个回复是否回答了我的问题"
budget_hint 成本 无法做分布式预算控制

倒数第四行（waiting_for）是本节留给第 2 节的关键伏笔：死锁检测的全部前提是"能构造出等待图"，而等待图只能从消息里的 waiting_for 字段重建。没有它，环只能靠"系统卡住了"这种事后观察来猜。

一个设计原则：协议字段应当在发送时由框架自动填充（而不是让模型生成）。因为模型生成的字段会漏、会不一致，而漏掉 idem_key 或 waiting_for 的后果是安全性与可诊断性的直接损失：

协议字段的可信度⟺由框架填充而非由模型生成

代码：三种拓扑的最小可运行模型#

下面的代码实现：(1) 追加式黑板（带版本 CAS、隔离视图）；(2) 消息总线（at-least-once + 丢失/重复/乱序扰动 + 幂等去重）；(3) 编排者（fan-out/fan-in + 集中预算 + 超时处置 + 只保留摘要与句柄）；(4) 通信成本模型。

"""
ch6-l1：共享黑板 / 消息传递 / 编排者 三种拓扑的最小可运行模型。

设计目标：把"谁持有状态"这个差别做成可运行的对照，
并证明协议字段（尤其 idem_key 与 waiting_for）不是装饰。
"""
import random
from dataclasses import dataclass, field


# ==================== (1) 黑板 ====================
@dataclass
class Entry:
    key: str
    writer: str
    version: int
    value: object
    visibility: set[str]                     # ★ 哪些角色可见（隔离视图）
    deps: dict[str, int] = field(default_factory=dict)   # 依赖的其它条目版本
    invalidated: bool = False


class Blackboard:
    """追加式只读共享 + 单写者 + 带版本的条件写。

    ★ 设计决策：写入不是"覆盖"而是"追加新版本"，旧版本保留。
      这让黑板天然可回放（第 4 章），也让"谁在什么时候基于哪个版本做了什么"可审计。
    """

    def __init__(self) -> None:
        self.versions: dict[str, list[Entry]] = {}
        self.log: list[str] = []
        self.cas_failures = 0

    def read(self, key: str, role: str) -> Entry | None:
        """隔离视图：角色看不见的条目对它就是不存在。"""
        for e in reversed(self.versions.get(key, [])):
            if e.invalidated:
                continue
            if role in e.visibility or "*" in e.visibility:
                return e
        return None

    def snapshot(self, role: str) -> dict[str, object]:
        """给某个角色的切片视图 —— 证明"隔离"是结构而不是口号。"""
        out = {}
        for k, vs in self.versions.items():
            e = self.read(k, role)
            if e is not None:
                out[k] = e.value
        return out

    def write(self, key: str, writer: str, value: object, visibility: set[str],
              expected_version: int, deps: dict[str, int] | None = None) -> tuple[bool, str]:
        """★ 带版本的条件写（CAS）：expected_version 不等于当前版本就拒绝。

        这是解决并发覆盖的关键：两人同时基于 v1 计算，后写的必须重读再决策，
        而不是静默覆盖前者的结果。静默覆盖是多智能体最难查的 bug 之一。
        """
        cur = self.versions.get(key, [])
        cur_ver = max((e.version for e in cur if not e.invalidated), default=0)
        if expected_version != cur_ver:
            self.cas_failures += 1
            self.log.append(f"CAS 拒绝：{writer} 想写 {key}（expected=v{expected_version}，"
                            f"current=v{cur_ver}）→ 必须重读再决策")
            return False, f"版本冲突：expected=v{expected_version} current=v{cur_ver}"
        e = Entry(key, writer, cur_ver + 1, value, visibility, deps or {})
        self.versions.setdefault(key, []).append(e)
        self.log.append(f"{writer} 写 {key}=v{e.version}")
        return True, f"ok v{e.version}"


# ==================== (2) 消息总线 ====================
@dataclass
class Message:
    msg_id: str
    sender: str
    recipient: str
    task_id: str
    body: dict
    idem_key: str
    clock: int                              # 逻辑时钟（判断乱序）
    depends_on_version: int = 0
    waiting_for: str | None = None          # ★ 死锁检测的唯一依据（第 2 节）
    expects_reply_by: float | None = None


class MessageBus:
    """at-least-once 投递 + 三种扰动 + 收方幂等去重。

    ★ 设计决策：把"丢失/重复/乱序"做成显式可注入的扰动，而不是靠祈祷。
      只有能被注入的故障才能被测试（第 7 章的可复现评测集也是同一原则）。
    """

    def __init__(self, drop_rate=0.0, dup_rate=0.0, reorder=False, seed=0) -> None:
        self.drop_rate, self.dup_rate, self.reorder = drop_rate, dup_rate, reorder
        self.rng = random.Random(seed)
        self.inbox: list[Message] = []
        self.delivered: list[Message] = []
        self.applied: dict[str, int] = {}        # idem_key -> 次数（去重表）
        self.dropped = 0
        self.duplicated = 0

    def send(self, msg: Message) -> None:
        if self.rng.random() < self.drop_rate:
            self.dropped += 1
            return
        copies = 2 if self.rng.random() < self.dup_rate else 1
        if copies == 2:
            self.duplicated += 1
        for _ in range(copies):
            self.inbox.append(msg)
        if self.reorder:
            self.rng.shuffle(self.inbox)

    def deliver_all(self, apply_fn) -> list[tuple[Message, str]]:
        """投递并按 idem_key 去重。★ 重复投递不会重复执行副作用。"""
        out = []
        for m in self.inbox:
            self.delivered.append(m)
            if m.idem_key in self.applied:
                self.applied[m.idem_key] += 1
                out.append((m, f"去重：{m.idem_key} 第 {self.applied[m.idem_key]} 次投递，跳过执行"))
                continue
            stale = [d for d in self.delivered
                     if d.recipient == m.recipient and d.clock > m.clock]
            if stale:
                out.append((m, f"★ 乱序：已收到更新的 clock={stale[0].clock}，丢弃 clock={m.clock}"))
                continue
            self.applied[m.idem_key] = 1
            out.append((m, apply_fn(m)))
        self.inbox = []
        return out


# ==================== (3) 编排者 ====================
@dataclass
class WorkerResult:
    worker: str
    ok: bool
    summary: str
    handle: str
    tokens: int
    cost: float


class Orchestrator:
    """星形 fan-out / fan-in：控制流集中，上下文只保留摘要 + 句柄。

    ★ 设计决策：编排者**不接收** worker 的完整过程，只接收 (summary, handle)。
      否则编排者会比任何 worker 更快地被上下文撑爆 —— 这是编排者拓扑最常见的塌方方式。
    """

    def __init__(self, budget: float, timeout: float) -> None:
        self.budget = budget
        self.timeout = timeout
        self.ctx: list[dict] = []             # 只放摘要与句柄
        self.ledger: list[WorkerResult] = []
        self.log: list[str] = []

    def dispatch(self, plan: list[tuple[str, float, bool]], actual: dict) -> list[WorkerResult]:
        """plan: [(worker, est_time, will_timeout)]；actual: worker -> (summary, handle, tokens, cost)"""
        out = []
        for worker, est_time, will_timeout in plan:
            if est_time > self.timeout or will_timeout:
                self.log.append(f"✗ {worker} 超时（est={est_time} > timeout={self.timeout}）"
                                f" → 编排者决定：重派给备用 worker 或降级")
                # 编排者只记录"超时事件"，不把 worker 的过程拉进来
                self.ctx.append({"worker": worker, "status": "timeout", "summary": "未完成"})
                continue
            summary, handle, tokens, cost = actual[worker]
            if cost > self.budget - sum(r.cost for r in self.ledger):
                self.log.append(f"✗ {worker} 会超总预算 → 拒绝派发（集中预算的价值）")
                continue
            r = WorkerResult(worker, True, summary, handle, tokens, cost)
            self.ledger.append(r)
            self.ctx.append({"worker": worker, "status": "ok",
                             "summary": summary, "handle": handle})
            out.append(r)
        return out

    def join(self) -> dict:
        """fan-in：用句柄而非内容做汇总。"""
        return {"子任务数": len(self.ledger),
                "产物句柄": [r.handle for r in self.ledger],
                "摘要": [r.summary for r in self.ledger],
                "总成本": round(sum(r.cost for r in self.ledger), 2),
                "编排者上下文条目": len(self.ctx),
                "★ 注意": "编排者上下文里没有 worker 的完整过程，只有摘要与句柄"}


# ==================== (4) 通信成本模型 ====================
def comm_cost(topology: str, n: int, per_msg_tokens: int = 800,
              rounds: int = 1, read_write_rounds: int = 3) -> dict:
    """★ 设计决策：把消息数写成 n 的函数，用来破除"加 Agent 就更强"的直觉。

    星形 O(n)、全连接 O(n²)、黑板 O(k·n)。
    结论：降低通信量最有效的手段是**改拓扑或减 Agent 数**，而不是优化消息体。
    """
    if topology == "star":
        msgs = rounds * (n - 1)
    elif topology == "mesh":
        msgs = rounds * n * (n - 1) // 2          # 无向对：C(n,2)
    elif topology == "blackboard":
        msgs = rounds * read_write_rounds * n
    else:
        raise ValueError(topology)
    return {"topology": topology, "n": n, "messages": msgs,
            "tokens": msgs * per_msg_tokens,
            "相对星形倍数": round(msgs / max(1, rounds * (n - 1)), 2)}

七处关键设计决策：

  1. Blackboard.write 是带版本的条件写（CAS），不是覆盖。这是 2.1 里"静默覆盖"的唯一结构性解法：两个 worker 同时基于 v1 计算，后写的会被拒绝并被迫重读再决策。演示里 comparator_B 第一次被拒、重读后成功 —— 这就是正确处置。
  2. Blackboard.snapshot(role) 实现按角色的切片视图。演示里 extractor 看不到 finance 写的 secret_fee。这一条把"上下文隔离"和"权限隔离"从提示词里的请求变成结构约束 —— 看不到就是看不到。
  3. Entry.visibility 与 Entry.deps 分别承载"谁能读"与"我基于哪些条目的哪个版本"。后者是 3.x 协议表里 depends_on_version 的落地，缺了它就无法判断"这个结论是基于哪个版本的产物"，也就无法解释两个 Agent 得出矛盾结论的原因。
  4. MessageBus 把丢失 / 重复 / 乱序做成可注入的扰动。这是刻意的：只有能被注入的故障才能被测试，而"丢失"这种静默故障如果不在测试里出现，就永远不会被发现（第 7 章可复现评测集同理）。
  5. MessageBus.deliver_all 的去重表按 idem_key 索引。演示里同一条消息投递 2 次、副作用只执行 1 次 —— 这就是 at-least-once + 幂等去重 = 业务上的"恰好一次"。注意去重的是收方，而键由发方（框架）填充。
  6. Message.waiting_for 在数据结构里显式存在。本节不用它，但它必须现在就有 —— 第 2 节的死锁检测只能从消息流里的这个字段重建等待图。协议里省掉一个字段，代价是一整类故障变成"不可诊断"。
  7. Orchestrator.ctx 只存 (worker, status, summary, handle)，而演示刻意打印了 编排者上下文条目 与"没有 worker 的完整过程"。这是 2.3 那条规定的代码化：编排者是星形拓扑最容易塌方的地方，而塌方方式就是把自己的上下文变成所有 worker 过程的垃圾场。

小结#

  • "多智能体"的收益只有两样：上下文隔离（第 3 节）与权限隔离（第 7 节）。它不是"判断力相加"。所以当任务既不需要隔离上下文也不需要隔离权限时，多角色收益为零、成本为正 —— 这正是第 2 节"负优化判据"的出发点。
  • 角色分工的本质是分区，不是人格。四要素：职责边界（产出可命名的对象）、可见信息、可执行动作、完成判据。工程上可检查的完备性条件是：产出对象集合两两不相交且并集覆盖依赖图的全部节点。
  • 三种拓扑的核心差别是"谁持有状态"，不是同步/异步。共享黑板 → 黑板持有；消息传递 → 各 Agent 自己持有；编排者 → 控制流集中、状态仍在各 Agent。
  • 黑板的正确形态是"追加式只读共享 + 单写者 + 带版本的条件写（CAS）"。写成功⟺expected_version=current_version。CAS 失败不是错误，而是一次被拦下的静默覆盖。它的失效模式是黑板变成巨型上下文（所以必须给角色切片视图）。
  • 消息传递必须面对三种扰动：丢失（静默，最危险 → 必须 ack + 超时重发）、重复（→ 幂等键去重）、乱序（→ 逻辑时钟 + 版本检查）。可靠投递=at-least-once+ack+重发+幂等去重；at-least-once + 去重给出"恰好一次的业务效果"（投递本身永远做不到恰好一次）。
  • 编排者不是"多一个 Agent"，而是把控制流集中化（P2P → 星形）。它买到可判定、可审计、可预算；代价是单点瓶颈/单点失败/上下文爆炸风险。所以规定：编排者只保留摘要 + 句柄，不收 worker 的完整过程。
  • 协议字段的设计标准是"缺了它会导致哪种故障不可诊断"。其中 idem_key（防重复副作用）与 waiting_for（死锁检测的唯一依据） 最关键。原则：协议字段的可信度⟺由框架填充而非由模型生成。
  • 通信成本：星形 O(n)、全连接 O(n2)、黑板 O(kn)。n=16 的全连接一轮就是 120 条消息。反直觉推论：降低通信量最有效的手段是改拓扑或减 Agent 数，不是优化消息体（后者只是常数因子）。用"通信占比"衡量，超过约 40% 就该动结构。

下一节：拓扑与协议选好了，但多智能体运行时会出现三类它特有的病：冲突（两个 Agent 改同一对象或对同一事实结论不同）、重复（职责重叠或消息重发导致重做）、死锁（互相等待成环）。第 2 节要把它们做成可检测的，并给出"什么时候多智能体是负优化"的判据。
