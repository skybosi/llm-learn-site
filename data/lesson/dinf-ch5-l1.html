服务化形态与请求生命周期：七环节的延迟预算与"层数买到了什么"#

这一节要解决什么#

第 4 章结束时，整门课的账已经闭环了：并行怎么拆（第 1 章）、batch 与 KV 怎么调度（第 2 章）、通信走在哪根线上（第 3 章）、要几个副本、给谁先跑、坏了怎么办（第 4 章）。但那份闭环里有一个被刻意省略的前提：

请求从客户端到 GPU 之间，**没有中间环节**

第 2 章的 TTFT= 排队 + prefill，第 4 章的 ρ=λ/(Rμ)，都把"一个请求到达服务"当成一个不需要建模的事件。真实的推理服务不是这样：

客户端 → 网关(接入/鉴权/限流) → 路由(选实例) → 调度器(排 batch) → 执行器(GPU)
                   ↑ 每多一个环节，就多一笔固定成本、一次排队机会、一条失败路径

于是第 4 章算出来的那些数会遇到一个新问题：它们算的是"执行器里"的账，而线上测到的是"端到端"的账。两者的差全部落在这些中间环节上。 这一节就把这个差算清楚，并回答四个问题：

① 一次请求到底经过哪些环节？每个环节各自能加多少延迟（含分位）？
② 网关 / 路由 / 调度 / 执行器的职责边界应该切在哪？切粗切细各付什么？
③ 层数、跳数、连接复用怎么换成可用性与容量？它们分别进哪个不等式？
④ 逐层分位与端到端分位的关系是什么？为什么"逐层 p99 相加"是错的预算做法？

一、请求生命周期的七个环节#

1.1 先把环节列全：分成五组#

不用一张架构图，用一个必须串行的清单。判据是：这一步没做完，下一步能不能开始？不能，就是一个环节。

组 环节 谁负责 典型量级 与负载的关系
A 接入 TLS 握手 / keep-alive / 会话 网关 0.3 ms（复用）～ 20 ms（新建 mTLS） 与 req/s 线性（不复用时）
B 鉴权 令牌校验 / 配额检查 / 计费打点 网关 0.1～1 ms 线性，但可本地化（见 §2.3）
C 路由 选实例（一致性哈希 / 负载感知）/ 元数据查询 路由器或网关 0.3～3 ms 弱相关；故障时会放大（见 §5.3）
D 排队 网关自身排队 / 调度器排队（等 batch 位或 KV 位） 网关、调度器 0～数百 ms 强非线性，是 p99 的唯一来源
E 执行 prefill + 首 token（TTFT 的"实数部分"） 执行器 5～30 ms 弱相关（batch 大时变慢）

这张表的用法：A/B/C 是固定成本（可预算、可压），D 是排队成本（不可压，只能改 ρ），E 是第 2-4 章算过的东西。把 D 与 E 混在一起是服务化账目最常见的错。

1.2 每一环节的延迟为什么是"固定 + 排队"两部分#

对任意一个环节 i，它的耗时可以写成

ti​=服务时间si​​​+排队等待wi​​​​

其中 si​ 由实现决定（常数或随 batch 缓变），wi​ 由该环节的利用率 ρi​ 决定。用 M/M/1 做最小模型（第 4 章用过同样的口径）：

Pr{wi​>t}=ρi​e−(μi​−λi​)t⟹wip​=μi​−λi​ln(ρi​/(1−p))​(ρi​<1)

三个直接读出来的结论：

  1. 等待分位对 p 是对数：p 从 0.99 提到 0.999，ln 里分子只涨 ln10=2.3，所以分位涨 2.3 倍 —— 这就是第 4 章"百分位税"的另一种写法。
  2. 等待分位对 (μ−λ) 是倒数：余量减半，分位翻倍。ρ 从 0.60（μ−λ=20）走到 0.90（μ−λ=3.33），余量掉 6 倍，分位涨 6 倍。
  3. 服务时间只加常数，等待时间加乘数：这就是为什么"优化执行时间"在低负载下有效、在高负载下几乎无效（§3 会给算例）。

这张表要说三件事：

第一，逐层 p99 相加不等于端到端 p99，而是它的上界。 本节数据：248.3 ms vs 218.9 ms（1.13×）。工程含义是双重的：

  • 用它做预算 → 偏保守（安全，但会多买机器）；
  • 用它做故障归因 → 错。因为"所有环节同时踩中 p99"不是 p99 事件，而是一个概率极低的联合事件。p99 的真实形态是"某一层踩中尾部 + 其余层在均值附近"。

第二，p50 由固定成本主宰，p99 由排队主宰。 固定成本（前三个环节 + 批组装 + 执行）之和是 21.1 ms，而端到端 p50 是 25.0 ms —— 固定成本解释了 84%。但到 p99 时，调度排队一项就占 67.8%。所以：

动 si​ (kernel、精度、算力)压 p50​​与动 ρi​ (并发位、限流、副本)压 p99​​是两把不同的旋钮

第三，尾部放大倍率本身是一个可测的指标。 表里"路由"的 p99/p50 是 10.12×，比"执行"的 2.74× 高得多，但它的绝对值只有 3.42 ms。所以排序时必须用"占端到端 p99 的比例"，不能用放大倍率（放大倍率是给"哪一层最不稳定"用的，见第 5 章第 4 节）。

二、职责切分：网关 / 路由 / 调度器 / 执行器#

2.1 四层各自的不可替代职责#

切分的原则只有一条：谁持有做这个决定所必需的状态，谁就做这个决定。

决定 必需状态 天然归属 放到别处的代价
拒绝谁（准入） 全局配额、当前在飞数 网关（或独立限流器） 放执行器 → 拒绝时已经付了建连与路由成本
送给哪个实例 实例健康、负载、KV 缓存亲和 路由器 放网关 → 网关被状态污染，扩缩容时状态迁移
这一批放哪些请求 每实例的 batch/KV 余量、优先级 调度器（每实例一个） 放路由器 → 需要全局视图，延迟随集群规模涨
这一 token 怎么算 权重、KV、kernel 执行器 ——

注意第二行与第三行的区别：路由器只回答"去哪台机器"（一次决策，几微秒），调度器回答"这台机器上先算谁、和谁一起算"（每 step 一次决策）。前者是无状态近似（一致性哈希 + 健康检查），后者是必须精确（batch 与 KV 都是硬约束）。把它们合成一层会导致：路由决策的粒度被调度周期绑死（要么路由太慢，要么调度太粗）。

2.2 为什么网关要"薄"：一个可算的判据#

网关每加一个处理步骤（改写 prompt、做内容审核、拼装工具调用），它的服务时间 sgw​ 就涨，而网关是所有请求的必经之路（乘数效应）。设网关有 ngw​ 个副本、每副本服务率 μgw​，则网关侧的排队分位是

wgwp​=ngw​μgw​−λln(ρgw​/(1−p))​,ρgw​=ngw​μgw​λ​

判据（"这一步该不该放网关"）：把它放网关带来的全局服务时间增量为 Δs，放到执行器只影响 ρexec​。当

∂sgw​∂wgwp​​⋅λ>∂sexec​∂wexecp​​⋅λ即(ngw​μgw​−λ)2λ​>(Cexec​−λ)2λ​

时，放网关更贵。代入本节数据（ngw​μgw​=1200、Cexec​=50）：

(1200−30)21​=7.3×10−7≪(50−30)21​=2.5×10−3

差了 3400 倍。所以判据是反的直觉的：网关的余量通常远大于执行器的余量，同样 1 ms 的服务时间增量，放在执行器上对端到端 p99 的伤害是放在网关上的 3400 倍。

正确读法：这不是"网关可以随便加东西"，而是"网关的预算要用绝对延迟卡（如 p99 ≤ 5 ms），执行器的预算要用利用率卡（如 ρ≤0.6）"。两个环节的成本结构不同，所以约束的形式也不同。

2.3 鉴权为什么必须本地化：一个容量判据#

令牌校验如果每次请求都远程调用鉴权服务，就多一跳网络（2α≈0.5 ms）+ 一个失败域。本地化（把公钥与配额缓存在网关进程内）的代价是一致性延迟：密钥轮转后最坏 Tttl​ 秒内旧令牌仍被接受。

判据是"额外一跳的容量成本 ≤ 缓存不一致的风险成本"：

每秒多付的网络时间λ⋅2α​​≤每秒的缓存维护成本Tttl​1​⋅ngw​⋅mkey​​​

本节口径（λ=30、α=0.25 ms、ngw​=8、mkey​=64 KiB、Tttl​=300 s）：左边 =15 ms/s，右边 =1.7 KiB/s。左边压倒性更大，所以本地化是明确正确的。真正的约束不是成本，而是轮转时的撤销语义：要求"立刻撤销"的场景（封禁、超额）必须走一个带版本号的短 TTL + 推送机制，而不是把 Tttl​ 调到 0（那等于取消缓存）。

3.2 层数买到的是什么：三笔账#

买到 量化的收益 代价
独立扩缩 网关与执行器的扩缩比例解耦：网关 CPU-bound（μ 随核数线性），执行器 GPU-bound（μ 随卡数线性）。合成一层时两者被同一个副本数绑死 每层固定成本 1.21 ms

关键的三条读法：

  1. 固定成本是确定的、可预算的（+3.62 ms 分摊到 3 层），但尾部代价测不出来：本节 n=400000 的蒙特卡洛里，端到端 p99 的差（4.8 ms）与固定成本同量级 —— 因为排队方差把真正的尾部差异吞掉了。加层不改变排队强度，只增加"排队机会"，而 p99 对机会数不敏感（它只关心最坏那一次）。
  2. 所以层数的尾部代价要用最坏路径去估：budgetp99​≥∑i​tip99​⋅(1−重叠率)。重叠率的经验值取决于各环节的独立性；完全相关（同一台机器）时重叠率接近 0，完全独立时端到端 p99 会明显低于逐层相加（本节 218.9 vs 248.3，重叠率约 12%）。
  3. "层数"和"跳数"不是一回事。同一层内部可能是同进程函数调用（0.01 ms），跨层可能是跨机 RPC（0.5 ms + 一条失败路径）。§5 单独算跳数。

3.3 什么时候该合并：一个反例#

"网关 + 路由"在下列条件下适合合并：集群实例数 NR​≤ 单机可维护的哈希环规模（约 103），且不需要跨可用区路由。合并后省掉 0.34 ms + 一次失败路径，但扩缩容时哈希环变化会同时影响接入（网关重启 → 全部后端连接重建）。判据：

NR​⋅∂NR​∂（一致性哈希的迁移量）​=NR​Nkeys​​≤网关每秒可重建的连接数×Tdrain​

本节口径（Nkeys​=8192 个 KV 前缀块、NR​=8 → 迁移 1024 个、网关需重建 1024 条后端连接、每秒可建 20000 条）→ Tdrain​=51 ms。结论：小集群下可以合并；当 NR​ 涨到 64 时迁移 128 个（更少），但网关重启时的入口连接重建量会变成主导。所以正确的形态是：

网关无状态化⇒路由有状态化（环外置）⇒两者可分层部署而不必合并​

四、一次请求的完整走法：把七环节写成一个函数#

把 §1 的模型写成一个可执行的流水线（下面代码的第 (1)(2) 段），得到的逐层数字就是 §1.3 / §1.4 的表格。这里先把"读法"说清：

① 端到端 p50 = 25.0 ms   ← 固定成本 21.1 ms + 调度排队均值（≈ 4 ms）
② 端到端 p99 = 218.9 ms  ← 固定成本贡献 21.1 ms，调度排队贡献 204.5 ms 的"单层分位"

一个必须记住的换算：把调度队列的 p99 从 204.5 ms 压到 50 ms，需要的不是"快 4 倍的 GPU"，而是把 ρ 从 0.60 降到约 0.20（μ 从 50 提到 150）：

w0.99=μ−λln(ρ/0.01)​:ρ=0.60,μ=50⇒204.7 ms;ρ=0.20,μ=37.5⇒76.9 ms

等等 —— ρ 降到 0.20 需要 μ=150，此时 w0.99=ln(0.2/0.01)/120=2.996/120=25 ms。所以"压 p99"的成本是"把服务率提到 3 倍"，而"压 p50"的成本是"服务时间降 30%"。 这两个成本的比就是尾部税的另一种形式。

4.1 为什么调度器要"每实例一个"#

如果调度器是全局单点，它必须持有所有实例的 KV/batch 状态，而状态的新鲜度受限于心跳周期 Thb​。设调度周期 Tstep​=10 ms、心跳 Thb​=100 ms，则调度器看到的余量最多过时 100 ms —— 在这段时间里它会把请求派给已经满载的实例，造成假性超卖。超卖率的量级是

超卖率≈Tstep​Thb​​⋅实例容量每周期未上报的容量变化​=10100​⋅Cinst​Cinst​⋅Phb​​=10Phb​

其中 Phb​ 是"心跳间隔内实例负载变化的比例"。Phb​=1% 时超卖率 10%。所以调度器必须靠近执行器（同进程或同机），而路由器可以是全局的（它只需要"去哪台"，不需要"还有多少"。）

4.2 批组装窗口：4 ms 买到什么#

批组装窗口是故意引入的等待（见下面代码里 批组装(等待窗口) 的 U(0,4) ms）。它的收益是让 batch 更大（第 2 章的摊销逻辑），代价是 p50 加 2 ms（均匀分布的均值）。判据：

Δ吞吐收益=f(BW)−固定成本摊销vsΔ延迟=BW/2

本节口径：BW=4 ms 让 batch 从 12 涨到 18（+50%），TPOT 从 8.6 降到约 7.9 ms（摊销）；换来的 p50 是 +2 ms、p99 是 +1.96 ms。这是一个明确的划算交易，但注意：

批组装窗口对 p50 加 BW/2，对 p99 加 BW（上界）⟹TTFT 预算紧时 BW 是第一个该调的旋钮​

三条读法：

  1. n=6 把 q=10−3 放大到 5.99×10−3（6 倍），年不可用从 17.5 小时变成 52.4 小时 —— 这已经吃掉一个"三个九"预算的大半。
  2. 重试能救，代价是流量：k=3 把失败率压 6 个数量级，但进入系统的请求量变成 λ(1+q+q2) 倍。用第 4 章的稳定判据：λ(1+q+q2)<μ。q=10−2 时是 1.0101λ —— 重试把容量判据的左边放大了 1%。
  3. 重试必须幂等。LLM 推理天然幂等（同样输入同样输出，除非采样；采样时用种子保证幂等），但计费与副作用（工具调用）不幂等。所以架构上要区分"重试推理"（可重试）与"重试副作用"（不可重试，必须用去重键）。

5.2 连接复用：0.35 ms 的两种命运#

复用次数 每请求握手 CPU 占 1 ms 网关预算 并发连接 连接表内存
1 0.350000 ms 35.0000% 7200 56.2 MiB
100 0.003500 ms 0.3500% 7200 56.2 MiB
10⁴ 0.000035 ms 0.0035% 7200 56.2 MiB
10⁶ 0.000000 ms 0.0000% 7200 56.2 MiB

0.35 ms 的 mTLS 握手，不复用时占网关预算的 35%，复用 10⁴ 次后是 0.0035%。 代价是连接表：由 Little 定律，稳态连接数 =ngw​⋅λ⋅Thold​=8×900×1=7200 条，按每连接 8 KiB 内核缓冲算 56.2 MiB —— 在网关的预算里可以忽略。

长连接不是优化项，而是"让建连成本不进入关键路径"的前提​

边界：连接复用把"建连成本"从每请求变成每连接，代价是粘性。三个具体后果：(a) 负载均衡变成"连接级"的，一个长连接上的突发流量会全打到同一个后端（需要用 HTTP/2 多路复用 + 权重或 L4 负载均衡修正）；(b) 后端重启时必须优雅关闭（drain），否则长连接上的在飞请求会失败 —— 这正是第 3 节的主题；(c) 空闲连接要保持（keep-alive 探测），否则中间设备会静默断开。

5.3 故障时的路由放大#

路由环节在正常时是 0.34 ms，但它有一个隐藏的尾部：当某个实例不健康时，路由的失败检测延迟（心跳超时 Thbfail​）会把请求送到坏实例，产生 qroute​=Thbfail​/Thb​ 的额外失败。把这一项代入 §5.1：

qeff​=qnet​+qroute​,qroute​=Thb​Tdetectfail​​

Tdetectfail​=3 s、Thb​=1 s（连续 3 次心跳丢失才判死）、实例故障率 1/天 → qroute​≈3/(86400/1) 换算到"故障期间"的那一小段窗口……准确的写法是"每秒处于误判状态的期望请求比例"：

qroute​=λNdead​⋅Tdetectfail​⋅λ/NR​​=NR​⋅Tbetween​Ndead​⋅Tdetectfail​​

本节口径（NR​=64、每实例每天故障 1 次、Tbetween​=86400 s、Tdetectfail​=3 s）：qroute​=3/(64×86400)=5.4×10−7 —— 比 qnet​=10−3 小 3 个数量级，不是主要项。但把故障率换成"每天 100 次滚动重启"（第 3 节的场景），qroute​ 涨到 5.4×10−5，就开始进入可用性预算。

六、取舍与边界#

  1. "端到端 p99"必须固定口径：是"等待 + 服务"（sojourn）还是只看"等待"？本节全部用 sojourn（含服务时间），第 4 章第 3 节区分过这一点（闭式算等待、蒙卡算逗留，差一个服务时间）。口径不同，p99 差 20% 以上。
  2. M/M/1 是每环节的最小模型，不是全部：多副本环节应换 M/M/c（第 4 章的 Erlang-C），有批处理的环节服务时间接近确定性（CV²→0），此时尾部比指数尾更瘦，本节的 wgwp​ 是保守估计。而真实到达有突发（CV²>1），尾部更胖。两种偏差方向相反，所以工程上取区间。
  3. "逐层 p99 相加"可以当上界，不能当预算：本节的 1.13× 是在"各环节独立"的假设下测出来的；如果各环节共享同一台机器（CPU 争抢、同一块网卡），尾部正相关，端到端 p99 会逼近逐层相加。判据是同机率 πsame​：overlap≈1−πsame​。
  4. 环节的划分影响可观测性：本节把"网关排队"和"调度排队"分成两个环节，因为它们属于不同的资源（网关 CPU vs 执行器并发位），修法不同。如果把它们合成"排队"一项，就失去了"该加 CPU 还是加副本"的判据。
  5. 跳数不是越少越好：把网关与执行器合并能省 0.5 ms 与一条失败路径，但会导致"网关 CPU 尖峰直接变成 TTFT 尖峰"。判据是资源争抢的耦合度：合成后两者的峰值是否重叠（网关的峰值在请求到达处，执行器的峰值在 token 生成处，通常错开）。
  6. 重试只在幂等且有余量时成立：第 4 章的重试放大判据（λ(1+q+q2)<μ）在这里第一次有了具体的 q —— 它是跳数与单跳失败率的函数，不是经验值。

"""第 5 章第 1 节：服务化形态与请求生命周期 —— 把"一次请求经过哪些环节"算成延迟预算。

纯标准库。五块：

  - 分位是**端到端**的分位；每层的"尾部放大"指该层 p99 与它自己 p50 的差
  - 排队用 M/M/1 抽样（P(W>0)=ρ，W|W>0 ~ Exp(μ-λ)），与第 4 章的 Erlang 闭式同源
  - 所有打印值单位统一为 ms
"""
import math
import random

# ---------------- 一、七环节的延迟模型 ----------------
# (环节, 固定 p50 ms, 处理时间 CV²：0 表示常数)
STAGES = [
    ("接入(TLS/keep-alive)", 0.30, 0.0),
    ("鉴权/配额(本地令牌桶)", 0.20, 0.0),
    ("路由(一致性哈希+元数据)", 0.60, 1.5),
    ("网关排队(M/M/1)", 0.00, 1.0),
    ("批组装(等待窗口)", 2.00, 0.0),
    ("调度排队(M/M/1)", 0.00, 1.0),
    ("执行(首 token)", 8.60, 0.25),
]

LAM_GW, MU_GW = 900.0, 1200.0        # 网关自身：λ=900 req/s，服务率 1200 req/s（ρ=0.75）
LAM_PF = 30.0                        # 到达率 30 req/s（调度器那个队列）
BATCH_WINDOW = 4.0                   # 批组装窗口 ms（连续批处理的等待代价）


def queue_wait_ms(rng, lam, mu):
    """M/M/1 等待时间抽样（ms）：P(W>0)=ρ，W|W>0 ~ Exp(μ-λ)。"""
    rho = lam / mu
    if rho >= 1.0:
        return float("inf")
    if rng.random() < rho:
        return rng.expovariate(mu - lam) * 1000.0
    return 0.0


def wq_p99_ms(lam, mu):
    """M/M/1 等待分位的闭式（ms）：P(W>t)=ρ·e^{-(μ-λ)t} ⇒ t=ln(ρ/(1-p))/(μ-λ)。"""
    rho = lam / mu
    if rho >= 1.0:
        return float("inf")
    if rho <= 0.01:
        return 0.0
    return math.log(rho / 0.01) / (mu - lam) * 1000.0


def sample_request(rng, topology, mu_pf):
    out = {}
    for name, fixed, cv2 in STAGES:
        if name not in topology:
            continue
        if name == "网关排队(M/M/1)":
            out[name] = queue_wait_ms(rng, LAM_GW, MU_GW)
        elif name == "调度排队(M/M/1)":
            out[name] = queue_wait_ms(rng, LAM_PF, mu_pf)
        elif name == "批组装(等待窗口)":
            out[name] = rng.random() * BATCH_WINDOW
        elif cv2 == 0.0:
            out[name] = fixed
        else:
            k = 1.0 / cv2                     # 伽马(k, fixed/k)：均值 fixed，CV²=cv2
            out[name] = rng.gammavariate(k, fixed / k)
    return out


def run_mc(topology, mu_pf, n=200000, seed=7):
    rng = random.Random(seed)
    acc = {name: [] for name in topology}
    totals = []
    for _ in range(n):
        s = sample_request(rng, topology, mu_pf)
        for k, v in s.items():
            acc[k].append(v)
        totals.append(sum(s.values()))
    totals.sort()
    q = lambda arr, p: arr[min(len(arr) - 1, int(p * len(arr)))]
    rows = []
    for name in topology:
        arr = sorted(acc[name])
        rows.append((name, q(arr, 0.50), q(arr, 0.99), sum(arr) / len(arr)))
    return rows, q(totals, 0.50), q(totals, 0.99), sum(totals) / n

# ---------------- 三、成功率与连接模型 ----------------
def fleet_success(hop_fail, hops, attempts):
    per_attempt = 1.0 - (1.0 - hop_fail) ** hops
    ok = 1.0 - per_attempt ** attempts
    return per_attempt, ok, (1.0 - ok) * 365 * 24 * 3600


def attempts_for_target(hop_fail, hops, target=0.999):
    per_attempt = 1.0 - (1.0 - hop_fail) ** hops
    if per_attempt <= 0:
        return 1
    return math.ceil(math.log(1.0 - target) / math.log(per_attempt))


def connection_cost(handshake_cpu_s, reuse, req_per_s, n_gw, think_s=1.0, buf_kib=8):
    cpu_new = handshake_cpu_s * 1000.0
    cpu_pers = cpu_new / reuse
    entries = n_gw * req_per_s * think_s
    return cpu_new, cpu_pers, entries, entries * buf_kib / 1024.0


# ---------------- 四、瓶颈分类器 ----------------
def classify(obs):
    total_p99 = sum(v[1] for v in obs.values())
    total_p50 = sum(v[0] for v in obs.values())
    rows = [(name, a, b, b / total_p99, (b - a) / max(1e-9, a))
            for name, (a, b) in obs.items()]
    rows.sort(key=lambda r: -r[3])
    return total_p50, total_p99, rows

五处关键设计决策：

  1. 每个环节都只有"固定 + 排队"两项，没有第三项。因为任何更复杂的环节（重试、缓存命中/未命中分支）都可以先展开成"带分支的串行链"，再对每条链算固定成本。这个约束让整张表可加、可比。
  2. 排队用"伯努利 + 指数抽样"而不是事件驱动模拟：M/M/1 的等待时间分布是 P(W>0)=ρ、W∣W>0∼Exp(μ−λ)，所以两次抽样就够。这是第 4 章第 3 节 mc_sojourn 的同款技巧，跑 20 万次只要几秒。
  3. wq_p99_ms 与蒙卡并列打印（第 (2) 段）：如果闭式与模拟在每一行都同量级，说明抽样没写错。这是本节唯一的内建校验，没有它，"我写了个模拟"和"我写了个 bug"无法区分。
  4. 形态用"环节名列表"表示，而不是写三份模拟：MONOLITH / THREE_TIER / SIX_TIER 是同一个 STAGES 的子集，所以三者的差异只来自环节的增删，不来自参数漂移。这个设计让 §3 的"每层入场费"是可比的。
  5. classify 的排序键是"占端到端 p99 的比例"，不是"尾部放大倍率"。表里"路由"的放大倍率 9.06× 比"调度排队"的 5.06× 还高，但它的绝对贡献只有 3.42 ms。用放大倍率排序会把注意力引到无关紧要的层上；放大倍率只用来回答另一个问题："哪一层的抖动最不可控"。

小结#

  • 请求生命周期分成五组：接入（固定）、鉴权（固定、可本地化）、路由（弱相关、故障时放大）、排队（强非线性、p99 的唯一来源）、执行（第 2-4 章算过）。任何环节的耗时都是 ti​=si​+wi​​。
  • 逐层 p99 相加是上界不是预算：本节 248.3 vs 218.9 ms（1.13×）。用它买容量会多买，用它做归因会指错层。p99 的真实形态是"某一层踩中尾部 + 其余层在均值附近"。
  • p50 与 p99 是两把不同的旋钮：p50 由固定成本 ∑si​ 主宰（本节解释 84%），p99 由排队项主宰（本节 67.8%）。所以"我们的瓶颈是 X"必须先报 ρ —— 排队项在 p99 里的占比从 ρ=0.30 时的 53% 涨到 ρ=0.90 时的 97%。
  • 职责切分的原则是"谁持有状态谁决策"：网关（全局配额）、路由器（去哪台、无状态近似）、调度器（这台机器上算谁、必须精确、必须靠近执行器）、执行器（怎么算）。判据：§2.2 的 λ/(C−λ)2 差 3400 倍 —— 网关用绝对延迟卡，执行器用利用率卡。
  • 层数买的是可运维性，付的是固定成本 + 跳动机会：本节每层入场费约 1.21 ms；固定成本增量是确定的、可预算的，而尾部代价测不出来（被排队方差吞掉），要用最坏路径估。
  • 跳数是可用性的乘数：1−(1−q)n 把 q=10−3 在 6 跳上放大到 0.599%；幂等重试 k=3 能压到 99.99998%，代价是 λ(1+q+q2) 的额外流量（必须走第 4 章的稳定判据）。
  • 长连接不是优化项而是前提：0.35 ms 的 mTLS 握手占网关预算 35%，复用 10⁴ 次后降到 0.0035%；代价是连接级负载均衡的粘性与 drain 语义（下一节）。
  • 一句话：端到端 SLO 的执行器部分由第 1-4 章决定，而它的"差额"由中间环节的固定成本与排队组成；固定成本用加法算，排队用 ρ 算，两者不能合成一个数。

下一节：这一节把"一次请求走过哪些环节"算清了，但漏掉了服务化里省时间最多的一类机制：既然批组装窗口是故意引入的等待，那么"等待谁"、"和谁一起等"就是可优化的；既然同一段系统提示被成千上万个请求共享，那么"重复算的时间"就是可回收的。第 2 节把连续批处理的实现要点与前缀/KV 复用的落地条件写成可算判据（收益 = 命中率 × 重算时间，成本 = 显存 × 单价），并给出缓存收益与缓存污染风险的边界。
