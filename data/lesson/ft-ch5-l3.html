评估#

微调完的模型到底变好了还是变坏了？这是每个实践者最关心、也最容易自欺的问题。因为 LLM 的生成任务是开放式的，没有一个"标准答案"可以直接算准确率，所以评估远比分类任务复杂。这一课我们建立一套务实的评估框架：从"它说得多像参考答案"的自动指标，到"它答得对不对"的基准评测，再到"人类觉得好不好"的判断——并强调那个最容易被忽略的问题：别只看分数，要看它和基座相比有没有真的变强、有没有变傻。

一、概念讲解#

1. 为什么 LLM 评估难#

分类任务有唯一标签，算个准确率就完事；但"把这句话翻译成英文"可以有无穷多种正确说法。用 BLEU、ROUGE 这类基于 n-gram 重叠的指标去卡生成文本，会把"同样正确但措辞不同"的回答判为低分。所以评估 LLM 要多指标、多角度，没有单一银弹。

2. 三大类指标#

① 困惑度（Perplexity, PPL）：衡量模型对一段文本"有多不惊讶"。PPL 越低，说明模型认为这段文本越"自然"。它适合在验证集上快速比较训练前后的语言建模能力，但它只反映"流畅/拟合"，不反映"回答得对不对"。

② 重叠类指标（ROUGE / BLEU）：把生成结果和参考答案做词/子串层面的重叠比较。ROUGE-L 看最长公共子序列，对摘要、问答这类"有参考答案"的场景有一定参考价值；但对开放性回答会严重低估质量。适合"有黄金答案"的窄任务。

③ 偏好/正确性评测（LLM-as-judge、基准集）：让一个更强的模型（如 GPT-4）当"裁判"，对回答打分或做对比；或者在一批标准基准上做题——MMLU（知识问答）、MT-Bench（多轮对话）、AlpacaEval（偏好胜率）、HumanEval（代码）。这类评测更贴近"好不好用"，是当前社区的主流做法。

3. 最关键的评估原则：和基座对比#

一个微调模型在基准上拿了 60 分，不代表微调成功——如果基座本来就能拿 62 分，说明这次微调反而有害。评估 SFT 的标准动作是：

  1. 同题同参：基座和微调模型用完全相同的 prompt、解码参数跑同一批题；
  2. 看增量：比较两者分数差，而不是孤立看绝对分；
  3. 防退化：检查模型是否"过拟合到指令而忘了通用能力"（在通用能力集上是否掉分）；
  4. 留出集：数据上一定要切一块从未参与训练的验证集，训练集上的分数只能证明"背下来了"。

4. 评估的工程落地#

评估要自动化、可复现：固定随机种子、固定 temperature（对比正确性时建议用贪心解码）、固定 prompt 模板，把评测脚本纳入 CI。用 lm-evaluation-harness（EleutherAI）可以一键跑 MMLU 等主流基准，省去自己写评测循环。

二、可运行代码示例#

下面演示两件最小可用的事：计算验证集的困惑度，以及用 ROUGE-L 对"有参考答案"的摘要任务打分。依赖 transformers、rouge_score（或 evaluate）。

import torch
from transformers import AutoModelForCausalLM, AutoTokenizer
from rouge_score import rouge_scorer

model_id = "gpt2"
tokenizer = AutoTokenizer.from_pretrained(model_id)
tokenizer.pad_token = tokenizer.eos_token
model = AutoModelForCausalLM.from_pretrained(model_id)

# 1) 困惑度：对一段验证文本，算模型"平均每个 token 有多惊讶"
texts = [
    "人工智能正在改变世界。",
    "大语言模型的微调方法有很多种。",
]
enc = tokenizer(texts, return_tensors="pt", padding=True, truncation=True)
with torch.no_grad():
    out = model(**enc, labels=enc["input_ids"])
    # 语言模型自带 loss = 平均交叉熵；困惑度 = exp(loss)
    ppl = torch.exp(out.loss).item()
print(f"验证集困惑度（PPL）：{ppl:.2f}")

# 2) ROUGE-L：对有参考答案的任务打分
scorer = rouge_scorer.RougeScorer(["rougeL"], use_stemmer=True)
reference = "大语言模型可以通过 LoRA 进行高效微调。"
candidate = "LoRA 是一种大语言模型的高效微调方法。"  # 措辞不同但意思相近
scores = scorer.score(reference, candidate)
print(f"ROUGE-L：{scores['rougeL']}")

运行后你会看到：gpt2 在这两句话上的 PPL 是一个具体数值（越小越好）；而 ROUGE-L 的 fmeasure 通常不高——因为候选句和参考句措辞差异大，尽管意思接近。这正印证了本课的核心观点：重叠指标会低估开放生成的质量，所以它只适合"有标准答案"的窄任务，开放对话还得靠基准和裁判。

提示：若要跑 MMLU 等标准基准，推荐直接使用 EleutherAI 的 lm-evaluation-harness，一条命令即可：lm_eval --model hf --model_args pretrained=<model> --tasks mmlu --num_fewshot 5。

三、练习#

  1. 用上面 PPL 代码，分别测基座模型和你微调后的模型在同一批验证文本上的 PPL，比较两者大小；再想一想：PPL 更低，是否一定代表"更会回答"？为什么？
  2. 把 ROUGE 示例里的 candidate 改成与 reference 几乎逐字相同的句子，观察 fmeasure 的跳升，体会重叠指标"偏爱字面相同"的偏置。
  3. 安装并跑一次 lm-evaluation-harness 的 mmlu 任务（可只跑 mmlu 的一两个子集），记录分数，思考 5-shot 的 few-shot 提示对分数的影响。
  4. 设计一个"防退化"小实验：准备 10 条通用能力题（如简单算术、常识问答），分别让基座和微调模型回答，人工比较——判断你的微调是否损害了通用能力。
