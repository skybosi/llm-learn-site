成本-质量前沿：延迟分解与每查询成本核算#

这一节要解决什么#

前面的三节把"一次问答"的内部机制讲完了：长上下文的成本（§5.1）、上下文预算怎么分（§5.2）、证据为什么会被读到或没被读到（§5.3）。但一个能上线讲清楚的系统还要回答最后一个问题：

这条链路的每一段各花多少毫秒、各花多少钱？我该在哪里省，省下来的代价是什么？

这个问题在实践中经常被两个错误回答掉：

  • "延迟高就优化检索" —— 实测发现，在输出 200+ token 的场景里，解码时间往往占 80% 以上，检索那几毫秒根本改不动指标（本节代码给出：k 从 5 涨到 50，ANN 只从 7.8ms 涨到 23.5ms，而总延迟从 1497ms 涨到 2269ms，涨的主要是 prefill 与恒定的 decode）。
  • "成本就是 token 费" —— 漏掉了检索/重排算力、GPU 摊销、缓存带来的折扣，以及重试与失败查询这些隐性成本。

本节要回答四个问题：

  1. 延迟怎么逐段分解，每段的量级由什么决定？哪些段随 k 变、哪些不随？
  2. 为什么尾延迟（P95/P99）在利用率高时会爆炸？要满足尾延迟 SLO，需要多少余量与副本？
  3. 每查询成本怎么算？哪些项最容易被漏掉？
  4. 把每个可调旋钮放到 (成本, 质量) 平面上，怎么找 Pareto 前沿、怎么算边际成本，最终怎么判断"这个升级值不值"？

结论先放在这里：延迟与成本都是分段、可算的；优化必须先定位到段，再动手。⚠️ 本节示例配置下，输出 220 token 时 decode = 1320ms，占总延迟 79%~88%，是唯一的主导段；而尾延迟由 1/(1−ρ) 型的分母决定，ρ 从 0.72 涨到 0.96 时 M/M/1 的 P99 从 651ms 涨到 4604ms。成本优化的正确顺序是"先看结构（哪一段主导）"，再看旋钮（边际成本） —— 否则会在检索参数上做无意义的调优。

一、延迟分解：逐段的模型#

1.1 分段#

一次 RAG 问答的端到端延迟可以分解为：

ttotal​=tnet​+tqueue​+tembed​+tann​+tfilter​+trerank​+tprefill​+tdecode​

段 模型 量级（示例） 随 k 变？
tnet​ 固定（网络往返） 25 ms 否
tqueue​ 排队等待（第 2 节） 15 ms 起，尾部可达秒级 否（但随负载）
tembed​ 一次编码前向 8 ms 否
tann​ 定位 + 扫描 + 展开：α+βk 7.8→23.5 ms（k: 5→50） 是（弱）
tfilter​ ACL/元数据过滤 2 ms 否
trerank​ cpair​×pool 45 ms（pool=50） 是（强）
tprefill​ 2N⋅nin​/(FLOPseff​) 119→875 ms（k: 5→50） 是（强）
tdecode​ nout​×tTPOT​ 1320 ms（220 token） 否

两个必须建立的直觉：

  1. **tann​ 只随 k **弱增长（近似 α+βk，β 很小），因为 ANN 的代价主要在"定位与展开"的固定开销上（ch2-l3 的三段模型）。所以"降低 k 来省检索延迟"通常收益极小。
  2. **tprefill​ 随 k **强增长（因为 nin​ 随 k 线性增长，而 prefill 算力 ∝nin​），而 tdecode​ 与 k 无关。当输出较长时，decode 是地板，k 只是在地板上加东西。

1.2 延迟预算反推#

给定 P95 SLO，把上式反解，得到最大 k：

kmax​=⌊β+2N⋅380/(FLOPseff​)⋅1000B−∑固定​t−tdecode​−tprefill​(k=0)−cpair​⋅pool​⌋

分母里 380 是每个 chunk 的平均 token 数（示例）。⚠️ 本节示例（SLO = 2000ms、输出 220 token、8 路张量并行）：

重排池 最大 k 总延迟 瓶颈段
0 34 1994 ms decode
50 31 1988 ms decode
100 29 1999 ms decode
200 23 1986 ms decode

关键读数：瓶颈段永远是 decode（1320ms），而不是检索。即使把重排池开到 200、k 砍到 23，也省不出多少 —— 因为 decode 是不可压缩的地板。要动这个地板，只有三条路：缩短输出、用小模型解码、或把输出也做缓存/流式（降低感知延迟而非总延迟）。

1.3 TTFT 与 TPOT 是两个预算#

工程上必须把首 token 延迟（TTFT）与每 token 延迟（TPOT）分开，因为它们对应的预算不同：

TTFT≈tnet​+tqueue​+tembed​+tann​+tfilter​+trerank​+tprefill​

TPOT≈tdecode​/nout​

交互式产品对 TTFT 敏感（用户要"立刻看到开始输出"），批处理产品对总延迟敏感。 而 TTFT 恰好是检索与 prefill 主导的那一段 —— 所以"检索优化"对交互体验仍有价值，即使它改不动总延迟。把这两个指标分开，才能避免"总延迟没变所以检索优化没用"的错误结论。

二、尾延迟与排队：为什么 P99 会爆炸#

2.1 M/M/1 的结论#

把服务建模成一个队列：到达率 λ、单副本服务率 μ、利用率 ρ=λ/μ。M/M/1 的平均停留时间与等待时间：

W=μ−λ1​=μ(1−ρ)1​

分母 (1−ρ) 就是全部问题的来源：ρ→1 时 W 爆炸。等待时间的尾分布：

P(Wq​>t)=ρe−(μ−λ)t

由此解出 P99 等待：

Wq99​=μ−λln(ρ/0.01)​

⚠️ 本节示例（μ=25/s，即服务时间 40ms）：

λ (QPS) ρ 解析 P99 模拟 P95 模拟 P99
5 0.20 190 ms 68.7 ms 149.9 ms
12 0.48 338 ms 174.4 ms 303.3 ms
18 0.72 651 ms 379.9 ms 600.0 ms
22 0.88 1532 ms 926.9 ms 1419.8 ms
24 0.96 4604 ms 2472.7 ms 3407.0 ms

ρ 从 0.72 涨到 0.96（负载只涨 33%），P99 从 651ms 涨到 4604ms（7 倍）。 这就是"容量按平均值配置"必然失败的原因：平均值算得下，尾延迟算不下。

2.2 多副本：M/M/c 与 Erlang-C#

c 个副本时，用 Erlang-C 公式给出"到达时需要等待"的概率 C(c,a)（a=λ/μ）：

B0​=1,Bk​=k+aBk−1​aBk−1​​,C(c,a)=c−a(1−Bc​)cBc​​

Wq99​=cμ−λmax(0,ln0.01C(c,a)​)​

⚠️ 示例：达到 P99 ≤ 500ms 所需的最小副本数：

λ c=1 c=2 c=3 c=4 c=6 c=8 最小 c
10 286 87 40 40 40 40 1
20 ∞ 144 70 40 40 40 2
40 ∞ 466 135 77 40 40 2
60 ∞ ∞ 318 124 55 40 3
100 ∞ ∞ ∞ ∞ 107 58 5
160 ∞ ∞ ∞ ∞ ∞ 136 7
300 ∞ ∞ ∞ ∞ ∞ ∞ 13

两个可迁移的结论：

  1. 副本数与负载不是线性关系：λ 从 10 涨到 40（4 倍），最小副本数只从 1 涨到 2；但 100→300（3 倍）需要 5→13。因为接近饱和时，多副本的收益被"每个副本的 ρ"吃掉。
  2. 低于某负载时 P99 就是服务时间本身（表中出现"40"这个地板）：一旦 C(c,a)<0.01，99 分位等待为 0，尾延迟 = 服务时间。这就是"留余量"的定量含义：把 ρ 压到使等待概率小于 1%。

2.3 批处理的代价#

动态批处理提升吞吐（把多个请求合成一个 batch），但会引入两类延迟：

  • 排队延迟：请求要等"批凑齐"或超时窗口；
  • 队头阻塞（head-of-line blocking）：一个长输出会把同批的短输出一起拖住。

因此批处理的正确使用方式是分层：短输出请求与长输出请求分开批；对 TTFT 敏感的请求优先或单独通道。"批越大越好"只在吞吐维度成立。

三、每查询成本：完整账本#

3.1 四类成本#

Cquery​=token 费cin​nin​+cout​nout​​​+算力摊销3600tcompute​​⋅pGPU​⋅nGPU​​​+索引存储摊销Cstorage​/Qday​​​+重试/失败Cfail​​​

其中算力摊销要注意用利用率而不是标称价格：

peff​=寿命×利用率pGPU​⋅nGPU​​

利用率是杠杆最大的项：同样一张卡，利用率 20% 与 60% 的有效单价差 3 倍。这也是为什么"批量/缓存把空闲填满"往往比"换更便宜的模型"更有效。

3.2 最容易被漏掉的成本项#

漏项 为什么容易被漏 典型量级
重试与失败查询 失败的请求也消耗算力，但不计费/不进指标 失败率 3% 时约 +3%~8%
索引重建 周期性全量重嵌入，与查询量解耦 与语料规模成正比
重排/嵌入算力 不在 token 账单里 在高 k 时可占 20%+
人力运维 评测集维护、告警处理、权限变更 常超过算力成本
缓存失效的浪费 缓存穿透时成本回到无缓存水平 取决于 TTL 与命中率

3.3 缓存的折扣项#

前缀缓存把 nin​ 中"稳定前缀"那部分从计费与算力里去掉。若前缀占比 p，则

Cquerycached​≈Cquery​−p⋅cin​nin​

⚠️ 示例里"k=50 + 重排 50 + 缓存"把成本从 0.08011 元降到 0.04406 元（0.55 倍），质量不变（同一配置只是加了缓存）。这是 Pareto 前沿上最"便宜"的一次改进 —— 因为它不改变质量，只砍成本。

四、质量-成本前沿与边际成本#

4.1 把旋钮放到同一张图上#

可调旋钮与它们的作用方向：

旋钮 质量影响 成本影响 拐点/反效果条件
k（证据数） 收益随 k 饱和（∼1−e−k/25） nin​ 线性 ↑ k 大后干扰超过收益
重排池 ∼1−e−pool/60 饱和 每对固定成本 × pool pool 超过候选质量上限
模型档位 全面提升 线性/超线性 ↑ 质量目标已达成时纯浪费
缓存 无（质量不变） ↓（前缀占比决定） 前缀不稳定时失效
chunk 大小 两端都差（太大噪声、太小碎片） 影响 nin​ 需按语料测
查询改写 特定查询类型上有效（ch4） 一次 LLM 调用 在"排序问题"上完全无效

4.2 Pareto 前沿与支配#

配置 A 支配 B，当且仅当

quality(A)≥quality(B) ∧ cost(A)≤cost(B) ∧ (严格其一)

⚠️ 示例结果（8 个配置）：

Pareto 前沿：

小模型 k=5 无重排            质量=0.5935 成本=0.01067
小模型 k=10 无重排           质量=0.5988 成本=0.01472
大模型 k=10 无重排           质量=0.6805 成本=0.03096
小模型 k=50 重排50+缓存       质量=0.7078 成本=0.03118
大模型 k=50 重排50+缓存       质量=0.8043 成本=0.04406
大模型 k=100 重排200         质量=0.8523 成本=0.15834

被支配（存在更便宜且不差的配置）：大模型 k=50 无重排、大模型 k=50 重排50。

这句话的实践含义很重要：加了缓存之后，"大模型 k=50 重排50 + 缓存"（0.04406 元）同时比"大模型 k=50 重排50"（0.08011 元）便宜、且质量相同 —— 后者被支配。被支配的配置不该存在于生产里；每一次上线前的配置评审，第一步就是检查有没有被支配项。

4.3 边际成本：判断"值不值"#

沿 Pareto 前沿相邻点的边际成本：

MC=ΔcostΔquality​

⚠️ 示例：

小模型 k=5   -> 小模型 k=10   : Δq=+0.0053 Δc=+0.00405  MC=1.3
小模型 k=10  -> 大模型 k=10   : Δq=+0.0817 Δc=+0.01625  MC=5.0
大模型 k=10  -> 小模型 k=50重排: Δq=+0.0273 Δc=+0.00022  MC=125.6
小模型 k=50重排 -> 大模型 k=50重排: Δq=+0.0965 Δc=+0.01288  MC=7.5
大模型 k=50重排 -> 大模型 k=100重排200: Δq=+0.0480 Δc=+0.11428  MC=0.4

读法：

  • MC=125.6 那一步（从小模型切到大模型前的"小模型 + 重排 + 缓存"）是最划算的一步：花 0.00022 元买到 0.0273 质量；
  • MC=0.4 那一步（把 k 从 50 抬到 100、重排池 50→200）是最不划算的：花 0.114 元只买到 0.048 质量；
  • 判据：给定"单位质量的价值" V，只有当 MC⋅V>1（即质量增益的价值超过成本）时才做这一步。MC 把"该不该升级"变成了一个可计算的阈值，而不是感觉。

4.4 边界与陷阱#

陷阱 表现 修正
用离线指标当质量 离线涨 2%，线上无感 质量的输入必须是端到端任务指标（ch7-l2）
用平均值配容量 平均 ρ=0.7 很安全，P99 崩 按尾延迟配（§2）
忽略 decode 地板 反复优化检索，总延迟不动 先量各段占比（§1.1）
缓存当免费午餐 前缀不稳定 → 命中率低 → 成本不降 用命中率×前缀占比算实际折扣
平摊延迟预算 每个请求都按平均段耗时 尾延迟由最慢段主导，按分位数分配
忽略失败成本 成本模型偏乐观 5%~10% 把失败率与重试计入

代码#

三段代码：延迟分解与预算反推、排队与副本数、质量-成本 Pareto。

# -*- coding: utf-8 -*-
"""(a) 延迟分解与 SLO 反推；(b) M/M/1 与 M/M/c 尾延迟；(c) 质量-成本 Pareto。
   ⚠️ 硬件参数与单价是示例值（以官方为准），质量为合成代理。"""
import math, numpy as np

# ===== (a) 延迟分解 =====
LAT = dict(net=25, queue=15, embed=8, ann_base=6, ann_per_k=0.35, acl=2, decode_per_tok=6)
N_PARAMS, FLOPS_PEAK, EFF, TP = 70e9, 9.9e14, 0.40, 8
RERANK_MS = 0.9

def latency(k=10, rerank_pool=0, n_in=None, n_out=220, model_scale=1.0, tp=TP):
    ann = LAT["ann_base"] + LAT["ann_per_k"] * k
    if n_in is None:                       # 证据 token 随 k 增长
        n_in = 800 + 380 * k
    rr = RERANK_MS * rerank_pool if rerank_pool else 0.0
    prefill_ms = (2 * N_PARAMS * model_scale * n_in) / (FLOPS_PEAK * EFF * tp) * 1000
    decode = LAT["decode_per_tok"] * n_out * model_scale * (8 / tp)   # 解码受显存带宽限制
    total = (LAT["net"] + LAT["queue"] + LAT["embed"] + ann + LAT["acl"] + rr
             + prefill_ms + decode)
    return dict(ann=ann, rerank=rr, prefill=prefill_ms, decode=decode, total=total)

print("== (a) 延迟分解（ms；示例硬件 8×加速卡、tp=8）==")
print(f"{'配置':<26} {'ANN':>6} {'重排':>7} {'prefill':>8} {'decode':>7} {'总':>8}")
for name, kw in [("k=5 无重排", dict(k=5)), ("k=10 无重排", dict(k=10)),
                 ("k=50 无重排", dict(k=50)), ("k=50 + 重排池50", dict(k=50, rerank_pool=50)),
                 ("k=100 + 重排池200", dict(k=100, rerank_pool=200)),
                 ("k=50 + 小模型(0.2×)", dict(k=50, model_scale=0.2))]:
    d = latency(**kw)
    print(f"{name:<26} {d['ann']:>6.1f} {d['rerank']:>7.1f} {d['prefill']:>8.1f} "
          f"{d['decode']:>7.1f} {d['total']:>8.1f}")

SLO = 2000.0
print(f"\n-- 在 P95 SLO={SLO:.0f}ms 下反推最大 k --")
print(f"{'重排池':>7} {'最大k':>7} {'最长段':>8} {'总延迟':>9} {'瓶颈段':>10}")
for pool in (0, 50, 100, 200):
    best = max((k for k in range(0, 500)
                if latency(k=k, rerank_pool=pool)["total"] <= SLO), default=None)
    if best is None:
        print(f"{pool:>7} {'无解':>7}"); continue
    d = latency(k=best, rerank_pool=pool)
    segs = {"ANN": d["ann"], "重排": d["rerank"], "prefill": d["prefill"], "decode": d["decode"]}
    print(f"{pool:>7} {best:>7} {max(segs.values()):>8.1f} {d['total']:>9.1f} "
          f"{max(segs, key=segs.get):>10}")

# ===== (b) 排队尾延迟与副本数 =====
def erlang_c(c, a):
    b = 1.0
    for k in range(1, c + 1):
        b = a * b / (k + a * b)
    return c * b / (c - a * (1 - b))

def p99_mmc(lam, mu, c):
    a = lam / mu
    if a >= c:
        return float("inf")
    C = erlang_c(c, a)
    wq99 = max(0.0, math.log(C / 0.01)) / (c * mu - lam)   # C<0.01 时 99 分位等待为 0
    return wq99 + 1 / mu

def sim_mm1(lam, mu, n=200000, seed=0):
    """Lindley 递推模拟 M/M/1 的等待时间。"""
    r = np.random.default_rng(seed); W = 0.0; out = []
    for _ in range(n):
        W = max(0.0, W + r.exponential(1 / mu) - r.exponential(1 / lam))
        out.append(W)
    return float(np.percentile(out, 95)), float(np.percentile(out, 99))

print("\n== (b) M/M/1 尾延迟（服务时间示例 40ms -> μ=25/s）==")
mu = 25.0
print(f"{'λ(QPS)':>7} {'ρ':>6} {'解析P99(ms)':>12} {'模拟P95(ms)':>12} {'模拟P99(ms)':>12}")
for lam in (5, 12, 18, 22, 24):
    s95, s99 = sim_mm1(lam, mu, n=200000, seed=1)
    print(f"{lam:>7} {lam/mu:>6.2f} {p99_mmc(lam, mu, 1)*1000:>12.1f} "
          f"{s95*1000:>12.1f} {s99*1000:>12.1f}")

print(f"\n-- 达到 P99 ≤ 500ms 所需副本数（每副本 μ=25/s）--")
print(f"{'λ(QPS)':>7} " + " ".join(f"{'c='+str(c):>9}" for c in (1, 2, 3, 4, 6, 8)) + "   最小c")
for lam in (10, 20, 40, 60, 100, 160, 300):
    row = [(lambda v: "∞" if v > 500 else f"{v:.0f}")(p99_mmc(lam, mu, c) * 1000)
           for c in (1, 2, 3, 4, 6, 8)]
    c_min = next((c for c in range(1, 60) if p99_mmc(lam, mu, c) * 1000 <= 500), None)
    print(f"{lam:>7} " + " ".join(f"{v:>9}" for v in row) + f"   {c_min}")

# ===== (c) 质量-成本 Pareto =====
print("\n== (c) 质量-成本工作点（示例单价，以官方为准；质量为合成代理）==")
C_IN, C_OUT, GPU_HOUR = 2.0 / 1e6, 8.0 / 1e6, 6.0

def config(name, model_scale, k, pool, use_cache):
    recall = 0.62 + 0.30 * (1 - math.exp(-k / 25))          # 召回收益随 k 饱和
    rerank_gain = 0.10 * (1 - math.exp(-pool / 60)) if pool else 0.0
    distract = 0.035 * math.log1p(max(0, k - 8))            # 干扰惩罚
    quality = min(0.99, recall + rerank_gain - distract) * (0.85 + 0.15 * min(1, model_scale))
    n_in = 250 + k * 380 + (pool * 90 if pool else 0)
    tokens = C_IN * n_in + C_OUT * 220
    compute = latency(k=k, rerank_pool=pool, model_scale=model_scale)["total"] / 1000 \
        * (GPU_HOUR * 8 / 3600)
    cost = tokens + compute
    if use_cache:
        cost *= 0.55                                        # 前缀缓存折扣
    return dict(name=name, quality=quality, cost=cost, n_in=n_in)

小结#

  • 延迟必须先分段再优化。⚠️ 示例（输出 220 token、tp=8）：decode = 1320ms 是主导段，占总延迟 79%~88%；k 从 5→50 只让 ANN 从 7.8→23.5ms，却让 prefill 从 119→875ms。在输出较长的场景里，检索侧优化改不动总延迟。
  • tann​ 随 k 弱增长、tprefill​ 强增长、tdecode​ 与 k 无关。所以"降 k 省延迟"收益极小，正确做法是分别优化主导段。
  • TTFT 与 TPOT 是两个预算：TTFT 由检索 + prefill 主导（交互体验），总延迟由 decode 主导（批处理成本）。混用会得出错误结论。
  • 尾延迟由 1/(1−ρ) 决定：⚠️ M/M/1 的 P99 从 ρ=0.72 的 651ms 涨到 ρ=0.96 的 4604ms（负载只涨 33%）。按平均值配容量必然在尾部崩。
  • 多副本用 Erlang-C：⚠️ 达到 P99 ≤ 500ms 所需副本数在 λ≤40 时只需 1~2 个，λ=100 需 5 个，λ=300 需 13 个。"留余量"的定量含义是把等待概率压到 1% 以下（此时尾延迟回落到服务时间本身）。
  • 成本账本有四类：token 费、算力摊销（用利用率而不是标称价）、存储摊销、失败与重试。最易漏的是失败成本、索引重建与人力运维。
  • Pareto 前沿 + 边际成本 MC=Δq/Δc 是"值不值"的判据：⚠️ 示例里最划算的一步 MC=125.6，最不划算的一步 MC=0.4；两个配置被支配（有更便宜且同质量的选择）。被支配配置不该出现在生产里。
  • 缓存是不改变质量的降本：⚠️ 示例里加缓存把成本从 0.08011 降到 0.04406 元、质量不变，因此"同质量的非缓存配置"被支配。
  • 一句话：延迟与成本都是算术题：先分段定位主导项，再用分位数配容量，最后用边际成本决定要不要升级 —— 每一步都有可算的判据，没有一步需要凭感觉。
