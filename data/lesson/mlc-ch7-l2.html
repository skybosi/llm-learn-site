生成质量：与手写 kernel 的差距从哪里来#

Triton 官方 matmul 教程里有一个很容易被跳过的细节：同一份 kernel、同一组 tile，只把 block 的发射顺序从行优先改成分组，前 9 个输出块需要同时留在片上的 block 数就从 90 降到 54，教程注明这在某些硬件上能带来超过 10% 的差别。这说明"生成质量"不是玄学——它由几件可以逐项算清的事情组成：调度决策、形状余数、资源约束。本课把这三项拆开，每一项都给一个能打印出来的数，最后给出"把局部差距折成端到端差距"的算法。

一、概念讲解#

1. 差距只有三个来源#

调度决策：tile 多大、K 方向分几段、block 之间按什么顺序发射、流水几级、几个 warp。这些是第 6 课搜索空间里的点，也是生成器与手写 kernel 差距的主战场。 形状余数：固定 block 遇到非整除 shape，必须靠掩码或 padding 收口，多发射的 lane 就是纯浪费。 资源约束：累加器、操作数、地址各占多少寄存器，片上缓冲够不够，决定了 occupancy 与"再大一点就变慢"的拐点。

一个模型在端到端上的差距，是这三项在各自覆盖的时间段上的加权结果——所以归因永远先于优化。

2. 形状余数：差一个元素，浪费率差两个数量级#

代码第 1 节给出实测：BLOCK=128 时，shape 1024 浪费 0%，1000 浪费 2.34%，1025 浪费 11.02%；8191 只浪费 0.01%。规律是"发射 lane 数 = ceil(shape/block) × block"，所以浪费率在"刚过一个整数倍"处最难看。这解释了两条工程习惯：一是尽量让 batch/序列长度取到 block 的整数倍，二是把一个点链的逐元素部分与归约部分分别选块，不要让一个块的取整误差污染整网。

3. 访问顺序决定工作集：90 → 54#

同一份 GEMM，产出前 9 个输出块时，行优先顺序要触及 9 个 A block 加 81 个 B block（共 90）；按 3 行一组、组内列优先发射，A、B 各 27，共 54。本课代码复现了这两个数，与 Triton 教程一致。放大到 M=N=4096、K=4096、BLOCK_M=BLOCK_N=128、BLOCK_K=64：行优先要 2112 个 block，GROUP_SIZE_M 取 4 或 8 时都是 768——注意 4 与 8 打平不是巧合，块数按 A 与 B 的对称形状最小化，组太扁或太长都会让另一侧变差。

4. 资源约束：累加器先吃掉寄存器#

BLOCK_M×BLOCK_N 的累加器要摊到 num_warps×32 个线程上：128×256 / 256 线程 = 每线程 128 个累加器，而多数架构单线程寄存器上限是 255（以 NVIDIA compute capability 文档为准）。累加器只是下限，再加上操作数与流水缓冲，大 block 会把 occupancy 压下去——这正是"tile 不是越大越好"的定量解释，也是自动调优存在的理由。

5. 差距账本与归因#

代码第 4 节把可调项列成账本：tile 尺寸、访问顺序、软件流水、掩码尾部、epilogue 融合、K 方向并行度（split-K / stream-K）、寄存器与 occupancy 权衡，都能在搜索空间里补；只有"为唯一常量形状写死的 persistent kernel / swizzle"通常不在生成器输出里。第 5 节用 Amdahl 折账：局部提速 20%、若只覆盖 25% 的时间，端到端只有约 5%；哪怕点链提速 5 倍，覆盖 25% 时间也只换来 1.26 倍。先定位时间花在哪一段，再问那一段归谁生成——这是本课最该记住的顺序。

6. 常见坑#

  • 拿微基准的加速比当端到端收益：忽略覆盖比例，结论会大一个数量级（第 5 节）。
  • 只调 tile 不看发射顺序：访问顺序几乎不花编译时间，收益却可能超过换块。
  • 把"用满寄存器"当目标：寄存器用得越满，occupancy 越低，访存延迟越藏不住。
  • 对掩码尾部不设防：大 batch 跑得漂亮、小 batch 或奇数长度掉一半，都是尾部问题。
  • 忘了 K 方向的并行度：K 很小、M×N 很大时，网格并行度不足，需要 split-K 再加一次归约。

二、可运行代码示例#

纯标准库 Python（本机 python3.10.16 实跑），只需要 math。五段：形状余数表、block 访问顺序的工作集计数（含 Triton 教程的 90/54 复核）、block 尺寸到每线程累加器、差距账本、Amdahl 折账。

# ---- 第 2 课：生成质量的差距从哪里来（纯标准库，无需 numpy / GPU）----
import math

# ============ 1. 固定 block 与任意 shape 的尾巴浪费 ============
def tail(shape, block):
    useful = shape
    lanes = math.ceil(shape / block) * block
    return lanes, lanes - useful, (lanes - useful) / lanes

print("=== 1. block 取整：同一条生成规则，不同 shape 的浪费率差两个数量级 ===")
print(f"  {'shape':>6} {'BLOCK':>6} {'发射 lane':>10} {'空转':>6} {'浪费率':>9}")
for shape, block in [(1024, 128), (1000, 128), (1025, 128), (4096, 128), (4097, 256), (8191, 128)]:
    lanes, waste, ratio = tail(shape, block)
    print(f"  {shape:>6} {block:>6} {lanes:>10} {waste:>6} {ratio:>8.2%}")
print("  对齐的 shape 浪费 0；差 1 个元素就要多发射一整个 block —— 这就是 padding / 掩码的代价")

# ============ 2. block 访问顺序 → 工作集大小（LRU 缓存模拟）============
def launch_order(cm, cn, group_m):
    """Triton 官方 matmul 教程的 pid → (pid_m, pid_n) 映射：组内按列优先，组间按行。"""
    order = []
    for pid in range(cm * cn):
        num_pid_in_group = group_m * cn
        group_id = pid // num_pid_in_group
        first_pid_m = group_id * group_m
        group_size_m = min(cm - first_pid_m, group_m)
        pid_m = first_pid_m + ((pid % num_pid_in_group) % group_size_m)
        pid_n = (pid % num_pid_in_group) // group_size_m
        order.append((pid_m, pid_n))
    return order

def working_set(cm, cn, k_tiles, group_m, first_p):
    """产出前 first_p 个输出 block 期间，触及过的 A/B block 去重计数。"""
    touched = set()
    for pid_m, pid_n in launch_order(cm, cn, group_m)[:first_p]:
        for k in range(k_tiles):
            touched.add(("A", pid_m, k))
            touched.add(("B", k, pid_n))
    a_blocks = sum(1 for t in touched if t[0] == "A")
    b_blocks = sum(1 for t in touched if t[0] == "B")
    return a_blocks, b_blocks

print("\n=== 2. 同一份计算，只改 block 访问顺序：工作集 90 → 54 ===")
cm = cn = 9
k_tiles = 9
for group_m, tag in [(1, "行优先（GROUP_SIZE_M=1）"), (3, "分组：3 行一组")]:
    a, b = working_set(cm, cn, k_tiles, group_m, first_p=9)
    print(f"  {cm}x{cn} 个输出 block，K 方向 {k_tiles} 片，产出前 9 个 block：")
    print(f"    {tag}：A {a} + B {b} = {a + b} 个 block 需要同时留在片上缓存")
print("  这与 Triton 官方 matmul 教程给出的 90 / 54 一致 —— 差异只来自访问顺序")

cm = cn = 32
k_tiles = 64
print(f"\n  放大到 M=N=4096, K=4096, BLOCK_M=BLOCK_N=128, BLOCK_K=64（{cm}x{cn} 个输出 block，K 方向 {k_tiles} 片）：")
for group_m in (1, 4, 8, 16):
    a, b = working_set(cm, cn, k_tiles, group_m, first_p=cm)
    print(f"    GROUP_SIZE_M={group_m:>2}：A {a:>4} + B {b:>4} = {a + b:>5} 个 block（产出前 {cm} 个）")

# ============ 3. block 尺寸 → 每线程累加器 ============
print("\n=== 3. block 尺寸直接决定每线程的累加器数量（寄存器压力的第一来源）===")
print(f"  {'BLOCK_M':>7} {'BLOCK_N':>7} {'warps':>5} {'线程':>5} {'acc/线程':>8} {'片上 acc 总量(MB)':>18}")
for bm, bn, warps in [(128, 256, 8), (128, 128, 4), (64, 128, 4), (64, 64, 4), (32, 32, 4)]:
    threads = warps * 32
    acc_per_thread = bm * bn / threads
    acc_total_mb = bm * bn * 4 / 2**20
    print(f"  {bm:>7} {bn:>7} {warps:>5} {threads:>5} {acc_per_thread:>8.0f} {acc_total_mb:>18.2f}")
print("  单线程寄存器上限多数架构为 255（以 NVIDIA compute capability 文档为准）；")
print("  acc 只是下限，加上操作数、地址、流水缓冲，大 block 会先把 occupancy 压下去")

# ============ 4. 差距账本：哪些部分生成器补得上、哪些补不上 ============
print("\n=== 4. 差距账本：每一项对应一个可调旋钮 ===")
LEDGER = [
    ("tile 尺寸选择", "自动调优扫 BLOCK_M/N/K × num_warps × num_stages", "可补"),
    ("block 访问顺序", "分组顺序提升片上/L2 复用（第 2 节）", "可补"),
    ("软件流水", "num_stages：预取下一片，掩盖访存延迟", "可补"),
    ("尾部与掩码", "shape 取整带来的空转（第 1 节）", "部分可补：改 shape 或专门 ptx 化"),
    ("epilogue 融合", "把 bias/激活融进 GEMM 模板，省一次 DRAM 往返", "可补（模板支持时）"),
    ("K 方向并行度", "split-K / stream-K：K 小、M×N 大时切 K", "可补（需要额外归约）"),
    ("寄存器/occupancy 权衡", "num_warps 与 block 大小的联合搜索", "可补（搜索空间内）"),
    ("常量形状特化", "为唯一形状写死的 persistent kernel / swizzle", "生成器通常不做"),
]
for item, knob, cover in LEDGER:
    print(f"  {item:<18}{knob:<46}{cover}")

# ============ 5. 用 Amdahl 把"局部差距"折成端到端差距 ============
def speedup(parts):
    """parts: [(占比, 该部分加速比)]；1/(Σ 占比/加速比)。"""
    total = sum(frac / sp for frac, sp in parts)
    return 1.0 / total

print("\n=== 5. 局部差距 → 端到端差距（模型估算，占比是假设值）===")
for parts, tag in [
    ([(0.70, 1.00), (0.25, 1.20), (0.05, 1.10)], "点在 matmul（外部库）上的模型"),
    ([(0.30, 1.00), (0.60, 1.20), (0.10, 1.10)], "点在点链/归约上的模型"),
    ([(0.70, 1.00), (0.25, 5.00), (0.05, 1.10)], "点链加速 5x 的乐观上界"),
]:
    print(f"  {tag}：端到端加速 = {speedup(parts):.3f}x")
print("  结论：局部 20% 的提升，若只覆盖 25% 的时间，端到端只有约 5%；")
print("  所以：生成质量要先看时间花在哪一段，再看那一段归谁生成")

三、练习#

  1. 实现：把第 2 节的 working_set 扩展成同时支持"按 GROUP_SIZE_M 分组"与"按 N 方向分组（对称写法）"，找出 M=N=4096、BLOCK=128、K 方向 64 片时使总块数最小的分组方式，并解释为什么最优解接近正方形。
  2. 解释：为什么 shape=1025, BLOCK=128 的浪费率（11.02%）远高于 shape=8191, BLOCK=128（0.01%）？如果把块改成 256，这两个 shape 的浪费率各变成多少？
  3. 对比/验证：用第 3 节的公式算出 BLOCK_M=BLOCK_N=256, num_warps=8 时每线程的累加器数量，并与 128×128, num_warps=4 比较；解释为什么前者的实测往往更慢，尽管 tile 更大。
  4. 思考：假设某模型 60% 时间在 extern GEMM（生成器无法改）、40% 在生成的点链。若你要把端到端提高 15%，点链至少要快多少倍？这个数字如果不可能达到，说明决策应该转向哪里？
