Docker 与容器化#

把模型服务"跑在裸机上"只适合演示。一旦要交付、要上 Kubernetes、要给别人一键拉起，就必须容器化。这一课讲 Docker 的核心概念、GPU 容器怎么配、怎么基于 vLLM 官方镜像做二次封装，以及用 Compose 把服务、端口、健康检查、资源限制写成可复现的配置文件。

一、概念讲解#

1. 镜像、容器与分层#

  • 镜像（image）：一个只读的、自包含的"文件系统快照 + 启动配置"，由 Dockerfile 描述如何构建；
  • 容器（container）：镜像的一个运行实例，拥有独立的进程、网络、文件系统视图，但共享宿主机内核；
  • 分层（layer）：Dockerfile 每条指令（FROM/RUN/COPY）都会产生一层，构建时逐层缓存。把变化频繁的步骤放在 Dockerfile 后面，能最大化利用缓存、加快重复构建。

对推理服务来说，镜像里最重要的几样东西：CUDA 运行时、Python 环境、推理引擎（vLLM）、以及启动命令。模型权重通常不打进镜像（动辄几十 GB，会让镜像膨胀且无法复用），而是通过 -v 挂载宿主机目录或云盘/网络存储进入容器。

2. GPU 怎么进容器#

容器默认看不到 GPU。要让 CUDA 在容器内可用，宿主机需要装 NVIDIA Container Toolkit（提供 nvidia-container-runtime），然后 docker run --gpus all 把 GPU 设备暴露进去。没有这一步，容器里 nvidia-smi 会直接报错。这也是很多"镜像能起但找不到 GPU"问题的根因。

3. 为什么用官方镜像起步#

vLLM 官方维护了 vllm/vllm-openai 镜像，内置了匹配版本的 CUDA、PyTorch、vLLM 和 OpenAI 兼容服务入口，开箱即用。不要从 python:3.11 裸镜像手搓 CUDA 环境——版本矩阵（CUDA × PyTorch × 驱动）极容易踩坑。正确的姿势是在官方镜像基础上做轻量扩展：加健康检查、加自定义启动脚本、约定自己的模型挂载路径。

4. 容器化推理的关键配置#

  • --shm-size：共享内存。PyTorch 数据加载和部分通信依赖 /dev/shm，默认只有 64MB，训练/推理常因它 OOM，建议给到 8g 以上；
  • -p 8000:8000：端口映射，宿主机端口 → 容器端口；
  • --ipc=host：共享宿主机 IPC，多进程（张量并行）时几乎必须；
  • 健康检查（healthcheck）：用 curl /health 或 /v1/models 周期性探测，容器"起得来"不等于"服务就绪"；
  • 资源限制：--gpus 限 GPU，--memory/--cpus 限 CPU 和内存，防止单个容器拖垮宿主机。

二、可运行示例#

示例 1：直接跑官方镜像#

# 拉取官方镜像并启动（模型权重挂载到 /models）
docker run --rm \
  --gpus all \
  --shm-size 8g \
  --ipc=host \
  -p 8000:8000 \
  -v /data/models:/models \
  vllm/vllm-openai:latest \
  --model /models/Llama-3.1-8B-Instruct \
  --served-model-name llama-8b

示例 2：写一个自定义 Dockerfile#

# 基于官方镜像做二次封装
FROM vllm/vllm-openai:latest

# 安装额外依赖（例如业务侧需要的健康检查/监控工具）
RUN pip install --no-cache-dir httpx

# 放一个自定义启动脚本
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh

# 覆盖入口：先做初始化，再拉起 vLLM
ENTRYPOINT ["/entrypoint.sh"]

配套的 entrypoint.sh：

#!/bin/bash
set -e
# 启动前探测 GPU 与模型目录，失败立即退出，便于排障
nvidia-smi
ls /models || { echo "模型目录 /models 不存在"; exit 1; }
# 把剩余参数原样传给 vLLM 服务入口
exec vllm serve "$@"
# 构建镜像
docker build -t my-llm-serve:0.1 .

示例 3：用 Docker Compose 编排服务#

# docker-compose.yml
services:
  vllm:
    image: my-llm-serve:0.1
    command: >
      --model /models/Llama-3.1-8B-Instruct
      --served-model-name llama-8b
      --max-model-len 8192
    ports:
      - "8000:8000"
    volumes:
      - /data/models:/models:ro        # 只读挂载权重，防止误改
    environment:
      - HF_HUB_OFFLINE=1               # 离线模式，不访问外网
    shm_size: "8g"
    ipc: host
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]      # 申请 1 张 GPU
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 30s
      timeout: 10s
      retries: 5
      start_period: 120s               # 模型加载慢，给足预热时间
# 一键拉起
docker compose up -d
# 查看健康状态
docker compose ps
# 看日志
docker compose logs -f vllm

三、练习#

  1. 在示例 3 里把 count: 1 改成 count: 2，体会多卡如何通过 Compose 的 devices 声明，并思考它与 vLLM 的 --tensor-parallel-size 2 要如何配合。
  2. 故意不写 shm_size，跑一个长上下文请求观察是否出现共享内存不足；再补上 shm_size: 8g 重试。
  3. 把 healthcheck 的 start_period 调小到 10 秒，观察 Compose 如何因为"模型还没加载完"就判定不健康，说明预热时间的作用。
  4. 思考：为什么模型权重"不打进镜像"？把它挂载成 :ro（只读）能带来哪些安全和运维上的好处？
