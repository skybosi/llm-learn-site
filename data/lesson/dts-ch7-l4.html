多机多卡排障：慢节点、拓扑错配、性能回归#

同步训练有一条残酷的规则：每个集合通信都等最慢的那个成员。一个 rank 慢 50%，整组吞吐就可能掉三成；而"集群变慢了"毫无信息量——可能是慢节点、拓扑接错，也可能是你昨天改的参数。本课给出一条从现象到结论的诊断路径。

一、概念讲解#

1. 先把现象分成三类，第一动作完全不同#

现象 特征 第一动作
慢 训练在动，但吞吐低于预期 量每 rank 单步时间分布，找离群者
停 长时间无输出，step 数不动 看超时日志与集合通信栈，而不是先调超参
报错 进程退出、异常栈 读第一条异常（往往不是最后一条）

把"慢"与"停"混谈最浪费时间：前者靠统计定位，后者几乎总是顺序/规模不一致导致的挂死，处理方式相反。

2. 慢节点为什么能拖住整组：一个算得出来的例子#

设一步 = 最慢 rank 的计算 + 一次全体同步的通信。示例 1 取 96 个 rank，95 个单步 500 ms、1 个 750 ms，通信 100 ms：

  • 全部正常 600.0 ms；有一个慢 rank 850.0 ms；整组吞吐下降 29.4%。
  • 换算成浪费：多花的 250 ms 在 96 卡上是 576 GPU·h/天。

节点内 DP=8 视角更直观：最慢卡是平均的 1.25 倍时损失 18.2%，2 倍时 47.2%，4 倍时 72.8%。"慢一点没关系"是错的，它被同步放大。

3. 定位慢节点：看分布的形状，而不是看平均值#

让每个 rank 记录自己每步的耗时（几百步即可），然后看分布：

分布形状 指向
个别 rank 持续偏高 该卡/进程的硬件或环境（降频、ECC、被抢占）
同节点多个 rank 同时偏高 该节点的共享资源：供电、散热、PCIe、NUMA、网卡
全部一起偏高且随步数恶化 通信层或存储 I/O（检查点、数据加载）
周期性尖刺 别的东西在抢资源（其它任务、日志刷盘、监控）

示例 2 就是第二行的典型指纹：node1 的中位数 621.5 ms 比全体中位数 502.0 ms 高 119 ms，而且只有该节点的一半卡偏高——这几乎可以排除网络（网络问题通常全节点一致），指向该节点的供电/散热/PCIe 链路。

只报"平均单步时间"的监控查不出慢节点：96 卡里 1 张慢 50%，平均值只动约 0.5%，吞吐却掉了 29%。

4. 拓扑错配：同一个"8 卡机器"，链路可能完全不同#

第 3 章讲过：节点内 NVLink 域、跨节点 NIC、rail 是否对齐，带宽差一个数量级。最常见的错配形态是：

  1. 同构性被打破：多数节点 8 卡全 NVLink（topo -m 显示 NV#），少数插在 PCIe switch 后（PIX/PHB）→ 处处垫底；
  2. P2P 未打开：NVLink 存在却不被使用（查 nvidia-smi topo -p2p n）→ 通信悄悄走 PCIe 或主机内存；
  3. NCCL 看到的拓扑与物理不符：NCCL_TOPO_FILE 指错、容器里拓扑文件缺失、MIG 导致枚举不一致；
  4. rail / 网卡绑定错：跨节点走了慢 rail，或同一环混用不同代际的网卡。

诊断顺序是"先证明下层没问题，再怀疑上层"：nvidia-smi topo -m → topo -p2p n → ib_write_bw / ib_write_lat（跨机点对点）→ nccl-tests 跨机对拍。如果 nccl-tests 也慢，问题在硬件/拓扑/驱动层，回 Python 调参是白费功夫。

5. 性能回归的判据：强扩展与弱扩展#

"感觉变慢了"没有可操作性，两个标准判据才可操作：

  • 强扩展（strong scaling）：总工作量固定，卡数增加时单步应变小。效率 =T理想​/T实测​，其中理想按算力线性折算；
  • 弱扩展（weak scaling）：每卡的工作量固定，卡数增加时单步应基本不变。效率 =TP0​​/TP​。

示例 3 用"计算项 + 通信项"的模型说明：强扩展效率必然随卡数下滑，因为每卡计算越小、固定通信项占比越高（128 卡只剩 42.5%）；弱扩展的下滑就是"卡数翻倍的通信与调度税"（128 卡降到 75.0%，单步 0.120 → 0.160 s）。报回归必须说清是哪种扩展。

6. 单变量原则与三个能立刻用的开关#

排障的最后一步是 A/B：一次只改一个变量，离开时撤掉诊断开关（NCCL_DEBUG=INFO 在千卡上会显著拖慢甚至撑爆日志盘）。常用工具：

  • TORCH_NCCL_TRACE_BUFFER_SIZE + TORCH_NCCL_DUMP_ON_TIMEOUT：PyTorch 在 NCCL 超时时把各 rank 的集合通信调用序列落盘（flight recorder），用于判断"谁没到"；
  • NCCL_DEBUG=INFO + NCCL_DEBUG_SUBSYS=INIT,GRAPH,TUNING：看选了哪些链路、环/树形状、算法与协议；
  • CUDA_LAUNCH_BLOCKING=1：只在"怀疑 kernel 报错但栈不对"时临时开，会严重拖慢，不能长期开。

这些都指向同一句经验：先定位到"哪一层的哪个 rank"，再谈优化。 第 8 章的三本账回答"这套配置值不值得"，排障回答"它有没有按你以为的方式在跑"。

二、可运行代码示例#

三段纯 Python（标准库）：慢节点放大效应、按节点分组的指纹识别、强/弱扩展效率。

# ===== 示例 1：一个慢节点怎么拖住整个同步组（集合通信是"全员到齐"） =====
def one_step(compute_s, comm_s):
    """一步 = 最慢 rank 的计算 + 一次全体同步的通信（同步组里所有 rank 等最慢的那个）。"""
    return max(compute_s) + comm_s

data = [0.500] * 95 + [0.750]          # 96 个 rank：95 个 500 ms，1 个 750 ms
comm = 0.100                           # 一次 allreduce 的通信时间（示例）
t_healthy = one_step([0.500] * 96, comm)
t_slow = one_step(data, comm)
print("示例 1：96 卡同步训练，1 个 rank 慢 50%")
print(f"  全部正常单步      {t_healthy*1e3:7.1f} ms")
print(f"  有一个慢 rank     {t_slow*1e3:7.1f} ms")
print(f"  整组吞吐下降      {(1 - t_healthy/t_slow)*100:5.1f}%   ← 1/96 的卡拖慢全部 96 张")
print(f"  按 24h 计，这一步多花的 GPU 时间 = {(t_slow-t_healthy)*86400*96/3600:7.1f} GPU·h")

print("\n  另一个角度：节点内 DP=8，最慢卡是平均的几倍 → 整组损失多少")
base, comm8 = 0.500, 0.060
for slow in (1.1, 1.25, 1.5, 2.0, 4.0):
    t = base * slow + comm8
    print(f"    最慢是平均的 {slow:>4.2f}× → 单步 {t*1e3:6.1f} ms，损失 {(1-(base+comm8)/t)*100:5.1f}%")

# ===== 示例 2：从每个 rank 的迭代时间反解瓶颈位置 =====
import statistics
intra = {
    "node0": [0.502, 0.501, 0.503, 0.500, 0.501, 0.502, 0.500, 0.501],
    "node1": [0.503, 0.502, 0.501, 0.502, 0.741, 0.740, 0.742, 0.741],
    "node2": [0.503, 0.502, 0.501, 0.500, 0.501, 0.502, 0.500, 0.502],
}
print("\n示例 2：按 rank 分组统计单步时间，区分“卡慢”与“通信慢”")
for node, times in intra.items():
    print(f"  {node}  中位数 {statistics.median(times)*1e3:6.1f} ms  "
          f"最大 {max(times)*1e3:6.1f} ms  极差 {(max(times)-min(times))*1e3:5.1f} ms")
allt = [t for v in intra.values() for t in v]
med, n1 = statistics.median(allt), statistics.median(intra["node1"])
print(f"  全体中位数 {med*1e3:.1f} ms；node1 的 4 张卡高出 {(n1-med)*1e3:+.0f} ms")
print("  判读：同节点内一半卡偏慢 → 先查该节点的供电/散热/PCIe 链路，而不是网络")

# ===== 示例 3：强/弱扩展的判据（计算项 + 通信项的解析模型，参数为示例量级） =====
import math
C_PER_SEQ = 0.020      # 每序列前反向时间 (s)，示例
T_COMM0  = 0.05        # 单卡基线的固定通信开销 (s)，示例
K_COMM   = 0.010       # 每翻一倍卡数，通信税增益 (s)，示例：T_comm = T_COMM0 + K_COMM*log2(P)

def t_step(micro, p):
    """单步 = 每卡计算（micro 序列）+ 通信（随 P 对数增长）。"""
    return micro * C_PER_SEQ + T_COMM0 + K_COMM * math.log2(p)

print("\n示例 3A：弱扩展（每卡 micro-batch 固定 = 2，全局 batch 随 P 增长）")
print("     P   实测单步   相对 P=8 的增量   弱扩展效率")
t8 = t_step(2, 8)
for p in (8, 16, 32, 64, 128):
    t = t_step(2, p)
    print(f"  {p:>5}  {t:7.3f} s   {t-t8:+8.3f} s        {t8/t*100:5.1f}%")

print("\n示例 3B：强扩展（全局 batch 固定 512 序列，micro = 512/P）")
TOTAL = 512
print("     P   每卡 micro   实测单步   理想单步   加速效率")
for p in (8, 16, 32, 64, 128):
    t = t_step(TOTAL / p, p)
    ideal = t_step(TOTAL / 8, 8) * 8 / p
    print(f"  {p:>5}  {TOTAL/p:9.1f}   {t:7.3f} s   {ideal:7.3f} s   {ideal/t*100:5.1f}%")
print("  判读：卡数越多，每卡那份计算越小，固定的通信项占比越高 → 强扩展效率必然下滑")

三、练习#

  1. 实现：写一个 find_stragglers(per_rank_step_times, node_of_rank)，输出三类结论：全局离群 rank、节点内一致偏慢的节点、"全部一起变慢"。用示例 2 的数据验证它能识别 node1。
  2. 解释：为什么"平均单步时间"这个指标在 96 卡规模上几乎测不出一个慢 50% 的 rank？给出具体数字（用示例 1 的数据算平均值的变化幅度）。
  3. 对比/验证：把示例 3 的 K_COMM 从 0.010 改成 0.002 与 0.050，重算 3A 与 3B 两表；说明 K_COMM 在真实系统里对应什么（提示：梯度 AllReduce、TP AllReduce、EP AllToAll 各增长多快）。
  4. 思考：某次实验把 PP 从 4 加到 8，吞吐反而下降。列出三种可能原因（气泡、通信、负载不均），并各给一个只用日志或 nccl-tests 就能完成的判别实验。
