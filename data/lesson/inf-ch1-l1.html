prefill 与 decode#

一次大模型推理请求，从"输入一段 prompt"到"输出完整回答"，内部并不是一个均匀的过程，而是被切成了两个性质截然不同的阶段：prefill（预填充，也叫提示处理）和 decode（解码，也叫生成）。理解这两个阶段，是理解 TTFT/TPOT、吞吐/延迟权衡、以及 KV Cache 为什么要存在的第一块基石。学完本课，你应当能画出一次推理的完整时序，并说出两个阶段各自的算力特征。

一、概念讲解#

1. 自回归生成是"一次并行 + 多次串行"#

大模型的文本生成是自回归的：每产生一个 token，都要把它拼回输入，再产生下一个 token，直到吐出结束符。因此一次推理在时间轴上会这样展开：

  1. prefill 阶段：把用户输入的整段 prompt（假设 S 个 token）一次性送进模型，并行算出这 S 个 token 的隐状态和注意力结果。这一步顺带产生了第一个新 token 的概率分布，从中采样得到第一个输出 token。
  2. decode 阶段：此后每生成一个新 token，就把"全部历史 + 这个新 token"再跑一遍模型。由于历史 token 的注意力结果（KV）已经被缓存，每步只新算 1 个 token，直到结束。

一句话概括：prefill 一次性"看懂"整个 prompt，decode 一个 token 一个 token 地"吐字"。

2. 两个阶段的计算瓶颈完全不同#

这是整个推理优化的核心事实，务必记住：

  • prefill 是计算密集（compute-bound）。它要并行处理 S 个 token，矩阵运算的规模是 S× 隐藏维度，GPU 的算力（FLOPS）会被打满，显存带宽反而用不满。
  • decode 是访存密集（memory-bound）。每步只处理 1 个 token，乘法运算量很小，但要把整个模型的权重从显存里读一遍。因此 decode 的耗时几乎由"权重总字节数 ÷ 显存带宽"决定，与算力关系不大。

这个差异直接决定了两件事：一是 decode 的每个 token 都很"贵"（要读几十 GB 权重）；二是当用户 prompt 很长时，prefill 会成为延迟的大头，而当回答很长时，decode 成为大头。

3. 计算量对比#

设 prompt 长度 S、生成长度 N、模型隐藏维度 d。粗略地：

  • prefill 的计算量与 S⋅d2 成正比——一次并行；
  • decode 每一步的计算量与 1⋅d2 成正比，共 N 步，总计 N⋅d2。

如果 S 和 N 都是几千 token，两阶段的计算量在同一数量级；但如果用户只问一句话（S 很小）而让模型写一篇长文（N 很大），那么 decode 主导；反之，给模型贴一大段文档做摘要（S 很大、N 较小），prefill 就主导了。

二、可运行示例#

下面的 Python 用简化参数模拟一次推理的 prefill/decode 时序，让你直观看到两阶段耗时如何随 prompt/生成长度变化。

# -*- coding: utf-8 -*-
# 模拟 prefill 与 decode 两阶段耗时，观察瓶颈如何随长度转移

def simulate(prompt_len, gen_len, d=4096, compute_ops=3.5e14,   # 模拟算力 (FLOPs/s)
             bandwidth=1.5e12,                                  # 显存带宽 (B/s)
             weights_bytes=14e9):                               # 权重字节数 (7B, FP16)
    """返回 (prefill 秒, decode 每token秒, decode 总秒)。"""
    # prefill：并行算 S 个 token，计算量 ~ S*d^2，计算密集，受算力限制
    prefill_flops = prompt_len * d * d * 2      # 一次矩阵乘约 2*S*d^2（粗估）
    prefill_time = prefill_flops / compute_ops
    # decode：每步算 1 个 token，访存密集，受带宽限制（读全部权重）
    per_token_time = weights_bytes / bandwidth
    decode_time = per_token_time * gen_len
    return prefill_time, per_token_time, decode_time

cases = [
    ("短问长答：prompt=64, 生成=512", 64, 512),
    ("长文摘要：prompt=4096, 生成=256", 4096, 256),
    ("均衡：prompt=512, 生成=512", 512, 512),
]
for name, s, n in cases:
    pf, pt, dec = simulate(s, n)
    total = pf + dec
    print(f"{name}")
    print(f"  prefill={pf*1000:6.1f} ms | decode={pt*1000:5.1f} ms/token | "
          f"decode总={dec:5.2f} s | 合计={total:5.2f} s | prefill占比={pf/total*100:4.1f}%")

运行后你会发现：

  • 短问长答：prefill 占比只有个位数百分比，decode 是绝对大头——这时候优化 decode 吞吐最划算；
  • 长文摘要：prefill 占比可能过半——这时候要优化 prefill，甚至用前缀缓存（后面章节会讲）来跳过重复计算。

三、练习#

  1. 改 prompt 长度：把 长文摘要 的 prompt 改成 8192、生成保持 256，观察 prefill 占比怎么变，说明为什么"长上下文"场景对 prefill 优化特别敏感。
  2. 改带宽：把 bandwidth 从 1.5e12 改成 3.35e12（H100 的 HBM 带宽），看 decode 每 token 时间怎么变，验证"decode 受带宽限制"的结论。
  3. 改权重：把 weights_bytes 改成 70e9（70B FP16），重跑三个 case，体会模型越大 decode 每 token 越贵。
  4. 思考：如果一个在线服务的用户大多只发一句话、模型回复两三句，从 prefill/decode 的角度，这个服务的延迟瓶颈最可能在哪一端？为什么？
