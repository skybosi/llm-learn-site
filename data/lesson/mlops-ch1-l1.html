实验追踪：什么必须记，以及追踪的 schema 与检索#

这一节要解决什么#

几乎每个团队都"有实验追踪"：训练脚本里塞一行 print(loss)，或者写进一个 CSV，或者用上了某个平台的 log_metric("acc", 0.87)。然后三个月后，产品问：

上一版模型为什么比现在这版好？能不能把当时那版重新训出来？

这时你会发现手上的记录回答不了。不是因为记得少，而是因为记的东西与要回答的问题不是同一类：

  • 你记了 acc = 0.87。可这个 0.87 是 在哪个数据集上、用哪个评分函数算出来的？如果当时的 accuracy 把无效输出算成了错、现在的算成了对，两个 0.87 根本不可比。
  • 你记了 lr = 3e-4。可这份配置从哪来？是上一版基础上改的？改之前是什么？那次改动的代码 commit 是哪个？
  • 你记了 final_loss。可"为什么这版好"的答案往往在训练过程中：它在第 3000 步就开始过拟合了，还是在第 12000 步？

这一节的目标是把"追踪"从"记几个数字"变成"为将来的一组问题建立索引"。 具体要回答：

  1. 追踪的最小充分集是什么？它怎么从"你未来要问的问题"倒推出来，而不是凭感觉列字段？
  2. 一条 run 记录的 schema 应该长什么样？为什么 config 必须能被规范化哈希，为什么 metric 必须是一个三元组而不是一个 (名字, 值)？
  3. 记录粒度（每步 vs 每次）与存储成本的关系，怎样量化"记多少步"这个决定？
  4. 检索有三种完全不同的形态（键值过滤 / 时间序列 / 血缘可达），它们各自需要什么数据结构？为什么用键值过滤去回答血缘问题必然失败？

最后一句要先立起来，它是本节所有取舍的判据：

一条记录的价值⟺它能改变一个未来的决策,追踪的设计=argschemamax​未来问题 q∑​v(q)⋅1[q 可被该 schema 回答]

"录得全"不是目标：录得全但检索不出来，等价于没录。

一、追踪的对象不是指标，是"一次实验的完整描述"#

1.1 loss 是观测，不是描述#

先把两个概念分开：

是什么 例子 谁决定它
实验的描述（declaration） 你选择了什么 代码版本、数据版本、超参、镜像、种子 你（有意的决策）
实验的观测（observation） 运行产生了什么 loss 曲线、准确率、耗时、显存峰值 环境（决策的后果）

loss 属于观测。观测无法反推描述：看到 loss=0.31 你不可能知道 learning rate 是多少。而"复现"这个动作要求的是从描述重新得到观测。所以只记观测的实验追踪，在原理上就不是追踪 —— 它是一份结果汇编。

这个区分推出一条硬规则：

凡是重新运行时会变化、且影响观测的东西，必须出现在描述里​

用这条规则扫一遍，光"超参"是不够的：数据文件的哈希会变、依赖版本会变、CUDA 版本会变、随机种子会变、甚至同一台机器换了张卡也会变。它们全部属于描述。

1.2 从反事实问题倒推最小充分集#

不要问"我该记什么"，要问"我将来要回答什么"。列出典型问题，再反推字段：

未来要问的问题 回答它必须有的字段 缺了会怎样
把这一版重新训出来 代码 commit、数据版本、超参、环境镜像、种子 只能重训出一个"相似"的模型，无法验证是谁的差异
这一版为什么比上一版差？ 上述字段 + 两版的 diff 只能猜
这个提升在另一个数据集上还在吗？ 每个指标必须带数据集标识与评分函数标识 指标不可比，可能拿 dev 比 test
训练是什么时候开始过拟合的？ 指标的逐步序列（至少到 step 粒度） 只有最终值，看不到过程
这次改动影响了哪些线上服务？ 血缘：run → artifact → deployment 无法评估影响面
这条结论有多少个配置参与比较？ 同一个实验族（family）的成员列表 + 预先声明的比较方式 无法做多重比较校正（第 4 节）

把这张表的左列并起来，就得到最小充分描述：

R∗=(codeC​​, dataD​​, hyperparamsH​​, environmentE​​, seed/RNGΣ​​, observationsM​​)

五个描述项 + 一个观测项。注意 Σ 不能并进 H：超参是"你选的"，种子在很多框架里是"框架默认的"，后者极易被忽略却直接决定复现成败（第 3 节会看到它其实还不够）。

1.3 三类记录，三种写入时机#

工程上，记录按谁来写、什么时候写分成三类，它们混在一张表里是很多追踪系统失控的起点：

类型 内容 写入时机 可变性
声明式（declaration） run 名、假设、config、代码/数据/环境引用、实验族 run 开始前（越早越好） 启动后不可改（改了就是一次新 run）
观测式（observation） 指标序列、耗时、资源峰值、异常 运行中持续写 追加，不覆盖
衍生式（derivation） 产出的权重、评测报告、导出的 ONNX、血缘边 运行结束或产物落盘时 追加；产物一旦生成不可变

为什么"声明必须在开始前完成"？ 因为运行开始后写进去的 config 是事后叙述，不是事前选择。一个常见的事故是：训练挂了，改了两个超参重跑，却把 config 覆盖到同一行 —— 于是记录里的 config 与实际训练用的不一致，这条 run 直接失去参考价值。用不可变的"启动即冻结"规则，可以让这类污染在 schema 层面就不可能发生。

二、run 的 schema：把描述写成可查询的对象#

2.1 实体与关系#

最小可用的实体模型只有 5 张表（下面的代码就是这个模型）：

runs        (run_id, name, hypothesis, family, status, started_at, ended_at,
             config_json, config_hash, code_ref, data_ref, env_ref, seed)
metrics     (run_id, name, value, step, dataset_ref, fn_ref)
artifacts   (artifact_id, kind, uri, sha256, bytes)          ← 内容寻址
run_artifacts(run_id, artifact_id, role)                     ← input / output
lineage     (parent_artifact, child_artifact, run_id)        ← 边

坐标系里有两个正交的维度，缺一不可：

  • run 内部的纵向：同一条 run 上，指标随 step 变化的序列；
  • run 之间的横向：同一份 config（或同一个实验族）下不同 run 的对比。

大量自研脚本只实现了纵向（画 loss 曲线），于是永远回答不了"哪个配置更好"；大量平台只实现了横向（表格排列），于是永远看不到"训练何时劣化"。两者都要。

2.2 config 必须可规范化哈希#

配置在程序里是嵌套字典，字典的键顺序在不同语言/序列化路径下不保证一致。所以"配置是否相同"这个判断不能靠字符串比较，必须靠规范化：

canon(x)=JSON(sort_keys(x), 无空白, 数值统一为十进制),h=H(canon(x))

三个必须固定下来的细节，每一个都能制造"同一配置两个哈希"的事故：

  1. 键序：sort_keys=True；
  2. 空白与浮点格式：separators=(',',':')，且 3e-4 与 0.0003 必须统一（否则同一意图两个哈希）；
  3. 缺省值：不写与写成 null 是否等价？必须提前声明：工程上的做法是"先与默认值字典做一次合并（defaults | cfg），再规范化"，这样"用户没写"与"用户写了默认值"被归一，代价是"显式覆盖默认值"这个意图被抹掉，需要额外一个 explicit_keys 字段保留。

h 有两个用途，都很关键：

  • 去重：同一配置重复启动（重试）不会污染统计（第 4 节的多重比较按 h 去重）；
  • 定位：h 出现在制品名与日志名里，任意一个产物都能反查它的配置。

2.3 metric 的语义是一个三元组，不是一个名字#

这是本节最容易被低估的一条。世界上不存在"accuracy"这个指标，只存在：

m=(名字n​​, 数据集版本D​​, 评分函数版本f​​)

理由很朴素：指标名称是人写的，定义是程序算的。把 (name, value) 当记录，会在三个场合直接失效：

事故 现象 正确 schema 怎么避免
换了个数据集，acc 从 0.91 掉到 0.84 结论"模型退化了" 两条记录的 D 不同，比较时被识别为不可比
评分脚本修了一个 bug（无效输出不再算对） 新旧 acc 混在一张图里 f 不同 → 断点，图上标出定义变更
同一 run 里既有 dev 也有 test 的 acc 表里两行同名指标，取到哪行看运气 (D,f) 是主键的一部分，可以精确取"test 上的那一条"

实现上，dataset_ref 与 fn_ref 都应该是内容哈希（第 2 节的制品 id），不是 "test_v2_final.csv" 这种人类字符串 —— 后者一定会出现 test_v2_final_final.csv。

2.4 artifact 引用与"输入/输出"两个方向#

制品表用内容寻址：artifact_id = sha256(字节)。这带来三个性质：

  1. 天然去重：同一份数据集被 30 个 run 使用，只存一份；
  2. 不可变：改一个字节哈希就变，不存在"同一个 id 指向不同内容"；
  3. 可校验：任何时刻可以对磁盘上的文件重算哈希，验证它没被覆盖。

run_artifacts.role 区分 input / output。只记 output 是最常见的错误：它让你能回答"这个 run 产出了什么"，却回答不了"这个 run 用了什么"，而后者才是复现的必要条件。最小规则是：

run 的输入制品集合⊇{C,D,E,tokenizer,prompt 模板,第三方权重}

最后三项经常被漏，尤其提示模板：在 LLM 系统里，它改一个词就能让评测分数动好几个点，而它常常只是代码里的一个字符串常量 —— 如果你不在启动时把它存成制品，它就随代码 commit 一起漂移，且无法从历史 run 里找回确切版本。

2.5 反面案例：把"实验标识"当成"配置"#

有些团队把 run_name 当唯一标识，命名成 exp_2026_09_22_lr3e4_final_v2。这有三个问题：

  • 不可解析：没有人能可靠地从名字里提取配置，于是任何检索都要靠人眼；
  • 不可比较：名字里没提的字段（batch、warmup、数据版本）差异不可见；
  • 会被继承：复制一个名字改两个字符，于是两条语义不同的 run 看起来是"同一实验的新版本"。

正确做法：name 只承载人类可读的假设（"warmup 从 2000 提到 5000 能否稳住后期 loss"），所有可计算的东西进 config，再加一个可选的 family（实验族）字段供第 4 节的多重比较使用。

三、粒度与成本：记多少步是可以算的#

3.1 两种粒度的用途不同#

粒度 记录什么 回答什么 成本
run 级 每个指标的最终值（或最优值） 哪次实验好 极低
step 级 指标随 step 的序列 何时劣化、是否震荡、是否早停过早 中（随步数线性增长）
batch 级 每个 batch 的 loss 数据顺序问题、坏样本定位 高（通常是 step 级的 102∼103 倍）
事件级 每次异常/重试/回退 稳定性问题 低（稀疏）

判据："这个粒度能不能回答一个 run 级记录回答不了的问题？"如果 step 级曲线的用途只是画图给人看，那么下采样（每 k 步记一次）在统计上几乎无损，却能省掉一个数量级的存储。

3.2 存储成本模型#

设 R 条 run、每条 S 步、每步 K 个指标、每行开销约 b 字节（含索引），则

存储≈R⋅S⋅K⋅b

代一组真实数字：R=200、S=2×104、K=8、b≈80 B：

200×2×104×8×80≈2.6 GB

对时序库来说这不算大；但查询成本不是线性的：画"所有 run 的 loss 曲线"要扫描 3200 万行，前端会卡死。所以实践中还有一层设计：为不同粒度建不同的保留策略。

保留规则：⎩⎨⎧​batch 级→只留统计量（均值/方差/分位）,step 级→全量，但按 k 下采样后入索引,run 级→永久​或保留 7 天k 使总点数≤103/run​

保留规则：⎩⎨⎧​batch 级→只留统计量（均值/方差/分位）,step 级→全量，但按 k 下采样后入索引,run 级→永久​或保留 7 天k 使总点数≤103/run​

下采样有一个统计陷阱必须说清：下采样会让"极小概率的尖峰"消失。如果你用 loss 尖峰来发现坏数据，那就不能只存均值 —— 需要额外存 max 与"超阈值次数"这两个极值统计量（它们不可从均值恢复）。

3.3 不要用追踪系统当日志系统#

日志是非结构化、高吞吐、短期；追踪是结构化、低吞吐、长期。把 print 全都灌进指标表的后果是：指标名爆炸（每个 f-string 一个名字），检索空间被噪声占满，第 4 节的"同一实验族"统计直接被脏数据毁掉。规则：

进指标表的条件=有固定名字∧有固定语义∧将来会被用于比较

其余的走日志，并在 run 记录里存一个日志 URI 作为制品。

四、检索：三种查询，三种数据结构#

追踪系统的价值不在于写，在于查。而"查"有三种本质不同的形态，用同一套键值索引去覆盖会失败。

4.1 形态一：键值 / 范围过滤#

"哪些 run 的 lr > 2e-4 且 optimizer = adamw"。需要的是配置字段的索引。实现路径：

方案 实现 优点 代价
全表扫描 + JSON 提取 json_extract(config_json, '$.lr') > ... 零维护 O(R)，105 条以上不可用
物化列 高频字段建真实列 快 schema 变更要迁移
倒排索引（键 → run 列表） 每个 key=value 一条索引记录 任意键都快 写入放大；需要处理"高基数键"（如 git_commit）

高基数键是易被忽略的坑：为 seed 或 data_hash 建倒排索引，索引大小会接近数据本身。工程上的折中是：只对"会被当作过滤条件的低基数键"建索引，高基数字段走全扫 + 哈希表。

4.2 形态二：时间 / 序列#

"画这 20 条 run 的 validation loss"。需要的是列式存储：同一列（value）连续存放，扫描时只读需要的列，且天然适合按 step 范围切分。用行存（如 SQLite 表）也能跑，但点数上了千万级就要换列存（Parquet / TSDB）。这是追踪平台与普通关系库分道扬镳的第一个地方。

4.3 形态三：血缘可达（本节与第 2 节的接缝）#

"这份数据集被哪些 run 用过，进而产出了哪些模型，进而被哪些服务加载？"这是一个图上的可达性问题，键值索引在原理上回答不了。为什么？

键值过滤回答的是 {r:attr(r)=v},血缘回答的是 {r:∃ 一条路径 D⇝r}

后者需要传递闭包，不能靠属性匹配表达（除非你把每个 run 的祖先集合物化成属性 —— 那就是在手工实现闭包，见 4.4）。

4.4 一个具体对比：为什么"记了数据版本"还不够#

假设每条 run 都规规矩矩地记了 data_ref。现在问：

数据 v3 里混入了 PII，需要下线。哪些模型必须重训？

  • 只有键值检索时，你能查到"data_ref = v3 的 run 列表"，得到一批中间产物（checkpoint）；
  • 但其中哪些 checkpoint 被后续的微调、量化、蒸馏继续使用了？这要求你沿 lineage 边走到底。若没建图，你只能靠人翻记录 —— 而这正是"事故响应慢"最常见的原因。

推论（值得写在团队规范里）：制品之间的关系必须在产出它的那个 run 结束时写入，不能事后补。事后补的血缘有两个必然缺陷：漏（忘了补）、错（补的时候凭记忆）。

4.5 检索接口应该长什么样#

把检索限制在"团队真正会问的问题"上，接口反而更稳定。最小集合：

# 1) 键值 + 范围
find_runs(config={"optimizer": "adamw"}, config_range={"lr": (2e-4, 1e-3)})
# 2) 指标条件（注意必须带 dataset/fn，否则不可比）
find_runs(metric=("accuracy", TEST_V3_ARTIFACT_ID, ACC_V2_ARTIFACT_ID), min_value=0.88)
# 3) 族内列表（供多重比较）
family_members(family_hash)
# 4) 影响面（血缘正向闭包）
descendants(artifact_id=D_V3)          # 下游全部制品
# 5) 归因链（血缘反向路径）
ancestors(artifact_id=MODEL_PROD, kind="dataset")
# 6) 不可复现的 run（缺关键引用）
incomplete_runs()

第 6 个查询是本节最有工程价值的一个：把它接到 CI 上，"启动时缺 code_ref/data_ref/env_ref 的训练直接失败"。这比事后写一百页规范有效得多 —— 因为它在信息还存在的时刻强制记录。

五、取舍#

决策 一侧 另一侧 判据
自动记录 vs 显式记录 框架钩子（不漏，但是"框架眼里的世界"，可能记不到你手工做的后处理） 手工 log_*（准确，但会漏） 对"无法自动感知"的步骤（人工过滤、prompt 编辑）必须显式；其余自动
记全 vs 记准 多记字段（检索噪声、腐化） 少记（不可复现） 用 1.2 的反事实表逐条论证，能回答问题的字段才留
中心化 vs 本地文件 中心库（可检索、可协作，但要维护、有隐私面） 本地 JSON/CSV（零依赖、但无法跨人比较） 团队 > 1 人，或"结论要跨时间比较" ⇒ 中心化
实时写入 vs 批量落盘 崩溃也能保住轨迹（I/O 压力、锁竞争） 结束再写（快，但挂掉就没有） 长任务（> 1 小时）必须实时；I/O 用异步队列 + 批量提交折中
用平台 vs 自研 功能全、UI 好 数据在自己手里、schema 可定制 本课程默认自研最小内核 + 可导出：schema 属于你，平台可以换

最后一条值得展开：追踪系统的真正资产是 schema 与历史数据，不是 UI。因此设计时永远保留一条"全量导出为开放格式"的路径（JSONL + Parquet + 制品清单）。当你要换平台时，导出能力就是你的迁移成本上限。

代码：一个能回答反事实问题的最小追踪器#

下面的代码只用标准库（sqlite3 / hashlib / json），实现 2.1 的 schema 与 4.5 的六类查询。注释里标出了每一处设计决策，重点看三处：config 的规范化哈希、metric 的三元组键、以及"只记 loss"的追踪器在哪些问题上失败。

"""
mlops-ch1-l1：最小实验追踪器。

设计目标：不是"记数字"，而是"让一组未来的反事实问题可被 SQL 回答"。
三处核心设计决策（见注释 ★）：
  ① config 规范化后哈希 —— 让"同一配置"成为可判定的事实
  ② metric 键为 (name, dataset_ref, fn_ref, step) —— 让"同名不同义"不可能发生
  ③ 制品内容寻址 + lineage 边 —— 让血缘查询成为图可达问题
只用标准库，可直接运行：python3 mlops_ch1_l1.py
"""
from __future__ import annotations

import hashlib
import json
import sqlite3
from collections import defaultdict, deque

SCHEMA = """
CREATE TABLE runs (
    run_id      TEXT PRIMARY KEY,
    name        TEXT NOT NULL,
    hypothesis  TEXT,              -- ★ 人类可读的假设，不进任何计算
    family      TEXT,              -- ★ 实验族：供多重比较（第 4 节）使用
    status      TEXT,
    started_at  TEXT,
    ended_at    TEXT,
    config_json TEXT NOT NULL,     -- 规范化后的完整配置（含默认值）
    config_hash TEXT NOT NULL,     -- ★ 决策①：配置指纹
    code_ref    TEXT,              -- git commit（含 dirty 标记）
    data_ref    TEXT,              -- 制品 id（内容哈希）
    env_ref     TEXT,              -- 镜像/锁文件指纹
    seed        INTEGER,
    explicit_keys TEXT             -- 用户显式写出的键（区别于"用了默认值"）
);
CREATE TABLE metrics (
    run_id      TEXT NOT NULL,
    name        TEXT NOT NULL,
    dataset_ref TEXT NOT NULL,     -- ★ 决策②：数据集制品 id
    fn_ref      TEXT NOT NULL,     -- ★ 决策②：评分函数制品 id
    step        INTEGER NOT NULL,
    value       REAL NOT NULL,
    PRIMARY KEY (run_id, name, dataset_ref, fn_ref, step)
);
CREATE TABLE artifacts (
    artifact_id TEXT PRIMARY KEY,  -- ★ 决策③：sha256(内容)
    kind        TEXT NOT NULL,     -- dataset | model | tokenizer | prompt | report | engine
    uri         TEXT NOT NULL,
    bytes       INTEGER
);
CREATE TABLE run_artifacts (
    run_id      TEXT NOT NULL,
    artifact_id TEXT NOT NULL,
    role        TEXT NOT NULL,     -- input | output
    PRIMARY KEY (run_id, artifact_id, role)
);
CREATE TABLE lineage (
    parent_artifact TEXT NOT NULL,
    child_artifact  TEXT NOT NULL,
    run_id          TEXT NOT NULL,
    PRIMARY KEY (parent_artifact, child_artifact, run_id)
);
CREATE INDEX idx_runs_config_hash ON runs(config_hash);
CREATE INDEX idx_metrics_key ON metrics(name, dataset_ref, fn_ref, step);
"""


# ---------------------------------------------------------------- 规范化
def canonical(obj) -> str:
    """★ 决策①：规范化序列化。

    三个必须固定的细节（每一个都能制造"同一配置两个哈希"的事故）：
      · 键序      -> sort_keys=True
      · 空白/分隔 -> separators 去掉空白，减少不同序列化器差异
      · 浮点格式  -> repr 会被 Python 自身规范化（3e-4 与 0.0003 的 repr 相同）
    """
    return json.dumps(obj, sort_keys=True, ensure_ascii=False, separators=(",", ":"))


def config_fingerprint(effective_cfg: dict) -> str:
    return hashlib.sha256(canonical(effective_cfg).encode("utf-8")).hexdigest()[:16]


def content_id(data: bytes) -> str:
    """内容寻址：id 由字节决定，因此不可变、天然去重。"""
    return hashlib.sha256(data).hexdigest()[:16]


def merge_defaults(defaults: dict, cfg: dict) -> dict:
    """把默认值合并进来再哈希 —— 让"没写"与"写了默认值"归一。

    代价：丢失"用户是否显式设置"的意图；所以另存 explicit_keys。
    这一步不做的话，"lr 未指定"和"lr=1e-4（默认值）"会是两个不同哈希，
    去重与族内比较都会多出一堆"伪不同"配置。
    """
    out = dict(defaults)
    for k, v in cfg.items():
        if isinstance(v, dict) and isinstance(out.get(k), dict):
            out[k] = merge_defaults(out[k], v)
        else:
            out[k] = v
    return out


# ---------------------------------------------------------------- 追踪器
class Tracker:
    def __init__(self, path: str = ":memory:"):
        self.db = sqlite3.connect(path)
        self.db.executescript(SCHEMA)

    # ---- 写入 ----------------------------------------------------
    def start_run(self, name: str, cfg: dict or None = None, *, hypothesis: str = "",
                  family: str = "", code_ref: str = "", env_ref: str = "",
                  seed: int = 42, defaults: dict or None = None) -> str:
        """★ 声明式记录必须在 run 开始前一次写完；启动后不可改。"""
        cfg = cfg or {}
        explicit = sorted(cfg)
        eff = merge_defaults(defaults or {}, cfg)
        h = config_fingerprint(eff)
        run_id = f"{h}-{seed}"
        self.db.execute(
            "INSERT OR IGNORE INTO runs (run_id,name,hypothesis,family,status,started_at,"
            "config_json,config_hash,code_ref,data_ref,env_ref,seed,explicit_keys)"
            " VALUES (?,?,?,?,?,datetime('now'),?,?,?,?,?,?,?)",
            (run_id, name, hypothesis, family or config_fingerprint({"family": name}),
             "running", canonical(eff), h, code_ref, None, env_ref, seed,
             canonical(explicit)))
        return run_id

    def add_artifact(self, kind: str, uri: str, data: bytes) -> str:
        """把制品登记进库（输入侧：数据集、tokenizer、prompt 模板、第三方权重）。

        ★ 决策③：id 来自内容哈希，所以"先登记再引用"是幂等的 ——
          同一份数据被 30 个 run 使用，库里也只有一行。
        """
        aid = content_id(data)
        self.db.execute("INSERT OR IGNORE INTO artifacts VALUES (?,?,?,?)",
                        (aid, kind, uri, len(data)))
        return aid

    def attach_input(self, run_id: str, artifact_id: str):
        """把已登记的制品挂到 run 的输入侧。

        ★ 设计决策：只挂 dataset 时额外写 runs.data_ref（把最高频的一条关系物化成列）；
          其余输入（tokenizer / prompt / 第三方权重）靠 run_artifacts 表查。
          它们同样不可省：prompt 模板改一个词就能让评测动几个点。
        """
        self.db.execute("INSERT OR IGNORE INTO run_artifacts VALUES (?,?,'input')",
                        (run_id, artifact_id,))
        row = self.db.execute("SELECT kind FROM artifacts WHERE artifact_id=?",
                              (artifact_id,)).fetchone()
        if row and row[0] == "dataset":
            self.db.execute("UPDATE runs SET data_ref=? WHERE run_id=?", (artifact_id, run_id))

    def log_metric(self, run_id: str, name: str, value: float, *,
                   dataset_ref: str, fn_ref: str, step: int = 0):
        """★ 决策②：dataset_ref 与 fn_ref 是必填参数，不是可选备注。

        强制它们必填，是为了让"同名不同义"在写入时就不可能发生 ——
        如果设成可选，半年后一定没人填，指标就退化成 (名字, 值)。
        """
        self.db.execute("INSERT OR REPLACE INTO metrics VALUES (?,?,?,?,?,?)",
                        (run_id, name, dataset_ref, fn_ref, step, float(value)))

    def log_artifact(self, run_id: str, kind: str, uri: str, data: bytes,
                     role: str = "output", parents: list[str] | None = None) -> str:
        """产物入账 + 写血缘边。★ 边在产出它的这个 run 里写，不事后补。"""
        aid = self.add_artifact(kind, uri, data)
        self.db.execute("INSERT OR IGNORE INTO run_artifacts VALUES (?,?,?)",
                        (run_id, aid, role))
        for p in parents or []:
            self.db.execute("INSERT OR IGNORE INTO lineage VALUES (?,?,?)", (p, aid, run_id))
        return aid

    def finish(self, run_id: str, status: str = "finished"):
        self.db.execute("UPDATE runs SET status=?, ended_at=datetime('now') WHERE run_id=?",
                        (status, run_id))

    # ---- 检索（4.5 的六类） ---------------------------------------
    def find_runs(self, *, config: dict | None = None, config_range: dict | None = None,
                  metric: tuple or None = None, min_value: float | None = None) -> list[str]:
        sql = "SELECT run_id FROM runs WHERE 1=1"
        args: list = []
        for k, v in (config or {}).items():
            sql += f" AND json_extract(config_json,'$.{k}') = ?"
            args.append(v)
        for k, (lo, hi) in (config_range or {}).items():
            sql += f" AND CAST(json_extract(config_json,'$.{k}') AS REAL) BETWEEN ? AND ?"
            args += [lo, hi]
        if metric:
            name, ds, fn = metric
            sql += (" AND run_id IN (SELECT run_id FROM metrics WHERE name=? AND "
                    "dataset_ref=? AND fn_ref=? AND value >= ?)")
            args += [name, ds, fn, min_value if min_value is not None else -1e18]
        return [r[0] for r in self.db.execute(sql, args)]

    def family_members(self, family_hash: str) -> list[str]:
        return [r[0] for r in self.db.execute(
            "SELECT run_id FROM runs WHERE family=?", (family_hash,))]

    def descendants(self, artifact_id: str) -> list[str]:
        """正向影响面：这份数据被撤销，下游还有哪些制品。BFS 求可达集。"""
        seen, q = set(), deque([artifact_id])
        while q:
            cur = q.popleft()
            for (child,) in self.db.execute(
                    "SELECT child_artifact FROM lineage WHERE parent_artifact=?", (cur,)):
                if child not in seen:
                    seen.add(child)
                    q.append(child)
        return sorted(seen)

    def ancestors(self, artifact_id: str, kind: str | None = None) -> list[str]:
        """反向归因链：这个模型的上游里，有哪些是 dataset（第 2 节会扩展成路径）。"""
        seen, q = set(), deque([artifact_id])
        while q:
            cur = q.popleft()
            for (parent,) in self.db.execute(
                    "SELECT parent_artifact FROM lineage WHERE child_artifact=?", (cur,)):
                if parent not in seen:
                    seen.add(parent)
                    q.append(parent)
        if kind:
            rows = self.db.execute(
                f"SELECT artifact_id FROM artifacts WHERE kind=? AND artifact_id IN "
                f"({','.join('?' * len(seen))})", (kind, *seen)).fetchall() if seen else []
            return sorted(r[0] for r in rows)
        return sorted(seen)

    def incomplete_runs(self) -> list[tuple[str, list[str]]]:
        """★ 缺关键引用的 run —— 接到 CI 上可以让这类 run 直接失败。"""
        out = []
        for rid, code, data, env in self.db.execute(
                "SELECT run_id, code_ref, data_ref, env_ref FROM runs"):
            miss = [n for n, v in (("code_ref", code), ("data_ref", data),
                                   ("env_ref", env)) if not v]
            if miss:
                out.append((rid, miss))
        return out

    def metric_series(self, metric: tuple, *, limit: int = 10) -> dict[str, list]:
        """带语义的指标序列：同名指标在 (dataset, fn) 不同时是不同序列。"""
        name, ds, fn = metric
        out: dict[str, list] = defaultdict(list)
        for rid, step, val in self.db.execute(
                "SELECT run_id, step, value FROM metrics WHERE name=? AND dataset_ref=? "
                "AND fn_ref=? ORDER BY run_id, step", (name, ds, fn)):
            out[rid].append((step, val))
        return dict(list(out.items())[:limit])

    def storage_report(self) -> dict:
        """成本模型落地：行数 × 每行字节 ≈ 存储。"""
        rows = {t: self.db.execute(f"SELECT COUNT(*) FROM {t}").fetchone()[0]
                for t in ("runs", "metrics", "artifacts", "lineage")}
        rows["metrics_est_bytes"] = rows["metrics"] * 80  # 含索引的粗估
        return rows

    DEFAULTS = {"optimizer": "adamw", "lr": 1e-4, "batch": 32, "warmup": 2000}
    t = Tracker()

    # 先登记输入制品（内容寻址）：两份数据、两个评分函数版本、一份测试集
    # ★ 这一步不能省：不登记的制品在血缘图里是"悬空节点"，反向归因会断链
    d_v2 = t.add_artifact("dataset", "s3://data/v2", b"dataset v2 rows...")
    d_v3 = t.add_artifact(
        "dataset", "s3://data/v3",
        b"dataset v3 rows... (with 3% duplicated samples)")
    acc_v1 = t.add_artifact("fn", "s3://eval/acc_v1", b"invalid output counts as wrong")
    acc_v2 = t.add_artifact("fn", "s3://eval/acc_v2", b"invalid output retried once")
    test_v3 = t.add_artifact("dataset", "s3://data/test_v3", b"test split of v3")
    tokenizer = t.add_artifact("tokenizer", "s3://tok/bpe_v4", b"bpe vocab v4")
    prompt = t.add_artifact("prompt", "s3://prompt/qa_v7", b"Answer in <=3 sentences.")

    print("=" * 78)
    print("【1】规范化哈希：同一意图必须得到同一指纹")
    h1 = config_fingerprint(merge_defaults(DEFAULTS, {"lr": 3e-4}))
    h2 = config_fingerprint(merge_defaults(DEFAULTS, {"lr": 0.0003}))
    h3 = config_fingerprint(merge_defaults(DEFAULTS, {}))
    h4 = config_fingerprint(merge_defaults(DEFAULTS, {"lr": 1e-4}))
    print(f"  lr=3e-4 与 lr=0.0003 同指纹: {h1 == h2}   ({h1})")
    print(f"  未写 lr   与 lr=1e-4(默认) 同指纹: {h3 == h4}   ({h3})")
    print("  → 若不做 merge_defaults，第三行会是 False：一个'伪不同'配置混进族内比较")

    print("=" * 78)
    print("【2】三次 run：v2 基线 / v3 数据 / v3+warmup 改动")
    fam = config_fingerprint({"family": "warmup-ablation"})
    r1 = t.start_run("Warmup 基线", {"lr": 3e-4}, hypothesis="基线，不调 warmup",
                     family=fam, code_ref="git:9f2c1a7", env_ref="img:torch2.4-cu121", seed=42,
                     defaults=DEFAULTS)
    t.attach_input(r1, d_v2)
    t.attach_input(r1, tokenizer)
    t.attach_input(r1, prompt)      # ★ prompt 模板也是制品，不是"代码里的一个字符串"
    r2 = t.start_run("换 v3 数据", {"lr": 3e-4, "data": "v3"},
                     hypothesis="v3 去重后基线是否变化", family=fam,
                     code_ref="git:9f2c1a7", env_ref="img:torch2.4-cu121", seed=42,
                     defaults=DEFAULTS)
    t.attach_input(r2, d_v3)
    r3 = t.start_run("v3 + warmup 5000", {"lr": 3e-4, "warmup": 5000, "data": "v3"},
                     hypothesis="后期 loss 震荡是否由 warmup 太短造成", family=fam,
                     code_ref="git:9f2c1a7", env_ref="img:torch2.4-cu121", seed=42,
                     defaults=DEFAULTS)
    t.attach_input(r3, d_v3)

    # 逐步指标：step 级记录，才能回答"什么时候开始劣化"
    for rid, (base, late_spike) in ((r1, (0.60, 0.02)), (r2, (0.585, 0.01)),
                                    (r3, (0.586, 0.005))):
        for step in range(0, 2001, 250):

            t.log_metric(rid, "val_loss", decay + spike, dataset_ref=test_v3,

        # ★ 同一 run 里 acc 有两条：dev 与 test；还有两个评分函数版本
        t.log_metric(rid, "accuracy", 0.86 + late_spike, dataset_ref=test_v3,

        t.log_metric(rid, "accuracy", 0.91 + late_spike, dataset_ref=d_v2,

    m3 = t.log_artifact(r3, "model", "s3://m/v3-w5000.pt", b"weights-3", parents=[d_v3])
    ft = t.log_artifact(r3, "model", "s3://m/ft.pt", b"weights-ft", parents=[m3])
    eng = t.log_artifact(r3, "engine", "s3://m/ft.trt", b"engine-bytes", parents=[ft])
    for r in (r1, r2, r3):
        t.finish(r)

    print("=" * 78)
    print("【3】键值 / 范围 / 指标检索（三种过滤可以叠加）")
    print("  lr 在 [2e-4, 1e-3] 的 run:", len(t.find_runs(config_range={"lr": (2e-4, 1e-3)})))
    print("  test 上 accuracy >= 0.86 的 run:",

    print(f"    同一 run 里 accuracy 还存了 {d_v2}(dev) 上 acc_v1 的版本，二者不可比")

    print("=" * 78)
    print("【4】step 级序列回答'何时劣化'")
    series = t.metric_series(("val_loss", test_v3, acc_v1))

        pts = series[rid]

        print(f"  {rid}  step0/1500/2000 = {jumps}")
    print("  → r1 在第 1500 步后抬升 +0.02，r3 只抬 +0.005：假设'warmup 太短'被支持")

    print("【5】血缘：数据撤销时的影响面 / 模型出问题时的归因链")

    print(f"  ★ 只用键值检索时你只能得到'用过 v3 的 run'，")

    for rid, miss in t.incomplete_runs():

    print("=" * 78)
    print("【7】存储成本模型（2.6 GB 是怎么来的）")
    print(" ", t.storage_report())

    print(f"  设计估算: R={R} run × S={S} step × K={K} 指标 × {b}B "

    print("  → 查询成本不是线性的：该量级必须下采样入索引，并保留 max/超阈次数等极值统计量")

七处关键设计决策：

  1. start_run 一次写完全部声明，之后不可改。这让"训练中途改配置再覆盖记录"在接口上不可能发生 —— 事故预防靠 schema，不靠自觉。
  2. merge_defaults 先合并再哈希，处理"没写 = 默认值"的归一。代价是丢失显式意图，所以另存 explicit_keys：归一是为了比较，保留是为了审计，两者不冲突。
  3. log_metric 把 dataset_ref/fn_ref 设为必填。这是本课最值钱的一行接口设计：可选参数等于没参数，半年后一定没人填。
  4. attach_input 对 dataset 类制品额外写 runs.data_ref。理由是检索便利：最常见的查询是"哪些 run 用了这份数据"，把最高频的一条关系物化成列，避免每次都走 join。
  5. log_artifact(parents=...) 在产出那一刻写血缘边。演示里 engine 是从 ft 微调/编译来的，它不在任何 run 的 data_ref 里：只有图能把它和数据 v3 连起来。这就是 4.4 那段的可执行版本。
  6. incomplete_runs 把"不可复现"变成一个可查询的状态，而不是一种感觉。这是把规范变成 CI 门禁的接缝。
  7. storage_report + 手算模型并列：先有量级判断（GB 级），再决定下采样策略；max/超阈次数这类极值统计量必须单独存，因为它们不可从均值恢复。

练习#

  1. 反事实倒推：下面五个问题分别需要 schema 里的哪些字段？如果字段缺失，你会用什么"事后补偿"手段，代价是什么？ （a）"这次训练用的是哪版 tokenizer？" （b）"这个模型是从哪个 checkpoint 继续训的？" （c）"同一批配置换了个 seed，结论还成立吗？" （d）"上周那条 0.89 是在 dev 还是 test 上？" （e）"把这条 run 的容器镜像找出来重建环境。"
  2. 规范化哈希的边界：设计 canon 时，下面四组输入应不应该算同一个配置？给出你的规则并说明代价：（a）{"a": 1} 与 {"a": 1.0}；（b）{"a": null} 与 {}（a 有默认值）；（c）列表顺序 [1,2] 与 [2,1]（当它是 layers 时 vs 当它是 tags 时）；（d）包含本地绝对路径的字段。
  3. 粒度与成本：某团队每天跑 60 条 run，每条 3 万步、每步 12 个指标。按 b=80 B 算年存储量；若改成每 50 步记录一次并额外记录每个指标的 max 与"超阈值次数"，年存储量是多少？这会不会让某类问题变得无法回答？举例说明。
  4. schema 演进：团队要在 metrics 上增加"指标的置信区间上下界"（来自 n 个种子的重复）。请给出迁移方案（新增列 / 新增表 / 新实体），并说明每种方案对"已有历史数据"的兼容性。提示：历史数据没有 CI，不能假装它是 0 宽。
  5. 检索性能：给出一个"配置有 200 个键、其中 5 个是低基数、3 个是高基数（commit/seed/data_hash）"的场景。设计索引方案，并估算倒排索引的规模（用键的取值数 × 平均 run 数表示）。哪种查询会退化到全表扫描？
  6. 设计题：为一个"用 LLM 做合同审阅"的系统设计追踪 schema。要求：trace 一条请求（prompt 版本、检索到的文档 id、模型版本、token 用量、延迟、人工反馈），设计至少两张表与三个查询，并说明哪些字段必须内容寻址。最后回答：如果只在最后记录了"用户是否采纳"，你会失去哪三个分析能力？
  7. 开放题（与第 2 节衔接）：你的追踪系统里，code_ref 记的是 git:9f2c1a7，但那天的训练脚本在跑之前有人手工改了一行（没有提交）。请设计一个机制，让"未提交改动"这件事至少留下痕迹；再说明为什么这个机制不能做到 100% 可靠。

小结#

  • 追踪的对象是"一次实验的完整描述"，不是它的观测。观测（loss/acc）无法反推描述；而"复现"要求从描述重建观测。硬规则：凡是重新运行会变化、且影响观测的东西，必须在描述里。
  • 最小充分集 R∗=(C,D,H,E,Σ,M) 应从"未来要问的反事实问题"倒推，而不是凭感觉列字段。种子 Σ 要单列，因为它常是框架默认、最易被忽略。
  • 三类记录要分开：声明式（启动前写完、不可改）、观测式（追加）、衍生式（产物与血缘边，产出即写）。声明在运行中可改，等于记录在事故中失效。
  • config 必须规范化后哈希（键序、空白、浮点、缺省值四条规则），metric 必须是三元组 (n,D,f) 加 step，制品必须内容寻址 —— 这三条分别解决"配置是否同一"、"指标是否可比"、"产物是否同一"三个可判定性问题。
  • 检索有三种形态：键值过滤（倒排索引，注意高基数键）、时间序列（列存 + 下采样，但极值统计量要单独存）、血缘可达（图上的传递闭包）。键值索引在原理上回答不了血缘问题 —— 只记 data_ref 无法找到经微调/量化链传下去的下游制品。
  • 成本是可算的：存储≈R⋅S⋅K⋅b；决定下采样率的是"哪些问题必须保留"，不是磁盘大小。
  • 把"不可复现"变成一个可查询状态（缺 code_ref/data_ref/env_ref 的 run），并接到 CI 上：在信息还存在的时刻强制记录，胜过事后一百页规范。

下一节：这一节把"一次实验"记全了。但 run 之间的引用关系还只是零散的 ref 字符串 —— 数据从哪来、模型往哪去、同一份数据的两次快照是不是同一份"逻辑数据"，都还没有答案。第 2 节要把这些引用升级成版本化的制品与血缘图，并回答一个本节只提了一句的问题：为什么"模型版本"单独存在时，归因在原理上不可能。
