激活与框架开销与 OOM#

把权重和 KV cache 都算进去，理论上显存应该够用了，可程序还是报 OutOfMemoryError——剩下的"隐形开销"往往藏在激活张量和框架自身里。学完本课，你应当能列出一张完整的"峰值显存账单"，判断一次推理会不会 OOM，并知道哪些手段能把它压下去。

一、概念讲解#

1. 激活：转瞬即逝的中间张量#

前向传播时，每一层都会产生中间结果——注意力分数、softmax 输出、前馈网络的隐层状态，这些统称激活（activation）。与权重不同，激活用完即弃，推理时不必像训练那样把它们全部存下来做反向传播，所以单次推理的激活占用通常远小于权重。但当批量大、序列长时，某些激活（尤其是词表很大的输出 logits，大小约 batch × seq × vocab × bytes）依然会形成可观的瞬时峰值。

2. 框架开销：看不到但确实存在#

即便你一个张量都不算，推理框架一启动就会吃掉一批显存：

  • CUDA 上下文（context）：驱动为 GPU 分配的工作区，通常数百 MB 到 1～2 GiB。
  • 内存分配器：PyTorch 的 caching allocator 为了性能会缓存已释放的块，导致"已 free 但未归还"的显存存在。
  • 碎片：反复申请/释放不同大小的张量会留下无法利用的缝隙。

这些加起来，轻则几百 MB，重则几 GiB，是很多"明明算下来够用却 OOM"的幕后原因。

3. 峰值显存账单与 OOM#

一次推理的峰值显存大致是四部分之和：

峰值=权重+KV cache+激活峰值+框架开销

当请求的峰值超过卡上可用显存（总容量减去系统已占用）时，就发生 OOM（Out of Memory，显存耗尽）。OOM 不是"参数太大"这么简单，而是这张账单里任何一项超支都可能触发。

4. 缓解 OOM 的手段#

对应账单的每一项，都有对应的省钱办法：

  • 压权重：INT8/INT4 量化；
  • 压 KV cache：GQA/MQA、缩短上下文、分页注意力（PagedAttention，vLLM） 消除缓存碎片；
  • 压激活：减小 batch、限制最大序列长度；
  • 摊开销：多卡张量并行把权重和激活切到多张卡上（下一章讲互连）。

二、可运行示例#

下面写一个"峰值显存估算器"：输入模型规模、上下文、批量，估算四部分显存并判断是否 OOM。

# -*- coding: utf-8 -*-
# 峰值显存 ≈ 权重 + KV cache + 激活峰值 + 框架开销

def weight_gb(params, bytes_per_param=2):
    return params * bytes_per_param / (1024 ** 3)

def kv_cache_gb(L, H_kv, D, seq, batch=1, bytes_per_elem=2):
    return 2 * L * H_kv * D * seq * batch * bytes_per_elem / (1024 ** 3)

def logits_gb(seq, batch, vocab, bytes_per_elem=4):
    """输出层 logits 张量：batch × seq × vocab，常以 FP32 存在。"""
    return seq * batch * vocab * bytes_per_elem / (1024 ** 3)

def peak_gb(params, L, H_kv, D, seq, batch, vocab, overhead_gb=1.5):
    """把四部分加总，返回各分项与峰值。"""
    w = weight_gb(params)
    kv = kv_cache_gb(L, H_kv, D, seq, batch)
    act = logits_gb(seq, batch, vocab)          # 这里只算 logits 这一项做近似
    return {"权重": w, "KV cache": kv, "激活(logits)": act, "框架开销": overhead_gb,
            "峰值": w + kv + act + overhead_gb}

# 以 LLaMA-3 8B (GQA) 为例：8B 参数、32 层、8 KV 头、头维度 128、词表约 128k
bill = peak_gb(params=8e9, L=32, H_kv=8, D=128,
               seq=8192, batch=4, vocab=128_256)

print("峰值显存账单（LLaMA-3 8B，seq=8192，batch=4）：")
for k, v in bill.items():
    print(f"  {k:<12} {v:>7.2f} GiB")

# 判断：能否塞进给定显存的卡？
for vram in (24, 48, 80):
    ok = bill["峰值"] <= vram
    print(f"  {'能' if ok else '不能'}装进 {vram} GiB 卡（峰值 {bill['峰值']:.2f} GiB）")

# 定位元凶：把 batch 或 seq 调大，看哪一项先失控
print("\n固定 batch=1，观察 KV cache 随上下文如何反超权重：")
for seq in (2048, 8192, 32768, 131072):
    b = peak_gb(8e9, 32, 8, 128, seq, batch=1, vocab=128_256)
    print(f"  seq={seq:>6} -> 权重 {b['权重']:>6.2f} GiB，KV {b['KV cache']:>7.2f} GiB，峰值 {b['峰值']:>7.2f} GiB")

运行后你会发现：batch=1 时权重占大头；但 seq 一旦拉到 32K、128K，KV cache 迅速反超，峰值随之突破常见单卡容量——这就是"KV cache 是 OOM 元凶"在账单上的直观呈现。

三、练习#

  1. 手算峰值：设权重 14 GiB、KV cache 2 GiB、激活 0.5 GiB、框架开销 1.5 GiB，峰值是多少？能否装进 16 GiB 的卡？
  2. 找元凶：在上面的代码里把 vocab 改成 32000 和 320000，观察"激活(logits)"一项的变化，说明超大词表为什么也会成为显存负担。
  3. 改 overhead：把 overhead_gb 从 1.5 改成 0.5 和 3.0，观察判断结果是否翻转，解释为什么"框架开销"估算不准会导致实际 OOM。
  4. 压账单：保持模型不变，通过调低 seq 或 batch 让 8B 模型在 24 GiB 卡上不 OOM，找出临界组合。
  5. 思考：为什么推理时激活占用通常远小于训练？如果训练要存每层激活做反向传播，激活这项会变成账单里多大的部分？
