完整案例：一个可运行的最小 RAG 系统、评测脚本与决策记录#

这一节要解决什么#

前两节分别给出了"从 SLO 反推架构"与"用评测驱动迭代"的方法。这一节把方法落到代码上：一个能跑、能被评测、能被诊断、能被改进的最小 RAG 系统。

它必须满足四个要求，缺一个就不算"完整案例"：

  1. 端到端可运行：只用 Python 标准库 + numpy，不依赖任何向量库或框架；
  2. 每个模块都能被单独消融：稀疏 / 稠密 / 混合 / 重排 可以逐个开关；
  3. 带工程底线：ACL 前置过滤 + canary 断言、带租户键的缓存、段式索引与回滚；
  4. 必须包含一次真实的"诊断 → 修复"：不是所有数字都好看，而是从评测结果里读出病根并改对。

这个案例最有价值的部分不是"它跑通了"，而是它的评测表第一次跑出来是这样的：

sparse                0.300   0.250     0.200     0.200
dense                 0.050   0.042     0.033     0.033
hybrid                0.250   0.068     0.033     0.033
hybrid+rerank         1.000   0.742     0.483     0.483     <- 召回 1.000，答案只有 0.483

召回@10 = 1.000，答案正确率只有 0.483。 这个 gap 就是全课反复讲的那句话的实证："找回来了"和"用上了"是两件事。而本节的后半部分会给出这个案例的病根与修复 —— 修复后答案正确率从 0.483 抬到 0.983。

要回答四个问题：

  1. 一个最小但完整的 RAG 系统由哪些模块组成？每个模块的"为什么"与失效条件是什么？
  2. 消融实验怎么设计才能一次看到全链路的贡献？
  3. 当"召回好、答案差"时，怎么定位到具体模块？
  4. 这个案例里的四个架构决策，各自的依据与"何时重审"是什么？

结论先放在这里：本案例的评测表给出了一个可复用的诊断判据 —— 若 recall@k 高而 答案正确率 低，瓶颈一定在排序/装配/生成，不在召回；反之才修召回。⚠️ 实测：v1 重排后的 recall@10 = 1.000、答案正确率 0.483（gap +0.517）；病根是重排特征只在 chunk 文本里查找实体键，而切分把键切到了另一个 chunk，导致该交互信号丢失。把键匹配提升为文档级特征（v2）后，MRR 0.742→0.992、答案正确率 0.483→0.983。

一、案例设定与需求量化#

1.1 场景#

一个多租户内部知识库问答。按第 7 章第 1 节的问卷量化：

需求项 取值 说明
语料 ⚠️ 合成：60 个黄金实体 + 180 篇竞争文档 + 200 篇同主题噪声 + 6 篇 canary 规模小到单机秒级，但足以暴露每条机制
租户 3 个（t0/t1/t2） 每租户 2 篇 canary 诱饵
查询类型 单跳事实（"某领域的某属性最新值是多少"） 全课的主线任务
延迟 P95 < 2s（本地 stub） 案例里的 ms 数字是单机相对值，不可外推
质量目标 recall@10 ≥ 0.9、引用一致率 ≥ 0.8 对应第 7 章第 2 节的指标树
成本约束 示例：成本 ∝ 上下文块数 用于演示"质量-成本"对照

为什么选这个规模：它能在秒级跑完全部消融 + canary 测试 + 回滚断言，因此可以作为 CI 的一部分。能进 CI 的案例，才是能持续的案例。

1.2 语料为什么这样构造#

⚠️ 合成数据。每个查询 i 对应：

  • 1 篇黄金文档：使用属性的同义词（"营收"→"收入"），带"最新/现行"标记，含正确答案 i；
  • 3 篇竞争文档：使用属性的精确词（"营收"），带"历史/废止"标记，含旧值 900+j；其中 1 篇属于同一租户，另 2 篇属于其他租户；
  • 200 篇同主题噪声：稀释候选池，让"检索回全量"变得不平凡。

这个构造精确地制造了三种真实困境：

构造 制造的困境 全课对应
黄金用同义词 词汇不匹配（稀疏的强项失效） ch1-l2
竞争文档用精确词 + 旧值 词法匹配对，事实错 ch3-l1（相似度≠相关性）
2/3 竞争文档属于他租户 不做 ACL 前置就会污染结果 ch6-l3

关键设计：黄金文档的键（K{i}）与值（i）在文本里相隔较远，会被切分切到不同 chunk。这不是疏忽，而是刻意复现一个真实病根 —— 本节的 v1 → v2 修复正来自它。

二、系统组成：逐模块的"为什么"#

案例共 10 个模块。每个模块给出设计理由与失效条件。

2.1 切分与内容寻址 id#

  • 做法：滑窗切分（窗口 14 token、重叠 4），chunk_id = sha1(doc_id | version | span | chunker_ver | embedder_ver)。
  • 为什么：内容寻址让"重跑流水线"幂等（ch6-l1）；把 chunker_ver 与 embedder_ver 写进 id，使版本变更时全量失效自动发生。
  • 失效条件：窗口过大 → 键与值落在同一 chunk 的概率上升（本例中反而更好）但噪声增加；重叠过大 → 重复证据挤占预算（ch5-l2）。

2.2 稀疏检索 BM25#

  • 做法：标准 BM25，k1​=1.2、b=0.75（ch1-l2 的默认值）。
  • 为什么：精确词匹配是稀疏的强项，"营收"这种属性词命中就能带来高 idf 分。
  • 失效条件：黄金用同义词 → 词法不匹配；竞争文档用精确词 → 稀疏会系统性地偏爱旧值文档。⚠️ 实测 sparse 答案正确率只有 0.200，低于随机猜测的 1/2 量级 —— 它不是"召回不到"，而是"稳定地选错"。

2.3 稠密检索（代理）#

  • 做法：hashing-trick 随机投影 + 主题向量（权重 1.8），余弦相似度。
  • 为什么这样写：真实双塔的价值是语义泛化（同义词映射到相近区域）。随机投影本身没有这个能力，所以我显式加入"主题向量"来模拟"主题级泛化"。这是一个代理，不是双塔。
  • 诚实的局限：主题向量让同一主题的所有 chunk 相似度几乎相同（⚠️ 实测同一主题的多个 chunk 得分都是 0.8848），因此它在主题内几乎没有区分能力；且黄金用同义词反而使它的词法分量更低。⚠️ 结果：dense 的 recall@10 = 0.050、答案正确率 0.033。
  • 失效条件：不要把本案例的 dense 数字当成真实双塔的表现。 真实双塔在本任务上 recall@10 通常远高于此；本节保留这个弱代理的原因见 §2.4。

2.4 RRF 融合 —— 一个必须如实报告的负结果#

  • 做法：1/(60+rank) 的倒数排名融合（ch3-l3）。
  • 预期：融合应优于任一单路。
  • 实际：⚠️ hybrid 的 recall@10 = 0.250、答案正确率 0.033 —— 低于 sparse 的 0.300 / 0.200。
  • 为什么：RRF 给每一路同等的信任。当其中一路（本案例的稠密代理）的排序接近随机时，它注入的不是互补信息而是噪声；RRF 无法识别"这一路不可信"。
  • 这正好验证了 ch3-l3 的判据：融合的收益取决于互补度，而互补度必须在真实数据上测出来，不能假设。"我们上了混合检索"不等于"效果更好"。
  • 工程处置：见 §4 的 ADR-001 —— 在稠密路未达标前，不单独依赖混合，把它作为候选而非默认。

2.5 交互式重排#

  • 做法：对 RRF 融合后的池（默认 50）逐候选打分：

score=baseRRF​+0.9⋅overlap+0.35⋅1[非陈旧]+0.25⋅1[键在 chunk 文本中]

  • 为什么：这是 cross-encoder 的代理 —— 它引入了 query×chunk 的交互特征（overlap）与文档级元数据（新鲜度）。真实 cross-encoder 用完整注意力替代这些手工特征，但"引入交互"这个机制是同一个。
  • 失效条件：特征必须是模型能看到的。⚠️ v1 的 adjacency 特征在 chunk 文本里找键，而切分把键切到了另一个 chunk —— 于是这个特征在黄金文档上从不触发。这就是本案例的病根（§3.3）。

2.6 ACL 前置过滤#

  • 做法：allow = ACL[tenant] 传入检索器，在打分阶段就跳过无权文档（ch6-l3 的实现 C）。
  • 为什么：post-filter 的可用条数 ∼Binomial(k,s)，s 小时功能不可用。
  • 失效条件：ACL 的更新必须走墓碑 + manifest 切换（ch6-l1），否则撤权不生效。

2.7 预算装配#

  • 做法：按重排分从高到低贪心，跳过"没有新增 token"的 chunk，直到 120 token 预算用尽（ch5-l2）。
  • 为什么：覆盖度贪婪能避免"多个 chunk 讲同一件事"。
  • 失效条件：预算过小 → 证据不足；per_chunk=14 是估算值，真实系统应用真实 tokenizer 统计。

2.8 抽取式生成 stub#

  • 做法：从入选证据里取分数最高的那一块，返回它的值 + 引用 id。
  • 为什么：完全可复现、不调用 LLM，因此评测不受生成随机性污染。这让"检索/排序"的问题能被干净地暴露出来。
  • 失效条件（重要）：它测不出第 5 章第 3 节那些生成层问题（位置折扣、干扰、先验冲突、引用装饰）。这是本案例最大的局限：它把 RAG 简化成了"检索+排序"，生成层被替换成了一个确定性函数。

2.9 带租户键的缓存#

  • 做法：key = sha1(tenant | manifest | acl_fingerprint | query)。
  • 为什么：缺任一维度都会造成隐蔽 bug（ch6-l2 §4）：缺 tenant → 跨租户泄漏；缺 manifest → 索引更新后返回旧内容；缺 acl_fingerprint → 权限变更后越权。
  • 失效条件：查询归一化不足会降低命中率；TTL 无法处理"文档更新"（需要 doc→key 反向失效）。

2.10 段式索引与回滚#

  • 做法：SegmentIndex（append-only 段 + 墓碑 + manifest），snapshot() / rollback()。
  • 为什么：可回滚是可上线的底线（ch6-l1）。
  • 失效条件：段数与墓碑比例需要压实阈值，否则查询放大。

三、评测脚本与消融实验#

3.1 指标#

指标 定义 作用
recall@k 黄金文档是否出现在最终 top-k 召回能力（含排序在 k 内的名次）
MRR 黄金文档名次的倒数均值 排序精细度
答案正确 抽取值是否等于期望值 端到端（stub 下等于"top-1 是黄金"）
引用一致 引用 chunk 是否属于黄金文档 引用可信度
P50(ms) 单机耗时中位数 仅相对比较，不可外推
成本 ∝ 上下文块数 质量-成本对照
上下文块 平均入选块数 预算装配的实际效果

3.2 消融表#

⚠️ 合成数据，N=60 查询，k=10，预算 120 token：

配置 recall@10 MRR 答案正确 引用一致 上下文块
sparse 0.300 0.250 0.200 0.200 2.0
dense 0.050 0.042 0.033 0.033 1.1
hybrid 0.250 0.068 0.033 0.033 2.0
hybrid+rerank (v1) 1.000 0.742 0.483 0.483 8.0
hybrid+rerank-v2 1.000 0.992 0.983 0.983 6.8

三个读数：

  1. 重排带来最大的一次跃迁（recall 0.250→1.000）。因为在 RRF 池（50）里已经包含了黄金文档，而重排的特征把它提到了前面。
  2. v1 的 recall 已满分，答案却只有 0.483 —— 这是本节的核心诊断信号。
  3. v2 只改了一个特征，答案正确率 +0.500，而且上下文块数还下降了（8.0→6.8）—— 更好的排序让更少的证据就够用，质量与成本同向改善（不是权衡）。

3.3 诊断：为什么"召回满分、答案只有一半"#

判定链条（第 7 章第 2 节的失败分类 + 第 5 章第 3 节的反事实）：

recall@10 = 1.000  -> 黄金证据确实进了 top-10          （不是召回失败）
MRR = 0.742        -> 黄金证据的平均名次约 1.35        （排序不够靠前）
答案 = 0.483       -> 生成取的是"分数最高的入选块"      （top-1 常常不是黄金）

于是问题定位在重排的特征上。检查 v1 的三个特征：

特征 作用对象 在黄金文档上的实际取值 问题
overlap chunk 文本 × 查询 较低（黄金用同义词，与查询词不重叠） 反而有利于竞争文档
freshness 文档元数据（非陈旧） +0.35（正常触发） 无
adjacency chunk 文本里是否含键 0（键被切到另一个 chunk） 特征从未触发

病根确定：v1 想用"实体键是否匹配"来区分"同一属性的新旧值文档"，但这个信号只在 chunk 文本里找，而切分把键切走了。因此 v1 手里没有任何区分新旧值的有效特征，只能靠 freshness 的 0.35 与噪声竞争 —— 于是 top-1 常常落在陈旧文档上。

这是一个"特征可见性"问题，不是"模型能力"问题。 它和真实系统里的 cross-encoder 失效同源：特征工程假设了"模型能看到的输入"，而输入被上游（切分）改变了。

3.4 修复（v2）与验证#

v2 只加一项：把键匹配提升为文档级交互特征 ——

key_match=0.60⋅1[doc.key∈query]

⚠️ 实测：MRR 0.742→0.992、答案正确率 0.483→0.983、上下文块 8.0→6.8。

注意 v2 的实现选择：它没有改切分（把键和值切到同一 chunk），而是把信号提升到文档级。理由见 ADR-005：改切分会触发全量重嵌入（ch6-l1 的代价表），而改重排特征只影响在线打分。"先用最便宜的杠杆验证假设"是调优顺序的原则。

3.5 k 与重排池的扫描#

k 扫描（v2）：

k recall@k MRR 答案正确 上下文块
1 0.983 0.983 0.983 1.0
3 1.000 0.992 0.983 3.0
5 1.000 0.992 0.983 4.6
10 1.000 0.992 0.983 6.8

读数：k≥3 之后指标完全饱和，而上下文块数继续涨（预算被更多低分块填满）。这与第 5 章第 2 节的结论一致：证据的边际收益在覆盖饱和后为零（甚至为负，因为干扰）。所以本案例的合理工作点是 k≈3∼5，不是 10。

四、决策记录（ADR）与下一步#

ADR-001：暂不单独依赖混合检索，以稀疏为基线#

  • 背景：稀疏 recall@10 = 0.300、稠密代理 0.050、混合 0.250。混合低于稀疏。
  • 决策：保留 hybrid 作为可选模式，默认配置使用"混合 + 重排"；但不把"混合本身"写进收益承诺。
  • 替代方案：① 直接上混合并宣称收益（被否：本地数据不支持）；② 放弃稠密路（被否：真实双塔的语义泛化能力尚未被本代理代表）。
  • 理由：RRF 假设两路都可信；本案例的稠密代理排序接近随机，融合注入的是噪声（ch3-l3 的互补度判据）。
  • 后果：需要为"稠密路是否可信"建一个可测判据（单路 recall@10 与互补度），并在换真实模型后重测。
  • 何时重审：接入真实双塔且其单路 recall@10 ≥ 0.6 时；或互补度（两路结果集的 Jaccard 逆指标）显著上升时。

ADR-002：ACL 必须前置过滤#

  • 背景：语料中 2/3 的竞争文档属于其他租户。
  • 决策：allow = ACL[tenant] 在打分阶段生效；canary 对抗测试进 CI。
  • 理由：post-filter 的可用条数 ∼Binomial(k,s)（ch6-l3），权限与本任务相关性无关，s 小时效用崩塌。⚠️ 实测：canary 交叉断言 12 条、泄漏 0 → PASS。
  • 后果：检索器必须接受 allow 参数；所有旁路（导出、评测、调试）都必须走同一入口。
  • 何时重审：租户数超过数百、或出现"大租户独占索引"的合规要求时，改为分区索引。

ADR-003：重排池 = 50#

  • 背景：池 0/10/50/200 的实测如上。
  • 决策：池 = 50。
  • 理由：10→50 是 recall 0.250→1.000 的关键区间；50→200 的边际质量增益为 0，成本仍上升。
  • 后果：每查询多约 50 次候选打分；需要重排模型的版本管理。
  • 何时重审：语料规模或查询分布变化导致"黄金文档名次分布"右移时（应重新扫池）。

ADR-004：缓存键必须带 tenant、acl 指纹与 manifest#

  • 背景：多租户共享缓存。
  • 决策：key = sha1(tenant | manifest | acl_fp | query)。
  • 理由：⚠️ 实测：同租户第 2 次查询命中（命中 1 次）；他租户同问不命中（未命中），因为 key 含 tenant 与权限指纹。缺任一项都会造成越权或陈旧内容（ch6-l2 §4）。
  • 后果：跨租户命中率下降（失去了"全局热门问题"的复用），但这是隔离的必要代价。
  • 何时重审：引入公共/共享语料分层时（公共部分可以跨租户共享，但必须与私有部分分键）。

ADR-005：先用文档级键匹配特征修复排序，而不是改切分#

  • 背景：v1 的 adjacency 特征因切分而失效（§3.3）。
  • 决策：在重排中加入文档级 key_match 特征（v2），暂不改切分参数。
  • 替代方案：① 缩小窗口让键与值同 chunk（成本：全量重嵌入 + 重建索引，ch6-l1）；② 增大重叠（成本：token 预算上升，ch5-l2）；③ 不修（质量不达标）。
  • 理由：v2 在零索引成本下把答案正确率从 0.483 抬到 0.983；①的预期收益不明确而代价确定。
  • 后果：重排器依赖文档级键的可得性；若未来把"键"改成多字段实体，需要同步更新该特征。
  • 何时重审：当切分本身被证明是其他失败的主因时；或当 key_match 对多实体查询失效时。

"""⚠️ 合成数据：最小可运行 RAG 系统 + 评测脚本。
   包含：切分/内容寻址 id、BM25、稠密代理（hashing-trick 随机投影）、RRF 融合、
   交互式重排、ACL 前置过滤、预算装配、抽取式生成 stub、带租户键的缓存、
   段式索引与回滚、消融评测、canary 对抗测试。
   ⚠️ 稠密表示是随机投影代理（不具备真实双塔的语义泛化）；生成是抽取式 stub（不调用 LLM）；
      语料为构造数据 —— 因此本文件的绝对数值不代表任何真实系统水平，只用于演示方法与结构。"""

# ============ 0. 合成语料 ============
TOPICS = [f"领域{t}" for t in range(10)]
ATTRS = ["营收", "延迟", "成本", "召回率", "吞吐"]
ATTR_SYN = {"营收": "收入", "延迟": "响应时间", "成本": "开销", "召回率": "查全率", "吞吐": "处理能力"}
rng = np.random.default_rng(2026)

@dataclass
class Doc:
    doc_id: str; tenant: str; topic: str; key: str; attr: str; value: str; stale: bool

def make_corpus(n_gold=60, n_decoy=200):
    docs = []
    for i in range(n_gold):
        t, a = TOPICS[i % len(TOPICS)], ATTRS[i % len(ATTRS)]
        # 黄金文档：用同义词（词汇不匹配）+ "最新"标记 + 现行值
        gold = (f"{t} {t} 季度 报告 {ATTR_SYN[a]} 指标 说明 现行 版本 生效 最新 {i} "
                f"{t} 摘要 补充 参考 附录 K{i}")
        docs.append(Doc(f"doc_g{i}", f"t{i%3}", t, f"K{i}", a, f"{i}", False))
        # 竞争文档：精确属性词（词法匹配强）+ "历史"标记 + 旧值；分布在不同租户
        for j in range(3):
            other = f"t{i%3}" if j == 0 else f"t{(i+1+j)%3}"
            stale = (f"{t} {t} 季度 报告 {a} 指标 说明 历史 版本 废止 旧 {900+j} "
                     f"{t} 摘要 补充 参考 附录 K{i}")
            docs.append(Doc(f"doc_s{i}_{j}", other, t, f"K{i}", a, f"{900+j}", True))
    for d in range(n_decoy):                      # 同主题噪声文档，稀释候选池
        t = TOPICS[d % len(TOPICS)]
        docs.append(Doc(f"decoy{d}", f"t{d%3}", t, f"D{d}", ATTRS[d % 5], f"{5000+d}", True))
    return docs

# ============ 1. 切分 + 内容寻址 id ============
CHUNKER_VER, EMBEDDER_VER = "chk-v1", "emb-v1"
def chunk_id(doc_id, version, span):
    raw = f"{doc_id}|{version}|{span}|{CHUNKER_VER}|{EMBEDDER_VER}"
    return "c" + hashlib.sha1(raw.encode()).hexdigest()[:14]

def tokenize(s): return re.findall(r"[A-Za-z0-9]+|[\u4e00-\u9fff]", s.lower())

@dataclass
class Chunk:
    cid: str; doc_id: str; tenant: str; text: str; tokens: list
    topic: str; key: str; value: str; stale: bool

def split_doc(d: Doc, version=1, size=14, overlap=4):
    toks = tokenize(d.text) if hasattr(d, "text") else tokenize(
        f"{d.topic} {d.topic} 季度 报告 {ATTR_SYN[d.attr] if not d.stale else d.attr} 指标 说明 "
        f"{'现行 版本 生效 最新' if not d.stale else '历史 版本 废止 旧'} {d.value} "
        f"{d.topic} 摘要 补充 参考 附录 {d.key}")
    out, i = [], 0
    while i < len(toks):
        span = (i, min(i + size, len(toks)))
        out.append(Chunk(cid=chunk_id(d.doc_id, version, span), doc_id=d.doc_id,
                         tenant=d.tenant, text=" ".join(toks[span[0]:span[1]]),
                         tokens=toks[span[0]:span[1]], topic=d.topic, key=d.key,
                         value=d.value, stale=d.stale))
        if span[1] == len(toks): break
        i += size - overlap
    return out

# ============ 2. 稀疏检索 BM25 ============
class BM25:
    def __init__(self, chunks, k1=1.2, b=0.75):
        self.chunks, self.k1, self.b = chunks, k1, b
        self.df = Counter()
        for c in chunks: self.df.update(set(c.tokens))
        self.N = len(chunks)
        self.tf = [Counter(c.tokens) for c in chunks]
        self.avgdl = sum(len(c.tokens) for c in chunks) / max(1, self.N)
    def score(self, q, allow):
        out = []
        for i, c in enumerate(self.chunks):
            if c.doc_id not in allow: continue
            s = 0.0
            for t in set(tokenize(q)):
                f = self.tf[i].get(t, 0)
                if not f: continue
                idf = math.log(1 + (self.N - self.df[t] + 0.5) / (self.df[t] + 0.5))
                s += idf * f * (self.k1 + 1) / (f + self.k1 * (1 - self.b + self.b * len(c.tokens) / self.avgdl))
            out.append((s, c))
        return sorted(out, key=lambda x: -x[0])

# ============ 3. 稠密检索（hashing-trick 随机投影代理）============
class Dense:
    """hashing-trick 随机投影 + 主题向量：模拟双塔的'主题级语义泛化'。
    ⚠️ 这只是代理：它没有真实的同义词/蕴含能力，不能替代真实双塔。"""
    def __init__(self, chunks, dim=64, seed=0, topic_w=1.8):
        self.chunks, self.dim, self.topic_w = chunks, dim, topic_w
        r = np.random.default_rng(seed)
        self.P = r.normal(0, 1, (4096, dim))
        self.TOPIC_VEC = {t: self._unit(r.normal(0, 1, dim))
                          for t in sorted(set(c.topic for c in chunks))}  # 排序保证可复现
        self.vecs = [self._enc(c.tokens, c.topic) for c in chunks]
    @staticmethod
    def _unit(v):
        n = np.linalg.norm(v); return v / n if n else v
    def _enc(self, toks, topic=None):
        v = np.zeros(self.dim)
        for t in toks:
            v += self.P[int(hashlib.md5(t.encode()).hexdigest()[:6], 16) % 4096]
        v = self._unit(v)
        if topic in self.TOPIC_VEC: v = self._unit(v + self.topic_w * self.TOPIC_VEC[topic])
        return v
    def score(self, q, allow):
        m = re.search(r"领域(\d+)", q)
        q_topic = f"领域{m.group(1)}" if m else None
        qv = self._enc(tokenize(q), q_topic); out = []
        for i, c in enumerate(self.chunks):
            if c.doc_id not in allow: continue
            out.append((float(np.dot(qv, self.vecs[i])), c))
        return sorted(out, key=lambda x: -x[0])

# ============ 4. RRF 融合 + 5. 交互式重排 ============
def rrf(rank_lists, k=60):
    agg = {}
    for lst in rank_lists:
        for rank, (_, c) in enumerate(lst):
            agg[c.cid] = agg.get(c.cid, 0.0) + 1.0 / (k + rank + 1)
    return sorted(agg.items(), key=lambda x: -x[1])

def rerank(query, fused, by_cid, pool=50):
    qt = set(tokenize(query)); out = []
    for cid, base in fused[:pool]:
        c = by_cid[cid]
        overlap = len(qt & set(c.tokens)) / max(1, len(qt))
        freshness = 0.35 if not c.stale else 0.0        # 版本新鲜度（文档元数据）
        adjacency = 0.25 if c.key.lower() in c.text.replace(" ", "") else 0.0
        out.append((base + 0.9 * overlap + freshness + adjacency, c))
    return sorted(out, key=lambda x: -x[0])

def rerank_v2(query, fused, by_cid, pool=50):
    """v2：在 v1 基础上加入'查询里的实体键是否命中该 chunk 所属文档'这个交互特征。
    v1 只在 chunk 文本里找 key，而切分把 key 切到了另一个 chunk，导致该信号丢失 —— 这就是 v1 的病根。"""
    qn = query.lower().replace(" ", "")
    qt = set(tokenize(query)); out = []
    for cid, base in fused[:pool]:
        c = by_cid[cid]
        overlap = len(qt & set(c.tokens)) / max(1, len(qt))
        freshness = 0.35 if not c.stale else 0.0
        adjacency = 0.25 if c.key.lower() in c.text.replace(" ", "") else 0.0
        key_match = 0.60 if c.key.lower() in qn else 0.0     # 文档级键匹配（v2 新增）
        out.append((base + 0.9 * overlap + freshness + adjacency + key_match, c))
    return sorted(out, key=lambda x: -x[0])

# ============ 6. 预算装配（贪心覆盖）============
def assemble(ranked, budget_tokens=120, per_chunk=14):
    sel, used, covered = [], 0, set()
    for s, c in ranked:
        if used + per_chunk > budget_tokens: break
        if covered and not (set(c.tokens) - covered): continue
        sel.append((s, c)); used += per_chunk; covered |= set(c.tokens)
    return sel

# ============ 7. 抽取式生成 stub ============
def generate(query, ctx):
    if not ctx: return "UNKNOWN", ""
    best = max(ctx, key=lambda x: x[0])[1]
    return best.value, best.cid

# ============ 8. 缓存（键含 tenant / 权限指纹 / manifest）============
class Cache:
    def __init__(self): self.d = {}; self.hits = 0; self.miss = 0
    def key(self, tenant, manifest, q, acl_fp):
        return hashlib.sha1(f"{tenant}|{manifest}|{acl_fp}|{q}".encode()).hexdigest()[:16]
    def get(self, k):
        if k in self.d: self.hits += 1; return self.d[k]
        self.miss += 1; return None
    def put(self, k, v): self.d[k] = v

# ============ 9. 段式索引 + manifest + 回滚 ============
@dataclass
class Segment:
    sid: int; chunks: list = field(default_factory=list); tomb: set = field(default_factory=set)

class SegmentIndex:
    _seq = 0
    def __init__(self):
        self.segments = []; self.by_cid = {}; self.manifest_id = "man-0"; self._v = 0
    def add(self, chunks):
        SegmentIndex._seq += 1
        s = Segment(SegmentIndex._seq, list(chunks)); self.segments.append(s)
        for c in chunks: self.by_cid[c.cid] = c
        self._v += 1; self.manifest_id = f"man-{self._v}"; return s
    def delete_doc(self, doc_id):
        for s in self.segments:
            for c in s.chunks:
                if c.doc_id == doc_id: s.tomb.add(c.cid)
    def live(self): return [c for s in self.segments for c in s.chunks if c.cid not in s.tomb]
    def stats(self):
        total = sum(len(s.chunks) for s in self.segments); live = len(self.live())
        return dict(segments=len(self.segments), live=live, total=total,
                    tomb=round((total - live) / total, 3) if total else 0,
                    manifest=self.manifest_id)
    def snapshot(self):
        return (self.manifest_id, [(s.sid, list(s.chunks), set(s.tomb)) for s in self.segments])
    def rollback(self, snap):
        mid, data = snap
        self.segments = [Segment(sid, list(ch), set(tb)) for sid, ch, tb in data]
        self.manifest_id = mid

# ============ 10. 流水线 ============
idx = SegmentIndex()
DEFAULT_VER = 1
idx.add([c for d in CORPUS for c in split_doc(d, version=DEFAULT_VER)])
LIVE = idx.live(); bm25 = BM25(LIVE); dense = Dense(LIVE)

def pipeline(query, tenant, mode="hybrid+rerank", k=10, pool=50, budget=120):
    allow = ACL[tenant]
    r1, r2 = bm25.score(query, allow), dense.score(query, allow)
    if mode == "sparse":   ranked = r1[:k]
    elif mode == "dense":  ranked = r2[:k]
    elif mode == "hybrid": ranked = [(v, idx.by_cid[cid]) for cid, v in rrf([r1, r2])[:k]]
    elif mode == "hybrid+rerank":
        ranked = rerank(query, rrf([r1, r2]), idx.by_cid, pool=pool)[:k]
    elif mode == "hybrid+rerank-v2":
        ranked = rerank_v2(query, rrf([r1, r2]), idx.by_cid, pool=pool)[:k]
    else: raise ValueError(mode)
    ctx = assemble(ranked, budget_tokens=budget)
    ans, cite = generate(query, ctx)
    return dict(ranked=ranked, ctx=ctx, ans=ans, cite=cite)

# ============ 11. 评测脚本 ============
def eval_set(n=60):
    return [dict(qid=i, tenant=f"t{i%3}", golden=f"doc_g{i}",
                 query=f"{TOPICS[i%len(TOPICS)]} 最新 {ATTRS[i%len(ATTRS)]} K{i} 是多少",
                 expect=str(i)) for i in range(n)]
EVAL = eval_set()

def evaluate(mode="hybrid+rerank", k=10, pool=50, budget=120, cache=None):
    rec = mrr = acc = cite = cost = 0.0; lat = []
    for e in EVAL:
        t0 = time.perf_counter()
        key = (cache.key(e["tenant"], idx.manifest_id, e["query"], len(ACL[e["tenant"]]))
               if cache else None)
        r = cache.get(key) if cache else None
        if r is None:
            r = pipeline(e["query"], e["tenant"], mode, k, pool, budget)
            if cache: cache.put(key, r)
        lat.append((time.perf_counter() - t0) * 1000)
        docs = [c.doc_id for _, c in r["ranked"][:k]]
        if e["golden"] in docs:
            rec += 1.0; mrr += 1.0 / (docs.index(e["golden"]) + 1)
        acc += 1.0 if r["ans"] == e["expect"] else 0.0
        if r["cite"]:
            cite += 1.0 if idx.by_cid[r["cite"]].doc_id == e["golden"] else 0.0
        cost += 0.002 * (1 + len(r["ctx"]))
    n = len(EVAL)
    return dict(mode=mode, recall=rec / n, mrr=mrr / n, answer=acc / n, citation=cite / n,
                p50_ms=float(np.percentile(lat, 50)), cost=cost / n,
                ctx_chunks=float(np.mean([len(pipeline(e["query"], e["tenant"], mode, k, pool, budget)["ctx"]) for e in EVAL[:10]])))

关键设计决策：整个案例最值得学习的一处，是评测表把"召回满分、答案一半"这个矛盾直接暴露出来。如果只统计一个端到端分数（比如 0.483），你会得出"这个系统还差一半"的模糊结论；而把 recall@10、MRR、答案正确 三个指标放在一起，诊断就是确定性的：召回没问题，是排序。这正是第 7 章第 2 节"指标树 + 失败分类"存在的意义 —— 它不是为了报告分数，而是为了让下一步行动没有歧义。

第二处值得学习的是 v2 的修复选择：发现问题在"键匹配信号不可见"之后，有两条路 —— 改切分（贵、影响全链路）或把信号提升到文档级（便宜、只影响在线打分）。选择后者不是因为后者更彻底，而是因为它用最小的代价验证了假设；如果 v2 之后仍然不达标，再动切分也不迟。这个顺序（先改在线、后改离线）是 ch6-l1 的"重建代价"与 ch5-l4 的"边际成本"共同推出的。

  3. 修复另一种病根。把语料构造成"黄金文档的键与值被切到同一 chunk"（缩小窗口），重跑 v1。回答：(a) v1 的答案正确率是否自己就好转？(b) 这验证了 §3.3 的结论吗？(c) 如果 v1 因此变好，那 ADR-005 的选择是否仍然正确？

小结#

  • 案例由 10 个模块组成：切分与内容寻址 id、BM25、稠密代理、RRF 融合、交互式重排、ACL 前置过滤、预算装配、抽取式生成 stub、带租户键的缓存、段式索引与回滚。每个模块都有明确的失效条件。
  • 消融表（⚠️ 合成，N=60，k=10，预算 120）：sparse recall 0.300 / 答案 0.200；dense 0.050 / 0.033；hybrid 0.250 / 0.033；hybrid+rerank(v1) 1.000 / 0.483；hybrid+rerank-v2 1.000 / 0.983。
  • 混合检索在本案例里没有带来增益，反而低于稀疏（0.250 < 0.300）。原因是 RRF 给每一路同等信任，而稠密代理接近随机 → 注入噪声。这正是 ch3-l3 互补度判据的实证："上了混合"不等于"更好"。
  • 核心诊断判据：recall@k 高而 答案正确率 低 ⇒ 瓶颈在排序/装配/生成；反之才修召回。⚠️ v1 的 recall@10 = 1.000、答案 0.483，gap +0.517。
  • 病根是"特征可见性"：v1 的键匹配特征只在 chunk 文本里查找，而切分把键切到了另一个 chunk → 该特征在黄金文档上从不触发。很多时候不是模型不够好，而是上游改变了输入的可见性。
  • v2 只加一个文档级 key_match 特征：MRR 0.742→0.992、答案 0.483→0.983、上下文块 8.0→6.8（质量与成本同向改善）。
  • k 的饱和点：k≥3 后指标完全饱和，而上下文块继续涨 → 合理工作点是 k≈3∼5，不是 10。重排池的拐点在 50（10→50 是 recall 0.250→1.000 的关键区间，50→200 收益为 0）。
  • 工程底线三项全部通过：canary 交叉断言 12 条泄漏 0（PASS）；缓存同租户命中、跨租户不命中；段式索引删除后回滚断言 PASS。
  • 五份 ADR 覆盖：不单独依赖混合（ADR-001）、ACL 前置（ADR-002）、重排池 50（ADR-003）、缓存键含租户与 manifest（ADR-004）、先改在线特征而非改切分（ADR-005）。每份都写了"何时重审"。
  • 本案例的三个诚实局限：① 稠密表示是随机投影代理，不具备真实双塔的语义泛化，故 dense 的 0.050 不可外推；② 生成是抽取式 stub，测不出生成层问题（位置/干扰/先验/引用装饰）；③ 延迟是单机数字，只能做相对比较。
  • 一句话：一个案例的价值不在于"跑通了"，而在于它把"哪一步错了"变成一个确定性的结论，并把"下一步做什么"变成一条有收益、有成本、有重审条件的决策记录。
