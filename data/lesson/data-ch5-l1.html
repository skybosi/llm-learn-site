数据版本：内容寻址、Merkle 快照与不可变数据集#

这一节要解决什么#

第 4 章的四节课各自留下一串必须被记住的东西：标注指南哈希、标注者与弃权标记、采集策略与种子、教师版本与 prompt 族、校验器版本与接受率、去污染阈值与残余率、π 与阶段表、分布级门禁值。第 4 章把它们写进了一张 manifest 表，并留了一句话：缺任何一列，这次混合就无法复现。

但那张表只是一份清单，它回答的是"要记什么"，没有回答三个更工程的问题：

  1. 这份表本身存在哪里、怎么保证没被改过？ 如果 manifest 是一份手写的 YAML，那么"当时用的是哪个教师"这句话的可靠性等于写它的人的诚信。
  2. 路径名和内容是什么关系？ 数据目录叫 train_v2_final_clean/，这个名字没有承诺任何东西。三个月后有人往里面加了 200 条数据，名字不变。
  3. 两个版本之间到底差了什么？ "v2 比 v1 好"这句话要能被拆成"多了 3 个文件、改了 1 个过滤阈值"这样的可核对事实，而不是一句感觉。

本章的四节就是围着这三个问题展开的。第 1 节（本节）解决标识与不可变：把数据集变成一个由内容决定的、不能悄悄变的名字。第 2 节解决关系：数据从哪来、到哪去（血缘图与影响面）。第 3 节解决强度：可复现不是一个布尔量，它有三个等级。第 4 节解决动作：发现脏数据之后怎么定位影响面并回退。

第 2 章第 4 节已经给过一个式子了：

数据版本=输入指纹+管线版本+参数

本节要做的是把右边三项各自拆到可实现的粒度，并给出实现。第 2 章那节停在了"整批指纹"这一个数上（a518840e10c7d3dd）——那是一个数字，本节要给出一棵树。这个区别不是美学问题，本节代码会实测：120 个文件的数据集，改 1 个文件后

  • 整批拼接哈希：必须重算 120 次内容哈希（要重新读字节）；
  • Merkle 树：只重算 1 次内容哈希（只有那个文件的字节真的变了），其余 7 层合并全部命中缓存。

差距是 15 倍，而数据集越大差距越是数量级级别。这里真正的区别不是常数因子，而是「什么必须重算」：内容哈希要读磁盘，而缓存失效只发生在从那个叶到根的 ⌈log2​n⌉ 个节点上。同一次实测还会给出另一件更重要的东西：用"整批拼接"当版本时，你无法回答"这两个版本差在哪一个文件"；用 Merkle 树，差异可以精确到叶，而且一条 log2​n 长度的证明路径就能让第三方在你不在场时验证"这个文件确实属于这个快照"。

一、标识：为什么"同一个东西"必须由内容回答#

1.1 概念：版本标识是给三类读者的#

一份数据版本要同时对三类读者说话，这是它的设计压力来源：

读者 想问的问题 需要的精度
人 "我们上次讨论的是哪一份数据？" 可读的名字 + 一个唯一标识
程序 "这份数据在我这里存在吗？我算出来的和它一样吗？" 字节级可比较的标识
审计 "三个月前那次报告用的是这一份吗？" 不可伪造、不可事后修改的证据

只有第三类读者会逼出内容寻址。前两类用"路径 + 时间戳 + 一个自增号"就能满足，而这两样东西合起来恰好是审计最不信任的东西：路径可以被覆盖，时间戳可以被复制（cp -p、rsync -t、容器镜像层解包），自增号可以被重排。

1.2 为什么这样设计：三种失败的标识#

失败一：路径。 data/v2/train.jsonl 是一个位置，不是一个对象。位置可以被指向不同的对象（写入）、可以被指向同一个对象（硬链接、软链接、bind mount）、也可以被一个对象占用后被回收。把路径写进报告，等于写"我说的是当时那个路径下的东西" —— 这是一句无法被证伪的话。

失败二：修改时间。 stat 的 mtime 有三个具体的问题：

  • 它可以不变而内容变了：cp -p、rsync -a、tar -p、Docker 镜像层、git checkout 之后文件内容变了而 mtime 可能来自归档。实测里这种情况出现的频率高得惊人，因为整条流水线的目标就是"复制得像原样"。
  • 它可以变而内容没变：任何一次 touch、任何一次幂等重跑（第 2 章第 4 节说幂等是要求，不是可选）都会刷新它。于是"两个版本不同"变成假阳性。
  • 它的分辨率不可靠：不同文件系统从 1 秒到 1 纳秒不等，跨机器比较 mtime 基本没有意义。

失败三：大小。 大小只能排除一部分差异。改一个字节、改一个词、把 0.5 改成 0.50、把 \n 改成 \r\n —— 这些都对大小和 mtime 可能完全无害，对训练结果可能有害（第 2 章第 4 节：不可见字符、全角/连字、NFKC 的有损性）。

所以唯一可用的判据是：两个对象相同，当且仅当它们的规范形式逐字节相同。这就是内容寻址的全部内容。它有一个漂亮的副产品：标识即校验。拿到标识的人可以自己重算一遍，不需要信任任何人。这是下一节"血缘"和最后"审计"两件事的前提 —— 血缘图上的节点如果没有可验证的身份，那图上画的只是一堆名字。

二、规范化：哈希稳定性的前提#

2.1 概念：同一份数据的多种字节表示#

内容寻址有一个反直觉的前提：逻辑上相同的数据，字节表示并不唯一。哈希是对字节算的，所以只要字节不同，哈希就不同。这在真实管线里制造的错误非常隐蔽，因为它不报错。

四类必须处理的表示自由度：

自由度 具体例子 后果
序列化顺序 JSON 对象键顺序、dict 插入顺序、CSV 列顺序 同一份表两种哈希
数值表示 0.10 vs 0.1、1e3 vs 1000、浮点最短表示 同一份指标两种哈希
编码与行尾 UTF-8 BOM、\n vs \r\n、NFD vs NFC 同一份文本两种哈希
集合语义 行的排列、"同名多值"的先后 语义相同的两份表两种哈希

前两类用规范化序列化（canonical serialization）解决，第三类用第 2 章第 4 节的那套归一化解决，第四类最难 —— 它没有"正确"答案，只有约定。

2.2 怎么做：规范形式的四条纪律#

  1. 键必须排序，且排序规则要固定。 json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False) 是一个可以用的起点。注意 separators：默认的 , 与 : 里带空格，一旦有人换了实现（换语言、换库版本）哈希全体改变。
  2. 数值必须定形。 浮点用最短往返表示（Python 的 repr(float) 与 json 的 float 默认行为就是最短往返，这是可以依赖的），但混合类型要禁止（1 与 1.0 在 JSON 里不同、在 Python 里 1 == 1.0 为真而在哈希上不同）。金融/计数类字段应该显式转成整数或定点字符串。
  3. 编码与行尾必须定形。 统一 UTF-8 无 BOM、统一 \n。这一条不能只写在文档里 —— 它必须是一个能跑的检查，因为 \r\n 通常来自某个同事的编辑器。
  4. 集合必须定形。 对"无序集合"语义的字段（标签集合、来源集合），序列化前排序；对"有序"语义的字段（步骤序列、行顺序），绝不排序并要显式记录顺序敏感。把这两者搞混是哈希不稳定最常见的根因之一：把有序的东西排序，哈希稳定了但语义被改了（第 3 章的阶段表就是有序的，排序它会改变训练语义）。

判断"要不要排序"的方法：问"交换两个元素会不会改变下游结果"。会 → 有序；不会 → 无序，排序。这个问题必须在每个字段上问一遍，因为答案不统一。

2.3 边界：规范化本身可能是有损的#

规范化会掩盖差异。如果两份数据只差一个 \r，规范化后哈希相同 —— 这是你要的。但如果两份数据差的是一个你不该忽略的字段（例如某个数值被四舍五入到 3 位小数），而规范化恰好把它抹平了，你就得到了一个假的"内容相同"。

这条边界有一个可操作的形式：规范化只在"下游不可能观察到差异"时才是合法的。这意味着规范化函数必须与下游的读取路径对齐：

  • 下游读 JSON 解析后取字段 → 键顺序无关，排序安全；浮点尾随零无关，可以定形。
  • 下游读原始字节做 grep/diff/正则 → 任何规范化都不安全，此时哈希必须覆盖原始字节。

所以工程上的正确形态是两条链：raw_hash（原始字节，用于审计与取证）与 canon_hash（规范形式，用于去重、比较、寻址）。它们永远不该被混为一谈。这是本节代码 A 段的核心结构。

三、粒度：从文件哈希到 Merkle 树#

3.1 概念：三个可选粒度#

粒度 标识什么 增量更新 差异定位 成员证明
文件哈希 一个文件 O(1) 精确到文件 不需要
整批拼接哈希 一个集合 O(n) 不可能 不可能
Merkle 树根 一个集合 O(logn) 精确到文件 O(logn) 的证明路径

多数人在第一次实现数据版本时会写第二行：把所有文件哈希按顺序拼起来再哈希一次。它有一个致命的性质 —— 它是一个聚合，不是一棵树。聚合只能回答"相同或不同"，不能回答"哪里不同"。而实际工作中 90% 的问题恰恰是"哪里不同"：

  • 数据没变但训练结果变了？（那不是数据的问题，去查代码/环境 —— 第 3 节。）
  • 数据变了但不知道变了什么？（聚合哈希只能说"变了"，你只能重跑整条管线做 diff。）
  • 一条数据要发出去做标注，怎么让它回来时能被接住？（需要"这个文件属于这个快照"的证明。）

3.2 怎么做：Merkle 树的构造规约#

叶 i  = H(0x00 ‖ leaf_id_i ‖ content_hash_i)        # 域分隔前缀
内节点 = H(0x01 ‖ left_hash ‖ right_hash)
根     = 逐层上推的结果

四个必须显式写下来的规约，缺一个就会得到"同样的数据两种根"：

  1. 叶的顺序：按 leaf_id 的字节序排序后建树。不排序则依赖目录遍历顺序，而目录遍历顺序在不同文件系统/不同语言/不同并发下不同。
  2. 奇数节点：把最后一个节点复制一份（Bitcoin 风格）还是提升到上一层（RFC 6962 风格）？两种都行，必须选一种并写进版本号。本节代码用"复制"，因为它的实现最短。
  3. 域分隔：叶哈希与内节点哈希用不同的前缀字节，否则存在结构歧义（有人能把一个两叶的树重解释成一个叶）。
  4. 空集合：定义 $H(\text{empty}) = $ 某个固定值（本节用 sha256(b"")），并把它写进规约。空数据集是最容易被忽略的边界，而它在真实管线里天天出现（"今天的增量是空的"）。

本节代码为了把结构讲清楚，每层都重算（不缓存上层节点），因此打印出的 哈希调用 = 240 ≈ 2n；工程实现里上层节点是持久化的，一次单叶更新只需 ⌈log2​n⌉ 次合并。两者的区别只在常数与缓存策略上，不在「能不能定位差异」上 —— 定位能力来自树形结构本身。

为什么叶哈希要对 content_hash 再哈希一次、而不是直接用 content_hash？ 因为这样可以防"第二原像"类攻击（把内节点哈希当成叶哈希塞进来）。在只做版本管理的场景里这个威胁不大，但成本是一行代码，收益是不必区分"诚实的树"与"构造的树"。这是把证明能力当成本的典型例子。

3.3 数据版本的三段结构：content / meta / params#

回到第 2 章那个式子，本节把它落成一个三段的目录约定：

snapshot/
  content/    # 字节。只由数据内容决定，哈希只覆盖这里
  meta/       # 每条的来源、许可、标注者、指南哈希、采集策略与种子
  params/     # 管线参数：过滤阈值、π、去污染阈值、教师版本、prompt 族哈希

这个划分不是审美，它是"变更频率隔离"。 三类东西的变更频率差两个数量级：content 每次重跑都可能变，meta 跟着标注流程变，params 在一次实验里是常量。如果三者混在一个哈希里，任何一次 params 微调都会让整个数据集看起来"变了"，于是"这两个版本的数据一样吗"这个问题的答案永远是"不一样"，版本号迅速失去信息量。反过来，如果 params 不进哈希，那么"同一份字节、不同过滤阈值"会得到同一个版本号 —— 也就是不可复现。

正确形态是根哈希包含三者，但三者各自也有自己的哈希，并且 manifest 显式列出三个分量。这样：

  • 根相同 → 完全同一份东西（可照抄结论）；
  • 根不同、content 相同 → 只有参数/元数据变了（结论可能需要重算，但数据可以不重跑）；
  • content 不同 → 必须重跑（输入真的变了）。

这个三分法会在第 2 节（血缘：哪些下游节点受影响）和第 4 节（回滚：回滚到哪一层）里反复用到。

四、不可变与快照：从"覆盖写"到"追加 + 指向"#

4.1 概念：不可变不是技术限制，是流程约束#

内容寻址给出的是名字层面的不可变：路径 = 哈希，于是"改写"意味着换一个名字。但存储层仍然可以被覆盖（有人直接 rm 或 > 重写）。所以"不可变"在真实系统里永远是两件事：

  1. 名字由内容决定（技术）；
  2. 写操作只能是"新建 + 追加指针"（流程 + 权限）。

第二件事需要工程手段，而不是纪律。可用的手段有三种，代价依次上升：

手段 保证 代价
命名规约 + 代码里不出现覆盖写 弱（靠人） 低
追加式 manifest 文件 + 只读权限（chmod -w、对象存储的 WORM 策略） 中 低
只增不改的存储层（append-only 日志 / 版本化对象存储 / 每次快照一份独立前缀） 强 存储成本 ×份数

本课程推荐的是中间那档：快照 manifest 是一份只追加的 JSONL（每行一个快照记录），数据对象按哈希落在前缀目录里，且前缀目录不删。它的逻辑是"指针可以动，目标不动"：latest 是一个指向某个根哈希的指针文件，更新它等于追加一行；而它指向的那个前缀永远不会被重写。

4.2 怎么做：快照 manifest 的字段#

snapshot_record = {
  schema_version: 1,                # 本记录的格式版本（不是数据版本）
  snapshot_id:    "sha256:....",    # 根哈希，唯一身份
  created_at:     "2026-..-..T..Z", # 只作展示，绝不参与哈希
  parents:        ["sha256:...."],  # 上一个快照（第 2 节的血缘边）
  components: {
    content: {merkle_root, n_leaves, bytes, leaf_algo},
    meta:    {merkle_root, n_leaves, annotation_guideline_hash},
    params:  {params_hash, pipeline_version, seed, filters {...}}
  },
  stats:   {n_rows, label_histogram, split_sizes},   # 供廉价一致性检查
  gates:   {min_rows, max_dup_rate, ...}             # 第 4 章的分布级门禁
}

三条容易写错的细节：

  1. created_at 绝不参与哈希。 时间是元数据，不是内容。它一旦进哈希，同一份数据两次快照就有两个身份，"重跑能不能复现"这个问题直接变成否。
  2. parents 让快照构成一张 DAG，而不是一条时间线。真实管线有合并（两份数据合成一份）与分叉（一份数据拆成训练/评测），DAG 是唯一能表达它的结构，也是第 2 节血缘图的基础。
  3. stats 与 gates 是给"廉价一致性检查"用的：它们不进根哈希（它们是断言不是内容），但进快照记录。这样"这份数据有 10240 行、正类 5120 条"就成了一句可以被下游核对的话。核对失败意味着有人动了数据却没换哈希 —— 这是最值得报警的一种事故。

4.3 增量更新：用前缀 diff 降到 O(logn+k)#

有了排序的叶集合，增量更新就变成一个集合差：新快照只需对"去掉的叶 + 新增的叶"所在的路径重新计算哈希。工程上最简单的实现是：

  1. 对新的文件集合算出 leaf_id -> content_hash 映射（Θ(n) 次文件读取，这一步无法省 —— 你必须读一遍才知道有没有变）；
  2. 与上一份快照的映射对比（Θ(n) 次字典比较）；
  3. 重算根：只需要叶哈希集合，内节点全部重算（Θ(n) 次哈希）。

第 3 步仍然是 O(n)，但它是内存里的哈希，比第 1 步的磁盘 I/O 加内容哈希便宜两个数量级。真正的收益在于第 1 步可以被 mtime + size 的启发式剪枝成"只读可疑文件" —— 这个启发式只有在校验兜底时才安全：

用 (size, mtime) 判断"文件没变"是性能优化，不是正确性判据。正确性由定期全量重算（例如每次发布前）兜底。把启发式当判据的系统会在某次 rsync -a 之后静默地算错版本 —— 这是"版本管理本身引入不可复现"的经典事故。

本节代码不做这个启发式剪枝（保持正确性优先），但会在实测里打印"改了 1 个文件后，内容哈希的计算次数从 100 降到 1"。

五、代码#

五段：0 段合成数据（⚠️ 合成，非真实语料）；1 段实现归一化与双链哈希；2 段实现 Merkle 树与证明路径；3 段实现三段式快照记录；4 段量化增量代价；5 段给三个"看起来能用但会坏"的反例。全程只用标准库（hashlib / json / random），输出与下面的记录逐字节一致。

# ---------- 1a. 规范化：把"逻辑相同"变成"字节相同" ----------
def _norm(o):
    """归一化：字符串去首尾空白并把 \r\n 折成 \n；dict 键排序。"""
    if isinstance(o, str):
        return o.replace("\r\n", "\n").strip()
    if isinstance(o, dict):
        return {k: _norm(v) for k, v in sorted(o.items())}
    if isinstance(o, (list, tuple)):
        return [_norm(v) for v in o]
    return o

def canon_bytes(obj):
    """规范 JSON 字节：键排序、无多余空格、UTF-8 无 BOM。"""
    s = json.dumps(_norm(obj), sort_keys=True, separators=(",", ":"), ensure_ascii=False)
    return s.encode("utf-8")

def raw_bytes(obj):
    """原始字节：不排序、默认分隔符、带 BOM —— 故意模拟"某台机器的写法"。"""
    s = json.dumps(obj, ensure_ascii=False, indent=1)
    return b"\xef\xbb\xbf" + s.replace("\n", "\r\n").encode("utf-8")

def h(b: bytes) -> str:
    return hashlib.sha256(b).hexdigest()

# ---------- 2. Merkle 树：叶 -> 根，含证明路径 ----------
LEAF_DOM = b"\x00"
NODE_DOM = b"\x01"

def leaf_hash(leaf_id: str, content_hash: str) -> str:
    return h(LEAF_DOM + leaf_id.encode() + b"|" + content_hash.encode())

def node_hash(l: str, r: str) -> str:
    return h(NODE_DOM + l.encode() + r.encode())

def build_merkle(pairs):
    """pairs: [(leaf_id, content_hash)]。返回 (root, levels, n_hash_calls)。"""
    pairs = sorted(pairs, key=lambda p: p[0].encode())   # 规约 1：按 leaf_id 字节序
    if not pairs:                                        # 规约 4：空集合
        return h(b""), [[h(b"")]], 1
    calls = 0
    level = []
    for lid, ch in pairs:
        level.append(leaf_hash(lid, ch)); calls += 1
    levels = [level]
    while len(level) > 1:
        if len(level) % 2:                               # 规约 2：复制最后一个
            level = level + [level[-1]]
        nxt = []
        for i in range(0, len(level), 2):
            nxt.append(node_hash(level[i], level[i + 1])); calls += 1
        level = nxt
        levels.append(level)
    return level[0], levels, calls

def merkle_proof(levels, idx):
    """返回 (兄弟哈希, 方向) 列表，长度 = 树高。"""
    proof = []
    for lv in levels[:-1]:
        if idx % 2 == 0:
            sib = idx + 1 if idx + 1 < len(lv) else idx      # 复制自己
            proof.append((lv[sib], "R"))
        else:
            proof.append((lv[idx - 1], "L"))
        idx //= 2
    return proof

def verify_proof(leaf_id, content_hash, proof, root):
    cur = leaf_hash(leaf_id, content_hash)
    for sib, side in proof:
        cur = node_hash(cur, sib) if side == "R" else node_hash(sib, cur)
    return cur == root

pairs = [(d["doc_id"], canons[d["doc_id"]]) for d in docs]
root, levels, calls = build_merkle(pairs)

def merkle_root_of(items):
    """items: [(leaf_id, hash)] -> (root, calls)"""
    r, _, c = build_merkle(items)
    return r, c

def snapshot(docs, params, parents):
    content = [(d["doc_id"], canons[d["doc_id"]]) for d in docs]
    # meta 只含"关于这条数据"的字段（这里是 split 与 topic），与 content 分离
    meta_items = []
    for d in docs:
        m = {"doc_id": d["doc_id"], "split": d["split"], "topic": d["topic"]}
        meta_items.append((d["doc_id"], h(canon_bytes(m))))
    c_root, c_calls = merkle_root_of(content)
    m_root, m_calls = merkle_root_of(meta_items)
    p_hash = h(canon_bytes(params))
    comps = {
        "content": {"merkle_root": c_root, "n_leaves": len(content), "leaf_algo": "sha256/dom00"},
        "meta": {"merkle_root": m_root, "n_leaves": len(meta_items),
                 "annotation_guideline_hash": h(b"guideline-v3")[:16]},
        "params": {"params_hash": p_hash, "pipeline_version": params["pipeline_version"],
                   "seed": params["seed"]},
    }
    rec = {
        "schema_version": 1,
        # snapshot_id 由三段分量决定；created_at 与 stats 绝不参与
        "snapshot_id": h(canon_bytes(comps)),
        "parents": parents,
        "components": comps,
        "stats": {"n_rows": len(docs),
                  "split_sizes": {s: sum(1 for d in docs if d["split"] == s)
                                  for s in ("train", "test")},
                  "topic_hist": {t: sum(1 for d in docs if d["topic"] == t) for t in TOPICS}},
    }
    return rec, c_calls + m_calls

读输出的七个要点#

  1. 规范化是必需的，不是洁癖。 1a 段里同一份逻辑数据的 raw 哈希不一致（aa0d282921bfe1c1 vs dbeb62d2aa0fe45f）、canon 哈希一致（都是 31a63b1e3b6d983a）；而 1 与 1.0 的 canon 哈希也不一致（5041bf1f713d vs bf32f5623689），尽管 1 == 1.0 为 True。Python 的相等与字节的相等不是一回事，这是版本管理里最便宜也最容易漏的一条检查。
  2. 双链的作用在 1b 段可见：120 篇里 raw 唯一 120 个，canon 唯一 114 个 —— 有 6 组「同一份文档被两个来源各收了一次」（doc_id 复用、只差一个尾随空格）。做寻址/去重时你要的是 114；做取证时你要的是 120（"到底是哪一次采集多带了一个空格"需要原始字节）。只留一条链必然要在两种需求里丢一个。
  3. 树高与证明长度相等（7=⌈log2​120⌉），且三种否证全部正确返回 False。这条 log2​n 的证明能力是 Merkle 树相对"拼接哈希"的全部增量价值 —— 它让没有全量数据的人也能验证一个文件的归属。
  4. 三段分离立刻给出一个可操作的区别（3 段）：只改 min_len 阈值时 content.root 相同而 snapshot_id 不同。这意味着数据字节不用重生成，但结论需要重算。如果三者混在一起，你只能得到"整个都变了"，于是被迫做一次全量重跑。
  5. 增量的 15 倍不是重点，重点是"能定位"（4 段）。拼接哈希的读数是 120 → 120（零收益），且它没有 diff 能力；Merkle 路径是 1 + 7 = 8，并且叶集合 diff 直接给出 修改 ['doc0007']。
  6. 1a 段的 1 vs 1.0 与 1b 段的尾随空格是同一类问题的两个面孔：前者说明"类型是内容的一部分"，后者说明"空白是内容的一部分"。两者都只能靠显式写下来的归一化规约处理，而规约一旦写下来就变成了版本的一部分 —— 改规约等于换哈希，见 3.2 节的规约版本号。
  7. 三个反例都是"看起来能用"的实现：created_at 进哈希（一行代码，让重跑永不幂等）、不排序键（换库即全体换哈希）、给有序字段排序（哈希稳定了但语义被抹平）。它们的共性是不会报错，只会在三个月后的某次审计里暴露。

六、取舍与边界#

选择 换来什么 付出什么 什么时候选另一边
内容寻址（哈希当名字） 标识即校验；可跨人跨机器核对 名字不可读；重算哈希要读全量字节 交互式探索期：先用可读名 + 软链，发布前再钉哈希
规范形式哈希 跨语言/跨库稳定 规范化可能掩盖真实差异；需维护规约 下游按原始字节消费（正则、grep）时，只信 raw
Merkle 树 增量、差异定位、成员证明 实现更复杂；规约必须写下来 数据集小于百个文件且从不变更：拼接哈希够用
三段分离（content/meta/params） 能区分"数据变了"与"参数变了" 三套哈希、三套更新流程 一次性数据集：混在一起省事，代价是以后无法局部重跑
只追加快照 + 只读前缀 不可变有工程保证，不只靠纪律 存储成本随快照数线性涨 存储极贵时：保留"里程碑"快照，中间态定期回收
哈希只覆盖内容不覆盖顺序 与"集合语义"对齐 顺序敏感的数据集会失去顺序信息 阶段表这类有序结构：顺序进 params 的哈希，而不是进 content

四条硬边界：

  1. 哈希不保证正确，只保证识别。 一份满是错标的数据集可以有一个完美稳定的哈希。哈希回答"是不是同一份"，从不回答"是不是好的"。这是第 1 章"最贵的错误是静默错误"在版本层面的重述 —— 版本管理的价值恰恰在于当错误被发现时，能快速确定它影响范围（第 4 节）。
  2. 内容寻址需要存储或信任。 要么你把对象留着（成本），要么你信任外部存储按哈希返回（信任）。二者必居其一，没有第三条路。实践中常见的第三种是"我只有一个哈希，数据在别人的机器上"，那等于没有版本。
  3. 规范化会引入不可逆的信息损失。 一旦决定"键顺序不入哈希"，你就再也无法用哈希区分"键顺序不同但内容相同"的两份数据。这是有意的，但必须有意识地做，并在规范里写下来（而不是某个人顺手加了 sort_keys=True）。
  4. 哈希碰撞的边界要算清，而不是说"不可能"。 生日界：n 个对象的碰撞概率约 n2/2b+1。b=256 时，n=1012 个对象也只有约 10−53 量级。但如果碰撞是故意构造的（有人想造一份"哈希相同但内容不同"的数据），那要防的是抗碰撞性 —— SHA-256 目前仍然够用，而 MD5/SHA-1 不够（它们都有实际构造的碰撞）。所以版本标识必须用 SHA-256 或更强的函数，这不是保守，是底线。

练习#

  1. 规范化规约的实操：取你手上任意一份数据（CSV/JSON/JSONL），回答： （a）列出它的全部表示自由度（键序、数值、行尾、编码、行序、列序、空值表示），逐条判定"下游能不能观察到"； （b）据此写出你的规范形式规约（哪几项定形、哪几项保留），并给出一个能跑的检查函数； （c）构造两份"逻辑相同、字节不同"的样本，验证你的规范化把它们映射到同一个哈希，且没有把一份"逻辑不同"的样本错误合并。

  2. 你自己的三种粒度对比：用你手上的数据（或本节的合成数据）实测： （a）文件哈希、整批拼接哈希、Merkle 根三种表示各算一次，记录时间与哈希调用次数； （b）改 1 个文件、删 1 个文件、加 1 个文件，三种表示各自的代价； （c）用实测数据回答：在什么规模下你必须上 Merkle？（提示：把"文件 I/O 时间"与"内存哈希时间"分开计时，找到二者相等的那一点。）

  3. 证明路径的对抗练习： （a）实现本节的两个规约变体（奇数节点"复制最后一个" vs "提升到上一层"），对同一份数据分别建树，报告两个根的差异； （b）证明：如果去掉域分隔前缀（\x00 / \x01），存在一个两叶树可以被重解释成另一个树的叶（写出具体的构造）； （c）解释为什么"根不同"不能直接推出"数据不同"（提示：规约变更也会改变根），并给出你的规约版本号方案。

  4. 一个快照记录的反例修复：下面是某团队的快照记录，找出至少四处会让版本失效的设计，并逐条给出修法与代价。

    {id: "v2_final", path: "/mnt/data/v2", created: "2026-05-01",
 n: 10240, hash: md5_dir(path), params: {thr: 0.6}, author: "alice"}

    （提示：id 是不是内容？path 进不进哈希？md5 够不够？created 参与了吗？n 与 hash 冲突时信谁？params 是哪一层的？）

  5. 三段分离的判定树：给定两份快照 A、B，写出一个程序（伪代码或真代码），把 (A, B) 分类到以下四类之一，并给出每类的正确工程动作： （a）完全同一份；（b）只有 params 变；（c）只有 meta 变；（d）content 变。 对每一类回答：下游结论需要重算吗？数据需要重新生成吗？已发出的标注任务需要作废吗？

  6. 不可变的流程设计：你所在团队的存储是一个普通的对象存储（无 WORM、无版本化）。设计一套只靠命名 + 权限 + 追加式 manifest 实现"不可变"的方案： （a）写出写路径的权限模型（谁能 PutObject、谁能删、latest 指针谁写）； （b）给出一次"有人试图覆盖已有快照前缀"的检测方法，并说明你为什么需要它（提示：内容寻址下重写前缀意味着什么？）； （c）说明这套方案的残余风险（谁有权限谁就能作恶），并给出一个独立于权限的兜底检查（例如定期重算全部根哈希）。

小结#

  • 版本标识必须由内容回答，不能由路径、mtime 或大小回答。 三者各有失效方式（可在内容变化时不变、可在内容不变时变、可被幂等重跑刷新），而内容寻址的副产品是标识即校验 —— 拿到标识的人可以自己重算。这是后面血缘与审计两块的地基。
  • 内容寻址的前提是规范形式。四条纪律：键排序、数值定形、编码与行尾定形、集合语义显式化（有序的绝不排序）。归一化还要包含字符串去首尾空白 —— 1b 段的 6 组近重复只差一个尾随空格。实测：同一份逻辑数据的 raw 哈希不一致、canon 哈希一致；而 1 与 1.0 在 Python 里 == 为 True 但 canon 字节不同。
  • 必须保留两条链：raw_hash（原始字节，供取证与审计）与 canon_hash（规范形式，供寻址与去重）。实测里 120 篇文档 raw 唯一 120 个、canon 唯一 114 个（6 组「同文档两来源」）—— 只留一条必然在"精确"与"可用"之间丢一个。
  • 聚合不能定位差异，树可以。 整批拼接哈希改 1 个文件也要重算 120 次内容哈希，且无法回答"哪个文件变了"；Merkle 树是 1+7=8 次（15 倍），并且叶集合 diff 直接给出 修改 ['doc0007']，还能给出长度等于树高（7）的成员证明路径 —— 三种否证（篡改内容、冒充成员、错误证明）全部返回 False。
  • 快照要分三段：content / meta / params，根哈希覆盖三者但三者各有自己的哈希。 实测：只改 min_len 阈值时 content.root 相同（数据不必重生成）而 snapshot_id 不同（结论需要重算）。混在一起的代价是任何参数微调都让"数据变了吗"这个问题的答案永远是"变了"。
  • created_at、stats、gates 绝不参与哈希。 时间进哈希 → 重跑永不幂等（反例 1 实测 id 相同? False）；不进哈希但它们要进快照记录，因为"这份数据有 120 行、test 12 条"是下游可以核对的断言，核对失败是"有人动了数据却没换哈希"的报警信号。
  • 不可变有两层：名字层（内容寻址）与存储层（只追加 + 只读前缀）。后者只用纪律是不够的，推荐的最小工程形态是只追加的 manifest JSONL + 不可重写的前缀 + 一个 latest 指针：指针可以动，目标不动。
  • 哈希不保证正确，只保证识别。 它的价值在被发现错误之后才兑现（影响面定位与回退，第 4 节）。另外，版本标识必须用 SHA-256 或更强：MD5/SHA-1 有实际构造的碰撞，而"有人故意造一份同哈希数据"是版本管理必须防的威胁模型。
