多卡为何不是线性加速#

"两张卡就该快两倍"是很多人对多卡的第一直觉，现实却几乎从不如此。学完本课，你应当能用量化的方式解释：为什么多卡加速远低于线性，以及通信、串行、负载不均衡各自吃掉多少收益。

一、概念讲解#

1. 理想与现实的差距#

理想情况下，把任务分给 N 张卡，时间缩短到 1/N，这叫线性加速（linear speedup）。但程序里总有没法并行、必须串行的部分，还有卡与卡之间要互相等待、交换数据的开销，所以实际加速比总是打折扣。

2. Amdahl 定律：串行部分决定上限#

Amdahl 定律刻画了最核心的约束：设任务中可并行部分占比为 p（0≤p≤1），用 N 张卡，则加速比为

S(N)=(1−p)+p/N1​

哪怕可并行部分高达 99%（p=0.99），当 N→∞ 时加速比上限也只有 1/(1-p) = 100 倍；现实中 p 往往远没这么高，串行部分（数据加载、启动、无法切分的计算）就成了天花板。

3. 通信开销：每算一步都要"开会"#

多卡并行不是各算各的，而是边算边同步：

  • 张量并行：一层矩阵乘切到多卡，每层结束都要 all-reduce 交换部分和，通信量随层数累加；
  • 流水线并行：卡之间传递中间结果，还会有气泡（bubble）——先填满流水线的阶段里，多数卡在空等；
  • 数据并行（训练）：每步都要同步梯度。

上一课算过：一次 2 GB 通信走 PCIe 要几十毫秒，走 NVLink 也要几毫秒；这些时间卡与卡之间是相互等待的，算得再快的卡也得停下来等最慢的那一跳。

4. 负载不均衡与尾延迟#

即使通信免费，还有两个"隐性打折"：

  • 负载不均衡：把工作切成 N 份，很难切得完全均匀，最慢的那张卡决定整体完成时间；
  • 尾延迟：多卡同时处理请求时，个别卡偶发抖动，整个批次的响应被拖慢。

于是真实曲线是：卡数越多，加速比越偏离线性，边际收益递减，甚至加到某个点后反而不如更少的卡。

5. 推理场景的特殊性#

推理的多卡（通常张量并行）还有个额外代价：权重虽被切分，但通信发生在每一层、每个 token 上，属于延迟敏感的短交互。相比之下，批量越大、单次计算越重，通信占比越低，加速越接近线性——这也是"小 batch 下多卡推理往往不划算"的原因。

二、可运行示例#

用 Amdahl 定律 + 一个简单的通信开销模型，画出"加速比随卡数增长后走平"的真实曲线。

# -*- coding: utf-8 -*-
# 多卡加速比 = Amdahl 串行上限 × 通信开销折扣

def amdahl(p, N):
    """Amdahl 定律：p 为可并行占比，N 为卡数。"""
    return 1.0 / ((1 - p) + p / N)

def with_comm(p, N, comm_fraction):
    """在 Amdahl 基础上再乘通信折扣：
       每张卡实际算的时间还要加上通信时间 comm_fraction（占并行段的比例）。
       近似：有效卡数 = N / (1 + comm_fraction * N)。"""
    effective_N = N / (1 + comm_fraction * N)
    return amdahl(p, effective_N)

Ns = [1, 2, 4, 8, 16, 32, 64]
print("加速比对比（p = 可并行占比 0.98）：")
print(f"{'卡数':>4} {'理想线性':>8} {'Amdahl':>8} {'+通信10%':>9} {'+通信25%':>9}")
for N in Ns:
    linear = N
    a = amdahl(0.98, N)
    c10 = with_comm(0.98, N, 0.10)
    c25 = with_comm(0.98, N, 0.25)
    print(f"{N:>4} {linear:>8.1f} {a:>8.2f} {c10:>9.2f} {c25:>9.2f}")

# 边际收益：每多加一倍卡，加速比多涨多少？
print("\n从 8 卡翻到 16 卡、32 卡的边际收益（含通信 15%）：")
prev = with_comm(0.98, 8, 0.15)
for N in (16, 32):
    cur = with_comm(0.98, N, 0.15)
    print(f"  {N:>2} 卡：加速比 {cur:.2f}，比 {N//2} 卡多涨 {(cur - prev):.2f}")
    prev = cur

# 推理场景：小 batch 通信占比高，大 batch 通信占比低
print("\n不同通信占比下，16 卡的加速比：")
for frac in (0.05, 0.15, 0.40, 0.80):
    print(f"  通信占并行段 {frac:>4.0%} -> 加速比 {with_comm(0.98, 16, frac):.2f}（线性=16）")

运行后你会发现：即便可并行度高达 98%，64 卡的 Amdahl 上限也远低于 64；再加上通信折扣，16 卡实际可能只到几倍加速。通信占比越高（小 batch 推理越典型），折扣越狠——这正解释了"多卡不是线性加速"。

三、练习#

  1. 手算上限：若可并行占比 p=0.95，当卡数趋近无穷时，加速比上限是多少？（提示：1/(1-p)）
  2. 改 p：把代码里的 p 改成 0.90 和 0.999，观察 Amdahl 曲线"走平"的高度如何变化，说明串行部分为什么是致命伤。
  3. 通信占比：把 comm_fraction 设为 0 与 0.5，分别代表"零通信"与"通信吃满"，对比 16 卡加速比，体会通信对可扩展性的毁灭性影响。
  4. 找拐点：固定 p 和通信占比，找到"再往上加卡加速比反而几乎不涨"的卡数，试着解释为什么实际部署不会无限堆卡。
  5. 思考：为什么推理场景下"小 batch"的多卡加速比通常比"大 batch"更差？如果服务商按卡时收费，你会建议在什么吞吐量下才值得上多卡？
