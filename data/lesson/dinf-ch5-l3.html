滚动升级与配置变更：停机时间、容量模型与版本一致性#

这一节要解决什么#

前两节的所有结论都建立在一个隐含前提上：这个配置会一直跑下去。但真实系统的配置天天在变：

① 模型更新（新权重、新精度、新量化方案）      → 必须重启推理进程（权重在显存里）
② 调度参数 / 限流阈值 / 缓存策略调整           → 可以热更新，但要保证一致性
③ 推理框架升级（kernel、CUDA、通信库）        → 必须重启，且可能改变数值结果
④ 副本扩缩（第 4 章）                          → 也走同一套上下线流程

每一次重启都意味着：在飞请求要被打断或等待、容量在窗口内下降、KV 缓存失效。而"不中断升级"这句话在工程上必须换成三个可算的量：

升级的代价=可用性被中断的请求数​​+延迟窗口内的容量缺口​​+算力与成本冷缓存的重算量​​​

本节把这三件事写成公式，并回答四个问题：

① 摘流量后要留多长的 grace period？它由什么决定（不是"30 秒"）？
② 滚动窗口内少 k 个副本，SLO 还撑得住吗？需要预留多少余量？
③ 版本偏斜（新旧版本同时在线上）会造成什么？KV 缓存能不能跨版本复用？
④ 滚动 / 蓝绿 / 金丝雀的取舍怎么算？金丝雀要跑多久才有统计意义？

一、drain：摘掉流量之后会发生什么#

1.1 "停止收新请求"与"关闭进程"是两件事#

不中断升级的第一步不是重启，而是从负载均衡里摘掉这个实例，但仍把在飞请求做完。这个动作叫 drain。它的时间账由三部分串起来：

Tdrain​=T摘除生效​+Tgrace​+T强制关闭​

阶段 量级 由什么决定 不算清会怎样
摘除生效 心跳周期 Thb​，1~5 s 负载均衡器的健康检查 新请求仍被送进来，drain 白做
grace 5~60 s 在飞请求的剩余服务时间（§1.2） 太短 → 请求被打断；太长 → 发布窗口变长
强制关闭 0~1 s 进程退出清理 慢 → 容量恢复更晚

"摘除生效"这一段最容易被忘掉：如果健康检查周期是 5 s、而 grace 只有 3 s，那么有一段时间新请求进来、老进程已经准备退出 —— 这些请求必然失败。判据是 T摘除生效​≤Thb​ 且 Tgrace​≥ 剩余服务时间的 p99。

1.2 grace period 要多长：一个指数模型的闭式#

设单请求的服务时间均值为 s（对 LLM 服务，s 是整个响应时长，不是 TTFT）。在指数服务下有一个关键性质：

一个"正在服务中"的请求，其剩余服务时间仍服从 Exp(1/s)(无记忆性)

drain 开始时该实例的在飞请求数是 Q≈λshare​⋅s（Little 定律，λshare​=λ/N）。所以：

P(单个请求在 grace Tg​ 内做不完)=e−Tg​/s,被打断的期望数=Qe−Tg​/s=λshare​se−Tg​/s​

本节算例：

三条读法：

  1. 打断数对 s 是指数的：s 从 1 s 涨到 20 s，同样 30 s 的 grace 让打断从 0 涨到 178.5 个。LLM 服务（生成一个回答要几十秒）的 drain 语义与普通 RPC 完全不同 —— 直接把"grace 30 s"抄过来会在长回答上产生 22% 的打断率。
  2. 正确的 grace 由 s 定，不由经验定：要让打断数 ≤1，需要

Tg∗​=sln(λshare​s)

Tg∗​=sln(λshare​s)

s=1 s、λshare​=40 → Tg∗​=3.7 s；s=20 s、λshare​=40 → Tg∗​=20ln800=133.6 s。后者已经超过很多团队愿意接受的发布窗口，所以长回答服务通常选择"接受少量打断 + 客户端重试"而不是"等所有请求做完"。

  1. "自然排空"的分位是硬上界：不做强制 grace 时的排空时间 = 在飞请求的最大剩余服务时间，其分位

tp​=−sln(1−p1/Q)

Q=800、p=0.99 → 225.7 s。这个数就是最坏情况下的停机时间上界，也是"为什么必须强制 grace"的理由。

二、容量模型：窗口内少几个副本#

2.1 两个不同的问题#

滚动升级时"同时不可用的副本数"k 决定了容量缺口。有两个层次的判据，它们的答案不同：

不中断（容量不垮）:λ≤(N−k)μ⟹N≥μλ​+k

不违反 SLO:ρdown​=(N−k)μλ​≤ρt​⟹N≥⌈μρt​λ​⌉+k−1

3 1 4 1.000 inf 否

λ/μ=2 的负载，不中断只要 3 个副本，不违反 SLO 要 4 个​

这一行就是"发布策略的成本"：多出来的那 1 个副本（+33% 算力）是为了在发布窗口里不违反 SLO 而付的，不是为负载付的。

2.2 窗口长度与容量缺口是乘起来的#

"少 k 个副本"只有在窗口内才成立，所以真正的代价是容量缺口的积分：

容量损失=Nk​⋅Twindow​(副本⋅秒)

=Nk​⋅(kbatch​N​)⋅Troll​=kbatch​N​Troll​(与 k 无关！)

这个结果很反直觉：并发更新更多的副本（k 大）不改变总的容量损失，只是把损失压缩到更短的窗口里。它的含义是：

发布的总代价由N（副本数）与Troll​（单实例更新时长）决定，与并发度无关​

所以优化的方向只有两个：减少副本数（不现实）或缩短单实例更新时间（Troll​：权重加载、CUDA graph 捕获、编译缓存）。第 4 章第 2 节算过冷启动的分解 —— 那里的 Tcold​ 就是这里的 Troll​，两节的账是同一笔。

2.3 并发度 k 该取多大：只由"允许的 ρdown​"决定#

既然总代价与 k 无关，k 的唯一约束就是窗口内的瞬时容量：

k≤N−⌈μρt​λ​⌉

本节：N=5、⌈λ/(μρt​)⌉=4 → k≤1。所以"一次更新一半副本"在这个负载下直接违反 SLO（ρdown​=2.0），与窗口长短无关。

三、缓存与预热：窗口内的缓存空洞#

3.1 冷副本把哪些请求打回全量 prefill#

第 2 节的缓存命中率 h 是稳态的。发布窗口内，新起来的副本缓存是空的，所以：

Pˉeff​=L(1−fcold​(1−h))

其中 fcold​ 是"当前处于冷状态"的副本比例（窗口内它随时间变化：从 0 涨到峰值再回到 0）。窗口内多付的重算量：

Δprefill=λTw​L(1−h)fcold​​

本节算例（L=3000、h=0.7、prefill 12,000 token/s、Tw​=180 s、λ=120）：

冷副本比例 额外 prefill（token） 折算卡秒 折算卡时 有效前缀长 prefill 利用率
1/3 6,480,000 540.0 0.150 2,700 0.899
1/2 9,720,000 810.0 0.225 2,550 0.849
2/3 12,960,000 1080.0 0.300 2,400 0.799
1.0 19,440,000 1620.0 0.450 2,100 0.699

有效前缀长=L(1−fcold​(1−h)):f=1/3→2700, f=1→2100

三条读法：

  1. 发布窗口内的 prefill 利用率上升 30%100%（λL/p=30 → 2127）。如果 prefill 本来就是瓶颈（第 2 节的 λPˉTstep​+b≤r），这个上升直接变成 TTFT 恶化。
  2. 冷缓存条目的 KV 是一次性投入：3000×320 KiB=938 MiB/条。预热 N 条就是 N×938 MiB —— 这笔账要算在"发布需要多少额外显存"里。
  3. 顺序很重要：如果先摘流量、后加载权重、最后预热缓存，那么"摘流量"到"预热完"之间这一整段都是冷缓存。并行的做法是「先起新实例 + 预热 + 再摘老实例」（蓝绿），这也是蓝绿贵但稳的原因。

3.2 预热策略：谁先热起来#

策略 做法 预热耗时 命中率恢复
不预热 新副本直接接流量 0 靠真实流量慢慢填（前几百个请求全是 miss）
回放预热 把最近的高频前缀主动重算一遍 Ccache​/p 窗口前就恢复
从对端拉 KV 从老副本把 KV 块传过来 Ccache​/βnet​ 秒级，但需要 KV 格式一致
钉住公共前缀 公共前缀单独一个池，永不失效 0（不随发布失效） 发布期间公共部分不掉

算一笔"从对端拉 KV"的账：16 GB 缓存、跨机 50 GB/s → 16/50=0.32 s。比重新 prefill 快得多（16 GB/(320 KiB/token×12,000 token/s)=4370 s）。但它有三个前提：(a) KV 格式跨版本兼容（§4）；(b) 网络带宽在同一时刻不被推理通信占用（第 3 章的 ρ⋅sbw​）；(c) 对端愿意被拉（老副本还在服务流量）。

四、版本一致性：偏斜窗口里的三种不一致#

4.1 版本偏斜的三个面#

滚动升级必然产生一段"新旧版本同时在线"的窗口。三个面都会出问题：

面 不一致 后果 判据
KV 缓存 新版本改了 KV 布局/量化/位置编码 复用旧 KV → 错误的输出（不是慢） KV 格式版本号必须进缓存 key
数值结果 框架升级改变 kernel 累加顺序 采样路径分叉，同一请求在不同副本上给不同答案 需要"最小公共版本"或固定采样种子
路由与会话 多轮对话的下一轮被路由到另一个版本 上下文理解突变、缓存失效 会话粘性 + 版本门槛

版本偏斜的正确处理不是"避免"，而是"让不一致可检测、可路由、可回滚"​

4.2 不中断升级的四个必要条件#

把 §1~§4.1 合起来，"不中断升级"可以写成一个合取式：

  1. 容量：λ≤(N−k)μρt​（§2.1）—— 否则窗口内 SLO 破。
  2. drain：Tg​≥sln(λshare​s)（§1.2）—— 否则打断率非零。
  3. 缓存：窗口内 Δprefill 有预算，或有预热/拉 KV 的机制（§3）。
  4. 一致性：缓存 key 含版本、会话有粘性、旧版本可回滚（§4.1）。

缺任何一条，"不中断"就退化成"低概率中断"。工程上常见的做法是把这四条做成发布流水线的四个 gate（自动检查），而不是靠人记。

4.3 回滚：最容易被忽略的指标#

回滚时间是发布系统的核心指标，它有三段：

Trollback​=Tdetect​+Tdecide​+Trestore​

段 由什么决定 典型值 可算的判据
检测 金丝雀样本量（§5.2） 8~93 s 见 §5.2 的 SPRT
决策 人工 or 自动阈值 0~300 s 自动：阈值 + 连续 m 个窗口
恢复 权重加载 + 预热 Tcold​（第 4 章第 2 节） 与升级本身一样贵

关键：Trestore​ 与升级的 Troll​ 同量级，所以"回滚很快"是一个需要算的结论，不是默认成立。如果回滚要 180 s，那么 §5.3 的错误预算账要按 180 s 重算。

七、取舍与边界#

  1. Tg​ 与 s 绑定，不是常数：Tg∗​=sln(λshare​s)。长回答服务（s=20 s）需要 130 s 级的 grace；短任务（s=0.2 s）2 s 就够。用同一个 grace 配所有服务是错的。
  2. "摘除生效"的延迟要单独算：它由健康检查周期决定（1~5 s），且与 grace 是串行的。Tdrain​=Thb​+Tg​，漏掉 Thb​ 会让新请求打在正在退出的进程上。
  3. 总容量损失与并发度无关（§2.2）：NTroll​/kbatch​。所以提升并发度只能缩短窗口（对 SLO 有利），不能减少总量。想减少总量只能缩短 Troll​。
  4. 冷缓存的代价是双向的：窗口内 prefill 需求上升（延迟），窗口前预热要一次性显存（成本）。判据是 λTw​L(1−h)f 与预热显存的比较（§3）。
  5. 版本偏斜不可消除，只能管理：三个面（KV 布局、数值结果、会话路由）各自需要机制。其中 KV 布局错误是"静默错误"，最危险 —— 必须把格式版本放进缓存 key。
  6. 回滚时间要单独测：Trestore​ 与 Troll​ 同量级（都要加载权重），所以"回滚很快"是幻觉。把回滚时间写进发布 gate。
  7. 不中断升级的四个条件是合取（§4.2）：容量、drain、缓存、一致性。任一条不满足，"不中断"就只是概率性的。

⚠️ 合成口径：服务时间按指数分布（无记忆性），副本服务率 μ 与到达率 λ 是设定值；Wilson 与 SPRT 是闭式统计量，无随机性。

"""第 5 章第 3 节：滚动升级与配置变更 —— 停机时间、容量模型与版本一致性。

纯标准库。五块：
  ① drain 模型：停止收新请求后，在飞请求还要多久、有多少会被打断
  ② 容量模型：滚动窗口内"少 k 个副本"的利用率、能否撑住 SLO、需要多少余量
  ③ 缓存与预热：冷缓存把哪些请求从 O(0) 打回 O(L)，窗口内要付多少 prefill
  ④ 金丝雀的样本量：要多少请求才能有把握说"新版没退化"
  ⑤ 三种策略（滚动 / 蓝绿 / 金丝雀）与版本偏斜的同坐标系对比 + 错误预算

口径（与第 4 章一致）：
  - 副本服务率 μ 以 req/s 计；利用率 ρ = λ/(N·μ)
  - 用 M/M/c 的等待分位闭式 W_p = ln(C/(1-p))/(cμ-λ) 作尾延迟
  - drain 的"停止收新请求"是从网关摘流量（不是关进程）
"""
import math
import random

# ---------------- 一、drain 模型 ----------------
def drain_model(lam_share, service_s, grace_s, seed=5, n=200000):
    """摘掉流量后，grace 窗口内还没做完的请求有多少？

    指数服务下，一个"正在服务中"的请求的**剩余服务时间**仍服从 Exp(1/service_s)
    （无记忆性）；drain 开始时在飞请求数 Q ≈ λ_share·service_s。
    所以：
      P(单个请求在 grace 内做不完) = exp(-grace_s/service_s)
      被打断 = Q · P(做不完)；若 grace 足够长（≥ 若干倍 service），打断趋近 0。

    返回 (Q, 打断概率, 被打断期望数, 需要多长的 grace 才能把打断压到 1 个以下)
    """
    Q = lam_share * service_s
    p_interrupt = math.exp(-grace_s / service_s)
    interrupted = Q * p_interrupt
    grace_for_one = service_s * math.log(max(1e-12, Q))     # 让 Q·e^{-g/s} = 1
    return Q, p_interrupt, interrupted, grace_for_one


def interrupted_prob(lam_share, T_drain_s, per_req_fail=0.0):
    """drain 窗口内到达该副本的请求数（期望），以及它们被打断的概率。"""
    n_arrive = lam_share * T_drain_s
    return n_arrive, 1.0 - (1.0 - per_req_fail) ** max(0.0, n_arrive)


def drain_tail(lam_share, service_s):
    """不做强制 grace 时，"自然排空"需要多久：Q 个在飞请求的最大剩余服务时间。

    精确分位：max 的 CDF 是 prod_i (1-e^{-t/(s/i)}) = (1-e^{-t/s})^Q，
    所以 t_p = -s·ln(1 - p^{1/Q}) —— 不需要逐样本模拟（第一版写了 Q×n 的重循环，
    Q=400、n=200000 时是 8×10^7 次抽样，直接在 60 s 超时）。
    """
    Q = max(1.0, lam_share * service_s)
    tail = lambda p: -service_s * math.log(max(1e-12, 1.0 - p ** (1.0 / Q)))
    return tail(0.50), tail(0.99), tail(1.0 - 1.0 / max(Q, 2.0))


# ---------------- 二、容量模型 ----------------
def erlang_c(c, a):
    B = 1.0
    for k in range(1, c + 1):
        B = a * B / (k + a * B)
    return B / (1 - a / c * (1 - B)) if a < c else 1.0


def wq_p99(c, lam, mu):
    a = lam / mu
    if a >= c:
        return float("inf")
    C = erlang_c(c, a)
    if C <= 0.01:
        return 0.0
    return math.log(C / 0.01) / (c * mu - lam) * 1000.0


def rollout_capacity(N, k_down, lam, mu, rho_target=0.6):
    """滚动窗口内 k_down 个副本不可用时的容量账。
    返回 (N_min, rho_down, W_p99_down_ms, ok)"""
    N_min = math.ceil(lam / (mu * rho_target))
    rho_down = lam / ((N - k_down) * mu)
    w = wq_p99(N - k_down, lam, mu)
    return N_min, rho_down, w, rho_down < 1.0


def min_replicas_for_drain(lam, mu, rho_target=0.6, k_down=1):
    """让"少 k_down 个副本"后仍不超 ρ_target 所需的最小 N。"""
    return math.ceil(lam / (mu * rho_target)) + k_down - 1


# ---------------- 三、缓存与预热 ----------------
def cache_window_cost(N, k_fraction, lam, L, hit, prefill_tok_s, T_window_s,
                      kv_kib_per_tok=320.0):
    """窗口内 k_fraction 比例的副本是冷缓存，要付多少额外 prefill（token 与卡秒）。"""
    extra_tok = lam * T_window_s * L * (1.0 - hit) * k_fraction
    extra_gpu_s = extra_tok / prefill_tok_s
    kv_mib = L * kv_kib_per_tok / 1024.0
    return extra_tok, extra_gpu_s, kv_mib


def prefill_load(lam, L, hit, k_cold_frac, prefill_tok_s):
    """命中率被冷副本摊薄后的 prefill 利用率。"""
    eff = L * (1.0 - k_cold_frac * (1.0 - hit))
    return lam * eff / prefill_tok_s, eff


# ---------------- 四、金丝雀样本量 ----------------
def wilson_halfwidth(n, p=0.01, z=1.96):
    center = (p + z * z / (2 * n)) / (1 + z * z / n)
    half = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / (1 + z * z / n)
    return center, half


def samples_for_halfwidth(target=0.005, p=0.01, z=1.96, n_max=10 ** 8):
    n = 100
    while n < n_max:
        _, h = wilson_halfwidth(n, p, z)
        if h <= target:
            return n
        n = int(n * 1.3)
    return None


def sprt_samples(p0, p1, alpha=0.05, beta=0.05):
    """序贯概率比检验：区分 p0 与 p1 平均需要的样本数（Wald 近似）。"""
    def kl(p, q):
        return p * math.log(p / q) + (1 - p) * math.log((1 - p) / (1 - q))
    A = math.log((1 - beta) / alpha)
    B = math.log(beta / (1 - alpha))
    n1 = (-B) / kl(p0, p1) if kl(p0, p1) > 0 else float("inf")   # 判 p1
    n0 = A / kl(p1, p0) if kl(p1, p0) > 0 else float("inf")      # 判 p0
    return n1, n0, kl(p0, p1)


# ---------------- 五、策略对比 ----------------
def strategy_table(N, lam, mu, T_roll_s, T_drain_s, k_batch=1):
    """滚动 / 蓝绿 / 金丝雀的停机与容量对比。"""
    rows = []
    # 滚动：分 ⌈N/k_batch⌉ 批
    batches = math.ceil(N / k_batch)
    rows.append(dict(name="滚动(逐副本)", down_cap=batches * k_batch / N,
                     extra_gpu=0.0, window_s=batches * T_roll_s,
                     rollback_s=T_drain_s + T_roll_s))
    rows.append(dict(name="滚动(半批)", down_cap=2 * (N // 2) / N,
                     extra_gpu=0.0, window_s=2 * T_roll_s,
                     rollback_s=T_drain_s + T_roll_s))
    rows.append(dict(name="蓝绿", down_cap=0.0, extra_gpu=N,
                     window_s=T_roll_s, rollback_s=T_drain_s))
    rows.append(dict(name="金丝雀(5%流量)", down_cap=0.0, extra_gpu=math.ceil(N * 0.05),
                     window_s=T_roll_s, rollback_s=T_drain_s))
    return rows


def version_skew_risk(lam, T_window_s, p_bad_deploy, T_detect_s):
    """版本偏斜窗口内被"坏版本"服务的请求数（期望）。"""
    return p_bad_deploy * lam * T_detect_s

五处关键设计决策：

  1. drain 用"剩余服务时间的无记忆性"，不用排队模拟。指数服务下"在飞请求还要多久"仍是指数分布，所以打断数有闭式 Qe−Tg​/s。第一版把 drain 建模成"Q 个请求排队逐个做完"，得出 Q/μ=120 s 级的"完成时间"——那是"把队列清空"的时间，不是"在飞请求做完"的时间，两者差一个数量级。先想清楚"在飞"是什么集合，再写模型。
  2. "自然排空"的分位用极值闭式：tp​=−sln(1−p1/Q)。第一版对每个样本抽 Q 次指数求最大值，Q=400、n=200000 时是 8×107 次抽样，直接把脚本跑到 60 s 超时。极值分位是有闭式的——先查闭式，再考虑模拟。
  3. 容量判据分成两个数（N≥λ/μ+k 与 N≥⌈λ/(μρt​)⌉+k−1）。前者是"不垮"，后者是"不违反 SLO"，本节的 λ/μ=2 让两者分别给出 3 和 4。只报一个数的容量规划会漏掉"发布窗口"这个场景。
  4. 金丝雀给两套样本量（Wilson 与 SPRT），因为它们的用途不同：Wilson 回答"我现在对失败率的估计有多准"，SPRT 回答"要花多少样本才能下判断"。SPRT 平均省 30%~50% 的样本（944 vs 1,774），但只有在你能接受序贯停止时成立。
  5. 错误预算的场景必须带"发现时间"：pfail​λcanary​Tdetect​/λ 里 Tdetect​ 是主导项。把"坏版本"写成一个静态的失败率而不写检测时长，会得出"发布必然超预算"或"发布不花钱"两种相反的错结论。

读输出的三处要点：

  • (1) 段的"自然排空 p99 = 225.7 s"（s=20 s）：这是"不做强制 grace"的停机时间上界。它比任何"发布窗口"都长，所以必须有 grace 与强制关闭，问题只是取多长。
  • (3) 段的"有效前缀长 2,700 → 2,100 token"：注意方向 —— 冷副本越多，有效前缀长越短（因为未命中的部分被 λL(1−h)f 表达为"额外重算量"，f 越大额外量越大）。这两个量是同一件事的两种写法，写错符号会得出"多更新更省算力"的荒谬结论。

小结#

  • 不中断升级的代价由三项组成：被中断的请求（可用性）、窗口内的容量缺口（延迟）、冷缓存的重算量（算力）。三项都有闭式。
  • drain 的 grace 必须与响应时长绑定：打断数 =Qe−Tg​/s，Q=λshare​s。s 从 1 s 涨到 20 s，30 s 的 grace 让打断从 0 涨到 178.5 个。让打断 ≤1 需要 Tg∗​=sln(λshare​s)。
  • 两个容量判据给出两个副本数：不中断要 N≥λ/μ+k，不违反 SLO 要 N≥⌈λ/(μρt​)⌉+k−1。本节 λ/μ=2 时分别是 3 和 4 —— 多出的那 1 个副本是"发布税"。
  • 发布的容量总损失与并发度无关：NTroll​/kbatch​（副本·秒）。提升并发度只压缩窗口，减少损失只能缩短 Troll​（权重加载、CUDA graph、编译缓存）。
  • 冷缓存空洞是可算的：Δprefill=λTw​L(1−h)fcold​，本节 6.48M19.44M token（0.150.45 卡时）。窗口内 prefill 利用率上升 30%~100%，如果 prefill 是瓶颈就直接变成 TTFT 恶化。
  • 金丝雀的观察时长由样本量决定：要把失败率的区间压到 ±0.5% 需要 1,774 个请求；用 SPRT 区分 1% vs 2% 只需 944 个。"检出多小的退化"是可以被采购的指标；低流量服务做不了统计意义的金丝雀，要用影子流量或离线回归。
  • 发布消耗错误预算，而主导项是检测时间：同一个 2% 的坏版本，120 s 发现花 0.127% 年预算，30 min 才发现花 1.90%（差 15 倍）。发布流水线的第一优先级是缩短检测时间。
  • 版本偏斜有三个面（KV 布局、数值结果、会话路由），其中 KV 布局错误是静默错误 —— 必须把格式版本放进缓存 key。回滚时间 Tdetect​+Tdecide​+Trestore​ 要单独测。
  • 一句话："不中断"不是一种配置，而是一个合取式（容量 ∧ drain ∧ 缓存 ∧ 一致性）；把它写成四个可算的判据，发布就从"赌一把"变成"过四个 gate"。
