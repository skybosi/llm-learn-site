可回滚的发布：版本一致性、缓存失效与回滚时间账本#

这一节要解决什么#

前三节把"该不该发"做成了可复算的判据，也承认了一件事：门禁只能降低事故概率，不能消除它。所以每一次发布都必须回答一个更硬的问题：

如果这次发出去坏了，我多久能回到"上一个好状态"？回到的是不是当时那个状态？

"回滚"在软件里通常被等价成 git revert + 重新部署。在模型发布里这个等价关系在四个地方断裂：

断裂点 软件 模型发布
回滚的对象 代码（一个 commit） 一个推理单元：权重 + tokenizer + prompt 模板 + 解码参数 + 引擎 + 后处理
"上个版本"是什么 上一个 commit，确定 指针指向的那个当时的绑定，而不是"用今天的数据重建的同一份代码"
状态 大多无状态 缓存、会话历史、特征服务、下游 schema 都可能已被新版本改写
时间 通常秒级 探测 + 决策 + 传播 + 重启 + 缓存预热，可能是分钟级

本节把"可回滚"做成一个可承诺、可测量、可演练的能力，四块内容：

  1. 版本一致性：把发布定义成一个不可变的绑定（manifest），任何一个部件漂移都改变整单元的哈希；以及为什么"改了 prompt 没改权重"是最常见的静默事故。
  2. 三层命名空间：内容寻址的制品层、只追加的逻辑版本层、可变的指针层。回滚 = 移动指针，不是重建制品。
  3. 缓存失效：缓存 key 必须含绑定哈希。不含它时，切换到新模型后会有约 60% 的回答来自旧模型（本节实测），而监控上看不出任何异常。
  4. 回滚时间账本（RTO 账本）：把 RTO 拆成探测 / 决策 / 传播 / 重启 / 预热五段，给出可算的预算分配，并说明先优化哪一段。

一句话给出本节的结论：可回滚性 = 内容不可变 + 依赖版本化 + 状态可隔离 + RTO 可测量；四者缺一，回滚就只是"希望"。

一、发布单元：一个不可变的绑定#

1.1 推理单元包含什么#

ch1-l2 已经给出"模型版本"的正确对象是推理单元。本节把它变成一个可计算的东西：

manifest = {
  weights       权重文件的内容哈希
  tokenizer     分词器版本 + 词表哈希
  prompt_tmpl   模板文本的哈希（含 system / few-shot / 变量顺序）
  decode        temperature / top_p / max_tokens / stop 序列
  engine        推理引擎及其版本（vLLM/TensorRT-LLM/自研）
  postproc      后处理规则（归一化、过滤、格式化）
}
binding_hash = md5(canonical_json(manifest))

canonical_json 的四条规范化规则（与 ch1-l1 的 config 哈希同源）：键排序、无多余空白、浮点统一 repr、缺省值显式化。代码实测：只改键序（等价 JSON）不改变哈希，而任何一个字段改变都会改变整单元的哈希：

  基线 manifest 哈希 = 2f5c8b75e4292f8130a03fd89fa695fe
  改 weights      → 8dbb106047ca78f5d8a48cf39522367b  同基线: False
  改 tokenizer    → e5e75f0d8a45b2b0db10843e4d386cbc  同基线: False
  改 prompt_tmpl  → 05179d571df169e72005497eb4ff3af6  同基线: False
  改 decode       → c09f3c859cbd53d8a1b27e89de7ab81a  同基线: False
  改 engine       → 38f265d42d5c8fb56ef905219d759586  同基线: False
  改 postproc     → 39ddf8c7d62eb5b43982fc3aebd01e06  同基线: False
  只改键序（等价 JSON）：True

为什么必须绑成一个哈希：制品库、配置中心、prompt 仓库、路由规则分散在四个系统里，发布时"逐个更新"必然出现"一半新一半旧"的中间态。绑成一个哈希以后，"当前处于什么状态"变成一个可比较的值，灰度检查、缓存 key、回滚目标全都从它派生。

1.2 版本漂移：最常见的静默事故#

代码第 2 节把四个副本与目标 manifest 逐个比对：

  pod-0: 漂移字段 ['prompt_tmpl', 'weights']
  pod-2: 漂移字段 ['prompt_tmpl', 'weights']
  pod-3: 漂移字段 ['prompt_tmpl']
  一致副本 1 / 4；不一致副本必须逐个修复，否则流量分布被污染。

注意 pod-3 只漂移了 prompt_tmpl：它的权重已经换成新版，prompt 还是旧版。这正是生产里最容易发生的事故形态：

  • 权重换了、prompt 没换 → 输出的风格/长度/格式变化无法归因（评测的 prompt 与新 prompt 不同）；
  • prompt 换了、权重没换 → 看起来"新版本变差了"，其实只是模板变了；
  • tokenizer 换了、权重没换 → 直接是错的（embedding 空间不匹配）。

纪律：发布系统必须原子地切换整个 manifest；灰度检查（每次滚动发布后）必须比较每个副本的 manifest 哈希，而不是"进程起来了就算成功"。

1.3 三层命名空间（ch1-l2 在发布侧的落地）#

层 可变性 内容 回滚时的操作
制品层 不可变、内容寻址 w-7f3a / pt-11 的实际字节 不操作（必须还在）
逻辑版本层 只追加 v41 = {weights: w-7f3a, prompt: pt-11, ...} 的 manifest 不操作
指针层 可变、留审计 prod → v42、canary → v43 回滚就是移指针

代码第 7 节的指针历史：

  2026-09-20T10:00Z prod → v41（权重 w-7f3a）
  2026-09-21T09:30Z prod → v42（权重 w-9c01）
  2026-09-21T11:10Z prod → v41（权重 w-7f3a）

三条纪律：

  1. 制品层不可覆写：v41 引用的权重文件必须永远按内容寻址可取回。一旦"就地更新已发布版本"，回滚就变成不可能（见第四节）。
  2. 逻辑版本只追加：修一个 bug 不能改写 v41 的内容，只能发布 v43。改写会让"当时线上是 v41"这个事实失效。
  3. 指针移动留审计：每条记录含时间戳、操作者、原因。事故复盘时，"什么时候切的、切了几次"必须能从指针历史回答。

二、缓存失效：一个哈希引起的 60% 陈旧回答#

2.1 问题#

线上推理几乎都有缓存（prompt 级、前缀 KV、结果级）。缓存 key 的设计决定了切换版本时缓存是否失效：

错误： cache_key = hash(prompt)
正确： cache_key = hash(prompt, manifest_hash)

代码第 3 节模拟一次 50% 处的版本切换（n=2×105，切换前命中率 0.90，旧模型的缓存条目在切换后仍可命中），实测：

  切换前命中率 0.90（预热充分）
  窗口总体命中率：key 含版本 = 0.450；key 不含版本 = 0.750
  切换后仍命中旧条目的比例（=陈旧回答） = 0.599

读法：key 不含版本时，切换到新模型后约 60% 的回答仍然来自旧模型 —— 而且这是一个静默故障：

  • 监控上：命中率漂亮（0.75 vs 0.45），延迟更低，成本更低；
  • 灰度上：实验组里有 60% 的流量其实跑的是旧模型，效应被稀释一半以上（你以为在测新模型，实际在测 40% 新 + 60% 旧的混合体）；
  • 事故中：新模型明明有个 bug，但线上只是偶尔触发（40% 的请求），难以复现。

这条把第 3 节的纪律补全了：灰度的四样对齐（权重 / tokenizer-prompt / 缓存 key / salt）里，缓存 key 是最容易漏、后果最隐蔽的一项。

2.2 缓存的代价：预热时间#

正确入 key 的代价是切换瞬间缓存全冷。预热时间：

Twarm​=rwarm​Ccache​​,rwarm​=并发×单请求生成速率

代码实测：

缓存容量 C 预热速率 r Twarm​ 占 300s RTO
200 GB 2.0 GB/s 100.0 s 33.3%
200 GB 20.0 GB/s 10.0 s 3.3%
2000 GB 20.0 GB/s 100.0 s 33.3%

工程含义：预热时间与缓存容量成正比、与预热并发成正比。所以降低"缓存全冷"的冲击有三条路（按性价比排序）：

  1. 预热而非等待自然命中：切换前用影子流量把新版本的缓存条目预先建好（第 3 节的影子流量在这里有第二个用途）；
  2. 双缓存并存：新 key 空间独立，旧 key 空间保留，命中率平滑过渡（代价是内存翻倍）；
  3. 给 key 加"版本代"而不是全哈希：例如 hash(prompt, manifest_major)，兼容的 minor 变更共用缓存（代价是偶发的跨版本命中，需要判断是否可接受）。

2.3 缓存之外的三类状态#

状态 是否随回滚恢复 处置
结果缓存 / 前缀 KV 否（key 正确时新版本自动隔离） key 含 manifest_hash
会话历史 否 标记版本，回滚后新会话用旧模型，旧会话显式收尾
下游特征/schema 否 依赖版本化 + 兼容窗口（见第四节）
日志/指标口径 是 记录 manifest_hash 以便按版本切分

三、回滚时间账本（RTO 账本）#

3.1 分解#

RTO=T探测​+T决策​+T传播​+T重启​+T预热​

代码第 6 节的算例（预算 300s）：

阶段 耗时 占比
探测（窗口 + 告警） 30.0 s 13.3%
决策（人 / 自动） 60.0 s 26.7%
传播（配置 / 路由下发） 15.0 s 6.7%
重启 / 切流 20.0 s 8.9%
缓存预热 100.0 s 44.4%
合计 225.0 s ≤ 300 s ✅

这张账本最重要的用法是排优先级：

  • 预热的绝对时间最大（100s），但它是可控的（加并发、预热、双缓存）；
  • 探测 + 决策 = 90s（40%），其中"决策 60s"说明回滚要等人点按钮 —— 这是最该被自动化替换的一段；
  • 传播 15s + 重启 20s 是基础设施的固有延迟，压它需要架构改造（热切换），性价比通常最低。

承诺 RTO 的正确姿势：不是"我们 5 分钟能回滚"（没人知道哪一段慢），而是给每一段定预算并测量：

SLORTO​=300s,预算=(30,60,15,20,100)s,每段 p95​ 超预算即告警

3.2 探测与熔断：不要用单个点触发回滚#

探测段的判据必须抗抖。代码第 5 节用"连续 3 个窗口超阈值"的规则（p99​>850ms）实测：

  单点抖动     p99=[700, 900, 710, 720, 705, 715] → 第 6 个窗口 未熔断
  持续劣化     p99=[700, 900, 910, 920, 930, 940] → 第 4 个窗口 熔断
  边界震荡     p99=[700, 860, 840, 870, 830, 880] → 第 6 个窗口 未熔断

三个设计要点：

  1. 连续计数而不是单点：单点抖动（一次 900ms）不触发，持续劣化在第 4 个窗口就熔断；
  2. 熔断判据 ≠ 实验判据：熔断看的是工程护栏（错误率、p99、成本），要求"立即、无争议"；实验判据（第 2 节）看的是统计显著性，要求"样本量与多重性"。两者不能用同一个阈值；
  3. 窗口长度与最小样本量要写死：例如"每 10 秒或每 1000 请求（取先到者）算一次 p99​"，避免单个慢请求触发全量回滚。

3.3 自动回滚的边界条件#

自动回滚很诱人，但以下四种情况不能自动：

情况 为什么
信号本身可疑（监控断流、上游抖动） 回滚会掩盖真正的问题，且造成无谓抖动
回滚需要数据/状态迁移 自动执行可能造成不可逆的数据损失
事故原因在依赖（下游 schema / 特征服务） 回滚本模型无效
无人值守时段 回滚后无人验证，可能连环失败

实践折中：分级自动 —— 护栏熔断（延迟/错误率）全自动（能自愈、可逆），主指标下降（需要判断）半自动（自动准备好回滚动作，人工确认）。

四、回滚的边界：什么时候回不去#

4.1 四种场景#

代码第 8 节把"回滚能不能成功"数量化：

  权重按内容寻址存放                  可恢复比例=1.00  把指针指回旧哈希即可，精确恢复
  就地覆盖了已发布权重                 可恢复比例=0.00  无法恢复（除非另有备份）
  下游特征服务已按新 schema 升级        可恢复比例=0.00  回滚权重无效：输入分布已变
  会话状态里有新模型生成的 KV/历史         可恢复比例=0.00  回滚只对新会话生效
  结论：可回滚性 = 内容不可变 + 依赖版本化 + 状态可隔离，三者缺一不可。

4.2 两个必须提前设计的东西#

(a) 依赖的兼容窗口。发布的 manifest 不仅要绑自己，还要声明依赖的版本范围：

manifest.deps = {feature_service: ">=3.2,<4", retrieval_index: "idx-2201"}

回滚的前提是"旧 manifest 的依赖在新环境里仍然可用"。所以：

  • 下游升级要保留至少一个版本的向后兼容（旧 schema 继续可读）；
  • 双写期：schema 变更时先双写、再迁移、最后删旧 —— 这样回滚窗口 = 双写期。

(b) 状态的隔离与清理。会话历史里如果混入了新模型生成的内容，回滚后这些会话要么：

  • 显式收尾（继续用旧模型处理，但历史里有新模型的内容）；
  • 或者重置到某个检查点（用户体验受损但一致）。

可算的判据：设新模型上线 t 小时后回滚，受影响会话比例

faffected​≈1−e−λt,λ=该用户群的会话到达率

例如 λ=0.5/h、上线 2 小时：f≈63%。这个数告诉你"回滚的干净程度"随时间快速下降 —— 越早回滚越干净，这也是把 RTO 压进 5 分钟的真实价值。

4.3 回滚 vs 向前修复#

并非所有故障都该回滚：

场景 选择 理由
新版本崩溃 / 严重错误率上升 回滚 旧版本已知良好
新版本小幅劣化，但已定位原因 向前修复（roll forward） 回滚会丢掉本次发布的全部收益，且要再做一次发布
配置类问题（阈值、prompt） 向前修复 改配置比切版本快，且不需要重新预热缓存
数据/schema 已迁移 只能向前 回滚会造成数据不一致

最容易踩的坑：把"回滚"当成"恢复到昨天的配置"。如果期间有其他配置变更（限流阈值、路由权重），回滚代码版本会把它们一起带回去。所以指针必须指向完整的绑定（代码 + 配置 + manifest），且回滚操作要能选择"只回滚模型、保留其他配置"。

五、取舍与边界#

  1. 绑定粒度越细，回滚越精确，但发布越慢：把 20 个参数全绑进 manifest，任何一个小改动都要走完整发布流程。折中：绑定"影响输出的东西"（权重、prompt、解码、引擎、后处理），不绑"不影响输出的运维参数"（副本数、日志级别）。
  2. 缓存 key 加版本的代价是命中率：每次发布都会缓存全冷（本例 0.90 → 0.45 的窗口总体命中率）。它换来的是正确性，不能省；但可以用预热/双缓存把代价压到可接受。
  3. RTO 是分布不是常数：承诺 300s 意味着 p95​ ≤ 300s，而不是"平均 300s"。事故往往发生在高负载时段，此时重启和预热都更慢 —— RTO 要在峰值压力下演练，而不是在凌晨低峰测一次。
  4. 回滚演练必须定期做：不演练的回滚路径在真正需要时必然失败（权限过期、脚本位腐化、制品被清理）。建议每月一次"无通知回滚演练"，并把实际耗时记入账本。
  5. "能回滚"不等于"该发布"：回滚能力降低事故代价（C放​），按第 2 节的框架它会放宽最优 α（更敢发）—— 但它不能替代门禁。正确的组合是：门禁挡住大部分明显坏的，可回滚性兜住剩下的。

"""第 2 章第 4 节：可回滚的发布 —— manifest 绑定、漂移检测、缓存失效、RTO 账本。

只用标准库。合成数据 ⚠️ 均已标注（固定种子，可逐字节复现）。
"""
import hashlib
import json
import random

# ---------------------------------------------------------------- manifest 绑定
FIELDS = ["weights", "tokenizer", "prompt_tmpl", "decode", "engine", "postproc"]


def canonical(obj):
    """规范化 JSON：键排序、无多余空白、浮点统一 repr。"""
    return json.dumps(obj, sort_keys=True, separators=(",", ":"),
                      ensure_ascii=False)


def binding_hash(m):
    """整单元的绑定哈希：任何字段变化都会改变它。"""
    return hashlib.md5(canonical(m).encode()).hexdigest()


def manifest(weights, tokenizer, prompt_tmpl, decode, engine, postproc):
    return {"weights": weights, "tokenizer": tokenizer,
            "prompt_tmpl": prompt_tmpl, "decode": decode,
            "engine": engine, "postproc": postproc}


# ---------------------------------------------------------------- 漂移检测
def drift(deployed, target):
    """返回漂移的字段列表（按字段名排序）。"""
    return sorted(f for f in FIELDS if deployed.get(f) != target.get(f))


def rollback_plan(deployed_list, target):
    """每个副本要改什么；返回 [(副本名, 漂移字段)] 与修复工作量估计。"""
    plan = []
    for name, dep in deployed_list:
        d = drift(dep, target)
        if d:
            plan.append((name, d))
    return plan


# ---------------------------------------------------------------- 缓存失效
def cache_sim(n, switch_at, old_hit, p_old_only=0.60, seed=11):
    """模拟一次版本切换前后各半个窗口的缓存命中。

    key 正确（含 manifest_hash）vs key 错误（不含）两种实现的命中率对比。
    """
    rng = random.Random(seed)
    before = int(n * switch_at)
    after = n - before
    hits_correct = hits_wrong = stale = 0
    for _ in range(before):
        if rng.random() < old_hit:
            hits_correct += 1
            hits_wrong += 1
    for _ in range(after):
        if rng.random() < old_hit:
            # 新模型的 key 正确版本：旧条目不再命中
            pass
        if rng.random() < p_old_only:
            hits_wrong += 1     # key 不含版本 → 命中旧条目
            stale += 1
    return {
        "hit_correct": hits_correct / n,
        "hit_wrong": hits_wrong / n,
        "stale_share": stale / after if after else 0.0,
    }


# ---------------------------------------------------------------- 熔断与 RTO
def detect_latency(samples, threshold, need=3):
    """连续 need 个窗口超阈值才判定熔断（避免单点抖动触发回滚）。"""
    streak = 0
    for i, p99 in enumerate(samples, start=1):
        streak = streak + 1 if p99 > threshold else 0
        if streak >= need:
            return i, True
    return len(samples), False


def rto_ledger(stages, budget):
    """累加各阶段耗时，给出门是否满足 RTO，并列出超预算项。"""
    total = sum(v for _, v in stages)
    worst = sorted(stages, key=lambda kv: -kv[1])[:2]
    return total, total <= budget, worst

练习#

  1. 给你现在的发布写一份 manifest 与漂移检查： （a）列出"改变输出"的全部部件，写出 manifest 的字段与规范化规则（键序、浮点、缺省值）； （b）计算一次真实发布的 binding_hash，并验证"只改键序不变、改任一字段必变"； （c）设计滚动发布后的漂移检查：怎么取到每个副本的实际 manifest？多久查一次？发现漂移怎么处置？

  2. 缓存 key 审计： （a）找出你系统里所有缓存（结果缓存、前缀 KV、embedding、检索结果），写出各自的 key 构成； （b）判断哪些 key 缺了 manifest_hash，估算"切换版本后陈旧命中的比例"（用本节 cache_sim，把 p_old_only 换成你的实测值）； （c）给出修复顺序（按影响面与改动成本排序）。

  3. RTO 账本实测： （a）把最近一次回滚（或一次演练）拆成五段，给出每段耗时； （b）计算各段占比，指出最该优化的一段； （c）写出你的 RTO SLO 与每段预算（p95​），并设计"超预算告警"。

  4. 熔断判据设计： （a）为错误率、p99 延迟、单请求成本各定窗口长度、最小样本量与连续窗口数； （b）用本节 detect_latency 检验你的判据对"单点抖动"和"持续劣化"的区分度； （c）说明哪些信号的熔断可以全自动，哪些必须人工确认，并给出理由。

  5. 依赖兼容窗口： （a）列出你的模型依赖的外部服务/schema（特征、检索、工具、下游）； （b）为每一个写出"回滚窗口"（旧版本还能用多久），并把它写进 manifest 的 deps； （c）设计一个双写 + 迁移 + 删旧的计划，标出每一步的可回滚性。

  6. 回滚演练： （a）设计一次"无通知回滚演练"的脚本：目标、判据、计时方式、成功标准； （b）在演练中记录实际 RTO，并与账本预算比较； （c）列出演练暴露的"回不去"问题（权限、制品被清理、脚本腐化、缓存未隔离），给出修复项。

  7. 回滚 vs 向前修复的决策： （a）为四类故障（崩溃 / 指标劣化 / 配置错误 / 数据迁移）分别给出默认决策； （b）写出各自的判据（多久能定位？修复成本？回滚会造成什么数据不一致？）； （c）用一个真实案例复盘：当时选的是回滚还是向前修复？按你的判据应该选哪个？

小结#

  • 发布单元是一个绑定，不是一个文件：manifest = {weights, tokenizer, prompt_tmpl, decode, engine, postproc}，binding_hash = md5(canonical_json(manifest))。代码实测：改任一字段哈希必变，只改键序不变。pod-3 只漂移 prompt_tmpl 是最典型的静默事故。
  • 三层命名空间：内容寻址的不可变制品层、只追加的逻辑版本层、可变的指针层。回滚 = 移指针；制品被就地覆写，回滚就从原理上不可能（可恢复比例 = 0）。
  • 缓存 key 必须含 manifest_hash：不含它时，切换版本后约 60% 的回答来自旧模型，而命中率、延迟、成本全部"看起来更好"，灰度效应被稀释一半以上 —— 这是最隐蔽的一类发布故障。
  • 缓存全冷的代价可算：Twarm​=C/r。200GB / 2GBps = 100s，占 300s RTO 的 33%；200GB / 20GBps 只要 10s。处置优先级：切换前预热 > 双缓存并存 > 粗粒度版本代。
  • RTO 要拆账：RTO=T探测​+T决策​+T传播​+T重启​+T预热​。算例 30+60+15+20+100 = 225s ≤ 300s；占比最大的是缓存预热（44%）与人工决策（27%）。承诺 RTO 的正确方式是给每段定预算并测量 p95​，而不是报平均值。
  • 熔断判据要抗抖：连续 3 个窗口超阈值 —— 单点 900ms 不触发、持续劣化第 4 个窗口熔断。工程熔断 ≠ 实验判据：前者要立即、无争议；后者要样本量与多重性。
  • 回滚的边界是依赖与状态：下游 schema 已升级、会话状态已被写入时，回滚权重无效。对策是依赖版本范围写进 manifest + 兼容窗口（双写期）+ 状态隔离。受影响会话比例 f≈1−e−λt，所以越早回滚越干净。
  • 回滚演练是纪律不是选项：权限过期、制品被清理、脚本腐化都会让"纸面上的回滚"在真实事故中失效。每月一次无通知演练，把实测耗时记入账本。

本章到此结束：第 1 节把数据门禁写成可算的期望成本，第 2 节把评测门禁写成假设检验 + 成本最优 α，第 3 节把发布门禁推到线上（影子 / 灰度 / 停止边界），第 4 节把"坏了怎么办"做成可承诺的 RTO。四条线合起来是一句话：流水线的价值 = 它拦下的事故的期望收益 − 它的运行成本；而这条式子里的每一个量（di​、Cesc​、α、C拦​/C放​、MDE、RTO）都必须能被测量或被明确假设。 测不出来的部分，就是这套流水线真正脆弱的地方。
