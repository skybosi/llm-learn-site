端到端账本：TTFT/TPOT/吞吐/成本逐项算，以及"为什么不是另一个方案"#

这一节要解决什么#

上一节选定了架构：TP=2、bf16、前缀缓存 h=0.45、N∗=3 副本（6 卡 / 2 节点）。但"选定"不等于"算清"。真实项目里，评审会问的是这些问题：

① 你这 49.2 ms 的 TTFT p99 是怎么来的？哪一项占大头？
② 6.82 ms 的 TPOT 里，有多少是"必须花的"、有多少是"配置不好"？
③ 20,000 tok/s 的需求，为什么是 6 卡而不是 2 卡？（下界算出来是 2.03）
④ 如果流量翻倍、或者上下文翻倍，成本涨多少？
⑤ 为什么不用 TP=4？为什么不开 FP8？—— 每一个"没选"的方案都要有账

本节把这些回答变成一张逐项可复核的账本。它的结构是固定的五本账：

延迟账 → 单位成本账 → 舰队账 → 采购账 → 敏感性账​

为什么"账本"比"结论"更重要：上一节已经给出结论（6 卡 / 5,832 元/月）。但如果账本不透明，一旦线上实测与模型差 20%，团队无法判断是"模型错"还是"配置错"。账本的作用是让误差可以归位到某一项。

一、延迟账：把 TTFT 与 TPOT 拆到不可再拆#

1.1 TTFT 的两项#

TTTFT,p99​=排队Wp99​(ρ)​​+prefill 算力Tprefill​(Lp99​(1−h))​​

代入本节（N=3、ρ=0.379、μ=qmax​/s=128/0.728）：

项 算式 数值 占 TTFT
排队 Wp99​ ln(50)/(μ−λ/N) 35.8 ms 72.8%
prefill 算力 Tprefill​ 2P⋅Lp99​(1−h)/(TP⋅PEAK⋅MFU)+T0​ 13.4 ms 27.2%
TTFT p99 合计 49.2 ms 用掉 SLO 的 16.4%

TTFT 的大头是排队（72.8%），不是 prefill 算力（27.2%）​

TTFT 的大头是排队（72.8%），不是 prefill 算力（27.2%）​

这条结论直接改变优化方向：如果只盯着"prefill 怎么更快"（换 kernel、调分块），最多把 49.2 ms 压到 35.8 ms；而降排队（加并发槽、加副本）能把 35.8 ms 里的绝大部分消掉。第 4 节的优化清单就是按这个比例排序的。

但要注意这个 72.8% 是"当前 N"的属性，不是服务的属性。N 越大 ρ 越小、排队占比越低：

N ρ 排队 p99 prefill TTFT p99 排队占比
3 0.379 35.8 ms 13.4 ms 49.2 ms 72.8%
4 0.271 29.2 ms 13.4 ms 42.5 ms 68.6%
5 0.211 26.2 ms 13.4 ms 39.6 ms 66.2%

为什么 N=3 依然选它：N=5 只把 TTFT 从 49.2 压到 39.6（省 9.6 ms），却要多花 3,888 元/月。在 TTFT SLO 是 300 ms 而实际只用 49.2 ms 的情况下，这 9.6 ms 不值得买 —— 钱应该花在能降低卡数的地方（第 4 节）。

1.2 TPOT 的三项#

TTPOT(b)​=max内存(cw​+bckv​)​​, 算力TP⋅PEAK⋅MFU2Pb​​​ + 固定T0​​​

项 数值 占 TPOT 能不能单独优化
读权重 cw​ 2.985 ms 41.8% 量化权重（FP8 减半）
读 KV bckv​ 1.152 ms 16.1% 压缩/量化 KV
固定开销 T0​ 3.000 ms 42.0% CUDA Graphs、融合 kernel
算力项 0.572 ms 8.0% 无效（被 max 吃掉）
合计 7.143 ms 用掉 SLO 的 23.8%

这张表最重要的两个数是"比较"而不是"数值"：

  1. cw​（2.985）与算力项（0.572）差 5.2 倍 → 彻底带宽受限，加算力无效（与上一节结论一致）。
  2. T0​=3.0 ms 占 42.0% —— 这是"配置不好"的那部分。T0​ 是每步的 kernel 启动、采样、调度开销，与 batch 无关，所以 batch 越小它占比越高。

T0​ 与 b 的权衡：N 越大 → 每副本需求批越小 → T0​ 摊销越差：

N b cw​ bckv​ T0​ tstep​ T0​ 占比
3 48.51 2.985 1.152 3.0 7.143 ms 42.0%
4 34.75 2.985 0.826 3.0 6.816 ms 44.0%
5 27.07 2.985 0.643 3.0 6.633 ms 45.2%

T0​ 的占比随 N 上升 —— 这是"扩副本"的隐性成本​

它的工程含义：N 从 3 加到 5 看起来只是"多买卡"，但每张卡的 T0​ 摊销都变差了（42% → 45.2%）。这条曲线给出了一个反直觉结论：在带宽受限的服务里，扩副本不是线性扩容。

1.3 端到端延迟：一个请求头到尾#

Te2e​=TTTFT​+Pout​⋅TTPOT​=49.2+100×7.143=763.5 ms

注意这不是 p99​：TTFT 与 TPOT 的尾是相关的（同一个请求既可能排队久、也可能 batch 大），所以 p99​ 的端到端不是两个 p99​ 相加（第 5 章第 1 节已经算过这个上界关系）。

量 均值口径 尾口径 说明
端到端 763.5 ms ≥763.5 ms 尾不能由分位相加得到
请求驻留 s 728 ms — 排队论里的服务时间

s=728 ms 与端到端 763.5 ms 的差是 35 ms：s 是从"开始服务"到"完成"，端到端还含排队。这个差在小 ρ 时不显著，ρ→1 时会主导（第 3 节的压测表会给出这个过渡）。

二、单位成本账：从卡时到 1M token#

2.1 每 token 卡时#

τtok​=btstep​(b)​=48.517.143 ms​=0.1472 ms=1.47×10−4 卡时/token

thrgpu​=τtok​1​=6,792 tok/s

这个 6,792 与上一节的"上限 9,846"差 31%：因为 N=3 时 b=48.51 没到 bcap​=77.01（需求没顶满显存）。这是"稳态工作点"与"单卡上限"的区别，两者必须分开记账。

2.2 最小卡数的三个口径#

口径 算式 结果 与实际的差
只算算力 λPout​/rprefill​ 20,000/84,771=0.236 卡 低 8.6×
用稳态吞吐 20,000/6,792=2.94 卡 与实际同量级 差在离散化
用单卡上限 20,000/9,846=2.03 卡 下界 不可达（显存夹住）

"下界 2.03 卡"与"实际 6 卡"之间差的是：离散化 + 显存 + SLO 余量​

把差额逐项摊开：

差额来源 影响 算式
离散化（副本→卡） 2.03 → 3 副本 ⌈⋅⌉ 到整数副本
副本→卡 3 副本 → 6 卡 ×TP
显存（b≤bkv​） 排除 2 副本解 bdem​=79.55>bkv​=77.01
SLO 与吞吐余量 吞吐裕 1.02× 硬约束 C1

最后一行是本节最值得注意的：吞吐裕度只有 1.02×。这意味着没有任何余量吸收"流量估算偏差" —— 如果真实 λ 是 220 而不是 200，N=3 立刻不成立（第 3 节的压测表显示 1.6× 就破）。这正是必须按峰值或冗余配置的数学理由（§3 与第 4 节）。

2.3 单位成本与预算线#

thrgpu​p​ [元/1M]=6,7922.70​×106=0.3975 106 tok元​ (稳态口径)

thrmax​p​=0.2743 106元​ (穷尽显存后的最好情况)

两条线之间的关系就是"钱花在哪"：稳态 τtok​ 比最优值高 44%，说明当前工作点还有 44% 的理论空间，办法是"让 b 更大"（即 N 更小）——但那会撞上 C1/C2/C5。这就是上一节解的权衡。

三、舰队账与采购账#

3.1 三档规模#

方案 N 卡 节点 月-竞价 月-按需 $/1M
稳态 N∗ 3 6 2 5,832 元 19,440 元 0.0817
稳态 +1 副本 4 8 2 7,776 元 25,920 元 0.1089
稳态 +2 副本 5 10 3 9,720 元 32,400 元 0.1360

加上非 GPU 项（网络/本地盘/镜像 20 元/节点/天）：

C稳态​=5,832+2×20×30=5,832+1,200=7,032 元/30 天

为什么把非 GPU 项单列：GPU 卡时费会随竞价波动 3 倍，而网络/存储基本固定。把两者混在一起会让"采购决策"看起来在影响一个它其实影响不了的量。

3.2 单节点失效的容量核算#

每节点 4 卡、每副本 2 卡 → 每节点 2 副本。所以失 1 节点 = 少 2 副本：

失效 剩余 N b 吞吐裕度 TTFT p99 判定
0 节点 3 48.51 1.02× 49.2 ms ✓
1 节点 2 77.01 0.98× 77.6 ms ✗ 吞吐 0.98× + 显存 + prefill 0.96×
2 节点 1 77.01 0.49× ∞ ✗ 排队论上不稳定（ρ=1.24）

稳态 N∗=3 是"零冗余可行解"；生产要 N≥4（8 卡）​

稳态 N∗=3 是"零冗余可行解"；生产要 N≥4（8 卡）​

注意 N=2 时 TTFT 反而"够用"（77.6 ms < 300 ms） —— 失败的原因是吞吐缺口与显存，不是延迟。这说明"看延迟指标决定是否扩容"是错的：容量不够时延迟可能还很好看，直到 ρ→1 才突然恶化（第 3 节的 1.5× 之后那段）。

3.3 采购：竞价的价格优势必须用中断率折价#

采购 单价 月成本（N=5） 相对按需
竞价 2.70 元/卡时 9,720 元 1.00×
按需 9.00 元/卡时 32,400 元 3.33×

两者的差别不是"成本"，而是"容量确定性"：竞价实例被回收后，C1 的裕度直接消失（因为裕度只有 1.02×）。所以正确的用法是：

稳态容量N竞价​​​+按需或跨区竞价N冗余​​​ ≥ N∗+kfail​

稳态容量N竞价​​​+按需或跨区竞价N冗余​​​ ≥ N∗+kfail​

本节取"2 节点竞价 + 1 节点按需"混合：

C混合​=4×2.70+2×9.00=10.80+18.00=28.80 元/h=20,736 元/月

它比全竞价贵 2.1 倍，但比全按需便宜 36%，且单节点失效时有两层保护。这就是"成本与可用性的显式兑换点" —— 第 4 节把它写进上线清单。

四、敏感性账本：一次只动一个量#

为什么必须一张一张地动：多个量同时变时，成本变化无法归因。下表每一行只改一个参数：

变动 N∗ 卡 吞吐裕 TTFT TPOT 月成本 Δ月
基准 λ=200 bf16 h=.45 3 6 1.02× 49.2 ms 7.14 ms 5,832 元 +0
λ=100 2 4 1.02× 42.5 ms 6.82 ms 3,888 元 −1,944
λ=150 2 4 1.02× 53.8 ms 7.32 ms 3,888 元 −1,944
λ=300 4 8 1.02× 53.8 ms 7.32 ms 7,776 元 +1,944
λ=500 6 12 1.02× 59.8 ms 7.50 ms 11,664 元 +5,832
Lp99​=800 2 4 1.01× 54.6 ms 6.86 ms 3,888 元 −1,944
Lp99​=2400 4 8 1.03× 50.9 ms 7.30 ms 7,776 元 +1,944
Lp99​=3200 5 10 1.03× 54.4 ms 7.40 ms 9,720 元 +3,888
h=0（关缓存） 4 8 1.03× 51.6 ms 6.83 ms 7,776 元 +1,944
FP8 权重 3 6 1.02× 36.9 ms 5.37 ms 5,832 元 0
TP=4 2 8 1.02× 35.0 ms 5.12 ms 3,888 元 −1,944
TP=4 + FP8 2 8 1.02× 28.3 ms 4.27 ms 3,888 元 −1,944

四组值得单独读的结论：

  1. h=0 时 N∗ 从 3 变成 4（+1,944 元/月）。这是缓存唯一影响卡数的路径：关掉后 Lp99​(1−h)=1600，prefill 裕度从 1.445 掉到 0.795，撞 C3（prefill 只有 0.795×），被迫加一个副本。这就是"缓存省卡"的准确机制：不是省 decode 带宽，而是不让 prefill 约束变成 binding。
  2. FP8 与 TP=4 都不改卡数（N∗=3 与 2 副本×4 卡都是 6 → 8 卡的变化只体现在单价上）。FP8 的价值全部在 TTPOT​ 从 7.14 → 5.37（省 25%）与单价 0.0817 → 0.0812（近似不变，因为与 TP=4 的组合才省钱）。
  3. TPOT 与 TTFT 两条 SLO 都不 binding：把 TPOT 从 30 收到 15 ms、TTFT 从 300 收到 200 ms，N∗ 与成本都不变。说明当前架构的瓶颈是 C1/C2/C3，不是 C4/C5 —— 这正是"先算约束、再谈 SLO"的顺序。
  4. 每加 1,944 元/月换一个 2 副本台阶：λ 从 200→300、Lp99​ 从 1600→2400 都是 +1,944。这是"卡数=2 副本台阶"的直接后果，容量规划的粒度是 1,944 元而不是几百元。

容量规划的粒度=一个节点=2 副本=3,888 元/月​

五、取舍记录：为什么不是另一个方案#

5.1 被否决的四个方案#

被否决的方案 它更便宜吗 否决理由 再用一个数确认
纯按需实例 ✗ 贵 2.33× 成本不可接受 32,400 vs 5,832 元
N=2（少 2 卡） ✓ 省 1,944 元 C1/C2/C3 三条同时破 吞吐 0.98×、b 撞 bkv​
关缓存 h=0 ✓ 省缓存运维 撞 C3，被迫 N=4 prefill 裕度 0.795
TP=1 ✗ 反而贵 每卡只有 4,085 tok/s 5,832 vs 19,440 元

"N=2 省 1,944 元"这一行值得展开：从纯成本看不亏，但它是零冗余的（b 已经贴着 bkv​），任何流量抖动都会直接变成 p99​ 恶化。所以它被否决不是因为"现在不行"，而是因为它把可用性预算花光了。

5.2 三条"不能同时满足"的取舍#

想同时要 代价 折中方案
N 最小 + 单节点容错 需要 b<bkv​ 的裕度 N=4（8 卡），多 1,944 元
竞价便宜 + 容量确定 需要按需兜底 混合采购，20,736 元/月
缓存省钱 + 高命中率 需要 key 设计与隔离 先量 h，再按 h∗ 决定

三个取舍的共同结构：每一个都在花"余量"，而余量是同一份​

这句话是本节的总结：吞吐余量、显存余量、采购余量、缓存命中率余量 —— 它们最终都折算成"还能不能扛住下一次变化"。账本的价值就是把这些余量显式列出来，而不是等到出事才发现某一项已经为零。

代码#

这段程序产出本节的四本账：单请求延迟账、单位成本账、舰队与采购账、敏感性账本。

⚠️ 合成数据：流量分布（Lp50​/Lp99​、Pout​）与价格（2.70 / 9.00 元/卡时）是设定值，用于演示账本的算法结构；真实项目必须换成压测与采购报价。

"""第 6 章第 2 节：端到端账本。

纯标准库。四块：
  ① 单请求的延迟账：TTFT 与 TPOT 的组成，逐项拆到"读权重 / 读 KV / 排队"
  ② 单 token 的成本账：每 token 卡时 → 单卡吞吐上限 → 最小卡数
  ③ 舰队与采购账：副本数、冗余、竞价/按需、网络与存储
  ④ 敏感性账本：lambda、序列长度、精度、SLO 各变一档，成本怎么动
"""
import math

GB = 1024 ** 3
P = 7.0e9
LAYERS, D_MODEL, KV_HEADS, HEAD_DIM = 32, 4096, 8, 128
PEAK, MFU = 989e12, 0.60
BW, BW_EFF = 3.35e12, 0.70
T0 = 3.0
VGPU = 24 * GB
ACT = 1.5 * GB
KV_B = 2 * LAYERS * KV_HEADS * HEAD_DIM * 2
LOG50 = math.log(50.0)

CFG = dict(lam=200.0, lp50=800.0, lp99=1600.0, pout=100.0,
           ttft=300.0, tpot=30.0, qmax=128, h=0.45,
           price=2.70, price_od=9.00, usd=0.74, node_gpus=4,
           net_per_node_day=20.0)


class Svc:
    def __init__(self, tp=2, wq=2, dtype_bytes=2.0, h=0.45, cross_node=False, **kw):
        self.__dict__.update(CFG)
        for k, v in kw.items():
            setattr(self, k, v)
        self.tp, self.wq, self.dtype_bytes, self.h = tp, wq, dtype_bytes, h
        self.cross_node = cross_node
        self.w_gpu = P * self.dtype_bytes / self.wq
        self.kv_budget = VGPU - self.w_gpu - ACT
        self.seq_max = self.lp99 + self.pout
        self.b_kv = self.kv_budget / (self.seq_max * KV_B)
        self.r_pref = self.tp * PEAK * MFU / (2 * P)
        self.Lkv = self.lp50 + self.pout / 2
        self.c_w = self.w_gpu / (BW * BW_EFF) * 1e3
        self.c_kv = self.Lkv * KV_B / (self.tp * BW * BW_EFF) * 1e3
        self.bw_tp = 25e9 if cross_node else 450e9
        self.thr_req = self.lam * self.pout
        self.b_cap = min(self.b_kv, self.qmax)
        self.thr_max = self.b_cap / (self.t_step(self.b_cap) / 1e3)

    def tp_comm_ms(self, b):
        act = b * D_MODEL * self.dtype_bytes / 2
        attn = self.tp * self.seq_max * HEAD_DIM * self.dtype_bytes / 2
        return 4.0 * (act + attn) / self.bw_tp * 1e3

    def t_step(self, b):
        return (max(self.c_w + b * self.c_kv, 2 * P * b / (self.tp * PEAK * MFU) * 1e3)
                + self.tp_comm_ms(b) + T0)

    def t_prefill(self, L):
        return (2 * P * L / (self.tp * PEAK * MFU) * 1e3
                + self.tp_comm_ms(self.b_cap) + T0)

    @property
    def T_pref(self):
        return self.t_prefill(self.lp99 * (1 - self.h))

    def solve(self, N):
        lam_r = self.lam / N
        cap = self.b_cap
        s = self.T_pref / 1e3 + self.pout * self.t_step(cap) / 1e3
        for _ in range(800):
            b = min(lam_r * s, cap)
            s_new = self.T_pref / 1e3 + self.pout * self.t_step(b) / 1e3
            if abs(s_new - s) < 1e-13:
                s = s_new
                break
            s = 0.5 * (s + s_new)
        b = min(lam_r * s, cap)
        t = self.t_step(b)
        thr = b / (t / 1e3)
        rho = lam_r / (self.qmax / s)
        tq = LOG50 / (self.qmax / s - lam_r) * 1e3 if rho < 1 else float("inf")
        ttft = tq + self.T_pref
        margin = thr * N / self.thr_req
        pref_m = self.r_pref * N / (self.lam * self.lp99 * (1 - self.h))
        why = []
        if margin < 1.0:
            why.append(f"吞吐{margin:.2f}×")
        if lam_r * s > cap + 1e-9:
            why.append("显存")
        if t > self.tpot:
            why.append(f"TPOT{t:.1f}")
        if ttft > self.ttft:
            why.append(f"TTFT{ttft:.0f}")
        if rho >= 1:
            why.append(f"ρ{rho:.2f}")
        if pref_m < 1:
            why.append(f"prefill{pref_m:.2f}×")
        return dict(N=N, gpus=N * self.wq, nodes=math.ceil(N * self.wq / self.node_gpus),
                    b=b, cap=cap, b_kv=self.b_kv, b_dem=lam_r * s, t=t, thr_gpu=thr,
                    thr_tot=thr * N, margin=margin, rho=rho, tq=tq, ttft=ttft,
                    kv_used=b * self.seq_max * KV_B / self.tp, pref_m=pref_m,
                    T_pref=self.T_pref, comm=self.tp_comm_ms(b), s=s,
                    ok=not why, why=" ".join(why))

    def best(self):
        for N in range(1, 80):
            r = self.solve(N)
            if r["ok"]:
                return r
        return None

    def money(self, r, price=None, days=30):
        price = self.price if price is None else price
        rev_h = r["N"] * price
        return dict(rev_h=rev_h, month=rev_h * 24 * days,
                    usd_M=rev_h * self.usd / (r["thr_tot"] * 3600) * 1e6)

五处关键设计决策：

  1. 排队项用 M/M/1 的 Wp99​=ln(C/(1−p))/(μ−λ)，其中 μ=qmax​/s：s 本身由 b 决定，所以排队与批大小是联立的。用"固定服务率"估排队会系统性低估高负载段的尾。
  2. cw​ 用每卡权重而不是总权重：TP 切分后每卡只读自己的分片，所以 cw​=W/(TP⋅BWη)。写成总权重会让 TP=4 看起来毫无收益。
  3. 单位成本同时给"稳态"与"上限"两个数：稳态 0.1104 元/1M、上限 0.0762 元/1M。只报一个数会让评审无法判断"还有多少空间"。
  4. 采购账把 GPU 与非 GPU 项分开：GPU 费随竞价波动 3 倍，网络/存储固定。混在一起会让采购决策看起来在影响它影响不了的量。
  5. 敏感性表"一次只动一个量"：多参数同时变时无法归因。表的每一行都是一个可独立复现的实验。

读输出的三处要点：

  • (1) 段的"排队占 TTFT 的 72.8%"：这是一个会随 N 改变的比例（§1.1 的表给了 3 个点）。它说明"TTFT 优化"的第一优先级是并发槽/副本，而不是 prefill kernel。
  • (2) 段的"N=2 时 b 撞上 77.01"：注意它的 TTFT（77.6 ms）居然比 N=3 更好看（49.2 反而更差？不 —— 77.6 > 49.2）。真正要看清的是吞吐 0.9846×：这是唯一否决 N=2 的硬指标，别被延迟误导。
  • (4) 段的"h=0 让 N∗ 从 3 变 4"：缓存影响卡数的路径是 C3（prefill），不是 C1/C2。这条结论直接决定了第 4 节的"什么时候该开缓存"。

小结#

  • 账本的五层结构：延迟账 → 单位成本账 → 舰队账 → 采购账 → 敏感性账。每层都能独立复核，误差可以归位到具体一项。
  • TTFT 的主要项是排队（本节 72.8%），TPOT 的主要项是读权重 + 固定开销（41.8% + 42.0%）。这两项的优化手段完全不重叠 —— 这是"TTFT/TPOT 不可折算"的账本证据。
  • 每 token 卡时是唯一正确的成本变量：τtok​=tstep​/b。稳态 0.1472 ms → 6,792 tok/s；忽略带宽会把卡数低估 8.6 倍。
  • "下界 2.03 卡"与"实际 6 卡"的差由四项构成：离散化、副本→卡（×TP）、显存夹住 b、SLO 余量。逐项摊开才能回答"为什么不是 2 卡"。
  • 稳态吞吐裕度只有 1.02×：这解释了为什么必须按"节点粒度"（=1,944 元/月）做冗余，也解释了第 3 节压测里 1.6× 负载就会破的原因。
  • h=0 让 N∗ 从 3 变 4：缓存影响的是 C3（prefill）约束。这是"开缓存"的准确机制，不是"省带宽"。
  • 被否决的方案必须留账：N=2（三条约束同时破）、纯按需（贵 2.33×）、TP=1（每卡只有 4,085 tok/s）、关缓存（撞 C3）。没有账的否决会在下一次评审被重新提出。
  • 一句话：端到端账本的作用不是"证明方案对"，而是"把每一分钱和每一毫秒都挂到一个可测量的量上" —— 这样线上出现偏差时，才知道该改哪一行。
