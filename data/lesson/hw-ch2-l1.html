SM 与 CUDA Core#

上一章我们从外面看 GPU，这一章拆开来看。GPU 不是一个"巨大的核"，而是由几十上百个 SM（Streaming Multiprocessor，流式多处理器） 拼出来的；每个 SM 里又有一堆 CUDA Core。理解了这一层，你就能自己算出"一张卡的 FP32 算力为什么是那个数"。

一、概念讲解#

1. SM：GPU 的基本计算单元#

把 GPU 想象成"一栋楼里有很多个办公室"，每个 SM 就是一个办公室。H100 有 132 个 SM，A100 有 108 个。每个 SM 内部自成一个"迷你处理器"：有自己的寄存器文件、共享内存、计算单元和调度器，彼此相对独立。GPU 的性能，本质上就是"所有 SM 的算力之和"。

2. SM 内部有什么#

一个 Hopper 架构的 SM 大致包含：

  • 128 个 CUDA Core（FP32/INT32 单元）：做标量乘加的主力；
  • 4 个 Tensor Core：专做矩阵乘的加速单元（下一课主角）；
  • 共享内存 / L1 缓存：片上小容量高速存储（Hopper 上合计约 228 KB）；
  • 寄存器文件：每个 SM 约 256 KB，分给活跃线程；
  • 特殊函数单元（SFU）：算倒数、指数、三角函数等；
  • Warp 调度器：把指令派发给线程。

3. CUDA Core：一个"乘加"单元#

一个 CUDA Core 每个时钟周期能做一次 FMA（Fused Multiply-Add，融合乘加），即 a×b+c。FMA 一次做乘法和加法，计为 2 次浮点运算（FLOPs）。于是一个 SM 的 FP32 算力可以这样写：

SM 算力=CUDA Core 数×2 FLOP×时钟频率

整张卡的 FP32 算力再乘以 SM 数：

FP32 TFLOPS=SM 数×每 SM 的 Core 数×2×时钟(GHz)/1000

代入 H100：132×128×2×1.98≈67 TFLOPS，和官方标称的 FP32 算力吻合。这就是"算力数字从哪来"的答案。

4. 线程的组织：thread → warp → block → grid#

GPU 执行的最小单位是线程，但调度是按 warp（32 个线程一组） 进行的：

  • thread：一个线程，执行同一份代码；
  • warp：32 个线程锁步执行同一条指令（SIMT 的最小调度单位）；
  • block：一组线程（多个 warp），被调度到某个 SM 上；
  • grid：整个 kernel 的所有 block。

理解 warp 很关键：GPU 的并行是"同一指令、不同数据"。如果 32 个线程走了不同分支，会发生线程发散（divergence），性能打折——这也是"为什么 GPU 不喜欢分支多、逻辑乱的代码"。

二、可运行代码示例#

下面亲手"拼"出一张卡的 FP32 算力，并模拟 warp 锁步执行。

# ---- 例 1：用"核数 x 2 x 频率"自己算 FP32 算力 ----
def fp32_tflops(num_sm, cores_per_sm, clock_ghz):
    # 每个 CUDA Core 每时钟 1 次 FMA = 2 FLOPs
    return num_sm * cores_per_sm * 2 * clock_ghz / 1000.0

# (SM 数, 每 SM 的 FP32 Core 数, 加速时钟 GHz) —— 公开规格近似值
cards = {
    "A100 SXM": (108, 64, 1.41),      # 108 SM * 64 FP32 core
    "H100 SXM": (132, 128, 1.98),     # 132 SM * 128 FP32 core
    "RTX 4090":  (128, 128, 2.52),    # 128 SM * 128 FP32 core
}
for name, (sm, core, clk) in cards.items():
    print(f"{name}: 自算 FP32 = {fp32_tflops(sm, core, clk):.0f} TFLOPS")

# ---- 例 2：验证 H100 官方 FP32 约 67 TFLOPS ----
h100 = fp32_tflops(132, 128, 1.98)
print(f"\nH100 自算 FP32 = {h100:.1f} TFLOPS（官方约 67 TFLOPS）")

# ---- 例 3：模拟一个 warp 的 32 个线程"锁步"执行 ----
class Warp:
    def __init__(self):
        self.threads = [0.0] * 32   # 32 个线程的数据（寄存器值）

    def simt_add(self, val):
        # 同一条"加 val"指令，同时作用于 32 个线程
        self.threads = [t + val for t in self.threads]

w = Warp()
w.simt_add(1.0)
w.simt_add(2.0)
print(f"\nwarp 锁步执行后，线程 0..3 的值 = {w.threads[:4]}（应为 [3.0, 3.0, 3.0, 3.0]）")

# ---- 例 4：线程发散——为什么 GPU 怕分支 ----
def divergent_time(divergence_ratio):
    # 简化模型：发散的分支要串行执行两条路径，时间翻倍
    serial_part = divergence_ratio * 2.0
    parallel_part = 1.0 - divergence_ratio
    return serial_part + parallel_part

for ratio in [0.0, 0.2, 0.5, 1.0]:
    print(f"分支发散比例 {ratio:.0%} -> 相对执行时间 {divergent_time(ratio):.1f}x")

要点：例 1、例 2 证明"算力数字不是玄学，是核数、频率的简单乘积"；例 3、例 4 让你体会 SIMT 的两面性——数据并行时高效，遇到分支就发散。这正是"GPU 爱矩阵乘、怕复杂控制流"的微观原因。

三、练习#

  1. 计算：用 fp32_tflops 反推——如果一块卡有 144 个 SM、每 SM 128 个 FP32 Core、频率 1.5 GHz，它的 FP32 算力是多少 TFLOPS？
  2. 验证：A100 官方 FP32 约 19.5 TFLOPS。用表格里的参数（108 SM、64 Core、1.41 GHz）算一遍，看是否吻合，并解释 64 和 128 的差异来源（架构代际）。
  3. 解释：为什么 FMA 一次算作 2 个 FLOPs，而不是 1 个？
  4. 思考：warp 大小为 32 意味着什么？如果一个 kernel 里每个线程都要做完全不同的分支判断，性能会怎样？结合例 4 说明。
