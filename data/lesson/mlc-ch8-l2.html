编译缓存与多设备：端侧与云侧的差异#

上一课算的都是"模型跑起来之后"的账。服务扩容时最刺眼的数字却在第一次请求上：8 个新进程同时冷启，各自从头编译同一张图。缓存的难点不在"存"而在键——键少了会把云侧产物发给手机（正确性事故），键多了又会让端侧因机型碎片化永远命不中。本课讲清键的构成、命中率的三条杠杆，以及端侧与云侧的两种约束。

一、概念讲解#

1. 缓存省的是编译延迟，不是执行延迟#

编译缓存（compilation cache）保存"某个键 → 一份可加载产物"的映射，命中就跳过捕获与代码生成直接加载。第 1 课埋过一个细节：TVM 运行时会缓存首次取到的函数句柄，那是最小粒度的进程内缓存；这里讲跨进程、跨重启甚至跨机器的磁盘/远端缓存。它只减少冷启动（cold start）时间，与 kernel 快不快无关——两者必须分开度量，否则会把"命中"当成"编译效果好"。

2. 三层缓存与它们的键#

层 典型形态 作用范围
进程内 guard 与形状判定、句柄缓存 单个进程生命周期
磁盘 Inductor 的 FXGraphCache、TritonCache、AOTAutogradCache、PGO/AutotuningCache，统一写在 TORCHINDUCTOR_CACHE_DIR；JAX 的 jax_compilation_cache_dir 同机、跨进程、跨重启
远端 Redis 式远程缓存；Mega-Cache 用 save_cache_artifacts() / load_cache_artifacts() 跨机搬运产物 跨机器、跨实例

键里必须放什么，JAX 文档给了清单：非优化 HLO、jaxlib 版本、相关 XLA 选项、设备配置（设备数与拓扑、GPU 名称）、压缩算法、自定义 hook。PyTorch 的表述同样直接：缓存会校验产物来自相同的 PyTorch 与 Triton 版本，CUDA 设备还要求相同 GPU。两条合起来是硬结论：缓存绑定"设备 + 编译栈"——换机型不是换参数，是换键。

3. 命中率的三条杠杆#

  1. 共享介质。多机多进程时只有 rank 0 写持久缓存、其余进程都读，因此缓存必须落在共享文件系统或远端存储上。代码第 1 节 C 与 A 就是这个对比：同样 8 个请求，缓存各挂本地总编译 20.0 s，共享盘 2.5 s。
  2. 容量 ≥ 工作集。代码第 2 节用 3 轮遍历 6 个键模拟多设备轮转：容量 2/4 条时 LRU 循环淘汰，18 次请求全未命中；容量到 6 条才有 66.7% 命中。真实访问有热点时部分容量够用，但"每种 SoC 一份"是并列工作集，不是热点。
  3. 键的粒度。形状特化会把每个 batch 变成新键；符号形状加 PGO 式运行时决策，就是用少量运行期判断换掉整次重编。还有阈值：JAX 默认要编译时间超过 jax_persistent_cache_min_compile_time_secs（默认 1.0 秒）且条目够大才落盘。

4. 端侧与云侧：一套编译器，两种约束#

维度 云侧 端侧
编译时机 JIT 为主 + 预热；AOT 用于压低冷启动 必须 AOT：端上没有编译器与功耗预算
运行时代价 可接受较大运行时与依赖 越小越好（TVM 运行时约 200K–600K 字节）
缓存介质 共享盘/对象存储/Redis，重启仍在 包内静态资源 + 首启落盘，升级即失效
键的维度 机型池化、代内同构 → 命中率高 SoC × ABI × 形状组合多 → 键爆炸
自动调优 预算充足，结果也要进缓存 离线 tune 后固化，端上不再搜索
更新与回滚 服务端灰度、可回滚 随 App 发版，受商店审核与升级率限制
主要风险 首 token 延迟抖动、扩容风暴 首启白屏、包体膨胀

5. 常见坑#

  • 把"清缓存"当万能药：重编不是 bug，是键变了；不看键就清缓存，等于把延迟换成事故。
  • 漏维度：代码第 3 节里漏掉目标设备后两个键哈希相同——省 2.5 秒编译，代价是加载即崩或静默算错；命中后必须校验产物元信息。
  • 缓存是受信任的输入：文档明确警告，能写缓存目录的人等于能在你的进程里执行代码；不要放进人人可写的目录。
  • 跨机并发写：多节点同写共享缓存会撞车，实践上挂到具备单写者语义的共享文件系统。
  • 升级后不失效：编译栈版本进键就是为了让升级自动重编；绕过校验会把两代产物混在一起。

二、可运行代码示例#

下面这段纯 Python（无第三方依赖）模拟缓存全过程：六维键构造、LRU 磁盘缓存、四种部署形态的编译账、容量对命中率的影响，以及"漏键维度"的正确性后果；耗时为假设参数。

# ---- 第 2 课示例：纯 Python 模拟"编译缓存 + 多设备" ----------------
# 无第三方依赖。COMPILE_S / HIT_LAT_MS 都是显式假设的模型参数，不是任何真实平台的实测值。
import json, hashlib

COMPILE_S   = 2.5     # 假设：一次未命中触发的编译耗时（秒）
HIT_LAT_MS  = 0.4     # 假设：命中读盘 + 反序列化耗时（毫秒）
COLD_LAT_MS = COMPILE_S * 1000 + HIT_LAT_MS

# 缓存键的六个维度：少任何一个都可能造成"错误复用"，多任何一个都可能让键爆炸
def make_key(spec):
    return hashlib.sha1(json.dumps(spec, sort_keys=True).encode()).hexdigest()[:8]

def spec(graph, shape_mode, dtype, target, stack, flags):
    return {'graph': graph, 'shape_mode': shape_mode, 'dtype': dtype,
            'target': target, 'stack': stack, 'flags': flags}

class Cache:
    """磁盘缓存：容量按条目数限制，LRU 淘汰（真实系统还会按体积/时间限制）。"""
    def __init__(self, cap=None):
        self.cap, self.d, self.tick = cap, {}, 0
        self.hit = self.miss = self.evict = 0
    def get(self, k):
        self.tick += 1
        if k in self.d:
            self.hit += 1; self.d[k] = self.tick; return True
        self.miss += 1; self.d[k] = self.tick
        if self.cap and len(self.d) > self.cap:
            del self.d[min(self.d, key=self.d.get)]; self.evict += 1
        return False

def run(requests, cap=None, drop_field=None):
    """requests: [(spec, 节点数)]；drop_field 用来模拟"键里漏了某个维度"。"""
    c = Cache(cap); total_compile, lat, keys = 0.0, [], {}
    for sp, _ in requests:
        s = dict(sp)
        if drop_field: s.pop(drop_field, None)          # ← 故意的缺陷：键退化了
        k = make_key(s); keys.setdefault(k, len(keys))
        hit = c.get(k)
        if not hit: total_compile += COMPILE_S
        lat.append(HIT_LAT_MS if hit else COLD_LAT_MS)
    n = len(requests)
    return {'req': n, 'keys': len(keys), 'hit': c.hit, 'miss': c.miss, 'evict': c.evict,
            'compile_s': total_compile, 'hit_rate': c.hit / n,
            'first_ms': lat[0], 'p95_ms': sorted(lat)[int(n * 0.95) - 1]}

def merge(rs):
    a = {'req': 0, 'keys': 0, 'hit': 0, 'miss': 0, 'evict': 0, 'compile_s': 0.0}
    for r in rs:
        for k in a: a[k] += r[k]
    a['hit_rate'] = a['hit'] / a['req']; a['first_ms'] = a['p95_ms'] = COLD_LAT_MS
    return a

def specs(target, stack='abi64', flags='-O2', shape_mode='symbolic', n=1):
    return [(spec('mlp-2layer', shape_mode, 'f16', target, stack, flags), 9)] * n

def show(name, r):
    print(f'  {name:<28}{r["req"]:>4}{r["keys"]:>7}{r["hit"]:>6}{r["miss"]:>7}{r["evict"]:>6}'
          f'{r["hit_rate"]*100:>8.1f}%{r["compile_s"]:>9.1f}s{r["first_ms"]:>9.1f}ms{r["p95_ms"]:>9.1f}ms')

if __name__ == '__main__':
    print('=== 1. 四种部署形态的缓存账（假设：编译 2.5 s、命中 0.4 ms）===')
    print(f'  {"场景":<28}{"请求":>4}{"唯一键":>7}{"命中":>6}{"未命中":>7}{"淘汰":>6}{"命中率":>9}{"总编译":>10}{"首请求":>9}{"p95":>9}')
    show('A 云侧 8 进程(共享盘)', run(specs('cloud-gpu-x', n=8)))
    show('B 云侧滚动升级(双编译栈)', run(specs('cloud-gpu-x', stack='stack-A', n=4)
                                      + specs('cloud-gpu-x', stack='stack-B', n=4)))
    show('C 多机 8 进程(缓存各挂本地)', merge([run(specs('cloud-gpu-x', n=1)) for _ in range(8)]))
    edge = []
    for t in ('edge-soc-a', 'edge-soc-b', 'edge-soc-c'):
        for abi in ('abi32', 'abi64'):
            edge += specs(t, stack=abi, n=2)
    show('D 端侧碎片化(3 SoC×2 ABI)', run(edge))
    print('  读法：请求数一样时，唯一键的数量决定编译次数；C 与 A 的差别只在"缓存是否共享"')

    print('\n=== 2. 磁盘缓存容量对命中率的影响（3 轮遍历 6 个键 = 18 次请求，LRU）===')
    ws_specs = [sp for t in ('edge-soc-a', 'edge-soc-b', 'edge-soc-c')
                   for abi in ('abi32', 'abi64') for sp in [spec('mlp-2layer', 'symbolic', 'f16', t, abi, '-O2')]]
    work = [(sp, 9) for _ in range(3) for sp in ws_specs]   # 每轮把 6 个键各请求一次
    for cap in (2, 4, 6, 8):
        r = run(work, cap=cap)
        print(f'  容量 {cap:>3} 条  命中率 {r["hit_rate"]*100:>5.1f}%  未命中 {r["miss"]:>2} 次'
              f'  淘汰 {r["evict"]:>2} 条  总编译 {r["compile_s"]:>5.1f} s')
    print(f'  工作集 {len(ws_specs)} 个键：容量 < 工作集时 LRU 循环淘汰，命中率直接归零')

    print('\n=== 3. 键里少一个维度：不是性能问题，是正确性问题 ===')
    a = spec('mlp-2layer', 'symbolic', 'f16', 'cloud-gpu-x', 'stack-A', '-O2')
    b = spec('mlp-2layer', 'symbolic', 'f16', 'edge-soc-a',  'stack-A', '-O2')
    print(f'  完整键（目标不同）: {make_key(a)} vs {make_key(b)}  → 不同，安全')
    a2 = {k: v for k, v in a.items() if k != 'target'}; b2 = {k: v for k, v in b.items() if k != 'target'}
    print(f'  漏掉 target 维度  : {make_key(a2)} vs {make_key(b2)}  → 相同，云侧 artifact 会发给端侧')
    r = run(specs('cloud-gpu-x', n=4) + specs('edge-soc-a', n=4), drop_field='target')
    print(f'  该缺陷下的账：唯一键 {r["keys"]} 个（正确应为 2）→ 省下 {COMPILE_S:.1f} s 编译，')
    print('  代价是加载即崩或静默算错；所以命中后必须校验 artifact 的元信息（版本、目标、dtype）')

实际运行结果（Python 3.14，无第三方依赖）：

=== 1. 四种部署形态的缓存账（假设：编译 2.5 s、命中 0.4 ms）===
  场景                            请求    唯一键    命中    未命中    淘汰      命中率       总编译      首请求      p95
  A 云侧 8 进程(共享盘)                 8      1     7      1     0    87.5%      2.5s   2500.4ms      0.4ms
  B 云侧滚动升级(双编译栈)                 8      2     6      2     0    75.0%      5.0s   2500.4ms   2500.4ms
  C 多机 8 进程(缓存各挂本地)              8      8     0      8     0     0.0%     20.0s   2500.4ms   2500.4ms
  D 端侧碎片化(3 SoC×2 ABI)          12      6     6      6     0    50.0%     15.0s   2500.4ms   2500.4ms
  读法：请求数一样时，唯一键的数量决定编译次数；C 与 A 的差别只在"缓存是否共享"

=== 2. 磁盘缓存容量对命中率的影响（3 轮遍历 6 个键 = 18 次请求，LRU）===
  容量   2 条  命中率   0.0%  未命中 18 次  淘汰 16 条  总编译  45.0 s
  容量   4 条  命中率   0.0%  未命中 18 次  淘汰 14 条  总编译  45.0 s
  容量   6 条  命中率  66.7%  未命中  6 次  淘汰  0 条  总编译  15.0 s
  容量   8 条  命中率  66.7%  未命中  6 次  淘汰  0 条  总编译  15.0 s
  工作集 6 个键：容量 < 工作集时 LRU 循环淘汰，命中率直接归零

=== 3. 键里少一个维度：不是性能问题，是正确性问题 ===
  完整键（目标不同）: 3c4508f8 vs 9840497d  → 不同，安全
  漏掉 target 维度  : 5a5bf848 vs 5a5bf848  → 相同，云侧 artifact 会发给端侧
  该缺陷下的账：唯一键 1 个（正确应为 2）→ 省下 2.5 s 编译，
  代价是加载即崩或静默算错；所以命中后必须校验 artifact 的元信息（版本、目标、dtype）

三个可核对结论：共享与否比"缓存多大"更早决定成败（8 个进程本地盘 20.0 s、共享盘 2.5 s）；容量低于工作集时 LRU 退化成 0 命中（2/4 条容量下 18 次全未命中）；键少一个维度换的是省时间、赌的是正确性（两个不同目标哈希相同）。

三、练习#

  1. 实现：给 Cache 加"按字节容量"淘汰（每条目假设 4 MiB、上限 20 MiB），重跑第 2 节，解释两种口径为何给出不同最优配置。
  2. 解释：第 1 节 B 行里两个编译栈版本各占 2 个键。若滚动升级中故意让新版本复用旧缓存，哪些信号能最快发现问题？提示：从产物元信息与端到端数值校验两边找。
  3. 对比/验证：把 drop_field 依次换成 'stack'、'flags'、'dtype'，记录唯一键数量与"省下的编译时间"，并讨论哪种漏维度最危险。
  4. 思考：App 升级让旧缓存全部失效。要让用户升级后首启不卡，除了"不失效"还有什么办法？提示：权衡包内预编译产物数量与机型覆盖率。
