环境与工具链：驱动/Toolkit/容器版本对齐、ncu 与 nsys#

代码在本机编译通过、在配好卡的机器上却报 cudaErrorNoKernelImageForDevice；同一份镜像在 A 集群能跑、在 B 集群启动即失败。这类问题有确定的因果链（驱动 ↔ Toolkit ↔ 编译目标 ↔ 运行期），知道四个量各由谁决定就能快速定位。这一课讲清这条链，并把 ncu / nsys 放回它们该在的位置。

一、概念讲解#

1. CUDA 软件栈的五个角色#

按"谁决定谁"排（上层依赖下层，但版本各自独立）：

角色 由谁决定 看什么命令 关键特征
GPU 器件 你买/租的硬件 nvidia-smi -L 有固定的 compute capability
驱动（driver） 宿主机/云镜像的管理员 nvidia-smi 提供对最高 CUDA 版本的支持，向上兼容
Toolkit（编译工具链） 你的开发环境 nvcc --version 决定 libcudart、编译出的 PTX/SASS
运行时（runtime） 你的进程实际加载的库 torch.version.cuda 决定进程要走哪条兼容路径
容器镜像 你写的 Dockerfile docker run ... nvcc --version 镜像不含驱动，靠 --gpus 把宿主驱动注入

一句话分界：驱动在宿主机（或由容器运行时注入），Toolkit 与库在镜像/环境里——所以"换镜像里的 Toolkit"和"升级宿主驱动"是两件必须分别搞定的事。

2. 三个版本号必须对齐，以及它们各自对齐什么#

nvidia-smi 顶部那行 CUDA Version: 不是"本机装了哪个 CUDA"，而是这个驱动能支持的最高 CUDA 运行时版本。它与 nvcc --version 报的 Toolkit 版本经常不同，而不同本身完全正常。

对齐规则（来源：NVIDIA CUDA Compatibility 文档的 Minor Version Compatibility 表）：

关系 结果
Toolkit 版本 > 驱动支持的最高 CUDA 必然失败：初始化阶段报 cudaErrorInsufficientDriver（CUDA 3），设备 Query 直接 Result = FAIL
Toolkit 与驱动同一主版本（如都是 12.x） 走小版本兼容（CUDA 11 起默认）：功能集受限；用 PTX 路径时可能报 cudaErrorCallRequiresNewerDriver；必须显式传 -arch=sm_xx
Toolkit 版本 < 驱动支持的最高 CUDA 通常没问题：驱动的向后兼容覆盖旧 Toolkit

表格里"驱动支持的最高 CUDA 主版本"对应官方表 1 的最低驱动：CUDA 11.x 需 ≥ 450、12.x 需 ≥ 525、13.x 需 ≥ 580（Linux；完整表以官方 Release Notes 为准）。小版本兼容的条件是"同主版本 + 达到最低驱动"，不是"随便哪个驱动都行"。

3. 怎么读输出：三个命令各看什么#

nvidia-smi                       # 驱动版本 + 驱动支持的最高 CUDA + 进程/显存占用
nvcc --version                   # 编译期 Toolkit 版本（决定 libcudart、PTX ISA）
nvidia-smi -L                    # 器件列表；配 --query-gpu 可拿到 compute_cap
nvidia-smi --query-gpu=name,compute_cap,driver_version,memory.total --format=csv

无 GPU 环境下这些命令不存在是正常的：本课全部判定逻辑都能用注入文本演练（见 §二），这正是"无 GPU 也能学完"的路径。

4. compute capability → sm_XX → SASS/PTX：二进制兼容链#

驱动的兼容性只解决"库能不能加载"；kernel 能不能跑由另一条链决定：

  1. 器件有固定的 compute capability（形如 9.0，即 sm_90）。
  2. nvcc 把它编译成对应的 SASS（实际机器码）。若编译目标里没有当前器件的 sm_XX，运行时报 cudaErrorNoKernelImageForDevice。
  3. 若同时嵌入了 PTX（中间码），驱动可在首次运行时 JIT 成该器件的 SASS——这是"一个二进制跑多种架构"的备选路径，代价是首次执行变慢。
  4. 只嵌 SASS 的二进制不会在更新架构上自动可用；只嵌 PTX 则完全依赖 JIT。

编译目标要显式给全，例如 -gencode arch=compute_90,code=sm_90 -gencode arch=compute_80,code=sm_80。最常见的错误不是算错，而是默认架构：nvcc 缺省只编一个通用目标，未必覆盖你的卡。

5. ncu 与 nsys：分工不同#

两个工具常被混着叫"性能分析"，但回答的是不同问题：

工具 回答的问题 粒度 典型用法
nsys（Nsight Systems） 时间线：整个训练/推理步里，时间花在哪些 kernel、拷贝、同步、CPU 侧调用上 系统级，一次看全 nsys profile -o out ./app，先找"哪个 kernel 最贵"
ncu（Nsight Compute） 单个 kernel 内部：带宽/算力用了多少、是否 memory-bound、访存是否合并 kernel 级，很贵 ncu --set full -k <kernel_name> ./app，判断"它为什么慢"

正确顺序是先 nsys 定位、再 ncu 深挖：直接对全部 kernel 跑 ncu --set full 会让程序慢几个数量级，也产不出可读结论。

6. 常见坑#

  • 把 nvidia-smi 的 CUDA Version: 当成"已安装的 CUDA"：它是驱动上限，用它去对 nvcc 会得出错误结论。
  • 把驱动版本当成 CUDA 版本：驱动版本形如 580.65.06，与 13.0 是两个坐标系。
  • 升级了 Toolkit 却没动驱动：容器里 nvcc 13.x + 宿主驱动只支持到 12.x，就是"必然失败"。
  • 只编一个架构：在 A100 上开发、跑到 H100 上报 cudaErrorNoKernelImageForDevice。
  • 忽略"小版本兼容"的功能缺口：能跑不等于特性齐全，cudaErrorCallRequiresNewerDriver 常出现在用到新 API 时。

二、可运行代码示例#

下面这段纯标准库代码是本课的"环境对齐自检"：优先读真实的 nvidia-smi / nvcc 输出，无 GPU 时自动回落到注入文本，让三个判定分支（通过 / 警告 / 失败）都能被真实演练。样本值取自 NVIDIA 文档，用于演示逻辑，不是对任何具体机器的断言。

# ---- 环境对齐自检：解析 nvidia-smi / nvcc 输出，判定「驱动 ↔ Toolkit ↔ 目标架构」----
import argparse, re, shutil, subprocess

# 小版本兼容的最低驱动（来源：NVIDIA CUDA Compatibility 文档 Table 1，Linux）
MIN_DRIVER = {11: 450, 12: 525, 13: 580}

def run(cmd):
    """优先跑真实命令；本机没有该工具时返回 None（纯 CPU 学习环境下照样能跑）"""
    if shutil.which(cmd[0]) is None:
        return None
    try:
        return subprocess.run(cmd, capture_output=True, text=True, timeout=10).stdout
    except Exception:
        return None

def parse(smi_text, nvcc_text):
    v = {'driver': None, 'driver_major': None, 'driver_max_cuda': None,
         'toolkit': None, 'devices': []}
    if (m := re.search(r'Driver Version:\s*([0-9.]+)', smi_text)):
        v['driver'], v['driver_major'] = m.group(1), int(m.group(1).split('.')[0])
    if (m := re.search(r'CUDA Version:\s*([0-9.]+)', smi_text)):
        v['driver_max_cuda'] = tuple(int(x) for x in m.group(1).split('.'))
    if (m := re.search(r'release\s+([0-9.]+)', nvcc_text)):
        v['toolkit'] = tuple(int(x) for x in m.group(1).split('.'))
    for line in smi_text.splitlines():
        if (m := re.match(r'^([^,]+),\s*([0-9]+\.[0-9]+),\s*(\d+)\s*MiB', line.strip())):
            v['devices'].append((m.group(1).strip(), m.group(2), int(m.group(3))))
    return v

def fmt(t): return '.'.join(map(str, t)) if t else '-'

def verdicts(v):
    """返回 (级别, 说明) 列表；级别 ∈ 通过 / 警告 / 失败 / 检查"""
    if not v['driver']:
        return [('跳过', '本机没有 nvidia-smi（纯 CPU 环境），用注入的示例文本演练判定逻辑')]
    out = []
    tk, mx = v['toolkit'], v['driver_max_cuda']
    if tk and mx:
        if tk > mx:
            out.append(('失败', f'Toolkit {fmt(tk)} 高于驱动上限 {fmt(mx)}：'
                                f'初始化即报 cudaErrorInsufficientDriver'))
        elif tk[0] == mx[0]:
            need = MIN_DRIVER.get(tk[0])
            if need and v['driver_major'] < need:
                out.append(('失败', f'CUDA {tk[0]}.x 要求驱动 >= {need}，当前 {v["driver_major"]}'))
            else:
                out.append(('警告', f'Toolkit 与驱动同为 {tk[0]}.x：走小版本兼容，功能集受限；'
                                    f'PTX 路径可能报 cudaErrorCallRequiresNewerDriver，'
                                    f'且必须显式 -arch=sm_xx'))
        else:
            out.append(('通过', f'Toolkit {fmt(tk)} 低于驱动上限 {fmt(mx)}：向后兼容'))
    for name, cap, mem in v['devices']:
        gencode = f'arch=compute_{cap.replace(".", "")},code=sm_{cap.replace(".", "")}'
        out.append(('检查', f'{name}（capability {cap}，显存 {mem} MiB ≈ {mem/1024:.1f} GiB）'
                            f'→ 编译目标必须含 -gencode {gencode}'))
    return out

SCENARIOS = [
    ('场景 A：驱动上限高于 Toolkit（正常）', """NVIDIA-SMI 580.65.06    Driver Version: 580.65.06    CUDA Version: 13.0
Tesla T4, 7.5, 15360 MiB""", """Cuda compilation tools, release 12.8, V12.8.61"""),
    ('场景 B：与驱动同主版本（只能小版本兼容）', """NVIDIA-SMI 570.86.10    Driver Version: 570.86.10    CUDA Version: 12.8
NVIDIA H100 PCIe, 9.0, 81559 MiB""", """Cuda compilation tools, release 12.8, V12.8.61"""),
    ('场景 C：Toolkit 高于驱动上限（必然失败）', """NVIDIA-SMI 550.54.14    Driver Version: 550.54.14    CUDA Version: 12.4
Tesla T4, 7.5, 15360 MiB""", """Cuda compilation tools, release 13.0, V13.0.48"""),
]

def main():
    ap = argparse.ArgumentParser(description='CUDA 环境对齐自检')
    ap.add_argument('--smi-file', help='nvidia-smi 输出文本；缺省则现场执行')
    ap.add_argument('--nvcc-file', help='nvcc --version 输出文本；缺省则现场执行')
    args = ap.parse_args()
    smi = open(args.smi_file).read() if args.smi_file else (run(['nvidia-smi']) or '')
    nvcc = open(args.nvcc_file).read() if args.nvcc_file else (run(['nvcc', '--version']) or '')
    print('== 真实环境（本机）==')
    if not smi:
        print('  未检测到 nvidia-smi：本机是无 GPU 学习环境，不影响下面的判定逻辑')
    for lvl, msg in verdicts(parse(smi, nvcc)):
        print(f'  [{lvl}] {msg}')
    print()
    print('== 三种典型输入下的判定结果 ==')
    for tag, s, n in SCENARIOS:
        print(f'--- {tag} ---')
        for lvl, msg in verdicts(parse(s, n)):
            print(f'  [{lvl}] {msg}')
        print()

main()

最后一步是验证工具链真的能出正确结果。这不依赖 CUDA 硬件知识，只依赖"对照"的习惯：把同一个算子在 CPU 与 GPU 上各算一遍，比较数值（第三课会把容差写成判据）。

# ---- 可选（需自备 GPU 或云上按需租用）：确认工具链端到端可用 ----
# 关键点：第一次运行可能触发 PTX 即时编译（JIT），所以要先预热、再计时/比对。
import torch

assert torch.cuda.is_available(), '没有可用 GPU：本节跳过，前两段纯 Python 代码已完成本课全部验证'
print('构建期 CUDA 版本 torch.version.cuda =', torch.version.cuda)   # 运行时版本
print('器件能力 =', torch.cuda.get_device_capability(), '名称 =', torch.cuda.get_device_name())

a = torch.randn(512, 512)
ref = a @ a.T                                     # CPU 参考实现
for _ in range(3):
    out = (a.cuda() @ a.cuda().T).cpu()           # 预热：让 JIT/缓存就绪
torch.testing.assert_close(out, ref, rtol=1e-3, atol=1e-3)
print('CPU 与 GPU 结果一致（fp32 容差 rtol=atol=1e-3）')

三、练习#

  1. 实现：给 verdicts() 增加判定——Toolkit 与驱动主版本相同时，额外打印文档要求的最小驱动，并说明它属于"小版本兼容"而非"任意驱动可用"。
  2. 解释：为什么升级 Toolkit 后 nvidia-smi 的 CUDA Version: 不会变？它由谁决定？
  3. 对比/验证：分别只编 SASS（code=sm_XX）与只编 PTX（code=compute_XX）各一份，比较同一器件上的首次运行耗时；并说明 cudaErrorNoKernelImageForDevice 与 cudaErrorInsufficientDriver 分属链路的哪一环。
  4. 思考：容器镜像装了 Toolkit 13.x，宿主驱动只支持到 12.x。除"升级驱动"外还有哪些出路？代价如何？
