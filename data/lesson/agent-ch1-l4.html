设计目标：可靠性、可观测、可组合、可回滚、成本可控#

这一节要解决什么#

上一节把 Agent 的结构补全了。但"结构补全"不等于"能用"：同样的四件事，可以做得让系统稳定交付，也可以做得只能跑 demo。差别在于你有没有先把"好"的定义写下来。

这一节是本章第二个难点，也是整门课的度量基准。要做三件事：

  1. 给定五个设计目标各自的可操作度量 —— 不是"要可靠"，而是"用什么数判断它可靠"。
  2. 给出它们之间的冲突结构 —— 不是罗列"可能冲突"，而是指出哪几对是结构性冲突（不可调和），哪几对可以通过设计解耦。
  3. 用一个完整的取舍案例，演示"取舍如何写进设计文档" —— 这是本节真正的产出物形态。

学完这一节你应该能回答：

  • "可靠性"到底该用一个数还是两个数衡量？为什么只看平均成功率会误导决策？
  • 五个目标里，哪一个是唯一没有替代品的（不满足就不能上线）？
  • 当"可靠性"和"成本可控"冲突时，正确的处理方式是什么？（答案不是"选一个"，而是"把冲突显式参数化"。）
  • 你能写出一个别人可以照着实现的取舍决策记录吗？

一、为什么先定目标：没有目标的优化就是随机游走#

先给一个工程上的理由，而不是"因为规范要求"。上一节已经说明：Agent 的每一处结构都是一个设计决策（校验、授权、幂等、裁剪、终止、验证……）。这些决策互相耦合，而且大多数是双向的：

更严的参数校验  → 更少"发明参数"的失败，但更多合法的表达被拒（灵活性↓）
更早的终止      → 成本更低，但更多任务被判定为未完成（成功率↓）
更全的轨迹记录  → 归因更容易，但存储/隐私面更大，且可能拖慢热路径
更多重试        → 成功率↑，成本↑、延迟↑，且可能放大非幂等副作用

没有目标，你只能凭直觉在每一处"就严一点吧"或"就松一点吧"，结果是这些局部决策互相打架：一边给工具加了严格校验，另一边在重试逻辑里把校验放在重试之后，于是"非法参数"被重试了三次。目标的作用就是给这些局部决策一个统一的偏好方向。

关键认识：目标不是"全都要"，而是一个带优先级的约束系统。写在设计文档里的应该是"在 X 情况下优先 A 牺牲 B"，而不是"我们力求做到 A、B、C、D、E 都很好"——后者等于没有任何指导。

二、五个目标各自的度量#

度量的基本要求：可观测、可归因、可比较。下面是每个目标的"主指标 + 辅助指标 + 反指标"三件套。反指标（anti-metric）是你为了优化主指标而恶化的那个数 —— 不写出来，你的优化一定是局部最优。

2.1 可靠性（Reliability）#

定义：同一任务在相同设置下多次运行，能达成可接受结果的概率及其稳定性。

项 度量 为什么是它
主指标 成功率 p^​succ​=#运行#可接受完成​，N≥30 次同一任务 单次结果没有统计意义
稳定性 成功率的置信区间半宽，或"通过率 @ k 次取最好"（pass@k） 见下方"方差比均值更重要"
成本维度 成功所需的期望步数 / 期望 token 可靠但每次要 50 步的系统成本失控
反指标 延迟、成本、以及"拒答率"（把任务判为"做不到"的比例） 提高成功率最偷懒的办法是拒答

为什么可靠性必须是"两个数"（均值 + 方差）：上一节提过，p 本身是随机变量。设两个系统平均成功率都是 80%：

系统 A：{[0.75, 0.85]}       —— 几乎每次都差不多
系统 B：{[0.3, 0.98]}        —— 一半时间很好，一半时间很糟

对运维而言差别是决定性的：

  • A 可以给 SLA：重试没有意义（每次都差不多），但可以承诺"20 次里 16 次成功"，容量规划可做。
  • B 不能给 SLA：用户会遇到完全不可预测的体验，而你无法通过"多跑几次"改进它 —— 因为差的那些运行不是同一类失败（可能模型在某类输入上系统性崩）。

工程含义：B 类系统的第一优先级不是提高均值，是找出方差来源（哪一类输入/哪一类状态导致崩）。用一个切分维度（任务类型、输入长度、工具调用数）分组统计成功率，方差往往立刻定位到一个子集上。这与第 7 章"失效归因四象限"是同一件事的离线版。

一个可用的可靠性判据（写进设计文档的形式）：

可靠⟺p^​succ​≥pmin​∧CI95%​半宽≤0.05∧拒答率≤rmax​

注意最后一项：没有它，"少做少错"会成为最优策略 —— Agent 遇到难任务直接说"我做不到"，成功率反而很好看。

2.2 可观测（Observability）#

定义：能否在事后（以及必要时的事中）重建"发生了什么、为什么"。

可观测不是"打日志"，它有明确的层级。每一层能回答的问题不同，成本也不同：

层级 记录什么 能回答的问题 成本
L1 事件轨迹 每步：动作、参数、结果、耗时、token、代价 "第几步开始偏的？" 低（结构化日志）
L2 因果链 每步的输入上下文摘要 + 该步引用了哪些上一步的输出 "它为什么这么决定？它看到了什么？" 中（要存上下文快照，需脱敏）
L3 可重放 固定随机性（seed / 解码参数）+ 工具桩（录制-回放） "把提示词改一个字，结果会变吗？" 高（要版本化一切外部依赖）
L4 可干预 断点、单步、人工注入反馈 "如果我在这里纠正它，会怎样？" 很高（要暂停/恢复能力）

设计决策：按失败代价选择层级。 一个只读的检索 Agent，L1+L2 足够（出错就重跑）；一个会发钱/删数据的 Agent，L3 是底线（必须能复现事故现场）。

反指标：记录的完整度与隐私/合规、存储成本、热路径开销直接冲突。这里有一个真实的两难：L2 要存上下文，而上下文里常常含用户数据。 三种常见处置，各有代价：

处置 代价
全存 合规风险；需要加密 + 严格访问控制 + 保留期策略
存哈希 + 长度 无法回放语义；L2 退化成 L1
存脱敏摘要 摘要可能抹掉正是问题所在的细节（这是最隐蔽的失败）

取舍的写法：不要写"我们做了脱敏"，要写"L2 上下文以脱敏摘要形式保留 30 天；已知代价：PII 相关失败无法从轨迹定位，需依赖线上复现。"——把代价说出来的才是决策，不说的只是愿望。

2.3 可组合（Composability）#

定义：系统的部件（工具、子 Agent、验证器）能否独立地被替换、测试、复用，而不牵动整体。

可组合的度量比前两个难，但可以操作化：

项 度量 说明
替换成本 换掉一个工具/子 Agent 需要改动的文件数 / 契约数 越小越好
独立可测 部件能在无模型条件下被断言（给定输入 → 期望输出） 这是可组合的硬测试
接口泄漏 跨边界传递的隐含约定数量（约定必须写下来才算数） 泄漏越多越难换
组合覆盖 端到端测试里被覆盖的部件组合路径比例 组合爆炸下永远不足，看关键路径

硬测试："这个工具能不能在没有 LLM 的情况下被单测？"如果答案是"不能，因为它依赖模型给的参数格式"，那它不可组合 —— 它的契约寄生在提示词里，而提示词不是接口。

为什么会冲突：可组合要求窄接口 + 显式契约，而"把全部历史塞进提示词让模型自己看着办"这类技巧，威力恰恰来自利用隐含约定（模型能推断出没说出口的东西）。这是本章最尖锐的取舍之一：

强接口：参数是结构化的、语义显式的   → 可组合、可测试，但模型"聪明的推断"用不上了
弱接口：提示词里暗示、参数自由文本   → 效果好，但换不了、测不了、行为随提示词漂移

处置方向（不是"选一个"）：把跨边界的部分做强接口（工具、子 Agent 的输出 schema），把边界之内的部分留给提示词技巧。也就是说：漂移必须止步于接口。

2.4 可回滚（Rollback）#

定义：高副作用动作在出错后，能否被撤销或补偿，使系统回到一个已知良好状态。

项 度量
可回滚覆盖 #全部写操作#带补偿动作的写操作​
补偿成功率 补偿本身失败的概率（补偿也会失败 —— 这是最常见的疏忽）
回滚粒度 最近一次可回滚检查点到失败点的动作数（越小损失越小）
回滚时延 从决定回滚到状态一致的时间

三种可逆性，必须区分清楚（这决定了你能承诺什么）：

类型 例子 回滚手段 代价
可逆 写自己的数据库 事务 / 反向写 低，但要求设计时就成对写
可补偿 转账、发邮件、下单 反向操作（退款、发更正邮件、取消） 中；补偿有可见副作用（客户已经看到那封邮件了）
不可逆 删除外部数据、对外发布、消耗性操作 只能预防（审批 + 沙箱），不能回滚 高；必须前置拦截

关键设计结论："可回滚"的设计动作发生在正向动作之前，而不是之后。 事后想加回滚，通常只能加"补偿"，而补偿在语义上永远不如真正的回滚（用户已经看到了）。所以有一条硬规则：任何不可逆动作，必须在写代码时就确定它的前置拦截方案（授权/沙箱/双人确认/软删除），不准许"先上线，回头再加回滚"。

反指标：可回滚要写两套逻辑（正向 + 反向），并且反向逻辑也必须被测试。实践中反向逻辑的测试覆盖率往往远低于正向 —— 于是"我们有回滚"变成一句无法兑现的承诺。度量里的"补偿成功率"就是防这个的。

2.5 成本可控（Cost Controllable）#

定义：每个任务的资源消耗有一个可预测的上界，且系统在接近上界时会有明确行为（降级/终止），而不是无限增长。

项 度量
主指标 每任务的 token 上界 / 工具调用上界 / 时延上界（三个独立维度，不能只算钱）
分布 每任务成本的 p50 / p95 / p99 —— 长尾才是事故来源
上界兑现率 实际超预算的运行占比（应该接近 0；不为 0 说明上界是假的）
成本归因 按步骤类型拆分的成本占比（哪一步最贵）
反指标 成功率、延迟（省钱的方式之一是少做，见"拒答率"）

为什么"上界"比"平均成本"重要：Agent 的成本分布是重尾的。一次跑偏的循环（模型反复重试同一个失败工具）可以把单任务成本拉到 p50 的 20 倍。只看平均值做容量规划，会被 1% 的尾部打爆。所以：

预算规则：cost(t)=wtoken​Tt​+wcall​Ct​+wtime​Lt​≤B,∀t

上界必须在每一步检查（而不是跑完再算）。这直接连到第 2 章的终止条件：预算/步数/置信度三把闸。注意这里的一个微妙点：预算检查必须是"执行前检查"，而不是"执行后统计" —— 否则你已经付了那笔钱。

成本与其他目标的冲突（本节的核心之一）：

想改善 常见手段 成本后果
可靠性 多次采样取最好（best-of-n）、加验证步、加重试 ×n（线性放大）
可观测 L2/L3 记录、上下文快照、重放桩 存储与热路径开销
可组合 独立可测的部件、额外的接口层 少量固定开销，但常需多一次模型调用做格式转换
可回滚 补偿逻辑、软删除、两阶段写 正向路径多一到两步

三、冲突结构：哪几对是结构性的#

把上面五节的内容整理成冲突矩阵。注意区分结构性冲突（原理上不可同时最优，只能取舍）与可解耦冲突（可以通过设计同时改善）：

可靠性 可观测 可组合 可回滚 成本可控
可靠性 — 弱 弱 正相关 结构性 ▼
可观测 弱 — 正相关 正相关 结构性 ▼
可组合 弱 正相关 — 正相关 弱 ▼
可回滚 正相关 正相关 正相关 — 结构性 ▼
成本可控 结构性 ▼ 结构性 ▼ 弱 ▼ 结构性 ▼ —

三个结论：

  1. 可靠性、可观测、可组合、可回滚之间基本是正相关的 —— 它们共同的基础是"显式化"：把状态、契约、判据、副作用都写出来。这解释了为什么"做对设计"往往同时改善四个目标：它们不是四个方向，而是同一个方向的四个侧面。
  2. 成本可控与其余四个全部结构性冲突 —— 因为其余四个的实现手段普遍是"多做一点"（多验证、多记录、多一层接口、多一步补偿）。所以成本不是第五个平等目标，它是那个"预算约束"：它决定其余四个能做到什么程度。
  3. 可回滚与可靠性正相关（不是冲突）—— 这点常被误判。直觉上"可靠的系统不需要回滚"，实际上回滚是可靠性的组成部分：上一节证明过，可回滚是唯一能从根上打断漂移指数放大的手段。

最重要的工程结论：真正的取舍只有一个方向 —— 在固定成本预算下，如何分配"多做一点"的额度。这就是为什么本节最后要给一个完整的取舍案例，而不是五段"要重视 X"。

四、把冲突参数化：预算下的选择问题#

既然冲突的实质是"额外工作量的分配"，就可以把它写成一个显式的分配问题。设总预算为 B，四种"多做一点"的花费分别为 cr​,co​,cp​,cb​（可靠/观测/组合/回滚），对应带来的可靠性增益为 Δr​,Δo​,Δp​,Δb​：

xr​,xo​,xp​,xb​max​p^​succ​(x)s.t.i∑​ci​xi​≤B

这个式子本身解不出数（收益函数未知），但它给了两条可操作的启发式：

启发式一：先补齐"使其他手段生效"的那一项。 由上一节：错误可检测率 d 会把重试的收益以 (1−d)k 放大。所以当 d 接近 0 时，投在"可观测/可检测"上的第一块钱的边际收益远高于投在"重试"上。判断顺序：

d ≈ 0（错误静默传播）       → 先投可观测/校验（否则重试无效）
d 高但无回滚（错误可检测但不可恢复）→ 投可回滚
d 高、可回滚、但成本失控     → 投预算闸与剪枝（第 2、5 章）
以上都有，成功率仍低         → 才是投向模型/提示词

启发式二：把"拒答"当作成本的一部分。 任何"少做少错"的优化都会推高拒答率。所以成本约束应该写成：

可接受⟺costp99​≤B∧拒答率≤rmax​

只写前半句，系统会学会"遇事就说做不到"。

五、取舍案例：一个对外发邮件的调研 Agent#

现在把上面全部内容落到一个完整案例上。选择"对外发邮件"是因为它同时含不可逆动作、语义质量要求和成本压力 —— 五个目标全部在场。

5.1 任务与约束#

任务：给定一个话题，检索资料 → 写一份调研摘要 → 通过邮件发给指定收件人。
约束：
  · 邮件一旦发出不可撤回（对外不可逆）
  · 摘要质量无法完全机械判定（需要语义判断）
  · 收件人可能是客户（错误代价高）
  · 需要控制成本：预期每天运行 200 次

5.2 目标优先级与理由（写进设计文档）#

优先级 目标 为什么排这里
1 可回滚（=不可逆动作的前置拦截） 邮件不可撤回 → 这是唯一没有替代品的目标，必须最高
2 可靠性 错误代价高（对客户）；宁可慢，不可错
3 可观测 出问题必须能归因到"检索错/写作错/判据错"
4 可组合 未来要换检索源与写作模型，接口要稳
5 成本可控 排在最后，但必须给出上界（不是不控，是不为省钱牺牲前四项）

注意第 1 和第 5 的排序理由不同：可回滚排第一是因为"不可逆动作没有替代品"（不是"它更重要"）；成本排最后是因为它有硬上界兜底（p99 ≤ B，超了就拒答而不是降质）。

5.3 具体取舍（每条都带代价）#

取舍 1：发送动作加"草稿 → 人工确认 → 发送"两阶段（牺牲延迟与人力）

  • 得到：不可逆动作被前置拦截覆盖（可回滚目标的唯一可行实现）。
  • 代价：端到端时延从秒级变成"直到人工确认"；每天 200 次里若 30% 需确认，是 60 次人工介入。
  • 为什么接受：邮件不可撤回。可补偿（发更正邮件）在客户场景下语义上不是回滚。

取舍 2：加一道独立的模型评审（牺牲成本，换可靠性）

  • 得到：拦住"内容看似完整但偏离话题"的漂移（上一节的机制一：子目标置换）。
  • 代价：每次多一次模型调用（成本 ×1.3 量级）+ 增加 p95 延迟。
  • 边界条件（重要）：评审器必须用不同的 rubric 和独立上下文。若让同一个模型在同一上下文里"检查自己"，会退化成自评 s^，收益接近 0。

取舍 3：L2 因果链只保留摘要（牺牲部分可观测性，换合规与成本）

  • 得到：能回答"第几步偏了、它看到了什么"（摘要级）。
  • 代价：已知盲区 —— PII 相关的失败无法从轨迹复现，需要线上复现或让用户提供输入。
  • 为什么接受：完整上下文留存带来合规成本；折中方案必须把盲区写清楚，而不是假装可观测已经完备。

取舍 4：不设"best-of-3 重写"（牺牲一点成功率，换成本上界）

  • 得到：成本 p99 可控。
  • 代价：写作环节的成功率少几个百分点（多采样取最好通常能提升若干点）。
  • 为什么接受：写作质量由取舍 2 的评审器兜底；重复采样与评审器功能重叠，边际收益被两者取其一覆盖。

取舍 5：把"检索"与"写作"做成强接口（牺牲一点提示词技巧，换可组合）

  • 得到：可以独立替换检索源、独立测试写作（给定固定资料 → 期望摘要结构）。
  • 代价：检索结果必须结构化（字段固定），丢掉了"把原始文档整段塞给模型让它自行取舍"的灵活性。
  • 边界：接口之内（写作阶段内部）仍可用长上下文技巧 —— 漂移止步于接口。

5.4 这套设计的"承重墙"在哪#

一个可复用的自检：如果只允许你保留一条设计决策，留哪条？

  • 本案例里是取舍 1（两阶段发送）。
  • 理由：其余四条被去掉，系统会变差；取舍 1 被去掉，系统会变危险（不可逆动作失去拦截）。
  • 对应的通用判据："去掉它会不会让系统从'不好用'变成'不能用/危险'" —— 会的那条就是承重墙，必须最先实现、最先测试、最不能妥协。

代码：把五个目标的度量算出来（可运行的度量骨架）#

这个代码不实现 Agent，它实现度量。设计决策是：把度量做成可以跑的函数，而不是文档里的一句话 —— 不可执行的度量在项目里必然会腐烂。

import math
from dataclasses import dataclass, field
from typing import Optional

# ---------- 2.1 可靠性：两个数（均值 + 稳定性），外加拒答率 ----------
def reliability(runs: list[bool], refused: list[bool],
                p_min: float = 0.8, r_max: float = 0.1) -> dict:
    """
    runs    : 每次运行是否'可接受完成'
    refused : 每次运行是否'判为做不到'（反指标！不许靠拒答刷成功率）
    设计决策：置信区间半宽与拒答率同时入判据 —— 缺任一项，指标都可被游戏化。
    ⚠️ 注意 half 是'均值的估计精度'，不是'运行间的离散度'：
       两个成功率相同的系统会有几乎相同的 half。要看稳定性，必须看下面的 stability()。
    """
    n = len(runs)
    if n == 0:
        return {"ok": False, "why": "没有样本"}
    p_hat = sum(runs) / n
    half = 1.96 * math.sqrt(max(p_hat * (1 - p_hat), 1e-9) / n)   # 正态近似
    ref = sum(refused) / n
    return {"成功率": round(p_hat, 3), "CI95半宽": round(half, 3),
            "拒答率": round(ref, 3),
            "可靠": p_hat >= p_min and half <= 0.05 and ref <= r_max}

def stability(costs: list[float]) -> dict:
    """
    ★ 可靠性的第二个数：运行之间的离散度。看两个无量纲量 ——
      · CV（变异系数 = sd/mean）：'同样的任务，每次差多少'
      · p95/p50：长尾倍数。CV 小但 p95/p50 大 ⇒ 偶发灾难（比持续不稳更危险）
    设计决策：不看方差本身，因为方差的量纲随任务规模变化，无法跨任务比较。
    """
    n = len(costs)
    if n < 2:
        return {"可估": False}
    mean = sum(costs) / n
    sd = math.sqrt(sum((c - mean) ** 2 for c in costs) / (n - 1))
    s = sorted(costs)
    p50, p95 = s[n // 2], s[min(n - 1, int(0.95 * n))]
    return {"CV": round(sd / max(mean, 1e-9), 3),
            "p95/p50": round(p95 / max(p50, 1e-9), 1),
            "可给SLA": sd / max(mean, 1e-9) <= 0.3}

def split_variance(groups: dict[str, list[bool]]) -> dict:
    """
    分维度统计成功率 → 定位方差来源（B 类系统的第一优先级）。
    设计决策：方差诊断按维度切分，因为'哪一类输入崩'才是可行动的信息。
    """
    return {k: round(sum(v) / len(v), 3) for k, v in groups.items() if v}

# ---------- 2.5 成本可控：上界 + 长尾 ----------
@dataclass
class CostBudget:
    """三维度独立预算。设计决策：token/调用/时延不能合成一个'钱'，因为瓶颈可能只有一个。"""
    max_tokens: int = 60_000
    max_calls: int = 20
    max_seconds: float = 90.0
    def check(self, tok: int, calls: int, secs: float) -> Optional[str]:
        """★ 必须在'执行下一步之前'调用 —— 事后再算，钱已经付了。"""
        if tok >= self.max_tokens: return f"token 预算耗尽 ({tok}/{self.max_tokens})"
        if calls >= self.max_calls: return f"调用预算耗尽 ({calls}/{self.max_calls})"
        if secs >= self.max_seconds: return f"时延预算耗尽 ({secs:.0f}s/{self.max_seconds:.0f}s)"
        return None

def cost_tail(costs: list[float]) -> dict:
    """看 p99 而不是 mean：Agent 成本是重尾分布，均值会骗你。"""
    s = sorted(costs)
    def q(f): return s[min(len(s) - 1, int(f * len(s)))]
    return {"p50": round(q(.5), 2), "p95": round(q(.95), 2),
            "p99": round(q(.99), 2), "mean": round(sum(s) / len(s), 2),
            "尾部倍数": round(q(.99) / max(q(.5), 1e-9), 1)}

# ---------- 2.4 可回滚：覆盖 + 补偿自身的可靠性 ----------
@dataclass
class RollbackLedger:
    writes: int = 0
    compensable: int = 0
    compensations_ok: int = 0
    compensations_tried: int = 0
    def coverage(self) -> float:
        return self.compensable / self.writes if self.writes else 1.0
    def compensation_success(self) -> float:
        """设计决策：补偿也会失败。不度量它，'我们有回滚'就是空话。"""
        return (self.compensations_ok / self.compensations_tried
                if self.compensations_tried else float("nan"))

# ---------- 2.3 可组合：用'能否无模型单测'做硬测试 ----------
def is_composable(tool) -> tuple[bool, str]:
    """
    硬测试：工具能否在没有 LLM 的情况下被断言？
    不能 → 它的契约寄生在提示词里 → 不可组合（换不掉、测不了）。
    """
    if not hasattr(tool, "schema") or not hasattr(tool, "call"):
        return False, "没有显式 schema/调用入口"
    if not hasattr(tool, "unit_assertions"):
        return False, "未提供无模型断言（契约隐含在提示词里）"
    return True, "ok"

# ---------- 2.2 可观测：层级选择必须与失败代价挂钩 ----------
def required_observability_level(side_effect: str, spend: bool) -> str:
    """
    设计决策：可观测层级不是'越高越好'（成本/隐私），而是按下行风险选择。
    """
    if side_effect == "irreversible" or spend:
        return "L3 可重放（必须能复现事故现场）"
    if side_effect == "compensable":
        return "L2 因果链（要能定位到补偿点）"
    return "L1 事件轨迹（只读，重跑即可）"

# ---------- 冲突参数化：预算下的分配启发式 ----------
def where_to_spend(detect_rate: float, has_rollback: bool,
                   cost_p99_over_budget: bool) -> str:
    """
    启发式一：先补齐'使其他手段生效'的那一项（顺序比金额重要）。
    """
    if detect_rate < 0.5:
        return "先投可观测/校验：错误静默传播时，重试的收益趋于 0"
    if not has_rollback:
        return "投可回滚：错误可检测但不可恢复时，可回滚是唯一能打断漂移放大的手段"
    if cost_p99_over_budget:
        return "投预算闸与剪枝：p99 已经超界，此时加采样/重试只会更糟"
    return "最后才投模型/提示词：前面的杠杆都用尽后，它才是瓶颈"

if __name__ == "__main__":
    # ==== 可靠性：成功率 + 拒答率（两个游戏化防线）====
    A = [True] * 34 + [False] * 6        # 成功 0.85，稳定
    print("成功率与拒答率:", reliability(A, [False] * 40))

    # ==== 稳定性：这才是'两个系统均值相同、可用性不同'的判别处 ====
    # 两个系统各 40 次运行的'每任务步数'（均值都约 12 步）：
    stable   = [11, 12, 12, 13, 12, 11, 12, 12, 13, 12] * 4          # 波动小
    unstable = [4, 5, 6, 38, 40, 42, 7, 36, 5, 39] * 4               # 双峰：偶发 40 步
    print("稳定系统:", stability(stable))
    print("不稳定系统:", stability(unstable))
    # ★ 两者的均值接近，但 CV 与 p95/p50 差异巨大 →
    #   只有稳定那个能给 SLA。'可靠性不是一个数'在这里才真正可见。

    print("分维度成功率:", split_variance({
        "短任务": [True] * 19 + [False],
        "长任务(>15步)": [True] * 3 + [False] * 7,   # 方差来源在这里
    }))
    print("成本尾部:", cost_tail([1.2] * 90 + [8.0, 11.0, 25.0, 3.0, 2.0, 1.5, 1.8, 2.2, 1.9, 2.0]))
    print("该往哪花钱:", where_to_spend(detect_rate=0.2, has_rollback=False,
                                       cost_p99_over_budget=False))

这段代码的四处设计意图：

  1. reliability 把拒答率作为判据的一部分。任何只统计成功率的度量都会被"少做少错"策略攻破。
  2. reliability 与 stability 刻意分成两个函数。因为"均值的估计精度"（CI 半宽）和"运行间的离散度"（CV、p95/p50）是两件事：两个成功率完全相同的系统会有几乎相同的 CI，却在可用性上天差地别。把它们合成一个"可靠性得分"，这两种信息会互相掩盖。
  3. CostBudget.check 注释里强调"执行前检查"。这是最容易写错、也最贵的一处 —— 事后统计只让你知道自己超了，不让你避免超。
  4. where_to_spend 返回的是顺序而不是金额。因为在收益函数未知时，"先修哪个"比"投多少"更可判断 —— 这正是第四节启发式一的落地。

练习#

  1. 度量设计：为"代码修复 Agent"（读 issue → 改代码 → 跑测试 → 提 PR）写出五个目标各自的主指标 + 反指标。要求每个反指标都必须是这个任务里真实可能被游戏化的那一个，并说明它会被怎么游戏化。
  2. 方差定位：某 Agent 成功率 78%，但 p50 运行只需 6 步、p95 需要 34 步。请给出三个可能的方差来源（提示：与"步数"强相关的因素有哪些），并为每一个设计一个能区分它的切分维度。
  3. 冲突判断：下面四对目标冲突里，哪些是结构性冲突（不可同时最优），哪些其实正相关（可以通过设计同时改善）？逐条给理由。 （a）可观测 vs 成本可控；（b）可回滚 vs 成本可控；（c）可靠性 vs 可组合；（d）可回滚 vs 可靠性。
  4. 写取舍记录：为练习 1 的代码修复 Agent 写一份取舍决策记录，格式照第五节的"取舍 N"（得到 / 代价 / 为什么接受 / 边界条件）。至少写 4 条，并且必须包含一条关于不可逆动作的（提示：提 PR 可回滚吗？force push 呢？删分支呢？）。
  5. 承重墙：从你第 4 题的 4 条取舍里找出"承重墙"（去掉它会让系统从"不好用"变成"危险"），说明理由。然后回答：如果项目时间只够实现两条，你留哪两条，为什么？
  6. 反例：构造一个例子，说明"把可观测做到 L3 可重放"反而降低了系统可靠性（提示：想想热路径开销、记录失败时的行为、以及"为了可重放而把工具也固定住"带来的灵活性损失）。

小结#

  • 五个目标的度量三件套：主指标 + 稳定性/分布 + 反指标。没有反指标的度量一定会被"少做少错"游戏化（典型：成功率很漂亮，拒答率 40%）。
  • 可靠性是两个数：成功率 + 稳定性。均值相同、方差不同的两个系统，一个能给 SLA，一个不能；后者的第一优先级是定位方差来源（分维度切分），不是提高均值。
  • 可观测有四层（L1 轨迹 / L2 因果链 / L3 可重放 / L4 可干预），按失败代价选择层级，不是越高越好；L2 的成本与隐私冲突必须把盲区写清楚。
  • 可组合的硬测试：这个部件能不能在没有模型的情况下被断言？不能 → 它的契约寄生在提示词里。
  • 可回滚分三级：可逆 / 可补偿 / 不可逆。设计动作发生在正向动作之前；不可逆动作只准预防，不准事后补回滚。补偿也会失败 —— 必须度量"补偿成功率"。
  • 成本是约束而不是平等目标：看 p99 而非均值（重尾分布），必须执行前检查，且拒答率要计入成本判据。
  • 冲突结构：可靠 / 可观测 / 可组合 / 可回滚之间基本正相关（共同基础是"显式化"）；只有"成本可控"与其余四个是结构性冲突。所以真正的取舍方向只有一个：在固定预算下分配"多做一点"的额度。
  • 顺序启发式：d 低先投可检测性 → 再投可回滚 → 再投预算闸 → 最后才投模型/提示词。
  • 承重墙判据：去掉它会不会让系统从"不好用"变成"危险"？会的那条最先做、最不能妥协。

本章到此结束。五章之后你会拿到具体的设计手法，但判断标准从这一节开始就不再变：任何一个 Agent 设计，都要能回答"它的五个目标各自怎么度量、冲突处取舍了什么、承重墙是哪一条"。第 2 章从控制循环开始 —— 循环的基本形态、ReAct 与 plan-execute 的取舍、终止条件的三把闸，以及为第 7 章评测铺路的可观测性设计。
