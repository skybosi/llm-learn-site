KV cache 分页与显存账：从"按最大长度预留"到每 token 字节#

这一节要解决什么#

前两节把调度算清了，但每一节都留了一个"待定参数"：并发上限。上一节的 TTFT 不可达、上上一节的 bKV​，都取决于"显存里能放多少个请求的 KV"。

这一节把这件事算到底。三个层次：

  1. 每 token 的 KV 字节数：KV1​=2Lnkv​dhead​σ。它是所有 KV 账的地基，也是唯一一个可以精确算出来的量（不需要实测标定）。
  2. 分配策略的碎片账：按最大长度预留 → 内部碎片率可以到 80% 以上；分页（PagedAttention）把它降到个位数，但引入了块内碎片与块表开销。三者的账要一起算。
  3. 给定显存下的最大并发：这不是"池大小 / 平均长度"这么简单 —— 因为请求长度是重尾分布，而"能装下 K 个平均长度的请求"不等于"能装下 K 个真实请求"。

先给本节最重要的一组数（示例：L=32、nkv​=8、dhead​=128、fp16、模型 6.57B、单卡 80 GB）：

KV1​=128 KiB/token⟹⎩⎨⎧​s=4096⇒512 MiB/序列s=32768⇒4 GiB/序列66 GiB 的 KV 池⇒约 540k token 的容量​

KV1​=128 KiB/token⟹⎩⎨⎧​s=4096⇒512 MiB/序列s=32768⇒4 GiB/序列66 GiB 的 KV 池⇒约 540k token 的容量​

而"540k token 容量"对应的并发数完全取决于长度分布：全是 512 token 的请求能装 1055 个；全是 32k 的请求只能装 16 个。同一块显存，并发数差 66 倍。

一、每 token 的 KV 字节数#

1.1 公式与它的三项#

decoder-only Transformer 的 KV cache，每层每 token 存 2nkv​dhead​ 个数（K 与 V 各 nkv​ 个头、每头 dhead​ 维）：

KV1​=K,V2​​⋅L⋅nkv​⋅dhead​⋅σ  字节/token​

项 含义 可优化性
2 K 与 V 不可省（除非放弃注意力）
L 层数 不可省（每层独立 KV）
nkv​ KV 头数（GQA 的关键） 可由架构降低：MHA→GQA 可降 4~8 倍
dhead​ 每头维度 架构决定
σ 每元素字节（fp16=2） 可由 fp8/int8 降 2~4 倍

示例计算：

2×32×8×128×2=131072 B=128 KiB/token

1.2 三个可比的降 KV 手段#

手段 带宽/显存收益 代价 是否需要重训
GQA / MQA（降 nkv​） nkv​ 从 32 降到 8 → 4× 质量（需评估） 架构级，必须重训
KV 量化 fp16 → fp8/int8（降 σ） 2× / 2× 精度损失、反量化开销 通常免训（后处理）
按 KV 头分片（TP） ×1/N 需要 nkv​ 可被 N 整除 免训（推理配置）

⚠️ 三者的收益是可乘的，但代价性质不同：GQA 要重训、量化要评估精度、分片要通信。所以工程上的顺序是"先分片（免训、免费）→ 再量化（免训、要评估）→ 最后才动架构"。

一个常见的量级错误：把 KV 显存当成一次性的常数。实际上 KV 是随序列长度线性增长、且每 token 都要读写一次的：

KV 显存=KV1​⋅s,KV 带宽=B2KV1​⋅s⋅b​ 每步

示例：s=4096、b=64 → KV 访存 =2×128KiB×4096×64/3TB/s=22.9 ms/步。这已经超过纯权重访存（4.38 ms）5 倍 —— 这就是上一章"长上下文把 b∗ 从 330 压到 248"的机制来源。

二、分配策略的碎片账#

2.1 三种策略#

策略 机制 碎片类型
按最大长度预留（naive） 每个请求进入时分配 max_len × KV1 内部碎片（预留了但没用）
分页（PagedAttention） KV 切成固定大小的块（如 16 token/块），按需分配 块内碎片 + 块表开销
连续增长 + 拷贝 每次扩容时分配更大连续块并拷贝 拷贝开销（O(s2) 总拷贝量）

2.2 内部碎片：可以算到 80% 以上#

按最大长度预留时，一个实际用了 s 个 token 的请求占了 max_len 个 token 的空间，利用率：

ηnaive​=max_lens​

以真实请求长度的分布取期望。实测负载通常是重尾（多数请求很短、少数很长）：

长度分布（2000 个请求） E[s] 按 4096 预留的总量 真实 KV 总量 利用率 浪费
全部 4096 4096 1000.0 GiB 1000.0 GiB 100% 0%
均匀 U(500,4096) 2269 1000.0 GiB 553.9 GiB 55.4% 44.6%
指数（均值 800、截断 4096） 796 1000.0 GiB 194.3 GiB 19.4% 80.6%
重尾（Pareto α=1.2、截断 4096） 557 1000.0 GiB 136.0 GiB 13.6% 86.4%

（表中的比例来自本节代码第 (2) 段的模拟；注意“真实 KV 总量”是 2000 个请求的全部 token，而“按 4096 预留”是它们被实际占掉的容量。）

这就是 PagedAttention 的动机：它不省单 token 的字节，它省的是"预留但没用"的那部分。

2.3 分页的碎片与开销#

分页把 KV 切成大小 Bblk​（token 数，典型 16）的块：

ηpaged​=块内碎片：平均浪费半块(1−Bblk​E[块内剩余]​)​​⋅元数据(1−块表开销比)​​

块内碎片：每个序列最后一块平均浪费 Bblk​/2 个 token 的槽位。所以相对浪费：

浪费比=E[s]Bblk​/2​

Bblk​ E[s]=512 E[s]=2048 E[s]=8192
8 0.8% 0.2% 0.05%
16 1.6% 0.4% 0.1%
32 3.1% 0.8% 0.2%
64 6.3% 1.6% 0.4%

块表开销：每个块需要一个表项（块号），加上引用计数、哈希键等元数据。设每个块表项 e 字节、块装 Bblk​ 个 token 的 KV（Bblk​⋅KV1​ 字节）：

开销比=Bblk​⋅KV1​e​

示例：KV1​=128 KiB、Bblk​=16、e=64 B（哈希 + 引用计数 + 块号）→ 开销比 =64/(16×131072)=0.003% —— 可以忽略。

⚠️ 但这只在"每块装很多 token"时成立。如果 Bblk​ 取 1（一个 token 一块），开销比变成 64/131072=0.05%（仍然小），但块数变成 s 个，块表的查询/分配开销会进入关键路径（每次 decode step 都要遍历块表）。所以：

Bblk​ 的下限由"块表查询开销"决定（CPU 侧），上限由"块内碎片"决定（显存侧）​

Bblk​=16 是这两个约束的折中：块内碎片在 1% 量级，块数是 s/16（s=32768 时 2048 块，块表仍可控）。

2.4 那"连续增长 + 拷贝"为什么不行#

如果每次 KV 需要更多空间就重新分配一块更大的连续内存并拷贝：

总拷贝量=i=1∑⌊s/Δ⌋​iΔ≈2Δs2​ token 的 KV 字节

示例：s=32768、Δ=256（每次扩 256 token）→ 总拷贝 =327682/(2×256)≈2.1×106 token 的 KV =2.1×106×128KiB=256 GiB 的显存搬运。这是一个请求的开销。 所以"连续增长 + 拷贝"在推理里完全不可行 —— 这是分页的第二个动机（它把 O(s2) 的拷贝变成 O(s) 的块分配）。

三、给定显存下的最大并发#

3.1 池大小与容量#

KV 池=HBM−ΨB​/N权重​​−留 5% 10%激活与临时缓冲​​−CUDA context 等框架开销​​

示例（单卡 80 GB、6.57B fp16、N=1）：

项 数值
总显存 80 GiB
权重（fp16） 12.24 GiB
激活与临时缓冲（10%） 8 GiB
框架/CUDA context ~2 GiB
KV 池 ≈ 57.8 GiB
KV 容量（÷128 KiB） ≈ 473k token

3.2 并发数：一个由分布决定、而不是由池大小决定的量#

并发上限=E[s]KV 容量​(粗略)或更严格：max{K:∑i≤K​si​≤KV 容量}

并发上限=E[s]KV 容量​(粗略)或更严格：max{K:∑i≤K​si​≤KV 容量}

"更严格"那个才是对的，因为长度是随机的：装下 10 个"平均长度"请求不等于装下任意 10 个请求。用重尾分布时，尾部那几个长请求会吃掉大部分池子：

负载（2000 个请求，KV 池 59.2 GiB） E[s] KV 总量 按最大长度预留能装 分页能装 分页/预留
全部 4096 4096 1000.0 GiB 118 118 1.0×
均匀 U(500,4096) 2269 553.9 GiB 118 222 1.9×
指数（均值 800、截断 4096） 796 194.3 GiB 118 572 4.8×
重尾（Pareto α=1.2、截断 4096） 557 136.0 GiB 118 872 7.4×

读法有三层：

  1. 分布越重尾，分页相对预留的收益越大（1.0× → 7.4×），因为重尾负载里短请求多，而预留策略把每个短请求都按 4096 计费；
  2. 预留策略的并发数是恒定的 118，与负载无关（59.2 GiB/(4096×128 KiB)=118）—— 它被 max_len 完全决定。这本身就是“按最大长度预留”最致命的性质：你的并发上限由配置里的一个常数决定，而不是由真实负载决定；
  3. KV 总量一列（1000 → 136 GiB）说明真实负载其实很省：重尾负载的期望长度只有 557 token，但 P99 附近的长请求把预留策略彻底拖垮。

所以容量规划必须用真实长度分布做装填模拟，不能只用平均值，也不能只用分位数。

3.3 池大小 vs batch size：本章开头那条式子的落地#

回到第 2 章 index 里那条方程：

∂(KV 配额)∂(吞吐)​=第 4 节命中率提升的收益​​−第 1 节batch 缩小的损失​​=0

本节先给出损失项的量化形式。设 KV 池为 C、平均长度 sˉ，则并发 bKV​=C/(KV1​sˉ)；每步耗时 Tstep​≈max(ΨB​/B, 2Ψb/Cflop​)。吞吐：

Θ(C)=Tstep​(bKV​(C))bKV​(C)​

  • 若 bKV​<b∗（访存瓶颈）：Tstep​ 与 b 无关 → Θ∝C（线性，KV 直接换吞吐）；
  • 若 bKV​>b∗：Tstep​∝bKV​ → Θ 饱和（再加 KV 池不再提吞吐）。

KV 池的边际价值在 bKV​ 越过 b∗ 之后归零​

KV 池的边际价值在 bKV​ 越过 b∗ 之后归零​

这就是"给 KV cache 更多显存 = 吞吐更高"的精确版本：不是永远不等价，而是过了某个点之后不等价。示例：b∗=330、sˉ=2048 → 需要 C=330×2048×128KiB=82.5 GiB —— 超过单卡显存。所以在 b<b∗ 的整个区间里，KV 池的边际价值都是线性的，直到显存装不下为止。

这解释了为什么第 4 节的"KV 配额 vs 缓存命中率"取舍在多数部署里并不尖锐：因为 KV 池还在"线性换吞吐"区间，而缓存命中率同时也是线性受益的 —— 两者不冲突。冲突只在 bKV​ 接近 b∗ 时出现。（第 4 节会给出判据。）

四、取舍表与失效模式#

选择 收益 代价 失效条件
分页（Bblk​ 小） 内部碎片↓、拷贝↓ 块表查询开销↑（CPU 关键路径） Bblk​<8 且 s 很大时块数爆炸
分页（Bblk​ 大） 块表小 块内碎片↑ Bblk​>64 且请求短
KV 量化 fp8 容量 ×2 精度、反量化开销 长上下文对精度敏感时
按 KV 头分片（TP） 容量 ×N nkv​ 整除约束；跨节点时通信贵 N>nkv​
减少预留（按需分配） 碎片↓ 请求可能中途失败（OOM） 无抢占机制时
抢占 允许超卖 重算或换出成本（第 2 节） 长序列 + 高负载

⚠️ 最后两行是一对：按需分配（over-commit）必须配合抢占，否则一个长请求会在用到第 3 万个 token 时因为"没有块了"而失败。这是分页系统里最容易被忽略的正确性要求：分页把"准入决策"从"开始时一次性"变成了"每一步都可能失败"。

分页 + 按需分配 ⟹ 必须有抢占机制（否则 OOM 发生在中途）​

代码：KV 显存账、碎片模拟与并发上限#

脚本做四件事：(1) 算每 token 的 KV 与池容量；(2) 模拟三种分配策略（按最大长度预留 / 分页 / 连续增长拷贝）在同一负载下的碎片与并发；(3) 用真实长度分布比较"按均值估算"与"实际能装下"的差距；(4) 算 KV 池的边际价值曲线（吞吐 vs 池大小）。

"""
KV cache 的显存账与分配策略（只用标准库）。

设计决策：
  1. 每 token 的 KV 用解析式算（不需要标定），分配策略用离散模拟比较。
     前者可以精确到字节，后者只能看趋势 —— 混在一起会让人误以为碎片率也能"算准"。
  2. 三种策略在同一份长度序列上比较，并且**用同一个随机种子**：
     否则"分页比预留好 4 倍"这种结论会混入负载差异（正文 2.1）。
  3. 「按均值估算并发」与「模拟实际能装下」并列输出。容量规划里最常见的错误
     就是拿池大小除一个平均长度 —— 本脚本用数据把这件事暴露出来（正文 3.2）。
  4. 连续增长拷贝的 O(s²) 只算「总搬运字节」，不算时间。因为它的作用是证明
     这条路线不可行（256 GiB 搬运对一个请求），时间模型反而会稀释这个结论。
"""
import random

# ==================== 模型与硬件口径 ====================
L, NKV, DH, DTYPE = 32, 8, 128, 2
KV1 = 2 * L * NKV * DH * DTYPE               # 字节/token
HBM_CAP = 80 * 2 ** 30                       # 单卡 80 GiB
WEIGHT_BYTES = 2 * (L * 12 * 4096 ** 2 + 32000 * 4096)
RESERVE_FRAC = 0.10                          # 激活与临时缓冲比例
FRAMEWORK = 2 * 2 ** 30                      # CUDA context / 框架


def kv_pool(hbm=HBM_CAP, weight=WEIGHT_BYTES, reserve=RESERVE_FRAC,
            framework=FRAMEWORK, tp=1):
    """KV 池字节数（tp 为张量并行度：权重与 KV 都按 1/tp 分）。"""
    w = weight / tp
    avail = hbm - w - framework
    return max(0.0, avail * (1 - reserve)), w


# ==================== 长度分布 ====================
def sample_lengths(kind, n, rng, maxlen=4096):
    if kind == "constant":
        return [maxlen] * n
    if kind == "uniform":
        return [rng.randint(500, maxlen) for _ in range(n)]
    if kind == "exponential":                    # 均值 ~800，截断
        return [min(maxlen, max(1, int(rng.expovariate(1 / 800)))) for _ in range(n)]
    if kind == "heavy":                          # Pareto，重尾
        out = []
        while len(out) < n:
            x = int(200 / (rng.random() ** (1 / 1.2)))
            if x <= maxlen:
                out.append(max(1, x))
        return out
    raise ValueError(kind)


# ==================== 三种分配策略 ====================
def used_naive(lengths, maxlen):
    """按最大长度预留：每个请求占 maxlen 个 token 的 KV。"""
    return len(lengths) * maxlen * KV1


def used_paged(lengths, blk=16, entry_bytes=64):
    """分页：按块向上取整，加块表元数据。"""
    total = 0.0
    for s in lengths:
        nblk = (s + blk - 1) // blk
        total += nblk * blk * KV1 + nblk * entry_bytes
    return total


def max_concurrent(lengths, pool_bytes, policy, blk=16, maxlen=4096):
    """按到达顺序装填，返回池子里最多能同时装下的请求数。"""
    used, k = 0.0, 0
    for s in lengths:
        need = (maxlen * KV1 if policy == "naive" else used_paged([s], blk))
        if used + need > pool_bytes:
            break
        used += need
        k += 1
    return k


def copy_traffic(s, delta=256):
    """连续增长 + 拷贝的总搬运字节：Σ i·delta ≈ s²/(2·delta) 个 token 的 KV。"""
    return (s * s / (2 * delta)) * KV1


if __name__ == "__main__":
    print("=" * 88)
    print(f"KV 口径：L={L}、n_kv={NKV}、d_head={DH}、fp16 → KV1 = {KV1} B = {KV1/1024:.0f} KiB/token")
    pool, w = kv_pool()
    print(f"显存 {HBM_CAP/2**30:.0f} GiB − 权重 {w/2**30:.2f} GiB − 框架 {FRAMEWORK/2**30:.0f} GiB"
          f" − 预留 {RESERVE_FRAC:.0%} → KV 池 {pool/2**30:.1f} GiB = {pool/KV1/1e3:.0f}k token")
    print(f"示例序列：s=4096 → {4096*KV1/2**20:.2f} MiB；s=32768 → {32768*KV1/2**30:.2f} GiB")

    print("\n" + "=" * 88)
    print("(1) KV 显存与带宽：它不只是「占地方」，每步都要读写")
    print(f"{'s':>8}{'KV/序列 MiB':>14}{'b=64 的 KV 访存 ms':>20}{'相对权重访存':>13}")
    w_read_ms = WEIGHT_BYTES / 3.0e12 * 1e3
    for s in (512, 2048, 8192, 32768):
        kv_traffic = 2 * KV1 * s * 64 / 3.0e12 * 1e3
        print(f"{s:>8}{s*KV1/2**20:>14.2f}{kv_traffic:>20.3f}{kv_traffic/w_read_ms:>13.2f}×")
    print("  读法：s=4096、b=64 时 KV 访存已超过权重访存数倍 → 长上下文压低免费 batch 上限")

    print("\n" + "=" * 88)
    print("(2) 三种分配策略的碎片（每个负载 2000 个请求、同一随机种子）")
    print(f"{'负载':>12}{'E[s]':>8}{'KV 总量 GiB':>13}{'预留 GiB':>11}{'分页 GiB':>11}"
          f"{'能装(预留)':>12}{'能装(分页)':>12}")
    for kind in ("constant", "uniform", "exponential", "heavy"):
        rng = random.Random(11)
        L2k = sample_lengths(kind, 2000, rng)
        print(f"{kind:>12}{sum(L2k)/len(L2k):>8.0f}{sum(L2k)*KV1/2**30:>13.1f}"
              f"{len(L2k)*4096*KV1/2**30:>11.1f}{used_paged(L2k)/2**30:>11.1f}"
              f"{max_concurrent(L2k, pool, 'naive'):>12}"
              f"{max_concurrent(L2k, pool, 'paged'):>12}")
    print("  读法：预留策略永远只能装 118 个（被 max_len 卡死）；分页在重尾负载下能装 872 个；")
    print("        注意重尾负载的 KV 总量只有 136 GiB（P99 由少数长请求撑起），池子 59.2 GiB")

    print("\n" + "=" * 88)
    print("(3) 块大小 B_blk 的两个约束")
    print(f"{'B_blk':>7}{'块内碎片(短)':>14}{'块内碎片(长)':>14}{'块数(s=32768)':>15}"
          f"{'块表开销比':>12}")
    for blk in (8, 16, 32, 64, 128):
        waste_short = (blk / 2) / 512
        waste_long = (blk / 2) / 8192
        nblk = (32768 + blk - 1) // blk
        overhead = 64 / (blk * KV1)
        print(f"{blk:>7}{waste_short:>13.2%}{waste_long:>14.2%}{nblk:>15}"
              f"{overhead:>12.4%}")
    print("  读法：B_blk 小 → 碎片小但块数多（CPU 侧块表开销）；B_blk 大 → 反之")
    print("        16 是折中：碎片 1.6%（短请求）、块数可控、块表开销可忽略")

    print("\n" + "=" * 88)
    print("(4) 连续增长 + 拷贝为什么不可行：总搬运量 O(s²)")
    print(f"{'s':>8}{'总搬运 GiB':>14}{'相当于 KV 池的':>16}")
    for s in (4096, 16384, 32768):
        tr = copy_traffic(s) / 2 ** 30
        print(f"{s:>8}{tr:>14.1f}{tr/(pool/2**30):>15.1f}×")
    print("  读法：一个 32k 请求的扩容搬运量就是整个 KV 池的几十倍 → 必须分页")

    print("\n" + "=" * 88)
    print("(5) 池大小 → 吞吐的边际价值（b* = 330）")
    b_star = 330
    print(f"{'池 GiB':>9}{'b_KV (s=2048)':>15}{'是否越过 b*':>12}{'吞吐趋势':>12}")
    for c_gib in (10, 20, 40, 80, 160):
        c = c_gib * 2 ** 30
        b_kv = c / (2048 * KV1)
        over = "是" if b_kv > b_star else "否"
        trend = "饱和" if b_kv > b_star else f"线性(×{min(b_kv,b_star)/min(10*2**30/(2048*KV1),b_star):.1f})"
        print(f"{c_gib:>9}{b_kv:>15.0f}{over:>12}{trend:>12}")
    print("  读法：要越过 b*=330 需要 82.5 GiB 的池（单卡装不下）→")
    print("        在可达到的范围内，KV 池一直是「线性换吞吐」，还轮不到饱和")

六处关键设计决策：

  1. KV1 用解析式、碎片用模拟。前者的正确性可以逐字节核对（2LHnkv​dhead​σ），后者是统计量。两类结论的可信度不同，代码结构上就分开，避免读者把碎片率也当成"能算准"的数。
  2. max_concurrent 按给定顺序装填（first-fit 顺序），不重新排序。这是刻意的：真实的到达顺序就是随机的，重排会人为提高装填率。要展示"平均长度估算有多乐观"，就必须用真实的到达顺序。
  3. used_paged 把块表元数据也算进去（nblk * entry_bytes）。虽然示例里它占比极小（0.003%），但把它显式写出来才能让"Bblk​ 下限由 CPU 侧开销决定"这条结论有依据。
  4. copy_traffic 只算字节不算时间。这条路线的问题是"量级上不可能"（一个请求搬 256 GiB），不是"慢几倍"。用时间模型反而会给出"慢 100 倍"这种不够震撼、且依赖假设的数。
  5. 第 (5) 段显式声明 b∗=330 并做交集判断。它把第 1 章的拐点、第 2 章的并发、本节的池容量串成一条链："KV 池换吞吐"的边际价值什么时候归零，取决于 b∗ 是否可达。
  6. 第 (2) 段四种负载共用 random.Random(11)。同一个种子保证"分页/预留"的差异只来自策略，不来自负载抽样 —— 这类对照实验里最容易犯的错就是让两组用不同数据。

四处值得单独读的数字：

  • 第 (1) 段的最后一列：s=2048、b=64 时 KV 访存已经是权重访存的 2.6 倍，s=32768 时 41.8 倍。所以"KV 只是显存问题"是错的 —— 它首先是带宽问题，而且带宽代价比显存代价更早成为瓶颈（显存是容量，带宽是每步）。
  • 第 (2) 段"能装(预留)"整列都是 118 —— 与负载完全无关。这是"按最大长度预留"最致命的性质：并发上限由配置里的常数决定，而不是由负载决定。
  • 第 (3) 段的最后两列一起看：Bextblk​ 从 8 到 128，块内碎片涨 16 倍（0.78% → 12.5%），块数降 16 倍（4096 → 256）。两个方向都是线性的，所以最优值在中点附近 —— 这正是 16 的算术来源。
  • 第 (5) 段：b∗=330 要 82.5 GiB 的池才能越过，而单卡最大只能用 ~59 GiB。所以"KV 池的边际价值归零"这件事在单卡上不会发生 —— 这意味着第 4 节的"KV 配额 vs 缓存命中率"取舍只有当模型用 TP/PP 摊薄权重后才需要认真算。

小结#

  • 每 token 的 KV 字节是可精确算的：KV1​=2Lnkv​dhead​σ，示例 = 128 KiB/token。s=4096 就要 512 MiB，s=32768 要 4 GiB。它是所有 KV 账的地基。
  • KV 不只是"占地方"：每步都要读写。s=4096、b=64 时 KV 访存已超过纯权重访存数倍 —— 这是长上下文压低"免费 batch"上限（b∗ 从 330 到 248）的机制。
  • 降 KV 的三条路可乘但代价不同：GQA（架构级、要重训）、量化（免训、要评估精度）、按头分片（免训、要通信）。工程顺序：先分片、再量化、最后才动架构。
  • "按最大长度预留"在真实负载下浪费 80%+（重尾负载下利用率仅 17~19%）。这是 PagedAttention 的动机：它不省单 token 字节，省的是"预留但没用"的部分。
  • 分页引入两种开销，方向相反：块内碎片 ∝Bblk​/sˉ（Bblk​ 要小），块表规模 ∝smax​/Bblk​（Bblk​ 要大）。Bblk​=16 是折中：块内碎片约 1.6%（短请求）、块数可控、块表开销可忽略（0.003%）。
  • "连续增长 + 拷贝"不可行：总搬运量 O(s2)，一个 32k 请求就是 256 GiB 搬运（KV 池的几十倍）。分页的第二个收益是把 O(s2) 拷贝变成 O(s) 块分配。
  • 并发上限由长度分布决定，不由池大小单独决定：按均值估算最多可以乐观 44%（重尾负载）。容量规划必须用真实分布做模拟或至少用分位数。
  • "KV 池换吞吐"不是永远成立：在 bKV​<b∗ 时是线性的，越过 b∗ 后饱和。示例中要越过 b∗=330（sˉ=2048）需要 82.5 GiB 的池 —— 单卡装不下，所以现实部署里 KV 池一直处于"线性换吞吐"区间。
  • 分页必须配抢占：分页把准入决策从"开始时一次性"变成"每一步都可能失败"。"按需分配 + 无抢占"= OOM 发生在请求中途，而"阻塞等待"会导致所有在飞请求互相等待的死锁。
  • 一句话：KV 显存账的第一性原理是"每 token 128 KiB × 序列长 × 并发数"；分页不改变这个乘积，它改变的是"你为没用到的那部分付了多少钱"。

下一节：KV 的显存账已经算清，但有一个被忽略的浪费 —— 多个请求共享同一段前缀时，那段 KV 是逐份复制的。在"统一系统提示 + 长文档问答 + 少样本模板"的负载里，这个浪费可以超过前面所有优化的总和。第 4 节讲前缀共享、命中率曲线与驱逐策略。
