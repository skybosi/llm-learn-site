沙箱、权限与前置审批；成本与延迟的工程约束#

这一节要解决什么#

前六章把 Agent 的能力补齐了：循环、工具、状态、规划、协作。第 7 章前两节让它可测量、可归因。最后一节处理边界：它被允许做什么、什么时候必须停下来问人、以及这一切要花多少钱和多长时间。

这一节要拆掉一个默认假设：安全是能力之外的附加约束。实际上：

能力上限=它能做什么;风险上限=它被允许做什么

设计得好不好，直接决定三件事：最坏情况会造成多大破坏、用户愿意等多久、每任务多少钱。而这三者是互相挤压的：

  • 要更安全 → 加审批 → 延迟上升、用户放弃率上升；
  • 要更低延迟 → 减少验证与审批 → 风险与错误率上升；
  • 要更高可靠性 → 重试 + 更强模型 + 更多验证 → 成本上升。

所以这一节的产出不是一个"最佳配置"，而是一组显式的取舍规则，以及一条最实用的结论：什么时候不该用 Agent。

学完这一节你应该能回答：

  • 能力的三个层级怎么分？各层的默认策略是什么？
  • 沙箱"能防什么"和"不能防什么"？（后者更容易被忽略。）
  • 审批应该拦在循环的哪一步？三种位置的延迟与风险覆盖有什么区别？
  • 什么是"审批疲劳"？它怎么被量化？
  • 每任务成本的公式由哪几项组成？哪一项通常是主因？
  • 降本应该按什么顺序做？为什么"换更便宜的模型"应该是最后一步？
  • 什么条件下应该明确说"这里不该用 Agent"？

一、能力的三个层级#

1.1 分层与默认策略#

层级 典型动作 默认策略 审计要求 失败处置
只读 查询、检索、读文件、读数据库 放行（沙箱内） 记录读集合（供归因） 重试/换源
可逆写 写草稿、创建可撤销的记录、发内部通知 沙箱内放行 / 限额 记录写集合与幂等键 补偿/撤销（第 3 章）
不可逆写 付款、发外部邮件、提交申报、删除数据 默认需审批 记录 + 人工可查 + 二次确认 不可撤销：只有补偿/对账

分层的意义在于：风险不是由"模型多听话"决定的，而是由"这个动作属于哪一层"决定的。一个只读 Agent 即使被完全劫持（提示注入），它能造成的破坏上限就是"读错东西" —— 因为它没有写权限的凭据。

风险上限=f(被允许的动作集合)而不是f(提示词的约束强度)

提示词是请求，权限是结构。 这是本节的第一条原则。

1.2 沙箱：能防什么#

机制 防什么 不防什么
进程/容器隔离 逃逸到宿主、读到不该读的文件 在沙箱内合法地做错事
只读挂载 + 临时可写层（用完即焚） 持久化污染、留下后门 在临时层里把活干错（结果照样传出去）
无出网 / 白名单出网 数据外泄、调用未审计的外部动作 通过白名单内的通道外泄（提示注入的经典路径）
资源限额（CPU/内存/时间/磁盘） 失控循环、成本爆炸（第 5 章第 4 节） 在限额内低效地烧钱
凭据隔离（短时效、最小范围令牌） 长期密钥泄露、越权范围过大 在令牌有效期内做该令牌允许的坏事
网络流量记录 事后审计 实时阻止（除非有 DLP 规则）

1.3 沙箱不能防的四类（必须承认）#

沙箱⊊安全⟸四类风险在沙箱的语义之外

类型 例子 为什么沙箱管不了 该谁管
语义层面的错 动作完全合法，但业务上错误（给错误的客户退了正确的金额） 沙箱只看"能不能做"，不看"该不该做" 业务校验 + 审批 + 评测（第 1 节）
提示注入诱导的合法越权 工具权限给得太宽，注入让 Agent 用了它 动作在权限内，沙箱放行是正确行为 最小权限（收紧权限集合）
沙箱外的人按它的建议操作 Agent 说"请手动执行这条命令" 沙箱管不到人 输出审查 + 明确"不要照着做"的界面设计
不可逆动作的既成事实 钱已经转了 沙箱不是时间机器 前置审批（本节第三节）+ 补偿（第 3 章）

第二类最危险，因为它是"系统按设计正常工作"的结果：权限给宽了，Agent 用满了，一切合法。这就是最小权限不是"最佳实践"而是必需的原因 —— 它是唯一能限制"合法但有害"的手段。

最小权限⟺动作集合=完成任务所必需的集合（不是"可能有用"的集合）

二、权限模型#

2.1 四维授权#

一条权限 = 主体 × 动作 × 对象 × 条件：

Permission=(subject, action, object, condition)

维度 内容 例
主体 哪个 Agent（含子 Agent，第 6 章） refund_agent，不是"所有 Agent"
动作 具体操作 refund.create（不是 refund.*）
对象 作用范围 order_id ∈ 本会话关联的订单
条件 数值/时间/状态约束 amount ≤ 500、仅在 09:00–18:00、仅当已通过风控

"对象"维度是防越权的关键：给 refund.create 权限但不限定对象，等于给"对所有订单退款"的权限。会话级作用域是最常用也最有效的对象约束。

2.2 时效化与最小范围#

令牌=(scope, expiry, subject, max_uses)

四个字段缺一不可：

字段 缺失后果
scope 权限过大（越权面）
expiry 泄露后永久可用
subject 任何 Agent 都能用（无法归因）
max_uses 令牌被重复使用（第 3 章的幂等面）

短时效令牌的一个副作用很重要：它让"长期密钥不进 Agent 上下文"成为可能。Agent 看到的只是一个有时效的句柄，即使这个句柄被注入攻击泄露，损失也被时间与范围限制住。

凭据暴露面=有效期×范围

2.3 权限随依赖图下发#

第 6 章讲了上下文隔离，权限隔离是它的孪生：子 Agent 只拿到自己那部分权限。

主 Agent：持有全局预算与协调权限
 ├─ 子 Agent A（检索）：只读权限，无写权限，无外部网络
 ├─ 子 Agent B（起草）：可逆写权限（写草稿区），无外部网络
 └─ 子 Agent C（提交）：不可逆写权限，但**只此一个**，且需审批

这样做的效果是结构性的：A 和 B 即使被提示注入完全控制，也没有能力造成不可逆后果 —— 它们的令牌里没有那个 scope。这就是第 6 章 3.4 说的"能力上限被结构限制"。

2.4 权限提升的正确路径#

Agent 遇到权限不足时，有两种可能的行为：

行为 评价
申请提权（发起审批请求，说明需要什么、为什么） ✓ 正确：把限制变成一次显式的人机交互
绕过（换一个等价工具、猜参数、请求用户提供凭据） ✗ 危险：这恰恰是提示注入想要的结果

权限提升必须是显式的、可审计的、有上限的(次数上限+范围上限)

"换一个等价工具"这条特别隐蔽：如果系统里同时有一个受审批保护的工具和一个不受保护的等价工具，Agent 会（在被拒绝后）学会走后者。所以等价能力必须受同等管控：

∀ capability c: 管控(c)=tool∈implements(c)max​管控(tool)

三、前置审批：拦在哪一步#

3.1 审批不是一个开关，而是一个位置#

这是本节最重要的设计判断。三种位置：

位置 机制 延迟 风险覆盖 用户体验
A. 动作执行前 每次不可逆动作前拦一次 最高（每次一步） 最完整（逐个动作可审） 频繁打断
B. 计划生成后、执行前 一次批准整个计划 一次性（1 次等待） 覆盖计划内的动作；计划偏离时失效 最舒服
C. 风险阈值触发时 按金额/对象/不可逆性动态拦 中（只拦高风险的） 取决于阈值定义 最经济

B 位置的前提是"计划可预演" —— 这正是第 5 章第 2 节的用途：如果计划是可验证的对象（前置/后置/副作用显式），人可以在执行前一次性审完；如果计划是一段自然语言，人无法审出"它到底会不会付款"。所以：

计划的可验证性⟹审批可以前移到计划层，从而降低延迟

这是一个跨章的因果链：第 5 章的表示 → 审批位置可行 → 延迟下降。反过来，计划不可验证的系统只能选 A（频繁打断）或 C（依赖阈值精确）。

B 的关键风险是"计划偏离"：执行中发生了重规划（第 5 章第 3 节），新计划可能包含未经审批的动作。处置：

重规划后必须重新审批⟺新计划引入了未在已批准集合中的不可逆动作

3.2 审批疲劳：可量化的失败模式#

审批的失效不是"审批被绕过"，而是审批变成无意识的点击：

审批疲劳⟺通过率→1 ∧ 平均审阅时间→0

指标 健康区间 危险信号
审批次数 / 任务 0~2 > 5（用户在无脑点）
通过率 0.6~0.9 > 0.97（审批没有拦下任何东西）
平均审阅时间 > 10 秒 < 3 秒（没看就点）
拒绝后的补救时间 短 长（拒绝让人更麻烦 → 更倾向通过）

缓解手段（按有效性）：

  1. 批量审批（B 位置）：把 5 次打断变成 1 次审阅。
  2. 风险分级：只有高风险动作需要人审，低风险走事后抽样审计。
  3. 事后审计 + 抽样复核：把"事前全审"换成"事后抽检 + 异常告警"。它的前提是动作可撤销或可补偿 —— 不可逆动作不能用这个模式。
  4. 默认安全值：把"拒绝"设为默认（超时未审批 = 拒绝），避免"超时自动通过"。

审批设计目标=max(拦下的真实风险)s.t.审阅时间≥tmin​, 次数≤nmax​

3.3 审批的延迟代价#

延迟=执行tmodel​+ttool​​​+审批napprove​⋅(thuman​+twait​)​​

其中 twait​ 是排队等待（人可能不在），它是方差最大的项。所以审批位置的选择还要考虑一个因素：

交互式场景⇒优先 B/C（少次数）;批处理场景⇒A 也可接受（总时长不敏感）

四、成本模型#

4.1 每任务成本的构成#

Ctask​=模型 tokeni∑​(ciin​Tiin​+ciout​Tiout​)​​+工具调用j∑​cjtool​​​+沙箱/并发/存储Cinfra​​​+重试与回退Cretry​​​+人工审批Chuman​​​

逐项说明：

项 内容 常常被低估的地方
模型 token 输入/输出分别计价（输出通常贵 3~4 倍） 输入 token 是主要驱动（上下文长度，第 4 章）
工具调用 外部 API 单价 × 次数 重试会放大（乘 E[重试次数]）
基础设施 沙箱实例、并发、存储、日志 长尾任务（P95​）占用的实例时间
重试与回退 期望值：∑step​cstep​⋅E[重试] + 补偿成本 第 5 章第 4 节的 n∗ 直接影响这一项
人工审批 napprove​×thuman​×chourly​ 被完全忽略（因为不进 API 账单）

输入 token 成本∝上下文长度⟹上下文工程是成本手段，不是优化细节（第 4 章第 3 节）

这是本节最实用的一条：把上下文从 40k 剪到 12k，就是最直接的降本 —— 比换模型更有效、且不损失能力（前提是剪掉的是干扰，第 4 章的 g(N)）。

4.2 延迟模型#

墙钟=关键路径（第 5 章第 1 节）v∈关键路径∑​(tvmodel​+tvtool​)​​+napprove​⋅(thuman​+twait​)+tqueue​

关键路径决定下界（第 5 章 2.2）：并行化不能突破关键路径。所以"加并发降延迟"只对关键路径之外的节点有效 —— 而它们本来就不影响延迟。这是"加资源无效"的常见来源。

交互式场景的延迟预算（经验量级，用于设计而非精确承诺）：

场景 人的容忍 设计取向
同步对话 秒级 流式输出（首 token 时间优先）、单次模型调用、减少工具往返
站内助手 十几秒 允许 2~3 步；审批用 B 位置
后台任务 分钟~小时 允许长链路；审批可用 A 位置；成本优先
批处理 无硬约束 成本与正确率优先；可接受重试

"慢但便宜"vs"快但贵"：可以先出草稿再细化（流式 + 分级模型）、可以缓存/前缀复用（第 4 章）、可以把非关键路径的工作推到后台。

4.3 成本-可靠性-延迟三角#

三个目标不可同时最优⟹必须显式写下一个作为约束、一个作为目标、一个作为可接受损失

想要 代价
更高可靠性 重试 + 更强模型 + 更多验证（第 5 章第 2 节的四级检查）→ 成本↑ 延迟↑
更低延迟 减少验证与审批、跳过预演 → 可靠性↓ 风险↑
更低成本 剪上下文 + 减少无效调用 + 缓存 + 分级模型 → 若过度则可靠性↓

4.4 降本的顺序（重要）#

正确的降本顺序是"先改设计，最后才降模型规格"：

顺序 手段 典型收益 是否损失能力
1 剪裁上下文（去掉干扰项，第 4 章） 输入 token 降 40~70% 不损失，常常提升
2 减少无效调用（第 2 章的终止条件 + 第 5 章第 3 节的同因失败升级） 调用数降 20~40% 不损失（去掉的是白做的）
3 缓存/前缀复用（对稳定前缀） 输入成本降 30~50% 不损失
4 计划层剪枝（第 5 章第 4 节的分支定界 + 最优停止） 期望成本降 10~30% 不损失（砍的是不划算的分支）
5 把简单任务路由到小模型（按难度分级） 成本降 30~60% 可能损失（分级判错时）
6 换更小的模型 成本降 50~80% 会损失

为什么顺序不能颠倒：14 是"去掉浪费"（负收益的动作），56 是"降低质量换钱"。先做 56 会在一个仍然浪费的系统上降低单次成本，结果是"便宜但更差"，而且你把 14 的收益空间也一起压掉了。

先把浪费去掉，再考虑降质(否则你为浪费付了降价后的钱)

4.5 什么时候不该用 Agent#

这一条是本节最实用的结论。不该用 Agent 的四种场景：

场景 判据 替代方案
任务确定性高 步骤固定、输入结构化、不需要判断 确定性流水线/规则引擎（更快、更便宜、可证明正确）
强合规要求 每一步必须可审计到规则条款、不接受概率性输出 规则系统 + 人工复核
可靠性要求极高 需要 1−10−6 级别的正确率 确定性系统 + 校验和；Agent 只做"建议"
成本高于人力 Ctask​×频率> 人工成本，且质量无显著提升 人工（或人机混合：Agent 只做草稿）

用 Agent⟺收益Δ质量​⋅V+Δ速度​⋅Vt​​​>成本Ctask​+C风险​+C维护​​​

最后还有一个常被忽略的项：维护成本。Agent 系统的维护不是"修 bug"，而是持续的评测集维护、提示词迭代、工具契约演进、模型版本迁移（第 4 章的环境指纹会不断变化）。一个能跑通 demo 的 Agent 与一个能上线的 Agent，差的往往就是这部分持续投入。

4.6 上线前清单#

□ 能力分级：每个动作属于只读 / 可逆写 / 不可逆写，并写明默认策略
□ 权限矩阵：主体 × 动作 × 对象 × 条件；含会话级作用域
□ 凭据：短时效、最小 scope、有 max_uses；长期密钥不进上下文
□ 沙箱：只读挂载 + 临时可写层 + 出网白名单 + 资源限额
□ 审批位置：A/B/C 选定并说明理由；重规划后的重新审批规则
□ 审批健康度指标：次数/任务、通过率、平均审阅时间、超时策略（默认拒绝）
□ 预算硬闸：金额/时间/副作用次数（第 5 章第 4 节）；超限的降级策略
□ 可观测：轨迹字段齐全（第 2 章）；幂等键与不可逆动作清单可查
□ 评测：双级评测集 + 失效模式覆盖 + held-out（第 1 节）
□ 归因：四象限判据可执行、有回归用例、有高代价误判率指标（第 2 节）
□ 回滚/补偿预案：每个不可逆动作都有对应的补偿或对账方案（第 3 章）
□ 成本与延迟 SLO：$P_{95}$ 而非均值；有告警
□ 降本顺序已执行 1~4，才考虑 5~6

    "read": "allow_in_sandbox",
    "reversible": "allow_with_quota",        # 沙箱内放行，但有配额与幂等要求
    "irreversible": "require_approval",      # ★ 默认必须审批
}


def classify(action: str, amount: float = 0.0,
             shared_object: bool = False) -> tuple[str, str]:
    """★ 设计决策：分级**由动作语义决定**，不由调用者传入。

    让调用者自己声明"我这个动作是可逆的"，等于让被约束者写约束 ——
    分级必须集中在策略表里，才能被审计。
    """
    table = {
        "search": "read", "read_file": "read", "query_db": "read",
        "write_draft": "reversible", "create_ticket": "reversible",
        "send_internal_note": "reversible",
        "pay": "irreversible", "send_email_external": "irreversible",
        "submit_filing": "irreversible", "delete_record": "irreversible",
    }
    tier = table.get(action)
    if tier is None:
        return "irreversible", f"未知动作 {action!r}：保守按不可逆处理（默认拒绝）"
    return tier, f"{action} → {tier}（{DEFAULT_POLICY[tier]}）"


@dataclass
class CapabilityPolicy:
    """★ 设计决策：条件（金额/对象/次数）写进策略，而不是写在提示词里。

    "不要退款超过 500 元"写在提示词里是**请求**；写在策略里并在工具入口校验才
    是**约束**。Agent 被注入攻击后，前者会失效，后者不会。
    """
    max_amount_without_approval: float = 500.0
    require_dual_approval_above: float = 5000.0
    max_irreversible_per_task: int = 2

    def decide(self, action: str, amount: float = 0.0,
               used_irreversible: int = 0) -> dict:
        tier, why = classify(action, amount)
        if tier == "read":
            return {"动作": action, "层级": tier, "决策": "allow", "理由": why}
        if tier == "reversible":
            return {"动作": action, "层级": tier, "决策": "allow",
                    "理由": why + "；需幂等键（第 3 章）+ 配额"}
        # irreversible
        if used_irreversible >= self.max_irreversible_per_task:
            return {"动作": action, "层级": tier, "决策": "deny",
                    "理由": f"本任务已执行 {used_irreversible} 个不可逆动作，"
                            f"达上限 {self.max_irreversible_per_task}（硬闸，第 5 章第 4 节）"}
        if amount > self.require_dual_approval_above:
            return {"动作": action, "层级": tier, "决策": "dual_approval",
                    "理由": f"金额 {amount} > {self.require_dual_approval_above} → 双人审批"}
        if amount > self.max_amount_without_approval:
            return {"动作": action, "层级": tier, "决策": "approval",
                    "理由": f"金额 {amount} > {self.max_amount_without_approval} → 单人审批"}
        return {"动作": action, "层级": tier, "决策": "approval",
                "理由": why + "；不可逆动作一律审批（即使金额小）"}


# ==================== (2) 权限矩阵 ====================
@dataclass
class Token:
    subject: str
    scope: set[str]                # 允许的动作
    objects: set[str]              # 允许作用的对象（会话级作用域）
    expiry: float                  # 过期时刻
    max_uses: int
    used: int = 0


class PermissionMatrix:
    """四维授权：主体 × 动作 × 对象 × 条件。

    ★ 设计决策：越权是**结构性拒绝**（返回 deny），不是靠提示词说"请不要"。
      第 6 章 3.4 的"能力上限被结构限制"在这里落地。
    """

    def __init__(self) -> None:
        self.tokens: list[Token] = []
        self.denials: list[dict] = []

    def grant(self, token: Token) -> None:
        self.tokens.append(token)

    def check(self, subject: str, action: str, obj: str, now: float,
              amount: float = 0.0) -> tuple[bool, str]:
        for t in self.tokens:
            if t.subject != subject:
                continue
            if now >= t.expiry:
                self.denials.append({"subject": subject, "action": action,
                                     "why": "令牌过期"})
                return False, "deny：令牌已过期（时效化：凭据暴露面 = 有效期 × 范围）"
            if t.used >= t.max_uses:
                self.denials.append({"subject": subject, "action": action,
                                     "why": "超过最大使用次数"})
                return False, "deny：令牌使用次数耗尽（max_uses）"
            if action not in t.scope:
                self.denials.append({"subject": subject, "action": action,
                                     "why": f"scope 不含 {action}"})
                return False, (f"deny：{subject} 的 scope 不含 {action} "
                               f"（最小权限：必需集合，不是'可能有用'的集合）")
            if obj not in t.objects and "*" not in t.objects:
                self.denials.append({"subject": subject, "action": action,
                                     "why": f"对象 {obj} 超出作用域"})
                return False, (f"deny：对象 {obj} 超出会话级作用域 {sorted(t.objects)}"
                               f"（对象维度是防越权的关键）")
            t.used += 1
            return True, f"allow：命中令牌（{t.used}/{t.max_uses}）"
        return False, "deny：没有匹配的授权"


# ==================== (3) 审批位置 ====================
@dataclass
class ApprovalOutcome:
    position: str                 # pre_action | after_plan | risk_triggered
    n_approvals: int
    approved: int
    wait_seconds: float
    human_seconds: float
    abandoned: bool = False       # 用户放弃


def simulate_approval(position: str, actions: list[dict],
                      t_human: float = 25.0, t_wait: float = 120.0,
                      fatigue_after: int = 4, reject_risk: float = 0.7) -> ApprovalOutcome:
    """三种位置的对比。

    ★ 设计决策：显式建模**审批疲劳**：超过 fatigue_after 次之后，
      人的审阅时间降到 1/5、通过率升到 ~1.0（无脑点通过）。
      这把"审批次数"从体验问题变成**安全指标**：次数多的位置会自己废掉自己的防线。
      同时把"被审的动作集合"按位置分别确定 —— pre_action 审全部不可逆动作，
      after_plan 只审计划一次（此时无法逐个看风险），risk_triggered 只审高风险动作。
    """
    irreversible = [a for a in actions if a["tier"] == "irreversible"]
    high_risk = [a for a in irreversible if a.get("risk", 0) >= 0.5]

    if position == "pre_action":
        to_review = irreversible
    elif position == "after_plan":
        to_review = [] if not irreversible else [{"risk": 0.3, "plan_level": True}]
    elif position == "risk_triggered":
        to_review = high_risk
    else:
        raise ValueError(position)

    approved, human_total = 0, 0.0
    for i, a in enumerate(to_review):
        if i < fatigue_after:
            human_total += t_human
            approved += int(a.get("risk", 0.3) < reject_risk)     # 未疲劳：按风险裁决
        else:
            human_total += t_human / 5.0                          # ★ 疲劳：审阅时间骤降
            approved += 1                                         # ★ 疲劳：无脑通过
    return ApprovalOutcome(position, len(to_review), approved,
                           len(to_review) * t_wait, human_total)


def approval_health(o: ApprovalOutcome) -> dict:
    """3.2 的审批健康度指标。"""
    pass_rate = o.approved / max(1, o.n_approvals)
    avg_review = o.human_seconds / max(1, o.n_approvals)
    flags = []
    if o.n_approvals > 5:
        flags.append("审批次数/任务 > 5 → 用户会无脑点")
    if pass_rate > 0.97 and o.n_approvals:
        flags.append("通过率 > 0.97 → 审批没有拦下任何东西")
    if 0 < avg_review < 3:
        flags.append("平均审阅 < 3 秒 → 审批疲劳")
    return {"位置": o.position, "次数": o.n_approvals, "通过率": round(pass_rate, 3),
            "平均审阅秒": round(avg_review, 2), "等待秒": round(o.wait_seconds, 1),
            "风险信号": flags or ["健康"]}


# ==================== (4) 成本模型 ====================
@dataclass
class CostModel:
    c_in: float = 0.000002      # 元 / 输入 token
    c_out: float = 0.000008     # 元 / 输出 token（通常是输入的 3~4 倍）
    tool_price: dict[str, float] = field(default_factory=lambda: {
        "search": 0.02, "read_file": 0.0, "write_draft": 0.0,
        "pay": 0.05, "send_email_external": 0.01})
    infra_per_min: float = 0.01
    human_hourly: float = 120.0


def task_cost(m: CostModel, steps: list[dict], retries: int = 0,
              n_approvals: int = 0, t_human: float = 25.0,
              minutes: float = 2.0) -> dict:
    """4.1 的公式：token + 工具 + 基础设施 + 重试 + 人工。

    ★ 设计决策：把**人工审批**计入成本。它不进 API 账单，所以最容易被完全忽略，
      但在需要审批的流程里它常常是最大的一项。
    """
    token = sum(s["in_tokens"] * m.c_in + s["out_tokens"] * m.c_out for s in steps)
    tool = sum(m.tool_price.get(s["tool"], 0.0) for s in steps)
    retry = sum(m.tool_price.get(s["tool"], 0.0) + s["in_tokens"] * m.c_in * 0.5
                for s in steps[:retries]) if retries else 0.0
    human = n_approvals * t_human / 3600.0 * m.human_hourly
    infra = minutes * m.infra_per_min
    total = token + tool + retry + infra + human
    return {"模型 token": round(token, 4), "工具": round(tool, 4),
            "重试": round(retry, 4), "基础设施": round(infra, 4),
            "★ 人工审批": round(human, 4), "总计": round(total, 4),
            "_share": {"输入 token": round(sum(s["in_tokens"] for s in steps) * m.c_in / total, 3)
                       if total else 0}}


def cost_reduction_order(m: CostModel, steps: list[dict],
                         n_approvals: int = 0) -> list[dict]:
    """4.4 的降本顺序实验：先去掉浪费，最后才降质。

    ★ 设计决策：默认 `n_approvals=0`，即只比较**技术成本**（token + 工具 + 基础设施）。
      理由：人工审批不随技术手段变化，把它算进来会淹没所有技术手段的效果，
      从而看不出"1~4 优于 5~6"这件事。人工成本单独在 task_cost 里呈现。
    ★ 设计决策：逐项独立计算"如果只做这一项"的降幅，并标注**是否损失能力**。
    """
    base = task_cost(m, steps, n_approvals=n_approvals)["总计"]
    out = []

    # 1 剪裁上下文：把每步输入 token 降 60%（去掉干扰项）
    cut = [dict(s, in_tokens=int(s["in_tokens"] * 0.4)) for s in steps]
    out.append({"顺序": 1, "手段": "剪裁上下文（去干扰，第 4 章）",
                "新成本": round(task_cost(m, cut, n_approvals=n_approvals)["总计"], 4),
                "损失能力": "否（常常提升）"})

    # 2 减少无效调用：去掉 25% 的步骤
    fewer = steps[: max(1, int(len(steps) * 0.75))]
    out.append({"顺序": 2, "手段": "减少无效调用（终止条件 + 同因失败升级）",
                "新成本": round(task_cost(m, fewer, n_approvals=n_approvals)["总计"], 4),
                "损失能力": "否"})

    # 3 缓存/前缀复用：输入 token 成本降 40%
    cached = [dict(s, in_tokens=int(s["in_tokens"] * 0.6)) for s in steps]
    out.append({"顺序": 3, "手段": "缓存/前缀复用",
                "新成本": round(task_cost(m, cached, n_approvals=n_approvals)["总计"], 4),
                "损失能力": "否"})

    # 4 计划层剪枝：砍掉 20% 的步骤（不划算的分支）
    pruned = steps[: max(1, int(len(steps) * 0.8))]
    out.append({"顺序": 4, "手段": "计划层剪枝（分支定界 + 最优停止，第 5 章）",
                "新成本": round(task_cost(m, pruned, n_approvals=n_approvals)["总计"], 4),
                "损失能力": "否（砍的是不划算的分支）"})

    # 5 分级路由：1/3 的步骤走小模型（输出成本减半）
    m_small = CostModel(m.c_in, m.c_out * 0.5, m.tool_price, m.infra_per_min, m.human_hourly)
    routed = [dict(s, out_tokens=int(s["out_tokens"] * 0.5)) if i % 3 == 0 else s
              for i, s in enumerate(steps)]
    out.append({"顺序": 5, "手段": "简单任务路由到小模型（按难度分级）",
                "新成本": round(task_cost(m_small, routed, n_approvals=n_approvals)["总计"], 4),
                "损失能力": "可能（分级判错时）"})

    # 6 换小模型：输入输出都便宜 70%
    m_cheap = CostModel(m.c_in * 0.3, m.c_out * 0.3, m.tool_price,
                        m.infra_per_min, m.human_hourly)
    out.append({"顺序": 6, "手段": "换更小的模型",
                "新成本": round(task_cost(m_cheap, steps, n_approvals=n_approvals)["总计"], 4),
                "损失能力": "会"})
    for r in out:
        r["相对基线降幅"] = f"{(1 - r['新成本'] / base):.1%}" if base else "n/a"
    return out


# ==================== (5) 延迟模型 ====================
def wall_clock(critical_path: list[float], parallel_time: float = 0.0,
               n_approvals: int = 0, t_human: float = 25.0,
               t_wait: float = 120.0) -> dict:
    """4.2：关键路径 + 审批等待（关键路径决定下界，加并发只在路径之外有效）。"""
    exec_s = sum(critical_path)
    approval = n_approvals * (t_human + t_wait)
    return {"关键路径执行": round(exec_s, 1), "并行部分": round(parallel_time, 1),
            "审批等待": round(approval, 1),
            "总墙钟": round(max(exec_s, parallel_time) + approval, 1),
            "★ 下界": round(exec_s, 1)}


# ==================== (6) 该不该用 Agent ====================
def should_use_agent(deterministic: bool, compliance: str, required_reliability: float,
                     quality_gain: float, freq_per_day: int, cost_per_task: float,
                     manual_cost: float, risk_cost: float = 0.0,
                     maintenance_per_day: float = 0.0) -> dict:
    """4.5 的判据：四个否决项 + 收益 vs 成本。

    ★ 设计决策：结论有三个（不是两个），并把"算下来亏"与"被否决"分开报。
      因为它们的处置不同：被否决 → 换方案；算下来亏 → 改设计降本或缩小范围。
    """
    vetoes = []
    if deterministic:
        vetoes.append("任务确定性高 → 用确定性流水线/规则引擎（更快更便宜可证明）")
    if compliance == "high":
        vetoes.append("强合规 → 规则系统 + 人工复核（不接受概率性输出）")
    if required_reliability >= 0.999999:
        vetoes.append(f"可靠性要求 {required_reliability} 超出概率系统的合理承诺")
    gain = quality_gain * manual_cost
    cost = cost_per_task + risk_cost + maintenance_per_day / max(1, freq_per_day)
    net = gain - cost
    if cost >= manual_cost and gain <= 0:
        vetoes.append(f"成本 {cost:.2f}/任务 ≥ 人工 {manual_cost:.2f} 且质量无提升 → 用人工")
    verdict = ("不该用 Agent（被否决）" if vetoes else
               "可用 Agent（需满足清单其余项）" if net > 0 else
               "算下来不划算（未被否决，但期望净收益为负）")
    return {"结论": verdict, "否决项": vetoes,
            "单任务收益": round(net, 4),
            "日成本": round(cost * freq_per_day, 2),
            "日人工对照": round(manual_cost * freq_per_day, 2),
            "提醒": "成本项含风险与维护——后者常被忽略（提示词迭代/评测集/契约/模型迁移）"}

    def cumulative(m: CostModel, steps: list[dict], order: list[int]) -> tuple[float, list[str]]:
        """按顺序累积执行降本手段，返回最终成本与执行轨迹。"""
        cur, trace = steps, []
        mm = m
        for k in order:
            if k == 1:
                cur = [dict(s, in_tokens=int(s["in_tokens"] * 0.4)) for s in cur]
            elif k == 2:
                cur = cur[: max(1, int(len(cur) * 0.75))]
            elif k == 3:
                cur = [dict(s, in_tokens=int(s["in_tokens"] * 0.6)) for s in cur]
            elif k == 4:
                cur = cur[: max(1, int(len(cur) * 0.8))]
            elif k == 5:
                mm = CostModel(m.c_in, m.c_out * 0.5, m.tool_price, m.infra_per_min,
                               m.human_hourly)
                cur = [dict(s, out_tokens=int(s["out_tokens"] * 0.5)) if i % 3 == 0 else s
                       for i, s in enumerate(cur)]
            elif k == 6:
                mm = CostModel(mm.c_in * 0.3, mm.c_out * 0.3, mm.tool_price,
                               mm.infra_per_min, mm.human_hourly)
            trace.append(f"{k}")
        return task_cost(mm, cur, n_approvals=0)["总计"], trace

    for label, order in (("正确顺序 1→2→3→4→5→6", [1, 2, 3, 4, 5, 6]),
                         ("先降质 6（再想优化）", [6]),
                         ("先降质 6，然后才 1→2", [6, 1, 2])):
        cost, trace = cumulative(m, steps, order)
        print(f"    {label:24s} 最终 {cost:.4f} 元（相对基线 {(1 - cost / base):.1%}）")
    print("    ★ 关键不是'哪一项最省'，而是'最终能到多低'：")
    print("      先做 6 会同时降低后续每一步的绝对收益空间（存量变小），")
    print("      而且它损失能力 —— 你为了省 47% 付掉了质量，而省下的量还能通过 1~4 拿更多")

    print("=" * 82)
    print("【6. 延迟：关键路径决定下界，加并发只在路径之外有效】")
    cp = [1.2, 3.5, 0.8, 2.0]        # 关键路径上的步骤（秒）
    for n_appr in (0, 1, 2):
        print(f"    审批 {n_appr} 次: {wall_clock(cp, parallel_time=2.0, n_approvals=n_appr)}")
    print("    ★ 并行部分 2.0 秒 < 关键路径 7.5 秒 → 加再多并发也不降低总墙钟")
    print("    ★ 交互式场景（秒级容忍）必须走 B/C 位置，否则 145 秒的审批等待直接劝退")

    print("=" * 82)
    print("【7. 该不该用 Agent（四个否决项）】")
    scenarios = [

                                                     required_reliability=0.9,

八处关键设计决策：

  1. classify 的动作分级表是集中的，不接受调用者传入层级。让调用者声明"我这个动作是可逆的"等于让被约束者写约束 —— 分级必须集中在策略里才能被审计。演示里未知动作 frobnicate 被保守判为不可逆（默认拒绝），这是安全方向上的默认值。
  2. CapabilityPolicy 把条件（金额阈值、单任务不可逆次数上限）写进策略对象并在决策时校验。这与"把'不要退款超过 500'写进提示词"有本质区别：注入攻击能让模型违反提示词，但不能改变策略对象的判定。
  3. PermissionMatrix.check 逐条返回具体的拒绝理由（scope 不含 / 对象越界 / 令牌过期 / 次数耗尽）。这四类拒绝对应四个权限字段，缺任何一个字段就会少一类防线。演示里 7 次检查中 4 次被结构性拒绝。
  4. Token.objects 实现会话级作用域。注释点明"对象维度是防越权的关键"：只给 pay 权限不限定对象，等于给"对所有订单退款"的权限。
  5. simulate_approval 显式建模审批疲劳（超过 fatigue_after 次后审阅时间降到 1/5、通过率升到 1.0）。这把"审批次数"从体验问题变成安全指标：演示里 pre_action 位置因为次数多，通过率被推到 1.0（审批没有拦下任何东西），而 risk_triggered 保持了健康的分布。
  6. task_cost 把人工审批计入总成本。它不进 API 账单所以最容易被完全忽略，但在需要审批的流程里常常是最大的一项 —— 演示第 4 段用 0/1/2 次审批的对比把这个效果显示出来。
  7. cost_reduction_order 逐项独立计算降幅并标注是否损失能力。这是 4.4 的可执行形式：14 项是"去掉浪费"（不损失能力），56 项是"降质换钱"。有了这张表，"先换小模型"为什么错就变成了一个可以算出来的结论，而不是一句原则。
  8. should_use_agent 实现四个否决项（而不是打分），并在成本里含 risk_cost 与 maintenance_per_day。演示最后一段刻意放了一个"看起来划算但其实不划算"的退款场景：加进风险与维护成本后，单任务收益被压掉 —— 这就是"demo 能跑通"与"能上线"的差别所在。

小结#

  • 风险上限由"被允许做什么"决定，不是由"模型多听话"决定。提示词是请求，权限是结构。能力分三层：只读（放行 + 记录读集合）、可逆写（沙箱内放行 + 配额 + 幂等键）、不可逆写（默认需审批）。
  • 沙箱能防：逃逸、持久化污染、数据外泄、失控资源占用、凭据泄露。沙箱不能防四类：语义层面的错（合法但业务上错）、提示注入诱导的合法越权（权限给宽了）、沙箱外的人按它的建议操作、不可逆动作的既成事实。第二类最危险，且只有最小权限能限制它。
  • 权限是四维的：主体 × 动作 × 对象 × 条件，且对象维度是防越权的关键（会话级作用域）。令牌必须有 scope / expiry / subject / max_uses 四字段，凭据暴露面=有效期×范围。权限随依赖图下发（第 6 章的权限隔离）：只读子 Agent 即使被完全注入也没有能力造成不可逆后果。
  • 权限提升必须显式、可审计、有上限；"换一个等价工具"是最隐蔽的绕过路径，所以 管控(c)=maxtool​管控(tool)（等价能力同等管控）。
  • 审批不是一个开关，而是一个位置：A 动作执行前（最完整、延迟最高）、B 计划生成后（最经济、前提是计划可预演 —— 第 5 章的表示在这里产生延迟收益）、C 风险阈值触发（最平衡）。重规划后若引入未批准的不可逆动作，必须重新审批。
  • 审批疲劳是可量化的失效模式：通过率→1∧审阅时间→0。健康区间：次数 ≤ 2、通过率 0.6~0.9、审阅 > 10 秒。缓解顺序：批量审批 → 风险分级 → 事后审计 + 抽样（只适用于可撤销动作）→ 默认拒绝（超时未审批 = 拒绝）。
  • 成本模型：Ctask​=∑(cinTin+coutTout)+∑ctool+Cinfra​+Cretry​+Chuman​。两个最常被低估的项：输入 token（∝ 上下文长度 → 上下文工程是成本手段）与人工审批（不进 API 账单）。
  • 降本顺序不能颠倒：① 剪裁上下文 ② 减少无效调用 ③ 缓存/前缀复用 ④ 计划层剪枝 —— 这四项是"去掉浪费"，不损失能力；⑤ 分级路由 ⑥ 换小模型是"降质换钱"，必须放在最后。先做 6 会在一个仍然浪费的系统上降低单价，得到"便宜但更差"，还压掉了 1~4 的空间。
  • 延迟由关键路径决定下界（第 5 章 2.2）：加并发只对关键路径之外的节点有效，而它们本来就不影响墙钟。审批等待 n⋅(thuman​+twait​) 是方差最大的一项，交互式场景必须用 B/C 位置。
  • 什么时候不该用 Agent（四个否决项）：任务确定性高、强合规、可靠性要求极高（≥1−10−6）、成本高于人力且质量无提升。判据是 Δ质量​V+Δ速度​Vt​>Ctask​+C风险​+C维护​ —— 维护成本（评测集、提示词迭代、契约演进、模型迁移）最常被漏掉。
  • 上线清单的价值在于"逐项有主"：能力分级、权限矩阵、凭据时效、沙箱形态、审批位置与健康度指标、预算硬闸、可观测字段、双级评测、四象限归因、补偿预案、成本延迟 SLO、降本顺序。缺项不是"还没做"，而是"上线后的第一个事故点"。

全课收束：这门课从"LLM 是一个无状态、无记忆、无行动能力的函数"出发，补上了四件事 —— 循环（第 2 章）、行动（第 3 章）、状态与记忆（第 4 章），以及在行动之前先想清楚（第 5 章的规划与预算）。第 6 章处理"一个执行者不够时怎么办"，并给出了一个反直觉但重要的结论：多智能体的正当性主要来自上下文与权限的隔离，而不是"人多力量大"。第 7 章把前六章的设计变成可测量、可归因、可上线的东西。第 1 章立的五个设计目标 —— 可靠性、可观测、可组合、可回滚、成本可控 —— 到这里各自获得了一条可跑的指标：可靠性是 pass^k 与回退率，可观测是轨迹字段与双级评测，可组合是工具契约与子 Agent 接口，可回滚是幂等键与补偿预案，成本可控是多维预算与降本顺序。它们仍然互相冲突，仍是取舍 —— 但至少现在，每一次取舍都可以被算出来，也可以被验证。
