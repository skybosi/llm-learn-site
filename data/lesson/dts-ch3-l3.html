拓扑感知：rail-optimized 与跨域通信为何骤降#

上一课把跨机通信当成"一条边"，但真实集群里节点之间并不平等：卡 0 到对端卡 0 只需要过一台 leaf 交换机（一跳），卡 0 到对端卡 3 却要穿过 spine 层。更反直觉的是——同一份梯度、同一个 ring 算法，只把 rank 的排列顺序换一下，预测时间就从 121 ms 掉到 40 ms（3 倍）。本课用一张分层的拓扑加上一段可运行的排法模拟，把"跨域骤降"算成账。

一、概念讲解#

1. 集群不是"一堆 GPU"，而是三层#

把 8 卡机接到集群上，通信要穿过的层级：

层级 介质 典型带宽量级 谁在这里竞争
节点内（NVLink 域） NVLink + NVSwitch 数百 GB/s 单向 同机其它 GPU
rail（leaf 内） IB/RoCE，同号卡一台 leaf 数十 GB/s 单向/口 同 rail 的所有节点
spine（跨 rail） leaf–spine–leaf 受收敛比打折 全集群跨 rail 流量

NVIDIA 的 DGX SuperPOD 参考架构写得很直白：每 32 节点一组 rail-aligned，同一 rail 到其它 31 个节点的流量永远只有一跳，而节点间或 rail 间的流量要经过 spine 层。这就是本课的全部物理前提。

2. rail-optimized 是什么#

定义：机内槽位 i 的 GPU 通过自己的 NIC 接到第 i 条 rail 的 leaf；因此"所有节点的第 i 号卡"共享同一条 rail。8 卡机就有 8 条 rail，每条一台（或一对）leaf。

三个直接后果：

  • 同号卡通信只过 leaf：节点a.卡i ↔ 节点b.卡i 不需要看到 spine。
  • 跨号卡通信必须过 spine：卡i → 卡j (i≠j) 是 leaf(i)–spine–leaf(j)，跳数与延迟都增加。
  • spine 是共享资源：多条跨 rail 流一起排队，收敛比大于 1 时有效带宽按比例下降。

所以"拓扑感知"不是玄学，它只有一句话：尽量让通信发生在同号卡之间。

3. 环的排法决定一切#

ring AllReduce 每一步里环上所有边同时传输，所以步时间 = 最慢那条环边的时间，总时间 = 2(p−1)×步时间——环边经过哪些设备直接决定总时间。三种排法：

排法 跨越点落在哪 跨 rail 环边数 spine 流量（8 节点 × 8 卡，1 GiB）
naive（节点顺序） 每节点末尾接下一节点开头 → 卡7→卡0 8 16128 MiB
aligned（节点交替反向） 两个跨越点落在同一条 rail 上 0 0 MiB
interleaved（rail 交错） 每个跨越点都换 rail 8（另有 56 条同 rail） 16128 MiB

aligned 的做法只有一句：偶数号节点按 0→7 排、奇数号节点按 7→0 排，于是出、回两条跨越边的两端同号——跨越点自动对齐到 rail。示例 1 的模拟结果：

排法 2 节点 × 8 卡 8 节点 × 8 卡
naive 121.10 ms 128.10 ms
aligned 40.45 ms 43.03 ms
interleaved 121.10 ms 128.10 ms

4. 跨域为何骤降：两个乘数相乘#

跨 rail 的代价由两项相乘：

  • 跳数：同 rail 一跳，跨 rail leaf→spine→leaf；延迟项从 α 涨到 α′；
  • 收敛比：spine 上行被多条 rail 共享。示例取 3:1，则跨 rail 的有效带宽从 50 GB/s 降到 16.7 GB/s，即每条跨 rail 环边的带宽项扩大到 3 倍。

两者叠加：以 2 节点 × 8 卡、每步每条环边 64 MiB 为例，同 rail 环边 6+50GB/s64MiB​≈1.35 ms，跨 rail 环边 10+16.7GB/s64MiB​≈4.04 ms；整步时间由这条最慢边决定（30 步合计 40.45 ms vs 121.10 ms）。naive 与 interleaved 的差别则在 spine 总流量（都过 spine，叠加程度不同）——spine 流量就是拥塞风险的账本。

示例模型按"每条环边独立"计算，是下界：未计多条流在 spine 上的排队，真实差距通常更大。

5. NCCL 在工程上怎么做#

NCCL 自己会探测拓扑并挑选路径，需要知道的开关有：

  • NCCL_CROSS_NIC：0＝同一 ring/tree 固定用同一块 NIC，避免跨 rail（官方建议用于"每 NIC 一台 leaf、rail 间连接慢"的网络）；1 允许换 NIC；2（默认）尽量同 NIC、必要时才换。
  • NCCL_NET_MERGE_POLICY=RAIL：rail-optimized 系统专用——按 rail 合并多口网卡，避免把不同 rail 的设备合成一个；NCCL_IB_HCA 还支持 <hca>:<port>:<rail>:<plane>，可手工标注 rail/plane 身份。
  • NCCL_TOPO_FILE / NCCL_TOPO_DUMP_FILE：导入/导出拓扑 XML。官方提醒：多节点 NVLink 系统导出的 XML 含整个 NVLink 域，但回填 NCCL_TOPO_FILE 时只应写单节点拓扑。
  • 算法层面：两级算法先在节点内用 NVLink 合并，再让节点代表走同 rail 的 NIC——"把跨域通信压到最少"的通用配方。

6. 常见坑#

  • 把"同 rail"当成"相邻 rank"：同号卡才是同 rail；按 rank 顺序排环，跨越点常落在不同号卡上。
  • 只调算法不管 rank 顺序：同样的 ring，排法不同差 3 倍。
  • 手写 NCCL_TOPO_FILE 出错：多节点 NVLink 系统只写单节点拓扑；写错会让 NCCL 按错误距离决策，带宽莫名不达标。
  • 忽略收敛比：账上"每口 400 Gb/s"要乘 spine 的实际收敛比，才是跨 rail 的可用带宽。

7. 这一课到哪里为止#

现在你有了三层带宽与"跨域更贵"的结论。把它放回训练循环，就能回答最后一个问题：为什么加卡不是线性加速——下一课给出带宽、延迟、同步三本账。

二、可运行代码示例#

示例 1 把 rail-optimized 拓扑抽象成"边分类器"，对三种 rank 排法做账本审计：每条环边的类别、spine 上要搬多少字节、按 α-β 模型预测的时间。纯标准库。

# ===== 示例 1：rail-optimized 拓扑上，rank 的排法决定通信走不走 spine =====
GPUS = 8


def edge_class(a, b):
    """a、b 是 (节点号, 卡号)。返回 (类别, α_μs, β_GB/s)。
    节点内走 NVSwitch；跨节点同号卡走本 rail 的 leaf（一跳）；跨节点不同号卡必须过 spine。"""
    (na, ga), (nb, gb) = a, b
    if na == nb:
        return "节点内 NVLink", 2.0, 450.0
    if ga == gb:
        return "跨机 同 rail", 6.0, 50.0
    return "跨机 跨 rail", 10.0, 50.0 / 3.0        # spine 3:1 收敛，有效带宽降到 1/3


def ring_orders(nodes):
    """三种排法：naive=节点顺序；aligned=每节点交替方向，让两个跨越点落在同一条 rail；
    interleaved=按 rail 交错（同 rail 的卡挨着，但每个跨越点都换 rail）。"""
    naive = [(n, g) for n in range(nodes) for g in range(GPUS)]
    aligned = []
    for n in range(nodes):
        gs = range(GPUS) if n % 2 == 0 else range(GPUS - 1, -1, -1)
        aligned += [(n, g) for g in gs]
    interleaved = [(n, g) for g in range(GPUS) for n in range(nodes)]
    return {"naive": naive, "aligned": aligned, "interleaved": interleaved}


def audit(order, grad_mib=1024.0):
    """按 ring AllReduce 的账本统计：每条环节点的类别、spine 上要搬多少字节、总时间。"""
    P = len(order)
    s = grad_mib * 2**20 / P                     # 每步每条环边的消息字节数
    edges = [edge_class(order[i], order[(i + 1) % P]) for i in range(P)]
    cross = [e for e in edges if e[0] == "跨机 跨 rail"]
    step_us = max(a + s / (b * 1e9) * 1e6 for _, a, b in edges)   # 每步所有环边同时动，取最慢边
    spine_bytes = len(cross) * 2 * (P - 1) * s
    kinds = {k: sum(1 for e in edges if e[0] == k) for k in
             ("节点内 NVLink", "跨机 同 rail", "跨机 跨 rail")}
    return kinds, spine_bytes, 2 * (P - 1) * step_us / 1e3


for nodes in (2, 8):
    P = nodes * GPUS
    print(f"\n{nodes} 节点 × {GPUS} 卡 = {P} rank，1 GiB 梯度，每步消息 {1024 / P:.2f} MiB：")
    for name, order in ring_orders(nodes).items():
        kinds, spine, ms = audit(order)
        print(f"  {name:<12} 环边={kinds}  spine 流量={spine / 2**20:9.1f} MiB"
              f"  预测时间={ms:8.2f} ms")

三、练习#

  1. 实现：把 ring_orders 扩到 N 个节点、每节点 4 卡，再写一个通用的 aligned 构造（提示：让跨越点落在两端节点同号的那条 rail 上），再用 audit 验证跨 rail 环边数为 0。
  2. 解释：为什么 ring 的步时间取"最慢环边"而不是"所有环边之和"？请用"所有环边同时传输"这个事实说明。
  3. 对比/验证：把 edge_class 里 spine 的 3:1 改成 1:1（不收敛），重跑示例 1；再解释为什么真实集群会主动选择收敛比 > 1 的设计。
  4. 思考：如果训练用的是张量并行（TP），你会把它放在节点内、同 rail，还是跨 rail？请从"每步通信量"与"每步延迟次数"两个角度各给一条理由。
