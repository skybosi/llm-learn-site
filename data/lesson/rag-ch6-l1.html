离线索引流水线：增量更新、版本与回滚#

这一节要解决什么#

前面五章都在回答"给定一份索引，怎么把一次问答做到最好"。但从这一节开始，问题变成：

这份索引本身会变 —— 文档新增、修改、删除，切分策略要调，嵌入模型要升级。每一次变化都要在不打断线上服务的前提下生效，并且出错能退回去。

这件事在倒排索引里是日常（倒排表本来就是增量可写的），在向量索引里却很难，原因有三层：

  1. 结构性：HNSW 类图索引的删除会破坏连通性，增量插入会让"小世界"性质缓慢退化（第 2 章第 4 节已经算过代价）；
  2. 一致性：嵌入模型的版本一变，所有向量都必须重算 —— 新旧向量在同一空间里不可比；
  3. 可运维性：线上正在被查询的索引不能被原地改坏，必须有版本、有指针、有回滚。

本节要回答四个问题：

  1. 有哪几类变更？各自的代价如何量化？哪些能增量、哪些必须全量？
  2. 为什么"段式不可变索引"（LSM 风格）是这一层的正确抽象？墓碑与压实的代价怎么算？
  3. 什么让一次重建是可复现的？chunk id 为什么必须内容寻址？
  4. 发布与回滚怎么做？"什么时候该全量重建"能不能给一个可执行的阈值？

结论先放在这里：索引不是"一个文件"，而是一组不可变的段 + 一个原子切换的 manifest 指针。所有更新都是"写新段 + 打墓碑"，删除不是删除而是墓碑，查询时过滤；一致性靠指针切换而不是原地修改；回滚就是把指针切回去。而"该不该全量重建"有一条可算的阈值：当每日变更率超过单位成本之比 cfull​/cinc​ 时，全量更便宜（⚠️ 示例：理论阈值 0.72，含压实开销后实测交叉点 0.4）。

一、变更的类型与代价#

1.1 五类变更#

变更类型 例子 能否增量 代价构成
新增文档 新上传一篇 PDF 能 解析 + 切分 + 嵌入 + 写入新段
修改文档 某篇被编辑 能（墓碑旧版 + 新段） 同上 + 墓碑
删除文档 权限撤销 / 过期 能（墓碑） 几乎为零，但留下空间放大
重嵌入 换 embedding 模型 不能（全量） N 次嵌入 + 全量重建
切分策略变更 chunk 大小/重叠调整 不能（全量） 重新切分 + 重嵌入 + 重建

这里有一条容易忽略的规则：

chunk id 必须包含"决定它的所有版本号"。 切分策略变了 → 同一段文字会切出不同的 span → chunk 边界全变；嵌入模型变了 → 同一 chunk 的向量在新空间里不可比。这两类变更都不能"部分更新"，必须整体重建，否则索引里会同时存在两个不可比的空间。

1.2 更新代价为什么不能按"变更比例"线性估#

直觉是"改了 1% 的文档，就只花 1% 的重建代价"。这个直觉在每单位成本相同时成立，但真实系统里增量更新的单位成本更高，原因有三：

  1. 批处理效率低：全量重建可以大批量顺序写、批量嵌入；增量更新是零散的小写入，GPU 利用率低、I/O 是小随机写。
  2. 查询放大：每次增量写入产生一个新段，查询要扫更多段（见 §2.3）。
  3. 压实开销：段多了必须合并，合并本身要重写存活数据。

把这三项放进模型：设每次全量重建的单位成本 cfull​、增量的单位成本 cinc​，且 cinc​>cfull​（因为批处理优势），则每日变更比例 δ 下的成本比较是：

增量/天cinc​⋅δN​​vs全量/天cfull​⋅N​​

解得阈值：

δ∗=cinc​cfull​​

δ∗=cinc​cfull​​

  • δ<δ∗：增量便宜，做增量；
  • δ>δ∗：全量重建更便宜 —— 这反直觉但正确：变更太多时，"零散的逐篇更新"比"一次整齐的全量"更贵。

⚠️ 示例（cinc​=1.0、cfull​=0.72、N=1200、30 天、含压实）：理论 δ∗=0.72，但含压实开销后实测交叉点在 0.4 —— 因为压实把增量路径的额外成本又抬高了一截。这说明阈值必须实测，不能只算理论比值。

二、段式不可变索引#

2.1 结构#

把索引组织成一组不可变的段（segment），与 LSM-Tree 的 memtable/sstable 思路同构：

写入:  新文档/更新 -> 生成新段（append-only）
删除:  在旧段上打 tombstone（不改数据）
查询:  并行搜所有活跃段 -> 过滤 tombstone -> 归并 top-k
压实:  段数/墓碑超限 -> 合并为一个只含存活 chunk 的新段
发布:  manifest 指针原子切换 -> 新段集合生效

为什么不可变是对的抽象：

  • 并发安全：读操作永远看到一致的段集合（只需保证指针读取与段列表一致）；写操作只追加，不需要锁；
  • 回滚免费：旧段只要没被删除就还在，"回滚"只是把指针指回去；
  • 增量与全量统一：全量重建 = 写一个大段；增量 = 写一个小段。同一条代码路径。

2.2 墓碑的代价：召回损失与空间放大#

墓碑（tombstone）不是免费的。设某段的墓碑比例为 τ，要返回 top-k 条存活结果，从该段至少要取回：

kraw​≈1−τk​

因为墓碑也占名额。若段内过滤是在"取出 top-k 之后"做的，实际召回会下降；正确做法是先过滤再排名（或取 k/(1−τ) 再过滤）。

空间放大定义为：

amp=存活 chunk 数存储的 chunk 总数​=1−τ1​

⚠️ 示例：更新 10 篇后 τ=0.143（放大 1.17），删除 5 篇后 τ=0.214（放大 1.27）。删除只增空间不减空间，直到压实。

2.3 压实：触发条件与收益#

压实把一个或多个段合并为一个只含存活数据的新段。触发条件（任一满足）：

触发条件 阈值（示例） 理由
段数超限 >8 查询代价 ≈a+b⋅S，段数直接乘在每查询开销上
墓碑比例超限 >20% 召回损失与空间放大同时上升
定期（低峰） 每天/每周 合并碎片、回收空间
索引版本变更 重建时 顺便统一版本

查询代价的段数依赖可以量化为每查询

tquery​(S)≈a+b⋅S

在 ANN 里 a 是单段的图下降与候选展开，b 是每段的固定开销（打开、初始化、归并）。⚠️ 示例模型 a=20,b=3（任意单位）：

段数 S 1 2 4 8 16 32 64
单查询代价 23 26 32 44 68 116 212
相对单段 1.00 1.13 1.39 1.91 2.96 5.04 9.22

所以"段数上限"不是审美要求，而是延迟预算要求：S≤8 把查询代价限制在单段的 1.91 倍以内。

2.4 边界#

  • 段式结构的代价是读放大（每次查询要扫多个段）与空间放大（墓碑）。二者的平衡点由 Smax​ 与 τmax​ 决定。
  • 墓碑必须在所有查询路径上生效（包括缓存、评测、导出），否则会出现"删了还能查到"的隐蔽 bug —— 这是第 3 节权限泄漏的一条路径。
  • 压实需要额外存储（新旧段并存一段时间），峰值空间是稳态的约 2 倍。

三、内容寻址、manifest 与可复现性#

3.1 chunk id 必须内容寻址#

chunk_id=hash(doc_id∥doc_version∥span∥chunker_ver∥embedder_ver)

这个定义带来三个直接性质：

  1. 幂等：相同的输入必然产生相同的 id。重跑一次流水线不会产生"新"chunk，因此不会重复写入、不会让缓存失效。
  2. 可追踪：从引用（citation）里的 chunk_id 能反推出文档、版本、位置与两个算法版本 —— 这是第 4 节审计与第 6.4 节可观测性的基础。
  3. 变更可见：换 embedder 会让 id 全变（⚠️ 示例：6af1c5701d85d550 → e4d9be395419f1bc），因此所有依赖 id 的东西自动失效 —— 缓存、引用、评测集里的黄金证据标注。这是好事：它把"版本不一致"从一个隐蔽 bug 变成一次显式的全量失效。

反例：如果 chunk_id 用自增序号或随机 uuid，那么"重跑一次流水线"就会让所有引用失效、让缓存全部 miss、让评测集对不上。这是最常见也最贵的可复现性事故。

3.2 manifest：版本的载体#

manifest 是"当前生效的索引状态"的完整描述：

{
  "manifest_id": "...",
  "segments": [{"sid": 12, "chunks": 216, "bytes": 0}],
  "embedder": "emb-v2",
  "chunker": "chk-v1",
  "doc_hashes": {"doc0": "sha1:...", "...": "..."},
  "counts": {"docs": 55, "chunks": 216, "tomb": 0.0},
  "created_at": "..."
}

要点：

  • manifest 不包含向量本体，它只是一个指针集合 + 版本信息，因此很小、可以快速读取与切换；
  • doc_hashes 是增量的依据：只有 hash 变化的文档才需要重新处理（内容寻址的第二层应用）；
  • counts 与 tomb 是压实触发器与告警的输入。

3.3 幂等与可复现#

判据：给定同一份文档集合与同一组算法版本，重跑流水线应当得到逐字节相同的 manifest（除了时间戳）。实现要点：

  • 段内 chunk 的排序稳定（按 chunk_id 排序，而不是按插入顺序）；
  • 浮点嵌入的确定性（同一硬件、同一 kernel、同一精度下可复现；跨硬件可能不可复现，需记录）；
  • 不把"当前时间""随机 id""进程号"写进影响 id 的字段。

四、发布、回滚与重建触发#

4.1 蓝绿与指针切换#

         ┌──────────┐   atomically swap   ┌──────────┐
线上查询 ─┤ manifest ├────────────────────┤ 新 manifest │
         └────┬─────┘                     └────┬─────┘
              │                                │
        旧段集合（保留）                   新段集合（已就绪）

切换必须是原子的：查询要么看到旧 manifest，要么看到新 manifest，不能看到"一半新一半旧"。实践中用"读别名 → 解析到 manifest_id → 用该 id 的段列表查询"实现。

双写/影子期：新索引就绪后，可先让一小部分流量（或离线评测）走新索引，对比指标后才全量切换。

4.2 一致性窗口#

在"新段已写入但 manifest 尚未切换"的窗口里：

  • 新写入的文档查不到（因为指针还是旧的）—— 这是一致性窗口；
  • 处理方式：要么接受"延迟可见"（明确 SLA，例如"文档上传后 5 分钟内可检索"），要么在写路径上"双读"（查询时同时读新旧段并去重），代价是复杂度与延迟。

必须显式定义这个窗口，否则"刚上传的文档搜不到"会被当成 bug 反复排查。

4.3 回滚：RTO 与 RPO#

概念 定义 段式索引下的值
RTO（恢复时间目标） 从发现故障到恢复服务的时长 ≈ 指针切换时间（秒级），前提是旧段保留
RPO（恢复点目标） 允许丢失多少更新 = 旧 manifest 之后的所有更新

代价：旧段必须保留 → 存储翻倍（或按保留代数计算）。这是"回滚能力"的明码标价。

4.4 重建触发规则（可执行）#

触发条件 动作 预期耗时
embedder / chunker 版本变更 全量重建 O(N) 嵌入 + 写入
每日变更率 δ>δ∗（实测 0.4 量级） 全量重建 O(N)
段数 S>Smax​（示例 8） 压实 O(存活 chunk)
墓碑比例 τ>τmax​（示例 0.2） 压实 同上
线上召回监控跌破基线（例如 −3%） 先回滚，再排查后重建 切换秒级
距上次全量重建超过 T 天 全量重建（防漂移累积） O(N)

最后一行容易被忽略：即使所有增量都正确，长期的"切分边界漂移 + 小世界退化"也会让索引质量缓慢下降。定期全量重建是一种"重置漂移"的手段，不是浪费。

代码#

一个最小但完整的段式索引：内容寻址 id、墓碑、压实、全量重嵌入、manifest、回滚断言，以及"增量 vs 全量"的成本扫描。

# -*- coding: utf-8 -*-
"""⚠️ 合成数据：段式不可变索引 —— 增量更新 / 墓碑 / 压实 / manifest / 回滚 + 重建成本交叉。
   嵌入用 hashing-trick 代理（不是真实双塔），只为让索引机制可见。"""
import hashlib, numpy as np

DIM = 32
def _h(s):
    """稳定整数哈希：不用内置 hash()（按进程加盐，会破坏可复现性）。"""
    return int(hashlib.md5(s.encode()).hexdigest()[:8], 16)

def embed(text, embedder_ver, seed=0):
    r = np.random.default_rng(_h(f"{seed}|{embedder_ver}") % (2**32))
    P = r.normal(0, 1, (256, DIM)); v = np.zeros(DIM)
    for w in text.lower().split(): v += P[_h(w) % 256]
    n = np.linalg.norm(v); return v / n if n else v

def chunk_id(doc_id, ver, span, chunker_ver, embedder_ver):
    raw = f"{doc_id}|{ver}|{span}|{chunker_ver}|{embedder_ver}"
    return hashlib.sha1(raw.encode()).hexdigest()[:16]

class Segment:
    """不可变段：写入后不再修改（LSM 风格）。"""
    _seq = 0
    def __init__(self):
        Segment._seq += 1; self.sid = Segment._seq; self.items, self.tomb = {}, set()
    def put(self, cid, vec, meta): self.items[cid] = (vec, *meta)
    def kill(self, cid):
        if cid in self.items: self.tomb.add(cid)
    def live(self): return {c: v for c, v in self.items.items() if c not in self.tomb}

class IndexManager:
    def __init__(self):
        self.embedder_ver, self.chunker_ver = "emb-v1", "chk-v1"
        self.segments, self.doc_chunks, self.doc_text = [], {}, {}
    def _write_doc(self, doc_id, ver, text):
        s = Segment(); self.segments.append(s); cids = []; words = text.split()
        for i in range(0, max(1, len(words)), 6):          # 定长窗口切分
            span = (i, min(i + 6, len(words)))
            cid = chunk_id(doc_id, ver, span, self.chunker_ver, self.embedder_ver)
            txt = " ".join(words[span[0]:span[1]])
            s.put(cid, embed(txt, self.embedder_ver), (doc_id, ver, span, txt))
            cids.append(cid)
        self.doc_chunks.setdefault(doc_id, {})[ver] = cids
        self.doc_text[doc_id] = text
    def upsert(self, doc_id, text, ver=None):
        old = self.doc_chunks.get(doc_id, {})
        new_ver = ver if ver is not None else (max(old) + 1 if old else 1)
        for v, cids in old.items():                        # 旧版本全部打墓碑
            for s in self.segments:
                for c in cids: s.kill(c)
        self._write_doc(doc_id, new_ver, text)
    def delete(self, doc_id):
        for v, cids in self.doc_chunks.get(doc_id, {}).items():
            for s in self.segments:
                for c in cids: s.kill(c)
        self.doc_chunks.pop(doc_id, None); self.doc_text.pop(doc_id, None)
    def compact(self):
        s = Segment()
        for seg in self.segments[:-1]:
            for c, v in seg.live().items(): s.items.setdefault(c, v)
        self.segments = [s]
    def reembed_all(self, new_ver):
        """换 embedder：必须全量重嵌入（chunk_id 含 embedder_ver，也会全变）。"""
        docs = dict(self.doc_text); vers = {d: max(self.doc_chunks[d]) for d in docs}
        self.embedder_ver = new_ver; self.segments, self.doc_chunks = [], {}
        for d, t in docs.items(): self._write_doc(d, vers[d], t)
    def search(self, q, k=10):
        qv = embed(q, self.embedder_ver); hits = []
        for seg in self.segments:
            for c, v in seg.live().items():
                hits.append((float(np.dot(qv, v[0])), c, v[4]))
        hits.sort(reverse=True); return hits[:k]
    def stats(self):
        live = sum(len(s.live()) for s in self.segments)
        total = sum(len(s.items) for s in self.segments)
        return dict(segments=len(self.segments), live=live, total=total,
                    tomb=round((total - live) / total, 3) if total else 0,
                    disk_amp=round(total / live, 2) if live else 0)

rng = np.random.default_rng(0); VOCAB = [f"w{i}" for i in range(120)]
def rand_text(n=24): return " ".join(rng.choice(VOCAB, n))

idx = IndexManager()
for d in range(60): idx.upsert(f"doc{d}", rand_text())
print("== 时间线（段式索引）==")
print(f"插入 60 篇           : {idx.stats()}")
for d in range(10): idx.upsert(f"doc{d}", rand_text())
print(f"更新 10 篇           : {idx.stats()}")
for d in range(5): idx.delete(f"doc{d}")
print(f"删除 5 篇            : {idx.stats()}")
idx.compact(); print(f"压实后               : {idx.stats()}")
snap_old = idx.search(" ".join(VOCAB[:6]), k=10)

snapshot = [(s.sid, dict(s.items), set(s.tomb)) for s in idx.segments]   # 发布前存快照
idx.reembed_all("emb-v2")                                               # 换 embedder（全量重嵌）
snap_new = idx.search(" ".join(VOCAB[:6]), k=10)
print(f"换 embedder 全量重嵌  : {idx.stats()}")
print(f"新版本 top1 = {snap_new[0][2][:26]}...")
print(f"旧版本 top1 = {snap_old[0][2][:26]}...")
idx.segments = []
for sid, items, tomb in snapshot:                    # 回滚 = 指针切回旧段快照
    s = Segment(); s.sid = sid; s.items = dict(items); s.tomb = set(tomb); idx.segments.append(s)
idx.embedder_ver = "emb-v1"
print(f"回滚断言（与旧结果逐条相等）: {idx.search(' '.join(VOCAB[:6]), k=10) == snap_old}")
print("chunk_id 随 embedder 版本变化: ",
      chunk_id("doc0", 1, (0, 6), "chk-v1", "emb-v1"), "->",
      chunk_id("doc0", 1, (0, 6), "chk-v1", "emb-v2"), "（id 变了，缓存/引用随之失效）")

print("\n== (a) 重建成本：增量 vs 全量（每日变更率 delta）==")
N, D, C_INC, C_FULL, C_COMPACT, SMAX = 1200, 30, 1.0, 0.72, 0.35, 8
print("  说明：增量按篇处理、批处理效率低 -> 单位成本 1.0；全量可批量化 -> 0.72")
print(f"{'delta':>7} {'增量总成本':>12} {'全量总成本':>12} {'更优':>6} {'平均段数':>9}")
cross = None
for delta in (0.01, 0.05, 0.1, 0.2, 0.4, 0.6, 0.72, 0.8, 1.0):
    inc, nseg, seg_hist = 0.0, 1, []
    for _ in range(D):
        inc += C_INC * delta * N
        nseg += max(1, int(delta * N / 6))            # 简化：新增段数随变更量增长
        if nseg > SMAX: inc += C_COMPACT * N; nseg = 1
        seg_hist.append(nseg)
    full = D * C_FULL * N
    who = "增量" if inc < full else "全量"
    if cross is None and inc >= full: cross = delta
    print(f"{delta:>7.2f} {inc:>12.0f} {full:>12.0f} {who:>6} {np.mean(seg_hist):>9.1f}")
print(f"理论阈值 delta* = c_full / c_inc = {C_FULL/C_INC:.2f}；含压实后实测交叉点 ≈ {cross}")

关键设计决策：把删除实现成墓碑而不是物理删除，是这份代码里最重要的选择。物理删除会带来三个连锁问题：(1) 段变成可变对象，破坏并发安全；(2) 回滚不再可能（数据已经没了）；(3) 图索引的连通性被破坏。改用墓碑后，"删除"退化成一次集合写入，代价被推迟到压实 —— 这就是 LSM 的核心思想：把随机写变成顺序写，把一致性交给不可变性。 代价是查询时必须过滤（读放大）与空间放大，两者都有明确的可调阈值。

练习#

  1. 墓碑召回损失的精确推导。设在某段内墓碑比例 τ、段内 chunk 按相关度排序无关（随机），要返回 k 条存活结果。证明：若只取 top-k 再过滤，期望存活数约为 k(1−τ)；并推导"取 k/(1−τ) 再过滤"使存活数达到 k 的概率。用模拟验证两个公式。

  2. 压实策略比较。实现三种压实触发：(a) 段数超限即全合并；(b) 分层压实（小段合并成大段，模仿 leveled compaction）；(c) 定时压实。在"每天 δ=0.05 变更、持续 90 天"的仿真里比较三种策略的总写入量、平均段数、P95 查询代价。给出你的推荐及理由。

  3. 证明幂等性并构造反例。证明 §3.1 的 chunk_id 定义下"重跑流水线"是幂等的；然后构造一个不幂等的 id 方案（例如含时间戳或自增序号），并说明它会造成哪三类事故（提示：缓存、引用、评测集黄金证据）。

  4. 回滚的存储代价。设每天全量重建一次、保留 g 代 manifest 供回滚。推导存储放大随 g 的表达式；给定存储预算 B 与单份索引大小 S，求最大 g。再回答：如果改为"只保留 1 代 + 每日增量备份"，RTO/RPO 各变成多少？

  5. 一致性窗口的 SLA 设计。设文档上传到可检索的延迟目标为 T。比较两种实现：(a) 定时批量切换 manifest（每 T 切换一次）；(b) 每次写入立即切换。分别计算切换次数（每天）、平均可见延迟、以及切换失败的爆炸半径。给出在什么规模下选 (a)、什么规模下选 (b)。

  6. δ∗ 的敏感性。用代码里的成本模型，扫描 cinc​/cfull​∈{1.1,1.4,2.0,3.0} 与 Smax​∈{2,8,32}，输出各自的实测交叉点 δ∗。回答：压实阈值 Smax​ 越大，δ∗ 往哪个方向移动？为什么？

  7. 段数上限与延迟预算的联立。给定 P95 延迟预算 L、单段查询耗时 a、每段开销 b、以及"段数超限时需要压实（一次压实约耗时 Tc​）"。推导最大段数 Smax​ 并说明它如何与"每日变更率"共同决定压实频率。

  8. 给一个真实系统设计索引发布流程。写出从"文档上传"到"线上可检索"的完整状态机（含：解析失败、切分失败、嵌入超时、manifest 切换失败、回滚触发），标注每个状态的可观测信号与超时阈值。这份状态机就是第 4 节要讲的可观测性的一部分。

小结#

  • 五类变更，两类必须全量：新增/修改/删除可增量；换 embedder、换切分策略必须全量，因为 chunk 边界与向量空间都变了。
  • 段式不可变索引是这一层的正确抽象：写新段 + 打墓碑 + 指针切换 + 压实。它同时给出并发安全、回滚能力、以及"增量与全量同一条代码路径"。
  • 墓碑有代价且可算：要返回 k 条存活结果需取回约 k/(1−τ)；空间放大 =1/(1−τ)。⚠️ 示例：更新 10 篇后 τ=0.143、删除 5 篇后 τ=0.214（放大 1.27），删除只增空间不减空间。
  • 查询代价随段数线性增长（a+bS）：⚠️ 示例 S 从 1 到 8 使单查询代价从 23 涨到 44（1.91 倍），到 64 则 9.22 倍。Smax​ 是延迟预算决定的，不是审美。
  • 全量重建的阈值可算：δ∗=cfull​/cinc​；⚠️ 示例理论值 0.72，含压实后实测 0.4。超过它，全量更便宜 —— 因为增量的单位成本更高（批处理效率低 + 查询放大 + 压实）。
  • chunk id 必须内容寻址，且含 chunker_ver 与 embedder_ver。它同时给出幂等、可追踪、以及"版本变更时自动全量失效"。⚠️ 示例 id 从 6af1c5701d85d550 变成 e4d9be395419f1bc。
  • manifest 是版本的载体：段列表 + 算法版本 + 文档哈希 + 计数。指针切换必须原子；回滚 = 指针切回，RTO 秒级、RPO = 旧 manifest 之后的更新。
  • 一致性窗口要显式定义（"文档上传后 N 分钟可检索"），否则"刚上传搜不到"会被当成 bug 反复排查。
  • 重建触发规则：版本变更 → 全量；δ>δ∗ → 全量；段数/墓碑超限 → 压实；召回跌破基线 → 先回滚；超过 T 天 → 定期全量重置漂移。
  • 一句话：索引不是一个文件，而是"一组不可变段 + 一个可原子切换的指针"。把更新变成追加、把删除变成墓碑、把发布变成换指针、把回滚变成换回来 —— 索引运维就从"危险的原地修改"变成了"可预测的状态机"。
