工具即接口：schema 设计、参数语义与限制的表达#

这一节要解决什么#

把工具当成"一个函数 + 一段 JSON Schema"来写，是这一章所有事故的起点。

一个工具对 Agent 而言不是函数，而是三个东西的合成体：

工具 = 能力声明（description：这个世界能做什么）
     + 调用协议（schema：怎么调用它，什么算合法调用）
     + 结果语义（返回值里哪个字段表示什么状态的什么事实）

模型能看到的只有这三者的文字形式。它看不到实现、看不到数据库表结构、看不到权限表、看不到上次调用是在哪个租户下发生的。于是有一个必须记住的推论：

模型的行为=f(契约面所表达的信息)+模型从训练分布带来的先验

当契约面没写清楚时，先验会替它做决定 —— 而先验是"互联网上代码的平均习惯"，不是你的系统语义。这就是为什么"参数语义"不是文档问题而是能力边界问题。

这一节的三个目标：

  1. 把工具设计从"写 schema"提升到"设计接口面"：粒度、可选性、限制、错误语义四个维度。
  2. 说清 schema 能表达什么、不能表达什么 —— 边界之外的部分必须用别的手段补（运行时校验、描述文字、工具拆分）。
  3. 给出可执行的契约审查清单：一组能在 review 阶段机械检查出来的设计缺陷。

学完这一节你应该能回答：

  • 一个"既能读又能写"的工具，为什么通常应该拆成两个？什么时候不该拆？
  • limit: integer 与 limit: integer, minimum: 1, maximum: 100, default: 20 对模型的差别有多大？为什么"默认值"是契约的一部分而不是实现的细节？
  • 两个参数语义上互斥（query 与 doc_id），schema 该怎么表达？表达不了的后果是什么？
  • 为什么"返回一个字符串"是最贵的接口设计？结构化返回的收益在哪里出现？

一、契约面是 Agent 唯一的接口面#

1.1 与 RPC / 系统调用的同构与差别#

工具契约与传统接口设计高度同构 —— 同样的粒度问题、同样的版本问题、同样的默认值问题。但有三处关键差别，它们决定了不能照搬：

维度 传统 RPC Agent 工具
调用方 程序员（读文档、可调试） 模型（只读描述、不试错成本敏感）
参数来源 编译期/运行期确定的代码 生成式采样（可能造出从未存在的参数）
错误处理 异常向上传播，由代码分支处理 错误变成文本回到上下文，影响后续所有决策
约束表达 类型系统 + 运行时校验 + 文档 只有 schema + description（弱表达力）
变更代价 改调用方代码 改模型行为，需重跑评测集

第三条最容易被低估：在传统系统里错误是控制流，在 Agent 里错误是输入。 一个 500 错误在传统系统里让一个函数返回失败；在 Agent 里它会改变模型接下来的十几步行为（可能让它"学会"绕开这个工具，或者开始编造结果）。

1.2 描述文本的注意力位置#

工具描述不是均匀生效的。它同时出现在两个位置，作用不同：

  • 工具选择时：所有工具的 name + description 一起出现在候选列表里，模型在这里决定"用哪个"。此时描述的作用是区分度。
  • 参数生成时：被选中工具的 schema 被展开，模型在这里决定"填什么"。此时描述的作用是约束传递。

这两个位置对描述的要求是冲突的：为了区分度，描述要强调"这个工具与那个工具的不同"；为了约束传递，描述要强调"参数边界与前置条件"。把两件事塞进同一段文字，是描述写不好的主要原因。

实用做法：把 description 写成两段 —— 第一句写何时用/何时不用（区分度），中间写参数语义与前置条件（约束传递），末尾写返回什么（结果语义）：

search_docs(query, limit, cursor)
  何时用：需要从内部知识库检索事实时。不用于查实时价格（用 fetch_price）。
  约束：query 必须是自然语言问句，不是关键词串；库内只覆盖 2023 年后的内部文档。
  返回：{items: [{doc_id, title, snippet, score}], next_cursor}。score 是相对分，不可跨查询比较。

最后一句（"score 不可跨查询比较"）是典型的必须写在契约里、schema 完全表达不了的信息。不写，模型就会拿两次调用的 score 做阈值判断。

二、粒度：原子工具、复合工具与"事务边界"#

2.1 粒度问题的真实形态#

"工具该切多细"不是风格问题，而是权限、幂等与回退粒度的交叉点：

粒度 例子 优点 代价
原子（单资源单动作） get_user, set_user_email 权限可精确到动作；幂等易实现；回退粒度细 工具数量膨胀（选择变难，见第 4 节）；模型要自己组合多步
复合（一个意图一个工具） update_user_profile 工具数少、选择简单；一次调用完成一个意图 内部有多个副作用 → 幂等与补偿复杂；权限粗；部分成功难表达
通用逃逸舱 run_sql, run_shell 表达力无限 权限无法约束；幂等无法保证；注入面巨大

设计准则（按优先级）：

  1. 副作用边界就是工具边界。如果一个工具内部会对两个独立资源做写操作，它就必须要么是原子的（有事务），要么必须支持"按子步骤报告部分成功"。否则模型无法知道"付了钱但没发货"这种状态。
  2. 读与写分开。search_then_update 这类工具会让幂等设计无从下手：读的部分可以重试，写的部分不能。分成两个工具后，读可以自由重试、写单独走幂等通道。
  3. 默认不给逃逸舱。run_sql / run_shell 应当是受限沙箱里的最后手段（第 7 章展开），且应提供"只读"与"只写指定表"的裁剪版本，而不是一个万能口子。

2.2 复合工具的正确形态：显式事务语义#

必须提供复合工具时，正确做法是把事务语义写进契约，而不是让模型猜：

{
  "name": "transfer_funds",
  "description": "在同一租户内转账。★ 本操作是原子的：要么整体成功，要么整体不生效。返回值 transaction_id 在 24 小时内可用于幂等重放（见 idempotency_key 参数）。",
  "parameters": {
    "idempotency_key": {"type": "string", "description": "调用方生成的唯一键；相同键重复调用不会重复转账"},
    "from_account": {"type": "string"},
    "to_account": {"type": "string"},
    "amount_cents": {"type": "integer", "minimum": 1}
  }
}

注意这段描述回答了三个模型自己问不出来的问题：这个操作是不是原子的？重复调用会怎样？我怎么撤销/核对？契约的完备性就是由这类问题定义的。 下面给一个检查表。

2.3 契约完备性检查表#

对每个工具，逐条回答；答不上来的条目就是设计缺陷：

# 问题 表达位置
1 这个工具会改变世界吗？（只读 / 可逆写 / 不可逆写） description + 权限声明
2 重复调用一次会怎样？（幂等 / 累加 / 报错） description（必须写）
3 参数有取值范围吗？越界会怎样（拒绝 / 截断 / 静默钳制）？ schema 的 min/max/enum + description
4 有没有"必须同时给"或"最多给一个"的参数组合？ schema 的 oneOf/allOf/required（见 3.3）
5 参数是"名字"还是"标识"？同名资源的歧义如何消解？ 用 ID 而非名字（3.4）
6 失败时返回值告诉你哪一部分失败了吗？ error schema（第 3 节）
7 返回值的每个字段是"事实"还是"模型的声明"？ 字段命名 + description
8 有没有前置条件（先读后写、需先登录、配额）？ description
9 这个工具的副作用可撤销吗？撤销手段是什么？ description
10 它会不会与其他工具产生顺序依赖？ description（"必须在 open_session 之后调用"）

第 1、2、9 条是幂等设计的输入（第 2 节），第 4、6 条是错误反馈的输入（第 3 节），第 1、8 条是权限的输入（第 7 章）。所以这张表不是文档清单，而是后面三节的接口。

三、可选性、默认值与"参数语义"的精确表达#

3.1 可选性是契约的语义，不是实现的细节#

对比两个 schema：

{"query": {"type": "string"}}
{"query": {"type": "string", "description": "自然语言问句"},
 "limit": {"type": "integer", "minimum": 1, "maximum": 100, "default": 20,
           "description": "返回条数上限。默认 20；超过 100 会被拒绝而不是截断。"},
 "cursor": {"type": "string", "description": "上一次返回的 next_cursor；用于翻页。不要自行构造。"}}

差别不在于"更啰嗦"，而在于后者消除了四类模型必须靠猜的决定：

模型要决定的事 只有 {"type":"string"} 时 有完整约束时
要不要传 limit 猜（可能不传、可能传 1000） 知道有默认值，可以不传
传多大 从训练先验取一个数（常见 10） 知道合法区间与默认值
越界会怎样 不知道 → 可能反复试 知道会被拒绝，不会浪费步数
cursor 从哪来 不知道 → 可能编造 明确"不要自行构造"

一个反直觉的结论：把约束写严（maximum: 100）通常提高成功率，而不是降低。因为模型不需要在巨大空间里猜一个"安全"的值，也不需要靠试错发现边界。约束的作用是把开放决策变成封闭决策。

反过来，"静默钳制"是危险的默认行为：limit=1000 时悄悄改成 100 并按 100 返回，模型会以为"最多就 100 条"，从而在结论里声称"全库只有 100 条"。要么拒绝（推荐），要么在返回值里显式告知被钳制了：

{"items": [...], "limit_applied": 100, "limit_requested": 1000, "truncated": true}

3.2 默认值必须写进 schema，而不是藏在实现里#

如果 limit 的默认值 20 只写在代码里，schema 里没有，会发生什么？模型不知道默认值存在，于是每次都会显式传一个数 —— 传的是它自己的先验（10、50、100）。结果是：

  • 模型的行为与实际默认值不一致，且这种不一致不可见；
  • 当你想通过调默认值来改变行为（比如省钱）时，发现没有效果（因为模型总是显式传参）；
  • 评测集里的调用与线上调用分布不同。

规则：凡是"不传也有确定行为"的参数，默认值必须在 schema 里写出来。它不是实现细节，它是契约的一部分 —— 因为它决定了"省略"这个模型的合法动作意味着什么。

3.3 互斥与联动：schema 表达力的边界#

常见参数关系有三类，schema 的表达力依次递减：

关系 例子 schema 表达 备注
值域约束 limit ∈ [1,100] ✓ minimum/maximum/enum 最可靠
结构约束 一个对象必须有一个字段 ✓ required、oneOf、allOf、not 模型对复杂组合的理解会退化
语义联动 "query 与 doc_id 二选一且不能都给" △ 可用 oneOf 表达，但很多工具链不支持 需要在运行时校验并给可修复的错误
跨字段算术 "start_date ≤ end_date"、"amount ≤ balance" ✗ 无法表达 只能运行时校验
跨调用状态 "必须先 open 再 write" ✗ 无法表达 只能 description + 运行时状态检查

表达不了的部分必须在失败时给可修复的错误（第 3 节），而不是"参数错误"。这里有一个实用技巧：把语义联动改写成工具拆分。

✗ fetch(source_type, query, doc_id)   → source_type 决定哪个参数有效
✓ search_by_query(query) / get_by_id(doc_id)   → 两个工具，各自参数单一

工具拆分的判据是：如果两个参数在语义上互斥到"给了另一个就完全无效"，它们通常属于两个不同的工具。 代价是工具数量上升（第 4 节的选择问题），所以这是一个真正的取舍，不是单向优化。

3.4 用标识而不是名字：歧义的来源#

这是最容易在真实系统里出事的一条。看两个参数设计：

get_user(name="张三")      ← "张三" 可能对应 0 个、1 个、多个用户
get_user(user_id="u_8f3a")  ← 唯一

名字参数的问题不是"可能重名"，而是失败模式是静默的：重名时工具可能返回第一个、返回全部、或报错 —— 三种行为都"看起来合理"，但模型无从判断它拿到的是不是它想要的那个。它会继续用这个结果做后续决策（可能是给错误的人退款）。

规则：

  1. 写操作必须用不可变标识（ID/主键/URI），不接受名字。
  2. 只读操作接受名字时，必须返回候选列表而不是"最佳匹配"：
{"status": "ambiguous", "candidates": [
  {"user_id": "u_8f3a", "display": "张三 (产品部)", "match": "exact"},
  {"user_id": "u_1b02", "display": "张三 (销售部)", "match": "exact"}],
 "hint": "用 user_id 重新调用以消除歧义。"}
  1. 名字→ID 的解析应是一个独立工具（resolve_user(name)），并且它本身幂等、只读。

这个模式一般化后是一条重要的接口设计原则：把"需要判断的步骤"与"执行动作的步骤"分开。前者可以重试、可以问人、可以返回多候选；后者必须确定。这与 2.1 的"读写分开"是同一个原则的两种表现。

四、从"参数 schema"到"结果 schema"#

4.1 返回值是最被忽视的契约面#

大多数团队在设计工具时会写参数 schema，但返回值只用一句 -> str 带过。这是成本最高的省略，因为返回值是模型判断"世界现在是什么状态"的唯一依据。

三种返回形态的对比：

形态 例子 模型能做什么 代价
自由文本 "查询成功，找到 3 条相关文档，分别是..." 只能整体理解 无法做字段级判断；解析不稳定；易被注入（第 4 节）
列表/标量 ["doc1", "doc2"] 能枚举 无元数据（score、时间、来源），无法判断可信度
结构化对象 {"items":[{...,"score":0.7}], "truncated":false, "next_cursor":null} 字段级判断、可校验、可程序化后处理 设计成本；token 略多

收益出现的位置：当循环里存在"基于结果的判断"时（是否有更多页、是否被截断、置信度多少、是否需要重试），结构化返回是唯一可行的形态。文本返回把这类判断变成"模型再读一遍再猜"，而它猜错的概率不低。

4.2 返回 schema 的四条设计规则#

  1. 状态字段优先于内容字段。返回值应当先回答"这次调用发生了什么"，再给内容：
{"status": "ok" | "empty" | "ambiguous" | "truncated" | "denied" | "retry_later",
 "items": [...],
 "meta": {"truncated": false, "next_cursor": null, "elapsed_ms": 120}}

status 是一个枚举 —— 模型对枚举的处理远比对自由文本可靠（与 3.1 的"封闭决策"同理）。

  1. 区分"事实"与"声明"。如果字段是某个上游系统的断言，命名要显式：
{"status": "ok", "items": [{"doc_id": "d_1", "content": "...",
                            "content_source": "external_doc", "fetched_at": "2026-03-01T10:00:00Z",
                            "verified": false}]}

模型的输出、第三方返回的内容都属于声明。后续要不要信任它，取决于 content_source / verified / fetched_at —— 第 4 章的写入门槛会直接消费这些字段。

  1. 不要返回空。null 或空字符串是最差的返回：模型既不知道"没找到"，也不知道"出错了"。空结果必须显式：
{"status": "empty", "searched_scope": "internal_docs_2023+",
 "hint": "该库不覆盖 2023 年前文档；如需历史数据请用 archive_search。"}

hint 的价值在于它指出下一步。一个只说"empty"的返回值会让模型做随机重试。

  1. 不要返回"解读"。工具返回值里混入结论（"这条数据不重要，可以忽略"）会掩盖事实，且不可追溯。工具给事实与元数据，判断留给循环或验证器。

4.3 参数与结果的对称性#

有一个好用的自检：参数名与返回字段名应当构成一致的词汇表。如果参数叫 limit，返回里就该有 limit_applied；如果参数叫 cursor，返回里就该有 next_cursor。词汇表不一致是契约腐化的最早信号，也是模型最容易踩的坑（它会以为 next_cursor 可以传回 cursor 之外的参数）。

五、宽松 schema 为什么是最贵的省事#

"先写个宽松 schema，跑通再说"是极常见的路径，它的代价是延迟出现且难以归因的。四类代价：

代价 机制 何时显现
模型自造参数 没有 additionalProperties: false，模型会传 sort_by、filters 之类它"以为有"的参数 立刻（但常被静默忽略）
值域靠试错 没有 min/max，模型用二分试错找边界，烧步数与预算 中期（成本曲线异常）
静默错误 实现里做了默认钳制，模型不知道 晚期（结论错误，难归因）
评测失真 评测集里的调用分布与线上不同 引入评测时

建议的最小严格集（成本低、收益高）：

{
  "additionalProperties": false,
  "required": ["query"],
  "properties": {
    "query": {"type": "string", "minLength": 1, "maxLength": 500},
    "limit":  {"type": "integer", "minimum": 1, "maximum": 100, "default": 20}
  }
}

四个关键字（additionalProperties: false、required、minimum/maximum、default）覆盖了上面四类代价中的前三类。它们的总成本就是几行 JSON。

代码：契约审查器 + 运行时校验 + 参数收敛#

下面的代码做三件事：(1) 一个能在 CI 里跑的契约审查器（检查 2.3 检查表里可机械化的条目）；(2) 一个不依赖第三方库的 schema 子集校验器；(3) 一个"参数规范化"步骤，把校验放在调用之前，让错误由我们产生（可修复、可分类），而不是由下游系统产生（不可读）。

import ast
import json
from dataclasses import dataclass, field
from typing import Any, Optional

# ==================== (1) 契约审查器 ====================
# ★ 设计决策：把"可机械检查的契约缺陷"变成 CI 断言。
#   review 时靠人记的规则一定会漏；能被 assert 的规则不会漏。
WRITE_VERBS = ("create", "update", "delete", "set", "send", "transfer", "submit", "publish")


@dataclass
class ToolSpec:
    """工具契约的机器可读形态。★ 注意 return_schema 与 description 都是必填 ——
    它们和参数 schema 一样是契约面，不是可选装饰。"""
    name: str
    description: str
    parameters: dict
    return_schema: dict
    side_effect: str = "read"          # read | reversible_write | irreversible_write
    idempotent: Optional[bool] = None  # None = 未声明（本身就是缺陷）


def audit_tool(spec: ToolSpec) -> list[str]:
    """
    返回缺陷列表（空列表 = 通过）。
    ★ 设计决策：只检查"能机械判定"的项。跨字段算术、前置条件这类语义问题
      审查器不假装能查出来，而是强制它们出现在 description 里（见 issues 的产生逻辑）。
    """
    issues: list[str] = []
    p = spec.parameters
    props = p.get("properties", {})

    # A. 宽松 schema 的四个典型信号
    if p.get("additionalProperties") is not False:
        issues.append("A1 未关闭 additionalProperties：模型会自造参数并被静默忽略")
    if not p.get("required"):
        issues.append("A2 没有 required：模型无法判断哪个参数是必需的")
    for key, sch in props.items():
        if sch.get("type") == "integer" and "maximum" not in sch:
            issues.append(f"A3 整数参数 {key} 无上界：模型会靠试错找边界")
        if sch.get("type") == "string" and "maxLength" not in sch:
            issues.append(f"A4 字符串参数 {key} 无 maxLength：注入与超长输入无约束")
        if "description" not in sch:
            issues.append(f"A5 参数 {key} 无 description：模型只能用先验填语义")

    # B. 副作用与幂等必须显式声明（第 2 节的输入）
    if spec.side_effect in ("reversible_write", "irreversible_write"):
        if spec.idempotent is None:
            issues.append("B1 写工具未声明幂等性：重试策略无从设计")
        if "幂等" not in spec.description and "重复" not in spec.description:
            issues.append("B2 写工具的 description 未说明重复调用的后果")
    if spec.side_effect == "irreversible_write" and "撤销" not in spec.description:
        issues.append("B3 不可逆写未说明撤销/核对手段（可回滚目标的落地形式）")

    # C. 名字参数 vs 标识参数（3.4）
    for key in props:
        if spec.side_effect != "read" and key.endswith(("_name", "name")):
            issues.append(f"C1 写工具使用了名字参数 {key}：重名时失败是静默的")

    # D. 返回值契约
    if not spec.return_schema.get("properties"):
        issues.append("D1 未声明返回 schema：模型无法做字段级判断")
    else:
        if "status" not in spec.return_schema["properties"]:
            issues.append("D2 返回无 status 枚举：无法区分 empty/denied/partial")
        if spec.return_schema["properties"].get("status", {}).get("type") != "string":
            issues.append("D3 status 不是 string：应为枚举字符串以便模型读取")

    # E. 语义约束的表达力兜底：表达不了就必须写进 description
    semantic_markers = ("必须", "不能", "只允许", "前置", "之前")
    if not any(m in spec.description for m in semantic_markers):
        issues.append("E1 description 未见任何前置条件/限制语：语义约束无处表达")

    # F. 命名一致性：参数 → 返回字段（4.3 的对称性自检）
    for key in props:
        if key == "limit" and "limit_applied" not in spec.return_schema.get("properties", {}):
            issues.append("F1 有 limit 参数但返回无 limit_applied：钳制将不可见")
        if key == "cursor" and "next_cursor" not in spec.return_schema.get("properties", {}):
            issues.append("F2 有 cursor 参数但返回无 next_cursor：翻页语义不闭合")
    return issues


# ==================== (2) 最小 schema 校验器 ====================
# ★ 设计决策：刻意只实现 JSON Schema 的一个子集。
#   全量 JSON Schema 的复杂度会把"调用前校验"变成一个新的事故来源；
#   而实践中覆盖 95% 需求的就是这几个关键字。
_TYPE_MAP = {"string": str, "integer": int, "number": (int, float),
             "boolean": bool, "array": list, "object": dict}


class SchemaError(ValueError):
    """带路径的校验错误。★ 路径是给模型的（第 3 节），不是给程序员的。"""

    def __init__(self, path: str, msg: str):
        super().__init__(f"{path}: {msg}")
        self.path, self.msg = path, msg


def validate(value: Any, schema: dict, path: str = "$") -> None:
    t = schema.get("type")
    if t is not None:
        expect = _TYPE_MAP[t]
        # ★ bool 是 int 的子类：不排除会让 True 通过 integer 校验
        if isinstance(value, bool) and t in ("integer", "number"):
            raise SchemaError(path, f"期望 {t}，得到 boolean")
        if not isinstance(value, expect):
            raise SchemaError(path, f"期望 {t}，得到 {type(value).__name__}")

    if t == "string":
        if "minLength" in schema and len(value) < schema["minLength"]:
            raise SchemaError(path, f"长度 < {schema['minLength']}")
        if "maxLength" in schema and len(value) > schema["maxLength"]:
            raise SchemaError(path, f"长度 > {schema['maxLength']}")
        if "enum" in schema and value not in schema["enum"]:
            raise SchemaError(path, f"不在允许集合 {schema['enum']} 中")
    elif t in ("integer", "number"):
        if "minimum" in schema and value < schema["minimum"]:
            raise SchemaError(path, f"小于下界 {schema['minimum']}")
        if "maximum" in schema and value > schema["maximum"]:
            raise SchemaError(path, f"大于上界 {schema['maximum']}")
    elif t == "array":
        item_schema = schema.get("items")
        if item_schema:
            for i, item in enumerate(value):
                validate(item, item_schema, f"{path}[{i}]")
    elif t == "object":
        props = schema.get("properties", {})
        for req in schema.get("required", []):
            if req not in value:
                raise SchemaError(f"{path}.{req}", "缺少必需参数")
        for k, v in value.items():
            if k not in props:
                if schema.get("additionalProperties") is False:
                    raise SchemaError(f"{path}.{k}", f"未知参数（可用：{sorted(props)}）")
                continue
            validate(v, props[k], f"{path}.{k}")
        # oneOf：用于表达"二选一且不可都给"（3.3 的语义联动）
        if "oneOf" in schema:
            hits = sum(1 for sub in schema["oneOf"] if _satisfies(value, sub))
            if hits != 1:
                names = [sorted(s.get("required", [])) for s in schema["oneOf"]]
                raise SchemaError(path, f"必须且只能满足其中一组：{names}（当前满足 {hits} 组）")


def _satisfies(obj: Any, sub: dict) -> bool:
    try:
        validate(obj, sub)
        return True
    except SchemaError:
        return False


# ==================== (3) 参数规范化 + 契约内校验 ====================
@dataclass
class Normalized:
    ok: bool
    args: dict = field(default_factory=dict)
    # ★ 错误信息面向模型：含路径、当前值、合法域、可行动提示
    feedback: Optional[str] = None


def normalize_and_check(raw_args: dict, spec: ToolSpec) -> Normalized:
    """
    ★ 设计决策：把校验放在"我们这一侧、调用之前"。
      下游系统的报错是面向程序员的（栈回溯/内部字段名），
      而我们这里的报错可以面向模型设计（路径 + 合法域 + 下一步）。
      同一个失败，两种报错的可修复性差一个数量级。
    """
    schema = spec.parameters
    args = dict(raw_args)

    # 默认值必须由 schema 注入，而不是由实现偷偷注入（3.2）
    for key, sch in schema.get("properties", {}).items():
        if key not in args and "default" in sch:
            args[key] = sch["default"]

    try:
        validate(args, schema)
    except SchemaError as e:
        hint = _hint(e, schema)
        return Normalized(ok=False, feedback=f"参数不合法 → {e}. {hint}")
    return Normalized(ok=True, args=args)


def _hint(err: SchemaError, schema: dict) -> str:
    """把校验错误翻译成模型能据以修改参数的建议。★ 这是第 3 节"反馈设计"的最小形态。"""
    leaf = err.path.split(".")[-1].split("[")[0]
    sch = schema.get("properties", {}).get(leaf)
    if not sch:
        return f"可用参数：{sorted(schema.get('properties', {}))}"
    bits = []
    for k in ("type", "minimum", "maximum", "minLength", "maxLength", "default", "enum"):
        if k in sch:
            bits.append(f"{k}={sch[k]}")
    return f"参数 {leaf} 的约束：{', '.join(bits)}。修改后重新调用，不要重复提交相同参数。"

    def write_guard(session_open: bool, args: dict) -> Normalized:

            return Normalized(ok=False, feedback=(

五处关键设计决策：

  1. audit_tool 把契约规则变成 CI 断言。审查器的价值不在于它检查得多全，而在于它检查的每条都不会再被漏掉；语义类问题（跨字段算术、前置条件）则通过 E1 强制它们出现在 description 里 —— 审查器检查"约束有没有被表达"，而不是"约束是什么"。
  2. validate 刻意只实现 JSON Schema 子集，并且显式处理 bool 是 int 子类这个坑。调用前校验的意义是把错误的产生者换成我们（可分类、可修复），而不是下游（不可读）。
  3. normalize_and_check 在调用之前注入默认值。这让"省略参数"这个模型动作有确定语义，也让 schema 成为默认值的唯一来源（避免实现与契约漂移）。
  4. _hint 生成的是面向模型的措辞：参数名、约束、下一步、以及"不要重复提交相同参数"。最后一句是第 3 节要展开的防重复机制的最小形态。
  5. 最后的 write_guard 演示了 schema 表达力之外的约束如何落地：运行时检查 + 明确指出前置工具名 + 可执行的下一步。

练习#

  1. 契约审查：拿你实际用过（或设计过）的一个工具，用 2.3 的十问表逐条填。至少找出三项答不上来的，并说明：如果模型在真实任务里遇到这个"没答上来的地方"，它最可能采取的错误行为是什么？再把它们按"加 schema 约束 / 改 description / 拆工具 / 加运行时校验"归到四类修复手段里。

  2. 粒度取舍：某系统原本有一个工具 edit_document(doc_id, mode, content)，mode ∈ {append, replace_section, replace_all}。请给出至少两种拆分或改造方案，并逐个分析：(a) 幂等键该怎么设？(b) 权限如何更细？(c) 部分成功如何表达？(d) 工具数量增加后选择难度如何变化？最后给出你的选择与理由。

  3. 静默钳制的代价：某工具对 limit 做静默钳制（>100 时按 100 处理），返回里不含任何提示。请构造一个具体任务，说明模型会因为这个设计得出一个错误结论（要写出它看到的返回值、它得出的结论、以及真实情况的差别）。然后给出返回 schema 的修正方案。

  4. schema 表达力的边界：下面三条约束，分别判断能否用 JSON Schema（含 oneOf/allOf/not，required，minimum）表达。不能表达的，写出你的落地方式（运行时校验 + 反馈文案）： （a）start_date ≤ end_date；（b）query 与 doc_id 必须且只能给一个；（c）调用本工具前必须先调用过 open_session 且会话未过期。

  5. 返回值设计：为"在外部工单系统里创建一个工单"的工具设计完整的返回 schema。要求覆盖：成功、字段非法被拒、权限不足、上游限流、上游超时（结果未知）、以及部分成功（工单已建但标签写入失败）。对每个状态说明：模型收到它之后应该采取的下一个动作是什么？其中哪一个状态必须携带幂等键或查询手段？

  6. 描述的两段式改写：找一段你写过的工具 description，按 1.2 的两段式（何时用/何时不用 → 参数语义与前置条件 → 返回什么）重写。要求：重写后，一个之前会被误选到相邻工具的场景不再被误选。说明你加入了哪一句、它为什么起作用（是提高区分度还是传递约束）。

  7. 名字 vs 标识（判断）：某只读工具 search_orders(customer_name, status) 在真实数据里大量重名。请设计：它该返回什么？如果产品要求"直接返回最匹配的一条"，你要付出什么代价来让它安全？（提示：想想后续哪个写操作会消费这个结果。）

小结#

  • 工具对模型而言是不可见实现的接口面：能力声明 + 调用协议 + 结果语义三合一。契约没写清的空白会被模型的训练先验填上，填错是契约的缺陷，不是模型的错。
  • 位置决定作用：description 在"选工具"时提供区分度，在"填参数"时提供约束传递。两段式写法同时服务两个位置；把两件事混成一段是描述写不好的主因。
  • 粒度 = 副作用边界。读写分开、写操作可原子或可报告部分成功、默认不给 run_sql/run_shell 这类逃逸舱。
  • 约束写严通常提高成功率：它把开放决策变成封闭决策。默认值必须写进 schema（它是契约，不是实现细节），越界应拒绝而不要静默钳制；必须钳制时要在返回里显式报告 limit_applied/truncated。
  • schema 表达力有限：值域 ✓、结构（oneOf）△、跨字段算术 ✗、跨调用状态 ✗。表达不了的必须在失败时给可修复的错误；互斥到"给了就无效"的参数组，通常应拆成两个工具。
  • 写操作用标识不用名字：名字参数的失败是静默的（返回第一个/全部/报错都"看起来合理"）。让"解析"独立成一个只读工具，把"需要判断的步骤"与"执行动作的步骤"分开。
  • 返回值是被忽视的契约面：优先 status 枚举、区分事实与声明、不要返回空、不要返回解读。返回值是模型判断"世界现在什么样"的唯一依据。
  • "先宽松后收紧"是最贵的省事：四个关键字（additionalProperties: false、required、minimum/maximum、default）就能覆盖大部分代价，成本只有几行 JSON。
  • 调用前校验把错误的生产者换成自己：下游的报错面向程序员，我们的报错可以面向模型设计（路径 + 合法域 + 下一步 + "不要重复提交"）。

下一节：契约写清楚了，"调用"这件事还有一半没解决 —— 调用发出去了，但你没收到回复。此时世界到底变没变？这一节要处理的就是这个"未知区间"，以及它为什么让幂等键成为 Agent 可靠性的地基。
