幻觉问题#

语言模型最危险的一点，不是它"不知道"，而是它不知道却说得煞有介事。这种"一本正经地胡说八道"叫幻觉（hallucination），是 LLM 落地最大的障碍之一。本课讲清幻觉的几种类型、它产生的深层原因，以及如何用代码"抓"到它。

一、概念讲解#

1. 什么是幻觉#

幻觉指模型生成的文本内容与事实不符，或与给定上下文不符，却表达得流畅、自信，让人难以分辨。它大致分三类：

  • 事实性幻觉（factual）：编造不存在的事实——虚构论文、编造引用、捏造人物数据。
  • 忠实性幻觉（faithfulness）：给定了一段上下文（如让模型总结一篇文章），模型答出的内容上下文里根本没有。
  • 逻辑性幻觉：推理步骤看似自洽，实则逻辑断裂或偷换前提。

2. 为什么 LLM 会幻觉#

幻觉不是 bug，而是自回归语言模型的固有倾向：

  • 目标决定的：预训练优化的是"预测下一个最可能的词"，不是"输出事实"。模型学的是"人最可能怎么说"，而非"什么才是真的"。
  • 数据里的噪声：训练语料本身就包含错误、过时、偏颇的内容，模型照单全收。
  • 解码的随机性：采样（temperature/top-k）引入了随机 token，随机累积就会"编"。
  • 缺乏 grounding（外部锚点）：模型无法访问实时世界，对训练后发生的、或它没记牢的事实只能"编一个像样的"。
  • 过度自信：RLHF 对齐让模型"更愿意给确定答案"，有时反而压抑了"我不知道"，逼它硬编。

3. 幻觉有什么危害#

  • 误导决策：医学、法律、金融场景里，一条编造的建议可能造成真实伤害。
  • 污染信息：模型输出的假引用、假链接会被当作真材料二次传播。
  • 侵蚀信任：用户一旦发现模型"会编"，就不敢再信它说的任何话。

所以"检测并缓解幻觉"是 LLM 工程的重中之重——这正是下一课的主题。

二、可运行示例#

下面的代码制造了一个幻觉场景，再写一个事实核对器把它抓出来，让你直观看到"检测幻觉"的思路。

# —— 一个"知识库"，代表模型的可靠事实来源 ——
KNOWLEDGE = {
    "水的沸点": "100 摄氏度",
    "北京": "中国首都",
    "太阳": "恒星",
}

def mock_llm(question, grounded):
    """mock 模型：grounded=True 时查知识库回答，否则'凭感觉编'。"""
    if grounded:
        return KNOWLEDGE.get(question, "我不知道")
    # 未接地：不管问题是什么，都流利地编一个像样的答案
    fabrications = {
        "水的沸点": "水的沸点是 120 摄氏度。",
        "北京": "北京是日本的首都。",
        "太阳": "太阳是一颗行星。",
    }
    return fabrications.get(question, "这是一个众所周知的事实：答案是 42。")

def fact_checker(question, answer):
    """核对器：把模型答案与知识库对照，给出'可信/幻觉'判定。"""
    truth = KNOWLEDGE.get(question)
    if truth is None:
        return "无法核对（知识库无此条目）"
    # 判断标准答案的关键词是否出现在模型回答里
    return "可信 ✓" if truth in answer else "疑似幻觉 ✗"

for q in ["水的沸点", "北京", "太阳"]:
    bad  = mock_llm(q, grounded=False)   # 未接地的模型
    good = mock_llm(q, grounded=True)    # 接地的模型
    print(f"问：{q}")
    print(f"  未接地回答：{bad}  ->  {fact_checker(q, bad)}")
    print(f"  接地回答  ：{good}  ->  {fact_checker(q, good)}")

这段代码揭示了两件事：不接地的模型会流利地编造（"北京是日本的首都"）；只要引入可靠来源做核对，幻觉就能被自动发现。真实系统的核对器会对接检索库、搜索引擎或知识图谱，但"拿答案去对权威来源"这个核心动作完全一样。

三、练习#

  1. 分类练习：为下面三句话各归一类幻觉——① "根据 2019 年论文《XX》…"（该论文不存在）；② 总结一篇文章时写出了原文没有的观点；③ "因为 A=B 且 B=C，所以 A=D"。
  2. 扩展知识库：往 KNOWLEDGE 里加 3 条事实，并为 mock_llm 补对应的"编造答案"，观察核对器能否全部抓出。
  3. 更严的核对：fact_checker 用子串匹配太脆弱（"不是 100 摄氏度"也会被判可信）。改进它：当回答里出现否定词时判为幻觉。
  4. 思考采样：为什么提高 temperature 会加剧幻觉？在自回归逐 token 生成中，随机性是如何被一步步放大的？
  5. 思考信任：如果模型总爱编，为什么 RLHF 有时反而让它更"嘴硬"（不愿说"我不知道"）？这对产品设计有什么启示？
