归约：朴素 → 树形 → warp shuffle → 多级#

求和看起来是最不需要设计算法的操作。但在 GPU 上它同时踩了三个坑：串行依赖太长、跨线程通信太贵、浮点加法的结合律不成立。一片 1024 个数、256 个线程的归约，朴素写法要 1023 步；树形只要 11 步；把最后几级搬进寄存器（warp shuffle）才摸到显存带宽允许的上限。这一课把三代写法的代价账与误差账都算成可打印的数字，并给出无 GPU 的复现路径。

一、概念讲解#

1. 归约的定义与并行化的两个代价#

归约（reduction）是把 N 个元素通过一个满足结合律的二元算子合并成 1 个结果，例如 s=∑i=0N−1​xi​。并行化它要付两种代价：时序步数（depth，最长依赖链长度，决定延迟）与总工作量（work，全部加法次数之和，决定吞吐）。

顺序累加 depth =N−1、work =N−1；树形归约 work 同样是 N−1，但 depth =log2​N。并行归约的收益全在 depth 上，不在 work 上——所以块内归约常常是 memory-bound（受显存带宽限制）：加法便宜，把数据搬进来贵。

2. 块内树形归约：步数从 1023 降到 11#

把 N 个元素平均分给 256 个线程，每个线程先串行累加自己那 N/256 个（步数 N/256−1），再在 shared memory 上做 8 级树形合并（每级活跃线程减半）。N=1024 时每线程 4 个元素：(4-1) + 8 = 11 步，相比单线程的 1023 步快 93 倍。

一个关键工程细节：合并方式选 s[i] += s[i + stride] 而不是 s[i] += s[i - stride]。后者在部分线程上会造成显式的分支发散（divergent branch），而前者在 stride 小于 warp 尺寸时整个 warp 一起执行、由 if (tid < stride) 统一屏蔽。这不是"更快一点"，而是让最后 5 级可以整段替换成 shuffle。

3. warp shuffle：把最后 5 级搬进寄存器#

warp shuffle（线程束内数据交换）用一条指令让同一 warp 的线程互读对方的寄存器，不经过 shared memory，也不需要 __syncthreads()。典型模式：

for (int offset = 16; offset > 0; offset >>= 1)
    val += __shfl_down_sync(0xffffffffu, val, offset);

__shfl_down_sync(mask, val, offset) 让每个线程拿到"比自己大 offset 号"的那个线程的 val；mask 指明参与这次交换的线程集合。N=1024、256 线程时，5 级 shuffle 换掉 5 级 shared memory 往返，每级省掉一次 __syncthreads()。

mask 不是可有可无的礼貌参数：块内 shuffle 阶段常常只有部分线程活跃（例如只剩 8 个线程在算）。若让未参与协作的线程也进入 __shfl_down_sync，而 mask 没有如实描述活跃集合，行为就是未定义的。规则很简单：mask 里的每个线程都必须执行同一个 shuffle 调用；不足一个 warp 时用 __activemask() 或显式传 (1u << count) - 1。

4. 多级归约与跨块合并#

单块最多管几万元素。N 到百万级时必须多级：每个 block 各自归约出一份部分和，再合并这些部分和。合并有三条路：

方案 做法 代价
两级 kernel 第一 kernel 写部分和数组，第二 kernel 再归约 多一次全量读写 + 一次 launch
单 kernel + 原子 每块最后一个线程 atomicAdd 到全局累加器 浮点结果不确定
协作组 grid cg::this_grid().sync() 后在最后一块里完成合并 需 cooperative launch，grid 尺寸受限

shared memory 树形归约的每一级之间必须有 __syncthreads()：少了它编译器可能把另一线程写的值缓存在寄存器里，读到的还是旧值。这是第 5 章内存模型在本课的直接落脚点。

5. 误差账：树形归约顺带买到的精度#

浮点加法不满足结合律：(a+b)+c=a+(b+c)。串行累加每一步都把"巨大的前缀和"与"单个元素"相加，相对误差按 n 累积；树形归约每一步只把量级相近的两个部分和相加，相对误差按 log2​n 累积。树形归约不只是更快，在精度上也通常更稳。

下一节用 struct 手工做 float32 舍入把这件事量出来：225 个 1.0f 丢给顺序累加会停在 224（224+1 在 float32 里无法表示），而树形累加得到正确值。长序列的求和、方差、均值都会撞上它。

6. 常见坑#

  • 最后一级 shuffle 读越界：活跃线程只剩 3 个却仍从 offset=16 走，会拿到垃圾数据；必须按活跃集合裁剪 offset 起点。
  • 以为 shuffle 能替代 __syncthreads()：shuffle 只在 warp 内有效，跨 warp 通信仍要走 shared memory + 屏障。
  • 每级都写全局内存：把部分和每级写回 HBM，会把树形归约省下的带宽加回去（第 4 章的账本同样适用）。
  • 用 atomicAdd 做可复现实验的基线：原子加的执行顺序由调度决定，同一输入两次运行可能差几个 ULP。
  • 忽略收尾：N 不是线程数整数倍时，边界线程必须传单位元（0.0f），否则垃圾会参与求和。

二、可运行代码示例#

三段纯 Python（只用标准库 random / struct / math，无 GPU、无需 numpy）分别做三件事：算清三种策略的代价账、展开块内树形归约的逐级规模、量化求和顺序对 float32 精度的影响。

# ===== 本课示例：三种归约策略的代价账 + 求和顺序对精度的影响 =====
import random, struct, math

# ---------- 1. 三种策略的代价账：加法次数、参与的线程、跨线程通信 ----------
N, TPB = 1024, 256          # 元素数、每块线程数

def sequential_work(n):
    """单线程累加 n 个数：n-1 次加法，0 次跨线程通信。"""
    return dict(adds=n - 1, steps=n - 1, threads=1, cross_thread=0)

def tree_reduce_work(n):
    """块内树形归约：每线程先串行加 n/TPB 个，再做 log2(TPB) 级跨线程合并。"""
    per_thread = n // TPB
    levels = int(math.log2(TPB))
    return dict(adds=(per_thread - 1) + levels, steps=(per_thread - 1) + levels,
                threads=TPB, cross_thread=levels)

def shuffle_reduce_work(n, warp=32):
    """warp shuffle 版本：最后 log2(warp) 级在寄存器里交换，不经过 shared memory。"""
    per_thread = n // TPB
    levels = int(math.log2(warp))
    shared_levels = int(math.log2(TPB // warp))
    return dict(adds=(per_thread - 1) + levels, steps=(per_thread - 1) + levels,
                threads=TPB, cross_thread=shared_levels + levels)

print(f"归约 N={N}，每块 {TPB} 线程")
print(f"{'策略':<14} {'每线程加法':>8} {'跨线程轮数':>9} {'时序步数':>7}")
for name, d in (("顺序(单线程)", sequential_work(N)),
                ("树形+shared", tree_reduce_work(N)),
                ("树形+shuffle", shuffle_reduce_work(N))):
    print(f"{name:<14} {d['adds']:>8} {d['cross_thread']:>9} {d['steps']:>7}")
print(f"顺序策略步数 / shuffle 策略步数 = {sequential_work(N)['steps'] / shuffle_reduce_work(N)['steps']:.0f}x")

# ---------- 2. 块内树形归约的逐级规模（shared memory 视图） ----------
print("\n块内树形归约各级（跨线程合并）：")
stride, active, level = 1, TPB // 2, 1
while stride < TPB:
    print(f"  第 {level} 级：活跃线程 {active:>3}，比较距离 {stride:>3}")
    stride, active, level = stride * 2, active // 2, level + 1

# ---------- 3. 求和顺序与浮点误差：float32 下逐次 vs 成对 ----------
def f32(x):
    return struct.unpack('<f', struct.pack('<f', x))[0]

def seq_sum(vals):
    acc = f32(0.0)
    for v in vals:
        acc = f32(acc + v)
    return acc

def pair_sum(vals):
    cur = [f32(v) for v in vals]
    while len(cur) > 1:
        nxt = [f32(cur[i] + cur[i + 1]) for i in range(0, len(cur) - 1, 2)]
        if len(cur) % 2:
            nxt.append(cur[-1])
        cur = nxt
    return cur[0]

random.seed(7)
print("\n随机均匀分布 [-1,1]，用 math.fsum 作精确参考：")
for n in (1024, 4096, 16384, 65536):
    vals = [random.uniform(-1, 1) for _ in range(n)]
    exact = math.fsum(vals)
    print(f"  n={n:>6} 精确={exact:+.8f} 逐次误差={abs(seq_sum(vals)-exact):.2e}"
          f" 成对误差={abs(pair_sum(vals)-exact):.2e}")

# ---------- 4. 极端情形：全部是 1.0f，顺序累加会在 2^24 处停住 ----------
print("\n全部元素为 1.0f（预期和 = n）：")
for n in (1 << 24, 1 << 25, 1 << 26):
    ones = [1.0] * n
    print(f"  n={n:>11,} 逐次累加={seq_sum(ones):>12.0f} 成对累加={pair_sum(ones):>12.0f}")

三、练习#

  1. 实现：把 pair_sum 改写成"Kahan 补偿求和"，在 n=65536 的随机数据上比较它与成对累加的误差。再把它和树形归约（8 级）的误差放一起，解释为什么 Kahan 的 work 更高但常数更小。

  2. 解释：为什么块内树形归约的合并要用 s[i] += s[i + stride] 而不是 s[i] += s[i - stride]？从"分支发散"与"能否替换成 shuffle"两个角度各写一句。

  3. 对比/验证：把 N 改成 1000（不是 256 的整数倍）。写出边界线程应传什么值、最后一级 shuffle 的 offset 起点应取多少（活跃线程 1000 的尾块只有 232 个，不足 8 个 warp），再用 pair_sum 在 1000 个随机数上验证树形结果的误差量级。

  4. 思考：若要求"同一输入两次运行结果逐位相同"，上面三种跨块合并方案里哪些不合格？如果又要求单次 kernel launch，还剩哪条路，代价是什么？
