需求分析（延迟/吞吐/成本）#

上一课我们学会了给部署场景"画像"，这一课把画像翻译成可量化、可验收的数字。需求分析做不好，后面要么"过度采购"白花钱，要么"容量不足"上线即崩。核心就三件事：流量（来多少人）、延迟（多快算及格）、成本（花多少钱封顶），外加一个把它们串起来的容量规划公式。学完本课，你应当能从"日活 10 万、每次 200 token"这样一句业务描述，推算出需要几张卡、多少个副本。

一、概念讲解#

1. 流量：从业务指标反推 QPS#

业务给的往往是"日活、人均次数、每请求 token 数"，工程上要的是每秒请求数（QPS/RPS）。换算链路：

峰值 QPS ≈ 日活 × 人均请求次数 × 峰值系数 / 86400 秒
  • 平均 QPS：把一天的总请求数摊到 86400 秒；
  • 峰值 QPS：业务有潮汐（早高峰、促销），峰值通常是平均的 3–10 倍，用峰值系数表达；
  • token 吞吐：QPS ×（输入 token + 输出 token）。

例：日活 10 万、人均 3 次、每次输入 300 token 输出 200 token、峰值系数 5：

平均 QPS = 100000 × 3 / 86400 ≈ 3.5
峰值 QPS = 3.5 × 5 ≈ 17.5
峰值 token 吞吐 = 17.5 × (300 + 200) = 8750 token/s

容量必须按峰值规划，否则高峰期排队、超时、雪崩。

2. 延迟：承诺要落在分位数上#

延迟指标（上一门课已学）：TTFT（首 token 时间）和 TPOT（每 token 时间）。需求分析阶段要写死三个数字：

  • 目标值：如"P99 TTFT ≤ 1.5s"；
  • 分位数：P50 看整体、P99/P99.9 看长尾，承诺必须写分位数，平均值会骗人；
  • 可用性：如"月度 ≥ 99.9%"，对应每月最多 43 分钟不可用。

延迟目标反过来约束吞吐：批越大、并发越高，单请求排队越长。所以"峰值吞吐"和"P99 延迟"是一对必须同时满足的约束。

3. 成本：算单位 token 成本，而不是总价#

只看"一张 A100 每小时 3 美元"没意义，要算到产出上：

单位成本(美元/百万token) = GPU 单价 × 卡数 × 服务时长 / 总产出 token × 10^6

关键洞察：同一张卡，吞吐越高，单位 token 成本越低。所以量化、大批量、高利用率都是在"用同样的钱产出更多 token"。但压低成本有边界——不能跌破延迟 SLO。

4. 容量规划：三个量闭环#

把流量、延迟、吞吐、成本串起来，得到容量规划四步：

  1. 从业务反推峰值 QPS 与峰值 token 吞吐；
  2. 实测（或估算）单实例在满足 P99 延迟前提下的最大吞吐（token/s）；
  3. 所需副本数 = 峰值 token 吞吐 / 单实例达标吞吐，再乘 1.2–1.5 的冗余系数；
  4. 用副本数 × GPU 单价 × 时长，算出月成本，与预算对比，超标则回头降档（换量化/换小模型）。

二、可运行示例#

下面的脚本走完一遍"业务描述 → 容量 → 成本"的完整链路，并演示冗余系数如何影响成本。

# -*- coding: utf-8 -*-
# 容量规划：从 DAU/人均次数/峰值系数，反推副本数与月成本

def plan_capacity(dau, req_per_user, in_tok, out_tok, peak_factor,
                  single_instance_tps, slo_headroom=1.3, gpu_hour=3.5, gpus_per_instance=1):
    """single_instance_tps: 单实例在满足 P99 延迟前提下的 token/s（需实测）。
       slo_headroom: 冗余系数（留 30% 余量抗流量尖峰）。"""
    avg_qps = dau * req_per_user / 86400.0
    peak_qps = avg_qps * peak_factor
    peak_tps = peak_qps * (in_tok + out_tok)

    replicas_raw = peak_tps / single_instance_tps
    replicas = max(1, round(replicas_raw * slo_headroom))

    gpus = replicas * gpus_per_instance
    monthly_cost = gpu_hour * gpus * 720  # 每月 720 小时
    cost_per_million = monthly_cost / (peak_tps * 3600 * 720 / 1e6)  # 按峰值吞吐粗估
    return dict(avg_qps=avg_qps, peak_qps=peak_qps, peak_tps=peak_tps,
                replicas=replicas, gpus=gpus, monthly_cost=monthly_cost,
                cost_per_million=cost_per_million)

# 业务需求：日活 10 万，人均 3 次，输入 300 / 输出 200 token，峰值系数 5
r = plan_capacity(dau=100000, req_per_user=3, in_tok=300, out_tok=200,
                  peak_factor=5, single_instance_tps=1800)
print(f"平均 QPS = {r['avg_qps']:.1f} | 峰值 QPS = {r['peak_qps']:.1f} | 峰值吞吐 = {r['peak_tps']:.0f} token/s")
print(f"需副本数 = {r['replicas']} | GPU 数 = {r['gpus']} | 月成本 ≈ ${r['monthly_cost']:.0f} | 单位成本 ≈ ${r['cost_per_million']:.2f}/百万token")

# 对比：单实例吞吐翻倍（量化/调优后）→ 副本与成本怎么变
r2 = plan_capacity(dau=100000, req_per_user=3, in_tok=300, out_tok=200,
                   peak_factor=5, single_instance_tps=3600)
print(f"吞吐翻倍后 -> 副本数 = {r2['replicas']} | 月成本 ≈ ${r2['monthly_cost']:.0f} | 单位成本 ≈ ${r2['cost_per_million']:.2f}/百万token")

运行后你会看到：单实例吞吐翻倍，副本数和月成本几乎腰斩。这就是为什么"调优单实例吞吐"比"多买卡"更划算——它同时降低了硬件成本和单位 token 成本。

三、练习#

  1. 换业务参数：把日活改成 100 万、峰值系数改成 10，重跑脚本，观察副本数与成本如何跳变，说明为什么超大流量下必须引入自动扩缩容而非常驻满配。
  2. 改冗余系数：把 slo_headroom 从 1.3 调到 1.0 和 2.0，体会"冗余越足越贵但越稳"，并说说你会在什么业务上选哪种。
  3. 倒推 SLO：某服务实测单实例在 P99 TTFT=2s 时吞吐 2500 token/s，客户要求 P99 TTFT≤1.5s。解释为什么不能简单按 2500 规划，必须重新在更严延迟下实测。
  4. 成本反推：预算月成本 3000 美元、GPU 单价 3.5 美元/小时，反推最多能常驻多少张卡，再结合峰值吞吐判断这个预算能撑起多大的业务。
