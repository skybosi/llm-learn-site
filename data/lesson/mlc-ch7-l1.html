代码生成路径：TorchInductor / XLA / TVM → CUDA / Triton#

第 6 课把 schedule 选了出来，但 schedule 只是一份意图：tile 多大、哪层并行、要不要融合。把它变成可执行代码是另一件事——这一步决定你最终拿到的是 Triton 源码、LLVM IR 还是 CUDA C。三条主流路线给出的东西并不一样，要回答的问题却完全一样：哪个算子值得生成、哪个交给库、生成的代码长什么样。本课把三家的出口对齐到同一张派发表，并算出"融合一次省多少"。

一、概念讲解#

1. 同一张图，最后一公里各不相同#

TorchInductor 是 torch.compile 的默认后端，用 Python 实现，核心 IR 是 define-by-run 的循环层 IR：每个 buffer 由一个 inner_fn(index) 描述"第 index 个元素怎么算"，索引是 SymPy 表达式，所以符号 shape 能一路流到代码里。它刻意只保留两个下层目标——GPU 生成 Triton，CPU 生成 C++/OpenMP（PyTorch 官方公告的原话是"两个代表设计空间不同位置的 lower-level execution targets"）。官方另一条关键信息是：除 matmul / conv 走带 epilogue 融合的模板之外，其余 kernel 都由 IR 生成；尚未实现的算子先走 ATen 回退。

XLA 的工作面在 HLO / StableHLO：先在 HLO 层做融合（producer-consumer fusion）与 layout 决策，再由 GPU 后端的 emitter 把 fusion 变成代码——XLA 源码里就有这一层（xla/backends/gpu/codegen/triton/fusion_emitter.cc），Triton 与循环两种发射器最终都交给 LLVM 出 PTX。

TVM 把"算什么"和"怎么算"彻底分开：Relax 描述计算、TE / TensorIR 描述调度，tvm.build 先降到目标源码（CUDA C 等）再交给 nvcc 之类的工具链。它还开了一条与"自己生成"并列的路——BYOC（Bring Your Own Codegen）：用 DFPattern 把 matmul + bias + relu 这类片段标记出来，交给 cuBLAS / CUTLASS / cuDNN，剩下的计算仍由 TVM 生成的 kernel 负责，两者在 relax.build() 时链接成同一个可执行体。

路线 前端 IR 调度在哪一层 出口 谁产出机器码
TorchInductor FX 图 + define-by-run 循环层 IR Python scheduler（can_fuse / score_fusion）+ 自动调优 Triton（GPU）、C++/OpenMP（CPU） Triton 编译器、主机 C++ 编译器
XLA HLO / StableHLO HLO pass、fusion、layout assignment Triton 融合发射器 / LLVM IR LLVM（→ PTX）
TVM Relax + TE / TensorIR AutoTVM / Ansor 搜出的 schedule 目标源码（CUDA C 等）+ BYOC 外部库 nvcc / LLVM / 外部库自身

2. 出口只有三条，责任边界完全不同#

把上表压平，任何算子最终落进三格之一：

  • extern（库调用）：把 GEMM / 卷积交给已经按形状调过的库。它的能力上限就是库的上限，代价是默认不参与前后融合——只有模板提供 epilogue 槽位时，bias、激活才能搭车。
  • generated（生成 kernel）：点链、归约、索引变换这类"每个框架版本都在变"的算子。收益来自融合与省 DRAM 往返，风险来自 tile 选择、掩码边界与资源约束（第 2 课）。
  • fallback（回退）：没有 lowering 的算子。它保证语义、牺牲性能，而且必须被显式记账（第 3 课）。

《The Deep Learning Compiler: A Comprehensive Survey》把代码生成归成"编译生成"与"调用库"两类——上面这张表就是那套分类在三条真实路线上的投影。

3. 循环层 IR：三家最后一块"可编程"的地方#

不管前端长什么样，到了循环层就只剩：循环嵌套 + 并行/向量化标注 + 掩码/谓词 + buffer 读写。这一层还能用文本表达、也能用解释器执行。本课代码就用它算：一条 4 段点链在 8M 个 float32 元素上，未融合要写 3 个中间张量、4 次 kernel 启动，按"每个 kernel 一遍读一遍写"的模型估算是 256 MiB 流量；融合后中间值只活在寄存器里，1 次启动、64 MiB——4 倍差距全部来自"中间张量有没有落 DRAM"，与算力无关。

4. block 层程序：Triton 把并行映射接走了#

Triton 把上一步再抬一层：一个 program instance 负责一个 block，地址写成 pid * BLOCK + arange(BLOCK)，边界靠掩码收口，tl.dot 的累加器默认在 fp32。程序员只声明"块多大"，块内线程、共享内存、向量化交给编译器。这也解释了 Inductor 为什么选它：官方在公告的讨论里直说 Triton"需要的调优少得多"，而 TVM 的强项是众多非 GPU 目标。分工因此稳定：上游决定什么被生成，块层语言决定生成得多容易，编译器决定生成得多好。

5. 常见坑#

  • 以为 matmul 也是生成的：多数路线下它是模板或库调用；打印出的"生成代码"里看不到 GEMM 主体是正常的。
  • 把 IR 打印当成目标代码：循环层 IR 之后还有索引扁平化、内存分配、device/线程绑定，之后才是 C 或 PTX。
  • 只看能否跑通，不看有无 fallback：一段能跑通的产物可能有一半算子在回退（第 3 课给出台账方法）。
  • 在生成路径上忽略 dtype 与 layout 的一致性：生成器对签名比 eager 严格，类型或步长对不上就整段回退。

二、可运行代码示例#

纯 Python + numpy（本机 python3.10.16 + numpy 1.26.2 实跑，无需 GPU）。五段对应上面五节：派发表、融合/未融合的循环层 IR 与流量模型、Triton 风格 block 程序与掩码统计、生成代码与 eager 的逐元素对拍、三条出口的分工。

# ---- 第 1 课：同一张图 → 三条代码生成出口（numpy，本机 python3.10.16 + numpy 1.26.2 实跑）----
import numpy as np

# ================= 1. 派发表：每个算子走哪条出口 =================
DISPATCH = [
    ("matmul(x, W)",  "extern",    "调用 cuBLAS/cuDNN 等外部 kernel", "库已按形状调过，生成器正面打很难赢"),
    ("add(_, bias)",  "generated", "融进 matmul 的 epilogue",        "点链与模板做后融合才免一次往返"),
    ("relu(_)",       "generated", "与点链合成同一个 kernel",         "逐元素算子收益最大、风险最低"),
    ("sum(_, dim=1)", "generated", "归约 kernel（跨线程/block）",      "归约要额外的通信与中间缓冲"),
    ("mul(_, 0.5)",   "generated", "并入同一个融合区域",              "标量广播不需要单独搬数据"),
    ("custom_op(_)",  "fallback",  "没有 lowering，回退到框架 eager",  "正确性优先：回退必须保证语义不变"),
]

print("=== 1. 派发表：同一个图，出口不止一条 ===")
print(f"  {'算子':<15}{'出口':<11}{'生成物':<30}理由")
for op, path, what, why in DISPATCH:
    print(f"  {op:<15}{path:<11}{what:<30}{why}")

# ================= 2. 循环层 IR：融合前 vs 融合后 =================
N_EL = 8 * 1024 * 1024          # 8M 元素
BYTES = 4                       # float32
ARRAY_MB = N_EL * BYTES / 2**20

def ir_text(fused):
    if not fused:
        return [
            "kernel0: for i in range(0, %d, 4): vec4 { t1[i] = a[i] * 2 }" % N_EL,
            "kernel1: for i in range(0, %d, 4): vec4 { t2[i] = t1[i] + 1 }" % N_EL,
            "kernel2: for i in range(0, %d, 4): vec4 { t3[i] = max(t2[i], 0) }" % N_EL,
            "kernel3: for i in range(0, %d, 4): vec4 { out[i] = t3[i] * 0.5 }" % N_EL,
        ]
    return [
        "kernel0: for i in range(0, %d, 4): vec4 {" % N_EL,
        "           t = a[i] * 2          # 四段点链折成一串表达式",
        "           t = t + 1",
        "           t = max(t, 0)",
        "           out[i] = t * 0.5       # 中间张量 t1/t2/t3 全部消失",
        "         }",
    ]

def traffic_mb(kernels_read_write):
    return kernels_read_write * ARRAY_MB

print("\n=== 2. 循环层 IR：同语义、两种 schedule（流量是模型估算，不是实测）===")
print("  [未融合] 4 个 kernel，每个中间张量都要落一次 DRAM：")
for line in ir_text(False):
    print("   ", line)
print("  [融合]   1 个 kernel，中间值只活在寄存器里：")
for line in ir_text(True):
    print("   ", line)
print(f"  元素数 {N_EL}，float32 单个张量 {ARRAY_MB:.0f} MiB")
print(f"  未融合：4 kernel × (读 1 + 写 1) 张量 = {traffic_mb(8):.0f} MiB，中间张量 3 个")
print(f"  融合后：1 kernel × (读 1 + 写 1) 张量 = {traffic_mb(2):.0f} MiB，中间张量 0 个")
print(f"  流量比 = {traffic_mb(8) / traffic_mb(2):.1f}x，kernel 启动次数比 = 4.0x")

# ================= 3. block 层程序：Triton 风格（带掩码） =================
def triton_like(shape, block):
    n = int(np.prod(shape))
    grid = (n + block - 1) // block
    return [
        "@triton.jit",
        "def pointwise(a_ptr, out_ptr, n, BLOCK: tl.constexpr):",
        "    pid = tl.program_id(0)",
        "    offs = pid * BLOCK + tl.arange(0, BLOCK)",
        f"    m = offs < n                  # 掩码：n={n} 不是 {block} 的整数倍时兜住尾巴",
        "    x = tl.load(a_ptr + offs, mask=m, other=0.0)",
        "    y = tl.maximum(x * 2.0 + 1.0, 0.0) * 0.5",
        "    tl.store(out_ptr + offs, y, mask=m)",
        f"# grid = ({grid},)  # cdiv(n, BLOCK) = ceil({n}/{block})",
    ]

print("\n=== 3. block 层程序：一个 program 处理一个 block，边界靠掩码 ===")
for line in triton_like((1000,), 128):
    print("  " + line)
print("  块内地址 offs = pid*BLOCK + arange(BLOCK)：整除性、对齐、边界三件事都由掩码收口")
total_lanes = ((1000 + 127) // 128) * 128
waste = total_lanes - 1000
print(f"  有效 1000 个元素 / 实际发射 {total_lanes} 个 lane，空转 {waste} 个 = {waste / total_lanes:.2%}")

# ================= 4. 三种出口的执行对拍 =================
def gen_exec(a, cache):
    """按照生成的循环层 IR 执行：中间值只走寄存器（cache），不落 DRAM。"""
    out = np.empty_like(a)
    for i in range(a.size):
        t = a[i] * np.float32(2.0)
        cache["t1_reg"] = t
        t = t + np.float32(1.0)
        t = max(t, np.float32(0.0))
        out[i] = t * np.float32(0.5)
    return out

def eager_exec(a, cache):
    """未融合：每一步的材料化中间张量都要写回内存。"""
    t1 = a * np.float32(2.0); cache["t1"] = t1
    t2 = t1 + np.float32(1.0); cache["t2"] = t2
    t3 = np.maximum(t2, np.float32(0.0)); cache["t3"] = t3
    return t3 * np.float32(0.5)

rng = np.random.default_rng(7)
a = rng.standard_normal(64 * 96).astype(np.float32)
cache_g, cache_e = {}, {}
g = gen_exec(a, cache_g)
e = eager_exec(a, cache_e)
print("\n=== 4. 对拍：生成代码与 eager 必须逐元素一致（正确性是底线）===")
print(f"  生成 kernel 与 eager 最大绝对差 = {np.abs(g - e).max()}")
print(f"  逐元素全等 = {np.array_equal(g, e)}")
print(f"  eager 需常驻的中间张量：{sorted(cache_e)}（每个都占 {a.size * 4 / 1024:.0f} KiB）")
print("  生成路径：点链折成一串表达式，中间值只在寄存器里活一瞬，不进 buffer 分配表")

# ================= 5. 三条出口的分工小结 =================
print("\n=== 5. 三家的分工（同一张图的三段不同命题）===")
for name, claim, evidence in [
    ("外部库(out)", "把 GEMM/卷积做到硬件极限", "cuBLAS/cuDNN：模板化 kernel，不参与融合则多一次 DRAM 往返"),
    ("生成 kernel", "把点链/归约融成少数 kernel", "Triton / C++(OpenMP)：Inductor 的两条唯一出口"),
    ("回退路径", "保证没 lowering 的算子仍然正确", "ATen/框架算子：慢但语义与 eager 完全一致"),
]:
    print(f"  {name:<12}{claim:<22}{evidence}")

三、练习#

  1. 实现：给派发表加一列"能否融合"，规则自定（例如只有点链与归约可融、extern 不可融），再把第 2 节的流量模型改成读派发表自动求和；对"4 段点链 + 1 次 GEMM"的混合图算一遍流量，与"全融合"的乐观上界对比。
  2. 解释：为什么融合能让流量从 256 MiB 降到 64 MiB，却完全不影响浮点运算次数？指出一条"融合不省流量也不省启动"的图，并说明这类图该不该融。
  3. 对比/验证：把第 4 节的 block 程序改成 BLOCK=64 与 BLOCK=256 两版，分别算出 1000、1025、4096 三个 shape 下的空转 lane 比例；解释为什么"块越大越浪费"和"块越大越省地址计算"会同时成立。
  4. 思考：如果某个模型 70% 时间在 extern 的 GEMM 上、25% 在生成的点链上、5% 在回退算子上，那么"把点链生成质量提升 20%"能把端到端提高多少？这个账对"该不该自研编译器"的决策意味着什么？
