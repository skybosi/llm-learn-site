库内机制：拓扑探测、通道、算法与协议选择#

上一章你已经能算出"这次通信至少该花多少时间"。可真跑起来，同一份 AllReduce 代码在两台机器上能差好几倍——差别不在你的 Python 里，而在 ncclAllReduce() 调用之后、kernel 启动之前的那段决策：拓扑怎么读、消息切成几个通道、选哪个算法、用哪个协议。本课把这条决策链拆成可算、可打印的四步。

一、概念讲解#

1. 一次集合操作在库内走过的四步#

NCCL 和"cudaMemcpy + 本地归约 kernel"的写法最大的不同是：一个集合操作被实现成一个 kernel，通信与计算在同一个 kernel 里完成（官方 Overview 原话：handling both communication and computation operations），因此同步快、资源占用小。这个 kernel 怎么发，取决于启动前定下的四件事：

阶段 决定什么 在日志里看什么
拓扑探测 谁和谁之间有 NVLink / PCIe / NIC，走几条路 NCCL_DEBUG_SUBSYS=GRAPH 的探测输出
图搜索 环（ring）与树（tree）的形状 Ring 00 : ...、Tree 0 : -1 -> 0 -> 1/-1/-1
通道划分 并发度、CUDA block 数量与显存占用 channel{Lo..Hi}={0..31}
算法 + 协议 Ring / Tree / NVLS / PAT… 与 LL / LL128 / Simple Algo RING proto SIMPLE

2. 拓扑探测：NCCL 内部也在做一份 topo -m#

nvidia-smi topo -m 是你从外面看拓扑；NCCL 初始化时自己建一份等价的内部模型：默认加载 /var/run/nvidia-topologyd/virtualTopology.xml（如果存在），可用 NCCL_TOPO_FILE 覆盖、用 NCCL_TOPO_DUMP_FILE 导出成 XML 复查。它存在的原因很实际：容器、MIG、多节点 NVLink 域里，PCI 枚举与实际通路并不总一致，把拓扑写成文件才可复现。探测结果直接喂给图搜索，最终体现为 NCCL_DEBUG_SUBSYS=GRAPH 打印的环与树。

3. 环速率由"最慢一跳"决定，而不是平均带宽#

ring AllReduce 是流水线：2(P−1) 步里，各跳同时搬运不同 chunk，所以整环的吞吐由最慢一跳决定，而不是所有跳的平均值：

Tring​≈2(P−1)(α+βslow​schunk​​)

其中 α 是单跳固定延迟，schunk​ 是每步传输字节数，βslow​ 是环上最慢一跳的带宽。用示例参数（8 卡 2 节点、节点内 300 GB/s、跨节点单 NIC 25 GB/s、跨 rail 再打五折、α=5 μs）算 100 MiB 梯度：

  • rank 顺序环 0→1→…→7→0：跨节点两跳踩到跨 rail，最慢一跳只有 12.5 GB/s，总时间 117.51 ms；
  • rail 对齐环 0→1→2→3→7→6→5→4：跨节点两跳落在同一 rail，最慢一跳 25.0 GB/s，总时间 58.79 ms；
  • 两级分解（节点内 ring + 跨节点代表，2 节点）：3.19 ms；
  • 参考：若 8 卡全在 NVLink 域内，单环只要 0.68 ms。

这就是 NCCL_CROSS_NIC 存在的理由：默认值 2 表示"尽量让同一个环在各节点用同一张 NIC"，只有在 rail 优化网络里它才不必要。

4. 通道（channel）：三条不可越过的上限#

官方口径很明确：NCCL_NTHREADS 是每个 CUDA block 的线程数（默认 512，允许 64/128/256/512），而 NCCL 为每个通信通道启动一个 CUDA block；通道数由 NCCL_MAX_CTAS / NCCL_MIN_CTAS 控制（旧的 NCCL_MAX_NCHANNELS / NCCL_MIN_NCHANNELS 自 2.17 起弃用，两者同时设置时取更严格的值）。每个通道一对收发缓冲，大小是 NCCL_BUFFSIZE，默认 4 MiB。

通道把消息切成 C 份并行发送，但有三条上限：

  1. 延迟地板：步数还是 2(P−1)，所以 T≥2(P−1)α，通道再多也压不下去。示例里 1 MiB 消息从 C=1 的 118.9 μs 降到 C=4 的 82.2 μs 就停住，地板是 70 μs。
  2. 链路并行度：通道数超过链路能同时服务的数据流数后，带宽项不再下降。64 MiB 从 C=1 的 3201.7 μs 降到 C=4 的 852.9 μs，之后 C=8、C=16 都停在 852.9 μs。
  3. 显存：量级是"通道数 × 缓冲大小"。C=32、NCCL_BUFFSIZE=4 MiB 时约 256 MiB/rank，这是调大通道数必须付出的代价。

5. 算法与协议：自动选择的边界在哪#

NCCL_ALGO 可取的算法包括 Ring、Tree（2.5+）、CollnetChain / CollnetDirect（2.14+）、NVLS（2.17+）、NVLSTree（2.18+，这两者走 NVLink SHARP 卸载）、PAT（2.23+）；不设置时 NCCL 按拓扑与架构自动选。选择结果会以日志形式给出，官方示例的形状是：

NCCL INFO AllReduce: 33554432 Bytes -> Algo RING proto SIMPLE channel{Lo..Hi}={0..31}

两条判据足以解释大多数选择：小消息被 α 支配，树只需 O(logP) 步，比环的 2(P−1) 次 α 便宜；大消息被带宽支配，环的带宽最优性胜出。协议层 NCCL_PROTO 只有 LL、LL128、Simple 三个取值，官方明确不建议用户设置，例外是怀疑 bug 时关掉某个协议——因为在不支持 LL128 的平台上强开它会导致数据损坏。

6. 常见坑#

  • 拿 nvidia-smi 显示的"理论带宽"当预期：那是链路上限，不是 NCCL 能拿到的有效带宽。
  • 用已弃用的 NCCL_MAX_NCHANNELS / NCCL_MIN_NCHANNELS 做长期配置；新版本请用 NCCL_MIN_CTAS / NCCL_MAX_CTAS。
  • 盲目设置 NCCL_PROTO：官方把这条写进了"不应留在脚本里"的一类。
  • 把拓扑错配当算法问题：跨 rail 导致的带宽腰斩，改算法改不回来。
  • 只看平均值：环的速率由最慢一跳决定，拓扑里有一条慢链路就足以拖住整环。

二、可运行代码示例#

第一段代码不需要 GPU：它把"拓扑 → 环搜索 → 通道 → 算法协议"整条链做成可以打印的模型。链路带宽、α 都是示例值，请换成你自己机器的实测值。

# ===== 示例 1：拓扑感知的环搜索；环速率由"最慢一跳"决定 =====
# 参数全部是示例量级，请用 nvidia-smi topo -m 与 nccl-tests 的实测值替换
NV   = 300.0   # 节点内 NVLink 级：单跳可用带宽 (GB/s)
NIC  = 25.0    # 跨节点单 NIC 端口带宽 (GB/s)
PEN  = 0.5     # 跨 rail 惩罚（示例：不同 rail 要过一层交换，有效带宽打折）
ALPHA = 5.0    # 单跳固定延迟 (us)
PER_NODE = 4   # 每节点 4 卡，rank 0..3 在节点 0，rank 4..7 在节点 1

def pair_bw(a, b):
    """两两有效带宽：等价于 NCCL 拓扑图搜索的结果（这里直接给定）。"""
    if a // PER_NODE == b // PER_NODE:
        return NV
    return NIC if a % 4 == b % 4 else NIC * PEN    # rail 对齐与否

def ring_step(order, s):
    """一个环的每跳时间：流水线里各跳并发，整环速率由最慢一跳决定。"""
    hops = [pair_bw(order[i], order[(i + 1) % len(order)]) for i in range(len(order))]
    slow = min(hops)
    return ALPHA + s / (slow * 1e9) * 1e6, slow

def ring_total(order, s):
    step, slow = ring_step(order, s)
    return 2 * (len(order) - 1) * step, slow

S = 100 * 2**20   # 100 MiB 梯度
naive = list(range(8))
railed = [0, 1, 2, 3, 7, 6, 5, 4]
print("示例 1：8 个 rank 组成的环，100 MiB AllReduce（2(P-1) 步）")
for name, order in (("rank 顺序环", naive), ("rail 对齐环", railed)):
    t, slow = ring_total(order, S)
    print(f"  {name:<9} {order}  最慢一跳 {slow:5.1f} GB/s  总时间 {t/1e3:7.2f} ms")

def two_level(s, nodes=2, per_node=PER_NODE):
    """两级分解：节点内先各归约一份，节点间只跨 (nodes-1) 跳，再回节点内广播。"""
    inner = 2 * (per_node - 1) * (ALPHA + (s / nodes) / (NV * 1e9) * 1e6)
    outer = 2 * (nodes - 1) * (ALPHA + (s / per_node) / (NIC * 1e9) * 1e6)
    return inner + outer

print(f"  两级分解（节点内 ring + 跨节点代表）          总时间 {two_level(S)/1e3:7.2f} ms")
t_all = 2 * 7 * (ALPHA + (S / 8) / (NV * 1e9) * 1e6)
print(f"  参考：同机 8 卡全 NVLink 单环                 总时间 {t_all/1e3:7.2f} ms")

# ===== 示例 2：通道数 C 把消息切成 C 份并行，但撞上 2(P-1)*alpha 的延迟地板 =====
def chan_time(s, P, C, c_sat, alpha=ALPHA, bw=NV):
    """C 个通道各做一遍 2(P-1) 步；通道超过链路并行度 c_sat 后带宽不再涨。"""
    per_chan = s / C
    steps = 2 * (P - 1)
    serial = -(-C // c_sat)               # ceil(C / c_sat)：链路上要串几轮
    return steps * (alpha + per_chan / (bw * 1e9) * 1e6 * serial)

print("\n示例 2：通道数与延迟地板（P=8，示例 c_sat=4，NVLink 级链路）")
for s_mib, tag in ((1, "1 MiB"), (64, "64 MiB")):
    s = s_mib * 2**20
    print(f"  {tag:>6}：", end="")
    for C in (1, 2, 4, 8, 16):
        print(f" C={C:<2} {chan_time(s, 8, C, 4):7.1f}us", end="")
    print(f"   地板 2(P-1)a={2*7*ALPHA:.0f}us")

# ===== 示例 3：算法/协议选择的自动判定（模拟 NCCL_DEBUG_SUBSYS=TUNING 的输出形状） =====
TREE_MAX = 256 * 2**10   # 示例：小于 256 KiB 走树（步数 O(log P)，付 alpha 更少）
LL_MAX   = 8 * 2**10     # 示例：小于 8 KiB 走 LL 协议

def tuning_line(nbytes):
    algo = "TREE" if nbytes < TREE_MAX else "RING"
    proto = "LL" if nbytes < LL_MAX else "SIMPLE"
    hi = max(0, min(31, nbytes // (1 << 20) - 1))
    return (f"NCCL INFO AllReduce: {nbytes} Bytes -> Algo {algo} proto {proto} "
            f"channel{{Lo..Hi}}={{0..{hi}}}")

print("\n示例 3：同一份梯度账本，不同消息大小选出的算法/协议（模拟 TUNING 日志行）")
for nbytes in (4 * 2**10, 1 * 2**20, 32 * 2**20):
    print("  " + tuning_line(nbytes))

三、练习#

  1. 实现：把示例 1 的 pair_bw 换成从 nvidia-smi topo -m 输出解析出来的矩阵（同一台机器跑一次，把矩阵抄进代码），重新算 100 MiB 的单环时间，并指出最慢一跳落在哪条边上。
  2. 解释：为什么"通道数从 4 加到 16，64 MiB 消息时间完全不变"，而 1 MiB 消息在 C=4 之后也不再变？分别用带宽项与延迟地板回答。
  3. 对比/验证：把示例 2 的 c_sat 改成 1 与 8，重算 64 MiB 在各通道数下的时间；解释 c_sat 在真实系统里对应什么（提示：NVLink 与 PCIe 的并行数据流数不同）。
  4. 思考：如果 TUNING 日志显示 4 KiB 的 AllReduce 选了 RING + SIMPLE，而预期的 TREE + LL 没被选中，列出三种原因和各自的验证方法。
