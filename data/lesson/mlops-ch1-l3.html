环境的确定性：种子能固定什么，以及可复现的三个等级#

这一节要解决什么#

前两节把"记什么"和"怎么连"解决了。现在做一个实验，验证一下这套流程的下限：

代码 commit 相同   →  ✓
数据版本相同       →  ✓
超参相同           →  ✓
torch.manual_seed(42)  →  ✓

然后在两台机器上各跑一次。结果：

机器 A 机器 B
最终 val_loss 0.3124 0.3287
评测 accuracy 0.874 0.869

差 0.5 个点。 同一份记录、同一个种子，却没有得到同一个数。于是三个问题立刻出现：

  1. 那 0.5 个点里，有多少是"真实差异"、多少是"数值噪声"？——如果不知道噪声的量级，任何小于它的结论都不可信。
  2. 我们应该追求"两次完全一致"（bitwise 相同）吗？为此要付出什么代价？
  3. 如果不能完全一致，验收标准应该是什么，才能既不放过真实退化、又不被浮点噪声反复误报？

这一节回答这三个问题，核心是两句话：

种子只能固定"你显式调用的随机数"，不能固定"框架与硬件替你做的选择"​

bitwise 复现是一个可选的最强等级，而不是默认的验收标准​

一、可复现性的三个等级#

先把"复现"这个词拆开。它其实是三个不同的目标，代价与敌人完全不同（沿用文献中的 Repeatability / Reproducibility / Replicability 三分法，并给出工程翻译）：

等级 谁执行 什么可以不同 结果要求 主要敌人 典型用途
L1 可重复（repeatable） 同一人 什么都不许不同：同机、同镜像、同进程配置 bitwise 相同 调度抖动、预热状态、非确定核函数 调试、定位崩溃、数值回归
L2 可复现（reproducible） 不同人 / 不同机器 硬件、驱动、库小版本、线程数 容差内一致（统计等价） 浮点归约顺序、算法选择、BLAS 实现 生产回归门禁、团队协作
L3 可复算（replicable） 不同人 + 不同实现 代码重写、数据重采样、流程重搭 结论一致（方向与量级） 结论本身脆弱（效应量太小） 论文、决策结论、跨团队验收

三个等级的关系是嵌套的：L1 ⇒ L2 ⇒ L3（能 bitwise 相同当然容差内一致，容差内一致当然不影响结论）。反向不成立。选择等级的判据是这个数字将被用来做什么：

需要 L1⟺差异本身就是研究对象（崩溃、精度回归、算子替换）

需要 L2⟺差异要用于"这次改动是否退化"的判决

需要 L3⟺差异要用于"这个结论是否成立"的判决

最常见的两类错误：

  • 用 L1 的要求做 L2 的事：把 CI 门禁写成 assert metric == baseline。结果是把"换了张卡"的正常数值波动判成失败，团队被迫关闭所有并行优化（性能掉 30%），最后开始给断言加 abs=0.01 的白名单 —— 等于悄悄退化成 L2，但没有任何统计依据。
  • 用 L3 的宽松做 L2 的事：只看"方向没变、量级差不多"就放过。于是 0.2 个点的真实退化被噪声掩盖，累积三个月后线上掉了 3 个点。

正确的姿势是把等级与判据一起写进实验规范，并且明确写出该等级下"允许的差异"。

二、依赖确定性：从声明到字节#

2.1 四个层次，成本递增#

层次 做法 确定性覆盖 遗留的不确定
声明 requirements.txt 写 torch>=2.4 无 一切
锁定 lockfile + 哈希校验（--require-hashes） 传递依赖的版本 系统库、CUDA、驱动、编译期选项
镜像 容器 digest（不是 tag）+ 固定基础镜像 用户态系统库、CUDA runtime 驱动、GPU 型号、硬件非确定性
全环境 镜像 + 驱动版本 + GPU 型号 + 线程/算法配置 到能保证 L1 的程度 调度与物理抖动（仍可能不同）

一个必须纠正的直觉：image:latest 不是锁定。tag 是可变的指针（第 2 节的三层分离在这里同样适用）：必须用 digest image@sha256:…。

2.2 依赖图的隐含项：容易被漏掉的四样#

隐含项 为什么影响结果 怎么记
BLAS 实现（MKL / OpenBLAS / oneDNN 的不同版本） 同一矩阵乘的不同分块与归约顺序 → 最后几位不同 → 长训练里被放大 进 lockfile + 环境指纹

PYTHONHASHSEED 这一条值得单独演示，因为它违反直觉：Python 默认对 str 的哈希加随机盐（防止哈希碰撞攻击），于是：

set(["a","b","c"])   # 迭代顺序在不同进程里可能不同

如果训练数据的读取顺序来自 set 或 dict（比如"按去重后的 id 集合遍历"），那么同一种子、同一份数据、不同进程会得到不同的样本顺序 —— 这足以让最终指标差出零点几个点。解法有两层：

治标:固定 PYTHONHASHSEED;治本:任何有语义的顺序都显式 sort，不依赖容器迭代顺序

2.3 环境指纹#

把上面这些压成一个可比较的字符串，就是 env_ref：

env_ref = sha256(canonical({
  lockfile_hash, image_digest, python_version, cuda, cudnn, cublas,
  blas_impl, driver_version, gpu_model, n_gpu, omp_threads,
  deterministic_flags: {...}
}))

注意 gpu_model 与 n_gpu 也在里面：换了卡型或卡数，结果可以合法地不同。把这两项放进指纹的意义是：当两个 run 的指标不一致时，先比 env_ref —— 不同就说明"这不是噪声，是不同环境"，归因优先级完全不同。

两个 run 的指标不可比⟺env_ref=env_ref′ ∧ 差异未被纳入容差模型

2.4 取舍：锁定 vs 更新#

策略 一侧 另一侧 做法
完全锁死 确定性高 安全补丁与性能改进进不来；一年后无法升级 锁 + 定期重锁，每次重锁跑等价性检验（4.3）
跟随最新 新特性 每周一个"为什么结果变了" 只在离线实验允许；生产与门禁必须锁定

三、随机性的三个来源，以及种子的管辖边界#

3.1 三张来源清单#

来源 例子 种子能固定吗 要靠什么
(a) 算法随机性 初始化、dropout、数据打乱、采样（temperature/top-p）、数据增强 能（只要每次调用顺序固定） 种子 + 调用顺序
(b) 并行归约顺序 梯度 allreduce、softmax 分母、LayerNorm、atomicAdd 累加 不能 确定性算法开关 / 固定线程块 / 单线程
(c) 库与硬件选择 cuBLAS 启发式选算法、cudnn.benchmark autotune、TF32、Winograd、kernel 版本 不能 环境指纹 + 显式 flags

这张表就是"固定种子还不够"的完整答案：(b) 与 (c) 完全不在种子的管辖范围内，而它们的影响会随着训练步数累积。

3.2 种子的正确用法：派生独立子流，而不是共用一条流#

最常见的错误实现是"一个全局种子走天下"：

torch.manual_seed(42)          # 全局
# 之后所有组件共用同一条 RNG 流：初始化、数据打乱、dropout、数据增强……

它的问题不是"不够随机"，而是耦合：任何一个组件多消耗一个随机数，后面所有组件的随机序列全部平移。具体后果：

  1. 改数据顺序就等价于改了 dropout：DataLoader 的 shuffle 顺序一变，dropout mask 全变；
  2. resume 会漂移：从 checkpoint 恢复时若只存种子，重新"快进"到第 k 步需要精确复现前 k 步的所有随机调用次数 —— 而变长序列、跳过的 batch、动态早停都会打破它；
  3. 并行 worker 之间相关性：多个 dataloader worker 若都用 seed，会拿到相同序列（重复的数据增强）。

正确做法是把随机性按用途域分离：

stream=R(base_seed,purpose),purpose∈{init,data,dropout,augment,worker_i}

这样"改数据顺序"只影响 data 流，不会挪动 dropout 流。工程上对应的实现是 NumPy 的 SeedSequence.spawn() / PyTorch 的 torch.Generator（每处一个）+ 显式的 worker_init_fn。

resume 必须保存 RNG 状态而不是种子：

resume 等价于连续训练⟺恢复 {Rinit​,Rdata​,Rdropout​,…} 的完整状态（含 dataloader 的迭代位置）

保存的是 getstate() 那样的状态对象（几百字节），不是 42。否则 resume 与"从头连续跑"就是两个不同的实验，却共用同一个 run id —— 这属于第 1 节的"记录污染"。

3.3 浮点非结合性：为什么"顺序"是结果的一部分#

浮点加法不满足结合律。经典反例：

(1+1016)−1016=0,1+(1016−1016)=1

同一个加法集合，两种顺序，结果是两个不同的数。这不是"精度不够"，而是浮点表示的本质：1 加到一个 1016 量级数上，在 fp64（有效位约 15–16 位十进制）里被完全舍掉。

对 n 个数的求和（从左到右累加），前向误差的经验界是：

∣s^−s∣≲(n−1)ui=1∑n​∣xi​∣,u=21​ulp=⎩⎨⎧​2−532−242−8​fp64fp32bf16（尾数 8 位）​

三个直接推论：

  1. 误差随 n 线性增长 → 归约的元素越多（大 batch 梯度、长序列 softmax、大词表），顺序差异造成的结果差异越大；
  2. 低精度放大误差：bf16 的 u 比 fp32 大 216 倍。这就是累积型算子（softmax、LayerNorm、loss 归约）必须用 fp32 累加的原因；
  3. 树形归约把 n 换成 logn：误差界变成 O(logn⋅u∑∣xi​∣) —— 并行归约本身不是坏事，是"不同的分块方式"让结果不同。

于是"不同线程数 → 不同结果"就成了必然：线程数决定分块，分块决定结合顺序。

3.4 硬件与库的非确定性#

现象 机制 处置
atomicAdd 非确定性 GPU 上多个线程对同一地址做浮点原子加，完成顺序不确定 改用确定性归约算子；或接受它（例如 embedding 梯度）
cudnn.benchmark=True 启动时对每个形状做 autotune，选出的算法可能随机器负载/显存状态变化 关闭 benchmark，或固定 torch.backends.cudnn.deterministic=True
TF32 / 混合精度默认值变化 某个版本把默认打开/关闭，同一代码换版本行为不同 显式设置；进环境指纹
cuBLAS 算法选择 启发式依赖形状与硬件；不同 workspace 配置会换算法 CUBLAS_WORKSPACE_CONFIG=:4096:8 + torch.use_deterministic_algorithms(True)
多卡 allreduce 拓扑感知算法（ring / tree / NVLS）随卡数变化 固定并行配置；把差异放进容差模型
稀疏/动态形状 kernel 例如 MoE 的 token 路由，不同长度触发不同 kernel 固定分桶（bucketing）策略

L1（bitwise）的成本在这里变得具体：torch.use_deterministic_algorithms(True) 会让一批算子退化到较慢的确定实现，并让另一些算子直接报错（没有确定实现）。典型代价是吞吐下降百分之几到几十（必须自己测，不要用别人的数），换来的是"两次运行逐位相同"。

L1 的代价=Δ吞吐+算子受限带来的返工;L1 的收益=差异可被完全归因

结论不是"永远开确定性模式"，而是：在需要它的场景（数值 debug、算子替换验收、崩溃复现）开，在长训练里用 L2 的容差判据代替。

四、当 bitwise 不可能时：容差带与统计等价#

4.1 验收标准应该对着"决策"，不是对着"比特"#

L2 的现实是：两次运行的指标总会有微小差异。判断"有没有退化"的正确形式不是"差异是否为零"，而是差异是否超出了噪声能解释的范围。

先量化噪声：用 n 个不同种子（其余全部相同）重复同一配置，得到 {Δ1​,…,Δn​}，则

Δˉ=n1​i∑​Δi​,s=n−11​i∑​(Δi​−Δˉ)2​,SE=n​s​

容差带取 ε=t1−α/2,n−1​⋅SE（小样本下用 t 而不是 1.96）。关键纪律：

\boxed{\varepsilon \text{ 必须来自历史重复实验的 } s，不能拍脑袋}}

拍脑袋的 ε 有两个方向都错的风险：设太小（如 0.001）→ 天天误报；设太大（如 0.05）→ 真实退化被放过。用种子重复估出的 s 通常比直觉大得多：同一配置换种子差 0.3–1 个点的模型，非常常见。

4.2 等价性检验（TOST）：把"差不多"变成可判定的假设#

"差异在容差内"这句话要能进入门禁，必须写成检验。用双单侧检验（Two One-Sided Tests, TOST）：

H0​: ∣μΔ​∣≥Δm​（不等价）H1​: ∣μΔ​∣<Δm​（等价）

其中 Δm​ 是业务上可接受的边界（例如"差 0.5 个点以内可以接受"）。两个单侧检验：

plow​=1−Ft​(SEΔˉ+Δm​​;n−1),pup​=Ft​(SEΔˉ−Δm​​;n−1),

pTOST​=max(plow​,pup​)

当 pTOST​<α 时判定"等价"。等价还可以等价地表达成区间包含：

(Δˉ−t1−2α,n−1​SE, Δˉ+t1−2α,n−1​SE)⊂(−Δm​, Δm​)

三个必须说清的细节：

  1. 这不是"证明没差异"，而是"证明差异小于 Δm​"。样本不足时 TOST 会给"不等价"（未证明），而不是给"通过" —— 这正是回归门禁需要的保守方向。
  2. Δm​ 必须来自业务损失，不能来自数据。它是"这个退化值多少钱"的翻译，第 2 章的门禁会展开。
  3. 样本量决定可检测边界：n 个种子下，若真实差为 Δ，检验力约由 Δ/(s/n​) 决定。想检测 0.2 个点的差异而种子间 s=0.4，就需要 n≈(2.8⋅s/Δ)2=31 个种子 —— 成本是必须提前算的。

n≳(Δ(z1−α​+z1−β​)s​)2

4.3 把"环境差异"纳入模型，而不是塞进容差#

一个常见的错误做法：机器不同导致差 0.4 个点，就把 ε 从 0.2 提到 0.6，于是门禁形同虚设。正确做法是分层：

εtotal​=同环境、换种子εseed​​​+换机器/库版本εenv​​​

并且要求：门禁对比的两个 run 必须 env_ref 相同（否则先用 env_ref 的差异解释，而不是放宽 ε）。这与第 2 节的环境指纹直接接上。

4.4 报告规范#

任何进入决策的数字，至少带三样：

metric: 0.874   n_seeds: 3   mean±sd: 0.872 ± 0.004   CI95: [0.862, 0.886]
env_ref: 5f82dcacc7f7e655   config_hash: 1c1455b9e5ca8c1b

单次运行的单个数字不能作为结论 —— 它不是"一个数据点"，而是"一个未知分布的样本量为 1 的观测"。第 4 节会说明，加上"从很多配置里挑最大值"这个动作之后，单个数字的偏差会有多大。

五、取舍#

决策 一侧 另一侧 判据
是否开确定性模式 可能 bitwise 相同、差异可归因 吞吐下降、部分算子不可用 数值 debug / 算子验收 ⇒ 开；长训练 ⇒ 关，用容差
单一全局种子 vs 派生流 代码简单 组件解耦、resume 稳定 一律派生流；这不增加成本，只是写法
锁死依赖 vs 定期更新 确定性 安全与性能 生产锁 + 每季度重锁 + 等价性检验
容差拍脑袋 vs 实测 s 快 可信 门禁相关的一律实测；探索阶段可临时用
bitwise 断言 vs TOST 失败信号明确 与"决策"对齐 只有 L1 场景用 bitwise；门禁用 TOST

代码：非结合性、种子派生、环境指纹、TOST 等价检验#

下面四段代码都是标准库实现，可直接运行。它们分别把 3.3 / 3.2 / 2.3 / 4.2 的论断变成可观察的现象。

运行：python3 mlops_ch1_l3.py
"""
from __future__ import annotations

# ==================================================================== ① 浮点非结合
print("=" * 78)
print("【1】浮点非结合性：结果取决于归约顺序，而不只是输入")


def sequential_sum(xs):
    s = 0.0
    for x in xs:
        s += x
    return s


def tree_reduce(xs, fanin):
    """模拟并行归约：每一层把相邻 fanin 个元素相加。fanin 由块大小/线程数决定。"""
    level = list(xs)
    while len(level) > 1:
        nxt = []
        for i in range(0, len(level), fanin):
            chunk = level[i:i + fanin]
            s = 0.0
            for v in chunk:
                s += v
            nxt.append(s)
        level = nxt
    return level[0]


# 经典反例：三种顺序，两个答案
trio = [1.0, 1e16, -1e16]
print(f"  左结合  ((1+1e16)-1e16) = {sequential_sum(trio):.1f}")
print(f"  右结合  (1+(1e16-1e16)) = {sequential_sum(list(reversed(trio))):.1f}")
print(f"  精确求和 math.fsum      = {math.fsum(trio):.1f}")
print("  → 同一组数，不同答案；'精度不够'不是解释，可表示范围才是")

# 规模效应：n 个随机数的求和，比较不同顺序与 math.fsum（精确求和）
rng = random.Random(7)
data = [rng.gauss(0, 1) for _ in range(100_000)]
exact = math.fsum(data)
u = 2.0 ** -53                      # fp64 单位舍入
bound = (len(data) - 1) * u * sum(abs(x) for x in data)
print(f"\n  n={len(data)}, 参考值 math.fsum = {exact:.12f}")
for name, val in (("顺序累加", sequential_sum(data)),
                  ("逆序累加", sequential_sum(list(reversed(data)))),
                  ("树形 fanin=2", tree_reduce(data, 2)),
                  ("树形 fanin=8", tree_reduce(data, 8)),
                  ("树形 fanin=1024", tree_reduce(data, 1024))):
    print(f"    {name:14s} 绝对误差 {abs(val - exact):.3e}  相对误差 "
          f"{abs(val - exact) / abs(exact):.3e}")
print(f"  前向误差界 (n-1)·u·Σ|x| = {bound:.3e}（fp64 的 u=2^-53）")
print("  → 界随 n 线性增长；树形把有效 n 换成 log n。若把 fp64 换成 bf16(u=2^-8)，")
print("    同一个界会放大 2^45 倍 —— 这就是累积型算子必须 fp32 累加的原因")

def dropout_mask_global(seed, steps, extra_draws_before):
    """模拟：一个全局 RNG 流。extra_draws_before 表示之前被别的组件消耗掉的随机数。"""
    r = random.Random(seed)
    for _ in range(extra_draws_before):
        r.random()
    return [round(r.random(), 4) for _ in range(steps)]


def dropout_mask_streams(seed, steps):
    """★ 正确做法：按用途派生独立流。改数据顺序不会挪动 dropout 流。"""
    r = random.Random(f"{seed}:dropout")
    return [round(r.random(), 4) for _ in range(steps)]


a = dropout_mask_global(42, 4, extra_draws_before=0)
b = dropout_mask_global(42, 4, extra_draws_before=3)     # 数据 shuffle 多消耗了 3 个
c = dropout_mask_streams(42, 4)
d = dropout_mask_streams(42, 4)
print(f"  全局流, 无额外消耗: {a}")
print(f"  全局流, 之前多消耗 3 个随机数: {b}")
print(f"  → 只因为数据顺序变了，dropout mask 全变: {a != b}")
print(f"  派生流 (dropout): {c}")
print(f"  派生流 (dropout, 重复): {d}  → 与数据顺序无关: {c == d}")


def resume_with_seed(seed, resume_at, draws_per_step):
    """只存种子 + 快进：每个 step 消耗的随机数必须完全相同。"""
    r = random.Random(seed)
    for t in range(resume_at):
        for _ in range(draws_per_step[t]):
            r.random()
    return round(r.random(), 6)


def resume_with_state(seed, resume_at, draws_per_step):
    """★ 存状态：从断点直接续，不依赖"前 k 步消耗了多少随机数"。"""
    r = random.Random(seed)
    for t in range(resume_at):
        for _ in range(draws_per_step[t]):
            r.random()
    return round(r.random(), 6)

def pyhash_of(s: str, hashseed: int) -> str:
    """在子进程里取 string hash —— 展示 PYTHONHASHSEED 造成的跨进程差异。"""
    env = dict(os.environ, PYTHONHASHSEED=str(hashseed))
    out = subprocess.run([sys.executable, "-c", f"print(hash({s!r}))"],
                         capture_output=True, text=True, env=env)
    return out.stdout.strip()

def _betacf(a, b, x, itmax=300, eps=3e-16):
    qab, qap, qam = a + b, a + 1.0, a - 1.0
    c, d = 1.0, 1.0 - qab * x / qap
    d = 1.0 / (d if abs(d) > 1e-30 else 1e-30)
    h = d
    for m in range(1, itmax + 1):
        m2 = 2 * m
        aa = m * (b - m) * x / ((qam + m2) * (a + m2))
        d = 1.0 + aa * d
        c = 1.0 + aa / c
        d = 1.0 / (d if abs(d) > 1e-30 else 1e-30)
        c = c if abs(c) > 1e-30 else 1e-30
        h *= d * c
        aa = -(a + m) * (qab + m) * x / ((a + m2) * (qap + m2))
        d = 1.0 + aa * d
        c = 1.0 + aa / c
        d = 1.0 / (d if abs(d) > 1e-30 else 1e-30)
        c = c if abs(c) > 1e-30 else 1e-30
        delta = d * c
        h *= delta
        if abs(delta - 1.0) < eps:
            break
    return h


def betainc(a, b, x):
    """正则化不完全 Beta 函数 I_x(a,b)，用连分式（Numerical Recipes 的方法）。"""
    if x <= 0.0:
        return 0.0
    if x >= 1.0:
        return 1.0
    lbeta = math.lgamma(a + b) - math.lgamma(a) - math.lgamma(b)
    front = math.exp(lbeta + a * math.log(x) + b * math.log1p(-x))
    if x < (a + 1.0) / (a + b + 2.0):
        return front * _betacf(a, b, x) / a
    return 1.0 - math.exp(lbeta + b * math.log1p(-x) + a * math.log(x)) \
        * _betacf(b, a, 1.0 - x) / b


def t_cdf(t, df):
    p = 0.5 * betainc(df / 2.0, 0.5, df / (df + t * t))
    return p if t <= 0 else 1.0 - p


def t_ppf(p, df):
    lo, hi = -200.0, 200.0
    for _ in range(200):
        mid = (lo + hi) / 2
        if t_cdf(mid, df) < p:
            lo = mid
        else:
            hi = mid
    return (lo + hi) / 2


# 自检：t 分布的三个已知分位点（与教科书表对照）
for df, p, expect in ((2, 0.975, 4.303), (9, 0.975, 2.262), (29, 0.95, 1.699)):
    got = t_ppf(p, df)
    print(f"  t_ppf({p}, df={df}) = {got:.3f}   教科书值 ≈ {expect}")
print("  → 自检通过后，检验结果才可信；否则统计量错一点，门禁结论就反了")


def tost(diffs, margin, alpha=0.05):
    n = len(diffs)
    d = statistics.fmean(diffs)
    s = statistics.stdev(diffs)
    se = s / math.sqrt(n)
    df = n - 1
    p_low = 1.0 - t_cdf((d + margin) / se, df)     # H0: μ ≤ -margin
    p_up = t_cdf((d - margin) / se, df)            # H0: μ ≥ +margin
    tc = t_ppf(1.0 - alpha, df)
    return {"n": n, "mean": d, "sd": s, "se": se,
            "p_tost": max(p_low, p_up), "equivalent": max(p_low, p_up) < alpha,
            "ci90": (d - tc * se, d + tc * se)}


def tolerance_from_seeds(diffs, alpha=0.05):
    """容差带必须来自种子重复实验的 s，而不是拍脑袋。"""
    n = len(diffs)
    se = statistics.stdev(diffs) / math.sqrt(n)
    return t_ppf(1 - alpha / 2, n - 1) * se

七处关键设计决策：

  1. tree_reduce 用 fanin 参数化分块，而不是写一个"顺序求和"和一个"并行求和"。原因是：真实差异不是"并行 vs 串行"，而是分块粒度（线程数、块大小）在变。参数化之后，你可以直接观察"fanin 从 2 改到 1024"的误差变化。
  2. 误差界与实测并列打印。实测的绝对误差比界小几个数量级是正常的（界是保守的最坏情况）；并列的意义是给出可推理的尺度。把 u 从 fp64 换成 bf16 时，界会放大 245 倍 —— 这是"累积算子必须 fp32 累加"的定量依据。
  3. dropout_mask_global 显式暴露"之前消耗了多少随机数"这个参数。这是全局种子耦合的直接演示：只要上游组件多抽一个随机数，下游序列全部平移。"改数据顺序 = 改 dropout"这件事在真实训练里天天发生，却极少被意识到。
  4. dropout_mask_streams 用 f"{seed}:dropout" 这样的域分离键。对应 NumPy 的 SeedSequence.spawn / 每处一个 torch.Generator：随机性按用途解耦，是零成本的确定性提升。
  5. resume_with_seed 与 resume_with_state 成对出现（当前两者对同一个 draws 列表是一致的，因为消耗模式没变）。演示要说明的是：一旦中间的 draws 因分批实现、早停、变长序列而变化，只存种子的快进就会漂移 —— 所以正确做法是保存 RNG state。这一条直接决定"断点续训"是不是同一个实验。
  6. env_fingerprint 把 gpu_model/n_gpu/omp_threads/deterministic 都算进去。理由是这些量合法地改变数值；把它们纳入指纹，才能让"指标不一致"先走"环境不同"这条分支，而不是无脑放宽容差（4.3）。
  7. t_cdf 用不完全 Beta 的连分式实现，并先用三个教科书分位点自检。统计检验的实现错误是最危险的错误 —— 它不会报错，只会给出错误的门禁结论。自检打印必须留在代码里。
  8. tost 同时给出 p 值与 90% 置信区间：区间更直观（是否包含 ±Δm​），p 更适合接门禁。场景 C 特意展示"样本不足 ⇒ 未证明等价"，因为回归门禁宁可保守。

小结#

  • "复现"有三个等级，代价与敌人各不相同：L1 可重复（同人同环境，bitwise）、L2 可复现（不同机器，容差内一致）、L3 可复算（不同实现，结论一致）。它们是嵌套关系；验收标准必须与等级匹配。用 L1 的标准做 L2 的事，会逼团队关掉并行优化再偷偷放宽断言。
  • 依赖确定性有四个层次：声明（无锁）→ 锁定（hash pin）→ 镜像 digest → 全环境（驱动 + 卡型 + 线程 + 算法开关）。image:latest 不是锁定。容易漏的四项：BLAS 实现、CUDA/cuDNN、PYTHONHASHSEED、线程数。
  • PYTHONHASHSEED 是隐藏的跨进程非确定性来源：它改变 set/dict 的迭代顺序，从而改变数据顺序。治本是有语义的顺序显式排序。
  • 种子只能固定算法随机性（初始化 / dropout / 打乱 / 采样），固定不了并行归约顺序与库/硬件选择（atomicAdd、cudnn autotune、cuBLAS 算法、TF32 默认值）。而且全局单一 RNG 流会让组件互相耦合：改数据顺序等于改 dropout。
  • 正确做法是按用途派生独立流（SeedSequence.spawn / 每处一个 torch.Generator），并且 resume 必须保存 RNG state 而不是 seed —— 保存种子只在"每步随机消耗量完全不变"时才成立。
  • 浮点不满足结合律：(1016+1)−1016=0 而 1016+(1−1016)=1；前向误差界 ≲(n−1)u∑∣xi​∣ 随 n 线性增长、随精度剧烈变化（bf16 的 u 是 fp32 的 216 倍）。并行归约本身没问题，"分块方式不同"才是差异来源。
  • 当 bitwise 不可能时，判据应当是统计的：用种子重复估出 s 与 SE，容差带 ε=t⋅SE（必须实测，不能拍脑袋），并用 TOST 把"差不多"变成 H1​:∣μΔ​∣<Δm​ 的假设检验；Δm​ 来自业务损失，样本量 n≳((z1−α​+z1−β​)s/Δ)2 必须提前算。
  • 环境差异要分层处理：env_ref 不同就先解释环境，而不是把 ε 从 0.2 放宽到 0.6 把门禁做废；εtotal​=εseed​+εenv​。
  • 任何进入决策的数字都要带 n、均值、s、CI 与 env_ref、config_hash。单次运行的单个数字是"样本量为 1 的观测"，不是结论。

下一节：到这里，我们能让同一份记录在不同机器上给出统计等价的数了。但真正的污染不来自机器，来自人：跑了 50 组配置挑最好的那组、不断调整评测集、只报告显著的对比。第 4 节要把"实验管理"落到统计上：族错误率、多重比较校正、winner's curse，以及配额与命名规范为什么是可信度的前提。
