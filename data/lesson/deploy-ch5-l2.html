批处理与并发调优#

上一课我们靠量化"省"资源，这一课靠调度把已有资源榨得更干。同样一张卡、同一个模型，参数调得对不对，吞吐能差出数倍。核心是理解连续批处理（continuous batching）下的几个关键旋钮，以及它们背后那条绕不开的曲线：并发越高吞吐越高，但延迟也随之恶化——你要做的，是在这条曲线上找到自己的甜点。

一、概念讲解#

1. 连续批处理为什么能榨干 GPU#

回顾推理优化课：传统静态批处理要求一个 batch 里的请求"同时开始、同时结束"，短请求必须等长请求，GPU 大量时间在空转。连续批处理则把 batch 当作一个动态池——每个调度步（step）推进 1 个 token，有请求结束就立刻让排队的请求补位，几乎无缝。于是 GPU 在 decode 阶段始终保持"满 batch"，吞吐大幅提升。

理解这一点后，调优的核心就变成了：给引擎多大的"批"、多长的"队列"，才能在吞吐和延迟之间取得平衡。

2. 四个关键旋钮#

参数 含义 调大 → 调小 →
max_num_seqs 同时服务的最大序列数（batch 上限） 吞吐↑，显存↑，延迟↑ 吞吐↓，延迟↓
max_num_batched_tokens 单步最多处理的 token 数（含 prefill chunk） prefill 更快，但单步更慢 单步更快，prefill 更慢
gpu_memory_utilization 显存中划给 KV Cache 的比例（0~1） 容纳更多 KV → 并发↑ 留更多余量，更稳
enable_chunked_prefill 长 prompt 的 prefill 是否分块 长 prompt 不阻塞 decode prefill 完整算完

几个直觉：

  • max_num_seqs 是最主要的吞吐/延迟旋钮。它决定 decode 阶段能同时推进多少个序列，直接影响吞吐上限；但并发越大，每个请求被"轮着"推进，单请求延迟自然上升；
  • gpu_memory_utilization 决定池子有多大。KV Cache 池越大，能同时容纳的序列越多；但给太高（如 0.98）可能 OOM，要留缓冲；
  • enable_chunked_prefill 是长文场景的救星。不开启时，一个 32K token 的长 prompt 会在 prefill 阶段独占 GPU，把其它请求的 decode 全部卡住；分块后长 prompt 被切成小块，与 decode 交替执行，短请求的 TTFT 明显改善。

3. 那条绕不开的曲线：吞吐 vs 延迟#

随着并发从 1 逐渐升高，会发生三件事：

  1. 吞吐先升：GPU 从"吃不饱"到"吃饱"；
  2. 吞吐触顶：GPU 饱和后，吞吐不再随并发增长（受算力/带宽上限约束）；
  3. 延迟持续恶化：请求在队列里排队等待的时间越来越长，P99 延迟指数式上升。

所以"甜点"通常在吞吐接近上限、但延迟仍满足 SLA 的那个并发区间。超过甜点继续加并发，只是把请求塞进更长的队列，吞吐不涨、体验崩坏。这就是为什么要做并发扫描（concurrency sweep）。

4. 排队理论的一点点直觉#

可以把服务近似看成一个排队系统：到达率 λ（每秒来多少请求）、服务率 μ（每秒能处理多少请求）。当 λ 接近甚至超过 μ（利用率趋近 100%）时，队列长度会急剧增长，平均等待时间发散——这就是"延迟爆炸"的数学根源。永远不要让你的服务长时间跑在 100% 利用率上，要给突发流量留出缓冲。

二、可运行示例#

示例 1：启动时设置调度参数#

# 显式指定批处理与显存相关参数
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --served-model-name llama-8b \
  --max-model-len 8192 \
  --max-num-seqs 64 \                 # 最多同时跑 64 个序列
  --max-num-batched-tokens 4096 \     # 单步最多处理 4096 token
  --gpu-memory-utilization 0.85 \     # 85% 显存划给 KV Cache
  --enable-chunked-prefill            # 长 prompt 分块 prefill

示例 2：并发扫描，画出吞吐-延迟曲线#

# -*- coding: utf-8 -*-
# 对同一服务做并发扫描：从低到高测吞吐与 P99 延迟，找到甜点区间
import time, asyncio, aiohttp

async def one_request(session, url, payload):
    t0 = time.perf_counter()
    async with session.post(url, json=payload) as r:
        await r.json()
    return time.perf_counter() - t0

async def sweep(base, model, concurrency, n_req=40):
    url = f"{base}/v1/chat/completions"
    payload = {"model": model,
               "messages": [{"role": "user", "content": "用 100 字介绍缓存。"}],
               "max_tokens": 150, "temperature": 0.0}
    async with aiohttp.ClientSession() as sess:
        sem = asyncio.Semaphore(concurrency)
        async def run():
            async with sem:
                return await one_request(sess, url, payload)
        t0 = time.perf_counter()
        latencies = await asyncio.gather(*[run() for _ in range(n_req)])
        wall = time.perf_counter() - t0
    latencies.sort()
    p99 = latencies[int(len(latencies) * 0.99)]
    return n_req / wall, p99 * 1000

async def main():
    print(f"{'并发':>4} | {'吞吐(req/s)':>12} | {'P99(ms)':>9}")
    for c in [1, 2, 4, 8, 16, 32, 64, 128]:
        thr, p99 = await sweep("http://localhost:8000", "llama-8b", c)
        print(f"{c:>4} | {thr:>12.2f} | {p99:>9.0f}")

asyncio.run(main())

观察输出：吞吐会先升后平，P99 则持续上升。找到"吞吐基本触顶、P99 仍低于你的 SLA 目标"的那个最大并发，就是你的甜点。

示例 3：对比开关 chunked prefill#

# 用一批"长 prompt + 短 prompt 混合"的请求压测，对比两种配置
# 配置 A：不开分块
vllm serve .../Llama-3.1-8B-Instruct --max-num-seqs 32
# 配置 B：开分块
vllm serve .../Llama-3.1-8B-Instruct --max-num-seqs 32 --enable-chunked-prefill

重点观察短请求的 P99 TTFT：开了分块后，短请求不再被长 prompt 的 prefill 卡住，TTFT 应显著下降。

三、练习#

  1. 用示例 2 的脚本，固定并发 64，把 max_tokens 从 150 改成 500，观察吞吐怎么变，解释"输出变长"为何降低吞吐（提示：decode 总步数变多）。
  2. 保持并发不变，把服务的 --max-num-seqs 从 64 降到 16，重跑扫描，观察吞吐上限是否下降，验证 max_num_seqs 是吞吐上限的主要约束。
  3. 构造一组"1 个 8000 token 长 prompt + 多个短 prompt"的混合请求，对比开关 enable_chunked_prefill 时短请求的 TTFT，说明分块的价值。
  4. 思考：一个客服机器人白天高峰 QPS 是凌晨低谷的 10 倍。从排队理论角度，为什么"按峰值常驻"比"按均值常驻"更安全？这会给下一课的成本核算埋下什么伏笔？
