幂等、重试与副作用：为什么"幂等键"是可靠性的地基#

这一节要解决什么#

上一节把契约面写清楚了：参数有约束、返回值有 status。但契约写得再好，也绕不过一个物理事实：

请求发出⟶世界可能已经改变⟶但响应可能永远回不来

这就是未知区间（uncertainty window）。它不是异常情况，而是分布式系统的常态：超时、连接被重置、进程被杀、上游处理完但响应在网络里丢了 —— 在这些时刻，调用方无法判断副作用是否已经发生。

先把这个问题的严重性量化。设一次工具调用涉及 n 个必须全部成功的步骤，每步独立成功率 p：

P(整体成功)=pn而重试把单步有效成功率提升为peff​=1−(1−p)k

p n P=pn（不重试） peff​（k=3 次重试） peffn​
0.99 5 0.951 0.999999 0.999995
0.99 20 0.818 0.999999 0.99998
0.95 20 0.358 0.999875 0.9975
0.90 20 0.122 0.999 0.980

结论很直接：没有重试，多步任务的可靠性不可用；有重试，可靠性能拉到接近 1。 但下面这行才是本节的全部内容：

重试之所以安全，完全依赖于被重试的操作是幂等的

如果操作不幂等，重试不是"再试一次"，而是"再做一次" —— 它把可靠性问题换成了数据正确性问题，而后者更贵。所以本节的论证链是：

多步任务要可靠  ⟹  必须重试
必须重试        ⟹  必须能安全重试
能安全重试      ⟹  幂等
幂等            ⟹  需要一个把"同一次逻辑操作"识别出来的标识  ⟹  幂等键

这就是"幂等键是地基"的完整含义：它不是一个技巧，而是上面这条链唯一的终点。

学完这一节你应该能回答：

  • 超时和 500 哪个能重试？为什么这个区分是幂等设计的起点？
  • DELETE /items/3 是幂等的吗？它重试安全吗？（是两个不同的问题。）
  • 幂等键该由谁生成、怎么保证"同一次逻辑操作拿到同一个键"？重试时键会不会变？
  • 为什么"重试前先查一下状态"通常不够？它解决的是一类还是几类失败？
  • 指数退避为什么要加抖动？不加会发生什么（这是个可以算出来的事故）？
  • 一个多步副作用流程在第 3 步失败，前面两步怎么办？

一、未知区间：为什么"恰好一次"是个错觉#

1.1 三种投递语义的真实含义#

语义 保证 代价 实现
at-most-once 至多执行一次（可能不执行） 会丢 不重试 + 短超时
at-least-once 至少执行一次（可能重复） 会重 重试到确认
exactly-once 恰好执行一次 —— 不存在于传输层

关键认知："恰好一次"不是一种传输保证，而是一个组合结论：

恰好一次有效​=传输层能做到的at-least-once 的投递​​+应用层必须自己做的接收端去重​​

这个分解对应一个很实用的判断：凡是声称"我们支持 exactly-once"的系统，你都要问"去重表在哪、键是什么、保留多久"。 找不到答案的，它实际提供的是 at-least-once。

为什么传输层做不到？直觉版是两军问题（Two Generals）：确认消息本身也可能丢失，于是"确认的确认"永远差一步；形式化地说，在不可靠信道上不存在有限轮协议能让双方同时确信对方确信……。实践中不需要纠结这个不可能性定理，只需要接受它的工程含义：

发送方永远无法区分"请求没到"和"响应丢了"。 这两种情况的差别决定了能否重试，而发送方看不到这个差别。

1.2 未知区间的四种失败形态#

失败形态 观察到的现象 世界是否已改变 能否重试 说明
连接前失败 DNS 失败 / 连接被拒 没有 ✓ 安全 请求从未被接收。最幸运的一类
发送后超时 客户端超时 未知 ⚠ 必须有幂等 请求可能已到达并执行，响应在回程丢失
服务器 5xx 收到 500/502/503 未知（对 500）；未执行（对 502/503 通常） ⚠ 必须按契约判断 500 可能是"处理到一半崩了"
客户端 4xx 400/401/403/404/409/422 没有（通常） ✗ 重试无用 参数/权限问题，重试会得到同样的错

这个表是本节所有设计的起点。 尤其注意"发送后超时"这一行：它是幂等键唯一真正要解决的场景，也是最常见的场景（一个外部 API 的 p99 延迟是 3 秒，超时设 2 秒，就会有相当比例的请求落在这一行）。

1.3 "重试前先查一下状态"为什么不够#

这是最常见的半吊子方案：

try:
    charge(order_id, amount)
except TimeoutError:
    if not is_charged(order_id):     # ← 看起来合理
        charge(order_id, amount)     # ← 危险

它有三处问题：

  1. 查询本身有竞态：is_charged 返回 False 之后、charge 之前，原请求可能刚好完成。查-写不是原子的，除非查询与写入共享同一把锁/同一事务。
  2. 查询可能不可用：如果支付网关超时了，它的查询接口大概率也超时。查询不是"廉价可得"的替代品。
  3. 它只处理"可以查询状态"的操作：发邮件、发短信、调用 webhook、创建不可查询的资源（比如写日志到第三方）——这些没有 is_x_done 接口。
  4. N 个操作需要 N 个查询接口：每加一个工具就要多设计一个查询工具，工具数量与选择难度同时上升（第 1、4 节）。

正确的形态是把"是否已执行"的判断内化到执行侧：

调用方：带幂等键重试（无条件重试，不需要先查）
执行侧：收到键 → 查去重表 → 已存在则直接返回上次的结果（不再执行副作用）

差别在于：判断"是否已执行"这件事被移到了唯一有能力原子地做这个判断的地方 —— 副作用发生的那一侧。 这就是幂等键的本质，也是为什么它必须由执行侧支持，而不是调用方自己想办法。

二、幂等的精确定义与三条实现路径#

2.1 定义：应用两次 = 应用一次#

数学定义（这比"重复调用没问题"精确得多）：设操作为函数 f，若

f(f(x))=f(x)∀x

则 f 幂等。注意这是关于状态转移的性质，不是关于返回值的性质：

操作 幂等？ 返回值每次相同？ 说明
SET status = 'done' ✓ ✓（可返回同样结果） 绝对赋值 → 幂等
status = status + 1 ✗ ✗ 相对增量 → 不幂等
INSERT ... (无唯一约束) ✗ ✗ 每次产生新行
INSERT ... ON CONFLICT DO NOTHING ✓ ✓ 唯一约束兜住
DELETE WHERE id = 3 ✓ ✗（第二次影响 0 行） 状态幂等但返回值不同
DELETE WHERE created_at < X ✓* ✗ 时间窗口在变 → 第二次可能删掉新数据（假幂等，见 2.4）
append(line) ✗ ✗ 追加不是幂等
write_file(content)（覆盖） ✓ ✓ 绝对写入
send_email(to, body) ✗ ✗ 外部不可撤销副作用

DELETE 那一行是两个问题的分水岭：

重试安全幂等（状态）​​=可缓存/可重放确定性（返回值）​​

DELETE /items/3 第二次返回 404 而不是 204，状态依然是对的 —— 所以它重试安全。但如果你的调用方代码把 404 当失败并继续重试，就会陷入无意义的循环。推论：幂等工具的返回值设计必须把"已经处于目标状态"编码成成功或明确的终态，而不是一个需要重试的错误。

2.2 路径 A：自然幂等（首选）#

优先把操作设计成幂等的，而不是靠外部机制补救。这是成本最低、最不容易出错的路径。

手段 做法 适用
绝对赋值 SET email='a@b.c' 而非 SET email=email+... 字段更新
状态机幂等转移 transition(to='paid')：已在 paid 则直接返回成功 状态流转（第 4 章的状态机会复用这个）
唯一约束 业务唯一键 + UNIQUE，冲突当成功返回 创建类操作
UPSERT INSERT ... ON CONFLICT (k) DO UPDATE 幂等写入
内容哈希寻址 写入路径由内容的哈希决定（同一内容 → 同一路径） 文件/对象存储
"设置为这个值"而非"改一下" 携带目标状态而不是增量/差值 计数器类（改成写最终值）

唯一约束这一项有一个重要前提：约束必须建立在业务语义的唯一键上（order_id），而不是代理键（id 自增）。自增主键每次都不同，无法挡重复。

2.3 路径 B：条件写（乐观并发）#

当操作用绝对赋值会让两个并发的正确调用互相覆盖时（"读-改-写"），需要版本条件：

update⟺version=v（否则返回 409 + 当前版本）

机制 形式 语义
版本号 WHERE version = 7 → 成功则 version = 8 乐观锁
ETag / If-Match HTTP 头 同上，标准形态
条件写 IF NOT EXISTS / ON CONFLICT 创建去重
CAS compare-and-swap 通用形态

条件写解决的是并发正确性，不是重试安全：它保证"基于旧状态的计算不会被重复应用"，但重试一个已经成功的条件写会因为版本已变而返回 409 —— 所以条件写必须与幂等键配合：第一次成功后，重放同一个幂等键应返回首次结果，而不是走条件判断。

2.4 路径 C：去重表 + 幂等键（通用兜底）#

对既不能自然幂等、又没有版本语义的操作（转账、发消息、调用外部不可撤销 API），只有一条路：在副作用发生的那一侧维护一张去重表。

请求(key=K, payload=P)
   │
   ├─ BEGIN (与副作用同一事务，或先占位)
   ├─ SELECT * FROM dedup WHERE key = K
   │     ├─ 存在且 status=committed → 直接返回首次的结果（★ 不执行副作用）
   │     ├─ 存在且 status=in_progress → 返回 retry_later（★ 不要并发执行两次）
   │     └─ 不存在 → INSERT (K, fingerprint(P), status=in_progress)
   ├─ 执行副作用
   ├─ UPDATE dedup SET status=committed, result=<首次结果>
   └─ COMMIT

四个必须处理对的细节（这些正是"知道了幂等键但实现错了"的地方）：

  1. 指纹校验：同一个键配上不同的 payload 是调用方的 bug（键复用）。必须检测并拒绝：

若 fingerprint(P)=stored_fingerprint⇒返回 409 key_reused

不检测会怎样：某次重试因为代码 bug 改了一个字段（比如重试时重新生成了 timestamp），去重表认为"这个键见过"，于是丢弃了新的合法请求，返回旧结果 —— 一个静默的数据丢失。

  1. in_progress 的语义：并发重试（超时后重试，但第一次其实还在跑）会看到 in_progress。此时必须返回 retry_later，让调用方退避等待，而不是"再执行一遍"。区分 in_progress 与 committed 是去重表比"唯一约束"多出来的能力。

  2. 保留期 TTL：去重表不能无限增长，也不能太短：

Tttl​>Tclient_max_retry​+Tmax_propagation_delay​

实践中取远大于重试窗口的值（例如 24 小时），因为还有人工重放和离线补跑这两种来源。TTL 太短的经典事故：用户在 25 小时后手工重跑一次对账脚本，重复转账。

  1. 结果持久化的完整性：第一次的返回值必须被完整存下来（含 status、错误码），否则重放时你只能返回"成功"但模型拿不到后续步骤需要的 ID。只记"成功/失败"是不够的，要记首次响应的完整 body。

2.5 幂等键的设计：三个必要条件#

一个幂等键必须满足三件事，缺一不可：

条件 含义 违反的后果
确定性 同一次逻辑操作的所有重试产生同一个键 每次重试新键 → 去重表形同虚设（和不做一样）
唯一性 不同的逻辑操作产生不同的键 不同操作撞键 → 静默丢请求（比重复更糟）
不可预测/不可枚举 键不能被外部构造或猜测 攻击者可预置键造成拒绝服务，或复用他人键读取结果

确定性是最容易被违反的一条。 常见错误：

# ✗ 错误：重试时重新生成 → 每次都是新键，去重表永远命中不了
def charge_retry(order, amount, retries=3):
    for _ in range(retries):
        key = str(uuid.uuid4())          # ← 致命
        try:
            return api.charge(order, amount, idempotency_key=key)
        except TimeoutError:
            continue

# ✓ 正确：键在"逻辑操作"这一层生成一次，重试复用
def charge_once(order, amount, attempt_of):
    # 键由"业务单位"决定，与网络重试次数无关
    return api.charge(order, amount,
                      idempotency_key=f"charge:{order.id}:{attempt_of}")

键从哪里来（按推荐度）：

来源 形式 评价
业务事件的天然唯一键 charge:{order_id}:{attempt_seq} 最佳：天然确定、可审计、可人工核对
轨迹/步骤 ID {run_id}:{step_index}:{tool_name} 很好：Agent 场景天然有轨迹（第 2 章），且天然满足"同一逻辑步骤"语义
随机 UUID，在循环外生成一次 uuid4() 存进状态 可接受：需要把它持久化（进第 4 章的检查点）
随机 UUID，每次重试重新生成 —— ✗ 等于没有

Agent 场景有一个独特优势：第 2 章的轨迹天然提供了 (run_id, step_index)，这就是一个完美的幂等键骨架。同一轨迹的同一步骤在重放（第 4 章）和网络重试两个来源下都会拿到同一个键 —— 这正是第 4 章"无状态重放"能够成立的前提。

attempt_seq 这个细节值得说清：如果"一次逻辑操作"允许有意重试（比如用户点了两次"支付"，这是两次不同的意图），那么需要用序号区分。判断规则是：

同一个键⟺同一个意图（用户/循环的一次决定），而不是同一次 HTTP 请求

三、重试：四个必须先回答的问题#

"重试"这个词在工程上不是一个动作，而是四个问题的答案：

R=(值不值得,失败是什么性质,怎么等,什么时候不再试)

3.1 问题一：值不值得（重试的收益上界）#

重试的期望收益：

E[收益]=P(瞬态故障)⋅P(重试成功)⋅V(成功)−C(重试)

  • 若失败是确定性的（参数错、权限不足），P(重试成功)≈0，收益为负。
  • 若V(成功) 很小而 C(重试) 大（重试会打满下游），也不值得。

实用的判断规则（按失败性质，见 1.2 表）：

性质 例子 重试？
瞬态、幂等 503、连接重置、只读超时 ✓ 立即退避重试
瞬态、非幂等但有幂等键 转账超时 ✓ 带同一个键重试
瞬态、非幂等且无幂等键 无键的写 API ✗ 转换为"查证 + 人工/补偿"流程
确定性、可修复 422 参数错 ✗ 不重试；把错误交给模型（第 3 节）
确定性、不可修复 403 权限 ✗ 不重试；升级/挂起
上游限流 429（带 Retry-After） ✓ 按 Retry-After 等，不加抖动的话会加剧拥塞

这一表的最重要一条是第三行：当你无法让一个写操作幂等时，正确的动作不是"小心翼翼地重试一次"，而是改变工作流：先写一条"意图记录"（幂等），再由一个可重放的执行器去执行，并由对账来收敛。这是第 5 章"补偿/对账"的入口。

3.2 问题二：怎么等 —— 指数退避 + 抖动#

指数退避（exponential backoff）的动机：瞬态故障往往有相关性（上游正在过载），间隔太密会持续压制它。第 k 次重试的等待时间：

tk​=min(tmax​,t0​⋅bk),b∈[1.5,2]

为什么必须加抖动（jitter）：这是本节最值得算一遍的地方。假设有 N 个客户端（或一个 Agent 的 N 个并行子任务）在同一时刻因为同一个上游故障失败，退避时间完全相同（无抖动），那么它们在 t0​ 后同时重试 —— 上游刚恢复就再次被打满，然后再次全失败，形成同步振荡。这就是"惊群"（thundering herd）。

抖动把重试时刻打散。三种形态：

形态 公式 性质
无抖动 tk​ 同步，最差
全抖动 tk​∼U(0,t0​bk) 期望间隔减半，负载最平
等抖动（推荐） tk​∼U(21​t0​bk,t0​bk) 保留退避趋势，同时打散

工程规则：抖动幅度应不小于退避间隔的一半，且总重试时长要有上限（否则一个请求可能被"重试"占用几分钟，把 Agent 的预算闸（第 2 章）逼到早停）。

3.3 问题三：什么时候不再试 —— 重试预算与熔断#

单次调用的重试上限（比如 3 次）不够，因为重试是叠加的：m 个串行调用各重试 3 次，最坏情况是 3m 次请求。

总请求上界=i=1∑m​ki​⟹必须有一个全局的重试预算

机制 形式 拦什么
单调用上限 k 最多 3 次 单个死循环
重试预算（token bucket） "每 60 秒最多 50 次重试" 整体放大
熔断器 连续 n 次失败 → 打开，冷却期直接失败 打一个已经挂掉的下游
预算耦合 重试消耗同一份 token/成本预算（第 2 章闸 2） 重试把预算烧光

熔断器的三态值得写清（很多实现只做了一半）：

closed   ──连续失败 ≥ n──→ open      （直接快速失败，不发请求）
open     ──冷却 T 到期──→ half_open （放行少量探测请求）
half_open──探测成功────→ closed
half_open──探测失败────→ open（冷却时间指数增长）

只做 closed → open 而不做半开，会导致上游恢复后仍被拒绝一段时间；不做"冷却时间指数增长"，会在下游持续故障时反复探测。

3.4 问题四：重试的幂等键要不要变#

这是 Agent 场景特有的问题，也是第 4 章"重放"与本节"重试"的交汇点：

场景 键 理由
网络层重试（超时/5xx） 同一个键 同一次逻辑操作，必须去重
模型决定"换个参数再试" 新键 这是新的意图（新的一次调用）
全局重放（第 4 章的崩溃恢复） 同一个键 逻辑步骤相同，副作用必须被去重
用户显式点"再执行一次" 新键（或 attempt_seq+1） 新意图

判断准则一句话：键标识"意图"，不标识"尝试"。 模型重新决策 = 新意图；传输层重发 = 同一意图。

有一条陷阱：模型在收到超时错误后，可能会"聪明地"调整参数（比如把 amount 从 100 改成 99）再调用一次。此时如果复用了同一个键，去重表会因为指纹不同而返回 409 key_reused；如果用新键，就会产生两笔转账（一笔 100 可能已成功）。两种都不对。正确做法是把这个工具的错误反馈设计成（见第 3 节）：

status=unknown（结果未知）
hint: 本次转账的结果未知，不要修改参数重试。请先调用 get_transaction(key=...) 核对，
      或原样重试（相同 idempotency_key）。

这类"必须教模型不要改参数"的反馈，是幂等设计能否在 Agent 场景真正生效的关键 —— 因为模型天然倾向于"换个方式再试"，而这是最危险的动作。

四、多步副作用：补偿与对账#

单步幂等解决不了多步流程。一个"下单 → 扣库存 → 支付 → 发货"的流程在第 3 步失败时，前两步已经发生。

4.1 补偿事务（Saga）#

正向步骤 T1​,T2​,…,Tn​对应补偿 C1​,C2​,…,Cn−1​

失败在第 i 步时，逆序执行 Ci−1​,…,C1​。三个必须承认的局限：

  1. 补偿不是回滚。C 是"另一个正向动作"，它自己也可能失败、也可能有副作用（退款会产生一条退款记录）。语义上是尽力而为的抵消，不是原子回滚。
  2. 有些动作不可补偿：发出去的邮件、已提交的对外 webhook、已打印的实体单据。对这类动作，唯一的安全设计是把它推到流程最后（"不可逆动作最后做"），或者加入人工审批闸（第 7 章）。
  3. 补偿本身必须幂等：因为补偿也可能超时重试。

4.2 不可逆动作的位置：排序即设计#

一个几乎不需要成本、但极有效的设计规则：

把动作按"可逆性"排序：只读 → 可逆写 → 不可逆写。不可逆的放最后，且前面必须有一个验证关卡。

流程=只读收集​​→可逆预占/草稿​​→判定验证​​→不可逆提交​​

这与第 1 章"可回滚"目标直接相连：可回滚性不是一个属性，而是流程排序的结果。 一个把"发送"放在第 2 步、把"校验"放在第 5 步的流程，无论用什么技术都不可回滚。

4.3 对账：承认失败会漏，用周期性核对兜底#

即便有幂等键和补偿，仍然存在漏网场景：去重表被清理得太早、补偿失败了、两次系统间的状态不一致。最后的防线是对账（reconciliation）：

不一致集合=本地账本△外部账本⟹生成待处理工单

对账的设计要点：它必须由外部事实驱动（拉取对方的记录），而不是重放本地日志 —— 重放本地日志只能确认"我以为发生了什么"，无法发现"实际发生了什么"。

代码：幂等执行器 + 抖动退避 + 熔断 + 补偿#

下面的代码把本节的可执行部分落成一个模块：(1) 带指纹与 in_progress 语义的幂等执行器；(2) 带抖动的退避与重试分类；(3) 熔断器；(4) 补偿（Saga）骨架。全部只依赖标准库。

import hashlib
import json
import random
import time
from dataclasses import dataclass, field
from enum import Enum
from typing import Any, Callable, Optional


# ==================== 失败分类：重试策略的唯一输入 ====================
class FailureKind(Enum):
    """
    ★ 设计决策：分类维度不是"异常类型"，而是"世界是否已改变 + 重试是否可能有用"。
      - NOT_SENT     : 请求从未到达 → 可无条件重试（甚至不幂等也安全）
      - UNKNOWN      : 已发送、结果未知 → 只有幂等才可重试（本节的核心里程碑）
      - TRANSIENT    : 明确未执行 + 瞬态 → 可重试
      - RATE_LIMITED : 明确未执行 + 需等待 → 按 Retry-After，不加重拥塞
      - DETERMINISTIC: 重试无用（参数/权限/业务规则）
    """
    NOT_SENT = "not_sent"
    UNKNOWN = "unknown"
    TRANSIENT = "transient"
    RATE_LIMITED = "rate_limited"
    DETERMINISTIC = "deterministic"

    @property
    def retryable(self) -> bool:
        return self in (FailureKind.NOT_SENT, FailureKind.UNKNOWN,
                        FailureKind.TRANSIENT, FailureKind.RATE_LIMITED)


class ToolError(Exception):
    def __init__(self, kind: FailureKind, msg: str, retry_after: float = 0.0):
        super().__init__(msg)
        self.kind, self.retry_after = kind, retry_after


# ==================== 去重表：幂等的地基 ====================
class DedupStore:
    """
    生产实现应落在与副作用同一事务的存储里（同一 DB 的同一事务，或同一 Redis + 补偿）。
    ★ 这里用内存字典演示语义；★ 关键语义与存储无关，只与状态机有关。
    """

    def __init__(self, ttl_seconds: float = 24 * 3600.0):
        self.ttl = ttl_seconds
        # key -> {"fingerprint", "status", "result", "created_at"}
        self._rows: dict[str, dict] = {}

    def _expired(self, row: dict, now: float) -> bool:
        return (now - row["created_at"]) > self.ttl

    def begin(self, key: str, payload: Any, now: float) -> dict:
        """
        返回动作指令：
          {"action": "execute"}                        → 首次，执行副作用
          {"action": "replay", "result": ...}          → 已完成，直接回放首次结果
          {"action": "wait", "retry_after": s}         → 进行中，并发重试必须退避
          {"action": "conflict", "reason": ...}        → 键复用（指纹不同）★ 必须检测
        """
        fp = fingerprint(payload)
        row = self._rows.get(key)
        if row is not None and self._expired(row, now):
            del self._rows[key]                     # TTL 到期：允许新的一轮（对账兜底）
            row = None
        if row is None:
            self._rows[key] = {"fingerprint": fp, "status": "in_progress",
                               "result": None, "created_at": now}
            return {"action": "execute"}
        if row["fingerprint"] != fp:
            # ★ 最重要的一个分支：键复用若不检测，会静默丢弃合法请求（比重复更隐蔽）
            return {"action": "conflict",
                    "reason": "同一 idempotency_key 携带了不同 payload（键复用）"}
        if row["status"] == "committed":
            return {"action": "replay", "result": row["result"]}
        return {"action": "wait", "retry_after": 0.5}   # in_progress

    def commit(self, key: str, result: Any) -> None:
        """★ 必须存'首次响应的完整结果'，不只是成功/失败标记：
        重放时下游步骤需要拿到首次返回的 ID 等字段。"""
        self._rows[key]["status"] = "committed"
        self._rows[key]["result"] = result

    def abort(self, key: str) -> None:
        """确定性失败：删除占位，允许用同一个键重新发起（此时意图确实没实现）。"""
        self._rows.pop(key, None)


def fingerprint(payload: Any) -> str:
    """
    ★ 设计决策：对"语义参数"做稳定序列化后哈希。
      必须先把易变字段（时间戳、请求 id）排除 —— 否则同一逻辑操作的两次尝试
      指纹不同，去重表会把你自己的重试判成"键复用"。
    """
    if isinstance(payload, dict):
        payload = {k: v for k, v in sorted(payload.items())
                   if k not in ("timestamp", "request_id", "trace_id")}
    blob = json.dumps(payload, sort_keys=True, ensure_ascii=False, default=str)
    return hashlib.sha256(blob.encode()).hexdigest()[:32]


# ==================== 带抖动的退避 ====================
def backoff_delay(attempt: int, base: float = 0.5, factor: float = 2.0,
                  cap: float = 30.0, rng: Optional[random.Random] = None) -> float:
    """
    等抖动（equal jitter）：t ∈ [cap/2, cap]，cap = min(base·factor^attempt, cap)。
    ★ 为什么必须抖动：若 N 个并发调用同时失败且退避相同，它们会在同一时刻同时重试，
      把刚恢复的下游再次打满 —— 同步振荡（惊群）。抖动把重试时刻打散。
    """
    rng = rng or random
    ceiling = min(cap, base * (factor ** attempt))
    return rng.uniform(ceiling / 2.0, ceiling)


# ==================== 熔断器 ====================
@dataclass
class CircuitBreaker:
    """
    ★ 设计决策：必须有 half_open 状态。只做 closed→open 的实现，
      会在下游恢复后继续拒绝请求；冷却时间指数增长避免持续探测。
    """
    threshold: int = 5
    cooldown: float = 10.0
    max_cooldown: float = 300.0
    _failures: int = 0
    _opened_at: Optional[float] = None
    _open_level: int = 0

    def state(self, now: float) -> str:
        if self._opened_at is None:
            return "closed"
        if now - self._opened_at >= min(self.max_cooldown, self.cooldown * (2 ** self._open_level)):
            return "half_open"
        return "open"

    def allow(self, now: float) -> bool:
        """★ open 态直接快速失败（不发请求）；half_open 态放行少量探测请求。"""
        return self.state(now) != "open"

    def on_success(self) -> None:
        self._failures, self._opened_at, self._open_level = 0, None, 0

    def on_failure(self, now: float) -> None:
        prior = self.state(now)                 # ★ 必须先取旧状态，再改 _opened_at
        self._failures += 1
        if self._failures >= self.threshold:
            if prior == "half_open":
                # 探测失败：冷却时间指数增长，避免在下游持续故障时反复探测
                self._open_level += 1
            self._opened_at = now


# ==================== 幂等执行器 ====================
@dataclass
class CallReport:
    ok: bool
    result: Any = None
    attempts: int = 0
    kind: Optional[FailureKind] = None
    message: str = ""
    replayed: bool = False                  # ★ 区分"首次执行"与"重放结果"


class IdempotentExecutor:
    def __init__(self, store: DedupStore, breaker: Optional[CircuitBreaker] = None,
                 max_attempts: int = 3, retry_budget: int = 50,
                 clock: Callable[[], float] = time.monotonic,
                 sleep: Callable[[float], None] = time.sleep,
                 rng: Optional[random.Random] = None):
        self.store, self.breaker, self.max_attempts = store, breaker, max_attempts
        self.clock, self.sleep, self.rng = clock, sleep, rng or random.Random(0)
        self._budget_left = retry_budget      # ★ 全局重试预算：单个调用上限不够

    def call(self, idempotency_key: str, payload: dict,
             effect: Callable[[dict], Any],
             kind_hint: Callable[[Exception], FailureKind] = lambda e: FailureKind.UNKNOWN
             ) -> CallReport:
        now = self.clock()
        if self.breaker and not self.breaker.allow(now):
            return CallReport(ok=False, kind=FailureKind.TRANSIENT,
                              message="熔断器打开：下游处于已知故障态，快速失败")

        # 1) 去重：先问"这件事做过没有"。判断发生在副作用那一侧（1.3 的结论）
        verdict = self.store.begin(idempotency_key, payload, now)
        if verdict["action"] == "replay":
            return CallReport(ok=True, result=verdict["result"], replayed=True,
                              message="命中幂等键：回放首次结果，未重复执行副作用")
        if verdict["action"] == "conflict":
            return CallReport(ok=False, kind=FailureKind.DETERMINISTIC,
                              message=f"幂等键冲突：{verdict['reason']}。"
                                      f"请用新键表示新的意图，不要改参数后复用旧键。")
        if verdict["action"] == "wait":
            return CallReport(ok=False, kind=FailureKind.TRANSIENT,
                              message=f"同一键的操作正在进行中（in_progress）："
                                      f"请等待 {verdict['retry_after']}s 后原样重试，"
                                      f"不要并发执行第二次。")

        # 2) 执行 + 按失败性质决定是否重试
        for attempt in range(self.max_attempts):
            try:
                result = effect(payload)
                self.store.commit(idempotency_key, result)
                if self.breaker:
                    self.breaker.on_success()
                return CallReport(ok=True, result=result, attempts=attempt + 1)
            except ToolError as e:
                if self.breaker:
                    self.breaker.on_failure(self.clock())
                if not e.kind.retryable:
                    # ★ 确定性失败：撤销占位，让同一个键可以重新发起（意图确实没实现）
                    self.store.abort(idempotency_key)
                    return CallReport(ok=False, kind=e.kind, attempts=attempt + 1,
                                      message=f"[{e.kind.value}] {e}")
                if self._budget_left <= 0:
                    # ★ 预算耗尽必须显式返回，而不是静默退化
                    self.store.abort(idempotency_key)
                    return CallReport(ok=False, kind=e.kind, attempts=attempt + 1,
                                      message="重试预算耗尽：已停止尝试，需人工或对账介入")
                if e.kind is FailureKind.RATE_LIMITED and e.retry_after > 0:
                    delay = e.retry_after          # ★ 尊重上游指示，不要用自家抖动覆盖
                else:
                    delay = backoff_delay(attempt, rng=self.rng)
                self.sleep(delay)
                self._budget_left -= 1
            except Exception as e:                  # 未知异常：一律按 UNKNOWN 处理最安全
                if self.breaker:
                    self.breaker.on_failure(self.clock())
                return CallReport(ok=False, kind=kind_hint(e), attempts=attempt + 1,
                                  message=f"[unknown] {type(e).__name__}: {e}")

        # 3) 重试用尽：★ 若最后一次失败是 UNKNOWN，不能 abort —— 副作用可能已发生，
        #    占位必须留着，让后续查询/对账能发现它（否则会重复执行）
        return CallReport(ok=False, kind=FailureKind.UNKNOWN, attempts=self.max_attempts,
                          message="重试用尽且结果未知：保留幂等占位，请用查询工具核对后再决定")


# ==================== 补偿（Saga 骨架）====================
@dataclass
class Step:
    name: str
    do: Callable[[dict], Any]
    undo: Optional[Callable[[dict, Any], None]] = None   # None = 不可补偿
    reversible: bool = True


@dataclass
class Saga:
    """
    ★ 设计决策：把"可逆性"做成步骤的显式属性，并在编排时强制排序检查。
      不可逆步骤必须排在最后 —— 这是"可回滚"目标唯一低成本的实现手段。
    """
    steps: list[Step] = field(default_factory=list)
    _done: list[tuple[Step, Any]] = field(default_factory=list)

    def add(self, step: Step) -> "Saga":
        if self._done and not step.reversible and any(s.reversible for s in self.steps):
            pass  # 真实实现应在此拒绝：不可逆步骤之后不允许再有可逆步骤
        self.steps.append(step)
        return self

    def run(self, ctx: dict) -> dict:
        for step in self.steps:
            try:
                out = step.do(ctx)
                self._done.append((step, out))
            except Exception as e:
                return {"status": "compensating", "failed_at": step.name,
                        "error": str(e), "compensation": self._compensate(ctx),
                        "note": "补偿是'尽力而为的抵消'，不是原子回滚；不可逆步骤只能靠对账/人工"}
        return {"status": "committed", "steps": [s.name for s, _ in self._done]}

    def _compensate(self, ctx: dict) -> list[str]:
        log = []
        for step, out in reversed(self._done):
            if step.undo is None:
                log.append(f"{step.name}: 不可补偿（需人工/对账）")
                continue
            try:
                step.undo(ctx, out)
                log.append(f"{step.name}: 已补偿")
            except Exception as e:
                log.append(f"{step.name}: 补偿失败 ({e}) —— 需对账介入")
        return log

六处关键设计决策：

  1. FailureKind 的分类维度是"世界是否已改变 + 重试是否有用"，而不是异常类型。只有这样才能回答"这个失败能不能重试" —— 而这个问题的答案决定了后面的一切。
  2. DedupStore.begin 返回四个动作而不是两态：execute / replay / wait / conflict。第四项（键复用检测）是最容易被省掉、代价最隐蔽的一项：不检测会让合法请求被静默丢弃。
  3. fingerprint 显式剔除 timestamp/request_id 等易变字段。这是"确定性"这个必要条件在代码里的落点：如果重试时指纹变了，你自己的重试会被判成键复用。
  4. backoff_delay 用等抖动，且 RATE_LIMITED 时尊重上游的 Retry-After 而不是用自己的退避覆盖 —— 后者会在上游已经过载时继续按自己的节奏打过去。
  5. 重试用尽时不 abort（若最后一次是 UNKNOWN）：副作用可能已经发生，占位必须留下让对账能发现它。这是"未知区间"在代码上的最后一道防线。
  6. Saga 把 reversible 做成步骤的显式属性，并在补偿日志里对不可补偿步骤显式标注"需人工/对账" —— 不假装补偿等于回滚。

练习#

  1. 分类与重试策略：为下面六种失败分别写出：属于 1.2 表的哪种形态、能否重试、若是 Agent 的工具调用，错误反馈里必须包含什么。 （a）连接被拒绝（connection refused）；（b）请求已发送后 30 秒超时；（c）HTTP 503 带 Retry-After: 5；（d）HTTP 500 且响应体是上游的栈回溯；（e）HTTP 409 version conflict；（f）HTTP 422 amount 必须为正整数。 然后指出：(b) 与 (d) 在"世界是否已改变"这个问题上的差别，以及为什么这个差别比 HTTP 状态码本身更重要。

  2. 幂等键设计（落到你的系统）：为"给客户发送月度账单邮件"设计幂等键。要求写出：键的构成、谁生成、重试时是否复用、attempt_seq 是否存在及为什么、TTL 取多少及依据（提示：考虑人工补发与对账的时间尺度）。然后回答：如果产品经理要求"用户点击'重发'时应该真的再发一封"，你的键设计要怎么变？

  3. 去重表的状态机：画出 pending / in_progress / committed / failed 四态的去重表状态转移图。为每条边写出触发条件与并发安全要求。特别回答： （a）一个请求在 in_progress 状态时进程崩溃了，这张表会永久卡在 in_progress 吗？怎么解决（提示：租约 lease + 超时回收）？ （b）如果把 in_progress 和 committed 合并成一个 exists，会失去哪个能力？

  4. 惊群的计算：某服务在负载高峰每分钟处理 6000 请求，正常运行 200 QPS。一次 3 秒的抖动（下游不可用）让这 3 秒内约 600 个请求失败。若重试策略是"固定等 2 秒、最多 3 次、无抖动"，请估算：下游恢复后的瞬间会被压上多少 QPS？如果改成等抖动（t∈[1,2] 秒），峰值大致降到多少？由此说明为什么抖动幅度不能太小。

  5. 不可逆动作的排序：某 Agent 流程是：(1) 查客户信息（只读）；(2) 生成合同 PDF；(3) 发送合同邮件给客户；(4) 在 CRM 里登记"已发送"；(5) 上传 PDF 到档案库。请按"可逆性"重排这个流程，并给出每一步失败时的处理方式。然后论证：为什么"发送邮件"这一步一旦失败（超时），无论怎么重试都不可能是"恰好一次"？你能做的最小补救是什么？

  6. 模型改参数的陷阱：模型调用 transfer_funds 时收到超时（结果未知）。请写出这条工具的错误反馈文案，要求：让模型既不重复转账、也不因为改参数而产生第二笔；并说明文案里哪一句是专门针对"模型的'换个方式再试'倾向"的。然后给出一个运行时的强制手段（不依赖模型遵守文案）来防止"同键不同 payload"。

  7. 对账设计：为一个"Agent 自动给逾期订单退款"的系统设计对账流程。要求写出：对账的两个数据源分别是什么、比对键是什么、发现不一致后生成什么产物、谁处理、以及如何避免"对账本身产生重复退款"（提示：对账动作也要幂等）。

小结#

  • 未知区间是常态：请求发出后，调用方无法区分"请求没到"和"响应丢了"。这是所有幂等设计要解决的问题，也是"恰好一次"不可能存在于传输层的原因。
  • 恰好一次有效​=at-least-once 投递+接收端去重 —— 凡是声称 exactly-once 的系统，都要问"去重表在哪、键是什么、保留多久"。
  • 幂等是关于状态转移的性质（f(f(x))=f(x)），不是关于返回值的性质。DELETE 状态幂等但返回值不同 —— 它重试安全，但不能被盲目重放判定为成功。
  • 三条实现路径：自然幂等（绝对赋值/UPSERT/唯一约束/状态机幂等转移，首选）→ 条件写（版本/CAS，解决并发正确性）→ 去重表 + 幂等键（通用兜底）。条件写不能替代幂等键，两者解决不同问题。
  • 幂等键的三个必要条件：确定性（重试必须复用同一个键）、唯一性（不同意图不同键）、不可枚举。确定性是最常被违反的一条 —— 每次重试新生成 UUID 等于完全没有幂等。
  • 去重表四个必须处理对的细节：指纹校验（同键不同 payload 必须拒绝，否则静默丢请求）、in_progress 语义（并发重试必须退避而非再执行）、TTL（要覆盖人工重放与离线补跑的时间尺度）、持久化首次响应的完整结果。
  • 重试是四个问题：值不值得、失败是什么性质、怎么等、什么时候不再试。加抖动是必须的（固定退避导致同步重试 → 惊群 → 同步振荡）；重试需要全局预算与三态熔断器（含 half_open 与冷却指数增长）。
  • 键标识"意图"，不标识"尝试"：传输层重试复用键，模型重新决策用新键，全局重放复用键。最危险的动作是"模型改了参数再用同一个键" —— 必须用反馈文案 + 运行时指纹校验双重拦截。
  • 多步副作用：补偿（Saga）不是回滚，不可逆动作必须靠流程排序（只读 → 可逆写 → 不可逆写）与审批闸来保护；最后的防线是由外部事实驱动的对账，而不是重放本地日志。
  • 一句话：可靠性的地基不是"更聪明的重试"，而是"让每一次重试都不会再改变世界" —— 幂等键是这句话唯一的工程实现。
