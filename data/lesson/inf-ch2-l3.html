PagedAttention#

上一课我们算清了 KV Cache 的账，但还没回答一个更隐蔽的问题：这些 KV Cache 在显存里怎么放？ 如果给每个请求预先分配一大块"最大可能长度"的连续显存，就会产生大量碎片和浪费。PagedAttention 把操作系统的"分页"思想搬进了 KV Cache 管理，是 vLLM 吞吐能提升 2–4 倍的核心技术之一。学完本课，你应当能画出 PagedAttention 的 block table 结构，并说出它解决的三个问题。

一、概念讲解#

1. 朴素分配的三大浪费#

如果沿用"每个请求预分配一整段连续显存"的做法，会遇到三个问题：

  • 内部碎片：请求实际只生成了 50 个 token，却按上限预留了 2048 个 token 的空间，中间的差就是白白占用的碎片；
  • 外部碎片：不同请求的缓存反复分配/释放，显存被切成许多用不上的小块，即使总量够也拼不出一块大的；
  • 无法共享：两个请求有相同的 prompt 前缀（比如同一个系统提示词），朴素做法各存一份，重复占用。

2. 核心思想：把 KV Cache 切块、按需分配#

PagedAttention 借鉴操作系统的虚拟内存分页：

  1. 把 KV Cache 划分成固定大小的 block（页），例如每 block 存 16 个 token 的 KV；
  2. 一个请求的 KV Cache 由若干个非连续的 block 组成，用一张 block table（页表） 记录"逻辑 token 位置 → 物理 block 地址"的映射；
  3. 请求需要更多空间时，按 block 动态申请，只申请当前真的需要的量，几乎不产生内部碎片；
  4. 请求结束，block 归还到空闲池，可被新请求立刻复用。

注意力计算时，GPU 通过 block table 找到每个 token 的 KV 在哪，按块做 kernel 计算——结果与连续存储完全一致，只是物理位置不同。

3. 三个直接收益#

  • 显存利用率大幅提升：碎片消除后，同一张卡能装下更多并发请求（论文报告可提升至 2–4 倍 batch），吞吐随之上升；
  • 内存共享：block 是只读的、可复制的，多个请求共享同一个前缀时，可以让它们的 block table 指向同一批物理 block（写时复制），beam search 或并行采样也能共享 prompt 前缀；
  • 灵活调度：因为缓存是分块的，continuous batching（第 1 章）里请求的动态进出、KV 的动态增删都变得非常自然。

4. 一个直观类比#

把 KV Cache 想象成一本活页笔记本：普通做法是给每个学生发一本固定页数、装订死的本子（会浪费、不好复用）；PagedAttention 是发可插拔的活页，用到几页发几页，用完回收给下一个人，两个人还能共用同一页笔记。页表（block table）就是"这本笔记哪些内容在第几页"的目录。

二、可运行示例#

下面的 Python 用简化的 block 池 + 页表，模拟 PagedAttention 的按需分配、碎片对比与前缀共享。

# -*- coding: utf-8 -*-
# 模拟 PagedAttention：block 池 + 页表，对比朴素分配

BLOCK_TOKENS = 16  # 每个 block 存 16 个 token 的 KV

def naive_memory(requests, max_len=2048):
    """朴素分配：每个请求预分配 max_len 的连续空间。"""
    return len(requests) * max_len

def paged_memory(requests):
    """PagedAttention：按实际长度向上取整到 block，且共享相同前缀。"""
    prefix_blocks = {}   # 前缀内容 -> 已分配的 block 列表
    total = 0
    for prompt, gen in requests:
        total_len = prompt + gen
        blocks = (total_len + BLOCK_TOKENS - 1) // BLOCK_TOKENS
        # 若 prompt 前缀已存在，则那部分 block 可共享（写时复制）
        if prompt not in prefix_blocks:
            prefix_blocks[prompt] = True
            total += blocks
        else:
            # 前缀已共享，只新增"生成部分"的 block（简化）
            gen_blocks = (gen + BLOCK_TOKENS - 1) // BLOCK_TOKENS
            total += gen_blocks
    return total

# 20 个请求，多数共享同一个 128 token 的系统提示词，生成长度随机
requests = [("SYS:" * 32, 200) for _ in range(20)]  # prompt 约 128 token
naive = naive_memory(requests)
paged = paged_memory(requests)
print(f"朴素分配（预留2048）：{naive} token 空间")
print(f"PagedAttention（按需+共享）：{paged} token 空间")
print(f"显存节约：{(1 - paged/naive)*100:.0f}%")

# 展示一张请求的页表结构
print("\n某请求的页表示例（逻辑位置 -> 物理 block）：")
prompt, gen = requests[0]
total_len = prompt + gen
blocks = (total_len + BLOCK_TOKENS - 1) // BLOCK_TOKENS
for i in range(blocks):
    print(f"  token [{i*BLOCK_TOKENS:>3} .. {min((i+1)*BLOCK_TOKENS, total_len):>3}] -> block #{100+i}")

运行后你会发现，PagedAttention 按实际用量分配、且共享相同前缀时，能省下大量显存——这正是它能把更多请求塞进同一张卡的原因。

三、练习#

  1. 改 block 大小：把 BLOCK_TOKENS 从 16 改成 8、32，观察总分配量的变化，讨论 block 太大/太小的各自缺点（太大→内部碎片，太小→页表开销大）。
  2. 去掉共享：把 paged_memory 里"前缀共享"那段改成"每个请求都独立分配"，显存节约率还剩多少？说明"共享前缀"这一项对系统提示词场景的价值。
  3. 加动态增长：模拟一个请求先生成 100 再继续生成 200 token，展示它如何"边生成边追加 block"，体会按需分配对连续批处理的配合。
  4. 思考：PagedAttention 的 block table 本身也要占显存（页表开销）。在什么极端场景下，页表开销可能超过它的收益？结合第 2 课的公式谈谈。
