多流与异步：stream、事件与并发执行#

到现在为止，我们的 kernel 都是"排队执行"的：H2D 拷完 → kernel 算 → D2H 拷回，一步等一步。可这三步用的根本不是同一批硬件——拷贝走拷贝引擎（copy engine）与内存带宽，kernel 用 SM 与寄存器，于是顺序执行时总有一半机器在闲着。这一课讲怎么用 stream（流）把它们叠起来，怎么用 event（事件）表达"谁等谁"，以及为什么很多人"写了双流却量不到任何 overlap"：问题几乎总出在默认流的隐式同步语义上。

一、概念讲解#

1. stream 是什么：一条按序执行的队列#

stream 是一串按提交顺序执行的操作队列：同一个 stream 内严格 in-order（前一个操作没完成，后一个不会开始），不同 stream 之间没有顺序关系，因此可能并发。kernel<<<grid, block, 0, stream>>>(...) 里的第四个参数就是 stream；cudaMemcpyAsync 也接受 stream 参数。

能让两条 stream 真正重叠的前提是"资源不冲突"：

资源 谁在用 能否与别的操作并行
SM / 寄存器 kernel 两个都占满 SM 的 kernel 不会重叠；各占一半才可能
拷贝引擎 H2D/D2H 拷贝 与 SM 上的 kernel 可并行，与另一条拷贝串行
内存带宽 拷贝与访存型 kernel 共享，抢起来会互相拖慢
依赖关系 你自己写的事件 有依赖就必须等，与资源无关

这就是本课代码里模型的形状：一条拷贝引擎 + 两个"SM 槽位"，于是"拷贝与 kernel 重叠"能发生，而"两个拷贝"永远串行。

2. 异步拷贝的真正门槛：pinned memory#

官方文档明确要求：要真正异步，主机内存必须是 page-locked（pinned，锁页） 的，否则 cudaMemcpyAsync 可能退化成同步拷贝，stream 参数形同虚设。原因是设备要直接访问主机内存做 DMA，操作系统不能把这页换出去。常用做法是用 cudaHostAlloc/cudaMallocHost 分配（或对已有内存用 cudaHostRegister 注册），代价是这类内存分配慢、占用物理内存、过多会拖慢整个系统——所以常见模式是分配一小块 pinned 缓冲做流水线，别把整个数据集都钉住。

3. 最常见的坑：legacy 默认流会把并发"抹平"#

如果你不指定 stream，操作落在默认流（legacy default stream）上。它的语义是：默认流里的操作与所有阻塞流（blocking stream）互相隐式同步——默认流中的 kernel 没结束，别的流里的活就不能开始（反之亦然）。于是"一半任务用默认流、一半用自定义流"的写法量不到任何 overlap。官方文档把这件事拆成三节讲清楚：Blocking and Non-Blocking Streams、Legacy Default Stream、Per-Thread Default Stream。出路有两条：

  1. 显式创建 stream 并全程使用（cudaStreamCreate，或 cudaStreamCreateWithFlags(..., cudaStreamNonBlocking) 让流不与默认流隐式同步）；
  2. 用 per-thread 默认流（编译选项 --default-stream per-thread），每个 host 线程有独立的默认流，彼此不再互相等待。

4. event：跨 stream 的依赖与 GPU 时间线计时#

event（事件） 是一个可被"记录"到某条 stream 里的时间标记：cudaEventRecord(ev, stream) 之后，cudaStreamWaitEvent(otherStream, ev) 就让另一条 stream 等到这个点再继续；cudaEventSynchronize(ev) 让主机等；cudaEventElapsedTime(&ms, a, b) 量两个事件之间的 GPU 时间。

三个容易踩的细节：

  • 计时前必须同步。cudaEventElapsedTime 要求两个事件都已完成，否则读到的是垃圾值（常见现象：量出 0 ms）。
  • 事件量的是 GPU 时间线，不是主机墙上时间：它把重叠的执行也算成"同时发生"，这正是分析流水线想要的口径。
  • 依赖要写全。只把任务丢进不同 stream 而不写事件依赖，可能读到没准备好的数据（正确性问题，性能调优前先保正确）。

5. 常见坑#

  • 在循环里 cudaDeviceSynchronize()：一次同步就把流水线打平，前面排的并发全白费。
  • 假异步：用未 pinned 的主机内存做 cudaMemcpyAsync，看起来异步、实际同步。
  • 假设"不同 stream 一定并发"：资源冲突、显存不够、依赖未满足时都不会重叠，必须实测。
  • 不测就信：overlap 要用 timeline 工具看（Nsight Systems 的 GPU timeline），或至少用事件对比"总耗时 vs 各段耗时之和"。
  • 流开太多：硬件侧能真正并发的队列数有限（与 CUDA_DEVICE_MAX_CONNECTIONS 这类设置有关，见官方 Environment Variables），流数量远大于能并发的操作数只是增加调度开销。

二、可运行代码示例#

下面用一个纯 Python 的"资源槽 + 事件依赖"离散事件调度器，把 stream 并发算出来：哪些操作能叠、瓶颈在拷贝引擎还是 SM、完工时间是多少。模型很简单——一条拷贝引擎、两个 SM 槽位、同一 stream 内严格串行、跨 stream 靠显式依赖——但足以解释真机上的典型现象。

# ---- 无 GPU 模拟 stream 并发：资源槽 + 事件依赖的离散事件调度（纯 Python）----
CAP = {'copy': 1, 'sm': 2}     # 1 条拷贝引擎 + 2 个 SM 资源槽（每个 kernel 占 1 槽）


def simulate(tasks, cap=CAP, legacy_default=False):
    """tasks: [{'name','stream','res','units','dur','deps'}]；同一 stream 内按列表顺序串行。"""
    for i, t in enumerate(tasks):
        t['i'] = i
        t['seq'] = sum(1 for u in tasks[:i] if u['stream'] == t['stream'])
    for t in tasks:                    # legacy 默认流：与非默认流互相隐式同步
        if legacy_default and t['stream'] != 'default':
            t['deps'] = list(t['deps']) + [u['i'] for u in tasks if u['stream'] == 'default']

    done, running, free, plan = set(), {}, dict(cap), {}
    time, horizon = 0, 500
    while len(done) < len(tasks) and time <= horizon:
        for i, (end, t) in [x for x in running.items() if x[1][0] <= time]:
            free[t['res']] += t['units']      # 任务结束，归还资源
            done.add(i)
            del running[i]
        for t in tasks:
            if t['i'] in done or t['i'] in running:
                continue
            if any(u['stream'] == t['stream'] and u['seq'] < t['seq']
                   and u['i'] not in done for u in tasks):
                continue                       # 同 stream 的更早的活还没完
            if any(d not in done for d in t['deps']):
                continue                       # 事件依赖未满足
            if free[t['res']] < t['units']:
                continue                       # 资源不够
            free[t['res']] -= t['units']
            running[t['i']] = (time + t['dur'], t)
            plan[t['i']] = (time, time + t['dur'])
        time += 1
    return plan, max(e for _, e in plan.values())


def chart(tasks, plan):
    lanes = {r: [[] for _ in range(CAP[r])] for r in CAP}
    for t in tasks:
        s, e = plan[t['i']]
        for lane in lanes[t['res']]:
            if all(not (s < oe and os_ < e) for os_, oe, _ in lane):
                lane.append((s, e, t['name']))
                break
    span = max(e for _, e in plan.values())
    print('    时间 →   ' + ''.join(str(i % 10) for i in range(span)))
    for r, ls in lanes.items():
        for k, lane in enumerate(ls):
            row = ['.'] * span
            for s, e, name in lane:
                for x in range(s, e):
                    row[x] = name[0]
            print(f'  {r}[{k}]      ' + ''.join(row))
    print('  图例：' + '  '.join(
        f'{t["name"][0]}={t["name"]}' for t in sorted(tasks, key=lambda t: t['i'])))


def run(title, tasks, **kw):
    plan, makespan = simulate(tasks, **kw)
    print(f'=== {title} ===')
    for t in sorted(tasks, key=lambda t: plan[t['i']]):
        s, e = plan[t['i']]
        print(f'  {t["name"]:<7} stream={t["stream"]:<5} {t["res"]:<5} '
              f'{s:>3}→{e:<3}（{t["dur"]}ms）')
    chart(tasks, plan)
    print(f'  完工时间 = {makespan} ms\n')
    return makespan


def chunk(tag):
    """一块数据三步：H2D 拷贝 → kernel → D2H 拷贝。"""
    return [dict(name=f'H2D_{tag}', stream=tag, res='copy', units=1, dur=2, deps=[]),
            dict(name=f'K_{tag}', res='sm', units=1, dur=3, deps=[f'H2D_{tag}']),
            dict(name=f'D2H_{tag}', res='copy', units=1, dur=2, deps=[f'K_{tag}'])]


def build(spec):
    """spec: [(stream, tag)]；deps 用名字写，这里统一换成下标。"""
    tasks = []
    for stream, tag in spec:
        for t in chunk(tag):
            t['stream'] = stream
            tasks.append(t)
    idx = {t['name']: i for i, t in enumerate(tasks)}
    for i, t in enumerate(tasks):
        t['i'] = i
        t['deps'] = [idx[d] for d in t['deps']]
    return tasks


print(f'单块数据顺序执行 = 7 ms（H2D 2 + kernel 3 + D2H 2）；下面看两条 stream 怎么把它压下去\n')

two = build([('A', 'A'), ('B', 'B')])
m2 = run('两个 stream、各 1 块数据：D2H 与另一个 kernel 叠起来了', two)
m1 = run('同一批活全塞进一个 stream：只能串行', build([('S', 'A'), ('S', 'B')]))
print(f'两条 stream 相对单 stream 的加速比 = {m1 / m2:.2f}x\n')

run('4 块数据、4 条 stream：拷贝引擎（只有 1 条）成为瓶颈',
    build([(f's{i}', f't{i}') for i in range(4)]))

legacy = build([('A', 'A'), ('B', 'B')])
for i, t in enumerate(legacy):        # 前 3 个任务改用默认流，触发隐式同步
    if i < 3:
        t['stream'] = 'default'
ml = run('同两个 stream，但走 legacy 默认流语义：隐式同步抹平并发', legacy, legacy_default=True)
print(f'legacy 默认流下比显式双流慢 {ml / m2:.2f}x —— 这是"量不到 overlap"的最常见原因')

三、练习#

  1. 实现：给 simulate 加"拷贝引擎有 2 条"的配置（CAP = {'copy': 2, 'sm': 2}），重跑 4 块数据、4 条 stream 的场景，记录完工时间与瓶颈资源的变化；再改成 {'copy': 1, 'sm': 4}，说明瓶颈从哪儿转移到了哪儿。
  2. 解释：为什么 cudaMemcpyAsync 在主机内存没有 pinned 时会退化成同步？请从"设备要靠 DMA 直接读主机内存"这一点出发，说明操作系统为什么必须保证这些页不被换出。
  3. 对比/验证：把 2 条 stream 的例子改成"两个 kernel 各占 2 个 SM 槽位"（把 units 从 1 改成 2 且 CAP['sm'] = 2），重新运行，观察两个 kernel 是否还能重叠；解释这个结果对应真机上哪一类现象。
  4. 思考：本章的模型把"拷贝引擎"和"SM"当成两个独立资源池。真机上还有哪些资源会成为并发上限（提示：显存容量、L2、CUDA_DEVICE_MAX_CONNECTIONS 限制的硬件队列数、以及同一 kernel 内部对 SM 的占用）？为什么"流越多越快"是错的？
