在线服务的缓存与批处理：收益、风险与阈值#

这一节要解决什么#

上一节把索引变成了"可增量、可版本、可回滚"的段式结构。索引会更新了，但线上查询本身还有大量浪费：

  • 同一个问题被反复问（客服场景里比例很高）；
  • 相似但不相同的问题被当成新问题处理；
  • 每个请求都要重新 prefill 一遍一模一样的系统提示；
  • 请求稀疏时 GPU 空转，请求密集时又没有批处理。

缓存在这里看起来是免费午餐。但这一节要说清楚的是：缓存有四层，风险谱完全不同。最安全的（embedding 缓存）和最危险的（语义缓存）相差极大，而语义缓存恰恰是最容易被"加上去"的那一层。

本节要回答四个问题：

  1. 四层缓存各自的收益与失效条件是什么？
  2. 前缀缓存（prefix caching）能省多少？它成立的前提是一个硬约束，违反它收益会瞬间归零。
  3. 语义缓存的两类错误怎么算？最优阈值是什么，什么时候"不开"才是最优解？
  4. 缓存键怎么写才不会绕过权限？批处理的收益与尾延迟代价怎么权衡？

结论先放在这里：前缀缓存的收益取决于最长公共前缀的长度，所以"稳定内容放前面"是硬约束（⚠️ 示例：稳定前缀布局可复用 68.0% 的 token，把检索片段插到最前面只剩 6.7%，插在中间 51.5%）。语义缓存的命中阈值不是一个"设高一点就安全"的参数：⚠️ 示例中当错答代价是漏命中代价的 100 倍以上时，语义缓存的最优期望损失已经高于"根本不开缓存" —— 也就是说，正确决策是不开。而缓存键漏掉 tenant 会造成跨租户答案泄漏，这是缓存层最常见的越权路径。

一、四层缓存：风险谱#

层 缓存什么 典型收益 失效条件 安全风险
Embedding 缓存 query → 向量 高（重复查询多） 模型版本变更 几乎无（只依赖 query 文本 + 模型版本）
检索结果缓存 query → top-k chunk id 中高 索引更新、权限变化 中：必须带租户/权限/索引版本，否则越权或返回已删文档
重排缓存 (query, chunk) → 分数 中 重排模型/版本 低（但同样要带版本）
生成缓存 前缀 KV / 完整回答 高 前缀不稳定、答案时效性 高：完整回答缓存会固化错误、跨租户泄漏、时效过期

三条判据：

  1. 缓存的键必须包含所有"能改变结果"的版本量。少一个维度 = 一类隐蔽 bug（§4）。
  2. 缓存的收益随层数上升，风险也随层数上升。工程上应当从最安全的层开始做，把生成缓存（尤其语义缓存）留到最后，并且要用数据决定要不要做。
  3. "质量不变、成本下降"是缓存唯一合法的收益形式。一旦缓存改变了质量（哪怕只在一小部分请求上），它就必须按"质量-成本前沿"（第 5.4 节）的方式评估，而不是按"省钱"评估。

二、前缀缓存：机理与硬约束#

2.1 机理#

自回归生成时，prompt 的每个 token 都要算 KV。如果两次请求的 token 前缀逐字相同，那么这段前缀的 KV 就是相同的，可以直接复用，不必重算。

省下的是 prefill，不是 decode：

\text{节省比例} = \frac{n_{\text{reuse}}}{n_{\text{prefill}}}} \quad(\text{仅在 prefill 项上})

其中

nreuse​=LCP(promptt​, promptt−1​)

这就是硬约束：可复用的 token 数等于最长公共前缀长度。前缀一旦在某处不同，后面的全部作废 —— 哪怕后面的内容完全一样。

2.2 布局决定收益#

典型的 RAG prompt 有四段：系统提示 / 租户与版本头 / 检索证据 / 用户问题。四种摆放方式的可复用比例（⚠️ 合成实验，近似 token 切分，平均 prompt 长度 194 token）：

布局 平均可复用 token 可复用比例 说明
stable-first：系统 + 租户头 + 证据 + 问题 132.0 0.680 稳定内容在前，公共前缀 = 系统 + 租户头
interleaved：系统 + 证据 + 租户头 + 问题 100.0 0.515 租户头被挤到证据后，只能复用系统提示
docs-first：证据 + 系统 + 租户头 + 问题 13.0 0.067 证据每次不同 → 公共前缀塌到几乎 0

三个可操作的结论：

  1. 把最稳定的东西放最前面：系统提示 → 租户/权限/版本头 → 证据 → 问题。顺序不能反。
  2. 任何"每请求都变"的内容都不能插在前面：时间戳、request id、用户名、检索结果 —— 插一个就把前缀切断。
  3. 收益可以被预先计算：只要统计各段长度与变化频率，就能算出期望可复用比例，不必上线后猜。⚠️ 示例中 stable-first 与 docs-first 的差距是 10 倍（0.680 vs 0.067），这是纯粹的布局选择，零额外成本。

2.3 失效条件与边界#

情况 后果 处置
检索片段插在系统提示前 前缀命中率塌到接近 0 重排 prompt 结构
模板版本变更（多一个空格） 旧缓存全部失效 把模板版本写进监控指标
多轮对话每轮拼接方式不同 前缀断裂 固定"追加"式拼接（只往后加）
前缀缓存跨请求但跨租户共享 越权（KV 里含他人内容） 缓存键必须含租户与权限指纹
位置编码与缓存实现不匹配 复用结果错误 依赖框架保证；不要手工拼 KV

多轮对话是前缀缓存的最佳场景，因为"历史 + 新问题"天然是追加式的：只要每轮都把新内容加在尾部，前缀就能不断复用。反过来说，如果你在每轮重写系统提示或重排历史，就等于主动放弃这块收益。

三、语义缓存：把"要不要开"算出来#

3.1 机制与两类错误#

语义缓存用"相似度 >τ"代替精确匹配：

hit(q)⟺q′∈cachemax​sim(q,q′)>τ

它有两类错误，方向相反：

  • 假命中（FPR）：不同意图的问题被判为同一意图 → 复用了错误的答案。这类错误很难被发现（用户拿到了一个通顺但答错的内容），而且会被缓存固化（越多人命中，越难纠正）。
  • 假未命中（FNR）：同一意图没被认出 → 白付一次完整成本。

期望损失（每查询，Cmiss​=1 为归一化单位）：

E(τ)=psame​⋅FNR(τ)⋅Cmiss​+(1−psame​)⋅FPR(τ)⋅Cwrong​

其中 psame​ 是"本次查询在缓存里确实有同意图条目"的先验比例。

3.2 阈值扫描：结论与直觉相反#

⚠️ 合成实验（同意图相似度 ∼Beta(9,1.6)、不同意图 ∼Beta(6,3)、psame​=0.35、Cmiss​=1）：

τ FNR FPR E（Cwrong​/Cmiss​=10） E（100） E（1000）
0.700 0.097 0.449 2.9523 29.2167 291.8613
0.800 0.272 0.203 1.4162 13.3034 132.1754
0.900 0.618 0.038 0.4639 2.6930 24.9844
0.950 0.840 0.005 0.3293 0.6485 3.8396
0.975 0.941 0.001 0.3342 0.3793 0.8297

最优阈值与"值不值得开"：

最优 tau*(C_wrong/C_miss=  10) = 0.950  最小期望损失 = 0.3293  | 禁用缓存损失 = 0.3500 -> 值得开
最优 tau*(C_wrong/C_miss= 100) = 0.975  最小期望损失 = 0.3793  | 禁用缓存损失 = 0.3500 -> 不如不开
最优 tau*(C_wrong/C_miss=1000) = 0.975  最小期望损失 = 0.8297  | 禁用缓存损失 = 0.3500 -> 不如不开

这是本节最重要的结论，它有两个层次：

  1. 最优阈值随两类代价之比移动：错答代价越高，阈值越高；"设 0.95 就安全"是错的。
  2. 更关键的是：当错答代价足够高时，语义缓存的最优期望损失超过"不开缓存"。此时正确决策不是"调高阈值"，而是不做语义缓存。⚠️ 示例中阈值只差 2.5%（0.100/0.975）时，Cwrong​/Cmiss​=100 就已经越过了这条线。

所以语义缓存的正确用法是：

  • 只在答案本身低风险（措辞建议、格式转换、公开常识）处启用；
  • 绝不在个性化、时间敏感、权限相关的问答上启用；
  • 上线前必须测出 psame​、同类/异类相似度分布、Cwrong​/Cmiss​，算出 E(τ∗) 并与"不开"比较。

3.3 边界#

  • "多正确答案"问题：同一个问题的多个答案都能接受时，假命中的危害小；反之（如"我的订单状态"）危害大。
  • 缓存污染：一旦一条错误答案进入缓存，它会持续命中。必须有按 doc_id / 反馈触发的失效索引（§4.2）。
  • 分布漂移：psame​ 与相似度分布会随时间变化（新用户、新话题），因此 τ 需要定期重估，不是一次调好。
  • 冷启动：新租户/新语料下缓存命中率低，语义缓存的价值要等流量起来才显现 —— 不要用冷启动期的数据下结论。

四、缓存键：不绕过权限是底线#

4.1 键必须包含的维度#

key = hash(tenant | user_or_acl_fingerprint | index_manifest_id |
           model_version | prompt_template_version | language | time_bucket | query_norm)

逐个说明为什么不能省：

维度 省掉的后果
tenant / user 跨租户/跨用户答案泄漏（⚠️ 实测：无租户键时 globex 命中了 acme 的答案）
acl_fingerprint 权限变更后仍返回旧权限下的内容
index_manifest_id 索引已更新/回滚，缓存仍返回旧文档内容
model_version 模型换了，旧答案与新模型风格/能力不一致
prompt_template_version 模板改了（引用格式、拒答规则），缓存答案不遵守新契约
language 多语言场景下语义相似度跨语言误命中
time_bucket 时间敏感问题（价格、政策、库存）返回过期答案
query_norm 不做归一化会让"同一问题不同写法"完全 miss（收益损失）

注意最后两条方向相反：time_bucket 是"宁可不命中"，query_norm 是"尽量命中"。缓存键的设计就是在这两个方向之间按业务选。

4.2 失效：需要反向索引#

缓存 TTL 不足以应对"某篇文档刚更新"的场景：所有引用了该文档的缓存答案都该失效。做法是维护反向索引：

doc_id→{cache_key}

文档变更时按 doc_id 批量失效。没有这个反向索引，"文档更新了但用户还看到旧答案"会持续到 TTL 到期（可能是几小时）。

4.3 跨租户泄漏的最小复现#

⚠️ 合成实验：

tenant=acme    q=问题A  无租户键命中=False  带租户键命中=False
tenant=globex  q=问题A  无租户键命中=True   命中内容租户=acme   带租户键命中=False
tenant=acme    q=问题A  无租户键命中=True   命中内容租户=acme   带租户键命中=True
跨租户泄漏次数（无租户键）= 1（带租户键 = 0）

这并不是"巧合命中"，而是缓存键设计缺陷的必然结果：只要两个租户问同一个问题，先到者的答案就会被后到者拿到。而 RAG 系统里的答案几乎总是含私有内容。

4.4 缓存的三个隐性成本#

缓存的收益容易看到（成本下降、延迟下降），成本却常被漏掉。三项必须在设计时就算清：

隐性成本 机理 量化方式
命中率下降即负载回流 缓存失效或未命中时，请求全部回到 GPU；若缓存层本身也参与容量规划，则 GPU 容量必须按"全 miss"配置 容量按 1−h 的负载设计，h 是稳态命中率
失效的传播成本 一次文档更新可能触发大量缓存条目失效（反向索引 m 条） m× 单条失效成本；m 大时改用版本号校验
新鲜度与命中率的权衡 TTL 越长命中率越高但越陈旧；时间桶越细越新鲜但命中率越低 用"陈旧答案比例"与"命中率"画二维工作点，按业务选

判据：如果一个缓存方案的容量规划假设了高命中率，那么它在缓存击穿（重启、清空、变更键维度）时会直接打垮下游。正确做法是按"缓存全 miss"配置容量，把命中率当作成本与延迟的优化项，而不是可用性假设。

4.5 边界#

  • 缓存一致性只能做到"最终一致"：文档更新到缓存失效之间总有窗口。要把这个窗口写成 SLA（"文档更新后 N 分钟内生效"），而不是假设它为零（ch6-l1 §4.2）。

五、批处理与调度#

5.1 收益与代价#

批处理把多个请求合成一个 batch 前向，提升吞吐。设单请求服务时间 S、批大小 b、凑批等待 w：

吞吐(b)≈S(b)b​,单请求延迟(b)≈w+S(b)

其中 S(b) 随 b 次线性增长（矩阵乘效率提升），所以吞吐上升而延迟也上升。存在一个吞吐最优的 b∗ 与一个尾延迟允许的最大 bmax​，工作点必须落在 b≤bmax​ 内。

5.2 缓存与批处理的交互#

命中缓存的请求不占用 GPU，因此正确顺序是：

请求 -> 精确缓存 -> [命中] 直接返回（0 GPU）
              -> [未命中] -> 前缀缓存分流 -> 动态批 -> 生成

把缓存放在批处理之前，等于把 GPU 的负载先减掉一块，再对剩下的做批处理。反过来（先进批再查缓存）会让缓存命中白白占用批容量。

5.3 尾延迟的注意事项#

  • 长短输出混批会队头阻塞：短请求被长请求拖住。按预期输出长度分桶。
  • 批处理对稀疏流量无效：λ 很低时凑批等待 w 主导，反而不如单请求。
  • 缓存命中率下降会同时抬高成本与尾延迟（负载回流到 GPU），所以缓存命中率必须与延迟指标一起监控。

代码#

# -*- coding: utf-8 -*-
"""⚠️ 合成数据：前缀缓存命中率（按 prompt 布局）/ 语义缓存阈值-期望损失 / 跨租户泄漏。"""
import re, numpy as np

# ============ (a) 前缀缓存：prompt 布局决定可复用比例 ============
_TOK = re.compile(r"[A-Za-z0-9_=\-\[\].]+|[^\sA-Za-z0-9]")
SYS = "你是企业内部助手。回答必须只依据给定资料，并逐句标注来源。" * 3   # 稳定
TEN = "租户=acme；权限指纹=acl-7f3a；索引版本=man-2026-09-22；" * 2       # 半稳定
def docs(i):                                   # 每查询不同
    return " ".join(f"[doc{j}] 这是第{j}段资料，内容编号{i}-{j}。" for j in range(4))
def query(i): return f"问题{i}：请说明指标变化的原因。"

def build(style, i):
    d, q = docs(i), query(i)
    if style == "stable-first": return SYS + TEN + d + q
    if style == "docs-first":   return d + SYS + TEN + q
    if style == "interleaved":  return SYS + d + TEN + q
    raise ValueError(style)

def lcp_tokens(a, b):
    """近似 token 切分：拉丁词整块、CJK 逐字（接近 BPE 粒度）。"""
    ta, tb = _TOK.findall(a), _TOK.findall(b)
    n = 0
    for x, y in zip(ta, tb):
        if x != y: break
        n += 1
    return n

rng = np.random.default_rng(0); N_REQ = 300
print("== (a) ⚠️ 合成：前缀缓存可复用比例（按 prompt 布局）==")
print(f"{'布局':<14} {'平均总tok':>9} {'最大前缀tok':>11} {'平均可复用tok':>13} {'可复用比例':>10}")
for style in ("stable-first", "docs-first", "interleaved"):
    prompts = [build(style, i) for i in range(N_REQ)]
    lens = [len(_TOK.findall(p)) for p in prompts]
    lcps = [lcp_tokens(prompts[i], prompts[i-1]) for i in range(1, N_REQ)]
    avg_lcp = float(np.mean(lcps))
    print(f"{style:<14} {np.mean(lens):>9.1f} {max(lcps):>11} {avg_lcp:>13.1f} "
          f"{avg_lcp/float(np.mean(lens)):>10.3f}")

# ============ (b) 语义缓存：阈值 -> 期望损失 ============
print("\n== (b) ⚠️ 合成：语义缓存的阈值扫描（两类代价不对称）==")
rng = np.random.default_rng(1); M = 200000
same = rng.beta(9, 1.6, M)          # 同意图相似度（偏高）
diff = rng.beta(6, 3.0, M)          # 不同意图相似度（有重叠区 -> 风险来源）
P_SAME = 0.35

def rates(tau):
    return float((same <= tau).mean()), float((diff > tau).mean())   # FNR, FPR

print(f"{'tau':>5} {'FNR':>7} {'FPR':>7} " +
      " ".join(f"{'E(r='+str(r)+')':>10}" for r in (10, 100, 1000)))
best = {r: (None, 1e9) for r in (10, 100, 1000)}
for tau in np.arange(0.5, 0.99, 0.025):
    fnr, fpr = rates(tau); row = []
    for r in (10, 100, 1000):
        E = P_SAME * fnr * 1.0 + (1 - P_SAME) * fpr * r     # C_miss=1, C_wrong=r
        row.append(E)
        if E < best[r][1]: best[r] = (float(tau), E)
    print(f"{tau:>5.3f} {fnr:>7.3f} {fpr:>7.3f} " + " ".join(f"{e:>10.4f}" for e in row))
NO_CACHE = P_SAME * 1.0            # 禁用语义缓存：同意图也全部 miss
for r in (10, 100, 1000):
    verdict = "值得开" if best[r][1] < NO_CACHE else "不如不开"
    print(f"  最优 tau*(C_wrong/C_miss={r:>4}) = {best[r][0]:.3f}  最小期望损失 = {best[r][1]:.4f}"
          f"   | 禁用缓存损失 = {NO_CACHE:.4f} -> {verdict}")

# ============ (c) 跨租户缓存泄漏 ============
print("\n== (c) ⚠️ 合成：缓存键漏掉 tenant 的后果 ==")
cache_bad, cache_good = {}, {}
def key_bad(q): return f"{q}"                        # 缺 tenant/权限/版本
def key_good(q, tenant, acl, man): return f"{tenant}|{acl}|{man}|{q}"
events = [("acme", "acl-1", "问题A", "ACME 内部答案：预算=100万"),
          ("globex", "acl-2", "问题A", "GLOBEX 内部答案：预算=8万"),
          ("acme", "acl-1", "问题A", "ACME 内部答案：预算=100万")]

关键设计决策：语义缓存部分没有去"调一个更好的阈值"，而是把"开不开"也变成一个可比较的数量（E(τ∗) vs 不开缓存的损失）。这是这份代码最重要的选择：工程上大量"缓存效果不好"的问题，本质不是参数没调好，而是这类缓存在这个业务上就不该开；只有把"不开"作为基线放进同一个期望损失里，这个结论才会显式出现。

练习#

  1. 算你自己 prompt 的可复用比例。把你们真实的 prompt 模板按段拆开（系统/租户/证据/问题），统计各段 token 数（用真实分词器），计算四种布局下的期望可复用比例。回答：(a) 现有布局浪费了多少 prefill？(b) 换成最优布局需要改哪些代码？(c) 折算成每查询成本是多少？

  2. 多轮对话的前缀复用。设第 t 轮 prompt = 历史（t−1 轮的拼接）+ 新问题。证明：如果每轮只往后追加，则第 t 轮的可复用前缀 = 第 t−1 轮的整个 prompt。然后说明："每轮重新生成摘要替代历史"会如何破坏这个性质，以及代价是多少 token 的重算。

  3. 语义缓存的 psame​ 估计。设计一个从线上日志估计 psame​ 的方法（提示：用人工标注的小样本 + 相似度分布做校准）。说明为什么 psame​ 会随租户/话题变化，以及你会怎么分桶估计。

  4. 推导 τ∗ 的一阶条件。对 E(τ)=pFNR(τ)+(1−p)rFPR(τ)，写出 dE/dτ=0 的条件，并说明它如何用两个相似度分布的密度函数表示（提示：设两类分布的密度为 f1​,f2​，则 FPR′=−f2​(τ)、FNR′=f1​(τ)，得到似然比阈值 f2​(τ)f1​(τ)​=p(1−p)r​）。解释这个式子的含义：它正是贝叶斯最优决策阈值。

  5. 缓存键的完备性测试。为你的缓存层设计一组单元测试：对每一个键维度，构造两个"只在该维度不同"的请求，断言它们不共享缓存条目。列出至少 7 个维度的测试用例，并说明哪一个维度最容易被漏掉。

  6. 反向失效索引的成本。设缓存条目 C 条、每篇文档平均被 m 条缓存引用。推导维护 doc→cache_key 反向索引的存储与写入成本。回答：当 m 很大时（热门文档），有没有更省的做法（提示：存 doc 版本号，在缓存读取时校验版本，而不是主动失效）？

  7. 批处理工作点。给定 S(b)=8+2b ms、凑批等待 w=15 ms、尾延迟上限 200 ms。求 bmax​；再假设 60% 请求命中缓存不占用 GPU，重算到达 GPU 的有效 λ，并给出推荐批大小与预期吞吐。

  8. "缓存改变质量"的评估。假设语义缓存让 3% 的请求返回了"接近但不完全正确"的答案。用第 5.4 节的 Pareto 框架，把"语义缓存开/关"作为两个配置，说明如何用端到端质量与每查询成本判断它是否被支配。需要什么数据？如果只有离线指标，能否得出结论？

小结#

  • 四层缓存的风险谱：embedding（几乎无风险）< 重排 < 检索结果 < 生成/语义（高风险）。工程上从最安全的一层开始做。
  • 前缀缓存的硬约束：可复用 token 数 = 最长公共前缀长度；省的是 prefill，不是 decode。⚠️ 布局决定 10 倍差距：stable-first 0.680、interleaved 0.515、docs-first 0.067。
  • 布局规则：系统提示 → 租户/权限/版本头 → 证据 → 问题。任何每请求都变的内容插在前面，都会把前缀切断。 多轮对话要保持"只往后追加"。
  • 语义缓存的两类错误方向相反：假命中（错误答案、难发现、会被固化）与假未命中（白付成本）。期望损失 E(τ)=pFNR+(1−p)rFPR；最优阈值由似然比 f2​f1​​=p(1−p)r​ 决定，即贝叶斯最优决策。
  • 最关键的一条：最优阈值随两类代价之比移动，而当错答代价足够高时，"不开语义缓存"才是最优决策。⚠️ 示例：r=10 时值得开（0.3293 < 0.3500），r=100 与 r=1000 时都"不如不开"（0.3793、0.8297 > 0.3500）。上线前必须把"不开"作为基线算进去。
  • 缓存键必须包含：tenant/user、权限指纹、索引 manifest 版本、模型版本、prompt 模板版本、语言、时间桶、归一化查询。⚠️ 实测：缺 tenant 时 globex 命中了 acme 的答案（泄漏 1 次；带租户键 0 次）。
  • 失效需要反向索引 doc→{cache_key}；否则"文档更新了但用户看到旧答案"会持续到 TTL 到期。替代方案是把 doc 版本写进键、读取时校验。
  • 批处理的正确顺序：先查缓存（命中不占 GPU）再做动态批；长短输出分桶避免队头阻塞；稀疏流量下批处理反而更差。
  • 三个隐性成本：命中率下降导致负载回流（容量必须按"全 miss"配置）、失效传播成本（doc→m 条缓存条目）、新鲜度与命中率的权衡（TTL 与时间桶）。
  • 缓存只提供最终一致：更新到失效之间存在窗口，必须写成 SLA，而不是假设为零。
  • 缓存不是可用性组件：它是优化组件。容量必须按「全 miss」设计，命中率下降只应表现为成本与延迟上升，而不是服务不可用。
  • 一句话：缓存唯一合法的收益形式是"质量不变、成本下降"。前缀缓存靠布局（免费），语义缓存靠概率（有风险），而权限必须靠键（不可妥协）。

下一节：缓存能省钱，但缓存也是绕过权限最方便的一条路。下一节把多租户与文档级 ACL 讲透：为什么"先取 top-k 再过滤"必然漏、高选择性前置过滤为什么也会掉召回，以及怎么用可证伪的 canary 测试证明"不漏"。
