融合的代价核算：寄存器压力、occupancy 与实测回归#

既然融合能省流量，为什么不把整张图融成一个内核？因为融合不免费——它把"中间值"从显存搬到片上，而片上容量有限：寄存器用超了就溢出到局部内存（又是显存），occupancy 掉下来，收益当场反转。本课把这条链算成一张可复核的账，并说明"融合多少"在真实编译器里是启发式而非规则，最终只能靠实测回归定夺。

一、概念讲解#

1. 融合把流量换成寄存器#

融合内核的寄存器需求由三个量决定：活值数（live values，每个"在飞"元素同时要保留的值；纯逐元素链约 2——输入值加中间值；合并多个归约会升到 3~4）、每线程并行元素数 L（lanes，为隐藏访存延迟而给单线程的多份独立工作）、固定开销（地址、循环变量、索引）。模型就一行：

regs≈base+L×live_per_lane

注意链长本身不直接吃寄存器：链内是顺序依赖，编译器可复用一个值；推高寄存器的是"同时有多少份工作在飞"——想加深访存流水（提高 L）就得交寄存器。

2. 寄存器 → occupancy：一条会掉头的曲线#

寄存器按 warp 分配，粒度 256 个（每线程 8 个的倍数）；硬上限 255，超过就溢出。每 SM 可驻留的 warp 数因此是

warps=min(⌊⌈regs⋅32/256⌉⋅256regfile/SM​⌋, max_warps)

代码用示例参数（寄存器文件 64K/SM、每 SM 最多 48 warp、每 block 128 线程）算表：L 从 1 涨到 32，寄存器 18 → 80，occupancy 从 100% 掉到 52%，每 block 片上工作集从 1.0 KiB 涨到 32.0 KiB。参数只是示例，请换成你自己架构的官方数值；结论形状不变：occupancy 与每线程并行元素互为跷跷板。

3. 溢出：多融一块，就多一趟显存#

活值数上去更危险。代码第二张表取活值数 16（如合并多个归约、强行展开长链）：每线程 16 个元素就要 272 个寄存器，超过 255 的硬上限——编译器改走局部内存（local memory），而它在显存里。省下的带宽被溢出流量吃掉，相对代价按示例折算飙到 61.7x。方向一定，幅度取决于溢出的实际访问次数，须以实测校准。

4. 融合预算是启发式，不是正确性条件#

真实编译器里确实有"融合上限"这类旋钮。本机 torch 2.3.1 的调度器源码 can_fuse 里就能读到这类闸门：节点是 extern/nop 时拒绝、两侧无共享数据时拒绝（除非开了 aggressive_fusion）、以及 len(node1.get_nodes()) + len(node2.get_nodes()) > config.max_fusion_size 时拒绝——源码注释还写明这是 heuristic not needed for correctness（正确性不需要它），本机该配置项默认值为 64。

一个实测把它的性质说清：本机把 max_fusion_size 改成 4 后重新编译那条 8 算子逐元素链，生成的仍然是一个融合内核（cpp_fused_add_div_mul_relu_sigmoid_sub_0）。所以它不是"单核最多融几个节点"的硬上限，只是调度器合并两个已融合节点时的启发式闸门之一。实践含义：别靠调阈值控制融合规模，要用代价核算 + 实测。

5. 把三笔账合成一个决策#

一次融合决策要同时看三样：流量（越低越好）、occupancy（越低越难藏延迟）、溢出（出现即加流量）。代码把它们放进同一张表：一个内核融 8 个算子相对代价 1.00；切成两个 2.00（纯流量代价）；"活值数 16、并发 16"的超融合是 61.71——比切分还差。与第 1 课的真内核实测对照可见两端：切分是可预期的 ≈2.1x，超融合可能是数十倍的灾难。工程顺序：按类别划出候选（第 2 课）→ 核算器淘汰明显亏的 → 目标硬件上做实测回归。

6. 有卡怎么量，无卡怎么替代#

有 GPU 时三个根量都能直接读：ncu --metrics launch__registers_per_thread,sm__warps_active,dram__bytes 分别给出每线程寄存器、活跃 warp 比例与显存流量；把"融合/切分"两版各跑一次就能把回归钉在数据上。没有 GPU 时核算器给的是方向与量级：occ 掉头、溢出触发、切分代价翻倍都是算式结论，可直接当判据；阈值留到有卡时校准。

7. 常见坑#

  • 把 occupancy 当越高越好：有些内核宁可低 occupancy、用更多寄存器换 ILP；occupancy 只是手段。
  • 只看寄存器不看共享内存：共享内存同样是 occupancy 约束项，融合常顺带抬高它。
  • 用一次计时下结论：回归幅度常小于噪声，至少跑多次取最小值，并固定输入形状。
  • 忘了溢出不报错：溢出合法（走局部内存），不会编译失败，只会悄悄变慢——最容易被漏掉。

二、可运行代码示例#

纯 Python（无第三方依赖）的代价核算器：第 1 段把"每线程并行元素数 → 寄存器 → occupancy → 片上工作集 → 是否溢出"算成两张表；第 2 段把流量与 occupancy 放进同一张账，给出融合与切分的相对代价。

# ---- 第 3 课示例：融合代价核算器（纯 Python，无第三方依赖）----
# 参数全部是"示例值"：请按目标架构的官方 Occupancy 文档替换后再做决策
REG_FILE = 65536        # 每 SM 的 32-bit 寄存器数
MAX_REGS = 255          # 每线程寄存器上限（超过就溢出到局部内存）
MAX_WARPS = 48          # 每 SM 最大 warp 数
THREADS = 128           # 每 block 线程数
BW_PER_SM = 1.5e12 / 132   # 示例：总带宽 1.5 TB/s 均摊到 132 个 SM
BYTES_PER_ELEM = 8      # 逐元素链：读 4 B + 写 4 B（fp32）

def regs_per_warp(regs):
    """寄存器按 warp 分配，粒度 256 个寄存器（= 每线程 8 个的倍数）。"""
    return max(256, -(-regs * 32 // 256) * 256)

def occupancy(regs):
    """受寄存器文件限制的 warp 数，再受每 SM warp 上限约束；regs > 255 时溢出。"""
    warps = min(REG_FILE // regs_per_warp(regs), MAX_WARPS)
    return warps, regs <= MAX_REGS          # 第二个返回值 = 没溢出

print('=== 1. 每线程并行元素数（ILP/tile）决定寄存器，寄存器决定 occupancy ===')
print('    live_per_lane = 每个"在飞"元素同时活着的值数：点链 2（输入 + 中间值），'
      '多个归约合并 3~4')
for live in (2, 16):
    print(f'\n  每元素活值数 = {live}：')
    print(f'    {"每线程元素":>10}{"寄存器/线程":>13}{"warp/SM":>9}{"occupancy":>11}'
          f'{"每 block 片上工作集":>20}   溢出')
    for lanes in (1, 2, 4, 8, 16, 32):
        regs = 16 + lanes * live
        warps, no_spill = occupancy(regs)
        ws = THREADS * lanes * live * 4
        print(f'    {lanes:>10}{regs:>13}{warps:>9}{warps / MAX_WARPS * 100:>10.0f}%'
              f'{ws / 1024:>17.1f} KiB   {"是 → 走局部内存" if not no_spill else "否"}')
print('\n  同一段融合体，想提高"每线程并行元素"来加深访存流水，就要拿 occupancy 去换；')
print('  活值数变大（例如把多个归约合并进同一个内核）时，先在 255 上撞墙、开始溢出。')

print('\n=== 2. 融合还是切分：把"流量"和"occupancy"放在同一张账上 ===')
def rel_time(kernels, regs, spill_lanes=0):
    """相对时间 ∝ 每元素字节数 / occupancy；溢出按每元素多一次 4 字节访问折算（示例系数）。"""
    warps, no_spill = occupancy(regs)
    occ = warps / MAX_WARPS
    bytes_per_elem = kernels * BYTES_PER_ELEM + (0 if no_spill else spill_lanes * 4)
    return bytes_per_elem / occ, occ, bytes_per_elem

rows = [('一个内核融 8 个算子', 1, 16 + 8 * 2),
        ('切成两个内核各 4 个算子', 2, 16 + 8 * 2),
        ('一个内核（活值数 16，并发 16）', 1, 16 + 16 * 16),
        ('一个内核（活值数 16，并发 32）', 1, 16 + 32 * 16)]
base = rel_time(1, 16 + 8 * 2)[0]
print(f'  {"方案":<28}{"寄存器/线程":>12}{"occupancy":>11}{"每元素字节":>12}{"相对时间":>10}')
for tag, k, regs in rows:
    t, occ, b = rel_time(k, regs, spill_lanes=16)
    print(f'  {tag:<28}{regs:>12}{occ * 100:>10.0f}%{b:>12}{t / base:>10.2f}')
print('  读法：切分的代价是流量翻倍（第 2 行 = 2.00）；融合过头的代价是 occupancy 掉下来、')
print('  甚至溢出到局部内存（第 4 行），相对代价反而比切分更差。')

print('\n=== 3. 切分代价的账面值（与第 1 课的真内核实测对照）===')
t1, _, b1 = rel_time(1, 16 + 8 * 2)
t2, _, b2 = rel_time(2, 16 + 8 * 2)
print(f'  一个内核融 8 个算子：每元素 {b1} 字节 → 相对时间 {t1 / base:.2f}')
print(f'  切成两个内核各 4 个：每元素 {b2} 字节 → 相对时间 {t2 / base:.2f}（账面就是 2 倍）')
print('  第 1 课同机同尺度的 numba 实测（多次最小值，计时浮动 ±10%）：1 内核 ≈13 ms →')
print('  2 内核 ≈28 ms（≈2.1x，与账面 2x 吻合）；8 内核 ≈57 ms（≈4.1x，不足 8x：每次内核启动')
print('  与并行调度有固定开销）。')
print('  本机没有 GPU，寄存器压力只能用上面的参数化核算推演：真回归必须在目标卡上用 ncu 量')
print('  launch__registers_per_thread / sm__warps_active / dram__bytes 三个指标（见可选块）。')

三、练习#

  1. 实现：把核算器的 REG_FILE 改成 32768（模拟寄存器文件更小的档位），重跑表 1 与表 2，找出 occupancy 开始下降与触发溢出的 L，并解释两者为何不同。
  2. 解释：为什么"链长"不直接吃寄存器，而"每线程并行元素数"吃？若一条链有 8 个互相独立的头部（如 8 个输入相加），寄存器需求会怎么变？
  3. 对比/验证：把 MAX_WARPS 从 48 改成 64，表 1 的 occupancy 百分比整体变化，但"溢出点"不变——解释为什么溢出点只由 MAX_REGS 与活值数决定。
  4. 思考：本课把溢出折算成每元素多一次 4 字节访问。若真实溢出访问是 8 次，表 2 第 4 行会怎样变化？要拿到这个倍数需测哪两个量？
