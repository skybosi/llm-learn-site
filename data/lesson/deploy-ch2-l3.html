显存与吞吐调优#

服务能跑起来只是及格线，这一课把单卡"榨干"。显存和吞吐在单卡上是一对可以通过参数调配的权衡：显存分给 KV Cache 越多，能同时接的请求越多、吞吐越高，但留给激活的空间越少、越容易 OOM。调优的本质是先算清显存账，再在"不 OOM"的边界内把吞吐推到最大。学完本课，你应当能独立估算一个模型 + 配置的显存占用，并用 gpu-memory-utilization、max-num-seqs、max-model-len 三个旋钮把单卡吞吐调上去。

一、概念讲解#

1. 显存都去哪了#

一次推理的显存占用由四块构成：

显存占用 ≈ 权重 + KV Cache + 激活/中间结果 + 碎片/运行时开销
  • 权重：加载后固定不变，FP16 约 2 字节/参数，INT4 约 0.5 字节/参数；
  • KV Cache：随"并发序列数 × 序列长度"增长，是吞吐调优的核心变量；
  • 激活/中间结果：prefill 时随批量大小波动，通常几十 MB 到几百 MB；
  • 碎片/开销：CUDA 上下文、通信缓冲、分页管理，经验上留 10–15% 余量。

2. KV Cache 估算：调优的钥匙#

KV Cache 每个 token 占用：

每 token KV 字节 = 2(K和V) × 层数 × KV头数 × 头维度 × 精度字节数

以 Qwen2.5-7B（28 层、GQA 4 个 KV 头、头维度 128、FP16）为例：

每 token KV = 2 × 28 × 4 × 128 × 2 字节 = 57344 字节 ≈ 56 KB

那么"并发 128 条序列、每条最长 8192 token"的 KV Cache 上限：

128 × 8192 × 56 KB ≈ 56 GB   ← 这已经是 7B 模型的主战场

结论：长上下文 + 高并发的 KV Cache 往往比权重本身还大，这就是为什么不能只按权重大小选卡。

3. 三个调优旋钮#

  • --gpu-memory-utilization：显存池上限（默认 0.9）。调大能装更多 KV Cache，但太接近 100% 易 OOM，建议 0.85–0.95；
  • --max-num-seqs：同时处理的序列数上限。调大提高批内并行、吞吐上升，但单请求排队可能变长、KV Cache 占用变多；
  • --max-model-len：单序列最大长度。调小能显著省 KV Cache、提吞吐，但超长输入会被截断或报错。

调优方向一句话：在满足业务最大上下文的前提下，把 max-model-len 压到必要值，把 max-num-seqs 提到显存允许的上限，再微调 gpu-memory-utilization 兜底。

4. 换卡/换量化的"断点式"收益#

参数微调是"渐进式"收益，而换量化（FP16→AWQ 4-bit）或换卡（24G→80G）是"断点式"收益：权重或显存直接砍半/翻倍，KV Cache 容量随之跳变。所以调优顺序应是：先做选型级的量化/换卡决策，再用三个旋钮做精细榨取。

二、可运行示例#

示例 1：显存估算脚本#

# -*- coding: utf-8 -*-
# 显存估算：权重 + KV Cache + 余量，判断配置是否装得下

def estimate_vram(params_b, quant_bits, layers, kv_heads, head_dim,
                  max_num_seqs, max_model_len, dtype_bytes=2, overhead=0.15):
    """quant_bits: 权重位宽(16/8/4); 返回各块显存(GB)。"""
    weight_gb = params_b * quant_bits / 8 * 1e9 / 1e9          # 权重 GB
    per_token_kv = 2 * layers * kv_heads * head_dim * dtype_bytes
    kv_gb = max_num_seqs * max_model_len * per_token_kv / 1e9  # KV Cache GB
    act_gb = 0.5                                               # 激活/中间结果粗估
    total = weight_gb + kv_gb + act_gb
    with_overhead = total * (1 + overhead)
    return dict(weight=weight_gb, kv=kv_gb, act=act_gb,
                total=total, with_overhead=with_overhead)

# 场景 A：7B FP16，128 并发，8192 上下文
a = estimate_vram(7, 16, layers=28, kv_heads=4, head_dim=128,
                  max_num_seqs=128, max_model_len=8192)
# 场景 B：7B AWQ 4-bit，同样配置
b = estimate_vram(7, 4, layers=28, kv_heads=4, head_dim=128,
                  max_num_seqs=128, max_model_len=8192)
for name, r in [("7B FP16", a), ("7B AWQ4", b)]:
    print(f"{name}: 权重={r['weight']:.1f}GB KV={r['kv']:.1f}GB 激活={r['act']:.1f}GB "
          f"合计={r['total']:.1f}GB 含余量={r['with_overhead']:.1f}GB")
print("判断：7B FP16 需约 74GB(含余量) -> 80G 卡可跑，24G 卡必 OOM；AWQ4 则 24G 卡可跑")

运行后你会发现：FP16 的 KV Cache（约 56GB）是权重的 4 倍，量化只砍权重、不砍 KV Cache。想真正扩大并发，还得压 max_model_len 或用更省 KV 的量化（如 KV 量化、FP8 KV）。

示例 2：三旋钮调优对比#

# 基线：默认保守配置
vllm serve Qwen/Qwen2.5-7B-Instruct --host 0.0.0.0 --port 8000 \
    --gpu-memory-utilization 0.9 --max-model-len 8192 --max-num-seqs 128

# 调优 1：压上下文到业务真实需要的 2048，释放 KV Cache 给并发
vllm serve Qwen/Qwen2.5-7B-Instruct --host 0.0.0.0 --port 8000 \
    --gpu-memory-utilization 0.95 --max-model-len 2048 --max-num-seqs 256

# 调优 2：加载 AWQ 量化，权重减半，进一步加大并发
vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ --host 0.0.0.0 --port 8000 \
    --quantization awq --gpu-memory-utilization 0.95 \
    --max-model-len 2048 --max-num-seqs 512

用上一课的压测脚本对三套配置分别扫 QPS，记录"P99 TTFT≤2s 时的最大吞吐"。典型结果：调优 1 比基线吞吐提升 40–80%，调优 2 再提升 30–50%——省出来的显存都变成了吞吐。

三、练习#

  1. 改模型参数：把示例 1 换成 13B（40 层、8 个 KV 头），重算显存，判断 24G 卡在 FP16 和 AWQ4 下分别能否装下、能开多大 max-num-seqs。
  2. 找 OOM 边界：在示例 2 的调优 2 基础上，把 max-num-seqs 一路加到 1024，观察是否 OOM 或吞吐不再上升，解释为什么"并发不是越大越好"。
  3. KV 量化：查 vLLM 文档里 KV Cache 量化的参数（如 --kv-cache-dtype fp8），说明它能怎样在几乎不掉吞吐的前提下进一步扩大 KV Cache。
  4. 写调优清单：为一个"上下文 ≤ 2048、峰值 64 并发"的客服场景，写一份完整的 vLLM 启动参数清单，并标注每个参数选值的理由。
