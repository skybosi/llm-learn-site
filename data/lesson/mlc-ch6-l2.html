调度空间：tile / unroll / vectorize / 并行化 / 流水（与 CUDA 优化一一对应）#

第 1 课证明了"同一算法可以有很多正确调度"，但没说这些调度之间怎么组合、组合起来有多大空间。先看一个小空间：6 个 tile 形状 × 2 种次序 × 2 种向量宽度 × 3 种展开次数 = 72 条，最差与最好相差约 3.4 倍。更关键的是每个原语的收益量级差得很远：取消分块让代价涨 8.4 倍，而取消向量化只涨 0.2%——搜索预算该怎么花，答案在这张表里。

一、概念讲解#

1. "能改顺序"不等于"随便改"：合法性先立边界#

调度原语不是自由改写，每个都带前提。tile / split 要求拆出的两层覆盖原范围（tiles 必须整除维度）；vectorize 要求被向量化的维在内存里连续，否则硬件拒绝或退化成标量；bind 允许把输出维绑到线程块，但归约维绑核会让不同线程写同一个累加器；unroll 展开后寄存器用量上升，溢出就变慢。所以调度空间是"合法子集里的地形"，不是整个笛卡尔积。

2. 五个原语的收益量级差得很远#

代码第 3 节做单变量对比：从最优调度出发，每次只动一个原语。结果分三档。

第一档是分块：tile=(128,64,8) 换成未分块，代价从 23.0 MB 涨到 192.8 MB（×8.4）——未分块时每个输出元素都要把一整行 a 与一整列 b 从上级存储取回，复用完全消失。分块决定"数据在片上能活多久"，是量级问题。

第二档是并行绑定：把 ('i','j') 改成只并 j，代价 ×3.6。并行维的切分定义了复用边界，块与块之间不能共享片上数据——所以并行策略必须与 tile 形状一起选（第 1 课结尾的"只并 j"是同一现象）。

第三档是向量化与 unroll：改成 vec=1 或 unroll=8 只带来 0.2% 上下的变化。这不是说它们不重要，而是说明在这条基线上它们不是瓶颈：访存已被分块压到最低，指令数占比本来就小。unroll 的价值在隐藏延迟，只有访存顺畅、流水线有空隙时才体现。

3. 好调度是稀有的：把 720 条分成十档#

把取值集合放大（10 个 tile × 2 次序 × 2 种归约提前 × 3 向量宽 × 2 绑核 × 3 unroll）就有 720 条候选。按代价分十档：每档 72 条，而第 1 档（23.0 MB 上下）与第 5 档（42.5 MB 起）几乎断开——劣档不是渐变，而是断崖，从某一档开始驻留量超过 L2，DRAM 账突然乘上倍数。

这解释了自动调优的两个事实：好区域只占 10%，随机碰运气效率不高；但同一档内的 72 条差别很小，没必要精确到小数第三位。第 3、4 课分别处理这两件事：用代价模型把搜索导向好区域，用预算账决定"搜多久才划算"。

4. 与 CUDA 优化一一对应，但顺序要反过来#

把五个原语翻译成前一门课的语言：tile → 共享内存分块；reorder/归约提前 → 循环交换与流水；vectorize → 向量化访存；bind → 网格/线程块划分；unroll → #pragma unroll。手工优化的经验顺序是"先分块、再看并行度、最后向量化和展开"；自动调优的搜索顺序反过来——先解决量级最大的那一项。

5. 常见坑#

  • tile 越大越好？ 不是。tile 面积超过片上缓存后驻留量溢出，DRAM 账反弹（第 1 课"只并 j"的 1124 MB 即是此类）。
  • 把"合法"当"好"：tiles=(1,1,1) 与 (8,8,1) 都合法，代价差 1.4 倍；合法性检查不保证性能。
  • 并行度只看块数：('i','j') 与 ('j',) 都能开很多块，但后者改变了 a 的驻留量，代价 ×3.6。
  • 忽略 unroll 的寄存器账：本课用 {1: 1.6, 4: 1.0, 8: 2.4} 的压力因子近似它，真实硬件上是寄存器溢出——该因子要按实测标定。

二、可运行代码示例#

# ---- 第 2 课：调度空间 = 五个原语的可选组合（纯 Python，无第三方依赖）----
import itertools


def cost(order, tiles, file_loop, vec, parallel, unroll, M=1024, N=1024, K=1024,
         l2=131072, elem=4, inst_equiv=2.5e-5):
    """解析代价模型（越小越好），四项相加，都在"等效字节"量纲上：
       ① 跨层搬运：驻留工作集装不进 L2 就按超出倍数补；
       ② 片上搬运：tile 越大，块内复用越充分；
       ③ 指令数：向量化按宽度摊薄；unroll 4 以内藏延迟，unroll 8 反受寄存器压力；
       ④ 并行度不足的启动开销。"""
    ti, tj, tk = tiles
    on_chip = (M / ti) * (N / tj) * (ti * K + K * tj) * elem
    ws_a = (ti if 'i' in parallel else M) * K
    ws_b = K * (tj if 'j' in parallel else N)
    dram = (M * K + K * N) * elem * (max(1.0, ws_a / l2) + max(1.0, ws_b / l2)) + M * N * elem
    inst = (2 * M * N * K) / vec
    reg = {1: 1.6, 4: 1.0, 8: 2.4}[unroll]        # unroll 4 最优：再多寄存器压力上来
    launch = 0.0 if len(parallel) == 2 else M * N * elem * 0.5
    return dram + on_chip * 0.02 + inst * inst_equiv * reg + launch


TILES = [(1, 1, 1), (8, 8, 1), (16, 16, 1), (32, 32, 1), (64, 64, 1),
         (16, 16, 4), (32, 32, 8), (64, 64, 16), (128, 64, 8), (64, 128, 8)]
ORDERS = [('i', 'j', 'k'), ('j', 'i', 'k')]
FILE = [None, 'k']
VECS = [1, 2, 4]
PARS = [('i', 'j'), ('j',)]
UNROLLS = [1, 4, 8]
FIELDS = ('order', 'tiles', 'file_loop', 'vec', 'parallel', 'unroll')


def space():
    for t, o, fl, v, p, u in itertools.product(TILES, ORDERS, FILE, VECS, PARS, UNROLLS):
        yield dict(tiles=t, order=o, file_loop=fl, vec=v, parallel=p, unroll=u)


def evaluate(s, **kw):
    return cost(s['order'], s['tiles'], s['file_loop'], s['vec'], s['parallel'], s['unroll'], **kw)


if __name__ == '__main__':
    all_s = sorted(space(), key=evaluate)
    print(f'=== 1. 调度空间规模：{len(TILES)} tile × {len(ORDERS)} 次序 × {len(FILE)} 归约提前 '
          f'× {len(VECS)} 向量宽 × {len(PARS)} 绑核 × {len(UNROLLS)} unroll = {len(all_s)} 条 ===')

    print('\n=== 2. 按代价排序：前 4 名（并列说明哪几个原语在这组里真的起作用）与后 3 名 ===')
    for tag, rows in (('最优', all_s[:4]), ('最差', all_s[-3:])):
        for s in rows:
            print(f'  {tag}  tile={str(s["tiles"]):<12} order={"".join(s["order"])} '
                  f'file={str(s["file_loop"]):<5} vec={s["vec"]} par={"".join(s["parallel"])} '
                  f'unroll={s["unroll"]:<2} 代价={evaluate(s) / 1e6:7.2f} MB')

    print('\n=== 3. 单变量对比：从最优调度出发各动一处 ===')
    base = all_s[0]
    b = evaluate(base)
    print(f'  基线：tile={base["tiles"]} order={"".join(base["order"])} vec={base["vec"]} '
          f'par={"".join(base["parallel"])} unroll={base["unroll"]}  代价={b / 1e6:.2f} MB')
    for name, mut in [('取消分块 tile=1', dict(tiles=(1, 1, 1))),
                      ('取消向量化 vec=1', dict(vec=1)),
                      ('放弃 i 并行 par=j', dict(parallel=('j',))),
                      ('unroll 8（寄存器压力）', dict(unroll=8)),
                      ('归约不提前 file=None', dict(file_loop=None)),
                      ('只改循环次序 jik', dict(order=('j', 'i', 'k')))]:
        t = dict(base); t.update(mut)
        c = evaluate(t)
        print(f'  {name:<24} 代价 {c / 1e6:7.2f} MB   相对基线 ×{c / b:5.2f}')

    print('\n=== 4. 好调度有多稀有：把 720 条按代价分十档 ===')
    step = len(all_s) // 10
    print('  档位  代价区间(MB)   档内 tile 分布')
    for k in range(10):
        chunk = all_s[k * step:(k + 1) * step]
        lo, hi = evaluate(chunk[0]) / 1e6, evaluate(chunk[-1]) / 1e6
        tiles = sorted({str(s['tiles']) for s in chunk})
        print(f'  {k + 1:>2}/10  {lo:6.2f} ~ {hi:6.2f}   {" ".join(tiles[:4])}')
    print(f'  最优 / 中位 = {evaluate(all_s[0]) / evaluate(all_s[len(all_s) // 2]):.2f}×；'
          f'最优 / 最差 = {evaluate(all_s[0]) / evaluate(all_s[-1]):.2f}×')

三处可核对的结论：分块是量级项（取消分块 ×8.4，其余原语都在 ×1.01 以内）；并行绑定与 tile 绑在一起（只并 j 就 ×3.6，因为 a 的驻留量变成 K×N 全体）；好区域是断崖不是斜坡（第 1 档 23.0 MB、第 5 档直接跳到 42.5 MB，说明"驻留量是否装得下 L2"比连续调参更关键）。

三、练习#

  1. 实现：给 cost() 增加一项"片上容量检查"：若 ti*K 或 K*tj 超过给定的 shared memory 容量（例如 48 KB / 4 B），返回无穷大。重跑第 2 节，看最优调度是否从 (128,64,8) 变成更小的 tile。
  2. 解释：为什么"取消向量化"只涨 0.2%，而真实 GPU 上 fp16 输入不向量化可能慢一倍？提示：本课把访存字节与指令数分开算，而真实硬件里低精度访存必须按 128 位打包。
  3. 对比/验证：把 ORDERS 换成三种次序（含 ('k','i','j')，即归约维在最外），观察最优调度的变化；再解释为什么"归约维在最外"在有流水的硬件上反而可能是好选择。
  4. 思考：第 1 档的 72 条代价几乎相同，但真实硬件上差距可能远超模型预测（寄存器压力、L2 行为、指令发射）。只有 20 次真测预算时，你会怎么在这 72 条里取样？
