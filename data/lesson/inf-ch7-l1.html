API 与流式#

前六章解决的是"把模型算得快、装得下"。这一章进入最后一环——模型服务化：把训练/优化好的推理引擎变成一个可被外部系统调用的服务。第一步就是对外接口：以 HTTP API 的形式把模型暴露出去，并支持流式（streaming）输出，让用户在第一个 token 出来时就先看到结果，而不是干等整段回答。这一课讲清楚 OpenAI 兼容接口的结构、SSE 流式的原理，以及如何自己起一个服务并调用它。

一、概念讲解#

1. 为什么要做 API，而不是直接 import 模型#

在笔记本里 model.generate(...) 和在生产里"服务化"是两回事。生产环境有这些诉求：

  • 解耦：调用方（App 后端、前端、其他服务）不想关心模型怎么加载、在哪些卡上；
  • 复用：一个推理实例同时服务成千上万请求，而不是每个请求加载一次模型；
  • 标准化：用统一的 HTTP 协议，任何语言都能调；
  • 可运维：能监控、能限流、能灰度、能独立扩缩容。

于是业界收敛到一个事实标准——OpenAI Chat Completions 接口。vLLM、SGLang、TensorRT-LLM、llama.cpp 等都提供与之兼容的服务端点，你的代码写好一次就能在不同后端之间切换。

2. Chat Completions 接口的结构#

一次对话补全请求的核心字段：

  • model：模型名；
  • messages：消息列表，每条含 role（system/user/assistant）与 content；
  • stream：是否流式返回（true/false）；
  • temperature、max_tokens、top_p 等采样参数。

响应分两种模式：

  • 非流式：一次性返回完整的 choices[0].message.content；
  • 流式：把回答切成一个个增量（chunk），每个 chunk 携带 choices[0].delta.content 的一小段（往往就是一个或几个 token），逐步推送。

流式正是本章重点，因为它直接决定了用户体感。

3. 流式的原理：SSE 与增量推送#

LLM 是逐 token 生成的。非流式接口必须等最后一个 token 出来才返回，于是用户看到"转圈 → 突然整段文字"；流式接口每生成一个 token 就立刻把增量发出去，用户看到文字一个字一个字地长出来。对长回答，流式能把用户感知到的首屏时间从"整段耗时"缩短到"首 token 耗时（TTFT）+ 一小段"。

技术上，流式通常用 Server-Sent Events（SSE） 实现：服务器持有连接，持续向客户端推送多段数据，每段以 data: {json}\n\n 为帧，最后以 data: [DONE] 结束。SSE 是单向的、基于 HTTP 的简单协议，天然适合"服务器不断吐结果"的场景，比 WebSocket 更轻量。客户端只需逐行解析 data: 帧，把每帧的 delta.content 拼起来即可。

4. 服务如何启动，客户端如何解析#

推理引擎通常提供一个"启动即服务"的命令（如 vllm serve），默认监听 8000 端口，暴露 /v1/chat/completions 等路由。客户端可用官方 SDK（openai Python 包指向自己的 base_url）或直接 curl。解析流式响应时，注意两点：增量是碎片化的（不要假设一次收到一个完整 token），末尾要有 [DONE] 或连接关闭作为结束信号，还要处理网络中断后的重连与续传。

二、可运行代码示例#

示例 1：用 vLLM 起一个 OpenAI 兼容服务#

# 启动服务（默认监听 http://localhost:8000）
vllm serve meta-llama/Llama-3.1-8B-Instruct \
    --dtype bfloat16 \
    --max-model-len 4096

服务起来后，用 curl 直接发一个流式请求，直观看到 SSE 的原始帧：

curl -N http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "meta-llama/Llama-3.1-8B-Instruct",
    "stream": true,
    "messages": [{"role": "user", "content": "用一句话解释流式输出"}]
  }'

你会看到一行行 data: {"choices":[{"delta":{"content":"流"}}]} 之类的增量，最后一行是 data: [DONE]。-N 关掉 curl 的缓冲，让增量逐条显示。

示例 2：用 Python 客户端消费流式并拼出完整回答#

import json
import urllib.request

url = "http://localhost:8000/v1/chat/completions"
payload = {
    "model": "meta-llama/Llama-3.1-8B-Instruct",
    "stream": True,
    "messages": [{"role": "user", "content": "数到 5，并解释什么是 SSE"}],
}
req = urllib.request.Request(
    url, data=json.dumps(payload).encode("utf-8"),
    headers={"Content-Type": "application/json"},
)

answer = ""
with urllib.request.urlopen(req, timeout=60) as resp:   # 返回的是一个持续写入的流
    for line in resp:                                     # 逐行读取
        line = line.decode("utf-8").strip()
        if not line.startswith("data:"):
            continue
        data = line[5:].strip()                           # 去掉 "data:" 前缀
        if data == "[DONE]":                              # 结束标记
            break
        chunk = json.loads(data)
        delta = chunk["choices"][0]["delta"].get("content", "")
        answer += delta
        print(delta, end="", flush=True)                  # 边收边打印，模拟前端逐步渲染

print("\n\n完整回答长度:", len(answer))

这段代码演示了客户端解析 SSE 的完整逻辑：去 data: 前缀 → 判断 [DONE] → 取 delta.content → 累积。生产里你可以用 openai SDK 的 stream=True 一行搞定，但理解底层帧格式能帮你在排查连接问题时看清真相。

三、练习#

  1. 用 curl -N 请求一个流式接口，把原始输出保存到文件，数一数共有多少个 data: 帧、每个帧的 delta.content 平均几个字，理解"增量是碎片化的"。
  2. 把示例 2 改造成"边收边把增量写入网页/终端"的体验，并测量：首个 data: 帧到达的时间（近似 TTFT）与整段完成时间的差。
  3. 对比同一个问题在 stream=false 与 stream=true 下的用户感知首屏时间，说明为什么流式能显著改善长回答的体验。
  4. 用 openai SDK 指向 base_url="http://localhost:8000/v1" 重写示例 2，并尝试处理网络中断（加超时与重试），说明断点续传的难点。
