提示工程#

经过三阶段训练后，模型参数已经冻结，我们无法也不该再动它——这时还能"调"的，就是喂给它的输入。提示工程（prompt engineering）就是精心设计输入文本（提示），在不改参数的前提下，把模型已有的能力"引导"出来。本课讲清提示的结构、关键技巧、以及为什么提示如此敏感，并用代码演示提示如何被渲染成模型的真实输入。

一、概念讲解#

1. 什么是提示#

提示（prompt）是给模型的一段输入，通常包含三要素：

  • 系统消息（system）：设定角色、语气、约束，如"你是一名严谨的中文翻译"。
  • 用户消息（user）：具体问题或指令，如"把下面这句话翻成英文：今天天气很好"。
  • 示例（examples）：可选的输入—输出示范，用于演示任务格式（few-shot）。

这三部分会被拼接成模型真正"看到"的 token 序列。提示工程的本质，就是把"想让模型做的事"翻译成它最能正确理解的文字。

2. 核心技巧#

  • 指令具体化：帮我写点东西 远不如 写一段 200 字的产品介绍，语气专业，分三点列出卖点 有效。
  • 给示例（few-shot）：把输入输出格式演示给模型看，胜过干巴巴描述。
  • 给角色（role prompting）：你是一位有十年经验的儿科医生 会显著改变回答的专业度与谨慎度。
  • 约束输出格式：只输出 JSON，不要解释 能把回答限定成可解析的结构。
  • 分步与拆解：把大任务拆成小步骤（这正与后面要讲的思维链呼应）。

3. 为什么提示如此敏感#

同一句话换个说法，结果可能天差地别。原因是模型是统计的、上下文相关的：它根据整个提示的条件概率分布来续写，提示里的措辞、顺序、示例都会改变这个分布。这既是提示工程的用武之地，也是它的痛点——提示需要反复试错，且很难有"唯一正解"。

4. 解码参数：提示之外的"旋钮"#

除了文字本身，解码参数也直接影响输出：

  • temperature（温度）：T→0 输出确定性、更保守；T 增大输出更随机、更多样。
  • top-k / top-p：只在概率最高的 k 个（或累计概率 p 以内的）token 里采样，抑制低概率噪声。

这些参数不改变模型，只改变"从分布里怎么挑词"，是提示工程的重要补充。

5. 边界与风险#

提示工程不是万能的：它不能给模型注入新知识，也无法突破模型的固有缺陷。还要警惕提示注入（prompt injection）——攻击者把恶意指令藏在输入文本里，诱导模型违背系统设定，这是工程上必须防御的。

二、可运行示例#

下面用两段代码演示：① 如何把 system / user / few-shot 渲染成一条真实输入；② 温度与 top-k 如何改变解码结果。

# —— 示例一：把多角色消息 + few-shot 渲染成模型输入 ——
def render_prompt(messages):
    """把 OpenAI 风格的 messages 列表拼成一条文本（示意）。"""
    role_prefix = {"system": "【系统】", "user": "【用户】", "assistant": "【助手】"}
    return "\n".join(f"{role_prefix[m['role']]}{m['content']}" for m in messages)

messages = [
    {"role": "system", "content": "你是一名严谨的中文翻译，只输出译文，不解释。"},
    {"role": "user", "content": "苹果 → apple\n天气 → weather"},
    {"role": "assistant", "content": "明白，请继续。"},
    {"role": "user", "content": "猫 → ?"},
]
print(render_prompt(messages))
# —— 示例二：温度与 top-k 如何改变解码结果 ——
import torch
import torch.nn.functional as F

torch.manual_seed(0)

# 模型对下一 token 输出的 logits（示意：有 5 个候选词）
logits = torch.tensor([3.0, 2.0, 1.5, 1.0, 0.5])
words = ["猫", "狗", "鸟", "鱼", "虫"]

def sample(logits, temperature=1.0, top_k=None):
    scaled = logits / temperature                 # 温度缩放
    if top_k is not None:
        kth = torch.topk(scaled, top_k).values[-1]  # 第 k 大的分数作为阈值
        mask = scaled < kth                         # 低于阈值的位置屏蔽
        scaled = scaled.masked_fill(mask, float("-inf"))
    probs = F.softmax(scaled, dim=-1)
    return probs

probs_cold = sample(logits, temperature=0.2)       # 低温：更集中
probs_hot  = sample(logits, temperature=5.0)       # 高温：更平坦
probs_topk = sample(logits, temperature=1.0, top_k=2)  # top-2：只留前两名

print("低温 T=0.2 概率 :", [f"{w}:{p:.2f}" for w, p in zip(words, probs_cold.tolist())])
print("高温 T=5.0 概率 :", [f"{w}:{p:.2f}" for w, p in zip(words, probs_hot.tolist())])
print("top-2 概率     :", [f"{w}:{p:.2f}" for w, p in zip(words, probs_topk.tolist())])

可以看到：低温时"猫"几乎独吞概率（输出稳定、保守），高温时各词概率被拉平（输出多样、易跑偏），top-k 则直接砍掉低概率候选。这些"旋钮"与提示文字一起，决定模型最终吐什么。

三、练习#

  1. 改写指令：把"帮我写个邮件"改写成一条含角色、受众、语气、长度、格式约束的完整提示，逐项标注你用了哪些技巧。
  2. 观察温度：跑示例二，把 temperature 依次取 0.1、1.0、10.0，观察概率分布从"尖"到"平"的变化，并说明各适合什么场景。
  3. 手算 top-p：给定概率 [0.5, 0.3, 0.15, 0.05]，若 top_p=0.8，哪些候选会被保留？（提示：按概率从大到小累加，直到 ≥0.8）
  4. 设计 few-shot：为一个"商品评论情感三分类（正面/中性/负面）"任务，写 3 条 few-shot 示例，注意示例要覆盖边界情况。
  5. 思考风险：为什么"把用户输入直接拼进系统提示"可能带来提示注入风险？设计一个简单的防御思路。
