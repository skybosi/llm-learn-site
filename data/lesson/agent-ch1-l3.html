从「一次调用」到「闭环系统」：Agent 的定义与必须补上的四件事#

这一节要解决什么#

"Agent" 这个词已经被用坏了。市场上它同时指：一个套了系统提示词的 chatbot、一个 function calling 转发器、一个自动化脚本、一个多角色协作编排框架。当同一个词指四样东西时，讨论就没法继续了。

这一节要做的是把定义收回来：给一个可操作、可判别的定义 —— 拿到一段代码，你能判断它是不是 Agent；以及一个推导式的结构 —— 那四件事不是列表，而是上一节数学结论的直接产物。

学完这一节你应该能回答：

  • 一个"能调工具的 chatbot"和一个 Agent，差别到底在哪一行代码上？
  • 为什么"必须补上四件事（状态 / 行动 / 反馈 / 验证）"这个说法是对的？它从哪推出来？
  • 一个 Agent 的最小完整形态有多大？哪些组件是不可以省的？
  • "多智能体"是不是更高级的 Agent？（提前预告第 6 章：常常是负优化。）

一、先排除三个冒充者#

在给定义之前，先清理三个常见的误用，因为它们各自都缺了定义里的关键一环。

冒充者一：Function Calling 转发器。 它的形态是"模型说要调 get_weather，你调了，把结果塞回去，模型总结一句给你"。问题：它没有循环，也没有目标判据。 它只做一次"决策 → 执行 → 回填"，然后结束。它是一次调用的延伸，不是闭环。

冒充者二：固定工作流（workflow）。 形态是"if 用户问的是 A 就走 A 流程"。它的控制流是你写死的，模型的角色只是每个节点上的文本处理器。这类系统很有价值（而且常常比 Agent 更可靠、更便宜 —— 见第 2 章），但它的"下一步做什么"不由模型决定，因此不满足 Agent 的定义。

冒充者三：提示词工程包装的 chatbot。 它连"行动"都没有：模型只生成文本，没有任何副作用，也没有环境反馈。它是 LLM 的原生形态，不是 Agent。

三者共同缺的东西：由模型驱动、逐步推进、直到某个判据成立的控制流。 现在可以把定义写出来。

二、Agent 的判别式定义#

定义（判别式）：一个系统是 Agent，当且仅当它满足以下三条：

  1. 模型驱动：每一步"做什么"由模型在运行时决定，而不是由代码写死的分支决定。
  2. 闭环：上一步的真实结果（工具返回、环境状态）会被送回下一步的决策输入，而不是丢弃。
  3. 有终态判据：存在一个在循环之外的判据，能判断"目标已达成"或"必须放弃"，而不依赖模型自己声明。

三条缺一不可，而且第三条最容易缺。注意第 3 条里的关键词是"在循环之外"：如果判据是"模型说自己做完了"，那依据上一节的机制二（自评吸引子），这个判据会被局部最优俘获。

用一句话概括三者的差别：

形态 谁决定下一步 结果是否回流 谁判定结束
一次调用 你（prompt） 不回流（无下一步） 你（拿到输出就结束）
固定工作流 你（代码分支） 回流，但路径固定 你（流程走完）
工具转发器 模型（但只有一轮） 回流一次 模型（它说完了）
Agent 模型（每轮） 每轮都回流 循环外的判据

这张表的用法：拿到任何"Agent 框架"，问它这三个问题，就能知道它在哪一档。多数所谓的 Agent 框架实际上在第二档（工作流），这不是缺点 —— 是选型问题：如果任务能被工作流覆盖，用工作流（更可靠、更便宜、可测试）。Agent 只在你写不出那张分支图的时候才必要。

三、四件事：从上一节的数学里推出来#

现在回到上一节的结论，推导为什么是这四件（状态 / 行动 / 反馈 / 验证），而不是别的：

上一节的结论 缺了它会发生什么 必须补上的东西
Pn​=pn：误差随步数指数衰减 上一步的结果不进下一步，等于每步都从零开始（n 白费） 状态：跨步携带的、显式的中间结论
漂移机制三：误差经 L>1 的状态映射指数放大 只读的文本历史是扩张的，误差无阻尼 状态（收缩视图）+ 可回滚
p 是四环节乘积，瓶颈常在执行 模型能"描述"但不能"执行" 行动：受控的、有契约的副作用入口
错误可检测率 d 是最大杠杆 错误静默传播，d=0 时重试无效 反馈：把真实结果结构化地送回去
漂移不报错；自评 s^ 有偏 循环停在"看起来像进展"的地方 验证：循环外的硬约束判据

于是定义的四件事不是清单，而是四个洞的补丁：

3.1 状态（State）：把"记住了什么"从模型移进代码#

上一节讲过：模型无状态，对话历史存在你的代码里。但"状态"比"历史"要求更高：

历史（history）  ：发生过什么 —— 追加式、扩张、用于审计与重放
状态（state）    ：现在是什么情况 —— 收缩式、结构化、用于决策

两者必须分开存。混在一起的经典后果：把 40 轮的工具输出全塞回上下文，然后抱怨"模型在第 30 步开始胡言乱语" —— 你给它的不是状态，是一堆需要它自己去重的事实。

状态的结构也决定了漂移是否可控（上一节 L 的取值）：

状态形式 L 的量级 后果
自由文本不断追加 L>1（只能变大） 误差可被后续误读放大
结构化 KV（字段固定、枚举、数值） L≤1（字段被覆写） 误差被阻尼，漂移有界
显式类型化状态机（有限状态集合） L<1 漂移不可能（状态非法即被拒），但表达力受限

取舍：状态越结构化，越可验证、越抗漂移，但越难表达"部分完成""待确认"这类模糊中间态。第 4 章会给分层方案（工作记忆 + 长期记忆 + 检索式记忆）。

3.2 行动（Action）：受控的副作用入口#

"无行动能力"是模型的原生边界，所以行动必须由你提供。这里的核心设计不是"怎么调 API"，而是行动入口的契约：

① 声明：这个动作是什么（名字 + schema + 语义说明）
② 校验：参数在执行前被机械检查（类型、范围、必填、互斥）
③ 授权：高副作用动作在执行前可被拦截（人工 / 策略 / 限额）
④ 执行：真正产生副作用，且带幂等键
⑤ 回填：把结果（成功/失败的分类 + 可读信息）结构化地送回循环
⑥ 记录：动作、参数、结果、耗时、代价进入轨迹

这六步里有一步缺失，就会长出对应的经典 bug：

缺失 长出的 bug
② 校验 模型发明参数（传了 schema 里没有的字段，或把日期写成"下周三"）
③ 授权 Agent 自己删了生产库（demo 里真的发生过很多次）
④ 幂等键 超时重试导致重复下单
⑤ 结构化回填 模型看不懂错误，反复用同样的错参数重试
⑥ 记录 线上出问题后无法归因（第 7 章四象限做不了）

取舍：这六步都是成本。一个只读的 search() 工具不需要 ③；一个幂等的 get_page() 不需要 ④。按副作用强度分级：只读 / 幂等写 / 非幂等写 / 不可逆，四级分别配不同强度的 ②③④。第 3 章整章在展开这张表。

3.3 反馈（Feedback）：把真实结果变成一个"可学习的信号"#

反馈不只是"把结果塞回去"。它的设计标准是：这个反馈能不能让一个理性行动者改正错误？ 三个要求：

  1. 可判定：成功和失败要能被区分，且错误要分类（是参数错、权限错、还是目标不存在？）—— 不同的类对应完全不同的下一步。
  2. 可行动：反馈里要包含"改什么"的信息。{"error": "failed"} 是不可行动的；{"error": "field_missing", "field": "start_date", "hint": "ISO-8601"} 是可行动的。
  3. 不撒谎：不能把异常吞掉变成"操作成功"。把 5xx 包成 {"ok": true} 会让 Agent 在错误的状态上继续走 —— 这是漂移最廉价的制造机。

为什么"不要把异常原样抛给模型"（第 3 章第 3 节的主题）：原始栈追踪对模型既不必要（暴露实现细节，甚至可能被注入利用）又不可行动（它不知道该怎么改参数）。正确做法是在工具边界上把异常翻译成模型能行动的诊断。

3.4 验证（Verification）：循环外的那把尺#

定义里的第三条要求，也是四件事里最容易被省略、代价最高的一件。验证分两层：

过程验证（process）：每一步/每一段结束时检查硬约束 —— 拦住漂移
结果验证（outcome）：整条轨迹结束时检查目标达成 —— 决定交付与否

关键设计决策：验证器不能是模型自己。 理由在上一节的机制二：自评 s^ 与真实 s 有偏差，把判据交给生成者会让循环优化 s^。可行方案按可靠性排序：

验证器 可靠性 成本 适用
确定性断言（assert file_exists(...)、SQL 计数、schema 校验） 最高 极低 一切可机械检查的目标
独立模型评审（另一个模型 + 明确 rubric） 中 中 语义质量（"这份总结是否覆盖了要点"）
人工抽检 / 审批 高但慢 高 不可逆动作、高风险输出
模型自评 低（有系统性偏差） 低 仅作为提示信号，不可作为终止判据

取舍：确定性断言写不出来的时候（比如"这份文案够不够动人"），你只能退到模型评审或人工 —— 但此时必须接受一个更弱的终止保证，并把不确定性显式写进设计（比如"评审通过即交付，但抽样人工复核 5%"）。

四、最小完整 Agent 的组件图#

把四件事落成组件，一个不可再省的 Agent 长这样：

┌─────────────────────────────────────────────────────────────┐
│  外部输入（任务 / 事件 / 用户消息）                          │
└───────────────────────┬─────────────────────────────────────┘
                        ▼
        ┌───────────────────────────────┐
        │  状态存储 State                │◄──────────────┐
        │  · 工作状态（收缩、结构化）    │               │
        │  · 轨迹日志（扩张、只追加）    │               │
        └───────────┬───────────────────┘               │
                    ▼                                   │
        ┌───────────────────────────────┐               │
        │  上下文组装（第 4 章）         │               │
        │  从状态里挑出"这一步该看见的"  │               │
        └───────────┬───────────────────┘               │
                    ▼                                   │
        ┌───────────────────────────────┐               │
        │  决策：模型（唯一的模型环节）  │               │
        └───────────┬───────────────────┘               │
                    ▼                                   │
        ┌───────────────────────────────┐               │
        │  行动网关（契约/校验/授权/幂等）│               │
        └───────────┬───────────────────┘               │
                    ▼                                   │
        ┌───────────────────────────────┐               │
        │  环境 / 工具（真实世界）       │               │
        └───────────┬───────────────────┘               │
                    ▼                                   │
        ┌───────────────────────────────┐               │
        │  反馈翻译（异常 → 可行动诊断） │───────────────┘
        └───────────┬───────────────────┘
                    ▼
        ┌───────────────────────────────┐
        │  验证器（循环外）              │
        │  过程：硬约束逐步检查          │
        │  结果：目标达成判定 → 终止     │
        └───────────────────────────────┘

这个图里唯一的模型环节是"决策"。其余六块全是工程。这直接量化了上一节的结论：Agent 的能力上限由两侧工程决定，而不是由中间的模型决定 —— 因为模型即使完美，缺了"反馈翻译"，它也看不见世界；缺了"验证器"，它不知道何时停。

哪些组件不可以省？ 逐一做消融：

省掉 立刻出现的症状 能否用"更强的模型"弥补
状态存储 每步从零开始，重复劳动，n 白费 ✗ 模型再强也没跨调用记忆
上下文组装 要么爆上下文，要么漏关键信息 部分（长窗口缓解，但代价线性、注意力稀释）
行动网关 参数乱飞、越权、重复副作用 ✗ 模型不知道该守什么契约
反馈翻译 模型看不懂错误 → 盲目重试 部分（强模型更会猜，但仍然靠猜）
验证器 不知道何时停 → 耗尽预算或提前停 ✗ 自评有系统偏差

结论：只有"上下文组装"和"反馈翻译"能被更强的模型部分弥补，其余三块不能。 这就是为什么"等模型更强就好了"是对 Agent 最有害的期待。

五、Agent、工作流、多智能体：什么时候该用哪个#

这是本节的"取舍"部分。工程上正确的顺序是从下往上，而不是从最花哨的往下：

① 一次调用 / 固定工作流   —— 能写死分支就用它：最可靠、最便宜、可测试
② 单 Agent 闭环          —— 只在"分支写不出来"时用
③ 多 Agent               —— 只在"同一上下文里装不下"或"确实需要独立视角"时用（第 6 章）

判断是否该从 ① 升到 ②，问三个问题（对应定义的三条）：

  1. 下一步做什么，能否在运行前确定？（能 → 工作流）
  2. 中间的真实结果是否会改变后续路径？（不会 → 工作流）
  3. 是否存在一个可机械检查的终态判据？（没有 → 你根本没法知道它做完了，先解决这个）

三个问题里有一个答"不能/不会/没有"，就说明你在做的工作流覆盖不了 —— 才轮到 Agent。

这带来一个反直觉但正确的推论：能写死的部分要写死。 Agent 的成本、延迟、方差全部来自"让模型自由决定"，所以把能确定的决策（参数来源、重试策略、权限检查、终止条件）从模型手里收回来，是提高可靠性的主要手段，而不是"限制了 Agent 的能力"。第 5 章的 plan-execute 正是在说这件事：先把能规划的固定下来，再让模型处理剩下的不确定性。

代码：把判别式定义写成可执行的检查#

from dataclasses import dataclass, field
from typing import Callable, Any

@dataclass
class AgentSpec:
    """
    一个声明式的 Agent 规格。注意：四个字段恰好对应'必须补上的四件事'。
    设计决策：规格是数据，不是代码 —— 这样它才能被检查、被版本化、被测试。
    """
    # ① 状态：工作状态（收缩）+ 轨迹（扩张），两者分开
    state: dict = field(default_factory=dict)
    trace: list = field(default_factory=list)

    # ② 行动：工具注册表，每个工具有副作用等级
    tools: dict = field(default_factory=dict)      # name -> Tool

    # ③ 反馈：把工具结果/异常翻译成模型可行动的诊断
    translate: Callable[[Any], dict] = lambda r: {"ok": True, "result": r}

    # ④ 验证：循环外的判据（硬约束 + 终态）
    invariants: list = field(default_factory=list)  # list[Callable[[dict], bool]]
    is_done: Callable[[dict], bool] = lambda s: False


def is_agent(spec_or_code) -> tuple[bool, list[str]]:
    """
    判别式定义的可执行版本。返回 (是否 Agent, 缺了什么)。
    用法：把任何'号称是 Agent 的东西'传进来，看它缺哪一条。
    """
    missing = []
    # ① 模型驱动：必须有一个'每步调用模型'的入口
    if not hasattr(spec_or_code, "decide"):
        missing.append("模型驱动：没有每步调用模型的决策入口（可能是写死的工作流）")
    # ② 闭环：必须有把结果回填进下一步的机制（轨迹的存在是必要条件）
    if not getattr(spec_or_code, "trace", None):
        missing.append("闭环：没有结果回填/轨迹记录（结果被丢弃，等于每步从零开始）")
    # ③ 终态判据在循环之外：必须存在非模型提供的判据
    if not getattr(spec_or_code, "invariants", None):
        missing.append("验证：没有循环外的硬约束（只有模型自评 → 会被局部最优俘获）")
    if getattr(spec_or_code, "is_done", None) is None:
        missing.append("终止：没有终态判据（不知道何时该停）")
    return (len(missing) == 0), missing


def run_agent(spec: AgentSpec, task: str, decide, budget: int = 12):
    """
    最小闭环。每一行都标注它在补哪个洞 —— 这是本课反复要练的'读设计'能力。
    """
    spec.state["task"] = task

    for step in range(budget):
        # ④ 过程验证：每步先检查硬约束 —— 在违规当步就停，而不是跑完再看（拦住漂移）
        for inv in spec.invariants:
            if not inv(spec.state):
                return {"status": "violation", "step": step, "state": spec.state}

        # ① 决策：唯一的模型环节；输入是"收缩后的状态视图"，不是全部历史
        decision = decide(spec.state, spec.trace)

        if decision["kind"] == "final":
            # ④ 结果验证：模型说完了不算数，必须过 is_done 才算完成
            if spec.is_done(spec.state):
                return {"status": "done", "step": step, "state": spec.state}
            # 模型声称完成但判据不成立 → 这是'目标漂移'的典型现场，必须显式反馈
            spec.trace.append({"step": step, "event": "false_finish"})
            continue

        tool = spec.tools.get(decision["name"])
        if tool is None:
            # ③ 反馈：未知工具不抛异常，而是把'可用清单'作为可行动诊断送回去
            spec.trace.append({"step": step, "event": "unknown_tool",
                               "hint": list(spec.tools)})
            continue

        # ② 行动网关：校验 → 授权 → 执行（带幂等键）→ 回填
        if not tool.validate(decision.get("args", {})):
            spec.trace.append({"step": step, "event": "bad_args",
                               "hint": tool.schema_hint()})
            continue
        if tool.side_effect and not tool.authorized(spec.state):
            spec.trace.append({"step": step, "event": "denied",
                               "tool": tool.name})
            continue

        raw = tool.call(decision.get("args", {}), idem_key=f"{step}:{tool.name}")
        spec.trace.append({"step": step, "event": "call", "tool": tool.name,
                           "args": decision.get("args"), "raw": raw})
        # ③ 反馈翻译：把原始结果/异常变成'改什么'的信息，而不是栈追踪
        spec.state["last_feedback"] = spec.translate(raw)

    # 终止：预算耗尽也是一种'可解释的结论'，不是崩溃
    return {"status": "budget_exhausted", "step": budget, "state": spec.state}

三处值得停下来看的设计决策：

  1. decide(spec.state, spec.trace) 把当前状态和完整轨迹分开传 —— 这不是为了对称好看。状态是收缩的（决策用），轨迹是扩张的（审计用）。把它们合并传参，就是在代码层面承认"我要把全部历史塞进上下文"。
  2. 模型声称完成时要走 is_done 复检。这一段 if 就是"漂移"和"完成"的分界线：没有它，模型的自评直接等于终止条件。
  3. bad_args / unknown_tool 分支都不抛异常、不 return，而是记录 + continue。这是"反馈要可行动"的落地：一次参数错误不应该终止整个轨迹，它应该变成下一步的输入。

练习#

  1. 分类：下面四个系统各属于"一次调用 / 固定工作流 / 工具转发器 / Agent"哪一档？给出你依据的定义条款。 （a）RAG 问答：检索 → 拼上下文 → 回答； （b）"读邮件 → 判断是否要回复 → 若需要则起草 → 发出去"，中途会根据邮件内容查资料； （c）模型可以连续调用任意工具，直到它自己输出"任务完成"； （d）模型可以连续调用任意工具，但当且仅当 tests_pass() 为真时终止。
  2. 消融：从第四节的组件图里只删掉"反馈翻译"，写出一个具体的失败场景（要具体到工具名、错误类型、模型的下一步行为）。然后回答：把模型换成强一档的模型，这个场景会消失吗？为什么？
  3. 设计判据：为"帮我把这个仓库的依赖升级到最新且测试通过"写出（a）3 条过程硬约束、（b）1 条结果判据，要求全部可机械检查。然后指出：这个任务里哪些部分不可能有机械判据，只能靠模型评审？这类部分应该怎么处理（提示：见第三节验证器表格的"取舍"）。
  4. 反向题：下面这个任务，请论证"它不该做成 Agent"，并给出一个固定工作流的实现草图：每天 9 点抓取指定 5 个 RSS 源，去重，按固定模板生成摘要，发到邮箱。指出在这个任务里，Agent 的哪几条定义条款没有任何收益。
  5. 代码：用本节的 AgentSpec 实现一个"文件整理 Agent"（列出目录 → 判断文件类型 → 移动到对应子目录），要求：移动动作有幂等键、有硬约束"不删任何文件"、结果判据是"目标目录里不存在未分类文件"。跑起来后再故意让模型声称完成（返回 final）但目录里还有未分类文件，观察 false_finish 是否被记录。

小结#

  • 判别式定义（三条，缺一不可）：① 模型驱动每步决策；② 真实结果回流到下一步；③ 存在循环之外的终态判据。
  • "能调工具的 chatbot"缺 ②③；"固定工作流"缺 ①；"模型说自己做完了就停"缺 ③ 的"循环之外"这个限定。
  • 四件事是四个洞的补丁，不是清单：状态补"无记忆"、行动补"无行动能力"、反馈补"错误不可检测"、验证补"漂移不报错"。
  • 状态分两层：收缩的结构化工作状态（决策用）+ 扩张的轨迹日志（审计用）。混在一起是"第 30 步胡言乱语"的根因。
  • 行动是六步网关（声明/校验/授权/执行/回填/记录），按副作用等级分级配置，不是一律全套。
  • 验证器不能是模型自己：自评 s^ 有系统偏差，会把循环拉向"看起来像进展"的地方。可靠性排序：确定性断言 > 独立模型评审 > 人工 > 自评。
  • 组件图的七块里只有"决策"是模型；只有"上下文组装"和"反馈翻译"能被更强的模型部分替代，其余不能 —— 所以"等模型更强"不是策略。
  • 能写死的就写死：把确定的决策从模型手里收回，是提高可靠性的主要手段（不是限制能力）。

下一节：既然四件事都补上了，那么"补得好不好"怎么衡量？五个设计目标（可靠 / 可观测 / 可组合 / 可回滚 / 成本可控）各自的度量是什么，它们之间怎么冲突，以及一个真实的取舍案例应该怎么写进设计文档。
