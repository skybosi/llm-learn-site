前沿与变化中的变量：硬件、算法、服务形态三条轴上的可确证趋势#

这一节要解决什么#

上一节把账本的边界写清楚了：给定输入，我们知道"什么时候必须重算"。但真实世界里的输入一直在变 —— 换一代卡、换一种解码算法、换一种服务形态。于是出现一个很难做的动作：

面对一条新进展，判断它"会不会改变我的结论"

这件事难在两处：

  1. 不编数字就写不出"前沿"。任何"下一代 HBM 带宽是 X TB/s"的说法，只要 X 不是可查证的事实，就是在编。
  2. 不写机制就只剩名词。堆"FP4、稀疏、MoE、端云协同"这些词，读者拿不到任何可操作的东西。

本节的处理办法是把"前沿"翻译成三种可确证的陈述：

类型 形式 例子 可确证的理由
① 同一性/机制式 该变量进入哪一项、方向如何 "HBM 带宽只进 cw​ 与 ckv​" 从 tstep​ 的结构直接推出
② 单调方向式 在某区间内单调，不给具体数字 "带宽上升使 cw​ 下降 ⇒ TPOT 下降" 只需要方向，不需要未来产品的参数
③ 阈值/条件式 翻转需要多少倍、在什么条件下兑现 "C/B 要变化 6.09 倍才换 binding" 可算，且不依赖具体产品

明确不做的第四种：预测某个产品的具体指标、把"某公司说下一代是 N 倍"当论据、用未发布的规格做算例。这三种都不写。

一、方法：先划出"不变的那部分"#

要让"变化中的变量"可讨论，第一步不是列举变化，而是先划出不变的。本节的程序用四个检验把不变式钉住：

检验 1A：把 (B, C) 同时 ×k → I_mach、b_ridge、binding 标签完全不变（只有 c_w 按 1/k 变）
检验 1B：把 (P, B) 同时 ×k → c_w 不变，但 b_kv 随 k 线性下降（显存没同步）
检验 2 ：b_kv 与算力无关 —— C 变化 16 倍，b_kv 恒为 77.01
检验 3 ：n ≳ 10/(1−p) —— 与硬件、算法、形态都无关
检验 4 ：S* = N·α·β —— decode 的消息尺寸远小于 S*，所以"降 α"比"提 β"值钱

这套账依赖的是一组无量纲比值： 2BσC​, VGPU​WB​​, WB​kv1​sˉ​, Ctcomm​2P​​

为什么这很重要：它意味着"前沿"里的大部分变化不会改变账本的形式，只会挪动这几个比值。于是判断一条新进展就变成了一个可操作的动作：

① 它动了哪个比值？
② 比值动完之后，binding 标签会不会换？
③ 换了之后兑现的是成本、延迟还是容量？

第 1 节到第 4 节就是把三条轴上的每一项都放到这套流程里跑一遍。

二、硬件轴：三类变化，三条不同的通道#

2.1 HBM 带宽：只走延迟通道#

机制：带宽只出现在两个地方

cw​=B⋅ηWB​/TP​,ckv​=B⋅ηkv1​Lˉkv​/TP​

方向：B↑⇒cw​,ckv​↓⇒tstep​↓⇒ TPOT↓、TTFT↓。

兑现多少（程序第 (1) 段，B×2）：

Δ吞吐 = +0.8%     ΔTPOT = −31.5%     ΔTTFT = −30.5%     Δb_kv = 0     ΔN* = 0     Δ月成本 = 0

带宽 ×2 把 TPOT 降 31.5%，但一个月成本都不省 —— 它只走延迟通道​

为什么：成本是 N∗ 的阶梯函数，而 N∗ 由 C1​（吞吐裕度）决定；在需求受限区（b<bcap​），tstep​ 下降的同时 b=λs/N 也下降，两者近似抵消（第 1 节的弹性 Sthr​(B)=+0.013）。"延迟变好"与"成本变低"在这一区间不是同一件事。

边界：若当前 binding 是 C2​（KV 容量），带宽仍然不改 bkv​ —— 容量帽只由显存、权重字节与序列长度决定。

这条结论落在程序第 (1) 段的哪一行：NVLink 带宽 ×2 → Δ吞吐 0.0%、ΔTPOT −0.0%、ΔTTFT −0.1% —— 旋钮无效。不是 NVLink 不重要，而是"提带宽"这个方向对本工作点不重要。

怎么做：能降 α 的手段是"减少通信步数"与"缩短路径"（更深的域内互连、在网归约、更少的跳数），而不是"更大的管道"。这与第 3 章第 1 节"步数 ∝N、字节趋于饱和"是同一个结论。

2.3 新精度：同时改三条通道，但方向相反#

机制：σ（字节/参数）同时进入三项：

cw​∝σ,ckv​∝σ,bkv​∝σ1​,bridge​=2BσC​∝σ

方向：σ↓⇒ 延迟通道放松（TPOT/TTFT 下降），容量通道放松（bkv​ 上升），但拐点通道变紧（bridge​ 下降 ⇒ 更早进入算力区）。

兑现（程序第 (1) 段，bf16 → FP8）：

Δ吞吐 = +0.8%     ΔTPOT = −31.5%     ΔTTFT = −30.5%     Δb_kv = +140.8%     Δ月成本 = 0

新精度的收益在哪一侧兑现，取决于当前 binding 的是 C1​ 还是 C2​​

  • 本例 b/bkv​=0.63（C1​ binding）⇒ 精度提升不省卡，只降延迟；
  • 若把 Lp99​ 提到 8,000（b/bkv​→1.00）⇒ 容量变成 binding，此时同一个 FP8 会直接省副本。

边界：精度还带一个第 6 章已经量化过的非性能代价 —— 数值风险。第 6 节说过"每一步上线前必须给出三个数（收益/风险/回退）"，对精度这一步而言，风险那一栏是回归集上的最大相对误差 ≤ 1e-3。

2.4 硬件轴上唯一"结构性"的事实：容量与算力解耦#

程序检验 2 的结果值得单独抄出来：

C × 0.25 / × 1 / × 4  →  b_kv = 77.01 / 77.01 / 77.01（完全相同）

bkv​=s⋅kv1​VGPU​−WB​/TP−Wact​​ 里没有算力​

所以硬件演进分成两类，它们的兑现通道完全不同：

类型 例子 兑现通道 会不会省钱
算力类 FLOPS、稀疏 Tensor Core 无（在带宽区） 不会
访存/容量类 HBM 带宽、HBM 容量、精度、KV 压缩 延迟 + 容量 只在 C2​ binding 时

这是一条判断新硬件的通用规则：先问"它动的是 FLOPS 还是 bytes/capacity"，再问"当前 binding 的是谁"。

3.1 稀疏：只有"算力项是 max"时才兑现#

程序第 (1) 段的两行是最直接的证据：

稀疏 2×  → Δ吞吐 0.0%   ΔTPOT 0.0%   Δb_kv 0.0%   Δ月成本 0   → 旋钮无效
稀疏 4×  → Δ吞吐 0.0%   ΔTPOT 0.0%   Δb_kv 0.0%   Δ月成本 0   → 旋钮无效

兑现条件:访存项算力项​=cw​+bckv​2Pb/(NCsp​)​>1

本例该比值为 0.138：算力侧要加速 7.23 倍才追平访存项；而追平之后 max 不变，收益仍然是 0。提高吞吐的唯一路径是压低访存项（更小的 σ、更小的 kv1​、更短的 Lˉ）。

税①=C1​ (容量因子),税②=1+2lnE(1−E1​)TKE​​1​

第 1 节算过：E=64、K=2、decode 的 T=b=48.5 时，税②达 30.1%，与 1/C=80% 相乘只剩 24.1%。

方向与边界：T 越大税②越小。decode 下 T=b（每序列一步一 token），prefill 下 T= 整段 prompt 长度 ——

MoE 的收益在 prefill 侧兑现得比 decode 侧充分；decode 侧先被两笔税各削一刀​

怎么做：把 MoE 的判据写成"T 是否够大"，而不是"专家数是否够多"。要 95% 的税②效率需要 T≈94,585 token/步。

3.4 算法轴改不动的东西#

  • α-β 结构：算法不改变"每步要发几次消息"的量级（除非把整类并行去掉）。
  • n≳10/(1−p)：算法不改变分位可测性的样本量。
  • 统计波动的 ⋅​ 律：E[max]≈μ+σ2lnN​、P(min>t)=P(X>t)2 与算法无关。

这就是"不变式"的用法：一条新算法如果声称"能改善尾延迟"，先看它是否改变了 ⋅​ 律里的哪一项；如果什么都没改，那它改善的只会是 μ。

4.3 分池与混池#

多模型路由与多租户其实共享同一个结构：把不同分布的请求放进同一个池子，会让池子的容量按最坏分布预留。第 1 节已经量化过这一点（KV 混合税 1.82×，分池只省 10.6% 显存），第 4 章给出了它对延迟的影响（慢租户把快租户挤到 p99​ 4540 ms）。所以形态演进的判据不是"要不要分池"，而是：

分池⟺（延迟隔离的价值）>（池子碎片化的成本）

这是"服务形态"这一轴唯一一条跨形态通用的判据。

class Svc:
    def __init__(self, **over):
        d = dict(BASE)
        d.update(over)
        self.__dict__.update(d)
        self.kv_1 = 2 * self.layers * self.kv_heads * self.head_dim * self.wbytes
        self.w_gpu = self.P * self.wbytes / self.wq
        self.kv_budget = self.vgpu - self.w_gpu - self.act
        self.seq_max = self.lp99 + self.pout
        self.b_kv = self.kv_budget / (self.seq_max * self.kv_1 * self.kv_scale)
        self.Lkv = self.lp50 + self.pout / 2
        self.c_w = self.w_gpu / (self.bw * self.bw_eff) * 1e3
        self.c_kv = self.Lkv * self.kv_1 * self.kv_scale / (self.tp * self.bw * self.bw_eff) * 1e3
        self.thr_req = self.lam * self.pout
        self.b_cap = min(self.b_kv, self.qmax)
        self.thr_max = self.b_cap / (self.t_step(self.b_cap) / 1e3)

    def t_mem_ms(self, b):
        return self.c_w + b * self.c_kv

    def t_comp_ms(self, b):
        return 2 * self.P * b / (self.tp * self.peak * self.sparse * self.mfu) * 1e3

    def t_comm_ms(self, b):
        act = b * self.d_model * self.wbytes / 2
        attn = self.tp * self.seq_max * self.head_dim * self.wbytes / 2
        return 4.0 * (act + attn) / self.nvlink * 1e3

    def t_step(self, b):
        return max(self.t_mem_ms(b), self.t_comp_ms(b)) + self.t_comm_ms(b) + self.t0

    def t_prefill(self, L):
        return (2 * self.P * L / (self.tp * self.peak * self.mfu) * 1e3
                + self.t_comm_ms(self.b_cap) + self.t0)

    @property
    def T_pref(self):
        return self.t_prefill(self.lp99 * (1 - self.h))

    def solve(self, N):
        lam_r = self.lam / N
        cap = self.b_cap
        s = self.T_pref / 1e3 + self.pout * self.t_step(cap) / 1e3
        for _ in range(800):
            b = min(lam_r * s, cap)
            s_new = self.T_pref / 1e3 + self.pout * self.t_step(b) / 1e3
            if abs(s_new - s) < 1e-13:
                s = s_new
                break
            s = 0.5 * (s + s_new)
        b = min(lam_r * s, cap)
        t = self.t_step(b)
        thr = b / (t / 1e3)
        mu = self.qmax / s
        rho = lam_r / mu
        tq = math.log(50.0) / (mu - lam_r) * 1e3 if rho < 1 else float("inf")
        ttft = tq + self.T_pref
        margin = thr * N / self.thr_req
        pref_m = (self.tp * self.peak * self.mfu / (2 * self.P)) * N / (self.lam * self.lp99 * (1 - self.h))
        why = []
        if margin < 1.0:
            why.append("C1")
        if lam_r * s > cap + 1e-9:
            why.append("C2")
        if t > self.tpot_slo:
            why.append("C4")
        if ttft > self.ttft_slo:
            why.append("C5")
        if rho >= 1:
            why.append("R0")
        if pref_m < 1:
            why.append("C3")
        return dict(N=N, gpus=N * self.wq, b=b, cap=cap, b_kv=self.b_kv, t=t, thr_gpu=thr,
                    thr_tot=thr * N, margin=margin, rho=rho, ttft=ttft, pref_m=pref_m,
                    kv_used=b * self.seq_max * self.kv_1 * self.kv_scale / self.tp,
                    ok=not why, why=" ".join(why))

    def best(self, nmax=300):
        for N in range(1, nmax):
            r = self.solve(N)
            if r["ok"]:
                return r
        return None

    def money(self, r):
        rev_h = r["N"] * self.price
        return dict(month=rev_h * 24 * 30, rev_h=rev_h,
                    cny_M=rev_h * 24 * 30 / (r["thr_tot"] * 3600) * 1e6)

五处关键设计决策：

  1. 兑现表按"通道"而不是"大小"分类：一个进步可以改 31.5% 的 TPOT 却省 0 元（HBM ×2）。只看百分比会把"延迟改善"误读成"成本改善"。
  2. 不变式用两组对照检验，而不是一次缩放：1A（只缩放 B,C）证明结构结论不变、架构结论会变；1B（缩放 P,B）证明 cw​ 不变但 bkv​ 会变。一次缩放检验不出"哪些量没跟着缩放" —— 而结论翻转恰恰发生在这里。
  3. 端云协同分两笔否决理由：字节比（32,768×）与端算力（59×）。它们对应两种完全不同的修复手段（压缩 KV/换上行 vs 换端侧芯片），合并成一句"端云不划算"就丢掉了可操作性。
  4. 级联的两个阈值分开算：qcost∗​=0.762 而 qlat∗​=0.364。只写"路由能省 70% 成本"会掩盖"它在 q>36% 时已经违反均值 SLO"。
  5. p99​ 的结论写成"硬结论"：q≥1% 时 p99​ 必然走升级路径 —— 这不是估算，而是分位定义的直接推论。凡是定义级推论，就不该用"经验上"来表述。

读输出的三处要点：

  • (1) 段的 "稀疏 2×/4× 两行的 Δ 全为 0.0%"：这是本节最有说服力的一行。它把"稀疏省钱"从宣传变成了条件命题。
  • (2) 检验 1A 的 "N 从 3 → 2 → 1"*：结构结论（binding 标签）不变，架构结论（副本数）变了。判断"一条进展要不要跟"时，这两类结论必须分开问。
  • (3) 段的 "B/A = 34× 且不再下降"：带宽从 20 Mbps 提到 10 Gbps，比值从 188× 只降到 34× —— 剩下的 34 倍全部来自端算力，不是网络。所以"加带宽就能端云协同"是错的。

小结#

  • "前沿"可以只写三种陈述：机制/同一性式、单调方向式、阈值/条件式。不写第四种（预测具体产品指标）。
  • 这套账依赖一组无量纲比值：σC/(2B)、WB​/VGPU​、kv1​sˉ/WB​。检验 1A 显示：(B,C) 同比例提升时，Imach​、bridge​、binding 标签完全不变，但 N∗ 会从 3→2→1 —— 结构结论不变、架构结论会变。
  • 硬件分两类：算力类（在带宽区不兑现）与访存/容量类（走延迟与容量通道）。bkv​ 与算力无关（C 变 16 倍它恒为 77.01）—— 买快卡不解决容量。
  • 算法只有两条路径：降每 token 访存字节（cw​,ckv​）或降二次项系数（s∗）。稀疏在本工作点 Δ 全为 0（算力项/访存项 = 0.138）；MoE 要付 1/C 与波动两笔税（C=1.25、T=48.5 时只剩 24.1%），而它在 prefill 侧兑现得更充分。
  • 互连只有"降 α"值钱：decode 的消息是 KiB 量级，远小于 S∗=Nαβ（N=2 时 4.4 MiB）—— 所以"NVLink 带宽 ×2"的 Δ 吞吐是 0.0%。
  • 端云协同被两笔独立的账否决：KV 上行 vs prompt 上行差 32,768 倍；端算力差 59 倍。可用的形态是端侧自己 decode，而它受端显存带宽限制（ttok​=Pσ/Bdev​）—— 与第 1 章"decode 是带宽区"闭合。
  • 多模型路由有两个不同阈值：qcost∗​=0.762、qlat∗​=0.364，延迟先 binding；且只要 q≥1%，p99​ 就 100% 走升级路径（路由救不了尾延迟，hedge 可以，代价 +20% 成本）。
  • 八条不变式是判断变化的工具：无量纲性、容量解耦、拐点、稀疏兑现条件、α-β 结构、MoE 两笔税、⋅​ 律、分位可测性。它们都不依赖具体产品参数。
  • 一句话：判断一条新进展只需要三步 —— 它动了哪个比值？binding 会不会换？换完兑现的是成本、延迟还是容量？ 三步都对不上的进展，不管新闻里多大，都不会改变你的结论。
