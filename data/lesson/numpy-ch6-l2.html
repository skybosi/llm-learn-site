性能对比#

上一课我们讲了向量化"为什么快"的道理。但"快多少"、"什么时候值得向量化"、"是不是所有循环都要消灭"，这些实际问题需要实测来回答。这一课我们学会如何科学地测量代码性能，用数据说话，并建立对"何时向量化"的理性判断。

一、概念讲解#

1. 如何测量一段代码的耗时#

测量耗时最直接的工具是 Python 标准库的 time.perf_counter()：在代码前后各取一次时间戳，相减得到耗时（秒）。它精度高、不依赖第三方库，适合在脚本里对比两段代码。

import time
t0 = time.perf_counter()
# ... 被测代码 ...
t1 = time.perf_counter()
print(f"耗时 {t1 - t0:.6f} 秒")

如果希望更严谨，可以用标准库的 timeit 模块，它在后台多次运行并取最优，能有效降低系统负载波动带来的噪声。不过对"宏观对比 Python 循环 vs 向量化"这种量级差异，perf_counter 已经足够说明问题。

2. 差距有多大：数量级的鸿沟#

Python 循环与向量化之间的差距通常不是"快 10%"，而是快几十倍到几百倍，而且数据量越大，差距越悬殊。原因在于：

  • 向量化的耗时基本与数据量成线性增长，且常数极小；
  • Python 循环的耗时也随数据量线性增长，但每个元素的"解释器开销"常数很大。

于是随着 N 增大，两者都线性上升，但斜率的差距被无限放大——N 从 1 万变成 100 万时，向量化可能只慢几倍，而 Python 循环会慢几十倍、几百倍。

3. 复杂度：决定"要不要向量化"的根本依据#

判断一段代码该不该向量化，先看它的时间复杂度：

  • 如果本来就是一个 O(N) 的逐元素操作，向量化能带来巨大常数优化，强烈建议向量化；
  • 如果算法本身是 O(N²) 的双重循环（如朴素的两两比较），向量化仍能提速，但更该优先思考"算法本身能不能优化"——例如用排序、哈希、分治把复杂度降下来，往往比"把循环挪进 C"收益更大。

4. 向量化不是万能的：哪些场景要克制#

向量化也有代价，不能无脑堆：

  • 内存占用：某些向量化写法会构造巨大的中间数组（比如显式扩展维度），数据量极大时可能撑爆内存；
  • 可读性：过度"炫技"的一行向量化，可能让代码难以维护；
  • 小数组：数据只有几十个元素时，向量化的"固定开销"可能反而比循环大，不过这种差异微乎其微、通常无需纠结。

务实的态度是：热点代码优先向量化，非热点代码以清晰为先。

二、可运行示例#

示例 1：用 perf_counter 对比循环与向量化

import numpy as np
import time

N = 1_000_000
x = np.random.default_rng(0).random(N)

# ---- 版本一：Python 循环逐元素求平方和 ----
t0 = time.perf_counter()
total = 0.0
for v in x:
    total += v * v
t1 = time.perf_counter()
loop_time = t1 - t0

# ---- 版本二：向量化求和 ----
t0 = time.perf_counter()
total_vec = np.sum(x ** 2)
t1 = time.perf_counter()
vec_time = t1 - t0

print(f"Python 循环耗时: {loop_time:.4f} 秒")
print(f"向量化耗时:     {vec_time:.4f} 秒")
print(f"向量化快了 {loop_time / vec_time:.1f} 倍")
# 结果应一致（可能有极小浮点误差）
print("结果一致:", np.isclose(total, total_vec))

示例 2：规模增大时倍数的变化

import numpy as np
import time

def bench(n):
    x = np.random.default_rng(1).random(n)

    t0 = time.perf_counter()
    s = 0.0
    for v in x:
        s += v
    t_loop = time.perf_counter() - t0

    t0 = time.perf_counter()
    s2 = np.sum(x)
    t_vec = time.perf_counter() - t0
    return t_loop, t_vec

# 用不同规模测试，观察倍数随 N 增长
for n in [1_000, 10_000, 100_000, 1_000_000]:
    t_loop, t_vec = bench(n)
    print(f"N={n:>9,}  循环 {t_loop:.4f}s  向量化 {t_vec:.4f}s  加速 {t_loop/t_vec:.0f}x")

示例 3：np.where 与 Python 条件循环的对比

import numpy as np
import time

N = 500_000
scores = np.random.default_rng(2).integers(0, 101, size=N)

# Python 循环版
t0 = time.perf_counter()
result_loop = ["及格" if s >= 60 else "不及格" for s in scores]
t1 = time.perf_counter()

# 向量化版
t2 = time.perf_counter()
result_vec = np.where(scores >= 60, "及格", "不及格")
t3 = time.perf_counter()

print(f"列表推导耗时: {t1 - t0:.4f} 秒")
print(f"np.where 耗时: {t3 - t2:.4f} 秒")
print("结果一致:", list(result_vec) == result_loop)

示例 4：用 timeit 做更稳定的测量

import numpy as np
import timeit

x = np.random.default_rng(3).random(1_000_000)

# timeit 的第一个参数是要计时的语句字符串，number 是执行次数
t_loop = timeit.timeit("sum(v*v for v in x)", globals=globals(), number=5)
t_vec = timeit.timeit("np.sum(x ** 2)", globals=globals(), number=5)

print(f"timeit：循环 5 次总耗时 {t_loop:.4f}s")
print(f"timeit：向量化 5 次总耗时 {t_vec:.4f}s")
print(f"加速比 ≈ {t_loop / t_vec:.0f}x")

三、练习#

  1. 亲手测一次：用 time.perf_counter 对比"Python 循环求均值"与"np.mean"，数组规模取 100 万，报告各自的耗时与加速倍数。
  2. 规模扫描：写一个函数，对 N = 1000、1 万、10 万、100 万分别测量"循环求和 vs np.sum"，观察加速倍数随 N 的变化趋势并解释。
  3. 更复杂的操作：对比"用双重循环计算两个各含 200 个点的点集距离矩阵"与"用向量化广播计算"，报告加速比。注意循环版规模别设太大以免等太久。
  4. 内存意识：思考并回答——为什么说"某些向量化写法会占用大量中间内存"？试着举一个"显式扩展维度导致内存暴增"的例子。
  5. 反思：回顾你自己写过的一段 Python 代码，找出一处可以用向量化加速的地方，说明改写思路，并评估它是否属于"热点代码"、值不值得改写。
