异步拷贝与双缓冲：cp.async 与流水线#

上一课把搬运量降了一个数量级，但块内循环仍然是"搬完才能算、算完才能搬"：一次 HBM 访问的延迟是几百个周期量级，而一次 T×T 块的计算只要几十个周期。串行执行的结果是流水线大半时间在空转。这一课讲清 cp.async（Ampere 起提供的异步拷贝）与多级缓冲（double buffering / multi-stage pipeline）如何把这段延迟藏起来。

一、概念讲解#

1. 同步搬运的三个代价#

一段同步的 shared memory 装载代码长这样：LDG（global → 寄存器）→ STS（寄存器 → shared memory）→ __syncthreads() → 计算。它有三个问题：

  1. 延迟完全暴露：装载必须全部完成才轮到计算，等待期无法用别的活填补。
  2. 占着寄存器：数据在寄存器里过一遍，在飞的 load 越多，被占的寄存器越多，直接压低 occupancy（第 4 课）。
  3. 指令可能被穿插：官方文档在 stencil 例子里明确指出，条件代码下编译器可能生成 LDG/STS/LDG/STS… 交替序列，而不是理想的"3 个 LDG 全发出去再 3 个 STS"——那样才能让多个 load 同时在飞。

2. cp.async（LDGSTS）：把数据直接写进 shared memory#

cp.async 是 Ampere（compute capability 8.0）引入的异步拷贝机制，官方文档按 PTX 指令名叫它 LDGSTS。它的关键性质都是可查的硬约束：

  • 尺寸：一次拷贝 4、8 或 16 字节。4/8 字节走 L1 ACCESS 模式（数据也会缓存进 L1），16 字节走 L1 BYPASS 模式（不污染 L1）。
  • 方向：只支持 global → shared memory；写回 global 仍要走寄存器。
  • 对齐：指针按 4/8/16 字节对齐（取决于拷贝尺寸）；两边都 128 字节对齐时性能最好。
  • 不经寄存器：数据从 global 直接落到 shared memory，这是它同时省指令和省寄存器的原因。

它带来的是三个问题换一个：拷贝发起之后线程可以继续干活，但"数据到底到了没有"必须显式等。完成信号走 pipeline 机制：__pipeline_commit() 提交当前一批拷贝，__pipeline_wait_prior(N) 表示"最多允许还有 N 批没完成"。还有一条容易踩的规则：默认每个线程只等自己的拷贝，所以只要拷贝结果会被别的线程读，wait_prior 之后必须再补一个 __syncthreads()。

CUDA 提供三层 API 做同一件事，理解差异比记住函数名重要：

API 完成机制 备注
__pipeline_memcpy_async + __pipeline_commit + __pipeline_wait_prior（<cuda_pipeline.h>） pipeline 最底层、最啰嗦，但保证底层用 LDGSTS
cuda::memcpy_async（配 cuda::barrier） 异步 barrier 可用 cuda::aligned_size_t<N>() 声明对齐以启用 LDGSTS
cooperative_groups::memcpy_async cg::wait(block) 写法最短；文档明确指出它每次拷贝立即提交，失去了批量提交的优化

3. 双缓冲：把"搬"和"算"摆到同一段时间里#

思路一句话：在计算第 i 块的同时，让硬件去搬第 i+1 块。shared memory 里开两块缓冲，交替使用。

用一个可验证的周期模型算账（下一节代码实跑）：设每轮拷贝发起占 2 周期、数据在发起后 40 周期可用、每轮计算 20 周期，共 12 轮：

缓冲级数 S 总周期 每轮 相对 S=1 说明
1 720 60.0 1.00× 完全串行（40+20）
2 380 31.7 1.89× 只能提前 1 轮，藏不完 40 周期的延迟
3 280 23.3 2.57× 等于下界 40+12×20，延迟已完全隐藏
4 280 23.3 2.57× 再深无收益，只多占 shared memory

规律很清楚：要藏住延迟 L、每轮计算 C，需要的级数约为 L/C+1。这正是官方 prefetch 示例里 num_stages 与 consumer_wait_prior<num_stages-1> 的语义——允许提前 num_stages-1 批拷贝在飞。

寄存器侧同样有账可算。一个 128×64 的 fp16 tile = 16 KiB，用 256 线程搬：

  • 同步路径：每线程 64 字节 = 4 次 16 字节访问，需要 4 条 LDG.128 + 4 条 STS.128 = 8 条指令，外加约 16 个在飞数据寄存器；
  • cp.async：每线程 4 条指令，数据寄存器 0 个（16 字节模式走 L1 BYPASS）。

指令少了、寄存器空了——省下的寄存器正是留给累加器和更大 tile 的（第 4 课）。

4. 级数不是越多越好#

每加深一级就多一份 shared memory：S 级 × 每块 T×T 的 A/B 条带。T=32、单精度时一份 8 KB，3 级就是 24 KB 起步；shared memory 是 occupancy 的四个限制因素之一。所以实践中常见 2~4 级：先按 L/C+1 估下界，再看 shared memory 允许多少。此外，级数超过 k 段数（K/T）毫无意义——没有那么多块可提前搬。

5. 常见坑#

  • 漏 __syncthreads()：cp.async 默认只等自己那批，别的线程可能读到半成品数据。
  • 漏 wait_prior：数据没到就读，读到的是 buffer 里的旧值——结果错得"看起来合理"，最难查。
  • 对齐没做：16 字节拷贝要求指针 16 字节对齐，否则退化甚至报错；两边 128 字节对齐才拿到最好性能。
  • 想用 cp.async 写回 global：不支持，方向只有 global → shared。
  • 缓冲生命周期搞错：一个 stage 还没被消费完就又拿去发起新拷贝（producer/consumer 顺序颠倒）。
  • 无脑加深：延迟藏住之后加深只浪费 shared memory 和同步开销。

二、可运行代码示例#

下面的纯 Python（标准库，无需 GPU）把两件事算清楚：流水线的周期账（级数 → 收敛时间）与搬运指令/寄存器账。

# ===== 本课示例：软件流水线的周期账 + cp.async 的指令/寄存器账 =====
def pipeline(S, n=12, latency=40, t_copy=2, t_comp=20, trace=False):
    """S 级缓冲的软件流水线：拷贝引擎按发起顺序串行；数据在发起后 latency 周期可用。"""
    issue_free, buf_free, comp_end = 0, [0] * S, 0
    rows = []
    for i in range(n):
        s = i % S
        start = max(issue_free, buf_free[s])       # 该级缓冲被上一轮计算占着就得等
        ready = start + latency
        prev_end = comp_end
        cs = max(prev_end, ready)                  # 计算要等数据到，也要等上一轮算完
        ce = cs + t_comp
        buf_free[s], issue_free, comp_end = ce, start + t_copy, ce
        rows.append((i, start, ready, cs, ce,
                     '等数据就绪' if ready > prev_end else '等上轮计算'))
    if trace:
        print(f"  {'轮次':>4} {'发起':>5} {'就绪':>5} {'计算起':>7} {'计算止':>7}  卡在哪")
        for i, st, rd, cs, ce, why in rows:
            print(f"  {i:>4} {st:>5} {rd:>5} {cs:>7} {ce:>7}  {why}")
    return comp_end

n, lat, tc, tf = 12, 40, 2, 20
print(f"模型：每轮 copy 发起占 {tc} 周期，数据 {lat} 周期后就绪，计算 {tf} 周期，共 {n} 轮\n")
base = pipeline(1)
print(f"{'缓冲级数 S':>10} {'总周期':>7} {'每轮周期':>9} {'相对 S=1':>9}  {'说明':<12}")
for S in (1, 2, 3, 4):
    tot = pipeline(S)
    note = '完全串行' if S == 1 else ('延迟尚未藏完' if tot > n * tf + lat else '延迟已完全隐藏')
    print(f"{S:>10} {tot:>7} {tot/n:>9.1f} {base/tot:>8.2f}x  {note:<12}")
print(f"\n理想下界（prologue + n×计算）= {lat + n*tf} 周期\n")
print("S=2 的时序：")
pipeline(2, trace=True)

print("\n--- 一个 128×64 fp16 tile（16 KiB）的搬运指令账，block = 256 线程 ---")
TILE_BYTES, THREADS = 128 * 64 * 2, 256
per_thread = TILE_BYTES // THREADS
print(f"每线程搬运 {per_thread} 字节 = {per_thread//16} 次 16B 访问")
print(f"同步路径 LDG.128 + STS.128 : {2*per_thread//16} 条指令/线程，"
      f"~{per_thread//4} 个寄存器在-flight")
print(f"cp.async.cg 16B           : {per_thread//16} 条指令/线程，0 个数据寄存器")
print(f"TMA（Hopper，整块描述符）  : 1 条指令/线程块（由 1 个线程发起）")

三、练习#

  1. 实现：改 pipeline 让每轮计算时间不均匀（例如前 6 轮 20 周期、后 6 轮 5 周期），找出仍能完全隐藏 40 周期延迟的最小 S，并解释为什么它比均匀时要大。
  2. 解释：为什么 __pipeline_wait_prior(N) 的语义是"最多还有 N 批没完成"，而不是"等第 N 批完成"？用 S=3 的时序说明它与"提前 2 轮发起拷贝"是同一件事。
  3. 对比/验证：取真实量级 L=400、C=8，用公式 S≈L/C+1 估算最少级数；再假设每级要 T×T 的 A/B 条带（T=64、fp16），算出 shared memory 占用，解释为什么实践中常见 2~4 级而不是 50 级。
  4. 思考：如果 K 只有 2 段（即块内循环只跑 2 轮），双缓冲还能带来收益吗？如果这个 kernel 的计算只占每轮时间的 10%，你更应该去优化什么？
