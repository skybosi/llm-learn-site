吞吐 vs 延迟与 continuous batching#

前两课讲了延迟的两个指标，这一课把它们与吞吐放到天平两端，并引入现代推理引擎最核心的一项调度技术——continuous batching（连续批处理）。正是它，让 vLLM 等引擎能比朴素的静态批处理把吞吐提高数倍，同时控制住延迟。学完本课，你应当能解释"静态批处理浪费在哪"，以及"连续批处理如何用分时复用把 GPU 喂饱"。

一、概念讲解#

1. 吞吐与延迟的跷跷板#

  • 吞吐（throughput）：单位时间内系统产出的 token 数（tokens/s），衡量"GPU 的产能"。
  • 延迟（latency）：单个请求从发出到完成的时间（或 TTFT/TPOT），衡量"单个用户的体验"。

两者天然对立：把一个 GPU 同时喂给更多请求（batch 更大），它每秒能产出的总 token 数会上升（吞吐↑），但每个请求分到的算力/带宽变少，延迟也上升（延迟↑）。理想状态是在不明显牺牲延迟的前提下，把 GPU 的利用率拉满。

2. 静态批处理（static batching）的问题#

早期推理服务用"攒一批、跑一批"的静态批处理：等若干请求到齐，把它们 pad（补齐）到同一长度，一次性 prefill + decode，全部结束后再处理下一批。它有两个致命浪费：

  • 填充浪费：短请求被 pad 到与最长请求一样长，多算了大量无意义 token；
  • 木桶效应：一个 batch 里只要有一个长请求没结束，整批的 GPU 都要陪它等，其他已结束的请求槽位空转。

结果就是 GPU 大量时间在"等"，吞吐远低于理论峰值。

3. continuous batching：让 GPU 一刻不停地跑#

continuous batching（也叫 in-flight batching / dynamic batching / iteration-level scheduling）的核心思想：不再以"整批请求"为单位，而是以"一次迭代（iteration）"为单位调度。

  • 每个迭代，把所有活跃请求各推进一个 decode token（或对刚到的请求做一次 prefill）；
  • 有请求结束了，立刻从等待队列拉一个新请求顶上空位；
  • 新请求来了，可以在任意迭代插入，不必等下一批。

这样 GPU 的每个迭代几乎都是满的，空闲槽位被实时填补，吞吐因此大幅提升——vLLM 论文报告相比传统方法吞吐提升可达 2–4 倍（在相同延迟约束下甚至更高）。

4. 两个关键配套#

continuous batching 能落地，依赖两个配套能力：

  • KV Cache 按需分配与回收：请求动态进出，KV Cache 必须能随时为新请求分配、为结束请求释放（第 2 章会讲 PagedAttention 如何优雅地做这件事）；
  • prefill/decode 混排调度：既要快速响应新请求的 prefill，又不能饿死正在 decode 的老请求，调度器要在两者间平衡（比如对 prefill 分块 chunked prefill，避免一个超长 prompt 独占 GPU）。

二、可运行示例#

下面的 Python 用离散事件模拟，对比"静态批处理"与"连续批处理"在同一批请求下的吞吐差距。

# -*- coding: utf-8 -*-
# 对比 static batching 与 continuous batching 的吞吐
import random

def gen_requests(n):
    """生成 n 个请求，每个有 prompt 长度和生成长度。"""
    return [{"prompt": random.randint(32, 512),
             "gen": random.randint(50, 500)} for _ in range(n)]

def static_batching(requests, batch_size=8, per_token_cost=1.0):
    """静态批处理：每批 pad 到最长，整批串行处理，长请求拖累整批。"""
    total_tokens = 0
    total_time = 0.0
    for i in range(0, len(requests), batch_size):
        batch = requests[i:i+batch_size]
        max_len = max(r["prompt"] + r["gen"] for r in batch)
        # 每个槽位都按 max_len 计算（pad 浪费），GPU 一次算完整批
        total_tokens += sum(r["prompt"] + r["gen"] for r in batch)
        total_time += max_len * per_token_cost   # 串行处理一批
    return total_tokens / total_time

def continuous_batching(requests, per_token_cost=1.0):
    """连续批处理：每个迭代只推进所有活跃请求 1 个 token，空位实时填补。"""
    queue = list(requests)
    active = []          # 活跃请求：[剩余生成 token 数]
    total_tokens = 0
    total_iters = 0
    # 简化：每个迭代为所有活跃请求各算 1 个 token，不区分 prefill/decode 代价
    while queue or active:
        # 每个迭代拉满并发槽位（假设 GPU 上限 32 个活跃请求）
        while queue and len(active) < 32:
            r = queue.pop(0)
            active.append(r["prompt"] + r["gen"])  # 总剩余长度（含 prefill 部分）
        # 本迭代推进 1 步
        if active:
            total_iters += 1
            total_tokens += len(active)
            active = [rem - 1 for rem in active if rem - 1 > 0]
    return total_tokens / (total_iters * per_token_cost)

requests = gen_requests(200)
tp_static = static_batching(requests)
tp_cont = continuous_batching(requests)
print(f"静态批处理吞吐：{tp_static:.1f} tokens/单位时间")
print(f"连续批处理吞吐：{tp_cont:.1f} tokens/单位时间")
print(f"吞吐提升：{tp_cont/tp_static:.2f} 倍")

运行后你会发现，连续批处理的吞吐明显更高——因为它不让 GPU 停下来"等长请求"，空闲槽位被立即填补。真实引擎的差距来源更丰富（消除 padding、内存复用、调度优化），但"不让 GPU 空转"是共同的本质。

三、练习#

  1. 改 batch_size：把静态批处理的 batch_size 从 8 改成 16、4，吞吐怎么变？结合"木桶效应"解释。
  2. 改请求分布：把 gen_requests 里的生成长度改成固定值（如都生成 500），两种方法的吞吐差距是变大还是变小？为什么请求长度越均匀，静态批处理的浪费越小？
  3. 加槽位上限：把连续批处理的槽位上限从 32 改成 8，吞吐怎么变？说明 GPU 容量对连续批处理收益的影响。
  4. 思考：连续批处理本质上是"用延迟换吞吐"还是"在不牺牲延迟下榨吞吐"？结合上一课的 TTFT/TPOT 谈你的理解。
