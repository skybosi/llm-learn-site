冲突、重复与死锁（什么时候多智能体是负优化）#

这一节要解决什么#

上一节选好了拓扑、定好了协议。系统跑起来之后，多智能体会出现三类它特有的病 —— 不是"Agent 不够聪明"导致的，而是"有多个执行者共享一个世界"导致的：

冲突：两个 Agent 改同一个对象，或对同一事实得出不同结论
重复：同一件事被做了两遍（有时是事故，有时是"冗余"设计）
死锁：互相等待成环（或更隐蔽的：活锁、饥饿）

这三类病的共同特征是它们不产生异常。没有报错、没有失败的工具调用，系统只是"卡住了"或"结果不对"。所以它们必须靠结构化的检测机制发现，而不是靠"看日志觉得不对"。

这一节还要回答本章最实际的问题：

什么时候多智能体是负优化？

这个问题有一个好消息：它是可以算的。把总开销拆开：

Cmulti​=Cwork​+Ccomm​+Ccoord​+Crework​+Cfailure​

Cwork​ 是单 Agent 也要付的，其余四项是协作的代价。如果这四项之和超过了"上下文隔离 + 权限隔离"带来的收益，那多智能体就是负优化：任务能跑通，但比单 Agent 更贵、更慢、更不可靠。

负优化⟺协作代价Ccomm​+Ccoord​+Crework​+Cfailure​​​>协作收益Δisolation​+Δpermission​​​

  • 重复工作的三个来源分别怎么检测？"有意冗余"与"意外重复"的区别在哪？
  • 死锁的四个必要条件在 Agent 场景的对应物是什么？检测死锁需要轨迹里有什么字段？
  • 什么是活锁？它和死锁的检测手段为什么不同？
  • "系统卡住了"这个观察为什么不能用于诊断？正确做法缺哪一步？
  • 什么信号出现时，你应该不要上多智能体？替代方案是什么？
  • 为什么"再派一个 Agent 去检查第一个 Agent 的输出"常常不提升质量？

一、冲突：两种类型，两套解法#

1.1 资源冲突（写同一对象）#

定义：两个 Agent 的写集合有交集，且它们可能同时执行。

资源冲突(A,B)⟺W(A)∩W(B)=∅ ∧ time(A)∩time(B)=∅

这与第 5 章第 1 节的"假并行"是同一件事，区别是：那里是计划时的静态检测，这里是运行时的实际冲突。两者都要做 —— 静态的是预防，运行时的是兜底。

两类解法，各有代价：

解法 机制 代价 适用
事前串行化 给两个节点加控制依赖（第 1 节） 放弃并行收益 冲突频率高
条件写（CAS/版本号） 后写者失败后重读再决策（第 1 节 2.1） 重试成本 + 可能活锁 冲突频率低、写者少
分区（避免共享） 让每个 Agent 写自己的对象，最后合并 合并逻辑 + 可能语义冲突 冲突对象可切分
租约（lease） 谁拿到租约谁能写，租约超时释放 单点 + 超时处理 长事务

"分区 + 合并"值得单独说，因为它是把资源冲突转化为信念冲突的手段：两个 Agent 各写自己的文件（无冲突），但合并时可能发现"两人对同一个字段给了不同值" —— 冲突没有消失，只是从"写冲突"变成了"合并时的语义冲突"。转形不是消除，所以要问：转形后的冲突是否更容易解决？答案通常是是 —— 因为合并是集中在一点、可以显式裁决的，而并发写冲突是分散的、静默的。

1.2 信念冲突（对同一事实结论不同）#

定义：两个 Agent 对同一事实给出不同结论，而且各自都有理由。这是多智能体特有的、也最容易被忽视的一类。

信念冲突⟺conclusion(A,f)=conclusion(B,f) ∧ 两者都有证据

关键认识：加锁解决不了信念冲突。 锁保护的是"写的原子性"，而信念冲突是两个 Agent 基于不同的信息或不同的先验得出了不同的结论。它们的写操作可能完全不冲突（写的是不同 key），但结论矛盾。

三类来源：

来源 机制 检测
信息不同 A 读到了 B 没读到的文档 比对两者的 inputs 集合
版本不同 A 基于产物 v1，B 基于 v2 比对 depends_on_version（第 1 节协议字段）
先验不同 同一信息、不同推理 无法从结构检测，只能靠裁决规则

正确处置不是"合并成一个平均值"（那会得到一个没人支持过的结论），而是把冲突变成显式的待裁决记录：

冲突记录：
  · fact: 争议的事实（例如"该公司上季度营收"）
  · claims: [{value, agent, evidence_refs, depends_on_version, confidence}]
  · 采纳的裁决规则: 证据优先 / 来源可信度 / 时间新近 / 指定权威
  · 裁决结果与理由

四条裁决规则及其适用：

裁决=⎩⎨⎧​证据优先来源可信度时间新近指定权威/人工裁决​一方能给出可核验的引用（最优先）一方来源是权威系统（对账、主数据）两者都是观测值，取更新的（注意：这要求两条都记录时间）前三条都不适用，或冲突代价很高（付款金额、合规判断）​

裁决=⎩⎨⎧​证据优先来源可信度时间新近指定权威/人工裁决​一方能给出可核验的引用（最优先）一方来源是权威系统（对账、主数据）两者都是观测值，取更新的（注意：这要求两条都记录时间）前三条都不适用，或冲突代价很高（付款金额、合规判断）​

一个必须避免的默认行为：静默覆盖。"后写的赢"在系统里看起来是"最后一致性"，但它把"两个证据矛盾的结论"变成了"一个没人审查过的结论"。这在第 7 章的失效归因里会表现为"线索断了" —— 因为矛盾的证据被覆盖掉了。

1.3 冲突矩阵与它的用途#

把"谁持有什么、谁要什么"写成矩阵，可以把上面两类冲突统一检测：

# 冲突矩阵：行 = 对象/事实，列 = Agent，单元格 = 读/写/主张值
#   资源冲突：同一行有两个 W
#   信念冲突：同一行的两个主张值不同

它的第三个用途是容量分析：如果某个对象被 m 个 Agent 同时写，那就是一个热点，应当考虑分区或指定唯一写者。

二、重复：三个来源与两种性质#

2.1 三个来源#

来源 机制 检测手段
职责重叠 角色定义不清，两个 Agent 都认为自己该产出 x（第 1 节 1.1） 产出物指纹：两处产出了同名/同内容的产物
通信重发 消息丢失后重发，或超时重派（第 1 节 2.2） 幂等键去重表命中（第 1 节 2.2 的实现）
分叉重放 崩溃恢复后从检查点重跑，重跑了已完成的步骤（第 4 章） journal 的 COMMIT 标记（第 4 章）

检测手段的核心是"意图指纹"：在执行任何有成本或有副作用的动作前，先检查"这个意图是否已经/正在被执行"：

意图指纹=hash(task_id, subgoal, normalized_args)

三个字段各有作用：task_id 区分任务、subgoal 区分目标、normalized_args 区分同目标下的不同调用（归一化很关键：{"a":1,"b":2} 与 {"b":2,"a":1} 必须得到同一个指纹）。这与第 3 章的幂等键同构，区别是粒度更粗：幂等键防"同一个动作被执行两次"，意图指纹防"同一件事被两个 Agent 各做一遍"。

2.2 有意冗余 vs 意外重复#

冗余可以是有意的（为了可靠性或交叉验证），但必须满足一个条件：存在判别规则。

冗余有价值⟺有独立的判别规则（或投票机制）能识别"哪个结果对"

否则冗余只是"把成本乘以 n，然后把两个矛盾的结论都留在系统里"。这就是为什么 2.4 节要专门讨论"多数投票在 Agent 场景常常失效"。

2.3 重复工作的成本#

重复成本=(重复次数−1)×(cwork​+cside-effect​)

其中 cside-effect​ 在副作用不可逆时可以非常大（重复付款）。重复的检测应该尽量前移：在动作执行前检查意图指纹（便宜、无副作用），而不是在执行后比对产物（贵、副作用已发生）。这是"检测点位置"的通用原则：

检测点越靠前，代价越小，但误报率可能越高（信息更少）

三、死锁、活锁与饥饿#

3.1 死锁：四个必要条件在 Agent 场景的对应物#

操作系统里的死锁四条件，可以逐一映射：

条件 操作系统含义 Agent 场景的对应物
互斥 资源一次只能被一个进程占用 某工具/文件/外部对象独占（例如"只能有一个 Agent 写报表"）
持有并等待 占有资源的同时等待新资源 Agent 已产出 draft，正在等 review（而 review 的 Agent 在等 draft 的最终版）
不可剥夺 资源不能被强行夺走 中间产物不能从另一个 Agent 手里"抢"过来 —— 它已经基于该产物做了后续工作
循环等待 存在等待环 等待图里有环：A 等 B 的产物，B 等 C 的，C 等 A 的

打破死锁的四个方向（对应四个条件，任意打破一个即可）：

预防={资源有序分配 (破环), 一次性申请 (破持有并等待), 租约超时 (破不可剥夺), 避免独占 (破互斥)}

最重要的工程结论：只要协议里记录了 waiting_for（在等谁的哪个产物），等待环就可以在运行时被检测。检测算法是标准的：把 waiting_for 边构成有向图，找环（DFS 或 Tarjan 强连通分量）。

可检测死锁⟺∀ 等待中的 Agent, ∃ 字段记录它等谁

这就是第 1 节强调 waiting_for 必须由框架自动填充的原因：它不是一个可选的调试字段，而是一整类故障能否被诊断的前提。缺了它，"系统卡住"只能靠观察猜，而观察无法区分"真死锁"与"某个 Agent 在做一个很慢的调用"。

检测到环之后的处置（不能只是报警）：挑一个"牺牲者"回退，选择的依据是最小代价：

牺牲者=argv∈环min​(已投入成本(v)+回退代价(v)+副作用风险(v))

注意第三项：如果环里的某个 Agent 已经做了不可逆操作，它就不该是牺牲者 —— 回退它意味着重复副作用。这是第 5 章第 3 节的回退粒度理论在协作场景的应用。

3.2 假死锁：租约超时打破它#

真实的运行时里，很多"死锁"其实不是环，而是某个 Agent 死了或卡住了，而别人永远在等它。区分方法：

真死锁⟺环上的每个 Agent 都活着且都在等待

假死锁（挂起）⟺环上至少一个 Agent 已死/已超时⟹等待边应失效（租约过期）

所以等待边必须带租约（lease）：

等待边有效⟺now<lease_deadline,过期⇒该边从等待图里删除

删掉过期边之后，环可能自然消失（因为环被打破），剩下的只是一个"需要重派任务"的问题。这就是"假死锁"的正确处置：不是解环，而是让等待失效。

3.3 活锁与震荡#

活锁：没有环，但系统永不收敛。典型形态：

  • 两个 Agent 反复协商（"你先改"、"不，你先改"），每轮都推进一点但永远不结束。
  • 编排者反复重派同一个任务（worker 每次都失败在同一个地方）。
  • 两个 Agent 互相让步（都改成对方要的样子，然后又发现不一致）。

检测手段与死锁不同（这是本节的一个关键区分）：

死锁 活锁
结构特征 等待图有环 无环，但状态重复
检测依据 waiting_for 图 状态指纹重复 + 无进展
处置 破环（牺牲者回退 / 租约） 回合上限 + 单调进展要求

活锁⟺∃ t1​<t2​: fingerprint(St1​​)=fingerprint(St2​​) ∧ 进展(t1​,t2​)=0

抑制手段（按有效性）：

  1. 单调进展要求：每轮协商必须使某个可度量指标严格改善（已确认事实集增大、分歧项减少）。没有进展的轮次直接终止。
  2. 回合上限：协商轮数 ≤k（k 通常 2~3）。超过就升级给人或按预设规则裁决。
  3. 随机化退避：打破对称性 —— 两个 Agent 完全对称时，让其中一个以随机延迟先动。
  4. 状态指纹去重：与第 5 章第 3 节的"重规划震荡抑制"是同一套机制（rejected_paths）。

3.4 饥饿与优先级反转#

饥饿：某个 Agent 永远拿不到配额（编排者总把预算给别人）。优先级反转：低优先级任务占住了高优先级任务需要的资源。

处置是"配额 + 租约"：给每个 Agent 一个预算配额（第 5 章第 4 节的多维预算），并给独占资源加租约超时。这两者一起保证了"没有人能无限期占着资源":

公平性⟺每轮至少有一个等待者的配额被满足（或它的请求被明确拒绝）

"明确拒绝"比"无限等待"好：一个被拒绝的请求可以让 Agent 换路径（第 5 章第 3 节的可替换失败），而一个无限等待只是把问题留给超时。

四、什么时候多智能体是负优化#

4.1 成本分解与可测指标#

Cmulti​=Cwork​+Ccomm​+Ccoord​+Crework​+Cfailure​

每一项都有代理指标（这些指标在轨迹里都能算出来，第 7 章会用）：

项 内容 代理指标
Cwork​ 真正干活 工具调用数、有效 token
Ccomm​ 消息与黑板读写 通信 token / 总 token（通信占比）
Ccoord​ 协调决策（编排者思考、协商轮次） 协调轮次、编排者的 token
Crework​ 重复工作与返工 意图指纹重复数、作废产物数
Cfailure​ 协作引入的新失效（死锁、冲突、丢失） 死锁/活锁事件数、超时重派数、冲突裁决数

通信占比=Cmulti​Ccomm​​,返工率=总意图数重复执行的意图数​

4.2 负优化判据表#

# 信号 判据 替代方案
1 单上下文装得下 全部信息占可用预算 <50% 单 Agent + 工具（这是最强的信号：隔离收益为零）
2 写集合交集大 可并行节点对中写同一对象的比例 >50% 串行化，或分区 + 合并
3 需要全局一致的世界观 存在必须同时看到全部信息才能满足的性质（统一术语、总预算、语气） 单 Agent；或用编排者持有全局约束
4 串行依赖度高 串联度 s>0.8（第 5 章第 1 节） 单 Agent 单循环
5 通信占比过高 Ccomm​/Cmulti​>40% 改拓扑（全连接 → 星形）或减 Agent 数
6 协调成本超过单元成本 编排者 token > 执行者 token 之和 去掉编排者，改为流水线
7 返工率过高 重复执行的意图 >20% 加意图指纹去重 + 明确角色产出边界
8 任务很短 步骤数 ≤3 单 Agent：协调的固定开销占比过高

第 1 条与第 5 条是最常用的判据，因为它们的输入最容易测（上下文预算估算、通信 token 计数）。

4.3 为什么"多数投票"在 Agent 场景常常失效#

这是"冗余"最常见的误用。设 n 个 Agent 对同一问题的答案是"正确/错误"，正确率都是 p。独立假设下多数投票的错误率为：

Pwrongvote​=k>n/2∑​(kn​)(1−p)kpn−k

p=0.7,n=3 时约 0.216（低于单体的 0.3），看起来不错。但 Agent 场景破坏独立性假设：

破坏机制 后果
错误相关 同一个模型、同一个上下文、同一个先验 → 错的地方一样，投票等于做三次同一个错误
成本乘 n 收益是"错误率从 0.3 到 0.216"，成本是 3 倍
流畅性偏差 错误答案往往更"流畅自信"，投票可能系统性地偏向它
同质化 如果另一个 Agent 能看到第一个的答案，它会趋同（锚定，第 4 章的位置偏差）

投票的价值⟺错误（近似）独立⟹必须让成员在信息、先验或模型上真正异源

推论：如果要用冗余，要同时满足"异源"与"有判别规则"。只满足一个的冗余是浪费。第 5 章第 2 节的"自评不是验证"是同一个结论在单 Agent 上的形态 —— 独立性是全部价值所在。

    lease_deadline: float | None = None
    idem_key: str = ""
    version: int = 0


# ==================== (1) 等待图与死锁检测 ====================
class WaitForGraph:
    """从事件流重建等待图。

    ★ 设计决策：图是**重建**出来的，不是维护出来的。
      因为只有从轨迹重建才能保证"检测依据 = 实际发生的事"，而不是某个 Agent 的自我报告。
      代价是必须遍历事件流 —— 这与第 7 章"轨迹级评测"的前提一致。
    """

    def __init__(self, events: list[Event], now: float) -> None:
        self.edges: dict[str, set[str]] = {}
        self.now = now
        self.expired_edges: list[tuple[str, str]] = []
        for e in events:
            if e.kind != "wait" or not e.waiting_for:
                continue
            # ★ 租约：过期的等待边视为失效（假死锁的正确处置，3.2）
            if e.lease_deadline is not None and self.now >= e.lease_deadline:
                self.expired_edges.append((e.agent, e.waiting_for))
                continue
            self.edges.setdefault(e.agent, set()).add(e.waiting_for)
            self.edges.setdefault(e.waiting_for, set())

    def find_cycle(self) -> list[str] | None:
        state: dict[str, int] = {}
        stack: list[str] = []

        def dfs(u: str) -> list[str] | None:
            state[u] = 1
            stack.append(u)
            for v in sorted(self.edges.get(u, ())):
                if state.get(v, 0) == 1:
                    return stack[stack.index(v):] + [v]
                if state.get(v, 0) == 0:
                    got = dfs(v)
                    if got:
                        return got
            stack.pop()
            state[u] = 2
            return None

        for n in sorted(self.edges):
            if state.get(n, 0) == 0:
                got = dfs(n)
                if got:
                    return got
        return None

    def strongly_connected(self) -> list[list[str]]:
        """Tarjan：找出所有强连通分量（可能有多个不相交的等待环）。"""
        index: dict[str, int] = {}
        low: dict[str, int] = {}
        on: dict[str, bool] = {}
        stack: list[str] = []
        out: list[list[str]] = []
        counter = [0]

        def strong(u: str) -> None:
            index[u] = low[u] = counter[0]
            counter[0] += 1
            stack.append(u)
            on[u] = True
            for v in self.edges.get(u, ()):        # ★ 修：用 self.edges
                if v not in index:
                    strong(v)
                    low[u] = min(low[u], low[v])
                elif on.get(v):
                    low[u] = min(low[u], index[v])
            if low[u] == index[u]:
                comp = []
                while True:
                    w = stack.pop()
                    on[w] = False
                    comp.append(w)
                    if w == u:
                        break
                if len(comp) > 1:
                    out.append(sorted(comp))
        for n in sorted(self.edges):
            if n not in index:
                strong(n)
        return out

    def pick_victim(self, cycle: list[str],
                    invested: dict[str, float],
                    rollback_cost: dict[str, float],
                    has_irreversible: dict[str, bool]) -> dict:
        """挑牺牲者：最小 (已投入 + 回退代价)，但有不可逆副作用的**排除**。

        ★ 设计决策：不可逆者一票否决，而不是加权。
          因为回退它意味着重复副作用 —— 那是不可接受的代价，不是"稍微贵一点"。
        """
        scored = []
        for a in cycle:
            if has_irreversible.get(a):
                scored.append((a, float("inf"), "★ 已被排除：有不可逆副作用，回退会重复执行"))
                continue
            cost = invested.get(a, 0.0) + rollback_cost.get(a, 0.0)
            scored.append((a, cost, "可回退"))
        scored.sort(key=lambda x: x[1])
        return {"牺牲者": scored[0][0], "评分": scored}


# ==================== (2) 冲突检测 ====================
@dataclass
class AgentProfile:
    name: str
    writes: set[str] = field(default_factory=set)
    reads: set[str] = field(default_factory=set)
    claims: dict[str, object] = field(default_factory=dict)   # 对事实的主张


def detect_write_conflicts(agents: list[AgentProfile]) -> list[dict]:
    """资源冲突：写集合交集非空。"""
    out = []
    for i, a in enumerate(agents):
        for b in agents[i + 1:]:
            inter = a.writes & b.writes
            if inter:
                out.append({"类型": "资源冲突", "对": [a.name, b.name],
                            "对象": sorted(inter),
                            "处置": "事前：加控制依赖或分区；运行时：条件写（CAS）"})
    return out


def detect_belief_conflicts(agents: list[AgentProfile]) -> list[dict]:
    """信念冲突：对同一事实的不同主张。

    ★ 设计决策：不自动"取最新"或"取平均"，而是产出**待裁决记录**。
      静默覆盖会把"两个证据矛盾的结论"变成"一个没人审查过的结论"，
      并在第 7 章的归因里表现为"线索断了"。
    """
    out = []
    facts: dict[str, list[tuple[str, object]]] = {}
    for a in agents:
        for f, v in a.claims.items():
            facts.setdefault(f, []).append((a.name, v))
    for f, claims in facts.items():
        values = {repr(v) for _, v in claims}
        if len(values) > 1:
            out.append({"类型": "信念冲突", "事实": f,
                        "主张": [{"agent": n, "value": v} for n, v in claims],
                        "建议裁决": "证据优先 → 来源可信度 → 时间新近 → 人工裁决",
                        "禁止": "静默取最后写入（会销毁矛盾证据）"})
    return out


# ==================== (3) 重复工作检测 ====================
def intent_fingerprint(task_id: str, subgoal: str, args: dict) -> str:
    """★ 设计决策：args 必须**归一化**（排序键 + 去空白）。

    否则 {"a":1,"b":2} 与 {"b":2,"a":1} 会得到不同指纹，重复检测完全失效。
    """
    import json
    blob = json.dumps(args, sort_keys=True, ensure_ascii=False, default=str)
    return f"{task_id}|{subgoal}|{hash(blob) & 0xFFFFFFFF:08x}"


def detect_duplicate_work(events: list[Event]) -> list[dict]:
    """三个来源统一由"意图指纹被执行两次"呈现（2.1）。"""
    seen: dict[str, list[tuple[float, str]]] = {}
    for e in events:
        if e.kind == "done" and e.idem_key:
            seen.setdefault(e.idem_key, []).append((e.t, e.agent))
    return [{"指纹": k, "执行者": [a for _, a in v], "次数": len(v),
             "时间": [t for t, _ in v],
             "处置": "若为职责重叠 → 明确产出边界；若为重发 → 幂等键去重；若为有意冗余 → 必须有判别规则"}
            for k, v in seen.items() if len(v) > 1]


# ==================== (4) 活锁检测 ====================
def detect_livelock(state_history: list[tuple[float, frozenset, float]],
                    window: int = 4) -> dict:
    """★ 设计决策：活锁的判据是"状态指纹重复且进展为零"，不是"等待成环"。

    死锁与活锁必须用不同的检测手段 —— 这是本节最容易被混为一谈的一点。
    """
    if len(state_history) < window:
        return {"活锁": False, "原因": "样本不足"}
    recent = state_history[-window:]
    fps = [s for _, s, _ in recent]
    progress = [p for _, _, p in recent]
    repeated = len(set(fps)) < len(fps)
    no_progress = max(progress) - min(progress) <= 0
    return {"活锁": repeated and no_progress,
            "状态重复": repeated, "进展变化": round(max(progress) - min(progress), 4),
            "轮次数": len(recent),
            "处置": "回合上限 + 单调进展要求 + 随机化退避（不是解环）"}


# ==================== (5) 负优化判据 ====================
@dataclass
class MultiAgentLedger:
    work_tokens: int = 0
    comm_tokens: int = 0
    coord_tokens: int = 0
    rework_intents: int = 0
    total_intents: int = 0
    failure_events: int = 0
    context_fit: float = 1.0        # 单上下文可容纳性（1.0 = 刚好装得下）
    write_overlap: float = 0.0
    sequentiality: float = 0.0
    global_property: bool = False
    steps: int = 10


def negative_optimization_verdict(L: MultiAgentLedger) -> dict:
    """4.2 的判据表实现。返回结论 + 命中的信号清单。"""
    total = L.work_tokens + L.comm_tokens + L.coord_tokens
    comm_ratio = L.comm_tokens / max(1, total)
    rework_rate = L.rework_intents / max(1, L.total_intents)
    coord_ratio = L.coord_tokens / max(1, L.work_tokens)
    hits: list[str] = []
    if L.context_fit <= 0.5:
        hits.append(f"① 单上下文装得下（u={L.context_fit}）→ 隔离收益为零，用单 Agent + 工具")
    if L.write_overlap > 0.5:
        hits.append(f"② 写集合交集大（{L.write_overlap:.2f}）→ 串行化或分区 + 合并")
    if L.global_property:
        hits.append("③ 需要全局一致的世界观 → 单 Agent，或让编排者持有全局约束")
    if L.sequentiality > 0.8:
        hits.append(f"④ 串行依赖度高（s={L.sequentiality:.2f}）→ 单 Agent 单循环")
    if comm_ratio > 0.40:
        hits.append(f"⑤ 通信占比过高（{comm_ratio:.0%}）→ 改拓扑或减 Agent 数")
    if coord_ratio > 1.0:
        hits.append(f"⑥ 协调成本超过单元成本（编排者/执行者={coord_ratio:.2f}）→ 去掉编排者")
    if rework_rate > 0.20:
        hits.append(f"⑦ 返工率过高（{rework_rate:.0%}）→ 加意图指纹去重 + 明确产出边界")
    if L.steps <= 3:
        hits.append(f"⑧ 任务很短（{L.steps} 步）→ 协调固定开销占比过高，单 Agent")
    return {"结论": "负优化：不该上多智能体" if hits else "多智能体可能有正收益（仍需实测）",
            "命中信号": hits,
            "指标": {"通信占比": round(comm_ratio, 3), "协调比": round(coord_ratio, 3),
                     "返工率": round(rework_rate, 3), "总 token": total}}

八处关键设计决策：

  1. WaitForGraph 从事件流重建等待图，而不是让 Agent 自我报告"我在等谁"。理由是检测依据必须等于实际发生的事：自我报告会漏、会说谎、会漏报"我忘了说自己还在等"。
  2. 等待边带 lease_deadline，过期的边在构造图时就被剔除。这就是 3.2 的"假死锁"处置：真死锁需要解环，假死锁只需要让等待失效。演示里同一条事件流在 now=2.0 时成环、在 now=5.0 时无环 —— 区分二者的唯一信息就是租约。
  3. pick_victim 对"有不可逆副作用"的 Agent 一票否决（代价记为 inf）而不是加权惩罚。回退一个已做不可逆操作的 Agent 意味着重复副作用，那是不可接受的代价，不是"稍微贵一点"，所以不该让它在数值上仅略微不利。
  4. detect_belief_conflicts 刻意不自动取最新或取平均，而是产出待裁决记录。这是对"静默覆盖"的正面拒绝：覆盖会把"两个证据矛盾的结论"变成一个没人审查过的结论，并在第 7 章的归因里表现为线索断裂。
  5. intent_fingerprint 用 sort_keys=True 归一化参数。少了这一步，{"a":1,"b":2} 与 {"b":2,"a":1} 会得到不同指纹，重复检测完全失效 —— 这是一个"看起来能跑但完全不工作"的典型 bug。
  6. detect_livelock 的判据是"状态指纹重复 且 进展为零"，与 WaitForGraph 的环检测完全独立。这不是实现冗余，而是因为死锁与活锁是两种不同结构：有环 vs 无环但状态回环。用环检测去找活锁会永远找不到。
  7. negative_optimization_verdict 把 4.2 的八条判据做成命中清单而不是单一分数。理由是不同信号对应不同的替代方案（信号 ① → 单 Agent；信号 ⑤ → 改拓扑），一个标量分数会丢掉"该怎么做"的信息。
  8. 演示最后一段把 4.3 的多数投票公式算出来（p=0.7：单体 0.300、n=3 0.216、n=5 0.163），再用文字点破"独立性被破坏后这个收益不存在"。把理想数字算出来再拆掉它的前提，比只说"投票不可靠"有说服力得多。

  5. 活锁的判据：下面三组状态历史，哪一组是活锁？说明你的判据，并指出"进展"这个量应该怎么定义才有意义。 （a）{draft:v1}→{draft:v2}→{draft:v3}，进展 0 → 0.1 → 0.25； （b）{draft:v1}→{draft:v2}→{draft:v1}→{draft:v2}，进展 0.1 → 0.1 → 0.1 → 0.1； （c）{draft:v1}→{draft:v1}→{draft:v1}，进展 0 → 0 → 0。

小结#

  • 冲突有两类，解法不同：资源冲突（写集合交集，可用串行化 / CAS / 分区 / 租约解决）与信念冲突（对同一事实不同结论，加锁无效，必须显式裁决）。裁决规则优先级：证据优先 → 来源可信度 → 时间新近 → 人工裁决。必须避免的默认行为是静默覆盖 —— 它把"矛盾的证据"变成"没人审查过的结论"。
  • "分区 + 合并"是把资源冲突转形为信念冲突。转形不是消除，但通常更好 —— 因为合并是集中一点、可显式裁决的，而并发写冲突是分散、静默的。
  • 重复工作有三个来源：职责重叠（检测：产出物指纹）、通信重发（检测：幂等键去重表）、分叉重放（检测：journal 的 COMMIT）。统一的检测手段是意图指纹 hash(task_id,subgoal,normalized_args)，且参数必须归一化（排序键），否则指纹会漏。检测点应尽量前移（执行前查比执行后比便宜，且副作用尚未发生）。
  • 冗余只有在"成员异源 + 有独立判别规则"时才有价值。多数投票的理想数字（p=0.7,n=3⇒0.216）建立在独立性假设上，而 Agent 场景系统性破坏它：同模型、同上下文、同先验 → 错的地方一样。这与第 5 章"自评不是验证"是同一个结论。
  • 死锁四条件在 Agent 场景都有对应物（互斥→独占对象、持有并等待→产物依赖、不可剥夺→中间产物不能抢、循环等待→等待环）。关键工程结论：只要协议里记录了 waiting_for，环就能在运行时被检测（DFS / Tarjan）。检测到环之后必须处置：挑代价最小的牺牲者回退，而有不可逆副作用的 Agent 一票否决（回退它 = 重复副作用）。
  • 假死锁（某个 Agent 已死）的正确处置不是解环，而是让等待边失效 —— 所以等待边必须带租约，过期即从等待图删除。
  • 活锁与死锁的检测手段不同：死锁看等待环，活锁看状态指纹重复 + 进展为零。活锁的抑制是回合上限、单调进展要求、随机化退避。"明确拒绝"比"无限等待"好 —— 被拒绝的请求能让 Agent 换路径（第 5 章第 3 节的可替换失败）。
  • 负优化是可算的：Cmulti​=Cwork​+Ccomm​+Ccoord​+Crework​+Cfailure​。八条判据里最常用的三条：单上下文装得下（隔离收益为零）、写集合交集大、通信占比 > 40%。区分信号而不是算一个总分，因为不同信号对应不同替代方案（单 Agent / 串行化 / 改拓扑 / 明确角色边界）。
