性能工程方法论：基线 → profile → 优化 → 回归；何时不值得优化#

"我把这个 kernel 优化了三倍"——若没有基线、profile 证据、可复现的测量协议，这句话在工程上等于零：kernel 快 3 倍、端到端可能只快 4%；也可能这次"快"只是噪声。这一课建立把性能主张变成可判定结论的流程，以及何时不该继续优化。

一、概念讲解#

1. 闭环的四步，以及每步的产出物#

步骤 做什么 产出物（没有它这一步就没做完）
① 基线 在固定的输入、dtype、形状、计次与预热条件下测当前实现 基线数字 + 它的波动范围（标准差/分位数）
② profile 先 nsys 看端到端时间线，再 ncu 看热点 kernel 内部 时间分解表：kernel / 拷贝 / 启动 / 同步 / 框架各占多少
③ 优化 只针对占比最大且可改的那一项动手 改动 + 预期收益（用第一课的账本预估上限）
④ 回归 重新测量并做显著性判定；同时跑正确性回归 "变化 X% ± Y%，判定为真/无法判定" + 正确性结论

第 ① 步里最容易被跳过的是"波动范围"。不知道噪声，就没法判断任何差异是不是真的——这正是第 4 步的判据基础。

2. 测量协议：预热、重复、配对、看分布#

四条纪律，缺一条结论就不可靠：

  1. 预热（warmup）：首次运行包含 context 初始化、显存分配、PTX JIT、库惰性加载，必须排除。
  2. 重复（repeat）+ 看分布：报中位数而不是均值。长尾（调度、降频）会把均值抬高，中位数不会被单个坏样本带跑。
  3. 配对（paired）：A/B 交替测（A、B、A、B……），用同一 run 的差值比较；同一时刻的机器状态对两者影响相同，公共噪声相减时被抵消。
  4. 显著性判定：用配对差值的 t 统计量（t = 差值中位 / (差值标准差 / √n)）对照临界值，并报告胜场数（12 次里 B 赢几次）。

3. 用 nsys 拆时间：为什么"只优化 kernel"常常没用#

先看一个具体的账本（代码里会真实打印）：

环节 耗时 占端到端
kernel 执行 100 µs 12.5%
kernel 启动开销 5 µs 0.6%
H2D 拷贝（主机→设备） 300 µs 37.5%
D2H 拷贝（设备→主机） 300 µs 37.5%
Python/框架调度 40 µs 5.0%
同步与事件 55 µs 6.9%
合计 800 µs 100%

Amdahl 定律给出残酷结论：把 100 µs 的 kernel 优化到 0，端到端最多从 800 降到 700 µs，上限 12.5%；而把两次拷贝合并或让计算留在设备上，收益大得多。所以"先 profile 再优化"不是流程洁癖，而是收益排序：不拆时间线，你不知道自己在优化 12.5% 还是 87.5% 的那一段。

4. 显著性：把"看起来变快"变成"可判定"#

配对测量的判定流程（本课代码可跑）：

  1. 算每对样本的差值 d_i = t_baseline,i − t_candidate,i（正数表示新版更快）。
  2. 取 d 的中位数为收益估计、标准差为噪声估计。
  3. t = median(d) / (stdev(d) / √n)；n = 12 时双侧 95% 的临界值约 2.2（查表值）。
  4. 附带胜场数以免误读：12/12 与 7/12 含义完全不同。

代码给出两组真实打印：12% 提升 → t = 8.71，显著；2% 提升 → t = 1.60，落在噪声地板内。后者才是工程中最常见的情形。

5. 什么时候不该优化#

这一条比"怎么优化"更省时间。出现下列任一情况就该停手：

  • 改动部分占端到端比例太小：kernel 占 5%，优化它 2 倍 → 端到端 2.5%，小于噪声地板。
  • 收益小于噪声地板：本机 RSD 约 2.9%（代码真实测得），判定 2% 差异需要极多次重复。
  • 瓶颈不可改：数据必须往返主机、必须保持 fp32、受上游接口限制。
  • 已接近账本上限：实测带宽已达器件可达带宽九成以上，继续调只在噪声里打转。
  • 维护成本不划算：手写 kernel 有正确性、可移植性成本；能用 cuBLAS/CUTLASS 覆盖时，"用库"通常就是最优解（第 7 章）。
  • 该换的是算法不是 kernel：O(n²) 换 O(n log n)、减少搬运、换 dtype，收益常大于任何微调。

6. 常见坑#

  • 一次测量一个数字：没有分布就没有判据。
  • 拿带长尾的样本比均值：一个 9.8 ms 的坏样本能把均值从 4.02 抬到 4.49，中位数几乎不动。
  • 不配对、顺序测：先测 A 再测 B，把"机器变热/变慢"的漂移记成 A 的劣势。
  • 忘了正确性回归：性能改动常引入数值差异；快而错等于没做。
  • 只在一种形状/dtype 上验证：真实输入分布会变，收益可能在别的形状下倒退。

二、可运行代码示例#

下面这段纯标准库代码把第 2～4 节变成可运行产物：同一份测量数据在"配对 + 中位数 + t 判据"下得出两种结论（显著 / 无法判定），并打印噪声地板与成本拆解。它不需要 GPU 与 numpy——方法论与硬件无关。

# ---- 性能工程闭环：把「看起来变快了」变成「可判定的结论」----
import re, statistics as st

JIT_A = [0.10, -0.12, 0.18, -0.05, 0.08, -0.15, 0.14, -0.09, 0.06, 0.02, -0.11, 0.13]
JIT_B = [0.13, -0.17, 0.09, 0.16, -0.08, 0.11, -0.14, 0.05, 0.19, -0.06, 0.07, -0.21]
T95 = 2.2      # df=11 时双侧 95% 的 t 临界值（查表值）

def build_log(gain):
    """模拟 12 次配对测量：同一 run 下 baseline 与 candidate 各测一次（ms）"""
    lines = []
    for i in range(12):
        lines.append(f'run={i:02d} variant=baseline  ms={4.00 + JIT_A[i]:.2f}')
        lines.append(f'run={i:02d} variant=candidate ms={4.00 + JIT_B[i] - gain:.2f}')
    return '\n'.join(lines)

def parse(log):
    out = {}
    for line in log.strip().splitlines():
        m = re.match(r'run=(\d+)\s+variant=(\w+)\s+ms=([\d.]+)', line)
        if m:
            out.setdefault(m.group(2), {})[int(m.group(1))] = float(m.group(3))
    return out

def report(tag, log):
    d = parse(log)
    keys = sorted(set(d['baseline']) & set(d['candidate']))
    a = [d['baseline'][k] for k in keys]
    b = [d['candidate'][k] for k in keys]
    diff = [x - y for x, y in zip(a, b)]      # 配对：同一 run 相减，公共噪声被抵消
    med_a, med_b, med_diff = st.median(a), st.median(b), st.median(diff)
    sd, n = st.stdev(diff), len(diff)
    t = med_diff / (sd / n ** 0.5)
    wins = sum(1 for v in diff if v > 0)
    print(f'--- {tag} ---')
    print(f'  baseline 中位={med_a:.3f} ms   candidate 中位={med_b:.3f} ms')
    print(f'  配对差值：中位={med_diff:+.3f} ms（{med_diff/med_a*100:+.1f}%）  '
          f'标准差={sd:.3f} ms  胜场 candidate {wins}/{n}')
    print(f'  配对 t 统计量={t:.2f}（df={n-1}，双侧 95% 临界值 {T95}）'
          f'  →  {"显著" if t > T95 else "落在噪声地板内，不能下结论"}\n')

print('== 1. 配对测量：把「两次跑分」变成一次可判定的比较 ==')
report('12% 提升', build_log(0.48))
report('2% 提升（低于噪声地板）', build_log(0.08))

print('== 2. 噪声地板：同一段代码重复测 12 次，波动有多大 ==')
base = [4.00 + j for j in JIT_A]
rsd = st.stdev(base) / st.median(base) * 100
outlier = base[:8] + [9.80] + base[9:]
print(f'  12 次样本：中位={st.median(base):.3f} ms  标准差={st.stdev(base):.3f} ms  相对波动 RSD={rsd:.1f}%')
print(f'  混入一个 9.80 ms 长尾（调度抖动）：均值 {st.mean(base):.3f} → {st.mean(outlier):.3f} 被抬高，'
      f'中位 {st.median(base):.3f} → {st.median(outlier):.3f} 基本不动')
print(f'  可检出的最小加速比 ≈ {T95} × RSD / sqrt(n) ≈ {T95 * rsd / len(base) ** 0.5:.1f}%')

print()
print('== 3. 成本拆解：kernel 只有 100 µs，为什么端到端是 800 µs ==')
parts = [('kernel 执行', 100), ('kernel 启动开销', 5), ('H2D 拷贝', 300),
         ('D2H 拷贝', 300), ('Python/框架调度', 40), ('同步与事件', 55)]
total = sum(v for _, v in parts)
for name, us in parts:
    print(f'  {name:<16}{us:>5} µs {us/total*100:>5.1f}%  ' + '#' * max(1, round(us / 20)))
print(f'  合计 {total} µs；只优化 kernel（100 µs），端到端天花板是 {100/total*100:.0f}%')

真实运行输出：

  配对 t 统计量=8.71（df=11，双侧 95% 临界值 2.2）  →  显著

  配对差值：中位=+0.090 ms（+2.2%）  标准差=0.195 ms  胜场 candidate 7/12
  配对 t 统计量=1.60（df=11，双侧 95% 临界值 2.2）  →  落在噪声地板内，不能下结论

== 3. 成本拆解：kernel 只有 100 µs，为什么端到端是 800 µs ==
  kernel 执行         100 µs  12.5%  #####
  kernel 启动开销         5 µs   0.6%  #
  H2D 拷贝            300 µs  37.5%  ###############
  D2H 拷贝            300 µs  37.5%  ###############
  Python/框架调度        40 µs   5.0%  ##
  同步与事件              55 µs   6.9%  ###
  合计 800 µs；只优化 kernel（100 µs），端到端天花板是 12%

两个必须读出来的结论：

  1. 同样"看起来快了"，一个显著、一个不显著：12% 提升的 t 是 8.71，2% 提升只有 1.60——判据在你开口之前就把话说死了。
  2. "最小可检出加速比 1.8%" 与 2% 案例只差一点点：在 RSD = 2.9%、n = 12 的条件下，2% 处在判定边缘；想稳就得增加重复次数或降低噪声（锁频、独占机器、固定输入）。

第 3 节的账本解释了为什么"先 nsys 再 ncu"：不先拆端到端，你连该不该动 kernel 都不知道。以下两条是可选路径（需自备 GPU 或云上按需），没有 GPU 不影响本课结论。

# ---- 可选（需自备或云上按需）：系统级 / kernel 级的两级 profile ----
nsys profile -o baseline --force-overwrite=true python3 train_step.py
#   → 打开生成的 baseline.nsys-rep，先看时间线：kernel / memcpy / 同步各占多少
ncu --set full -k my_kernel --launch-count 3 python3 train_step.py
#   → 只看名叫 my_kernel 的 kernel：带宽利用率、算力利用率、是否 memory-bound
#   注意：ncu 会显著改变执行速度，它的绝对值只当量级看，趋势与比值更可信。
#           先 nsys 定位「谁最贵」，再 ncu 回答「它为什么贵」——顺序反了会浪费大量时间。
# ---- 可选（需自备 GPU 或云上按需）：用 CUDA event 把 kernel 时间和端到端时间分开 ----
# 关键点：CUDA 是异步的，计时必须用 event 或 synchronize 把 kernel 真正等到结束。
import time, torch

x = torch.randn(4096, 4096, device='cuda')
for _ in range(3):
    y = x + 1.0                                  # 预热
torch.cuda.synchronize()

t0 = time.perf_counter()
for _ in range(50):
    y = x + 1.0
torch.cuda.synchronize()                         # 端到端：含所有启动开销
print(f'端到端 平均 {((time.perf_counter() - t0) / 50) * 1e6:.1f} µs')

start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)
start.record()
for _ in range(50):
    y = x + 1.0
end.record()
torch.cuda.synchronize()
print(f'设备侧 平均 {start.elapsed_time(end) / 50 * 1e3:.1f} µs')
# 两个数字的差 = 主机侧调度/启动开销；把它和「kernel 实际执行时间」对齐，
# 就能回答：优化 kernel 到底能拿到多少端到端收益（对应 §3 的账本）。

三、练习#

  1. 实现：把 report() 改成报告胜场数与分位数（差值中位数与 90 分位），并加"显著 / 不显著 / 数据不足"三态结论（n < 8 时输出"数据不足"）。
  2. 解释：为什么配对测量比"各测 20 次比均值"更灵敏？并举一个会让配对失效的场景（提示：两版本交错测互相干扰，如显存占用差异）。
  3. 对比/验证：把 report('12% 提升', ...) 的 gain 依次改成 0.48、0.20、0.08、0.03，记录每次的 t 与结论，找出刚好跨过临界值的 gain，解释它与"最小可检出加速比"的关系。
  4. 思考：一个 kernel 占端到端 40%，优化 25%（该段降到 75%）后端到端提升多少？若噪声地板是 5%，能判定吗？若它同时是最难维护的手写实现，你做还是不做？
