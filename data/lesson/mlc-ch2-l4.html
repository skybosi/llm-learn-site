图断裂（graph break）：成因、代价与诊断#

第 3 课的 guard 处理的是"形状变了怎么办"，但还有一类让编译器更难受的情况：这段 Python 的语义根本没法进图。loss.item() 把张量压成 Python 数字，print(loss) 有副作用，if x.sum() > 0: 的条件来自张量值——这些语句一旦出现，前端只能把已捕获的前缀编译成一段图、把剩下的交回 eager 执行，再从断点继续跟踪。这个动作叫图断裂（graph break）。它的代价不是"多一个 kernel"，而是每断一处就多一条 Python 语言的边界：中间张量被迫物化回 eager、跨边界的算子链失去融合机会、每段还要各付一次调度开销。本课把断裂规则写成可打印的规则表与诊断器。

一、概念讲解#

1. 前端为什么必须"停"#

Dynamo 类前端接管的是字节码派发，它能安全编译的语义有个硬边界：图里只能有张量计算。一旦某条指令的语义依赖"Python 世界的对象"——标量、容器、异常、IO、模块属性——编译结果就无法只用张量运算表达，必须停。这不是实现偷懒，而是图的表达能力决定的：FX 图只有"算子 + 张量边"，没有 Python 的对象模型。

2. 五类常见断因#

断因 典型代码 为什么不能进图
张量 → Python 标量 loss.item()、float(x) 标量脱离图，后续 Python 逻辑无法在图上表达
数据相关控制流 if x.sum() > 0:、while x[i] < 0: 条件来自张量值，图里只能记 guard，不能选支
Python 副作用 print、写文件、改全局 输出/IO 的顺序与内容不归图管
Python 容器修改 stats['n'] += 1、list.append 图只跟踪张量，容器状态留在 Python 里
依赖张量值的断言 assert x.max() > 0 失败要让 Python 抛异常，控制流在 Python 侧

与之相对，纯张量链（matmul → add → relu → matmul）不会断；torch.where、张量算术形式的条件选择也能留在图里——这是"改写掉断裂"的主要手段。

3. 代价：不是"多一个 kernel"这么简单#

断裂把函数切成 S 段、留下 B 处断点，开销至少有三块：

  1. 边界物化：每段结尾的张量必须写回 eager 的存储，下一段再从那里读，段间无法融合。
  2. 调度与派发：每段是一次独立的图执行（各自的内核启动、参数准备），S 段就有 S 份固定开销。
  3. Python 往返：每到断点都要回到 Python 解释器执行一条语句（这正是断因本身），再重新进入跟踪。

本课代码用一个示意模型把这三块压成两个参数：每段固定开销 12 单位、每断点 25 单位。它不是实测性能，只用来比较相对大小；结论是同一个 7 算子的模型，四处断裂时固定开销是无断裂时的约 11 倍（12 → 136）。

4. 诊断方法#

断裂本身不报错，所以诊断靠"让编译器说出来"：Dynamo 会在日志里打印断点位置与原因（TORCH_LOGS=graph_breaks 一类开关，具体名称以本机文档为准），再配合 torch._dynamo.explain 给出每段的算子数与断因。拿到断因表之后，动作是固定的两步查表：

  • 能改写就改写：if x.sum() > 0 → torch.where；.item() 移到编译区外。
  • 改不了就隔离：把副作用、日志、容器状态挪到被编译函数的外面，让编译器只看见张量。

5. 常见坑#

  • 只数算子数：段数少不等于收益高，一段里塞满互相依赖的算子可能刚好塞满寄存器。
  • 把断裂当 bug：它是前端的安全策略（宁可退回 eager 也不编错）；要处理的是代价，不是存在性。
  • 用 fullgraph=True 当优化开关：它把断裂变成报错，只适合"我要确认这段代码能整体进图"的验收场景。

二、可运行代码示例#

下面用纯标准库（本机 python3.10 与 python3.14 输出一致）写一个极简前端模拟器：trace_program 按"算子可编译则并进当前段，否则结束当前段并记断点"的规则切段，BREAK_RULES 是断因表，最后把断点翻译成"改哪一行"的诊断表。

# ===== 图断裂：哪些语句会让前端"切一刀"，以及切完的代价 =====
# 纯标准库实现（本机 python3.10 与 python3.14 输出一致）

# ---------- 0. 被前端接管的算子（其余语句一律按"不可编译语义"处理） ----------
COMPILABLE = {'matmul', 'add', 'mul', 'sub', 'div', 'exp', 'relu'}

class Seg:
    def __init__(self, start): self.start, self.ops = start, []
    def __repr__(self):
        return f'段@{self.start}({len(self.ops)} 个算子)'

def trace_program(program):
    """program 是 (op, *args) 语句表。规则：算子可编译就并进当前段；
    不可编译语句结束当前段（若无段则跳过），并记成一处断点。"""
    segs, breaks, cur = [], [], None
    for i, stmt in enumerate(program):
        if stmt[0] in COMPILABLE:
            if cur is None: cur = Seg(i); segs.append(cur)
            cur.ops.append(stmt[0])
        else:
            if cur is not None: cur = None
            breaks.append((i, stmt[0]))
    return segs, breaks

# ---------- 1. 断因表：Dynamo 式前端在哪几类语句上必须停 ----------
BREAK_RULES = {
    'item':   ('张量 → Python 标量', '标量脱离图，后续 Python 逻辑无法在图上表达'),
    'bool':   ('数据相关控制流',     '条件值来自张量，图里只能记 guard，不能在两支里选'),
    'print':  ('Python 副作用',      '输出/IO 不属于张量计算，顺序也无法进图'),
    'dictop': ('Python 容器修改',    '图只跟踪张量，容器状态要留在 Python 里'),
    'assert': ('依赖张量值的断言',   '断言失败要让 Python 抛异常，控制流不归图管'),
}

# ---------- 2. 一段真实风格的模型代码，故意埋了四处断裂点 ----------
PROGRAM = [
    ('matmul', 'x', 'W'), ('add', 'v0', 'b'), ('relu', 'v1'),
    ('item',),                     # loss = v2.mean().item()
    ('print',),                    # print(loss)
    ('matmul', 'v2', 'W2'), ('relu', 'v5'),
    ('dictop',),                   # stats['count'] += 1
    ('bool',),                     # if x.sum() > 0: ...
    ('add', 'v6', 1.0), ('mul', 'v9', 2.0),
]

def report(program, name):
    segs, breaks = trace_program(program)
    print(f'=== {name} ===')
    print(f'  段划分：{segs}')
    print(f'  断点 {len(breaks)} 处：')
    for i, op in breaks:
        reason, detail = BREAK_RULES[op]
        print(f'    第 {i:>2} 条语句 {op:<6} → {reason}（{detail}）')
    n_ops = sum(len(s.ops) for s in segs)
    print(f'  可编译算子 {n_ops} 个被切成 {len(segs)} 段；没有断裂时本可合成 1 段')

print('--- 代价模型：段数 S 与断点数 B 决定固定开销 ---')
SEG_COST, BREAK_COST = 12.0, 25.0     # 单位是"示意值"，此处只比较相对大小，不是实测性能
for name, prog in (('无断裂', [p for p in PROGRAM if p[0] in COMPILABLE]),
                   ('一处断裂', PROGRAM[:4] + [p for p in PROGRAM[5:] if p[0] in COMPILABLE]),
                   ('四处断裂', PROGRAM)):
    segs, breaks = trace_program(prog)
    n_ops = sum(len(s.ops) for s in segs)
    over = len(segs) * SEG_COST + len(breaks) * BREAK_COST
    print(f'  {name:<6} 算子 {n_ops:>2} 个 → 段 {len(segs)} 个、断点 {len(breaks)} 个，'
          f'开销 {over:>5.1f}（每段 {SEG_COST} + 每断点 {BREAK_COST}）')

print()
report(PROGRAM, '四处断裂的模型代码')

print('\n=== 融合边界：断裂会把能融合的算子链拆开 ===')
segs, _ = trace_program(PROGRAM)
for s in segs:
    print(f'  {s}：链内可整段融合；链尾必须把中间张量交回 eager')

print('\n=== 诊断表：把断点翻译成"改哪一行" ===')
FIX = {'item': '把 .item() 移出被编译函数（评测/日志阶段再取值）',
       'bool': '改成张量运算（如 torch.where），或用编译器的动态形状开关',
       'print': '移出编译区，或改用编译期可控的日志',
       'dictop': '状态提到函数外，或用图外的封装层',
       'assert': '只对 shape/dtype 断言（编译期可判定）'}
for i, op in trace_program(PROGRAM)[1]:
    print(f'  {i:>2} {op:<6} {BREAK_RULES[op][0]:<14} → {FIX[op]}')

实际运行结果（python3.10.16，与 python3.14.5 一致）：

--- 代价模型：段数 S 与断点数 B 决定固定开销 ---
  无断裂    算子  7 个 → 段 1 个、断点 0 个，开销  12.0（每段 12.0 + 每断点 25.0）
  一处断裂   算子  7 个 → 段 2 个、断点 1 个，开销  49.0（每段 12.0 + 每断点 25.0）
  四处断裂   算子  7 个 → 段 3 个、断点 4 个，开销 136.0（每段 12.0 + 每断点 25.0）

=== 四处断裂的模型代码 ===
  段划分：[段@0(3 个算子), 段@5(2 个算子), 段@9(2 个算子)]
  断点 4 处：
    第  3 条语句 item   → 张量 → Python 标量（标量脱离图，后续 Python 逻辑无法在图上表达）
    第  4 条语句 print  → Python 副作用（输出/IO 不属于张量计算，顺序也无法进图）
    第  7 条语句 dictop → Python 容器修改（图只跟踪张量，容器状态要留在 Python 里）
    第  8 条语句 bool   → 数据相关控制流（条件值来自张量，图里只能记 guard，不能在两支里选）
  可编译算子 7 个被切成 3 段；没有断裂时本可合成 1 段

=== 融合边界：断裂会把能融合的算子链拆开 ===
  段@0(3 个算子)：链内可整段融合；链尾必须把中间张量交回 eager
  段@5(2 个算子)：链内可整段融合；链尾必须把中间张量交回 eager
  段@9(2 个算子)：链内可整段融合；链尾必须把中间张量交回 eager

=== 诊断表：把断点翻译成"改哪一行" ===
   3 item   张量 → Python 标量 → 把 .item() 移出被编译函数（评测/日志阶段再取值）
   4 print  Python 副作用     → 移出编译区，或改用编译期可控的日志
   7 dictop Python 容器修改    → 状态提到函数外，或用图外的封装层
   8 bool   数据相关控制流        → 改成张量运算（如 torch.where），或用编译器的动态形状开关

三处可核对的结论：断裂是按语义切、不是按算子切——同一份代码里 7 个可编译算子被 4 处断点切成 3 段；固定开销随段数与断点数一起涨——12 → 49 → 136，示意模型下四处断裂是 11 倍；诊断结果是行动项——每条断因都有对应的"改写或隔离"动作，.item()、print、容器状态三类可以靠移动代码消除，数据相关控制流要么换成张量运算、要么接受它。

三、练习#

  1. 实现：给 trace_program 加"断点代价分级"——print 只算一次轻微开销、数据相关控制流算最高级，重跑代价模型，观察四处断裂的开销是否变化。
  2. 解释：为什么 if x.sum() > 0 必须断，而 x = torch.where(x > 0, x, 0) 不必？从"图的表达能力"角度回答。
  3. 对比/验证：把 PROGRAM 里的 item/print/dictop 三条从列表里删掉、只留 bool，重跑代价模型；再解释为什么"移动代码"能消掉三类断因，却消不掉数据相关控制流。
