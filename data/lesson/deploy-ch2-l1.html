环境准备与量化#

从这一章开始动手。部署第一步不是敲启动命令，而是把环境搭对、把模型"压缩"到能上卡的程度。环境准备三件事——驱动/CUDA、容器/运行时、模型权重；量化则是把上一章的选型落到磁盘上，产出真正能加载的量化文件。学完本课，你应当能在干净机器上装好 vLLM，并把一个 7B 模型量化成 AWQ 4-bit 或 GGUF，且能解释每一步在做什么。

一、概念讲解#

1. 环境准备三步#

第一步：驱动与 CUDA。GPU 推理需要 NVIDIA 驱动 + CUDA 运行库。验证命令：

nvidia-smi                      # 看驱动、显卡型号、显存、CUDA 版本
nvcc --version                  # 看 CUDA 工具链版本（若只跑推理，驱动够用即可）

经验：先看 nvidia-smi 右上角的 CUDA 版本，让 Python 库的 CUDA 版本 ≤ 驱动支持的版本。比如驱动支持 CUDA 12.x，就装 cu124 的 PyTorch。

第二步：容器或虚拟环境。生产环境强烈推荐 Docker（隔离 + 可复现），需要装 NVIDIA Container Toolkit：

docker --version
docker run --rm --gpus all nvidia/cuda:12.4.0-base-ubuntu22.04 nvidia-smi   # 验证容器内能看到 GPU

本机开发则用 conda/venv 建独立环境，避免污染系统 Python。

第三步：模型权重。从 Hugging Face 下载，或用国内镜像加速：

pip install -U "huggingface_hub[cli]"
HF_ENDPOINT=https://hf-mirror.com huggingface-cli download Qwen/Qwen2.5-7B-Instruct --local-dir ./Qwen2.5-7B-Instruct

2. 装 vLLM#

pip install vllm        # 官方 wheel 已内置对应 CUDA，通常无需自装 CUDA
python -c "import vllm; print(vllm.__version__)"   # 验证

装完后 vllm serve --help 能列出全部启动参数，说明环境就绪。

3. 量化：把选型落到磁盘#

上一章选了量化方案，这里动手产出量化文件。两条主流路径：

  • AWQ（4-bit，GPU 在线推理）：用 AutoAWQ 对模型做一次激活感知量化，产出 model.safetensors（约原 FP16 的 1/4 大小）；
  • GGUF（端侧/CPU）：先转成 GGUF FP16，再用 llama-quantize 量化成 Q4_K_M 等档位，供 llama.cpp 加载。

量化要点：量化是一次性的离线重写权重，推理时只加载、不再训练，所以量化成本要算"一次付出、长期收益"。4-bit 会牺牲一点精度（通常 <1% 的下游指标下降），换来显存减半以上。

4. 量化前先想清楚"为什么量"#

量化收益排序：省显存（可装更大模型/更大批）> 提吞吐（访存减少）> 省磁盘。如果你只是"7B 跑在 80G 卡上"，量化收益有限；但如果是"70B 想塞进单张 80G"，量化几乎是唯一选择。别为了量化而量化。

二、可运行示例#

示例 1：一条命令序列完成环境准备#

# ---- 1. 检查 GPU 与驱动 ----
nvidia-smi                        # 应看到显卡型号 + 驱动支持的 CUDA 版本

# ---- 2. 建虚拟环境（conda 示例） ----
conda create -n llm python=3.11 -y
conda activate llm

# ---- 3. 装推理引擎 ----
pip install -U vllm               # 内置 CUDA，免手动装

# ---- 4. 下载模型（用国内镜像加速） ----
pip install -U "huggingface_hub[cli]"
HF_ENDPOINT=https://hf-mirror.com huggingface-cli download \
    Qwen/Qwen2.5-7B-Instruct --local-dir ./Qwen2.5-7B-Instruct

# ---- 5. 验证环境 ----
python -c "import vllm; print('vLLM', vllm.__version__, '就绪')"

示例 2：AutoAWQ 量化 7B 模型为 4-bit#

# -*- coding: utf-8 -*-
# 用 AutoAWQ 把 Qwen2.5-7B 量化为 AWQ 4-bit，产出可被 vLLM 加载的 safetensors
from awq import AutoAWQForCausalLM
from transformers import AutoTokenizer

model_path = "./Qwen2.5-7B-Instruct"     # 已下载的原始权重
quant_path = "./Qwen2.5-7B-Instruct-AWQ" # 量化输出目录

quant_config = {
    "zero_point": True,   # 是否用零点（群组量化偏移）
    "q_group_size": 128,  # 每 128 个权重共享一个缩放因子
    "w_bit": 4,           # 4-bit 量化
    "version": "GEMM",    # GEMM 内核，vLLM/TensorRT-LLM 兼容
}

# 加载原始模型并量化（AWQ 会跑一小批校准数据，耗时约几分钟）
model = AutoAWQForCausalLM.from_pretrained(model_path)
tokenizer = AutoTokenizer.from_pretrained(model_path)
model.quantize(tokenizer, quant_config=quant_config)

# 保存量化权重 + 分词器 + 量化配置
model.save_quantized(quant_path)
tokenizer.save_pretrained(quant_path)
print(f"量化完成，输出目录：{quant_path}")
print(f"提示：磁盘大小约从 14GB(FP16) 降到 4GB(4-bit)")

示例 3：GGUF 量化（llama.cpp 路径）#

# 1. 转换脚本：把 HF 权重转成 GGUF FP16
python llama.cpp/convert_hf_to_gguf.py ./Qwen2.5-7B-Instruct \
    --outfile Qwen2.5-7B-Instruct-f16.gguf

# 2. 量化到 Q4_K_M（约 4.3 bit 混合精度，端侧常用档）
./llama-quantize Qwen2.5-7B-Instruct-f16.gguf Qwen2.5-7B-Instruct-Q4_K_M.gguf Q4_K_M

# 3. 看文件大小对比（示例数值）
#   FP16 约 14.3GB  ->  Q4_K_M 约 4.7GB，缩小约 67%

三、练习#

  1. 补验证：在示例 1 的命令序列后加一条"用 vllm serve --help | head 检查启动参数"的验证命令，并解释为什么这能证明环境完整。
  2. 量化对比：把示例 2 的 q_group_size 改成 64 和 256，分别跑量化，观察输出大小与速度差异，说明群组大小对"精度-体积"权衡的影响。
  3. 算磁盘收益：70B 模型 FP16 约 140GB，估算 AWQ 4-bit 与 GGUF Q4_K_M 后的体积，并说明为什么离线传输/端侧分发场景特别在意这个数字。
  4. 排查练习：python -c "import vllm" 报 CUDA 版本不匹配时，写出你的排查顺序（先看 nvidia-smi 的 CUDA 版本 → 再看 wheel 的 cu 版本 → 决定重装哪个）。
