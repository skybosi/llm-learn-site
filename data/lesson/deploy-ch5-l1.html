量化对比实验#

把模型从 FP16 压到 INT8 甚至 INT4，能显著省显存、提吞吐，但代价是可能掉精度。问题是：掉多少？值不值？ 各家论文和 README 里的数字往往在"自己最有利的设置"下测得，未必符合你的场景。这一课教你自己设计一次公平的量化对比实验，用同一套硬件、同一批数据、同一组指标，把 FP16 / INT8 / INT4 放上擂台。

一、概念讲解#

1. 量化到底是什么权衡#

回顾推理优化课的内容：量化的本质是把权重（有时还有激活值）从高精度（FP16，每参数 2 字节）映射到低精度，从而同时换来三样东西——更小的显存占用、更快的 decode（每 token 要读的权重字节变少，访存压力下降）、以及可能在有限显存里塞下更大的模型或更多 KV Cache。代价是数值精度损失，可能体现在困惑度（perplexity）上升或下游任务准确率下降。

几种主流方案：

方案 位宽 特点
FP16（基线） 16bit 无量化，作对照
FP8 8bit 需要较新 GPU（H100 等），权重+激活都量化，速度快
INT8（如 bitsandbytes） 8bit 权重量化为主，精度损失小
INT4（AWQ） 4bit 基于激活分布保护重要通道，速度好
INT4（GPTQ） 4bit 逐层误差最小化，校准成本高但效果好

注意还有一类"KV Cache 量化"（如 FP8 KV Cache），它量化的是缓存而非权重，目的是省显存容纳更长上下文/更多并发，与权重量化是两码事，别混淆。

2. 为什么要自己测，而不是信 README#

因为量化的精度损失高度依赖模型、任务和校准数据。同一个 AWQ INT4，在通用对话上可能几乎无损，在数学推理或代码生成上却可能明显退化。此外吞吐数字还受硬件（显存带宽、算力）和引擎实现影响。所以"你的模型 + 你的任务 + 你的硬件"这三者组合出的结论，只能由你自己的实验得出。

3. 一次公平实验的四要素#

公平对比要控制变量，只让"量化方案"这一个变量变化：

  1. 同一硬件：同一张卡、同一驱动、同一引擎版本；
  2. 同一批测试数据：固定一组有代表性的 prompt（覆盖你真实业务的长短、领域），质量评测用同一份 benchmark；
  3. 同一采样设置：temperature、max_tokens、seed 一致，避免随机性干扰；
  4. 四个维度的指标都要收：
    • 质量：困惑度（PPL）或下游任务准确率；
    • 显存：加载后峰值显存占用；
    • 吞吐：稳定负载下的 token/s（或 req/s）；
    • 延迟：TTFT 与 TPOT 的分位数。

只有四维一起看，才能下"值不值"的结论——有时 INT4 掉了 1 个点准确率，却把吞吐翻倍、显存减半，对成本敏感场景完全可接受。

4. 显存速算#

一个参数为 P（如 7B）、位宽 b bit 的模型，纯权重约需 8P×b​ 字节：

  • 7B FP16：7×109×2=14 GB；
  • 7B INT8：约 7 GB；
  • 7B INT4：约 3.5 GB（再加少量量化元数据与运行时开销）。

别看 INT4 省得爽，它的"人均精度"通常也是掉得最多的，所以实验要回答的正是"省下的这 10GB 显存，用多少精度换来的"。

二、可运行示例#

示例 1：用 vLLM 分别启动三种量化配置#

# 基线：FP16
vllm serve meta-llama/Llama-3.1-8B-Instruct --served-model-name llama-fp16

# AWQ INT4（需下载对应 AWQ 量化权重）
vllm serve casperhansen/Llama-3.1-8B-Instruct-AWQ \
  --quantization awq --served-model-name llama-awq

# FP8（需较新 GPU，权重+激活都量化）
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --quantization fp8 --served-model-name llama-fp8

启动后记下日志里打印的"峰值显存占用"，这是第一个对比维度。

示例 2：写一个吞吐与延迟测量脚本#

# -*- coding: utf-8 -*-
# 对指定服务打固定负载，测吞吐与延迟分位数，保证各配置可比
import time, asyncio, aiohttp

async def one_request(session, url, payload):
    t0 = time.perf_counter()
    async with session.post(url, json=payload) as r:
        await r.json()
    return time.perf_counter() - t0

async def benchmark(base, model, n_req=60, concurrency=8):
    url = f"{base}/v1/chat/completions"
    payload = {"model": model,
               "messages": [{"role": "user", "content": "用 200 字介绍推荐系统。"}],
               "max_tokens": 200, "temperature": 0.0}
    async with aiohttp.ClientSession() as sess:
        sem = asyncio.Semaphore(concurrency)   # 控制并发，模拟真实负载
        async def run():
            async with sem:
                return await one_request(sess, url, payload)
        t0 = time.perf_counter()
        latencies = await asyncio.gather(*[run() for _ in range(n_req)])
        wall = time.perf_counter() - t0
    latencies.sort()
    p99 = latencies[int(len(latencies) * 0.99)]
    # 吞吐：总请求数 / 墙钟时间（含排队），反映并发下的真实吞吐
    print(f"吞吐={n_req/wall:.1f} req/s | 平均延迟={sum(latencies)/n_req*1000:.0f}ms | P99={p99*1000:.0f}ms")

asyncio.run(benchmark("http://localhost:8000", "llama-awq"))

把 model 分别换成 llama-fp16 / llama-awq / llama-fp8，各跑一遍，记录吞吐、P99 延迟，连同示例 1 的显存一起填入对比表。

示例 3：质量评测（用 lm-eval 测困惑度或任务分）#

# 用 lm-evaluation-harness 对同一任务测不同量化版本，得到可比的质量分
pip install lm-eval
# 以 8-shot MMLU 为例（对 FP16 与 AWQ 各跑一次）
lm_eval --model vllm --model_args pretrained=meta-llama/Llama-3.1-8B-Instruct \
        --tasks mmlu --num_fewshot 8 --batch_size auto
lm_eval --model vllm --model_args pretrained=casperhansen/Llama-3.1-8B-Instruct-AWQ \
        --tasks mmlu --num_fewshot 8 --batch_size auto

把四维结果整理成一张表：

配置 峰值显存 吞吐(req/s) P99 TTFT 质量(MMLU)
FP16 ~16GB 参考值 参考值 参考值
INT4 AWQ ~6GB ↑ 略升 略降
FP8 ~9GB ↑↑ 略降 几乎持平

三、练习#

  1. 用示例 1 的三种配置，各自记下启动日志里的峰值显存，验证示例 4 节的显存速算是否大致吻合，并解释差异来自哪里（运行时开销、KV Cache 预留）。
  2. 把示例 2 的 max_tokens 从 200 改成 800，重测三种配置的吞吐，观察"输出变长"时 INT4 相对 FP16 的吞吐优势是变大还是变小，为什么（提示：decode 访存占比）。
  3. 选一个数学或代码类 benchmark（如 GSM8K 或 HumanEval），对比 FP16 与 INT4 的质量分，说明为什么"量化掉多少精度"和任务类型强相关。
  4. 思考：如果一个服务 90% 的请求是短文本分类（输出 < 20 token），量化带来的吞吐收益还会明显吗？此时更该优先考虑哪种优化？
