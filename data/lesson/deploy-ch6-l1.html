项目规划#

前面五章把"部署场景、单卡、多卡、服务化、成本优化"逐个击破，这一章要把它们串成一个真实项目：从需求出发，走完"规划 → 实现 → 验收"的完整闭环。本课先做规划——定义一个可落地的目标、量化 SLA 与容量、敲定技术选型与架构，为下一课的动手实现铺路。

一、概念讲解#

1. 项目目标：一个智能客服问答服务#

我们以一个典型业务为背景：为一家中型电商公司搭建「智能客服问答助手」，对外提供 OpenAI 兼容 API，供官网聊天窗和内部工单系统调用。它的特点很有代表性：白天高峰、夜间低谷、短问答为主、偶发长文档检索，几乎覆盖了我们前面讲过的所有权衡。

一句话目标：在满足"P99 TTFT ≤ 1.5s、可用性 ≥ 99.9%、每百万 token ≤ 2 元"的前提下，扛住峰值 20 QPS。

2. 需求分析：把"要什么"翻译成可测的数字#

模糊的需求无法验收。规划第一步是把需求落成 SLA 表（回顾第 4 章 l3 的 SLI/SLO）：

维度 目标（SLO） 说明
吞吐 峰值 20 QPS，平均输出 150 token 决定 GPU 张数
首 token 延迟 P99 TTFT ≤ 1.5s 用户体感核心
生成速度 P99 TPOT ≤ 30ms 读起来顺不顺
可用性 ≥ 99.9%（月度） 错误预算约 43 分钟/月
成本 ≤ 2 元 / 百万 token 盈亏红线

3. 技术选型：用决策树走一遍#

回看第 1 章的选型决策树，逐项敲定：

  • 模型：Llama-3.1-8B-Instruct——8B 在单卡/双卡上性价比较高，指令跟随够用；
  • 量化：AWQ INT4——客服场景对精度宽容度高，但吞吐和显存收益大（第 5 章 l1 的结论）；
  • 引擎：vLLM——连续批处理成熟、OpenAI 兼容 API 开箱即用、指标完备；
  • 硬件：2 张 A100-80G，张量并行 TP=2——8B + INT4 单卡其实能装，但双卡 TP 能分摊 decode 的访存压力、提升吞吐并留余量（第 3 章）；
  • 服务化：Docker 容器 + OpenAI 兼容 API + Nginx 网关（第 4 章）；
  • 可观测：Prometheus + Grafana 盯 P99 TTFT 与排队长度（第 4 章 l3）。

4. 架构设计#

分层架构如下（箭头表示请求流向）：

客户端(官网聊天窗/工单系统)
        │  OpenAI 兼容协议 (HTTP/SSE)
        ▼
   Nginx 网关(统一入口、限流、SSE 透传)
        │
        ▼
   vLLM 服务(OpenAI 兼容 API, AWQ INT4, TP=2)
        │
        ▼
   模型权重(挂载卷)          Prometheus ── Grafana(大盘+告警)

要点：网关负责对外暴露、做限流与鉴权；vLLM 只对内；监控走旁路采集 /metrics，不与业务请求抢资源。

二、可运行示例#

示例 1：容量规划脚本#

# -*- coding: utf-8 -*-
# 从 SLA 反推需要几张卡、以及单位成本
import math

peak_qps = 20               # 峰值每秒请求数
avg_out_tokens = 150        # 平均每个回答的输出 token 数
peak_out_tps = peak_qps * avg_out_tokens   # 峰值输出 token/s

single_gpu_tps = 3000       # 单卡 A100 + INT4 满载吞吐（示意值）
util_target = 0.6           # 目标利用率 60%，留 40% 余量
gpus_needed = peak_out_tps / (single_gpu_tps * util_target)
print(f"峰值输出需求 = {peak_out_tps} token/s")
print(f"建议 GPU 数 = {gpus_needed:.2f} -> 向上取整 {math.ceil(gpus_needed)} 张")

# 成本核算：满载时每百万 token 成本
gpu_price = 20.0            # A100 预留实例单价（元/小时，示意）
cost_per_m = gpu_price / (single_gpu_tps * 3600) * 1_000_000
print(f"满载时每百万 token 成本 = {cost_per_m:.2f} 元")

示例 2：把需求落成配置文件清单#

规划阶段就应把"要交付什么"列成清单，下一步实现时逐项勾掉：

项目交付物清单（检查表）
[ ] docker-compose.yml          # vLLM + 网关 + 监控编排
[ ] nginx.conf                  # SSE 透传、限流、统一入口
[ ] prometheus.yml              # 抓取 vLLM /metrics
[ ] 模型权重挂载目录（AWQ INT4 权重）
[ ] 验收脚本（压测 + 断言 SLO）
[ ] Grafana 大盘（P99 TTFT / 排队 / 吞吐）

三、练习#

  1. 把示例 1 的 avg_out_tokens 从 150 改成 400（客服开始做长摘要），观察 gpus_needed 怎么变，说明"平均输出长度"为何是容量规划的第一变量。
  2. 若某天双十一峰值 QPS 是日常的 5 倍，用示例 1 的公式算需要临时扩到几张卡，并说明你倾向于"常驻扩容"还是"临时按需/spot 扩容"（结合第 5 章 l3 的计费）。
  3. 补充一张"风险登记表"，至少包含：GPU OOM、模型加载失败、SSE 被网关缓冲、监控指标缺失四类风险，并各写一条应对措施。
  4. 思考：为什么把"每百万 token ≤ 2 元"也写进 SLO？它和吞吐/延迟目标之间可能产生怎样的张力？
