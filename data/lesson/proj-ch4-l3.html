结果与复盘（本地部署与成本核算）#

上一课你拿到了四条路线的实测显存、吞吐、延迟。这一课把散落的数字汇总成一份成本核算报告，并把它变成面试里能讲 10 分钟的话术。这是本项目的收官课，也是整个项目"差异化价值"最集中的地方——别人会部署，你会"算账"。

一、目标与步骤#

1. 本课目标#

产出三样东西：① 一张量化对比表；② 一份成本核算报告（含 70B 推算）；③ 一段面试话术。三样东西合起来，就是你 GitHub 仓库里的 README 主体和简历上的项目条目。

2. 分步#

  1. 汇总实测数据 → 量化对比表；
  2. 把吞吐翻译成钱 → 成本核算报告；
  3. 用 7B 规律外推 70B → 卡数与成本；
  4. 写面试话术 + 复盘踩过的坑。

二、结果汇总：量化对比表与成本报告#

1. 量化对比表（填你的实测值）#

下面表格的数值是"示例量级"，请替换成你在上一课 nvidia-smi 与压测脚本得到的真实数字。关键是有三列可对比：显存、吞吐、延迟。

方案 引擎 权重精度 显存占用（示例） 吞吐 tokens/s（示例） TTFT P99（示例）
FP16 基准 vLLM 16-bit ~17 GB ~400 ~2.1 s
AWQ vLLM 4-bit ~9 GB ~900 ~1.4 s
GPTQ vLLM 4-bit ~9 GB ~850 ~1.5 s
GGUF Q4_K_M llama.cpp 4-bit ~6 GB ~120 ~2.8 s

读这张表能得出三个结论（面试时直接讲）：

  1. 量化省显存：4-bit 把权重从 ~15 GB 压到 ~4 GB，整卡占用近乎减半；
  2. 省下的显存 → 更高并发 → 更高吞吐：AWQ/GPTQ 在同卡上吞吐约为 FP16 的 2 倍，因为能塞进更大的 batch；
  3. 路线决定定位：llama.cpp+GGUF 吞吐远低于 vLLM，但它 CPU 能跑、体积小，适合边缘/低资源，不是"更差"，是"用途不同"。

2. 成本核算报告（算清账）#

核心公式只有一条：把吞吐折算成"每百万 token 多少元"。

每百万 token 成本(元) = GPU小时单价(元) × 卡数 ÷ (吞吐 tokens/s × 3600 ÷ 1e6)

用上面示例值（GPU 小时单价 $1.2、单卡）算：

# cost_report.py —— 把上一课的吞吐数字折算成钱（示例数值）
def cost_per_million(gpu_hour_price, num_gpus, throughput_tps):
    tokens_per_hour = throughput_tps * 3600
    return gpu_hour_price * num_gpus / (tokens_per_hour / 1e6)

price = 1.2   # 示例：24GB 云卡每小时单价（元），替换为你的账单
for name, tps in [("FP16", 400), ("AWQ", 900), ("GPTQ", 850), ("GGUF", 120)]:
    c = cost_per_million(price, 1, tps)
    print(f"{name:6s} 每百万 token ≈ {c:.2f} 元")

输出量级大概是：FP16 每百万 token 约 0.83 元，AWQ 约 0.37 元，GGUF 约 2.8 元。注意 GGUF 单看"每百万 token 成本"反而更贵，因为 llama.cpp 吞吐低——这说明"成本"和"场景"绑在一起：GGUF 的价值是能在没有高端 GPU 的机器上跑，而不是单位成本最低。

报告里再补两个维度，账才算完整：

  • 常驻成本：GPU小时单价 × 24 × 30，即"这个服务挂着不管有没有人用，一个月多少钱"；
  • 单次请求成本：平均输出 token × 每 token 成本，例如平均回复 200 token，AWQ 下约 0.007 元/次。

3. 从 7B 外推到 70B（面试高频）#

用 7B 量出的规律，推算 70B 的卡数和成本（权重 ≈ 参数 × 每参数字节）：

70B 方案 权重 放得下的组合（示例） 每小时成本（示例单价）
FP16 ~140 GB 2× A100 80GB（张量并行） ~4.0 元
AWQ 4-bit ~35 GB 1× A100 80GB 或 2× A10 24GB ~2.0 元

结论一句话："70B 用 4-bit 量化后约 35 GB，一张 A100 80GB 就能装下；FP16 要 140 GB，得 2 张 A100 做张量并行。预算有限时，先用 AWQ 单卡落地，再用并发/批处理摊薄成本。" 这就是 P10 项目要你练成的判断力。

三、面试话术与复盘#

1. 面试话术（能讲 10 分钟）#

被问"说说你的部署项目"时，用 STAR 结构：

  • S 背景："我想搞清一个真实问题：给一个开源 LLM 和固定预算，到底该怎么选卡和量化方案。网上全是经验值，没有一份我能信的数字。"
  • T 任务："于是我部署了 Qwen2.5-7B-Instruct，用 vLLM 跑 FP16 基准和 AWQ/GPTQ 量化，用 llama.cpp 跑 GGUF，实测它们的显存、吞吐、延迟。"
  • A 行动："我写了一个异步压测脚本，从并发 1 到 16 打流，记录 TTFT P99 和整体吞吐；用 nvidia-smi 记录每条路线的显存；最后按公式把吞吐折算成每百万 token 成本。"
  • R 结果："4-bit 量化把权重从约 15 GB 压到约 4 GB，显存占用几乎减半；省下的显存换来更高并发，AWQ 吞吐约为 FP16 的 2 倍，每百万 token 成本从约 0.8 元降到约 0.4 元。我还外推了 70B：FP16 要 2 张 A100，AWQ 单卡就够。"

高频追问，这样接：

  • "为什么 AWQ 比 GGUF 吞吐高？" —— "因为 vLLM 走 GPU + PagedAttention + continuous batching，专为在线高并发优化；llama.cpp 主打 CPU/边缘、单文件分发，吞吐不是它的强项，是定位不同。"
  • "量化会不会掉质量？" —— "4-bit 相对 FP16 有轻微质量损失，但 AWQ/GPTQ 是激活感知/二阶误差补偿的量化，7B 级别上多数任务可接受；我做了几组样例对比，差异很小，这是用极小质量代价换 2 倍吞吐。"
  • "给你 70B 和固定预算怎么选？" —— 用上面外推结论答：先 AWQ 单卡落地，再并发摊薄，必要时 spot/弹性实例降常驻成本。

2. 常见坑与复盘#

坑 教训
只看吞吐不看延迟 高并发下 TTFT P99 会变长，报告必须吞吐+延迟一起给
抄网文数字当实测 数字必须来自自己的 nvidia-smi 和压测，否则面试一追问就露馅
把 GGUF 说成"差" GGUF 是低资源路线，价值在"能跑"不在"最快"，要讲清场景
单价用错币种/计费方式 云 GPU 有按秒/按小时/预留实例/spot 多种计费，报告里注明口径

  1. 用你的真实数据重跑 cost_report.py，写出三行结论：显存省了多少、吞吐提了多少、每百万 token 降了多少。
