协作组与线程束特化（warp specialization）#

前两课解决"跨 block 怎么安全地传一个值"。这一课把 block 内不同 warp 分成不同角色：一部分专职搬数据、一部分专职算——这就是 Hopper 起被反复提到的 warp specialization（线程束特化），FlashAttention 等 kernel 的实现层都用它。前提要先说清：只有当流水线两个阶段本来就要互相等待时，拆分角色才有收益。

一、概念讲解#

1. 三个层次的协作，同步成本依次上升#

第 2 课已经给过 thread_scope_block / _device / _system 三档作用域，协作组（cooperative groups）把"我在哪个范围内协作"从约定变成类型：

层次 对象 同步手段 约束
warp 内 cg::coalesced_threads()、tiled_partition<32> shuffle、__syncwarp 无额外约束
block 内 cg::this_thread_block() cg::sync(block)（等价 __syncthreads()）、cg::barrier 参与方必须全部到达
grid 内 cg::this_grid() grid.sync() 必须用 cudaLaunchCooperativeKernel 启动，且所有 block 必须能同时驻留
cluster 内（cc 9.0+） cg::this_cluster() cluster.sync()、cluster.barrier_arrive/wait cluster 大小受 portable 上限限制

grid 同步的硬约束：grid 里每个 block 都要在 SM 上同时活着，否则先到的等不到后到的，直接死锁。尺寸上限 ≈ SM 数 × 每 SM 可驻留 block 数。用示例参数（132 个 SM、每 SM 最多 32 个常驻 block）算：上限 4,224；启动 8,192 个时 根本不能用，得改用"多轮 kernel 启动"或"fence + 原子计数"。因此 grid.sync() 适合"迭代不多、每轮要全局对齐"的算法，不适合内层循环。

2. 协作组还顺手给了什么#

cg::reduce(group, v, cg::plus<T>())、cg::inclusive_scan / exclusive_scan、cg::invoke_one 把参与方集合变成 API 的一部分：谁参与、多大范围、什么操作都写进了类型。cc 8.0+ 上 cg::reduce 对 4 字节类型走硬件加速，更早架构或更大类型走软件回退。它未必比手写两级归约快——换来的是正确性与可维护性。

3. warp specialization：把"等"变成"并行"#

看 FlashAttention 一轮循环：① 从全局内存搬一块 K/V 到 shared；② 用 shared 里的数据做 MMA。不分工时同一批线程先搬后算，搬时算力闲置、算时搬运单元闲置——两段串行。

warp specialization 的做法是 fork 出两类 warp：

  • 生产者 warp：只负责发起搬运（TMA 的 cp.async.bulk.tensor，或第 4 课的 cp.async），然后等待可用的空缓冲；
  • 消费者 warp：只负责计算（MMA / 归约），消费满缓冲，算完后把缓冲还给生产者。

两者之间用一个环形缓冲队列 + 一对计数信号（"空位"与"满位"）同步，或用 cuda::pipeline / mbarrier。生产者不等消费者算完就在准备下一块，两段的延迟被重叠掉。

4. 收益的边界：什么时候不值得#

下面这张表是一个纯参数化的流水线模型（256 批，缓冲深度 S=4）算出总周期数，两列都在同一模型里：

每批生产 每批消费 不重叠 专业化 加速比
4 16 5120 4100 1.25×
8 8 4096 2056 1.99×
16 16 8192 4112 1.99×
1 16 4352 4097 1.06×

读法：专业化把每批总周期从 tprod​+tcons​ 压到 max(tprod​,tcons​)，加速比趋近 1+min/max。两段越接近收益越大（8:8 与 16:16 都是 1.99×，理想值 2×）；极度不对称时收益很小（1:16 只有 1.06×）——瓶颈段没变短，而启动与收尾各要一个完整周期。

第二个结论来自缓冲深度：S 从 1 提到 2，总周期从 5120 掉到 4100；再加到 3、4、8、16 一点没变——"生产者提前一块写、消费者延后一块读"，深度 2 就够覆盖一跳。缓冲区吃 shared memory，不是越大越好，第 4 章的占用率约束会随后回来找你。

5. 两个前提，缺一不可#

  1. 必须有"等待"可以重叠。纯带宽受限（搬完就没别的活）或逐元素算子（元素间无依赖）拆角色的收益近似为零：那点收益来自"多一个 warp 干活"，不是流水线。用同一模型算：4096 个元素、每元素"算 6 存 2"，不分工 32768 周期、分工 16384 周期——2.00×，纯粹是线程数翻倍。
  2. 专业化不改变语义。缓冲区只影响重叠程度，不影响累加顺序：示例 2 里串行求和与深度 2 的流水线求和都是 325.0。若为了让生产者提前跑而改了数据顺序，就回到第 1 课的非结合律问题。

6. 常见坑#

  • fork 出 warp 后忘了同步：生产者与消费者之间的"空/满"计数必须用原子或 barrier，不能靠"我觉得它已经好了"。
  • 以为 cg::sync() 语义不同：官方明确它与 __syncthreads() 给出同样两条保证（到达 + 之前的内存访问可见）；但参与方集合必须完全一致，在条件分支里创建/使用子组是数据竞争。
  • barrier_wait 的语义想当然：barrier_wait 只保证组内所有线程都调用了 barrier_arrive，不保证它们都调用了 barrier_wait。
  • grid 同步塞进内层循环：每轮都要全体驻留，尺寸一超就是死锁或启动失败。
  • 忘了 cluster 的 portable 上限（第 4 课讲过）：跨 SM 的分布式共享内存只在 cluster 内成立。

二、可运行代码示例#

第一段纯 Python（无 GPU）：用参数化模型算出"专业化在什么条件下值钱"，并验证流水线不改变数值结果。

# ===== 示例 1：生产者-消费者流水线 —— 专业化快在哪、什么时候不快 =====
def pipeline(need, t_prod, t_cons, S, specialized=True):
    """t_prod：生产一批的耗时；t_cons：消费一批的耗时；S：环形缓冲区深度。
    specialized=True 时生产与消费由不同 warp 承担、可以重叠；S=1 时退化为不重叠。
    返回 (总周期, 分摊到每批的周期)。"""
    if not specialized or S == 1:
        return need * (t_prod + t_cons), (t_prod + t_cons)
    cycles = t_prod + (need - 1) * max(t_prod, t_cons) + t_cons
    return cycles, cycles / need

need = 256
print("每批生产/消费耗时不同时，专业化流水线（S=4）的收益：")
print(f"{'t_生产':>7}{'t_消费':>7}{'不重叠':>9}{'专业化':>9}{'加速比':>9}")
for tp, tc in ((4, 16), (8, 8), (16, 4), (16, 16), (1, 16)):
    seq, _ = pipeline(need, tp, tc, 4, specialized=False)
    spec, per = pipeline(need, tp, tc, 4, specialized=True)
    print(f"{tp:>7}{tc:>7}{seq:>9}{spec:>9}{seq/spec:>8.2f}x")

print("\n环形缓冲区深度 S（t_生产=4，t_消费=16）：")
for S in (1, 2, 3, 4, 8, 16):
    spec, per = pipeline(need, 4, 16, S, specialized=True)
    print(f"  S={S:>2}：总周期 {spec:>5}，每批 {per:>5.1f}")

# ===== 示例 2：不同重叠程度下，结果必须完全一致 =====
import numpy as np
def consume_serial(batches):
    return sum(batches)

def consume_pipelined(batches, S):
    """环形缓冲：生产者按序放，消费者按序取；S 只改变重叠程度，不改变顺序。"""
    buf, out = [], []
    for b in batches:
        buf.append(b)
        while buf and len(buf) <= S:
            out.append(buf.pop(0))
            break
    while buf:
        out.append(buf.pop(0))
    return sum(out)

rng = np.random.default_rng(0)
batches = [float(rng.integers(1, 10)) for _ in range(64)]
print(f"\n顺序 vs 流水线（S=2）的结果：{consume_serial(batches):.1f} vs "
      f"{consume_pipelined(batches, 2):.1f}（缓冲区只影响重叠，不影响结果）")

# ===== 示例 3：grid 同步的驻留约束（每 SM 最多 32 个常驻 block） =====
def grid_sync_feasible(blocks, sms=132, blocks_per_sm=32):
    resident = sms * blocks_per_sm
    return resident, blocks <= resident

print("\ngrid 同步要求所有 block 同时驻留（SM 数与每 SM 驻留上限以自己显卡官方规格为准；")
print("下面用 132 个 SM × 32 个 block 作示例）：")
for blocks in (132, 1056, 4224, 8192):
    resident, fit = grid_sync_feasible(blocks)
    print(f"  启动 {blocks:>5} 个 block：驻留上限 {resident} → "
          f"{'可用 grid.sync()' if fit else '超出上限，必须换方案'}")

对应的 CUDA 骨架：block 内两级协作组 + 一个生产者/消费者环。下面只保留骨架（真实实现里的搬运应换成 TMA / cuda::pipeline，等待应换成 mbarrier，否则生产者 warp 的自旋会在 L2 上打转）：

#include <cooperative_groups.h>
namespace cg = cooperative_groups;

__global__ void specializedKernel(const float* __restrict__ g, float* __restrict__ out,
                                  int batches, int S) {
    cg::thread_block block = cg::this_thread_block();   // 尽早取句柄（在任何分支之前）
    extern __shared__ float buf[];                      // S 块滚动缓冲，每块 blockDim.x 个 float
    __shared__ int produced;                            // 已产出的批数（生产者写、消费者读）

    if (threadIdx.x == 0) produced = 0;                 // 初始化必须在同步之前
    cg::sync(block);

    int warp = threadIdx.x / 32;
    if (warp == 0) {                                    // 生产者 warp：只负责搬数据
        for (int t = 0; t < batches; ++t) {
            int slot = t % S;
            // 骨架：真实实现用 cp.async.bulk.tensor + mbarrier 完成通知
            for (int i = threadIdx.x; i < blockDim.x; i += blockDim.x)
                buf[slot * blockDim.x + i] = g[t * blockDim.x + i];
            __threadfence_block();                      // 数据已写进 shared，对块内可见
            if (threadIdx.x == 0) atomicAdd(&produced, 1);
        }
    } else {                                            // 消费者 warp：只负责算
        for (int t = 0; t < batches; ++t) {
            int slot = t % S;
            while (atomicAdd(&produced, 0) <= t) { }    // 等第 t 批就绪
            out[t * blockDim.x + threadIdx.x] =
                buf[slot * blockDim.x + threadIdx.x] * 2.0f;
            cg::sync(block);                            // 消费完本批才允许覆盖这个 slot
        }
    }
}

// grid 级同步：必须配 cudaLaunchCooperativeKernel，且 grid 尺寸不超过驻留上限
__global__ void gridScale(float* g, int rounds) {
    cg::grid_group grid = cg::this_grid();
    for (int r = 0; r < rounds; ++r) {
        g[threadIdx.x] *= 1.0001f;
        grid.sync();                                    // 全体对齐后才进下一轮
    }
}

三、练习#

  1. 实现：把示例 1 的模型扩成"生产者与消费者各占若干 warp、角色内还有各自并行度"的两级模型，找出 t_prod=4, t_cons=16 时让总周期最小的缓冲深度与角色配比。
  2. 解释：为什么缓冲深度从 2 加到 16 总周期一点没变？如果生产者是"每批耗时抖动很大"的随机变量，这个结论还成立吗？
  3. 对比/验证：把示例 3 的 blocks_per_sm 从 32 降到 8（模拟每块寄存器/共享内存占用很高的情况），重新算驻留上限；再查一次自己显卡（或云上实例）的 SM 数与每 SM 驻留上限，说明 grid 同步在你的机器上最多能带多少个 block。
  4. 思考：FlashAttention 的"分块 + 在线 softmax"里，哪些步骤适合交给生产者 warp、哪些必须留在消费者？如果一个 warp 同时做两者，收益会在哪里丢掉？
