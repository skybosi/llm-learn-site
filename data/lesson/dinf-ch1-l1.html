推理并行的收益条件：α-β 账本与"拆到第几张卡会变慢"#

这一节要解决什么#

llm-inference-optimization 第 5 章告诉你"模型装不下就上张量并行"；distributed-training-systems 第 8 章第 3 课告诉你"推理的通信比训练高一个量级"。这两句话说完了之后，留下一个没有答案的问题：

到底拆几张卡？

"经验上不超过 8"不是答案，因为它既没有给出 8 是怎么来的，也无法解释为什么换个网络（NVLink → InfiniBand）、换个模型宽度、换个 batch，这个数就变了。

这一节要把这个问题变成可闭式求解的。你会得到三个结果：

  1. 一条下界：在 N 张卡上做一次全归约，每卡至少要收 2NN−1​S 字节 †。环形算法恰好达到它 —— 所以"换一个更聪明的通信库"不是出路。（† 严格地说：这是"每卡至少接收 S 字节新信息、且总发送量不低于 2NN−1​S"的紧下界；证明见第二节。）
  2. 一条判据：最优并行度出现在"省下的访存时间 = 多付的通信时间"这一点上。它不是"越大越好"，也不是"装得下就好"。
  3. 一个反直觉的结论：在典型的 decode 形态下（b=1、h=4096、fp16），通信时间比带宽项大三个数量级 —— 通信完全是 α（固定延迟）项在主导，字节数几乎无关。这直接推出："把消息合并成大包再发"这种训练侧的常规优化，在推理 decode 上基本不起作用。

先把这一节的账本符号定下来，全章通用：

符号 含义 示例值（本章固定口径）
L,H 层数、隐藏维 32、4096
Ψ 参数量 6.574×109
N 并行度（参与切分的卡数） 变量
α 单次通信的固定延迟 5μs（NVLink）、10μs（跨机）
β 单卡可用的单向互连带宽 450 GB/s（NVLink）、25 GB/s（IB）
B 显存带宽 3.0 TB/s
C 算力（bf16 稠密） 989 TFLOP/s
b,s batch、序列长 变量

一、把"每 token 成本"写成两项之和#

1.1 为什么必须以"每 token"为口径#

训练侧习惯以"每步"为口径：一个优化器步里通信几次、每次多少字节。这个口径在推理侧必然算错，原因很直接：

推理的时间预算=一次TTFT​​+每个输出 token 都要付(nout​−1)⋅TPOT​​

TPOT 是逐 token 重复的成本，而权重访存、层间通信也是逐 token 重复的；但请求级的固定开销（HTTP、调度、tokenize）只在 TTFT 里出现一次。所以凡是"每 token 都要付"的东西（权重读、层内通信）必须折到单 token，凡是"每请求付一次"的东西不能折。口径混用是这类估算最常见的错误来源。

1.2 decode 阶段的时间下界：只看两个量#

对 batch b、序列长 s 的一次 decode 前向，单卡上的两个下界是：

Tmem​=B2Ψ权重字节⋅并用 ΨB​ 表示(fp16: 2 B/参数)​​​+B2Lnkv​dhead​sb​,Tflop​=C2Ψb​

用电容口径统一写（避免"参数量"与"字节数"混着用）：

Tmem​=BΨB​+KVB​​,Tflop​=C2Ψb​

为什么两项都要算，但我们最后只用一项？ 因为 decode 的算术强度是

I=ΨB​+KVB​2Ψb​≈2Ψ2Ψb​=b  FLOP/byte(b=1 时)

而示例硬件的拐点（roofline knee）是 C/B=989/3.0≈330 FLOP/byte。1≪330，差两到三个数量级，所以 decode 必然是访存瓶颈，Tflop​ 可以忽略。但这句"可以忽略"有边界：当 b 涨到约 330 时（或换成更窄的权重 dtype 使 ΨB​ 下降时）算力才会接棒。第 2 章的连续批处理正是往这个方向推的 —— 提前记住这一点。

⚠️ prefill 是另一回事：s 大时算术强度 ≈2bs/(2b+attn) 随 s 上升，prefill 很快进入算力瓶颈。把 prefill 与 decode 平均成一个数，是这类估算里最贵的错误（llm-inference-optimization 第 1 章已经建立了这个区分，这里只重申它的量级后果）。

1.3 拆到 N 张卡之后：两项各自怎么变#

  • 访存项：权重被切了，每卡只读 1/N → Tmem​(N)=NA​，其中

A=BΨB​+KVB​​

  • 通信项：每层前向有两次全归约（Megatron-LM 口径：MLP 的输出投影一次、注意力的输出投影一次），每次的数据量是 b⋅h 个元素（fp16 即 2bh 字节）。L 层共 2L 次。这一项与 N 的关系取决于算法，见第二节。

于是估算式就是

T(N)=访存，∝1/NNA​​​+通信，∝N 或 logN2L⋅TAR​(N)​​​

这一个式子的形状（A/N+cN）就决定了后面所有结论。

二、通信项的 N 依赖：下界与"为什么换算法没用（带宽上）"#

2.1 全归约的环形算法#

N 个 rank 各持一个长度 S 的向量（元素数；字节数 =Sσ，σ 为每元素字节），要求所有 rank 得到它们的和。环形做法分两半：

ReduceScatter（N-1 步）：rank i 在第 k 步把 chunk (i-k) mod N 发给 i+1，
                          收到后累加 → N-1 步后 rank i 持有第 i 块部分和的**完整**值
AllGather（N-1 步）    ：把各自的完整块沿环 broadcast → N-1 步后人人有全部
每步消息大小 = S/N 个元素

总通信量（每 rank）：

bytes=reduce-scatter 发NN−1​Sσ​​​+all-gather 发NN−1​Sσ​​​=2NN−1​Sσ​

步数：2(N−1)。在 α-β 模型下：

TARring​(N,Sσ​)=延迟项2(N−1)α​​+带宽项2NN−1​βSσ​​​​

2.2 下界的证明：为什么 2NN−1​ 不可改进#

下界一（带宽）：每个 rank 最终要知道 S 个元素的完整和，其中 (N−1)/N 的信息来自别人。设 rank i 从别人处接收的字节数为 Ri​。Ri​ 必须不少于 NN−1​Sσ​：把"和"看成 N 个部分和的函数，rank i 若没收到 rank j 贡献的那一块，就无法算出那一块的和（在一般（无结构）输入下这是信息论要求）。因此

Ri​≥NN−1​Sσ​⟹TAR​≥NN−1​βSσ​​

下界二（延迟）：至少需要 ⌈log2​N⌉ 轮消息（每次消息只能把一个 rank 的信息合并进另一处，rank 数最多翻倍；等价地，N 个 rank 的聚合是个深度至少 log2​N 的归约树）。所以

TAR​≥2⌈log2​N⌉α+NN−1​βSσ​​

（因子 2 来自"reduce + broadcast 两阶段"。）

两条下界的含义完全不同，这是本节最重要的一处区分：

环形算法 下界 紧不紧
带宽项 2NN−1​Sσ​/β NN−1​Sσ​/β 差 2 倍（环形多付了 all-gather 那一半）
延迟项 2(N−1)α 2⌈log2​N⌉α 差 O(N/logN)，很松

所以：

"换更好的通信算法"能赢的是 α 项（logN 而非 N），不是 β 项​

对 N=8、Sσ​=2×4096=8192 B，实测两部分的量级差：

N 单次延迟项 单次带宽项 延迟/带宽 每层（2 次） 全模型（32 层）
2 10.0μs 0.018μs 549× 20.0μs 0.641 ms
4 30.0μs 0.027μs 1099× 60.1μs 1.922 ms
8 70.0μs 0.032μs 2197× 140.1μs 4.482 ms

读法：b=1、h=4096 时消息只有 8 KB，而 NVLink 的 α 约 5μs。带宽项小到可以忽略（0.03 μs），所以 TP 在 decode 上是纯延迟问题。

这是一个可以直接落地的判据：当 2NN−1​Sσ​/β<α 时（本例：Sσ​<450GB/s×5μs×2(N−1)N​≈2.25 MB），通信量无关紧要，只该优化步数。 反过来，prefill 阶段 b⋅s 很大（如 b=32,s=4096 → Sσ​=512 MB），带宽项立刻反超，那时合并消息、压缩激活才有意义。

2.3 树/递归算法把 α 项压到 logN：多快？#

用递归倍增（或 halving-doubling）可以把步数从 2(N−1) 降到 2⌈log2​N⌉，同时保持带宽最优。代入同一模型：

N 环形总时间 树形总时间 提速 环形 tok/s 树形 tok/s
1 4.382 ms 4.382 ms — 228 228
2 2.832 ms 2.832 ms 1.00× 353 353
4 3.017 ms 2.377 ms 1.27× 331 421
8 5.030 ms 2.470 ms 2.04× 199 405
16 9.876 ms 2.836 ms 3.48× 101 353

这张表是本节最有操作价值的结果：换算法不改变"最优 N 在 4 附近"这个结论，但它把曲线整体抬高了 2 倍（N=8 时 199 → 405 token/s）。也就是说，"拆几张卡"和"用什么算法"是两个独立的旋钮，先调哪个的收益是能算出来的。实践中 NCCL 会根据消息大小与拓扑自动在 ring / tree / 混合之间选择（distributed-training-systems 第 4 章第 1 节），推理侧的小消息恰好落在 tree 更优的区间 —— 这也是为什么同一个集群上"训练跑得很好的配置"搬到推理不一定好。

三、最优点：省下的访存 = 多付的通信#

3.1 闭式解#

把 A/N 与通信项放一起。通信项里与 N 相关的主项是延迟项；带宽项在 decode 下可忽略，且它的 N 依赖是 (N−1)/N→1（饱和），所以近似取常数。于是

T(N)≈NA​+cN,c=2L⋅2α(环形),c=2L⋅2⌈log2​N⌉α(树形，近似取 logN≈const)

对 N 求导置零：

−N2A​+c=0⟹N∗=cA​​​

而最小时间 T(N∗)=2Ac​，且此时两项恰好相等：

N∗A​=cN∗⟺访存时间=通信时间

这就是"收益条件"的精确形式：当拆卡省下的访存时间还不够付新增加的通信时间时，继续拆就是负收益。

3.2 数值：NVLink 与 InfiniBand 的差别在哪#

固定口径：A=(2Ψ+KVb=1​)/B=4.382 ms，环形 c=2L⋅2α=4Lα。

互连 α β c N∗=A/c​ 说明
NVLink（域内） 5μs 450 GB/s 0.640 ms 2.62 → 取 4 域内延迟极低，但通信项仍不容小觑
IB（跨机） 10μs 25 GB/s 1.280 ms 1.85 → 取 2 延迟翻倍，最优立刻退到 2
IB + 拥塞（α 实测 20 μs） 20μs 25 GB/s 2.560 ms 1.31 → 取 1~2 跨机 TP 直接不成立

逐行读：

  • NVLink 下 N∗=2.6 —— 意味着"N 取 2 或 4"都在最优点附近，因为 T(N)=A/N+cN 在极值附近是平的（T(2)=2.83 ms、T(4)=3.02 ms，差 7%）。所以"经验值 8"其实是错的：在这个口径下 N=8 已经比 N=2 慢 78%。
  • 跨机时 N∗<2 —— 跨机 TP 从账面上就不成立。它有时仍被采用，原因是"显存装不下"（容量约束，不是时间约束）。这是一个必须区分的动机：为时间而拆，与为容量而拆，判据完全不同（见 3.4）。
  • α 从 5μs 涨到 20μs（拥塞、跨 NUMA、共享网卡）会把 N∗ 从 2.62 打到 1.31。所以在实测里看到"TP 越大越慢"，先量 α，再怀疑别的。

3.3 为什么 N∗ 与模型大小的关系比直觉弱#

A∝Ψ、c∝L，而 Ψ≈12LH2+VH。对大模型：

N∗≈4Lα2Ψ/B​​≈4LαB2⋅12LH2​​=HαB6​​

N∗≈4Lα2Ψ/B​​≈4LαB2⋅12LH2​​=HαB6​​

L 被消掉了。 所以决定最优并行的主要是隐藏维 H（即层的"宽度"），不是层数。H 从 4096 涨到 8192，N∗ 翻倍；层数翻倍则 N∗ 不变。

这条推论解释了为什么"70B 用 TP=8、7B 用 TP=2"这类说法在数量级上合理但对不齐：真正该看的是 H。（70B 级模型 H=8192，N∗≈5.2；7B 级 H=4096，N∗≈2.6。）当然真实阈值会被 b、s、KV 与 kernel 效率修正 —— 但起点是这个式子，不是"经验值"。

3.4 两种拆卡动机：为时间 vs 为容量#

这是必须显式区分的一处，因为它们的判据完全相反：

动机 约束 判据 越界的后果
为时间（降 TPOT） T(N)<T(1) N<2N∗（超出后比不拆还慢） 直接变慢
为容量（装得下） ΨB​/N+KV≤HBM N≥⌈ΨB​/(HBM−KV)⌉ 跑不起来

示例：2Ψ=12.24 GiB，H100 80 GB 扣掉 KV 与激活留出 60 GB，N=1 完全装得下 → 容量动机不成立。所以对这个模型，"上 TP"唯一正当的理由是时间，而时间账算出 N∗≈2.6。

只要容量允许，就不要为了"看起来更快"把 TP 加上去；先算 N∗​

四、batch 与 prefill 如何改变结论#

4.1 batch 会同时放大两项，但方式不同#

KV 项随 b 线性涨（加进 A），通信次数不变、每次消息随 b 线性涨（带宽项涨）。代入 b∈{1,8,32,128,512}、N=8：

b 访存 Tmem​ 通信 Tcomm​ 比值
1 0.548 ms 4.482 ms 8.18
8 0.548 ms 4.496 ms 8.20
32 0.549 ms 4.545 ms 8.28
128 0.553 ms 4.741 ms 8.57
512 0.570 ms 5.524 ms 9.69

读法：b 从 1 涨到 512，访存只涨 4%（权重是常数项、KV 还很小），通信涨 23%（延迟项不变、带宽项开始有感）。比值几乎不动 —— 所以在 N=8 这种"已经拆过头"的配置上，加大 batch 救不回来。

那 batch 什么时候能救回来？回到 A=(ΨB​+KV(b))/B 与 c 的结构：N∗(b)=A(b)/c(b)​。当 b 大到 KV 项主导时（b≳2000 量级，此时 I≈b 已超过拐点、算力接管），模型形态变了，Tflop​ 不能再忽略。结论是：

增大 batch 到拐点之前，N∗ 几乎不变；超过拐点后问题变成"算力够不够"，不再是"访存够不够"

增大 batch 到拐点之前，N∗ 几乎不变；超过拐点后问题变成"算力够不够"，不再是"访存够不够"

这解释了第 2 章为什么会把"连续批处理把 batch 推大"与"少用 TP"绑在一起看。

4.2 prefill：同一个 N∗ 公式给出完全不同的答案#

prefill 阶段 b⋅s 大（例如 b=32,s=2048 时消息 Sσ​=32⋅2048⋅4096⋅2=512 MB），于是带宽项 2NN−1​βSσ​​ 从 μs 级跃到 ms 级：

  • N=8、NVLink：带宽项 =2⋅87​⋅512MB/450GB/s=1.99 ms，延迟项仍是 70μs → 带宽项主导 28 倍；
  • 此时 α 与 β 同时重要，prefill 的并行账要两项都算。

⚠️ 但不要把 prefill 的结论用到 TPOT 上：prefill 是每请求一次、decode 是每 token 一次。混用会得出"TP 值得拆到 8"的错误结论（对 decode 而言）。

4.3 与计算重叠：把 c 而非 A 压下去#

上面的模型假设通信完全串行。真实引擎会把通信切成 chunk 并与相邻层的计算重叠（distributed-training-systems 第 4 章第 2 节）。重叠的效果不是把 c 变 0，而是把 c 里能被计算掩盖的部分扣掉：

ceff​=max(0,c−η⋅Tcompute​)

其中 η 是可重叠比例。在 decode 下 Tcompute​≪Tmem​ 且通信在关键路径上（下一层要用它），所以 η 很小；在 prefill 下 η 可以接近 1。这把第 3.2 节的表整体左移 —— 但不会改变 N∗∝A/c​ 的形式，只是把 c 换小、N∗ 变大。工程上看到"实测 TP=8 比账面好"，十有八九是重叠与算法选择在起作用。

4.4 取舍：什么时候该放弃 TP，改用别的旋钮#

情形 该动的旋钮 为什么不是 TP
吞吐不够、延迟有余 加副本（DP）、加大 batch DP 不动关键路径
延迟不够、容量有余 权重低精度（fp8/int4）、speculative decoding、算子融合 它们直接压 A，不引入 c
容量不够 TP 或 PP（或 offload） 只有它们减单卡权重
序列很长、KV 主导 KV 分页 / 量化 / 驱逐（第 2 章） TP 对 KV 的收益是 ∝1/N，但通信是 N

这张表的读法：TP 是唯一同时"减权重访存"和"增加关键路径通信"的旋钮，所以它是唯一需要先算 N∗ 的旋钮。其他旋钮要么不碰关键路径（DP、batch），要么只减不减加（低精度、融合）。

代码：α-β 账本与最优并行度求解器#

下面的脚本只用标准库，做四件事：(1) 建立模型与硬件的成本口径；(2) 实现环形与树形全归约的 α-β 模型并打印"延迟 vs 带宽"拆解；(3) 扫 N 得到 token/s 曲线并数值求最优；(4) 用闭式解交叉验证，并打印"为时间"与"为容量"两套判据。

"""
推理并行的 α-β 账本与最优并行度（只用 Python 标准库）。

设计决策：
  1. 口径统一为「每 token」：凡是每 token 都要付的成本（权重访存、层内通信）
     才进这个账本；请求级的一次性成本（HTTP、调度、tokenize）明确排除 ——
     混用口径是这类估算最常见的错误（正文 1.1）。
  2. 通信项同时给环形与树形两种算法，因为差值就在 α 项上（O(N) vs O(log N)）。
     这一项直接决定"换算法"和"换卡数"哪个收益大（正文 2.3）。
  3. 显式区分「为时间而拆」与「为容量而拆」两套判据（正文 3.4），
     因为两者的不等式方向相反，混着看必然给出错误建议。
  4. 所有硬件参数都是示例量级（H100/NVLink/IB），请换成你的实测值；
     脚本只做解析账，不做实测 —— 实测方法见本章第 2 节的 nccl-tests 口径。
"""
from math import ceil, log2, sqrt

# ==================== (1) 模型与硬件口径 ====================
class Model:
    """一个 6.57B 级 decoder-only 模型的示例配置。"""

    def __init__(self, layers=32, hidden=4096, n_kv_heads=8, head_dim=128,
                 vocab=32000):
        self.L, self.H, self.NKV, self.DH, self.V = \
            layers, hidden, n_kv_heads, head_dim, vocab

    @property
    def params(self):
        """12·L·H²（注意力 + MLP）+ V·H（词表）。"""
        return self.L * 12 * self.H ** 2 + self.V * self.H

    def weight_bytes(self, dtype_bytes=2):
        return self.params * dtype_bytes

    def kv_bytes_per_token(self, dtype_bytes=2):
        """2(K 与 V) · L · n_kv · d_head · 1(token) · dtype。"""
        return 2 * self.L * self.NKV * self.DH * dtype_bytes


class Hardware:
    """示例：单卡 HBM 带宽、bf16 稠密算力、互连的 α 与 β。"""

    def __init__(self, hbm_bw=3.0e12, flops=989e12,
                 alpha=5e-6, link_bw=450e9, hbm_cap=80 * 2 ** 30):
        self.hbm_bw, self.flops = hbm_bw, flops
        self.alpha, self.link_bw = alpha, link_bw
        self.hbm_cap = hbm_cap

    @property
    def knee(self):
        """roofline 拐点（FLOP/byte）：低于它 → 访存瓶颈。"""
        return self.flops / self.hbm_bw


# ==================== (2) 全归约的 α-β 模型 ====================
def allreduce(N, n_bytes, hw, algo="ring"):
    """
    返回 (总时间, 延迟项, 带宽项, 步数)。
      ring: 2(N-1) 步，每 rank 发送 2(N-1)/N 字节（reduce-scatter + all-gather）
      tree: 2·ceil(log2 N) 步，带宽项取同样的紧下界 (N-1)/N
    """
    if N <= 1:
        return 0.0, 0.0, 0.0, 0
    if algo == "ring":
        steps = 2 * (N - 1)
        bw_bytes = 2 * (N - 1) / N * n_bytes
    else:                                   # tree / recursive-doubling
        steps = 2 * int(ceil(log2(N)))
        bw_bytes = 2 * (N - 1) / N * n_bytes
    lat = steps * hw.alpha
    bw = bw_bytes / hw.link_bw
    return lat + bw, lat, bw, steps


def decode_time(model, hw, N=1, batch=1, seq=1, dtype=2, algo="ring",
                ars_per_layer=2):
    """
    返回一个 dict：各分项与合计（秒/token）。
    ars_per_layer=2 是 Megatron-LM 口径：MLP 输出投影 + 注意力输出投影各一次。
    """
    w = model.weight_bytes(dtype) / N
    kv = model.kv_bytes_per_token(dtype) * seq * batch
    t_mem = (w + kv) / hw.hbm_bw
    t_flop = 2 * model.params * batch / (N * hw.flops)
    S = batch * model.H * dtype                       # 每次全归约的字节数
    t_ar, lat, bw, steps = allreduce(N, S, hw, algo)
    t_comm = model.L * ars_per_layer * t_ar
    return {"T_mem": t_mem, "T_flop": t_flop, "T_comm": t_comm,
            "T_total": max(t_mem, t_flop) + t_comm,
            "lat_share": lat / t_ar if t_ar else 0.0,
            "comm_share": t_comm / (max(t_mem, t_flop) + t_comm),
            "steps": steps, "S": S}


# ==================== (3) 闭式最优与两种判据 ====================
def optimal_N(model, hw, batch=1, seq=1, dtype=2, algo="ring"):
    """
    T(N) = A/N + c·N  →  N* = sqrt(A/c)，且最优点满足「访存时间 = 通信时间」。
    A = (权重字节 + KV 字节)/B ；c = L·ars·steps_per_N·α
    """
    A = (model.weight_bytes(dtype) + model.kv_bytes_per_token(dtype) * seq * batch) \
        / hw.hbm_bw
    coeff = 2 if algo == "ring" else 2          # α 密集度：环形 2(N-1)，树形 2log2N
    if algo == "ring":
        c = model.L * 2 * coeff * hw.alpha
    else:
        # 树形 c 随 N 变，用 log2 在当前 N 的斜率近似；给一个保守估计：2·log2(8)=6
        c = model.L * 2 * 2 * 3 * hw.alpha
    N = sqrt(A / c)
    return N, A, c, 2 * sqrt(A * c)


def capacity_N(model, hw, dtype=2, reserve=12 * 2 ** 30):
    """为容量而拆所需的最小 N：单卡权重 + 预留 ≤ 显存。"""
    avail = hw.hbm_cap - reserve
    return max(1, int(ceil(model.weight_bytes(dtype) / avail))), avail

四处关键设计决策：

  1. 口径严格限定为"每 token"。decode_time 里没有 HTTP、调度、tokenize 的任何项 —— 它们属于 TTFT（第 2 章）。一个把请求级成本混进 TPOT 的账本，会系统性高估通信占比、得出"TP 没用"的错误结论。
  2. 同时实现环形与树形，并在输出里把"延迟/带宽"比打出来。这个比值是本节的诊断工具：它 >100 时，"合并消息、压缩激活"这类带宽侧优化基本无效，只该优化步数。
  3. optimal_N 返回 (N∗,A,c,Tmin​) 四个量而不是一个 N∗，因为数值最优点附近曲线是平的（T(2)=2.83 vs T(4)=3.02），只报一个整数会掩盖"这段区间内怎么选都差不多"这个事实。
  4. capacity_N 单独成函数，与 optimal_N 并列。这是正文 3.4 的结构化表达："为时间"与"为容量"是两套方向相反的不等式，代码里也不该混在一起。

小结#

  • 推理并行必须用"每 token"口径核算：T(N)=A/N+2L⋅TAR​(N)，其中 A=(ΨB​+KVB​)/B。请求级成本属于 TTFT，混进 TPOT 账本会系统性高估通信占比。
  • 通信有两项，性质完全不同：延迟项 ∝ 步数 ×α，带宽项 ∝ 字节 /β。在 decode 形态（8 KiB 消息）下，延迟项比带宽项大 3 个数量级（N=8 时 2197×）。所以"合并消息/压缩激活"基本无效，只该优化步数。
  • 下界：每 rank 至少接收 NN−1​Sσ​（紧），至少 ⌈log2​N⌉ 轮（紧）。环形算法带宽上只差 2 倍、延迟上差 O(N/logN)。"换更好算法"赢的是 α 项 —— 树形全归约把 N=8 的 token/s 从 199 抬到 405（2.04×）。
  • 收益条件有闭式解：N∗=A/c​，最优点处访存时间 = 通信时间。T(N)=A/N+cN 在极值附近是平的，所以"2 还是 4"差别很小，而"8"可能已经比"1"慢。
  • N∗ 主要由隐藏维决定：N∗≈H6/(αB)​，层数 L 被消掉。所以"70B 用 TP=8、7B 用 TP=2"的数量级关系来自 H 的差别，不是来自参数量的直接比例。
  • 必须区分两种拆卡动机：为时间（判据 N<2N∗）与为容量（判据 N≥⌈ΨB​/(HBM−KV)⌉）。方向相反，混着看必然给出错误建议。 示例模型容量上不需要 TP，所以它的 TP 完全由时间账决定。
  • batch 在拐点之前救不回被通信吃掉的收益：b 从 1 到 512，N=8 时的通信/访存比只从 8.18 涨到 9.69。
  • prefill 与 decode 要分开算：prefill 是带宽项主导（512 MB 消息时带宽项比延迟项大 28 倍）、可重叠；decode 是延迟项主导、在关键路径上。
  • 一句话："拆几张卡"不是一个经验值，而是一个关于 α、β、B、H 的不等式；先算 N∗，再决定拆不拆。
