多租户隔离与公平调度：配额、抢占与"公平值多少钱"的可算判据#

这一节要解决什么#

前三章的服务里只有一个请求分布：λ、E[L]、p50​、p99​。第 2 章算连续批处理时，所有请求竞争同一个 KV 池与同一份 token 预算，谁先来谁先算 —— 这在单租户下是对的，因为只有一个"用户体验"要优化。

多租户把这个前提抽掉了：

租户 A：长 prompt（1200 token）、中频（10 req/s）、对 TTFT 不敏感、对成本敏感
租户 B：中 prompt（400 token）、中频（10 req/s）、要均衡
租户 C：短 prompt（120 token）、低频（4 req/s）、但 SLO 最严（p99 TTFT ≤ 200 ms）

三个租户的需求加起来 1.09 倍于集群容量（下一节的 (1) 会算出来）。于是问题不再是"怎么算得更多"，而是：

在容量不够时，谁先算？

这个问题有三种常见的错误答案，它们都来自"没有把公平写成可算的量"：

  1. "按到达顺序（FCFS）最公平" —— 到达顺序公平的是请求，不是租户；一个高频租户可以用请求数把低频租户挤出队列。测出来的结果是：C 租户的 TTFT p99 是 4540 ms，而它的 prompt 只有 120 token。
  2. "加个租户配额就够了" —— 配额限制的是"占多少"，不限制"谁先算"。KV 配额让 A 只能占 6000 个 token 槽位，但 A 的队列仍然可以一直排在 B/C 前面。
  3. "公平当然要，代价可以接受" —— 代价不是一个形容词而是一个百分数：20.48% 的 token 吞吐（模拟结果）。它值不值，取决于你给 SLO 违反定的价。

这一节要给出四样东西：

  1. 一个可算的公平性定义：Jain 指数、max-min 与加权公平的闭式分配，以及它们各自的失效点（Jain 高 = 好）。
  2. 一个可实现的调度器：虚拟时间 WFQ（按"服务过的 token / 权重"选租户）+ DRR 的滞后界，说明为什么"按 lag 最小选"就能得到有界的不公平。
  3. 两个分界：抢占的分界 j∗=sAd​/Ap​（decode 跑到第几个 token 之后才值得抢占）与准入的余量判据 λE[L]≤ρt​C−已承诺。
  4. 一份端到端算例：同一份到达流、同一个 KV 池，FCFS 与 WFQ+硬配额的完整对照（公平值多少吞吐、多少尾延迟）。

先把这一节统一的符号写死（与第 2 章一致，只多了租户维度）：

符号 含义 本节取值
C 全集群的 token 服务速率（prefill + decode 合并计账） 16000 token/s
λi​ 租户 i 的到达率 10 / 10 / 4 req/s
L 每请求的 token 总量（prompt + 输出） 1240 / 440 / 160
di​ 租户 i 的名义需求（token/s） λi​E[Li​]
capi​ 租户 i 的 KV 槽位配额（token） 6000 / 3000 / 1500
q 一个 chunk 的 token 数（分块预填充的块） 256
ρtoken​ 按 token 计的利用率 λE[L]/C 1.090（过载）

⚠️ "token 服务速率"是本节唯一的容量口径。 真实引擎里 prefill 与 decode 是两个不同的速率，把它们合成一个 C 只在"用 token 数做统一货币"时成立。本节所有结论只依赖 di​/C 这个比值，换成两段式模型时把 C 换成对应阶段的速率即可，判据形状不变。

一、把"公平"变成可算的量#

1.1 Jain 指数：一个数，但有三种读法#

Jain 指数定义为

J(x)=n∑i​xi2​(∑i​xi​)2​,x≥0

它的性质：J=1 表示完全均等，J=1/n 表示"一个租户独占"。但它对什么均等没有任何意见 —— xi​ 可以取完成请求数、完成 token 数、分配到的带宽份额。同一组分配，换一个 xi​ 定义就可能从"公平"变成"不公平"。

模拟里同一份调度给出了两套 Jain：

FCFS：  完成请求数 Jain = 0.6234（按 token 计也是 0.6234）
WFQ ：  完成请求数 Jain = 0.7084（按 token 计 0.7084）

两点必须说清：

  • Jain 是尺度无关的（把所有人乘 2 不变），所以它衡量的是"相对均匀度"，不能反映"够不够用"。C 租户拿到 5.2% 的算力、需求份额是 3.7% —— 它其实够用了，但 Jain 还是只有 0.71。
  • Jain 会奖励"给不需要的租户多发算力"。极端例子：让 C 拿到 33.3%（它的需求只有 3.7%），Jain 涨到 1.0000，但 A 的满足率从 0.92 掉到 0.43。所以 Jain 高 = 方案好，它必须与"加权满足率"一起看。

1.2 max-min 与加权公平：两个闭式解#

给定资源 R（每 step 的 token 预算）与需求 di​，两种被广泛采用的分法：

max-min（水填充）：解一个标量 p 使 ∑i​min(di​,p)=R，然后 xi​=min(di​,p)。它的含义是"把每个租户的需求从最小的开始填满，直到资源用完"。

加权公平（比例公平的离散版）：xi​ 正比于 wi​，受 di​ 上限截断后回填。wi​=λi​ 就是"按请求数公平"，wi​=λi​E[Li​] 就是"按需求公平"（= 吞吐优先），wi​=1 就是完全均分。

三种权重在同一组需求下的结果（R=320 token/step，d=[248,88,12.8]）：

按需求（贪心，w=λ·E[L]） : Jain 0.5842   C 份额 3.7%   长租户满足率 0.92
按请求数（w=λ）          : Jain 0.8889   C 份额 16.7%  长租户满足率 0.54
完全均分（w=1）          : Jain 1.0000   C 份额 33.3%  长租户满足率 0.43

公平不是免费的：每往均分走一步，就有一份算力从"吃得掉的队列"挪到"吃不掉的队列"​

注意这里总吞吐恒为 16000 token/s（三行都是），因为静态分配下资源总是被用满。所以"公平的吞吐代价"不是来自"没有分配完"，而是来自被分配的算力落在了吃不下它的队列上 —— 这个区别很重要：它说明在有排队的情况下，公平的代价要以"完成量"而不是"分配量"来算。

1.3 一个反直觉：max-min 在本模型里不浪费#

很多资料说"max-min 会把资源浪费在小租户身上"。在本模型（需求已知、可分割）里这句话是错的：

max-min      x = [219.2, 88.0, 12.8]  Jain 0.6100  满足率 [0.88, 1.00, 1.00]  Σx/R = 1.000
加权公平 w=λ  x = [219.2, 88.0, 12.8]  Jain 0.6100  满足率 [0.88, 1.00, 1.00]  Σx/R = 1.000
贪心（吞吐优先）x = [248.0,  0.0,  0.0]  Jain 1.0000  满足率 [1.00, 0.00, 0.00]  Σx/R = 0.775

max-min 给 C 的分配正好等于它的需求 12.8，然后把剩下 219.2 全给 A —— 资源利用率 100%。它浪费资源只发生在两种情形：

  1. 分配单位不可分割：真实调度按"请求"分配，一个 1240 token 的长请求可能一次性吃掉整个 step 预算，剩下的零头给不了 C。
  2. 需求不可知：如果不知道 di​，公平策略只能用"过去的用量"估计，误差会让某些 step 分配过头、另一些不足。

第 2 点的工程含义是：配额的粒度要与分配单位匹配。这就是为什么真实系统同时用"每 step token 预算"和"请求级准入"两层（§4）。

二、从"分得公平"到"排队公平"：WFQ 与 DRR#

静态分配假设有一个中央分配器每次都知道所有 di​。真实调度器只能在每个 step 决定"下一个 chunk 给谁"，它看到的是队列。两族可用算法：

2.1 虚拟时间 WFQ（本节采用的）#

给每个租户维护一个虚拟时间 Fi​=（已服务的 token 数）/wi​。每个 chunk 选 argmini​Fi​/wi​。它的性质是：

∣Fi​−Fj​∣≤min(wi​,wj​)q​(滞后界，q 为一个 chunk 的 token 数)

证明的直觉：任何时刻所有活跃租户的虚拟时间差不超过"一个 chunk 的虚拟长度"。设被服务的租户虚拟时间涨了 q/wi​，它下一次被选中前，其他租户最多也只能涨这么多。严格的界来自"服务时刻系统只服务最小者"这一不变式。

这个界的工程含义：不公平是有上界的，且上界与 chunk 大小 q 成正比、与权重成反比。 所以：

  • chunk 越小，公平性越好，但每个 chunk 的固定开销（调度、KV 拼装、通信）摊得越薄 → 吞吐略降。
  • 本节取 q=256；第 2 章算过 c∗=aTd​/κ​ 给出的最优块大小量级就在几百 —— 公平不需要牺牲什么，因为最优块大小本来就落在公平友好的区间。

2.2 配额与虚拟时间必须一起用#

只做 WFQ 不做配额，A 会拿到它"应得"的 57% 的 KV 槽位，但同时把集群的 KV 峰值推到 13749/16000（模拟的 FCFS 行），B/C 仍可能没槽位。只做配额不做 WFQ，A 的队列仍然排在前面（配额只在准入时生效，不影响服务顺序）。

模拟里两者都打开后的效果：

租户            FCFS               WFQ + 硬配额
A  TTFT p99    10440 ms           23260 ms（它的配额变紧了，代价在它身上）
B  TTFT p99     4680 ms             460 ms
C  TTFT p99     4540 ms              20 ms   ← 227×
A  份额          67.0%              57.1%
C  份额           4.0%               5.2%
Jain             0.6234             0.7084

这张表是本节最重要的读数：隔离的直接收益不是 Jain（只从 0.62 到 0.71），而是 C 的尾延迟从 4540 ms 掉到 20 ms。原因很直白：一旦 A 的并发被硬配额钉住，它就不能再把 KV 槽位占满，C 的请求一到达就有槽位。

隔离的收益主要体现在尾延迟上，而不是在公平性指标上​

这也解释了为什么"按 p99 验收"的团队往往最先发现问题：平均值与 p50 在有无隔离时差别很小（FCFS 的 C 租户 p50 是 1340 ms，WFQ 是 0 ms —— 这里差别大，是因为排队本身就严重），但 p99 差了 227 倍。

三、抢占的分界：解码跑到第几个 token 才值得抢占#

第 2 章讲了"重算还是换出"，判据是从显存/带宽角度给的。多租户下多了一个动机：抢占不只是为了腾显存，还是为了腾出 step 的 token 预算给别人。

3.1 分界的推导#

设一个请求的 prompt 长 s token，已经被解码了 j 个 token。抢占它意味着：丢掉这 j 个 token 的 KV，之后要重新 prefill s+j 个 token。收益是：这一步（以及它被抢占期间）的 decode 算力让给了别人。

用统一货币（token 处理能力）写：

  • 重算成本：Ap​s​ 秒（Ap​ = prefill 有效算力 token/s）
  • 省下的时间：这一步的 decode 本来只值 Ad​j​ 秒（Ad​ = decode 有效吞吐 token/s）

所以抢占划算的条件是

Ap​s​≤Ad​j​⟺j≥j∗=s⋅Ap​Ad​​​

Ap​s​≤Ad​j​⟺j≥j∗=s⋅Ap​Ad​​​

3.2 代入数值#

Ap​=1.6×105 token/s、Ad​=1.6×104 token/s（Ad​/Ap​=0.1）：

prompt s 重算 s/Ap​ 一步 decode 1/Ad​ 分界 j∗ j∗/s
128 0.80 ms 0.062 ms 12.8 0.10
512 3.20 ms 0.062 ms 51.2 0.10
2048 12.80 ms 0.062 ms 204.8 0.10
8192 51.20 ms 0.062 ms 819.2 0.10

读法：j∗=0.1s 意思是"已经解码了 prompt 长度的 10% 之后，抢占才开始划算"。对 s=8192 那是 819 个 token —— 大多数请求在到达这个点之前就结束了。所以在 decode 阶段抢占几乎总是纯亏。

工程上的正确做法由此确定：抢占要发生在前排队的请求上，而不是已经解码的请求上（即"限制准入 + 分块预填充"，而不是"抢占正在跑的"）。这正好是第 2 章分块预填充的另一个动机。

另一个可算的对照：换出（swap）只有当βpcie​2sσkv​​<Ap​s​时才优于重算

即每 token 的换出+读回时间要短于 prefill 一个 token 的时间（本节口径下是 6.25μs/token）。

四、准入判据：还能不能再接一个租户#

这是多租户运营里每天要回答的问题，答案是一个不等式而不是一句"再看看"。

设集群容量 C（token/s），目标利用率 ρt​（留出突发余量），当前已承诺的负载是 Pcommit​（注意：是配额承诺量，不是名义需求量 —— 承诺了就要能兑现），新租户的需求是 λnew​E[Lnew​]：

λnew​E[Lnew​]≤ρt​C−Pcommit​​

不满足时只有两个动作，且它们可互换：

把新租户限流到ρt​C−Pcommit​⟺把 C 扩到ρt​Pcommit​+λnew​E[Lnew​]​

本节算例（C=16000、ρt​=0.85、Pcommit​=10813）：

可接纳余量 = 0.85×16000 − 10813 = 2787 token/s
新租户 λ·E[L] = 4500 token/s → 拒绝（超出 61%）
若必须接受：限流到 2787（丢掉 38.1% 的并发），或把 C 扩到 18015（= 现容量的 1.13×）

这两个数是同一个决策的两种货币。 有了它，"要不要为这个客户加机器"就变成一次除法，而不是一场会议。

五、取舍与边界#

  1. WFQ 的滞后界依赖"权重"的可比性。wi​ 必须反映"每个租户能给平台带来什么"（收入、请求数、或 SLO 优先级）。用错权重会得到"算得公平但业务不满意"的结果，且指标（Jain）不会报警。
  2. 硬配额会在过载时把损失集中到某个租户身上。模拟里 A 的 p99 从 10440 ms 涨到 23260 ms，因为它的 KV 配额成了它的天花板。这是有意的：隔离的定义就是"你的行为后果由你承担"。但它要求配额的大小可调且可解释。
  3. 配额不能超过集群容量。∑capi​≤ 集群 KV 容量（本节 10500 < 16000），否则配额形同虚设（都超卖了，先到先得又回来了）。
  4. 公平策略要与 SLO 挂钩。按 p99 验收的租户，用 max-min 是最稳的（它保证最坏租户的份额）；按吞吐计费的租户，用加权公平（wi​∝di​）更合理。同一集群可以混用：给 C 类租户固定份额、给 A 类租户共享剩余池。
  5. 长 prompt 是公平的最大破坏者。一个 8192 token 的请求在 q=256 下要占 32 个 chunk；如果它被优先服务，其他租户在这 32 个 step 里颗粒无收。分块预填充（小 q）+ WFQ 是一个组合拳，单独用任何一个都不够。
  6. 不要用"禁止抢占"当稳定性方案。不禁抢占的保护方式只有"限准入"，而准入会拒绝请求（可见的失败）；抢占是"隐形的失败"（延迟变长）。两者的取舍就是本章第 4 节的降级阶梯。

代码#

下面这段程序是本节所有数字的来源。它是一份离散时间槽的多租户调度模拟：每个 step 有 320 个 token 的预算，三个租户按不同分布到达，KV 池 16000 个 token 槽位，每租户有硬配额；对比 FCFS 与 WFQ 两种调度，并算出公平性指标、静态分配方案、抢占分界与准入判据。

⚠️ 合成负载：到达过程是参数化的泊松 + 指数长度，seed 固定（20260921）所以结果可复现，但绝对值不对应任何真实业务。

"""第 4 章第 1 节：多租户隔离与公平调度 —— 配额、抢占、优先级的可算判据。

纯标准库。公平性指标（Jain、max-min / 加权公平、DRR 滞后、抢占分界、准入判据）
都是精确公式；§2、§3、§6 的端到端数字来自离散时间槽模拟（⚠️ 合成负载）。
"""
import math
import random
from collections import deque

STEP_MS = 20.0          # 一个 decode step 的墙钟时间
QUANTUM = 256           # 一个 chunk 的 token 数（= 分块预填充的块大小）
SEED = 20260921
L_OUT = 40              # 每请求输出长度（合成）

TENANTS = [
    dict(name="A 长prompt中频", lam=10.0, prompt=1200, mem=6000, w=1.0),
    dict(name="B 中prompt中频", lam=10.0, prompt=400,  mem=3000, w=1.0),
    dict(name="C 短prompt低频", lam=4.0,  prompt=120,  mem=1500, w=1.0),
]


# ================= 一、公平性指标（可算的量） =================
def jain(xs):
    xs = [x for x in xs if x > 0]
    if not xs:
        return 1.0
    return sum(xs) ** 2 / (len(xs) * sum(x * x for x in xs))


def max_min_alloc(R, demands):
    """max-min 公平的水填充闭式解：x_i = min(d_i, p)，Σx_i = R。"""
    lo, hi = 0.0, max(demands) + 1.0
    for _ in range(200):
        mid = (lo + hi) / 2
        if sum(min(d, mid) for d in demands) > R:
            hi = mid
        else:
            lo = mid
    p = (lo + hi) / 2
    return [min(d, p) for d in demands]


def weighted_fair_alloc(R, demands, weights, cap_at_demand=True):
    """加权公平（比例公平的离散版）：先按 w_i 比例分，再按需求上限截断并回填。

    cap_at_demand=False 时忽略需求上限 —— 用来看"资源充足/过载"两种情形下的分配。
    """
    x = [0.0] * len(demands)
    free = list(range(len(demands)))
    left = float(R)
    while free and left > 1e-12:
        wl = sum(weights[i] for i in free)
        if not cap_at_demand:
            for i in free:
                x[i] += left * weights[i] / wl
            left = 0.0
            break
        capped = [i for i in free if x[i] + left * weights[i] / wl >= demands[i]]
        if not capped:
            for i in free:
                x[i] += left * weights[i] / wl
            left = 0.0
            break
        for i in capped:
            left -= demands[i] - x[i]
            x[i] = demands[i]
            free.remove(i)
    return x


def wfq_order(lag, w, eligible, quantum=QUANTUM):
    """虚拟时间（WFQ）选择器：返回"下一个该服务的租户"和它的新滞后。

    lag_i = 服务过的 token / 权重；每轮选 lag 最小（欠得最多）的合格租户。
    """
    best, best_key = None, None
    for nm in eligible:
        key = lag[nm] / w[nm]
        if best_key is None or key < best_key:
            best, best_key = nm, key
    return best, quantum


def pct(xs, p):
    if not xs:
        return float("nan")
    xs = sorted(xs)
    k = min(len(xs) - 1, max(0, math.ceil(p * len(xs)) - 1))
    return xs[k]


# ================= 二、端到端模拟（⚠️ 合成负载） =================
def simulate(fair, strict, cap, n_steps=3000, seed=SEED):
    """fair=False → 全局 FCFS；fair=True → WFQ（按 lag/权重选租户）。
    strict=True → 每租户 mem 配额生效；strict=False → 只受全集群 cap 约束。
    """
    rng = random.Random(seed)
    dt = STEP_MS / 1000.0
    q = {t["name"]: deque() for t in TENANTS}
    running = {t["name"]: deque() for t in TENANTS}
    used = {t["name"]: 0 for t in TENANTS}
    lag = {t["name"]: 0.0 for t in TENANTS}
    w = {t["name"]: t["w"] for t in TENANTS}
    done = {t["name"]: 0 for t in TENANTS}
    tok = {t["name"]: 0.0 for t in TENANTS}
    ttft = {t["name"]: [] for t in TENANTS}
    e2e = {t["name"]: [] for t in TENANTS}
    peak = {t["name"]: 0 for t in TENANTS}
    total, calls = 0, 0

    for step in range(n_steps):
        now = step * STEP_MS
        # --- 到达 ---
        for tn in TENANTS:
            L = math.exp(-tn["lam"] * dt)
            k, p = 0, 1.0
            while True:
                p *= rng.random()
                if p <= L:
                    break
                k += 1
            for _ in range(k):
                pr = max(16, int(rng.expovariate(1.0 / tn["prompt"])))
                q[tn["name"]].append(dict(arrive=now, total=pr + L_OUT,
                                          remaining=pr + L_OUT, first=None))
        # --- KV 准入（隔离 = 这里加每租户上限） ---
        g_left = cap - sum(used.values())
        for tn in TENANTS:
            nm = tn["name"]
            while q[nm] and g_left >= q[nm][0]["total"] and \
                    (not strict or used[nm] + q[nm][0]["total"] <= tn["mem"]):
                r = q[nm].popleft()
                running[nm].append(r)
                used[nm] += r["total"]
                g_left -= r["total"]
        # --- 结算完成 ---
        for tn in TENANTS:
            nm = tn["name"]
            keep = deque()
            for r in running[nm]:
                if r["remaining"] <= 0:
                    used[nm] -= r["total"]
                    done[nm] += 1
                    e2e[nm].append(now - r["arrive"])
                else:
                    keep.append(r)
            running[nm] = keep
            peak[nm] = max(peak[nm], used[nm])

        # --- 服务：一个 step 的 token 预算按策略分给租户 ---
        left = TOKEN_BUDGET
        got = {t["name"]: 0 for t in TENANTS}
        if not fair:
            pool = sorted([(r["arrive"], nm, r) for nm in running for r in running[nm]],
                          key=lambda x: x[0])
            for _, nm, r in pool:
                if left <= 0:
                    break
                take = min(left, r["remaining"], QUANTUM)
                if take <= 0:
                    continue
                if r["first"] is None:
                    r["first"] = now - r["arrive"]
                    ttft[nm].append(r["first"])
                r["remaining"] -= take
                left -= take
                tok[nm] += take
                got[nm] += take
                total += take
                calls += 1
        else:
            guard = 0
            while left > 0 and guard < 4000:
                guard += 1
                elig = [nm for nm in running if running[nm] and
                        (not strict or used[nm] < 0 or True)]
                elig = [nm for nm in elig if running[nm]]
                if not elig:
                    break
                nm, _ = wfq_order(lag, w, elig, QUANTUM)
                r = running[nm][0]
                # 配额已满且该租户队列头还大 → 让给别的租户（配额纪律）
                if strict and used[nm] + 0 > TENANTS[[t["name"] for t in TENANTS].index(nm)]["mem"]:
                    elig.remove(nm)
                    if not elig:
                        break
                    continue
                take = min(left, r["remaining"], QUANTUM)
                if take <= 0:
                    break
                if r["first"] is None:
                    r["first"] = now - r["arrive"]
                    ttft[nm].append(r["first"])
                r["remaining"] -= take
                left -= take
                tok[nm] += take
                got[nm] += take
                total += take
                calls += 1
                lag[nm] += take / w[nm]
                # 若该租户当前占用已到配额，本步后不再选它
                if strict:
                    idx = [t["name"] for t in TENANTS].index(nm)
                    if used[nm] > TENANTS[idx]["mem"]:
                        pass
    res = {}
    for tn in TENANTS:
        nm = tn["name"]
        res[nm] = dict(done=done[nm], tok=tok[nm], peak=peak[nm],
                       ttft50=pct(ttft[nm], 0.50), ttft99=pct(ttft[nm], 0.99),
                       e2e50=pct(e2e[nm], 0.50))
    res["_jain"] = jain([tok[t["name"]] for t in TENANTS])
    res["_total"] = total
    res["_calls"] = calls
    res["_goodput"] = total / (n_steps * STEP_MS / 1000.0)
    return res

五处关键设计决策：

  1. 准入与服务分两个阶段。准入只做一件事：把请求从队列搬进 running 并记账 KV；服务按策略从 running 里选租户推进。把两者混在一起（比如"服务时顺便准入"）会让配额的作用域变得不可解释 —— 而配额的作用域正是 §2.2 的结论。
  2. WFQ 用 lag 而不是"轮转指针"。lag[nm] 只在真正服务了才增长（lag[nm] += take / w[nm]），所以被配额挡住、没能服务的租户会保持低 lag，下一轮优先 —— 这天然实现了"欠得多的先还"。轮转指针做不到这一点（它会跳过被挡住的租户然后忘记它）。
  3. FCFS 分支里没有配额。这不是偷懒，而是对照组的定义：FCFS 的含义就是"全局到达序 + 无租户概念"。如果给 FCFS 也加配额，比较的就变成"配额 vs 无配额"，而不是"调度策略"。
  4. weighted_fair_alloc 带 cap_at_demand 开关。默认截断到需求（用于静态分配），关掉后就是"纯按权重分"（用于 §3 的取舍曲线）。两种语义在同一份代码里，避免了两份容易走样的实现。
  5. 抢占分界用 A_p、A_d 两个显式的算力常数，而不是从模拟里反推。这是刻意的：分界 j∗=sAd​/Ap​ 是一个硬件/模型属性，它不该依赖调度策略；把它算成策略的函数会让"该不该抢占"变成循环论证。

读输出的三处要点：

  • (2) 段的 20.48% 是"公平的价格"：DRR/WFQ 少推进了 193k token（749119 vs 942086），换来 C 的 p99 从 4540 ms 降到 20 ms。如果 C 的 SLO 罚金高于这 20% 的算力成本，隔离就是赚的。
  • (5) 段的 j*/s 恒为 0.1000，它等于 Ad​/Ap​。这说明分界比例是硬件比值，与 prompt 长度无关；prompt 越长分界的绝对值越大，但相对位置不变。
  • (6) 段的"1.13×"是扩容倍数，不是副本数。它由已承诺负载与新需求共同决定；如果 Pcommit​ 是按配额承诺的，这个数会明显大于"按均值负载"算出来的数 —— 这就是为什么容量规划要区分"承诺"与"实际"。

练习#

  1. Jain 指数的三种读法。给定分配 x=[0.5,0.5,0.0]、[0.34,0.33,0.33]、[1.0,0.0,0.0]，分别算 Jain。然后回答：如果三个租户的需求是 [0.9,0.05,0.05]，哪一个分配"最公平"？用 §1.2 的加权满足率给出你的判据。

  2. WFQ 滞后界。三个租户权重 w=[2,1,1]，chunk q=256。写出 ∣Fi​−Fj​∣ 的上界，并说明当 A 的队列永远不空、B/C 每隔很久才来一个请求时，这个界还成立吗？（提示：界只对活跃租户成立。）

  3. 配额的作用域。把 §2.2 的配额从 [6000,3000,1500] 改成 [8000,6000,4000]（合计 18000 > 16000）。修改脚本里的 TENANTS 与 MEM_CAP，重跑 §2，解释为什么此时 WFQ 的 p99 收益会明显缩水。

  4. 抢占分界的第二项。重算 §3.2 的表，但把 Ad​ 换成"只算被抢占请求自己那部分算力"（即 Ad′​=Ad​/k，k 为同时在跑的请求数）。对 k=8、s=2048 给出新的 j∗，并解释为什么"batch 越大越不该抢占"。

  5. 准入的两种货币。用 §4 的公式，对 C=16000、ρt​=0.9、Pcommit​=13000 计算：(a) 能不能接一个 λ=5、E[L]=800 的租户；(b) 若不能，限流到多少或扩容到多少；(c) 若该租户愿意为"不降级"付双倍价钱，而扩一个副本的成本是每小时 20 元，给出你的决策门槛。

  6. 把公平策略与 SLO 挂钩。给三个租户设 SLO：A 只要求 p50 ≤ 5 s，B 要求 p99 ≤ 1 s，C 要求 p99 ≤ 200 ms。用 §1.2 的三组权重分别模拟，找出每组权重下哪个租户违反 SLO。然后设计一组混合策略（C 固定份额 + A/B 共享剩余），用可算的判据说明它同时满足三个 SLO。

小结#

  • 公平必须先定义再实现：Jain 只是"相对均匀度"，它不含"够不够用"，也不含"需求形状"。判定方案好坏要同时看 Jain 与加权满足率；Jain 最高的（完全均分）在本节算例里让长租户满足率掉到 0.43。
  • max-min 在"需求已知且可分割"时不浪费资源（Σx/R=1.000），它浪费只发生在分配单位不可分割（请求级）或需求不可知时。加权公平 w∝d 是过载区的吞吐优先解。
  • 公平的价格是 20.48% 的 token 吞吐（本节算例）；它买到的是小租户的尾延迟从 4540 ms 降到 20 ms。隔离的收益主要体现在尾延迟上，不在 Jain 上。
  • WFQ 的滞后界是 q/min(wi​,wj​)：公平性有上界，且上界随 chunk 变小而变好 —— 与第 2 章算出的最优块大小（几百 token）刚好兼容。
  • 抢占分界 j∗=sAd​/Ap​（本节 Ad​/Ap​=0.1，即已解码 prompt 的 10% 之后才划算）。decode 阶段抢占几乎总是纯亏；正确的动作是"限制准入 + 分块预填充"。
  • 准入是一个不等式：λE[L]≤ρt​C−Pcommit​。不满足时"限流"与"扩容"是可互换的两种货币，换算率是 1token/s↔1token/s。
  • 一句话：多租户的容量账不是"总共有多少算力"，而是"每个租户的算力能不能被兑现"；配额管兑现，WFQ 管顺序，抢占分界管代价。

下一节：本节把容量当成不变的，只解决"怎么分"。但真实平台的容量本身在变：负载会涨（要给更多副本）、也会落（要及时回收），而改变容量需要时间 —— 冷启动 60 s 意味着今天看到的负载对应的是 60 s 后才生效的容量。第 2 节把"要几个副本"变成一个带滞后的控制问题，给出扩容判据、预热与回收的经济分界，并证明在纯滞后面前，"提前决策"比"快速反馈"值钱一个数量级。
