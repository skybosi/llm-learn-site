这一节要解决什么#

前五章把推理系统的每一层都算清楚了：第 1 章的通信下界、第 2 章的调度与 KV、第 3 章的拓扑、第 4 章的弹性与 SLO、第 5 章的服务化壳。但它们都是给定条件算结论。真实项目的顺序是反的：

这中间的一步（"需求 → 架构"）在多数团队里靠经验和拍板，于是出现三类典型事故：

一、需求：三类硬约束 + 一个软约束#

1.1 SLO 必须同时给出两个数#

延迟 SLO 最常见的写法是错的："端到端 p99​≤ 1 s"。因为端到端是 TTFT 与 TPOT 的组合，而这两项由完全不同的部件决定：

端到端=排队+prefillTTTFT​​​+decode×长度(Pout​−1)⋅TTPOT​​​

把 1 s 摊在两处可以有无穷多种分法，而不同的分法对应完全不同的架构：

分法 TTFT TPOT 需要的优化
A 100 ms 9 ms prefill 优先（缓存、分块预填充）
B 500 ms 5 ms decode 优先（KV 压缩、权重量化）
C 100 ms 5 ms 两者都要（成本最高）

所以本节的口径是分开给：

TTTFT,p99​≤300 ms且TTPOT,p99​≤30 ms​

为什么这两个数不可互相折算：TTFT 由"请求进入系统到第一个 token"决定，其成本项是 prefill 算力 + 排队；TPOT 由"每个后续 token 的间隔"决定，其成本项是每步的内存带宽 + 固定开销。让 prefill 更快（加算力、开缓存）对 TTPOT​ 一点帮助都没有 —— 它们花的不是同一份资源。

1.2 吞吐与可用性：三个必须显式写出来的量#

量 记法 本节取值 为什么必须写出来
稳态到达率 λ 200 req/s 所有容量算式的自变量
峰值倍率 kpeak​ 2.5× 决定"扩副本"还是"限流"，第 3 节算
月度可用性 A 99.9% 换成错误预算 43.2 min/月，第 4 节算

"输出量"是最容易被漏掉的约束。真正决定成本的不是 λ，而是输出 token 速率：

Rout​=λ⋅Pout​=200×100=20,000 tok/s

它是 decode 侧的需求量；而前面给的是请求速率 λ。两者的比值 Pout​ 直接决定了"每卡能服务多少请求" —— 这也是为什么"输出长度"必须是需求的一部分，而不是上线后才知道的观测量。

1.3 预算：把软约束换成一个硬阈值#

给定预算上限 12,000 元/30 天，能反推出可接受的单位成本：

预算/产出=12,000 元/(20,000 tok/s×2592 ks)=0.23 元/1M token≈0.31 USD/1M

这个数在架构决策里非常有用：它把"要不要用更贵的方案"变成一个比较。如果某个方案算出 0.30 元/1M，那它就在预算内；算出 0.45 元/1M 就必须解释为什么值得超。

二、先把"单 token 的显存量"算成常数#

2.1 kvB​：一行公式决定后续一切#

注意力 KV cache 的每 token 字节数：

kvB​=2⋅nlayer​⋅nkv_head​⋅dhead​⋅bdtype​

代入本节的模型（GQA 8 个 KV 头是关键）：

kvB​=2×32×8×128×2=131,072 B=128 KiB/token

这个数必须与模型架构绑定，不能事后调。对比一下不做 GQA 的代价：

配置 nkv_head​ kvB​ 1700 token 的 KV
MHA（32 头） 32 512 KiB/token 870 MB
GQA（8 头） 8 128 KiB/token 218 MB
MQA（1 头） 1 16 KiB/token 27 MB

4 倍的差别在"并发上限"上会被放大：同样的 16 GB KV 预算，MHA 只能放 31 个 1700-token 的序列，GQA 能放 128 个。所以"kvB​ 是架构决策的第一颗扣子"这句话是字面意义上的：它决定了后面所有容量算式的量级。

2.2 权重与 KV 抢同一块显存#

每卡的显存分成三块，只有中间那块能放 KV：

Bkv​=24 GBVgpu​​​−权重W/TP​​−激活+workspace+框架Wact​​​

本节取 Wact​=1.5 GB（7B 模型 + 分页 KV 管理器的经验值）：

TP 权重/卡 Bkv​ bkv​（1700 token/序列） 有效并发槽
1 13.04 GB 9.46 GB 45.6 45.6
2 6.52 GB 15.98 GB 77.0 77.0
4 3.26 GB 19.24 GB 92.7 92.7

权重每减半，KV 容量翻倍​

这条性质解释了为什么"并行策略"与"并发容量"不是两件事：TP 越大 → 每卡权重越小 → KV 预算越大 → 能同时服务的序列越多。但它同时带来两个反向代价（通信、卡数），所以 TP 的选择是三方平衡 —— 第 3 小节算。

2.3 并发槽上限：bkv​ 与 qmax​ 取小#

bcap​=min(bkv​, qmax​)

  • bkv​：显存能放下多少并发序列（硬上限）。
  • qmax​：调度器允许的最大批（软上限，常由"每步固定开销要摊薄"或"抢占风暴"决定）。

为什么两个都要设：只设 qmax​ 会让显存不受控；只设 bkv​ 会让 batch 在显存允许时无限膨胀，把每步时间拉到 SLO 之外（第 2 节算）。本节的 qmax​=128 在 TP=2 下不是 binding 的（77 < 128），所以真正的上限是显存。

三、单卡吞吐：三个组成部分与一条单峰曲线#

3.1 把 tstep​ 拆成三项#

一步 decode 的时间由"读多少字节"和"要做多少 FLOPs"里更慢的那个决定，再加固定开销：

tstep​(b)=max(内存带宽cw​+bckv​​​, 算力TP⋅PEAK⋅MFU2Pb​​​)+T0​

用本节的数（TP=2，b=48.51）：

项 公式 数值 占比
读权重 cw​ Wgpu​/(BW⋅η) 2.985 ms 41.8%
读 KV bckv​ b⋅Lkv​kvB​/(TP⋅BWη) 1.152 ms 16.1%
固定开销 T0​ kernel 启动 + 采样 + 调度 3.0 ms 42.0%
算力项 2Pb/(TP⋅PEAK⋅MFU) 0.572 ms 8.0%（被 max 吃掉）
合计 7.143 ms

这张表就是"瓶颈在哪"的答案：算力项只有内存项的 1/7，说明这台服务是彻底的带宽受限，加算力（更高算力的卡、更好的 kernel）一点用都没有。

3.2 吞吐是 b 的单峰函数#

thr(b)=tstep​(b)b​=cw​+bckv​+T0​b​

对 b 求导取零：

dbd​thr=0 ⟹ b∗=ckv​cw​+T0​​​,thrmax​=ckv​+2ckv​(cw​+T0​)​1​

dbd​thr=0 ⟹ b∗=ckv​cw​+T0​​​,thrmax​=ckv​+2ckv​(cw​+T0​)​1​

代入本节：b∗=(2.985+3.0)/0.02376​=15.9（若不受显存限制），thrmax​ 随 bcap​ 单调增 —— 因为 bkv​=77.0>b∗ 时吞吐已经在下降段，所以单卡上限出现在 bcap​ 处：

thrmax​=2.985+77.01×0.02376+3.077.01​=9,846 tok/s

这条曲线的形状有两个工程含义：

  1. 吞吐随 batch 先增后减（"batch 越大越划算"在超过 b∗ 后是错的）。
  2. 要突破上限只能压 cw​ 或 ckv​：量化权重压 cw​，量化/压缩 KV 压 ckv​。这是第 4 节"优化清单"的全部理论基础。

3.3 最小卡数的下界#

Nmin​=thrmax​λPout​​=9,84620,000​=2.03 卡

注意这个下界与副本无关（副本是"卡数 / TP"的取整），而且它假设每卡都跑在吞吐最优点。真实系统还要满足 TTTFT​、TTPOT​ 与显存约束，所以实际卡数只会更多 —— 第 4 小节算。

4.2 为什么是这个排序：一张"每 token 卡时"的表#

延迟最优的 TP=4 每卡最快（10,192 tok/s），但它的卡数是 TP=1 的 1.6 倍。所以真正要比较的是单位成本：

每 token 卡时=btstep​(b)​ [卡时/token]

策略 tstep​/b 卡时/1M token 元/1M USD/1M
只算算力（忽略带宽） 0.042 ms 0.042 0.0088 0.0120
TP=2 bf16（稳态 48.51） 0.147 ms 0.530 0.1104 0.1492
TP=2 bf16（上限 bcap​） 0.102 ms 0.366 0.0762 0.1029
TP=2 FP8（上限） 0.073 ms 0.260 0.0542 0.0732

忽略带宽会把卡数低估 8.6× —— 这就是"按算力买卡"的典型错误​

为什么 TP=4 的每 token 成本不比 TP=2 低太多（0.0546 vs 0.0817，都在预算内）：TP 每加一路，cw​ 减半、ckv​ 减半，看起来是双重收益；但卡数同时翻倍，而 bkv​ 只翻倍（KV 预算变大），所以吞吐与卡数同比例增长 —— 单位成本趋平。TP 的收益来自"权重变小让 KV 预算变大"，而不是"算得更快"。

4.3 跨节点 TP：代价的准确量级#

TP 每层的 all-reduce 有确定性的通信量。按每步 4 次集合通信计：

tcomm​=BWtp​4(bdmodel​bdtype​/2+TP⋅Lseq​dhead​bdtype​/2)​

通道 节点内（NVLink 450 GB/s） 跨节点（IB 25 GB/s） 倍率
激活（b×4096×2） 0.002 ms 0.036 ms 18×
partial attention（小） 0.003 ms 0.05 ms 18×
合计（b=48.5） 0.005 ms 0.086 ms 18×

这个量级说明两件事：

  1. 节点内 TP 的通信开销可以完全忽略（0.005 ms / 7.143 ms = 0.07%），所以"TP 一定要在节点内"是对的，但原因不是"省了 0.005 ms"。
  2. 真正的理由是"跨节点会破坏 KV 预算的算术"：跨节点 TP 时每卡的 all-reduce 走 25 GB/s，而 bkv​ 受显存限制不变，于是 ckv​ 不变、cw​ 不变，只有 tcomm​ 涨 —— 单位成本涨、吞吐降。在第 3 章我们算过这个账；本节把它折算成了"每 token 卡时"的增量。

五、副本数：五个约束联立#

5.1 五个约束（全章统一）#

C1 吞吐C2 显存C3 prefillC4 TPOTC5 排队​:N⋅thr(b)≥λPout​:b≤bkv​=Bkv​/(Lseq​kvB​):N⋅rprefill​≥λLp99​(1−h):tstep​(b)≤TTPOTSLO​:Wp99​(ρ)+Tprefill​≤TTTFTSLO​,ρ=qmax​/sλ/N​​

C1 吞吐C2 显存C3 prefillC4 TPOTC5 排队​:N⋅thr(b)≥λPout​:b≤bkv​=Bkv​/(Lseq​kvB​):N⋅rprefill​≥λLp99​(1−h):tstep​(b)≤TTPOTSLO​:Wp99​(ρ)+Tprefill​≤TTTFTSLO​,ρ=qmax​/sλ/N​​

其中 s 是请求驻留时间，由 Little 定律与批大小自洽确定：

s=Tprefill​+Pout​tstep​(b),b=min(Nλ​s, bcap​)

这组方程必须联立解（而不是先估 b 再算 s）：b 越大 → tstep​ 越大 → s 越大 → 需求批 λs/N 越大。本节用不动点迭代解，收敛很快。

缓存还有一笔隐性收益本节没算：它把 Lp99​(1−h) 从 1600 降到 880，直接影响 C3 与 TTTFT​ —— 实测里缓存常常是让某个 N 变得可行的那个条件，而不是直接省钱（第 2 节的敏感性表给出了这个对比）。

ACT = 1.5 * GB
KV_B = 2 * LAYERS * KV_HEADS * HEAD_DIM * 2

REQ = dict(lam=200.0, lp50=800.0, lp99=1600.0, pout=100.0,
           ttft=300.0, tpot=30.0, qmax=128, h=0.45,
           ttft_budget=700.0, price=2.70, usd=0.74, node_gpus=4)


class Svc:
    """按"并行策略 + 精度 + 缓存"参数化的一台推理服务。"""

    def __init__(self, tp=2, wq=2, dtype_bytes=2.0, h=0.45, lam=200.0,
                 cross_node=False, **kw):
        self.tp, self.wq, self.dtype_bytes, self.h = tp, wq, dtype_bytes, h
        self.lam, self.cross_node = lam, cross_node
        self.__dict__.update({k: v for k, v in REQ.items() if k not in self.__dict__})
        for k, v in kw.items():
            setattr(self, k, v)
        self.w_gpu = P * self.dtype_bytes / self.wq
        self.kv_budget = VGPU - self.w_gpu - ACT
        self.seq_max = self.lp99 + self.pout
        self.b_kv = self.kv_budget / (self.seq_max * KV_B)
        self.r_pref = self.tp * PEAK * MFU / (2 * P)
        self.Lkv = self.lp50 + self.pout / 2
        self.c_w = self.w_gpu / (BW * BW_EFF) * 1e3
        self.c_kv = self.Lkv * KV_B / (self.tp * BW * BW_EFF) * 1e3
        self.bw_tp = IB if cross_node else NVL
        self.thr_req = self.lam * self.pout
        self.b_cap = min(self.b_kv, self.qmax)
        self.b_star, self.thr_max = self._peak()

    def _peak(self):
        best, bb, b = -1.0, 1.0, 1.0
        while b <= self.b_cap * 1.0001:
            thr = b / (self.t_step(b) / 1e3)
            if thr > best:
                best, bb = thr, b
            b *= 1.0025
        return bb, best

    def tp_comm_ms(self, b):
        act = b * D_MODEL * self.dtype_bytes / 2
        attn = self.tp * self.seq_max * HEAD_DIM * self.dtype_bytes / 2
        return 4.0 * (act + attn) / self.bw_tp * 1e3

    def t_step(self, b):
        return (max(self.c_w + b * self.c_kv,
                    2 * P * b / (self.tp * PEAK * MFU) * 1e3)
                + self.tp_comm_ms(b) + T0)

    def t_prefill(self, L):
        return (2 * P * L / (self.tp * PEAK * MFU) * 1e3
                + self.tp_comm_ms(min(self.qmax, self.b_cap)) + T0)

    @property
    def T_pref(self):
        return self.t_prefill(self.lp99 * (1 - self.h))

    def solve(self, N):
        lam_r = self.lam / N
        cap = self.b_cap
        s = self.T_pref / 1e3 + self.pout * self.t_step(cap) / 1e3
        for _ in range(800):
            b = min(lam_r * s, cap)
            s_new = self.T_pref / 1e3 + self.pout * self.t_step(b) / 1e3
            if abs(s_new - s) < 1e-13:
                s = s_new
                break
            s = 0.5 * (s + s_new)
        b = min(lam_r * s, cap)
        t = self.t_step(b)
        thr = b / (t / 1e3)
        rho = lam_r / (self.qmax / s)
        tq = math.log(50.0) / (self.qmax / s - lam_r) * 1e3 if rho < 1 else float("inf")
        ttft = tq + self.T_pref
        margin = thr * N / self.thr_req
        pref_m = self.r_pref * N / (self.lam * self.lp99 * (1 - self.h))
        why = []
        if margin < 1.0:
            why.append(f"吞吐{margin:.2f}×")
        if lam_r * s > cap + 1e-9:
            why.append("显存")
        if t > self.tpot:
            why.append(f"TPOT{t:.1f}")
        if ttft > self.ttft:
            why.append(f"TTFT{ttft:.0f}")
        if rho >= 1:
            why.append(f"ρ{rho:.2f}")
        if pref_m < 1:
            why.append(f"prefill{pref_m:.2f}×")
        return dict(N=N, gpus=N * self.wq, nodes=math.ceil(N * self.wq / self.node_gpus),
                    b=b, cap=cap, b_kv=self.b_kv, b_dem=lam_r * s, t=t, thr_gpu=thr,
                    thr_tot=thr * N, margin=margin, rho=rho, tq=tq, ttft=ttft,
                    kv_used=b * self.seq_max * KV_B / self.tp, pref_m=pref_m,
                    T_pref=self.T_pref, comm=self.tp_comm_ms(b), ok=not why, why=" ".join(why))

    def best(self):
        for N in range(1, 80):
            r = self.solve(N)
            if r["ok"]:
                return r
        return None

    def money(self, r, days=30):
        rev_h = r["N"] * self.price
        return dict(rev_h=rev_h, month=rev_h * 24 * days,
                    usd_M=rev_h * self.usd / (r["thr_tot"] * 3600) * 1e6)

五处关键设计决策：

  1. 用"每 token 卡时"而不是"延迟"做决策变量：延迟是 SLO 约束（tstep​≤30 ms），成本是目标函数。把两者混在一起（"更快的方案更好"）会导致上一节算出的错误 —— TP=4 延迟最低但卡数最多。
  2. ckv​ 用平均序列长 Lkv​=Lp50​+Pout​/2，而 bkv​ 用 p99 上限：带宽是平均量的函数（每步实际读多少），显存是峰值量的函数（最坏情况放不放得下）。混用这两个会同时高估成本与低估容量。
  3. 不动点迭代而不是解析解：s 与 b 互相定义，解析式在 b 撞上 bkv​ 时会出现分段，代码里用 800 次带阻尼的迭代（收敛判据 10−13）更稳。
  4. h∗ 的分子是"缓存的全成本"而不是"显存成本"：包括运维、key 设计、缓存失效带来的重算、以及第 5 章讲的多租户污染。只算显存会把 h∗ 低估一个数量级。
  5. 瓶颈判据用"实测值离哪条上限最近"：本节三条上限（带宽 9,846 / 显存 9,846 / 算力 84,771）相差 8.6 倍，所以判据是单值的、不会歧义 —— 这是第 3 节压测要验证的第一件事。

读输出的三处要点：

  • (3) 段的"算力上限比带宽上限高 8.6×"：这是本节最重要的一个数。它意味着在这台服务上加算力（换更快的卡、写更好的 kernel）完全无效，因为瓶颈在内存带宽。任何"提升 MFU"的优化都不会改变 tstep​。
  • (4) 段的"TP=4 只要 2 副本 8 卡"：注意它与 TP=2 的月成本相差 1,944 元（3,888 vs 5,832）。这个差额应该与"TP=4 的额外风险"对比：每副本 4 卡意味着单卡故障就损失 1/2 容量，而 TP=2 只需重新调度 2 卡。第 4 节把这类风险写进决策记录。
  • (5) 段的"h∗=0.545 对应 4,000 元/月"：把"开不开缓存"变成一条线。缓存方案报上来的成本只要超过这条线，就应该先问"命中率能不能提到 0.545 以上"，而不是直接批准。

小结#

  • 需求必须给出两个延迟数：TTFT 与 TPOT 由不同资源决定（prefill 算力 vs 每步带宽），不可互相折算。此外吞吐、可用性、输出长度、预算也必须显式写出。
  • kvB​ 是第一颗扣子：2⋅nlayer​⋅nkv_head​⋅dhead​⋅b。本节 128 KiB/token；换成 MHA 就是 512 KiB，并发上限差 4 倍。
  • 权重与 KV 抢显存：Bkv​=Vgpu​−W/TP−Wact​。权重每减半，KV 容量翻倍 —— 这是"并行策略决定并发上限"的机制，也是 TP 真正的收益来源。
  • 单卡吞吐是 b 的单峰函数：tstep​=max(cw​+bckv​, 2Pb/(TP⋅PEAK⋅MFU))+T0​。本节 b∗=15.9（受显存夹到 77.0），thrmax​=9,846 tok/s。
  • 必须用"每 token 卡时"排序方案：忽略带宽会把卡数低估 8.6 倍。TP=2/bf16 的 N∗=3（6 卡 / 5,832 元/月）；TP=4 要到 2 副本 8 卡才更便宜，代价是每副本 4 卡的故障域。
  • 副本数由五个约束联立决定：C1 吞吐 / C2 显存 / C3 prefill / C4 TPOT / C5 排队。N=2 失败是因为 b 撞上 bkv​ 后吞吐无法再涨 —— 是容量问题不是延迟问题。
  • 冗余按节点粒度算：每节点 2 副本，所以"扛单节点失效"要 N=5（10 卡 / 3 节点），比 N∗=3 多 3,888 元/月。
  • 缓存决策是 h∗：h∗=Ccache​/(λLp99​Tp/rprefill​)。本节 prefill 全量价值 7,338 元/月，h=0.45 值时 h∗=0.545 以下的缓存成本都值得。
  • 一句话：架构不是选出来的，是"把五个约束联立后取每 token 卡时最小的那个解"；而所有输入（SLO、kvB​、Lp99​、λ、单价）都必须先变成数，否则后面四节无法复核。
