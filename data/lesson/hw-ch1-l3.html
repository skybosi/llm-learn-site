为什么 GPU 适合矩阵运算#

前两课说 GPU 是"吞吐主力"，但还没解释它到底怎么做到的。这一课深入一个具体问题：矩阵乘法为什么恰好长在 GPU 的爽点上。核心只有两个词——并行和数据复用。

一、概念讲解#

1. 矩阵乘天生可并行#

看 C=AB，其中 A 是 m×k，B 是 k×n：

C[i,j]=k∑​A[i,k]⋅B[k,j]

C 里有 m×n 个元素，每个元素的计算都独立——算 C[0,0] 不需要等 C[0,1] 算完。这意味着可以同时开 m×n 路并行计算。GPU 有成千上万个核心，天然就适合这种"同一段程序，喂不同数据"的模式，也就是 SIMT（单指令多线程）：一条指令同时作用于 32 个线程（一个 warp）。

2. 关键洞察：算得多、搬得少#

GEMM 的计算量是 2mnk（三次方量级），但它需要搬运的数据只有 A 的 mk 个元素加 B 的 kn 个元素（平方量级）。当 n 很大时：

算术强度=字节数FLOPs​≈n22n3​∝n

也就是说，矩阵越大，每搬 1 字节数据能做的运算越多。这种"算得多、搬得少"的算子叫计算密集算子，正好对上 GPU 高算力 + 高带宽的组合——数据搬得动，算力也不会闲置。

3. GPU 的三板斧#

GPU 之所以能把 GEMM 跑到接近峰值，靠三件事：

  1. 海量线程：把输出矩阵切成小片，每片交给一堆线程去算，把延迟隐藏在海量并行里；
  2. 分块（tiling）：把 A、B 切成能塞进片上共享内存的小块，让每个数据被复用多次，大幅减少对慢速 HBM 的访问；
  3. 高带宽 HBM：即便要访问全局内存，H100 的 3.35 TB/s 也能喂饱这些计算单元。

4. 对比：CPU 为什么吃力#

CPU 也有 SIMD（单指令多数据）和较大的缓存，但它的核数少、带宽低。同样一个 40963 的 GEMM，CPU 需要反复从内存取数、核之间还要同步，效率和 GPU 差出数量级。差距不在"能不能算"，而在"能不能同时算、以及数据喂得够不够快"。

二、可运行代码示例#

亲手算一算 GEMM 的"算术强度"，并对比朴素实现与分块思路的访存量差异。

import numpy as np

# ---- 例 1：GEMM 的算术强度 ----
def gemm_intensity(n):
    flops = 2 * n * n * n                 # 2mnk，这里 m=n=k=n
    # 朴素实现：从内存读 A、B 各 n*n，写 C 共 n*n（忽略片上复用）
    bytes_moved = 3 * n * n * 4           # 3 个 n*n 矩阵，FP32 每元素 4 字节
    return flops, bytes_moved, flops / bytes_moved

for n in [64, 256, 1024, 4096]:
    f, b, intensity = gemm_intensity(n)
    print(f"n={n}: FLOPs={f/1e9:.2f}G, 访存={b/1e6:.0f}MB, 算术强度={intensity:.0f} FLOP/byte")

# ---- 例 2：分块如何减少"对外部内存"的访问 ----
# 朴素：C[i,j] 需要从内存取 A 的第 i 行、B 的第 j 列，各 n 个元素，
# 整个矩阵乘一共要取 2*n^3 次元素访问。
# 分块：把 n 分成 tile 大小的方块，块内数据放在共享内存里反复复用，
# 每个数据被复用 tile 次，外部访问次数从 2*n^3 降到约 2*n^3/tile。
def memory_access_naive(n):
    return 2 * n ** 3

def memory_access_tiled(n, tile):
    return 2 * n ** 3 // tile   # 近似：复用 tile 次，外部访问除以 tile

n = 1024
for tile in [16, 64, 256]:
    naive = memory_access_naive(n)
    tiled = memory_access_tiled(n, tile)
    print(f"n={n}, tile={tile}: 外部访问 {naive/1e6:.0f}M -> {tiled/1e6:.0f}M，减少 {naive/tiled:.0f} 倍")

# ---- 例 3：用手写三重循环验证 2*m*n*k 的 FLOPs 计数 ----
def naive_gemm_count(a, b):
    m, k = a.shape; k2, n = b.shape
    assert k == k2
    flops = 0
    c = np.zeros((m, n))
    for i in range(m):
        for j in range(n):
            s = 0.0
            for kk in range(k):
                s += a[i, kk] * b[kk, j]   # 1 次乘法 + 1 次加法
                flops += 2
            c[i, j] = s
    return c, flops

m = k = n = 8
a = np.random.rand(m, k); b = np.random.rand(k, n)
c, flops = naive_gemm_count(a, b)
print(f"手写循环统计 FLOPs = {flops}，公式 2*m*n*k = {2*m*n*k}，二者一致：{flops == 2*m*n*k}")

要点：例 1 显示矩阵越大、算术强度越高（计算密集）；例 2 说明分块的本质是让数据在片上被复用，从而少访问慢速外部内存。GPU 的共享内存正是为此而设——下一章会展开。

三、练习#

  1. 推导：证明 GEMM 的算术强度随 n 线性增长（用 2n3/(3n2) 量级近似即可），并说明为什么 n 越大越"计算密集"。
  2. 计算：用 gemm_intensity 算 n=8192 时的算术强度，再算 H100（989 TFLOPS、3.35 TB/s）在理想情况下跑完它大约要多少秒。
  3. 改造：把例 2 的 memory_access_tiled 换成"每个数据复用 tile 次"的更精确推导，解释为什么减少的倍数约等于 tile。
  4. 思考：如果矩阵非常"瘦长"（比如 m=1,n=4096,k=4096，即矩阵乘向量），它的算术强度会怎样？这暗示了 LLM 推理的什么特性？（提示：想一下 decode 阶段每生成一个 token 在算什么。）
