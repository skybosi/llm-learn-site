前缀共享与驱逐策略：把缓存当成本核算的边际问题#

这一节要解决什么#

上一节把 KV 显存算清了，但漏掉了一段结构性浪费：当多个请求共享同一段前缀时，那段前缀的 KV 在朴素实现里是逐份复制的。

这在实际负载里不是小事。几乎每个 LLM 服务的 prompt 都长这样：

[系统提示 2000 token] + [检索到的文档 6000 token] + [用户问题 50 token]
[few-shot 模板 1200 token] + [用户输入 300 token]

同一段前缀会被成百上千个请求重复计算、重复存储。 而上一节的结论是每 token 128 KiB —— 所以"共享一段 4000 token 的前缀"在 8 路并发下省下的不是 4 GB，而是3.5 GB。

这一节要算四个量：

  1. 共享率 h=min(1,P/n)，以及一条反直觉的结论：h 与请求数 b 完全无关。
  2. 命中率-容量的收益递减曲线：多给 1 GiB 缓存能提升多少命中率？
  3. 边际判据：缓存收益 vs batch 损失的最优点（本节代码算出它在 2 GiB 附近）。
  4. 驱逐策略的成本核算：为什么最优策略是"保留最可能被再次访问的"，以及它与 LRU 的差距来自哪里。

先给本节最重要的一条：

前缀共享是把 KV 从「每请求一份」变成「全服务一份」；它的收益上界是 h⋅s⋅b 而不是常数​

含义：共享的收益与并发数成正比（因为省下的是 b−1 份），而成本是一个前缀一份。所以：

净收益=(b−1)P⋅KV1​−极小(块表与哈希开销)​​

并发越高，前缀共享越划算 —— 这与"前缀共享是个锦上添花的优化"的印象相反：在 b 很大时它是数量级级别的节省。

一、机制：为什么"块哈希"就够了#

1.1 块级哈希与共享#

上一节把 KV 切成固定大小的块（Bblk​=16 token）。前缀共享的做法是给每个块一个由内容决定的键：

keyi​=hash(tokens[iBblk​:(i+1)Bblk​], keyi−1​)

关键设计：键是链式的（第 i 块的键包含第 i−1 块的键）。这个设计有两个不可替代的作用：

  1. 保证前缀语义：两个请求共享第 i 块，等价于它们共享第 0..i 块（因为键是链式的）。若键只由本块 token 决定，两个不同前缀可能在某个中间块上碰撞，从而共享到不该共享的 KV；
  2. 保证注意力正确：第 i 块的 KV 是"在完整前 i 块上下文中算出"的。只有在前缀完全相同的前提下，这个 KV 才可以复用 —— 链式键恰好形式化了这个前提。

前缀共享的正确性完全依赖「键是链式的」这一点​

⚠️ 工程陷阱：链式键里还应该包含 tokenizer / 模板版本。同一个字符串在不同 tokenizer（或同一 tokenizer 的不同版本）下会切成不同 token；如果两块 KV 被判定共享但 token 实际不同，就会静默地给出错误输出。所以实际实现里：

key0​=hash(tokenizer_id, template_id, tokens[0:Bblk​])

这是一个"错了不会报错、只会输出垃圾"的地方，必须在第一块就把版本信息混进去。

1.2 共享率 h#

设前缀长 P、请求总长 n（含前缀）、并发 b 个请求共享这个前缀。

不共享时的 KV 占用：b⋅n⋅KV1​。 共享后的占用：前缀一份P⋅KV1​​​+各请求的非共享部分b(n−P)⋅KV1​​​。

定义共享率 h 为"被共享的 token 占总 token 的比例"：

h=bnbP−P​=nP​⋅bb−1​

而"KV 占用下降的比例"（这才是我们能观测到的量）：

Δ=1−bnP+b(n−P)​=bnP(b−1)​=nP​(1−b1​)

两处必须分清：

复用率（一份被几个人用）=b,占用下降比例=nP​(1−b1​)​

当 b 很大时 Δ→P/n —— 这就是"h 是 P/n、与 b 无关"这条直觉的精确版本：占用下降比例的上限是 P/n，而 b 只决定你多快接近这个上限：

b 1−1/b 若 P/n=0.5 的占用下降
1 0 0%
2 0.50 25.0%
4 0.75 37.5%
8 0.875 43.8%
32 0.969 48.4%
∞ 1 50.0%

数值实例（P=4000、n=8000、b=8、KV1​=128 KiB）：

方案 KV 占用 相对
不共享 8×8000×128 KiB=8000 MiB 100%
共享 4000×128 KiB+8×4000×128 KiB=500+4000=4500 MiB 56.3%

省下 3500 MiB=43.8% (=nP​(1−b1​)=0.5×0.875)

⚠️ "h 与 b 无关"这句话要小心表述：P/n 与 b 无关，但实际节省比例 nP​(1−b1​) 与 b 有关。把这两者混起来会得出"前缀共享在低并发下也有用"的错误结论 —— 实际 b=1 时它完全没有收益（省下 0）。

二、命中率-容量曲线：收益递减发生在哪#

2.1 两级共享：完全匹配 vs 前缀匹配#

匹配类型 条件 典型场景 命中粒度
完全匹配 整个 prompt 相同 固定模板 + 固定问题（评测、分类） 整段
前缀匹配 前 k 个块相同 系统提示 + 不同用户输入 前 k 块

前缀匹配是主要战场，因为它对"用户输入不同"这件事免疫。

2.2 一个真实的负载模型#

要算命中率曲线，必须先假设前缀长度分布。本节用一个常见的形状：少数几个高频前缀 + 长尾：

前缀来源 占比 长度
主系统提示 60% 2000 token
次系统提示 15% 1200
长文档模板 10% 3000
few-shot 模板 5% 500
长尾（每请求不同） 10% 0~300

用块级 LRU 模拟（Bblk​=16、4000 个请求）：

缓存容量 命中率（LRU） 命中率（LFU）
0.25 GiB（2048 token） 0.67% 6.76%
0.5 GiB（4096 token） 36.36% 48.81%
1 GiB（8192 token） 55.28% 56.77%
2 GiB（16384 token） 68.24% 68.49%
4 GiB（32768 token） 68.54% 68.55%
8 GiB（65536 token） 68.65% 68.66%

三处必须读懂的地方：

  1. 0.25 GiB → 0.5 GiB 出现了一个 54 倍的跃迁（0.67% → 36.36%）。原因很直接：2000 token 的主提示需要 2000×128 KiB=250 MiB，而 0.25 GiB 的容量刚好装不下它（还差一点点）。命中率曲线的形状由"最长的高频前缀有多长"决定，不是一个平滑的函数。
  2. 1 GiB 之后收益迅速饱和：55.3% → 68.2% → 68.5% → 68.7%。"再给缓存加显存"在 1~2 GiB 之后就几乎无效了。
  3. 饱和值 68.7% 而不是 100%：因为 10% 的请求根本没有可共享前缀（长尾），另外那些高频前缀的命中率也不是 100%。这个饱和值就是"这个负载的可共享上界"，它由业务决定，调不出来。

缓存命中率曲线是「台阶 + 饱和」，不是「平滑指数」​

这解释了一个运维现象：给缓存加了 2 GiB 显存却看不到改善 —— 因为你已经过了饱和点，而"加容量"只在台阶附近有效。

2.3 缓存容量的下限：至少要装下最长的高频前缀#

由上一条直接得到一条可操作的容量规则：

Cmin​=高频前缀max​(length)×KV1​

示例：主系统提示 2000 token → Cmin​=250 MiB。低于这个值，那个前缀永远无法被完整缓存，命中率会掉到接近 0（因为前缀匹配要求从第 0 块开始连续命中，缺一块就全断）。

⚠️ "缺一块全断"这个性质很重要：前缀共享是前缀的，所以缓存块的不连续存放不影响命中，但缺任何一块都会截断命中。所以缓存的有效容量由"能整段放下多少个高频前缀"决定，而不是"总共能放多少块"。

三、边际判据：缓存 vs batch#

3.1 成本与收益的两条曲线#

这是本章 index 里那条方程的落地。

成本（缓存拿走显存）：缓存 C 个 token 就少了 C⋅KV1​ 字节的 KV 池，于是并发从 b0​ 降到

b(C)=sˉ⋅KV1​KV 池−C⋅KV1​​

吞吐（在 b<b∗ 区间，Tstep​ 与 b 无关）：

Θraw​(C)∝b(C)=b0​−sˉC​

收益（命中率高 → 省下 prefill 工作）：每秒有 λ 个请求、平均 n 个 token，命中率 h(C)，则每秒省下的 prefill 时间：

ΔTsaved​=λnh(C)⋅a(秒/秒)

把它折成"等效吞吐"：Θeff​(C)=Θraw​(C)⋅(1+ΔTsaved​)。

最优 C 满足：

缓存拿走显存的损失Θraw′​(C)⋅(1+ΔTsaved​)​​+命中率提升的收益Θraw​⋅λnah′(C)​​=0​

即 h′(C) 下降到 Θraw​λnaΘraw′​​ 时停止加缓存。

3.2 数值：最优点在哪#

用 2.2 的负载（sˉ=2000、KV 池=59.2 GiB、a=66.7μs/token、λn≈ 由吞吐反推）：

缓存 GiB 命中率 batch 原始吞吐 tok/s prefill 节省 tok/s 净收益
0 0% 242 55 332 0 55 332
0.25 0.67% 241 55 098 369 56 454
0.5 36.36% 240 54 864 19 947 127 859
1 55.28% 238 54 397 30 069 163 495
2 68.24% 234 53 462 36 484 183 564 ← 峰
4 68.54% 226 51 593 35 361 173 280
8 68.65% 210 47 855 32 851 152 710
16 68.74% 177 40 377 27 757 115 132

三处必须读懂的地方：

  1. 净收益在 2 GiB 附近达峰，之后下降（4 GiB 已经比 2 GiB 差 5.7%，8 GiB 差 17%）。"缓存越大越好"是错的 —— 过了峰值，从 batch 拿走的吞吐超过命中率带来的收益。
  2. 峰值位置远小于 KV 池（2 GiB vs 59.2 GiB）。原因是命中率在 1 GiB 就饱和了（h′ 趋近 0），而 batch 的损失是线性的。这就是"边际分析"的价值：它给出的是一个远小于直觉的容量。
  3. Δ 的形状由 h(C) 决定，所以它也是"台阶 + 饱和 + 下降"。第 0.25 → 0.5 GiB 那一步使净收益翻倍多（56k → 133k），说明"缓存容量必须跨过最长高频前缀那道坎"是本节的第一个操作结论。

⚠️ 但这个峰的位置对参数很敏感，不要把 2 GiB 当常数：

参数变化 峰值位置
sˉ 变长（2000 → 8000） 左移（batch 对显存更敏感，缓存成本变高）
b 接近 b∗ 左移（吞吐进入饱和区，batch 的边际价值变成延迟）
高频前缀占比更高（60% → 90%） 右移（h 的上界更高，收益更大）
请求速率 λ 更高 右移（缓存收益 ∝λ，成本与 λ 无关）

缓存配额不是配置项，是「负载的函数」​

四、驱逐策略：保留谁#

4.1 每个块的价值都是一样的，区别只在"被再次访问的概率"#

先澄清一个常见误解："有些块更重要"是不成立的。每个块的重算成本都等于 a⋅Bblk​（同样的 prefill 计算），所以：

驱逐的期望成本(x)=px​⋅a⋅Bblk​

其中 px​ 是"块 x 在下次被驱逐前会被再次命中"的概率。所以最优策略极其简单：

驱逐 argxmin​px​(保留最可能被再次访问的块)​

这就是 LFU（least frequently used） 的形态。而真实系统里 LRU 更常见，原因是：

策略 依据 何时最优 何时失效
LRU 最近访问时间 访问有局部性（时间局部性） 周期性/突发性负载（一个前缀很久不用，然后一次涌入）
LFU 历史访问频次 有稳定的热点前缀 热点会变（历史高频 ≠ 未来高频）
带老化（aging）的 LFU 频次随停留时间衰减 通用 需要调衰减系数
前缀感知 知道哪段是系统提示 有明确的高频前缀 需要应用层告知

LRU 最经典的失效场景就是系统提示：它可能每 10 分钟才被用一批（比如定时任务），而中间穿插的短请求把它的块全挤出去 —— 于是下一批又要完整重算。

工程上的折中（真实系统的做法）：

驱逐优先级=老化频次块在缓存中的停留时间块被访问的次数​​​+应用提示β⋅1[块属于已知高频前缀]​​

第二项就是"pin 住系统提示"的实现方式。它的收益可以算：若一个 P=2000 的前缀被周期性地使用，pin 它只需 250 MiB（例：2000×128 KiB），而每次不命中要重算 2000×66.7μs=133 ms。只要这个前缀每 250 MiB/133 ms 的有效成本周期内被用一次以上，pin 就划算。

4.2 驱逐还要考虑"驱逐它会不会打断正在运行的请求"#

一个块可能正在被活跃请求引用（引用计数 > 0）。驱逐规则必须是：

可驱逐⟺引用计数=0

否则会把别人的 KV 从中抽走。这就是引用计数在分页系统里的作用（它同时服务于前缀共享与写时复制）。

⚠️ 共享块被多个请求引用时，它的生命周期由最后一个引用者决定。这带来一个反直觉的现象：

一个被 100 个请求共享的块，其"最后一次访问"总在最近⇒它在 LRU 下几乎永不被驱逐

所以共享本身就在保护被共享的块（这是 LRU 的一个隐藏优点），而"pin 系统提示"主要是为了对抗间歇性访问模式（长时间没人用 + 中间涌入其他请求）。

4.3 一个必须说的正确性约束#

前缀共享引入了一类只在并发下出现的 bug：写时复制（COW）。

请求 A 命中前缀块 0..k
请求 B 也命中同样的块
→ 两个请求共享这些物理块
→ 若其中一个继续生成新 token 并"原地写"这些块 → 另一个被污染

处置：当某个共享块要被写入时，先复制一份（COW），并把该请求的引用指向副本。代价是：

COW 触发率=#{共享块}#{共享块中被写入请求续写的}​

在 decode 场景里，共享的只有前缀，而前缀在 decode 阶段不再被写（它已经算完了）—— 所以 COW 的实际触发率很低。但"很低"不是"零"：当中途插入新 token（如工具调用的结果回填到 prompt 中间）时，共享块就可能被写。这类操作必须在实现层显式处理。

代码：前缀共享的节省账、命中率曲线与缓存配额最优#

脚本做四件事：(1) 算共享率与占用下降比例（含与 b 的关系）；(2) 用块级 LRU 模拟命中率-容量曲线；(3) 算"缓存配额 vs batch"的净收益曲线并找出峰值；(4) 比较 LRU 与 LFU 在同一负载下的命中率差异。

"""
前缀共享的收益、命中率曲线与缓存配额最优（只用标准库）。

设计决策：
  1. 用「块级哈希」而不是「整段相等」建模共享，因为真实负载里前缀长度不同、
     匹配是「从第 0 块开始连续命中的最长前缀」——整段相等会严重低估命中率（正文 1.1）。
  2. 缓存配额的最优值用「净收益曲线」找，而不是给一个推荐数字。
     因为峰值位置对平均长度、并发水平、请求速率都敏感（正文 3.2 的敏感度表）。
  3. LRU 与 LFU 用同一份负载、同一个种子比较。命中率差异必须来自策略，
     不能来自抽样 —— 这是这类对照实验最常见的错误（正文 4.1）。
  4. 前缀用 (prefix_id, length) 显式建模，而不是用随机字符串。
     这样才能表达「少数几个高频前缀 + 长尾」这个真实形状，
     并且能直接看出「0.25→0.5 GiB 的台阶」来自某个具体前缀的长度（正文 2.2）。
"""
import random
from collections import OrderedDict

L, NKV, DH, DTYPE = 32, 8, 128, 2
KV1 = 2 * L * NKV * DH * DTYPE            # 128 KiB/token
BLK = 16                                  # 每块 token 数
PARAMS = L * 12 * 4096 ** 2 + 32000 * 4096
WEIGHT = 2 * PARAMS
HBM, FLOPS = 3.0e12, 989e12
KV_POOL_BYTES = 59.2 * 2 ** 30            # 上一节算出的 KV 池
A_PF = 66.7e-6                            # prefill 每 token 秒（上一节标定）


# ==================== 负载 ====================
PREFIX_ENV = [(1, 2000, 0.60), (2, 1200, 0.15), (3, 3000, 0.10),
              (4, 500, 0.05)]             # (id, 长度, 占比)


def gen_requests(rng, n, maxlen=4096):
    """生成 (prefix_id, prefix_len, total_len) 序列。10% 长尾请求无共享前缀。"""
    out = []
    for _ in range(n):
        r = rng.random()
        acc = 0.0
        pid, plen = 0, 0
        for p, ln, frac in PREFIX_ENV:
            acc += frac
            if r < acc:
                pid, plen = p, ln
                break
        else:
            pid, plen = 100 + rng.randint(0, 200), rng.randint(0, 300)
        total = min(maxlen, plen + rng.randint(50, 1500)) if plen else rng.randint(50, 800)
        out.append((pid, plen, total))
    return out


# ==================== 块级缓存模拟 ====================
def simulate(reqs, cap_tokens, policy="lru", blk=BLK):
    """
    返回命中的前缀 token 数与总 token 数。
    命中规则：从第 0 块开始连续命中，遇到第一个缺失块就停（前缀的语义，正文 2.3）。
    """
    cache = OrderedDict()          # key -> 访问计数（LFU 用）
    hit_tokens = total_tokens = 0
    for pid, plen, total in reqs:
        total_tokens += total
        i = 0
        while i * blk < plen and (pid, i) in cache:
            hit_tokens += blk
            if policy == "lru":
                cache.move_to_end((pid, i))
            else:
                cache[(pid, i)] += 1
            i += 1
        for j in range((total + blk - 1) // blk):
            key = (pid, j)
            if key in cache:
                if policy == "lru":
                    cache.move_to_end(key)
                else:
                    cache[key] += 1
                continue
            while len(cache) * blk + blk > cap_tokens and cache:
                if policy == "lru":
                    cache.popitem(last=False)
                else:                     # LFU：淘汰访问计数最小的
                    victim = min(cache, key=lambda k: cache[k])
                    del cache[victim]
            cache[key] = 1
    return hit_tokens, total_tokens


def throughput_and_batch(cache_bytes, mean_len=2000):
    """给定缓存占用的字节，返回 (原始吞吐 token/s, 并发数)。"""
    pool = KV_POOL_BYTES - cache_bytes
    b = max(1.0, pool / (mean_len * KV1))
    t_step = max(WEIGHT / HBM, 2 * PARAMS * b / FLOPS)
    return b / t_step, b

六处关键设计决策：

  1. 命中规则写成"从第 0 块开始连续命中"。这是前缀共享的语义，不是实现细节：块 i 的 KV 依赖第 0..i 块，所以缺一块就全断。用"最长公共块数"而不是"块命中总数"是正确建模的关键。
  2. gen_requests 用 (prefix_id, prefix_len) 显式建模。这样才能让读者算出"主提示 2000 token 需要 250 MiB，所以 0.25 GiB 装不下" —— 台阶的来源是可见的。随机字符串模型不会给出这个可解释性。
  3. LRU 与 LFU 用同一份 reqs。这是对照实验的基本要求；命中率差异必须完全来自淘汰策略。
  4. throughput_and_batch 用 max(权重访存, 算力)，并且只让缓存影响 b（不影响 Tstep​ 的函数形式）。这样"缓存拿走显存 → batch 变小 → 吞吐下降"这条链路是可追踪的，而不是靠一个折扣系数。
  5. 净收益用 tps * (1 + saved_tok * A_PF) 而不是 tps * (1 + h)。前者有物理含义（省下的是 prefill 时间，可折算为等效吞吐），后者是把命中率直接当吞吐增益 —— 后者会系统性地高估缓存的收益。
  6. 第 (4) 段把每条前缀的缓存需求单独列出。这条"容量下限"规则（Cmin​=P⋅KV1​）是本节最有操作价值的结论，必须让读者能对号入座地算。

四处值得单独读的数字：

  • 第 (1) 段的 b=1 行：省下 0.0 MiB —— 这是"前缀共享在低并发下没有价值"的定量证明。任何"我们上了前缀缓存所以变快了"的说法，在 b 很小时都不成立。
  • 第 (2) 段 0.25 → 0.5 GiB 的台阶（0.67% → 36.36%）：主系统提示 2000 token 需要 250 MiB，0.25 GiB 刚好装不下。这个台阶可以精确预测（250 MiB vs 256 MiB），是"缓存容量必须跨过最长高频前缀"的直接证据。
  • 第 (2) 段 LRU 与 LFU 的差距只在低容量时显著（0.25 GiB：0.67% vs 6.76%，差 10 倍；1 GiB 以上差 <3%）。含义：容量充裕时淘汰策略几乎不重要，容量紧张时策略决定成败。所以"该不该花精力改淘汰策略"有一个可以算的前提条件。
  • 第 (4) 段的 838 MiB：四条高频前缀全缓存只需要 838 MiB，而第 (3) 段的峰值在 2 GiB。两个数一起说明一件事：把高频前缀全部 pin 住（838 MiB）就已经拿到了绝大部分收益，剩下的容量用于容纳"低频但仍可复用"的块。这就是配置的起点：先 pin 高频前缀，再把剩下的给 LRU。

小结#

  • 前缀共享的机制是"块级链式哈希"。键必须包含前一块的键（保证"共享第 i 块 ⇔ 共享前 i 块"），并且第一块的键要混入 tokenizer 与模板版本 —— 否则会静默地共享到 token 不同的 KV，输出垃圾而不报错。
  • 占用下降比例 Δ=nP​(1−b1​)：b=1 时是 0，b→∞ 时趋近 P/n。所以"h 与 b 无关"是对上限成立，实际节省与 b 有关。前缀共享的收益与并发成正比（省下的是 b−1 份）。
  • 命中率曲线是"台阶 + 饱和"，不是平滑曲线：台阶由"最长高频前缀有多长"决定（示例：主提示 2000 token 需 250 MiB，所以 0.25 GiB 装不下它 → 命中率从 0.69% 跳到 38.71%）；饱和值（示例 68.5%）由业务的可共享比例决定，调不出来。
  • 容量下限规则：Cmin​=max高频前缀​P⋅KV1​。低于它那条前缀永远无法命中（前缀匹配要求从第 0 块连续命中，缺一块全断）。
  • 缓存配额有最优值，示例在 2 GiB 附近（远小于 59.2 GiB 的 KV 池）。理由是命中率在 1 GiB 就饱和，而 batch 损失是线性的。"缓存越大越好"是错的 —— 4 GiB 比 2 GiB 差 5.7%，8 GiB 差 17%。
  • 峰值位置是负载的函数：平均长度变长 → 左移；b 接近 b∗ → 左移；高频前缀占比更高 → 右移；请求速率更高 → 右移。缓存配额不是配置项。
  • 驱逐的正确形式：每个块的重算成本都是 a⋅Bblk​，所以只需比较"被再次访问的概率"，即预算 argminx​px​（LFU 形态）。LRU 在周期性/间歇性访问（典型是定时任务用的系统提示）下会失效；工程折中是"老化频次 + pin 已知高频前缀"。
  • 引用计数是硬约束：只驱逐引用计数为 0 的块，否则会把活跃请求的 KV 抽走。共享块的生命周期由最后一个引用者决定 —— 这让被大量共享的块在 LRU 下几乎永不被驱逐（共享本身就在保护被共享的块）。
  • 写时复制（COW）是必须实现的正确性约束：共享块被写入前要复制。纯 decode 场景下触发率很低（前缀已算完），但"工具调用结果回填到 prompt 中间"这类操作会显著提高触发率。
  • 一句话：前缀共享把 KV 从"每请求一份"变成"全服务一份"，它的收益上是 P/n、与并发同阶；而缓存的正确规模不是"越大越好"，而是"跨过最长高频前缀那道坎，然后在命中率饱和之前停下"。

本章把调度的静态与动态账都算完了：连续批处理摊销固定成本、分块预填充把 prefill 的延迟成本分期、分页把显存碎片压到个位数、前缀共享与驱逐把公共部分只存一份。剩下的问题是：这些数字在多租户、弹性扩缩容与故障下如何保持 —— 那是 SLA、公平性与成本核算的范畴。
