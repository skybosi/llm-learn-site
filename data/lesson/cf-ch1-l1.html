编译器在做什么：前端 / 中端 / 后端与 LLVM 生态#

在写第一行编译器代码之前，我们需要一张地图。编译器是少数"实现方式反过来决定语言设计"的领域：为什么 C 里必须先声明后使用？为什么 Pascal 要求类型声明写在块的开头？答案不在语言理论里，而在当年的编译器只能单遍处理这个工程事实里。不理解这层，后面所有"为什么要这样设计"都会变成背结论。

一、概念讲解#

1. 编译器是一条"表示变换"流水线#

编译器把源文本逐级变换成机器能执行的形态。关键在于：每一级变换都让语义更显式——从"一串字符"到"谁引用了谁"，再到"要算哪些数、以什么顺序"。

源码文本 → token 序列 → 语法树 → 带语义的树 → 中间表示 → 优化后的 IR → 目标代码
语义：越来越显式                                        实现：越来越贴近机器

这个"先上山（理解语义）、再下山（降到机器）"的比喻来自 Robert Nystrom 的 Crafting Interpreters（第 2 章）：上山阶段我们逐步看清"这段代码到底要做什么"，下山阶段我们把它一步步降成 CPU 能执行的指令。

2. 六个阶段的职责#

阶段 输入 → 输出 要做的事 会报的错
词法分析（scanning/lexing） 字符流 → token 流 切词、去掉空白与注释 非法字符、未闭合字符串
语法分析（parsing） token 流 → 语法树（AST） 按文法把扁平序列组织成嵌套结构 语法错误（括号不匹配、缺分号）
语义分析（static analysis） AST → 带绑定/类型的 AST 名字解析（作用域）、类型检查 未定义变量、类型不匹配
中间表示（IR） AST → IR 换成与源语言/目标机都不强绑定的形态 ——
优化 IR → 等价但更快的 IR 常量折叠、死代码消除、内联… ——
代码生成 IR → 汇编/机器码 指令选择、寄存器分配、指令调度 寄存器不足（溢出处理）

前三段合称前端（依赖源语言），最后一段是后端（依赖目标架构），夹在中间的 IR 与优化叫中端——这个词是后来补出来的，因为人们发现"与两边都无关"的优化（常量传播、死代码消除）完全可以共享。

3. 为什么必须有中间表示#

假设要支持 M 种源语言、N 种目标架构。没有通用 IR 时，你要写 M × N 个完整编译器（Pascal→x86、C→ARM、……）。有了共享 IR，只需 M 个前端 + N 个后端：前端各自降到同一个 IR，后端各自从该 IR 出发。

这正是 GCC 能支持 Modula-3 跑在 Motorola 68k 上的原因，也是 LLVM 成为现代工具链"通用中端"的原因——它在两端都提供了稳定的接口。

4. 实现路线不止一条#

教科书常讲"六阶段走完"，真实实现充满捷径（以下都对应真实语言）：

路线 做法 代价 / 例子
单遍编译 解析时直接产出代码，不建 AST/IR 语言被迫"先声明后使用"（C、Pascal 的语法限制就源于此）
树遍历解释器 解析成 AST 后直接遍历求值 实现简单、慢；早期 Ruby(MRI)、教学语言常用
字节码 + 虚拟机 编译成虚拟指令，由 VM 执行 可移植；CPython、JVM、早期 Ruby(YARV)
transpiler（源到源） 生成另一种高级语言源码，交给它的工具链 借力生态；TypeScript→JS、早期 C 作为目标语言
JIT 运行期编译成机器码，并按热点重优化 最快但最复杂；HotSpot JVM、V8

这条表最重要的启示：实现方式会反过来塑造语言。单遍编译不是"偷懒"，它直接解释了 C 的语法约束；这也提醒我们，看待一门语言的设计先问"它当年的编译器是什么样"。

5. "编译器 vs 解释器"是个假二分#

  • 编译是一种实现技术：把源码翻译成另一种（通常更底层的）形式；
  • 解释器指"拿源码直接执行"的实现。

二者并不互斥。CPython 是解释器，但它内部有一个编译器（把源码编译成字节码再交给 VM 执行）；Go 更典型：go build 时它是编译器，go run 时它是解释器，而它内部始终在编译。判断一个实现属于哪种，看用户是否直接看到中间产物，而不是看它内部有没有编译。

6. LLVM 生态：通用中端的现实长相#

clang（前端）→ LLVM IR（.ll 文本 / .bc 字节码）→ opt（优化 pass）→ llc（后端）→ .s → as/ld → 可执行
                                                  └── lli 可直接解释执行 IR（便于验证）
  • clang：C/C++/ObjC 前端，产出 LLVM IR；
  • LLVM IR：既像汇编又保留类型信息的中间语言，有文本形式便于阅读——这是它比"只活在内存里"的 IR 更适合学习的原因；
  • opt：跑优化 pass 管线，可逐个开关、可打印每一步之后的 IR（第 3 课要用它做"调试 pass"）；
  • llc：从 IR 生成目标汇编；
  • MLIR：LLVM 之上的多级 IR 框架，正是《深度学习编译器与算子生成》那一门的主角之一。

二、可运行代码示例#

下面这段 Python（无第三方依赖）用不到 60 行搭出"编译器骨架"：同一段源码，走完词法 → 语法 → IR 三个形态。它是本章后续课时与整门课的地基。

# ---- 例 1：一个最小编译器骨架（源码 → token → AST → 三地址码）----
import re

TOKEN = re.compile(r'\s*(?:(\d+)|([a-zA-Z_]\w*)|([-+*/()=]))')

def tokenize(src):
    """词法分析：字符流 → token 流（这里只认数字、标识符、运算符）"""
    out, i = [], 0
    while i < len(src):
        m = TOKEN.match(src, i)
        if not m:
            raise SyntaxError(f'非法字符 {src[i]!r} at {i}')
        i = m.end()
        num, name, op = m.groups()
        if num:  out.append(('NUM', int(num)))
        elif name: out.append(('NAME', name))
        elif op:   out.append(('OP', op))
    return out

def parse(tokens):
    """语法分析：token 流 → AST（这里只处理赋值与二元运算，够用即可）"""
    pos = 0
    def peek():
        return tokens[pos] if pos < len(tokens) else (None, None)
    def eat(kind, value=None):
        nonlocal pos
        k, v = peek()
        if k != kind or (value is not None and v != value):
            raise SyntaxError(f'期望 {kind}{value or ""}，得到 {(k, v)}')
        pos += 1
        return v
    def expr():
        node = term()
        while peek() == ('OP', '+') or peek() == ('OP', '-'):
            op = eat('OP'); node = ('bin', op, node, term())
        return node
    def term():
        node = atom()
        while peek() == ('OP', '*') or peek() == ('OP', '/'):
            op = eat('OP'); node = ('bin', op, node, atom())
        return node
    def atom():
        k, v = peek()
        if k == 'NUM':  eat('NUM');  return ('num', v)
        if k == 'NAME': eat('NAME'); return ('var', v)
        if (k, v) == ('OP', '('):
            eat('OP', '('); node = expr(); eat('OP', ')'); return node
        raise SyntaxError(f'表达式起始处意外 token {(k, v)}')
    name = eat('NAME'); eat('OP', '=')
    return ('assign', name, expr())

def lower(node, out, tmp=[0]):
    """中间表示：AST → 三地址码（每条指令最多一个运算，结果存临时名）"""
    if node[0] == 'num':
        return ('const', node[1])
    if node[0] == 'var':
        return ('name', node[1])
    _, op, l, r = node
    a, b = lower(l, out), lower(r, out)
    tmp[0] += 1
    t = f't{tmp[0]}'
    out.append((t, op, a, b))
    return ('name', t)

src = 'average = (min + max) / 2'
toks = tokenize(src)
ast  = parse(toks)
ir   = []
print('token:', toks)
print('AST  :', ast)
lower(ast, ir)
for ins in ir: print('IR   :', ins)

运行后你会看到同一段代码的三种形态：

token: [('NAME','average'), ('OP','='), ('OP','('), ('NAME','min'), ...]
AST  : ('assign', 'average', ('bin', '/', ('bin', '+', ('var','min'), ('var','max')), ('num',2)))
IR   : ('t1', '+', ('name','min'), ('name','max'))
IR   : ('t2', '/',  ('name','t1'),  ('const',2))

注意 AST 与 IR 的差别：AST 是嵌套的（能看出语法结构），IR 是扁平指令序列 + 临时变量（每一行只做一件事）。这个"从嵌套到扁平、把依赖关系显式化"的动作，就是后面所有优化的前提。
