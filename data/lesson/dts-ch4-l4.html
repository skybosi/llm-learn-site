故障排查：带宽不达标、hang / timeout 的定位路径#

多卡训练的事故只有两类：慢（带宽不达标、扩展性差）和停（hang、超时后自动中止）。两类事故的共同陷阱是：一上手就改环境变量或加超时。本课给一条从"硬件上限"到"应用层顺序"的自上而下排查路径，并先把每种现象会等多久、该看哪几行日志算清楚。

一、概念讲解#

1. 三类现象，第一动作不同#

现象 第一动作 别做
慢：busbw 只有链路峰值的零头 先量硬件上限（nvidia-smi topo -m、nvbandwidth、ib_write_bw） 直接抄调参配方
停：初始化阶段就挂住 NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,BOOTSTRAP,NET 先加大超时
错：报错后进程退出 读 NCCL WARN 原文 + 版本/插件不匹配告警 用 mismatch 类开关跳过

2. 慢：先证明硬件能给多少，再怀疑 NCCL#

官方给的顺序很具体：节点内先看 nvidia-smi topo -m，再用 nvidia-smi topo -p2p n（NVLink）或 -p2p p（PCIe）确认逐对 P2P 是否 OK；然后用 nvbandwidth（或 nvloom）量 GPU↔GPU 实际带宽。跨节点用 ib_write_bw 量带宽、ib_write_lat 量延迟——官方特别指出带宽好而尾延迟差的情况要用延迟测试抓；rdma statistic 里 rnr_nak_retry_err、packet_seq_err、local_ack_timeout_err 增长说明在丢包重传，ibstat/ibstatus 看端口是否 Active、速率有无降档，perfquery 看 SymbolErrorCounter 类错误计数。

如果硬件测试达标而 NCCL 不达标，问题在配置这一层，此时才轮到第 3 课的变量。判定用账本：取两个大消息实测点反解 β，与拓扑给出的链路等级比；取小消息点反解 α，与算法/协议选择比。

3. 停：先分清"初始化挂起"与"运行中挂起"#

  • 初始化挂起：官方推荐的诊断是 NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,BOOTSTRAP,NET，看三件事：bootstrap 连接是否建立、选中的网络接口对不对（自动选择可能挑到"UP 但跨节点不通"的接口，此时需要显式 NCCL_SOCKET_IFNAME）、版本/插件是否一致。TCP 端口范围可用内核参数收窄，便于放行防火墙。
  • 运行中挂起：最常见的原因是各 rank collective 顺序/参数不一致。官方明确：集合操作必须每个 rank 都用同样的 count 与 datatype 调用，否则是 undefined behavior，表现为 hang、崩溃或数据损坏。PyTorch 侧另有几个专用开关：TORCH_NCCL_DESYNC_DEBUG（找不同步的元凶 rank）、TORCH_NCCL_ASYNC_ERROR_HANDLING（默认 3：不 abort 通信子直接销毁进程）、以及 flight recorder——TORCH_NCCL_TRACE_BUFFER_SIZE（必须 > 0）配合 TORCH_NCCL_DUMP_ON_TIMEOUT、TORCH_NCCL_DEBUG_INFO_TEMP_FILE 在超时时导出各 rank 的最后若干次集合操作。

4. 每种"停"默认会等多久#

默认值不是随便定的，它给大集群留了余量，所以"卡了很久"往往只是还在正常等待：

层级 默认口径 出错前的等待量级
socket 建连重试 NCCL_SOCKET_RETRY_CNT=34、NCCL_SOCKET_RETRY_SLEEP_MSEC=100 约 60 s（官方给的总时间公式 (N+1)N/2×sleep）
InfiniBand NCCL_IB_TIMEOUT=20、NCCL_IB_RETRY_CNT=7 单次超时 4.295 s × 7 ≈ 30 s
PyTorch 进程组 init_process_group(timeout=...) NCCL 默认 10 分钟（其他后端 30 分钟，以所装版本文档为准）

对照一下：一次正常的 576 MiB AllReduce（按 25 GB/s 算）只要约 24 ms——IB 的默认预算就是它的 1200 倍以上。所以"hang 了三分钟"完全可能仍在等一个正常的超时，先量预算再改超时。

5. 被忽略的环境/权限类原因#

  • PCIe P2P 被 IOMMU 拦住：官方明确指出，Linux 裸机上 CUDA/驱动栈不支持开启 IOMMU 的 PCIe P2P；症状不像 NCCL 报错，而像应用或框架的 bug。检查 cat /proc/cmdline 与 dmesg | grep -i iommu，Default domain type: Translated 值得警惕。
  • PCI ACS 同样会让 P2P 退化，表现为"拓扑看起来 OK、带宽就是上不去"。
  • GDRDMA 没生效：GPU 直连网卡需要 nvidia-peermem 模块，节点重启后要确认已加载（modprobe nvidia-peermem / lsmod）。
  • 多进程争用同一张 GPU：PyTorch 文档明确，NCCL 后端下每个进程必须独占它使用的每张 GPU，否则可能死锁或触发 NCCL invalid usage。
  • 网卡/端口不匹配：NCCL_IB_HCA 漏配会让部分通信绕远路，表现出来仍是"慢"，不是"停"。

6. 定位顺序（按代价从低到高）#

  1. 读日志：NCCL WARN 原文、GRAPH 的环/树、TUNING 的算法/协议/通道；
  2. 量硬件：nvbandwidth / ib_write_bw / ib_write_lat；
  3. 反解 α、β，与链路等级比对；
  4. 查环境：接口、HCA、IOMMU/ACS、CPU 亲和、进程数 × 卡数；
  5. 最后才查应用：collective 顺序、count/dtype、no_sync() 用法、分支导致的 rank 不同步。

7. 常见坑#

  • 用 NCCL_P2P_DISABLE=1 之类开关"试出来能跑"就留在生产脚本里，掩盖真实原因。
  • 用 NCCL_IGNORE_NET_MISMATCH / NCCL_IGNORE_COLLNET_MISMATCH 跳过配置错误告警。
  • 不加 NCCL_DEBUG_FILE 就在 8 卡 × 多节点上开 NCCL_DEBUG=INFO：日志互相覆盖，官方建议用 %h.%p 分文件。
  • 只看平均带宽不看尾延迟：ib_write_lat 的高尾延迟才是"间歇性变慢"的线索。

二、可运行代码示例#

第一段解析一份 NCCL 调试日志（形状取自官方示例输出）并分类；第二段把超时预算算成一张表；第三段把两个实测点拆成 α、β 再给结论。三段都不需要 GPU。

# ===== 示例 1：先解析 NCCL 日志分类，再决定查什么（形状取自官方示例输出） =====
import re, collections

LOG = """node-01:1895811:1895822 [0] NCCL INFO Tree 0 : -1 -> 0 -> 1/-1/-1
node-01:1895811:1895822 [0] NCCL INFO Ring 00 : 1 -> 0 -> 1
node-01:631398:631398 [0] NCCL INFO Channel 00/0 : 0[0] -> 1[1] via P2P/CUMEM
node-01:631398:631398 [0] NCCL INFO Channel 01/0 : 1[1] -> 0[0] via SHM/direct/direct
node-01:1897709:1897731 [0] NCCL INFO Channel 00/0 : 0[0] -> 1[1] [send] via NET/Socket/0
node-01:631871:631871 [0] NCCL INFO AllReduce: 33554432 Bytes -> Algo RING proto SIMPLE channel{Lo..Hi}={0..31}
node-01:631871:631871 [0] NCCL INFO AllReduce: 1048576 Bytes -> Algo TREE proto SIMPLE channel{Lo..Hi}={0..15}
node-01:1896826:1896838 [0] NCCL INFO NCCL_SOCKET_IFNAME set by environment to eth0
node-01:1897709:1897731 [0] NCCL WARN NET/Socket : Could not find any interface for 10.0.0.0/24
node-01:1897709:1897731 [0] NCCL WARN A job is running with different NCCL version
"""

def triage(log):
    stats = collections.Counter()
    rings, tunings, warns, envs = [], [], [], []
    for line in log.strip().splitlines():
        if m := re.search(r"via (\S+)", line):
            stats[m.group(1)] += 1
        if m := re.search(r"Ring (\d+) : (.+)", line):
            rings.append((m.group(1), m.group(2).strip()))
        if m := re.search(r"(\w+): (\d+) Bytes -> Algo (\w+) proto (\w+)", line):
            tunings.append((int(m.group(2)), m.group(3), m.group(4)))
        if "NCCL WARN" in line:
            warns.append(line.split("NCCL WARN", 1)[1].strip())
        if m := re.search(r"(NCCL_\w+) set by environment to (\S+)", line):
            envs.append((m.group(1), m.group(2)))
    return stats, rings, tunings, warns, envs

stats, rings, tunings, warns, envs = triage(LOG)
print("示例 1：NCCL 日志分类")
print("  传输路径统计：", dict(stats))
print("  环：", rings)
print("  算法/协议选择：")
for size, algo, proto in sorted(tunings):
    print(f"    {size:>9} Bytes -> {algo:<5} {proto}")
print("  生效的环境变量：", envs)
print("  警告 %d 条：" % len(warns))
for w in warns:
    print("    -", w)

# ===== 示例 2：超时/重试预算表（数值全部取自官方文档口径） =====
def socket_budget(retry, sleep_ms):
    return (retry + 1) * retry / 2 * sleep_ms / 1000.0          # 官方公式 (N+1)*N/2*sleep

print("\n示例 2：超时预算（默认值 -> 出错前要等多久）")
print(f"  socket：NCCL_SOCKET_RETRY_CNT=34, SLEEP=100ms -> {socket_budget(34, 100):.1f} s（官方约 60 s）")
for t in (18, 20, 23):
    print(f"  IB：NCCL_IB_TIMEOUT={t}, RETRY=7 -> {4.096e-6*2**t*7:6.2f} s/次重试总额 "
          f"（单次超时 {4.096e-6*2**t*1000:6.1f} ms）")
print("  PyTorch ProcessGroupNCCL 默认超时：10 分钟（其他后端 30 分钟，以所装版本文档为准）")
normal_ms = 576 * 2**20 / 25e9 * 1e3
print(f"  对照：一次正常的 576 MiB AllReduce（25 GB/s）约 {normal_ms:.0f} ms；"
      f"IB 默认预算 = 它的 {30.06*1000/normal_ms:.0f}x，socket 预算 = 它的 {59.5*1000/normal_ms:.0f}x")

# ===== 示例 3：带宽不达标时，用两个实测点把差距拆到 α 与 β =====
def fit(sizes, times):
    (s1, t1), (s2, t2) = list(zip(sizes, times))
    beta = (s2 - s1) / ((t2 - t1) * 1e-6) / 1e9
    return t1 - s1 / (beta * 1e9) * 1e6, beta

def verdict(alpha, beta, expected_bw, expected_alpha=60.0):
    out = []
    if beta < 0.5 * expected_bw:
        out.append(f"β 只有链路峰值的 {beta/expected_bw:.0%}：查拓扑/rail/协议（GRAPH、TUNING 日志）")
    if alpha > 3 * expected_alpha:
        out.append(f"α 偏大（{alpha:.0f}us）：小消息或算法选择问题（树 vs 环、协议）")
    return out or ["α、β 与预期同量级：瓶颈更可能在重叠或排队，不在 NCCL 参数"]

print("\n示例 3：把实测点拆成 α、β 再下结论（期望 β≈250 GB/s，期望 α≈60us）")
cases = {
    "健康":  ([8 << 20, 256 << 20], [60 + s / (250e9) * 1e6 for s in (8 << 20, 256 << 20)]),
    "带宽腰斩": ([8 << 20, 256 << 20], [60 + s / (100e9) * 1e6 for s in (8 << 20, 256 << 20)]),
    "延迟偏大": ([8 << 20, 256 << 20], [300 + s / (250e9) * 1e6 for s in (8 << 20, 256 << 20)]),
}
for name, (sizes, times) in cases.items():
    a, b = fit(sizes, times)
    print(f"  {name:<8} α={a:7.2f}us β={b:6.2f}GB/s -> {'；'.join(verdict(a, b, 250.0))}")

三、练习#

  1. 实现：给示例 1 的 triage 加上"按 rank 分组"的能力（日志行里有 [0] 这样的 rank 字段），输出每个 rank 的算法/协议选择；说明什么情况下不同 rank 的选择不一致、以及为什么那属于配置错误。
  2. 解释：为什么官方给 socket 重试的总时间公式是 (N+1)N/2×sleep 而不是 N×sleep？把 NCCL_SOCKET_RETRY_CNT=34 代进去验证约 60 s。
  3. 对比/验证：把示例 2 的 NCCL_IB_TIMEOUT 从 20 改成 24 再算一遍，并解释"总预算 8 分钟"与"PyTorch 默认超时 10 分钟"谁会先触发。
  4. 思考：一个 8 卡任务每 200 步随机卡住一次，重启后正常。给出你的排查顺序，并说明 TORCH_NCCL_DESYNC_DEBUG、rdma statistic、ib_write_lat 三者分别能排除什么假设。
