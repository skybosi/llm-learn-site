监控与日志#

服务上线后，最怕的不是"慢了"，而是"慢了却没人知道"。前面学过的 TTFT、TPOT、吞吐这些指标，只有被持续采集、可视化、告警，才算真正进入生产状态。这一课讲 LLM 推理服务要盯哪些指标、vLLM 怎么暴露 Prometheus 指标、日志怎么记，以及如何串成 Grafana 大盘 + 告警。

一、概念讲解#

1. 推理服务要盯的四个层面#

  1. 硬件层：GPU 利用率、显存占用、温度、功耗。显存占用尤其关键——它决定了还能不能容纳更多 KV Cache；
  2. 引擎层：运行中的请求数、排队长度、KV Cache 使用块数/命中率、prefix cache 命中率、prefill/decode token 数；
  3. 服务质量层（SLO）：TTFT、TPOT、首 token 分位数（P50/P99）、端到端延迟、每秒吞吐、错误率。这是对用户承诺的核心；
  4. 业务层：请求总量、按客户/模型维度的 token 消耗、限流触发次数——这些直接关联到账单。

记住一句话：监控不是"看数字"，而是"为 SLA 和成本提供证据"。没有 P99 TTFT 的历史曲线，你既无法证明自己达标，也无法在用户投诉时定位"是哪个时刻、哪批请求慢了"。

2. vLLM 的 Prometheus 指标#

vLLM 内置 Prometheus 格式的指标暴露，默认挂在 /metrics 端点。常用指标：

指标名 含义
vllm:num_requests_running 正在运行的请求数（水位线）
vllm:num_requests_waiting 排队等待的请求数（拥塞信号）
vllm:gpu_cache_usage_perc KV Cache 使用百分比
vllm:time_to_first_token_seconds TTFT 直方图，可算 P50/P99
vllm:time_per_output_token_seconds TPOT 直方图
vllm:generation_tokens_total 累计生成 token 数
vllm:prompt_tokens_total 累计输入 token 数
vllm:request_success_total 成功请求数

这些指标本质是把上一课的"时序"变成了"可聚合的时间序列"。通过 Prometheus 的 histogram_quantile 可以算出任意分位数，进而和 SLA 对齐。

3. 日志：结构化 + 请求链路#

日志分两类：

  • 引擎日志：vLLM 自身的启动、加载、调度信息，排障第一现场；
  • 访问日志（access log）：每条请求的元信息——时间、模型名、输入/输出 token 数、TTFT、TPOT、状态码、耗时。这些字段是成本核算和用户计费的原始凭证，一定要结构化（JSON），方便后续聚合。

生产上通常让容器把日志打到标准输出（stdout/stderr），由编排层（K8s / docker 日志驱动 / fluent-bit）统一采集到 Loki / ELK。不要把日志写死在容器内的文件里——容器一重建就丢了。

4. 告警要"少而准"#

告警不是越多越好。典型的 LLM 服务告警就三条：

  1. num_requests_waiting 持续 > 阈值（如 20）超过 5 分钟 → 排队拥塞，需要扩容或降载；
  2. P99 TTFT 超过 SLA 目标（如 3s）→ 体验劣化；
  3. 错误率（5xx）超过 1% → 服务异常。

每条告警都要能回答"接到告警后我该做什么"，否则就是噪音。

二、可运行示例#

示例 1：查看 vLLM 暴露的指标#

# 服务启动后，直接抓取 Prometheus 格式指标
curl -s http://localhost:8000/metrics | grep -E "vllm:(num_requests_waiting|gpu_cache_usage_perc|generation_tokens_total)"

输出片段（示意）：

vllm:num_requests_waiting 0.0
vllm:gpu_cache_usage_perc 32.5
vllm:generation_tokens_total{model_name="llama-8b"} 123456.0

示例 2：Prometheus 抓取配置#

# prometheus.yml：让 Prometheus 周期拉取 vLLM 指标
global:
  scrape_interval: 15s
scrape_configs:
  - job_name: "vllm"
    static_configs:
      - targets: ["vllm:8000"]     # 容器网络里用服务名
    metrics_path: /metrics

示例 3：用 Python 算 P99 分位数（演示直方图的用法）#

# -*- coding: utf-8 -*-
# 演示如何从一批 TTFT 观测值算出分位数，理解 P99 的意义
import random

# 模拟 1000 次请求的 TTFT（秒）：大部分很快，少量偶发慢
random.seed(42)
ttft = [0.3 + random.random() * 0.5 for _ in range(990)]
ttft += [3.5 + random.random() * 2.0 for _ in range(10)]  # 10 个慢请求

def percentile(vals, p):
    s = sorted(vals)
    k = (len(s) - 1) * p / 100.0
    lo = int(k)
    return s[lo] if lo == k else s[lo] + (s[lo + 1] - s[lo]) * (k - lo)

print(f"平均 TTFT = {sum(ttft)/len(ttft):.2f}s")          # 平均值：被少数慢请求掩盖
print(f"P50 TTFT  = {percentile(ttft, 50):.2f}s")
print(f"P99 TTFT  = {percentile(ttft, 99):.2f}s")         # P99：暴露了那 1% 的糟糕体验

跑一遍你会发现：平均 TTFT 可能只有 0.5s 左右，但 P99 已经冲到 4s 以上——这就是为什么 SLA 必须盯分位数而非平均值。

示例 4：写一条结构化访问日志#

# 请求完成后，落一条结构化日志，供成本核算与排障
import json, time

def log_request(model, in_tokens, out_tokens, ttft, tpot, status):
    entry = {
        "ts": time.strftime("%Y-%m-%dT%H:%M:%S"),
        "model": model,
        "prompt_tokens": in_tokens,
        "completion_tokens": out_tokens,
        "ttft_ms": round(ttft * 1000),
        "tpot_ms": round(tpot * 1000),
        "status": status,
    }
    # 结构化 JSON 便于后续聚合（Loki/ELK 直接解析）
    print(json.dumps(entry, ensure_ascii=False))

log_request("llama-8b", 128, 256, 0.42, 0.018, 200)

三、练习#

  1. 起一个 vLLM 服务，用 curl /metrics 观察 num_requests_waiting 在空载时是否为 0；再用并发脚本打一批请求，看它是否上涨，验证"排队长度是拥塞信号"。
  2. 把示例 3 的慢请求占比从 1% 改成 10%，重算平均值和 P99，体会"平均值的欺骗性"随长尾加重而变大。
  3. 基于示例 2 的配置，把 Prometheus + Grafana 起起来，画一张"P99 TTFT 与 KV Cache 使用率"双轴大盘，说明两者可能如何关联（cache 打满 → 排队 → TTFT 上升）。
  4. 设计三条告警规则（排队长度、P99 TTFT、错误率），写出它们的 PromQL 表达式雏形，并说明每条告警触发后你的处理动作。
