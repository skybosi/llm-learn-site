Tiling 与数据复用：从 GEMM 讲起#

同一段矩阵乘，改成分块写法后浮点指令一条没少，实测却快好几倍。差距不在"算了多少"，而在"搬了多少"：naive 版本把绝大部分时间花在等 HBM（High Bandwidth Memory，显卡上的主存）的数据。这一课把搬运量算成一本可以逐项核对的账，并用 tiling（分块）这个通用手法把复用从 HBM 搬到片上。

一、概念讲解#

1. 先把"账"的边界定清楚#

第 3 章给过存储层次的量级：寄存器与 shared memory（共享内存，片上可编程缓存）比 HBM 快一到两个数量级，但容量小三到五个数量级（具体倍数以自己显卡的官方规格为准）。所以访存优化的第一步永远是同一个问题：这一层（HBM）到底被搬了多少字节？

衡量它的标准量是算术强度（arithmetic intensity）：浮点运算次数 ÷ 搬运字节数，单位 FLOP/Byte。它把"算得多"和"搬得多"放进同一个刻度，是判断一个 kernel 是 memory-bound（受带宽限制）还是 compute-bound（受算力限制）的最简工具。

tiling 的定义就一句话：把大矩阵切成子块，让每块在被搬上片之后被反复使用多次再丢弃。这里的"子块"有三层：grid 层的输出块（block tile）、shared memory 里的输入条带、以及每个线程自己算的那一小块（thread tile，第 6 章细讲）。

2. naive GEMM 的账：0.25 FLOP/Byte#

设 C[M,N]=A[M,K]×B[K,N]，浮点运算次数（每个输出元素 K 次乘加，各算 1 次浮点操作）：

FLOPs=2MNK

naive 写法里，每个线程负责一个输出 C[i][j]，内层循环 k 读 A[i][k] 与 B[k][j]，于是每个输出元素要读 2K 个元素：

搬运元素数=M⋅N⋅2K=2MNK

单精度下每个元素 4 字节，算术强度 =2MNK/(4×2MNK)=0.25 FLOP/Byte。这个数字和矩阵大小无关——naive GEMM 无论多大，每搬 1 字节只做 0.25 次浮点运算。

对照硬件拐点：roofline 模型的拐点 = 峰值算力 ÷ 峰值带宽。以常见数据中心 GPU 的量级（算力 1013 FLOP/s 上下、HBM 带宽 1012 Byte/s 上下）估算，拐点在 101∼102 FLOP/Byte 区间（近似值，请用自己显卡的官方规格算）。0.25 比拐点低两到三个数量级，结论很硬：这类 kernel 加再多浮点指令也没用，时间全在等数据。

3. 分块之后：搬运降 T 倍#

做法：每个 block 负责输出的一块 T×T，把 K 维按 T 切成若干段；每段把 A 的 T×T 子块和 B 的 T×T 子块从 HBM 搬进 shared memory，块内所有线程共享使用，做 T3 次乘加。

把搬运量重新数一遍：

搬运元素数=块数TM​⋅TN​​​×k 段数TK​​​×每段搬 A/B 各一块2T2​​=T2MNK​

搬运量降了 T 倍，算术强度升到 0.25T（各列数字见下一节的运行输出）。换个说法：从 HBM 搬进来的一个 A 元素，在片上被 T 个不同的输出列各用一次。

T HBM 搬运（元素） 相对 naive 算术强度 片上缓冲
8 2.68×10⁸ 8× 2.00 FLOP/B 512 B
16 1.34×10⁸ 16× 4.00 FLOP/B 2 KB
32 6.71×10⁷ 32× 8.00 FLOP/B 8 KB
64 3.36×10⁷ 64× 16.00 FLOP/B 32 KB

4. 为什么"顺序"本身就值一个数量级#

tiling 之外还有一层更朴素的收益：同一批数据，换个遍历顺序，L1/L2 的命中率就完全不同。下一节的可运行代码用一个玩具 LRU 模型量了这件事：同一块 512×512 的数据，分块内按行遍历的命中率 96.9%、有效字节比 100%；按列优先遍历（naive 内层循环的形状）命中率 0%、有效字节比 3.1%。

把它和第 3 章连起来看：合并访存（coalescing）解决"一次访存事务里有多少字节是有效的"，tiling 解决"搬上片的字节被用了几次"。有效带宽 = 事务效率 × 复用次数，两者是乘法关系。

5. 常见坑#

  • 只在 block 层分块，线程层不复用：block 内每个线程只算一个输出，A、B 条带在 shared memory 里被反复读，读放大只是从 HBM 转移到了 shared memory。
  • 边界不处理：M、N、K 不是 T 的整数倍时，越界读会读到脏数据甚至崩，必须显式判边界（本课代码用 min(T, M-i) 处理）。
  • 以为 tile 越大越好：搬运量虽然按 1/T 降，但片上容量是硬约束；tile 变大还直接吃寄存器，这是第 4 课的主题。
  • 只盯 FLOPs：算术强度没到拐点之前，优化浮点指令的收益是 0。
  • 累加器位置写错：乘加结果必须留在寄存器里跨 k 段累积，每段都写一次 HBM 会把降下来的搬运量加回去。

二、可运行代码示例#

下面三段纯 numpy/Python（无 GPU、无额外依赖）分别做三件事：算清搬运账、实现分块 GEMM 并验证结果与搬运次数、用玩具 LRU 量遍历顺序对命中率的影响。

# ===== 本课示例：GEMM 的搬运账本 + 分块实现 + 命中率模型 =====
import numpy as np
from collections import OrderedDict

# ---------- 1. 搬运量账本：naive vs tiled ----------
def gemm_traffic(M, N, K, T, item=4):
    """返回 HBM↔SM 的元素搬运次数。naive：每个输出元素读 K 个 A + K 个 B。"""
    naive = 2 * M * N * K
    tiled = (M // T) * (N // T) * (2 * K * T)   # 每个块搬 A/B 各一个 T×K 条带
    return naive, tiled

M = N = K = 1024
naive, _ = gemm_traffic(M, N, K, 1)
print(f"GEMM {M}x{N}x{K}，FLOPs = {2*M*N*K:,}")
print(f"{'T':>3} {'HBM 搬运(元素)':>16} {'相对 naive':>10} {'算术强度':>10} {'片上缓冲(B)':>12}")
for T in (8, 16, 32, 64):
    _, t = gemm_traffic(M, N, K, T)
    print(f"{T:>3} {t:>16,} {naive/t:>9.0f}x {2*M*N*K/(4*t):>9.2f} {2*4*T*T:>12,}")
print(f"naive 算术强度 = {2*M*N*K/(4*naive):.2f} FLOP/Byte；A/B/C 驻留 {3*M*M*4/2**20:.0f} MiB\n")

# ---------- 2. 分块 GEMM：结果正确 + 搬运次数与公式吻合 ----------
def blocked_gemm(A, B, T):
    M, K = A.shape; N = B.shape[1]
    C = np.zeros((M, N), dtype=A.dtype); loads = stores = 0
    for i in range(0, M, T):
        for j in range(0, N, T):
            acc = np.zeros((min(T, M - i), min(T, N - j)), dtype=A.dtype)
            for k in range(0, K, T):
                at, bt = A[i:i+T, k:k+T], B[k:k+T, j:j+T]
                loads += at.size + bt.size      # 一次搬运，T 次复用
                acc += at @ bt
            C[i:i+T, j:j+T] = acc; stores += acc.size
    return C, loads + stores

rng = np.random.default_rng(0)
A = rng.standard_normal((256, 256), dtype=np.float32)
B = rng.standard_normal((256, 256), dtype=np.float32)
ref = A @ B
for T in (16, 32):
    C, moved = blocked_gemm(A, B, T)
    _, t_formula = gemm_traffic(256, 256, 256, T)
    print(f"T={T:<3} max|C-ref|={np.abs(C-ref).max():.2e}  实测搬运={moved:,}"
          f"  公式={t_formula + 256*256:,}")

# ---------- 3. 遍历顺序决定命中率：256 行的玩具 L2 ----------
class LRU:
    def __init__(self, n):
        self.n, self.m, self.hits, self.misses = n, OrderedDict(), 0, 0
    def touch(self, line):
        if line in self.m:
            self.hits += 1; self.m.move_to_end(line); return
        self.misses += 1; self.m[line] = None
        if len(self.m) > self.n:
            self.m.popitem(last=False)

LINE, K2, N2 = 32, 512, 512               # 一条 line 放 32 个 float32 = 128 字节
line_of = lambda k, j: k * (N2 // LINE) + j // LINE
def walk(tiled, T=32):
    c = LRU(256)
    if tiled:
        for kk in range(0, K2, T):
            for jj in range(0, N2, T):
                for k in range(kk, kk + T):
                    for j in range(jj, jj + T):
                        c.touch(line_of(k, j))
    else:
        for j in range(N2):
            for k in range(K2):
                c.touch(line_of(k, j))
    return c

print()
tot = K2 * N2
for name, c in (("分块内按行遍历 T=32", walk(True)), ("列优先遍历（naive）", walk(False))):
    useful = tot * 4 / (c.misses * LINE * 4)
    print(f"{name:<20} 访问 {tot:,} | 缺行 {c.misses:>7,} | 命中率 {c.hits/tot:6.1%}"
          f" | 有效字节比 {useful:6.1%}")

三、练习#

  1. 实现：在 blocked_gemm 之外再加一层线程级 tile——每个线程算 4×4 个输出，统计每个线程的累加器数量与 shared memory 访问次数，说明总的 HBM 搬运量是否变化、shared memory 访问量是否变化。
  2. 解释：为什么算术强度是 0.25T 而不是 0.25T2？（提示：分块同时降低了搬运量、但没有改变浮点运算总数。）
  3. 对比/验证：把玩具 L2 的 LINE 改为 8、LRU(256) 改为 LRU(64)，两个遍历顺序的命中率各是多少？再把 cache 放大到能装下一整列（≥512 行），解释列优先为什么也能命中。
  4. 思考：如果 tile 只受 shared memory 容量限制（例如每块最多用 100 KB），你会不会把 T 取到最大？要回答这个问题，还需要哪两个量？（分别对应第 4 课的 occupancy 与 thread tile 的寄存器占用。）
