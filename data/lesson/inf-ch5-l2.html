流水线并行与数据并行#

上一课的张量并行解决的是"单个矩阵都装不下"的场景。但分布式推理还有另外两种更宏观的切法：流水线并行（Pipeline Parallelism，PP）按"层"把模型切成若干段，各段放到不同卡上，像工厂流水线一样接力；数据并行（Data Parallelism，DP）则是把完整模型复制多份，各处理一批不同的请求。三者解决的是不同层次的瓶颈，真实系统里往往混着用。这一课把 PP 和 DP 讲清楚，并给出选型思路。

一、概念讲解#

1. 流水线并行：按层切，接力处理#

流水线并行的对象是层。一个 80 层的模型切 4 段，每段 20 层，分别放到 4 张卡上。一个请求先由卡 0 算前 20 层，把激活值传给卡 1，卡 1 算完再传给卡 2……像流水线一样逐段前进。

它的优点很明显：单卡显存占用只有整模型的 1/N，通信只发生在段与段的边界（传输的是激活值，量小、次数少），因此 PP 天然适合跨机器部署——用普通以太网连接多台服务器即可，不必依赖 NVLink。

但它有一个致命缺点：流水线气泡（bubble）。同一时刻只有一张卡在"干活"，其余卡在等上家的输出，GPU 利用率很低。解决思路是把一个请求的序列切成多个 micro-batch（微批次），交错地喂进流水线，让后面的卡在处理微批次 i 的同时，前面的卡已经在算微批次 i+1。业界常用的 1F1B（one-forward-one-backward） 调度就是在训练里通过交错前向/反向来压气泡；推理只有前向，问题更单纯，但气泡依然存在，段数越多、段间负载越不均衡，气泡越明显。

2. 数据并行：复制模型，分摊请求#

数据并行把完整模型复制到每张卡，把请求流按批分给各卡独立处理。它不切模型，因此单卡必须放得下整个模型（否则要配合量化、或改用 TP/PP）。对推理而言，DP 是最"便宜"的扩展方式：加卡 = 加吞吐，几乎线性扩展，卡之间推理阶段不需要同步（不像训练要 AllReduce 梯度），只有参数更新时（比如在线更新权重）才通信一次。

DP 的短板是：它只增加吞吐，不降低单个请求的延迟；而且每张卡都要存一份完整 KV Cache，显存没有被分摊。所以 DP 适合"高并发、请求独立、单卡装得下"的在线服务场景，PP/TP 适合"单模型超大、单卡装不下"的场景。

3. 三种并行的对比与组合#

维度 张量并行 TP 流水线并行 PP 数据并行 DP
切分对象 单个权重矩阵 模型的层 完整模型（复制）
单卡是否装得下全模型 否 否 是
通信频率 高（每层多次） 低（仅段边界） 极低（仅参数更新）
通信量 中（权重/激活） 小（激活值） 中（梯度/参数，训练时）
对互联带宽要求 极高（需 NVLink） 低（以太网即可） 低
主要收益 降延迟 + 降单卡显存 降单卡显存 提吞吐

一句话选型经验：先把单卡显存问题交给 TP/PP，再把吞吐问题交给 DP。常见组合如 70B 模型用 TP=4 × PP=2 × DP=3 铺满一个 24 卡集群：4 卡切张量、2 段切流水线、3 份做数据并行副本。

4. 流水线并行的负载均衡#

切流水线时若各段层数不均（或某些层更耗时），慢的那张卡会成为瓶颈，其余卡空转等它——气泡放大。因此切分时要按实际每层计算量而不是简单按层数均分，让各段耗时尽量接近。这是 PP 调优里最容易踩的坑。

二、可运行代码示例#

示例 1：用 Python 模拟流水线气泡与微批次调度#

下面代码不依赖 GPU，用一个"每段耗时不同"的抽象模型，直观展示：单请求串行 = 满屏气泡；切成微批次交错喂入后利用率显著提升。

import time

# 假设模型切成 4 段（4 张卡），每段处理一个微批次的耗时（秒）
stage_cost = [0.4, 0.5, 0.3, 0.4]
n_stages = len(stage_cost)

def pipeline(micro_batches):
    """模拟流水线执行：返回总耗时与各卡实际忙碌时长。"""
    busy = [0.0] * n_stages
    # 每个微批次按顺序经过各段；第 m 个微批到达第 s 段时，要等 s 段空闲
    stage_ready = [0.0] * n_stages      # 每段最早可开始处理下一任务的时间
    for m in range(micro_batches):
        t = 0.0
        for s in range(n_stages):
            t = max(t, stage_ready[s])  # 上家输出 + 本段空闲，取较晚者
            stage_ready[s] = t + stage_cost[s]
            busy[s] += stage_cost[s]
            t += stage_cost[s]
    makespan = max(stage_ready)
    util = [b / makespan for b in busy]
    return makespan, util

# 串行：只喂 1 个微批次（等价于不切微批次，气泡最大）
ms1, u1 = pipeline(1)
print(f"1 个微批次：总耗时 {ms1:.2f}s，各卡利用率 {[f'{u:.0%}' for u in u1]}")

# 交错：喂 8 个微批次
ms8, u8 = pipeline(8)
print(f"8 个微批次：总耗时 {ms8:.2f}s，各卡利用率 {[f'{u:.0%}' for u in u8]}")
print(f"吞吐提升倍数（每微批平均耗时）：{(ms1/1)/(ms8/8):.2f}x")

可以看到，微批次一多，前面卡的空等被后续微批次填满，利用率逼近 100%——这就是 1F1B 类调度在推理里"填气泡"的原理。

示例 2：vLLM 中指定 PP 与 DP#

vLLM 用 --pipeline-parallel-size 控制 PP 段数，数据并行则体现在"同一模型起多个服务实例、前置负载均衡"（服务化章节详述）。TP + PP 可叠加：

# 8 张卡：TP=4 切张量，PP=2 切流水线（4×2=8）
vllm serve meta-llama/Llama-3.1-70B-Instruct \
    --tensor-parallel-size 4 \
    --pipeline-parallel-size 2 \
    --dtype bfloat16

经验法则：TP 吃高速互联（单机内），PP 吃网络（可跨机）。先定 TP 让它等于单机卡数，剩下的卡数再摊给 PP 和 DP。

三、练习#

  1. 把示例 1 的 stage_cost 改成 [0.5, 0.1, 0.1, 0.1]（第一段明显更慢），观察微批次增多后利用率是否仍能逼近 100%；说明瓶颈段对整体吞吐的决定作用。
  2. 推导：4 段流水线、段均耗时 T、共 M 个微批次时，理想 makespan 约为 (M + 3) × T；与 M=1 时 4T 对比，解释"微批次越多气泡占比越低"。
  3. 结合上一课，解释为什么 TP 通常只在单机内、PP 可以跨机；若一个 70B 模型单卡装不下而你有 2 台 4 卡服务器，给出一个 TP/PP/DP 的组合方案并说明理由。
  4. 用 vLLM 分别以 tensor_parallel_size=1/2/4 跑同一模型，记录 TTFT 与最大吞吐，观察 TP 提升是否随卡数递减（通信占比上升）。
