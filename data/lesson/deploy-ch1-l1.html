部署场景分类#

部署不是"起个服务"这么简单——同样的模型，做成客服机器人、做成离线批量打分、做成手机端侧助手，对延迟、吞吐、成本、安全的要求几乎完全不同。本课是整个部署实战的地图：先学会用一套统一维度给任何 LLM 部署需求"画像"，后续的需求分析、选型、调优才有落点。学完本课，你应当能拿到一个业务需求，在 5 分钟内说出它属于哪类场景、关键指标是什么、大致该用什么形态承载。

一、概念讲解#

1. 四个分类维度#

任何 LLM 部署需求，都能用下面四个维度切分。它们不是相互独立的，通常组合成一个"场景画像"：

  • 交互模式：在线交互（一问一答，用户盯着等结果）还是离线批处理（提交一批任务，稍后取结果）还是流式（逐 token 边生成边返回）；
  • 部署位置：公有云（租 GPU 实例）、私有化/本地机房（数据不出域）、端侧/边缘（直接跑在手机、车载、工业设备上）；
  • 延迟敏感度：对 TTFT（首 token 延迟）和 TPOT（每 token 延迟）要求多严格，是"秒级可等"还是"毫秒级体感"；
  • 并发规模：同时服务的用户数是 10、1 万，还是 100 万——这决定单卡够不够、要不要多副本。

2. 六大典型场景#

场景 交互模式 延迟要求 典型指标 代表产品/用途
对话助手 / Chat 在线 + 流式 高：TTFT 0.3–2s，TPOT 30–80 ms/token P99 延迟、QPS 智能客服、Copilot、AI 助理
内容生成 / 批量 离线批处理 低：分钟级可等 吞吐 token/s、单位成本 营销文案、SEO 文章、代码补全语料
端侧 / 边缘 本地推理 中：本地毫秒级，但受算力限制 首 token、内存占用、功耗 手机输入法、离线翻译、IoT 质检
实时流式 / RAG 在线 + 流式 高，且长上下文 TTFT、检索+生成总延迟 文档问答、知识库助手
Agent / 工具调用 在线多轮 中高，多次调用 单轮延迟、成功率 自动办公、代码 Agent
评估 / 离线评测 批量 低 吞吐、成本 评测集打分、RLHF 数据生产

一句话记忆：在线看延迟，离线看吞吐，端侧看显存和功耗，多租户看并发和隔离。

3. 为什么"先分类"能省钱#

分类决定了你后续所有决策的优先级。同样是 7B 模型：

  • 做在线客服：你优先选 vLLM 这类 PagedAttention + continuous batching 的引擎，把延迟压在 SLO 内；
  • 做夜间批量生成 100 万条文案：你优先选能打满吞吐的配置（大批量、甚至 spot 实例），延迟无所谓；
  • 做手机离线翻译：你只能选 GGUF 量化 + llama.cpp，因为端侧没有 80GB 显存。

先分类再选型，能避免"用高延迟引擎做在线服务"或"用昂贵常驻 GPU 跑离线任务"这类最贵的错误。

二、可运行示例#

下面的脚本把"场景画像"变成结构化数据：输入几个布尔/数值特征，输出推荐的场景标签和该场景的关键指标，帮助你快速分类。

# -*- coding: utf-8 -*-
# 部署场景分类器：根据交互模式/延迟/并发等特征，输出场景画像与关键指标

def classify(interactive: bool, streaming: bool, latency_ms: float,
             max_concurrency: int, device_memory_gb: float = 80):
    """interactive: 是否在线一问一答; streaming: 是否流式;
       latency_ms: 能接受的 TTFT 上限(毫秒); max_concurrency: 峰值并发用户数;
       device_memory_gb: 目标设备可用显存(GB)。"""
    # 关键指标 = f(场景)，先按"位置"粗分
    if device_memory_gb < 16:
        tag = "端侧/边缘"
        metrics = "首 token 延迟、内存占用、功耗"
    elif not interactive:
        tag = "离线批处理"
        metrics = "吞吐(token/s)、单位成本(token/美元)"
    elif streaming and latency_ms <= 2000:
        tag = "在线对话 / RAG（流式）"
        metrics = "P99 TTFT、P99 TPOT、QPS"
    else:
        tag = "在线非流式 / API"
        metrics = "P99 端到端延迟、并发数"

    # 关键指标里补充并发维度
    if max_concurrency > 1000:
        metrics += "、多副本/自动扩缩容"
    return tag, metrics

cases = [
    ("客服机器人",   dict(interactive=True,  streaming=True,  latency_ms=1500, max_concurrency=2000, device_memory_gb=80)),
    ("夜间批量文案", dict(interactive=False, streaming=False, latency_ms=60000, max_concurrency=8,    device_memory_gb=80)),
    ("手机离线翻译", dict(interactive=True,  streaming=True,  latency_ms=500,  max_concurrency=1,    device_memory_gb=8)),
    ("代码 Agent",   dict(interactive=True,  streaming=True,  latency_ms=3000, max_concurrency=500,  device_memory_gb=80)),
]
for name, feat in cases:
    tag, metrics = classify(**feat)
    print(f"{name} -> 场景：{tag} ｜ 关键指标：{metrics}")

运行后你会看到四个需求被分到四类，各自的关键指标完全不同——这提醒你：先问清"在线还是离线、延迟多严、并发多大"，再谈技术方案。

三、练习#

  1. 补充特征：给 classify 增加"是否需要工具调用 / 多轮"特征，让 Agent 场景被单独识别出来，并给出它的关键指标。
  2. 反推场景：一个产品要求"P99 TTFT ≤ 1.5s、峰值 5000 QPS、数据不能出内网"，写出它的完整场景画像（交互模式、位置、延迟、并发），并判断端侧/离线/在线哪一类。
  3. 对比延迟与吞吐：解释为什么"离线批处理"可以容忍分钟级延迟，而"对话助手"不行——从成本角度说明两种场景各自该优先优化什么。
  4. 梳理你的业务：选一个你熟悉的 LLM 产品（或设想一个），按本课四维度写出它的画像，并列出它最该盯的 3 个指标。
