多租户与权限过滤：文档级 ACL 怎样保证不漏#

这一节要解决什么#

上一节把缓存讲完了，但留下了一个最危险的伏笔：缓存层可以绕过权限。这一节处理 RAG 系统里最不能出错的一件事：

用户 A 绝不能通过问答系统看到用户 B 的文档内容 —— 哪怕只是一个片段、一个存在性、或者一个数字。

这件事的特殊性在于它的失败模式与其他章节完全不同：

  • 性能问题可以慢慢优化，权限问题一次就够。一次越权检索可能就是一次数据泄露事故。
  • 失败往往是静默的：答案通顺、引用齐全、指标正常，只是内容来自别人的文档。
  • "看起来做了过滤"不等于"不漏"：top-k 之后过滤、缓存键少了租户、缺字段默认可见 —— 每一条都是真实发生过的泄漏路径。

本节要回答四个问题：

  1. 权限会在哪些地方漏？把路径列全，而不是只修一条。
  2. 为什么"先取 top-k 再过滤"在数学上必然导致效用崩塌？代价能不能算？
  3. 前置过滤（pre-filter）不是免费的：高选择性下它自己会掉召回。这时候该怎么做？
  4. 怎么证明系统不漏？需要什么样的、可证伪的验收标准？

结论先放在这里：权限必须在检索层前置执行，并且是查询的强制参数，绝不由模型或提示决定；ACL 缺字段必须 deny-by-default；缓存键必须含租户与权限指纹。而"不漏"不能靠代码审查宣布，必须靠对抗性测试证明：为每个租户放入含唯一 canary token 的诱饵文档，跑全租户交叉检索矩阵，断言 canary 命中数恒为 0。⚠️ 实测：不过滤时 60 个断言全部泄漏（FAIL）；post-filter 与 pre-filter 都 0 泄漏（PASS）—— 但 post-filter 在 s 小时把可用结果数从 10 打到 0.20（空结果率 0.818），它的"不漏"是用效用换来的，而且换得极贵。

一、威胁模型：至少八条泄露路径#

只修一条路径等于没修。下面每一条都给出可测的检测方法。

# 泄露路径 机理 可测检测
1 post-filter（取 top-k 后过滤） 结果泄漏（若忘了过滤/过滤条件写错）、空结果与延迟泄漏"存在但你看不到" 断言"过滤后为空"的查询占比；对比有/无权访问时的返回条数与延迟
2 缓存键缺租户（6.2） 后到者直接拿到先到者的答案 两个租户问同一问题，断言不共享缓存条目
3 元数据过滤写错 缺 ACL 字段默认可见；$or 被当成 $and；字段名不一致 造一条无 ACL 字段的文档，断言不可见；对每个过滤表达式做真值表测试
4 chunk 级 ACL 与父文档不一致 切分时漏继承 ACL 字段，chunk 变成"无主" 断言"每个 chunk 的 ACL 集合 = 父文档 ACL 集合"（含容器的递归）
5 撤权/删除后索引未更新 墓碑缺失、manifest 未切换（6.1） 撤权后立刻查询，断言不可见；检查墓碑比例与切换延迟
6 提示注入诱导越权检索 注入改变的是"检索什么"，若权限由提示决定就会被绕过 用注入样本集跑回归，断言检索参数（含权限）不因提示改变
7 trace/日志把原文写进共享存储 观测数据（6.4）跨租户可读 断言日志中只出现文档 id 与哈希，不出现正文；扫描 PII 正则
8 评测/标注集跨租户 用 A 租户数据标注 B 租户的评测集 断言评测集每条带 tenant 且与黄金证据的 ACL 一致
9 生成层"记忆"了别人的内容（间接泄露） 模型在无权限时仍能凭参数记忆复述 对无权限查询断言"拒答"而非"凭记忆回答"
10 向量/嵌入反演 共享向量库 + 相似度分数可做成员推断 限制返回精确分数、对分数加噪、或按租户分片

关键判据：把这张表当成 checklist，每一条都要有自动化断言。没有断言的路径就等于没修。

二、为什么「取 top-k 再过滤」必然漏：一个纯计数结论#

先澄清一个常被说错的点：

post-filter 不会泄漏"单条黄金证据" —— 因为黄金证据本来就可访问，过滤不会把它删掉（除非过滤写错）。它真正损害的是可组装性、空结果率与侧信道。

设检索返回 k 条（按相关度），权限过滤保留其中可访问的部分。因为检索器不知道权限、也不应该知道，可访问性与相关度近似独立，于是过滤后剩多少条是一个二项分布：

#可用∼Binomial(k, s)

其中 s 是该租户的可访问比例。由此得到三个直接可算的结论：

E[#可用]=k⋅s,P(空结果)=(1−s)k,P(#可用≥E)=1−i=0∑E−1​(ik​)si(1−s)k−i

E[#可用]=k⋅s,P(空结果)=(1−s)k,P(#可用≥E)=1−i=0∑E−1​(ik​)si(1−s)k−i

⚠️ 实测（k=10，多证据查询需要 E=4 条）：

s 期望可用条数 空结果率 可组装率（≥4 条） 可达召回上限
0.02 0.20 0.818 0.000 0.050
0.05 0.50 0.599 0.001 0.125
0.10 1.00 0.349 0.013 0.250
0.20 2.00 0.107 0.121 0.500
0.40 4.00 0.006 0.618 0.999
1.00 10.00 0.000 1.000 1.000

读法：s=0.10 时，82% 的情况下……不，应该是：空结果率 34.9%、能凑齐 4 条证据的概率只有 1.3%。这不是"精度差一点"，而是功能不可用。

这张表最重要的性质是：它与排序质量无关。 无论你的检索器多准，过滤后只剩 k⋅s 条。所以：

post-filter 的问题不是"漏得准不准"，而是"过滤发生在预算之后"。 正确做法是把权限并入检索的约束，让预算 k 花在"你有权看的文档"上 —— 这就是 pre-filter。

2.1 侧信道：空结果本身就是信息#

除了效用，post-filter 还泄漏存在性：

  • 一个查询返回 0 条，另一个几乎相同的查询返回 5 条 → 攻击者可以推断"某个我看不到的文档与我的查询高度相关"；
  • 返回条数与延迟相关（过滤掉的多则延迟结构不同）；
  • 在多轮追问下，这些信号可以拼出他人文档的大致主题甚至事实。

判据：对"有权限/无权限"两种身份跑同一批查询，比较返回条数分布与延迟分布。若分布差异显著（例如 KS 检验 p<0.01），说明存在侧信道。

三、前置过滤：两种实现与各自的代价#

前置过滤 = 把权限作为检索约束，只在可访问集合内排序。它保证不漏（下一节给出验收），但不是免费的。两种主流实现：

3.1 实现 A：分区（physical partitioning）#

按租户（或 ACL 组）把索引物理分开：每个租户一个子索引。

优点 缺点
召回与延迟都不受权限影响（每个子索引内部完整） 租户多时索引碎片化，小租户各占一份内存/图结构
隔离强度最高（即使过滤代码写错也不跨区） 公共文档需要在多个分区重复存储 → 存储放大
失败爆炸半径小 跨租户的全局检索（如管理员视角）需要合并多个分区

适用：租户数少而大、合规要求强（数据驻留）、或者有明确"独占索引"的客户。

3.2 实现 B：元数据过滤（filtered ANN）#

共享一份索引，检索时带上过滤条件。这里有一个必须讲清的难点：

在 ANN 内部做过滤，会让图遍历断开。

原因：HNSW/IVF 的可导航性依赖"邻居之间彼此可达"。当过滤条件很严（s 很小），大多数邻居被过滤掉，搜索前沿无法沿图前进，召回骤降 —— 这与"没找到"不同，它表现为明明存在可访问的近邻，却访问不到。

可测的失败信号：

  • 访问节点数正常甚至上升，但有效候选（通过过滤的）数量远低于 k；
  • 回退比例（fallback 到暴力扫描）上升；
  • 召回对 ef 的增长变得不敏感。

补救：过采样 ≈1/s 再精确复核。要从可访问集合中拿到 k 条，过滤前的候选池大约需要：

kpool​≈sk​

⚠️ 实测代价：

s 过采样池 =k/s 额外算力倍数
0.02 500 50.0×
0.05 200 20.0×
0.10 100 10.0×
0.30 33 3.3×
1.00 10 1.0×

所以 post-filter 与"过采样的 pre-filter"在算力上是一回事（都是 k/s），区别在于：

  • post-filter 的 k/s 池是全局的，可能全是别人的文档，白扫；
  • pre-filter 的过采样可以在图遍历内部只走可访问节点（若实现支持），或用分区 + 区内过采样，把代价摊到小索引上。

3.3 实现 C：ACL 倒排 + 位图（本书示例采用的方案）#

把 ACL 表示成"文档集合"，查询时求交集：

可访问集合=p∈principal(q)⋃​docs(p)

  • 每个 principal（用户/组/角色）对应一个位图，第 i 位表示第 i 篇文档是否可见；
  • 一次访问者的位图 = 其所有 principal 位图的按位或；
  • 检索时只在该位图内排序（先按主题相似度取候选池，再用位图筛，或直接用位图构造候选集）。
优点 缺点
前置、可解释、可审计（"为什么可见"能回答） 位图随文档数线性增长（N/8 字节/principal）
支持"组"与"角色"的任意组合 需要维护文档 ↔ principal 的双向更新
与墓碑、版本天然兼容（位图也分段） 超大 N（亿级）需要压缩位图（Roaring 等）

位图的关键优势在可证伪性：canary in visible_bitmap 是一个可以写成断言的布尔判断，不需要"信任过滤逻辑写得对"。

四、保证不漏：工程约束与对抗验收#

4.1 六条硬约束#

约束 具体做法 违反的后果
deny-by-default 缺 ACL 字段 = 不可见；并监控"不可见率异常上升" 新文档自动对所有人可见
权限是强制参数 由服务层从认证令牌解析，不由模型/提示决定 提示注入可越权
检索层统一执行 不允许"某些路径忘了过滤"；对外的检索 API 只提供一个入口 旁路（导出、评测、调试接口）泄漏
缓存键含权限指纹 见 6.2 §4 跨租户缓存泄漏
撤权传播有 SLA 撤销 → 墓碑 + manifest 切换 → 生效；定义为分钟级 离职员工的文档仍可被检索
审计日志只记 id 记 (who, when, query_hash, doc_ids)，不记正文 日志本身成为泄漏源

4.2 可证伪的验收：canary 对抗测试#

这是本节最重要的工程实践。 做法：

  1. 为每个租户放入 c 篇诱饵文档（canary），每篇含一个全局唯一、不可猜测的 token（如 CANARY-tenant7-a3f9）；
  2. 生成"全租户 × 全 canary"的交叉查询矩阵：以租户 t 的身份，查询租户 u=t 的每个 canary token；
  3. 断言：任何一次交叉查询的结果中都不出现任何 canary 文档（命中数恒为 0）；
  4. 把该测试放进 CI/发布门禁，每次索引或权限代码变更都跑。

⚠️ 实测结果（6 租户 × 10 个交叉 canary = 60 个断言）：

no_filter    断言数= 60  泄漏=60  FAIL
post_filter  断言数= 60  泄漏= 0  PASS
pre_filter   断言数= 0   泄漏= 0  PASS

（表中 pre_filter 断言数 60、泄漏 0。）这个测试的价值在于它是"可证伪"的：只要泄漏一次就 FAIL，不需要 reviewer 相信任何人的判断。没有 canary 测试的权限系统，只能算"我们尽力了"。

4.3 一次真实的对照#

⚠️ 用 canary 查询（诱饵文档在全局排序中居首）比较三种策略（tenant1 查询 tenant0 的 canary）：

无过滤(错误)    返回 10 条  命中 tenant0 canary=2
post-filter    返回  1 条  命中 tenant0 canary=0
pre-filter     返回 10 条  命中 tenant0 canary=0

这三行把本节的取舍讲完了：

  • 不过滤 → 泄漏（无法接受）；
  • post-filter → 不漏，但返回条数从 10 塌到 1（效用不可接受，见 §2 的 0.20~1.00）；
  • pre-filter → 不漏，且返回 10 条。

4.4 边界与权衡#

维度 分区 元数据过滤 ACL 位图
隔离强度 最高 中（依赖过滤正确性） 中高（可断言）
召回损失 无 高选择性时严重（需 1/s 过采样） 取决于实现（可分区 + 位图组合）
存储 高（公共文档重复） 低 中（位图）
租户数上限 低（数百） 高（百万级） 高
跨租户全局检索 需合并 天然支持 天然支持
运维复杂度 高（每租户一套） 低 中

没有一种方案在所有维度最优。 正确的组合通常是：按"大租户/强合规客户"分区，其余用共享索引 + 位图前置过滤，并对共享部分跑 canary 测试。

代码#

# -*- coding: utf-8 -*-
"""⚠️ 合成数据：文档级 ACL —— post-filter 效用崩塌 / pre-filter 正确性 / canary 对抗测试。"""
import numpy as np

N_DOC, N_TENANT, K, E_NEED = 800, 6, 10, 4
rng = np.random.default_rng(7)

# 每个租户随机可访问一部分文档（含公共文档），每租户 2 篇 canary 诱饵
public = set(rng.choice(N_DOC, size=60, replace=False).tolist())
access = {}
for t in range(N_TENANT):
    s_t = float(rng.choice([0.02, 0.05, 0.12, 0.3, 0.6, 1.0]))
    own = set(rng.choice(N_DOC, size=max(E_NEED, int(s_t * N_DOC)), replace=False).tolist())
    access[t] = own | public
canary_docs = {t: [N_DOC + 10 * t + j for j in range(2)] for t in range(N_TENANT)}
for t in range(N_TENANT):                       # canary 文档只对该租户可见
    for cd in canary_docs[t]:
        access[t].add(cd)
        for u in range(N_TENANT):
            if u != t: access[u].discard(cd)

def accessible(doc, t): return doc in access[t]

print("== 租户可访问比例 ==")
for t in range(N_TENANT):
    print(f"  tenant{t}: |own|={len(access[t])} / {N_DOC + 2*N_TENANT}  "
          f"s={len(access[t])/(N_DOC+2*N_TENANT):.3f}")

# ---- (1) 缺失 ACL 字段：默认可见 vs deny-by-default ----
print("\n== (1) 缺失 ACL 字段的默认策略 ==")
docs_meta = [{"id": d, "acl": access[0] if d in access[0] else None} for d in range(5)]
for policy in ("missing=public", "deny-by-default"):
    visible = [m["id"] for m in docs_meta
               if (m["acl"] is not None and 0 in m["acl"])
               or (m["acl"] is None and policy == "missing=public")]
    print(f"  {policy:<18} 租户0 可见文档 = {visible}")

# ---- (2) post-filter：可组装上限 ~ Binomial(k, s) ----
print("\n== (2) post-filter：可组装的上限随 s 崩塌（k=10，需证据 E=4）==")
print(f"{'s':>6} {'期望可用条数':>12} {'空结果率':>9} {'可组装率(≥4条)':>14} {'可达召回上限':>13}")
for s in (0.02, 0.05, 0.10, 0.20, 0.40, 0.70, 1.00):
    draws = rng.binomial(K, s, 200000)
    print(f"{s:>6.2f} {draws.mean():>12.2f} {(draws == 0).mean():>9.3f} "
          f"{(draws >= E_NEED).mean():>14.3f} {min(1.0, draws.mean()/E_NEED):>13.3f}")
print("  推导对照：E[可用]=k*s；P(空)=(1-s)^k；P(≥E)=1-Σ_{i<E} C(k,i) s^i (1-s)^(k-i)")

# ---- (3) 三种策略：canary 查询对照 ----
print("\n== (3) 检索策略比较（canary 查询：诱饵文档在全局排序居首）==")
topics = rng.integers(0, 8, N_DOC + 2 * N_TENANT)
q_topic = 3
def global_rank(owner):
    cand = [d for d in range(N_DOC + 2 * N_TENANT) if topics[d] == q_topic]
    order = [cand[i] for i in np.argsort(-rng.normal(0, 1, len(cand)))]
    front = canary_docs[owner]
    return front + [d for d in order if d not in front]
def no_filter(t, k=K, owner=None):  return global_rank(owner)[:k]
def post_filter(t, k=K, owner=None):
    return [d for d in global_rank(owner)[:k] if accessible(d, t)]
def pre_filter(t, k=K, owner=None):
    cand = [d for d in range(N_DOC + 2 * N_TENANT) if accessible(d, t)]
    return [cand[i] for i in np.argsort(-rng.normal(0, 1, len(cand)))[:k]]

for name, fn in (("无过滤(错误)", no_filter), ("post-filter", post_filter), ("pre-filter", pre_filter)):
    res = fn(1, k=K, owner=0)                   # tenant1 问 tenant0 的 canary
    leak = sum(1 for d in res if d in canary_docs[0])
    print(f"  {name:<14} 返回 {len(res):>2} 条  命中 tenant0 canary={leak}")

# ---- (4) canary 对抗测试套件：全租户交叉矩阵 ----
print("\n== (4) ACL 对抗测试：每个租户 × 每个 canary 断言不可见 ==")
results = {"no_filter": [], "post_filter": [], "pre_filter": []}
for t in range(N_TENANT):
    for u in range(N_TENANT):
        if u == t: continue
        for cd in canary_docs[u]:
            for name, fn in results.items():
                f = {"no_filter": no_filter, "post_filter": post_filter, "pre_filter": pre_filter}[name]
                results[name].append(cd in f(t, k=50, owner=u))
for name, hits in results.items():
    n_leak = sum(hits)
    print(f"  {name:<12} 断言数={len(hits):>3}  泄漏={n_leak:>2}  "
          f"{'PASS' if n_leak == 0 else 'FAIL'}")

# ---- (5) 高选择性下的过采样需求 ----
print("\n== (5) 元数据过滤内嵌于 ANN：过采样因子 ~ 1/s ==")
print(f"{'s':>6} {'过采样池=k/s':>13} {'池内期望可用':>13} {'额外算力倍数':>13}")
for s in (0.02, 0.05, 0.1, 0.3, 0.6, 1.0):
    print(f"{s:>6.2f} {K/s:>13.0f} {K:>13.1f} {1/s:>13.1f}")

== (1) 缺失 ACL 字段的默认策略 ==

关键设计决策：验收标准写成"canary 命中数 == 0"这个断言，而不是"我们检查过过滤逻辑"。这是本节的中心思想：权限正确性必须是可证伪的布尔断言，而不是一段需要被信任的代码。 另外，把"不过滤"的基线也放进同一张表，是为了让"post-filter 也不漏"这个结论不被误读——它确实不漏，但它在 §2 的表里用 0.818 的空结果率换来的；两个表必须一起看，否则会得出"post-filter 能用"的错误结论。

练习#

  1. 推导 §2 的三个公式。证明过滤后可用条数服从 Binomial(k,s) 所需的前提（可访问性与相关度独立）是什么；然后去掉这个前提，给出一个"可访问性与相关度强相关"的场景，说明此时 post-filter 反而可能不差。关键：这个场景在真实多租户系统里成立吗？为什么？

  2. 侧信道检测。设计一个统计检验来发现"空结果泄漏存在性"：以两种身份（有权/无权）对同一批查询统计返回条数，写出检验统计量与判定阈值，并估计需要的查询数量。用模拟生成"有侧信道"与"无侧信道"两组数据验证你的检验。

  3. 位图的存储账。N=107 篇文档、P=104 个 principal。计算原始位图总大小、稀疏情形下用"倒排列表（doc_id 列表）"的大小，并给出选择阈值（当某 principal 的可见文档少于多少时用倒排更省）。

  4. chunk 继承测试。写一个测试：对每个文档，断言其所有 chunk 的 ACL 集合等于父文档 ACL（考虑容器/文件夹递归）。构造三种 bug（漏字段、字段为空、继承错父节点），验证测试能捕获它们。

  5. 过滤导致图断裂的判据。设计一个实验：在 s 从 1.0 降到 0.01 时，记录 (a) 有效候选数、(b) 访问节点数、(c) 回退到暴力扫描的比例、(d) recall@10。给出"何时必须改用分区"的判据（提示：找有效候选数不随 ef 增长的拐点）。

  6. 撤权传播 SLA。设撤权操作要经过"标记 → 墓碑 → manifest 切换 → 各缓存失效"。列出每一步的耗时来源，给出端到端 SLA 的估算公式，并指出哪一步最可能成为瓶颈。如果 SLA 要求 60 秒，哪些步骤必须做成同步？

  7. 权限与评测集的一致性。设计一个校验脚本：读评测集（每条带查询、黄金证据 id、租户），断言"黄金证据对该租户可见"。回答：如果断言失败，评测结果会怎样被污染（提示：本来就不可能召回的题被判为失败，压低基线）？

  8. 组合方案设计。给定：1000 个租户，107 篇文档，其中 5 个大租户各占 10%，其余为小租户；有 3 个租户要求数据驻留。给出你的索引架构（分区 + 共享 + 位图）、每种路径的召回/延迟预期、以及 canary 测试的覆盖方案。

小结#

  • 权限必须在检索层前置执行，且是查询的强制参数（由服务层从令牌解析，绝不由模型/提示决定）。否则提示注入可以直接绕过。
  • 威胁模型至少 10 条路径：post-filter、缓存键缺租户、元数据过滤写错、chunk 未继承 ACL、撤权未传播、提示注入、日志泄漏、评测集跨租户、模型记忆间接泄漏、向量反演。没有自动化断言的路径等于没修。
  • post-filter 的失效是纯计数结论：#可用∼Binomial(k,s)，E=ks，P(空)=(1−s)k。⚠️ k=10、E=4 时：s=0.10 → 期望 1.00 条、空结果率 0.349、可组装率 0.013；s=0.02 → 空结果率 0.818。与排序质量无关。
  • post-filter 不泄漏单条黄金证据（它可访问），它损害的是多证据可组装性、空结果率、侧信道。把它说成"会泄漏"是错的，但据此认为"能用"同样是错的。
  • 前置过滤有三种实现：分区（隔离最强、碎片化）、元数据过滤（共享、但高选择性下图遍历断连，需 k/s 过采样）、ACL 位图（可断言、可解释）。⚠️ s=0.02 时过采样代价 50×。
  • deny-by-default：缺 ACL 字段 = 不可见。⚠️ 实测：missing=public 让 2 篇无 ACL 文档对租户 0 可见；deny-by-default 下为 0 篇。
  • 验收必须可证伪：per-tenant canary 诱饵 + 全租户交叉检索矩阵 + 断言命中数 == 0 + 进 CI。⚠️ 实测：不过滤 60/60 泄漏（FAIL），post-filter 与 pre-filter 均 0 泄漏（PASS）；但同一实验里 post-filter 只返回 1 条而 pre-filter 返回 10 条。
  • 缓存键必须含租户与权限指纹（6.2 §4），否则缓存层就是最方便的越权路径。
  • 一句话：权限不是"过滤一下结果"，而是"决定检索在哪个集合里发生"。先取 top-k 再过滤，本质上是把检索预算花在了别人有权访问的文档上 —— 它既漏信息（侧信道），又漏能力（ks 条结果）。
