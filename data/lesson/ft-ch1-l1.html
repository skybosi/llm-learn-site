为什么微调#

你已经学完 LLM 原理，知道一个基座模型是"在海量语料上做下一个 token 预测"训练出来的。但拿到一个开源模型（比如 Qwen、Llama）之后，直接部署往往不够：它很会"接话"，却不一定按你要的格式、语气、领域知识来回答。本课回答一个最根本的问题——为什么要在预训练模型之上再做微调（fine-tuning），微调到底改了什么、解决什么、又有什么代价。

一、概念讲解#

1. 预训练教会模型"通识"，而不是"专业"#

预训练阶段的优化目标是语言建模（next-token prediction）：给定前面的 token，预测下一个 token。这让模型学会了语法、常识、推理的"通识能力"。但它没有针对任何一个具体任务做优化：

  • 它不知道你期望它输出 JSON 而不是散文；
  • 它不熟悉你的私有业务术语（"麦氏点压痛""GMV 环比"）；
  • 它不理解你的语气规范（客服要用敬语、法务要严谨、营销要有感染力）；
  • 它默认"回答即可"，而你可能需要它先判断再回答、回答不了就拒答。

预训练解决的是"会不会说话"，微调解决的是"按谁的规矩说话"。

2. 微调的定义：在预训练权重上继续训练#

微调（fine-tuning） 是指：拿一个已经在海量数据上预训练好的模型，把它的权重作为初始值，再用一份规模小得多、但和目标任务高度相关的数据继续训练，让模型朝目标方向调整参数。

它的本质是迁移学习（transfer learning）：把在通用任务上学到的表示，迁移到下游任务上。之所以"小数据就够"，是因为模型不需要从零重新学语言，只需要在已有能力上做一次"小幅修正"。

可以用一条公式概括微调前后的关系：

微调后权重 = 预训练权重 + Δ（在任务数据上学到的增量）

其中 Δ 就是训练时梯度下降改动的部分。后面第 3 章讲 LoRA 时，会专门研究"怎么用极少的参数去表达这个 Δ"。

3. 微调解决的几类问题#

把"为什么要微调"落成具体场景，通常有这几种：

诉求 典型例子 微调的作用
格式稳定 让模型稳定输出 JSON，供程序解析 把输出格式"烧进"权重，而不是每次都靠提示词碰运气
领域知识 医疗、法律、金融术语与推理习惯 让模型掌握公开语料里稀少的专业分布
私有数据 企业内部 SOP、产品手册、客服话术 把无法放进上下文的知识注入模型
风格语气 客服的敬语、品牌的人格化表达 稳定复现某种"人设"
对齐偏好 拒答危险问题、少说废话、更诚实 用偏好数据（RLHF/DPO）校准行为

一个常见误区是"微调是为了塞知识"。实际上，格式、风格、行为规范这类"能力/习惯"比"知识"更适合微调；纯事实性知识用检索增强（RAG）往往更稳、更新更容易。

4. 微调的代价与边界#

微调不是免费的午餐，动手前要清楚它的成本：

  • 算力与显存：全参数微调要存下权重、梯度、优化器状态，成本可能是推理的几十倍（第 2 章会细算）。
  • 数据成本：需要一批高质量、覆盖目标分布的标注数据。
  • 灾难性遗忘：训练过度会"抹掉"预训练学到的通用能力。
  • 维护成本：模型会过时，知识会过期，需要持续更新。

因此，微调的决策原则是：先用提示词和 RAG 试，确实解决不了、或需要长期稳定复现某种行为时，再上微调。下一课会详细对比这两条路线。

一句话总结：微调是在预训练模型的"通识"之上，用任务数据刻上"专业"的增量；它解决的是格式、领域、风格、偏好这些"怎么回答"的问题，而不是替代知识检索。

二、可运行代码示例#

下面用一个直观的实验说明"为什么需要微调"：加载一个预训练模型，喂给它一段领域文本，计算其困惑度（perplexity）。困惑度越高，说明模型对这个领域的文本越"陌生"，即它的通用分布和你的目标分布之间存在差距——这正是需要微调的信号。

import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

# 选择一个小型开源模型，便于本地快速演示
model_name = "Qwen/Qwen2.5-0.5B-Instruct"

tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, torch_dtype=torch.float32)

# 假设目标领域是"医疗问诊"：模型在通用语料里很少见过这类专业表达
domain_text = (
    "患者主诉右下腹持续性疼痛，伴发热、恶心，麦氏点压痛阳性，"
    "血常规提示白细胞升高，初步诊断为急性阑尾炎，建议急诊手术。"
)

# 编码后计算语言建模损失：模型对这段文本的"意外程度"
inputs = tokenizer(domain_text, return_tensors="pt")
with torch.no_grad():
    outputs = model(**inputs, labels=inputs["input_ids"])
    loss = outputs.loss
    perplexity = torch.exp(loss)

print(f"领域文本困惑度（perplexity）：{perplexity.item():.2f}")
print("解释：困惑度数值越大，表示模型对该文本分布越不熟悉，")
print("     意味着通用预训练能力与目标领域之间存在差距，")
print("     这正是需要通过微调来弥补的部分。")

再看一个更直观的行为差异：直接让基座模型回答一个需要"稳定结构化输出"的问题，观察它的"通识式"回答与业务要求的差距。

# 用同一模型演示：业务要求"只输出一句话结论 + 分类标签"，
# 但通用模型倾向于自由发挥，格式不稳定
question = "订单 10023 的退款申请：用户收到商品 7 天后以'质量问题'申请退款。请判定是否通过，并给出理由。"

messages = [
    {"role": "system", "content": "你是一名电商售后审核员。"},
    {"role": "user", "content": question},
]
text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
inputs = tokenizer(text, return_tensors="pt")

with torch.no_grad():
    generated = model.generate(**inputs, max_new_tokens=120, do_sample=False)

answer = tokenizer.decode(generated[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)
print("\n基座模型的回答：")
print(answer)
print("\n观察：回答可能很长、没有固定字段、结论不明确。")
print("微调的意义：用一批'标准答复样例'训练后，模型可稳定输出")
print("{'通过': false, '理由': '...'} 这样的结构化结果。")

说明：上面第二个例子依赖联网下载模型权重。若本地无 GPU，可将模型换成更小的 distilgpt2（英文）或仅运行第一个困惑度示例。代码意图是"量化差距"，而不是追求某个具体分数。

三、练习#

  1. 概念判断：以下诉求，哪些更适合用"微调"解决，哪些更适合"提示词/RAG"解决？
    • (a) 让模型稳定输出符合某 schema 的 JSON；
    • (b) 回答"今天的公司股价是多少"这类实时信息；
    • (c) 让客服机器人稳定使用"您"和敬语；
    • (d) 记住 500 页的内部产品手册。
  2. 填空：微调的本质是 ____ 学习，即把在通用任务上学到的表示迁移到下游任务；它是在 ____ 权重的基础上继续训练。
  3. 动手实验：把上面代码里的 domain_text 换成一段日常口语（例如"今天天气不错，我们去公园散步吧"），再算一次困惑度。对比两次结果，你能得出什么结论？
  4. 思考题：为什么说"把知识塞进模型"比"把格式/风格刻进模型"风险更高？结合灾难性遗忘和知识过时两个角度说说你的看法。
