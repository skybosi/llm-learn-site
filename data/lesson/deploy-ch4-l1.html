OpenAI 兼容 API#

前面几章我们学会了用 vLLM 把模型"跑起来"、压测出吞吐、甚至多卡并行。但一个推理引擎要真正变成"服务"，必须能被业务方调用——你的上游是 Python、Go、Node 写的业务代码，还有一堆现成的 Agent 框架、LangChain、Dify 之类的工具。它们不认识 vLLM 的内部协议，只认一个事实标准：OpenAI 的 API 格式。这一课讲清楚"OpenAI 兼容 API"到底是什么、怎么在自建引擎上开出来、怎么用现成 SDK 直连，以及流式输出背后的原理。

一、概念讲解#

1. 为什么"OpenAI 兼容"成了事实标准#

OpenAI 发布 ChatGPT 之后，它那套 HTTP API（尤其是 /v1/chat/completions）被海量应用和 SDK 抢先接入。后来几乎所有开源推理引擎——vLLM、SGLang、TGI、llama.cpp 的 server、Ollama——都选择实现同一套接口格式。这样做的收益是巨大的：

  • 一次接入，处处可用：业务代码只写一个 OpenAI SDK 调用，把 base_url 换成自己的服务地址，就能在"云厂商 API"和"自建 vLLM"之间无缝切换；
  • 生态复用：LangChain、LlamaIndex、AutoGen 以及各类 Agent 框架都内置了 OpenAI 兼容的 connector，你的服务不用做任何适配就能被它们调用；
  • 减少心智负担：团队不需要为每个引擎学一套新协议。

这里要区分两个概念：协议兼容（请求/响应的 JSON 字段长得一样）和语义兼容（每个参数的含义和取值范围一致）。大多数引擎做到的是前者 + 主要参数的后者，一些冷门采样参数（如 presence_penalty、logit_bias）可能被忽略或映射得不完全一致，接入时要留意。

2. 核心接口：chat/completions#

自建服务的"门面"通常是下面几个端点（endpoint），挂在统一前缀 /v1 下：

  • POST /v1/chat/completions：对话补全，是今天的绝对主力。请求体带 messages（角色 + 内容列表），返回 choices[0].message.content；
  • POST /v1/completions：老式"文本补全"，只收一个 prompt 字符串，不带对话角色；
  • GET /v1/models：列出当前服务加载的模型名，前端和框架常靠它做健康探测。

一次最小请求长什么样见下一节示例。响应里最关键的字段：

  • choices[0].message.content：模型回复正文；
  • usage.prompt_tokens / usage.completion_tokens：本次消耗的输入/输出 token 数——这是算成本、做限流、记日志的基础；
  • finish_reason：结束原因（stop 正常、length 被截断、tool_calls 要调用工具）。

3. 流式输出（streaming）：不是装饰，是体验刚需#

把 stream: true 传进去，响应就不再是一个完整 JSON，而是一串以 data: 开头的 SSE（Server-Sent Events）分片，每个分片带 choices[0].delta.content 的增量文本，最后一条 data: [DONE] 收尾。

为什么要流式？因为 LLM 是自回归的，第一个 token 到最后一个 token 之间可能隔几十秒。不流式，用户要盯着空白页面干等；流式则能做到"首字即出"（配合前面学过的 TTFT），体验天差地别。工程上流式也更好做取消——用户点停止，直接断开连接即可，省掉后续所有 token 的计算。

4. 采样参数如何映射#

OpenAI 协议里的采样参数，在 vLLM 里会被翻译成自己的调度参数，常用的对应关系：

OpenAI 参数 含义 备注
temperature 温度，越高越随机 与 top_p 二选一或组合
top_p 核采样阈值
max_tokens 输出上限（不含输入） 也叫 max_completion_tokens
n 采样几个候选 对应 vLLM 的 best_of
stop 停止词

注意 max_tokens 是输出 token 上限，输入长度由模型上下文窗口与 max_model_len 决定。理解这一点对控制成本很关键：输出 token 比输入更贵，因为它要逐 token 解码。

二、可运行示例#

示例 1：启动 vLLM 的 OpenAI 兼容服务#

# 启动 vLLM，监听 8000 端口，暴露 OpenAI 兼容 API
# --served-model-name 决定外部看到的模型名（可以和真实权重名不同）
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --host 0.0.0.0 \
  --port 8000 \
  --served-model-name my-llama-8b

服务起来后，先看模型列表（健康探测）：

curl http://localhost:8000/v1/models
# 返回 {"object":"list","data":[{"id":"my-llama-8b", ...}]}

示例 2：curl 发一次对话补全#

curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "my-llama-8b",
    "messages": [
      {"role": "system", "content": "你是严谨的技术助手，回答要简洁。"},
      {"role": "user", "content": "用一句话解释什么是 KV Cache。"}
    ],
    "temperature": 0.3,
    "max_tokens": 100
  }'

示例 3：用 OpenAI Python SDK 直连自建服务#

# -*- coding: utf-8 -*-
# 把官方 OpenAI SDK 的 base_url 指向自建 vLLM，代码零改动
from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:8000/v1",   # 关键：指向自己的服务
    api_key="EMPTY",                        # 自建服务通常不校验 key，填占位即可
)

resp = client.chat.completions.create(
    model="my-llama-8b",
    messages=[
        {"role": "user", "content": "列出三种降低推理成本的方法。"}
    ],
    temperature=0.2,
    max_tokens=200,
)
print(resp.choices[0].message.content)
print("输入 token:", resp.usage.prompt_tokens, "输出 token:", resp.usage.completion_tokens)

示例 4：流式输出#

# 流式读取：边生成边打印，模拟 ChatGPT 打字机效果
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")

stream = client.chat.completions.create(
    model="my-llama-8b",
    messages=[{"role": "user", "content": "写一段 50 字左右的自我介绍。"}],
    stream=True,          # 开启流式
)

for chunk in stream:
    delta = chunk.choices[0].delta
    if delta.content is not None:   # 最后一个分片 content 为 None
        print(delta.content, end="", flush=True)
print()

三、练习#

  1. 把示例 2 的 max_tokens 改小到 10，观察 finish_reason 变成 length，说明"被截断"是怎么通过协议反馈给调用方的。
  2. 用 GET /v1/models 确认服务可用后，写一个 Go 或 Node 的小脚本，用各自的 OpenAI SDK 连接同一服务，体会"一次接入处处可用"。
  3. 给示例 3 加上 stop=["。"]，对比加与不加时回复在哪里停住，理解 stop 参数的行为。
  4. 思考：如果一个多租户平台要给不同客户暴露不同模型名，--served-model-name 能解决什么问题？它和真实权重目录名是什么关系？
