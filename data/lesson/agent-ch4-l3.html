上下文工程：拼装顺序、剪裁与引用#

这一节要解决什么#

前面两节把记忆的内容设计好了：该写什么、怎么忘。但每一步真正决定模型行为的是另一件事：

模型这一步的行为=f(这一步上下文里到底有什么、以什么顺序)

上下文是每一步重新装配的，而不是"对话的累积"。这个视角的转变带来本节的全部内容：装配是一个带预算的优化问题，不是"把相关的东西放进去"。

先纠正一个流行的直觉错误："相关信息越多越好"。它错了三次，每次的机制都不同：

错误直觉 实际机制 后果
"多放点没关系，模型能自己挑" 注意力稀释：相关信息在 token 上的占比下降，被检索到的概率下降 该用的信息没用上
"相关的都放进去更保险" 干扰项效应：语义相近但结论不同的内容会拉偏判断 结论偏向干扰项
"重要的放哪都一样" 位置偏差：首尾位置的影响显著强于中间（lost-in-the-middle） 关键约束被忽略

三条合起来的结论是：

∃ k∗,准确率(k) 在 k∗ 处最大,k>k∗⇒准确率下降

∃ k∗,准确率(k) 在 k∗ 处最大,k>k∗⇒准确率下降

所以上下文工程的核心问题是"选什么、放多少、怎么排"，而不是"怎么塞"。

学完这一节你应该能回答：

  • 为什么把检索到的 10 个片段全塞进去，比只塞 3 个更差？这个 3 是怎么定的？
  • 剪裁上下文时，为什么"保留工具调用但删掉它的返回"比"两个都删"更糟？
  • 上下文里的内容该按什么顺序排？为什么"最重要的放中间"是错的？
  • 用引用（句柄）替代长文本，代价是什么？（不是免费的。）
  • 崩溃恢复时重装的上下文，该和第一次完全一样吗？

一、"塞更多更差"的四个机制#

1.1 机制一：注意力稀释#

模型对上下文的处理不是均匀的。近似地说，每条信息被"注意到"的程度随上下文变长而下降。用一个可用的简化模型：

Pr(用到信息 i)≈∑j​wj​wi​​⋅η(L),η′(L)<0

其中 wi​ 是信息 i 与当前任务的语义关联强度，L 是上下文长度，η 是随长度衰减的可用性因子。

两个可直接读出的推论：

  1. 加入低权重的信息，会稀释高权重信息的相对占比 —— 即使绝对位置没变。所以"多塞一些可能相关的东西"是以降低真正相关内容的比重为代价的。
  2. 当 L 已经很大时，唯一有效的改进是减少 L 或提高 wi​，而不是继续加信息。这解释了为什么在长上下文场景里，"改写查询/提高检索精度"的收益远大于"多召回"。

1.2 机制二：干扰项（distractor）效应#

更微妙的一类：语义相近但结论不同的内容，会主动拉偏结果。 它不是"浪费预算"，而是"造成错误"。

典型的干扰项形态：

形态 例子 后果
同名不同义 两个"收入"口径（确认收入 vs 签约额，第 3 章） 模型混用两个口径
旧版本文档 同一份政策的两版，结论不同 模型引用旧条款
相似但不同的实体 两个都叫"张总"的人 归因错误
反例与正例混杂 检索到"这个方法失败了"但没标出失败 模仿失败做法

关键结论：相关性排序（retrieval score）不等于"该放进上下文"。一条与查询高度相似、但与当前任务口径不符的内容，是负收益。所以装配阶段必须做过滤（按口径、版本、实体、结果标签过滤），而不只是排序取 top-k。

装配=过滤(口径/版本/实体/标签)→排序(相关性)→截取(k∗)

装配=过滤(口径/版本/实体/标签)→排序(相关性)→截取(k∗)

过滤必须在排序之前：一旦按相关性取完 top-k，其中一半是口径不符的内容，再过滤就只剩很少了。

1.3 机制三：位置偏差（首尾优势）#

经验上模型对上下文开头与结尾的利用显著优于中间（这一现象通常称为 lost-in-the-middle）。用一个实用的位置权重模型：

权重(p)≈α⋅1[p∈首]+β⋅1[p∈尾]+γ⋅1[p∈中],α,β>γ

这直接给出装配顺序的设计规则：

[开头] 稳定且必须始终生效的内容：目标、硬约束、输出格式要求、角色
[中间] 可被检索/参考的材料：文档片段、工具返回值、历史观察
[结尾] 当前这一步的决策所需：最新观察、当前待办、本次问题的明确表述

推论：不要把关键约束放在中间。一个常见的错误是把"不要修改生产数据库"这条硬约束写在很长的系统提示词的中段 —— 它会被中间位置的低权重吞掉。正确做法是首尾各出现一次（重复不是浪费，是对位置偏差的对冲）：

关键约束=开头声明+结尾复述（在决策前）

这与第 2 章"不要把真实终止判据写进提示词"不矛盾：硬约束（不能做什么）应当写且应当重复；判据（怎样算完成）不应写。 前者防有害动作，后者泄露答案。

1.4 机制四：上下文腐化（context rot）#

上下文里内容越杂，模型越容易被历史内容带偏，表现为：

  • 模仿历史格式：前面有一次输出用了表格，后面全部输出表格（即使不合适）；
  • 延续历史错误：前面一次把字段名写错，后面继续用错的名字；
  • 被历史的失败尝试锚定：前 5 步试了方案 A 失败，第 6 步仍在方案 A 的变体里打转。

缓解手段与前面两节呼应：

表现 手段
模仿历史格式 把格式要求放在结尾（最近位置），并在装配时丢弃旧输出的排版
延续历史错误 用结构化状态（工作记忆）替代"读历史推断"（第 1 节）
被失败尝试锚定 剪裁时把失败尝试压缩成一行教训，而不是保留完整过程（见 3.4）

1.5 最优 k 的存在性与估算#

把三条机制合成一个可估算的模型。设放入 k 条信息，其中含目标信息的概率为 p(k)（随 k 上升，但边际递减），而干扰项带来的错误概率为 q(k)（随 k 上升）：

准确率(k)≈p(k)−q(k),p′(k)>0, p′′(k)<0, q′(k)>0

若取具体形式 p(k)=p∞​(1−e−k/κ)、q(k)=λk，则最优：

k∗=κln(λκp∞​​)

k∗=κln(λκp∞​​)

这个公式的实用价值不在数值，而在它指出的四个量：

符号 含义 怎么估
κ 检索质量的"尺度"（多大 k 才能覆盖目标） 离线测 recall@k 曲线
p∞​ 上限召回率（检索系统的天花板） recall 曲线的渐近值
λ 每条干扰项的错误代价 人工标注干扰项比例 + 错误率
k∗ 最优条数 由上面三个算出，不是拍的

结论：k∗ 随检索质量提高而下降（κ 小 → 需要的条数少）。这与直觉相反但很重要：检索越好，越应该少放。一个 recall@10 = 0.95 的系统放 k=3 就够，而 recall@10 = 0.6 的系统放 k=3 会严重缺信息 —— 但放 k=10 会引入 7 条干扰项。这解释了"我的检索不好，所以多放点"是一个错误的自救方向。

二、装配的结构与顺序#

2.1 分块与显式边界#

上下文应当由有明确边界的块组成，每块有名字、来源、信任级别：

<system>        角色、能力边界、绝对硬约束（首）
<goal>          本次任务目标 + 验收标准
<memory>        装载的长期记忆（带来源与时效标记）
<episodes>      检索到的经验（成功/失败分开标注）
<state>         当前工作记忆的渲染（阶段、待办、已确认实体）
<evidence>      本次任务内已获得的证据（工具返回值，带 trust 标记）
<observation>   最新一步的观察（结尾）
<reminder>      硬约束复述 + 输出格式要求（尾）

为什么必须显式分块（三个理由）：

  1. 可剪裁：剪裁的单位是块，不是字符。知道哪些块可以整块丢，才能做安全的预算控制。
  2. 可归因：出问题时能定位到"是记忆错还是检索错"（第 7 章的失效归因需要块级来源）。
  3. 可声明信任：第 3 章的 T0/T1/T2 信任级别挂在块上，出口检查与验证器才能消费它。

2.2 顺序的三条规则#

规则 内容 机制
R1 稳定不变的内容放首（角色、约束、格式）；每步变化的内容放尾 利用首尾优势；且稳定前缀利于 KV cache 复用
R2 决策所需的最后一块必须紧邻生成位置 最近位置权重最高；模型看最后一段来决定动作
R3 硬约束首尾各一次 对冲位置偏差（1.3）

R1 里"稳定前缀利于 KV cache" 是一个额外的工程收益：前缀不变的部分可以被缓存复用，显著降低延迟与成本。这给了一条实用原则：

装配顺序应当按"变化频率"排序：变化越少的越靠前

这条原则同时优化了位置偏差与缓存命中率 —— 两者恰好同向。

2.3 预算分配#

上下文预算 B（token）必须显式分配，而不是"先放，放不下再说"。一个可用的初始配比（可按任务调）：

块 占比（典型） 说明
系统/角色/硬约束 5–10% 稳定前缀（可缓存）
目标 + 验收标准 3–5% 稳定
状态（工作记忆渲染） 5–10% 每步变，但短
记忆装载 10–15% 有硬上限（第 1 节的装载上限公式）
经验（成功 + 失败） 5–10% 分标签、条数少
证据/文档片段 30–40% 主要变量，剪裁主战场
最新观察 5–10% 结尾
硬约束复述 + 格式要求 3–5% 结尾
预留（输出 + 工具 schema + 回复） 10–20% ★ 最常被忘记的一项

最后一行是实际系统里最常见的超预算原因：把预算算到"输入刚好占满"，然后没有空间给工具 schema 与模型输出。规则：

Binput​≤Bctx​−Boutput​−Btool_schemas​−Bsafety_margin​

其中 Bsafety_margin​ 取 5–10%（tokenizer 差异、格式包边、系统注入）。

2.4 装配的时机：三种上下文#

一个容易忽略的区分：不同时刻需要不同的装配。

上下文类型 用于 特点
决策上下文 每一步生成动作 必须包含最新观察 + 待办 + 硬约束；短而精
总结上下文 压缩/写记忆 需要原始材料（第 2 节：从原始日志重算）；可以很长
恢复上下文 崩溃后重建 从检查点重建，必须与崩溃时一致或更完整；要标注"未结算副作用"

把三者混用是常见错误：用一个超长上下文既做决策又做总结，结果是决策被稀释、总结又没拿到完整原文。总结应当是一次独立的、专门的调用。

三、剪裁：保持结构完整性的删减#

3.1 剪裁的三条硬规则#

规则 内容 违反的后果
C1 配对完整 工具调用（tool_call）与它的返回（tool_result）必须成对保留或成对删除 模型看到"调用了但没结果"→ 以为工具挂了，重试或编造结果
C2 引用闭合 删掉被引用的原文时，必须同时删除/更新引用它的地方 悬空引用：模型去查一个不存在的句柄
C3 不变量保留 目标、硬约束、已确认的关键事实永不剪裁 任务漂移（第 1 章的机制二）

C1 值得展开，因为它是剪裁里最反直觉的一条。 直觉上"保留调用、删掉冗长的返回"是省 token 的好办法。但模型看到的是：

[assistant] 调用 search_docs(query="...")
（此处原本有 2000 token 的返回，被删掉了）
[assistant] 好，根据检索结果，我建议...

模型会推断"这个工具没有返回内容/失败了"，于是它可能重新调用（浪费预算），或者凭空编造检索结果（产生幻觉）。第二种更糟。

正确的剪裁单位是"调用—返回对"：要么都留（返回可摘要但必须带来源），要么都换成一行摘要（"step 3: search_docs 返回 12 条，已提取 doc_id 列表见 state"）。

C1​: keep(ci​)=keep(ri​)或both→一句话摘要

3.2 剪裁的优先级顺序#

当预算不足时，按下面的顺序剪（从最先牺牲到最不可牺牲）：

优先级 内容 处理
1（最先剪） 早期的、已被结构化抽取到状态的原始观察 替换为"step i: 摘要/引用"
2 失败尝试的完整过程 压缩为一行教训（进检索式记忆，第 1 节）
3 记忆装载中权重最低的条目 按衰减评分截断，记录截断
4 经验条目（保留失败先例优先于成功先例） 减少 k
5 文档片段 按 2.1 的过滤+排序减少 k
6（最后） 状态渲染中的非关键字段 只保留实体 ID，丢弃明细
不剪 目标、硬约束、最新观察、格式要求 C3

"失败先例优先于成功先例"这一条值得说明：成功先例告诉模型"该怎么做"，失败先例告诉它"别怎么做"。在预算紧张时，避免已知的坑比复用已知的成功更划算 —— 因为前者的代价是预算耗尽或不可逆错误，后者只是效率稍低。

3.3 引用（句柄）替代原文#

最长的那部分内容（文档片段、工具返回的大对象）应当被替换为句柄 + 摘要：

<evidence id="ev:doc_17" source="internal_wiki" trust="T1" chars="8200">
  summary: 该文档说明退款流程需在 7 日内发起，超期需走人工审批；例外：企业客户 30 日。
  handle: doc_17            ← 模型可用 fetch_handle("doc_17") 取回原文
</evidence>

收益：长内容从上下文里移出，token 成本大幅下降；而且按需取回意味着只有真正需要时才付费。

代价（不是免费的，三条）：

代价 说明 缓解
额外一轮交互 模型要发起取回，多一次往返（延迟 + 成本） 对高概率需要的内容直接内联（阈值：预期使用概率 > 0.5）
摘要的信息损失 模型可能因为摘要不全而不知道该取回什么 摘要必须保留"可判定性线索"（有什么、覆盖什么范围），而非只给结论
悬空风险 句柄可能过期/被删（第 2 节的遗忘） 取回失败必须返回明确错误，且给出"原文已归档/已删除"的区分（对应第 2 节墓碑）

内联 vs 引用的判据（实用形式）：

内联⟺该内容被用到的概率puse​​​⋅长度L​​>一次取回的代价croundtrip​​​

即：又短又可能用到 → 内联；又长又不一定用到 → 引用。

3.4 剪裁的信息损失：可测量吗#

可以。三种度量，都是离线可跑的：

度量 做法 判据
决策一致性 同样的状态，用剪裁前后两种上下文各跑 n 次，比较动作 一致性 > 阈值则剪裁安全
必要信息召回 人工标注"做这个决定必须看到的信息"，检查剪裁后是否还在 必须 100%
重放差异 用剪裁后的上下文做恢复，看是否与原始轨迹一致 见下一节

第一项是最实用的：它把"剪裁会不会出问题"变成一个可回归的实验，而不是"但愿没事"。

四、装配的检查清单#

把全节压成一份可以在 CR（code review）时逐条过的清单：

# 检查项 通过判据
1 预算是否显式分配 每个块有配额；总和 + 输出预留 ≤ Bctx​
2 硬约束是否首尾各一次 grep 得到两处
3 稳定前缀是否在最前 角色/约束在首，变化内容在尾（利于 KV cache）
4 最后一块是否紧邻生成位置 最新观察 + 本次问题在最后
5 工具调用与返回是否配对 遍历上下文，无孤立的 tool_call 或 tool_result
6 引用是否闭合 每个句柄在有界集合内；无悬空
7 外部内容是否包裹并标信任级别 每个 T1/T2 块有 source / trust / fetched_at
8 干扰项是否被过滤 装配前按口径/版本/实体/结果标签过滤，且过滤规则可测
9 记忆装载是否有条数上限与截断标记 超限时写入 truncated: true
10 是否区分决策/总结/恢复三种装配 代码里有三个入口，不是一个

代码：预算感知的装配器 + 配对完整性校验 + 引用闭合#

下面的代码实现：(1) 块化的上下文模型与预算核算（含输出预留）；(2) 按优先级的剪裁（强制执行工具调用—返回配对，并拒绝产生悬空引用）；(3) 位置策略（稳定前缀 / 最新观察与约束复述在尾）；(4) 内联 vs 引用的判据；(5) 干扰项过滤与"决策一致性"回归的骨架。

from dataclasses import dataclass, field
from enum import IntEnum
from typing import Any, Optional


# ==================== (1) 块化上下文 + 预算 ====================
class Priority(IntEnum):
    """★ 数字越大越不可牺牲（3.2 的顺序）。剪裁从最小的开始。"""
    EARLY_OBSERVATION = 1     # 早期原始观察（已被抽取到状态）
    FAILED_ATTEMPT = 2        # 失败尝试的完整过程
    MEMORY_ENTRY = 3          # 记忆装载（低权重者先走）
    EPISODE = 4               # 经验条目
    DOC_CHUNK = 5             # 文档片段
    STATE_DETAIL = 6          # 状态渲染的明细字段
    RECENT_OBSERVATION = 8
    GOAL = 9
    HARD_CONSTRAINT = 10      # 永不剪裁（C3）


@dataclass
class Block:
    kind: str                     # system | goal | memory | episode | state | evidence | observation | reminder
    text: str
    priority: Priority
    trust: str = "T0"             # T0 指令 / T1 数据 / T2 声明
    source: str = ""
    fetched_at: str = ""
    pair_id: Optional[str] = None  # ★ 工具调用与其返回共享同一个 pair_id（C1）
    handle: Optional[str] = None   # 引用句柄（3.3）
    pinned: bool = False           # 首尾固定位置（R1/R2/R3）

    @property
    def tokens(self) -> int:
        # 粗估：中文约 1 token/字，英文约 4 字符/token。真实实现应使用 tokenizer。
        return max(1, len(self.text.encode("utf-8")) // 3)


@dataclass
class ContextBudget:
    """
    ★ 设计决策：预算必须显式，且必须预留输出与工具 schema。
      "输入刚好占满"是实际系统里最常见的超预算原因（2.3）。
    """
    ctx_tokens: int = 60_000
    output_reserve: int = 4_000
    tool_schema_tokens: int = 3_000
    safety_margin_ratio: float = 0.08

    @property
    def input_budget(self) -> int:
        margin = int(self.ctx_tokens * self.safety_margin_ratio)
        return self.ctx_tokens - self.output_reserve - self.tool_schema_tokens - margin


def assemble(blocks: list[Block], budget: ContextBudget) -> dict:
    """
    ★ 设计决策：装配顺序 = 按"位置角色"排（首/中/尾），而不是按块的原始顺序。
      首：稳定且必须始终生效（角色、目标、硬约束）—— 同时利于 KV cache 复用。
      中：可参考材料（证据、记忆、经验、历史观察）。
      尾：最新观察 + 硬约束复述 + 格式要求（R2/R3 对冲位置偏差）。
    """
    head_kinds = ("system", "goal")
    tail_kinds = ("observation", "reminder")
    head = [b for b in blocks if b.kind in head_kinds]
    tail = [b for b in blocks if b.kind in tail_kinds]
    middle = [b for b in blocks if b.kind not in head_kinds and b.kind not in tail_kinds]
    return {"head": head, "middle": sorted(middle, key=lambda b: -b.priority), "tail": tail}


# ==================== (2) 剪裁：配对完整 + 无悬空引用 ====================
@dataclass
class TrimResult:
    kept: list[Block]
    dropped: list[Block]
    dropped_pairs: list[str] = field(default_factory=list)
    trims: list[str] = field(default_factory=list)


def trim(blocks: list[Block], budget: ContextBudget) -> TrimResult:
    """
    ★ 三条硬规则：
      C1 工具调用与返回成对保留/删除（pair_id 联动）
      C2 删除被引用原文时，同时删除引用它的块（否则出现悬空句柄）
      C3 目标 / 硬约束 / 最新观察永不剪裁
    ★ 设计决策：每次从**最高优先级**重新扫描（每轮只移除一个"单元"），
      因为删掉一个单元可能释放足够预算 —— 一次性按索引列表遍历会多删。
    """
    kept = list(blocks)
    dropped: list[Block] = []
    dropped_pairs: list[str] = []

    def total(bs: list[Block]) -> int:
        return sum(b.tokens for b in bs)

    while total(kept) > budget.input_budget:
        # 当前最低优先级者优先走；同优先级内先走更旧的（列表顺序即时间顺序）
        victims = sorted(kept, key=lambda b: (int(b.priority), kept.index(b)))
        if not victims:
            break
        victim = victims[0]                       # 已按优先级升序，第一个即最低
        if victim.priority >= Priority.RECENT_OBSERVATION or victim.pinned:
            break                                 # C3：剩下的都不可剪 → 停手并报告
        unit = [x for x in kept if victim.pair_id and x.pair_id == victim.pair_id] \
            if victim.pair_id else [victim]
        for u in unit:                            # C1：整组一起走
            kept.remove(u)
            dropped.append(u)
        if victim.pair_id:
            dropped_pairs.append(victim.pair_id)
        # C2：引用闭合 —— 删掉带 handle 的原文后，引用它的块也必须走
        if victim.handle:
            for x in [x for x in kept if victim.handle in x.text]:
                kept.remove(x)
                dropped.append(x)
    return TrimResult(kept=kept, dropped=dropped, dropped_pairs=dropped_pairs,
                      trims=[f"{b.kind}:{b.priority.name}" for b in dropped])


def check_pairing(blocks: list[Block]) -> list[str]:
    """
    ★ 剪裁后必须跑的校验：孤立的 tool_call / tool_result 会让模型
      "以为工具没返回" → 重试或编造结果（3.1 的 C1）。
    """
    issues: list[str] = []
    seen: dict[str, list[str]] = {}
    for b in blocks:
        if b.pair_id:
            seen.setdefault(b.pair_id, []).append(b.kind)
    for pid, kinds in seen.items():
        has_call = any("call" in k for k in kinds)
        has_result = any(("result" in k) or k == "observation" for k in kinds)
        if has_call != has_result:
            issues.append(f"孤立对 {pid}: {kinds} → 必须成对保留或成对删除")
    return issues


def check_references(blocks: list[Block]) -> list[str]:
    """★ 引用闭合校验：上下文里出现的每个句柄都必须在同一次装配内有对应原文或明确声明已归档。"""
    available = {b.handle for b in blocks if b.handle}
    issues = []
    for b in blocks:
        for m in set(_mention(b.text)):
            if m not in available and f"已归档:{m}" not in b.text:
                issues.append(f"{b.kind} 引用了不存在的句柄 {m} → 悬空引用（C2）")
    return issues


def _mention(text: str) -> list[str]:
    """极简：把 fetch_handle("x") / handle: x / 正文中的 doc_x 视作引用。"""
    out = []
    for tok in text.replace("(", " ").replace(")", " ").replace('"', " ").split():
        if tok.startswith("doc_") or tok.startswith("ev_"):
            out.append(tok.rstrip(".,。，、）)】:；;"))
    return out


# ==================== (3) 内联 vs 引用 ====================
def should_inline(p_use: float, length_tokens: int,
                  roundtrip_tokens: int = 1_200) -> tuple[bool, str]:
    """
    ★ 3.3 的判据：又短又可能用到 → 内联；又长又不一定用到 → 引用。
      roundtrip 代价包含取回本身与可能的第二次确认。
    """
    inline = p_use * length_tokens > roundtrip_tokens
    why = (f"p_use={p_use:.2f} × {length_tokens} = {p_use * length_tokens:.0f} "
           f"{'>' if inline else '≤'} roundtrip={roundtrip_tokens}")
    return inline, why


def make_evidence_block(doc_id: str, body: str, summary: str, p_use: float,
                        source: str, fetched_at: str) -> Block:
    inline, why = should_inline(p_use, max(1, len(body) // 3))
    text = (f"summary: {summary}\n" +
            (f"body: {body}" if inline else
             f"handle: {doc_id}（可用 fetch_handle 取回原文；摘要不足以判断时必须取回）")) + \
           f"\n（内联决策：{why}）"
    return Block(kind="evidence", text=text, priority=Priority.DOC_CHUNK,
                 trust="T1", source=source, fetched_at=fetched_at,
                 handle=doc_id)


# ==================== (4) 干扰项过滤 ====================
@dataclass
class Candidate:
    doc_id: str
    score: float                  # 相关性
    metric: str = ""              # 口径
    metric_version: str = ""
    entity: str = ""
    outcome: str = ""             # success | failure（经验类）


def filter_distractors(cands: list[Candidate], want_metric: str,
                       want_metric_version: str, want_entity: str) -> dict:
    """
    ★ 设计决策：过滤必须在排序**之前**（1.2）。
      相关性高但口径/版本/实体不符的内容是**负收益**，不是"可能有用"。
    """
    kept, rejected = [], []
    for c in cands:
        reasons = []
        if c.metric and want_metric and c.metric != want_metric:
            reasons.append(f"口径不符 {c.metric}≠{want_metric}")
        if c.metric_version and want_metric_version and c.metric_version != want_metric_version:
            reasons.append(f"版本过期 {c.metric_version}≠{want_metric_version}")
        if c.entity and want_entity and c.entity != want_entity:
            reasons.append(f"实体不符 {c.entity}≠{want_entity}")
        (rejected if reasons else kept).append({"doc": c.doc_id, "why": reasons,
                                                "score": c.score})
    return {"kept": sorted(kept, key=lambda x: -x["score"]),
            "rejected": rejected}


# ==================== (5) 决策一致性回归（剪裁安全性） ====================
def decision_consistency(decide_fn, states: list[dict],
                         full_ctx_fn, trimmed_ctx_fn) -> dict:
    """
    ★ 3.4：把"剪裁会不会出问题"变成可回归的实验，而不是"但愿没事"。
      返回一致率与不一致的样本，供人工检查"丢的是必需信息还是冗余"。
    """
    same, diff = 0, []
    for s in states:
        a = decide_fn(full_ctx_fn(s))
        b = decide_fn(trimmed_ctx_fn(s))
        if a == b:
            same += 1
        else:
            diff.append({"state": s, "full": a, "trimmed": b})
    return {"consistency": same / len(states) if states else 1.0, "mismatches": diff}

七处关键设计决策：

  1. ContextBudget.input_budget 把输出、工具 schema、安全边际都扣掉。"把输入算满"是最常见的超预算原因，把它做成一个属性而不是散落的减法，可以避免漏掉某一项。
  2. Block.pair_id 让"工具调用—返回"共享标识，trim 通过 pair_id 联动删除。这是 C1 在类型层面的强制：剪裁代码不可能只删一半。
  3. trim 在删除带 handle 的原文时，会连带删除引用它的块（C2）。这避免了"模型去查一个不存在的句柄"——这类悬空引用比信息缺失更糟，因为它会诱发一次无效调用。
  4. check_pairing / check_references 是剪裁之后必须跑的校验，并且在 __main__ 里用两个反面例子演示了它们能抓到的两种具体破损。
  5. assemble 按位置角色（首/中/尾）重排，而不是保持输入顺序。首部放稳定内容（顺带利于 KV cache），尾部放最新观察与约束复述（R2/R3）。
  6. filter_distractors 的过滤发生在排序之前，并且演示里相关性最高的 d1 被过滤掉了 —— 这是 1.2 最反直觉的结论：相似不等于该放进上下文。
  7. decision_consistency 把"剪裁是否安全"变成可回归的实验。它是唯一能回答"我剪掉的是冗余还是必需信息"的工程手段。

小结#

  • 上下文是每一步重新装配的，不是对话的累积。 模型这一步的行为由"上下文里有什么、以什么顺序"决定。
  • "塞更多更差"有四个机制：注意力稀释（相关信息的相对占比下降）、干扰项效应（语义相近但结论不同的内容主动拉偏）、位置偏差（首尾优势，中间最弱）、上下文腐化（模仿历史格式/延续历史错误/被失败尝试锚定）。
  • 装配=过滤(口径/版本/实体/标签)→排序→截取(k∗) —— 过滤必须在排序之前。相似 ≠ 该放进上下文。
  • 最优 k∗ 存在：k∗=κln(p∞​/(λκ))。检索越好，越应该少放 —— "检索不好所以多放点"是错误的自救方向。
  • 顺序三规则：稳定内容在首（顺带利于 KV cache 复用）、决策所需紧邻生成位置在尾、硬约束首尾各一次。硬约束应当重复；终止判据不应写（第 2 章的结论在这里得到位置层面的解释）。
  • 预算必须显式分配，并预留输出、工具 schema 与安全边际。Binput​≤Bctx​−Boutput​−Bschemas​−Bmargin​。
  • 剪裁三条硬规则：C1 工具调用与返回成对保留/删除（只删返回会让模型以为工具挂了 → 重试或编造）、C2 引用闭合（不留悬空句柄）、C3 目标/硬约束/最新观察永不剪。
  • 剪裁优先级：早期原始观察 → 失败尝试的过程 → 低权重记忆 → 经验 → 文档片段 → 状态明细。预算紧张时失败先例优先于成功先例（避免踩坑比复用成功更划算）。
  • 引用（句柄）替代原文：内联 ⟺puse​⋅L>croundtrip​。代价是额外往返、摘要信息损失、悬空风险；取回失败必须区分"已归档"与"已删除"（第 2 节的墓碑）。
  • 装配质量可以度量：决策一致性（剪裁前后同状态动作是否一致）、必要信息召回（必须 100%）、重放差异（下一节）。
