记忆的写入、压缩与遗忘：如何避免记忆污染#

这一节要解决什么#

上一节把三种记忆的职责分清了，也给出了写入门槛的骨架。但真正的难点现在才开始：

记忆系统的质量上限=写入纪律,而不是容量

一条错误的记忆比没有记忆更糟，因为它会被反复读取。而且它有一个自我强化的回路：

写入一条错误记忆
   → 未来某次任务读到它
   → 基于它做出决策，产出新的"结论"
   → 这个结论又被写回记忆
   → 下一次读到的"证据"更多了，看起来更可信

这个回路叫记忆污染（memory contamination），它是 Agent 系统里最隐蔽的失效模式：它不产生错误，它产生越来越自信的错误。

先量化一下为什么必须主动处理它。设单条记忆的错误率为 ϵ，一次任务平均读取 m 条、写出 1 条。若不作任何筛查，污染比例会随任务数 n 单调上升：

E[污染条数](n)≈ϵn+ϵ2(2n​)(第二项 = 污染被复制后再扩散)

第一项是线性的（自己写错的），第二项是超线性的（读别人的错再写出去）。这就是为什么"注入一点点幻觉"最终会毁掉整个记忆库 —— 增长不是线性的。

这一节的三个任务：

  1. 写入：把"该不该写"变成可执行的判据（写入门槛的完整版），并回答"该写什么形态"。
  2. 压缩：说清摘要为什么必然引入特定类型的信息损失，以及怎么测量这种损失。
  3. 遗忘：把遗忘当成一项正面能力来设计（衰减评分、墓碑删除、审计与"被遗忘权"的冲突）。

学完这一节你应该能回答：

  • 摘要一条对话，最容易丢的是哪四类信息？为什么是这四类？（可以列出来。）
  • 记忆库里有两条互相矛盾的条目，你怎么自动发现它们？"让模型判断是否矛盾"够用吗？
  • 一条三年前的"客户偏好"为什么可能是有害的？你该删除它还是降权它？
  • "只追加不删除"（append-only）与"用户要求删除我的数据"怎么调和？
  • 为什么"让模型自己判断这条记忆可不可信"不是一条有效防线？

一、写入：从"什么时候写"到"值不值得写"#

1.1 "立即写 vs 验证后写"是一个错误的对立#

常见的讨论把写入策略二分成"事件驱动立即写"和"验证后批量写"。但两者各有明确的失效模式，而且失败原因不同：

策略 优点 失效模式
立即写（eager） 不丢信息；崩溃也不丢（写入与事件同时持久化） 写入了大量未经核实的内容 → 污染源头
验证后写（lazy） 只保留高置信内容 验证本身有延迟；等待期间的信息会丢；验证失败时连"曾经观察到什么"都没了

关键观察是：这个对立是假的。 真正决定写入质量的是第三个变量：

写入质量=Φ(决定性来源可验证性​​, 次之时效性​​, 影响最小写入时机​​)

来源是否可验证，决定了这条记忆未来能不能被追责；写入时机只影响"丢不丢"。所以正确的设计不是选边，而是分层：

层 A（原始观察，立即写，只追加）：工具返回值、用户原话、外部系统快照
    —— 特点：来源明确、可核验、不解释、不总结。这一层永远安全。
层 B（结构化抽取，立即写，带来源指针）：实体 ID、字段值、状态转移
    —— 特点：可机器校验（schema/类型/域），且能回指层 A。
层 C（结论与偏好，验证后写）：从多个来源归纳出的规律、用户偏好、教训
    —— 特点：**唯一有污染风险的层**，必须过门槛。

这个分层的核心收益：把"污染风险"限制在层 C，而层 C 的条目数量比其他两层小一到两个数量级。你不需要让所有记忆都安全，只需要让有风险的那一小部分安全。

反过来说，一个常见的架构错误是把层 A 的内容（原始观察）用摘要塞进层 C —— 这时你就把一整层的信息放进了唯一有风险的那一层。

1.2 写入门槛的完整版（五问）#

把"该不该写"变成五个必须回答的问题。任何一问答不上来，就不写（宁可不写；记忆的召回失败比污染便宜得多）：

# 问题 不通过的处置
1 可核验吗？ 能在未来某个时刻拿外部事实核对吗？ 不写；或降级为 pending
2 去语境化后还成立吗？（上一节的判据） 留在工作记忆
3 可重算吗？ 能从已保存的原始数据推导出来吗？ 不写（单一事实来源）
4 会变化吗？多久？ 有 TTL 或版本机制吗？ 不写；或必须带 ttl / valid_from
5 来源是谁？ 用户 / 工具 / 模型 / 第三方？ 除用户与工具外，一律进 pending

第 1 问为什么排第一：它和"对不对"不同。一条记忆可能现在是对的，但如果它不可核验，你永远无法知道它什么时候变错了。不可核验的记忆必须只作为"线索"（低权重、且读取时必须标注未验证），不能作为"事实"。

可核验性=能否在未来用外部事实判定它的真值

第 3 问（可重算）有一个容易搞反的方向：不是"能算出来就不写"，而是"算出来的东西不要当记忆存"。因为重算的结果与原存的副本一旦不一致，你就无法判断哪个对 —— 而这类不一致最难归因（第 7 章的"记忆错"象限）。

1.3 该写什么形态：指针优先于结论#

同样是"记住客户地址是上海市 XX 路 3 号"，有三种写法，风险完全不同：

形态 例子 可核验 保鲜 token
原文 整段对话 ✓（但要人读） ✗（无法判断时效） 高
结论 "客户地址：上海市 XX 路 3 号" △（无出处） ✗（不知何时写的） 低
指针 {"source": "crm:customer:c_9", "field": "billing_address", "fetched_at": "...", "value_hash": "..."} ✓✓ ✓（可重取） 最低

指针优先的理由：

可重取⟹永不过期（只要源头在）,可核验⟹能被对账发现

但指针有一个前提：源头必须稳定可达。所以实践中是混合的：

指针 + 缓存值 + 获取时间 + 源头版本
  {"source": "crm:customer:c_9", "field": "billing_address",
   "cached_value": "上海市…", "fetched_at": "...", "source_version": "v42"}

这样读的时候可以直接用 cached_value（省一次调用），但必须检查新鲜度（fetched_at 与 source_version），不新鲜时重取。这是一个"缓存"而不是"事实" —— 命名上要体现这一点：字段叫 cached_value 而不是 value，能防止后续代码把它当权威值用。

1.4 一条常被忽略的写入：否定性记忆#

"不要做 X"这类记忆（约束、失败教训、用户拒绝过的行为）价值极高，但写入率极低 —— 因为它不在显式指令里：

来源 表现 应该写成的记忆
用户撤销/回退了一次操作 行为，不是陈述 constraint: 该用户不接受自动提交
工具连续返回权限错 失败模式 constraint: 该工具需要审批
某做法导致预算耗尽 失败教训 episodic: 当 X 时不要做 Y
用户拒绝了一个建议 隐性偏好 preference: 不使用 X 类方案（需确认，属模型推断）

否定性记忆的写入必须比肯定性记忆更谨慎：因为它的推断成分更高（"用户撤销"可能是误操作，不是偏好）。所以它的默认归宿是检索式记忆的失败先例（带结果标签，读取时由模型自己权衡），而不是长期记忆里的硬约束 —— 除非被明确确认。

判据：

否定性观察{写入长期记忆约束写入检索式记忆（failure 先例）​若被用户显式确认过若仅由行为推断​

二、压缩：摘要为什么必然有损，损在哪#

2.1 三种压缩手段与它们的失真类型#

token 预算是硬约束，所以压缩不可避免。三种手段的失真性质不同：

手段 做法 失真类型 可逆？
摘要（summary） 让模型把长文本改写成短文本 不可控的语义漂移 ✗
结构化抽取 只保留预定义字段（用 schema 约束） 丢失未定义的字段 △（可回原查）
引用（reference） 保留原文，只放句柄/指针 无失真 ✓

关键结论：摘要不是"少写点字"，它是一次有损的有损编码，而且损失是不可控的。 结构化抽取与引用是可控的。所以优先级是：

引用>结构化抽取>摘要

摘要只用在"必须变成自然语言才能用"的地方（比如给模型的简短提示、经验教训）。凡是可以放指针的地方，绝不摘要。

2.2 摘要丢掉的四类信息（可预测的损失模式）#

这是本节最实用的一张表。模型做的摘要有系统性的信息损失偏向：

类别 原文 典型的"摘要后" 后果
① 数值精度 "延迟从 320ms 涨到 1850ms，p99 是 4.2s" "延迟明显变高" 无法做阈值判断、无法回归对比
② 条件与例外 "除欧盟地区外可用；欧盟需额外授权" "基本可用" 在欧盟场景下违规使用
③ 时间与不确定性标记 "我推测（未验证）该配置已生效" "配置已生效" 不确定性被抹掉 → 幻觉固化的主通道
④ 否定与量词 "不建议在并发 >5 时使用；至少需要 2 个副本" "并发时需要谨慎，副本数要够" 约束失去可执行性

第 ③ 类是最致命的，因为它直接制造幻觉：模型把"我推测"改写成"是"，这个改写发生在摘要这一步（而不是在回答用户那一步），于是污染在写入时就完成了，后续所有读取都会看到一条无不确定性的"事实"。

可操作的缓解措施：

  1. 摘要必须保留模态词（推测/未验证/据 X 所述），并且强制进入结构化字段：
{"claim": "配置已生效", "modality": "inferred", "confidence": 0.6,
 "evidence": "tool_output:step_7", "verified": false}
  1. 数值必须原样保留，不允许"约""明显"这类模糊化。实现上可以让抽取器只允许复制原文中的数字 token（不允许生成新数字）。
  2. 条件与例外必须成对保留：如果摘出了"可用"，必须同时带出"在什么条件下不可用"。可以把它做成一个检查：摘要中出现的每个肯定断言，必须能在原文中找到对应的限定范围。
  3. 否定句不能被改写为肯定句的弱化版本。这是一个可以自动检测的规则：若原文含"不/禁止/仅限"，摘要中必须也含对应的否定标记，否则拒绝该摘要。

2.3 压缩的迭代失真：k 轮压缩后还剩什么#

工作中常见的做法是"上下文太长就总结一次"。如果这个操作会重复多次（长任务里每 20 步总结一次），就出现了级联压缩问题：

信息保留率≈(1−δ)k(δ=单轮失真率, k=压缩轮数)

单轮失真 δ k=1 k=3 k=5 k=10
0.05 0.95 0.86 0.77 0.60
0.15 0.85 0.61 0.44 0.20
0.30 0.70 0.34 0.17 0.03

这张表给出两条设计规则：

  1. 压缩必须尽可能压在原始材料上，而不是压在"上一次的摘要"上。 具体做法：保留原始观察在一个只追加的日志里（层 A），每次压缩都从原始日志重新生成摘要 —— 这叫重算而非叠代：

summaryk​=compress(raw1..n​)而不是summaryk​=compress(summaryk−1​)

这条规则把失真从 (1−δ)k 降回 (1−δ)，是全节收益最大的一处改动。

  1. 压缩的轮数要有硬上限并记录。超过 kmax​ 就应当分层归档（把旧步骤的原文移到冷存储，只留引用），而不是继续叠代摘要。

2.4 如何测量压缩的损失#

"摘要好不好"不能靠感觉。三种可操作的度量：

度量 做法 读数含义
事实召回率 从原文抽取 N 条事实断言，检查摘要里保留了几条 覆盖率；低于阈值就拒绝该摘要
矛盾率 检查摘要里是否出现原文没有的断言（幻觉） 最重要的指标，必须为 0（或极低）
决策充分性 用摘要作输入，能否复现原来的决策？ 端到端验证：摘要是否够用

"决策充分性"是最终判据：如果基于摘要的决策与基于原文的决策一致率高，说明摘要抓住了决策相关的信息；不一致时，看差异是"信息缺失"还是"信息失真"——前者可以补，后者必须重算。

充分性=Pr[decision(summary)=decision(raw)]

三、记忆污染：三个机制#

3.1 机制一：幻觉固化（hallucination fixation）#

回路：模型推断 → 写入 → 被读取 → 被当作事实引用 → 更强的"证据"。

最危险的形态是"自证"：Agent 在任务 A 里推断"该客户偏好 PDF 格式"，写进记忆；任务 B 读到它，在报告里写"根据客户偏好，交付 PDF"；这句话又被写回记忆（作为"客户偏好 PDF 已被使用并确认"）。三轮之后，这条记忆的来源已经无从追溯，而且看起来经过了实践检验。

防御的三道闸：

闸 手段 位置
1 来源分级：模型推断进 pending，不进可读集合（上一节的 propose） 写入
2 来源链不可丢失：任何条目的 source 必须能追溯到原始证据；派生条目的 source 必须是另一条记忆的 id，且该链上不能只有模型推断 结构
3 读取时标注：未验证条目在渲染进上下文时必须带标记（[未验证]），且不得作为硬约束使用 读取

第 2 条的具体判据值得写成公式：

条目可读⟺∃ 一条来源链e0​→e1​→⋯→ek​,e0​∈{user_explicit, tool_deterministic}

即每条可读记忆的溯源链上必须有一个"可信根"。这条规则把"来源"从一个装饰字段变成了可验证的图性质。

3.2 机制二：过时（staleness）#

写入时正确，但世界变了。它的隐蔽性在于没有任何信号提示它错了 —— 记忆库看起来一切正常。

三种过时：

类型 例子 检测方式
事实漂移 客户地址变了 定期重取源头比对（对账式刷洗）
语义漂移 某字段的口径变了（"active_user"的定义改了） 需要版本化的映射表；纯记忆层无法解决
环境漂移 工具升级了，旧经验不再适用 记忆条目带 env 指纹，环境变化时降权

语义漂移是最难的，因为它不是"数据错了"，而是同一个词的含义变了。这类问题不能靠记忆层修，只能靠"记忆里存口径版本"：

{"claim": "活跃用户 12 万", "metric": "active_user",
 "metric_version": "v3", "observed_at": "2026-01-10"}

于是当 active_user 升级到 v4 时，所有带 v3 的记忆可以被批量标记为"口径过期"。

3.3 机制三：错误泛化（over-generalization）#

在特定情境下正确的结论被过度推广。它是最有欺骗性的一类，因为原文是对的：

观察到：在任务 A（arXiv 摘要，PDF 很大）里，"先抓摘要再抓全文"效果好
错误泛化：「凡是文档任务都要先抓摘要」
问题：在"必须全文才能判定的任务"（如法律条款比对）里，这个规则会导致结论错误

根因是摘要与归纳过程丢掉了适用条件（2.2 的第 ② 类损失）。防御手段：

  1. 每条归纳型记忆必须携带 condition（适用条件）字段，且写入时检查该字段非空：

规则型记忆=(claim, condition),condition=∅⇒拒绝写入

  1. 反转测试：写入前问一句"是否存在一个合理的场景，这条规则是错的？"如果答不出"不存在"，就必须补条件。这是可以自动化的（让审查模型举反例）。
  2. 保留反例：泛化时同时记录"当时观察到的一个不支持该规则的例子"，防止规则被当成绝对真理。

3.4 污染的检测：四种手段与它们的强弱#

手段 做法 能检测 强度
可核验引用 每条记忆带 evidence 指针，定期重取核对 事实漂移、无源幻觉 强（但需要源头可达）
时效性检查 fetched_at / ttl / valid_from；读时降权过期条目 过时 中强
矛盾检测（新写 vs 已有） 写前检索同 (subject, key) 的已有条目，比对 前后矛盾、值漂移 最强（覆盖面最广）
来源隔离 不同来源的条目分区存放、分别统计错误率 系统性缺陷（某来源总是错） 中

矛盾检测必须写清楚的一点：让模型"判断两句是否矛盾"是不够的，因为：

  • 模型的判断本身有错（尤其对"部分矛盾"："支持导出 CSV" vs "导出功能已下线"）；
  • 不一致有三种形态，处置完全不同：
形态 例子 处置
真矛盾 "地址是 A" vs "地址是 B"（同一时刻） 取更可信/更新的；标记冲突待核
时序更新（不是矛盾） "地址是 A"（2025）vs "地址是 B"（2026） 保留两条 + supersedes 链，最新生效
条件不同（不是矛盾） "支持导出"（企业版）vs "不支持导出"（免费版） 补 condition，两条都保留

所以矛盾检测的正确形态是先分类再处置：

新条目 n 与已有权威条目 e 的 key 相同：
  ├─ 值相同 → 去重（仅更新 fetched_at，不改 source 链）
  ├─ 值不同 且 n.valid_from > e.valid_from → 时序更新：e.superseded_by = n（保留历史）
  ├─ 值不同 且 条件不同 → 两条并存，各自补 condition
  └─ 值不同 且 同时同条件 → ★ 真冲突：不自动解决，标记 conflict 并降权二者，
                            交给核验（重取源头 / 问用户）

"真冲突时不自动解决"是关键：自动取"新的"或"更可信的"会静默丢弃信息，而冲突本身往往是最有价值的信号（它说明某个来源不可靠，或世界真的变了）。

四、遗忘：一项正面能力#

4.1 为什么必须遗忘#

三个理由，逐个都不容回避：

  1. 检索质量随噪声衰减。记忆库越大，无关条目越多，召回精度越低。设库内相关条目比例 r，一次检索取 top-k 中期望相关条目数为 kr —— r 下降直接降低有效信息密度。
  2. 成本。每次装载都占 token 预算（上一节的装载上限公式）。
  3. 合规。个人数据有法定保留期限与"被遗忘权"；无期限保留是法律风险，不是工程选择。

4.2 衰减评分：把"该忘什么"变成可计算的#

遗忘不能只靠 TTL（时间不是唯一因素：常用且重要的条目不该因为"旧"被删）。用一个评分函数：

S(e)=wr​⋅新近度2−Δt/h​​+wf​⋅使用频率log(1+hits)​​+wi​⋅重要性importance(e)​​

其中 Δt 是距上次访问的时间，h 是半衰期，hits 是被检索命中次数。

S(e)<Smin​⇒进入淘汰候选（不是立即删除）

每一项的取舍：

项 作用 单独使用的问题
新近度 淘汰过时内容 会淘汰"很少用但关键"的条目（如合规约束）
频率 保留有用的 富者愈富：没被检索到就永远衰减（与推荐系统的冷启动问题同构）
重要性 保护关键条目 重要性由谁定？通常需人工/规则标注

"富者愈富"这一条需要用探索来对冲：对从未被检索但满足条件的条目，周期性地强制注入一次候选（exploration），看它是否有用。否则一条早期没被检索到的正确经验会永远消失。

4.3 淘汰 ≠ 删除：墓碑与分层存储#

直接硬删除有三个问题：不可审计、无法回答"我为什么忘了它"、以及并发/缓存副本里的残留会导致不一致。所以淘汰应当是状态转移：

active ──S < S_min──→ cold（移出检索集合，仍可手工访问）
cold   ──超过保留期──→ tombstoned（内容置空，只留元数据：id/时间/原因）
tombstoned ──法定保留期后──→ （物理删除）

墓碑（tombstone）的价值：

墓碑=(id, 被删原因, 删除时间, 原 source 指针)

它让"为什么这条记忆不见了"可回答（第 7 章的归因需要这个：Agent 说"我不知道客户地址"，是没记还是忘了？），也让审计可进行。

4.4 与"只追加"的冲突：如何调和#

上一节说记忆应当是追加式日志（不覆盖、不删除）。这一节说必须遗忘。这不是矛盾，而是两个层次：

不可变的事实历史追加日志​​ 派生 ​可遗忘可检索视图​​

  • 事实历史（immutable log）保留追加语义：用于审计、对账、归因。它的"遗忘"是加密擦除（crypto-shredding）：把内容用每主体独立的密钥加密，删密钥即等效删除，而日志结构不被破坏。
  • 可检索视图（view/index）可以任意删除、衰减、重建 —— 因为它可以从日志重算。

删除请求⇒删除主体密钥+重建索引(日志本身不变)

这是"只追加"与"被遗忘权"的标准调和方式，也是唯一一种既不破坏不可变历史、又能真正实现删除的形态。

代码：写入门槛 + 反常摘要检测 + 矛盾分类 + 衰减淘汰#

下面的代码实现：(1) 五问写入门槛；(2) 摘要的"反幻觉"校验（否定句丢失、不确定模态丢失、数值漂移、缺条件）；(3) 矛盾检测的四分类处置（去重 / 时序更新 / 条件不同 / 真冲突）；(4) 衰减评分与分层淘汰（含墓碑）。

# ==================== (1) 写入门槛：五问 ====================
VERIFIABLE_SOURCES = ("user_explicit", "tool_deterministic")


@dataclass
class WriteDecision:
    write: bool
    target: str                 # reject | pending | active
    reasons: list[str] = field(default_factory=list)


def gate_write(cand: dict) -> WriteDecision:
    """
    ★ 设计决策：五问全部通过才写进 active。任何一问不通过 → 降级或拒绝。
      宁可不写：召回失败（少一条）比污染（错一条且被反复读取）便宜得多。
    """
    reasons: list[str] = []

    # 问 1：可核验吗？不可核验的只能做"线索"，不能做"事实"
    if not cand.get("evidence"):
        reasons.append("Q1 无可核验引用 → 只能作为线索（pending），不得作为事实")

    # 问 2：去语境化后仍成立吗？
    if not cand.get("context_free", False):
        reasons.append("Q2 依赖本次任务语境 → 应留在工作记忆，不进长期记忆")

    # 问 3：可重算吗？
    if cand.get("derivable"):
        reasons.append("Q3 可由原始数据重算 → 不写（单一事实来源）")

    # 问 4：会变化吗？变化类必须有 TTL / 版本
    if cand.get("mutable") and not (cand.get("ttl_seconds") or cand.get("metric_version")):
        reasons.append("Q4 可变但无 TTL/口径版本 → 拒绝（未来无法判断是否过期）")

    # 问 5：来源是谁？
    src = cand.get("source", "unknown")
    if src not in VERIFIABLE_SOURCES:
        reasons.append(f"Q5 来源 {src} 非用户/工具确证 → 进 pending 待确认")

    hard_fail = any(r.startswith(("Q2", "Q3", "Q4")) for r in reasons)
    to_pending = hard_fail is False and any(r.startswith("Q5") for r in reasons)
    if hard_fail:
        return WriteDecision(False, "reject", reasons)
    if to_pending:
        return WriteDecision(False, "pending", reasons)
    return WriteDecision(True, "active", reasons or ["五问通过"])


# ==================== (2) 反幻觉摘要校验 ====================
NEG_MARKERS = ("不", "禁止", "仅限", "不得", "无法", "No ", "not ", "only")
MODAL_MARKERS = ("可能", "推测", "未验证", "据", "大约", "inferred", "unverified", "maybe")
NUM_RE = re.compile(r"\d+(?:[.,]\d+)?\s*(?:ms|s|%|万|k|M|GB|MB)?")


@dataclass
class SummaryAudit:
    ok: bool
    issues: list[str]
    coverage: float          # 数值覆盖率（2.4 的事实召回率的可计算代理）


def audit_summary(raw: str, summary: str) -> SummaryAudit:
    """
    ★ 设计决策：把 2.2 的四类可预测损失变成可机械检查的规则。
      这些规则拦不住所有失真，但它们拦住的都是"摘要制造幻觉"的那一类 —— 收益最高。
    """
    issues: list[str] = []

    # 损失 ③：不确定性被抹掉 → 这是幻觉固化的主通道
    raw_modal = [m for m in MODAL_MARKERS if m in raw]
    if raw_modal and not any(m in summary for m in MODAL_MARKERS):
        issues.append(f"模态丢失：原文有不确定性标记 {raw_modal}，摘要变成确定断言"
                      f" → ★ 污染风险最高，必须保留 modality 字段")

    # 损失 ④：否定与量词被弱化
    raw_negs = [m for m in NEG_MARKERS if m in raw]
    if raw_negs and not any(m in summary for m in NEG_MARKERS):
        issues.append(f"否定丢失：原文含 {raw_negs}，摘要无对应否定标记 → 约束失去可执行性")

    # 损失 ①：数值漂移 / 丢失
    raw_nums = set(NUM_RE.findall(raw))
    kept = {n for n in raw_nums if n.strip() in summary}
    coverage = len(kept) / len(raw_nums) if raw_nums else 1.0
    if raw_nums and coverage < 0.6:
        issues.append(f"数值覆盖率仅 {coverage:.0%}（原文 {len(raw_nums)} 个，保留 {len(kept)} 个）"
                      f" → 摘要中的数字必须从原文复制，不允许生成")

    # 损失 ②：条件与例外被丢掉
    if ("除" in raw or "但" in raw or "除…外" in raw) and ("除" not in summary and "但" not in summary):
        issues.append("条件/例外丢失：原文有条件从句，摘要只保留主句 → 规则会被泛化误用")

    return SummaryAudit(ok=not issues, issues=issues, coverage=coverage)


def compress_from_raw(raw_log: list[str], summarize_fn) -> dict:
    """
    ★ 设计决策：每次压缩都从**原始日志**重算，而不是压缩"上一次的摘要"。
      这把级联失真从 (1-δ)^k 降回 (1-δ) —— 本节收益最大的一处改动（2.3）。
    """
    joined = "\n---\n".join(raw_log)
    summary = summarize_fn(joined)
    audit = audit_summary(joined, summary)
    if not audit.ok:
        # ★ 审计不过则不采用该摘要：退回结构化抽取（可核验），而不是把有幻觉的摘要写进记忆
        return {"accepted": False, "fallback": "structured_extract",
                "issues": audit.issues, "coverage": round(audit.coverage, 2)}
    return {"accepted": True, "summary": summary, "coverage": round(audit.coverage, 2),
            "compression_round": 1, "source": "raw_log"}


# ==================== (3) 矛盾检测：四分类处置 ====================
@dataclass
class Assertion:
    aid: str
    subject: str
    key: str
    value: Any
    source: str
    valid_from: float
    condition: str = ""            # ★ 泛化型记忆必须有适用条件（3.3）
    metric_version: str = ""
    superseded_by: Optional[str] = None
    conflict: bool = False


def reconcile(new: Assertion, existing: list[Assertion]) -> dict:
    """
    ★ 设计决策：**不自动解决真冲突**。自动取"更新的"或"更可信的"会静默丢信息，
      而冲突本身是最有价值的信号（说明某来源不可靠，或世界真的变了）。
    """
    same_key = [e for e in existing if e.subject == new.subject and e.key == new.key]
    if not same_key:
        return {"action": "insert", "note": "无同键条目"}

    for e in same_key:
        if e.value == new.value:
            return {"action": "dedupe", "note": f"与 {e.aid} 值相同：仅更新 fetched_at，不动 source 链"}

    # 条件不同 → 不是矛盾，两条并存
    if any(e.condition and e.condition != new.condition for e in same_key):
        return {"action": "coexist", "note": "条件不同：两条都保留，各自补 condition"}

    # 时序更新 → 保留历史，建立 supersedes 链
    older = [e for e in same_key if e.valid_from < new.valid_from]
    if older and all(not e.condition for e in same_key):
        victim = max(older, key=lambda e: e.valid_from)
        victim.superseded_by = new.aid
        return {"action": "supersede", "superseded": victim.aid,
                "note": "时序更新：旧条目保留（可审计），最新生效"}

    # 同时同条件 → 真冲突：标记、降权、交人工/重取源头
    for e in same_key:
        e.conflict = True
    new.conflict = True
    return {"action": "conflict", "with": [e.aid for e in same_key],
            "note": ("★ 真冲突：不自动解决。降权二者，触发核验"
                     "（重取源头 / 询问用户）。冲突本身是『某来源不可靠』的信号")}


def generalization_guard(a: Assertion) -> Optional[str]:
    """★ 3.3：规则型记忆必须带适用条件，否则拒绝写入。"""
    rule_like = any(w in str(a.value) for w in ("必须", "总是", "不要", "凡是", "一律"))
    if rule_like and not a.condition:
        return "规则型记忆缺 condition（适用条件）→ 拒绝写入：无条件的规则会被错误泛化"
    return None


# ==================== (4) 衰减淘汰 + 墓碑 ====================
@dataclass
class MemEntry:
    aid: str
    payload: Any
    created_at: float
    last_hit_at: float
    hits: int = 0
    importance: float = 0.5
    state: str = "active"          # active | cold | tombstoned
    tombstone_reason: str = ""
    key_ref: str = ""              # ★ 加密擦除用的主体密钥引用（4.4）


def decay_score(e: MemEntry, now: float, half_life_days: float = 30.0,
                w_recency: float = 1.0, w_freq: float = 0.6,
                w_importance: float = 1.2) -> float:
    """
    ★ 设计决策：三项缺一不可。
      只用新近度会淘汰"很少用但关键"的合规约束；只用频率会陷入富者愈富
      （没被检索到就永远衰减）—— 所以 importance 项是冷启动的补偿，并配合
      周期性探索（force_explore）打破自证循环。
    """
    dt = max(0.0, now - e.last_hit_at)
    recency = 2 ** (-dt / (half_life_days * 86400.0))
    freq = math.log1p(e.hits)
    return w_recency * recency + w_freq * freq + w_importance * e.importance


def sweep(entries: list[MemEntry], now: float, s_min: float = 0.8,
          cold_retention_days: float = 180.0) -> dict:
    """分层淘汰：active → cold → tombstoned。★ 淘汰是状态转移，不是硬删除。"""
    moved_cold, tombstoned = [], []
    for e in entries:
        s = decay_score(e, now)
        if e.state == "active" and s < s_min:
            e.state, e.tombstone_reason = "cold", f"衰减评分 {s:.2f} < {s_min}"
            moved_cold.append(e.aid)
        elif e.state == "cold" and (now - e.last_hit_at) > cold_retention_days * 86400:
            e.state, e.tombstone_reason = "tombstoned", "超过冷层保留期"
            e.payload = None            # 内容置空，只留元数据（可审计"为什么忘了"）
            tombstoned.append(e.aid)
    return {"to_cold": moved_cold, "tombstoned": tombstoned}


def force_explore(entries: list[MemEntry], n: int = 1) -> list[str]:
    """
    ★ 反"富者愈富"：把从未被命中的条目强制注入一次候选集，
      否则一条早期没被检索到的正确经验会永远消失（4.2 的探索项）。
    """
    cold_never_hit = [e for e in entries if e.state == "active" and e.hits == 0]
    return [e.aid for e in sorted(cold_never_hit, key=lambda x: x.created_at)[:n]]


def crypto_shred(entries: list[MemEntry], key_ref: str) -> dict:
    """
    ★ 4.4：删除请求 = 删除主体密钥 + 重建索引，**追加日志本身不变**。
      这是"只追加"与"被遗忘权"唯一不冲突的调和形态。
    """
    affected = [e for e in entries if e.key_ref == key_ref]
    for e in affected:
        e.state, e.payload, e.tombstone_reason = "tombstoned", None, "crypto-shredded: 主体密钥已删除"
    return {"shredded_key": key_ref, "affected": [e.aid for e in affected],
            "note": "日志结构未变；检索视图需重建（可从日志重算）"}

          [e.aid for e in entries if e.aid == "m3" and e.state == "active"],
          "← importance=1.0 保住了它（只用新近度会误删）")
    print("  加密擦除 user:u_1:", crypto_shred(entries, "user:u_1"))

    # ---- 附带自检 ----
    assert len({hashlib.sha256(b"x").hexdigest() for _ in range(2)}) == 1

八处关键设计决策：

  1. gate_write 的五问里，Q1（可核验）排第一，且任何硬性问题（Q2/Q3/Q4）直接拒绝。理由是全节的成本不对称：漏记一条的代价是"少知道一件事"，写错一条的代价是"持续知道一件错事"。
  2. audit_summary 把 2.2 的四类损失变成机械检查。其中模态丢失检查排在最前，因为它是"摘要制造幻觉"的直接通道 —— 这条检查的收益远高于其他三条。
  3. compress_from_raw 强制从原始日志重算，并把 compression_round 固定为 1。这把级联失真 (1−δ)k 降回 (1−δ)，并且让"压缩轮数"成为一个可监控的量。
  4. 摘要审计不通过时退回结构化抽取而不是"接受这条有幻觉的摘要"。这是"引用 > 结构化抽取 > 摘要"这个优先级在代码里的落点。
  5. reconcile 把不一致分成四类并分别处置。最重要的一行是"真冲突不自动解决"：自动取值会静默丢信息，而冲突本身是"某来源不可靠"的信号。
  6. generalization_guard 强制规则型记忆携带 condition。无条件的规则就是错误泛化的定义（3.3）。
  7. decay_score 保留 importance 项并用 force_explore 对冲"富者愈富"。演示里的 m3（合规约束，500 天没动过）就是"只用新近度会误删"的例子。
  8. crypto_shred 演示"只追加"与"被遗忘权"的调和：删密钥 + 重建索引，日志结构不变。这是唯一既不破坏审计性又能真正删除的形态。

练习#

  1. 写入门槛实战：下面六条候选记忆，逐条过五问并给出处置（active / pending / reject）与理由： （a）"用户是财务总监"（模型从对话推断）；（b）"订单 o_123 总额 1000 元"（工具返回）； （c）"该 API 的 p99 是 1.8s"（工具返回，来自一次压测）；（d）"用户不喜欢红色"（用户说过"这个红色太刺眼"）； （e）"本次任务用了 42000 token"；（f）"客户 c_9 的信用等级是 A"（三年前从 CRM 读取）。

  2. 摘要审计：给出一段 200 字左右的原文与三份不同的摘要（一份忠实、一份丢模态、一份丢条件），用 2.2 的四类损失逐条标注每份摘要的问题。然后说明：如果这三份摘要都要进记忆，你会怎么处理？（提示：拒绝 / 结构化抽取 / 加 modality 字段。）

  3. 级联压缩的计算：某长任务 200 步，每 20 步压缩一次上下文。若单轮摘要的事实召回率是 0.88，请分别计算"叠代摘要"与"从原始日志重算"两种做法在第 200 步时的期望信息保留率。然后给出一个工程判据：什么时候必须放弃叠代、改为分层归档（给一个阈值与理由）。

  4. 矛盾分类：下面五组，逐组判定属于"真矛盾 / 时序更新 / 条件不同"，并给出处置： （a）"支持导出 CSV" vs "导出功能已下线"；（b）"地址 A"（2024）vs "地址 B"（2026）； （c）"支持导出"（企业版）vs "不支持导出"（免费版）；（d）"该客户已付款"（工具）vs "该客户未付款"（模型推断）； （e）"API 限流 100 QPS"vs"API 限流 100 QPS（突发可到 200）"。 其中哪一组必须触发人工/源头核验？为什么"自动取更新的"会丢信息？

  5. 污染检测设计：为"客户地址"这类高污染风险字段设计一套完整的检测机制。要求覆盖：写入门槛、源头重取（对账）的周期与触发条件、真冲突的处置流程、以及如何度量"这套机制真的把污染率降下来了"（给一个可计算的指标）。要说明"让模型自己判断这条地址对不对"为什么不是有效防线。

  6. 遗忘与合规：某系统有"只追加不可变日志 + 可检索视图"两层。现在收到一份个人数据删除请求。请写清：删什么、不删什么、如何保证检索视图不再返回该数据、如何验证删除完成、以及如何避免"日志里的密文被保留"被认定为未删除（提示：加密擦除与密钥管理）。

  7. 探索机制：为什么只用"使用频率"做遗忘评分会导致"富者愈富"？请构造一个具体场景说明一条正确的记忆会被永久淘汰，并设计探索机制（触发条件、探索预算、以及如何度量探索是否有效）。再回答：探索预算从哪来（它挤占了什么）？

小结#

  • 记忆系统的质量上限是写入纪律，不是容量。 污染的增长不是线性的：ϵn+ϵ2(2n​) —— 第二项是"污染被复制后再扩散"，这是必须主动处理它的原因。
  • "立即写 vs 验证后写"是假对立：决定写入质量的是来源可验证性。正确做法是分层：层 A 原始观察（立即写、只追加、安全）→ 层 B 结构化抽取（可校验、可回指）→ 层 C 结论与偏好（唯一有污染风险的一层，必须过门槛）。
  • 写入门槛五问：可核验吗 / 去语境化后成立吗 / 可重算吗 / 会变化吗 / 来源是谁。宁可不写 —— 召回失败的代价远低于污染。
  • 形态优先级：引用 > 结构化抽取 > 摘要。 引用（指针）可重取、可核验、永不过期；摘要是有损且有偏的编码。凡能放指针处不放摘要。指针式缓存要命名为 cached_value 并带 fetched_at / source_version。
  • 否定性记忆价值极高但写入率极低（它藏在行为里）。它比肯定性记忆更需要谨慎：仅由行为推断的否定观察进检索式记忆（failure 先例），只有被显式确认才进长期记忆的硬约束。
  • 摘要必然丢四类信息：数值精度、条件与例外、时间与不确定性标记（最致命，是幻觉固化的主通道）、否定与量词。这四类可以机械检查；摘要必须保留 modality 字段，数值只允许从原文复制。
  • 压缩要从原始日志重算，不要叠代摘要：(1−δ)k 降到 (1−δ)，这是本节收益最大的一处改动。压缩轮数要有硬上限并记录。
  • 污染三机制：幻觉固化（防御 = 来源分级 + 可信根（溯源链上必须有用户/工具确证的一环）+ 读取标注）、过时（事实漂移 / 语义漂移需口径版本 / 环境漂移需 env 指纹）、错误泛化（规则型记忆必须带 condition，无条件即错误泛化的定义）。
  • 矛盾检测先分类再处置：去重 / 时序更新（保留历史 + supersedes）/ 条件不同（并存）/ 真冲突（不自动解决，降权 + 核验）。自动取"更新的"会静默丢信息，而冲突本身是最有价值的信号。
  • 遗忘是正面能力：新近度 + 频率 + 重要性三项缺一不可（只用新近度会误删合规约束，只用频率会富者愈富 → 需 force_explore 探索）。淘汰 ≠ 删除：active → cold → tombstoned，墓碑让"为什么忘了它"可回答。
  • "只追加"与"被遗忘权"的调和：不可变事实历史 + 可重建的检索视图；删除 = 加密擦除（删主体密钥）+ 重建索引，日志结构不变。

下一节：现在你知道该写什么、该怎么忘了。但还有一个每步都在发生的问题：这一步该给模型看什么。记忆再多，能进上下文的只有那么多 token —— 而"塞更多"通常更差。这是上下文工程的问题。
