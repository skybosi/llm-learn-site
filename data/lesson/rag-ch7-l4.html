边界与失效清单：什么场景不该用 RAG#

这一节要解决什么#

前面 27 节都在讲"怎么把 RAG 做好"。最后一节反过来问一个更值钱的问题：

什么情况下，你根本不该用 RAG？

这个问题比它看起来重要得多，因为 RAG 有一个很坏的失败模式：它能让一个不适合检索的任务"看起来在工作"。用户问"这三年的营收同比是多少"，系统会检索到三份财报、把三段文字拼进上下文、生成一段听起来合理但算术错误的回答。没有任何异常，指标也不难看，但答案是错的。 如果这个任务本该用 SQL 或代码执行，那这套 RAG 系统的全部复杂度都是在制造可信的错误。

本节要回答四个问题：

  1. RAG 的适用条件是什么？不满足每一条时会怎样？
  2. 哪些场景不该用（或不该只用）RAG？替代方案是什么？怎么判断该迁移了？
  3. 参数记忆、检索、微调、工具 —— 四者怎么选？微调在什么条件下比 RAG 划算（给可算的判据）？
  4. 上线前必须逐条过的检查表长什么样？每一项的判据与处置是什么？

结论先放在这里：RAG 不是"默认正确的架构"，它是一个有明确适用边界的工程方案。判据是：知识可外部化为文档、会变、需要审计与授权、查询可分解为"定位 + 抽取/归纳"、能容忍非确定性、且有评测与维护能力。缺其中任何一条，都要先解决那一条，而不是先搭 RAG。 而"什么时候该迁移走"同样可判：当任务的正确性依赖精确计算、全局聚合、结构化查询或确定性规则时，检索结构性地给不了保证。

一、先立判据：RAG 的适用条件#

回到第 1 章立下的四条边界（容量 / 时效 / 可审计 / 可控），把它们展开成七条可检验的适用条件：

# 适用条件 不满足时的具体失效表现 怎么检验
1 知识可外部化为文档 知识存在于人的经验、流程、口头约定里 → 检索无内容可召 抽样 50 个真实问题，问"答案在哪份文里"；答不出的比例
2 知识会变，且变更频率高于重训成本 知识static 且已进参数 → 检索是纯粹的额外复杂度 统计知识变更频率与重训成本（§3 的盈亏平衡式）
3 查询可分解为"定位 + 抽取/归纳" 需要跨文档推理、计算、多步规划 → 检索给了材料但给不了结论 标注 100 题：多少题在找到证据后"读一遍就能答"
4 能容忍非确定性输出 同一问题两次回答必须逐字一致（合规/对账）→ 生成不满足 对同一批题跑 3 次，测答案一致率
5 有（或愿意建立）评测能力 无评测 → 改动无法判断好坏，错误被平均分掩盖 是否有带黄金证据的评测集与门禁（ch7-l2）
6 有权限与审计要求 无权限要求 → 检索的可授权优势用不上，长上下文可能更简单 是否存在多角色可见性差异
7 错误代价可承受（或可拒答） 错一次就是事故且不能拒答 → 需要规则引擎而非概率系统 单次错误的业务代价与拒答的可接受性

这七条不是"全都满足才能用"，而是"不满足的那条要先被解决"：

  • 不满足 1：先做知识沉淀（文档化），否则 RAG 无从下手；
  • 不满足 2：考虑微调或直接进提示（§3）；
  • 不满足 3：接工具（计算/查询/代码执行），把 RAG 降级为"提供工具参数"的一环；
  • 不满足 4：用检索 + 模板化输出（不生成自由文本），或改用规则；
  • 不满足 5：先建评测 —— 这是最容易被跳过、代价最大的一条；
  • 不满足 6：可以省掉权限层，架构会简单很多；
  • 不满足 7：加拒答策略，或整体换方案。

二、不该用（或不该只用）RAG 的场景清单#

下面 13 条，每条给出：为什么在这里 RAG 无效或低效（机制）→ 该用什么替代 → 迁移判据。

# 场景 为什么 RAG 在这里不行（机制） 替代方案 迁移判据
1 需要精确计算/聚合（同比、求和、比率） 检索提供的是文本，模型的算术没有符号保证；即使证据正确，计算也可能错 代码执行 / 计算器工具 / SQL 聚合 评测里出现"证据全对但答案错"的比例 > 5%
2 结构化数据与事务查询（订单、库存、账户） RAG 对结构化查询是有损近似：切分会破坏行/列结构，语义相似度不等于条件匹配 数据库直查 / SQL / API 查询可用 WHERE/JOIN 精确表达
3 单篇长文档深读（合同条款解释） 检索会切碎跨段指代与条款引用关系 长上下文直读（ch5-l1） 文档总长 < 有效上下文 neff​
4 全局摘要/计数/全集否定（"哪些文档没有提到 X"） 检索按相关度取样，天然漏；联合命中概率指数衰减（ch5-l1 §2.3） map-reduce / 层次摘要 / 结构化聚合 问题需要覆盖全语料而非"找到相关段"
5 必须 100% 确定且可审计的规则判定（风控、合规判定） 生成是非确定的；同一输入两次输出可能不同 规则引擎 / 决策表 / 有限状态机 存在不容许例外的判定规则
6 极低延迟（端到端 <100ms） decode 是固定地板（ch5-l4：输出 220 token ≈ 1320ms 量级），检索优化改不动它 缓存/预计算/小模型/不用 LLM P99 预算 < decode 地板
7 强多步数学/规划 检索不提供推理保证；证据齐全也可能算错 工具 + 验证器 + 推理模型 失败模式以"推理错"为主而非"证据缺"
8 数据不允许出域且无法本地部署 合规优先：任何便利都不能换 本地化部署 + 私有检索（需成本论证） 数据驻留是硬约束
9 没有评测能力也没有维护预算 无评测 → 错误被平均分掩盖；无预算 → 索引与评测集腐化 先补评测（ch7-l2） 无人能说出当前 recall 与失败分布
10 领域文档稀缺或质量极差 垃圾进垃圾出；检索放大噪声 先做数据工程（ch7-l1 的需求问卷） 抽样 50 题里"文档里根本没有答案"的比例高
11 高风险对抗输入且无隔离 提示注入会直接打穿检索层（ch6-l3 的威胁模型第 6 条） 先做安全边界与沙箱 输入来自不可信用户且系统有副作用
12 一次性/极低频问题 索引建设成本摊不薄 直接查文档/搜索 问题总次数 × 单次价值 < 建索引成本
13 需要跨文档因果推理而证据稀疏 每篇只说一部分，且因果链不在单篇里 知识图谱 / 结构化抽取 + 规则 标注显示"证据齐全仍无法答对"的比例高

使用这张表的正确姿势：不是"命中一条就放弃 RAG"，而是命中硬条件（1、2、5、6）时,必须引入替代方案；命中软条件（3、4、7、10、13）时，保留 RAG 但把它降级为流水线的一环（例如检索负责找参数，计算交给工具）。

2.1 一个常见误判：把"检索不到"当成"不该用 RAG"#

第 9、10 条很容易被误用成"RAG 不行"的借口。判别方法：

如果失败的主要形态是"证据根本不在语料里"，那是数据问题（先补数据）； 如果证据在语料里、检索也能找回，只是答案错，那才是方案问题（考虑替代方案）。

这个区分靠第 7 章第 2 节的失败分类："召回失败"占比高 ⇒ 数据/检索问题；"生成未用"占比高 ⇒ 方案问题。

三、参数记忆 / 检索 / 微调 / 工具：四选一还是组合#

3.1 四维对比#

维度 参数记忆（预训练/微调） 检索（RAG） 工具（计算/查询/API）
时效性 差（需重训） 好（改文档即生效） 好（实时）
可审计 差（无法给出证据） 好（doc/chunk id + 版本） 好（调用参数可记录）
可授权 差（无法按人裁剪权重） 好（ACL 前置过滤） 好（按凭证）
单次成本 低（无检索与长上下文） 中（检索 + 上下文 token） 中（一次工具调用）
更新成本 高（重训/重嵌入） 低（增量索引，ch6-l1） 中（改接口）
可控性 低（不可干预） 中（可干预证据） 高（参数可校验）
延迟 最低 中高 低
擅长 形式、风格、格式、领域语感 事实、时效、可追溯 精确计算、事务、副作用

一句话分工：

微调擅长"怎么说"，检索擅长"依据什么说"，工具擅长"算得对/查得准"。

3.2 微调什么时候比 RAG 划算：一个盈亏平衡式#

微调不是 RAG 的替代品，而是在某些条件下更划算的另一种手段。设：

  • 微调的一次性成本 Ctrain​（数据准备 + 训练 + 评测 + 上线，含人力）；
  • 微调后每次调用的节省 Δc（省掉检索与长上下文的 token 成本，或可用更小模型）；
  • 查询总量 Q（生命周期内）。

则微调划算当且仅当：

Ctrain​<Δc⋅Q

⚠️ 示例：设 Ctrain​=15 万元（含标注与人力），Δc=0.02 元/次（检索 + 上下文摊薄），则盈亏平衡点为

Q∗=0.02150000​=7.5×106 次

Q∗=0.02150000​=7.5×106 次

读法：在 750 万次调用之前，微调在纯成本上不划算。这意味着：

  • 高频、稳定、格式约束严格的场景（例如把结构化抽取固化进模型）值得微调；
  • 低频、知识多变、需要审计的场景，RAG 几乎总是更优。

注意这里的比较只算成本，不算质量。微调真正的价值常常在质量维度（更好的格式遵循、更稳定的抽取），此时应当用第 5 章第 4 节的边际成本框架比较，而不是只看 Q∗。

3.3 组合的三种形态#

形态 分工 适用
RAG + 微调 微调管格式与风格，检索管事实 输出格式严格（结构化字段、引用格式）且知识多变
RAG + 工具 检索找参数，工具做计算/查询 需要精确计算或事务（场景 1、2）
微调 + 工具（无检索） 知识已稳定且可进参数，实时数据走 API 知识 static、只差实时数据

判据：先问"这个任务的正确性依赖什么？"——依赖事实就上检索；依赖形式就上微调；依赖计算/事务就上工具。三者不冲突，冲突的是"以为一个能包打天下"。

四、上线前失效清单（可逐条打勾）#

这是全课的收敛资产：33 条检查项，分五类，每条给出"症状 → 判据 → 处置"。它的用法是在发布前逐条过，任何一条 FAIL 都阻断发布（硬条件）或记录豁免理由（软条件）。

五、维护成本与长期责任#

RAG 是持续运营，不是一次性项目。年度成本项至少包括：

成本项 驱动因素 典型频率
全量重建索引 embedder/切分版本变更、δ>δ∗ 每季度 ~ 每年
增量更新与压实 文档变更率 δ 每日
评测集维护 分布漂移、新租户、新话题 每季度换血
模型升级 上游模型换代、成本下降 每半年 ~ 每年
权限变更 组织调整、离职、租户增删 持续
成本增长 用量增长、上下文变长 持续（按月复核）
告警与事故处理 探针失败、版本漂移 持续
人员交接 文档、ADR、运行手册 每年

判据：如果这套成本没有被计入预算，那么"上线"只是把技术债转成了运营事故。第 7 章第 1 节的需求问卷里"运维"那一行，问的就是这件事。

def decide(feat):
    hits = [(k, why, alt, reason) for k, why, alt, reason in RULES if feat.get(k)]
    if not hits:
        return dict(verdict="用 RAG", why="检索能提供外部知识 + 可审计 + 可更新 + 可授权",
                    alternatives=[], note="仍需先建评测（ch7-l2）并量化 SLO（ch7-l1）")
    hard = {"need_exact_compute", "structured_data", "needs_determinism", "ultra_low_latency"}
    if any(k in hard for k, *_ in hits):
        return dict(verdict="不用（或不用纯）RAG", why=[h[1] for h in hits],
                    alternatives=[h[2] for h in hits], note="以上任一条成立，纯 RAG 都不划算")
    return dict(verdict="RAG + 其它手段（混合）", why=[h[1] for h in hits],
                alternatives=[h[2] for h in hits],
                note="保留检索，但对上述场景分别接工具/长上下文/先补数据与评测")

关键设计决策：decide() 故意写成规则而非打分模型。原因是这类决策必须可解释：当它给出"不用纯 RAG"时，必须能列出具体是哪条规则触发的，否则使用者无法反驳也无法修正规则。同理，audit() 的每一条都输出"症状 + 处置"，而不是一个分数 —— 检查表的价值在于它直接给出动作，而不是一个需要解释的数字。

练习#

  1. 给决策器加规则并验证不冲突。加入两条新规则："需要流式输出且首 token < 300ms"与"知识变更频率 < 1 次/年"。为每条写触发条件、替代方案与理由，然后构造两个场景验证它们不会与已有规则矛盾（提示：注意"知识不常变"与"需要时效"是互补条件）。

  2. 把清单做成 CI 门禁。把 §4 的 33 条整理成一个 JSON 配置（每条含 key、judge、severity、action），并实现一个脚本读取指标快照输出 PASS/WARN/FAIL 与退出码。说明 severity 怎么分（提示：越权与合规类应为 blocker）。

  3. 构造"看起来健康但危险"的快照。所有指标都在阈值内，但存在一个致命问题（例如 canary_leaks=0 但 acl_missing_docs 即将变成 100，或 refuse_rate=0.02 恰好在下界）。说明你的清单能否捕获它；如果不能，需要补哪一条检查项。

  4. 算一次微调的盈亏平衡。用你系统的真实单价估算 Ctrain​ 与 Δc，算出 Q∗。然后回答：如果把质量收益也计入（例如微调让格式遵循率从 80% 到 98%），你会怎么用第 5 章第 4 节的边际成本框架做决策？

  5. 为 13 个"不该用"场景各写一个判据实验。要求每个实验都能在一天内用现有数据跑出来（例如场景 1 的判据是"证据全对但答案错的比例 > 5%"，需要什么标注？）。说明哪些实验需要新标注、哪些只需现有日志。

  6. 审查你自己的系统。用 §1 的七条适用条件与 §4 的 33 条清单，给你的系统逐条打分（满足/不满足/未知）。对"未知"项写出获取答案的最小动作（找谁、看什么、跑什么）。然后给出结论：现在最该做的一件事是什么，依据是哪一条检查项。

  7. 降级路径设计。为 RAG 系统的四个外部依赖（LLM、检索、重排、缓存）各写一个降级动作与降级后的质量/延迟预期。回答：哪一条降级可以接受，哪一条应当直接拒绝服务，判据是什么。

  8. 写一份"退出方案"。假设你的 RAG 系统上线一年后发现不适合（例如失败分类显示 60% 是"推理错"），写一份迁移方案：迁移到哪个方案、需要保留哪些资产（评测集、权限层、trace）、迁移期的双跑与回滚安排。这份文档应当与 ADR 一样包含"何时重审"。

小结#

  • RAG 的七条适用条件：知识可外部化为文档、知识会变、查询可分解为"定位 + 抽取/归纳"、能容忍非确定性、有评测能力、有权限与审计要求、错误代价可承受。不满足的那一条要先被解决，而不是先搭 RAG。
  • 13 个不该用（或不该只用）RAG 的场景：精确计算、结构化/事务查询、单文档深读、全局聚合/计数/全集否定、确定性规则判定、极低延迟、强多步数学、数据不能出域、无评测无预算、文档稀缺、对抗输入无隔离、一次性问题、跨文档因果推理。每条都给了机制与替代方案。
  • 硬条件（1/2/5/6）必须引入替代方案；软条件保留 RAG 但降级为流水线一环。
  • 别把"检索不到"当成"不该用 RAG"：先看失败分类 —— 召回失败占比高是数据/检索问题，生成未用占比高才是方案问题。
  • 分工一句话：微调擅长"怎么说"，检索擅长"依据什么说"，工具擅长"算得对/查得准"。
  • 微调的盈亏平衡：Ctrain​<Δc⋅Q。⚠️ 示例：Ctrain​=15 万元、Δc=0.02 元/次 → Q∗=7.5×106 次。在 750 万次调用之前，纯成本上微调不划算（质量维度需另用 MC 框架比较）。
  • 上线前 33 条失效清单（数据 7 / 索引 6 / 检索 8 / 生成 6 / 运营 6），每条含症状、判据、处置；⚠️ 代码实现了其中 16 条的自动自检：健康快照 PASS=16 FAIL=0，病态快照 PASS=0 FAIL=16（含 canary_leaks=2、version_drift=5、recall_at_10=0.71）。
  • 清单必须是自动化断言（进 CI 或每日快照），否则等于没有检查。越权与合规类必须是 blocker，直接阻断发布。
  • RAG 是持续运营不是一次性项目：全量重建、增量压实、评测集换血、模型升级、权限变更、成本增长、告警处理、人员交接 —— 这八项都要进预算。
  • 一句话：RAG 不是默认正确的架构，而是一个有明确适用边界的方案。判断力体现在两处：动手前能说清"为什么需要检索"，上线后能说清"哪一条检查项不过、该换成什么"。

判断力清单 —— 遇到任何新的"知识问答"需求时，先问这九个问题：

  1. 知识在哪里？ 能不能外部化为文档？变更频率多高？
  2. 正确答案依赖什么？ 事实（检索）、形式（微调）、还是计算/事务（工具）？
  3. 失败的主要形态是什么？ 证据不在语料（补数据）、召回不到（修检索）、还是找到了不用（修排序/生成）？
  4. 有效上下文有多大？ 我有 neff​ 的实测值，还是只知道窗口标称值？
  5. 权限与审计的要求是什么？ 谁来裁剪可见性？怎么证明不漏？
  6. 质量怎么度量？ 有没有带黄金证据的评测集？它能检出多大的效应？
  7. 延迟与成本的瓶颈在哪一段？ 是 decode 地板，还是检索/prefill？
  8. 出错能退回去吗？ 索引、模型、模板、缓存，各自怎么回滚？
  9. 谁会维护它？ 评测集换血、模型升级、权限变更、成本增长，谁负责？

继续深入的方向：

  • 多模态检索：图像、表格、图表的统一表征与跨模态检索（现有课止步于文本）；
  • Agentic 检索：把检索当作工具，由模型决定何时检索、检索几次、是否重写（对应 agent-systems）；
  • 结构化与图检索：把知识图谱、SQL、表格与向量检索统一到一个查询计划里；
  • 检索与训练的联合优化：把检索器放进训练回路（如可微检索、检索增强微调），而不是把检索当成训练后的外挂；
  • 评测基准与失效分析：面向多跳、聚合、时效、权限的细粒度基准，以及"证据全对但答案错"这类失败的系统性归因。

到此为止，这门课给出的不是一份"最佳实践清单"，而是一套判断依据：每一个设计决策都能推导或给出可测判据，每一个结论都标明了它成立的边界。当你在真实系统里遇到本课没覆盖的情况时，希望你能用同样的方式把它推出来 —— 这才是"知其所以然"的全部意义。

全课收束：七章的主线是一条从"为什么"到"怎么做"再到"什么时候不该做"的链路。第 1 章立下外部知识的四条边界（容量/时效/可审计/可控），并证明稀疏、稠密、混合三条检索路线各自的成立前提与失效条件 —— 混合有效的关键不是"用了两种方法"，而是误差不相关。第 2 章把文档变成可检索单元：切分粒度是语义完整性与检索精度的定量交换；HNSW/IVF/量化的近似代价可算，端到端召回是"定位 × 展开 × 打分"三项之积；更新必须走墓碑与版本。第 3 章处理候选池到上下文之间的排序与融合：向量相似度不等于相关性是架构假设的必然结果，cross-encoder 用交互换精度、代价可算，RRF 稳健但需要互补度作前提。第 4 章把查询本身当作变量：词汇缺口、意图欠定、组合性三类缺陷的处方完全不同，选错类别等于白做。第 5 章划出长上下文的边界：窗口变大改变成本斜率而不改变判据，neff​ 要实测，上下文是一份要按边际收益分配的预算，"检索到了却没用"有四种可分离的病，延迟与成本可以逐段算清并落在 Pareto 前沿上。第 6 章把它变成能长期运行的系统：段式索引可回滚、缓存键决定权限边界、ACL 必须前置且要能被 canary 证伪、每次问答都要留下可重放的证据链。第 7 章把这一切收成一个能力 —— 从 SLO 反推架构、用指标树与统计判据驱动迭代、用一个完整案例走一遍"测量→诊断→修复"，最后知道什么场景不该用 RAG。
