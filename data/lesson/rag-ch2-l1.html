切分粒度的信息论视角：语义完整性与检索精度的定量取舍#

这一节要解决什么#

所有 RAG 教程都会给一个数字："chunk size 512 token，overlap 50~100 token"。很少有人解释这个数字从哪来。于是出现了两种同样糟糕的情况：

  • 有人把 512 当常数用，然后在"每一节都很短的 FAQ 文档"上把两个不相关的问题切进同一个 chunk，在"一个论证跨越三页的技术白皮书"上把关键结论切成三段、每段都不足以回答；
  • 有人意识到 512 不对，于是改成"越小越好"（因为"精度高"），结果生成器拿到的上下文全是碎片，答案被切断。

这一节要把"粒度"变成一个可分析的设计变量。核心结论是：

存在一个最优粒度。它不是经验值，而是两条相反曲线的交点： 片段越长，"自成一体、足以支撑回答"的概率越高（语义完整性上升）； 片段越长，它承载的独立信息越超出定长表示（向量或词袋）的容量，表示越"糊"，检索精度下降。

两条曲线一条上升、一条下降，所以乘积有内点最大值。这一节要：

  1. 把两条曲线写成可算的形式（不追求精确，追求能看出参数如何移动最优点）；
  2. 推出最优粒度的标度律，说明为什么它"主要不是被信息密度决定的，而是被文档的答案结构决定的"；
  3. 说明为什么定长切分在真实文档上必然次优（因为文档的内部结构是异质的），以及"语义边界切分"的判据是什么；
  4. 指出切分与检索参数的耦合：改了 chunk 长度，BM25 的 b、稠密表示的训练分布、去重的阈值都要跟着变 —— 这是"改了切分没改参数"这类隐性 bug 的来源。

一、先把"粒度"定义清楚：三个不同的量#

讨论切分最容易犯的错是把三个量混为一谈：

量 定义 谁决定
物理粒度（L） 一个 chunk 的 token / 字符数 切分算法与参数
语义粒度 一个 chunk 里"主题"的个数 文档结构与切分是否对齐
检索单元 索引里一条记录对应什么（chunk / 段落 / 整篇 + 摘要） 索引设计（可以与物理粒度不同）

关键点：物理粒度是手段，不是目标。 真正影响系统能力的是"语义粒度"——也就是"一个 chunk 在跨度的主题空间里覆盖了几个点"。两个物理长度完全相同的 chunk，一个覆盖单一主题，另一个横跨三个主题，它们的检索表现完全不同。

这解释了为什么"512 token"这种物理常数无法迁移：同样的 512 token 在不同文档里对应的语义粒度差异极大（API 文档的 512 token 可能是三条完整的方法说明；小说的 512 token 可能只是半个场景）。

所以本节的模型要把"物理长度"与"语义粒度"分开：物理长度只通过"信息量"和"覆盖度"两个通道起作用。

二、曲线一：语义完整性 —— 一个 chunk 何时能独立支撑回答#

2.1 定义#

设某查询 q 的正确答案所需信息在原文中占据一段跨度 Sq​（以 token 计）。一个长度为 L 的 chunk 能独立支撑回答 q，当且仅当它完整覆盖了 Sq​。定义：

Completeness(L)=P(一个随机位置的 L-chunk 完整包含 Sq​)

在"切分点均匀随机"的最坏假设下，这个概率有一个简单的上界（与第 4 章的"计划有效半衰期"同构）：

Completeness(L)≤LL−E[Sq​]​(L>Sq​),= 0(L≤Sq​)

读这个式子：

  • L≤E[Sq​] 时概率为 0 —— 不是"小"，是零：chunk 装不下答案，无论检索多准、生成多强，都不可能答对；
  • L 从 E[Sq​] 开始上升，且上升最快的一段就在附近；
  • L→∞ 时趋近 1，但上升越来越慢（1−E[Sq​]/L）。

这就是"语义完整性"的核心形状：在门槛处从 0 跳到快速增长，然后饱和。为了后面能求导，用一个光滑的替代形式（保留同样的"门槛 + 饱和"性质）：

Completeness(L)≈(1+z−c)−1,z=Lc​L​,c>0

其中 Lc​ 是"典型答案跨度"（chunk 长度达到它时完整性约 50%），c 控制门槛的陡峭度。

2.2 c 是什么：文档的"答案结构"#

c 不是拟合出来的抽象参数，它有明确的语义："答案是否集中在一个紧凑单元里"。

文档类型 典型答案跨度 Sq​ c 的定性 原因
FAQ / 问答对 一个问答块（几十~百余 token） 大 答案天然被封装成一节，超过这节再无增益
API 文档 一个方法的说明段 大 参数、返回值、示例集中在一处
法律条文 一条（"第 X 条"） 大 条文是自足的语义单元
教科书章节 一个概念的解释（几段） 中 需要定义 + 例子 + 讨论
论文 一个论点的完整论证 中偏小 论证跨段落，缺一环就不完整
小说 / 叙事 一个事件（可能跨多页） 小 完整性依赖长程上下文
会议记录 / 聊天 一段议题讨论 小 答案散落在多轮发言里

这张表给出本节第一个可操作的结论：

最优粒度首先由 c 决定，而 c 由文档的答案结构决定 —— 不是由"信息密度"或"模型能力"决定。

所以"把 YouTube 字幕和产品手册用同一套切分参数"是必然次优的：两者的 c 相差很大。

三、曲线二：检索精度 —— 表示容量如何被超出#

3.1 从"表示容量"出发#

第 1 章讲过双塔的信息瓶颈：d 维、每维 b bit 精度的向量，其可用的判别信息容量约为

Imax​≈d⋅bbit(上界；实际可用量远低于此)

一个长度为 L 的 chunk 携带的独立信息量近似随长度线性增长（自然语言的熵率大致恒定）：

Ichunk​≈ρLbit,ρ=每 token 的信息率（bit/token）

当 Ichunk​≫Imax​ 时，定长表示装不下 chunk 的内容，必然发生两类损失：

  1. 主题平均化：向量变成"多个主题的加权平均"，与任何单个主题的查询相似度都下降；
  2. 区分度丧失：不同 chunk 被映射到相近的向量（第 1 章 2.5 节的"塌缩"在单文档内部的版本）。

把这两点合起来，得到一条指数衰减形式的精度曲线：

Precision(L)≈exp(−Imax​Ichunk​​)=exp(−dbρL​)=e−az,a=dbρLc​​

a 的语义："在典型答案跨度处，chunk 的信息量相对表示容量超载了多少倍"。a 小 → 表示装得下，长度几乎不损害精度；a 大 → 表示早就饱和了，加长只会越来越糊。

这里有一个非常重要的工程含义：a 可以被设计降低：

提高 d（更大的 embedding 维度）        → a 变小
提高 b（更高精度 / 不量化）            → a 变小
降低 ρ（更"冗余"的文本：代码注释、表格）→ a 变小

所以"换一个维度更大的 embedding 模型"确实能允许更长的 chunk —— 这不是玄学，它降低的正是 a。这也说明切分粒度与 embedding 维度不是独立的设计决策：换模型要重定切分参数。

3.2 稀疏检索的精度曲线不是指数：它是另一种形状#

上面的推导针对定长稠密表示。稀疏（BM25）的"容量"不同：它的表示是词袋，容量随文档长度增长（长文档能容纳更多不同的词项，词表维度不受限）。但 BM25 有自己的长度问题：

在第 1 章 3.5 节，长度归一化因子是 K=k1​((1−b)+bavgdl∣d∣​)。考虑一个"多主题长 chunk"：它的 avgdl 被大量长 chunk 抬高，而单个查询词在其中的 tf 并不会随长度同比增长（因为篇幅被其他主题占用了）。设主题份额为 ϕ=L目标主题 token 数​，则查询词的期望词频 tf≈ϕ⋅L⋅(主题内词频率)。

代入饱和项：

sat(L)=tf+k1​((1−b)+bL/avgdl)tf(k1​+1)​

当 L→∞ 且 ϕ 固定时，分子 ∝L、分母 ∝L，饱和项趋于常数 —— 但那个常数与 ϕ、b、L/avgdl 的关系决定了它比单一主题的短 chunk 低多少。取 ϕ=1（单一主题）与 ϕ=1/3（三主题）对比：后者在同样的绝对词频下，归一化分母相同，分子只有 1/3 → 分数显著更低。

结论：稀疏检索同样惩罚"多主题 chunk"，但机制不同 ——

稠密（双塔） 稀疏（BM25）
惩罚机制 表示容量超载 → 主题平均化 长度归一化 + 主题稀释 → 饱和项下降
可缓解方式 提高 d / 精度 调 b（部分有效）、减小 k1​
可否彻底修好 不能（信息论限） 不能（同前）
失效形状 平滑（指数衰减） 较陡（在 L 超过 avgdl 后加速）

两者都指向同一个设计原则：chunk 应当尽量"单主题"。 而"单主题"正是"语义粒度小"的定义 —— 于是问题回到：怎么在不牺牲语义完整性的前提下让语义粒度小？

答案就是下一节的"语义边界切分"，以及第 2 节的"重叠"，以及一种更彻底的方案：父子结构（用小的检索单元匹配，用大的上下文单元生成）。

四、把两条曲线相乘：最优粒度的存在性与标度律#

4.1 目标函数#

以"一个 chunk 既能被检索到、又足以支撑回答"的联合概率作为目标（两者近似独立时相乘）：

U(z)≈完整性(1+z−c)−1​​⋅精度e−az​​,z=Lc​L​

对 logU 求导：

dzd​[→ 完整性项−log(1+z−c)​​−az]=−1+z−ccz−c−1​−a=−z(zc+1)c​−a

令其为零：

z(zc+1)c​=a⟹ zc(zc+1)=ac​ ​

当 zc≫1 时（也就是最优粒度明显大于 50% 门槛 Lc​ 时），近似为：

z∗≈(ac​)1/c

这就是本节的核心结果。 把它读透：

参数变化 对 z∗ 的影响 工程含义
c 变大（答案更集中） z∗ 变小 FAQ / API 文档 → 切碎一点更好
c 变小（答案跨度大） z∗ 变大 论文 / 叙事 → 需要更长的 chunk
a 变大（表示超载） z∗ 变小 维度小 / 被量化 / 信息密度高 → 切碎一点
Lc​ 变大（典型答案跨度大） z∗ 变大（因为 L∗=z∗Lc​） 答案本来就长 → chunk 必须跟着长

注意 1/c 次幂带来的一个反直觉性质：z∗ 对 a 是弱依赖 —— c=0.8 时 z∗∝a−1.25，看起来强；但 c 本身变化会让 z∗ 变化得更剧烈（因为 c 同时出现在底数与指数上）。这印证了第 2.2 节的结论：粒度首先由文档的答案结构（c）决定，其次才是表示能力（a）。

4.2 标定一组具体数字#

要让模型有用，必须把参数标到可比较的量级。取：

  • d=768、b=16 → Imax​≈1.2×104 bit（上界；实际可用量按经验只占一小部分，这里保留 Imax​ 作为"容量"的定义，误差被 ρ 吸收）；
  • ρ≈2 bit/token（自然语言熵率的粗略量级；代码与表格更低，口语更高）；
  • 先取 Lc​=400 token（"一个概念解释"量级），则 a=ρLc​/Imax​=2×400/12000≈0.067。
c a z∗(近似) L∗=z∗Lc​（token） 对应文档类型
1.4 0.067 11.8 ≈ 4700 极端集中（问答对）
1.0 0.067 14.9 ≈ 5900 条文/API
0.8 0.067 18.4 ≈ 7400 教科书小节
0.5 0.067 46.8 ≈ 18700 论文论证
0.3 0.067 233 ≈ 93000 叙事

这组数字明显过大 —— 而"过大"本身就是结论。 它说明这个模型里缺了一个约束：U(z) 只惩罚"精度"，没有惩罚"chunk 太大导致候选池里可容纳的 chunk 数变少"。而生成器的上下文预算 B（能放多少个 chunk）是真实的硬约束。

4.3 补上上下文预算：这才是决定量级的那一项#

设生成器的上下文预算为 B token，检索 k 个 chunk。则 k≤B/L。定义"答案至少出现在一个被检索到的 chunk 里"的概率（这是端到端答对的前提）：

P_{\text{cover}}(L) \approx 1 - \big(1 - p_{\text{hit}}(L)\big)^{k}, \qquad p_{\text{hit}}(L) = \text{单 chunk 同时被召回且完整（}= U(L)\text{ 乘以召回率）

取 k=⌊B/L⌋，B=4000 token，并把 U(z) 作为 phit​ 的代理（同乘一个常数召回率 r0​，不改变最优点）：

Pcover​(L)≈1−(1−r0​U(L))⌊B/L⌋

这一项对 L 是强惩罚：L 翻倍，可取回的 chunk 数减半；r0​U 很小时，1−(1−p)k≈kp，于是 Pcover​≈LB​r0​U(L) —— 多了一个 1/L 因子。重做优化：

logPcover​≈logB+logr0​−logL−log(1+z−c)−az

dzd​[−logz−log(1+z−c)−az]=−z1​−z(zc+1)c​−a=0⟹z1+zc+1c​​=−a

左边恒为正（z>0，c>0，a>0）—— 无解。这说明在"预算固定"的模型下，Pcover​ 对 L 单调递减：越小越好。

但这显然是错的（否则就该切成单句）。错在哪？错在生成器需要完整的上下文：即使答案所在的 chunk 被召回了，如果它不完整，生成器仍然答不对。所以端到端正确率不是 Pcover​，而是

Pcorrect​≈Pcover​(L)×Completeness(L)

（"召回并包含答案" 与 "chunk 自足" 两者都要满足。）代入：

logPcorrect​≈const−logL−az−2log(1+z−c)

dzd​[−logz−az−2log(1+z−c)]=−z1​−a−z(zc+1)2c​=0

左边仍恒为负 —— 还是单调递减。问题出在 k=B/L 这个假设上：它假定"chunk 越多越好，永远填满预算"。但工程上 k 有上界（排序质量、去重、延迟），而且召回率本身随 k 递减（排在后面的 chunk 相关性更低）。把 k 设为固定值（例如 k=8，这是实际系统的常见选择），1/L 因子就消失了：

Pcorrect​(L)≈1−(1−r0​U(L))kfixed​,kfixed​=8

这时最优粒度回到 U(L) 的最优点 z∗≈(c/a)1/c —— 但量级仍偏大。

所以模型给出的最重要的一条结论不是某个数字，而是这个结构性事实：

最优粒度的量级由"上下文预算 / 截断数 k"这个约束决定，而不是由信息论本身决定。

  • 如果系统"能把所有相关 chunk 都放进上下文"（预算充裕、k 大）→ 倾向于切细（覆盖更多、靠 k 兜住完整性）；
  • 如果系统"上下文预算紧张、只能放 3~5 个 chunk"（长文档问答的常见情形）→ 倾向于切粗（保证每个 chunk 自足，代价是精度）；
  • 而且两端都有硬地板：L<E[Sq​] 时完整性为 0；L≫ 表示容量时精度趋 0。

这就是为什么"512 token"在实践中有一定生命力：它落在一个不大不小的中间地带，避开了两端的地板。但它不是最优 —— 它的真实含义是"在什么都调的默认设置下不会立刻崩"。

4.4 一个可复核的判据（替代经验值）#

把上面的分析变成一个可执行的实验，而不是一个公式：

对候选粒度集合 L ∈ {128, 256, 512, 768, 1024, 1536, 2048}：
  ① 固定 k（例如 8）与 embedding 模型
  ② 用带标注的 (query, gold_span) 集合测：
       Completeness(L) = gold_span 被某个"已被召回"的 chunk 完整覆盖的比例
       Precision(L)    = 被召回 chunk 中相关的比例（或 MRR / nDCG@k）
       P_correct(L)    = 端到端答对率（若有可判定的答案）
  ③ 画 Completeness 与 Precision 随 L 的曲线，找 P_correct 的峰值
  ④ 检查峰值是否由一个"门槛效应"主导：
       若 P_correct 在 L 小时为 0，说明被 E[S_q] 卡住 → 只能增大 L 或改用父子结构
       若 P_correct 在 L 大时下降明显，说明表示超载（a 大）→ 考虑降 d 的损失、或换更大维度模型

这套流程的价值在于它把"调参"变成了"测量"，而且测量出的曲线形状会直接指出该往哪个方向移动（而不是盲搜）。

五、定长切分为什么必然次优：文档结构的异质性#

5.1 一个论证#

定长切分假设了"文档的语义密度与语义边界在全文是均匀的"。真实文档违反这条假设的结构性原因有三：

  1. 结构标记不均匀：标题、列表、表格、代码块、脚注的分布极不均匀。一个 512 token 的窗口可能恰好覆盖"一个完整小节"，也可能横跨"一个表格的后半 + 一个新章节的标题 + 两段引言"。
  2. 信息密度不均匀：定义句、结论句、参数表的信息密度高（ρ 大）；过渡段、举例、客套话的密度低。定长切分会让高密度区域被切断、低密度区域被合并。
  3. 引用依赖不均匀："如上所述"、"见 3.2 节"、"该参数"这类回指在文档里散落分布。定长切分把回指与指代对象切开的概率，正比于回指的密度。

定长切分唯一的优势是简单、可复现、易于增量更新（你确切知道每个 chunk 的边界，改一个段落不会牵动很远的 chunk）。这个优势在工程上不小 —— 所以合理的做法不是彻底抛弃它，而是用结构信息去约束它：

优先级从高到低的边界信号：
  ① 显式结构边界（标题、章节、列表项、表格、代码块边界）      —— 最强
  ② 段落边界（空行）                                        —— 强
  ③ 句子边界                                                —— 中
  ④ 语义相似度骤降点（相邻句的表示相似度局部最小）            —— 弱（下文详述）
  ⑤ 定长截断（兜底，防止单段过长）                          —— 最弱，仅当上述都没有时

5.2 语义边界切分的判据与它的陷阱#

"语义切分"最常见的实现是：计算相邻句子的 embedding 相似度，在相似度局部最小处切分。这个思路对不对？

它捕捉的东西是对的，但判据不完整。 相邻句相似度低只说明"这两个句子不像"，有两个截然不同的原因：

  • 话题切换（该切）：第 i 句在讲参数配置，第 i+1 句开始讲错误处理；
  • 正常的信息推进（不该切）：第 i 句给出定义，第 i+1 句给出这个定义的一个反例 —— 两者词汇相似度可能很低，但语义上必须在一起（拆开后反例失去指代对象）。

判据的完整形式应该是"内部一致性最大化"而不是"局部相邻相似度最小"。设把文档切成 C1​,…,Cm​，定义：

Cohesion=j∑​s,s′∈Cj​∑​sim(s,s′)(簇内相似度之和)

Separation=j=j′∑​sim(centroid(Cj​),centroid(Cj′​))(簇间相似度之和，越小越好)

目标是最大化 Cohesion−λSeparation。这与文本聚类 / 话题分割是同一个问题，标准做法是用动态规划在"每段是一个话题"的模型下求最优分段（代价函数 = 段内不一致度 + 段数惩罚）。关键区别是它允许分段点"跳过"一个看似不相似的句子，只要这样能让整段的内部一致性更高。

代价与工程现实：

方案 质量 复杂度 增量更新
定长 低 O(1) 好（局部）
结构边界 + 定长兜底 中高 O(1) 好
相邻相似度局部最小 中 O(n) 次 embedding 中（需重算邻域）
全局一致性最优分段（DP） 高 O(n2) 或带约束的 O(nk) 差（改动会牵动全局分段）

这里有一个重要的取舍必须点明：切分质量与增量更新能力是冲突的。 全局最优分段意味着"新增一个段落可能改变后面所有 chunk 的边界"，于是每次更新都要重切并重建索引的一大段。而结构边界切分是局部的：新段落只影响自己所在的 chunk。

对文档频繁变化的系统（产品文档、法律更新），这个冲突往往决定了方案选择 —— 选结构边界而不是全局最优分段，不是因为它更准，而是因为它可增量维护。第 4 节（索引更新）会把这份代价量化。

六、切分与检索参数的耦合：改了切分必须重标定的三件事#

这是实战中最容易出隐性 bug 的地方。切分粒度改变会同时改变多个下游统计量：

下游量 如何被 chunk 长度影响 不重标定的后果
BM25 的 avgdl chunk 长度直接就是文档长度，改 L 就改了 avgdl 原来的 b、以及任何硬编码的分数阈值全部失效（第 1 章 5.3）
BM25 的 dft​ chunk 变短 → 每个词出现在更少的 chunk 里 → df 下降 → IDF 整体上升 稀有词与常见词的相对权重改变；停用词剪枝阈值 θ 需要重算
稠密表示的"训练分布" 预训练双塔见过的"文档"平均长度与你的 chunk 长度不同 长度失配 → a 的实际值比估计的大（表示更容易超载）
去重阈值 短 chunk 之间更容易"近似重复"（共享模板、页眉） 去重阈值不调 → 误删（把不同事实的短 chunk 当重复）
检索结果的主题分布 短 chunk → Top-k 很容易被同一篇文档的连续 chunk 占满 上下文里全是同一段内容，信息覆盖面坍缩

最后一条值得展开，因为它是"切太小"最典型的实际症状：

若 L 很小、重叠较大 → 一份 20 页的文档产出 200 个 chunk
若该文档与查询高度相关 → 它的 20 个连续 chunk 都排进 Top-8
→ 上下文里 8 个 chunk = 同一段内容的不同切片
→ 生成器看到的"证据"其实只有一个点，其余主题完全没覆盖

对策：在检索结果上做文档级去重/配额（同一文档最多贡献 m 个 chunk，其余名额给其他文档）。这个策略的正当性来自本节的分析：检索的目的是覆盖"可能相关的语义单元"，而不是最大化相似度之和。 一个把 Top-8 全给同一文档的排序，在"覆盖"这个目标上等价于 Top-1。

这条策略的完整形态（多样性、MMR、按文档配额、按 chunk 位置去冗余）会在第 3 章"上下文拼装"里展开。这里先给出它与切分的耦合关系：切得越细，越需要多样性控制。

代码：把切分做成可测量的实验#

下面的代码做三件事：(1) 实现四种切分器（定长 / 结构边界 / 相邻相似度 / 带兜底的结构优先）；(2) 实现一个不依赖外部模型的"伪 embedding"（用词频哈希），使切分与检索的整条链路能在无 GPU 环境复现；(3) 计算"完整性 / 精度 / 端到端覆盖"三条曲线，并演示 z∗ 随 c 与 a 的移动。

"""
切分粒度的定量实验：完整性 × 精度 × 预算 三条曲线。

设计决策：
  1. 用"词频哈希伪 embedding"而不是真实模型。理由：本节要观察的是
     "粒度如何影响表示的可分性"，这个性质与嵌入器是否神经无关；
     用哈希向量能让整条链路（切分→索引→检索→评测）在无 GPU 环境可跑。
     若换成真模型，曲线形状不变但绝对值不同 —— 这正是 a 参数的语义。
  2. 显式构造"答案跨度 gold_span"，因为完整性（Completeness）的定义
     就是"chunk 是否完整覆盖答案跨度"。没有 gold span 就无法测切分质量，
     这是很多团队漏掉的第一步（他们只测最终答对率，无法归因）。
  3. 每个切分器都是独立函数，返回 chunk 列表 + 边界位置。
     边界位置是增量更新能力的关键（第 4 节）：改动一处会影响多少 chunk，
     取决于边界是否局部确定。
"""
import math
import re
from collections import Counter, defaultdict

# ------------------------------------------------------------------ 文档模型
def make_doc(n_sections=8, vocab=400, seed=0, filler_per_sent=8):
    """
    合成一份"有结构但结构不均匀"的文档。这是刻意的设计决策：

      · 每个 section 有自己的主题词分布（模拟真实文档的话题结构）；
      · **section 长度不等**（2~10 句）—— 这一条是让对比有意义的关键。
        若所有 section 都恰好在 6 句，那么"定长 6 句"就恰好等于结构切分，
        实验会得到"定长和结构一样好"的假结论；
      · gold span 的长度与位置都不规则，且**允许跨 section 边界**
        （模拟"答案跨节"的真实情形，切分不可能靠对齐结构免费拿到）；
      · filler_per_sent 控制"每句的无信息填充词数" —— 它决定同一主题的
        不同句子在哈希表示里有多容易混淆，也就是课程模型里的参数 a。

    返回 (sentences, section_of_sentence, gold_spans)。
    """
    import random
    rng = random.Random(seed)
    sents, sec_of, span_of = [], [], []
    for s in range(n_sections):
        n_sent = rng.choice([2, 3, 4, 5, 6, 8, 10])
        theme = [f"t{s}_{i}" for i in range(5)]        # 该 section 的主题词
        # 标题行（模拟解析器输出的结构标记）：真实文档里结构切分依赖它，
        # 而不是依赖"主题词变化"这种只有上帝视角才知道的信息
        sents.append(f"HEAD section_{s} " + " ".join(theme))
        sec_of.append(s)
        for _ in range(n_sent):
            toks = theme * 2 + [f"c{rng.randrange(vocab)}"
                                for _ in range(filler_per_sent)]
            rng.shuffle(toks)
            sents.append(" ".join(toks))
            sec_of.append(s)
    gold = []
    for s in range(n_sections):
        idx = [i for i in range(len(sents)) if sec_of[i] == s]
        if len(idx) < 2:
            continue
        start = rng.choice(idx)
        length = rng.choice([2, 3, 4])
        gold.append([start, min(start + length - 1, idx[-1] + 1)])  # 允许越界到下一节
    return sents, sec_of, gold


TOKEN_RE = re.compile(r"[a-z0-9_]+")


def tokenize(text):
    """与第 1 章一致的最小分词器：这里 token 即"词"，长度以 token 计。"""
    return TOKEN_RE.findall(text.lower())


# ------------------------------------------------------- 伪 embedding（词频哈希）
class HashingEmbedder:
    """
    词频哈希向量 + L2 归一化。

    设计决策：维度 dim 就是课程模型里的 d（可用容量）。把 dim 调小，
    相当于降低表示容量 → a 变大 → 最优粒度应当变小。
    这样"表示容量 vs 粒度"的耦合就能在实验里被直接观察到。
    """
    def __init__(self, dim=256):
        self.dim = dim

    def encode(self, text):
        v = [0.0] * self.dim
        for t in tokenize(text):
            v[hash(t) % self.dim] += 1.0
        n = math.sqrt(sum(x * x for x in v)) or 1.0
        return [x / n for x in v]


def cos(a, b):
    return sum(x * y for x, y in zip(a, b))


# ------------------------------------------------------------------ 切分器
def split_fixed(sents, size, stride=None):
    """
    定长：按句子数打包（近似 token 定长）。边界完全由 size 与起点决定。

    stride 的语义：滑动窗口的步长。stride=size 是真实系统里的"不重叠打包"；
    stride=1 是"每个位置都开一个窗口"，用于**隔离观察粒度本身的影响**
    （去掉"边界恰好落在哪里"这个随机因素）。
    正文的 Completeness(L) 定义就是 stride=1 的版本 —— 因为"随机位置的
    L-window 能否覆盖答案"正是那个定义。混淆这两种 stride 会得到
    非单调的完整性曲线（真实系统的噪声），不利于看清粒度效应。
    """
    step = stride or size
    chunks = []
    for i in range(0, len(sents), step):
        c = list(range(i, min(i + size, len(sents))))
        if c:
            chunks.append(c)
    return chunks


def split_structural(sents, max_sents=6):
    """
    结构优先 + 定长兜底：先按"结构标记"切（这里用段首的标记符模拟标题），
    段内再用 max_sents 兜底拆。

    设计决策：模拟真实文档的解析结果是"标题行 → 正文若干句"，
    而不是自造一个"主题词变化即边界"的理想检测器 —— 后者会把
    "同一 section 内的主题词差异"误当成结构边界，从而**低估**结构切分的质量。
    （这一点本身就是可迁移的教训：结构切分的下限取决于解析器，
      而不是取决于切分算法。）
    """
    chunks, cur = [], []
    for i, s in enumerate(sents):
        is_heading = s.startswith("HEAD ")
        if is_heading and cur:
            chunks.append(cur); cur = []
        cur.append(i)
        if len(cur) >= max_sents:
            chunks.append(cur); cur = []
    if cur:
        chunks.append(cur)
    return chunks


def split_by_similarity(sents, embedder, quantile=0.25, min_sents=2, max_sents=10):
    """
    相邻相似度局部最小：在相邻句相似度最低的 quantile 处断开。
    陷阱演示：它会把"定义 + 反例"这种低词面相似但语义必须相邻的对切开。
    """
    if len(sents) < 2:
        return [list(range(len(sents)))]
    sims = [cos(embedder.encode(sents[i]), embedder.encode(sents[i + 1]))
            for i in range(len(sents) - 1)]
    thr = sorted(sims)[max(0, int(len(sims) * quantile) - 1)]
    chunks, cur = [], [0]
    for i, s in enumerate(sims):
        if (s <= thr and len(cur) >= min_sents) or len(cur) >= max_sents:
            chunks.append(cur); cur = []
        cur.append(i + 1)
    if cur:
        chunks.append(cur)
    return chunks


# ------------------------------------------------------------------ 评测
def covers(chunk, span):
    """chunk 是否完整覆盖 gold span [a,b]。"""
    a, b = span
    return (not chunk) or (chunk[0] <= a and chunk[-1] >= b)


def completeness(chunks, gold):
    """
    Completeness(L)：有多少 gold span 被"至少一个 chunk"完整覆盖。
    这正是正文第二节定义的量 —— 注意它只需要切分结果，不需要检索。
    """
    hit = sum(1 for span in gold if any(covers(c, span) for c in chunks))
    return hit / len(gold) if gold else 0.0


def precision_at_k(chunks, sents, embedder, gold, k=8):
    """
    Precision@k：以"某个 gold span 的第一句"为查询，看 Top-k chunk 里
    有多少个**完整覆盖**该 span。它衡量端到端检索成功，
    但在**主题完全分离**的语料上会退化成"完整性"的复制 ——
    要么存在正确的 chunk（并被召回），要么根本不存在。
    因此本文件另外提供 precision_of_representation()，
    直接度量"chunk 的表示还能否代表它自己的内容"。
    """
    C = [embedder.encode(" ".join(sents[i] for i in c)) for c in chunks]
    hits = 0
    for span in gold:
        q = embedder.encode(sents[span[0]])
        order = sorted(range(len(C)), key=lambda j: -cos(q, C[j]))[:k]
        if any(covers(chunks[j], span) for j in order):
            hits += 1
    return hits / len(gold) if gold else 0.0


def precision_of_representation(chunks, sents, embedder, gold, k=8):
    """
    表示精度：被召回的 chunk 向量与"查询句"的平均相似度。

    这是正文第三节那条精度曲线 Precision(L) ≈ exp(−ρL/(d·b)) 的操作化：
    chunk 变长 → 定长向量要覆盖的内容变多 → 它与任何单个句子的相似度下降
    （正文说的"主题平均化"）。这个量**与检索是否成功无关**，
    因此在主题分离的合成语料上也能观察到随 L 的单调下降。

    设计决策：用 gold span 首句作查询（模拟真实查询的语义位置），
    而不是随机句 —— 避免引入与任务无关的噪声。
    """
    C = [embedder.encode(" ".join(sents[i] for i in c)) for c in chunks]
    vals = []
    for span in gold:
        q = embedder.encode(sents[span[0]])
        order = sorted(range(len(C)), key=lambda j: -cos(q, C[j]))[:k]
        vals.extend(cos(q, C[j]) for j in order)
    return sum(vals) / len(vals) if vals else 0.0


def model_curves(L_c=6.0, a=0.067):
    """
    课程模型 U(z) = (1+z^{-c})^{-1} · e^{−a z} 的最优 z。

    设计决策：用数值扫描而不是解析式 z*≈(c/a)^{1/c} —— 因为解析式在
    c/a 不大时（此时 z^c 不 ≫ 1）误差明显，而工程上恰恰关心这个区间。
    """
    rows = []
    for c in (0.3, 0.5, 0.8, 1.0, 1.4):
        zs = [0.05 * i for i in range(1, 4000)]
        best = max(zs, key=lambda z: (1 + z ** (-c)) ** -1 * math.exp(-a * z))
        rows.append({"c": c, "z*": round(best, 2), "L*=z*·L_c":
                     round(best * L_c, 1),
                     "完整性@z*": round((1 + best ** (-c)) ** -1, 3),
                     "精度@z*": round(math.exp(-a * best), 3)})
    return rows


def a_sensitivity(c=0.8, L_c=6.0):
    """a 变大（表示容量变小 / 信息密度变高）时，最优粒度怎么移动。"""
    out = []
    for a in (0.01, 0.03, 0.067, 0.15, 0.3):
        zs = [0.05 * i for i in range(1, 4000)]
        best = max(zs, key=lambda z: (1 + z ** (-c)) ** -1 * math.exp(-a * z))
        out.append({"a": a, "z*": round(best, 2), "L*": round(best * L_c, 1)})
    return out


def end_to_end_curve(sents, gold, embedder, sizes, k=8, stride=1):
    """
    "完整性(L) × 表示精度(L)" 随粒度的变化 —— 找最优粒度的实验版本。

    stride 的两种用法对应两个不同的问题，必须分清：
      · stride=1（默认）：每个位置开一个窗口 → 完整性变成"gold span 长度
        是否 ≤ L"的阶梯函数，**单调不减**，最适合观察"粒度本身"的效应；
      · stride=size（真实系统的打包方式）：边界落点变成随机因素 →
        完整性曲线会出现非单调抖动（见 demo 第 3 节的定长两行）。
        这个抖动不是噪声，它就是"定长切分靠运气撞上答案边界"的真实体现。

    设计决策：用表示精度而不是 Precision@k 作为第二个因子 ——
    在主题完全分离的语料上 Precision@k 与 Completeness 完全同步
    （见 precision_at_k 的注释），两者相乘就没有信息量。
    """
    out = []
    for size in sizes:
        ch = split_fixed(sents, size, stride=stride)
        comp = completeness(ch, gold)
        prec = precision_of_representation(ch, sents, embedder, gold, k=k)
        out.append({"L(句)": size, "chunk 数": len(ch),
                    "完整性": round(comp, 3), "表示精度": round(prec, 3),
                    "乘积": round(comp * prec, 3)})
    return out


def incremental_update_cost(splitter_name, before, after, insert_at):
    """
    插入一句之后，有多少**原有句子**的所属 chunk 变了（= 边界移动的规模）。

    设计决策：比较"同一句内容在插入前后的 chunk 归属"，而不是比较 chunk 列表
    本身 —— 后者会被"整体右移"误判成"完全没变"。插入位置之后的句子索引
    在 after 里整体加 1，必须显式补偿，否则这个度量会给出恰好相反的结论。
    """
    def owner(chunks):
        return {i: ci for ci, c in enumerate(chunks) for i in c}
    ob, oa = owner(before), owner(after)
    n = len(ob)
    changed = 0
    for i in range(n):
        j = i if i < insert_at else i + 1      # 插入点之后的原句索引 +1
        if ob[i] != oa.get(j):
            changed += 1
    return {"切分器": splitter_name, "原句数": n,
            "所属 chunk 变化的句子比例": round(changed / n, 3) if n else None,
            "说明": "比例越高 = 增量更新要重建的范围越大"}

    for name, ch in (("定长(4 句)", split_fixed(sents, 4)),
                     ("定长(6 句)", split_fixed(sents, 6)),
                     ("结构优先(6 句兜底)", split_structural(sents, 6)),
                     ("相邻相似度", split_by_similarity(sents, emb))):
        print(f"  {name:18}: chunk 数={len(ch):<4} "
              f"完整性={completeness(ch, gold):.3f} "
              f"表示精度={precision_of_representation(ch, sents, emb, gold):.3f}")

    print("\n== 4. 端到端曲线（定长，句数为粒度）==")
    for r in end_to_end_curve(sents, gold, emb, sizes=(2, 3, 4, 5, 6, 8, 12)):
        print(f"  L={r['L(句)']:<3} chunks={r['chunk 数']:<4} "
              f"完整性={r['完整性']:.3f} 表示精度={r['表示精度']:.3f} "
              f"乘积={r['乘积']:.3f}")
    print("  读法：完整性随 L 上升（L 小于最短 gold span 时恒为 0 —— 这是硬地板）、")
    print("        精度随 L 下降 → 乘积有内点峰值；这个峰值就是该语料上")
    print("        『可测』的最优粒度，不需要任何经验常数")
    print("  注意三件事：")
    print("   ① 合成语料的 gold span 只有 2~4 句 → 完整性在 L≥4 就饱和，峰值偏小；")
    print("      真实语料把最短 gold span 换成『一个完整论证』，峰值会整体右移。")
    print("   ② 这里用 stride=1（每个位置开窗）来隔离『边界落点』的随机性；")
    print("      真实系统的 stride=size 会让完整性曲线出现非单调抖动（见第 3 节）。")
    print("   ③ 表示精度用的是词频哈希，它对长 chunk 并不敏感（碰撞过早饱和）——")
    print("      **所以这条曲线里『精度』那一侧被明显低估了**。")
    print("      这也是一条可迁移的教训：替换表示会改变最优点的位置，")
    print("      所以 L 的标定必须用你线上真正使用的那个 embedding 模型来做。")

    print("\n== 5. 表示精度（gold 首句 vs Top-k chunk 的相似度）随 dim 与 L 的变化 ==")
    dims = [4, 8, 16, 64, 512]
    print("      L(句)  " + "".join(f"dim={d:<7}" for d in dims))
    for size in (2, 3, 4, 6, 8, 12):
        ch = split_fixed(sents, size)
        row = "".join(
            f"{precision_of_representation(ch, sents, HashingEmbedder(dim=d), gold):<11.3f}"
            for d in dims)
        print(f"      {size:<7}" + row)
    print("  两处读法（都很重要）：")
    print("   ① 沿『列』看（固定 dim，L 增大）：dim 越大，精度随 L 的下降越明显。")
    print("      dim 小时曲线反而是平的 —— 因为哈希碰撞把向量挤在一起、")
    print("      相似度普遍偏高，此时这个度量已失去分辨力")
    print("      （不是『表示很好』，而是『量不出来』）")
    print("      → 教训：评估指标本身也需要足够的表示容量才有意义。")
    print("   ② 沿『行』看（固定 L，dim 变化）：L 越大，增大 dim 带来的改善越多。")
    print("      这与课程模型一致：a ∝ 1/(d·b)，粗 chunk 对表示容量更敏感。")

    print("\n== 6. 增量更新代价：插入一句后，有多少原有句的所属 chunk 变了 ==")
    inserted = "t7_0 t7_1 t7_2 t7_3 t7_4 new fact inserted here"
    pos = 7                                        # 插在文档中部
    modified = sents[:pos] + [inserted] + sents[pos:]
    for name, splitter in (("定长(6 句)", lambda ss: split_fixed(ss, 6)),
                           ("结构优先", lambda ss: split_structural(ss, 6))):
        print(" ", incremental_update_cost(name, splitter(sents),
                                            splitter(modified), pos))
    print("  说明：定长切分的边界由**全局位置**决定 → 插入点之后所有 chunk 的边界右移；")
    print("        结构切分的边界只由**邻域的主题变化**决定 → 影响范围局部化")

三处关键设计决策：

  1. 用词频哈希代替真 embedding。本节要观察的性质是"粒度 → 表示可分性"，这是信息容量层面的性质，与嵌入器是神经还是哈希无关。哈希向量的好处是：可以把 d 当旋钮拧（dim=256 → 32），从而直接观察 a 变大时最优点如何左移 —— 用真模型时这个实验要做很多次训练。
  2. 显式构造 gold span，而不是只测最终答对率。因为"完整性"的定义就是"chunk 是否覆盖答案跨度"；没有 gold span，你只能测到端到端结果，无法区分"切分切坏了"和"检索没召回"。
  3. incremental_update_cost 把"可增量维护"变成度量。这是很多人选切分方案时忽略的维度，而它在一个文档天天变的系统里往往比切分质量更重要。把它做成可打印的数字，能让这个取舍进入决策，而不是停留在直觉。

练习#

  1. 推最优粒度的标度律：从 U(z)=(1+z−c)−1e−az 出发，证明最优点满足 zc(zc+1)=c/a，并说明当 zc≫1 时 z∗≈(c/a)1/c。然后算：c=0.8、a=0.067 与 c=0.8、a=0.2 两组参数下 z∗ 的比值。这个比值说明"换一个维度更小的 embedding 模型"对切分参数有多大影响？
  2. 量 c：设计一个实验测量某语料的 c。要求写出：(a) 怎么定义"答案跨度"（提示：标注或从 QA 对反推）；(b) 怎么从数据估计 Lc​ 与 c（提示：c 可以取 ln(P/(1−P)) 对 lnz 的回归斜率）；(c) 需要多少标注样本才能让这个估计稳定（考虑二项置信区间）。
  3. 两端的硬地板：给出一份具体文档（可以是产品手册与会议记录各一份），分别估计 E[Sq​] 与表示容量对应的上界。然后说明：这两端的地板在你的文档上分别把 L 限制在什么区间内？如果两个区间不相交（说明不存在可行的 L），你的替代方案是什么？（提示：父子结构、查询改写、或者接受某一端失败。）
  4. 验证上下文预算的作用：用 end_to_end_curve 的框架，把 k 从 8 改成 2、4、16，观察最优粒度是否移动。解释你观察到的方向，并说明它与"预算充裕时倾向切细、预算紧张时倾向切粗"这条推论是否一致。若不一致，检查你的模型哪里与推论的假设不同。
  5. 语义切分的陷阱：构造一段文本（可以是中文），其中包含"定义 + 反例"、"论点 + 论据"、"步骤 1 + 步骤 2"三类相邻关系。用相邻相似度法切分，找出它切错的位置，并说明"全局一致性最优分段"会怎么处理这些位置。然后回答：为了这个改进，你愿意付出多少增量更新代价？（用 incremental_update_cost 给出量化的答案。）
  6. 耦合实验：把 chunk 从 6 句改成 3 句，然后重算以下三个量并解释变化：(a) df 的分布（用 Counter 统计每个词出现在多少 chunk 里）；(b) avgdl；(c) 停用词剪枝阈值 θN 对应的具体词表。说明"改了切分但没改 BM25 参数"会造成什么后果（用第 1 章的公式指出具体哪一项被破坏）。
  7. 同一文档占满 Top-k 的问题：用 make_doc 生成一份文档，切成很小的 chunk（2 句），然后对一个与某个 section 相关的查询做 Top-8 检索。统计这 8 个结果来自多少个不同的 section。然后设计一个"每文档/每 section 最多 m 个"的配额策略，测量它对 Precision@k 的影响，并解释为什么它可能降低某个指标却提高端到端答对率。
  8. 设计一份切分方案（综合题）：给定三类文档（FAQ 库、产品手册、会议记录），分别给出：(a) 切分单位（结构 / 语义 / 定长）与粒度区间；(b) 需要的元数据字段（用于过滤与去重）；(c) 增量更新策略；(d) 你会用什么实验来验证这个方案。要求每一处选择都写出依据的是本节哪个量（c / a / E[Sq​] / 预算 / 增量代价）。

小结#

  • 粒度必须分成三个量看：物理粒度（token 数）、语义粒度（覆盖几个主题）、检索单元（索引记录对应什么）。物理粒度是手段，语义粒度才是影响能力的东西 —— 这就是"512 常数"无法迁移的根本原因。
  • 两条相反的曲线：
    • 语义完整性：L≤E[Sq​] 时为 0（硬地板，装不下答案就是不可能答对），之后上升并饱和。参数 c 表示"答案是否集中在一个紧凑单元里"（FAQ/API c 大，论文/叙事 c 小）；
    • 检索精度：表示容量 Imax​≈db 被 chunk 信息量 ρL 超越后指数衰减（稠密），或经长度归一化+主题稀释而下降（稀疏）。参数 a=ρLc​/Imax​ 表示"表示超载的倍率"。
  • 最优粒度存在且有标度律：zc(zc+1)=c/a，在大 z 近似下 z∗≈(c/a)1/c。z∗ 主要由 c（文档答案结构）决定，其次才是 a（表示容量）。
  • 真正的量级约束来自"上下文预算 / 截断数 k"：预算充裕、k 大 → 倾向切细（靠 k 兜住完整性）；预算紧张、只能放很少 chunk → 倾向切粗（保证每个 chunk 自足）。两端都有硬地板，所以"512"落在"不会立刻崩"的中间地带，而不是最优点。
  • 可复核的判据是实验而非公式：固定 k 与 embedding，扫描 L，画 Completeness / Precision / 端到端曲线，找峰值，并检查峰值是被门槛（E[Sq​]）还是被容量（a）主导 —— 这决定了往哪个方向移动。
  • 定长切分必然次优，因为文档的结构密度、信息密度、回指密度都不均匀。定长的唯一优势是边界局部确定、便于增量更新。合理做法是"结构边界优先 + 定长兜底"。
  • 语义切分的判据不是"相邻相似度最小"，而是"内部一致性最大"。相邻相似度低可能是话题切换（该切），也可能是"定义 + 反例"这种必须相邻的结构（不该切）。
  • 切分质量与增量更新能力冲突：全局最优分段（DP）质量高但改动牵动全局；结构边界局部确定但质量略逊。对文档频繁变化的系统，这个冲突常常是决定性因素。
  • 切分与检索参数强耦合：改 L 会同时改变 avgdl、df（进而改变 IDF 与剪枝阈值）、去重阈值、以及"同一文档占满 Top-k"的程度。改切分必须重标定这些量，否则会留下隐性 bug。
  • 切得越细，越需要多样性控制：Top-k 被同一文档的连续 chunk 占满时，在"覆盖潜在相关语义单元"这个目标上，Top-8 等价于 Top-1。

下一节：既然切分会把答案切断，最直接的补救是重叠。但重叠不是免费的，而且它的收益曲线有一个明确的形状。我们要推导：重叠比例覆盖了多少"边界损失"、为什么 20% 之后迅速饱和、以及重叠的真实成本（体积、重复召回、上下文浪费）为什么常常超过它带来的收益。
