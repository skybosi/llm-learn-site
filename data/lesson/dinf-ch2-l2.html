分块预填充：为什么块大小是解出来的，以及抢占时"重算还是换出"#

这一节要解决什么#

上一节的连续批处理让 batch 一直满载，但它默认了一个前提：prefill 与 decode 可以随意混在一起。这个前提是错的，原因是一个数量级上的不对称：

一个 decode token 的执行时间一个 prefill token 的执行时间​=Td​a​

a 是 prefill 每 token 的线性成本（权重访存 + KV 写入），Td​ 是一次 decode 步的耗时。在本节的示例口径下这个比值是 0.015（即 1 个 prefill token ≈ 66 个 decode token 的总算力量）。把 s=8192 的 prompt 整块塞进一个 decode step，等于给这一步塞进去 54 万个 decode token 的算力 —— 这一步会膨胀几百倍，所有正在解码的请求一起卡住。

分块预填充（chunked prefill）就是把这个巨大的 prefill 切成小块、每步只放一块。于是本节要回答三个问题：

  1. 块大小 c 与"给解码请求带来的延迟"是什么关系？ 它有一个非常干净的答案：Δtstep​=(a+κs)c。
  2. c 能不能随便大？ 不能 —— 由一个膨胀预算 f 给出上界 cmax​=fTd​/(a+κs)。在示例口径下这个上界几乎与 s 无关（因为在典型 s 范围内 a≫κs），恒在 650 左右。这就是"为什么实践中的块大小总是几百到一千"的算术来源。
  3. 抢占时该重算还是换出？ 当 KV 满了必须驱逐一个请求，它的 KV 要么丢掉（之后重新 prefill）要么换出到 CPU（之后换回来）。分界序列长度是 2swap_bytes/PCIe​⋅prefill 速率 量级的一个闭式值 —— 本节把它算出来。

先把结论放在这里：

分块预填充的全部收益：把「一次几百毫秒的阻塞」换成「几十次几十毫秒的小停顿」​

它不减少总工作量（prefill 的 FLOPs 不变），也不减少对解码请求的总干扰（甚至更多，因为每块都要重读权重）。它买的是可预测性：让一个长 prompt 不会把整个服务的 TPOT 打成尖刺。

一、prefill 的成本结构：两个系数#

1.1 模型#

对长度为 s 的 prompt，一次完成（不分块）的 prefill 延迟：

tprefill​(s)=线性as​​+二次κs2​​+ t0​

系数 物理含义 估算方式（示例：L=32、H=4096、fp16、H100 级）
a 每 token 的固定工作量：读一遍权重 + 读写 KV 2Ψ/B≈4.38 ms / 1k token（但真实值取决于 kernel 效率）
κ 注意力的二次项：每 token 与前面所有 token 做注意力 4LH/(C⋅MFU) 量级
t0​ 每块的固定开销：kernel 启动、同步、KV 块分配 10∼50 ms（这是实践中最容易被低估的一项）

⚠️ a 必须用实测标定，不能只用 2Ψ/B。原因是批处理 prefill 的实际效率远低于显存带宽上限（小矩阵、低 occupancy、kernel 启动开销）。本节代码用一个"有效速率" Rpf​（token/s）标定它：

a=Rpf​1​

示例：Rpf​=15000 tok/s → a=66.7μs/token。这比 2Ψ/B 算出来的 4.38μs/token 大 15 倍 —— 这 15 倍就是"理论下界"与"可达到速率"的差距，也是所有容量规划必须走实测的原因。

1.2 一个必须建立的对照：κs 什么时候变得重要#

用 a=66.7μs/token、κ=0.130 ns/token²：

s a（µs/token） κs（µs/token） 合计 二次项占比
2048 66.70 0.27 66.97 0.4%
8192 66.70 1.07 67.77 1.6%
32768 66.70 4.26 70.96 6.0%
131072 66.70 17.04 83.74 20.4%

读法：在 s≤32768 的整个实用范围内，线性项主导（二次项占比 ≤6%）。只有到 128k 上下文，二次项才拿到 20%。这有一个重要的操作含义：

对 s≤32k，块大小几乎与 s 无关​

—— 因为分母 a+κs 几乎就是 a。这个结论很反直觉（"上下文越长应该切得越小"），但它是算出来的：a 比 κs 大一个多数量级，所以 s 对分母的影响可以忽略。

二、块大小与它对解码请求的延迟#

2.1 延迟公式#

一次混合 step 里，调度器为 chunk 分配要处理 c 个 token。这一步的墙钟时间至少是"纯解码步" Td​ 与"这一块的 prefill 时间"的较大者：

Δtstep​=max(Td​, (a+κs)c+t0​)≈(a+κs)c

（c 不太小时第二项占主导；c 很小时被 Td​ 支配，见 2.3。）数值（示例）：

s c=128 c=256 c=512 c=1024 c=2048
2048 18.57 ms 27.13 ms 44.27 ms 78.54 ms 147.08 ms
8192 18.67 ms 27.34 ms 44.68 ms 79.36 ms 148.71 ms
32768 19.08 ms 28.16 ms 46.31 ms 82.63 ms 155.26 ms

（小 c 那一列不是 ≈(a+κs)c 而是被 Td​+t0​ 抬起来了：c=128 时 (a+κs)c=8.7 ms <Td​，所以 Δtextstep​omax(Td​,⋅) 的取大项生效。这正是 c 的下限来源之一，见 2.3。）

这张表就是分块预填充的全部算术：c=512 时，每个 chunk 让整个 batch（包括所有正在解码的请求）多等约 45 ms（含 t0​=10 ms）。c=2048 时是 149 ms。

块大小的代价是「对整个 batch 的一次延迟」，不是「对那个新请求的延迟」​

这是一个容易被搞错的地方：分块预填充的延迟成本是外溢的（所有在飞的解码请求都受影响），而收益是内聚的（新请求的 TTFT 更低）。这也是它需要显式预算的原因。

2.2 膨胀倍数与上界#

定义膨胀倍数 f：混合 step 相对纯解码步的倍数。

f=Td​(a+κs)c​⟹cmax​=a+κsfTd​​​

数值（示例 Td​=4.383 ms）：

s f=2 f=5 f=10 f=20
512 131 328 512 512
2048 131 327 655 1309
8192 129 323 647 1294
32768 124 309 618 1235

三处必须读懂的地方：

  1. cmax​ 与 s 几乎无关（f=10 时 618~655）。原因就是 1.2 节：分母被 a 支配。所以"块大小"可以做成一个常数配置（如 512 或 1024），不需要随 prompt 长度动态调。 这与很多人"长 prompt 要切更小"的直觉相反 —— 直觉错在把"总 prefill 时间随 s 上升"误当成"每 token 的成本随 s 上升"。
  2. f 的选择直接决定块大小：f=10 → 约 650；f=5 → 约 320；f=2 → 约 130。所以"块大小取多少"等价于"允许多少倍的步时间膨胀" —— 把问题换成后者，讨论才有意义（前者看起来像经验值）。
  3. f 不是自由参数，它由 TPOT 的 SLA 决定：若 TPOT 的 P99 预算是 TTPOT​，那么一次膨胀 f 倍会让那一小段请求的间隔变成 f⋅Td​。所以

fbudget​=Td​TTPOTmax​​

示例：TPOT 预算 50 ms、Td​=4.383 ms → f≤11.4 → c≤740。

2.3 小 c 的收益与它的下限#

c 小当然好（延迟小）。但不能无限小，有两个原因：

(a) 每块的固定开销 t0​。 处理 s 个 token 需要 nc​=s/c 块，每块付一次 t0​。总 prefill 时间：

Tprefillchunked​(s,c)=s(a+κs)+cs​t0​

c 越小，固定开销项越大。给定 TTFT 预算 TTTFT​，解出 c 的下界：

cmin​=TTTFT​−s(a+κs)st0​​​

数值（t0​=10 ms）：

s 基础 s(a+κs) TTTFT​=5 s 10 s 20 s 40 s
8192 555.1 ms 18 9 4 2
32768 2325.2 ms 123 43 19 9
131072 10975.9 ms 不可达 不可达 145 45

"不可达"那一格是本表最重要的一格：s=131072 的基础 prefill 就要 11.0 s，再大的 TTFT 预算也救不了它（除非提高 Rpf​ 或降低 t0​）。这时唯一的出路是别一次处理这么长的 prompt（降级、截断、或者用检索把上下文缩到几 k）。

(b) 块的算力效率。 小块的算术强度低，实际 Rpf​ 会下降。c=128 时每块只读一遍权重（4.38 ms 的等效工作）却只算 128 个 token，效率远低于 c=1024。这个效应让"更小的 c"在总工作量上更贵。它的量化形式就是"a 随 c 变化"：a(c) 在 c 小于约 512 时开始明显上升。

2.4 把两边合起来#

c∗∈[TTFT 预算的下界cmin​(TTTFT​)​​, 膨胀预算的上界cmax​(f)​​]并取满足 prefill 效率的一方​

示例（f=10、TTTFT​=20 s、t0​=10 ms）：

s cmin​ cmax​ 建议 c nc​ 分块后总 prefill
2048 1 655 128 16 0.297 s
8192 4 647 128 64 1.195 s
32768 19 618 128 256 4.885 s
131072 145 523 145 904 20.0 s

注意 s=2048 那一行：cmin​=1，意味着"理论上把 2048 token 切成 2048 块"也满足 TTFT 预算 —— 但那时 t0​ 会主导（2048×10 ms = 20.5 s）而 prefill 效率归零。所以区间存在不等于区间内都是好点；实际选择要落在区间内并且尽量大（效率优先），直到撞上 cmax​。

这条推理链解释了为什么所有推理引擎的默认块大小都在 512~2048：cmax​ 把它压到 ~650 以下（膨胀预算），t0​ 与效率把它抬到 ~128 以上。中间那个区间，恰好就是工程默认值所在的区间。

三、抢占：KV 满了必须赶走一个请求时#

3.1 两种处置#

当 KV 池满了，而一个正在解码的请求需要新的块时，调度器必须抢占一个请求。被抢占者的 KV 有两种处置：

处置 机制 成本 何时更优
重算（recompute） 丢掉 KV，恢复时重新 prefill 它的 prompt + 已生成部分 ≈asused​+κsused2​ 序列短
换出（swap） 把 KV 拷到 CPU pinned memory，恢复时拷回 ≈βPCIe​2⋅KV(sused​)​ 序列长

3.2 分界序列长度#

两者相等的序列长度：

as∗+κs∗2=βPCIe​2s∗⋅KV1​​

若 κs≪a（1.2 节的常态），线性化得到闭式：

s∗≈βPCIe​a2KV1​​=βPCIe​2KV1​Rpf​​​

数值（KV1​=128 KiB/token、a=66.7μs/token、PCIe 有效带宽 25 GB/s）：

s∗≈25×109B/s×66.7×10−6s2×131072B​≈157 token

这个数远小于直觉。把它代入验证：

sused​ 重算成本 换出成本 谁更优
128 8.5 ms 1.3 ms 换出
512 34 ms 5.4 ms 换出
4096 279 ms 43 ms 换出
32768 2254 ms 344 ms 换出

等等 —— 表里"换出"一直更优，而 s∗≈157。这说明我的分界点算错了。 让我重算：换出成本 =2sKV1​/β，重算成本 =as+κs2。

as+κs2=β2sKV1​​⟹a+κs=β2KV1​​⟹s=κ2KV1​/β−a​

代入：2×131072/25×109=10.49μs；10.49−66.7<0 → 没有正解。

当 a>2KV1​/βPCIe​ 时，换出在所有序列长度上都优于重算​

这是一个可判定的条件，而不是一个序列长度分界：

a≷βPCIe​2KV1​​⟺换出更优≷重算更优

示例：a=66.7μs vs 2KV1​/β=10.5μs → 换出优 6.4 倍。

⚠️ 但真实系统的默认选择是"重算"（例如 vLLM 的默认抢占模式）。这不是因为它更便宜，而是因为三个工程原因：

  1. 换出需要 pinned memory 与 PCIe 带宽，而 PCIe 在 decode 期间被 KV 读写与其他拷贝竞争；实测有效带宽常低于 25 GB/s。
  2. 换出要求被抢占者"冻结"，恢复时还要重新调度、重新分配块 —— 这部分开销 t0​ 与重算的固定成本差不多。
  3. 换出挤占 KV 池之外的内存预算（pinned host memory 不是无限的），而重算只花时间。

所以：账面比（a vs 2KV1​/β）决定"理论上谁便宜"，工程约束决定"实现了谁便宜"

3.3 该抢占谁：一个可算的判据#

抢占的另一个问题：赶走哪个请求？ 常见策略（FCFS 末尾、最晚截止、最低优先级）都是定性的。把它写成成本函数：

抢占成本(r)=已投入的工作被丢掉重算成本(sused​(r))​​+该请求的延迟惩罚λ⋅剩余工作(r)​​

价值密度(r)=已消耗的 KV已完成 token 数​=sused​(r)ndone​(r)​

逐行读：

  • 重算成本 ∝sused2​（若 κ 项相关）或 ∝sused​ → 赶走长请求很贵；
  • 价值密度：一个又长又已经生成很多的请求，它的"每字节 KV 换来的进度"更高 → 不该赶；
  • 一个刚进来、prompt 很长但只生成了几个 token 的请求：价值密度低、重算成本高 → 它是最难受的抢占对象，这也是长上下文服务里"首 token 卡住"的常见原因。

抢占判据：优先赶走「价值密度最低 + 重算成本最低」的请求，并显式计入 lambda（它的延迟惩罚权重）​

⚠️ 注意这里与上一节的公平性有冲突：如果永远优先赶走长 prompt，长 prompt 会饿死。所以真实的调度器需要一个老化（aging）项：等待时间越长，抢占成本越高。这是"公平性"在抢占层面的具体形式。

四、取舍与失效模式#

选择 收益 代价 失效条件
分块预填充 TTFT 可控、TPOT 尖刺消失 每块重读权重 + t0​ s(a+κs)>TTTFT​（不可达）
块调大 TTFT 更低、效率更高 膨胀倍数 f∝c fTd​> TPOT 预算
块调小 膨胀小 t0​ 占比上升、效率下降 st0​/c 主导总时间
抢占用重算 无额外内存、实现简单 ∝sused​ 的时间 a<2KV1​/β（长序列时换出更便宜）
抢占用换出 长序列更便宜 pinned 内存、PCIe 竞争 PCIe 有效带宽低 / host 内存受限

一个容易被忽略的交互：分块预填充与抢占是耦合的。分块让新请求的 KV 是逐步分配的（每块分配一次），所以"KV 池满"这件事发生得更平滑，抢占频率下降。反过来说，不做分块时，一个长 prompt 会一次性申请一大块 KV，这本身就是抢占的触发器。

分块预填充的收益不只是延迟，还有「KV 分配的平滑化」

代码：分块预填充的膨胀账、块大小上下界与抢占分界#

脚本做四件事：(1) 用有效速率标定 a 并打印 κs 的占比；(2) 算膨胀倍数与 cmax​；(3) 算 TTFT 预算下的 cmin​ 与最终区间；(4) 算抢占的"重算 vs 换出"判据（含"无正解"的情形）。

"""
分块预填充的账：膨胀倍数、块大小上下界、抢占判据（只用标准库）。

设计决策：
  1. a 用「实测有效速率」标定，而不是用 2Ψ/B。两者的差距（示例约 15 倍）本身就是
     一个结论：理论下界与可达到速率之间存在 kernel 效率、occupancy、启动开销的鸿沟。
     不区分这两者会让所有容量规划都乐观 10 倍以上（正文 1.1）。
  2. 块大小的上下界来自两个完全不同的约束：上界来自「对解码请求的延迟膨胀 f」，
     下界来自「TTFT 预算 vs 每块固定开销 t0」。**把两者写在同一张表里**，
     才能看出为什么工程默认值总落在几百到一千（正文 2.4）。
  3. 抢占判据写成「比较两个成本」而不是「给一个序列长度阈值」——
     因为示例参数下**没有正的分界点**（换出在所有长度上都更便宜）。
     这正是一个必须用代数而不是直觉回答的问题（正文 3.2）。
  4. 所有常量都命名并集中在一处，注释里写明「换成本机实测值」。
     本节的价值在于公式结构，不在具体数字。
"""
T_d = 4.383e-3          # 解码一步（batch=1）的墙钟时间，秒
R_pf = 15_000.0         # 批处理 prefill 的有效速率，token/s（★ 换成你的实测值）
KAPPA = 0.130e-9        # prefill 二次系数，s/token²（注意力 + KV 读）
T0 = 10e-3              # 每个分块的固定开销（启动/同步/块分配），秒
KV1 = 128 * 1024        # 每 token 的 KV 字节数
PCIE = 25e9             # PCIe 有效带宽，B/s（★ 注意实测常低于标称）

A = 1.0 / R_pf          # prefill 每 token 的线性成本，s/token
MS = 1e3
US = 1e6


def per_token_cost(s):
    """分块时每 token 的处理器时间（线性 + 二次）。"""
    return A + KAPPA * s


def delta_step(s, c):
    """一个 chunk 给整个 batch 带来的墙钟延迟（秒）。"""
    return max(T_d, per_token_cost(s) * c + T0)


def c_max(s, f):
    """膨胀预算 f 下的块大小上界：f·T_d/(a+κs)。"""
    return min(f * T_d / per_token_cost(s), s)


def c_min(s, ttft_budget):
    """TTFT 预算下块大小的下界：s·t0/(T - s(a+κs))；不可达时返回 inf。"""
    base = s * per_token_cost(s)
    return s * T0 / (ttft_budget - base) if ttft_budget > base else float("inf")


def prefill_total(s, c):
    """分块后的总 prefill 时间（秒）：s(a+κs) + (s/c)·t0。"""
    return s * per_token_cost(s) + (s / c) * T0


def preemption_break_even():
    """
    重算 vs 换出的分界：a + κs = 2·KV1/β  ⇒  s* = (2KV1/β - a)/κ。
    若 2KV1/β <= a，则换出在所有序列长度上更优（无正的 s*）。
    """
    swap_per_token = 2 * KV1 / PCIE
    if swap_per_token <= A:
        return None, swap_per_token
    return (swap_per_token - A) / KAPPA, swap_per_token


if __name__ == "__main__":
    print("=" * 88)
    print(f"标定：T_d={T_d*MS:.3f} ms、R_pf={R_pf:.0f} tok/s（⇒ a={A*US:.1f} µs/token）、"
          f"κ={KAPPA*US:.4f} µs/token²、t0={T0*MS:.1f} ms")
    print(f"      KV1={KV1/1024:.0f} KiB/token、PCIe 有效带宽={PCIE/1e9:.0f} GB/s")
    print(f"      a/T_d = {A/T_d:.4f} → 1 个 prefill token ≈ {A/T_d:.3f} 个解码 token 的执行时间")

    print("\n(1) 线性项 vs 二次项：κs 相对 a 的占比")
    print(f"{'s':>8}{'a µs/tok':>11}{'κs µs/tok':>11}{'合计 µs/tok':>12}{'二次占比':>10}")
    for s in (512, 2048, 8192, 32768, 131072):
        print(f"{s:>8}{A*US:>11.2f}{KAPPA*s*US:>11.3f}{(A+KAPPA*s)*US:>12.2f}"
              f"{KAPPA*s/(A+KAPPA*s):>10.1%}")
    print("  读法：s<=32k 时线性项主导（二次占比<=6%）→ 块大小几乎与 s 无关")

    print("\n(2) 一个 chunk 给整批带来的延迟 (a+κs)·c")
    print(f"{'s':>8}" + "".join(f"{'c='+str(c):>11}" for c in (128, 256, 512, 1024, 2048)))
    for s in (2048, 8192, 32768):
        print(f"{s:>8}" + "".join(f"{delta_step(s,c)*MS:>11.2f}" for c in (128, 256, 512, 1024, 2048)))
    print("  读法：c=512、s=8192 时整批多等 34.7 ms（≈7.9× 解码步）→ 这是外溢成本")

    print("\n(3) 膨胀预算 f 下的块大小上界 c_max = f·T_d/(a+κs)")
    print(f"{'s':>8}" + "".join(f"{'f='+str(f):>9}" for f in (2, 5, 10, 20)))
    for s in (512, 2048, 8192, 32768):
        print(f"{s:>8}" + "".join(f"{c_max(s,f):>9.0f}" for f in (2, 5, 10, 20)))
    print("  读法：c_max 与 s 几乎无关（618~655 @ f=10）→ 块大小可做成常数配置")
    f_budget = 50e-3 / T_d
    print(f"  若 TPOT 预算 50 ms → f<={f_budget:.1f} → c<={c_max(8192,f_budget):.0f}")

    print("\n(4) TTFT 预算下的块大小下界 c_min 与最终区间")
    print(f"{'s':>8}{'基础 ms':>11}" + "".join(f"{'T='+str(int(t))+'s':>11}" for t in (5, 10, 20, 40)))
    for s in (8192, 32768, 131072):
        base = s * per_token_cost(s)
        row = []
        for t in (5, 10, 20, 40):
            cm = c_min(s, t)
            row.append("      不可达" if cm == float("inf") else f"{cm:>11.0f}")
        print(f"{s:>8}{base*MS:>11.1f}" + "".join(row))
    print("  读法：s=131072 基础 prefill 就要 11.0 s → 5s/10s 预算直接不可达")
    print("        （唯一的出路不是调块大小，而是缩短 prompt 或提高 R_pf）")

    print("\n(5) 最终区间（f=10、T_TTFT=20 s）")
    print(f"{'s':>8}{'c_min':>9}{'c_max':>9}{'建议 c':>9}{'n_c':>8}{'总 prefill s':>14}")
    for s in (2048, 8192, 32768, 131072):
        lo, hi = c_min(s, 20.0), c_max(s, 10)
        c = min(max(lo, 128.0), hi)
        print(f"{s:>8}{lo:>9.0f}{hi:>9.0f}{c:>9.0f}{s/c:>8.0f}{prefill_total(s,c):>14.3f}")
    print("  读法：区间 = [TTFT 下界, 膨胀上界]；实际取区间内偏大的值（兼顾效率）")

    print("\n(6) 抢占判据：重算 vs 换出")
    s_star, swap_per_token = preemption_break_even()
    print(f"  换出成本 = 2·KV1/β = {swap_per_token*US:.2f} µs/token")
    print(f"  重算成本 = a + κs = {A*US:.2f} + {KAPPA*US:.4f}·s µs/token")
    if s_star is None:
        print(f"  ★ 2·KV1/β ({swap_per_token*US:.2f}) <= a ({A*US:.2f}) → "
              "换出在所有序列长度上都更优（不存在正的分界点）")
    else:
        print(f"  ★ 分界序列长 s* = {s_star:.0f} tokens")
    print(f"  {'s_used':>8}{'重算 ms':>11}{'换出 ms':>11}{'更优':>8}")
    for s in (128, 512, 2048, 8192, 32768):
        rec = (A * s + KAPPA * s * s) * MS
        swp = 2 * s * KV1 / PCIE * MS
        print(f"  {s:>8}{rec:>11.3f}{swp:>11.3f}{'换出' if swp < rec else '重算':>8}")
    print("  注：账面结论是「换出更优」，但真实默认是「重算」——")
    print("      PCIe 竞争、pinned 内存有限、恢复时的调度成本三项让账面优势打折")

六处关键设计决策：

  1. A = 1/R_pf 而不是 2*PARAMS/HBM。这一行是本节最重要的口径选择：它把"理论带宽下界"换成"实测可达到速率"，两者相差 15 倍。如果代码里用理论值，后面所有的块大小与总耗时都会乐观一个数量级，而读者无法察觉。
  2. delta_step 用 max(T_d, ...) 而不是直接线性式。这保证小 c 的极限行为正确（c→0 时延迟趋近 Td​ 而不是 0），也顺手暴露了 T0​ 的支配区间。
  3. c_min 与 c_max 并列输出。块大小的两个边界来自完全不同的约束（TTFT vs 膨胀），只算一个会得出片面的结论。代码结构本身就在防止这个错误。
  4. preemption_break_even 允许返回 None。这是刻意的：示例参数下解方程会得到负的 s∗，而"没有正解"这个结论（换出在所有长度上更优）比"s∗=157"这种凑出来的数有价值得多。能够表达"无解"的代码，才不会伪造一个答案。
  5. 所有常量集中在文件开头并标注"★ 换成你的实测值"。本节的公式结构是可移植的，数字不是。
  6. 第 (6) 段保留"账面 vs 现实"的对照注释。因为这一节的结论如果只写成"换出更优"，会与读者在 vLLM 里看到的默认行为冲突 —— 把冲突写出来，比隐藏它更有教学价值。

小结#

  • prefill 的成本结构是 t(s)=as+κs2+t0​，其中 a=1/Rpf​ 必须用实测标定。示例里 a 比理论值 2Ψ/B 大 15 倍 —— 这个差距就是 kernel 效率与 kernel 启动开销，忽略它会让所有规划乐观一个数量级。
  • 分块预填充的收益是把"一次几百毫秒的阻塞"换成"几十次几十毫秒的小停顿"。它不减少总工作量（甚至增加，因为每块重读权重），买的是可预测性。1 个 prefill token ≈ 66 个解码 token 的执行时间，这是两者不能直接混批的算术原因。
  • 块大小的代价是外溢的：Δtstep​=(a+κs)c 是整个 batch 的延迟，不只是新请求的。c=512、s=8192 时整批多等 44.7 ms（含固定开销；纯处理部分 34.7 ms ≈ 7.9× 解码步）。
  • 上界由膨胀预算给出：cmax​=fTd​/(a+κs)，而 f 由 TPOT 的 SLA 反推（f=TTPOTmax​/Td​）。在 s≤32k 时 cmax​ 几乎与 s 无关（618~655 @ f=10） —— 因为 a≫κs。所以"块大小"可以是常数配置，"长 prompt 要切更小"是错的。
  • 下界由 TTFT 预算给出：cmin​=st0​/(TTTFT​−s(a+κs))。当 s(a+κs)>TTTFT​ 时"不可达" —— 这时唯一出路是缩短 prompt 或提高 Rpf​，调块大小无济于事。
  • 工程默认值落在 512~2048 的算术原因：上界压到 ~650 以下（膨胀预算）、下界抬到 ~128 以上（t0​ 与效率），中间那个区间就是默认值。
  • 抢占的判据是"两个成本比大小"，不是"一个序列长度阈值"：重算 ∝s，换出 ∝2KV1​s/βPCIe​。当 a>2KV1​/β 时换出在所有长度上都更优（示例：66.7 vs 10.5μs）。但真实默认是重算，因为 PCIe 竞争、pinned 内存有限、恢复调度成本三项让账面优势打折 —— 账面比决定理论上谁便宜，工程约束决定实现了谁便宜。
  • 该抢占谁：优先赶走"价值密度最低 + 重算成本最低"的请求（ndone​/sused​ 低、sused​ 小），但必须带老化项否则长 prompt 会饿死。
  • 分块还有一个被忽略的收益：它把 KV 分配平滑化（每块分配一次），而不分块时长 prompt 会一次性申请一大块 KV —— 后者本身就是抢占的触发器。
  • 一句话：分块预填充不是"把 prefill 变快"，而是"把 prefill 的延迟成本从'一次性大额'改成'分期小额'，并让每期的额度可由 SLA 反推"。

下一节：分块预填充让"新请求"不再卡住老请求。但反过来 —— 老请求的 KV 会一直占着显存，新请求能不能进来完全取决于显存。而"按最大长度预留"这种做法会把显存浪费掉 80% 以上。第 3 节进入 KV cache 的分页管理与显存账。
