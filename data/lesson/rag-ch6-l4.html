可观测性与线上定位：把每次问答的证据链留下来#

这一节要解决什么#

前面三节把"长期运行"的四个工程问题解决了一半：索引会更新（6.1）、缓存能省钱且不越权（6.2）、权限不漏（6.3）。剩下最后一个，也是最影响迭代速度的一个：

线上用户说"它答错了"。你打开日志，只看到一句 query 和一句 answer。接下来怎么办？

传统服务的排障靠异常栈：出错就有栈，栈指向行号。RAG 没有栈。它的失败形态是：

  • 非确定性：同一问题两次回答可能不同；
  • 部分失败：答案通顺、引用齐全、格式正确，但内容是错的 —— 没有任何"异常"；
  • 链路长：召回、排序、装配、生成，任何一段出错都表现为同一个症状；
  • 信号滞后且稀疏：用户不点踩不代表答对；点踩了也往往不说原因。

所以这一节的核心产物不是"日志格式"，而是一次问答的证据链（evidence chain）：把"这次回答是基于哪些候选、哪几段证据、哪个版本的索引和模板"完整记录下来，使得任何一次失败都可以离线重放（replay）并用反事实实验定位到具体某一段。

要回答四个问题：

  1. 证据链必须记哪些字段？哪些字段绝不能记？
  2. 全量记太贵，采样怎么采才不丢关键案例？日志体积怎么估？
  3. 怎么把"答错了"定位到"召回 / 排序 / 生成"？需要哪几个反事实实验？
  4. 线上该监控什么、怎么告警才不疲劳？最常见的根因是哪三个？

结论先放在这里：把每次问答记录成一条 Trace（候选 + 入选上下文 + 版本 + 输出 + 引用 + 延迟分段），并对失败样本跑五个反事实实验（空上下文 / oracle 注入 / 放大 k / 重排 / 反事实交换），可以把"答错了"自动归因到四类之一。⚠️ 实测：在四类各 10 条的合成集上，归因准确率 0.950；两条 rank_fail 被误判为 recall_fail —— 而这恰恰是"真值本身带噪声"的表现，值得保留在结果里而不是藏起来。

一、为什么 RAG 的排障比普通服务难#

普通服务 RAG 系统
出错有异常栈 失败是"答了但错"，没有异常
请求是确定性的 采样、索引版本、缓存都会改变输出
指标单一（延迟、错误率） 质量指标不可直接观测，只能靠评测或人工
失败可复现（同输入同输出） 复现需要完整上下文 + 版本 + 采样参数

结论：RAG 的可观测性目标不是"记录发生了什么"，而是记录足够的信息以便事后重建那一次问答。判据很直接：

给定一条 trace，能否在离线环境里逐字节重建当时的上下文、候选、版本，并跑反事实实验？能，则这条 trace 合格；不能，则它只是一条日志。

二、证据链的字段设计#

2.1 必备字段#

字段 类型 含 PII？ 保留期（示例） 用途
trace_id str 否 90 天 关联与检索
tenant str 否（id） 90 天 权限审计、分租户指标
query_hash str（加盐） 否（不可逆） 90 天 去重、聚类、缓存分析
query_redacted str 可能 7 天 人工排查（需脱敏）
rewritten_query str 可能 7 天 归因查询改写（ch4）
candidates[] list 否（仅 id + 分数 + 名次） 90 天 判断召回/排序
context[] list of chunk_id 否 90 天 判断装配与位置
context_hashes[] list of hash 否 90 天 校验上下文未被篡改
prompt_template_ver str 否 90 天 版本对比
model_ver str 否 90 天 版本对比
index_manifest_id str 否 90 天 索引版本（6.1）
acl_fingerprint str 否 90 天 权限快照
output str 是 7 天或哈希 质量分析
citations[] list of chunk_id 否 90 天 引用一致率
latency_ms{} dict 否 90 天 分段延迟（ch5-l4）
cost float 否 90 天 成本归因
feedback enum/None 可能 180 天 标签回流的种子

2.2 为什么记 chunk_id 与哈希而不是正文#

三个理由，缺一不可：

  1. 可复现：有了 chunk_id 与 index_manifest_id，就能从当时的索引版本取回原文。若只存正文，你其实是在存一份快照，无法判断"当时正确的那段现在是否还在索引里"。
  2. 隐私与合规：正文里可能含个人信息；chunk_id 是引用，不是内容。内容留在有权限控制的文档存储里，日志只留指针。
  3. 体积：一条候选记录的 id + 分数约几十字节，而正文可能几百 token。

注意一个容易踩的坑：query_redacted 与 output 是最容易含 PII 的两个字段。要么不存，要么存加盐哈希（不可逆、但可用于去重与聚簇），要么只存 7 天并单独加密。

2.3 版本字段为什么必须在内#

RAG 的失败有一大类来自版本不一致：

  • 索引已经更新，但缓存还返回旧答案（6.1 + 6.2）；
  • prompt 模板改了，模型行为变了；
  • 模型本身升级了。

没有版本字段的 trace，无法区分"算法变差了"和"版本换了"。 这也是最常见的排障弯路：花两天调检索参数，最后发现是模板版本回滚了。

三、采样、体积与隐私#

3.1 分层采样#

全量记录 trace 的成本不能忽略。分层采样（而不是随机采样）是关键：

层 采样率 理由
用户点踩 / 报错 100% 这是最有价值的样本
低分 / 空结果 / 拒答 100% 失败集中区
新租户 / 新语料（前 7 天） 100% 冷启动问题
慢查询（P95 以上） 100% 延迟归因
canary / 探针查询 100% 权限与健康检查
正常查询 1%~5% 统计基线

判据：随机采样会系统性丢失罕见事件（而罕见事件恰好是故障）。所以采样必须以"是否异常"为条件，而不是"是否被抽中"。

3.2 体积估算#

设每条 trace 平均 c 个候选、每个候选约 40 字节、上下文与输出共 B 字节，则单条约：

S≈40c+B

c=50、B=2KB 时 S≈4KB。若 QPS 为 20、全量记录：

4KB×20×86400≈6.9 GB/天

这就是必须采样的量化理由（1% 采样 → 69MB/天，完全可控）。同时这说明：降低候选数 c（例如 trace 里只记 top-20 而不是全部候选）比降低采样率更划算 —— 因为候选列表是体积的主要来源。

3.3 隐私边界#

  • 加盐哈希：hash(salt || query) 不可逆，但同一 query 在同一个盐下可去重。盐必须与日志分开存储、可轮换（轮换后旧哈希只用于历史关联）。
  • 保留期分层：指针类字段 90 天，内容类字段 7 天（或哈希）。
  • 删除请求（GDPR 类）：因为日志只有哈希与 id，删除文档时同时删除其 chunk_id 相关记录即可；不需要在全文日志里做模糊匹配。
  • 审计日志只记 (who, when, query_hash, doc_ids)（6.3 §4）：保证"谁在何时访问了哪些文档"可审计，同时不复制内容。

四、反事实归因：把"答错了"定位到一段#

4.1 五个实验#

给定一条失败的 trace 与一个可重放的系统，依次跑：

# 实验 操作 结论方向
① 空上下文 去掉所有证据，只给问题 若仍答对 ⇒ 参数记忆已够，检索不是必需（可能「无需修」）
② oracle 注入 把黄金证据强制放在上下文首位 若修好 ⇒ 问题在检索/排序；若仍错 ⇒ 问题在生成
③ 放大 k k→5k 重跑 若修好 ⇒ 召回瓶颈（黄金证据没进候选池）
④ 重排 把黄金证据移到首位（仅当它在候选内） 若修好 ⇒ 排序/位置瓶颈
⑤ 反事实交换 改黄金证据中的关键值 输出是否跟随 ⇒ 是否真在用证据（ch5-l3）

4.2 判定逻辑#

if 基线正确:                      -> none
elif not oracle_ok:               -> gen_fail     （给了正确证据也不用）
elif 黄金证据不在候选:             -> recall_fail  （检索没找回来）
elif 放大k修好 且 重排没修好:       -> recall_fail  （候选池不足）
elif 重排修好:                     -> rank_fail    （找回来了但没排进上下文）
else:                             -> rank_fail    （兜底：装配/位置问题）

这套逻辑有一个重要性质：结论完全由可观测的反事实结果推出，不依赖任何人的判断。 这正是它比"人工看看日志"强的根本原因。

4.3 实测准确率与误判分析#

⚠️ 合成集：四类失败各 10 条，k=10、上下文预算 4 条。

true/pred             none  recall_fail    rank_fail     gen_fail    sum
none                    10            0            0            0     10
recall_fail              0           10            0            0     10
rank_fail                0            2            8            0     10
gen_fail                 0            0            0           10     10
归因准确率 = 0.950

两条 rank_fail 被误判为 recall_fail，原因是：这两条的黄金证据在放大 k 后仍不在候选池里（噪声把小 k 与大 k 的排序都压过了它），于是判定逻辑走了 not 黄金证据在候选 这一支。

这个误判不该被隐藏，它揭示了两个真实约束：

  1. 归因质量受候选池规模限制：如果 k 太小，你无法区分"没召回"与"召回了但排在后面"；
  2. 真值本身可能带噪声：预设的标签是"rank_fail"，但从可观测行为看它就是召回失败 —— 在真实系统里，"真值"往往是人工判断，本身就有误差。所以混淆矩阵里的非对角元不全是算法错。

4.4 边界#

  • 反事实实验需要可重放的系统：如果生成是外部 API 且不可复现（温度、版本漂移），归因结果带噪声。缓解：固定随机种子、记录并复用当时的版本。
  • oracle 注入测的是"生成能力上界"：它证明"给对证据能答对"，但不证明"排序没问题"。
  • 归因不是免费的：每失败一次要跑约 5 次推理。所以只对采样出的失败样本做归因，并把结论聚合（"本周失败中召回占 62%"）。
  • 归因结论会随 k、预算、模型变化：它描述的是当时配置下的瓶颈分布，不是系统的永久属性。

五、线上信号与告警#

5.1 三类信号#

类别 指标 为什么需要
健康 空结果率、拒答率、引用率、P95 延迟、错误率 用户能直接感知
质量代理 召回命中率（黄金证据在 top-k 的比例）、引用一致率、点踩率 无标注时的质量近似
版本与一致性 索引 manifest 漂移、模板/模型版本分布、缓存命中率 版本类故障（最容易漏）

5.2 金丝雀探针（synthetic probes）#

用一批固定答案的合成问题定时打线上（例如每分钟 1 条）：

  • 它们有确定的黄金证据与期望答案，因此可以不依赖用户反馈检测质量下降；
  • 覆盖三类：单跳事实、多跳、应拒答；
  • 与 canary 权限探针（6.3）合并成"端到端体检"。

判据：探针失败率 > 0 即告警（因为探针是确定的，失败一定是系统问题）。

5.3 用变化点检测代替固定阈值#

质量指标天然有波动（流量结构、语料变化），固定阈值会产生大量误报。工程上常用：

  • EWMA：mt​=αxt​+(1−α)mt−1​，对均值漂移敏感；
  • 3σ 控制限：∣xt​−mt​∣>3σt​ 才告警；
  • CUSUM：累积偏移 max(0,St−1​+xt​−mt​−k)，对缓慢持续的恶化最敏感。

告警设计原则：① 每个告警必须有对应的处置动作；② 阈值用"变化"而不是"绝对值"；③ 探针类（确定性）用零容忍，统计类（噪声大）用变化点检测。

5.4 最常见的三个根因#

按 §2.3 与 §5.1 的字段设计，线上失败最常见的三个根因是：

排名 根因 判据信号 处置
1 索引未更新/未切换 manifest 漂移、created_at 过旧、新文档查不到 检查发布流水线（6.1）
2 ACL 字段缺失/继承错 不可见率异常上升或下降、canary 失败 跑 ACL 对抗测试（6.3）
3 模板/模型版本不一致 版本分布出现双峰、缓存键版本混杂 统一版本、清缓存

这三个根因有一个共同点：它们都不是"算法问题"，而是"运维问题"。 所以可观测性的第一价值不是帮你调参，而是让你不必调参就能排除这三类。

代码#

# -*- coding: utf-8 -*-
"""⚠️ 合成数据：证据链 Trace + 反事实重放归因 + 混淆矩阵。
   检索/生成为可复现的确定性 stub，只为让归因逻辑可见。"""
import json, numpy as np
from dataclasses import dataclass, field, asdict

@dataclass
class Trace:
    trace_id: str; tenant: str; query: str; k: int; ctx_budget: int
    candidates: list = field(default_factory=list)   # [{doc,score,rank,in_ctx}]
    context: list = field(default_factory=list)      # [doc,...] 顺序即位置
    output: str = ""; citation: str = ""
    latency_ms: dict = field(default_factory=dict); cost: float = 0.0
    def to_jsonl(self): return json.dumps(asdict(self), ensure_ascii=False)

# ---------- 模拟系统 ----------
def pos_pen(i, n, kappa=1.3):        # 中部惩罚 -> 注意力 U 形
    d = i / max(1, n - 1)
    return kappa * (1 - abs(2 * d - 1))

def retrieve(q, k, rng):
    hits = []
    for d in range(q["n_doc"]):
        base = q["gold_base"] if d == q["gold"] else (
            q["dist_base"] if d in q["distract"] else -1.0)
        hits.append((base + rng.normal(0, 0.35), d))
    hits.sort(reverse=True)
    return [{"doc": d, "score": round(s, 4), "rank": i + 1}
            for i, (s, d) in enumerate(hits[:k])]

def generate(q, ctx):
    """ctx 是 (doc, score) 列表，顺序即位置。返回 (答案, 引用)。"""
    if q["type"] == "none":
        return q["prior"], ""                       # 参数记忆已足够，检索与否都对
    if q["type"] == "gen_fail":
        return q["wrong_ans"], "doc?"               # 先验压过证据：读到也不用
    if not ctx:
        return "UNKNOWN", ""
    logits = [s - pos_pen(i, len(ctx)) for i, (d, s) in enumerate(ctx)]
    d = ctx[int(np.argmax(logits))][0]
    return (q["gold_ans"] if d == q["gold"] else q["wrong_ans"]), f"doc{d}"

def run(q, k, ctx_budget, rng, ctx_override=None):
    cands = retrieve(q, k, rng)
    ctx = (ctx_override if ctx_override is not None
           else [(c["doc"], c["score"]) for c in cands[:ctx_budget]])
    ans, cite = generate(q, ctx)
    return Trace(trace_id=f"t{q['qid']}", tenant=q["tenant"], query=q["query"], k=k,
                 ctx_budget=ctx_budget,
                 candidates=[{**c, "in_ctx": c["doc"] in [d for d, _ in ctx]} for c in cands],
                 context=[d for d, _ in ctx], output=ans, citation=cite,
                 latency_ms={"retrieve": 9.0, "rerank": 0.0, "prefill": 120.0, "decode": 900.0},
                 cost=0.0007)

# ---------- 反事实归因 ----------
def attribute(q, k, ctx_budget, rng, base_trace=None):
    tr = base_trace or run(q, k, ctx_budget, np.random.default_rng(q["qid"] + 1000))
    ok = (tr.output == q["gold_ans"])
    gold_in_topk = any(c["doc"] == q["gold"] for c in tr.candidates)
    others = [(c["doc"], c["score"]) for c in tr.candidates if c["doc"] != q["gold"]]
    # ① oracle 注入：黄金证据强制放首位
    o_ans, _ = generate(q, [(q["gold"], 99.0)] + others[:max(0, ctx_budget - 1)])
    oracle_ok = (o_ans == q["gold_ans"])
    # ② 空上下文
    no_ret_ok = (generate(q, [])[0] == q["gold_ans"])
    # ③ 放大 k
    big_ok = (run(q, k * 5, ctx_budget, np.random.default_rng(q["qid"] + 2000)).output
              == q["gold_ans"])
    # ④ 重排：黄金证据放首位（仅当已在候选内）
    reorder_ok = False
    if gold_in_topk:
        sc = next(c["score"] for c in tr.candidates if c["doc"] == q["gold"])
        reorder_ok = (generate(q, [(q["gold"], sc)] + others[:max(0, ctx_budget - 1)])[0]
                      == q["gold_ans"])
    # ⑤ 反事实交换
    q2 = dict(q); q2["gold_ans"] = q["gold_ans"] + "-SWAPPED"
    follows = (generate(q2, [(q["gold"], 99.0)] + others[:max(0, ctx_budget - 1)])[0]
               == q2["gold_ans"])
    ev = dict(oracle=oracle_ok, no_ret=no_ret_ok, big=big_ok, reorder=reorder_ok, follow=follows)
    if ok:                       return "none", ev
    if not oracle_ok:            return "gen_fail", ev
    if not gold_in_topk:         return "recall_fail", ev
    if big_ok and not reorder_ok: return "recall_fail", ev
    if reorder_ok:               return "rank_fail", ev
    return "rank_fail", ev

# ---------- 构造 40 条查询（四类各 10 条）----------
rng = np.random.default_rng(3)
Q = []
for i in range(40):
    t = ["recall_fail", "rank_fail", "gen_fail", "none"][i % 4]
    gold_base, dist_base, n_dist = 2.0, 0.9, 6
    if t == "recall_fail": gold_base, dist_base, n_dist = 0.2, 1.6, 20    # 被挤出 top-k
    if t == "rank_fail":   gold_base, dist_base, n_dist = 1.00, 1.02, 12  # 在 top-k，排在预算外
    Q.append(dict(qid=i, tenant=f"t{i%3}", query=f"问题{i}", type=t, n_doc=120, gold=i % 50,
                  gold_base=gold_base, dist_base=dist_base,
                  distract=set(range(50, 50 + n_dist)),
                  gold_ans=f"A{i}", wrong_ans=f"W{i}", prior=f"A{i}"))
K, CTX = 10, 4
KINDS = ["none", "recall_fail", "rank_fail", "gen_fail"]
conf = {a: {b: 0 for b in KINDS} for a in KINDS}
for q in Q:
    pred, ev = attribute(q, K, CTX, rng)
    conf[q["type"]][pred] += 1

print("== ⚠️ 合成数据：反事实归因的混淆矩阵（行=预设真值，列=归因结果）==")
print(f"{'true/pred':<13} " + " ".join(f"{k:>12}" for k in KINDS) + f" {'sum':>6}")
for a in KINDS:
    print(f"{a:<13} " + " ".join(f"{conf[a][b]:>12}" for b in KINDS) +
          f" {sum(conf[a].values()):>6}")
print(f"归因准确率 = {sum(conf[a][a] for a in KINDS)/len(Q):.3f}")

print("\n== 一条 trace 的证据链（JSONL 单行）==")
tr = run(Q[0], K, CTX, np.random.default_rng(1))
line = tr.to_jsonl()
print(line[:300] + ("..." if len(line) > 300 else ""))
print(f"\n字段数={len(asdict(tr))}  含 query 原文={('query' in asdict(tr))}")

关键设计决策：归因函数的返回只依赖反事实实验的布尔结果（oracle_ok、gold_in_topk、big_ok、reorder_ok），没有任何"人工看一眼"的环节。这是这份代码最重要的选择：排障结论必须能被别人用同样的 trace 复算出来，否则"归因"就退化成个人经验。代码里那两个误判也没有被"修掉"——它们来自候选池规模与真值噪声，把它们保留下来才能暴露归因方法的真实边界。

练习#

  1. 补全 trace 字段并估算体积。为你的系统写出完整字段表（含类型、是否 PII、保留期），并计算：QPS=30、候选 100、每条上下文 8 段、输出 400 token 时的日志体积/天。然后给出两种把体积压到 1/10 的方案（提示：候选只存 top-20 + 分数分桶；输出存哈希）并比较各自丢失了什么能力。

  2. 构造 5 条"看起来正确但错"的失败。设计 5 条 trace，使其输出通顺、引用齐全，但答案错误或引用不支持。然后说明你的归因流程能否识别它们（提示：需要第 5 个实验"反事实交换"与引用一致率检查）。

  3. 归因的代价核算。每次归因跑 5 次推理。设失败率 3%、QPS=30、对所有失败做归因、每次推理成本 0.002 元。计算每天归因成本；再改为"对 20% 失败样本归因"重算。给出"归因覆盖率 vs 成本"的推荐工作点及理由。

  4. 采样偏差实验。构造一个场景：5% 的查询是"新租户的首次查询"，且它们的失败率是正常的 10 倍。分别用 (a) 1% 随机采样、(b) 分层采样（新租户 100%），估计总体失败率。比较两种估计的偏差与方差，说明为什么随机采样会系统性低估故障。

  5. 告警设计。为 空结果率 设计一个告警：给出 EWMA 与 CUSUM 的具体参数（α、k、h），并用模拟数据（正常波动 + 一次持续 2 小时的 3 倍恶化）比较两种方法的检测延迟与误报率。给出你推荐的方案。

  6. canary 探针与质量探针合并。设计一套 30 条的探针集：10 条单跳、10 条多跳、5 条应拒答、5 条跨租户 canary。写出每条探针的字段（问题、期望答案、黄金证据、期望行为），并说明如何用它在 1 分钟内判断"索引/权限/生成"三部分是否健康。

  7. 版本漂移的自动检测。设计一个任务：每天统计 trace 中 index_manifest_id、prompt_template_ver、model_ver 的分布，断言"线上版本集合 ⊆ 发布清单"。说明这个断言能捕获哪三类故障，并给出实现要点（提示：缓存键里的版本也会出现在 trace 里）。

  8. 反事实交换的归因增强。把第 5 个实验的 follow（是否跟随证据）加入判定逻辑，构造一个新的失败类型"引用装饰"（输出引用了证据但内容实际来自参数记忆）。给出判定条件与实测方法（提示：follow == False 且 oracle_ok == True）。

小结#

  • RAG 没有异常栈：失败是"答了但错"，且非确定、链路长、信号滞后。可观测性的目标是能重建那一次问答，不是"记一条日志"。
  • 证据链必备字段：trace_id / tenant / query_hash / rewritten_query / candidates(含分数与名次) / context / context_hashes / prompt_template_ver / model_ver / index_manifest_id / acl_fingerprint / output / citations / latency_ms / cost / feedback。
  • 只记 chunk_id 与哈希，不记正文：三个理由 —— 可复现（依赖当时索引版本）、隐私合规、体积。⚠️ 字段数 11、单条含候选列表的 JSONL 示例见代码输出。
  • 采样必须分层：点踩/低分/空结果/新租户/慢查询/canary 100%，正常 1%~5%。随机采样会系统性丢失罕见故障。 体积：S≈40c+B，QPS=20 全量约 6.9GB/天 —— 这就是要采样的量化理由。
  • 五个反事实实验：空上下文、oracle 注入、放大 k、重排、反事实交换。判定逻辑完全由布尔结果推出，可被他人用同一条 trace 复算。
  • 实测归因准确率 0.950（四类各 10 条）。两条 rank_fail 被误判为 recall_fail，原因是候选池太小 + 真值噪声 —— 非对角元不全是算法错，它暴露的是方法边界（k 太小时无法区分"没召回"与"排在后面"）。
  • 常见根因排序：① 索引未更新/未切换；② ACL 字段缺失或继承错；③ 模板/模型版本不一致。三者都是运维问题，可观测性的第一价值是让你不必调参就能排除它们。
  • 告警用变化点检测（EWMA / 3σ / CUSUM）而不是固定阈值；确定性探针（canary、金丝雀问答）零容忍，统计指标用变化点。
  • 一句话：把每次问答记成一条可重放的证据链，失败就能用反事实实验自动定位到召回/排序/生成；而在那之前，先用版本字段排除掉三类最常见的运维故障。
