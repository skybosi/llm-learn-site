warp 调度、分支发散与占用率的取舍#

上一课把线程分成了 warp：32 个线程共享一个取指单元。那么 SM 上常驻的几十个 warp，谁先发射？两条常见错答是"大家一起跑"和"平均轮转"。真相是：每个 warp scheduler 每周期只从就绪的 warp 里挑一个发一条指令；被挑中的 warp 里，32 个 lane 只有"这一刻该干活"的会产生结果。这两句话解释了发散的全部代价，也解释了 occupancy 为什么只是"延迟隐藏的预算"，不是性能指标本身。

一、概念讲解#

1. 发射模型：一个周期、一个 warp、一条指令#

把 SM 看成若干子分区（sub-partition），每个子分区一个 warp scheduler：每周期从名下 warp 中挑出一个就绪（ready）的，发射它的下一条指令；一条 warp 指令不论多少 lane 活跃，都只占一个 issue slot。非就绪原因有三类：

停顿原因 触发条件 典型修法
等访存 load/store 未返回 提 occupancy、预取、少访存
等依赖 上一条指令结果未就绪 增 ILP（展开、重排）、别的 warp 顶上
等屏障 __syncthreads() 等同伴（第 3 课） 减少屏障轮数、改用 warp shuffle

关键推论：性能取决于"每周期有多少 warp 能发指令"，而不是有多少 warp 存在。单个 warp 内部严格串行，SIMT 并行度只体现在 32 个 lane 上，所以一个 warp 再快也占不满发射端口。

2. 延迟隐藏：需要几个 warp 才够#

设平均停顿为 L 周期，单个 warp 大约每 L+1 周期才贡献一条指令；子分区想每周期都发得出去，就需要约 L+1 个 ready warp 轮着来：

平均停顿 L（量级估算） 单个子分区需要 4 个子分区合计
4（寄存器运算为主） ≈5 ≈20
16（L2 命中） ≈17 ≈68（已超常见 64 warp/SM 上限）
32+（HBM 访存） ≈33 ≈132（远超上限）

这些数字按"每条指令都取最坏停顿"估，是乐观上界（真实 kernel 是混合停顿），但给出了正确直觉：访存延迟靠"更多 warp"填，计算延迟靠"更多 ILP"填。需求超过硬件上限时，出路是减少访存次数、或用共享内存/寄存器复用数据（第 3、4 章）。

3. 分支发散：一条指令服务不了两拨 lane#

同一 warp 内线程走到不同路径时，硬件把当前路径不参与的 lane 掩掉（masked off），先让活跃 lane 执行这段指令，路径都走完再汇合。官方称之为 warp divergence，并指出 warp 内线程走同一路径时利用率最高。

代价可按 issue slot 直接算：两条路径各 k 条指令、16 lane 走 A、16 lane 走 B，该 warp 要发 2k 条指令，而有用的只有 32k 个 lane·指令——lane 效率降到 1/2。warp 内出现 p 条路径时串行次数接近 p 倍（本课代码扫出 1/2/4/8/16/32 条路径，最坏 1/32）。

什么时候不花钱？uniform branch（条件在整个 warp 内同向，如按 blockIdx 判断）不发散；短分支常被编译器改写成 branch predication（谓词化）——官方 Best Practices Guide 说明，谓词化时受条件控制的指令不会被跳过，而是每条带一个 per-thread 谓词决定该线程是否写回结果。可见它省的是跳转与重汇聚开销，不是两边指令量：两条路径都有真活时，它和发散一样贵。

判据是发散条件与谁相关：与 lane 索引相关（if (threadIdx.x % 2)、if (lane < 16)）几乎总是写法的锅，可通过重划任务边界让同 warp 线程干同一件事；与数据相关（if (a[i] > 0)）无法消除，只能平衡两条路径的工作量，让重路径上的 lane 尽量多。

4. occupancy：它是预算，不是 KPI#

occupancy（占用率） = 每 SM 实际驻留 warp 数 ÷ warp 数上限，由四类限制取最小值：① warp 上限 max_warps_per_sm ÷ ceil(blockDim/32)；② 寄存器——每线程寄存器数按分配粒度向上取整（多数现代架构按每 warp 256 个、即每线程 8 个），乘块内线程数得"每块实占寄存器"再除 regs_per_sm；③ 共享内存 smem_per_sm ÷ 每块共享内存（含每块开销与 carveout）；④ max_blocks_per_sm——32 线程的小 block 往往是它先卡住。

数值以官方 Programming Guide 附录 "Features and Technical Specifications" 表和本机 deviceQuery 为准；Runtime 另有 cudaOccupancyMaxActiveBlocksPerMultiprocessor() 可算。重点是取舍：

  • 访存密集（延迟长、靠大量 warp 填空）→ 要高 occupancy，先看寄存器与共享内存吃掉了多少常驻 warp；
  • 计算密集且 ILP 高（每路都有独立指令可重叠）→ 中等甚至偏低 occupancy 也能跑满，压寄存器只换来 spill（变量挤进本地内存，反增访存）；
  • 官方 Best Practices Guide 的立场：occupancy 高不保证性能高，它只衡量"够不够隐藏延迟"，真正的判据是 profile 出的 stall 原因（第 8 章）。

5. 常见坑#

  • 把 occupancy 当唯一目标：用 __launch_bounds__/maxrregcount 硬压寄存器，spill 增加、指令变多，性能反降。
  • 用小 block 提 occupancy：blockDim = 32 时 max_blocks_per_sm（常见 1632）先到顶，occupancy 卡在 25%50%。
  • 以为"分支短就没代价"：代价按"路径条数 × 路径长度"算，不是分支语句的视觉长度。
  • 边界判断写在热循环里：if (threadIdx.x < n) 在 n 非 32 倍数时必然多走一条空路径，通常可接受，但别嵌套。
  • 以为 warp 内线程自动同步：Volta 之后 warp 内线程独立调度，warp 级同步须显式写（第 3 课）。

二、可运行代码示例#

不碰 GPU 也能算清两件事：发散花掉多少 issue slot，occupancy 卡在哪一项。下面纯 Python 代码的上半部分是 issue slot 模型（含路径数扫描），下半部分用官方 occupancy 文档的"逐项取最小"算法扫描 block 大小、寄存器与共享内存。

# ---- issue slot 模型量化 warp 发散 + 官方 occupancy 公式算常驻 warp（纯 Python）----
WARP = 32


def report(name, paths, branch_overhead=0, useful=None):
    """paths: {路径名: (活跃 lane 数, 路径指令条数)}。
    关键假设：一条 warp 指令不论几个 lane 活跃，都占 1 个 issue slot —— 发散的代价由此而来。"""
    slots = sum(insts for _, insts in paths.values()) + branch_overhead
    if useful is None:                       # 默认：每个 lane 的结果都有用
        useful = sum(lanes * insts for lanes, insts in paths.values())
    print(f'{name:<30} issue slot={slots:>3}  有用 lane·指令={useful:>4}  '
          f'lane 效率={useful / (slots * WARP):.3f}')
    return slots


print('=== 同一段代码的三种写法（两条路径各 10 条指令）===')
a1 = report('无分支：全 warp 走同一路径', {'all': (32, 10)})
a2 = report('发散：16 lane 走 A、16 lane 走 B',
            {'A': (16, 10), 'B': (16, 10)}, branch_overhead=2)
a3 = report('谓词化：两条路径都发、都不跳过',
            {'A+pred': (32, 10), 'B+pred': (32, 10)}, useful=320)
print(f'两条路径都发时，发散比无反散多花 {a2 / a1:.1f}x issue slot；'
      f'谓词化省掉 {a2 - a3} 个 slot（跳转与重汇聚）\n')

print('=== warp 内被走到的路径数扫描（每路 10 条指令，lane 均分）===')
print(f'{"路径数":>5} {"每路 lane":>8} {"issue slot":>11} {"lane 效率":>10}')
for p in (1, 2, 4, 8, 16, 32):
    slots = p * 10
    print(f'{p:>5} {WARP // p:>8} {slots:>11} {(WARP * 10) / (slots * WARP):>10.3f}')

# ---- occupancy：按官方 occupancy 文档的"逐项取最小"算法 ----
# 参数取某代架构的常见量级；真值以官方 Programming Guide 的
# "Features and Technical Specifications" 表与实际 GPU 的 deviceQuery 输出为准
SM = dict(regs_per_sm=65536,       # 64K 个 32-bit 寄存器 / SM
          smem_per_sm=100 * 1024,  # 每 SM 可用共享内存，量级 100 KB（随架构与 carveout 变）
          max_warps_per_sm=64,     # 常驻 warp 上限
          max_blocks_per_sm=32,    # 常驻 block 上限
          reg_gran_per_warp=256)   # 寄存器分配按 warp 粒度 256 个向上取整（=8 寄存器/线程）


def occupancy(regs_per_thread, block_threads, smem_per_block, sm=SM):
    warps_per_block = -(-block_threads // WARP)
    reg_alloc = -(-regs_per_thread // 8) * 8                    # 每线程按 8 个向上取整
    per_block = max(reg_alloc * block_threads,
                    warps_per_block * sm['reg_gran_per_warp'])  # 每块实占寄存器
    limits = {'warps': sm['max_warps_per_sm'] // warps_per_block,
              'regs': sm['regs_per_sm'] // per_block,
              'smem': (sm['smem_per_sm'] // smem_per_block) if smem_per_block else 10 ** 9,
              'blocks': sm['max_blocks_per_sm']}
    blocks = min(limits.values())
    res_warps = blocks * warps_per_block
    limiters = [k for k, v in limits.items() if v == blocks]
    return blocks, res_warps, res_warps / sm['max_warps_per_sm'], limiters


def sweep(title, rows, header, label=lambda a: str(a[0])):
    print(f'\n=== {title} ===')
    print(header)
    for args in rows:
        b, w, o, lim = occupancy(*args)
        print(f'{label(args):>12} {b:>9} {w:>8} {o:>8.1%}  {"+".join(sorted(lim))}')


sweep('block 大小扫描：40 寄存器/线程、0 共享内存',
      [(40, bt, 0) for bt in (32, 64, 128, 256, 384, 512, 1024)],
      f'{"block 线程数":>12} {"常驻 block":>9} {"常驻 warp":>8} {"occupancy":>9}  限制项',
      label=lambda a: str(a[1]))

sweep('寄存器压力扫描：block = 256 线程、0 共享内存',
      [(rg, 256, 0) for rg in (24, 32, 40, 48, 64, 96, 128)],
      f'{"寄存器/线程":>12} {"常驻 block":>9} {"常驻 warp":>8} {"occupancy":>9}  限制项')

sweep('共享内存扫描：block = 256 线程、40 寄存器/线程',
      [(40, 256, kb * 1024) for kb in (0, 8, 16, 32, 48, 100)],
      f'{"KB/块":>12} {"常驻 block":>9} {"常驻 warp":>8} {"occupancy":>9}  限制项',
      label=lambda a: str(a[2] // 1024))

三、练习#

  1. 实现：给 report 加一个三路发散的例子：16 lane 走 A（10 条指令）、8 lane 走 B（6 条）、8 lane 走 C（4 条），算出 issue slot 与 lane 效率，解释"路径数相同但长度不同"与"均分"差在哪。
  2. 解释：为什么谓词化在两条路径都有真活时不比发散便宜？请从官方对谓词化的描述（受控指令不被跳过、只加 per-thread 谓词）出发，说明它省了什么。
  3. 对比/验证：把 occupancy() 的 max_blocks_per_sm 依次改成 16/8，重跑 block 大小扫描，找出 block = 32 时的 occupancy；解释小 block 为什么被它卡住。
  4. 思考：纯访存拷贝 kernel（每线程 1 次 16 字节 load、store）与矩阵乘 kernel，哪个更依赖高 occupancy？用第 2 节"延迟隐藏需要几个 warp"表论证，并各举一个压寄存器伤性能的场景。
