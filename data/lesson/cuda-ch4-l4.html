寄存器压力与 occupancy 的工程权衡#

前三课的方向都是"越大越好"：tile 越大搬运越省，缓冲越深延迟藏得越干净。它们花的是同一种资源——每线程可用的寄存器与每块可用的 shared memory。把 GEMM 的块 tile 从 128×64 提到 128×128，每线程累加器从 32 涨到 64，下面算出的 occupancy 就从 38% 掉到 25%。本课把"多省一点搬运"与"多留一点并行"的交换算成一笔可核对的账。

一、概念讲解#

1. occupancy 的定义与四个限制#

occupancy（占用率）= SM 上实际驻留的 warp 数 ÷ SM 支持的最大 warp 数。它不是性能指标，而是约束条件：驻留 warp 越多，越有机会在某个 warp 等访存时切到别人，把延迟藏掉。

它由四个资源分别决定，取其中最紧的那个：

  1. 寄存器：每线程寄存器数 × 每块线程数 → 每 SM 能放几块；
  2. 线程上限：每 SM 最多 2048 线程（= 64 warp）；
  3. 块数上限：每 SM 最多驻留 32 个 block；
  4. shared memory：每 SM 的共享内存容量 ÷ 每块占用。

以 Hopper（cc 9.0）为例，官方公开参数是：寄存器文件 64K 个 32-bit 寄存器/SM、每线程最多 255 个寄存器、最多 2048 线程 / 64 warp per SM、每 SM 最多 32 个 block、shared memory 228 KB/SM（单块最多 227 KB，官方保留 1 KB）。cc 9.0 的最大并发 warp 数与 Ampere 相同（64）。这些数字要按自己手上的卡核对：cudaDeviceProp 或官方 occupancy calculator 才是权威。

还有一条最容易被忽略的细节：寄存器按 warp 级、8 个寄存器/线程的粒度分配（向上取整）。所以 17 与 24 个寄存器/线程可能一样贵；"少用 3 个寄存器就能多住一个块"成立与否，取决于跨过的是哪一个 8 的倍数。

2. 一本可核对的账#

下一节的代码按上面的规则实现了 occupancy 计算。先看只受寄存器限制的情形（256 线程/块、不用 shared memory）：

regs/线程 允许块数 驻留线程 occupancy
24 8 2048 100%
32 8 2048 100%
40 6 1536 75%
64 4 1024 50%
96 2 512 25%
128 2 512 25%
168 1 256 12.5%
255 1 256 12.5%

再看 shared memory 一起参与（256 线程、每块 32 KB）：regs=32 时是 88%（限制因素变成 shared memory），regs=128 时 25%。这说明：压寄存器不一定能提高 occupancy——先看清是谁在卡。

最后看 GEMM 配置（按"累加器 + 约 40 个其他寄存器"量级估计）：

块 tile / 线程 累加器/线程 约计寄存器 occupancy（限制因素）
64×64 / 128 32 72 44%（寄存器）
128×64 / 256 32 72 38%（寄存器）
128×128 / 256 64 104 25%（寄存器）
128×128 / 128 128 168 19%（寄存器）

这张表就是本课的核心矛盾：tile 面积决定复用（第 1 课），而累加器面积就是寄存器面积。要更大的复用，就在同一个寄存器池里少留一点给并行。

3. 为什么 occupancy 重要：延迟隐藏的两条路#

要维持带宽 BW，在飞的字节数必须满足（Little 定律的形式）：

bytes in flight≥BW×L

L 是访存延迟，几百个周期量级，改不了；BW 是每个 SM 分到的带宽份额。左边的量只能靠两样东西凑：驻留 warp 数（occupancy）与每线程同时在飞的独立 load 数（ILP，指令级并行）。

下一节的代码用一个周期级仿真量了前者：1 个发射口/周期、每个 warp 只允许 1 个 load 在飞、延迟 400 周期、每次 load 后 8 条计算指令：

驻留 warp occupancy 仿真 IPC 发射口空闲
8 12.5% 0.175 82%
16 25% 0.345 65%
32 50% 0.655 34%
48 75% 0.886 11%
64 100% 0.955 5%

两个读数值得记住：occupancy 从 25% 提到 50%，吞吐几乎翻倍（0.345 → 0.655）；而从 75% 提到 100% 只多 7 个百分点，收益明显递减。所以"occupancy 越高越好"是错的，正确问法是"够不够撑起带宽目标"。

ILP 这条路解释了另一个现象：为什么真实 GEMM 在 25% occupancy 下依然很快。8×8 的 thread tile 意味着每线程有 8 条互相独立的累加链，一次能发出多个不相关 load，在飞字节数靠 ILP 就凑够了。低 occupancy + 高 ILP 与高 occupancy + 低 ILP 可以打平，选哪条取决于访存形态与寄存器预算。

4. 工程上的三个旋钮#

  1. __launch_bounds__(maxThreadsPerBlock, minBlocksPerMultiprocessor)：告诉编译器"我要至少 N 个块驻留，请把每线程寄存器压到 65536/(N×线程数) 以下"。编译器会照办，代价是可能 spill（把放不下的值溢出到 local memory）。
  2. -maxrregcount：给整个编译单元设每线程寄存器上限；粒度粗（非 per-kernel），一般不如 __launch_bounds__ 精确。
  3. 手工改造：减少同时活跃的临时值、复用寄存器、把大 tile 拆成两级——把"要复用"与"要并行"分别放在 shared memory 与寄存器上。

判断顺序永远是：先 profile 找到瓶颈，再决定动不动寄存器。 常用指标（以本机 ncu --query-metrics 为准）：launch__registers_per_thread、sm__warps_active.avg.pct_of_peak_sustained_active、launch__occupancy_limit_registers，以及 local memory/spill 相关指标。特别要警惕 spill：local memory 实际落在 off-chip 内存里，一次 spill 就是一次额外访存，可能把第 1 课省下来的搬运全部吐回去。

5. 常见坑#

  • 只盯 occupancy：带宽已经打满时，提高 occupancy 的收益是 0；先确认是延迟受限还是带宽受限。
  • 压寄存器压出 spill：没看 spill 指标就调 __launch_bounds__，结果搬运量涨了、时间没降。
  • 用 -maxrregcount 一刀切：为了一个大 kernel 的 occupancy，把同文件里的小 kernel 一起压坏。
  • 按"差 3 个寄存器"推 occupancy：忘了 8 个/线程的分配粒度。
  • 没发现是 shared memory 在卡：regs=32 + 32 KB/块的例子里，压寄存器完全无效。
  • 把 100% 当目标：工程目标应是"够用的 occupancy + 足够的 ILP"，不是把 SM 塞满。

二、可运行代码示例#

两段：occupancy 账本（按公开的 cc 9.0 参数实现四个限制的取最小逻辑）与延迟隐藏仿真（occupancy → 吞吐）。

# ===== 本课示例：occupancy 账本 + 延迟隐藏曲线 =====
REG_SM, THREAD_SM, WARP_SM = 65536, 2048, 64
BLOCK_SM, SMEM_SM, SMEM_RESERVED, REG_GRAN = 32, 228 * 1024, 1024, 8

def occupancy(threads, regs, smem_per_block):
    """按公开的 cc 9.0 参数算 occupancy；上限各自算"允许几个块"，再取最小。"""
    wpb = threads // 32
    regs_r = -(-regs // REG_GRAN) * REG_GRAN
    blk_reg = REG_SM // (regs_r * 32 * wpb) if regs_r else BLOCK_SM
    blk_thr = THREAD_SM // threads
    blk_smem = (SMEM_SM - SMEM_RESERVED) // max(smem_per_block, 1)
    blk_warp = WARP_SM // wpb
    caps = {'寄存器': blk_reg, '线程上限': blk_thr, '共享内存': blk_smem,
            '块/warp 上限': min(BLOCK_SM, blk_warp)}
    blocks = max(min(caps.values()), 0)
    limit = min(caps, key=caps.get)
    return blocks * threads, (blocks * threads) / THREAD_SM, blocks, limit

print("参数取 Hopper（cc 9.0）公开值：64K 寄存器/SM、2048 线程/SM、64 warp/SM、"
      "228 KB 共享内存/SM、32 块/SM。\n")
print(f"{'regs/线程':>9} {'块数':>5} {'驻留线程':>9} {'occupancy':>10} {'限制因素':>10}")
for R in (24, 32, 40, 64, 96, 128, 168, 255):
    live, occ, blocks, limit = occupancy(256, R, 0)     # 纯寄存器受限的 kernel
    print(f"{R:>9} {blocks:>5} {live:>9} {occ:>9.0%} {limit:>10}")

print("\n同样 256 线程，但每块占 32 KB 共享内存（双缓冲的一级）：")
for R in (32, 64, 128):
    live, occ, blocks, limit = occupancy(256, R, 32 * 1024)
    print(f"  regs={R:>3} → {blocks} 块 = {live} 线程，occupancy {occ:.0%}（限制：{limit}）")

print("\n输出 tile 越大越省搬运，但累加器直接吃寄存器：")
for bm, bn, th in ((64, 64, 128), (128, 64, 256), (128, 128, 256), (128, 128, 128)):
    acc = (bm * bn) // th
    regs = acc + 40          # ≈ 累加器 + A/B 片段 + 地址与循环变量（数量级估计）
    live, occ, blocks, limit = occupancy(th, regs, 2 * 128 * 32 * 2)
    print(f"  tile {bm:>3}x{bn:<3} / {th:>3} 线程 → 累加器 {acc:>3}/线程，"
          f"约 {regs:>3} 寄存器 → occupancy {occ:>4.0%}（{limit}）")

def simulate(n_warps, iters=40, latency=400, comp=8, jitter=64):
    """1 个发射口/周期；每 warp 同时只允许 1 个 load in flight；抖动只为打散相位。"""
    nxt=[0]*n_warps; pend=[0]*n_warps; left=[iters]*n_warps
    comp_left=[0]*n_warps; waiting=[False]*n_warps; issued=idle=0
    cyc=cursor=0
    while any(l>0 for l in left):
        got=False
        for _ in range(n_warps):
            w=cursor%n_warps; cursor+=1
            if left[w]==0 or nxt[w]>cyc: continue
            if waiting[w]:
                if pend[w]>cyc: continue
                waiting[w]=False; comp_left[w]=comp
            if comp_left[w]>0: comp_left[w]-=1
            else:
                waiting[w]=True
                pend[w]=cyc+latency+((w*13+(iters-left[w])*7)%jitter)-jitter//2
                left[w]-=1
            nxt[w]=cyc+1; issued+=1; got=True; break
        if not got: idle+=1
        cyc+=1
    return cyc, issued, idle

print(f"\n延迟隐藏：1 发射口/周期、每 warp 只允许 1 个 load in flight、"
      f"延迟 400 周期、每次 load 后 8 条计算")
print(f"{'驻留 warp':>9} {'occupancy':>10} {'仿真 IPC':>9} {'端口空闲':>9}")
for W, occ in ((8,'12.5%'),(16,'25%'),(32,'50%'),(48,'75%'),(64,'100%')):
    cyc, issued, idle = simulate(W)
    print(f"{W:>9} {occ:>10} {issued/cyc:>9.3f} {idle/cyc:>9.0%}")

三、练习#

  1. 实现：给 occupancy 增加 blocks_per_sm 上限之外的第五个限制——"每块的 shared memory 若有 carveout 限制（例如静态分配最多 48 KB，更大需显式 opt-in）"，用 48 KB 重跑 32 KB/块那一组，说明限制因素是否改变。
  2. 解释：为什么"每线程 17 个寄存器"与"每线程 24 个寄存器"可能给出完全相同的 occupancy？把 REG_GRAN 从 8 改成 1 再跑一次，说明差异来自哪里。
  3. 对比/验证：把延迟从 400 改成 200、计算从 8 改成 16，重跑仿真。在同样的 occupancy 下吞吐提升了多少？用"延迟/计算比"解释这个结果，并说明它对"要不要为了 occupancy 压寄存器"的启示。
  4. 思考：一个 GEMM kernel 在 25% occupancy 下达到了 90% 的 HBM 带宽。你会去调 __launch_bounds__ 提高 occupancy 吗？写出你的判断依据（需要看哪两个指标、什么条件下才值得动手）。
