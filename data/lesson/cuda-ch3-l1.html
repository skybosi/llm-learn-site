寄存器/共享内存/L1-L2/HBM：容量、带宽、延迟的数量级#

第 2 章回答了「谁来执行」。但同一个 kernel 换个数据布局就能快好几倍，瓶颈常常不在算，而在数据住在哪一层、搬一次多贵。本课给存储层次（memory hierarchy）建立三个坐标——容量、带宽、延迟，把每层的量级写清楚，并推导「延迟必须靠并发掩盖」这条贯穿全书的公式。全程不需要 GPU。

一、概念讲解#

1. 三个坐标：容量、带宽、延迟#

描述一层存储至少要三个量：

  • 容量（capacity）：能装多少数据。
  • 带宽（bandwidth）：单位时间搬多少字节，常用「每 SM 每周期字节数」或 GB/s、TB/s。
  • 延迟（latency）：一次访问从发出到数据可用要等多久，单位是周期或纳秒。

三者必须一起看：共享内存每 SM 只有几十 KB，却每周期供 128 字节、延迟几十周期；显存有几十 GB，但每 SM 平均分到的带宽与延迟都差一个数量级。下表是量级参照（近似值，随架构变化，以官方 Compute Capabilities 表为准）：

层级 物理位置 容量量级 带宽量级 延迟量级
寄存器 Register 每 SM 的寄存器堆，线程私有 每 SM 约 64K 个 32 位寄存器（≈256 KB）；每线程上限 255 个 每周期数百字节（多流水线并行读） 约 1 个周期
共享内存 Shared / L1 每 SM 上，二者物理同源 每 SM 几十 KB ~ 300 KB 量级，可在两者间划分 每周期 128 字节（32 bank × 4 字节） 几十个周期
L2 全卡共享（所有 SM 共用） 数 MB ~ 数十 MB（l2CacheSize 可查） 每周期数百字节 × 时钟 约 200 个周期
显存 HBM/GDDR（全局内存） 板卡上的 DRAM 数十 GB 全卡数 TB/s（型号差别大） 数百个周期

别背这些数，要会查：Compute Capabilities 附录按架构列规格，运行时可用 cudaGetDeviceProperties 读 sharedMemPerMultiprocessor、regsPerMultiprocessor、l2CacheSize。

2. 为什么必须分层：这是工艺决定的#

片上 SRAM 存 1 bit 要 6 个晶体管，DRAM 只要 1 个晶体管加 1 个电容：位密度与成本差几十倍，所以片上存储只能到 MB 量级，显存能到几十 GB。于是「把数据搬到更近的地方」的优化本质都是拿容量换时间——第 4 章的 tiling 就是显式做这笔交易。

3. 谁分配、谁可见、活多久#

不同层的可编程性差别很大：

层 谁分配 可见范围 生命周期
寄存器 编译器 单个线程 一次 kernel
共享内存 程序员（__shared__ 或 launch 第三个参数） 一个 block 内所有线程 一次 kernel
L1 硬件（与共享内存共用物理空间） 一个 SM 硬件管理
L2 硬件 全卡 硬件管理
全局内存 程序员（cudaMalloc） 整个 grid，也可拷回 host 应用

两个最容易忽略的点：

  1. 共享内存与 L1 是同一块物理存储（unified data cache）：多用共享内存就等于少给 L1，而 cudaFuncSetCacheConfig 只是偏好，官方明确说它不保证被采纳。
  2. local memory 的 "local" 指作用域而非位置：它物理在显存里，延迟与带宽和全局访存同档。寄存器不够时编译器把变量 spill（溢出）到那里，性能随之下滑——所以「寄存器越多越好」是错的。

4. 延迟靠并发掩盖：在飞行字节 = 带宽 × 延迟#

要把内存通道打满，必须让足够多请求同时在路上。设峰值带宽 B（字节/秒）、延迟 L（秒），稳定状态下在飞行中的数据量为 W = B × L。

示例参数 B = 2 TB/s、L = 500 ns → W = 1 MB；一次 warp 的合并访存带来约 128 字节在飞行，维持峰值就需约 8000 个 warp 同时等数据。单个 SM 只有几十个 warp，所以得靠「多 SM × 每 SM 多 warp」一起凑，并让每线程发出多个互不依赖的访存（ILP，指令级并行；双缓冲）。

这就是第 2 章 occupancy（占用率）的真正意义：occupancy 不是目的，足够多的并发访存才是目的。

5. 每 SM 的带宽账本：片上为什么贵#

把全卡带宽摊到每 SM：示例参数（HBM 2 TB/s、100 SM、1.2 GHz）下，显存每 SM 每周期约 17 字节，共享内存 128 字节，比值约 8:1。

所以「把复用数据搬进共享内存」通常划算：复用 2 次以上，省下的全局流量就超过搬运成本；只读一次就搬是纯亏。判断访存还是计算瓶颈看算术强度（arithmetic intensity，每读入一字节做多少次运算），第 4 章展开成 roofline 分析。

6. 常见坑#

  • 以为「用了共享内存就快」：不减少全局流量，只增加搬运与同步。
  • 把 L1 与共享内存当两份资源：物理同源，此消彼长。
  • 寄存器越多越好：寄存器压力压低 occupancy，甚至 spill 到显存。
  • 背数字：同一段代码跨架构能差一个量级，查官方表或现场读。

二、可运行代码示例#

这段只依赖 numpy：先在本机量出「带宽台阶」，再算延迟隐藏需要多少并发。它测的是 CPU 存储层次，方法可搬到 ncu 上复现。

# ---- 在 CPU 上把"存储层次"量出来（只需要 numpy）----
import time
import numpy as np

def timed(fn, reps):
    fn()                                     # 预热：首次触碰页面、让数据进 cache
    best = float('inf')
    for _ in range(reps):
        t0 = time.perf_counter()
        fn()
        best = min(best, time.perf_counter() - t0)
    return best

def copy_bandwidth(nbytes, reps):
    """顺序拷贝：读 n 个 float64 + 写 n 个，流量按读+写算 → GB/s"""
    n = max(nbytes // 8, 1)
    a = np.ones(n)
    b = np.empty_like(a)
    t = timed(lambda: np.copyto(b, a), reps)
    return 2.0 * n * 8 / t / 1e9

def read_bandwidth(nbytes, reps):
    n = max(nbytes // 8, 1)
    a = np.ones(n)
    return n * 8 / timed(lambda: a.sum(), reps) / 1e9

def gather_bandwidth(nbytes, reps=5):
    """随机 gather：读数据 + 读下标，流量按两份算"""
    n = max(nbytes // 8, 1)
    a = np.ones(n)
    idx = np.random.default_rng(0).integers(0, n, n)
    return 2.0 * n * 8 / timed(lambda: a[idx].sum(), reps) / 1e9

print('工作集      顺序拷贝(GB/s)')
for k in range(12, 28, 2):                   # 4 KB → 64 MB
    nb = 1 << k
    reps = max(8, min(3000, int(1e8 / nb)))
    print(f'{nb/1024:>7.0f} KB {copy_bandwidth(nb, reps):>16.1f}')

print()
print('工作集     顺序读   随机 gather   随机/顺序')
for nb in (1 << 22, 1 << 26):                # 4 MB、64 MB
    seq, rnd = read_bandwidth(nb, 10), gather_bandwidth(nb, 8)
    print(f'{nb/1024:>7.0f} KB {seq:>8.1f} {rnd:>13.1f} {rnd/seq:>11.2f}')

print()
print('带宽(TB/s) 延迟(ns) 在飞行字节(MB) 需要并发 warp 数(每次 128B)')
for bw_tbs, lat_ns in [(2.0, 400), (2.0, 700), (3.5, 500)]:
    inflight = bw_tbs * 1e12 * lat_ns * 1e-9
    print(f'{bw_tbs:>9.1f} {lat_ns:>9.0f} {inflight/1e6:>16.2f} {inflight/128:>20.0f}')

print()
print('示例：HBM 2 TB/s、100 个 SM、时钟 1.2 GHz')
per_sm = 2e12 / 100 / 1.2e9
print(f'  每个 SM 平均分到 {per_sm:.1f} 字节/周期；共享内存每周期 32 bank × 4 = 128 字节')
print(f'  片上 : 片外 ≈ {128/per_sm:.0f} : 1（示例参数下的量级）')

三点读法：

  1. 4 KB 反而最慢：数据量太小，调用固定开销占比过高，测不出存储速度——GPU 上「小 kernel 跑不出峰值带宽」同因。
  2. 1 MB 附近最高（约 133 GB/s），16 MB 掉到 68 GB/s：台阶位置即末级缓存容量，两侧高度比即两级带宽之比。
  3. 随机 gather 只有顺序读的 6%~17%：每个请求都要等延迟时，带宽就从「被预取掩盖」变成「被延迟限制」——这正是下一课与双缓冲要解决的问题。

三、练习#

  1. 实现：把 copy_bandwidth 的采样点加密到 32 KB / 64 KB / 128 KB / 256 KB / 512 KB，找出本机台阶位置；再解释为什么流式拷贝在 L1 边界看不到明显台阶。
  2. 解释：W = B × L 三个量的单位是什么？若延迟从 500 ns 变成 1 µs 而要维持同一带宽，在飞行字节数必须怎么变？
  3. 对比/验证：找出你所用架构的 sharedMemPerMultiprocessor、regsPerMultiprocessor、l2CacheSize（A：cudaGetDeviceProperties 打印，可选、需 GPU；B：查官方 Compute Capabilities 表），与上表量级对照并记录出处。
  4. 思考：共享内存为什么不做成整卡共享的一大块 SRAM？从「每周期 128 字节 × SM 数」与「容量-成本」两个角度各给一条理由。
