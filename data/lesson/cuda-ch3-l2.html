合并访存与对齐：一次访存能拿到多少有效字节#

上一课说显存延迟数百周期、每个 SM 平均只分到十几字节/周期。那么这十几字节真的能拿到吗？不一定：硬件搬运数据的最小单位不是 4 字节，而是 32 字节的扇区（sector）。32 个线程各要 4 字节时，地址凑得整齐就只搬 128 字节且全部有用；凑不齐就可能搬 1024 字节只用上 128。本课把它变成能手算的「有效字节率」，并用模拟器把常见访问模式的浪费量全部量出来。

一、概念讲解#

1. 一次访存到底搬多少：扇区与 cache line#

两个粒度必须分清：

  • 扇区（sector）：L2 与 L1/SM 之间搬运的最小单位，32 字节，也是计费单位；
  • cache line：L1 的一行是 128 字节，即 4 个扇区；DRAM 一侧按更长的 burst 取数，所以按行看有时更接近真实代价。

一个 warp 的 32 个地址先各自落到某个扇区上，落在同一扇区的多个线程只需搬一次。于是：

有效字节率 = 有用字节 / 实际传输字节 = 128 B / (扇区数 × 32 B)

连续访问的理想值是 4 个扇区（32 × 4 B = 128 B = 1 行），有效率 100%。这是最好的情况，也是所有布局优化的目标。

2. 常见形态：步长每翻一倍，有效率减半#

访问模式 覆盖扇区 传输字节 有效字节率
连续且对齐（stride 1 个 float） 4 128 B 100%
连续但起点偏移 4 B 5 160 B 80%
stride 2 个 float（8 B） 8 256 B 50%
stride 8 个 float（32 B） 32 1024 B 12.5%
stride 32 个 float（128 B） 32 1024 B（按行算 4096 B） 12.5%（按行 3.1%）
AoS：struct{float x,y,z;} 只取 x 12 384 B 33.3%
SoA：字段独立成数组 4 128 B 100%

规律很清楚：连续访问的扇区数 ≈ 覆盖跨度 ÷ 32；步长每翻一倍，扇区数翻一倍，有效率减半，直到每个线程各占一个扇区（warp 最多 32 个扇区）为止。到 stride 128 B 再往上，扇区数不再涨，但每个扇区落在不同的 cache line 上，按行计费时浪费还在放大——这就是「跨步访问」在 GEMM 转置读、卷积滑窗、稀疏访存里格外致命的原因。

3. 对齐：为什么偏移只多花一个扇区#

设 32 个 float 的连续访问起点偏移 o 字节，则它跨的扇区数是 4 + (o mod 32 != 0 ? 1 : 0)：只要不落在 32 字节边界上，就多搬一个扇区，有效率 80%。也就是说每次要多搬 1/4 的字节，连续访问的对齐损失上限就是 25%。

工程上要保证「每个线程访问的元素大小与地址对齐」（自然对齐，natural alignment）。cudaMalloc 返回的设备指针有对齐保证，实际踩坑多在自己造的偏移上：数组切片、结构体字段偏移、char* 指针运算、手工 reinterpret_cast。

4. AoS vs SoA：布局本身就是访存模式#

struct {float x, y, z;} p[N] 是 AoS（array of structs）。只取 p[i].x 时，相邻线程的地址隔了 12 字节，32 个线程铺开 384 字节、只用到 128 字节——有效率 33.3%。把它拆成三个独立数组（SoA，structure of arrays），同一个循环立刻回到 100%。

布局规则是「按同一 warp 同一时刻要用的字段来排」。另外，只读数据加 __restrict__ 与 const 能帮编译器选只读路径；但不要指望 texture 路径：官方文档已明确说明，在当前所有受支持的 GPU 上，纹理/表面访存对非纹理 load 不再提供额外性能收益。合并访存只能靠地址模式本身解决。

5. 边界线程与部分活跃的 warp#

模拟结果：32 个线程里只有 17 个活跃时，传输 3 个扇区（96 B）却只用 68 B，有效率 70.8%；活跃 24 个恰好落在扇区边界上，有效率仍是 100%。扇区按 8 个 float 对齐，活跃线程数落在扇区边界上才不浪费。

实践做法：block 尺寸取 32 的倍数；越界的线程直接 return，而不是让它去处理「剩余元素」；循环尾部让整个 warp 一起退出，避免出现「半个 warp 干活、半个 warp 空转还照样搬扇区」。

6. 常见坑#

  • 以为「每个线程读 4 字节 = 一次 4 字节传输」：计费按扇区。
  • 只看 cache line 不看扇区：行是取数单位，扇区才是计费单位。
  • 觉得步长「不大」就放松：stride 8 B 已经掉到 50%。
  • 忽略对齐：切片与字段偏移是最常见的来源。
  • 只算一次访存：循环里每次迭代都在浪费，代价要乘以迭代次数。

二、可运行代码示例#

下面这段纯 Python（只用标准库，装了 numpy 更好）把「32 个地址 → 扇区集合 → 有效字节率」算出来，覆盖连续、偏移、跨步、AoS/SoA、部分活跃五种情形。

# ---- 访存事务模拟器：一个 warp 的 32 个地址要搬多少字节 ----
SECTOR = 32          # 全局访存的最小传输单位：32 字节扇区
LINE   = 128         # L1 cache line：4 个扇区

def transactions(addrs_bytes):
    """返回本次 warp 访存覆盖的（扇区数, cache line 数）"""
    sectors = {(a // SECTOR) * SECTOR for a in addrs_bytes}
    lines   = {(a // LINE) * LINE for a in addrs_bytes}
    return len(sectors), len(lines)

def report(name, addrs_bytes, useful_bytes):
    s, l = transactions(addrs_bytes)
    print(f'{name:<26} 扇区 {s:>3} 行 {l:>3} 传输 {s*SECTOR:>5}B '
          f'有用 {useful_bytes:>4}B 有效率 {useful_bytes/(s*SECTOR)*100:>5.1f}%')

WARP, F = 32, 4      # 32 个线程，每线程取一个 4 字节 float
useful = WARP * F

report('连续（warp 天然对齐）', [i * F for i in range(WARP)], useful)
report('连续但起点偏移 4B',   [4 + i * F for i in range(WARP)], useful)
report('步长 2 字（stride 8B）',  [i * 2 * F for i in range(WARP)], useful)
report('步长 8 字（stride 32B）', [i * 8 * F for i in range(WARP)], useful)
report('步长 32 字（stride 128B）', [i * 32 * F for i in range(WARP)], useful)
report('AoS：取 vec3(12B) 的 x', [i * 12 for i in range(WARP)], useful)
report('SoA：取 x[] 连续（4B）', [i * 4 for i in range(WARP)], useful)

def min_sectors(addrs_bytes):
    return len({(a // SECTOR) * SECTOR for a in addrs_bytes})

print()
print('对齐实验：32 个连续 float，起始地址从 0 到 28 字节')
for off in range(0, 32, 4):
    a = [off + i * F for i in range(WARP)]
    print(f'  起始偏移 {off:>2}B → 扇区 {min_sectors(a)}  '
          f'有效率 {useful/(min_sectors(a)*SECTOR)*100:>5.1f}%')

print()
print('部分活跃的 warp（前 t 个线程有效，地址连续）')
for t in (32, 24, 19, 17, 16, 8, 1):
    a = [i * F for i in range(t)]
    print(f'  活跃 {t:>2}/32 → 扇区 {min_sectors(a):>2}  有用 {t*F:>3}B  '
          f'有效率 {t*F/(min_sectors(a)*SECTOR)*100:>5.1f}%')

三、练习#

  1. 实现：给模拟器加一个 float4 模式（每线程取 16 字节连续），验证 32 个线程共 512 字节 = 16 个扇区、有效率仍 100%；再说明它省下的到底是什么（提示：不是扇区，是请求数与指令数）。
  2. 解释：为什么 stride 8 B 的有效率是 50%，而 stride 32 B 掉到 12.5%？用「一个扇区装 8 个 float」这句话把两档串起来解释。
  3. 对比/验证：用 numpy 造 AoS（(N,3) 取一列）与 SoA（三个独立数组）两种布局，各做一次同规模求和并计时。GPU 上差距可达数倍，为什么在 CPU 上往往只有几十个百分点？
  4. 思考：如果只能改一处，你会先消除跨步还是先修对齐？给出定量依据（提示：比较两者的浪费比例上限）。
