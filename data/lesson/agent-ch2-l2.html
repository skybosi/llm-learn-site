ReAct 与 plan-execute 的取舍：何时该先规划、何时该边走边看#

这一节要解决什么#

循环的骨架定下来之后，第一个真正的设计选择就出现了：要不要在行动之前先规划？

两种极端形态：

  • ReAct（Reason + Act）：每一步都"想一下 → 做一个动作 → 看结果 → 再想"。不预先承诺任何计划。
  • plan-execute：先让模型输出一份完整计划（步骤列表），然后按计划执行，执行过程中原则上不重新规划。

实践中大部分讨论停留在"ReAct 灵活、plan-execute 稳定"这种口号层面。这一节要把它算清楚：

  1. 两者的期望步数 / 期望成本能不能写成公式？在什么参数下交叉？
  2. "先规划"的价值到底来自哪里？（答案不是"更聪明"，而是减少无效步数 + 避免局部最优）
  3. "计划过时"的代价怎么量化？什么时候先规划是纯浪费？
  4. 中间形态（receding-horizon planning，滚动规划）为什么在实践中胜出？

这是本章的计算题。学完你应该能对任何一个具体任务给出"该用哪种"的判断依据 —— 而且这个依据是一个可以估的量，不是感觉。

一、两种形态的严格描述#

先把两者写成可分析的算法，而不是风格描述。

ReAct（贪心逐步）

repeat:
    thought  = 模型看当前状态，决定下一个动作
    action   = 执行该动作
    obs      = 感知结果
until done

特征：每一步的最优性只在当前状态下定义。没有全局承诺，因此：

  • 好：环境一变，下一步自然适应（无需"发现计划过时"这个环节）。
  • 坏：没有全局视角 → 可能反复走"局部看似合理"的路（第 1 章机制二：局部最优吸引子）；且无法并行（下一步依赖上一步的结果）。

plan-execute（先规划后执行）

plan = 模型看任务，输出步骤列表 [s1, s2, ..., sk]
for s in plan:
    obs = 执行 s
    （原则上不重新规划；有的实现会在失败时补一个局部修复）

特征：承诺一份全局计划。因此：

  • 好：计划一旦正确，执行是照做，每一步的"决策难度"下降 → 单步错误率下降；且互不依赖的步骤可以并行。
  • 坏：计划可能与世界不符（过时、错、或本来就猜的）→ 整条计划白做；且错误会以"计划级"的粒度发生（不是某一步错，而是整条路错）。

一个关键的观察：plan-execute 把误差从"每步独立"变成了"一次性的计划级误差 + 执行误差"。这正是它在长任务上有优势的原因 —— 它缩短了需要模型做"开放决策"的次数。

回忆第 1 章的乘积 pn：如果 plan-execute 让 n 次"开放决策"变成 1 次"计划决策" + k 次"照做执行"（照做的 p 高得多），那么乘积的形状完全不同：

Pplan-exec​≈pplan​⋅pexeck​,pexec​≫preact​

这就是 plan-execute 的全部价值来源：不是模型更聪明，而是它需要"聪明"的次数变少了。

二、期望步数与成本：把两者算出来#

现在建立可比较的模型。定义：

符号 含义
k 任务的"关键动作序列"长度（真正必需的动作数，由任务决定）
a 每个动作的平均 token 成本（含决策与回填）
cp​ 一次规划调用的 token 成本（通常 cp​≈3∼8a）
pr​ ReAct 单步作出"正确且不重复"决策的概率
pe​ plan-execute 中"照做"的正确率（通常 pe​>pr​，因为决策被约束了）
pplan​ 计划整体正确的概率
u 每步发生"计划失效事件"的概率（环境变化、发现新约束）

2.1 ReAct 的期望步数#

ReAct 在每一步以 pr​ 做对、以 1−pr​ 做错。做错不会自动回退，但会产生无效步（重复查询、走错分支），并且要额外花步数回到正轨。用一个"有效步比例"来建模：需要的总步数 Nr​ 满足"其中 k 步有效、其余为无效步"，无效步的产生率与 1−pr​ 成正比：

E[Nr​]≈pr​k​⋅1+ρ1​

这个形式不够干净。换一个更好用的模型 —— 在"每一步只有一个正确动作"的假设下，ReAct 期望步数是"正确步 + 纠错步"。设每次错误需要平均 α 步才发现并纠正（α≥1，取决于反馈质量），则：

E[Nr​]≈k+α⋅k⋅pr​1−pr​​=k(1+αpr​1−pr​​)

读这个式子：当 pr​ 高（比如 0.98）且反馈快（α 小），ReAct 接近 k 步；当 pr​=0.8、α=3 时，E[Nr​]≈k(1+0.75)=1.75k —— 多花 75% 的步数。

E[costr​]≈a⋅k(1+αpr​1−pr​​)

2.2 plan-execute 的期望成本#

E[costp​]≈cp​+a⋅pe​k​+计划错误时的返工成本(1−pplan​)⋅R​​

其中 R 是整条计划作废后的重来成本（约等于 costp​ 本身乘以重试次数）。

关键点：plan-execute 的方差更大（要么全对、要么整条返工），而 ReAct 的成本随 k 线性平滑增长。这是后面"混合策略"的动机之一。

pr​ ReAct 期望步数 ReAct 成本 plan-exec 成本（pplan​=0.9，R=15） 谁更省
0.99 10.3 10.3 5 + 10.3 + 0.1·15 = 16.8 ReAct
0.95 11.6 11.6 16.8 ReAct
0.90 13.3 13.3 16.8 ReAct
0.85 15.3 15.3 16.8 接近

0.70 22.9 22.9 16.8 plan-exec

交叉点大约在 pr​≈0.85。这张表给了一个反直觉但正确的结论：

plan-execute 不是"更高级的做法"，它是"当你的单步决策不够可靠时，用来少做决策的补偿手段"。 如果你的 ReAct 单步已经很好（0.95+），先规划是纯浪费 —— 你花了 5 个单位的规划成本，换来一个本来也不需要的东西。

再换一个维度看：任务长度 k 的影响（固定 pr​=0.85，α=3）：

k ReAct 成本 plan-exec 成本（cp​=5, pplan​=0.9, R=1.5cp​+0.1k） 谁更省
3 5.3 5 + 3.1 + 0.1·(7.5+0.3)=8.9 ReAct
10 17.6 5 + 10.3 + 0.1·17.5 = 17.1 接近

两个交叉点合起来给出判据：

用 plan-exec 划算  ⟺  单步决策不可靠（p_r 低）  且  任务足够长（k 大）
用 ReAct 划算      ⟺  单步决策可靠                 或  任务短（k 小）

为什么"短任务不用规划"是硬道理：规划的固定成本 cp​ 与 k 无关。比如 k=3 时，cp​=5 已经超过了全部执行成本 —— 你在为一个 3 步的任务付一份完整计划的价钱。

三、"计划过时"：plan-execute 真正的软肋#

上面的模型里有一个被简化掉的东西：计划的有效期。计划是根据规划时刻的世界状态生成的，而世界会变。定义：

pstale​(t)=1−(1−u)t≈1−e−ut

即执行到第 t 步时，计划已经失效的概率。其中 u 是每步的"失效事件"概率（环境变化、发现新约束、上游数据变了）。

计划的有效半衰期（与第 1 章 n1/2​ 同构）：

t1/2​=ln(1−u)ln0.5​≈u0.693​

u（每步失效概率） 有效半衰期（步） k=30 时计划仍有效的概率
0.01 69 0.74
0.03 23 0.40
0.05 14 0.21
0.10 7 0.04

这张表是 plan-execute 的适用边界。当 u=0.05、任务 30 步时，先规划的计划有 79% 的概率在中途就过时了 —— 此时严格的 plan-execute（不重规划）几乎必然失败，而它比 ReAct 还贵（因为还要额外付 cp​）。

一个重要的设计结论："要不要规划"和"要不要重规划"是两个独立问题。 很多人把 plan-execute 理解成"规划一次，然后死板执行"，这在 u 大的任务里是最差的组合（贵 + 脆）。正确的问题顺序是：

  1. k 和 pr​ 是否支持规划（第二节的判据）？
  2. 如果是，u 是多少？→ 决定重规划的触发方式。

重规划的三个粒度#

一旦承认计划会过时，就必须选择重规划的粒度（这也直接是第 5 章第 3 节的主题，这里只给判据）：

粒度 触发条件 代价 什么时候用
整计划重来 计划失效事件 / 连续失败 高（丢掉已完成步的规划工作） 前提假设变了（任务的输入变了）
局部修补（替换/插入/删除若干步） 某步失败或发现新约束 低 默认选择：u 小、失败局部化
不改计划，只改执行（重试/换工具） 单步执行失败 极低 错误出在执行而非计划

判据：只在与"前提"有关的假设被推翻时才整计划重来。 如果失败只是"这一步的工具坏了"，重规划整条计划是浪费，而且会引入新的计划级误差 —— 重规划本身也是一次 pplan​ 的赌博，不能滥用。

四、中间地带：滚动规划（receding-horizon planning）#

两个极端都不好，好的设计在中间。借鉴控制理论里的 MPC（模型预测控制）：

每次只承诺未来 h 步（horizon），执行完这几步后重新规划，
但每次规划都用到"当前真实状态"（而不是规划时刻的状态）。

repeat:
    plan = 模型规划接下来 h 步（基于当前真实状态）
    执行 plan[0..h-1]
    （执行中收集真实结果）
    重新规划

为什么它胜出（三个原因，都可量化）：

  1. 控制计划过时。每次只承诺 h 步，计划失效概率降到 1−(1−u)h。取 h≤t1/2​ 就能把失效概率压在 50% 以下 —— 这是一个可算的 horizon 选择规则。
  2. 保留全局视角。相比纯 ReAct，它每次都看全局任务再规划 h 步，因此不会丢失"整体方向"（对抗局部最优吸引子）。
  3. 支持并行。在 h 步的窗口内，互不依赖的步骤可以并行执行 —— 纯 ReAct 做不到（每步都要等上一步的结果）。

窗口大小 h 的取舍（这是滚动规划唯一的调参）：

h 小（如 1） h 大（如 10）
退化成 ReAct，成本高、局部最优 计划过时风险高（1−(1−u)h）
适应性最好 并行度最好、规划调用最少
规划调用频繁（成本 ∝k/h⋅cp​） 规划调用少

最优 h 的平衡式（把两项成本相加后最小化）：

cost(h)≈规划调用成本hk​cp​​​+过时导致的纠错成本ak⋅(1−(1−u)h)⋅hα′​​​

对 h 求最小值（连续近似）给出一个可用的经验式：

h∗≈a⋅u⋅α′cp​​​

h∗≈a⋅u⋅α′cp​​​

这个式子的实用读法：h∗ 随 cp​ 增大而增大（规划贵 → 少规划几次），随 u 增大而减小（环境变得快 → 勤重规划）。举几个数（a=1,α′=2）：

cp​ u=0.01 u=0.05 u=0.10
3 h∗≈12 ≈5 ≈4
8 ≈20 ≈9 ≈6
20 ≈32 ≈14 ≈10

五、什么时候不该规划：三个反例#

除了"成本"这个理由，还有三个原则性的理由说明规划可能有害：

反例一：探索型任务。 如果任务本身就是"不知道会找到什么"（比如"研究一下这个库有没有性能坑"），那么规划的前提就不成立 —— 你无法在知道答案之前规划找答案的步骤。此时任何计划都是猜测的固化，它甚至有负面作用：模型会倾向于让证据符合计划（确认偏误的机械版本）。

反例二：强耦合的反馈链。 如果第 i+1 步的正确做法完全取决于第 i 步的具体结果（不是取决于"第 i 步成功/失败"，而是取决于"返回了什么样的数据"），那么预先规划就是在猜一个你还没看到的信息。判据：如果计划里出现"如果结果是 X 就走这个分支"这种占位，那说明这个任务需要 ReAct，而不是需要更详细的计划。

反例三：计划验证成本 > 执行成本。 有些任务里，验证"这个计划对不对"和直接做一遍的代价相当。此时先规划只是把成本翻倍。典型场景：廉价、幂等、可随意重试的只读查询。

三者的共同特征：规划的前提是"世界的结构在执行前就足够已知"。 不成立时，规划是有害的。

六、混合架构：实践中的默认答案#

把上面的分析合起来，得到一个分层的默认架构：

层 1：任务级规划（一次性，粗粒度）
      输出 3~7 个"子目标"，而不是具体动作 —— 子目标对世界变化的鲁棒性远高于动作
      ↓
层 2：每个子目标内：滚动规划 + ReAct 兜底
      · 正常情况下按 h 步窗口滚动
      · 计划连续失效 / 出现在计划外的新约束 → 退回 ReAct 自由探索
      ↓
层 3：如果 ReAct 也解决不了（如能力边界外） → 挂起求人（第 2.1 节的 Suspend）

这个架构的三条设计理由：

  1. 子目标层对世界变化不敏感。"把这份报告发给客户"这个子目标不会因为"PDF 转换工具换了"而失效；而"调用 convert_v1"这个动作会。规划越粗，越不容易过时 —— 这是"计划的有效半衰期"的直接推论。
  2. 窗口内滚动 = 用可控成本获得适应性。h 由第四节公式给出，而不是拍脑袋。
  3. ReAct 兜底是必要的，因为世界总有计划外的部分。一个只有 plan-execute 的 Agent 在遇到"计划外但可解"的问题时会整体失败，而 ReAct 能救回来。

取舍的诚实说法：混合架构的实现复杂度显著高于纯 ReAct（你要维护计划状态、失效检测、窗口推进、兜底切换）。所以：

能用纯 ReAct 搞定（p_r 高、k 小、u 小）    → 就用纯 ReAct，别上混合
计划稳定（u 小）且任务长（k 大）            → 纯 plan-execute + 局部修补就够
其余情况                                    → 混合

代码：一个可切换三种策略的循环#

from dataclasses import dataclass, field
from typing import Callable, Any, Optional

@dataclass
class StratConfig:
    """策略选择需要的全部参数 —— 设计决策：把它做成数据，方便按任务标定与 A/B。"""
    k: float = 10.0            # 任务关键动作数（可由历史轨迹统计）
    p_r: float = 0.85          # ReAct 单步正确率
    p_e: float = 0.97          # 照做单步正确率
    p_plan: float = 0.90       # 计划整体正确率
    u: float = 0.05            # 每步计划失效概率
    alpha: float = 3.0         # 发现并纠正一次错误所需步数
    c_plan: float = 5.0        # 规划调用成本（以'一次动作'为单位）
    a: float = 1.0             # 单次动作成本

def react_cost(c: StratConfig) -> float:
    """E[N_r] ≈ k(1 + α·(1-p_r)/p_r)；错误越多、纠错越慢，代价越大。"""
    return c.a * c.k * (1 + c.alpha * (1 - c.p_r) / c.p_r)

def plan_exec_cost(c: StratConfig) -> float:
    """
    规划固定成本 + 照做成本 + 计划错误时的返工（含重试一次）。
    设计决策：把'返工'显式计入 —— 只看成功路径会系统性低估 plan-execute。
    """
    exec_cost = c.a * c.k / c.p_e
    rework = (1 - c.p_plan) * (c.c_plan + exec_cost)
    return c.c_plan + exec_cost + rework

def optimal_horizon(c: StratConfig) -> int:
    """
    h* ≈ sqrt(c_plan / (a·u·α))（第四节的平衡式）。
    设计决策：h 是可算的，不是拍的 —— 规划越贵越少规划，环境变得越快越勤重规划。
    """
    import math
    h = math.sqrt(c.c_plan / max(c.a * c.u * c.alpha, 1e-9))
    return max(1, min(int(round(h)), 32))

def rolling_cost(c: StratConfig, h: int) -> float:
    """滚动规划：规划调用成本 + 过时导致的纠错成本。"""
    plan_calls = (c.k / h) * c.c_plan
    stale = 1 - (1 - c.u) ** h                    # 窗口内计划失效概率
    recover = c.a * c.k * stale * (c.alpha / h)
    return plan_calls + recover

def choose_strategy(c: StratConfig) -> dict:
    """
    判据（第二节 + 第三节）：
      · p_r 高 或 k 小  → ReAct（先规划是浪费）
      · u 大（计划半衰期 < k）→ 纯 plan-execute 在最差组合里
      · 否则             → 滚动规划（混合），h 由公式给出
    """
    r, p = react_cost(c), plan_exec_cost(c)
    half_life = (0.693 / c.u) if c.u > 0 else float("inf")
    if c.k <= 3 or (c.p_r >= 0.95 and c.k <= 15):
        choice = "ReAct"
    elif half_life >= c.k and c.k >= 10:
        choice = "plan-execute + 局部修补"
    else:
        choice = "滚动规划（混合）"
    h = optimal_horizon(c)
    return {"选择": choice, "ReAct成本": round(r, 1),
            "plan-exec成本": round(p, 1),
            "计划有效半衰期": round(half_life, 1),
            "建议窗口h": h, "滚动规划成本": round(rolling_cost(c, h), 1)}

# --------- 执行层：三种策略共用一个骨架 ---------
def execute(cfg: StratConfig, state, decide, act, plan, perceive,
            h: Optional[int] = None, budget: int = 40):
    """
    · plan=None 时退化为纯 ReAct（每步自由决策）
    · plan 给定且 h=None 时是 plan-execute（照单执行 + 局部修补）
    · plan 给定且 h 给定且 h<len(plan) 时是滚动规划（窗口执行后重规划）
    """
    cursor, step, window = 0, 0, (h or len(plan or []))

    while step < budget:
        # 滚动规划：窗口用尽 → 基于'当前真实状态'重新规划（不是规划时刻的状态）
        if plan is not None and cursor >= window:
            plan = plan(state)                # ★ 用当前状态重规划
            cursor = 0
        # 取下一步：有计划就照做，没有就让模型自由决策
        d = plan_step(plan, cursor) if plan is not None else decide(state)

        res = act(d, idem_key=f"{step}:{cursor}")
        state = perceive(state, res)          # 真实结果必须回流（闭环）
        step += 1

        if res.get("plan_invalid"):           # 失效检测：只在与'前提'相关时触发
            plan = plan(state)                # 整计划重来（谨慎使用）
            cursor = 0
        elif not res["ok"]:
            # ★ 局部修补优先：单步失败通常是执行问题，不该重规划整条计划
            plan = repair(plan, cursor, res)
            cursor += 1
        else:
            cursor += 1

        if done(state):                       # 终态判据在循环外（第 1 章定义第 ③ 条）
            return {"status": "done", "steps": step}
    return {"status": "budget", "steps": step}

def plan_step(plan, cursor): ...
def repair(plan, cursor, res): ...
def done(state): ...

三处关键设计决策：

  1. plan_exec_cost 把返工成本算进去。不这样做的成本模型会系统性偏向 plan-execute —— 因为它只看到"计划正确时的漂亮数字"。
  2. optimal_horizon 让 h 成为可计算的量。这是本节的实用产出：h 不该是超参数调出来的，它由 cp​/(auα) 决定。
  3. execute 里 plan_invalid 与 not ok 走不同路径：前者整计划重来，后者只 repair。这是"重规划粒度"判据的落地 —— 只有前提被推翻才重来整条计划。

练习#

  1. 算交叉点：某任务 k=25，pr​=0.88，α=2.5。计算 ReAct 与 plan-execute 的期望成本（cp​=6a，pe​=0.96，pplan​=0.85，返工算一次完整重来）。哪个更省？如果只把 pr​ 提到 0.94（其他不变），结论会反转吗？
  2. 计划半衰期：任务 k=40，每步失效概率 u=0.02。算出计划的有效半衰期；估"计划到结束时仍有效"的概率。然后回答：如果坚持纯 plan-execute（不重规划），你的成功率上限大约是多少（只考虑过时这一项）？
  3. 定 window：cp​=10a，u=0.04，α=2。用 h∗ 公式算出建议窗口。然后手算 h=2,5,10,20 时的 rolling_cost，验证公式给的 h∗ 确实接近最小值。若 u 变成 0.10，h∗ 怎么变？为什么方向是那样？
  4. 判据应用：下面四个任务，各该用 ReAct / plan-execute / 滚动规划里的哪个？给出具体参数估计（k,pr​,u 各约多少）和理由。 （a）"把这个 JSON 转成 CSV 并上传"（结构化、确定）； （b）"调研这三个竞品，各写一段分析，合成一份报告"（探索型、可并行）； （c）"实时对话中帮用户排查服务器故障"（环境在变、强耦合反馈）； （d）"给这 200 个文件逐个生成摘要"（高度重复、互相独立）。
  5. 反例构造：构造一个任务，使得先规划反而降低成功率（不只是更贵）。要求指出机制（提示：确认偏误 / 计划固化了错误的假设 / 掩盖了计划外的发现），并说明在混合架构里这个机制如何被避免。
  6. 设计：为任务 (b) 写出分层规划方案：3~7 个子目标（粗粒度，对世界变化鲁棒）+ 每个子目标内的窗口 h + 兜底条件。要求说明为什么你选的子目标粒度"不会因为工具更换而失效"。

小结#

  • plan-execute 的价值来源不是"更聪明"，而是"需要聪明的次数更少"：把 n 次开放决策变成 1 次计划决策 + n 次照做（pe​>pr​）。
  • 成本判据：ReAct 成本 ≈ak(1+αpr​1−pr​​)；plan-execute 成本 ≈cp​+ak/pe​+(1−pplan​)R。交叉点大约在 pr​≈0.85。
  • 两个条件同时成立才该规划：单步决策不可靠（pr​ 低）且任务足够长（k 大）。k≤3 时规划成本本身就已超过执行成本。
  • 计划会过时：pstale​(t)≈1−e−ut，有效半衰期 t1/2​≈0.693/u。先规划能不能用，取决于 t1/2​ 是否大于 k。
  • "要不要规划"和"要不要重规划"是两个独立问题；严格 plan-execute（不重规划）在 u 大时是最差组合（贵 + 脆）。
  • 重规划分三粒度（整计划 / 局部修补 / 只改执行），判据是：只在与"前提"有关的假设被推翻时才整计划重来。重规划本身也是一次 pplan​ 的赌博。
  • 滚动规划（MPC 式）是实践默认：每次承诺 h 步、用当前真实状态重规划。h∗≈cp​/(auα)​ —— 规划越贵越少规划，环境变得越快越勤重规划。
  • 三种情况不该规划：探索型任务（前提不成立）、强耦合反馈链（计划里需要"如果结果是 X"的占位）、计划验证成本 ≥ 执行成本。
  • 混合架构的分层理由：规划越粗越不容易过时 —— 子目标层对工具更换鲁棒，动作层不鲁棒。
