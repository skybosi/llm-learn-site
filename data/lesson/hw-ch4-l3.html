为什么 LLM 推理是访存密集#

这是本课程最"落地"的一课：把前面所有的工具——FLOPs、带宽、算术强度、Roofline——全部用上，回答一个现实问题：为什么大模型推理跑不快，以及怎样让它跑快。答案的核心是一句话：decode 阶段是访存密集的，速度由显存带宽决定，而不是算力。

一、概念讲解#

1. 推理的两个阶段#

LLM 生成文本分两步：

  • prefill（预填充）：一次性把整个 prompt 的所有 token 并行吃进去，算出每个位置的 KV；
  • decode（逐 token 生成）：自回归地一个 token 一个 token 吐出来，每生成一个 token 都要读一遍全部权重。

两个阶段的性能特征截然相反，这是理解推理性能的第一性事实。

2. decode：每 token 读一遍全部权重#

先算"每生成一个 token 要干多少活"。前向计算的浮点运算量约为 2P（P 为参数量，每个参数参与一次乘加）；而要搬的数据主要是权重，FP16 下为 2P 字节（再加少量 KV cache）。于是：

算术强度=2P 字节2P​=1 FLOP/byte

1 FLOP/byte！而 H100 的 ridge 高达 295。1 远远小于 295，所以 decode 死死落在 Roofline 的斜线（带宽限制）区上——它是彻头彻尾的访存密集。

3. decode 速度 ≈ 带宽 ÷ 每 token 字节数#

访存密集意味着耗时由带宽决定，于是 decode 的吞吐可以这样估：

tokens/s≈每 token 读的字节数显存带宽​

以 H100（3.35 TB/s）跑 70B 模型（FP16 权重 140 GB）为例：

140×1093.35×1012​≈24 tokens/s

这就是 H100 跑 70B FP16 的理论吞吐上限，和算力 989 TFLOPS 一点关系都没有——把算力翻十倍，这个数也不会变。

4. prefill：恰好相反，是计算密集#

prefill 一次处理 N 个 prompt token。浮点运算量是 2PN，但权重仍然只读一遍（2P 字节，N 个 token 共享）。于是强度约为 N FLOP/byte。当 N 较大（长 prompt 或大批量），强度轻松超过 ridge，prefill 变成计算密集，瓶颈回到算力。

5. 结论：优化方向全部指向"省字节"#

既然 decode 卡在带宽，那么提速的手段就非常清晰：

手段 效果
低精度量化（FP16→INT8/INT4） 字节数减半/减到 1/4，吞吐近似翻倍/翻四倍
增大 batch 一次读权重服务更多 token，摊薄权重读取
算子融合 省掉中间激活的读写
更高带宽的卡（如 H200） 直接提升带宽上限

这些正是业界推理优化（vLLM、量化、KV cache 优化等）背后的共同逻辑：既然卡在带宽，那就让每字节权重服务尽可能多的 token、让权重本身尽可能小。

二、可运行代码示例#

亲手算不同模型、不同精度、不同显卡上的 decode 吞吐，并把 prefill/decode 的强度对比画出来。

import numpy as np

# ---- 例 1：decode 吞吐 ≈ 带宽 ÷ 每 token 字节数 ----
def decode_tokens_per_sec(params, bytes_per_param, bw_tb_s, kv_bytes_per_token=0.0):
    bytes_per_token = params * bytes_per_param + kv_bytes_per_token
    return bw_tb_s * 1e12 / bytes_per_token

cards = {"A100 SXM": 2.0, "H100 SXM": 3.35, "H200 SXM": 4.8}
for name, bw in cards.items():
    tps = decode_tokens_per_sec(70e9, 2, bw)          # 70B FP16
    print(f"{name} 跑 70B FP16：理论 ≈ {tps:.0f} tokens/s")

# ---- 例 2：量化带来的吞吐提升 ----
print("\nH100 上 70B 模型不同精度：")
for label, bpp in {"FP16": 2, "INT8": 1, "INT4": 0.5}.items():
    tps = decode_tokens_per_sec(70e9, bpp, 3.35)
    print(f"  {label}: 权重 {70e9*bpp/1e9:.0f} GB -> ≈ {tps:.0f} tokens/s")

# ---- 例 3：小模型更快（字节更少） ----
print("\nH100 上 FP16 不同规模：")
for params, label in [(8e9, "8B"), (13e9, "13B"), (70e9, "70B")]:
    tps = decode_tokens_per_sec(params, 2, 3.35)
    print(f"  {label}: ≈ {tps:.0f} tokens/s")

# ---- 例 4：prefill 是计算密集，decode 是访存密集 ----
H100_RIDGE = 989.0 / 3.35
def phase_intensity(params, prompt_tokens):
    # decode：每 token 读一遍权重，强度≈1
    decode_ai = (2 * params) / (2 * params)
    # prefill：N 个 token 共享一次权重读取，强度≈N
    prefill_ai = (2 * params * prompt_tokens) / (2 * params)
    return prefill_ai, decode_ai

for N in [8, 128, 2048]:
    pre, dec = phase_intensity(70e9, N)
    print(f"prompt {N} token: prefill 强度≈{pre:.0f}, decode 强度={dec}；"
          f"H100 ridge≈{H100_RIDGE:.0f} -> "
          f"prefill={'计算密集' if pre > H100_RIDGE else '访存密集'}, decode=访存密集")

要点：例 1 到例 3 是一套完整的心算框架——decode 速度不看算力看带宽，量化和小模型都通过"减少每 token 字节数"来提速。例 4 直击核心：decode 的强度恒等于 1，永远是访存密集；prefill 的强度随 prompt 长度线性增长，长 prompt 下变成计算密集。这两句话，就是"为什么 LLM 推理是访存密集"的全部答案。

三、练习#

  1. 推导：验证"每 token 浮点运算 ≈ 2P"。提示：一个参数在矩阵乘里贡献一次乘法+一次加法（即 2 FLOP），前向时所有参数各参与一次。
  2. 计算：在 H200（4.8 TB/s）上，跑一个 8B 的 INT4 模型（权重约 4 GB），理论 decode 吞吐是多少 tokens/s？
  3. 对比：70B FP16 在 H100 上约 24 tokens/s。如果用 INT8（70 GB）和 INT4（35 GB），吞吐分别约多少？量化带来的提升是线性的吗？
  4. 思考：KV cache 也会随序列长度增长而占用带宽。序列越长，decode 每 token 要读的字节越多、吞吐越低。结合 decode_tokens_per_sec 里的 kv_bytes_per_token 参数，说说为什么长对话会拖慢生成。

为什么这样做？——理论推导#

"decode 是访存密集"这一结论，可以用 Roofline 模型三行推出来。这一节把推导补齐。

第一步：Roofline 模型的两个上限#

一块芯片能达到的实际算力，被两条"天花板"同时压着：峰值算力（每秒最多做多少 FLOP）和显存带宽（每秒最多搬多少字节）。可达到的算力满足：

可达 FLOP/s=min( π, β×AI )

其中 π 是峰值算力、β 是带宽，而算术强度（Arithmetic Intensity, AI）定义为单位字节数据上能做的浮点运算：

AI=字节数FLOPs​

两条线在 ridge point（拐点）ridge=π/β 处相交：AI 高于 ridge 时，受算力限制（水平线，计算密集）；AI 低于 ridge 时，受带宽限制（斜线，访存密集）。所以判断一个工作负载属于哪一类，只取决于它的 AI 落在 ridge 的哪一侧。

第二步：算 decode 的算术强度#

decode 阶段每生成一个 token，需要把全部权重读一遍再做一次前向。逐项数清楚：

  • FLOPs：一个参数在矩阵乘法里贡献一次乘法 + 一次加法，即 2 FLOP。前向时 P 个参数各参与一次，总计 ≈2P；
  • 字节数：FP16 下每个参数占 2 字节，读一遍全部权重就是 2P 字节（每 token 的 KV cache 与激活相对很小，可暂忽略）。

于是：

AIdecode​=2P 字节2P​=1 FLOP/byte

第三步：和 ridge 一比，结论落地#

以 H100 为例：峰值算力 989 TFLOPS，带宽 3.35 TB/s，ridge = 989/3.35≈295 FLOP/byte。decode 的 AI = 1，远远小于 295，因此它死死落在斜线（带宽限制）区。落入斜线区后，耗时只由"搬多少字节"决定：

时间=β字节数​⟹tokens/s≈每 token 字节数β​

时间=β字节数​⟹tokens/s≈每 token 字节数β​

时间=β字节数​⟹tokens/s≈每 token 字节数β​

算力项 π 从公式里消失——把算力翻十倍，吞吐一分不涨。这就是"推理优化 = 减少内存访问"的数学根源：量化（减字节）、增大 batch（一次读权重服务更多 token）、算子融合（省中间读写）、换更高带宽的卡，全部在动分母或摊薄分子，而不碰算力。

作为对照，prefill 一次吃进 N 个 token，FLOPs 是 2PN，但权重仍只读一遍 2P 字节，AIprefill​≈N。N 一大，AI 越过 ridge，prefill 就翻转到计算密集——同一条 Roofline，把两个阶段分到了两侧。

母原理连接：Roofline 是"木桶最短板"母原理（瓶颈分析）在硬件上的量化——实际性能被"算力"与"带宽"两条上限中更紧的那一条卡死。把它套到 decode 这个"读很多、算很少"的工作负载上，最短板立刻现形：卡在带宽。于是全部优化手段顺理成章地收敛到同一个方向——减少内存访问。
