CUTLASS / cuBLAS：什么时候该用库而不是手写#

前两课把"能写"补上了：手写 CUDA、Triton 都能出正确且不慢的算子。但工程上第一件该问的不是"怎么写"，而是"为什么觉得库不够用"。这一课拆开 CUTLASS 与 cuBLAS 的分层结构，给出四条能当场核对的选型判据。

一、概念讲解#

1. CUTLASS：把 GEMM 做成"可组合的分层模板"#

CUTLASS 的核心是一段分层阻塞的三重循环，每层对应 CUDA 执行模型的一层并发、存储层次的一层容量：

for cta_n / cta_m:                       ← threadblock 级并发（CTA tile 落 shared memory）
  for cta_k:                             ← mainloop：一次迭代=一个 stage（软件流水的单位）
    for warp_n / warp_m:                 ← warp 级并发（从 shared 取到寄存器 fragment）
      for warp_k:                        ← 在 CtaTileK 上完全展开（一个 k group）
        for mma_k / mma_n / mma_m:       ← Tensor Core 指令（mma.sync）
          mma_instruction(d, a, b, c)

三层 tile 各有明确职责：threadblock tile 决定从 global memory 搬多少（太大反而浪费在边界上，太小则 DRAM 带宽变瓶颈）；warp tile 决定 shared memory 的复用与 bank conflict；thread tile 决定寄存器内的复用。你手写时要自己拍的三组数字，在这里是 ThreadblockShape / WarpShape / InstructionShape 三个模板参数。

它的"工程增量"和你在第 4、5、6 章逐条打过照面：

  • epilogue 独立成阶段：MMA 的输出布局是为了算得快挑的，不适合直接写回 global memory；epilogue 让线程先通过 shared memory 交换数据，再合并写回——这也是融合激活/bias 的合法位置。
  • 软件流水线：threadblock tile 双缓冲 + warp fragment 双缓冲，把访存与计算重叠（第 4 课双缓冲的库化）。
  • threadblock rasterization：决定 CTA 与输出的映射顺序以提升 L2 复用（第 2 课在 Triton 里叫 GROUP_SIZE_M）。
  • split-K / sliced-K：M、N 小、K 大时用 K 维并行补足并行度——代价是多一个归约 kernel 与一块 workspace，下一节会算给你看。
  • 从 Hopper 起 CUTLASS 3.x 引入 warp specialization（producer/consumer warp group）与 tile scheduler，把第 5 课的 warp specialization 与第 4 课的 TMA 组合成库内默认路径。

2. cuBLAS / cuBLASLt：厂商调好的那一条路#

cuBLAS 是闭源但高度调优的 GEMM 实现，供应了列主序的经典 API；cuBLASLt 是它的轻量层：算法由启发式（heuristic）选择、支持 epilogue 融合、需要显式管理工作区，并且可以让你在若干候选算法里挑。使用它的三个必答题是：布局（cuBLAS 传统上是 column-major，与 PyTorch 的 row-major 约定不一致，需要转置或换 API）、workspace（大小请求与切分策略）、算法（默认启发式可能不是你形状上的最优）。

什么时候库会不如你？大致三类：形状极端（M 很小、K 很浅、batch 不规则）、融合超出它的 epilogue 菜单、需要非标准布局/精度组合。这三类恰好就是下一节决策函数的输入。

3. 四条判据：先分类，再决策#

  1. 形状：输出块数够不够铺满 SM？tile 补齐浪费多少？——这决定"库的 tile 是不是过大"。
  2. 融合：要融的算子是否在库的 epilogue 菜单里？不在就自己写（或 Triton）。
  3. 数据类型：fp16/bf16 库最全；fp8、int4 等低精度路径要看清支持矩阵。
  4. 布局/调度：需要自定义 tiling、persistent scheduler、非标准 stride 时，CUTLASS 才是对的层。

4. 三笔必须算清的账#

  • tile 利用率：M=1、N=4096、K=4096 用 128×128 的 tile，99.2% 的乘加落在补零 lane 上——无效计算放大到 128 倍（有效算术强度从 128 掉到 0.5 FLOP/B）。
  • 够不够铺满：把输出块数与 SM 数比。132 个 SM 时 4096×4096 有 1024 块（8 波，最后一波只剩 100 块），而 M=1 只有 32 块——整卡跑一排就没了。
  • 融合的经济学：单独一条 elementwise kernel 要读一遍 C、写一遍 C。以 4096×11008×4096 为例，融合把总流量从 376 MiB 降到 204 MiB（省下 172 MiB，约 54%），而且这部分收益与算力无关，纯粹是带宽。

5. 常见坑#

  • 拿 cuBLAS 的 TFLOPS 去比自己的小形状：库的启发式在标准大形状上接近峰值，小形状上可能选到不合适的 tile。
  • 忽略 split-K 的 workspace：它为并行度付的是"显存 + 一个归约 kernel"。
  • 在 cuBLASLt 上忘记 workspace 与布局约束：结果是静默走回退路径，看起来"库很慢"。
  • 用 CUTLASS 2.x 的教程去写 3.x 的代码：3.x 的 collective/builder 与 2.x 的 DefaultGemm 不是同一套抽象。
  • 手写只为了"可控"：目标形状在库的舒适区、也不需要额外融合时，手写通常只在维护成本上亏。

二、可运行代码示例#

下面的纯 Python 版本把四条判据实现成一个决策函数，并把三笔账（tile 浪费、铺满度、split-K workspace、融合收益）算成数字。不需要 GPU。

# ===== ch7-l3：什么时候该用库（cuBLAS/CUTLASS），什么时候该手写（纯标准库，无 GPU）=====
import math

# ---------- 1. 形状分类：tile 利用率才是第一道筛子 ----------
def classify(M, N, K, TM=128, TN=128, TK=64):
    bm, bn = math.ceil(M/TM), math.ceil(N/TN)
    tiles = bm * bn
    waste = 1 - (M*N) / (bm*TM * bn*TN)        # tile 补齐带来的无效计算占比
    k_steps = math.ceil(K/TK)
    if M*N <= TM*TN:            kind = "小方阵（单 tile 装得下）"
    elif M <= TM:               kind = "瘦长（解码期 / 小 batch）"
    elif K <= TK:               kind = "K 很浅（近似 outer product）"
    else:                       kind = "规整大方阵"
    return tiles, k_steps, waste, kind

print("[1] tile = 128x128x64 面对不同形状：输出块数、K 段数、补齐浪费")
print(f"{'M x N x K':>20} {'输出块':>7} {'K 段':>5} {'补齐浪费':>9}  类别")
for M, N, K in [(4096,4096,4096), (4096,11008,4096), (1,4096,4096), (16,4096,4096),
                (4096,4096,32), (128,128,128)]:
    t, ks, w, kind = classify(M, N, K)
    print(f"{f'{M}x{N}x{K}':>20} {t:>7} {ks:>5} {w:>8.1%}  {kind}")

# ---------- 2. 算术强度全账（含写回 C）+ 补零放大 → 有效算术强度 ----------
def intensity(M, N, K, TM, TN, elem=2, acc=4):
    """按第 4 章账本重数一遍，这次把写回 C 也算进去（roofline 的诚实口径）"""
    bm, bn = math.ceil(M/TM), math.ceil(N/TN)
    moved = bm*bn * K * (TM+TN) * elem + M*N*acc      # A/B 条带 + 写回 C
    flops = 2.0*M*N*K
    pad   = (bm*TM*bn*TN) / (M*N)                      # tile 内的无效 lane 也在做乘加
    return flops/moved, flops*pad/moved
print(f"\n[2] 含写回 C 的算术强度；括号里是『tile 内补零 lane 也参与计算』后的有效值")
print(f"{'shape':>18}" + "".join(f"{f'{tm}x{tn}':>20}" for tm, tn in [(64,64),(128,128),(256,256)]))
for M, N, K in [(4096,4096,4096), (4096,11008,4096), (1,4096,4096), (16,4096,4096), (128,128,128)]:
    cells = []
    for tm, tn in [(64,64),(128,128),(256,256)]:
        ai, eff = intensity(M, N, K, tm, tn)
        cells.append(f"{ai:>8.1f}({eff:>8.1f})")
    print(f"{f'{M}x{N}x{K}':>18}" + "".join(cells))

# ---------- 3. 够不够铺满：grid 深度与余数波 ----------
def waves(M, N, TM, TN, sm=132):
    tiles = math.ceil(M/TM) * math.ceil(N/TN)
    full = tiles // sm
    return tiles, full, tiles % sm, tiles/sm
print(f"\n[3] 以 132 个 SM 为例：需要多少个波次才铺满（余数波就是『最后一批 SM 闲着』）")
print(f"{'shape':>18} {'块数':>7} {'整波':>5} {'余数块':>7} {'波数(含余)':>10}")
for M, N, K in [(64,64,4096), (128,512,4096), (1,4096,4096), (16,4096,4096), (4096,4096,4096), (8192,8192,8192)]:
    t, full, rem, w = waves(M, N, 128, 128)
    print(f"{f'{M}x{N}':>18} {t:>7} {full:>5} {rem:>7} {math.ceil(w):>10}")

# ---------- 4. split-K：多出来的并行度要付 workspace ----------
def splitk(M, N, K, parts, TM=128, TN=128, elem=4):
    tiles = math.ceil(M/TM) * math.ceil(N/TN)
    grid = tiles * parts                       # partitionedK GEMM：每段 K 各出一批 block
    ws = tiles * parts * TM * TN * elem        # 部分和（fp32）落显存
    return grid, ws, ws*2                      # 归约 kernel 读+写
print(f"\n[4] split-K：用 K 维并行度换 workspace（fp32 部分和）与一个额外的归约 kernel")
print(f"{'shape':>18} {'parts':>6} {'grid':>8} {'workspace':>11} {'归约多搬':>10}")
for M, N, K in [(1024,1024,4096), (4096,4096,4096)]:
    for parts in (1, 4, 16):
        g, ws, red = splitk(M, N, K, parts)
        print(f"{f'{M}x{N}x{K}':>18} {parts:>6} {g:>8} {ws/2**20:>9.1f}MiB {red/2**20:>8.1f}MiB")

# ---------- 5. 融合的经济学：省下的正好是一次中间张量的读 + 写 ----------
def traffic(M, N, K, elem=2, fusable=True):
    gemm = (M*K + K*N)*elem + M*N*elem         # 主线：读 A/B，写 C
    extra = 2*M*N*elem if fusable else 0       # 独立 elementwise kernel：读 C + 写 C
    return gemm, gemm + extra
print(f"\n[5] 把激活/GELU/bias 融进 epilogue：省下一次 C 的读 + 写（纯带宽收益）")
print(f"{'shape':>18} {'不融合':>11} {'融合后':>10} {'省下':>10} {'相对收益':>9}")
for M, N, K in [(4096,11008,4096), (8192,8192,8192)]:
    g, gf = traffic(M, N, K)
    print(f"{f'{M}x{N}x{K}':>18} {gf/2**20:>9.1f}MiB {g/2**20:>8.1f}MiB {(gf-g)/2**20:>8.1f}MiB "
          f"{g/gf:>8.1%}")

# ---------- 6. 决策函数：把上面几条判据折成一个可核对的推荐 ----------
def recommend(M, N, K, batch=1, fuse="none", dtype="fp16", need_layout_control=False,
              TM=128, TN=128, sm=132):
    tiles, _, _, kind = classify(M, N, K, TM, TN)
    if need_layout_control:
        return "CUTLASS/CuTe DSL（要自定义 tile 与调度）"
    if batch > 1 and fuse != "none":
        return "CUTLASS grouped GEMM 或 Triton（融合 epilogue）"
    if batch > 1:
        return "cuBLAS strided-batched / torch.bmm"
    if tiles < sm or M <= TM:
        return "手写（或 Triton）：库的 tile 太大，grid 铺不满"
    if fuse != "none":
        return "cuBLASLt epilogue 融合，或手写 Triton 融合 kernel"
    if dtype in ("fp8", "int4"):
        return "cuBLASLt / CUTLASS（低精度路径更全）"
    return "直接调 cuBLAS"
print(f"\n[6] 决策函数在几个真实形状上跑一遍")
cases = [((4096,4096,4096), {}),
         ((1,4096,4096), {}),
         ((16,4096,4096), {}),
         ((16,11008,4096), dict(batch=16, fuse="silu")),
         ((8192,8192,8192), dict(fuse="bias+gelu")),
         ((4096,4096,4096), dict(dtype="fp8")),
         ((4096,4096,4096), dict(need_layout_control=True))]
for (M, N, K), kw in cases:
    print(f"    {f'{M}x{N}x{K}':>18} {str(kw):<36} → {recommend(M,N,K,**kw)}")

三处结论可以直接拿去用：

  • 第 2 段是选型的分水岭：4096×4096×4096 在 128×128 tile 下算术强度 62.1 FLOP/B（含写回 C 的诚实口径），足够越过一般数据中心 GPU 的 roofline 拐点；而 M=1 时只有 0.5 FLOP/B，补零 lane 把有效值放大了 128 倍这件事，说明这里的瓶颈根本不是矩阵乘——这是一个 GEMV/访存问题，该换公式而不是换 tile。
  • 第 3 段量的是"铺不铺得满"：M=1 时 32 块在 132 个 SM 上连一波都填不满；4096×4096 是 7 整波 + 100 块的余数波（约 8 波）。余数波的存在解释了为什么"同一形状换个 shape 就慢一截"。
  • 第 4 段是 split-K 的真价钱：1024×1024×4096 从 1 段开到 4 段，grid 从 64 涨到 256（终于铺满），但 workspace 从 4 MiB 涨到 16 MiB、归约 kernel 还要多搬 32 MiB。只有当"铺满"带来的收益大于这笔搬运时，split-K 才成立——而这笔账用上面几行就能算出来，不必先上卡。

三、练习#

  1. 实现：给 recommend 加一条判据——K 相对 M、N 极小（如 K ≤ 32）时推荐"把 K 维放进寄存器做外积，而不是走 GEMM 框架"。用第 6 章的 naive→tiling 账本说明理由，并把 4096×4096×32 的算术强度算出来。
  2. 解释：为什么 epilogue 要单独成阶段、而不是把 MMA 的输出直接写回？结合"MMA 的输出映射是按计算挑的、不适合合并写回"这一点，说明如果没有 epilogue，你的融合算子在正确性/带宽上会撞到什么。
  3. 对比/验证：用第 2 段与第 3 段的输出，在 4096×4096×4096 与 1×4096×4096 两个形状上分别算出"若换用 Triton 手写，应该把 BLOCK 取多大才既不浪费 tile 又能铺满 132 个 SM"，并说明两个形状的答案为什么差一个量级。
  4. 思考：假设你的算子形状完全在 cuBLAS 舒适区、也不需要额外融合，但团队坚持手写。请用本课的三笔账（tile 浪费、铺满度、融合收益）写出一份"不值得手写"的量化论证；再反过来给出一个"值得手写"的真实场景。
