成本核算与降本#

前面两课分别解决了"省资源"（量化）和"榨吞吐"（批处理）。但真正决定一个推理服务赚不赚钱的，是最后这道算术题：花出去的 GPU 钱，换回了多少 token，每百万 token 的成本是多少，以及能不能再降。这一课建立一套可复用的成本核算模型，并把前面的优化手段串成一张"降本清单"。

一、概念讲解#

1. 推理成本几乎就是 GPU 时间#

推理服务的成本构成里，GPU 占绝对大头（通常 80% 以上），其余是 CPU/内存/网络/存储和运维人力。所以核算的起点永远是GPU 单价 × 使用时长，再把"时长"折算成"服务了多少 token"。核心公式：

每百万 token 成本=吞吐（token/秒）×3600GPU 单价（元/小时）​×106

举个数：一张 H100 按 40 元/小时算，如果它稳定跑出 3000 token/s，则每百万 token 成本 = 40 ÷ (3000 × 3600) × 1,000,000 ≈ 3.7 元。如果同样的卡只跑出 1000 token/s（参数没调好或负载不满），成本立刻变成约 11 元——吞吐差 3 倍，单位成本就贵 3 倍。

2. 利用率：最容易忽略的隐性成本#

上面公式隐含了一个假设：GPU 一直满负载。现实中 GPU 大量时间在空转——夜里没人用、按峰值买了却只在高峰忙。于是有了第二个关键概念：

有效单价=利用率GPU 单价​

一台 40 元/小时的卡，如果利用率只有 25%，你实际为"每个有用的 token"付的是 160 元/小时。闲置 GPU 是推理服务最大的隐性浪费，比任何量化方案都"贵"。

3. 计费模式：按需、预留、抢占#

云厂商提供三种 GPU 计费，本质是"价格 vs 稳定性"的取舍：

模式 单价 特点 适合场景
按需（on-demand） 高 随时可用，随时释放 突发、不可预测流量
预留（reserved） 中（省 30~60%） 承诺 1~3 年 稳定的基线负载
抢占/竞价（spot） 低（省 60~90%） 可能被随时回收 离线批处理、可重试任务

一个成熟的降本策略是分层：用预留实例扛基线负载，用按需扛高峰，用 spot 跑离线评测、数据合成、批量摘要这类"不着急、可重试"的任务。

4. 降本三板斧（把前面所有课串起来）#

  1. 选对量化：INT4/FP8 让同样一张卡装下更大模型或更高并发 → 单位吞吐成本下降（上一课第 5 章 l1）；
  2. 榨干吞吐：调好批处理参数、开 prefix caching、开 chunked prefill → 同样的卡每秒多出 token（第 5 章 l2 与推理优化课）；
  3. 用对计费 + 弹性伸缩：预留打底、spot 削峰填谷、低谷缩容到 0 → 把利用率从 25% 拉到 80%。

三者相乘，往往比单点优化降幅大得多：量化省 40%、吞吐翻倍省 50%、利用率翻倍省 50%，叠加后单位成本可降到原来的六分之一以下。

5. 容量规划与盈亏#

规划时先估两个数：峰值吞吐需求（QPS × 平均输出 token 数）和单位成本红线（每百万 token 不能超过多少元）。用公式反推需要几张卡、什么计费组合，再和"不降价就赔钱"的红线比对，决定是否值得做更强的量化或裁剪。

二、可运行示例#

示例 1：算每百万 token 成本#

# -*- coding: utf-8 -*-
# 从"GPU 单价 + 吞吐"直接算出每百万 token 成本
def cost_per_million_tokens(gpu_price_per_hour, tokens_per_second):
    tokens_per_hour = tokens_per_second * 3600
    cost_per_token = gpu_price_per_hour / tokens_per_hour
    return cost_per_token * 1_000_000

scenarios = [
    ("FP16 未调优", 40.0, 1000),     # 40元/小时，1000 token/s
    ("FP16 调优后", 40.0, 3000),
    ("INT4 + 调优", 40.0, 6000),     # 量化后同卡吞吐翻倍
]
for name, price, tps in scenarios:
    c = cost_per_million_tokens(price, tps)
    print(f"{name:>12}: {c:6.2f} 元/百万token")

示例 2：把利用率算进有效单价#

# -*- coding: utf-8 -*-
# 闲置 GPU 会显著抬高"有效单价"
def effective_price(gpu_price, utilization):
    return gpu_price / utilization

for util in [1.0, 0.5, 0.25]:
    print(f"利用率 {util*100:>3.0f}% 时，40 元/小时的卡，有效单价 = "
          f"{effective_price(40.0, util):6.1f} 元/小时")

你会看到：利用率 25% 时，有效单价飙到 160 元/小时——先把空转的卡填满，比换任何更便宜的卡都划算。

示例 3：计费组合的成本对比#

# -*- coding: utf-8 -*-
# 同一份负载，三种计费策略的月成本对比
def monthly_cost(gpu_price, n_gpus, hours_per_month=730):
    return gpu_price * n_gpus * hours_per_month

# 假设基线需 4 张卡常驻，另有峰值溢出与离线任务
on_demand_only = monthly_cost(40.0, 4)                       # 全按需
reserved_base  = monthly_cost(22.0, 4)                       # 预留(约55折)打底
# 混合：2 张预留打底 + 峰值 2 张按需(每天只跑 4 小时) + spot 跑离线(约 1 折)
mixed = (monthly_cost(22.0, 2)
         + monthly_cost(40.0, 2) * (4 / 24)
         + monthly_cost(4.0, 2) * (8 / 24))

print(f"全按需        : {on_demand_only:>9,.0f} 元/月")
print(f"全预留        : {reserved_base:>9,.0f} 元/月")
print(f"混合(预留+按需+spot): {mixed:>9,.0f} 元/月")

三、练习#

  1. 用示例 1 的公式，把你的实际吞吐代入，算出当前每百万 token 成本；再把吞吐乘 1.5（假设优化后），看成本降到多少，量化"调优的 ROI"。
  2. 把示例 2 的利用率从 25% 提到 80%，计算有效单价的变化，说明为什么"弹性伸缩到 0"是降本的关键。
  3. 设计一个三层的计费组合：给"在线对话、离线批处理、评测跑分"三类任务各选一种计费模式，并说明理由。
  4. 思考：如果单位成本红线是"每百万 token ≤ 2 元"，而当前成本是 3.7 元，列出你能用的所有降本手段，并估算叠加后能否达标。
