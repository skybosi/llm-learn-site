一、连续批处理落地需要哪几件机制#

1.1 三个机制，缺一不可#

"连续批处理"在论文里是一句话（"每个 step 重新组 batch，完成的请求立刻退出、等待的请求立刻进入"），落地要三件东西：

机制 解决的问题 不给它会怎样 量
准入控制 谁能进 batch 请求全部涌入 → KV 爆、所有请求一起变慢 队列上限 Qmax​、KV 上限 Lkv​
token 预算 一个 step 算多少 token step 时间不定 → TPOT 不可预测、p99 失控 r token/step
服务顺序 预算给谁 长请求堵住短请求 / 短请求饿死长请求 FIFO / chunked / SJF

为什么"token 预算"是核心而不是"batch size"：因为 prefill 的 token 与 decode 的 token 成本不同但共用同一块算力。如果按"batch size"（请求数）分配，一个 8000 token 的 prefill 和一次 decode 会被当成同等的两票，step 时间就会抖动 100 倍。按 token 预算分配，step 时间近似恒定：

Tstep​≈吞吐率(token/s)r​⟹TPOT≈Tstep​ (每 step 每请求一个 token)

r=1024 token/step, Tstep​=8.6 ms⟹有效算力=0.00861024​=119,070 token/s

这就是本节所有账的"汇率"：1 token ≈ 8.6/1024 ms 的算力。

1.2 为什么必须"按 token"而不是"按请求"：一个数值算例#

设一个 step 里有 8 个 decode 请求（各 1 token）和 1 个 8000 token 的 prefill：

按请求数分配（batch=9）：这个 step 要吃 8 + 8000 = 8008 token 的算力
                          → step 时间是正常 step 的 8 倍
按 token 预算分配（r=1024）：8 个 decode（8 token）+ prefill 分到 1016 token
                          → 那个 8000 token 的 prefill 要 8 个 step 才做完

两者付出的总时间几乎一样（8008 token 的算力都要付），区别是：

按 token 预算⇒这一步里所有人的 TPOT 不变（可预测）;按请求数⇒长 prefill 到达时全体 TPOT 抖动​

这就是 TPOT p99 与 TPOT p50 的差从哪来的。工程结论：token 预算不是为了更快，而是为了让 TPOT 可预测。

三条可算的读法：

  1. 吞吐几乎不变（同一 token 预算下 11,981 / 12,732 / 12,757 tok/s）。所以"调度提升吞吐"是错的说法 —— 调度改变的是分位，不是总量。任何声称"换了调度器吞吐涨 30%"的度量，一定是顺带把 batch 或 KV 配额改了。
  2. SJF 把短请求 p99 压到 34.4 ms（唯一不随 λ 增长的），代价是长请求最大等待 1.1 s。这是一个零和的尾延迟交换：短请求的尾↔长请求的尾。所以"公平"在这里有一个精确的价格。
  3. 分块（chunk）不是白拿的：它让端到端 p50 从 8.6 涨到 34.4 ms（prefill 被切成 4 段才出首 token），换来"长请求最大等待"可控。它的收益要在 §1.4 的极端场景才显现。

  1. 它救不了 KV 天花板：拒绝数（910 → 828、1145 → 1135）几乎不动，因为那是 Lkv​/L 决定的，与顺序无关。把这两件事混在一起调，会得出"分块没用"或"分块万能"两种相反的错结论。

二、预算恒等式：攒批能攒到多大#

2.1 三个上限，谁先拐#

每个 step 的 token 预算 r 要同时付两笔账：

prefill 需求λ⋅Pˉ​​+decode 需求b⋅1​​≤预算r​​

其中 b 是这一 step 的 batch（每个 running 请求 1 个 token）。注意 λ 的单位是 req/s，Pˉ 是平均 prompt 长度（含缓存未命中的部分）。本节算例（r=1024 token/step、decode 预留 35%）：

λ（req/s） Pˉ prefill 需求（tok/step） decode 预算 需 b 合计 够？
4.0 600 21 358 358 379 是
8.0 600 41 358 358 400 是
8.0 1500 103 358 358 462 是
12.0 600 62 358 358 420 是
8.0 3000 206 358 358 565 是

这张表要说的是一件反直觉的事：在这组参数下 prefill 需求（21～206）远小于 decode 需求（358）。原因是 λPˉ 的单位错了 —— 它要乘上 Tstep​：

λPˉ⋅Tstep​=8×600×0.0086=41 token/step

所以判据的正确形式是：

λPˉTstep​+b≤r​⟺λPˉ+Tstep​b​≤Tstep​r​=算力（token/s）

代入数字：λPˉ=4,800 token/s，b/Tstep​=358/0.0086=41,628 token/s，合计 46,428 ≤ 119,070。decode 占了 90%。

在中等并发下，token 预算的绝大部分被 decode 吃掉，而不是 prefill​

这条结论决定了"加算力"能不能救 TTFT：如果 decode 占了 90% 的预算，那么把算力翻倍只能让 prefill 的可用预算从 10% 涨到 55%——TTFT 会改善，但 TPOT 不变。 反过来，如果 load 很低（batch 小），预算被 prefill 主宰，此时"加算力"直接改善 TTFT。

2.2 三个上限的先后#

上限 形式 谁先拐 本节参数
token 预算 b≤r/(1+λPˉTstep​/b) 低 KV 时先拐 b≲358
KV 容量 b≤Lkv​/(Pˉ+Oˉ) 长上下文时先拐 120,000/(600+120)=166
调度队列 Q≤Qmax​ 过载时先拐 由准入定

本节参数下 KV（166）比 token 预算（358）更紧，所以实测平均 batch 是 179.9（FIFO整段 @ λ=96）—— 正好在两者之间。这就是"平均 batch"这个数字为什么不能单独看：它同时被两个上限夹着，报这个数时必须说清"哪一个在 binding"。

2.3 队列上限与拒绝：一个可算的准入判据#

过载时唯一的正确动作是拒绝（而不是排队）。准入判据是"排队时间不超过 SLO 预算"：

Wq​≈吞吐Q​⟹Qmax​=吞吐⋅(TSLO​−Tservice​)

代入（吞吐 13,425 token/s ÷ 720 token/请求 ≈ 18.6 req/s、TSLO​=5 s、Tservice​≈1.1 s）：

Qmax​≈18.6×(5−1.1)≈73 个请求

注意 Qmax​ 是一个"随负载变化的量"：它应由准入器动态计算，而不是配一个常数。用常数队列上限的系统在负载上升时会突然从"轻微排队"跳到"大批超时"（本节的 λ=160 行：拒绝 1568 个）。

三、缓存：前缀复用的收益落在哪个指标上#

3.1 两级模型：命中概率 × 命中长度#

把"前缀命中"拆成两个独立的问题，因为它们的优化手段不同：

省下的 prefill token=命中概率h​​×命中的最长公共前缀长度Llcp​​​

命中率 h 命中长度 节省 prefill TTFT 节省 剩余重算 TTFT 剩余
0.50 2000 1000 tok 83.3 ms 1000 tok 83.3 ms
0.70 2000 1400 tok 116.7 ms 600 tok 50.0 ms
0.80 2000 1600 tok 133.3 ms 400 tok 33.3 ms
0.90 2000 1800 tok 150.0 ms 200 tok 16.7 ms

（prefill 速率 12,000 token/s）

三条读法：

  1. 收益与 h 线性、与 Llcp​ 线性。所以"命中率从 80% 提到 90%"和"命中长度从 2000 提到 2250"是等价的收益。这个等价关系是缓存调优的坐标系。
  2. TTFT 的节省与后续 prompt 长度无关。所以对短请求，缓存能把 TTFT 砍掉一大半（甚至 90%）；对长请求只是"少了一段"。缓存天然偏心短请求 —— 这与 SJF 偏心短请求的方向一致，两者叠加会让长请求的体验更差（第 4 节的可观测性会暴露这一点）。
  3. Pˉ 在预算恒等式里应该是"未命中的那部分"：Pˉeff​=Pˉ−hLlcp​。缓存直接改变 §2.1 的 prefill 需求项 —— 这是缓存与调度在同一个不等式里的接口。

3.2 缓存划不划算：盈亏平衡命中率 h∗#

缓存不是免费的：它占的显存本来可以放 KV。所以判据是：

每请求省下的卡秒h⋅pLlcp​​​​≥每请求分摊到的槽位损失λ⋅W占槽比​​​

其中 W 是该请求在系统里的驻留时间（Little 定律：活跃请求数 =λW）。解出

h∗=Llcp​/p占槽比/(λW)​​

h∗=Llcp​/p占槽比/(λW)​​

三条可算的结论（这就是"落地条件"）：

  1. 缓存长度 Llcp​ 越长，门槛越低：同为 2,000 token 显存、λ=100，Llcp​ 从 2,000 涨到 8,000 时 h∗ 从 37.3% 掉到 9.3%。
  2. 到达率 λ 越高，门槛越低：λ 从 50 到 200，h∗ 降到 1/4（74.5% → 18.6%）。高负载下缓存更值钱 —— 因为它省下的 prefill 算力更稀缺。
  3. 缓存占的显存越多，门槛越高：2,000 → 6,000 token 时 h∗ 从 37.3% 涨到 6.7%（因为 Llcp​ 也涨了，净效果仍是降，但占槽成本涨得更快）。

3.3 命中率达到多少才"正常"：一个参照系#

h 不是可以直接设定的——它由负载的前缀重合度决定。三个典型负载：

负载类型 前缀重合结构 典型 h 缓存该不该开
单租户 + 固定 system prompt 全部请求共享 2000~8000 token 前缀 0.8~0.95 必开（h∗≈ 10~37%）
多轮对话 每轮共享上一轮的完整历史 0.5~0.8（轮内高、轮间低） 开，但按会话分池
少样本 / RAG 模板共享、示例与检索结果不同 0.2~0.5（只有模板段命中） 看 h∗，常低于门槛
批量离线任务 每条 prompt 独立 ≈0 不开（纯占显存）

关键：这张表的第四行说明缓存不是默认正确的。判断依据就是 §3.2 的 h∗。

四、缓存的风险面：污染、驱逐级联与多租户挤占#

4.1 缓存的三种失效模式#

污染 长且不复用的前缀占满缓存，把高复用的短前缀挤出去 有效容量 Ceff​ 下降 按"预期复用次数 × 长度"定价（GDSF 式）

这是一个结构性冲突：缓存的收益来自"共享"，而多租户的隔离要求"分区"。三个可选的解法（各有代价）：

  1. 每租户配额：Ci​≤Ctotal​/n。代价：租户数涨时每租户的容量降，h 降。
  2. 按租户分池：物理隔离。代价：碎片（小租户用不满）、无法跨租户复用公共前缀。
  3. 钉住公共前缀 + 剩余空间按 LRU 给私有：公共前缀永不驱逐，私有部分共享。代价：需要一个"公共前缀"的显式声明（谁来决定哪些是公共的？通常是平台方）。

4.3 缓存的正确性风险（不是性能风险）#

前三节算的都是延迟与成本，但缓存还有一个非性能的失效面：KV 复用必须证明"被复用的 KV 与重新计算的 KV 逐位等价"。三个必须检查的点：

  1. 前缀必须从 token 0 开始对齐：不能只匹配中间一段（RoPE 的位置编码与注意力掩码都依赖绝对位置）。
  2. 所有影响 KV 的东西都要进 key：模型权重版本、LoRA 适配器、量化参数、attention 实现（FlashAttention vs 朴素）、甚至 system prompt 的模板版本。key 变少 = 静默错误。
  3. 采样参数不能进 key（它不影响 prefill），但任何会改变 logits 的配置必须进。

缓存 key 的设计判据：key 里少一个字段的后果是"错误的输出"，而不是"慢"​

五、取舍与边界#

  1. Pˉ 在预算恒等式里是"有效 prefill 长度"：开缓存后 Pˉeff​=Pˉ−hLlcp​，所以"要不要开缓存"和"要不要分块"是同一个不等式里的两个变量。
  2. token 预算不改变总容量，只改变分位：§1.3 的吞吐列几乎不动。任何"预算调大提升吞吐"的说法，实际提升来自"batch 变大"（第 2 章的摊销），不是来自预算本身。
  3. 分块的收益上界是 ⌈L/r⌉⋅Tstep​：L≤r 时上界是 0，此时分块纯亏。先看 prompt 分布再决定是否开分块。
  4. SJF 的公平性代价必须显式定价：它的长请求最大等待是秒级。生产上不能直接用纯 SJF，要用"加权公平（第 4 章第 1 节的 WFQ）"给长请求保底。
  5. 缓存命中率不是越高越好：h 高但 Llcp​ 短时，收益被"每次命中的固定开销"（哈希查找、块表遍历）吃掉。判据仍然是 h⋅Llcp​。
  6. 驱逐策略要有引用计数：前缀树上的一个块被 k 个后续块依赖时，驱逐它等于驱逐 k 个块。这是"驱逐级联"，第 2 章第 4 节算过"重算 vs 换出"的单项账，这里要乘上依赖链长度。
  7. 多租户与缓存的目标相反：共享→命中率高，隔离→命中率低。折中是"公共前缀钉住 + 私有 LRU"，但需要平台显式声明公共前缀。

"""第 5 章第 2 节：批处理编排与缓存 —— 连续批处理的实现要点与缓存的可算收益。

纯标准库。四块：
  ① 离散 step 的连续批处理模拟器（token 预算 + 分块预填充 + KV 上限）
     FIFO（整段 prefill）vs 轮转（块化交错），看 TTFT 分位与吞吐
  ② 预算恒等式：每个 step 的 token 预算怎么被 prefill + decode 分享，稳定边界在哪
  ③ 前缀/KV 复用的收益：命中率模型 + "重算 vs 换出"的斜率判据与分界序列长
  ④ 缓存的边际 ROI：边际命中收益 = 边际显存成本 解出最优缓存大小；多租户污染

口径（与第 2、4 章一致）：
  - 一个 step 的时间 = 解码一个 token 的基本单位，本节取 8.6 ms
  - 每个 step 有 token 预算 TOKEN_BUDGET：prefill token 与 decode token 共享它
  - KV 上限按 token 计，用于模拟显存约束下的并发上限
  - 所有分位用**测得的直方图**排序取，不做分布假设
"""
import math
import random

STEP_MS = 8.60                    # 一个 step 的时间（ms）
TOKEN_BUDGET = 1024               # 每个 step 可执行的 token 数（prefill + decode）
CHUNK = 128                       # 分块预填充的块大小（token）
KV_MAX_TOK = 120_000              # 单副本 KV 上限（按 token 计）
KV_PER_TOK_KIB = 320.0            # 每 token KV 字节数（第 2/4 章口径）


class Job:
    __slots__ = ("jid", "arrive", "prompt_len", "out_len", "prefilled",
                 "decoded", "first_token_step", "done_step")

    def __init__(self, jid, arrive, prompt_len, out_len):
        self.jid = jid
        self.arrive = arrive
        self.prompt_len = prompt_len
        self.out_len = out_len
        self.prefilled = 0
        self.decoded = 0
        self.first_token_step = None
        self.done_step = None


def _poisson(rng, lam):
    """一个 step 内的到达数 ~ Poisson(lam)。

    用**指数间隔累加**而不是 Knuth 的乘积法：乘积法在 lam<1 时会退化成
    「至少 1 个」（第一次乘法就把 p 打到 ≤1），这正是本节脚本第一版的 bug ——
    λ=16 req/s（=0.138/step）时它给出 1 个/step，把负载悄悄放大了 7 倍。
    """
    if lam <= 0:
        return 0
    n, t = 0, 0.0
    while True:
        t += rng.expovariate(lam)
        if t >= 1.0:
            return n
        n += 1


def simulate(lam, n_prompt, n_out, steps=3000, warmup=600, deadline=None,
             policy="fifo", seed=3, queue_max=30, uniform_prompt=False):
    # policy: "fifo"  = 把队首请求的整段 prefill 做完（长请求堵路）
    #         "chunk" = 每个请求最多做一个 CHUNK 再换人（分块预填充）
    #         "sjf"   = 每 step 按"剩余 prefill"升序服务（最短优先）
    """离散 step 的连续批处理。

    每 step：① 到达入队；② prefill（FIFO 整段 / RR 一块）；③ decode（每 running 一个 token）
    policy="fifo"：把队首请求的 prefill **做完**再服务下一个（长请求堵路）
    policy="rr"  ：每个请求只做一个 chunk 就换人（分块预填充的公平形态）
    deadline     ：等待超过这么多 step 就放弃（模拟客户端超时）
    """
    rng = random.Random(seed)
    running, waiting, finished, dropped, rejected = [], [], [], [], []
    kv_peak = 0
    batch_sum = 0
    batch_n = 0
    for t in range(1, steps + 1):
        for _ in range(_poisson(rng, lam)):
            if uniform_prompt:
                pl = int(n_prompt)
            else:
                pl = max(8, int(rng.lognormvariate(math.log(n_prompt), 0.8)))
            ol = max(1, int(rng.lognormvariate(math.log(n_out), 0.5)))
            jid = len(finished) + len(dropped) + len(rejected) + len(running) + len(waiting)
            j = Job(jid, t, pl, ol)
            # 准入：KV 与队列双约束；**不满足就拒绝**（而不是无声积压）
            kv_used = sum(x.prefilled + x.decoded for x in running) + \
                sum(x.prefilled for x in waiting)
            if kv_used + pl <= KV_MAX_TOK and len(waiting) < queue_max:
                waiting.append(j)
            else:
                rejected.append(j)
        # 超时放弃
        if deadline:
            keep = []
            for j in waiting:
                if t - j.arrive > deadline:
                    dropped.append(j)
                else:
                    keep.append(j)
            waiting = keep
        budget = TOKEN_BUDGET
        # ① prefill：策略只改**服务顺序**，不改 token 预算的总额
        if policy == "sjf":
            waiting.sort(key=lambda j: j.prompt_len - j.prefilled)
        i = 0
        while i < len(waiting) and budget > 0:
            j = waiting[i]
            need = j.prompt_len - j.prefilled
            take = min(need, budget) if policy == "fifo" else min(need, CHUNK, budget)
            j.prefilled += take
            budget -= take
            if j.prefilled >= j.prompt_len:
                j.first_token_step = t
                j.decoded = 1
                budget -= 1
                running.append(j)
                waiting.pop(i)
                continue
            i += 1
        # ② decode
        still = []
        for j in running:
            if budget > 0:
                j.decoded += 1
                budget -= 1
            if j.decoded >= j.out_len:
                j.done_step = t
                finished.append(j)
            else:
                still.append(j)
        running = still
        if t > warmup:
            kv = sum(j.prefilled + j.decoded for j in running)
            kv_peak = max(kv_peak, kv)
            batch_sum += len(running)
            batch_n += 1
    done = [j for j in finished if j.done_step and j.done_step > warmup]
    if not done:
        return None
    ttft = sorted((j.first_token_step - j.arrive) * STEP_MS for j in done)
    short = sorted((j.first_token_step - j.arrive) * STEP_MS for j in done
                   if j.prompt_len <= n_prompt)
    long_wait = max(((j.first_token_step - j.arrive) * STEP_MS for j in done
                     if j.prompt_len > 4 * n_prompt), default=0.0)
    tpot = sorted((j.done_step - j.first_token_step) * STEP_MS / max(1, j.decoded - 1)
                  for j in done)
    span_s = (steps - warmup) * STEP_MS / 1000.0
    q = lambda arr, p: arr[min(len(arr) - 1, int(p * len(arr)))] if arr else float("inf")
    return dict(n=len(done), dropped=len(dropped), rejected=len(rejected),
                ttft50=q(ttft, .50), ttft99=q(ttft, .99),
                short99=q(short, .99), long_max=long_wait, tpot99=q(tpot, .99),
                thr=sum(j.decoded for j in done) / span_s,
                batch=kv_peak and batch_sum / batch_n, kv_peak=kv_peak)


# ---------------- 预算恒等式 ----------------
def budget_inequality(lam_per_step, prompt_mean, r_tok_per_step=TOKEN_BUDGET,
                      decode_reserve=0.35):
    """每个 step 的 token 预算分解：λ·P̄（prefill）+ b·1（decode）≤ r。"""
    prefill = lam_per_step * prompt_mean
    decode_budget = r_tok_per_step * decode_reserve
    b_star = decode_budget                       # 每 running 请求每 step 1 token
    return prefill, decode_budget, b_star, prefill + b_star, r_tok_per_step


# ---------------- 缓存收益 ----------------
def lcp_hit(prefix_hit, lcp_mean):
    """两段式命中：命中概率 prefix_hit，命中长度 lcp_mean ⇒ 按 token 的节省。"""
    saved = prefix_hit * lcp_mean
    return saved, lcp_mean - saved


def prefill_ms(tok, rate_tok_per_s):
    return tok / rate_tok_per_s * 1000.0


def swap_vs_recompute(kv_kib_per_tok, bw_gb_s, prefill_tok_s, fixed_overhead_us=1000.0):
    """换出 vs 重算：返回 (重算斜率 ms/tok, 换出斜率 ms/tok, 分界序列长 tok)。"""
    slope_re = 1000.0 / prefill_tok_s                                  # ms / token
    slope_sw = 2.0 * kv_kib_per_tok * 1024 / (bw_gb_s * 1e9) * 1000.0  # ms / token
    if slope_sw >= slope_re:
        return slope_re, slope_sw, float("inf")
    s_star = (fixed_overhead_us / 1000.0) / (slope_re - slope_sw)
    return slope_re, slope_sw, s_star


def cache_break_even_hit(lam_slots_per_s, prefill_tok_s, cache_tok, prefill_save_tok,
                         out_tok, tpot_s):
    """缓存是否划算：单位显存的机会成本 vs 单位显存换来的 prefill 节省。

    显存的机会成本：cache_tok 个 token 的 KV 占掉 N = cache_tok/avg_ctx 个并发槽，
      每槽在系统里活 W = (avg_ctx + out)/out · tpot 秒（Little 定律），
      在到达率 λ 下这些槽位平均每秒能多服务 λ·(占槽比) 个请求。
      折算成"每请求的卡秒损失"：cost_per_req = N/(lam_slots_per_s·W)
    收益：命中率 h 时每请求省下 h·prefill_save_tok/prefill_tok_s 卡秒。
    ⇒ 盈亏平衡 h* = cost_per_req / (prefill_save_tok/prefill_tok_s)
    """
    W = (cache_tok + out_tok) / out_tok * tpot_s          # 该请求在系统里的驻留时间（秒）
    n_slots = 1.0                                         # 以"每单位显存对应的槽位"归一
    cost_slots = cache_tok / (cache_tok + out_tok)        # 占槽比
    cost_per_req = cost_slots / max(1e-9, lam_slots_per_s * W)
    save_per_req = prefill_save_tok / prefill_tok_s
    return W, cost_per_req, save_per_req, cost_per_req / save_per_req

五处关键设计决策：

  1. 泊松到达用"指数间隔累加"，不用 Knuth 的乘积法。乘积法在 λ<1（每 step 到达数）时会退化成"至少 1 个"：循环体第一次就把 p 乘到 ≤1，于是永远返回 ≥1。本节的第一次运行就踩了这个坑 —— λ=16 req/s（0.138/step）被悄悄放大成 1/step（7 倍负载），表现为"系统在 10% 利用率下就排队"。这类 bug 不会报错，只会给出错的分位数。
  2. 策略只改服务顺序，不改预算总额。fifo/chunk/sjf 三个分支共享同一份 TOKEN_BUDGET 和同一套准入，所以三者的吞吐差只能来自分摊效率（batch 大小），不能来自"多给了算力"。这就是 §1.3 那句"吞吐几乎不变"的可信度来源。
  3. 准入是显式的 reject，不是无声积压。第一版把不满足 KV 的请求留在 pending 里，结果它们既不进统计也不产出，脚本"看起来跑完了"而实际只处理了 5% 的请求。准入必须是一个有计数的事件（rejected），否则过载信号会被吞掉。
  4. (1b) 段单独跑"固定长度 prompt"，因为混合长度会掩盖队头阻塞：长请求的等待被平均进分布就看不见了。固定 L 之后，⌈L/r⌉ 这个量才在数据里显形（L=16384 时 p99/p50 = 8.07×）。
  5. 缓存的判据用"盈亏平衡命中率"而不是"最优缓存大小"。最初写的是对 C 求边际收益 = 边际成本，但那个式子的两个斜率都是常数项的组合，解出的 C∗ 对参数极不稳定（换个饱和度模型就变一个数量级）。换成 h∗ 之后，判据变成了一个可以直接与线上命中率比较的百分数 —— 这才是运维能用的形式。

读输出的三处要点：

小结#

  • 连续批处理落地要三件机制：准入控制（Qmax​、Lkv​）、token 预算（r）、服务顺序（FIFO/chunk/SJF）。token 预算不是为了更快，而是为了让 TPOT 可预测：按请求数分配时一个长 prefill 会让全体 TPOT 抖动 8 倍。
  • 调度改变分位，不改变吞吐：三种策略的吞吐几乎相同（11,981 / 12,732 / 12,757 tok/s），差别全在分位。SJF 把短请求 p99 压到 34.4 ms，代价是长请求最大等待 1.1 s —— 零和的尾延迟交换。
  • 分块预填充买的是抖动不是中位数：L≤r 时它是纯亏（p50 从 0 涨到 3 step）；L≫r 时把 p99/p50 从 8.07× 摊到 3.53×。先看 prompt 分布再决定开不开。
  • 预算恒等式：λPˉeff​Tstep​+b≤r。本节参数下 decode 吃掉 90% 的预算，所以"加算力"改善 TTFT 的效果取决于 decode 与 prefill 谁在 binding。三个上限（token 预算 / KV 容量 / 队列）必须先判断哪个先拐。
  • 缓存的收益落在 TTFT 上，与 h⋅Llcp​ 成正比；判据是盈亏平衡命中率 h∗=(占槽成本)/(省下卡秒)。λ 越高、Llcp​ 越长，门槛越低；缓存占的显存越大，门槛越高。本节 λ=100、L= 2000 时 h∗=37.3%。
  • 重算 vs 换出是一个纯斜率比较：重算 1/p vs 换出 2s/(βpcie​)，两者都是常数，分界序列长只由固定开销决定（约 16 token）。PCIe 代际把斜率差从 1.0× 拉到 16.3×。
  • 缓存的风险面：污染（长且不复用的前缀挤掉高复用短前缀）、驱逐级联（依赖链长度 D 放大成本）、多租户挤占（私有前缀按租户数线性侵占公共缓存，本节 5 租户时命中率从 0.396 掉到 0.201）。还有一条非性能风险：缓存 key 少一个字段的后果是错误输出，不是慢。
  • 一句话：批处理的全部内容是"把 step 的 token 预算分配给谁"，缓存的全部内容是"用多少显存换多少重算"；前者是分位问题，后者是一个可以用盈亏命中率算清的账。

下一节：本节的所有机制都假设"系统已经在这个配置上稳定运行"。但配置本身会变 —— 模型要更新、权重精度要调整、调度参数要改；而每一次变更都要重启进程，重启意味着在飞请求失败、容量下降、缓存失效。第 3 节把"不中断升级"写成可算的量：停机时间预算、容量模型、版本一致性与回滚时间，并给出滚动/蓝绿/金丝雀三种策略在同一坐标系下的算例。
