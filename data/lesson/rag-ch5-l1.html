长上下文不是 RAG 的替代品：把「塞得下」和「答得对」分开算#

这一节要解决什么#

上一节把查询理解讲到了多跳与迭代检索，也就是"用几轮检索去凑齐证据"。到这里必然会撞上一个反问：

既然模型的窗口已经能到 128k 甚至 1M token，为什么不干脆把整份知识库塞进去？ 检索这一整套（切分、索引、混合、重排、融合）是不是在窗口变大的过程中变成历史遗产了？

这个问题最容易被回答成立场表态：要么"RAG 已死"，要么"长上下文永远替代不了检索"。两种回答都不可用，因为它们不告诉你在自己的规模、自己的任务、自己的预算下该选哪条路。

本节不做表态，只做一件事：把"塞进去"这件事拆成可以算的量，把"答得对"拆成可以测的量，然后给出一个可执行的判据。 具体要回答四个问题：

  1. 把 n 个 token 放进上下文，要花多少显存、多少算力、多少钱？这三笔账的增长率一样吗？
  2. 证据在上下文里，和不被模型读到，是两件事。中间的损耗由什么决定？能不能量化？
  3. 什么任务上"检索"结构性地输给"全塞"，什么任务上"全塞"结构性地输给"检索"？
  4. 长上下文有没有什么是即使窗口无限大也拿不到的？如果有，那些东西恰好就是下一章（工程化）的全部内容。

结论先放在这里：窗口变大改变的是成本曲线的斜率，不是"检索是否必要"这个问题的答案。长度带来的是超线性成本与随干扰数衰减的证据取用概率，而检索解决的从来不只是长度问题 —— 它同时解决可审计、可更新、可授权这三件与长度无关的事。判据不是"窗口多大"，而是"单位证据的有效成本"与"证据取用概率"谁更低。

一、先算「塞得下」的账：KV cache、prefill 与 token 费用#

"塞得下"要付三笔账，且三笔账的增长率不同。把它们分开算，是本节所有结论的地基。

1.1 第一笔：KV cache 是随长度线性的显存#

自回归解码时，每一层的 Key 与 Value 都要为每一个历史 token保留一份，因此单序列的 KV cache 大小为：

KV(n)=2⋅L⋅Hkv​⋅dhead​⋅n⋅b字节

其中 2 是 K 与 V 各一份，L 是层数，Hkv​ 是 KV 头数，dhead​ 是每头维度，n 是序列长度，b 是每元素字节数（fp16 为 2）。

这里有一个必须讲清的工程细节：Hkv​ 不等于注意力头数 H。现代模型普遍用 GQA（分组查询注意力），多个查询头共享一组 K/V 头，典型 Hkv​ 是 H 的 1/8 到 1/4。不看这个比值，KV 账会算错一个数量级。

取一组示例配置（L=80、Hkv​=8、dhead​=128、fp16）：

KV(n)=2⋅80⋅8⋅128⋅2⋅n=327,680n 字节≈3.28×10−4n GB

代入具体长度（下面是可直接运行的代码给出的数）：

上下文 n KV 显存 说明
8k 2.62 GB 单张 80GB 卡能放几十路并发
32k 10.49 GB 单卡并发掉到个位数
128k 41.94 GB 单序列就占掉半张卡
512k 167.77 GB 单序列超过单卡
1M 327.68 GB 需要多卡 + KV 分页/驱逐

结论一：KV 显存随 n 线性增长，但线性系数很大。 "n 只涨 4 倍"听起来温和，实际是从"能服务 30 路并发"变成"只能服务 1 路"。这就是长上下文服务必须做 KV 分页、前缀共享、驱逐与量化（把 b 从 2 降到 1 甚至 0.5）的原因：不是因为长度本身，而是因为系数 × 并发数会击穿显存。

1.2 第二笔：prefill 算力是超线性的#

预填充（prefill）要把 n 个 token 一次性过一遍网络。算力有两个部分：

FLOPs(n)≈线性：每层权重乘加2Nn​​+二次：注意力 QK⊤ 与 AV4Ln2dhead​​​

N 是参数量。Θ(n2) 那一项来自注意力矩阵：每个 token 要和所有 token 算相似度。这就是"塞得下"和"算得起"分岔的地方：线性项随 n 温和增长，二次项随 n 平方增长，长度一过某个点，二次项就主导。

示例配置（N=70×109）下：

n prefill FLOPs 相对 8k
8k 1.12×1015 1×
32k 4.52×1015 4.0×
128k 1.86×1016 16.6×
512k 8.24×1016 73.4×
1M 1.81×1017 161.2×

结论二：从 8k 涨到 1M，长度涨 125 倍，prefill 算力涨约 161 倍。 多出来的那部分全是二次项。真实的 FlashAttention 类内核把常数压得很低、并用分块避免物化 n×n 矩阵，但它改变的是常数，不是 Θ(n2) 这个阶。所以：

在固定算力预算下，把窗口从 8k 开到 1M，你能服务的查询数不是除以 125，而是除以 161（示例配置），并且还要额外付出 1.1.1 节的 KV 显存代价。

1.3 第三笔：token 费用与"检索 vs 全塞"的倍数#

按输入 token 计费时，一次问答的输入成本是 cin​⋅nin​，输出是 cout​⋅nout​。把检索方案与全塞方案放在一起比较，定义成本倍数：

ρ=cin​⋅nretrieved​+cin​⋅ninstruction​+cretrieval​cin​⋅nstuffed​+cin​⋅ninstruction​​≈nretrieved​nstuffed​​

ρ=cin​⋅nretrieved​+cin​⋅ninstruction​+cretrieval​cin​⋅nstuffed​+cin​⋅ninstruction​​≈nretrieved​nstuffed​​

后面那个近似在 nretrieved​≫ninstruction​、且检索摊薄成本远小于 token 成本时成立。于是问题变成一句很朴素的话：

同一个问题，检索要付 8k token 的输入费，全塞要付 1M token 的输入费。检索只要把"漏掉正确答案"的代价控制在 125 倍成本差以内，它就还在赢。

这就是本节的核心不等式。它把"RAG 是否过时"从立场问题变成了两个可测量的量：

  1. 检索的漏洞代价：漏检率 pmiss​ 乘上漏检造成的业务损失 Cmiss​；
  2. 全塞的代价：额外的 token 成本 + 额外的延迟 + 干扰带来的准确率下降（下一节要量化的东西）。

选检索⟺pmiss​⋅Cmiss​+Cretrieval​<ΔCtokens​+ΔCdistract​+ΔClatency​

注意 ΔCdistract​ 这一项：它常常是压倒性的，而且它不在任何账单上。 下一节专门处理它。

二、「答得对」不是「看到了」：位置、干扰与多事实聚合#

把证据放进上下文，只完成了"可见"。模型还要在所有 token 的注意力竞争中真的把那一块读出来。这个竞争有两个可测的损耗来源。

2.1 位置损耗：准确率对证据深度的 U 形依赖#

把同一份证据放在上下文的不同深度（0% 在最前、100% 在最后、50% 在正中），固定其他一切，测同一批问题的准确率，得到的曲线不是平的，而近似 U 形：首尾高、中部低。

机理不神秘：训练语料里"重要信息在开头（指令/摘要）或结尾（最近内容）"的分布，塑造了注意力位置先验；中间位置既没有"最近"的优势，也没有"开头"的位置编码结构优势。把这个先验写成一个可算的代理：

ℓevidence​(depth)=rel−κ(1−∣2⋅depth−1∣)

κ 控制 U 形的深度。κ=0 时位置无关；κ>0 时中部被压制。这不是某个模型的确切公式，而是一个能被数据校准的代理：你可以在自己的模型上用几组位置实验反解 κ。

可测判据：定义顺序敏感度

Sorder​=π∈Πmax​acc(π)−π∈Πmin​acc(π)

Π 是证据排列的集合（全排列太大时抽样估计）。如果 Sorder​>5%，说明你的系统有免费的准确率躺在排列里 —— 先把重排做好，再谈换模型。

2.2 干扰损耗：softmax 的分母#

真实上下文里不只有证据，还有 m 个干扰块（检索回来的不相关 chunk、无关历史、工具输出噪声）。把"证据被读到"建模为一次 softmax 竞争：

P(evidence)=eℓevidence​+∑i=1m​eℓi​eℓevidence​​

这个式子有两个直接推论，都是可测的：

  1. 固定位置、增大 m，P 单调下降。示例配置下，最差位置（中部）从 m=1 的 0.581 掉到 m=10 的 0.124、m=50 的 0.030、m=200 的 0.008。
  2. 固定 m、移动位置，首尾的 P 高于中部（m=10 时 0.319 vs 0.124），这就是 2.1 的 U 形。
证据深度 m=1 m=10 m=50 m=200
0.00（最前） 0.822 0.319 0.092 0.025
0.35 0.665 0.168 0.042 0.011
0.50（正中） 0.581 0.124 0.030 0.008
0.65 0.665 0.168 0.042 0.011
1.00（最后） 0.822 0.319 0.092 0.025

⚠️ 合成数据：上表由本节的代码生成，是一个显式写出的 softmax 代理，不是任何真实 LLM 的实测读数；它的用途是展示"干扰进入分母"这个机制，以及给出可以校准到自己系统上的形式。真实数值必须自己在自己的模型和语料上测。

2.3 多事实聚合：联合概率是指数#

如果一个问题需要 m 块证据同时被读到（"比较 A、B、C 三年财报的三个指标"），而各块独立竞争，那么联合成功概率近似

Pjoint​(m)≈i=1∏m​P(evidencei​)

示例配置（中部、m=10 个干扰块，单块 P=0.106）：

需要证据块数 联合成功率
1 0.106
2 0.0112
4 1.3×10−4
8 <10−7

这是本节最重要的一个量化结论：单块证据的取用概率哪怕只降到 0.5，8 块联合也只剩 0.4%。所以

"多事实聚合/计数/全局比较"这类任务上，有效上下文远小于名义上下文，而且衰减是指数的、不是线性的。 这正是"窗口再大也答不好'一共有几条'"的原因 —— 不是长度不够，是需要同时命中的证据块太多。

2.4 有效上下文的可操作定义#

既然"名义窗口"没有意义，就要定义有效上下文：

neff​(ϵ)=max{n:acc(n)≥accmax​−ϵ}

其中 accmax​ 是你在短上下文下能达到的峰值准确率，ϵ 是容忍的绝对下降。两种常见测法：

  • 位置扫：固定总长度，移动证据深度，得到 U 形，取"中部准确率不低于峰值 −ϵ"的长度范围；
  • 长度扫：合成填充（distractor padding）把上下文从 4k 拉到 256k，看准确率随 n 的下降曲线。

在把"上下文变长"建模为"干扰块按比例增多"（密度 1 块/400 token）的合成设定下，本节的代码给出：

nctx​ 干扰块 相对峰值
4k 10 1.000
16k 40 0.302
64k 160 0.069
256k 640 0.017

并反解出 neff​(0.05)≈6k、neff​(0.10)≈15k。

这个绝对数字不可直接引用（合成代理、密度是假设的），但方法是可移植的：在任何真实系统上，你都可以用"长度扫 + 位置扫"测出自己的 neff​。而一旦测出来，你会发现它通常远小于 API 文档里的窗口大小 —— 差距可能是一个数量级。

三、判据：什么时候检索必输、什么时候全塞必输#

现在把三笔成本账（1.1–1.3）与两个损耗（2.1–2.3）合起来，做成决策判据。关键是把"任务形状"映射到"证据形态"，因为损耗取决于证据形态。

3.1 两条结构性结论#

全塞必输的条件（合取，满足越多越确定）：

  • 语料规模 Ntok​ 远超 neff​（例如 1M token 文档 vs neff​≈ 15k）；
  • 干扰密度高（大量近似重复或同主题不同事实的文档）；
  • 需要高频问答（token 成本线性累积），或延迟预算紧；
  • 有权限要求（不同用户可见文档不同）—— 全塞无法按人裁剪；
  • 有审计要求（必须给出引用来源与版本）；
  • 知识更新频繁（全塞意味着每次都要重新组织输入，且无法保证一致）。

检索必输的条件（合取或析取）：

  • 问题的答案不在任何单块里，而需要跨文档全局聚合（计数、最大值、全集否定"哪些文档没有提到 X"）；
  • 正确答案与查询词汇/语义差距极大，以至于检索器结构性地召不回（ch1 的两类失效）；
  • 语料本身就小（Ntok​<neff​）：此时检索是纯粹多出来的复杂度；
  • 单文档深读（"把这份合同第 7 条解释给我"）：一次给全文比检索更省心，且不会切碎上下文；
  • 需要严格确定性：检索是概率性的，且候选集随语料变化而漂移。

3.2 判据表#

任务/语料特征 证据形态 更优方案 理由（可验证）
语料 < 有效上下文 全文可放 长上下文直读 省掉索引与召回损失，且无切分损伤
语料巨大 + 单跳事实问答 局部块 检索 neff​ 与成本双重约束
需计数/聚合/全集否定 全局 检索 + 聚合（map-reduce/结构化查询） 全塞下联合概率指数衰减；检索也需专门聚合
多跳（A→B→C） 链式 迭代检索 ch4 已给收益条件；全塞等于把整库放进窗口

这张表的用法：不是"选一边"，而是先对每个特征判真，再看结论是否一致。如果同时满足"语料小"和"需要权限裁剪"，那么两者冲突 —— 此时应先满足不可协商的约束（权限、审计、确定性），再优化成本。

四、混合形态，以及长上下文永远拿不到的四件事#

4.1 主流形态：先检索缩小，再长上下文精读#

在实际系统里，最有性价比的形态既不是"纯检索 8k"，也不是"全塞 1M"，而是：

召回（便宜、宽）⟶W token 精读上下文（贵、窄）

  • 召回阶段的目标是 recall：可以用多路、便宜、甚至可以刻意"召回过多"（ch3 的融合），因为这一阶段便宜；
  • 精读阶段的目标是 precision 与推理：把候选压到 W≈neff​ 量级，让模型在低干扰下做比较、抽取、归纳；
  • W 的取值来自 2.4 节测出的 neff​，而不是 API 的最大窗口。

这个形态同时避开了两边的坑：不会因为窗口大就无视成本，也不会因为检索器不完美就丢掉"让模型自己看"的能力。它是"检索 + 长上下文"而不是"二选一"。

4.2 长上下文即使无限大也拿不到的四件事#

这是本节最需要记住的部分。以下四件事与窗口大小无关，是检索（作为一套系统）独有的：

  1. 可授权（authorization）：长上下文无法按查询者身份裁剪输入 —— 你不可能把整库发给每个用户，再指望模型"别看那些"。权限必须在检索层执行（ch6-l3 详述）。
  2. 可审计（auditability）：引用溯源需要稳定的 doc/chunk id、版本与分数；"模型读了整库"给不出可核验的证据链。
  3. 可更新（update）：知识变更要求改一处、立即生效、且不重算其他部分；把知识放进输入等于每次重新组织，且无法保证并发一致性。索引更新是 ch6-l1 的主题。
  4. 可计量（accounting）：按 token 计费时，检索把"每次问答的成本"与"语料规模"解耦了 —— 语料从 1 万涨到 1000 万，每次问答的输入 token 基本不变。全塞方案里，成本与语料规模强制耦合。

这四件事恰好是下一章（工程化与运营）的全部内容。 这也是本节标题的判断：长上下文改变成本斜率，不改变"检索是否必要"。当你在一个真实系统里发现自己在做权限、审计、更新、计费中的任何一件，你就已经在做检索了 —— 区别只是有没有把它做好。

4.3 边界与误用#

  • 不要用"窗口大小"当验收标准。验收标准是 neff​ 与单位证据成本，不是标称参数。
  • 不要用合成 needle 测试代替真实任务评测。"针在草堆里"测的是单块取用，测不出 2.3 的联合衰减与任务级正确率。
  • 不要把 κ、干扰密度当普适常数。它们是你自己模型+语料上的待校准参数；本节的公式是校准模板，不是查表数值。
  • 不要忽略 prefill 二次项的工程含义：它决定了长上下文的首 token 延迟随长度快速增长，因而与交互式产品的延迟预算直接冲突。

代码#

(a) KV cache、prefill 与 token 成本#

# -*- coding: utf-8 -*-
"""长上下文的成本账：KV 显存 / prefill 算力 / token 费用。"""
import numpy as np

L, H_kv, d_head, b = 80, 8, 128, 2          # 示例：70B 级、GQA 8 个 KV 头、fp16
kv_per_token = 2 * L * H_kv * d_head * b     # 2 = K 与 V 各一份
N, flops_eff = 70e9, 3.5e14                  # 参数量；示例有效算力 FLOP/s
c_in = 2.0 / 1e6                             # 示例单价 元/token，以官方为准

print("== (a) KV cache 与 prefill（示例配置；绝对秒数仅示意，看的是缩放）==")
print(f"{'n':>8} {'KV(GB)':>8} {'prefill(GFLOP)':>15} {'秒(示例)':>9} {'输入成本(元)':>12}")
for n in (8_000, 32_000, 128_000, 512_000, 1_000_000):
    kv_gb = kv_per_token * n / 1e9
    prefill = 2 * N * n + 4 * L * n * n * d_head   # 线性项 + 注意力二次项

关键设计决策：把 prefill 写成"线性项 2Nn + 二次项 4Ln2dhead​"而不是一个总数，是为了让读者看到拐点在哪里。当 4Lndhead​>2N 时，二次项开始主导：代入示例配置，n>N/(2Ldhead​)≈3.4×106 才会主导 —— 但注意那是"算力"意义上的拐点，而成本与延迟意义上的拐点要早得多，因为线性项本身已经很大，而且 KV 显存是线性的。第 4 节的混合形态正是针对这个"两项都贵"的区间。

(b) 有效上下文的合成代理#

# -*- coding: utf-8 -*-
"""⚠️ 合成数据：softmax 注意力竞争代理，用于展示位置与干扰的机制。"""
import numpy as np

def p_win(depth, n_distract, rel=2.5, mu_d=0.8, sd_d=0.5, pos_max=1.2, seed=0):
    """证据块与 n_distract 个干扰块竞争注意力；返回证据块胜出的概率。"""
    rng = np.random.default_rng(seed)
    pos_pen = pos_max * (1 - abs(2*depth - 1))          # 中部最大 -> U 形
    logit_e = rel - pos_pen
    logit_d = rng.normal(mu_d, sd_d, n_distract)
    m = max(logit_e, logit_d.max())
    num = np.exp(logit_e - m)
    den = num + np.exp(logit_d - m).sum()
    return float(num / den)

print("== (b) ⚠️ 合成数据：softmax 注意力竞争代理（不是真实 LLM 读数）==")
print(f"{'depth':>6} " + " ".join(f"{'d='+str(nd):>8}" for nd in (1, 10, 50, 200)))
for depth in (0.0, .15, .35, .5, .65, .85, 1.0):
    ps = [p_win(depth, nd, seed=1) for nd in (1, 10, 50, 200)]
    print(f"{depth:>6.2f} " + " ".join(f"{v:>8.3f}" for v in ps))

print("\n-- 多事实聚合：需要 m 块证据同时被读到（联合概率 = 各块胜出概率之积）--")
for nd in (10, 50):
    for m in (1, 2, 4, 8):
        p1 = p_win(0.5, nd, seed=3)          # 最差位置上的单块胜出概率
        print(f"干扰={nd:>3} 需证据块数 m={m}: 单块P={p1:.3f}  联合P={p1**m:.3e}")

关键设计决策：把这个代理写成显式的 softmax 竞争，而不是直接给准确率打折，是因为这样两个机制（位置折扣、干扰竞争）就是从公式里长出来的，而不是被硬编码成结论。读者可以只改 pos_max=0（关掉位置效应）或只改 sd_d=0（让干扰同质）来看每一项的独立贡献 —— 这是"可校准的模型"与"编出来的数字"的区别。

# -*- coding: utf-8 -*-
"""⚠️ 合成：把'上下文变长'建模为'干扰块按比例增多'，反解有效上下文。"""
def acc(n_ctx, density=1/400, seed=7):
    nd = max(1, int(density * n_ctx))
    return p_win(0.5, nd, seed=seed)          # 证据放正中（最差位置）

acc_max = acc(4000)

小结#

  • 窗口变大改变的是成本曲线斜率，不改变判据。 判据是"单位证据的有效成本"与"证据取用概率"，不是标称窗口大小。
  • 三笔成本账的增长率不同：KV 显存线性但系数极大（示例配置 3.28×10−4 GB/token，1M token 需 327.7 GB）；prefill 算力超线性（8k→1M 涨 161.2×，二次项主导）；token 费用线性且与语料规模强制耦合。
  • Hkv​=H。GQA 下 KV 头数常是注意力头数的 1/8∼1/4；不算这个比值，KV 账会错一个数量级。
  • "在上下文里"不等于"被读到"。位置损耗给出 U 形准确率曲线；干扰损耗来自 softmax 的分母（示例：中部证据在 m=1→200 时从 0.581 掉到 0.008）。
  • 多事实聚合的联合成功概率是指数衰减的：单块 0.106、4 块 1.3×10−4、8 块 <10−7。这是"窗口再大也数不清"的机制，不是长度问题。
  • 有效上下文 neff​(ϵ) 必须实测，并且通常远小于标称窗口；测法有两种（位置扫 / 长度扫），合成代理给出 neff​(0.05)≈6k、neff​(0.10)≈15k（仅示范方法）。
  • 可执行判据：全塞必输于"语料 ≫neff​ + 干扰密 + 高频 + 权限 + 审计 + 更新频繁"；检索必输于"全局聚合/计数、词汇语义缺口极大、语料本身就小于 neff​、单文档深读、需严格确定性"。
  • 主流形态是混合：宽而便宜的召回 → 压到 W≈neff​ 的精读上下文。W 由实测 neff​ 决定，不是 API 上限。
  • 长上下文永远拿不到的四件事：可授权、可审计、可更新、可计量。它们与窗口大小无关 —— 当你的系统需要其中任何一件，你就在做检索；区别只是做没做好。
  • 一句话："塞得下"是一道成本题，"答得对"是一道注意力竞争题，两者都不能由窗口大小回答。把 neff​ 测出来、把单位证据成本算出来，选哪条路就是算术结果。
