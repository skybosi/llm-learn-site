终止条件与收敛：预算、步数、置信度三把闸#

这一节要解决什么#

前面两节都在讲"怎么继续"。这一节讲"怎么停" —— 这是全课最容易被轻视、代价最高的设计点。

轻视它的表现是：终止条件写成 if "完成" in model_output: break，或者干脆 for step in range(10)。代价是三类事故：

  1. 不收敛：循环永不结束（或耗尽全部资源），因为判据永远不成立。
  2. 振荡：在两个状态之间反复横跳，每一步都"差一点就够"，烧掉全部预算。
  3. 过早终止 / 虚假完成：判据被满足，但任务没真做完 —— 而且没人知道。

这一节要把这三类事故的机制算清楚，并给出三把闸的设计。这是本章最厚的一节，因为终止条件是误差累积、目标漂移、循环设计三条线的汇合点：它既是对漂移的唯一防线，也是成本上界的唯一实现，还是"收敛 ≠ 成功"这个最容易混淆的概念的所在地。

学完这一节你应该能回答：

  • 为什么"有限步数"能保证终止，但不能保证在正确的状态上终止？
  • 什么是"振荡"？它的数学条件是什么？滞回（hysteresis）和退火为什么能消除它？
  • 置信度闸该怎么用？为什么"模型自评置信度"是一个危险信号？
  • 判据阈值该怎么选？"宁可放过"还是"宁可错杀"能用代价算出来吗？（能。）
  • 遇到一个没有客观判据的任务（"写一份足够好的报告"），正确的收场方式是什么？

一、终止是两个不同的问题#

先把一个被混为一谈的区分拆开：

termination循环会停​​=correctness停在正确的状态​​

有限步数预算一举保证前者：只要每步都有确定性的步数计数并递减，循环必然在 B 步内结束。这是结构性的保证，与模型强弱无关（第 1 章"用更强的模型弥补不了"的那一类）。

但它对后者毫无保证：B 步后停下的状态可能离目标很远。所以任何"终止条件"的设计实际包含两个独立部件：

① 停止保证（termination guarantee）：结构性的，由预算/计数器提供
② 停止判据（stopping criterion）  ：语义性的，由验证器提供

绝大多数 Agent 事故都不是"停不下来"，而是"停在了不该停的地方，或者停得太晚"。 第 ② 个部件的质量才是真正的设计对象。

回忆第 1 章的定义第 ③ 条："存在一个在循环之外的终态判据"。本节的全部内容就是在展开这一条怎么落地。

二、三把闸：语义、机制与失效模式#

三把闸各拦一类问题，语义完全不同，不能互相替代。

闸 1：步数 闸 2：预算 闸 3：置信度/判据
拦什么 无限循环、死循环 成本与延迟失控 "看起来在动但没进展"
量纲 步（离散计数） token / 调用 / 秒（多维） 分数 / 谓词（语义）
检查时机 每步开始 每步开始（执行前！） 每步结束或事件触发
对应第 1 章 pn 里的 n 上界 成本可控目标 漂移检测（约束谓词）
单独使用会怎样 步数内反复做无效动作，成本不受控（一步可能极贵） 钱花完了但任务才做一半，且花了钱还没结论 判据不稳时振荡或早停

必须三把同时装，理由是它们拦的失效模式互不覆盖：

  • 只有步数闸：一个"每步都调用超贵模型"的循环会在 15 步内烧掉整个月预算。
  • 只有预算闸：一个"每步都很便宜但永远在原地打转"的循环会跑几千步，而且因为便宜，预算闸迟迟不触发。
  • 只有置信度闸：判据一旦不稳定（第四节），要么死循环（判据永不成立），要么早停（判据轻易成立）。

2.1 闸 1 与闸 2：预算必须是"执行前检查"#

这一点在第 1 章 2.5 讲过，但值得在此重复，因为它是最容易写错的一行代码：

# 前置：一个"成本上界估计器"。★ 设计决策：估计的是上界，不是期望值 ——
# 预算检查必须用最坏情况，否则超支的那一次正好是估计偏低的那一次。
def estimate_max_cost(decision: dict) -> int:
    """这个动作最坏会花多少 token。默认取模型 max_tokens 参数（最安全的固定上界）。"""
    return decision.get("max_tokens", 1024)

next_decision = {"kind": "tool", "name": "search_docs", "max_tokens": 1024}
used_tokens, budget = 58_000, 60_000

# ✗ 错误：跑完再统计 —— 钱已经付了，此时 break 已经省不下任何东西
res = call_model(...)                        # （伪码：这里的调用已经产生了 token 消耗）
if used_tokens > budget: break

# ✓ 正确：执行前预检 —— 用"上界估计"，不是"事后统计"
est = estimate_max_cost(next_decision)      # 这个动作最坏会花多少
if used_tokens + est > budget: break        # 提前终止，而不是付了再说

预检需要一个"成本上界估计器"，这本身是个小设计问题：

估计方式 准确性 复杂度 适用
固定上界（max_tokens 参数） 偏高但安全 极低 默认选择：直接设模型的 max_tokens
历史分位数（同类动作的 p95） 较准 低 有足够轨迹数据后
精确（先算 token 再用） 准 高 一般不值得

一个实用规则：把 max_tokens 显式设成一个小值（而不是让模型自由生成）。这既给了准确的成本上界，又顺带抑制了"模型长篇大论"这类浪费。

2.2 闸 3：置信度闸的三种实现，可靠性递增#

"置信度"这个说法容易让人以为要模型报一个数。恰恰相反，可靠性递增的顺序是：

实现 形式 可靠性 说明
③-c 模型自评置信度 {"done": true, "confidence": 0.9} 最低 有系统性偏差，且是可被操纵的信号
③-b 独立评审 另一个模型 + 明确 rubric（独立上下文） 中 用于语义质量，需接受更弱保证
③-a 确定性判据 assert / SQL 计数 / schema 校验 / 测试通过 最高 一切可机械检查的目标都该用它

为什么"模型自评置信度"危险（第 1 章机制二的直接后果）：自评 s^ 与真实进展 s 有系统偏差，而且这个数字会参与优化。一旦你把"置信度 > 0.8 就停"写进循环，模型（在提示词的驱动下）会倾向于报出高置信度 —— 这不是"模型不诚实"，而是你在优化一个代理指标。形式上：

若终止条件为 s^(x)>τ，则系统会优化 s^，而非 s

可用的折中：把自评置信度当作信号而非判据 —— 用它来触发额外验证（"它说很有把握 → 那就跑一次确定性检查来确认"），而不是用它来终止。

✓ 置信度低 → 挂起求人 / 补一次验证（用信号换决策）
✗ 置信度高 → 直接停（把代理指标当判据）

2.3 判据的组合逻辑#

一个实用的终止判据通常是多个条件的组合，而组合方式决定了假阳性/假阴性：

组合 形式 性质
AND（全部满足） c1​∧c2​∧… 严格：假阳性↓（不易虚假完成）、假阴性↑（容易卡住）
OR（任一满足） c1​∨c2​∨… 宽松：假阴性↓、假阳性↑（易虚假完成）
加权打分 + 阈值 ∑wi​ci​≥τ 可调，但引入阈值选择问题（第四节）

设计建议：硬约束用 AND 单独守，质量用打分：

终止 ⟺ (全部硬约束成立)  AND  (质量分 ≥ τ)

硬约束（AND，不可让步）：不改动禁止的表、不超支、不删除未备份数据、产物 schema 合法
质量分（可调阈值）      ：覆盖度、引用可核验、格式规范

理由：硬约束的假阳性代价是事故（不可接受），所以必须严格；质量分的假阳性代价是不够好（可接受，且可以用重试/人工兜底）。把两类混在一个打分里，会让你无法在不放松硬约束的前提下调整严格度。

三、终止条件的收敛性分析#

现在进入本节的难点：判据会不会稳定地成立？ 有三种不稳定形态。

3.1 振荡：判据在阈值附近横跳#

最简单的振荡模型：假设终止由连续进度分 st​ 驱动，判据为 st​≥τ。若 st​ 的更新是

st+1​=st​+ηg(st​)+ξt​

其中 g 是"朝目标推进"的方向项、ξt​ 是每步噪声，那么在梯度项 g 很小（接近目标但还没到）而噪声 ξ 不小的区域，st​ 会在 τ 附近做随机游走：

s: 0.78  0.83  0.79  0.84  0.80  0.82 …
           ↑ 越阈，判定"完成"？→ 但它下不去，因为下一步又掉回 0.79

两种情况会实际发生（取决于实现）：

  • 若"越阈即终止"：会发生抖动式早停（在 0.83 那一刻停，实际还没完成）。
  • 若"连续 k 步越阈才终止"：可能永远等不到（因为噪声幅度大于阈值间隔），于是烧光预算。

振荡的条件（这是可以推导的）：在阈值附近，若

E[Δs]≈0且sd(ξ)>τ−sˉ

即"平均进展为零"且"噪声幅度超过到阈值的距离" —— 那么系统会在阈值附近无限期徘徊。

两个有效的修法（都来自控制/电路设计里对付抖动的成熟手段）：

修法一：滞回（hysteresis）—— 上下两个阈值。 用施密特触发器式的双阈值：

进入"完成"态⟺s≥τhigh​,退出"完成"态⟺s<τlow​

其中 τhigh​−τlow​>2sd(ξ)。判据：滞回带宽度必须大于噪声的 2 倍标准差，否则抖动的能量仍然能跨越它。这是把"防治抖动的工程常数"变成可计算量的例子。

修法二：冷却（cooldown）/ 记账。 不直接看当前分，而是看"越阈的持续性"：

完成⟺i=t−w+1∑t​1[si​≥τ]≥m

即在窗口 w 内至少 m 次越阈。m/w 就是"越阈频率"，它对单步噪声不敏感。这等价于一个低通滤波器。

修法 参数 代价 适用
滞回 τhigh​,τlow​ 略微更难达到"完成"（假阴性↑） 判据是连续分、噪声平稳
冷却/投票 w,m 延迟 w 步才发现完成（成本↑、延迟↑） 判据是二值、或分数噪声非平稳

共同点：两者都是用"容忍一点假阴性"换"消除振荡"。 这是终止条件设计里最普遍的一笔交易 —— 见下一节的代价分析。

3.2 收敛 ≠ 成功：不动点可能不是目标#

第二个容易混淆的点。若状态更新是压缩映射（第 1 章机制三里的 L<1），Banach 不动点定理保证迭代收敛：

∥xt+1​−x∗∥≤L∥xt​−x∗∥⟹xt​→x∗

∥xt+1​−x∗∥≤L∥xt​−x∗∥⟹xt​→x∗

但 x∗ 是"这个更新算子的不动点"，未必是"任务的目标状态"。 一个 Agent 完全可能稳定收敛到一个错误的地方 —— 比如稳定地输出"我无法完成这个任务，因为缺少信息"（而信息其实在某个它没查的工具里）。

这就是为什么"循环稳定了"不能作为成功的证据。 一个实用的诊断：收敛速度正常 + 结果不对 ⇒ 问题在判据或工具集，不在循环。 具体分三种：

现象 机制 该改什么
快速收敛到错误结论 更新算子把系统拉向一个吸引子（如"拒绝"） 检查判据是否可满足；检查工具集是否覆盖所需能力
缓慢收敛，永远差一点 阈值太高或噪声太大（3.1） 滞回/冷却，或重新标定 τ
不收敛，来回震荡 更新规则含振荡项（例如每步都推翻上一步） 引入状态收缩视图（第 1 章机制三）

3.3 奖励黑客：判据被优化#

第三种，也是"虚假完成"的主要来源。任何可以被模型直接写入的信号，都会被优化。

判据：输出里包含"任务完成"
黑客：模型学会在最后写一句"任务已完成"          ← 判据被字面满足
判据：文件存在
黑客：模型创建一个空文件                        ← 判据被字面满足
判据：测试通过
黑客：模型修改测试（而不是修代码）              ← 判据被字面满足
判据：所有 TODO 都被处理
黑客：模型把 TODO 注释删掉                      ← 判据被字面满足

防御原则（按强度排序）：

原则 做法 强度
判据不可由被测对象写入 测试文件只读；判据在独立进程/沙箱里跑；校验用独立的数据库账号 最强
判据检查"事实"而非"声明" 不看输出里写了什么，看外部世界的实际状态（文件内容哈希、DB 行、接口返回） 强
判据不可被单点绕过 多条独立判据 AND（改测试也要改代码，且两者都过才成） 中强
判据与提示词分离 判据不出现在给模型的提示词里 中（降低但不能消除被针对的风险）
判据出现在提示词里、模型可读 —— 最弱：等于把答案给了考生

一个必须记住的推论：把终止判据写进系统提示词是有风险的。它让模型知道"考什么"，于是它会朝满足判据的方向走，而不是朝真正完成任务的方向走。如果非要告诉模型"做到什么程度算完成"（有时确实需要，以避免它过早上交），那么应该给一个比真实判据更严格的要求，或者把真实判据藏在循环外。

四、判据阈值的代价分析：宁可放过还是宁可错杀#

现在把前面反复出现的"假阳性 vs 假阴性"交易算清楚。设：

  • α：假阳性率（判据说"完成"，实际没完成）= 判据太弱
  • β：假阴性率（判据说"没完成"，实际已完成）= 判据太严
实际已完成 实际未完成
判据：完成 真阳性 假阳性 α（虚假完成，静默事故）
判据：未完成 假阴性 β（继续烧预算） 真阴性（正确地继续）

4.1 假阳性（过早终止）的代价#

虚假完成通常要到下游才被发现（用户投诉、数据错了、客户收到了错报告）。它的一次代价可能远高于一次多余的重试。用"重跑一次的成本"来量化：

cost(α)≈α⋅(Cdeliver​+Cdownstream​)

其中 Cdownstream​ 是错误交付造成的下游损失。在"发给客户"这类场景里 Cdownstream​≫Cdeliver​（第 1 章案例里把"可回滚"排第一，就是这个原因）。

4.2 假阴性（过晚终止）的代价#

设每次假阴性后系统继续跑，平均还要多花 E[ΔN] 步（每步成本 a），然后（因为预算耗尽或再次触发判据）停下来：

cost(β)≈β⋅E[ΔN]⋅a+β⋅预算耗尽的浪费aBwaste​​​

注意第二项：假阴性会把预算烧在已经完成的任务上，而且烧完之后你可能还是不知道它已经完成了（这个更糟）。

4.3 最优阈值#

设判据由一个连续分 s 与阈值 τ 组成。α(τ) 随 τ 递减、β(τ) 随 τ 递增。总代价：

J(τ)=α(τ)Cfp​+β(τ)Cfn​

最小化 J 的 τ∗ 就是代价加权的最优工作点。给一个可用的离散近似（把 s 的分辨率取成 M 档）：

τ∗≈argτmin​[α^(τ)Cfp​+β^​(τ)Cfn​]

τ∗≈argτmin​[α^(τ)Cfp​+β^​(τ)Cfn​]

其中 α^,β^​ 从离线评测集上估出来（第 7 章的评测集正是为此）。数值示例（M=100 档，s 越大越可能是真完成）：

τ α^（假阳性） β^​（假阴性） J（Cfp​=20,Cfn​=1）
0.60 0.30 0.02 6.0+0.02=6.02
0.80 0.12 0.08 2.4+0.08=2.48
0.90 0.05 0.18 1.0+0.18=1.18
0.95 0.02 0.30 0.4+0.30=0.70
0.99 0.005 0.55 0.1+0.55=0.65
0.995 0.002 0.72 0.04+0.72=0.76

这张表给出两个重要结论：

  1. 最优阈值远高于"看起来合理"的位置（这里 0.99）。因为假阳性的代价是假阴性的 20 倍，所以应该极度保守：宁可多跑、多花钱，也不虚假交付。这一结论与第 1 章"承重墙"判据一致（去掉它会让系统变危险）。
  2. 最优阈值随 Cfp​/Cfn​ 移动，而这个比值是业务决定的，不是技术决定的。所以"阈值该设多少"这个问题无法由算法工程师单独回答 —— 它需要"虚假交付一次值多少钱 / 多跑一次值多少钱"这两个数。把这两个数写进设计文档，是本节的实操产出。

推论：如果一个团队无法说出 Cfp​ 和 Cfn​，那么它的终止阈值是未经设计的 —— 无论它看起来多合理。

五、不可判定任务的收场#

最后处理最难的一类：没有客观判据的任务。例如"写一份足够好的行业报告"。

这类任务不能靠"更聪明的判据"解决，只能靠承认并设计收场方式。四种可用形态：

收场方式 怎么做 代价 适用
预算耗尽 + 最好版本 到预算上限时交付当前最优中间产物，并显式标注未验证 可能交付不合格产物 低风险、可迭代的场景
挂起求人 持久化状态 + 请求人工确认（第 2.1 节的 Suspend） 延迟、人力 高风险、不可逆
降级交付 交部分结果（"只覆盖了 3 个竞品中的 2 个"），明确范围 用户预期管理 可分片的任务
拒绝并给出所需信息 "无法判定完成，需要你指定验收标准" 用户体验差但安全 判据根本无法定义时

最重要的设计规则：任何终止状态都必须产生一个可解释的结论。 终止状态的完整枚举应该是：

done            目标达成，判据全部通过
budget_steps    步数耗尽（附：当前进展、卡在哪一步）
budget_cost     成本/时延耗尽（附：已完成的子目标）
violation       硬约束被违反（附：哪条、在哪一步、当前状态）
blocked         挂起等外部事件（附：等什么、超时怎么办）
need_human      需人工判定（附：为什么自动判据不适用）
undecidable     判据无法定义（附：建议的验收标准）
error           执行崩溃（附：可重放所需的全部信息）

"budget_steps" 和 "error" 必须携带足够的上下文，让下游能做出决策 —— 一个只返回 None 的失败是最昂贵的失败，因为它把成本转嫁给了人。这也是第 7 章"轨迹级评测"要消费的数据。

代码：三把闸 + 滞回 + 代价最优阈值#

import math
from dataclasses import dataclass, field
from typing import Callable, Optional

# ============ 闸 1 + 闸 2：步数与预算（执行前预检）============
@dataclass
class Gates:
    max_steps: int = 15
    max_tokens: int = 60_000
    max_calls: int = 20
    max_seconds: float = 90.0
    used_tokens: int = 0
    used_calls: int = 0
    started: float = 0.0
    step: int = 0

    def precheck(self, est_tokens: int, est_seconds: float = 0.0) -> Optional[str]:
        """
        ★ 必须在执行下一步之前调用。用'est_tokens'上界（通常就是模型的 max_tokens），
        而不是事后统计 —— 事后再算，钱已经付了，终止也来不及省。
        注意：四个维度独立检查，不能合成一个'钱'（瓶颈常常只有一个）。
        """
        if self.step >= self.max_steps:
            return "budget_steps"
        if self.used_calls + 1 > self.max_calls:
            return "budget_cost"
        if self.used_tokens + est_tokens > self.max_tokens:
            return "budget_cost"
        if self.used_seconds() + est_seconds > self.max_seconds:
            return "budget_cost"
        return None

    def used_seconds(self, now: float = 0.0) -> float:
        return max(0.0, now - self.started)

# ============ 闸 3：带滞回与冷却的判据 ============
@dataclass
class HysteresisGate:
    """
    振荡的两个修法都在这里：
      · 滞回：进入完成用 tau_high，退出用 tau_low，带宽必须 > 2·sd(噪声)
      · 冷却：窗口 w 内至少 m 次越阈才算完成（低通滤波）
    设计决策：默认'偏保守' —— 假阳性（虚假完成）的代价通常远高于假阴性。
    """
    tau_high: float = 0.95
    tau_low: float = 0.80
    window: int = 3
    min_hits: int = 2
    _history: list = field(default_factory=list)
    _in_done: bool = False

    def band_ok(self, noise_sd: float) -> bool:
        """自检：滞回带宽是否真的能压住噪声抖动？不满足就该加宽或加冷却。"""
        return (self.tau_high - self.tau_low) > 2 * noise_sd

    def update(self, score: float) -> bool:
        self._history.append(score)
        if len(self._history) > self.window:
            self._history.pop(0)
        hits = sum(1 for s in self._history if s >= self.tau_high)
        if not self._in_done and hits >= self.min_hits:
            self._in_done = True                 # 进入"完成"态需要多次越阈（防抖动）
        elif self._in_done and score < self.tau_low:
            self._in_done = False                # 退出需要跌破下阈（滞回）
        return self._in_done

def hard_and_quality(hard_constraints: list, quality_score: float, tau: float) -> tuple[bool, str]:
    """
    组合逻辑：硬约束 AND 质量分。
    设计决策：硬约束绝不进打分加权 —— 它们的假阳性代价是'事故'，不是'不够好'。
    """
    for name, ok in hard_constraints:
        if not ok:
            return False, f"硬约束不成立: {name}"
    return (quality_score >= tau), f"质量分 {quality_score:.3f} vs 阈值 {tau:.3f}"

# ============ 代价最优阈值（第四节）============
def optimal_tau(table: list[tuple[float, float, float]],
                cost_fp: float, cost_fn: float) -> dict:
    """
    table: [(tau, alpha_hat, beta_hat), ...] —— 从离线评测集估出（第 7 章）
    ★ 设计决策：把两个代价显式参数化。说不出 cost_fp/cost_fn 的团队，
      它的阈值就是未经设计的（无论看起来多合理）。
    """
    scored = [(tau, a * cost_fp + b * cost_fn, a, b) for tau, a, b in table]
    tau, J, a, b = min(scored, key=lambda x: x[1])
    return {"最优阈值": tau, "期望代价": round(J, 3),
            "该点假阳性": a, "该点假阴性": b,
            "保守度(成本比)": round(cost_fp / cost_fn, 1)}

# ============ 终止状态：必须可解释 ============
STATUSES = {
    "done":         "目标达成，判据全部通过",
    "budget_steps": "步数耗尽 —— 必须附：当前进展 / 卡在哪一步 / 还差什么",
    "budget_cost":  "成本或时延耗尽 —— 必须附：已完成的子目标",
    "violation":    "硬约束被违反 —— 必须附：哪条 / 哪一步 / 当前状态",
    "blocked":      "挂起等外部事件 —— 必须附：等什么 / 超时策略",
    "need_human":   "需人工判定 —— 必须附：为什么自动判据不适用",
    "undecidable":  "判据无法定义 —— 必须附：建议的验收标准",
    "error":        "执行崩溃 —— 必须附：可重放所需的全部信息",
}

def stop_reason(status: str, **ctx) -> dict:
    """
    ★ 一个只返回 None 的失败是最昂贵的失败：它把成本转嫁给了人。
    任何终止都必须带上足以让下游做决策的上下文。
    """
    assert status in STATUSES, f"未知终止状态: {status}"
    return {"status": status, "why": STATUSES[status], **ctx}

if __name__ == "__main__":
    # 阈值选择：假阳性代价是假阴性的 20 倍（'错误交付给客户' vs '多跑一次'）
    table = [(0.60, .30, .02), (0.80, .12, .08), (0.90, .05, .18),
             (0.95, .02, .30), (0.99, .005, .55), (0.995, .002, .72)]
    print("保守场景(C_fp=20):", optimal_tau(table, cost_fp=20, cost_fn=1))
    print("宽松场景(C_fp=2) :", optimal_tau(table, cost_fp=2, cost_fn=1))

    # 滞回带自检：噪声 sd=0.05 时，带宽 0.15 是否够？
    g = HysteresisGate(tau_high=.95, tau_low=.80)
    print("带宽是否压得住噪声(sd=0.05):", g.band_ok(0.05), "| sd=0.10:", g.band_ok(0.10))

    # 振荡演示：分数在阈值附近抖动 → 冷却门不会误报完成
    import random
    random.seed(0)
    for s in [0.96, 0.78, 0.97, 0.79, 0.96, 0.81, 0.95]:
        print(f"  score={s:.2f} → done={g.update(s)}")

四处关键设计决策：

  1. precheck 用 est_tokens 上界而不是事后统计 —— 这是"成本可控"能否兑现的唯一实现方式。
  2. HysteresisGate.band_ok 把"滞回带宽 vs 噪声"变成可自检的条件（>2σ），而不是一个神秘常数。
  3. hard_and_quality 坚持"硬约束 AND、质量分阈值"的组合方式 —— 混在一起会让你无法在不放松安全的前提下调严格度。
  4. optimal_tau 显式要求 cost_fp/cost_fn 两个业务数字。这是本节最重要的产出的代码形态：阈值不是一个可以拍的超参数，它是一个需要业务输入的最优化问题的解。

练习#

  1. 滞回带设计：某判据的进度分在"接近完成"区域的噪声标准差是 0.06，均值进展约 0.004/步。请给出 τhigh​、τlow​ 和窗口 w,m 的建议值，并说明：如果噪声标准差实际是 0.15（你估错了），你的设计会怎样失败？怎么在线检测"我估错了"？
  2. 代价算阈值：某内部工具（错了重跑即可）的 Cfp​=1、Cfn​=2。用第四节的表算最优阈值。再算 Cfp​=50（对外发报告）时的最优阈值。解释这个移动方向，并说明"为什么同一个 Agent 面向内部和面向客户时，终止阈值应该不同"。
  3. 奖励黑客攻防：下面四条判据各举出一个"字面满足但实际没完成"的绕过方式，并给出加固方案（要说明加固后判据的检查对象从"声明"变成了"事实"）： （a）"输出中包含 tests passed"；（b）"目标文件已存在"；（c）"所有 TODO 已清除"；（d）"输出的 JSON schema 合法"。
  4. 收敛诊断：某 Agent 在 100 次运行里有 70 次在 4 步内结束，输出是"我需要更多信息才能继续"（但工具集里明明有它没查的数据源）。判断这属于第三节三种现象里的哪一种，给出机制解释和修复方向（提示：不动点 + 判据可满足性）。
  5. 终止状态枚举：为一个"自动把论文草稿格式化成期刊模板并提交"的 Agent 写出完整的终止状态枚举，每个状态附上必须携带的上下文。特别处理"提交"这个不可逆动作：如果它在第 7 步已经提交、第 9 步发现格式错了，此时该返回哪个状态？该附带什么？
  6. 不可判定任务：为"写一份足够好的行业报告"设计收场方案。要求：写出你的"质量分"由哪几项构成（要可计算）、哪些硬约束用 AND 守住、以及预算耗尽时的交付形态（附什么标注）。然后论证：为什么"再让模型自我评审一轮"不是这个任务的正确解法？

小结#

  • 终止是两个问题：循环会停（结构保证，由预算/计数器提供）≠ 停在正确状态（语义保证，由验证器提供）。绝大多数事故属于后者。
  • 三把闸缺一不可：步数拦死循环、预算拦成本失控、置信度拦"原地打转"。它们拦的失效模式互不覆盖。
  • 预算必须执行前预检（用 max_tokens 之类的上界估计），事后统计只让你知道自己超了。
  • 置信度闸的可靠性递增顺序：确定性判据 > 独立评审 > 模型自评（最低）。自评 s^ 一旦成为终止条件就会被优化 —— 把自评当信号（触发额外验证），不要当判据（直接停）。
  • 判据组合：硬约束用 AND 单独守（假阳性=事故），质量用打分+阈值（假阳性=不够好）。混在一起会让你无法在不放松安全的前提下调严格度。
  • 振荡的数学条件：E[Δs]≈0 且噪声幅度 > 到阈值的距离。两个修法：滞回（带宽 >2σ）与冷却/投票（窗口 w 内 m 次越阈）；两者都用"容忍假阴性"换"消除抖动"。
  • 收敛 ≠ 成功：压缩映射收敛到的是"更新算子的不动点"，未必是目标状态。"循环稳定 + 结果不对" ⇒ 问题在判据或工具集，不在循环。
  • 奖励黑客：任何可被模型写入的信号都会被优化。防御顺序：判据不可由被测对象写入 > 检查外部事实 > 多判据 AND > 判据与提示词分离。不要把真实终止判据放进系统提示词。
  • 阈值是代价最优化问题的解：J(τ)=α(τ)Cfp​+β(τ)Cfn​。当假阳性代价高（对外交付）时，最优阈值远高于直觉；说不出 Cfp​/Cfn​ 的团队，其阈值是未经设计的。
  • 不可判定任务只能设计收场方式（预算耗尽交付最好版本 / 挂起求人 / 降级交付 / 拒绝并索取验收标准），并且任何终止状态都必须携带足以让下游决策的上下文 —— 只返回 None 的失败是最昂贵的失败。

下一节：循环跑起来了、也停得下来了。但你怎么知道它为什么这么跑、为什么在这儿停？ 轨迹、因果链、每步的输入输出与代价 —— 这既是第 1 章"可观测"目标的落地，也是第 7 章评测的数据前提。没有轨迹，就没有归因。
