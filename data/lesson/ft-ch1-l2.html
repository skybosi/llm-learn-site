微调 vs 提示#

拿到一个 LLM，想让它的行为符合预期，有两条基本路线：提示工程（prompt engineering） 和 微调（fine-tuning）。前者不改权重，靠"说话方式"引导模型；后者改权重，靠"训练"塑造模型。本课系统对比两者，帮你建立"什么时候该用哪个"的决策框架。

一、概念讲解#

1. 两条路线的本质区别#

维度 提示工程 微调
是否改权重 否，权重冻结 是，更新部分或全部参数
生效方式 每次请求都把指令/示例写进上下文 把行为"固化"进权重，一次训练长期生效
需要的"资源" 推理时的 token（上下文越长越贵） 训练时的数据、算力、显存
迭代速度 分钟级，改了提示马上试 小时到天级，要准备数据 + 训练 + 评估
稳定性 依赖模型对提示的敏感度，易漂移 对特定行为更稳定、可复现
可更新性 随时改提示即可 需要重新训练或合并新适配器

核心区别可以这样记：提示是"每次临时叮嘱"，微调是"内化成本能"。叮嘱灵活但每次都要重复、还占用上下文；本能省事但要花时间养成。

2. 提示工程的能力边界#

提示工程的手段包括：零样本指令、少样本示例（in-context learning）、思维链（CoT）、结构化输出约束等。它的优势是零训练成本、即改即用。但它有几条硬边界：

  • 上下文长度有限：示例越多越占 token，成本线性上升，而且受模型上下文窗口限制。
  • 稳定性差：同一提示换一个模型、甚至换一个采样温度，输出就可能漂移。
  • 可注入的能力有限：靠几十个示例，很难稳定教会模型复杂的格式规范或深层的领域推理。
  • 知识无法持久：每次都重复大量背景知识，既贵又容易被长上下文"稀释"。

一句话：提示工程适合"临时、简单、可容忍偶尔失败"的场景。

3. 微调带来的"持久改变"#

微调把行为写进权重，换来的是：

  • 零/少示例：训练好之后，一个短指令就能稳定触发目标行为，不必每次都贴几十个示例。
  • 格式稳定：结构化输出、分类标签这类"机械重复"的要求，微调后复现率显著提高。
  • 降低推理成本：不需要在每个请求里重复背景知识和示例，token 开销下降。
  • 专属风格：客服话术、品牌人格这种需要长期一致的东西，微调更可靠。

代价是前期投入：要收集高质量数据、要训练、要评估，还要防止灾难性遗忘。

4. 决策框架：先提示，后微调#

一个实用的判断顺序是：

  1. 先用提示：写清楚角色、任务、输出格式，加几个示例。能稳定达到要求就到此为止。
  2. 提示不够时再加 RAG：如果缺的是"事实/知识"，把资料检索进上下文，通常比微调更合适。
  3. 仍不够才微调：当且仅当——需要长期稳定复现某种格式/风格/行为，或提示+示例的 token 成本已经高到不划算，或领域数据是私有的、无法靠检索获得时，再投入微调。
  4. 组合使用：实际产品里常见"微调打底 + 提示微调细节 + RAG 供知识"的组合，而不是二选一。

5. RAG：第三条路，别混淆#

这里补一个容易被忽略的角色——检索增强生成（RAG）。很多人把"模型不懂我的业务"直接等同于"要微调"，但其实：

  • RAG 解决"知识不足/过时"：把资料向量化后按需检索进上下文，知识更新快、可溯源。
  • 微调解决"行为/格式/风格"：把稳定的行为模式写进权重。

两者正交，常一起用。判断口诀："记不住"靠 RAG，"学不会（行为）"靠微调。

二、可运行代码示例#

下面用一段代码量化提示工程的上下文成本：少样本提示的 token 数会随示例数量线性增长，而微调后的模型理论上不需要这些示例。

from transformers import AutoTokenizer

# 任选一个分词器来估算 token 数（演示逻辑，与具体模型无关）
tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B")

# 模拟"业务分类"任务的少样本示例
examples = [
    {"q": "我的订单三天了还没发货，怎么回事？", "a": "物流咨询"},
    {"q": "这个商品可以七天无理由退货吗？", "a": "退换货政策"},
    {"q": "优惠券为什么用不了？", "a": "优惠券问题"},
]

def build_few_shot_prompt(examples, query):
    """把示例逐个拼进上下文，模拟 in-context learning 的 token 成本"""
    prompt = "你是客服工单分类助手。请把用户问题归入以下类别之一：物流咨询 / 退换货政策 / 优惠券问题。\n\n"
    for e in examples:
        prompt += f"问：{e['q']}\n答：{e['a']}\n\n"
    prompt += f"问：{query}\n答："
    return prompt

# 观察：示例越多，整个 prompt 占用的 token 越多
for k in [0, 1, 2, 3]:
    prompt = build_few_shot_prompt(examples[:k], "帮我查一下退款进度")
    n_tokens = tokenizer(prompt, return_tensors="pt")["input_ids"].shape[1]
    print(f"使用 {k} 个示例时，prompt 占 {n_tokens} 个 token")

print("\n结论：少样本提示的 token 成本随示例数线性增长，")
print("     而微调后的模型只需一句短指令即可稳定完成分类，")
print("     省去了每次重复示例的开销。")

再看一个"格式稳定性"的对比示意：我们模拟同一个任务被"提示"与"微调"两种方式处理时的差异（这里用字符串模拟输出，重点是展示格式漂移问题）。

# 模拟：同一分类任务，提示工程在多次调用中可能出现格式漂移
prompt_outputs = [
    "这个属于物流咨询。",
    "分类结果：物流咨询",
    "物流咨询",
    "我认为是：物流咨询类",
]
print("提示工程（多次调用的输出格式不稳定）：")
for i, out in enumerate(prompt_outputs, 1):
    print(f"  第 {i} 次: {out}")

# 微调后的模型被训练成固定输出 JSON，格式高度一致
finetuned_outputs = [
    '{"category": "物流咨询"}',
    '{"category": "物流咨询"}',
    '{"category": "物流咨询"}',
]
print("\n微调后（稳定输出结构化 JSON）：")
for out in finetuned_outputs:
    print(f"  {out}")

print("\n要点：提示工程能'碰巧'输出对的内容，但格式每次都可能变；")
print("     微调把格式规范内化进权重，输出可被下游程序稳定解析。")

三、练习#

  1. 分类判断：下列场景，分别优先选"提示工程 / RAG / 微调"中的哪一种？
    • (a) 客服机器人需要长期稳定地使用敬语和固定话术模板；
    • (b) 回答"公司最新的退款政策"这类会随时间变化的制度；
    • (c) 临时让模型把一段文字总结成 3 条要点。
  2. 成本分析：一个任务需要 20 个少样本示例，每个示例约 80 token，每天调用 10 万次。估算一下仅示例部分的每日 token 开销；再想想微调后这 20 个示例是否可以省掉。
  3. 动手实验：修改上面的 examples 列表，增加一个"退款进度咨询"类别，重新运行 token 统计，观察成本随示例增加的变化。
  4. 思考题：为什么"微调 + RAG + 提示"三者组合在真实产品里很常见？它们各自承担什么角色，会不会互相冲突？
