内存序与可见性：为什么有些 kernel 必须 fence#

"我用了 atomic，为什么还是错的？"——因为原子性（atomicity）和顺序性（ordering）是两件独立的事。atomicAdd 保证一次读-改-写不被打断，却不保证你之前写的别的变量已经对别人可见。本课把这件事讲到底：什么叫 happens-before、作用域为什么必须匹配、以及 __threadfence() 到底在保证什么。

一、概念讲解#

1. 一个 6 种执行的 litmus test#

取官方文档给出的最小例子：Block 0 的线程写 x = 42，然后置标志 f = 1；Block 1 的线程自旋等到 f == 1，再断言 x == 42。

  • 若 f 的 store 与 load 都是 relaxed（默认）语义，"f 先落地、x 后落地"是一种合法执行——读者看到 f == 1 却读到 x == 0。枚举两次 store 的落地顺序 × 两条 load 的插入位置共 6 种可行执行，其中 1 种失败。
  • 把 f 的 store 改成 release、load 改成 acquire，0 种失败。release/acquire 建立 happens-before 边：release 之前的全部写，对成功 acquire 到该值的线程可见。
  • 若 f 用 block 作用域而读方在另一个 block——又变成 1 种失败。两边都是原子的，但作用域不含对方线程，这不是顺序问题，而是数据竞争（data race），行为未定义。

结论：原子性解决"不丢更新"，内存序解决"顺序能否被观察到"，作用域解决"这套保证对谁有效"——三者缺一不可。

2. 模型：happens-before 与作用域#

C++ 内存模型的核心是两个关系：sequenced-before（同一线程内的程序顺序）与 synchronizes-with（跨线程的成对同步），二者组合出 happens-before。CUDA 的贡献是给 synchronizes-with 加了一个参数——作用域：

作用域 覆盖范围 典型用法
cuda::thread_scope_thread 只有自己 单线程内
cuda::thread_scope_block 同一个 block __syncthreads 覆盖的那批线程
cuda::thread_scope_device 同一张卡上的所有线程（同一 memory synchronization domain） 跨 block 的发布-订阅
cuda::thread_scope_system 整机，含 CPU 与其它 GPU 多卡/与主机通信

官方对原子性的定义直接挂在这个参数上：只有操作的作用域包含了执行另一个操作的线程，两者才真正"原子"。所以 thread_scope_block 的 store 配 thread_scope_device 的 load 是未定义行为——即使两边都用了原子指令。

3. 四种内存序，各自买什么#

内存序 保证 代价
relaxed 只有原子性，无顺序 最低
acquire 之后的读写不能上移到它前面 中
release 之前的读写不能下移到它后面 中
acq_rel / seq_cst 两个方向都有；seq_cst 额外要求全局单一总序 最高

配套入口有三类：cuda::atomic_ref<T, Scope> 的 load(acquire) / store(release)、cuda::atomic<T, Scope>、以及 __threadfence*() 系列。分工是：前两个把顺序绑在某个具体原子变量上；fence 不绑变量，是一条作用于线程的顺序屏障。

4. 三档 fence 与它们各自覆盖的范围#

入口 保证的范围
__threadfence_block() 本 block 内的内存操作顺序
__threadfence() 本 device 内的顺序（跨 block 的"我写完了"通知）
__threadfence_system() 含主机与其他 GPU 的系统范围顺序

"写到 global 之后、置标志之前插一句 __threadfence()"就是最经典的手写 release：本线程在这句之前发出的内存操作，在它之后发出的写之前完成并对 device 可见。它只是顺序保证、不是同步点：不等别的线程，也不保证对方"已经到了"。

5. 顺序之外还有编译器#

顺序问题不只来自硬件，也来自编译器。"自旋等标志位"的典型编译结果是：标志位被读进寄存器，循环里再也不回内存——即使硬件已经把新值写进 L2，自旋也永远看不到。可复现的两个观测：

  • 普通（非 volatile）标志：自旋 99 步后仍超时，永远拿不到数据；
  • volatile 标志：第 3 步就看到了新值。

volatile 强制每次访问回到内存层面，但它不提供跨线程的 happens-before，也不构成同步。正确分工是："volatile（或 relaxed 的 cuda::atomic_ref）负责让每次自旋真的去读，release/acquire 或 fence 负责顺序"。

6. 常见坑#

  • 以为 __syncthreads() 能跨 block：它只覆盖 block 内部；跨 block 的顺序要 fence + 原子标志，或者第 3 课的 grid 同步。
  • per-thread 循环里自旋读原子量：每轮都是一次 L2 事务；用第 3 课讲的"先读 shared 标志"或退避把它压下来。
  • device 写、host 读却没加 __threadfence_system()：mapped/pinned 内存上的通知会失效。
  • 拿 atomicAdd 当 fence 用：默认语义是 relaxed，不传递任何顺序（除非显式指定 release）。
  • 用 cuda::atomic_ref 忘了作用域参数：默认是 thread_scope_system，比实际需要的更贵，也会让习惯 device 语义的人读错代码。

二、可运行代码示例#

两段纯 Python 模拟（无 GPU）：枚举 litmus test 的全部可行执行、演示"编译器缓存标志位"的自旋失败与 volatile 修复，再给三种自旋做法的全局 load 次数。

# ===== 示例 1：litmus test —— 先写 x 再置 flag，对方能看到 x 吗？ =====
from itertools import permutations

def litmus(flag_order, scope_ok):
    """复现 CUDA Programming Guide §5.7.5 的 message passing 例子。
    写方 Block 0：x=42 然后 f=1；读方 Block 1：等到 f==1 后读 x。
    枚举写方两次 store 的落地顺序 × 读方两条 load 的插入位置 = 6 种可行执行。"""
    bad = 0
    for landed in permutations([("x", 42), ("f", 1)]):
        for insert in range(3):
            sched = list(landed[:insert]) + [("load_f", 0), ("load_x", 0)] + list(landed[insert:])
            x = f = 0
            seen_f = seen_x = None
            for op, v in sched:
                if op == "x":
                    x = v
                elif op == "f":
                    f = v
                elif op == "load_f":
                    seen_f = f
                else:
                    seen_x = x
            if seen_f == 1 and seen_x != 42:
                # 只有「f 是 release 且作用域覆盖读方」时，看到 f==1 才必然看到 x==42
                if flag_order == "relaxed" or not scope_ok:
                    bad += 1
    return bad

for name, order, scope in (
    ("relaxed store + relaxed load", "relaxed", True),
    ("release store + acquire load", "release", True),
    ("release/acquire，但用 block 作用域", "release", False),
):
    bad = litmus(order, scope)
    print(f"{name:<36} 6 种可行执行中有 {bad} 种读到 f==1 而 x==0 → {'不安全' if bad else '不会发生'}")

# ===== 示例 2：普通标志被编译器缓存进寄存器，自旋永远看不到 =====
def spin(flag_is_volatile, write_at):
    """生产者第 write_at 步把 flag 从 0 改成 1。
    普通变量的典型编译结果：循环里只读一次进寄存器；volatile 每次都回内存读。"""
    flag, data, cached, steps = 0, 0, 0, 0
    cached = flag                      # 循环之前取进的寄存器副本
    for step in range(1, 100):
        if step == write_at:           # 生产者
            data, flag = 42, 1
        steps += 1
        observed = flag if flag_is_volatile else cached
        if observed == 1:
            return steps, data
    return steps, None

for vol in (False, True):
    steps, data = spin(vol, 3)
    tag = "volatile 标志" if vol else "普通标志"
    print(f"{tag:<14} 自旋 {steps:>3} 步后读到 data = {data}"
          + ("（超时，永远看不到）" if data is None else ""))

# ===== 示例 3：把自旋的全局 load 量降下来 =====
def spin_loads(cycles, publish_every, mode):
    n = 0
    for c in range(1, cycles + 1):
        if mode == "每轮读全局":
            n += 1
        elif mode == "先读 shared，命中再读全局":
            n += 1 if c % publish_every == 0 else 0
        elif mode == "每轮读全局 + 8 轮退避":
            n += 1 if (c % 8 == 0 or c % publish_every == 0) else 0
    return n

CYCLES, PUB = 4096, 32
for mode in ("每轮读全局", "先读 shared，命中再读全局", "每轮读全局 + 8 轮退避"):
    print(f"{mode:<22} 全局 load {spin_loads(CYCLES, PUB, mode):>5} 次")

在 Python 3.14.5（纯标准库）下实际运行结果：

relaxed store + relaxed load         6 种可行执行中有 1 种读到 f==1 而 x==0 → 不安全
release store + acquire load         6 种可行执行中有 0 种读到 f==1 而 x==0 → 不会发生
release/acquire，但用 block 作用域         6 种可行执行中有 1 种读到 f==1 而 x==0 → 不安全
普通标志           自旋  99 步后读到 data = None（超时，永远看不到）
volatile 标志    自旋   3 步后读到 data = 42
每轮读全局                  全局 load  4096 次
先读 shared，命中再读全局       全局 load   128 次
每轮读全局 + 8 轮退避          全局 load   512 次

第三段说明自旋优化的落点是减少 L2 事务次数（第 3 章的存储层次在这里兑现）：4096 轮只发布了 128 次新值，逐轮读全局要 4096 次 load，退避后降到 512 次，"先查 shared 副本、只在疑似变更时才读全局"降到 128 次——等于变更次数。

对应的 CUDA 写法：release/acquire 的原子标志、以及等价的显式 fence 版本。

#include <cuda/atomic>

// 版本 A：release/acquire —— 顺序绑在 flag 这个变量上
__global__ void producerAcqRel(int* x, cuda::atomic<int, cuda::thread_scope_device>* flag) {
    if (threadIdx.x == 0) {
        *x = 42;                                            // 数据
        flag->store(1, cuda::memory_order_release);          // 发布：x 的写先于 flag 可见
    }
}
__global__ void consumerAcqRel(const int* x, cuda::atomic<int, cuda::thread_scope_device>* flag,
                               int* ok) {
    while (flag->load(cuda::memory_order_acquire) != 1) { }  // 订阅：等到就必须能看到 x
    if (threadIdx.x == 0) *ok = (*x == 42);
}
// 版本 B：显式 fence —— 顺序不绑定任何变量，作用于本线程
__global__ void producerFence(int* x, int* flag) {
    if (threadIdx.x == 0) {
        *x = 42;
        __threadfence();          // 本 device 范围：x 的写在 flag 的写之前完成
        *flag = 1;                // 普通写即可，顺序由上面那句保证
    }
}
__global__ void consumerFence(const int* x, volatile int* flag, int* ok) {
    while (*flag != 1) { }        // volatile：每次自旋真的回内存读
    __threadfence();              // 读侧也要一句，拒绝把后面的读上移
    if (threadIdx.x == 0) *ok = (*x == 42);
}

三、练习#

  1. 实现：把示例 1 的 litmus 改成"写方先写 x 与 y 两个数据，再置标志"，重新数一遍 relaxed / release-acquire 两种语义下的失败执行数，解释为什么数量会变。
  2. 解释：为什么"两个操作都是原子的"仍然可能构成数据竞争？把答案拆成"原子性"与"作用域"两句话。
  3. 对比/验证：把示例 2 的 spin 改成"生产者每轮都改标志"，比较 volatile 与非 volatile 的自旋步数；再给非 volatile 版本加上编译器屏障（asm volatile("" ::: "memory")）看能否修复，并说明这为什么不是可移植做法。
  4. 思考：一个 kernel 每 32 轮才需要发布一次进度，你会选"每轮读全局标志"还是"先读 shared 副本"？如果消费者与生产者不在同一个 block，共享内存方案是否还成立？
