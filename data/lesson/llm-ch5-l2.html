上下文学习#

提示工程教你"怎么把指令写清楚"，而上下文学习（In-Context Learning, ICL）回答一个更惊人的现象：模型不需要任何梯度更新，只要在提示里放几个示例，就能"当场学会"一个它从未专门训练过的任务。本课讲清 ICL 是什么、它和传统微调的本质区别、为什么示例的选取与顺序如此重要。

一、概念讲解#

1. 什么是在上下文中学习#

上下文学习是指：把任务描述和若干输入—输出示例直接写进提示里，模型就能在不更新任何参数的前提下，对新输入给出符合任务规律的输出。按示例数量分三档：

  • zero-shot（零样本）：只给指令，不给示例。
  • one-shot（一样本）：给 1 个示例。
  • few-shot（少样本）：给少数几个示例（通常 2~8 个）。

例如做"情绪标签改写"：给 高兴 → 开心、难过 → 悲伤 两个示例后，模型就能把 生气 → ? 答成 愤怒——它从这个模式里"临时学会"了规则。

2. 与微调的本质区别#

维度 微调（fine-tuning） 上下文学习（ICL）
是否改参数 是，需要反向传播更新权重 否，权重完全冻结
"学习"发生在哪 参数里 上下文（激活/注意力）里
成本 需要数据、算力、训练时间 只需构造提示
持续性 永久改变模型 换一次对话就"遗忘"

ICL 是涌现能力（emergent ability）：只有模型大到一定规模后，few-shot 才显著优于 zero-shot；小模型给了示例也学不会。

3. 为什么示例能起作用#

直觉上，ICL 相当于"用示例在输入层做了一次隐式检索与模式匹配"：模型在注意力机制里把查询与示例对齐，从相似示例的"输入→输出"变换里归纳出规则，再套用到查询上。它并没有真的"改记忆"，而是在前向传播过程中即时完成了一次任务推理。

4. 示例的选取与顺序：ICL 的脆弱面#

ICL 对示例极其敏感：

  • 示例质量：错误、矛盾的示例会直接带偏模型。
  • 示例顺序：同样的示例，换个排列顺序，答案可能不同（顺序敏感）。
  • 标签映射：示例里输出标签的措辞（如 正面 vs 好）会影响模型一致性。
  • 示例分布：示例若只覆盖一种情况，模型对新情况泛化就差。

因此，ICL 不是"随便丢几个例子"，而是需要像调参一样精挑细选、反复试验。

二、可运行示例#

下面的代码用一个最近邻检索式 mock，直观演示 ICL 的核心机制：模型"看到示例后"才能对新输入套用规则，示例越接近查询、越一致，效果越好。

# —— 一个"靠上下文里的示例"来完成任务的最小模型示意 ——
# 任务：把中文情绪词改写成同义表达。
# 关键设定：模型"参数里"其实存有同义词知识（类比真实模型的记忆），
# 但它不知道"现在要做的是同义词改写"——除非示例把这个任务格式点破。

SYNONYMS = {"生气": "愤怒", "高兴": "开心", "难过": "悲伤", "害怕": "恐惧"}

def mock_icl(query, demonstrations):
    """只有从示例中认出'这是同义词改写任务'时，才调用内部知识作答。"""
    if not demonstrations:
        return "（没有示例，猜不出你想让我做什么）"          # zero-shot：不知道任务格式
    # 识别任务格式：所有示例都应是 '词 -> 词'，且示例里的词都是同义词表的一员
    looks_like_synonym = all(len(p) == 2 and p[0] in SYNONYMS for p in demonstrations)
    if not looks_like_synonym:
        return "（示例对不上任务，无法确定你要做什么）"        # 示例质量差 → 认不出任务
    return SYNONYMS.get(query, "（不认识这个词）")

query = "生气"

# 1. zero-shot：没有示例，模型认不出任务格式，空有知识也使不出来
print("zero-shot :", mock_icl(query, []))

# 2. few-shot：相关示例点破任务，模型"唤醒"内部知识，正确作答
good_demos = [("高兴", "开心"), ("难过", "悲伤"), ("害怕", "恐惧")]
print("few-shot  :", mock_icl(query, good_demos))

# 3. 劣质示例：示例与任务无关，模型认不出格式，依然失败
bad_demos = [("苹果", "水果"), ("桌子", "家具")]
print("劣质示例 :", mock_icl(query, bad_demos))

这个 mock 复现了 ICL 最反直觉的一点：模型的知识一直在"参数里"，但它需要示例告诉它"现在要做什么"，才会调用这份知识——这正是 GPT-3 观察到的现象：同样的模型，zero-shot 答不出，加几个示例就答得出，而参数一个都没变。真实模型里，"从示例中认出任务并唤醒相应能力"由注意力机制在千亿参数上完成，机制远比这里复杂，但"零梯度更新、靠上下文激发"的本质完全一致。

三、练习#

  1. 设计实验：为任务"把英文单词变成复数"写 5 条 few-shot 示例，注意覆盖以 s、y、f 结尾的不同规则，说明你为何这样选。
  2. 破坏格式识别：往 good_demos 里混入一条无关示例（如 ("苹果", "水果")），观察 looks_like_synonym 如何从"认出任务"变成"认不出"，说明示例一致性的重要性。
  3. 对比 zero/few：选一个真实 LLM（如有 API），对同一任务分别用 zero-shot 和 5-shot 各问 5 次，记录准确率差异，验证 ICL 的收益。
  4. 思考成本：few-shot 提示更长，会消耗更多 token、可能顶到上下文窗口。讨论"示例数量"与"上下文长度预算"的权衡。
  5. 思考边界：ICL 能在多大程度上替代微调？什么情况下必须微调、什么情况下提示就够？
