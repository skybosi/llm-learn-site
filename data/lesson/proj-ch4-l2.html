核心实现（本地部署与成本核算）#

上一课定好了选型，这一课真正动手：搭环境 → 部署 FP16 基准 → 部署 AWQ/GPTQ/GGUF 三种量化 → 压测。每一步都给出可运行的命令和脚本，中文注释说明"为什么这么写"。做完这一课，你的项目就有了真实的显存、吞吐、延迟数据。

一、目标与步骤#

本课完成后，你应当跑通四条部署路线并拿到它们的实测数据：

路线 引擎 量化 输出
基准 vLLM FP16/BF16 显存/吞吐/延迟基线
在线量化 vLLM AWQ（INT4） 对比 FP16
在线量化 vLLM GPTQ（INT4） 对比 FP16
低资源 llama.cpp GGUF（Q4_K_M） CPU/边缘路线

分步：① 准备环境（CUDA + Python + Docker）→ ② vLLM 部署 FP16 → ③ vLLM 部署 AWQ/GPTQ → ④ llama.cpp 部署 GGUF → ⑤ 统一压测脚本 → ⑥ 记录 nvidia-smi 显存。

二、实现指导与代码骨架#

步骤 1：准备环境#

推荐用 Docker 隔离（vLLM 官方镜像自带 CUDA，最省心），也可以 conda 自建。二选一：

# 方案 A：conda 自建（需要先装好匹配的 NVIDIA 驱动与 CUDA toolkit）
conda create -n llm-deploy python=3.10 -y
conda activate llm-deploy
pip install vllm            # vLLM 会携带必要的 CUDA 运行时

# 方案 B：Docker（官方镜像，显卡用 --gpus all 透传）
docker pull vllm/vllm-openai:latest
docker run --gpus all -p 8000:8000 \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  vllm/vllm-openai:latest --model Qwen/Qwen2.5-7B-Instruct

环境坑：CUDA 版本、驱动版本、PyTorch/vLLM 版本三者要匹配。若 pip install vllm 报 CUDA 相关错误，优先改用 Docker 镜像，避免在驱动上折腾。

步骤 2：vLLM 部署 FP16 基准#

一条命令起服务，暴露 OpenAI 兼容接口：

vllm serve Qwen/Qwen2.5-7B-Instruct \
  --dtype bfloat16 \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90 \
  --host 0.0.0.0 --port 8000

参数含义：

  • --max-model-len 8192：最大序列长度，直接决定 KV Cache 上限；设太大显存爆，设太小长输入被截断。
  • --gpu-memory-utilization 0.90：允许 vLLM 占用 90% 显存，留 10% 给激活与系统，是"显存利用率 vs 稳定"的常用折中。
  • 服务起来后，接口地址为 http://localhost:8000/v1（OpenAI 兼容）。

步骤 3：vLLM 部署 AWQ / GPTQ 量化#

量化权重通常是预先量化好、上传到 HuggingFace 的现成模型（如 Qwen/Qwen2.5-7B-Instruct-AWQ、...-GPTQ-Int4），部署时用 --quantization 指定，vLLM 会自动识别并加载对应内核。

# AWQ（4-bit 权重量化，激活感知，保护重要通道）
vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ \
  --quantization awq \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90 --port 8001

# GPTQ（4-bit，二阶误差补偿的逐层量化）
vllm serve Qwen/Qwen2.5-7B-Instruct-GPTQ-Int4 \
  --quantization gptq \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90 --port 8002

想自己从 FP16 权重量化出 AWQ/GPTQ（而非直接下载现成量化版），用 autoawq / optimum 跑量化脚本即可；但项目里直接用官方量化版更稳、更可复现，且面试时能讲清"量化是离线做好的，部署是加载"这一层。

步骤 4：llama.cpp 部署 GGUF#

llama.cpp 走 GGUF 单文件，CPU 都能跑，有 N 卡可把层卸载到 GPU 加速。

# 1) 克隆并编译（Windows 也可用 CMake 或预编译二进制）
git clone https://github.com/ggerganov/llama.cpp
cd llama.cpp
cmake -B build -DGGML_CUDA=ON        # 有 NVIDIA 卡则开 CUDA
cmake --build build --config Release -j

# 2) 下载 Qwen2.5-7B-Instruct 的 GGUF 文件（Q4_K_M 是常用的 4-bit 档）
#    在 HuggingFace 搜索 "Qwen2.5-7B-Instruct-GGUF" 下载 qwen2.5-7b-instruct-q4_k_m.gguf

# 3) 启动 llama-server（-ngl 99 表示尽量把 99 层都卸载到 GPU）
./build/bin/llama-server \
  -m qwen2.5-7b-instruct-q4_k_m.gguf \
  -c 8192 \
  -ngl 99 \
  --host 0.0.0.0 --port 8080

llama.cpp 的量化档位极细：Q4_K_M（4-bit，质量/体积平衡，最常用）、Q5_K_M（5-bit，质量更高体积略大）、Q8_0（8-bit，接近原始）。GGUF 与 AWQ/GPTQ 不是同一套体系：GGUF 是 llama.cpp 的容器格式，AWQ/GPTQ 是 vLLM 系 GPU 部署的量化算法，对比时务必注明用的是哪条路线。

步骤 5：统一压测脚本#

用 OpenAI 兼容接口写一个异步压测脚本，并发发请求，采集三个指标：

  • TTFT：从发请求到第一个 token 的时间（用户"开始看到字"的延迟）；
  • TPOT：平均每个 token 的生成时间（"出字速度"）；
  • 吞吐：服务端整体 tokens/s（并发下看服务能力）。
# -*- coding: utf-8 -*-
# benchmark.py —— 并发压测 vLLM / llama.cpp 的 OpenAI 兼容接口
# 用法：python benchmark.py --base-url http://localhost:8000/v1 --concurrency 8
import argparse, asyncio, time
from openai import AsyncOpenAI

PROMPT = "请用三句话介绍人工智能，并各举一个真实应用例子。"

async def one_request(client, model):
    """单次流式请求，返回 (TTFT秒, 生成token数, 生成总耗时秒)。"""
    t0 = time.perf_counter()
    first = None
    n_tokens = 0
    stream = await client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": PROMPT}],
        max_tokens=128,
        stream=True,
    )
    async for chunk in stream:
        if chunk.choices and chunk.choices[0].delta.content:
            if first is None:
                first = time.perf_counter()      # 第一个 token 到达
            n_tokens += 1
    t1 = time.perf_counter()
    ttft = (first - t0) if first is not None else (t1 - t0)
    return ttft, n_tokens, (t1 - t0)

async def main(base_url, model, concurrency, requests):
    client = AsyncOpenAI(base_url=base_url, api_key="EMPTY")
    tasks = [one_request(client, model) for _ in range(requests)]
    # 用信号量控制"同时在进行"的请求数
    sem = asyncio.Semaphore(concurrency)
    async def limited():
        async with sem:
            return await one_request(client, model)
    t0 = time.perf_counter()
    results = await asyncio.gather(*(limited() for _ in range(requests)))
    wall = time.perf_counter() - t0
    ttfts = [r[0] for r in results]
    total_tokens = sum(r[1] for r in results)
    total_gen = sum(r[2] for r in results)
    ttfts.sort()
    p50 = ttfts[int(len(ttfts)*0.5)]
    p99 = ttfts[int(len(ttfts)*0.99)]
    print(f"并发={concurrency} 请求数={requests} 总耗时={wall:.1f}s")
    print(f"吞吐(整体 tokens/s)={total_tokens/wall:.1f} "
          f"(仅生成阶段 {total_tokens/total_gen:.1f})")
    print(f"TTFT  P50={p50*1000:.0f}ms  P99={p99*1000:.0f}ms")
    print(f"TPOT(平均每token)={total_gen/total_tokens*1000:.0f}ms")

if __name__ == "__main__":
    p = argparse.ArgumentParser()
    p.add_argument("--base-url", default="http://localhost:8000/v1")
    p.add_argument("--model", default="Qwen/Qwen2.5-7B-Instruct")
    p.add_argument("--concurrency", type=int, default=8)
    p.add_argument("--requests", type=int, default=40)
    a = p.parse_args()
    asyncio.run(main(a.base_url, a.model, a.concurrency, a.requests))

分别对四个端口（8000 起 FP16、8001 起 AWQ、8002 起 GPTQ、8080 起 GGUF）跑同一脚本，--concurrency 从 1、4、8、16 递增，记录每个并发档的吞吐与 TTFT P99——这就是"并发压测曲线"的数据来源。llama.cpp 的 --model 参数填 GGUF 文件名。

步骤 6：记录显存（关键数据）#

每个服务运行中执行 nvidia-smi，记下 Memory-Usage（已用显存）与 GPU 利用率：

nvidia-smi --query-gpu=name,memory.used,memory.total,utilization.gpu \
  --format=csv,noheader

记表：FP16 显存 X GB、AWQ 显存 Y GB、GPTQ 显存 Z GB、GGUF(ngl=99) 显存 W GB。这组数字 + 压测数字，就是下一课成本核算报告的原材料。

三、验收与复盘#

1. 本课验收（实现完成标志）#

  • 四条路线（FP16 / AWQ / GPTQ / GGUF）都能起服务并返回正常回答；
  • 压测脚本对每条路线跑出 ≥ 3 个并发档的吞吐与 TTFT P99；
  • 记录了每条路线的 nvidia-smi 显存占用，数字真实可复现。

2. 动手练习#

  1. 把 --max-model-len 从 8192 改成 4096、16384，观察显存与吞吐怎么变，说明 KV Cache 上限的作用。
  2. 把 AWQ 的 --gpu-memory-utilization 从 0.90 提到 0.98，看能否在不 OOM 的前提下塞进更高并发——体会"显存利用率"的边界。
  3. 在 llama.cpp 上对比 Q4_K_M 与 Q8_0 两个 GGUF 档位的吞吐与回答质量，说明"量化档位"在体积/速度/质量之间的权衡。

3. 复盘要点（实现阶段要避开的坑）#

  • OOM（显存不足）：先降 --max-model-len 或 --gpu-memory-utilization，再考虑换量化；不要一报错就加卡。
  • 冷启动慢：vLLM 首次加载要编译 CUDA graph，属正常现象，压测要等服务完全就绪后再打。
  • "吞吐高"≠"延迟低"：并发越高吞吐越高，但单请求 TTFT 往往变长（排队），所以压测要同时记录吞吐和延迟分位数，缺一不可。
  • GGUF 与 AWQ/GPTQ 别混为一谈：前者是 llama.cpp 的文件格式，后者是 GPU 量化算法，报告里要分路线陈述。
