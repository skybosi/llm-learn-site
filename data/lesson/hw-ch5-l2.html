KV cache 显存#

如果说权重是"入场费"，那 KV cache 就是"按字计费"的部分——它随上下文长度线性增长，是长上下文推理时最常把显存打爆、触发 OOM 的元凶。学完本课，你应当能写出 KV cache 的显存公式，手算任意模型在任意上下文长度下要占多少，并理解为什么厂商纷纷引入 GQA/MQA 来压缩它。

一、概念讲解#

1. 自回归推理为什么要缓存 K 和 V#

大模型生成是逐 token 的：每生成一个 token，都要用它去"看"之前所有 token。在注意力机制里，每个 token 会算出三个向量——查询 Q、键 K、值 V。要算第 t 个 token 的注意力，需要前 t-1 个 token 的 K 和 V。如果每个 token 都从头重算一遍历史 K/V，计算量会随上下文平方增长，慢到无法接受。于是推理引擎把已经算出来的 K、V 缓存下来，新 token 只需算自己的一份 Q、K、V，再和缓存里的历史 K、V 做注意力——这就是 KV cache。

2. KV cache 显存公式#

缓存的东西就是每层、每个头的 K 和 V 向量。显存大小由五个量决定：

KV cache=2×L×Hkv​×dhead​×s×b×bytes

  • 2：K 和 V 各一份；
  • L：层数（layer）；
  • H_kv：KV 头数（注意不是注意力头数，GQA 下两者不同）；
  • d_head：每个头的维度；
  • s：序列长度（上下文 token 数）；
  • b：批量大小；
  • bytes：每个元素的字节数（FP16 为 2）。

每个 token 的增量是固定的：2×L×Hkv​×dhead​×bytes，总显存随上下文长度 线性增长。

3. GQA/MQA：压缩 KV 头数#

传统多头注意力（MHA）里，KV 头数 = 注意力头数。多查询注意力（MQA）让所有注意力头共享同一套 K/V（KV 头数 = 1），分组查询注意力（GQA）则是折中：若干个 Q 头共享一组 K/V。KV cache 正比于 KV 头数，所以从 MHA 改成 GQA 能成倍压缩 KV cache——这是 LLaMA-2/3、Mistral 等模型普遍采用 GQA 的直接动因。

4. 为什么 KV cache 是 OOM 元凶#

权重是固定的，KV cache 却会"越聊越大"。一个 7B 模型在 4K 上下文下的 KV cache 大约 2 GiB，看似不多；但上下文拉到 128K，就是 30 多倍，轻松超过权重本身。长文档问答、多轮对话、批量服务（batch 增大也会成倍放大）都会把 KV cache 推到失控。这就是"为什么 OOM 往往不是权重太大，而是 KV cache 涨爆"。

二、可运行示例#

用纯 Python 手算几款模型的 KV cache，并和它们的权重显存做对比。

# -*- coding: utf-8 -*-
# KV cache 显存 = 2 × 层数 × KV头数 × 头维度 × 序列长度 × 批量 × 每元素字节数

def kv_cache_per_token(num_layers, num_kv_heads, head_dim, bytes_per_elem=2):
    """每个 token 的 KV cache 字节数（K、V 各一份，故乘 2）。"""
    return 2 * num_layers * num_kv_heads * head_dim * bytes_per_elem

def kv_cache_gb(num_layers, num_kv_heads, head_dim, seq_len, batch=1, bytes_per_elem=2):
    """给定上下文长度与批量，返回（每 token 字节数, 总 GiB）。"""
    per_token = kv_cache_per_token(num_layers, num_kv_heads, head_dim, bytes_per_elem)
    total_bytes = per_token * seq_len * batch
    return per_token, total_bytes / (1024 ** 3)

# (层数, KV头数, 头维度)。GQA 下 KV 头数小于注意力头数，务必用 KV 头数。
configs = {
    "LLaMA-2 7B (MHA)":  (32, 32, 128),   # 32 个注意力头都各自有 K/V
    "LLaMA-3 8B (GQA)":  (32,  8, 128),   # 8 组共享 K/V
    "Mistral 7B (GQA)":  (32,  8, 128),
    "LLaMA-2 70B (GQA)": (80,  8, 128),
    "LLaMA-3 70B (GQA)": (80,  8, 128),
}

SEQ = 4096
print(f"上下文 {SEQ} token、batch=1、FP16 时的 KV cache：")
print(f"{'模型':<22} {'每token':>9} {'KV cache':>10}")
for name, (L, H, D) in configs.items():
    per_token, gb = kv_cache_gb(L, H, D, SEQ)
    print(f"{name:<22} {per_token/1024:>7.1f}KB {gb:>9.2f}GiB")

# 对比：KV cache 如何随上下文长度增长（以 LLaMA-3 8B 为例）
print("\nLLaMA-3 8B (GQA) 不同上下文下的 KV cache：")
for s in (1024, 4096, 16384, 65536, 131072):
    _, gb = kv_cache_gb(32, 8, 128, s)
    print(f"  上下文 {s:>6} token -> {gb:>7.2f} GiB")

# 对比：MHA 与 GQA 的差距（同 7B 规模，8 头 vs 32 头）
_, mha = kv_cache_gb(32, 32, 128, SEQ)
_, gqa = kv_cache_gb(32, 8, 128, SEQ)
print(f"\n同规模下 MHA={mha:.2f} GiB vs GQA={gqa:.2f} GiB，GQA 省了 {1 - gqa/mha:.0%}")

观察输出：7B 的 MHA 在 4K 上下文约占 2 GiB，而 GQA 只有约 0.5 GiB；上下文拉到 128K 时，8B GQA 模型的 KV cache 会涨到 16 GiB 上下，已经和它 16 GiB 的 FP16 权重相当——这正是长上下文场景显存紧张的原因。

三、练习#

  1. 手算：一个模型 40 层、8 个 KV 头、头维度 128，FP16 下每个 token 的 KV cache 是多少字节？2K 上下文共多少 GiB？
  2. 批量放大：把上面代码的 batch 改成 8 和 32，观察 KV cache 如何随批量成倍增长，说说为什么并发服务多用户时会迅速吃满显存。
  3. 换精度：把 bytes_per_elem 改成 4（FP32 存 KV）和 1（INT8 存 KV），计算 70B 模型 4K 上下文的变化，体会"KV cache 不随权重一起量化"的代价。
  4. MQA 极限：把 KV 头数设为 1（MQA），重算 8B 模型的 KV cache，对比 GQA 和 MHA，量化三种方案各自的压缩效果。
  5. 思考：为什么说"权重是入场费、KV cache 是按字计费"？如果一家 API 服务商要对长上下文额外收费，从显存角度你会怎么解释这笔费用的合理性？
