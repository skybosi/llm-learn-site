计划的表示与可验证性#

这一节要解决什么#

上一节给出了依赖图：任务分成几件、怎么排、哪些可以并行。但"分成几件"这个决定本身是怎么来的？在绝大多数 Agent 里，它来自模型生成的一段文本：

1. 先读取用户上传的合同，提取关键条款
2. 然后核对公司模板里对应的条款
3. 如果条款有差异，生成一份说明
4. 最后把说明发邮件给法务

这段话"看起来挺合理"。问题是：你能对这段文字做什么检查？

  • 它有没有漏掉一步？（例如"确认用户有权上传这份合同"）
  • 第 3 步的"如果"分支在哪判断？判断需要的信息第 1 步真的提取了吗？
  • 第 4 步是不可逆动作（发邮件）。它在第 3 步之后 —— 可第 3 步失败了呢？
  • 这四步总共会花多少钱？在预算内吗？
  • 如果第 2 步发现"公司模板里没有对应条款"，这个计划还成立吗？

对自然语言计划，这些问题一个都答不了 —— 不是答得不好，而是没有可判定的依据。 这一节要把"计划合法性"从"人读一遍觉得行"变成一组可以跑的检查，并明确这组检查的能力边界：有些缺陷静态检查能抓，有些只能在执行中暴露。

可验证性⟺∃f:Plan×Context→{ok,finding}∗且 f 与生成计划的模型无关

可验证性⟺∃f:Plan×Context→{ok,finding}∗且 f 与生成计划的模型无关

最后半句是关键：如果检查器是同一个模型再看一遍，它不是验证器，只是又一次采样。 独立证据是"可验证"这个词的全部重量所在。

学完这一节你应该能回答：

  • 自然语言的计划到底缺了什么，以至于它不可检查？
  • 一个计划至少要带上哪些字段，才可能被机器判定为"合法"？
  • 可验证性分几级？每一级能抓到什么、抓不到什么、成本多大？
  • 为什么"让模型自己检查一遍计划"不能替代结构检查？什么情况下它的自评有增量？
  • 哪些计划缺陷永远抓不到（只能靠执行中暴露或靠事后归因）？
  • 前置条件只能部分观测时怎么办？

一、为什么自然语言计划不可验证#

1.1 缺的不是"表达力"，是"可判定性"#

自然语言在表达力上强于任何形式化表示：它能描述含糊边界的意图、能隐喻、能省略公认的常识。问题在于它的语义结构不可判定 —— 你无法机械地判断"这两句话是否矛盾"、"这个动作的输入是否被前一个动作产出"、"这个条件的所有分支是否都被覆盖"。

可验证⟺存在一个与生成者独立的判定过程，且该过程可在有限步内给出结论

对自然语言计划，"是否存在漏步"这个判定问题是不可判定的（甚至无法形式化地陈述"漏步"）。所以可验证性的第一步不是"更仔细地读"，而是换表示。

1.2 一个计划要能被检查，至少要带三类字段#

从"可检查"这个要求反推，计划必须显式携带：

类别 字段 不写它会怎样
动作语义 动作名、参数、参数的取值约束 无法判断参数是否合法（第 3 章的 schema 正是为此）
前置条件 执行该动作前必须为真的事实（显式陈述） 无法判断"顺序是否可行"；漏步完全不可见
后置条件/效果 执行后世界新增/改变的事实 无法判断"目标是否被某个动作达成"；也无法串联前置链
资源 成本估计、时间、是否需要审批（第 7 章） 无法判断预算；无法定位"贵在哪一步"
依赖 数据依赖与控制依赖（第 1 节） 无法判断并行与回退边界

最关键的是"前置/后置"这一对。 它们把计划从"文字序列"变成"状态转移链"：

计划合法⊇∀i: Pre(ai​)⊆Si−1​,Si​=(Si−1​∖Del(ai​))∪Add(ai​)

也就是说，每个动作的前置必须是前面积累的状态的子集，然后把它声明的新增事实加进状态。这条式子就是"预演"（dry-run）的全部数学内容，也是 1.3 里"漏步"能被检测出来的原因：如果目标里有一个事实没有任何动作能产生，预演后目标不可达 —— 这就是漏步的形式化信号。

1.3 表示形式的取舍：JSON / DSL / 动作语言#

表示 可判定性 表达力 生成难度（对模型） 适用
自由文本 + 非正式步骤 无 最高 最低 人类阅读的最终方案；不可作为执行依据
结构化 JSON（带 pre/post） 结构可判定，语义需预演 中 中（模型容易漏字段，需要 schema 约束解码） 绝大多数 Agent 的落点
受限 DSL / 动作语言 高（可做形式检查） 低（必须预先定义谓词与动作模式） 高（模型必须严格贴语法，易出错） 高风险的窄域任务（付款、合规）

取舍的真正分界不是"形式化程度越高越好"，而是：

形式化的收益=能提前抓到的缺陷数×每个缺陷的代价

形式化的成本=造语言的成本+模型生成失败的返工率

窄域 + 高风险（付款、医疗、法务合规）→ 值得造 DSL，因为一个漏步的代价极高而动作空间很小。宽域 + 低风险（写调研报告）→ 结构化 JSON 就够，造 DSL 只会让模型生成失败率飙升。

一个常见的错误：为了"严谨"选了 DSL，结果模型的计划生成成功率从 95% 掉到 60%，于是系统里多了一堆"格式错误重试"，净效果是可靠性和成本都变差。形式化是手段，不是目的。

二、可验证性阶梯：四级检查#

把"检查一个计划"拆成四级，从便宜到贵。每一级都是独立可实现的，工程上应当四级都跑（因为成本差异大，且每级抓不同的缺陷）。

级别 检查什么 能抓到的缺陷 抓不到的 成本
L1 语法可解析 计划是不是合法结构（字段齐、类型对、枚举值合法） 缺字段、类型错、动作名不存在 一切语义问题 极低
L2 结构可检查 依赖图性质：无环、依赖存在、目标可达、写集合冲突 错序（成环）、悬空依赖、漏步（目标不可达）、假并行 前提在实际世界是否成立、参数取值是否荒谬 低
L3 语义可预演 用状态转移链模拟执行：每个动作的前置在当前模拟状态是否成立；后置是否与工具契约一致 前置不满足、前置链断裂、后置不产生目标 真实世界的偏差（库存没了、API 变了） 中
L4 效果可度量 成本/时间/副作用次数是否在预算内；是否有更优计划 越预算、副作用过多、明显次优 实际执行效率 中（需要成本模型）

2.1 L1：语法可解析#

最便宜也最容易被跳过的一级。它的价值在于把"格式错误"和"逻辑错误"分开：如果模型的输出连字段都不齐，重试生成是正确处置；如果是逻辑错误，重试同样的提示词通常无用（这是第 3 章"错误分类决定修复主体"的同一原则在计划上的应用）。

L1 的实际痛点：模型很擅长生成"看起来对但字段缺失"的 JSON。所以 L1 必须严格：缺一个必需字段就判 L1 失败，不要试图用默认值补齐 —— 补齐会掩盖真实的生成失败，让 L3 拿到一个语义上错误但结构完整的计划。

2.2 L2：结构可检查（接第 1 节）#

L2 就是第 1 节的依赖图算法加上三项计划特有检查：

GoalReachable⟺在预演后（或按动作效果闭包）目标事实集合⊆i⋃​Add(ai​)

L2 的检查清单：
  ① 环检测 → 错序（第 1 节 find_cycle）
  ② 悬空依赖 → 引用了不存在的节点或未被任何节点产出的输入
  ③ 目标可达性 → 每个目标事实都必须有动作声明能产生它 ★ 漏步的形式化检测
  ④ 必需输入可得性 → 每个动作的输入要么来自外部初始状态，要么来自某个前驱输出
  ⑤ 写集合冲突 → 假并行（第 1 节 false_parallelism）
  ⑥ 覆盖性 → 分支条件是否穷尽？（枚举条件的取值，检查是否所有分支都有对应动作）

第 ⑥ 条是最容易被漏掉的一条。计划里出现"如果条款有差异，则生成说明"时，如果没有"条款无差异"的分支，那么在某些输入下计划会停在半路 —— 而且不报错，因为它只是"没有下一步"。这类缺陷的检测方式是：把条件动作的条件取值枚举出来，检查每个取值下都有后继。这也是"计划必须显式声明条件"的原因（自然语言里的"如果"根本没法枚举）。

2.3 L3：语义可预演（符号执行）#

L3 是把计划在符号状态上跑一遍，而不是真的执行：

S0​a1​​S1​a2​​⋯an​​Sn​,每步要求 Pre(ai​)⊆Si−1​

三个必须支持的能力：

  1. 未知值：真实计划的很多前置无法静态判定（"库存充足"）。处理方式不是"跳过"，而是让它成为执行时必须优先验证的假设（见 2.5）。
  2. 分支：条件动作在预演时两个分支都要走一遍（分别生成两个后继状态），这样才知道每个分支是否都能到达目标。
  3. 副作用标记：预演时标记哪些动作是 irreversible（第 3 章的分类），因为它们在后续的预算/回退检查里权重不同。

L3 能抓到的、L2 抓不到的典型缺陷：

缺陷 为什么 L2 抓不到 L3 怎么抓
前置链断裂 L2 只看"输出名是否被产出"，不看"是否在同一分支上" 分支 A 产出的东西被分支 B 的后续使用
顺序可行但语义不可能 "先删除再查询"在名字上完全合法 删除动作的 Del 让查询的前置失效
条件分支不完整 图上看不出 某个分支的状态无法满足后续动作的前置
参数取值越界（部分） 结构合法 参数约束是静态可判的那部分能在预演时检查

2.4 L4：效果可度量#

L4 用第 1 节的关键路径与第 4 节的预算模型做量化检查：

  • 成本估计是否在预算内？（第 4 节会给出多维预算闸门）
  • 副作用次数是否超过允许值？
  • 是否存在明显更优的计划（同样达成目标但成本更低 / 更少不可逆动作）？

L4 的价值常常在于"否决一个能跑通的计划"：一个计划通过了 L1~L3，但做了 3 次不可逆操作而只需要 1 次 —— 这时候应该改计划，而不是执行它。

2.5 静态检查的边界：抓不到的四类#

这是本节必须说清的部分。以下四类缺陷在原理上就不是静态检查的对象：

缺陷类型 例子 只能在哪里发现 处置
前提在真实世界不成立 计划假设"用户有退款权限"，实际没有 执行时工具的拒绝（第 3 章的错误分类） 把前置转成"执行时优先验证的假设"
工具返回与后置条件不符 计划声明"生成 PDF"，工具实际返回 HTML 执行时的后置校验 每个副作用动作后校验后置，失败即计划失效
参数语义正确但取值荒谬 send_email(to="test@example.com", amount=999999) 无法穷举 → 只能靠阈值护栏/审批（第 7 章） 审批 + 限额
目标本身写错了 计划完美达成"把 A 改成 B"，但用户其实想要"保留 A 另存 B" 事后归因或人工发现 目标澄清（在第 1 章的目标-规格区分里）

第一、二条的正确做法是把它们"延期"到执行时，而不是假装静态检查覆盖了：把无法判定的前置记为"待验证假设"，并按危险度排序，让循环优先验证最危险的那一条（如果它不成立，后面全白做）。

待验证假设排序=按 P(不成立)×不成立时的返工代价 降序

这一条与第 3 章的工具契约接合：契约里的后置条件就是"执行时校验"的依据。契约写得越精确，L3 越强、执行时校验越有依据 —— 这就是为什么第 3 章说"schema 是能力边界"。

三、自评不是验证：为什么"让模型再检查一遍"不算#

这是本节最反直觉、也最有工程价值的一条。

自评=同一个（或同分布的）模型，对同一个上下文，再做一次采样

它提供的不是独立证据。具体危害有三：

  1. 错误相关：模型漏掉某一步的原因通常是对任务的理解有偏差；让它"再检查一遍"，它用的是同一个有偏差的理解，于是同一个漏步被漏掉两次。
  2. 迎合倾向：给模型看自己的计划并要求"检查是否有问题"，常见结果是把明显的问题也判为"没问题"（计划文本本身成了锚点，第 4 章的位置偏差在这里的形态）。
  3. 成本翻倍而信息增量为零：第二次调用花了钱，但没有引入任何计划之外的信息。

自评什么时候有增量？ 只有当它能接触到计划文本之外的新信息时：

有增量的自评形态 为什么有增量
带着工具契约文档去核对参数是否合法 引入了外部事实（契约）
带着真实的状态快照去核对前置 引入了环境观测
带着验收标准逐条对照目标 引入了独立于计划的规格
用不同的模型做检查（异源） 错误相关性下降（但不为零）

检查的独立性⟺检查者接触到了生成者没有/忽略的信息，或使用了不同的先验

所以工程上的正确做法是：结构检查（L1~L4）必须有；自评只能作为 L3 的补充，且要给它喂进计划之外的信息（契约、状态、规格），否则它只是"多花一次钱把错误再说一遍"。

代码：计划校验器 + 语义预演器#

下面的代码实现四级校验器：(1) 动作与计划的数据结构（带前置/后置/删除/成本）；(2) L1 语法、L2 结构、L3 预演（含分支与未知值）、L4 效果；(3) 待验证假设排序；(4) 自评与结构检查的对比演示（证明自评漏掉结构性缺陷）。

"""
ch5-l2：计划校验器 + 语义预演器。

设计目标：把"计划看起来合理"变成四级可跑的检查，并明确每级的能力边界。
关键设计决策都在注释里 —— 尤其是"未知前置"与"分支"的处理方式。
"""
from dataclasses import dataclass, field

UNKNOWN = "?"


@dataclass
class ActionSpec:
    """动作模式。

    ★ 设计决策：pre / add / delete 三者必须同时存在，缺一不可：
      · 只有 pre  → 无法串联（不知道前面能提供什么）
      · 只有 add  → 无法发现"先删后查"这类语义矛盾
      · 没有 delete → 状态只增不减，会把已失效的事实当成仍然成立
    """
    name: str
    params: dict[str, str]                  # 参数名 -> 类型（供 L1 检查）
    pre: set[str] = field(default_factory=set)      # 前置事实（必须由状态提供）
    add: set[str] = field(default_factory=set)      # 新增事实
    delete: set[str] = field(default_factory=set)   # 删除事实
    requires: set[str] = field(default_factory=set) # 数据依赖：需要的输入对象
    provides: set[str] = field(default_factory=set)  # 产出的对象
    cost: float = 1.0
    side_effect: str = "none"               # none | reversible | irreversible
    # ★ 声明为"假定成立"的前置：静态无法判定的世界事实（权限、库存、对方在线）。
    #   它们不是 error 也不是可忽略项，而是"执行时必须优先验证的假设"（2.5）。
    declared_pre: set[str] = field(default_factory=set)


@dataclass
class PlanAction:
    step: int
    spec: str
    args: dict[str, object] = field(default_factory=dict)
    depends_on: list[int] = field(default_factory=list)
    condition: tuple[str, object] | None = None      # (事实名, 期望值)；分支动作


@dataclass
class Plan:
    goal: set[str]
    actions: list[PlanAction]
    budget: float = 100.0


@dataclass
class Finding:
    level: str          # L1..L4
    severity: str       # error | warn
    where: str          # 定位：步骤号或 "plan"
    message: str


# ==================== L1：语法可解析 ====================
def check_level1(plan: Plan, specs: dict[str, ActionSpec]) -> list[Finding]:
    """★ 设计决策：L1 严格 —— 缺字段即 error，不用默认值补齐。

    补齐会掩盖真实的生成失败，让 L3 拿到"结构完整但语义错误"的计划，
    从而把生成问题误诊成语义问题。
    """
    out: list[Finding] = []
    if not plan.actions:
        out.append(Finding("L1", "error", "plan", "计划为空"))
    seen: set[int] = set()
    for a in plan.actions:
        if a.step in seen:
            out.append(Finding("L1", "error", f"step{a.step}", "步骤号重复"))
        seen.add(a.step)
        spec = specs.get(a.spec)
        if spec is None:
            out.append(Finding("L1", "error", f"step{a.step}", f"未知动作 {a.spec!r}"))
            continue
        missing = set(spec.params) - set(a.args)
        extra = set(a.args) - set(spec.params)
        if missing:
            out.append(Finding("L1", "error", f"step{a.step}", f"缺参数 {sorted(missing)}"))
        if extra:
            out.append(Finding("L1", "error", f"step{a.step}", f"多余参数 {sorted(extra)}"))
    return out


# ==================== L2：结构可检查 ====================
def check_level2(plan: Plan, specs: dict[str, ActionSpec],
                 initial: set[str]) -> list[Finding]:
    """无环 / 依赖存在 / 目标可达 / 输入可得 / 条件分支穷尽。"""
    out: list[Finding] = []
    by_step = {a.step: a for a in plan.actions}

    # ① 环检测
    adj = {a.step: list(a.depends_on) for a in plan.actions}
    state: dict[int, int] = {}

    def dfs(u: int, stack: list[int]) -> list[int] | None:
        state[u] = 1
        stack.append(u)
        for v in adj.get(u, []):
            if v not in by_step:
                continue
            if state.get(v, 0) == 1:
                return stack[stack.index(v):] + [v]
            if state.get(v, 0) == 0:
                got = dfs(v, stack)
                if got:
                    return got
        stack.pop()
        state[u] = 2
        return None

    for a in plan.actions:
        if state.get(a.step, 0) == 0:
            cyc = dfs(a.step, [])
            if cyc:
                out.append(Finding("L2", "error", f"step{cyc[0]}", f"依赖成环：{cyc}"))
                break

    # ② 悬空依赖
    for a in plan.actions:
        for d in a.depends_on:
            if d not in by_step:
                out.append(Finding("L2", "error", f"step{a.step}", f"依赖不存在的步骤 {d}"))

    # ③ 目标可达性（漏步的形式化检测）
    producible = set(initial)
    for a in plan.actions:
        producible |= specs[a.spec].add if a.spec in specs else set()
    for goal in sorted(plan.goal):
        if goal not in producible:
            out.append(Finding("L2", "error", "plan",
                               f"★ 漏步：目标事实 {goal!r} 没有任何动作能产生"))

    # ④ 输入可得性
    available = set(initial)
    for a in plan.actions:
        spec = specs.get(a.spec)
        if spec is None:
            continue
        lack = {r for r in spec.requires if r not in available and r not in producible}
        if lack:
            out.append(Finding("L2", "error", f"step{a.step}",
                               f"输入 {sorted(lack)} 既非初始可得也无处产出"))
        available |= spec.provides

    # ⑤ 条件分支穷尽（枚举条件事实的取值）
    conds: dict[str, set[object]] = {}
    for a in plan.actions:
        if a.condition:
            conds.setdefault(a.condition[0], set()).add(a.condition[1])
    for fact, vals in conds.items():
        if {True, False} - vals and len(vals) == 1:
            out.append(Finding("L2", "warn", "plan",
                               f"★ 条件 {fact!r} 只覆盖 {vals}，另一分支没有对应动作（可能中途停住）"))
    return out


# ==================== L3：语义预演（符号执行） ====================
def check_level3(plan: Plan, specs: dict[str, ActionSpec],
                 initial: set[str]) -> tuple[list[Finding], list[dict]]:
    """在符号状态上跑一遍。

    ★ 设计决策：未知前置不跳过，而是收集为"待验证假设"（assumptions）。
      跳过会让预演虚假通过；直接报错会让所有真实计划都不可用。
    ★ 设计决策：条件动作两个分支都走，才能发现"某个分支到不了目标"。
    """
    out: list[Finding] = []
    assumptions: list[dict] = []

    # 分支预演：用 (事实集, 已执行步骤) 表示一条执行路径
    paths: list[tuple[set[str], list[int]]] = [(set(initial), [])]
    for a in plan.actions:
        spec = specs.get(a.spec)
        if spec is None:
            continue
        nxt: list[tuple[set[str], list[int]]] = []
        for facts, done in paths:
            # 条件动作：只有条件满足的路径才走这一步（否定分支直接透传）
            if a.condition is not None:
                fact, val = a.condition
                if val is False and fact in facts:
                    nxt.append((facts, done))
                    continue
                if val is True and fact not in facts:
                    nxt.append((facts, done))
                    continue
            # 前置分三类：已成立 / 声明为假定（收集成假设）/ 确实缺失（error）
            missing = spec.pre - facts
            assumed = spec.declared_pre - facts          # 声明为假定、尚未被证实
            real_missing = missing - spec.declared_pre
            if real_missing:
                out.append(Finding("L3", "error", f"step{a.step}",
                                   f"前置 {sorted(real_missing)} 在预演状态中不成立（链断裂）"))
            for u in sorted(assumed):
                assumptions.append({
                    "step": a.step, "assumption": u,
                    "risk": "high" if spec.side_effect == "irreversible" else "normal",
                    "note": f"{spec.name} 声明该事实为假定成立"})
            new_facts = (facts - spec.delete) | spec.add
            nxt.append((new_facts, done + [a.step]))
        paths = nxt

    # 每个分支都要能达成目标
    for facts, done in paths:
        if not plan.goal <= facts:
            lack = sorted(plan.goal - facts)
            out.append(Finding("L3", "error", "plan",
                               f"存在一条执行路径（已执行 {done}）无法达成目标，缺 {lack}"))
    return out, assumptions


# ==================== L4：效果可度量 ====================
def check_level4(plan: Plan, specs: dict[str, ActionSpec],
                 cost_model: dict[str, float] | None = None) -> list[Finding]:
    """成本 / 不可逆副作用次数 / 预算。"""
    out: list[Finding] = []
    cm = cost_model or {}
    total = sum(cm.get(a.spec, specs[a.spec].cost) for a in plan.actions if a.spec in specs)
    if total > plan.budget:
        out.append(Finding("L4", "error", "plan",
                           f"成本估计 {total:.1f} 超预算 {plan.budget:.1f}"))
    irrev = [a.step for a in plan.actions
             if a.spec in specs and specs[a.spec].side_effect == "irreversible"]
    if len(irrev) > 1:
        out.append(Finding("L4", "warn", "plan",
                           f"有 {len(irrev)} 个不可逆步骤 {irrev}：能否合并或推迟到最后？"))
    return out


# ==================== 待验证假设排序 ====================
def rank_assumptions(assumptions: list[dict],
                     fail_prob: dict[tuple[int, str], float],
                     rework_cost: dict[tuple[int, str], float]) -> list[dict]:
    """按 P(不成立) × 返工代价 降序 —— 循环应优先验证最危险的假设。"""
    def key(r: dict) -> float:
        k = (r["step"], r["assumption"])
        return -(fail_prob.get(k, 0.5) * rework_cost.get(k, 1.0))
    return sorted(assumptions, key=key)


# ==================== 自评 vs 结构检查 ====================
def model_selfcheck(plan: Plan, specs: dict[str, ActionSpec]) -> dict:
    """模拟"让模型自己看一遍"。

    ★ 设计决策：自评只检查它能"看懂"的东西（字段齐不齐、读起来顺不顺），
      对结构性缺陷（漏步、成环、分支不穷尽）系统性失明 —— 因为它没有
      独立的事实来源，只能复用生成计划时的那个理解。
    """
    has_fields = all(a.spec in specs for a in plan.actions)
    return {"verdict": "ok" if has_fields else "unclear",
            "note": "我只看到步骤顺序合理、字段基本齐全，未发现明显问题"}


# ==================== 演示 ====================
def make_specs() -> dict[str, ActionSpec]:

                                 declared_pre={"user_authorized"}),

                                      cost=1, side_effect="irreversible"),

def full_report(plan: Plan, specs: dict[str, ActionSpec],
                initial: set[str]) -> list[Finding]:
    f1 = check_level1(plan, specs)
    f2 = check_level2(plan, specs, initial)
    f3, _ = check_level3(plan, specs, initial)
    f4 = check_level4(plan, specs)
    return f1 + f2 + f3 + f4

八处关键设计决策：

  1. ActionSpec 强制同时声明 pre / add / delete。缺任何一个都会让某一类缺陷变得不可检测：只有 pre 无法串联，只有 add 发现不了"先删后查"，没有 delete 则状态只增不减、会把已失效的事实当成仍然成立。
  2. check_level1 严格到"缺参数即 error"，且不用默认值补齐。这一条对治最常见的误诊：模型生成的 JSON 缺字段，如果 L1 悄悄补齐，L3 会拿到"结构完整但语义错误"的计划，于是把一个生成问题诊断成规划问题。
  3. check_level2 的目标可达性检查（"目标事实没有任何动作能产生"）就是漏步的形式化检测。它把"这份计划好像少了一步"变成一条带定位的 error —— 这是自然语言计划永远做不到的事。
  4. check_level2 的第 ⑤ 项（条件分支穷尽）刻意只覆盖枚举型条件。这是它的能力边界：自然语言里的"如果情况复杂"根本无法枚举，所以只能检测"显式声明的布尔条件是否两侧都有分支"。把边界写进代码，比假装它能检查一切更诚实。
  5. check_level3 对未知前置采用"收集为假设"而不是"跳过"或"报错"。跳过 ⇒ 预演虚假通过；报错 ⇒ 所有真实计划都不可用（现实中几乎每个计划都有无法静态判定的前提）。收集成假设并排序，才让 L3 在实际系统里可用。
  6. check_level3 的条件动作两个分支都展开（paths 列表），且最后逐路径检查目标达成。这是它比 L2 强的核心：compare 只在 clauses 存在时执行，如果另一条路径无法达成 diff 目标，只有分支展开才能发现。
  7. rank_assumptions 用 P(不成立)×返工代价 排序。演示里 user_authorized 在 step6 出现（早）且返工代价 20，在 step7 出现但代价只有 2 —— 正确处置是在第一次用到它之前就验证，而不是等最后一步失败。
  8. model_selfcheck 刻意实现成"只看字段与顺序"的弱检查器，用来量化 2.x 的论断：对 计划2（漏了 audit_logged）与 计划3（成环、先删后读、分支不穷尽、越预算），模型自评都返回 ok，而结构检查分别抓到 1 个和 4 个 error。自评不是独立证据，它的信息增量为零，因为它的知识来源与生成者相同。

练习#

  1. 可验证性阶梯：下面五个缺陷分别能被哪一级（L1 / L2 / L3 / L4）抓到？如果抓不到，说明它在哪一级"应该"被抓、或者为什么原理上抓不到： （a）计划里 send_email 的 to 参数缺失； （b）计划目标是"生成审计日志"，但没有任何动作声明 add={"audit_logged"}； （c）计划先执行 delete_contract，之后又执行 extract_clauses（依赖同一份合同）； （d）计划的第 3 步参数是 amount=999999； （e）计划做 3 次不可逆操作而预算只允许 1 次。

  2. 漏步检测的边界：L2 的目标可达性检查依赖"动作声明了 add"。如果模型生成了一个动作，但它实际会产出目标事实而没有声明，你的检查会怎样？（会误报漏步。）请给出两种缓解方案（提示：一是把动作效果的声明与工具契约绑定，二是把 L2 的结果降级为 warn 并要求人工确认），并说明各自的代价。

  3. 分支穷尽：给"计划 3"补上 clauses 为空时的分支（例如"直接发送'无差异'通知"），并写出你新增动作的 pre / add。然后回答：check_level2 的第 ⑤ 项在什么情况下会漏报一个真实的不完整分支？（提示：条件不是布尔而是三值或连续值时。）

  4. 自评的增量实验：设计一个实验来量化"自评有没有增量"。要求写清：对照组（自评无外部信息）、实验组（自评时喂入工具契约与状态快照）、要测的指标（抓到的真实缺陷数、误报数、成本）、以及如何构造"有已知缺陷的计划集"。预测两组结果并说明你的预测依据。

  5. 形式化的取舍：某团队为一个"自动处理退款申请"的 Agent 造了一套 DSL，动作空间 12 个。上线后发现模型生成合法计划的成功率只有 58%，于是加了 3 次重试。请分析：这 3 次重试的期望成本是多少（用 1−(1−p)k 算）？如果改用结构化 JSON，生成成功率能到 92% 但漏步率会上升，你怎么量化对比这两套方案？（提示：把"漏步的代价"与"重试的成本"放在同一个单位下比较。）

  6. 执行时校验的设计：为 compare 动作写一个"后置校验"函数：声明是产出 diff，你要怎么在执行后判断它真的产出了可用的 diff？写出具体的校验项（≥4 项，例如字段齐、非空、条目数在合理范围、引用了存在的条款 ID），并说明每项失败时的错误分类（第 3 章）与给模型的反馈。

  7. 设计题：为一个"根据客户邮件自动生成报价单并发送"的 Agent 设计计划表示与四级校验清单。要求：给出动作集（≥6 个，含至少 2 个不可逆动作）、每个动作的 pre / add / delete、两条必须写进 L2 的自定义结构检查（针对报价这一域）、以及 L3 预演时需要哪些"未知前置"。最后回答：如果客户在邮件里没有说数量，这个缺陷是哪一级该抓、怎么抓？

小结#

  • 自然语言计划不可验证，缺的不是表达力而是可判定性。可验证的定义是：∃ 一个与生成者独立的判定过程，有限步内给结论。"让同一个模型再看一遍"不满足独立性。
  • 计划要能被检查，至少要显式携带：动作语义（含参数约束）、前置条件、后置条件/效果（含删除）、资源成本、依赖关系。前置/后置这一对是核心 —— 它把计划从文字序列变成状态转移链 Pre(ai​)⊆Si−1​。
  • 可验证性有四级的阶梯：L1 语法可解析（缺字段即失败，不要用默认值补齐）、L2 结构可检查（无环 / 悬空依赖 / 目标可达＝漏步检测 / 输入可得 / 写冲突 / 分支穷尽）、L3 语义可预演（符号执行，分支全部展开 + 未知前置收集为假设）、L4 效果可度量（成本 / 不可逆次数 / 预算）。
  • 漏步的检测方式是"目标事实必须有动作能产生它"；错序的检测方式是环检测 —— 但无环只保证顺序可行，不保证方向正确，方向错误要靠 L3 的前置链与目标匹配来抓。
  • 静态检查有原理性的边界：真实世界前提不成立、工具返回与后置不符、参数语义正确但取值荒谬、目标本身写错 —— 这四类只能在执行时或事后发现。正确做法是把无法判定的前置延期为"待验证假设"并按 P(不成立)×返工代价 排序，让循环优先验证最危险的那一条。
  • 自评不是验证：它与生成者共享知识来源，错误相关、迎合倾向、成本翻倍而无信息增量。它只有在接触到计划之外的信息（工具契约、真实状态、验收规格、异源模型）时才有增量：独立性⟺ 检查者接触到了生成者忽略的信息或用了不同先验。
  • 形式化程度的取舍由两边决定：收益=能提前抓到的缺陷数×缺陷代价，成本=造语言的成本+模型生成失败的返工率。窄域高风险值得造 DSL；宽域低风险用结构化 JSON，硬造 DSL 会让生成成功率塌方。

下一节：现在计划是可验证的了 —— 我们知道哪些缺陷能在执行前抓住。但真实世界会证伪前提、会超时、会拒绝。第 3 节要处理执行中的失败：回退到哪一层（动作 / 子目标 / 整体），以及回退粒度如何被"副作用能否补偿"锁定。
