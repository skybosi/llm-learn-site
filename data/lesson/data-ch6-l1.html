上线就绪与配方冻结：把「可以上线」写成可核对的一份 manifest#

这一节要解决什么#

第 5 章已经把版本、血缘与回滚做成了基础设施：快照有内容寻址的身份，账本能回答"这份数据有没有用过"，回滚点的单位是"数据版本 + 配比 + 阶段表"三元组。但第 5 章回答的是事后问题 —— 发现脏数据之后十分钟该做什么。它没有回答一个更前置的问题：在没出事之前，凭什么说这条管线可以上线？

前五章各自产出了一些东西：一条确定性的清洗管线（第 2 章）、一组配比与阶段表（第 3 章）、一份标注指南与合成元数据（第 4 章）、一套版本与血缘（第 5 章）。这些东西单看都对，但它们之间有一个一直没有回答的问题：

把这条管线跑到今天，产出的这批数据，是怎么来的？

这句话在工程上不是一句感慨，它对应四个必须能回答的动作：

  1. 复现：换一个人、换一台机器，能不能产出字节相同的结果；
  2. 归因：指标掉了 2 个点，是数据变了、契约变了、还是代码变了；
  3. 回退：发现这批数据有问题，能不能回到上一个已知好的点；
  4. 交接：半年后接手的人，能不能不追问原作者就读懂这批数据是怎么被造出来的。

前五章把"能回答"所需的零件都造齐了，但没有一样东西把它们装订在一起。这一节做这件事：把配方冻结成一份 manifest，用一个内容指纹 manifest_id 标识它，并把"要不要做这件事"本身也算成一道成本题。

它要给出四个具体答案：

  1. 可上线的定义：上线不是"跑通了"，而是"配方被冻结、每个字段都能被独立核对"。本节给出必须冻结的八类字段，以及"缺哪一类会让哪个动作失效"的对照表。
  2. 指纹怎么算才算数：用规范化编码（键排序、浮点取整、整数取值折叠）+ sha256。本节实测 7 项候选变异全部被抓（hex 差异位 58~63/64），以及"同一次运行再算一遍是否相同：True"。同时给出分辨率边界：eps=0.85 与 eps=0.8500001 判成同一版（10−7 不分辨），eps=0.850001 则不同 —— 这个边界是设计选择，不是 bug。
  3. 冻结强度是内点解：C(m)=cm+r[(L−v)e−λm+v] 的最优值是 m∗=λ1​lncλr(L−v)​=2.2842 项，净省 1.0446 人周（相对降幅 34.8%）。两端都可以算得很清楚：m=1 时事故期望还有 1.4406 人周，m=8 时检查成本已经 3.2000 人周。并且存在一个可行门槛 λ∗=c/[r(L−v)]=0.1524：低于它，第 1 项检查的边际收益就盖不住成本，整件事不值得做。
  4. 判决的敏感度必须写下来：治理与不治理的中性点 A^∗=E[治理]/(pup​Crebuild​30)=0.1050。本节给出四个收益档位下的结论，以及"离中性点还有多远"的裕度（B 档 2.0850 人周，相对 47.5%）。

一、什么叫「可以上线」：四份契约与八类字段#

1.1 概念：上线是一个陈述，不是一个状态#

团队里说"上线了"通常指三件事之一：接口能调通（服务上线）、包能装进端上（产物上线）、线上指标没掉（效果上线）。数据管线的"上线"必须额外包含一件事：这条管线产出的每一批数据都能被追溯到一份冻结的配方。

理由很直接：服务坏了，日志会报错；数据坏了，日志通常什么都不说。第 1 章把这类错误叫静默错误，并指出它最贵。冻结配方是静默错误的唯一"对账工具"——它把"我以为我在跑什么"变成一个可以核对的字符串。

于是"可以上线"这句话可以被拆成四条可检验的陈述：

# 陈述 检验方式 不成立的后果
1 配方被冻结，且有唯一 id 同一份配方算两次 id 相同 复现不可能，归因无从谈起
2 每个阶段都能被独立核对 逐阶段数量、指纹、分布三项对齐 出错只能整条重跑
3 产物带指纹，且指纹能分辨有意义的变化 变异全部被抓、噪声级差不换版本 回退点的边界说不清
4 决策（配比、阈值、阶段表）与数据版本绑定 manifest 里记了数据版本与评测集版本 换个过滤器，上一版最优配比直接失效

1.2 为什么是「一份 manifest」而不是「一份配置」#

配置是给程序读的，manifest 是给人和程序一起读的。差别在三个地方：

  • 配置的可选字段会被省略，manifest 的关键字段不允许缺省。例如 eval.set：配置里不写就是"用默认评测集"，而 manifest 里不写就意味着"这批数据没有对应的评测契约"，第 3 章的全部结论都无法附挂。
  • 配置不记录"为什么"，manifest 要记。配比 w 的每一位都来自第 1 节的目标函数与合规箱，manifest 里至少要能指回那次决策的 id。
  • 配置不参与指纹，manifest 本身要被哈希。这一点最关键：只有 manifest 自己有一个 id，才能把"数据版本"与"配方版本"分开记账（第 5 章的两层版本模型）。

1.3 必须冻结的八类字段#

下表是本节代码里那份 manifest 的结构，也是可以当作清单复用的一版：

# 字段 内容 漏掉它会让哪个动作失效
1 dataset 数据集名与版本 一切
2 source 快照 id、抓取日期、域清单 复现（不知道从哪个快照来的）
3 pipeline 各阶段版本串（去重 / 过滤 / 规范化） 归因（不知道哪一步变了）
4 dedup 方法、Jaccard 阈值、band/row 参数 归因（近似去重的参数决定重复率）
5 filter 质量过滤器清单、各自的阈值、保留率 复现（保留率是唯一可核对的产出量）
6 norm Unicode 形、大小写、空白折叠 复现（NFKC 是有损的，第 2 章）
7 label / synth 指南哈希 + α；教师版本 + prompt 族 + 种子 + 校验器版本 + 接受集错误率 归因（标签与合成的错都"看起来正常"）
8 mix / eval 配比向量 + 重复轮数上限；评测集版本 + 去污染阈值 + 残余泄漏率 判决（没有评测契约，全部结论悬空）

注意第 7 类里 label.guide_sha256 与第 8 类里 eval.set 是两类特别容易被漏掉的字段：它们不改变管线的字节，但改变数字的含义。一份指南改了 3 个判例、评测集换了一个版本，模型的分数会变，而数据的字节可能一模一样。

1.4 取舍与边界#

  • manifest 越全，维护成本越高。 极端情况是"每改一行都要动 manifest"，这会让人开始绕过流程。正确做法是把字段分成两类：影响字节的（阈值、形、种子、配比）必须进 manifest；只影响解读的（负责人、变更理由、实验 id）放进提交信息或决策记录，不参与哈希。
  • manifest 不能替代数据版本。 它记录的是"配方"，不是"产物"。产物要另算内容指纹（第 2 章），两者一起才能回答"这批数据是怎么来的"。
  • 冻结不等于不可改。 冻结的含义是"改动要走一次显式的版本递增"，而不是"锁死"。每次改动都应当产生一个新的 manifest_id，并保留旧 id 的结果。

二、指纹：规范化编码与它的分辨率#

二、一 概念：指纹要把「同一份配方」映射到同一个字符串#

朴素的做法是把 manifest 用 json.dumps 一转再哈希。这条路有三个坑，本节逐个实测：

  1. 键序：字典的迭代顺序在不同实现/版本里可能不同；
  2. 浮点字面量：1e-5、1.0e-05、0.00001 是同一个值，但字符串不同；
  3. 整数与浮点混写：2 与 2.0 在数值上相等，但在多数序列化里产出不同字节。

本节的规范化映射写死四条规则：

canon(x)=⎩⎨⎧​xrepr(round(x,6))⌊x⌋原样逐项规范化键排序后逐项规范化​x∈{bool}x∈R, round(x,6)=⌊x⌋x∈R, x 为整数值x∈Z∪strx 为 listx 为 dict​

其中第三条（整数取值折叠）是本节最关键的设计：它让 2（int）与 2.0（float）落进同一个规范形式 2。代码块 4 会实测这件事。

二、二 为什么指纹要参与「编码」，而不是直接哈希原始文本#

因为原始文本不是配方，它是配方的书写方式。同一个配方可以有无数种写法：键的顺序、浮点的精度、缩进、注释。如果指纹对书写方式敏感，那它标识的是"文件"，不是"配方"。

反过来，指纹也不能太粗：如果它把 0.80 与 0.85 也判成同一版，那它就失去了归因能力。所以规范化必须在"吸收书写差异"与"保留语义差异"之间选一条线。本节的线是 10−6（六位小数）。

二、三 怎么做：代码块 0 与代码块 1#

代码块 0 做三件事：构造 manifest、算 canonical、算 sha256 与 md5。打印结果里最有用的两行是：

  顶层字段数 = 10
  fingerprint(sha256) = cc37403af2c29fb6e3a2db2880751fe8c52bed2c61e418809a9264939b9f0523

代码块 1 把 7 项候选变异逐一注入 manifest，看指纹是否变化，并统计 hex 差异位：7 项全部变化，差异位在 58~63/64 之间。这不是"运气好"：sha256 的雪崩性意味着任意一位输入变化会让约一半输出位翻转，实测值与理论值（32 位）同量级。

二、四 边界一：指纹不分辨噪声级差异#

实测两行：

  eps=0.85 与 eps=0.8500001 是否同指纹（规范化到 6 位小数）：是 <- 1e-7 量级不分辨
  eps=0.85 与 eps=0.850001 是否同指纹：否

这不是 bug，而是必须写进判据的边界。它的工程含义是：如果两个实验只差 10−7 量级的阈值，它们的 manifest_id 相同，于是后续的归因会把它们当成同一版。要避免这种情况，只有一个办法：让所有会影响结果的参数都落在指纹的分辨率之上，或者把分辨率提高（提高位数）并承担"书写噪声导致版本爆炸"的代价。

本节选择保留 6 位，并在文档里把这条边界写下来。这比"提高精度到 15 位"更实用：后者会让 0.1+0.2 与 0.3 这种浮点噪声也换版本。

二、五 边界二：版本 id 与数据侧类型是两件事#

代码块 4 实测了一个容易被误读的地方：

  再看 int 与 float 混写：值 2 / 2.0 / 2.000001 相等？True / False
  规范化指纹（float 取整到 6 位 + 整数取值折叠 + sort_keys）：
    2（int）         canonical={"epochs_cap":2}         id=cfb112c8b7130f0c
    2.0（float）     canonical={"epochs_cap":2}         id=cfb112c8b7130f0c

版本 id 认为 2 与 2.0 是同一个版本（这是对的：配方里写 epochs_cap=2 与写 2.0 是同一个意思）。但第 2 节的数据契约不这么认为：quality.type=float 时，数据侧给一个 int 0 会被类型判据拒收。两者不矛盾，因为它们管的是不同的事：

  • 版本 id 管"配方是不是同一份"；
  • 类型契约管"数据流到下游时会不会因为类型不同而算错"。

把这两件事混成一件，通常的表现是"为了绕过类型判据去改契约"，而正确的修法是让产出侧显式写 0.0。

二、六 边界三：规范化必须幂等#

指纹算法有一个容易被忽略的要求：canon(parse(canon(m)))=canon(m)。如果它不幂等，那么"manifest 存盘再读回"就会换 id，而这类 bug 会在最不经意的时候出现（例如把一个 manifest 从 JSON 转成 YAML 再转回来）。

代码块 4 实测两行：

  规范化是否幂等（canonical 的输出再喂回 canonical）：True
  canonical -> 解析 -> 再 canonical 是否逐字节相同：True

二、七 怎么做：代码块 4 的完整实测#

代码块 4 还给出了一个更实用的对照：同一个值 2 用三种方式构造（int、float、2.000001），朴素指纹给出 3 个不同 id，规范化指纹给出 2 个：

  朴素指纹：8a3645a756ae362a / 28552de77bcc7a4b / ddbf12349b32c13d
  是否全同：False <- 同一份配方因字面量写法不同而分裂成 3 个版本

"朴素指纹把同一份配方分裂成 3 个版本"的代价是：版本表会被无意义的条目填满，真正有意义的变更被淹没。这是"指纹设计"在工程上最实际的收益。

三、冻结强度：它本身是一道成本题#

3.1 概念：冻结强度 m 是什么#

把"上线前检查了多少项"记成 m：来源快照核对、阈值与保留率对齐、形与规范化核对、指南哈希核对、合成元数据核对、配比与阶段表核对、评测集与去污染核对……每加一项都要花钱（人周），每加一项都会降低"带着未知缺陷上线"的概率。

本节用一个边际收益递减的模型：

C(m)=检查成本cm​​+事故期望 + 迁移期望r[(L−v)e−λm+v]​​

其中：

  • c：每项检查的成本（人周/项），本节取 0.40；
  • r：不检查时的事故发生频率（次/月），本节取 0.25；
  • L：一次事故的总损失（人周），本节取 12.0；
  • v：每次版本迁移的固定代价（人周），本节取 1.5；
  • λ：每项检查对事故概率的边际衰减率，本节取 0.60。

3.2 为什么阈值 v 会出现在里面，而且是一个固定项#

因为"做检查"这件事本身会产生迁移成本：一旦你冻结了配方，下游就得跟着这个版本走，每次版本递增都要付一次迁移代价。这项与 m 无关（做了检查就要付），所以它在 C(m) 里表现为固定项 rv。

把 v 单独列出来的好处是它让"检查的净收益"变得可读：

每项检查的边际收益=rλ(L−v)e−λm,第 1 项的边际收益=rλ(L−v)

实测：rλ(L−v)=0.25×0.6×10.5=1.57500 人周，而一项检查只要 0.40 人周，所以第一项检查一定值得做。这行数字就是"要不要开始做这件事"的判据。

3.3 怎么做：闭式最优与数值最优互校#

对 C(m) 求导置零：

C′(m)=c−rλ(L−v)e−λm=0 ⟹ m∗=λ1​lncλr(L−v)​​

C′(m)=c−rλ(L−v)e−λm=0 ⟹ m∗=λ1​lncλr(L−v)​​

实测 m∗=2.2842 项；数值最小（[0,8] 扫 800 段）给出 2.2800 项，C=1.9554 人周。把扫描区间扩到 [0,12] 结果不变（仍是 2.2800），说明最优值落在区间内部——这一句是防止"结论只是区间端点"的必要检查。

代码块 2 的成本表（节选）：

  不检查（m=0）期望代价 = 3.0000 人周；按 m*=2.2842 做 = 1.9554 人周
  净省 = 1.0446 人周（相对降幅 34.8%）

3.4 取舍与边界一：什么时候不该做#

模型的可行门槛是 rλ(L−v)>c，等价于：

λ>λ∗=r(L−v)c​=0.1524

λ>λ∗=r(L−v)c​=0.1524

如果每项检查对事故概率的衰减能力低于 0.1524/项，那么第 1 项检查就亏本。这在实践中对应两种情形：

  • 检查根本检不出东西：λ 小。例如"检查一个从不变化的快照 id"；
  • 事故很少或很轻：r 或 L−v 小。例如内部实验数据、发现错了重跑一次的代价本来就不高。

所以"上线前要过 20 项检查"不是一个可以照抄的清单：当 λ 只有 0.05 时，m∗=0，任何检查都是净支出。

3.5 取舍与边界二：网格误差的方向性#

代码块 5 扫了从 8 段到 3200 段的分辨率，实测：

  分辨率     8 段：m=2.0000  C=1.965635  相对闭式解的 C 差 = +0.010271
  分辨率   200 段：m=2.2800  C=1.955366  相对闭式解的 C 差 = +0.000002
  分辨率  3200 段：m=2.2850  C=1.955364  相对闭式解的 C 差 = +0.000000

规律是：粗网格系统性高估最小值（8 段时高出 0.010271 人周），随分辨率提高单调收敛。这一条在实践里对应"用三个点试一下"的做法：它给出的最优值总是不比真实最优点更好，所以它会低估这件事的收益。

3.6 取舍与边界三：m 是"项"，不是"人天"#

本节的 m 是抽象项数。真实项目里每项检查的成本差异很大（核对一个快照 id 是分钟级，做一次分布级门禁可能是天级）。要把模型用起来，正确做法是按成本归一化：把 m 记为"标准项"（例如 1 标准项 =0.4 人周），然后把贵检查拆成多个标准项。这样 c 就是常数，模型可用。

四、判决的敏感度：把「不确定性」写成数字#

4.1 概念：中性点#

上线决策里最常见的争论形态是：

A：「不做治理，重跑一次很贵，风险敞口太大。」 B：「做了治理，收益也就那样，还占两周人力。」

把这场争论写成一个可算的比较。设：

  • Cfix​：治理的固定成本，本节取 0.30 人周；
  • pbad​：治理期间"问题仍在扩散"的概率，取 0.01；
  • Cdelay​：每天扩散的代价，取 0.05 人周/天；
  • pup​：不做治理时"问题会导致重跑"的概率，取 0.04；
  • Crebuild​：一次重跑的成本，取 2.5 人周，按 30 天计；
  • A^：治理能把重跑成本压掉的比例。

于是：

E[治理]=Cfix​+pbad​Cdelay​⋅30,E[不治理]=pup​(1−A^)Crebuild​⋅30

实测 E[治理]=0.3000+0.0150=0.3150 人周，E[不治理] 在 A^=0 时是 3.0000 人周。中性点是让两者相等的 A^：

A^∗=pup​Crebuild​⋅30E[治理]​=0.1050

A^∗=pup​Crebuild​⋅30E[治理]​=0.1050

4.3 怎么做：用成本参数反推边界#

除了 A^∗，还有一个等价而更常用的边界：治理成本能涨到多少。令 E[治理]=E[不治理] 解 Cfix​：

Cfix∗​=1−pbad​1−pup​​⋅Cdelay​Crebuild​​⋅Cfix​

本节参数下实测 Cfix∗​=14.5455 人周。这个数字大到看起来没用（因为 Crebuild​/Cdelay​=50），但它恰好说明了一件事：这个决策对治理成本极不敏感，对收益估计极不敏感，真正决定它的是事故的频率与量级。这是"把不确定性写下来"的价值：它告诉你两件事里哪一件值得花时间去测。

4.4 取舍与边界#

  • 中性点是一个条件陈述，不是一个事实。 A^∗=0.1050 只在给定的五个成本参数下成立。把这些参数写进报告的脚注，比在正文里给一个"建议治理"的结论更诚实。
  • 成本参数本身有量纲问题。 人周、天、月混用时容易算错一个量级。本节的写法是把一切都折成"人周"，并显式写出乘 30 的位置（月 → 天）。
  • 不要用 p 值来替换这套比较。 "p<0.05 所以显著所以要做"在这里不成立：这里的比较是两个期望损失，不是两个分布。

def norm(x, d=6):
    """规范化映射：bool -> bool；int -> int；float -> 先按 d 位小数取整，
    整数取值的 float 折叠成 int；str -> str；list -> 逐项；dict -> 键排序后逐项。"""
    if isinstance(x, bool):
        return x
    if isinstance(x, float):
        v = round(x, d)
        return int(v) if v == int(v) else repr(v)
    if isinstance(x, int):
        return x
    if isinstance(x, (list, tuple)):
        return [norm(v, d) for v in x]
    if isinstance(x, dict):
        return {str(k): norm(x[k], d) for k in sorted(x)}
    return x

def canonical(m, d=6):
    return json.dumps(norm(m, d), ensure_ascii=False, sort_keys=True,
                      separators=(",", ":"))

def cid(m, mode="sha256"):
    if mode == "md5":
        h = hashlib.md5(canonical(m).encode("utf-8"))
    else:
        h = hashlib.sha256(canonical(m).encode("utf-8"))
    return h.hexdigest()

def cost(m):

            + R_INC * V_MIG)

def best_by_scan(lo, hi, steps):
    bm = min((lo + (hi - lo) * i / steps for i in range(steps + 1)), key=cost)
    return bm, cost(bm)

练习#

  1. 设计你所在项目的一份 manifest。 按 §1.3 的八类字段列出实际字段，并逐条回答："如果这个字段漏了，哪个动作（复现/归因/回退/交接）会失效？" 找出你列出的字段里不参与指纹的那些，说明为什么它们不该参与。
  2. 算一次指纹分辨率。 你的管线上有哪些参数是浮点阈值？它们的最小有意义差异是多少？如果小于 10−6，你会怎么处理（提高位数 / 把参数改成整数刻度 / 显式声明为噪声）？
  3. 复现 §4 的判决。 用你项目的数字填 Cfix​,pbad​,Cdelay​,pup​,Crebuild​，算出 A^∗。然后回答：你能把 A^ 的估计做到 ±0.3A^∗ 以内吗？如果不能，你的决策实际建在什么上？
  4. 给 §3 的模型换一组参数，使得 m∗=0（即任何检查都不值得）。写出这组参数，并解释它在现实里对应什么团队状态。
  5. 验证幂等性。 用你项目的 manifest，把它序列化成 JSON 存盘、读回、再序列化，比较两次字节。如果不同，找出是哪一条规范化规则缺失。
  6. 做一个"变异测试"：对 manifest 做 10 处有意义的改动（阈值、版本、配比、评测集……），跑一遍指纹，检查是否 10 处全部换版本。若有没换的，说明是分辨率边界还是字段没进指纹。
  7. 边界条件推演：如果 λ 从 0.60 降到 0.20，m∗、净省、以及"第 1 项检查是否值得"分别怎么变？请先手算再跑代码核对。

小结#

  • "可以上线"是一个陈述：配方被冻结、每个阶段能被独立核对、产物带指纹、决策与数据版本绑定。四条陈述里任何一条不成立，回退就变成赌博。
  • manifest 与配置的差别在三点：关键字段不允许缺省、要记录"为什么"、本身要被哈希。冻结的八类字段里，label.guide_sha256 与 eval.set 最容易漏，而它们不改变数据字节、只改变数字含义。
  • 指纹 = 规范化编码 + sha256。 规范化吸收书写差异（键序、浮点字面量、int/float 混写），保留语义差异。本节实测 7 项变异全部可检（差异位 58~63/64），幂等性与 JSON 往返都成立。
  • 指纹有分辨率边界：10−7 量级不换版本、10−6 换。这是设计选择，必须写进判据；它防止的是"浮点噪声导致版本爆炸"。
  • 冻结强度是内点解：m∗=λ1​lncλr(L−v)​=2.2842 项，净省 1.0446 人周。可行门槛 λ∗=0.1524：低于它，"多检查一项"本身就是亏的。
  • 判决要写不确定度：中性点 A^∗=0.1050 把"值不值得"变成"压掉 10.5% 重跑成本就划算"；裕度 47.5% 告诉你这个结论有多稳。
  • 网格与近似都会偏：粗网格系统性高估最小值（8 段时高 0.010271 人周）。凡是数值解，都要用闭式或更细的网格复核一次。
