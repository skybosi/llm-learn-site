从通用编译到 ML 编译：为什么深度学习需要自己的编译器#

一个 512×512 矩阵乘，用 C 三重循环交给 clang -O3，与交给深度学习编译器，性能可以差出数倍；而逐元素算子链的瓶颈往往不在算，而在搬。本课把前六章的通用编译视角平移到计算图：哪些能复用，哪些必须重建，为什么"融合"是第一优化。

一、概念讲解#

1. 编译对象换了：从"变量 + 循环"到"张量 + 图"#

通用编译器编译语句与循环；ML 编译器编译框架 trace 出来的计算图——第 1 章的前端四步在这里变成"捕获（capture）→ 图 IR"。三个根本差异：

  • 张量是一等公民：类型是 (dtype, shape, layout)，换个 layout 就是完全不同的性能。
  • 算子粒度大：优化单位从"指令"变成"算子与算子组"。
  • 程序动态生成：shape 与控制流到运行期才确定。
维度 通用编译器 ML 编译器
IR 单位 指令 / 基本块 / 函数 张量算子 / 数据流图
类型系统 标量类型 + 指针 dtype + shape + layout
首要优化 减少指令数 省访存与 kernel 启动
关键搜索 pass 顺序（固定管道） tile/unroll 等调度
正确性风险 别名、UB、浮点重排 数值等价、layout 语义、guard

2. 三个新代价#

① 算子边界。每个算子至少一次 kernel 启动，中间张量还要落显存。设一条 k 个逐元素算子的链、张量 N 个 fp32 元素：不融合时每算子"读 N + 写 N"，共 2k·N·4 字节；融合成一个 kernel 后只"读 1 + 写 1" = 2·N·4 字节——访存比恰好是 k，本课代码会打印这张表。

② 内存墙。逐元素算子算术强度极低，属于 memory-bound，"省一次访存"远比"省一条指令"值钱。这与第 6 章的延迟隐藏同类，只是尺度换成了 HBM 带宽。

③ 动态形状。shape 是运行期才知道的值，编译器只能先假设再验证，失败就重编译（guard + 编译缓存）。通用编译器"类型在编译期已知"的前提，在 ML 里变成工程要保证的运行时契约。此外 layout 变换与传播（NCHW↔NHWC、matmul 分块）也是图级 pass 的日常。

3. 头号优化是融合，不是常量折叠#

融合是通用编译器里循环融合（loop fusion）的图级形态（龙书第 9 章归入机器无关优化），收益有三处：省中间张量的写回与重读、省 kernel 启动、让中间值留在寄存器里复用。但融合需要边界：

  • 一个结果被多个消费者使用就必须落盘，链在此断开（本课代码里 t2 有两条消费者，6 个算子只能压成 3 组）。
  • 归约链与逐元素点链的融合规则不同，跨 reduce 往往要落盘。
  • 融合不是越多越好：寄存器压力升高会压低 occupancy，必须用 profiler 回归。

4. 调度与自动调优：通用编译器不做的事#

同一个 matmul 数学描述唯一，但"怎么算"选择很多：分块多大、向量化多宽、是否展开、如何并行。TVM 的核心贡献是算法与调度分离：算子描述与 schedule 分开写，调度空间交给搜索与代价模型。通用编译器不做这种搜索——pass 管道固定、面向"平均程序"；ML 编译器面对的却是少数占满运行时的热点算子，值得花编译时间去搜。代价是搜索预算与可复现性。

5. 哪些能复用，哪些必须重建#

复用（前六章成果）：SSA 与数据流分析、常量折叠/DCE/CSE、内联、循环变换与向量化、寄存器分配、指令调度、机器码生成。重建：图 IR 与张量语义、图级 pass 基础设施、算子分解与融合、调度空间与代价模型、内存规划、动态形状 guard。MLIR 把降级组织成可扩展的多层 dialect，通用编译器退居为最底层后端之一——所以再学 ML 编译器很顺：语言变了，IR + 优化正确性 + 后端没变。

6. 常见坑#

  • 把图优化当"无害"：浮点加法不满足结合律，NaN/Inf 会破坏重排的等价性；第 5 章的正确性纪律照旧适用。
  • 认为"融合一定更快"：寄存器压力、occupancy、归约维度的并行度都可能让它变慢。
  • 把动态 shape 当静态：guard 频繁失败会造成重编译风暴。
  • 只算运行期收益不算编译成本：搜索时间要进总账。

二、可运行代码示例#

下面这段纯 Python 把上面的代价模型量化：一个 6 算子的小图，用"不融合"和"融合"两条路径执行，逐元素核对一致，再统计 kernel 次数与访存量，并外推到 N=10⁶/10⁸。

# ---- 算子边界为什么贵：同一个算子链，不融合 vs 融合（纯 Python，无第三方依赖）----
import struct

N = 8        # 实际执行用的元素个数（小规模，逐元素核对数值）
K = 5        # 链上算子个数，用于按模型推算访存量

def f32(v):
    """把 Python float 截成 fp32，模拟真实张量的精度"""
    return struct.unpack('f', struct.pack('f', v))[0]

OPS = {   # 逐元素算子：arity=1 -> 一元，2 -> 二元
    'mul':  (2, lambda a, b: f32(a * b)),
    'add':  (2, lambda a, b: f32(a + b)),
    'sub':  (2, lambda a, b: f32(a - b)),
    'relu': (1, lambda a: f32(a if a > 0 else 0.0)),
    'sigmoid': (1, lambda a: f32(1.0 / (1.0 + pow(2.718281828459045, -a)))),
}

# 计算图（拓扑序）：relu(x*a+b) 有两条消费者，链在那里被迫断成两个 kernel
graph = [
    ('t1', 'mul',  ['x', 'a']),
    ('t2', 'add',  ['t1', 'b']),
    ('t3', 'relu', ['t2']),
    ('t4', 'mul',  ['t3', 'c']),
    ('y',  'add',  ['t4', 'd']),
    ('y2', 'mul',  ['t2', 'e']),          # t2 的第二个消费者 → 融合边界
]

inputs = {'x': [f32(v / 2 - 2) for v in range(N)],   # 数组输入
          'a': 1.5, 'b': -0.5, 'c': 2.0, 'd': 0.25, 'e': 0.5} # 标量输入（广播）

def elem(name, i, env):
    v = env[name]
    return v[i] if isinstance(v, list) else v

def run_unfused(graph, env, n):
    """朴素执行：每个算子一个 kernel，输入输出都要落一遍显存"""
    env, launches, bytes_moved = dict(env), 0, 0
    for out, op, ins in graph:
        arity, fn = OPS[op]
        assert len(ins) == arity, f'{op} 需要 {arity} 个输入，收到 {len(ins)} 个'
        vals = [fn(*[elem(k, i, env) for k in ins]) for i in range(n)]
        env[out] = vals
        launches += 1
        bytes_moved += (len(ins) * n + n) * 4      # 读 n 个输入元素 + 写 n 个输出元素（fp32）
    return env, launches, bytes_moved

def fusion_groups(graph):
    """融合 pass：把「只被一个后继消费」的逐元素算子串成一组，一组 = 一个 kernel"""
    consumers = {}
    for out, op, ins in graph:
        for k in ins:
            consumers.setdefault(k, []).append(out)
    groups, cur = [], []
    for out, op, ins in graph:
        if cur and consumers.get(cur[-1][0], []) != [out]:
            groups.append(cur); cur = []          # 上一个结果有别的消费者 → 必须落盘，链断
        cur.append((out, op, ins))
    if cur:
        groups.append(cur)
    return groups

def run_fused(groups, env, n):
    """融合执行：一组内所有中间值留在寄存器（这里的局部变量），只有输入输出走显存"""
    env, launches, bytes_moved = dict(env), 0, 0
    for g in groups:
        ext = sorted({k for _, _, ins in g for k in ins if k not in {o for o, _, _ in g}})
        for i in range(n):
            reg = {k: elem(k, i, env) for k in ext}      # 外部输入读一次
            for out, op, ins in g:
                arity, fn = OPS[op]
                assert len(ins) == arity, f'{op} 需要 {arity} 个输入'
                reg[out] = fn(*[reg[k] for k in ins])    # 中间结果只在寄存器里
            env.setdefault(g[-1][0], [0.0] * n)[i] = reg[g[-1][0]]
        launches += 1
        bytes_moved += (len(ext) * n + n) * 4
    return env, launches, bytes_moved

env_u, launches_u, bytes_u = run_unfused(graph, inputs, N)
groups = fusion_groups(graph)
env_f, launches_f, bytes_f = run_fused(groups, inputs, N)

print('计算图（拓扑序）：')
for out, op, ins in graph:
    print(f'  {out} = {op}({", ".join(ins)})')
print('\n融合 pass 输出（每组 = 一个 kernel）：')
for gi, g in enumerate(groups, 1):
    print(f'  组 {gi}: ' + ' → '.join(f'{o}={op}' for o, op, _ in g))

print(f'\n--- N={N} 逐元素核对 ---')
print('x  =', [round(v, 3) for v in inputs["x"]])
print('不融合 y =', [round(v, 6) for v in env_u['y']])
print('融合   y =', [round(v, 6) for v in env_f['y']])
diff = max(max(abs(a - b) for a, b in zip(env_u[o], env_f[o])) for o in ('y', 'y2'))
print(f'逐元素最大差 = {diff}   （两条路径执行同一串算子，结果必须逐位相同）')
print(f'本图实际开销：不融合 {launches_u} 次 kernel / 访存 {bytes_u} 字节；'
      f'融合 {launches_f} 次 / 访存 {bytes_f} 字节')

print('\n--- 算子边界代价（模型推算：fp32、逐元素链、标量为标量输入不占访存）---')
print(f'{"链长 k":>6} {"不融合访存":>12} {"融合访存":>10} {"访存比":>7} {"kernel 次数":>11}')
for k in (2, 5, 10, 20):
    unfused = 2 * k * 4      # 每算子：读 1 个向量 + 写 1 个向量
    fused = 2 * 4            # 融合后：读 1 个 + 写 1 个
    print(f'{k:>6} {unfused:>9} B/元素 {fused:>7} B/元素 {unfused/fused:>6.1f}x {k:>9} → 1')

print(f'\n{"N（元素）":>14} {"不融合":>12} {"融合":>10} {"省下":>10}')
for n in (10 ** 3, 10 ** 6, 10 ** 8):
    u, f = 2 * K * n * 4, 8 * n
    print(f'{n:>14,} {u/2**20:>9.2f} MiB {f/2**20:>7.2f} MiB {(u-f)/2**20:>7.2f} MiB')

  t2 = add(t1, b)
  t3 = relu(t2)
  t4 = mul(t3, c)

融合 pass 输出（每组 = 一个 kernel）：

  组 3: y2=mul

     2        16 B/元素       8 B/元素    2.0x         2 → 1
     5        40 B/元素       8 B/元素    5.0x         5 → 1
    10        80 B/元素       8 B/元素   10.0x        10 → 1
    20       160 B/元素       8 B/元素   20.0x        20 → 1

         N（元素）          不融合         融合         省下
         1,000      0.04 MiB    0.01 MiB    0.03 MiB
     1,000,000     38.15 MiB    7.63 MiB   30.52 MiB
   100,000,000   3814.70 MiB  762.94 MiB 3051.76 MiB

三个结论：① 两条路径逐元素最大差是 0.0——融合只改搬运方式，数值必须一致，这是融合 pass 的验收条件；② 因为 t2 有两个消费者，6 个算子只压成 3 组，访存从 544 字节降到 352 字节；③ 纯链模型下访存比等于链长 k，N=10⁶、k=5 时融合省下约 30.5 MiB 访存（模型推算，非实测带宽）。这和第 4 章是同一件事的两个尺度：fusion_groups 找"只被一个后继消费"的链，等价于在 CFG 上找可合并的基本块。

三、练习#

  1. 实现：把 fusion_groups 改成"允许跨分支融合"：当 t2 的两个消费者能放进同一组时就不必断链（提示：分组依据从"单个后继"改成"后继集合是否完整落在同组"）。验证分组数与访存量都下降。
  2. 解释：为什么"访存比 = k"只在 memory-bound 的逐元素链上成立？对 matmul 这类算子，融合的主要收益变成什么？
  3. 对比/验证：把 K 改成 20，算 N=10⁶ 时融合省下的访存量，并换算成"少读多少倍输入张量"；解释该比值为什么与 N 无关。
  4. 思考：自动调优把编译时间当成本。"模型每天推理 10⁹ 次、长期上线"与"每次请求都重新编译"两种场景，你会怎么分配搜索预算？
