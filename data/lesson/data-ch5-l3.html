可复现的三个等级：结果、实验与环境的重建#

这一节要解决什么#

前两节把数据变成了可验证的身份（第 1 节）并画出了依赖关系（第 2 节）。但两节都建立在一个没有检查过的假设上：同样的代码、同样的数据，跑两遍会得到同样的结果。

这句话在真实系统里几乎从不自动成立。本节把它拆成三个依次更强的等级，并给每个等级一个可以执行的验收测试：

等级 名字 承诺 验收测试
R1 结果可复现 同一进程/同一环境下，同输入 → 同输出（逐字节或容差内） 同一环境跑两次，比对输出指纹
R2 实验可重跑 换时间、换机器、换顺序，同输入 → 同结论（不是同字节） 两台机器各跑一次，比对结论与置信区间
R3 环境可重建 从零（新容器/新机器）按文档能装出等价环境并复现 R1 在一个干净环境里按 manifest 重建，跑同一份验收

三个等级的关系不是"好/更好/最好"，而是各自回答一个不同的问题：

  • R1 回答"这个数字是不是这台机器的产物"，
  • R2 回答"这个结论是不是那次运行的巧合"，
  • R3 回答"三个月后新同事能不能把这件事做出来"。

R1 不成立时 R2 和 R3 都没有意义（连同一台机器都重复不出，跨机器比较是噪声）；而 R3 成立不蕴含 R1（环境能装配起来，但管线本身带随机性）。这三层各自有独立的失效模式，所以必须分开验收 —— 把它们合成一个"可复现 ✅"是整个工程里最常见的一种自欺。

本节的组织：

  1. 为什么是三个等级：一个"可复现"布尔量为什么必然说谎；以及三个等级各自服务的决策。
  2. 不确定性的六个来源（按可测性排序），以及每一类的检测方法。重点是浮点归约顺序（本节会给出一个具体的、可以逐位看懂的差异）。
  3. 随机性的正确做法：显式种子传递（不依赖全局状态）。为什么"在脚本开头 seed(42)"是不够的 —— 它只让第一次运行可重复。
  4. 环境指纹与差异分类：同代码不同环境的四种差异，以及"哪一类差异会导致哪一类结论失效"。
  5. 验收门槛与容差：两个必须同时满足的测试（同一性 R1、独立性 R2），容差怎么定（不是"差不多就行"，而是"容差必须小于你要分辨的效应量"）。

一、为什么"可复现"必须分级#

1.1 一个布尔量的三种说谎方式#

"这次实验可复现"这句话在工程上有三种不同的含义，混用会直接导致错误决策：

说这句话的人想的 实际验证的 没说出口的风险
"我重跑了一次，数字一样" R1（同环境） 换台机器就不一样（R2 失败），但没人测
"别人照我的脚本跑出来了" R2 或 R3 他跑出的是另一个数字，但结论"差不多"，于是差异被忽略
"环境写进了 requirements.txt" 文档存在 从未在干净环境验证过；CUDA/驱动/BLAS 版本不在里面

三种说谎方式的共同结构是：用弱等级的通过去支撑强等级的结论。R3 是最容易被假装的（"我写了 README"），R1 是最容易被跳过的（"重跑太慢"），而 R2 是最容易被误解的（"数字不一样但结论一样"这句判断本身需要协议）。

1.2 三个等级各自服务哪个决策#

R1 结果可复现  ──→ "这个数是不是 bug？"    调试、对账、A/B 的差值是否真实
R2 实验可重跑  ──→ "这个结论能不能信？"    报告、论文、上线决策
R3 环境可重建  ──→ "这件事能不能交接？"    新人复现、审计、故障复盘

三条箭头都是单向的：R1 通过不保证 R2，R2 通过不保证 R3。所以工程上的正确目标不是"达到最高等级"，而是为目标决策配到需要的等级：

  • 一个数据清洗脚本：目标 R1（要逐字节确定）。
  • 一个训练实验：目标 R2（GPU 上逐字节可复现不现实，见 2.2 节）。
  • 一个要交给外部团队的数据集：目标 R3（他们要能从 manifest 重建）。

1.3 怎么做：把三个等级写成三张验收卡#

每张卡三行：测什么 / 怎么测 / 不过怎么办。

[R1] 测：同环境、同输入、两次运行的产物内容哈希是否相同
     测法：跑两次，比对 manifest 里每个产物的 hash；差异项逐一定位到随机源
     不过：先查随机源（种子/顺序/时间），再查浮点归约顺序

[R2] 测：两组独立运行（不同机器/不同顺序/不同时间）的结论与 CI 是否一致
     测法：配对比较 + 预先声明的 MDE；不一致的判定按第 3 章第 3 节的协议
     不过：先判断是"数字不同结论同"还是"结论不同"；后者必须停下查因

[R3] 测：在一个干净环境里按 manifest 重建，跑同一份 R1 验收
     测法：容器/新机器 + 锁定版本 + 数据内容哈希核对
     不过：把缺的东西补进 manifest（这是唯一正确的处置）

注意 R2 的"不过"分支里有一句"结论不同必须停下查因"：R2 的失败比 R1 的失败更危险，因为它意味着已经发出去的结论可能是那次运行的偶然产物。

二、不确定性的六个来源#

按可测性从高到低排。前三个可以在纯标准库里演示，后三个需要外部依赖的版本信息。

2.1 浮点归约顺序（可测、必然存在）#

浮点加法不结合：(a+b)+c 与 a+(b+c) 的结果可以不同。这不是 bug，是 IEEE 754 的定义。它出现在每一个求和里：loss 的 batch 归约、指标的累加、特征标准化、梯度同步（第 3 章第 4 节的 AllReduce）。

差异的量级可以用一个式子估计。对 n 个量级相近的数、单位舍入 u=2−53，两种归约顺序的期望相对差约

∣S∣∣S^−S∣​∼u⋅n​

（随机游走式的最坏情形是 u⋅n）。本节代码会给出一个具体例子：n=40000 时，朴素顺序求和与排序后求和的二进制表示不同、相对差 ≈4.5×10−16，正好在 un​ 的量级上。

这条的工程含义：如果你的验收标准是"逐字节一致"，那么任何并行归约都会让它失败。所以 R1 在浮点场景里必须写成容差内一致（见第五节），而"容差多大"必须由你要分辨的效应量倒推。

2.2 线程与块调度（可测、依赖硬件）#

同一个核函数、同一个 batch，两次运行的结果可以不同，因为：

  • 原子加的顺序不确定（atomicAdd 的完成顺序由调度决定）；
  • 归约树形状不确定（block 数与 warp 数由占用率与驱动决定）；
  • cuBLAS/cuDNN 的算法选择依赖设备状态与可用显存（同一份代码在 A100 与 H100 上选不同 kernel）。

检测：连续跑 k 次（k≥5），比较输出的哈希分布。如果 k 次里有 ≥2 个不同哈希，就说明存在非确定性 —— 而这不是"硬件坏了"。

处置的顺序很重要，成本从低到高：

  1. 先确认需求：你需要的真的是逐字节一致吗？大多数实验只需要 R2。
  2. 算子级白名单：只对确实需要的算子（例如最终的指标聚合）做确定性实现（确定性归约、固定分块）。
  3. 全局确定性开关：框架通常提供（如 torch.use_deterministic_algorithms、CUBLAS_WORKSPACE_CONFIG）。代价常常是性能下降 10%∼30%，以及"某些算子没有确定性实现，直接报错"。
  4. 不追求逐字节，改写验收：报告"k 次运行的均值与标准差"，把机器噪声当成测量误差的一部分 —— 这常常是最正确的选择。

2.3 全局随机源（可测、最便宜）#

random、numpy.random、框架的 manual_seed、以及数据加载器的 shuffle。它们的共同问题是全局状态：

  • 谁先调用谁影响后面的所有调用（顺序敏感）；
  • 多进程/多线程各自持有一份状态（分叉后不一致）；
  • 库内部的隐藏调用（某些数据增强、某些初始化）会消耗你的随机数，于是"同样的代码、多了一行无关的调用"会改变全部后续随机数。

处置：把随机性从全局状态改成显式参数传递。本节代码用一个小类把随机源做成对象，每个阶段拿自己的实例，并记录它的种子：

class RngStream:
    def __init__(self, seed, name): ...
    def rand(self): ...
    def shuffle(self, xs): ...

这样做的收益不只是可复现：随机源变成了 manifest 的一列（第 1 节的三段结构里它属于 params），于是"这次运行用了哪些种子"不再是考古。

2.4 顺序：字典、集合、文件系统（可测、最隐蔽）#

三个来源：

  • 哈希随机化：Python 的 hash(str) 默认每个进程不同（PYTHONHASHSEED 随机），于是集合/字典的迭代顺序在进程之间可能不同。字符串键的 dict 在 CPython 里保持插入顺序，但 set 的顺序与 dict 的哈希相关路径会受影响。
  • 文件系统遍历顺序：os.listdir 的返回顺序不保证；不同文件系统（APFS/ext4/NFS）差别明显。
  • 并行任务的完成顺序：multiprocessing / 线程池的结果顺序取决于调度。

处置：任何进入输出的顺序都必须显式排序。这不是可选的：第 1 节已经证明"逻辑相同但字节不同 → 哈希不同"，而顺序是字节差异最常见的来源。本节代码会实测：同一批字符串用 set 迭代在两次进程里有不同的顺序。

2.5 外部资源版本（可查、经常被漏）#

tokenizer、词典、预训练权重、评测脚本、标注指南 —— 它们都是输入，但通常不在数据目录里。它们的版本改变可以让结果改变，而数据哈希完全不变。

处置：把外部资源全部纳入第 1 节的三段结构（放进 params 或单独的 resources 段），并且用内容哈希而不是版本号/日期（"v2" 这个名字不承诺任何东西）。

2.6 时间、时区与浮点环境（可查、容易忽略）#

  • 时间：datetime.now()、time.time() 进任何进输出的字段（文件名、日志、ID）都会破坏 R1。
  • 时区：同一份代码在两台机器上（一台 UTC、一台 CST）产生不同的日期字符串。
  • 浮点环境：FMA（融合乘加）的开关、-ffast-math、x87 与 SSE 的差异、FLT_EVAL_METHOD。这些在 CPU 管线里真实存在，而且不在 requirements.txt 里。

三、环境指纹与差异分类#

3.1 概念：环境也是一份内容#

环境指纹 = 一组可哈希的项：

env_fingerprint = {
  python:   "3.14.5",
  platform: "macOS-15.3-arm64",
  packages: {name: version, ...},          # 排序后哈希
  native:   {cuda: "12.4", cudnn: "9.1", blas: "Accelerate", driver: "..."},
  locale:   {tz: "UTC", lang: "C.UTF-8"},
  env_vars: {PYTHONHASHSEED: "0", OMP_NUM_THREADS: "1", ...},   # 只含进哈希的白名单
}

三条纪律：

  1. packages 必须锁到精确版本（==，不是 >=），并且间接依赖也要锁（锁文件的作用就在这里）。
  2. env_vars 只放白名单：把所有环境变量都哈希进去会让指纹随无关变量（TERM、SSH_AUTH_SOCK）抖动，于是"环境变了"变成噪声。
  3. 原生库版本要单独记：CUDA/cuDNN/BLAS/驱动的组合不在 Python 的依赖图里，而它们决定了浮点归约与 kernel 选择。

3.2 四种差异，以及各自让哪一层结论失效#

差异类型 例子 R1 R2 R3 处置
纯粹顺序 字典/集合迭代顺序、文件遍历顺序 失败 通常通过 通过 显式排序
浮点环境 FMA 开关、BLAS 版本、线程数 失败 结论通常稳 通过 记录进指纹；R1 用容差
依赖版本 库的小版本升级、tokenizer 更新 可能失败 可能结论失效 失败 锁版本 + 内容哈希
硬件/驱动 GPU 型号、驱动版本、占用率 失败 可能结论失效 失败 记进指纹；结论里声明硬件

读这张表的方式："纯粹顺序"是最容易修的，"依赖版本"与"硬件"是最贵的（它们可能让结论失效，而不只是让数字变）。

3.3 怎么做：把差异分类做成一次算法#

拿到"两次运行不同"这件事之后，正确的动作不是立刻去查代码，而是先分类：

  1. 两次运行的环境指纹相同吗？
    • 不同 → 差异属于"环境"，对比 3.2 的表定位级别；先看 env_vars 白名单（PYTHONHASHSEED、OMP_NUM_THREADS 是最常见的两个）。
    • 相同 → 差异来自管线内部，继续第 2 步。
  2. 差异是"顺序"还是"数值"？
    • 排序后相同 → 顺序问题：找到那个没有排序的集合/字典。
    • 排序后仍不同 → 数值问题：查浮点归约顺序与随机源。
  3. 数值差异有多大？
    • 在 un​ 量级 → 浮点归约，正常；写进报告。
    • 远大于 un​ → 有真的 bug 或真的随机源。

这个三步分类的价值是把"查不出来"变成"按顺序排除"。本节代码（第 4 段）就是把这三步做成函数。

四、代码#

五段：0 段做出三个故意写成不可复现的管线变体（⚠️ 合成数据）；1 段验证随机源显式化的效果；2 段测浮点归约顺序的差异；3 段测哈希随机化对集合顺序的影响（用子进程 + 不同 PYTHONHASHSEED）；4 段实现三步差异分类器。

# data-ch5-l3: 三个可复现等级 + 不确定性来源的定位
# 纯标准库；数据为合成生成（⚠️ 合成数据，非真实语料）
import hashlib, json, os, random, struct, subprocess, sys

print(f"python {sys.version.split()[0]}")

# ---------- 0. 一个"看起来一样"的管线，两个变体 ----------
N, K = 2000, 500
CHILD_PATH = "/tmp/l3_child.py"        # 子进程脚本：只读它，不改

def make_rows(n=N):
    # 确定性合成数据：值由整数运算产生，不消耗任何随机源
    return [{"id": f"r{i:05d}",
             "v": ((i * 2654435761) % 1000003) / 1000003.0,
             "g": "abcde"[i % 5]} for i in range(n)]

ROWS = make_rows()
print("\n=== 0. 两个管线变体 ===")
print(f"   合成行数 = {len(ROWS)}  每行字段 = {sorted(ROWS[0])}")

def digest(x) -> str:
    return hashlib.sha256(json.dumps(x, sort_keys=True, separators=(",", ":"),
                                    ensure_ascii=False).encode()).hexdigest()

def pipeline_global():
    # 变体 A：全局随机源 + 集合顺序直接进输出
    random.seed()                                   # 不传种子 = 每次运行都不同
    pick = random.sample(ROWS, K)
    total = 0.0
    for r in pick:
        total += r["v"]
    return {"n": len(pick), "total": total,
            "groups": list(set(r["g"] for r in pick))}      # set 顺序进输出

class RngStream:
    # 每个阶段拿自己的随机源；种子进 manifest，不依赖全局状态
    def __init__(self, seed, name):
        self.name, self.seed = name, seed
        self._r = random.Random(seed)
    def sample(self, xs, k):
        return self._r.sample(xs, k)
    def rand(self):
        return self._r.random()
    def as_manifest(self):
        return {"stream": self.name, "seed": self.seed,
                "algo": "python-random-mt19937"}

def pipeline_explicit(seed=20260503):
    # 变体 B：显式种子对象 + 显式排序
    rs = RngStream(seed, "sample")
    pick = rs.sample(ROWS, K)
    total = 0.0
    for r in pick:
        total += r["v"]
    return {"n": len(pick), "total": total,
            "groups": sorted(set(r["g"] for r in pick)),
            "rng": rs.as_manifest()}

a1, a2 = pipeline_global(), pipeline_global()
print(f"   变体 A（全局随机源 + set）：两次摘要相同? {digest(a1) == digest(a2)}")
print(f"     A 指纹1 = {digest(a1)[:16]}   指纹2 = {digest(a2)[:16]}")

b1, b2 = pipeline_explicit(), pipeline_explicit()
print(f"   变体 B（显式种子 + sorted）：两次摘要相同? {digest(b1) == digest(b2)}")
print(f"     B 指纹 = {digest(b1)[:16]}   rng = {b1['rng']}")

# ---------- 1. 种子只解决"第一次"：全局状态的陷阱 ----------
print("\n=== 1. 为什么在脚本开头 seed() 不够 ===")

def global_seeded(extra_consumers=0):
    # 开头 seed(42)，但中间有别的调用会消耗同一个全局流
    random.seed(42)
    for _ in range(extra_consumers):        # 模拟"多了一行无关的调用"
        random.random()
    pick = random.sample(ROWS, 50)
    return round(sum(r["v"] for r in pick), 12)

g0, g1, g2 = global_seeded(0), global_seeded(1), global_seeded(5)
print(f"   seed(42) 后直接采样:      {g0}")
print(f"   中间多消耗 1 次 random(): {g1}   相同? {g0 == g1}")
print(f"   中间多消耗 5 次 random(): {g2}   相同? {g0 == g2}")
print("   -> 全局种子只让「第一次」可重复；任何消耗随机数的新代码都会移位")

# ---------- 2. 浮点归约顺序 ----------
print("\n=== 2. 浮点归约顺序 ===")

def seq_sum(vals):
    s = 0.0
    for v in vals:
        s += v
    return s

def tree_sum(vals):
    # 两两配对（模拟树形归约）
    buf = list(vals)
    while len(buf) > 1:
        nxt = [buf[i] + buf[i + 1] for i in range(0, len(buf) - 1, 2)]
        if len(buf) % 2:
            nxt.append(buf[-1])
        buf = nxt
    return buf[0]

def bits(x):
    return struct.pack(">d", x).hex()

# 例 1：量级悬殊 —— 灾难性吸收
mix = [1e16, 1e16, 1e16, 1e16, 1.0, 2.0, 3.0]
S_seq, S_sorted, S_tree = seq_sum(mix), seq_sum(sorted(mix)), tree_sum(mix)
print("   [例1] vals = 1e16 x4 + [1.0, 2.0, 3.0]")
print(f"     顺序求和 S = {S_seq!r}   bits = ...{bits(S_seq)[-6:]}")
print(f"     排序求和 S = {S_sorted!r}   bits = ...{bits(S_sorted)[-6:]}")
print(f"     树形归约 S = {S_tree!r}   bits = ...{bits(S_tree)[-6:]}")
print(f"     顺序 vs 排序: 相同? {S_seq == S_sorted}   "
      f"相对差 = {abs(S_seq - S_sorted) / abs(S_seq):.3e}（= 1 ulp）")

def as_list(d):
    # 把嵌套结构摊平成可比较的字符串列表（用于"是否是同一批元素"）
    if isinstance(d, dict):
        out = []
        for k in sorted(d):
            out.append(str(k))
            out += as_list(d[k])
        return out
    if isinstance(d, (list, tuple, set)):
        out = []
        for x in d:
            out += as_list(x)
        return out
    return [str(d)]

def classify(run_a, run_b, env_a, env_b):
    # 类别: 相同 / 环境 / 顺序 / 随机或浮点
    if run_a == run_b:
        return "相同", "逐字段一致"
    if env_a != env_b:
        diff = sorted(k for k in set(env_a) | set(env_b)
                      if env_a.get(k) != env_b.get(k))

    if sorted(as_list(run_a)) == sorted(as_list(run_b)):

    return "随机或浮点", "元素也不同 -> 查未播种的随机源与归约顺序"

读输出的七个要点#

  1. 变体 A 与变体 B 的差别只有两处（0 段）：A 用 random.seed()（不传参）+ list(set(...))；B 用显式种子对象 + sorted(set(...))。结果：A 两次摘要不同（指纹每次都在变，输出里那两行已标注），B 稳定在 ad5713ac7464c74e。可复现不是纪律问题，是两个具体的 API 选择。
  2. "开头 seed(42)"只保护第一次运行（1 段）：在采样之前多消耗 1 次 random()，总和从 25.000345998962 变成 25.005826982519；多消耗 5 次变成 24.464098607704。三个数看起来都"很正常"，而没有任何指标会报警。这是全局随机源最贵的地方：它不是随机，它是不可追溯。

五、验收门槛与容差#

5.1 两个必须同时做的测试#

测试 目的 通过条件 失败的常见原因
同一性测试（R1） 排除环境与顺序的偶然 同环境 k 次运行的产物哈希全同（或差异在容差内） 全局随机源、未排序的集合、时间戳进输出
独立性测试（R2） 排除"只有这一台/这一次能出这个结论" 两组独立运行的结论与区间一致 数据划分不稳定、种子太少、评测集太小

两个测试的关系是互补的：同一性测试不能发现"数据集划分本身是随机的"（每次跑都稳定地用同一个随机划分 —— 但如果那个划分是坏的，两次都坏），独立性测试不能发现"顺序不稳定"（换机器时顺序可能恰好相同）。

必须两个都做，而且都写进流程：一个只在本地跑过的管线，无论它多"确定"，都不能支撑对外结论。

5.2 容差怎么定：从效应量倒推#

容差不能靠"差不多就行"。正确的定义方式是：

tol≤41​MDE

其中 MDE 是你要分辨的最小效应量（第 3 章第 3 节的协议）。理由是误差合成：运行噪声与真实效应都会进入观测差值，若噪声的标准差接近 MDE，你需要把样本量放大 4 倍才能把它压下去（方差按平方）。取 1/4 是一个实用约定：

  • 容差太大 → 你会把"没复现出来"判成"复现出来了"，也检测不到小效应。
  • 容差太小 → 每一次微小的浮点差异都报警，最后所有人都学会忽略告警（这比没有告警更糟）。

本节代码给的量级可以当参照：单次归约的相对差在 10−16∼10−14；训练一个模型的两次运行差异通常在 10−3∼10−2（来自数据顺序、初始化、非确定性算子）。所以用 10−15 的容差去验收一次训练是没有意义的 —— 它必然失败，于是这个测试会被跳过。

六、取舍与边界#

选择 换来什么 付出什么 什么时候选另一边
追求 R1（逐字节） 调试容易；对账可靠 关掉并行确定性会损失 10%∼30% 性能；部分算子直接没有确定性实现 训练大模型时：改求 R2，把机器噪声当测量误差
只求 R2（结论一致） 便宜；与业务目标一致 无法逐字节对账；需要预先声明的 MDE 与容差 数据清洗/发布物：必须回到 R1
显式随机源（对象传递） 可追溯；随机源成为 manifest 一列 每个阶段都要改一行；库内部的隐藏随机无法覆盖 纯确定性管线：不需要
PYTHONHASHSEED=0 全局固定 一行解决集合顺序 掩盖了真正的修法（显式排序）；其他语言/工具无此开关 只在排查阶段临时用，不要写进生产配置
锁全部依赖（含间接） R3 可重建 锁文件冲突、升级成本、安全补丁滞后 库的纯研究环境：可以放松，但要在报告里声明
记录环境变量白名单 差异可定位 白名单漏项就是一个盲区 项数 >20 时：改成"只记录已知影响项 + 定期审计"

四条硬边界：

  1. R1 与性能常常直接冲突，而大多数团队需要的是 R2。 "我要完全可复现"这句话必须先翻译成"我要哪个等级的哪个承诺"。盲目追求逐字节会让实验慢 20%，而这个代价换来的往往是一个没人看的对账能力。
  2. 容差不是"可复现"的对立物，它是 R1 在浮点世界里的唯一可行形式。 要求浮点计算的逐字节一致，等于要求固定的归约顺序、固定的线程数、固定的算子实现 —— 这会锁死硬件。正确做法是"容差 ≤ MDE/4，并且容差本身写进 manifest"。
  3. 环境可重建（R3）是最容易被假装的一级。 一份 requirements.txt 不是可重建；在干净环境里真的重建过一次才是。所以 R3 的验收必须是"新容器里跑同一份 R1 验收"，而不是"文档写好了"。
  4. 可复现不等于正确。 一个可复现的管线可以稳定地产生错误结论（第 1 章第 1 节的噪声标签、第 4 章的一致地错）。可复现的价值是让"错"变成可调查的对象：你能区分"这次结果不同是因为我改了 X"和"这次结果不同是因为机器不同"。没有 R1/R2，任何比较都是噪声；有了 R1/R2，比较才有意义 —— 但它仍然不足以判定对错。

练习#

  1. 给你的管线做 R1 体检： （a）选一个你熟悉的脚本，同一环境连跑 3 次，比对全部产物的内容哈希； （b）对每一个不同的产物，用本节 3.3 节的三步分类器判定它属于哪一类（顺序 / 浮点 / 环境 / 随机）； （c）给出每一类的修法，并估算修完之后的性能代价。

  2. 浮点归约的实测与量级核对： （a）取一个真实的求和（loss 累加、特征标准化、指标计算），用顺序 / 排序 / 树形三种顺序各算一次，报告逐位差异； （b）把 n 从 102 扫到 107，画出（或列出）相对差与 un​ 的关系； （c）回答：在你的场景里，"逐字节一致"需要付什么代价？（提示：线程数、分块大小、算子实现。）

  3. 随机源的显式化改造： （a）找出你的代码里所有隐式随机源（random.*、numpy.random.*、框架 seed、数据加载器 shuffle、库内部增强）； （b）改造成显式对象传递，并把每个流的 (名字, 算法, 种子) 写进 manifest； （c）证明改造前后"多一行无关调用会不会改变结果"：构造那个"多消耗一次随机数"的场景，报告数值位移。

  4. 集合顺序的对抗测试： （a）在你的代码里找出所有"集合/字典迭代进入输出"的位置（for k in some_set、json.dumps 一个 set、",".join(set)）； （b）用不同 PYTHONHASHSEED 跑两次，报告哪些输出真的变了； （c）给出统一修法（显式排序 / 排序后序列化），并说明它对语义的影响（提示：有序的东西不能排序，第 1 节）。

  5. 三张验收卡落地：为你的项目写 R1/R2/R3 三张卡，每张包含"测什么 / 怎么测 / 不过怎么办"： （a）R1 卡上写明运行次数 k、比对的产物清单、容差与容差的来源（MDE 是多少？）； （b）R2 卡上写明"换什么"（机器 / 顺序 / 时间 / 划分）与"结论一致"的定义（主指标的区间？护栏？）； （c）R3 卡上写明重建步骤的每一步与验证点，并指出你现在拿不到的环境信息（拿不到意味着 R3 现在不成立）。

  6. 容差的敏感性分析：取你的主指标，人为注入 10−6,10−4,10−2 三档噪声。 （a）每档报告："用容差 10−15 / 10−6 / 10−3 验收"分别会判通过还是失败； （b）找出"误报率 ≈0 且不漏掉 MDE 一半的效应"的容差区间； （c）说明这个区间与你的评测样本量 n 的关系（提示：噪声的标准误 ∝1/n​）。

小结#

  • 可复现必须分三级：R1 结果可复现（同环境同输入 → 同输出/容差内）、R2 实验可重跑（换时间换机器 → 同结论）、R3 环境可重建（从零能装出来并复现 R1）。它们是单向蕴含：R3 ⇒ R1，R1 ⇒ R2。混成一句"可复现 ✅"是工程上最常见的自欺。
  • 本节代码里两个变体的差别只有两处 API 选择：random.seed()（无参）+ list(set(...)) 让指纹每次都变；改成显式种子对象 + sorted(set(...)) 后稳定在 ad5713ac7464c74e。可复现性不是纪律，是两个具体的写法。
  • "开头 seed(42)"只保护第一次运行：采样前多消耗 1 次 random()，总和从 25.000345998962 变成 25.005826982519；多消耗 5 次变成 24.464098607704。全局随机源的问题不是"随机"，是不可追溯（随机源没有变成 manifest 的一列）。
  • 浮点归约顺序必然带来差异，而且可以逐位验：4×1016+[1.0,2.0,3.0] 的顺序求和与排序求和相差正好 1 ulp（bits 尾 ...e08000 vs ...e08001）；1×10−3 累加 40000 次时顺序累加偏 6.306×10−14，与 un​=2.220×10−14（u=2−53）同阶。分块大小 40000/1000/100 给出三个不同的浮点数 —— 并行归约的块划分就是不确定性来源，而它由硬件与驱动决定，只能容差化。这条同时说明"验收必须比字节"与"容差不是可选项"。
  • 哈希随机化是默认开启的：同一个 set、不同 PYTHONHASHSEED，首元素分别是 annotate_batch / raw_web / raw_forum；sorted 后三次全是 annotate_batch。这不需要并行 —— 同一台机器、同一个解释器、不同进程就会发生。
  • 差异分类器把"查不出来"变成"按顺序排除"：先比环境指纹（差异字段一行可见），再比"元素是否相同、只是顺序不同"，最后才落到随机/浮点。顺序要放在环境之后：实测里"变体 A + 不同 PYTHONHASHSEED"同时具备两个特征，先比环境才得到正确的处置（改环境，而不是去排序）。直接读几千行代码是最贵的路径。
  • 两个验收测试缺一不可：同一性测试（R1，实测变体 B 通过? True 不同指纹数 1/3、变体 A 通过? False 不同指纹数 3/3）排除环境与顺序的偶然；独立性测试（R2，实测两次独立抽样的均值 0.48657559627321123 与 0.499328866013402，绝对差 1.275×10−2）排除"只有这一次能出这个结论"。前者发现不了坏的数据划分，后者发现不了顺序不稳。
  • 容差由效应量倒推：tol≤MDE/4，且容差本身要写进 manifest。容差太大会把"没复现"判成"复现了"，太小会让所有人学会忽略告警 —— 后者比没有告警更糟。
  • R3 是最容易被假装的一级：requirements.txt 不是可重建，在干净环境里真的重建过一次才是。所以 R3 的验收是"新容器里跑同一份 R1 验收"，不是"文档写好了"。
  • 可复现不等于正确。 它的价值是让"错"变成可调查的对象：能区分"结果变了因为我改了 X"与"结果变了因为机器不同"。没有 R1/R2，任何比较都是噪声；有了它们，比较才有意义 —— 但判定对错仍然需要另一套机制（第 1 章第 1 节、第 4 章）。

下一节：审计、影响面与回滚（data-ch5-l4）：发现脏数据之后的十分钟 —— 本节给出了"怎么让同一件事能重演"，但真实世界的顺序恰好相反：你先发现一个已经发生过的错误（三月前那批标注是错的），然后要回答"它影响了什么、要不要回滚、回滚到哪、代价多大"。下一节把前三节装成一套可执行的审计流程：账本（谁在什么时候用了哪个版本）、影响面查询（用第 2 节的图）、回滚单位与三种处置（全量重训 / 回滚检查点 / 隔离后局部重跑）的代价模型，以及一份案例演练：一个标注错误率 30% 的批次进了生产三个月，被 4 个模型用过、出现在 2 份对外报告里 —— 你要在十分钟内给出影响面与处置建议，并说明"不需要回滚"这个结论在什么条件下才成立。
