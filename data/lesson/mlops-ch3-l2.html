监控指标的四层设计：输入、输出、延迟、成本与其不确定度#

这一节要解决什么#

上一节给了判据：怎么区分数据漂移与概念漂移。但判据是规则，规则要跑在指标上。于是有三个直接的工程问题没答：

  1. 监控哪些指标？ 一个模型上线后，团队会面临几百个可算的量（每个特征、每种输出异常、每个延迟分位、每种成本口径）。全监控等于全不监控 —— 因为没人看得过来，告警必然被静音。
  2. 这些指标的不确定度有多大？ 一个 0.01 的拒答率、一个 1.9 秒的 p99 —— 它们各自的抽样误差是多少？如果误差比要检测的漂移还大，这个指标就是装饰品。
  3. 监控系统自己的成本是多少？ 采样、存储、计算、人。至少要能回答："把覆盖率从 1% 提到 10%，我能多看见什么、要多花多少。"

先看一个具体的失败例子，它同时踩中上面三点：

某团队上线后监控了 200 个指标，每 10 分钟算一次
两周后回看：真正的劣化（一次上游字段单位变更导致的输出异常）
   发生在周二 14:00
   被发现的时刻是周四 09:00，途径是「用户投诉」
   而在监控里，200 个指标从头到尾没有一个越过阈值
复盘发现：
   ① 劣化只体现在「输出长度分布」的一个窄分位上，没人监控它；
   ② 唯一相关的「格式失败率」基线是 0.0005，每窗只有 0.3 个正例，
      波动比劣化幅度还大 —— 它其实测不出任何东西；
   ③ 那个签名的指标在 20% 采样下运行，阈值还是按全量样本估的。

三条教训对应本节的三个主题：

四层指标表监控什么​​→不确定度 / 样本量测得多准​​→采样与成本账花多少钱看​​

一句话给本节定调：

一个没有样本量的指标不是指标，是一个数；一个没有不确定度的阈值不是阈值，是一个信念。 本节要求每个进入告警的指标都带三样东西：定义（算的是什么）、样本量（基于多少观测）、不确定度（区间或标准误）。

一、四层指标：为什么是这四层#

监控指标的分类方式有很多（业务 / 技术、在线 / 离线、领先 / 滞后）。本节采用四层：输入、输出、延迟、成本。理由不是美学，而是这四层各自回答一个不同的"为什么"，而且它们的采样成本与响应速度差着数量级。

层 回答的问题 典型指标 数据来源 计算成本
输入 "进来的是什么？" 分布漂移、缺失率、长度分位、类型异常 请求日志 低（可采样）
输出 "出去的是什么？质量如何？" 拒答率、格式失败率、输出长度、置信度分布 响应日志 中（要解析输出）
延迟 "多久、稳不稳？" p50/p95/p99、超时率、排队时长 系统埋点 低（全量便宜）
成本 "花多少？" 每千 token 成本、缓存命中率、重试率 计费/缓存日志 中（要汇总外部数据）

1.1 为什么不按"领先 / 滞后"分#

常见的另一种分法是"领先指标（leading）看趋势、滞后指标（lagging）看结果"。这个分法没错，但它不能指导设计：一个指标是领先还是滞后，取决于你监控什么，而不取决于它属于哪一类。举个例子 —— "检索命中率"可以是领先的（先掉，然后输出质量掉），也可以只是因为业务查询变简单而涨（那时候它是噪声）。

四层分法的优点是每一层有明确的"不监控就会瞎"的理由：

  • 不监控输入：你会看到输出变差，但不知道是"数据变了"还是"模型坏了"。这正是上一节要区分的东西。
  • 不监控输出：你会看到用户投诉，而不是劣化本身；而且输入正常、输出也正常、但两者关系坏了（概念漂移）这一类，只有输出层能先说话。
  • 不监控延迟：你会把"用户体验变差"误判成"模型答得不对"（这两件事的处置完全不同）。
  • 不监控成本：一次缓存失效或一次无意的重试放大，可以在输出质量完全不变的情况下把账单翻倍 —— 第 2 章第 4 节已经算过这个账。

1.2 每层一条"主指标"，以及为什么只能有一条#

工程上最容易被忽略的一条纪律是：每一层只留一条主指标，其余都是它的分解。理由是可解释性：

  • 当一层里有 5 条并列的主指标，告警时你不知道该信谁（它们可能在打架：拒答率涨、格式失败率跌，是变好还是变坏？）；
  • 主指标必须是能直接映射到一个动作的量。比如输出层的主指标选"可用回答率"（1− 不可用率），那么它下降的动作是明确的：查输出异常、查上游。

四层主指标的一个可用组合：

层 主指标 定义 变成负面的动作
输入 输入健康率 通过全部输入断言的请求占比 查上游 schema / 单位 / 流量构成
输出 可用回答率 非拒答、非格式错误、非截断的响应占比 查输出侧变化（模型、模板、后处理）
延迟 端到端 p99 从入队到返回的 99 分位 查队列、检索、推理引擎
成本 每千次请求成本 计费 / 请求数 查缓存、重试、token 膨胀

"其余都是分解" 的意思：拒答率、格式失败率、超长截断率是"不可用率"的分子分解；p50/p95 是延迟 p99 的分解；缓存命中率、平均 token 数是单位成本的分解。告警只挂在主指标上，分解项只用于定位。这就把"几百个指标一起告警"压成了"四条主指标 + 一张分解表"。

1.3 为什么每个指标都必须带样本量#

这是本节的核心论点，值得单独说清。

任何比率型指标的点估计都可以写成"k 次命中 / n 次观测"。它的标准误是

SE(p^​)=np(1−p)​​

注意 n 在分母上、在根号里。 这意味着两件事：

  1. 点估计在 n 小时会看起来完全正常（因为它就是 k/n，一个小样本的比例可以是任何值）；
  2. 两个不同 n 的指标不可比 —— 一个 n=100 的 2% 和一个 n=100000 的 2%，后者的可信度是前者的 31 倍。

所以工程规则是：任何进入阈值比较的指标，必须同时记录 n 与 p^​。只有 p^​ 而没有 n 的仪表盘，是在邀请你把噪声当信号。下面两节给的是 n 该取多少的判据。

二、比率型指标：样本量的两条判据#

比率型指标（各种"率"）占监控指标的大多数。它们的样本量需求有两条方向相反的判据，必须同时满足。

2.1 判据 A：相对误差（看的是"能不能分辨变化"）#

要求 p^​ 的相对标准误不超过 ρ：

pSE(p^​)​=pp(1−p)/n​​≈np​1​≤ρ⟹n ≥ pρ21​​

推导中用了 p(1−p)≈p（小概率事件），所以这是一条比精确值略紧的判据 —— 对小 p 足够好。

取 ρ=10%：

p 所需 n 实际 SE 95% 绝对误差
0.2000 500 0.01789 3.51×10−2
0.0500 2000 0.00487 9.55×10−3
0.0100 10000 0.00099 1.95×10−3
0.0020 50000 0.00020 3.92×10−4
0.0001 1000000 0.00001 1.96×10−5

注意最后两列的对比：p=0.0001 时，n 只需要一百万就能拿到 10% 的相对误差，而绝对误差只有 1.96×10−5 —— 好得离谱。这就是"相对判据随 p 变小而放松"的现象，它的含义是：对于罕见事件，"相对变化"很容易测准。这个结论有一个致命的前提，见下一条。

2.2 判据 B：零事件（看的是"能不能说它没发生"）#

监控里最常见的一句结论是"这个指标正常"。这句话的统计形式是"我们观测到 0 次"。上一条判据完全管不了这件事：如果 p=0.0001、n=1000，期望事件数是 0.1 —— 观测到 0 次的概率是 e−0.1≈90%，而这个 0 与真值 0 无法区分。

要让"观测到 0 次"成为一个有信息量的结论，需要事件数的期望足够大。取 Poisson 近似（n 大、p 小），"一次都没看到"的概率是 e−λ（λ=np）。要求它足够小，得到这条经验判据：

e−np≤0.05⟹np≥3⟹n ≥ p3​​

（严格地说，"观测到 0 次"之后能给出的是 p 的置信上界：p≤−ln(α)/n，α=0.05 时就是 3/n。）

对同一批 p，这条判据给出的 n 是：

p 零事件判据 n=3/p 判据 A 的 n（ρ=10%） 谁更紧
0.2000 15 500 A
0.0500 60 2000 A
0.0100 300 10000 A
0.0020 1500 50000 A
0.0001 30000 1000000 A

两条判据的对比给出了一个重要结论：在 ρ=10% 这个口径下，判据 A 总是更紧。但它们的性质不同：

  • 判据 A 是相对要求（我关心的是"这个率涨了 20%"）；放宽 ρ 到 100%，n 就降到 1/p，比判据 B 还松；
  • 判据 B 是绝对要求（"我要有资格说它没发生"），放宽不了 —— 它对应的是一个结论的资格，不是精度。

所以工程上的规则是：告警阈值用判据 A 定样本量，而"绿灯"结论用判据 B 定底线。一个 p=0.0005、每窗 n=30000 的格式失败率（λ=15）可以支撑"正常"这个结论；同一个指标若在 20% 采样下变成 n=6000（λ=3），就刚好卡在底线上；再降到 1% 采样（λ=0.15）时，"没报警"就几乎不携带信息了。

2.3 最小可检出偏离（MDE）#

反过来问：给定 n 与基线 p，多大的变化我才能可靠检出？ 用双侧 α=0.05、power =0.8 的标准公式（z0.975​=1.96、z0.8​=0.8416，合计 2.8）：

Δmin​=2.8⋅np(1−p)​​

同一分钟窗口（n=30000）下，各类比率型指标的可检出漂移：

层 指标 基线 95% 绝对误差 可检出绝对漂移 可检出相对漂移
输入 空值率 0.0040 7.14×10−4 1.02×10−3 25.5%
输入 超长截断率 0.0150 1.38×10−3 1.96×10−3 13.1%
输出 拒答率 0.0120 1.23×10−3 1.76×10−3 14.7%
输出 格式失败率 0.0005 2.53×10−4 3.61×10−4 72.3%
延迟 超时率 0.0010 3.58×10−4 5.11×10−4 51.1%
成本 缓存命中率 0.4500 5.63×10−3 8.04×10−3 1.8%

读数：同样的 n，基线越小、可检出的相对漂移越大。0.0005 的格式失败率要涨 72% 才看得见；而 0.45 的缓存命中率只要动 1.8% 就会被抓住。

这不是监控系统的缺陷，是比率型指标的信息下界。想看见小概率事件的相对变化，只有一条路：加大分母（提高采样率或延长窗口）。这条结论会在第 5 节变成采样率的成本账。

三、延迟指标：为什么 p99 不是一个"数"#

延迟是唯一一类必须用分位数而不能用均值的指标。原因是延迟分布长尾（本节用对数正态 σ=0.45 模拟，实际系统更极端）—— 均值被尾部主导，会随少数慢请求剧烈漂移，而"用户体验"几乎完全由高分位决定。

但分位数有一个反直觉的性质：它的抽样误差远大于均值的抽样误差。

3.1 分位数的抽样波动#

设样本量为 n、总体密度在 q 分位处为 f(q)。样本分位数 q^​n​ 的渐近标准差是

sd(q^​n​)≈f(q)n​q(1−q)​​

分母里的 f(q) 是关键：分布越平的地方，分位数越不稳。延迟分布的右尾很平（样本稀疏），所以 p99 的 f 小，sd 大。

实测（n=20000 的对数正态样本，100 次重抽样）：

分位 点估计 蒙特卡洛标准差 精确区间下界 精确区间上界 区间相对宽
0.50 0.9988 0.00409 0.9910 1.0389 4.8%
0.95 2.1146 0.01431 2.0850 2.2866 9.5%
0.99 2.8820 0.03565 2.8143 3.4739 22.9%

（精确区间不是用渐近公式算的，而是顺序统计量法：取第 r 个与第 s 个顺序统计量作上下界，覆盖率恰好是 Pr(r≤Bin(n,q)≤s−1)。这条路线不需要估计密度 f(q)，所以它在尾部比渐近公式可靠得多。）

3.2 三条工程推论#

  1. p99 的 95% 区间宽度约 23%：如果告警阈值是"p99 > 3.0s"，而当前 p99 是 2.88s、区间上界 3.47s —— 这个指标已经在噪声里越过了阈值。要么加大 n，要么把窗口拉长，要么把阈值定在 3.5s 以上。
  2. 不要对 p99 用"点值与阈值比较"的告警：应当用"区间下界越过阈值"或"连续 k 个窗口的点估计同向移动"（后者是第 3 节的 CUSUM 要处理的）。
  3. 分位数的"分解"要小心：p50/p95/p99 不是可加的量。四层表里"延迟层主指标 = 端到端 p99"，它的分解项应当写成"各阶段的 p99"（检索 p99 + 推理 p99 + 队列 p99），而不是各阶段的均值相加 —— 均值之和既不等于 p99，也不等于 p50。

3.3 顺序统计量的区间：一个必须留在代码里的自检#

顺序统计量区间的正确性完全依赖二项分布尾概率的计算。这里有一个静默失效的陷阱：如果 Pr(Bin(n,q)≤k) 用逐项递推实现，在 n 大时 (kn​)pk(1−p)n−k 的首项 (1−p)n 会下溢成 0，整个累加随之归零。后果是：

  • 不影响点估计（点估计不依赖它）；
  • 让基于它的搜索永不收敛（或者给出 r=1 这种荒唐的区间）；
  • 不抛异常、不报错，只是让置信区间看起来"宽得离谱"。

本节代码用正则化不完全贝塔函数 Pr(Bin(n,p)≤k)=I1−p​(n−k,k+1) 实现，并在 [0] 段用教科书值自检（Pr(Bin(10,0.5)≤2)=0.05469）。这条自检留在生产代码里是值得的：区间算错，所有基于区间的阈值都是错的，而且错得没有声音。

四、采样：覆盖率与漏报的定量关系#

监控系统不可能全量处理所有请求（成本、延迟、存储）。采样是必需的，但它不是免费的降级 —— 它直接改变判别力。

4.1 覆盖率的三种效应#

把采样率记为 ϕ（每窗样本数 n=ϕN），三个后果立刻可算：

效应 公式 方向
点估计的标准误放大 SE∝1/ϕ​ 变差（慢，​ 关系）
小概率指标的期望事件数 λ=ϕNp 变差（快，线性）
采样本身的选择偏差 若采样与指标相关（比如"只采成功的请求"），点估计有偏 可能致命

前两条都是"信息变少"，第三条是"信息变错"。第三条最危险，也最容易被忽略：任何非随机的采样规则都必须先证明它与被监控指标独立。常见的反例："只对通过的请求计延迟"（把最慢的那批直接排除掉了）、"只对缓存的请求算质量"（缓存命中的那批本来就更容易）。

4.2 漏报率的实测#

设定真实劣化率 p=0.012（拒答率），每窗全量样本 N=30000，看不同采样率下"这一窗能不能看见至少一个正例"：

采样率 每窗样本 期望检出数 检出 1 个的概率 单窗检出率
100.00% 30000 360.0 1.0000 100.0%
10.00% 3000 36.0 1.0000 100.0%
1.00% 300 3.6 0.9727 97.3%
0.10% 30 0.4 0.3023 30.4%

读数：从 100% 降到 1%，单窗检出率只从 100% 掉到 97.3%（因为期望事件数还有 3.6）；但降到 0.1%，期望事件数只有 0.4，单窗检出率掉到 30.4%。

关键推论是连续窗口的联合漏报率：若单窗检出率是 0.30、窗口之间近似独立，那么连续 3 窗全部漏掉的比例是 (1−0.30)3=0.343 —— 三分之一的机会，一个持续存在的劣化在三个窗口里完全没露面。而 p=0.012 这种"拒答率涨了 50%"的劣化，在很多团队里是要走事故流程的。

所以这条规则必须写进监控文档：

低覆盖率下的"没报警"，不能当作"指标正常"的证据。 每个告警项都要标注它的"每窗期望事件数"λ=ϕNp；当 λ<3 时，这个指标只能做趋势参考，不能做守门人。

这也解释了为什么小概率指标（格式失败率、超时率）在采样下最先失效：它们的 p 本来就小，λ=ϕNp 掉得最快。

五、怎么做：四层表与它的成本账#

现在把前面的判据组装成一张可交付的表：每个指标一行，带定义、样本量、不确定度、以及它变成负面的动作。

5.1 四层指标表模板#

列 必须写清 常见错误
层 输入/输出/延迟/成本 把"业务"混进来（业务指标是下游消费者，不是监控层）
主/分解 每层只有一条主指标 三条并列主指标，告警时互相打架
定义 分子、分母、时间窗、聚合方式 分母不同（"每请求"vs"每会话"）导致两个数永远对不上
基线 p 上周同口径的值 用上线前的值当基线（上线初期分布不同）
样本量 n 本窗实际观测数 只写"全量"却不写实际数字
判据类型 比率 / 分位 / 计数 给分位数用比率型公式
λ=np 每窗期望事件数 忽略；这是采样不足的直接指示
Δmin​ 最小可检出漂移 阈值定得比 Δmin​ 还小
动作 阈值触发后第一步查什么 写"查看"（等于没写）

5.2 采样成本的账#

设某个指标每窗的处理成本是 c（单位：元/样本），每天有 K 个窗口，则日成本是

Cday​=c⋅ϕ⋅N⋅K

反过来，给定日预算 Cbudget​，可承受的采样率是

ϕmax​=c⋅N⋅KCbudget​​

这两条式子的用途不是省钱，而是让你说清取舍：当你为了看清一个 p=0.0005 的指标而把覆盖率从 1% 提到 10%（期望事件数从 0.15 提到 1.5，仍然不够），你花了 10 倍的钱却依然看不见它。正确的处置是换指标（找一个 p 更大的代理），而不是加大采样 —— 因为所需 n 随 p 反比增长，成本是"用钱买概率"的生意，而这类生意的边际收益在 p 很小时是负的。

5.3 一个必须遵守的对齐规则#

监控指标与发布门禁必须用同名、同定义的指标。 如果门禁里算的是"离线评测集上的可用回答率"，监控里算的是"线上请求的可用回答率"，那么"离线通过、线上变差"这件事就无法归因 —— 你不知道是分布不同，还是两个指标的定义根本不同。

具体做法（三条）：

  1. 指标定义放在共享的代码/配置里，离线与线上引用同一份；
  2. 每次发布时记录"门禁用的指标定义版本的哈希"（沿用 ch2-l4 的 binding 思路）；
  3. 监控侧对同一指标保留至少两个时间口径（1 分钟看告警、1 小时看趋势），并且明确哪个口径对应门禁值。

"""
mlops-ch3-l2：监控指标四层（输入 / 输出 / 延迟 / 成本）的五个可运行实验。

① 基础函数自检：二项标准误 / 正态分位数 / 顺序统计量的分位区间
② 比率型指标的采样率：相对误差 1/sqrt(np) 与「零事件」的经验判据
③ 延迟分位数：p50/p95/p99 的抽样波动 + 顺序统计量的精确置信区间
④ 四层指标的成本与最小可检出漂移（在同一分钟窗口预算下）
⑤ 覆盖率与告警召回：采样少了，漏报率怎么涨

运行：python3 /tmp/mlops_ch3_l2.py
⚠️ 全部为合成数据（random，固定种子），目的是让每个数字可复算。
"""
from __future__ import annotations

import math
import random


# ==================================================================== 基础函数
def norm_cdf(x: float) -> float:
    return 0.5 * (1.0 + math.erf(x / math.sqrt(2.0)))


def norm_ppf(p: float) -> float:
    lo, hi = -40.0, 40.0
    for _ in range(200):
        mid = (lo + hi) / 2.0
        if norm_cdf(mid) < p:
            lo = mid
        else:
            hi = mid
    return (lo + hi) / 2.0


def mean(xs) -> float:
    return sum(xs) / len(xs)


def stdev(xs) -> float:
    m = mean(xs)
    return math.sqrt(sum((x - m) ** 2 for x in xs) / (len(xs) - 1))


def betacf(a: float, b: float, x: float) -> float:
    """正则化不完全贝塔函数的连分式部分（Lentz 法），只用标准库。"""
    FPMIN = 1e-300
    qab, qap, qam = a + b, a + 1.0, a - 1.0
    c, d = 1.0, 1.0 - qab * x / qap
    d = 1.0 / (d if abs(d) > FPMIN else FPMIN)
    h = d
    for m in range(1, 300):
        m2 = 2 * m
        aa = m * (b - m) * x / ((qam + m2) * (a + m2))
        d = 1.0 + aa * d
        d = 1.0 / (d if abs(d) > FPMIN else FPMIN)
        c = 1.0 + aa / c
        c = c if abs(c) > FPMIN else FPMIN
        h *= d * c
        aa = -(a + m) * (qab + m) * x / ((a + m2) * (qap + m2))
        d = 1.0 + aa * d
        d = 1.0 / (d if abs(d) > FPMIN else FPMIN)
        c = 1.0 + aa / c
        c = c if abs(c) > FPMIN else FPMIN
        delta = d * c
        h *= delta
        if abs(delta - 1.0) < 1e-15:
            break
    return h


def betai(a: float, b: float, x: float) -> float:
    """正则化不完全贝塔函数 I_x(a,b)。"""
    if x <= 0.0:
        return 0.0
    if x >= 1.0:
        return 1.0
    bt = math.exp(math.lgamma(a + b) - math.lgamma(a) - math.lgamma(b)
                  + a * math.log(x) + b * math.log(1.0 - x))
    if x < (a + 1.0) / (a + b + 2.0):
        return bt * betacf(a, b, x) / a
    return 1.0 - bt * betacf(b, a, 1.0 - x) / b


def binom_cdf(k: int, n: int, p: float) -> float:
    """P(Bin(n,p) <= k) = I_{1-p}(n-k, k+1)，走不完全贝塔函数。

    不要用“逐项递推”：n=20000、p=0.5 时 (1-p)^n 下溢成 0，整个递推归零 ——
    这类错误不抛异常，只把尾部概率静默变成 0，然后让基于它的搜索永不收敛。
    """
    if k < 0:
        return 0.0
    if k >= n:
        return 1.0
    if p <= 0.0:
        return 1.0
    if p >= 1.0:
        return 0.0
    return betai(n - k, k + 1, 1.0 - p)


def order_stat_interval(n: int, q: float, conf: float = 0.95):
    """分位数的无分布置信区间（顺序统计量法），返回秩区间 (r, s)。

    取第 r、s 个顺序统计量作上下界，真实覆盖率 = P(r <= Bin(n,q) <= s-1)。
    要 95% 覆盖：r 是满足 P(Bin(n,q) <= r-1) <= 0.025 的最小秩，
    s-1 是满足 P(Bin(n,q) <= s-1) <= 0.975 的最大秩。
    """
    mu, sd = n * q, math.sqrt(n * q * (1 - q))
    r = max(1, int(mu - 10 * sd))
    while r < n and binom_cdf(r - 1, n, q) <= 0.025:
        r += 1
    s = max(2, int(mu + 10 * sd))
    while s < n and binom_cdf(s - 1, n, q) <= 0.975:
        s += 1
    return r, s


def sample_quantile(sorted_xs, q: float) -> float:
    if not sorted_xs:
        return float("nan")
    pos = q * (len(sorted_xs) - 1)
    i = int(math.floor(pos))
    j = min(i + 1, len(sorted_xs) - 1)
    f = pos - i
    return sorted_xs[i] * (1 - f) + sorted_xs[j] * f

5.4 四处关键设计决策#

  1. binom_cdf 走不完全贝塔函数而不是逐项递推。这是本节写作中真实踩到的坑：递推版在 n=20000,p=0.5 时 (1−p)n 下溢为 0，整个 CDF 归零；后果不是报错，而是 order_stat_interval 的搜索永不收敛（跑到 r=1，区间宽得毫无意义）。"区间算错"是监控里最危险的一类错误：它不改变点估计，只改变你对点估计的信任度。

  2. 分位数的区间用顺序统计量法，不用渐近公式。渐近公式 sd≈q(1−q)​/(f(q)n​) 需要估计密度 f(q)，而在尾部这个估计本身极不稳定。顺序统计量法的覆盖率是精确的（Pr(r≤Bin(n,q)≤s−1)），不需要任何密度估计 —— 代价是区间是"数据点"，不平滑。

  3. Δmin​ 用 2.8 这个系数而不是 1.96。2.8=z0.975​+z0.8​ 对应"双侧 5% + 80% 功效"，也就是说：Δmin​ 是"我会有 80% 的机会检出它"的漂移量。用 1.96 得到的只是"这个偏离在 5% 水平上刚好看得见"，检出概率只有 50% —— 那就是抛硬币。

  4. 覆盖率的表格里同时给"期望检出数"与"单窗检出率"。这两个数看起来重复，其实不是：期望检出数是成本/信息的度量（λ=ϕNp），单窗检出率是决策的度量（这一窗我能不能下结论）。前者用于设计采样率，后者用于告诉值班同学"这个绿灯有多可信"。

练习#

  1. 算你团队的 n 与 λ：挑三个你们真的在用的比率型指标（比如"请求失败率""重试率""空结果率"）。 （a）写出它们各自的分母（每请求？每会话？每批次？）与上周的基线 p； （b）用判据 A（ρ=10%）算出所需 n，并和你们实际的窗口样本量比较； （c）用 λ=ϕNp 算出每窗期望事件数；对 λ<3 的指标，说明"绿灯"这句话现在值多少； （d）给每个指标写出一个 p 更大的代理指标，并说明它为什么与前者相关。

  3. p99 的置信区间与阈值：某服务的端到端延迟 n=10000，p99 点估计 1.80 s，用顺序统计量法算出 95% 区间 [1.62,2.31] s。 （a）如果 SLO 是"p99 ≤ 2.0s"，当前状态的判定是什么？（提示：注意区间上界） （b）要把区间宽度压到 10% 以内，n 需要多少？（提示：区间宽度大致 ∝1/n​，先用当前宽度反推） （c）给出一个"不看点值、看区间"的告警规则，并说明它在(c)的 n 下会不会太迟钝； （d）如果延迟分布突然多了一小撮超慢请求（比如 0.5% 的请求变成 10s），p50 与 p99 各会怎么动？为什么监控 p50 会完全看不见？

  4. 四层表：为一个你熟悉的 LLM 应用（问答 / 代码补全 / 客服）写完整的四层指标表，每层一行主指标 + 至少两条分解项。要求： （a）每条写清分子、分母、时间窗； （b）给出基线 p 与 Δmin​（可以用估计值，但要写出代入的数）； （c）写出"触发后第一步查什么"（必须是一个具体动作，不能是"查看"）； （d）指出这张表里最不可能被采样影响的一个指标，并解释为什么（提示：λ 与 p 的关系）。

  5. 成本与收益：某监控项全量处理成本是 c=2×10−6 元/样本，每窗 N=30000、每天 K=1440 窗。 （a）算出全量、10%、1% 三种覆盖率下的日成本； （b）假设给这项监控的人均响应成本是 1 元/次告警（每次告警 0.5 人时、人时 2 元），问日成本里"人"和"机器"各占多少； （c）如果 1% 覆盖率下漏报率 3%，而每次漏报的期望损失是 5000 元，问提高覆盖率到 10% 是否划算（用日成本差与漏报减少量算）； （d）说明这个计算里最不可信的那个参数是哪个，以及你会怎么给它一个区间。

  6. 对齐规则：你们的离线门禁用"评测集上的可用回答率"，线上监控用"请求级的可用回答率"。 （a）列出两个定义至少三处可能的差异（分母、异常判定、时间窗）； （b）设计一个"对齐检查"实验（提示：用同一批线上请求同时跑两条计算路径）； （c）如果两条路径的结果差 0.8 个百分点，你会先怀疑哪一处差异？ （d）把"指标定义版本的哈希"接进 ch2-l4 的 manifest，写出它的字段名与它保护的是什么。

  7. 开放题（接第 3 节）：本节的判据都是"单窗口比较"。请写出你会追问的五个问题（提示：多久看一次、连续窗口怎么合并、多个指标一起看的误报、阈值与代价的关系、突发 vs 渐变），并说明哪个问题最可能让"连续 3 窗同向"这条规则失效。第 3 节会把阈值写成代价模型的解，并给出 CUSUM/Page-Hinkley 两种序贯检测器。

小结#

  • 四层指标各回答一个不同的"为什么"：输入（进来的是什么，判据引 ch3-l1）、输出（出去的是什么，概念漂移的唯一早期信号）、延迟（多久多稳）、成本（花多少，ch2-l4 的账在这里被监控）。每层只留一条主指标，其余都是它的分解：主指标告警、分解项定位。
  • 比率型指标的两条样本量判据方向相反：相对误差判据 n≥1/(pρ2)（告警阈值用），零事件判据 n≥3/p（"绿灯"资格用）。p=0.0001 时前者只要一百万，后者要三万 —— 前者管"能不能分辨变化"，后者管"能不能说它没发生"。
  • 最小可检出漂移 Δmin​=2.8p(1−p)/n​。实测 n=30000 时：空值率（p=0.004）可检出 25.5% 的相对漂移，而格式失败率（p=0.0005）要涨 72.3% 才看得见。基线越小、越测不出相对变化 —— 这是信息下界，不是实现缺陷。
  • 延迟必须用分位数，而分位数的抽样误差远大于均值。实测 n=20000：p50 的精确区间宽 4.8%、p95 宽 9.5%、p99 宽 22.9%。p99 = 2.88s、区间上界 3.47s 时，一个 3.0s 的阈值其实已经在噪声里越界了。
  • 分位数的区间要用顺序统计量法：覆盖率是精确的 Pr(r≤Bin(n,q)≤s−1)，不需要估计尾部密度。但它的实现有一个静默陷阱 —— 二项 CDF 用逐项递推会在 n 大时下溢归零，让区间宽得离谱且不报错。本节用不完全贝塔函数 + 教科书值自检（0.05469 vs 0.054688）来防它。
  • 采样的三条效应：标准误放大 1/ϕ​（慢）、期望事件数按 ϕ 线性缩小（快）、非随机采样引入偏差（致命）。实测 p=0.012、N=30000 时，1% 采样的单窗检出率仍有 97.3%，但 0.1% 采样掉到 30.4% —— 连续 3 窗全漏的概率约 0.73≈34%。
  • "绿灯"需要资格：当 λ=ϕNp<3 时，这个指标只能做趋势参考、不能做守门人。低覆盖率下的"没报警"不是"没问题"的证据。
  • 监控指标与发布门禁必须同名同定义。否则"离线通过、线上变差"无法归因 —— 你分不清是分布不同，还是两个指标根本在算不同的东西。把指标定义的哈希接进 binding（ch2-l4），这条对齐才有强制力。

下一节：这一节把指标算出来了，也给了它们的不确定度，但没有回答"阈值定在哪"。给每个指标配一个 3σ 或 5% 的阈值，会在 200 个指标 × 每 10 分钟一次的规模上每天误报几十次（第 4 节的实测：整体日误报率 1.000）。第 3 节要把阈值写成代价模型的最小值：cost(τ)=Cfa​α(τ)Rfa​+Cmiss​α(τ)Rmiss​+Clate​Rfa​max(0,E[D]−SLO)，给出序贯 LLR 的误报-延迟权衡（E[D]≈τ/(δ2/2)）、报警疲劳的定量模型，以及"把 200 个指标的误报压到每天 0.05 次要付多少检出延迟"。
