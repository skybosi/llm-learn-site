prefix caching#

投机解码靠"猜"来少算，这一课靠"复用"来少算。回想 KV Cache 的本质：对给定前缀，注意力计算出的 K、V 是确定性的，跟后面接什么完全无关。于是就有了一个朴素而强大的想法——如果两个请求共享同一段前缀（prefix），这段前缀的 KV Cache 只需要算一次，之后直接复用。这就是 prefix caching（前缀缓存）。在系统提示词、少样本示例、RAG 文档、多轮对话这类"前缀高度重复"的场景里，它能省下可观的预填充计算。

一、概念讲解#

1. 前缀为什么能复用#

因果注意力里，第 i 个 token 只能看到 0..i 的 token，所以第 i 个位置的 K、V 只由 token[0..i] 决定，与 i 之后的内容无关。因此两段序列 P + A 和 P + B（P 是共同前缀），在 P 这一段产生的 KV Cache 完全一致。第一个请求算出 P 的 KV 后把它缓存下来，第二个请求就不用再算，直接跳过 P 的预填充，从 A 开始算。

能省多少取决于前缀重复率。典型受益场景：

  • 固定系统提示词：所有请求都带同一大段 system prompt，它的 KV 只需算一次；
  • 少样本示例（few-shot）：每次请求前面都拼同样的几个示例；
  • RAG / 检索增强：同一批文档被反复塞进不同问题里；
  • 多轮对话：新一轮 = 上一轮全部内容 + 新问题，前缀就是上一轮整段对话；
  • 多采样 / 评测：同一 prompt 采样多个回答，前缀完全相同。

2. 如何判定"前缀相同"：基于块的哈希#

前缀缓存不是逐 token 比较（那样本身就很慢），而是把 KV 按块（block/token 块）组织——这正好和 PagedAttention 的块式 KV 管理天然契合。给每个块的内容算一个哈希值，存进哈希表；新请求到来时，逐块计算哈希并查表，命中则复用，未命中则新建。命中的粒度是"块"，所以也叫 block-level prefix caching。

vLLM 把这一整套做成自动前缀缓存（Automatic Prefix Caching，APC）：用户无需任何标注，引擎在调度时自动识别并复用相同的 token 块前缀。SGLang 则用 RadixAttention——把缓存的 KV 组织成一棵基数树（radix tree / trie），树的每条路径对应一段 token 序列，公共前缀在树上自然共享，命中查找、插入、淘汰都更结构化，尤其擅长处理"海量请求共享不同长度公共前缀"的情况。

3. 缓存的生命周期与淘汰#

缓存的 KV 放在显存里，而显存是稀缺资源，必须淘汰。常见策略是 LRU（最近最少使用）：久未命中的块被优先驱逐，腾出空间给新块。一个关键权衡是：缓存命中收益 vs 显存占用成本。缓存占用的显存越多，可同时服务的"活跃 KV"就越少，可能反而降低并发吞吐。所以引擎通常让前缀缓存与正常 KV 共享同一块池，由调度器统一管理，命中率与吞吐在动态中取得平衡。

4. 什么时候收益最大#

前缀缓存的收益取决于两个因素：前缀重复率和前缀长度占比。前缀越长、重复越频繁，省的预填充就越多。反之，如果每个请求都是完全不同的长文（前缀几乎不重复），缓存不但没用还占显存。因此在设计服务时，把稳定不变的内容放在序列前面（system prompt、示例、文档在前，用户问题在后）能最大化命中；把每次都会变的内容放前面则会打散公共前缀，命中率骤降。

二、可运行代码示例#

示例 1：用哈希表手写一个简化版前缀缓存#

下面用"块 + 哈希"的思路模拟前缀缓存：把输入序列切成块，用哈希判断两块是否相同，命中则复用（不重复"计算"），未命中则标记为需计算。用"计算一次 KV"抽象为计数，直观展示能省多少。

def block_hash(block):
    """模拟 KV 块的哈希：真实实现用内容摘要（如 xxHash）。"""
    return hash(tuple(block))

def simulate_prefix_cache(requests, block_size=2):
    """requests: 一串 token 序列列表。返回每个请求里'需要新计算'的块数。"""
    cache = set()          # 已缓存块哈希
    stats = []
    for tokens in requests:
        computed = 0
        # 按块切分，逐块查哈希表
        for i in range(0, len(tokens), block_size):
            blk = tokens[i:i+block_size]
            h = block_hash(blk)
            if h in cache:
                continue            # 命中：复用，不重复计算
            cache.add(h)            # 未命中：计算并缓存
            computed += 1
        stats.append(computed)
    return stats

# 三个请求：前两个共享前缀 "SYSTEM_PROMPT"，第三个是全新内容
requests = [
    ["SYS", "PROMPT", "what", "is", "AI"],
    ["SYS", "PROMPT", "what", "is", "ML"],
    ["SYS", "PROMPT", "tell", "me", "jokes"],
]
blocksize = 2
stats = simulate_prefix_cache(requests, blocksize)
for i, s in enumerate(requests):
    print(f"请求{i}: {s} -> 需计算块数 {stats[i]}")

total_new = sum(stats)
total_all = sum(len(r) // blocksize for r in requests)
print(f"总共 {total_all} 块中，实际只计算了 {total_new} 块，复用 {total_all - total_new} 块")

三个请求共享 ["SYS", "PROMPT"] 这个前缀块，它只被计算一次，后两个请求直接复用——这就是 prefix caching 省算力的本质。把 block_size 改成 1，你会看到命中的粒度更细（但哈希查表次数更多），体现了"块粒度"的权衡。

示例 2：vLLM 与 SGLang 开启前缀缓存#

vLLM 的 APC 默认对可用场景自动生效（也可显式开关）：

# vLLM：--enable-prefix-caching 显式开启自动前缀缓存
vllm serve meta-llama/Llama-3.1-8B-Instruct --enable-prefix-caching

SGLang 的 RadixAttention 默认开启，且其调度器围绕前缀复用做了深度优化：

# SGLang：默认即启用 RadixAttention 前缀复用
python -m sglang.launch_server --model-path meta-llama/Llama-3.1-8B-Instruct

两者都不需要你改请求代码——只要把"稳定的公共内容放前面"，引擎就会自动命中复用。

三、练习#

  1. 把示例 1 的请求改成"每个请求前缀都不同"，观察复用块数降为 0；再把公共前缀拆开放到序列中间，说明"公共前缀被拆散"为何会破坏命中。
  2. 说明 prefix caching 与 PagedAttention 的"块式 KV 管理"为什么天然契合：为何按块而非按 token 缓存更高效？
  3. 对比 LRU 与"永不淘汰"两种缓存策略在多轮长对话 + 高并发场景下的吞吐差异，说明显存占用与命中率之间的权衡。
  4. 用 vLLM 起一个带 --enable-prefix-caching 的服务，构造一组共享长 system prompt 的请求，对比开/关缓存时的 TTFT 与预填充耗时变化。
