检查点、容错与恢复：大集群训练的必备工程#

反直觉的事实：在千卡规模上，最大的时间黑洞往往不是算法问题，而是恢复流程。一份"能续训"的检查点动辄近 1 TB，写一次要几十秒到几分钟；集群规模翻一倍，期望故障次数也翻一倍。本课把检查点当一等公民记账：写多少、写多快、隔多久、失败丢多少。

一、概念讲解#

1. 一个"能续训"的检查点里到底有什么#

很多人以为检查点 = 模型权重。要让训练从第 k 步无缝接上，至少要这些：

内容 量级 谁负责
模型参数（主权重） ∝ 参数量 框架
优化器状态（Adam 的 m、v） 常是权重数倍 框架
学习率调度器状态 可忽略 框架
训练进度（step / epoch / token 数） 可忽略 框架
RNG 状态 可忽略 框架
数据加载器 / sampler 位置 可忽略 常要自己写

最后一行是事故高发区：模型和优化器都恢复了，数据流却从头开始，表现为 loss 接得上但偶发跳变。PyTorch 的 torch.distributed.checkpoint（DCP）把前五项统一成 state_dict 语义，sampler 位置一般仍要显式保存。

2. 体积账：优化器状态常常是权重的好几倍#

70B 参数的模型：bf16 权重 140 GB；Adam 的 m、v 用 fp32 各 4 B/参数，合计 840 GB。示例 1 的结果是总计 980 GB。这个数字有一串直接后果：

  • 写盘时间由存储带宽决定：示例里 2 GB/s → 490 s、10 GB/s → 98 s、50 GB/s → 19.6 s。这是训练集群需要并行文件系统的原因；
  • 不能每个 rank 存一份完整模型：总写入量会乘以世界大小。正确做法是每个 rank 只写自己的分片（sharded / distributed checkpoint），墙钟时间由存储聚合带宽决定；
  • 恢复也一样：各 rank 并行读回分片而非广播。这也是 DCP 提供 resharding（重分片）的原因——换并行度后仍能从旧检查点恢复。

3. 间隔账：写盘开销 vs 故障丢失量的最优点#

设单步 ts​、写盘 tw​、加载 tl​、间隔 K：

写盘开销占比=Kts​+tw​tw​​,单次故障平均丢失=2Kts​​+tl​

示例 2（ts​=8 s、tw​=100 s、tl​=60 s）把这条曲线打出来：

间隔 K 写盘占比 单次故障丢失
50 20.00% 260 s
100 11.11% 460 s
200 5.88% 860 s
500 2.44% 2060 s
1000 1.23% 4060 s

没有普适最优解，只有权衡：把"写盘开销 <5%"与"单次丢失 <15 min"当约束，示例参数下 K 落在 200 附近。真正该改的是 tw​——异步保存（状态先拷到 CPU、立刻继续训练，后台线程写盘）能把循环里的 100 s 压到接近 0，代价是额外内存与快照一致性。

4. 故障率随规模线性增长：这是大集群的第一性问题#

若单 GPU 每小时故障率为 λ，N 卡集群的期望故障率为 λN。示例 3 取 λ=10−3（示例量级；真实集群可能差几个数量级，务必用自集群监控数据替换）：

集群规模 期望故障（24 h） 每次丢 14 min 时的额外时间
64 卡 1.54 次 ~0.4 h
1024 卡 24.58 次 ~5.9 h
4096 卡 98.30 次 ~23.5 h

重点不是数字精确，而是恢复时间在大规模上直接换算成可用率：单次恢复从 14 min 压到 5 min，4096 卡每天就多出十几个小时有效训练——比调学习率的收益更大也更确定。

5. 容错机制：谁在"重试"这件事上负责#

  • 弹性启动：torchrun 的 --max-restarts 配合 rendezvous 后端，可在成员失败后重建进程组并重启；官方教程称之为 fault-tolerant training。
  • 调度器层：Slurm/K8s 负责重新排队；它只保证"进程再起来"，不保证"状态正确"。
  • 框架层：DeepSpeed / Megatron 各有检查点格式与恢复流程；跨并行度恢复一般要经"重分片"或"转换"。换并行度前先确认检查点能否直接读。

6. 恢复的正确性：比"能起来"更难#

四个必须写进 runbook 的动作：

  1. 写在临时路径，成功后原子改名：否则写盘中途失败时唯一的检查点是坏的；
  2. 保留多版本并轮转：检查点被静默损坏（截断、位翻转）时才有退路；
  3. 不就地重试 collective：通信器状态已不一致，正确动作是整组干净重启并从检查点恢复；
  4. 记录读取耗时与校验：加载慢会让 MTTR 失控，抽查关键张量能在 30 秒内判定可用性。

至于"为什么不该自己写 AllReduce 再套重试"：第 2 章已证明 ring AllReduce 的带宽最优性与 2(p−1) 步结构，NCCL 在其上做了通道、拓扑、协议自适应；自研实现若漏掉一个错误处理条件，代价是静默的数值错误而非崩溃。

二、可运行代码示例#

三段纯 Python（标准库），把检查点体积、写盘时间、间隔权衡、故障率放大都算出来。

# ===== 示例 1：一个"能续训"的 checkpoint 到底有多大 =====
GB = 1e9
P_PARAM = 70e9
def ckpt_gb(params=P_PARAM, weights_bytes=2, opt_bytes_per_param=12, extra=1):
    """weights: bf16 主权重 2 B/参数；Adam 状态 fp32 12 B/参数（m + v 各 4 B + 主副本 4 B）。
    extra: 世界大小相关的小状态（scheduler/step/RNG），量级可忽略。"""
    return (params * (weights_bytes + opt_bytes_per_param)) / GB

total = ckpt_gb()
print("示例 1：70B 模型（Adam，bf16 权重 + fp32 优化器状态）的 checkpoint 体积")
print(f"  权重部分      {P_PARAM*2/GB:7.1f} GB")
print(f"  优化器状态    {P_PARAM*12/GB:7.1f} GB   ← 通常是权重的好几倍")
print(f"  合计          {total:7.1f} GB")
print("\n  写盘时间（示例存储带宽）：")
for bw in (2.0, 10.0, 50.0):
    print(f"    {bw:>5.1f} GB/s → {total/bw:7.1f} s")

# ===== 示例 2：checkpoint 间隔怎么选 —— 训练时间、故障率与丢失量的三角账 =====
def ckpt_overhead_frac(t_step_s, t_ckpt_s, interval_steps):
    """每 interval_steps 步写一次：写盘时间相对总训练时间的占比。"""
    return t_ckpt_s / (interval_steps * t_step_s + t_ckpt_s)

def expected_work_lost_s(interval_steps, t_step_s, t_load_s):
    """平均每次故障丢失的进度 = 半个检查点间隔 + 从最近检查点重新加载的时间。"""
    return interval_steps * t_step_s / 2 + t_load_s

print("\n示例 2：单步 8 s、写盘 100 s、加载 60 s（示例参数）")
print("   间隔(步)   写盘占比   每次故障丢失(s)")
for k in (50, 100, 200, 500, 1000):
    print(f"   {k:>8}   {ckpt_overhead_frac(8, 100, k)*100:7.2f}%   {expected_work_lost_s(k, 8, 60):14.1f}")

# ===== 示例 3：故障率随卡数线性增长 =====
print("\n示例 3：单 GPU 每小时故障率 λ=1e-3（示例量级，请替换为自集群数据），训练 24 h")
lam = 1e-3
lost = expected_work_lost_s(200, 8, 60)
for n in (64, 512, 1024, 4096):
    exp_fail = lam * n * 24
    print(f"  {n:>5} 卡 → 期望故障 {exp_fail:6.2f} 次/天，"
          f"每次丢 {lost/60:.0f} min → 全天额外 {exp_fail*lost/3600:5.1f} h")

示例 1 与示例 2 合起来给出第一条工程规则：先量 tw​（写一次多少秒），再定 K。若 tw​ 是 490 s 而 ts​ 只有 8 s，K=50 就意味着 60% 时间在写盘——出路是缩短 tw​（换存储、异步保存），而不是调间隔。

# 用一个占位模型（几十 MB 而不是 70B）实测 t_w 与 t_l，再按比例换算到大模型
# 1) DCP 分片保存/加载的标准写法（PyTorch 分布式检查点）
python3 - <<'PY'
import torch, torch.distributed.checkpoint as dcp
from torch.distributed.checkpoint.state_dict import get_state_dict, set_state_dict
sd = {"model": model.state_dict(), "optim": opt.state_dict()}
dcp.save(sd, checkpoint_id="ckpt/step-100")        # 各 rank 只写自己的分片
dcp.load(sd, checkpoint_id="ckpt/step-100")
PY
# 2) 换并行度后仍能恢复：dcp 的 resharding 会按新的分片布局重切
# 3) 弹性启动：让它在成员失败后自动重启（--max-restarts 只在弹性模式下有意义）
torchrun --standalone --nproc_per_node=2 --max-restarts=3 train.py

三、练习#

  1. 实现：写一个 pick_interval(t_step, t_write, t_load, max_overhead, max_loss_s)，返回同时满足"写盘占比 ≤ max_overhead"与"单次丢失 ≤ max_loss_s"的最小间隔 K（无解时返回 None 并指出哪条约束卡住）。
  2. 解释：为什么"每个 rank 各存一份完整模型"会让总写入量乘以世界大小，而"每个 rank 只写自己的分片"不会？后者在什么情况下反而更慢（提示：小文件数量、元数据操作）？
  3. 对比/验证：把示例 3 的 λ 改成 10−4 与 10−2，重算 4096 卡那一行的额外时间；再说出你要用集群上哪一份监控数据来标定 λ。
  4. 思考：某次恢复后训练能跑，但 loss 曲线在恢复点出现一次明显跳变，且之后收敛变慢。列出至少三种可能的原因（提示：优化器状态是否完整、数据流位置、RNG），并说明各自如何在恢复后 5 分钟内验证。
